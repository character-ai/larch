# Linting

Larch uses [pre-commit](https://pre-commit.com/) as the source of truth for linter configuration. Linter definitions, versions, and file filters live in `.pre-commit-config.yaml`. CI adds dedicated per-tool jobs on top of pre-commit for the most safety-relevant checks (secret scanning, agent-config linting) so individual failures can be diagnosed and re-run independently.

| [Clippy](https://github.com/rust-lang/rust-clippy) | Changed Rust packages and targets | The default pre-commit hook calls `python3 python/cli.py checks rust-clippy --repo-root .` with changed paths. A shared target-family module selects every target in that family. It runs one default-feature Clippy configuration with warnings denied, incremental compilation off, and dev/test debug information off. | [cargo-deny](https://github.com/EmbarkStudios/cargo-deny) | `Cargo.lock`, Cargo manifests | CI checks advisories, allowed licenses, duplicate versions, wildcard requirements, and dependency sources through `deny.toml`. |

### Python complexity ratchet

`make py-lint` enforces ruff `C901`, `PLR0911`, `PLR0912`, `PLR0913`, and `PLR0915` as hard errors for new `python/` production code. Current production debt is grandfathered in `python/ruff.toml` per-file ignores generated from a live ruff baseline, not from a checked-in static inventory in this document.

Production per-file ignore entries suppress only the listed complexity codes for the matched module until cleanup removes the entry. They are cleanup bookkeeping, not per-function budgets inside grandfathered files. After package splits, production complexity grandfathering must stay per-code tight so a cleaned file or sibling package does not inherit stale suppressions. The primary ratchet for growth inside already-grandfathered modules is `python/cli.py lint complexity-baseline`, which runs an audit-config ruff scan and compares it with `python/complexity-baseline.json`.

The baseline audit fails when it finds either of these regressions:

- A new `(file, code, qualified_symbol)` violation.
- An increased `metric` for an existing `(file, code, qualified_symbol)`.

The audit treats ruff exit `0` and `1` as success when JSON parses, because exit `1` means violations exist. Ruff exit `>= 2`, empty output, or unparseable output is a hard failure. Duplicate baseline identities are rejected during generation and load instead of being merged by last write.

`python/complexity-baseline.json` is a sorted top-level JSON array. Every row has `file`, `code`, `qualified_symbol`, `metric`, `added_at`, and `history`; `source_issue`, `reason`, and `operator_override` are optional. `added_at` is an ISO UTC date or `legacy`; a new row starts history with its creation measurement, while an increase appends another dated measurement. `qualified_symbol` is AST-derived and class-qualified when applicable because PLR rules do not include function names in messages, and bare names are ambiguous within a module. `file` paths are normalized without leading `./` or `python/` prefixes so audit runs from `cwd=python/` do not create duplicate keys. Baseline keys omit line numbers so innocent line shifts above a grandfathered function do not require rebaselining. Renaming or moving a function changes `qualified_symbol` and requires intentional baseline cleanup.

Use `make regen-complexity-baseline REASON='why this growth is necessary'` whenever regeneration adds a row or increases a metric. `REASON` is optional for unchanged or shrinking-only regeneration, and whitespace-only reasons are rejected. Regeneration preserves matching metadata, including a manually authored `operator_override`, but never creates or changes an override; overrides require a nonblank reason and positive linked issue.

The baseline lint fails when a symbol has a second metric-growth event within an inclusive 14-day window. It groups lint codes by `(file, qualified_symbol)`, keeps code-tagged event provenance, and deterministically attributes equal-date events. A valid override on the later offending row silences only that event and remains visible in lint output. The operator choices are to simplify the function, split it, or add a manual override.

`python3 python/cli.py lint complexity-debt --report` (or `make lint-complexity-debt`) is the non-CI debt view. It prints entry count, age buckets, top metrics, symbols with at least two bumps in the last 30 days, and active overrides. It is intentionally outside `lint`, `py-lint`, and CI aggregation.

The combined mechanism primarily blocks new production modules through per-file grandfather bookkeeping, and blocks new complexity anywhere through the baseline manifest. `make regen-complexity-baseline` is the source of truth for live baseline rows. `python/ruff.toml` production per-file ignores keep only complexity codes still present in the regenerated baseline for the matched production path, while unrelated suppressions stay intact.

Tests are exempt through the existing `"test_*.py"` block. Pytest harness modules outside that glob, `conftest.py`, `test_support.py`, and `review_test_support.py`, are exempt through dedicated per-file ignore entries with the same five codes. These test-facing exemptions are permanent and are not part of production split cleanup.

When a production file is simplified, remove matching per-file ignore codes from `python/ruff.toml`, remove the corresponding `(file, code, qualified_symbol)` rows from `python/complexity-baseline.json`, and remove the whole per-file entry when no ignored codes remain.

### Python test assertion convention

Prefer stable machine tokens over full human-facing warning strings. Assert exit codes, argv evidence, structured `KEY=value` lines, finding IDs, status enums, and artifact basenames. Pinning complete prose makes legitimate wording changes fail the suite without improving coverage.

### Runtime type validation

Treat annotations as the contract for values already inside a typed boundary. Do not re-check a field after its annotation and surrounding guards have narrowed it; omit the redundant check.

Validate only untyped or untrusted boundary inputs. When exact built-in type semantics are required, such as rejecting `bool` and subclasses for an `int`, use `type(value) is not int  # pylint: disable=unidiomatic-typecheck  # exact runtime type rejects bool and subclasses`. When `isinstance()` is necessary for a dynamic value that pyright cannot infer, use `isinstance(value, T)  # type: ignore[reportUnnecessaryIsInstance]  # runtime value originates outside the typed boundary`. Each suppression needs a same-line reason, and never add both suppressions to the same check.

`make py-lint-main` also runs custom AST ratchets over Python production modules. All skip symlinks, `test_*.py` at any depth, `conftest.py`, `test_support.py`, and `review_test_support.py`. The subprocess ratchet also skips the runner module at `python/larch/core/proc.py`. The environment ratchet skips the config module at `python/larch/core/config.py`. `python/cli.py lint subprocess-via-runner` flags direct `subprocess.run`, `subprocess.Popen`, `subprocess.check_output`, and `subprocess.call` call sites. Its baseline identity is `(file, qualified_symbol, callee, occurrence)`. Exemption rows in `python/subprocess-via-runner-exemptions.json` have exactly `file` and `reason`; unknown keys fail the linter.

`python/cli.py lint env-via-config-constant` parses `python/larch/core/config.py` for `ENV_*` constants and flags matching bare string literals in `os.environ.get(<literal>)`, defaulted `os.environ.get(<literal>, ...)`, and `os.environ[<literal>]` load or store access. It ignores literals ending in `_SH` and literals with no matching config constant. Its baseline identity is `(file, qualified_symbol, env_name, constant, access, occurrence)`. Exemption rows in `python/env-via-config-constant-exemptions.json` require `file` and `reason`, with optional `env_name` and `constant` scoping keys. `env_name`-only rows match that literal, `constant`-only rows match that constant, and rows with both optional keys require both fields to match.

`python/cli.py lint suppression-reason` scans production `python/**/*.py` modules for suppression-family comments that lack an accepted same-line reason. Bare suppression-family comments without required codes or reasons are violations, and file-level suppressions use the same same-line reason rule; preceding or following comment lines do not count. Grandfathered rows live in `python/suppression-reason-baseline.json` with fields `(file, suppression_kind, text, occurrence, reason)`. Regenerate with `make regen-suppression-reason-baseline`; routine regeneration preserves existing reasons and drops obsolete rows. It runs through `py-lint-checks-fast`, `make py-lint`, pre-commit, and CI.

`python/cli.py lint tempfile-dir` scans `python/larch/**/*.py` and flags `tempfile.mkstemp`, `tempfile.mkdtemp`, `tempfile.NamedTemporaryFile`, and `tempfile.TemporaryDirectory` calls without a `dir=` keyword. Its baseline identity is `(file, qualified_symbol, callee, occurrence)`. Grandfathered rows live in `python/tempfile-dir-baseline.json`; the `reason` field documents why the site deliberately remains ambient.

`python/cli.py lint tmpdir-arg-env-fallback` scans `python/larch/**/*.py` and flags bare or attribute `validate_tmpdir` calls whose first argument is exactly `args.tmpdir`, and sole-argument `Path(args.tmpdir)` calls. `BoolOp` fallback forms such as `args.tmpdir or os.environ.get(config.ENV_IMPLEMENT_TMPDIR, "")` (or a local `ENV_IMPLEMENT_TMPDIR` name) are outside the direct-node rule. Baseline identity is `(file, qualified_symbol, pattern_name, occurrence)` with `pattern_name` of `validate_tmpdir` or `Path`. Grandfathered rows live in `python/tmpdir-arg-env-fallback-baseline.json`; stale rows fail. Regenerate with `make regen-tmpdir-arg-env-fallback-baseline`. The lint runs through `make py-lint-checks-fast` and the Python CI lint shard. Pytest coverage lives in `python/tests/lint/test_lint_tmpdir_arg_env_fallback.py`.

`python/cli.py lint wire-artifact-pairing` scans `python/wire-artifact-manifest.json` and fails when a curated wire artifact has production reader evidence under `python/larch/` but no production writer evidence. Manifest rows have exactly `{kind, artifact}` with `kind` set to `basename` or `relative_path`; the manifest has no `reason` field. Baseline rows in `python/wire-artifact-pairing-baseline.json` have exactly `{artifact, side, reason}`, where `side` is `external-writer`, `external-reader`, or `intentionally-one-sided`. Reader scope is production Python under `python/larch/`; writer scope is production Python under `python/` plus production shell writers under `scripts/` and `skills/*/scripts/`. Python tests, fixtures, `scripts/test-*.sh`, `skills/*/scripts/test-*.sh`, and `SKILL.md` prose do not count as writers. Shell write evidence includes committed production `touch`, `printf ... >`, `tee`, redirection, and `mv ... artifact` patterns. Regenerate with `make regen-wire-artifact-pairing-baseline`; routine regeneration preserves reasons and fails closed when a new one-sided artifact has no reason.

`python/cli.py lint module-manifest` enforces the host-or-justify principle for lint modules: every `python/larch/lint/lint_*.py` module must own a record in `python/lint-module-manifest.json`. The manifest is a top-level JSON object with `schema_version` (currently `1`) and a `modules` array sorted by module name. Each record has exactly `{module, host_decision, justification, source_issue}`, where `module` is a safe `lint_*.py` basename, `host_decision` is `legacy` or `new-module-justified`, `justification` is a string, and `source_issue` is an integer with booleans rejected. `legacy` rows are the frozen `LEGACY_SEED_MODULES` set that predates the ratchet, seeded with an empty justification and `source_issue` `0`; a new module cannot claim the legacy exemption. `new-module-justified` rows require a non-empty justification and a positive `source_issue` naming the commissioning issue. The lint compares the validated manifest with the live `lint_*.py` inventory through the shared lint engine and reports findings for missing entries, stale entries, `legacy` rows outside the seed, and incomplete new-module justifications. Malformed JSON, invalid schema or field types, duplicate modules, unsafe module names, symlinked or unreadable manifest input, and symlinked or non-regular inventory entries return the tool-error exit rather than being silently skipped. It has no baseline; fix the manifest to clear a finding. It runs through `make lint-module-manifest`, `make py-lint-checks-fast`, and local `make lint`. Pytest coverage lives in `python/tests/lint/test_lint_module_manifest.py`.

`python/cli.py lint engine-adoption` is the shared-engine adoption ratchet for `python/larch/lint/lint_*.py`. It is an engine-backed thin rule: discovery uses `git ls-files` pathspecs, detection walks each module AST, and comparison / stale reporting / guarded writes go through `run_rule`. Two violation classes use fixed messages and anchors so baseline identity is `(path, rule_id, message, anchor)` and source line is display metadata only:

- `argparse-construction`: operational `argparse.ArgumentParser` construction (module or symbol import, including aliases). Imports, bare references, subclass declarations, comments, docstrings, and string literals are ignored. A module is exempt from this class only when its module-level `main` directly delegates through a binding imported from `larch.lint.engine.run_rule`. An import without a call, an unrelated `run_rule`, or a call confined to an unused helper does not qualify.
- `baseline-io`: direct sibling `*-baseline.json` I/O, including `Path(...)` / `/` composition such as `root / "python" / BASELINE_FILENAME`, flows into `read_text` / `write_text` / `open` / JSON load-write shapes, and same-module helper indirection (`load_baseline` and serialization helpers). Unrelated JSON parsing, non-baseline files, and imported helper internals are outside this direct sibling-I/O rule. Engine adoption never exempts duplicated baseline plumbing.

At most one finding is emitted per module and class. Grandfathering is baseline-only via `python/lint-engine-adoption-baseline.json` (anchored generic rows with required non-empty reasons). `allow_inline_suppression` is false: a same-line `# lint-engine-adoption: ok <reason>` pragma does not clear a finding, even though other rules may keep reason-bearing pragma compatibility. New live debt fails; removed debt becomes stale (warning by default, failure with `--strict-stale`); check mode leaves baseline bytes unchanged; `--write` regenerates and cannot add a row without an explicit `--initial-reason`. Run via `make lint-engine-adoption` and `make py-lint-checks-fast`; there is no dedicated CI workflow change. Pytest coverage lives in `python/tests/lint/test_lint_engine_adoption.py`.

`python/cli.py lint layering` scans `python/larch/**/*.py` and flags imports where a lower-tier package imports from a higher-tier package. The tier ordering is: tier 0 (leaf utils: `larch.errors`, `larch.io`, `larch.outcomes`), tier 1 (`larch.core`), tier 2 (all other domain sub-packages), tier 3 (`larch.cli`). Its baseline identity is `(file, qualified_symbol, imported_package, occurrence)`. Grandfathered rows live in `python/layering-baseline.json`; the baseline shrinks as refactoring moves dependencies to the correct tier.

`python/cli.py lint shared-convention-regex` scans production `python/larch/**/*.py` modules and fails on copied architectural heading regexes, module-level `[BUG] in:title` selector constants, and lifecycle-prefix stripping loops. Comparison and match contexts cover the `startswith` family, equality and membership compares, and `re` pattern calls. Grandfathered rows live in `python/lifecycle-prefix-literal-baseline.json`; regenerate with `make regen-lifecycle-prefix-literal-baseline`. Direct target: `make lint-lifecycle-prefix-literal`. Exact-case tokens such as `[BUG]`, `[DONE]`, and `[STALLED]` remain allowed. The rule runs through `make rust-lint` and local `make lint`; coverage lives in `crates/larch-lint/tests/prefix_case_variant.rs`.

It flags direct and attribute calls to `_invalidate_guidelines_note` and directs callers to `_pin_or_invalidate_guidelines_note`. Same-line suppression uses `# lint-guidelines-note-wrapper-bypass: ok <reason>`. It has no baseline and should stay empty from day one.

`python3 python/cli.py lint gh-argv-literal` scans every regular, non-symlink `python/**/*.py` source file. It flags any list literal whose first element is the exact string `"gh"`; tuples, including CLI dispatcher keys, are not findings. Only `python/larch/git/` is exempt. Intentional fixtures under `python/tests/` need a same-line `# lint-gh-argv-literal: ok <reason>` pragma on the list's opening line. Test files are otherwise scanned, production pragmas never suppress findings, and there is no baseline. The lint runs through `py-lint-checks-fast`, pre-commit, and CI.

`larch lint rule guideline-no-exception` scans `ARCHITECTURAL_GUIDELINES.md` for entries whose deviate bullet starts with `n/a` or `never`, while ignoring Markdown fences. The baseline file is `crates/larch-lint/config/guideline-no-exception-baseline.json`, with rows shaped exactly as `{guideline_id, reason}`. New live findings fail, baselined live findings warn, and stale rows fail so the baseline shrinks when an entry is promoted or gets a real deviate clause. There is no `--write` mode or regen target; edit the baseline by hand.

The baseline-backed ratchets sort their baseline JSON by the full identity tuple. Every committed baseline row has a non-empty `reason`; missing, empty, extra-key, duplicate, or malformed records exit `2`. Existing violations are grandfathered with documented reasons, not silent keys. Baselined live findings warn and exit `0`; unbaselined live findings exit `1`. The renderer golden-test and Rust guideline no-exception ratchets also exit `1` for stale baseline rows.

For baseline-backed ratchets, occurrence numbers are assigned before baseline or pragma suppression. They count every matching site in source order within the nearest enclosing function, method, class body, or module body. The traversal is lexical pre-order over AST body lists, not `ast.walk`. Baseline identities deliberately omit line numbers, so cleanup removes obsolete rows rather than preserving old line positions.

Regenerate the generated baselines with `make regen-subprocess-via-runner-baseline`, `make regen-tempfile-dir-baseline`, `make regen-tmpdir-arg-env-fallback-baseline`, `make regen-env-via-config-constant-baseline`, `make regen-renderer-golden-tests-baseline`, `make regen-suppression-reason-baseline`, `make regen-layering-baseline`, `make regen-unreachable-branch-baseline`, `make regen-status-routing-truthiness-baseline`, and `make regen-markdown-heading-fence-state-baseline`. These targets pass `--initial-reason` only when the baseline file is absent. Routine regeneration preserves matching per-record reasons and fails closed when a new live identity has no preserved reason. The guideline no-exception baseline is hand-edited and has no regen target. Inline suppressions require reasons where supported: `# lint-subprocess-via-runner: ok <reason>`, `# lint-env-via-config-constant: ok <reason>`, `# lint-renderer-golden-tests: ok <reason>`, `# lint-guidelines-note-wrapper-bypass: ok <reason>`, `# lint-layering: ok <reason>`, `# lint-markdown-heading-fence-state: ok <reason>`, `# lint-self-disarmable-gate: ok <reason>`, `# lint-unreachable-branch: ok <reason>`, and `# lint-status-routing-truthiness: ok <reason>`.

`renderer-golden-tests` and `guidelines-note-wrapper-bypass` run under `make py-lint` through `py-lint-checks-fast`; Rust Markdown policy rules run in the dedicated Rust CI lane.

There are four pre-commit-driven paths:

- **CI** — The `lint` job runs `make lint-only` (repo-wide pre-commit over all files) with dedicated-job hooks skipped. `agent-lint`, `agnix`, and `lintlang` share the consolidated `agent-lint` job; `shellcheck`, `gitleaks`, ruff, and pyright have separate CI jobs or matrices. CI owns every exhaustive Rust operation: all-target/all-feature linting, builds, tests, dependency policy, and coverage. CI runs regression harnesses through the `test-harnesses` matrix (`make test-harnesses-1` through `make test-harnesses-5`) instead of one serial harness job. Non-secret-scan jobs use sparse checkouts. `gitleaks` and `trufflehog` keep full source history. Remote run archives pass the run-log scrubber before publication and are not fetched into CI. Local `make lint` also runs the direct static checks between harnesses and pre-commit; it does **not** run `py-lint` or `py-test` as make targets. CI also runs `contains-pins`, `python-lint`, `python-pyright`, and `python-tests`, so every relevant-checks local phase has a CI counterpart while pylint, pytest, and harnesses stay parallelized in CI.
- **Relevant checks CLI (`python/cli.py checks run-relevant`)** — The Python dispatcher finds branch, staged, unstaged, and untracked changes; filters existing regular files for `pre-commit run --files`; and runs the contains-pin scanner. The scoped pre-commit phase carries ruff autofix (`ruff check --fix`) for changed Python files. Pyright and agent/config scans are manual or dedicated-CI work. For Rust paths, the filename-aware hook selects and logs the exact Cargo packages and targets, then runs one bounded Clippy configuration. A deleted or otherwise non-regular Rust path skips that hook and uses the same bounded entry point once as a compatibility fallback. A missing proof marker fails closed. The CLI never follows pre-commit with `make rust-check`, `cargo check`, a full-repository `agent-lint`, tests, or coverage. A no-change run is a fast freshness check. `/implement` and `/review` use the CLI to capture verbose output under the session tmpdir and emit a one-line `RELEVANT_CHECKS_OK=true ...` green-path envelope when checks succeed. The default path fails closed on structural errors; `RELEVANT_CHECKS_SKIPPED=true` is reserved for explicit `--allow-skip` test paths. On failure, orchestrators read `DIGEST_FILE` first when the helper envelope includes it, then fall back to `REDACTED_LOG_FILE`; folded composite stdout may place those keys after leading file or git KVs, so consumers must scan the full composite stdout for both keys. `REDACTED_LOG_FILE` remains the full-log fallback and repair-loop input.
- **Local git hook** — Run `make setup` (or `pre-commit install`) to enable pre-commit hooks on every commit. Bypassable via `git commit --no-verify`; the CI jobs are the enforced backstop.
- **Manual pre-commit stage** — Run `pre-commit run --hook-stage manual --all-files` only when deliberately requesting repository-wide policy, agent/config, secret, or type scans. It is not part of relevant checks or the default git hook.

`.github/workflows/requirements-lint.txt` is the central pinned dependency file for the CI Python lint environment. The `lint`, `shellcheck`, `test-harnesses` matrix cells, and `agent-sync` all use it for `actions/setup-python` pip caching and `pip install -r`.

Pylint duplicate-code (`R0801`) is disabled in CI during the Rust migration. The
commented `duplicate-code` and `duplicate-code-full` jobs preserve the old
differential and exhaustive definitions for reference. Neither job is a required
status check. The manually dispatched
`.github/workflows/duplicate-code.yaml` workflow remains available for deliberate
Python baseline maintenance. Rust duplicate detection remains required through
the `larch-lint` rule documented above and runs as part of `rust-lint`.

## Shellcheck Engine

The shellcheck pre-commit hook is local so it can run one file per shellcheck process through `scripts/pre-commit-shellcheck.sh` and `xargs -P`. ## CI sharding of `test-harnesses`

`make test-harnesses` remains the local umbrella target and runs every regression harness wired into the `test-harnesses-N` shards plus the partition guard (`make test-harness-shards-coverage` reports the active inventory; the `Makefile` is the source of truth). CI fans the same inventory out across five parallel matrix cells named `test-harnesses (1)` through `test-harnesses (5)`, each invoking `make test-harnesses-N`.

The shard lists live directly in `Makefile`. After #5429 and the contract-unification partition, harness shards contain only **direct Bash leaves**: recipe-bearing `test-*` targets whose complete recipe is Bash-harness work (no pytest), plus valid non-`test-*` `*-bash-harness` leaves such as `write-final-report-bash-harness`. Public aggregates that combine a pytest leaf with a delegation smoke (for example `test-write-final-report`, `test-step-7a`, `test-oos-disposition-gate`, `test-flush-execution-issues`) may run both lanes locally but must not appear in a shard. Pytest behavioral authorities stay on `make py-test` and the focused `*-py-harness` / aggregate targets. Converted pytest structure targets (`test-alias-structure`, `test-bug-structure`, `test-design-structure`, `test-implement-structure`, `test-learn-from-bugs-structure`, `test-research-structure`, `test-review-structure`) likewise stay outside Bash shard lists. Rebalance shards by measured CI timing with `/rebalance-tests --kind harness` (see Refreshing shard balance below). New Bash leaves must be assigned to exactly one `test-harnesses-N:` prerequisite list; `make test-harness-shards-coverage` checks for missing, orphaned, non-leaf, duplicated, or non-standard entries. The matrix uses `fail-fast: false`, so all five shards finish even after one fails. This spends more CI minutes but preserves complete diagnostics.

Local ordering changed: under `make test-harnesses` and therefore `make lint`, harnesses now execute in shard order (`test-harnesses-1`, then `test-harnesses-2`, and so on), not in the old single prerequisite-list order. Direct `make test-X` invocations are unchanged. CI shards run on separate VMs; local `make -j20 test-harnesses` can run shard targets concurrently, so fixed `/tmp` paths in individual harnesses remain a local-parallelism limitation even though the CI split is isolated.

Measured CI timing for the five-shard layout remains balanced enough that this reconciliation keeps five shards; do not change the workflow matrix solely because pytest and aggregates left the Bash-leaf inventory. Rebalance only when complete `larch ci-timing harness` totals show material, non-local imbalance.

### Refreshing shard balance

Rebalance the harness shards by measured CI timing with the `/rebalance-tests`
dev skill (`.claude/skills/rebalance-tests/`):

```bash
python3 .claude/skills/rebalance-tests/scripts/rebalance.py --kind harness
```

Harness mode LPT-packs `LARCH_HARNESS_TIMING` medians into the `test-harnesses-N`
shard lists and verifies real per-shard CI job wall-clock against
`--max-shard-wall-clock` (default 60s); the wall-clock report is warning-only. To
add a single new target, append it to any shard, run `make
test-harness-shards-coverage` to verify the partition, then rebalance by timing.

For Python unit test shards, use the `/rebalance-tests` dev skill
(`.claude/skills/rebalance-tests/`):

```bash
python3 .claude/skills/rebalance-tests/scripts/rebalance.py --kind python
```

Python mode refreshes the checked-in `python/shard-assignments.json` map from
`python-tests` pytest `--durations=0` `call` rows. Merge is left to the operator.

Python verification fails closed when verification logs contain zero parseable
rows, do not cover every expected shard, or exceed `--balance-threshold`.

Before any write, branch, or PR, the unified pre-write gate runs in memory.
Python work rejects empty timing rows, dedupes retried shard attempts before
medians, and validates `--n-python-shards` against the observed `python-tests`
matrix shard count. The current matrix count is 20, and the parser prefers the
`shard X of N` total from CI logs over the maximum shard id seen in rows.

The artifact cleanliness gate requires `python/shard-assignments.json` to be
clean in git. Dirty paths abort with a named error and no branch or PR.

After PR creation, one shared `workflow_dispatch` loop runs for every selected
kind before leg-specific verification collection. Python fail-closed checks run
only after those verification runs finish.

The Rust `larch ci-timing pytest` command parses `call` rows and dedupes retried
shards by duration-section attempt for both baseline packing and verification
totals. At runtime, assigned nodeids use `python/shard-assignments.json`;
unassigned nodeids keep the global collection-index round-robin fallback.
Malformed maps, including JSON booleans as shard ids, fail closed during pytest
collection. A non-empty map whose maximum shard id does not match the runtime
`PYTEST_SHARD_COUNT` is ignored in favor of round-robin selection so coverage is
not reduced.

See `.claude/skills/rebalance-tests/SKILL.md` for flags and full workflow
documentation. Rust fixture and wire-contract tests live in
`crates/larch-core/src/ci_timing.rs` and `crates/larch-core/src/test_shards.rs`.
Python consumer tests are `python/tests/test_rebalance_script.py` and
`python/tests/test_pytest_sharding.py`; the executable boundary is covered by
`crates/larch-cli/tests/test_shards.rs`. Run the targeted Cargo and pytest
commands before changing the rebalance contract.

**`LARCH_HARNESS_TIMING` format** (from `python/larch/report/timing.py harness docs`): each
wrapped `bash` invocation emits one tab-separated row to stdout:

```
LARCH_HARNESS_TIMING<TAB><test-name><TAB><N.NNs>
```

The trailing `s` suffix is stripped and the remainder parsed as decimal seconds.
Current output uses exactly two fractional digits (e.g. `0.34s`, `7.62s`);
older published logs may contain integer-only seconds — both forms are accepted.

### Branch protection migration

Before the sharded CI shape merges, an admin must update main-branch protection. In GitHub, open repository Settings → Branches → the `main` rule → Require status checks. Remove the old single `test-harnesses` required check and add these required checks:

- `test-harnesses (1)`
- `test-harnesses (2)`
- `test-harnesses (3)`
- `test-harnesses (4)`
- `test-harnesses (5)`

Save the rule before merging the PR, or GitHub may report green matrix checks while branch protection still waits for the retired single check. When adding a split CI job such as `python-pyright`, add that new status check to branch protection before relying on it to gate merges. If the repository uses rulesets in addition to classic branch protection, verify the same required-check list there too.

The `shellcheck` job runs as a dedicated CI job in parallel with `lint`; the `lint` job SKIPs the shellcheck hook to avoid paying the pre-commit env-install cost twice.

### Changing the shard count (lockstep edit)

The shard count today is `5`, hard-coded in two places (the partition guard is shard-count-agnostic — it discovers `test-harnesses-N:` rules by parsing the Makefile):

1. `Makefile` — five `test-harnesses-N:` shard targets and the umbrella `test-harnesses:` aggregating them.
2. `.github/workflows/ci.yaml` — the matrix `shard: [1, 2, 3, 4, 5]` strategy on the `test-harnesses` job.

`scripts/test-harness-shards-coverage.sh` does NOT need editing on a shard-count change: it discovers the active `test-harnesses-N:` rules from the Makefile (`extract_shard_prereqs` parses them) and validates that `test-harness-shards-coverage` is first in the shard that contains it. The umbrella-expected list is built from the same discovered set.

A partial edit that updates the Makefile but forgets the workflow YAML would silently drop a CI shard while local `make test-harness-shards-coverage` still passes. Any change to shard count must touch both locations in the same commit and re-run the branch-protection migration above with the new check identities.
