# Orchestrator NEVER List

Cross-skill anti-pattern rules for single-iteration larch orchestrators. Skills should read this file when a step or recovery path explicitly references it; do not assume every skill loads it at session start.

1. **NEVER improvise ScheduleWakeup outside skill-script direction.** **Why**: single-iteration skills end at their terminal cleanup step. The orchestrator calling `ScheduleWakeup` on its own initiative, or narrating "next iteration" / "loop sleeping until ..." prose, is improvisation outside the skill's steps. Recurring behavior is owned exclusively by `/loop`'s `<<autonomous-loop-dynamic>>` sentinel mechanism — never by orchestrator improvisation in a child skill's terminal turn. **How to apply**: do not call `ScheduleWakeup` from any skill that does not have a numbered step directing the call. See AGENTS.md for the project-wide rule. **CI-backed**: yes — `scripts/test-anti-improvised-wakeup.sh` pins the literal at this site.

2. **NEVER treat a sub-skill's terminal output as the parent skill's terminal output.** **Why**: skills invoked via the Skill tool (for example `/larch:issue`, `/larch:review`, `/larch:design`) produce visually-terminal output — machine footers (`ISSUES_*`, `REVIEW_*`), sentinel writes, and human-readable summaries — that collectively read like a stopping point. Producing a summary and ending the turn after a sub-skill returns has caused observed regressions (issue #2681: `/design` Step 5b halt skipped Step 5c rename to `[DESIGNED]` after `/larch:issue` returned). The sub-skill's terminal output marks the SUB-skill's end, NOT the parent skill's. **How to apply**: when a Skill-tool sub-skill returns, immediately continue with the parent skill's NEXT numbered step (or sub-step) before producing any summary or human-readable closing prose. See `skills/design/SKILL.md` `Anti-halt continuation reminder` and the per-sub-step `Continue to Step` banners for the /design-specific application. **CI-backed**: yes — `scripts/test-design-structure.sh` pins the literal at this site.

3. **NEVER make progress-observation tool calls between a background launch and its `<task-notification>`.** **Why:** after a background launch, any probe that observes progress keeps the orchestrator in the turn instead of yielding. Issue #3175 burned turns in `/implement` by polling task output. Run `1890FD62-0DA8-4259-B652-BE9FFD962A76` repeated the failure at larger scale in `/design` by listing tmpdir and reviewer artifacts while Step 3 ran. **How to apply:** between a background launch and its `<task-notification>`, the orchestrator makes **ZERO progress-observation tool calls**. This ban is intent-based, not path-shape-based. Non-exhaustive banned shapes include Bash probes such as `ls`, `cat`, `wc`, `stat`, `find`, `head`, `tail`, `test`, or `grep`; Read of the session tmpdir, task outputs, result env files, reviewer output files, or plan-review directories; TaskOutput on the running task; backgrounded `sleep N &&` probe calls; backgrounded watcher loops; and Monitor waits for completion. Rely on the Bash `<task-notification>` for one-shot completion. Read outputs once, after completion. **Premature-notification recovery split:** For `/design`, when a premature `<task-notification>` fires with non-empty task output and the child is still running, the sanctioned recovery path is one foreground terminal-sentinel probe per explicit recovery turn, using `[ -f … ]` or `test -f …` against the terminal sentinel for that `/design` fence. A foreground probe returns synchronously and cannot fire a task-notification, so it does not amplify. For `/design`, when task output is empty, end the turn without probing (#5240). For `/implement`, when a premature `<task-notification>` fires while the child is still running (empty or non-empty task output), end the turn without sentinel probing and wait for the next `<task-notification>`; do not probe `$DESIGN_TMPDIR` or design-only sentinels. `/implement` long-running fences do not use `/design` sentinels, and the hook whitelist does not apply to implement recovery. Implement remains notification-driven until real implement terminal sentinels and hook support exist. NEVER launch a background recovery waiter (`until [ -f … ]; do sleep N; done`) for either skill: it is itself a zero-output background task that fires its own premature notification and multiplies into a re-engagement loop; `scripts/hook-bg-poll-guard.sh` denies it (#4725). `WAIT` when absent is expected for `/design` foreground probes. When the `/design` terminal sentinel is present, proceed to normal post-notification parsing guarded by it; do not wait for a second notification. When the `/design` terminal sentinel is absent, end the turn without `ps` polling and repeat only that one-shot probe on the next explicit recovery turn. Do not probe `.completed/step-3`, `.completed/step-5c`, result envs, task outputs, progress artifacts, or reviewer directories as completion conditions. This relies on one documented platform assumption: the backgrounded task reliably re-fires a `<task-notification>` on completion (current evidence indicates it does). Do NOT fall back to Monitor. **CI-backed**: yes; `scripts/test-design-structure.sh` pins the contract token at this site.

4. **NEVER poll a `run_in_background` result file with a Bash sleep loop.** **Why:** the task stays registered as running until `<task-notification>` fires. Polling that finds the result file first can leave a dangling task handle. The handle can block session exit. **How to apply:** after a successful `run_in_background` launch, wait for `<task-notification>` before parsing stdout or reading any result file. Do not run a Bash `for`/`while`/`until` + `sleep` loop to watch for the result file. Narrow `/design` exception: the foreground terminal-sentinel probe described in NEVER #3 is not result-file polling, and it applies only to `/design` premature notifications with non-empty task output while the child process is still running. `/implement` recovery remains notification-only for all premature notifications per implement NEVER #8; do not use the NEVER #3 `/design` probe. The background recovery waiter is not a sanctioned exception; it is denied by `scripts/hook-bg-poll-guard.sh` (#4725). Do NOT fall back to Monitor. **CI-backed**: yes; `scripts/test-implement-anti-polling-rule.sh` pins the literal at this site.
