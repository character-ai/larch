# Orchestrator NEVER List

Cross-skill anti-pattern rules for all single-iteration larch orchestrators. Load once per session via the MANDATORY directive in each skill's SKILL.md.

1. **NEVER improvise ScheduleWakeup outside skill-script direction.** **Why**: single-iteration skills end at their terminal cleanup step. The orchestrator calling `ScheduleWakeup` on its own initiative, or narrating "next iteration" / "loop sleeping until ..." prose, is improvisation outside the skill's steps. Recurring behavior is owned exclusively by `/loop`'s `<<autonomous-loop-dynamic>>` sentinel mechanism — never by orchestrator improvisation in a child skill's terminal turn. **How to apply**: do not call `ScheduleWakeup` from any skill that does not have a numbered step directing the call. See AGENTS.md for the project-wide rule. **CI-backed**: yes — `scripts/test-anti-improvised-wakeup.sh` pins the literal at this site.

2. **NEVER treat a sub-skill's terminal output as the parent skill's terminal output.** **Why**: skills invoked via the Skill tool (for example `/larch:issue`, `/larch:review`, `/larch:design`) produce visually-terminal output — machine footers (`ISSUES_*`, `REVIEW_*`), sentinel writes, and human-readable summaries — that collectively read like a stopping point. Producing a summary and ending the turn after a sub-skill returns has caused observed regressions (issue #2681: `/design` Step 5b halt skipped Step 5c rename to `[DESIGNED]` after `/larch:issue` returned). The sub-skill's terminal output marks the SUB-skill's end, NOT the parent skill's. **How to apply**: when a Skill-tool sub-skill returns, immediately continue with the parent skill's NEXT numbered step (or sub-step) before producing any summary or human-readable closing prose. See `skills/design/SKILL.md` `Anti-halt continuation reminder` and the per-sub-step `Continue to Step` banners for the /design-specific application. **CI-backed**: yes — `scripts/test-design-structure.sh` pins the literal at this site.

3. **NEVER make progress-observation tool calls between a background launch and its `<task-notification>`.** **Why**: after a background launch, any probe that observes progress keeps the orchestrator in the turn instead of yielding. Issue #3175 burned ~80 turns in `/implement` by polling task output. Run `1890FD62-0DA8-4259-B652-BE9FFD962A76` repeated the failure at larger scale in `/design` by listing tmpdir and reviewer artifacts while Step 3 ran. **How to apply**: between a background launch and its `<task-notification>`, the orchestrator makes **ZERO progress-observation tool calls**. This ban is intent-based, not path-shape-based. Non-exhaustive banned shapes include Bash probes such as `ls`, `cat`, `wc`, `stat`, `find`, `head`, `tail`, `test`, or `grep`; Read of the session tmpdir, task outputs, result env files, reviewer output files, or plan-review directories; TaskOutput on the running task; backgrounded `sleep N &&` probe calls; backgrounded watcher loops; and Monitor waits for completion. Rely on the Bash `<task-notification>` for one-shot completion. Read outputs once, after completion. Premature-notification recovery carve-out: only after an empty `<task-notification>` fires prematurely while the underlying child process is still running, the sanctioned recovery path is one foreground terminal-sentinel probe per explicit recovery turn, using `[ -f … ]` or `test -f …` against the terminal sentinel for the step (`.completed/step-3-terminal`, `.completed/step-5c-terminal`, or `.completed/step-final-summary`) only. A foreground probe returns synchronously and cannot fire a task-notification, so it does not amplify. NEVER launch a background recovery waiter (`until [ -f … ]; do sleep N; done`) for this: it is itself a zero-output background task that fires its own premature notification and multiplies into a re-engagement loop; `scripts/hook-bg-poll-guard.sh` denies it (#4725). Bash tool calls do not persist `$DESIGN_TMPDIR`; when it is not already exported, prefix the probe with a single `DESIGN_TMPDIR=<absolute-path>;` assignment so the sentinel resolves. `/implement` long-running fences do not use those `/design` sentinels, and the hook whitelist does not apply to implement recovery; implement remains notification-driven until real implement terminal sentinels exist. `WAIT` when absent is expected. When the terminal sentinel is present, proceed to normal post-notification parsing guarded by it; do not wait for a second notification. When absent, end the turn without `ps` polling and repeat only that one-shot probe on the next explicit recovery turn. This relies on one documented platform assumption: the backgrounded task reliably re-fires a `<task-notification>` on completion (current evidence indicates it does). Do not probe `.completed/step-3`, `.completed/step-5c`, result envs, task outputs, progress artifacts, or reviewer directories. **CI-backed**: yes; `scripts/test-design-structure.sh` pins the contract token at this site.

4. **NEVER poll a `run_in_background` result file with a Bash sleep loop.** **Why**: The task stays registered as running until `<task-notification>` fires. Polling that finds the result file first can leave a dangling task handle. The handle can block session exit. **How to apply**: after a successful `run_in_background` launch, wait for `<task-notification>` before parsing stdout or reading any result file. Do not run a Bash `for`/`while`/`until` + `sleep` loop to watch for the result file. Narrow exception: the foreground terminal-sentinel probe described in NEVER #3 is not result-file polling, but only after the empty `<task-notification>` has fired early and the child process is still running. The background recovery waiter is no longer a sanctioned exception — it is denied by `scripts/hook-bg-poll-guard.sh` (#4725). **CI-backed**: yes — `scripts/test-implement-anti-polling-rule.sh` pins the literal at this site.
