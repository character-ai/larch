# Orchestrator NEVER List

Cross-skill anti-pattern rules for single-iteration larch orchestrators. Skills should read this file when a step or recovery path explicitly references it; do not assume every skill loads it at session start.

1. **NEVER improvise ScheduleWakeup outside skill-script direction.** **Why**: single-iteration skills end at their terminal cleanup step. The orchestrator calling `ScheduleWakeup` on its own initiative, or narrating "next iteration" / "loop sleeping until ..." prose, is improvisation outside the skill's steps. Recurring behavior is owned exclusively by `/loop`'s `<<autonomous-loop-dynamic>>` sentinel mechanism — never by orchestrator improvisation in a child skill's terminal turn. **How to apply**: do not call `ScheduleWakeup` from any skill that does not have a numbered step directing the call. See AGENTS.md for the project-wide rule. **CI-backed**: yes — `scripts/test-anti-improvised-wakeup.sh` pins the literal at this site.

2. **NEVER treat a sub-skill's terminal output as the parent skill's terminal output.** **Why**: skills invoked via the Skill tool (for example `/larch:issue`, `/larch:review`, `/larch:design`) produce visually-terminal output — machine footers (`ISSUES_*`, `REVIEW_*`), sentinel writes, and human-readable summaries — that collectively read like a stopping point. Producing a summary and ending the turn after a sub-skill returns has caused observed regressions (issue #2681: `/design` Step 5b halt skipped Step 5c rename to `[DESIGNED]` after `/larch:issue` returned). The sub-skill's terminal output marks the SUB-skill's end, NOT the parent skill's. **How to apply**: when a Skill-tool sub-skill returns, immediately continue with the parent skill's NEXT numbered step (or sub-step) before producing any summary or human-readable closing prose. See `skills/design/SKILL.md` `Anti-halt continuation reminder` and the per-sub-step `Continue to Step` banners for the /design-specific application. **CI-backed**: yes — `scripts/test-design-structure.sh` pins the literal at this site.

3. **NEVER make progress-observation tool calls between a background launch and its `<task-notification>`.** **Why:** after a background launch, any probe that observes progress keeps the orchestrator in the turn instead of yielding. Issue #3175 burned turns in `/implement` by polling task output. Run `1890FD62-0DA8-4259-B652-BE9FFD962A76` repeated the failure at larger scale in `/design` by listing tmpdir and reviewer artifacts while Step 3 ran. **How to apply:** between a background launch and its `<task-notification>`, the orchestrator makes **ZERO progress-observation tool calls**. This ban is intent-based, not path-shape-based. Non-exhaustive banned shapes include Bash probes such as `ls`, `cat`, `wc`, `stat`, `find`, `head`, `tail`, `test`, or `grep`; Read of the session tmpdir, task outputs, result env files, reviewer output files, or plan-review directories; TaskOutput on the running task; backgrounded `sleep N &&` probe calls; backgrounded watcher loops; and Monitor waits for completion. Rely on the Bash `<task-notification>` for one-shot completion. Except for the `/design` classification `Read` below, read outputs once, after completion. **Premature-notification recovery split:** For `/design`, after a premature `<task-notification>`, first run exactly one `Read` of the active `tasks/*.output` to classify the file bytes, not the notification wrapper text. Missing or whitespace-only task-output bytes mean silent yield (#5240): after that classification `Read`, use no further probe, parse, or prose tools. prefix-identical repeat non-empty task-output bytes (first 200 chars) for the same wait with the relevant terminal sentinel absent also mean silent yield. New or changed non-empty task-output bytes allow one foreground terminal-sentinel probe per explicit recovery turn, using `[ -f … ]` or `test -f …` against the terminal sentinel for that `/design` fence. A foreground probe returns synchronously and cannot fire a task-notification, so it does not amplify. For `/implement` Steps 3 and 5, premature notifications remain notification-only: end the turn without probing, reading task output, using TaskOutput, or using Monitor while the child is still running. If a read of the just-completed Step 3 or Step 5 task output is denied immediately after that same step's genuine completion notification, run exactly one foreground same-step sentinel probe: `test -f "$IMPLEMENT_TMPDIR/.completed/step-3-terminal"` for `implement-step3-checks`, or `test -f "$IMPLEMENT_TMPDIR/.completed/step-5-terminal"` for `implement-step5-review`. The braced `${IMPLEMENT_TMPDIR}` forms and one leading `IMPLEMENT_TMPDIR=<absolute-path>;` assignment are allowed. When the sentinel is present, retry the just-denied output read once. When it is absent after a genuine completion notification, do not wait for another notification; route through that step's existing failure or stall handling. For `/implement` Step 8, run one foreground non-sleeping `IMPLEMENT_TMPDIR=$(awk 'BEGIN{p="IMPLEMENT_TMPDIR="} index($0,p)==1{print substr($0,length(p)+1); exit}' "$HOME/.cache/larch/sessions/current-implement-env-$PPID.sh" 2>/dev/null); test -f "$IMPLEMENT_TMPDIR/.step-8-ship-handoff.rc"` at notification time; the probe is hook-allowed only while `implement-step8-ship` is live and clamped when rc stays absent. `/implement` writes `.completed/step-3-terminal` (Step 3 checks), `.completed/step-5-terminal` (Step 5 review), and `.step-8-ship-handoff.rc` (Step 8 ship) release sentinels; `scripts/hook-bg-poll-guard.sh` recognizes these and denies Monitor and TaskOutput calls during any active bg-wait. NEVER launch a background recovery waiter (`until [ -f … ]; do sleep N; done`) for either skill: it is itself a zero-output background task that fires its own premature notification and multiplies into a re-engagement loop; `scripts/hook-bg-poll-guard.sh` denies it (#4725). `WAIT` when absent is expected for `/design` foreground probes. When the `/design` terminal sentinel is present, proceed to normal post-notification parsing guarded by it; do not wait for a second notification. When the `/design` terminal sentinel is absent, end the turn without `ps` polling and repeat only that one-shot probe on the next explicit recovery turn. Do not probe `.completed/step-3`, `.completed/step-5c`, result envs, task outputs, progress artifacts, or reviewer directories as completion conditions. This relies on one documented platform assumption: the backgrounded task reliably re-fires a `<task-notification>` on completion (current evidence indicates it does). Do NOT fall back to Monitor. **CI-backed**: yes; `scripts/test-design-structure.sh` pins the contract token at this site.

4. **NEVER poll a `run_in_background` result file with a Bash sleep loop.** **Why:** the task stays registered as running until `<task-notification>` fires. Polling that finds the result file first can leave a dangling task handle. The handle can block session exit. **How to apply:** after a successful `run_in_background` launch, wait for `<task-notification>` before parsing stdout or reading any result file. Do not run a Bash `for`/`while`/`until` + `sleep` loop to watch for the result file. Narrow `/design` exception: the classification `Read` and foreground terminal-sentinel probe described in NEVER #3 are not result-file polling, and the probe applies only after a `/design` premature notification whose task-output bytes are new or changed and non-empty while the child process is still running. `/implement` recovery is scoped: Steps 3 and 5 have their own narrower post-denial same-step sentinel probe after a genuine completion notification, while Step 8 uses the one foreground `IMPLEMENT_TMPDIR=$(awk 'BEGIN{p="IMPLEMENT_TMPDIR="} index($0,p)==1{print substr($0,length(p)+1); exit}' "$HOME/.cache/larch/sessions/current-implement-env-$PPID.sh" 2>/dev/null); test -f "$IMPLEMENT_TMPDIR/.step-8-ship-handoff.rc"` probe described in implement NEVER #8; do not use the NEVER #3 `/design` probe for `/implement`. The background recovery waiter is not a sanctioned exception; it is denied by `scripts/hook-bg-poll-guard.sh` (#4725). Do NOT fall back to Monitor. **CI-backed**: yes; `scripts/test-implement-anti-polling-rule.sh` pins the literal at this site.

5. **NEVER generate more than K consecutive no-progress turns under an active bg-wait marker.** **Why:** spurious `<task-notification>` re-invocations can drive the orchestrator into an unbounded turn loop that burns dozens to hundreds of turns before a human intervenes (observed: `BC8DDA64` ~40 uncapped turns). The `PreToolUse` probe-clamp in `scripts/hook-bg-poll-guard.sh` only catches turns that make a denyable tool call; prose-only turns are invisible to it. **The universal backstop**: `scripts/hook-no-progress-guard.sh` registers a `Stop` hook that counts every turn end while a bg-wait marker is live, and a `UserPromptSubmit` hook that blocks the next turn once the count reaches `LARCH_NO_PROGRESS_GUARD_THRESHOLD` (default 5). The circuit breaker auto-disarms when the bg task's terminal sentinel is written (or the marker is removed by the EXIT trap), so a genuine completion notification is never blocked. **How to apply:** do not generate prose-only "still waiting" turns under a live bg-wait marker; end the turn silently per the rules in NEVER #3 and `skills/shared/design-background-wait.md`. If you are blocked by the circuit breaker, the operator message identifies the session tmpdir and threshold so the stale marker can be cleared. The threshold is intentionally small (5 turns) to bound worst-case cost while still allowing 1–3 legitimate continuation turns on normal completion. **CI-backed**: `scripts/test-hook-no-progress-guard.sh`.
