### In-Scope Findings
- **code-quality** `skills/shared/scripts/oos-serialize.sh:48` — The new header security probe uses `\<security\>`, which is GNU-awk word-boundary syntax; on macOS/BSD `awk` (the repo’s Bash 3.2 target) `\<`/`\<` are not word boundaries and only match a literal `<security>` substring, so headings like `### FINDING_1: security hardening [OUT_OF_SCOPE]` are not classified as security the way `scripts/lib-vote-tally.sh:67-70` does with Python `\bsecurity\b`. That leaves `oos-serialize.sh`’s standalone `OOS_ACCEPTED_COUNT=0` rebuild path with weaker security filtering than the tally path on the same machine. **Suggested fix:** Replace the `\<security\>` alternative with a POSIX/BSD-safe heuristic (e.g. keep `\[security\]`, add an explicit `[[:space:]]security([[:space:]]|$|…)` branch, or call the existing Python `is_security_block` helper instead of approximating `\b` in awk).

- **code-quality** `skills/review/scripts/tally-code-votes.sh:597-605` — Accepted OOS blocks are captured via `normalized=$(…)` command substitution and then re-printed, while `skills/review-and-fix/scripts/review-and-fix.sh:1467-1469` streams normalization straight into the sink with `>>`. Command substitution loads the whole block into shell memory, strips all trailing newlines (bash behavior), and is more exposed to `ARG_MAX`/memory pressure on large blocks than the redirect pattern used elsewhere in this fix. **Suggested fix:** Match the review-and-fix pattern: append with `"$NORMALIZE_OOS_HELPER" --seq "$OOS_WRITE_SEQ" --block-file "$block" >> "$OOS_ACCEPTED_FILE"` (and mirror via a temp file or a second append only when `OOS_ACCEPTED_OUT != OOS_ACCEPTED_FILE`), avoiding multi-line `$(…)`.
