# scripts/collect-agent-results.sh — contract

The `.meta` parser is intentionally line-oriented: each record is split on the first `=` and no escaping layer is applied while reading. On duplicate keys (`TIMEOUT=`, `CMD_JSON=`, etc.), the last assignment wins. This matches the existing parser convention; sidecars with internal contradictions are accepted as long as the final value satisfies validation. Keep this parser in sync with the writer-side `.meta sidecar grammar` contract in `scripts/run-external-agent.md`, which documents the per-field guarantees for `TOOL`, `TIMEOUT`, capture booleans, `OUTPUT_FILE`, and `CMD_JSON`.

## `--paths-file` (orchestrator handoff)

Instead of positional output paths, callers may pass `--paths-file <file>` with one reviewer output path per line (blank lines skipped). The file must be readable and yield at least one non-blank line; otherwise the collector exits **1** (`paths-file contains no entries (preserves anti-pattern #4)` or `paths-file not readable: …`). `--paths-file` is mutually exclusive with positional output-file arguments.

Paths-files are expected to be dispatcher-written, session-local artifacts under `/design` or `/review` orchestration. They drive `wait-for-reviewers.sh` polling and downstream reads; treat them as trusted only within that model. Optional future hardening: caller-side prefix allowlisting against `$DESIGN_TMPDIR` / `$REVIEW_TMPDIR` if a surface ever accepts paths-files from less-trusted writers.

Wait usage errors (for example, invalid `--timeout` from the caller) and other wait fatals (for example, `mktemp` failure in `scripts/wait-for-reviewers.sh`) on the **initial** `wait-for-reviewers.sh` invocation surface as collector exit 1 with the wait script's stderr message followed by a `collect-agent-results.sh: wait-for-reviewers.sh exited <N>` trailer line, rather than being silently masked into `SENTINEL_TIMEOUT` / `EMPTY_OUTPUT` reviewer records (closes #1188 / umbrella #1200). The **empty-output retry-phase** wait (later in the same script) deliberately keeps `>/dev/null 2>&1 || true` because retry outcomes are re-checked from sentinel state downstream; tightening that path could surface transient `mktemp` / IO failures as fatal collector exits in cases where the retry result still has a usable sentinel. On the initial-wait success path, wait's stderr (per-poll dot progress and per-minute status lines) is captured to a temp file under `${TMPDIR:-/tmp}` and removed via an `EXIT` trap (covering signal-driven exits as well as success and explicit-failure branches), preserving today's quiet-success orchestrator UX. Argument-presence validation for `--timeout` is owned by the collector itself (parameter-expansion `:?` at the option-parsing case arms in `scripts/collect-agent-results.sh`); argument-value validation (positive-integer plus `10#` floor) is owned by wait. The collector treats wait's value-validation as authoritative rather than swallowing it. The regression harness `scripts/test-wait-for-reviewers.sh` pins both the wait-side rejection contract (R1-R8) and the collector-side passthrough (C1/C2).

**Retry-failure `EXIT_CODE` propagation (#1290).** On retry failure, the collector propagates the retry `.done` sentinel value as `EXIT_CODE=<RETRY_EXIT>` rather than masking non-zero exits as `EXIT_CODE=0`. All collector-side fail-closed rows that do not have a child-process sentinel value to propagate (pre-launch retry-metadata invalid and post-launch missing retry sentinel) emit `EXIT_CODE=99` for consistency. The retry success branch (`.done` is `0` AND retry output non-empty) continues to emit `STATUS=OK|EXIT_CODE=0`. Note: `EXIT_CODE=0` can still appear on a retry **failure** row when the sentinel is `0` but the retry output stayed empty (`STATUS=EMPTY_OUTPUT`); `EXIT_CODE=0` alone is therefore not a success signal — `STATUS=OK` (and an empty `FAILURE_REASON`) is. Both initial and retry sentinel read sites pass the sentinel bytes (after the `cat` command-substitution trailing-newline trim) through `normalize_exit_code_or_99`, which accepts only `^[0-9]{1,3}$` digit strings in the `0..255` range; invalid bytes stderr-log and force `99`. The length bound is load-bearing because Bash arithmetic is fixed-width and can otherwise accept oversized digit strings after overflow, so the guard also protects the pipe-delimited `RESULTS` invariant from newlines, `|`, control bytes, and oversized values in `.done` content. The companion `exit_code_was_coerced` returns `true|false` for a given raw sentinel; the initial-sentinel call site uses it to detect coercion (since `normalize_exit_code_or_99` runs in a `$(...)` subshell, any global it sets cannot propagate back). When coercion fired AND the output file is empty, the initial-sentinel branch routes to the retry path rather than to `STATUS=FAILED` — a corrupt or partially-written `.done` should not deny the one-shot empty-output recovery the retry path was designed for. Real (non-coerced) non-zero exits with empty output still route to `STATUS=FAILED` because the wrapper genuinely reported a failure. `build_missing_retry_sentinel_result` is the single source of truth for the missing-retry-sentinel result block and is exercised directly by `scripts/test-collect-agent-retry.sh` Case K; no executable-path override or other production retry seam is shipped.

**Empty-output retry deserializer prerequisites.** The inner `CMD_JSON` retry path requires `jq` (CMD_JSON validate + per-element decode via `jq -r '.[] | @base64'`) and `base64 -d` (the `-d` flag is portable across GNU coreutils, BSD/macOS, and BusyBox; `--decode` is rejected by BusyBox). The outer-launcher Cursor/Codex branch does not deserialize `CMD_JSON`, but it still requires `TIMEOUT=` and valid `OUTER_LAUNCHER*` path metadata before launch. `jq` is a hard repo prerequisite documented at the wrapper contract in `scripts/run-external-agent.md`; it is repeated here because the collector consumes that contract on a different code path. If either binary is unavailable at retry time, the inner retry path fails closed for that index by rewriting the original result to `STATUS=EMPTY_OUTPUT`. Missing, non-digit, or zero/zero-padded `TIMEOUT=` also fails closed for that reviewer before any retry arithmetic or launch. The retry-phase wait timeout starts with a 30s safety floor and then rises to the maximum queued `TIMEOUT+60`, so short reviewers do not inherit a fixed 180s wait while long reviewers keep their full grace window. Other indices in the same collector invocation that have valid metadata still launch retries; the per-`j` `RETRY_LAUNCHED` array preserves their fail-closed `FAILURE_REASON` strings against the post-wait result-update loop, and a `_decode_failed` flag in the deserializer skips the empty-array branch so a base64-decode failure surfaces as `Retry metadata invalid: CMD_JSON decode failed` rather than the misleading `empty CMD_JSON array after decode`. Distinct missing-key messages — `missing CMD_JSON and TOOL`, `missing CMD_JSON`, `missing TOOL`, `TIMEOUT missing`, and the `OUTER_LAUNCHER*` field-specific messages — narrow each `FAILURE_REASON` to the field actually absent or invalid.

## NOT_SUBSTANTIVE retry (section 3.7)

When `--substantive-validation` or `--structured-reviewer-validation` is passed and any entry is downgraded to `STATUS=NOT_SUBSTANTIVE` in sections 3.5 or 3.6, the collector attempts a one-shot retry with a stronger structured-output demand prepended to the reviewer prompt.

**Retry eligibility**: the entry must have a `.meta` sidecar at `<REVIEWER_FILE>.meta` with valid `OUTER_LAUNCHER`, `OUTER_LAUNCHER_PROMPT_FILE`, `OUTER_LAUNCHER_WORKDIR`, `TOOL`, and `TIMEOUT` fields. Only reviewer types that record an OUTER_LAUNCHER (cursor/codex specialist reviewers launched via `launch-review.sh`) are retried; entries without a `.meta` or without the OUTER_LAUNCHER field are skipped silently.

**Stronger prompt**: a structured-output demand header is prepended to a temp copy of the original prompt file. The header explicitly refuses narrative output and demands either structured `### FINDING_N:` blocks or `NO_ISSUES_FOUND`.

**Retry outcome**: the retry output is validated with `validate-research-output.sh` (same flags as section 3.5). If validation passes, the collector first attempts to copy the first-pass content of `<base>.txt` to `<base>-first-pass.txt` for observability. If that copy fails, the collector logs a stderr error and leaves the entry at `STATUS=NOT_SUBSTANTIVE` rather than overwriting the first-pass output. After a successful first-pass copy, the collector copies the validated retry body onto `<base>.txt` and keeps the original `<base>-ns-retry.txt` artifact on disk so committed round logs can recover both first-pass and retry transcripts. If publishing the validated retry body back to `<base>.txt` fails, the collector logs a stderr error, removes `<base>-first-pass.txt`, and leaves the entry at `STATUS=NOT_SUBSTANTIVE` so the tree does not imply a successful publish. For structured retries the sidecar (`.tsv` or `.jsonl`) is validated at the retry path first; after the prose publish succeeds, the collector best-effort copies that sidecar to the final `<base>.txt.{tsv,jsonl}` path. If the sidecar copy fails, stderr records the warning and `STRUCTURED_SIDECAR=` keeps pointing at the validated retry-path sidecar instead of naming a missing final-path file. If validation fails again, the entry keeps `STATUS=NOT_SUBSTANTIVE` and no sidecar is created.

**Temp prompt cleanup**: the temp prompt file is removed via a background wait-and-cleanup child after the retry process exits.

**NS_RETRY_REASON annotation**: at the moment of NOT_SUBSTANTIVE classification in sections 3.5 and 3.6, the collector derives an `NS_RETRY_REASON` token from the `validate-research-output.sh` exit code and records it in the pipe-delimited RESULTS entry. After waiting for the retry, the token is appended as `NS_RETRY_REASON=<token>` to `<base>-ns-retry.txt.meta` (best-effort, skipped when the meta file is absent or is a symlink). Token vocabulary: `NO_ISSUES_FOUND_TOO_THIN` (exit 2 or 3 from substantive mode — body too thin or no provenance marker); `OUTPUT_EMPTY` (exit 4 — file missing or unreadable); `JSON_PARSE_FAIL` (exit 5 in structured mode — structured records not found); `UNKNOWN` (fallback for unmapped exits).

## Structured reviewer validation (`--structured-reviewer-validation`)

When `--structured-reviewer-validation` is passed, the collector adds a Section 3.6 pass after substantive validation for each `STATUS=OK` entry. This flag is used for renderer-backed specialist slots (e.g., Cursor and Codex plan-review archetype slots in `skills/design/references/plan-review.md`) that emit JSONL/TSV structured records alongside prose output. Generic external reviewer slots launched with inline prompts are NOT wired to this flag.

**Section 3.6 — structured sidecar validation**:
1. Derive the sidecar path: `<REVIEWER_FILE>.jsonl` for Claude-path outputs, `<REVIEWER_FILE>.tsv` for specialist (Cursor/Codex external) outputs.
2. Invoke `validate-research-output.sh --structured-reviewer-mode --write-structured <sidecar-path>` on the REVIEWER_FILE.
3. On exit 0: emit `STRUCTURED_SIDECAR=<sidecar-path>` as a new field appended before `FAILURE_REASON`. The output grammar is `REVIEWER_FILE|TOOL|STATUS|EXIT_CODE|STRUCTURED_SIDECAR|FAILURE_REASON`. Consumers should parse by KEY=value.
4. On exit 5 or non-zero: rewrite the entry to `STATUS=NOT_SUBSTANTIVE` with a diagnostic in `FAILURE_REASON`.

**Callers wired**: `skills/design/references/plan-review.md` Step 3 collect call for all archetype slots (Cursor and Codex: `cursor-plan-arch-output.txt`, `cursor-plan-edge-output.txt`, `codex-primary-plan-innovation-output.txt`, `codex-primary-plan-pragmatic-output.txt`, and their cross-tool fallback variants). Generic reviewer slots in `skills/review/SKILL.md` and `skills/research/references/validation-phase.md` are NOT wired and continue with `--substantive-validation --validation-mode` only.

On non-zero exit, `FAILURE_LOG=<path>` may appear on stdout.
