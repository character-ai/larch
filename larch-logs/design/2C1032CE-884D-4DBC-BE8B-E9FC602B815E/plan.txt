## Approach

Keep the change narrow.

First, move only the shared vendor-row column-count literal into `python/larch/report/timing.py`. This matches the approved outline and keeps the constant near timing-ledger task/vendor definitions. Do not move unrelated column index constants.

Second, treat `gate-b-apply` as an apply lane for row-cap purposes. The label already exists. The missing piece is only membership in `_CODER_APPLY_TASK_KINDS`.

Third, add direct tests around the private helper because the current coverage exercises only the happy path through `_write_design_round_meta`. Use direct helper tests for boundary behavior and one integration-style test for no-vendor rows.

Do not implement the excluded issue items:
- No per-attempt design round timing rows.
- No flock-timeout retry or `execution-issues` surfacing.
- No public Gate B helper export or module restructuring.

## Edge cases

- A ledger with no readable vendor rows must not invent a Gate B apply span.
- A vendor row ending exactly at `end_s` leaves no positive Gate B apply window.
- A vendor row ending after `end_s` must not produce a negative or clamped apply span.
- A duplicate `gate-b-apply-round-N.out` row must keep idempotency.
- Row-cap logic must keep total rows at `PROGRESS_GANTT_ROW_CAP` while preserving `gate-b/apply`.

## Failure modes

1. **Constant import drift**
   - Warning signal: pyright or import errors in `progress_report.py` or `plan_review_loop.py`.
   - Mitigation: import only from `larch.report.timing`, which both modules already depend on or can safely depend on.

2. **Gate B row still disappears under cap**
   - Warning signal: new cap regression test fails or rendered phase detail lacks `gate-b/apply`.
   - Mitigation: ensure `_progress_vendor_rows` marks `kind in _CODER_APPLY_TASK_KINDS` after deriving the row kind.

3. **Unreadable-ledger test is platform-flaky**
   - Warning signal: test passes locally but fails in CI due to permissions behavior.
   - Mitigation: monkeypatch `Path.read_text` for the target ledger to raise `OSError` instead of relying only on chmod.
