# Implementation Plan — ship-pr → Python Phase 3: Rebase component

Create `python/rebase.py`: a pure, idempotent rebase component that brings the feature
branch up to date on `origin/main`, deterministically auto-resolves trivial/bump-only/
CHANGELOG conflicts, drops the stale bump (+ companion CHANGELOG) commit before replay,
runs an in-process fixer-agent waterfall for non-trivial conflicts, re-classifies/re-bumps,
and force-pushes with lease. The module returns a typed `StepResult`/`Outcome` and raises
`NeedsUserInput`/`Stalled` on exhaustion. No persisted state machine; recovery is from
git/gh ground truth (locked decision #1). No live `/implement` wiring (locked decision #2).

## Approach
- Reimplement logic in Python; shell out only to `git`/agent CLIs through the injected `Runner`
  (locked decision #3). Reuse the Phase 1/2 surfaces (`changelog.auto_resolve`,
  `version_bump.*`, `bump_worktree.*`, `git.*`, `agents.run_waterfall`) — do not re-implement them.
- The fixer is **full and in-process** (Round 1 decision): rebase.py builds the conflict prompt,
  runs the waterfall, then verifies the tree and continues the rebase. Tests inject a stub
  `launch_fn`, so no real agent runs.
- Idempotent and stateless: every decision (what to drop, whether already fresh, how many attempts)
  reads from git ground truth. No `REBASE_COUNT` file, no resume flags, no `record_failure`
  issue-logging, no larch-logs fixup — those stay with the future `ship.py` driver.
- Escalation is by return value: uncertain conflicts the waterfall cannot clear → `NeedsUserInput`;
  attempt-cap / unrecoverable git state → `Stalled`. The component never prompts or exits the process.

## Edge cases
- Detached HEAD before rebase → `Stalled` via `try_current_branch` (no `ShipError` leak).
- `drop_bump_commit` returns `dropped=False` with a real error (dirty tree, parent missing) →
  `Stalled`; "no bump commit found" is benign (nothing to drop) → continue.
- Companion changelog drop uses versioned `changelog.drop_changelog_commit`; guarded
  `dropped=False` → `Stalled` (prevents #2952 replay loop).
- Re-bump always ends with `_commit_changelog_after_rebump` after `apply_bump` (plugin.json-only
  bump commit is insufficient for push parity).
- HEAD already contains `base_target` → already-fresh short-circuit (skip rebase, still re-bump+push
  in push mode).
- Fork mode: `PUSH_REMOTE` ≠ `base_remote`; resolve via per-branch pushRemote/remote config.
- Force-push lease rejected but remote tip already equals local HEAD (a prior attempt landed) →
  treat as success.
- Multi-hop rebase: a later replayed commit conflicts after a clean resolution → re-enumerate the
  fresh unmerged-path list each `--continue` iteration (never reuse the stale list).
- Empty/already-applied commit during `--continue` → `git rebase --skip`, then retry.

## Failure modes
- **Stale-bump replay loop** — dropping the bump but not its companion CHANGELOG commit would replay
  `Update CHANGELOG …` forever. Signal: `drop_replay_commit` returns non-None or the CHANGELOG
  subject reappears. Mitigation: versioned `changelog.drop_changelog_commit` after bullet extract;
  `Stalled` if the companion drop fails (not generic subject-depth replay).
- **Bump without CHANGELOG tail** — `apply_bump` alone leaves no `Update CHANGELOG for NEW` commit.
  Mitigation: `_commit_changelog_after_rebump` with bullets / `replaces_version` fallback; `Stalled` on failure.
- **Lease overwrite of a concurrent runner** — refreshing the lease OID across retries could clobber
  another push. Signal: lease rejection after a remote-tip change. Mitigation: compute
  `EXPECTED_REMOTE_OID` once and reuse it across retries (bash parity), short-circuit on tip==HEAD.
- **Infinite rebase storm** — repeated `ACTION=rebase` triggers. Signal: attempt count ≥
  `REBASE_MAX_ATTEMPTS`. Mitigation: hard cap derived from git state → `Stalled`.

## Testing strategy
- Colocated `python/test_rebase.py` with a stub `proc.Runner` (scripted per-argv `CommandResult`)
  and a stub `launch_fn` returning canned `TierAttempt`s. Cover every deterministic path, the
  waterfall win/exhaust branches, `REBASE_MAX_ATTEMPTS` cap, multi-hop `--continue`, and the
  force-push lease/retry argv.
- Extend `python/test_git.py` for the five new git helpers (`try_current_branch`, `is_ancestor`,
  plus the three rebase/push helpers).
- Bars: `make py-lint` (ruff + pylint + pyright) and `make py-test` green; `test_stdlib_only.py`
  still passes (rebase.py imports stdlib + sibling modules only). No twin-repo harness against the
  embedded `run_rebase_rebump` (Round 1 decision: deterministic-path parity via unit tests).

## Shared context (applies to every phase)

**Why this exists.** `scripts/ship-pr.sh` (~3,400 lines) is the `/implement` post-review state machine (rebase → checks → bump → PR → CI → merge → post-merge). **Locked architecture decisions:**
1. **Single idempotent process** — recovery via gh/git **ground truth**, NOT a persisted state file. No `ship-pr-state.sh`, no `--resume-phase`.

## Phase 3 — Rebase component

A large, stateful unit: bring the feature branch up to date on `origin/main` and recover from conflicts autonomously. This is the first step of the top-level flow (and the `GOTO Rebase` target of the CI-monitor loop).

### Module to create
- **`rebase.py`**
  - rebase the branch onto `origin/main`;
  - **deterministic auto-resolve** of trivial / bump-only / CHANGELOG / auto-generated conflicts (uses `changelog.py` from Phase 2);
  - **drop the stale bump commit** (and its companion `Update CHANGELOG …` commit) before replay;
  - for **non-trivial conflicts**, invoke the **fixer-agent waterfall** in-process to resolve them — replacing today's bounce out to the LLM orchestrator via `conflict-resolution.md`;
  - **re-classify / re-bump** after a successful rebase (uses `version_bump.py`);
  - **force-push-with-lease**;
  - a **cap** on rebase attempts (escalate to `Stalled`/`NeedsUserInput` on exhaustion).

### `.sh` to port / read
`rebase-push.sh`, the `run_rebase_rebump` function in `ship-pr.sh`, `auto-resolve-changelog.sh` (shared with Phase 2), and the `conflict-resolution.md` procedure (the parts that are deterministic vs. the parts now handled by the in-process fixer).

### Acceptance criteria
- Parity vs `rebase-push.sh` for the deterministic paths.
- Conflict-fixer path exercised with a **stub agent waterfall** (no real `cursor`/`codex`/`claude`).
- Drop-bump / drop-changelog replay correctness; attempt-cap enforcement.
