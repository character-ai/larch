**Architectural approach.** The cleanest integration treats `manual_gate_b` as a *third* sticky run-parameter boolean that mirrors the precedent of `partition_requested` / `brainstorm_requested`: parse `--manual` / `-m` in the same argv pre-parser that already produces flags for `write-run-params.sh`, forward it as `--manual-gate-b true|false` to that script, and persist it under a new `manual_gate_b` key in `run-params.json`. Every Gate B entry then reads `manual_gate_b` from `run-params.json` (single source of truth, so Step 3 re-entries from Gate C(c) "Re-run review panel" automatically inherit the same mode without re-prompting). The Gate B prompt section in `approval-gates.md` gets a leading branch: **if `manual_gate_b == true`** → unchanged 3-option `AskUserQuestion` (Apply all / Go through each / Switch to discussion mode); **else (default, auto-apply)** → execute the existing "Apply all" body verbatim, but preceded by the new compact findings table and the `🔶 /design 3.5: gate B (auto-apply N findings)` breadcrumb and with no prompt. Critically, the auto-apply branch funnels into the *same* downstream pipeline that "Apply all" already uses today — dedup-sweep → `dedup-sweep: removed <N> duplicate line(s) from plan.txt` breadcrumb → `ACTION=EMIT_PLAN` → `invoke-plan-validator-if-not-quick.sh` (when `review_budget=full`) → Step 2b.5 plan-size threshold → Step 3b → Step 4 → Step 4b (Gate C). That keeps every existing invariant intact because we are reusing the "Apply all" code path, not forking it. The zero-findings short-circuit (`accepted-plan-findings.md` empty → "nothing to apply" breadcrumb → Step 3b) is untouched in both modes, and Gate C's three options (Approve / Discuss further / Re-run review panel) remain the user's mid-flow escape hatch for everything auto-applied.

**Files to modify.** Five surfaces, ordered by load-bearing weight: (1) `scripts/write-run-params.sh` — add `--manual-gate-b` flag with `require_enum ... true false`, a `MANUAL_GATE_B` variable, the `--arg manual_gate_b "${MANUAL_GATE_B:-false}"` jq binding, and `manual_gate_b: ($manual_gate_b == "true")` in the emitted JSON, exactly paralleling the two existing booleans. (2) `skills/design/references/approval-gates.md` — the Gate B "Prompt" subsection gets the mode branch described above, the new compact findings list (`FINDING_N, severity, reviewer, concern excerpt`) for the auto-apply path, the new breadcrumb spec, and **State Invariant #4 is rewritten** from "No-auto-apply contract" to something like "Gate B apply contract: in default (auto-apply) mode, every accepted in-scope finding is applied without prompting after the compact findings list and auto-apply breadcrumb; in `--manual` mode the user must explicitly pick (a) or (b) for any plan revision. Gate A and Gate C never auto-revise `plan.txt`. The tally script still writes artifact files only." (3) `skills/design/SKILL.md` — argv parsing block gains `--manual`/`-m` recognition, sets `MANUAL_GATE_B=true`, forwards it to `write-run-params.sh`; the public flag table near the top of SKILL.md gets a one-line entry. (4) `skills/design/references/flags.md` — full per-flag documentation entry for `--manual`/`-m` explaining scope ("Gate B only — Gate A and Gate C unchanged"), default behavior change, and sticky-across-Step-3-re-entries semantics. (5) Any test fixture under `scripts/test-*.sh` that asserts on `run-params.json` schema (the `partition_requested`/`brainstorm_requested` precedent tests) will need a `manual_gate_b: false` default-case update — grep `test-write-run-params` or similar before final commit. SKILL.md and approval-gates.md are the only places that need to agree on the *behavioral* semantics; everything else is mechanical wiring.

**Tradeoffs and risks.** The dominant drift risk is exactly the SKILL.md ↔ approval-gates.md axis: SKILL.md Step 3.5 currently delegates entirely to `approval-gates.md` for Gate B semantics, so as long as the new branch lives only in `approval-gates.md` and SKILL.md just adds `--manual` to the argv table plus a one-sentence pointer ("Gate B behavior, including auto-apply default and `--manual` opt-out, is normative in `approval-gates.md` §Gate B"), drift stays bounded. The secondary risk is **run-params.json fallback recovery**: if a stale or upgrade-mid-flight `run-params.json` lacks the `manual_gate_b` key, every Gate B reader must coerce missing/`null` to `false` (auto-apply) — this should be a single defensive `jq -r '.manual_gate_b // false'` idiom used at every read site, matching how the existing booleans behave on absent keys. On **Step 3 re-entry from Gate C(c)**: because `manual_gate_b` is whole-run sticky in `run-params.json` and Gate B reads from that file on every entry (not from in-memory state), re-entries Just Work; the only subtle case is a user who started without `--manual`, hit auto-apply, then on Gate C(c) wants finer control — they cannot get it mid-run, which is by design per the settled Round 1 decision (Gate C "Discuss further" is the documented escape valve, not mode-switching). Finally, the compact findings list adds a small amount of pre-prompt output even in the silent auto-apply path; this is intentional (apply visibility) but increases the chance of operators conflating "list shown" with "prompt coming" — the breadcrumb wording `🔶 /design 3.5: gate B (auto-apply N findings)` should be unambiguous on that, and #2667's later Gate B multi-round presentation work (blocked-by this issue) can refine the visual cue if needed.
