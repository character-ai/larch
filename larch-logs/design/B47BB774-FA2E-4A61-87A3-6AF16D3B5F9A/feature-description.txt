# [BUG] /implement Step 5 review panel-failed despite completed reviewers; stalls run…

## Summary

`/implement` Step 5 code review can return `panel-failed` and hard-stall the run even though all reviewers complete and produce parseable output. Observed on plugin **v51.1.0**, run `3C3F080B-365B-4B00-A891-F1CD01DE9B96` (issue #4547): the 10-slot panel (6 static + 4 dynamic) all ran to completion, "consolidating findings" printed, then `STEP5_REVIEW_STATUS=stall STALL_REASON=panel-failed` with a 0/0/0 tally. The committed run log shows the panel produced 7 parseable findings and `Reviewer slot failures: 0`, so the panel did not actually lose its reviewers — the consolidation/threshold gate reported zero successful slots anyway. Step 18a stall recovery then classified the stall `transient-infra` and dispatched `step8-shippr`, creating a non-merged PR (#4603) and silently downgrading the operator's `--merge` to `pr-created`.

## Original report

review panel failure

(Filed from a live `/implement --merge` run on issue #4547. The Step 5 code-review panel stalled the run with `panel-failed`; this issue captures the observed mechanism, supporting evidence from the committed run log, and the downstream recovery downgrade.)

## Reproduction scenario

Not deterministically reproducible (panel/collector outcome depends on reviewer output shape and stochastic format adherence). Observed scenario:

1. Run `/implement --merge <issue>` (here: `/im 4547`). Step 2 (Codex) implements and commits; Step 3 checks pass.
2. Step 5 launches the code-review panel: `→ review: launching 10 reviewers (3 Cursor static, 3 Codex static, 4 dynamic)`.
3. All 10 reviewers run to completion (round-1 timing window 0:00–11:41; per-slot 251s–700s).
4. `→ review: consolidating findings` prints, then the wrapper returns `STEP5_REVIEW_STATUS=stall`, `STALL_REASON=panel-failed`, `ROUNDS_COMPLETED=1`, `FINAL_REVIEW_AND_FIX_STATUS=panel-failed`.
5. `/implement` follows the Step 5 `stall` branch (seed `ship-pr-state.sh`, skip to Step 16), then Step 18a classifies `transient-infra` / `RESUME_HINT=step8-shippr` and reships → PR created without merge.

The exact gate input (`collector-results.env` / `review-core-threshold.env`) could **not** be re-confirmed after the run because those files live only in the session tmpdir and are removed at Step 18 teardown (see Observability gap below).

## Expected behavior

- When the reviewer panel launches and the reviewers run to completion and produce parseable output (even if only out-of-scope observations), consolidation should succeed and the round should complete (zero in-scope findings is a valid "clean" review), not hard-stall the whole run as `panel-failed`.
- A `panel-failed` that the run summary itself records as `Reviewer slot failures: 0` is internally inconsistent: the panel-failure accounting and the summary's slot-failure accounting should agree.
- A transient review-panel/consolidation failure should not silently convert an explicit `--merge` request into a non-merged `pr-created` outcome; if it must, the downgrade should be loud and unambiguous to the operator (not just visible in the tracking-issue summary).

## Observed behavior

- `REVIEW_CORE_STATUS=panel-failed` after the consolidation step; the entire `/implement` run stalled at Step 5.
- `code-review-tally.json`: `accepted_count=0, rejected_count=0, exonerated_count=0` (the `panel-failed` path writes a zero tally).
- `review-findings-full.jsonl`: 7 records, **all** `"outcome":"out_of_scope"` — i.e. reviewers produced parseable findings, just no in-scope ones.
- `final-summary.md`: `**Reviewer slot failures**: 0`.
- Recovery: Step 18a classifier → `FAILURE_CLASS=transient-infra`, `MATCHED_CLASSIFIER_PATTERN=transient-output`, `RESUME_HINT=step8-shippr`; the reship created PR #4603 with `merge_result=""` (no merge, because the stall profile forces `MERGE=false`). Final outcome `pr-created` rather than the requested merge.

## Root cause analysis

Two `panel-failed` exits exist in `python/legacy_review_shell/review-core.sh`:

- Line ~737: dispatch failed (zero reviewers launched). Fires **before** "consolidating findings".
- Lines ~902–932: the reviewer-failure **threshold gate** returned `THRESHOLD_OK=false`. Fires **after** "consolidating findings".

This run printed "consolidating findings", so it took the **threshold-gate** path. `THRESHOLD_OK` can be set false by three sub-conditions:

1. `FAILED_SLOTS >= 50%+1` of intended static slots (`check-reviewer-failure-threshold.sh:245-251`; `NOT_SUBSTANTIVE` slots count as failed).
2. `launched_success_count == 0` — "no successful launched reviewer output" (`review-core.sh:876-888`, derived from `collector_success_count` over `collector-results.env`).
3. static archetype coverage gate failed (`review-core.sh:889-901`).

**Inference (not proven from committed artifacts):** sub-condition 2 is the most likely trigger here. `round-meta.json` records `"collector": ""` (empty collector record) and `final-summary.md` reports `Reviewer slot failures: 0` — together suggesting the collector did not surface any successful per-slot record (`collector_success_count == 0`), which trips the "no successful launched reviewer output" gate even though the reviewers ran and 7 OOS findings were later aggregated and filed (issue #4602). A plausible contributing factor: the static reviewers emitted only out-of-scope observations / no in-scope structured findings, and that output shape is treated as non-substantive/unsuccessful per slot.

This is in the same subsystem that issue #4547 is changing (the reviewer **collector** + failure-threshold), but it is a distinct defect: #4547 reworks `NOT_SUBSTANTIVE` retry/tally handling, whereas this is a consolidation-accounting failure where the panel is declared failed despite completed reviewers and parseable output. `NOT_SUBSTANTIVE` slots will still count toward the >50% threshold after #4547, so #4547 does not obviously fix this.

Separately, the stall classifier mapping `panel-failed` → `transient-infra` → `step8-shippr` is a deliberate degraded path, but its side effect — silently turning `--merge` into a non-merged PR — is surprising for the operator.

## Affected files

- `python/legacy_review_shell/review-core.sh` — emits `REVIEW_CORE_STATUS=panel-failed`; owns the post-consolidation threshold gate and the `launched_success_count==0` ("no successful launched reviewer output") check. Primary site for the inconsistency between "0 slot failures" and `panel-failed`.
- `python/legacy_review_shell/check-reviewer-failure-threshold.sh` — `THRESHOLD_OK` / `FAILED_SLOTS` / `NOT_SUBSTANTIVE_SLOTS` accounting and the >50% rule; relevant to whether an all-OOS / no-in-scope round should count as failed slots.
- `python/legacy_review_shell/collect-findings.sh` and `python/collect_results.py` — produce `collector-results.env`; the empty `"collector"` field in `round-meta.json` suggests the collector record was empty/absent for this round.
- `python/review_and_fix.py` — maps `REVIEW_CORE_STATUS=panel-failed` to `STEP5_REVIEW_STATUS=stall` / `STALL_REASON=panel-failed`.
- `python/stall_recovery.py` (+ `skills/implement/scripts/stall-recovery-report.*`) — classifies `panel-failed` as `transient-infra` with `RESUME_HINT=step8-shippr`, the path that downgrades `--merge` to a non-merged PR.
- Run-log composition for `round-meta.json` / `round-1/` — does not commit `collector-results.env` / `review-core-threshold.env`, blocking post-hoc root-cause (observability gap).

## Suggested fix(es)

No single confirmed fix; candidate directions:

1. **Reconcile the accounting.** A round the run summary records as `Reviewer slot failures: 0` should not also be `panel-failed`. Make the `launched_success_count==0` / coverage gate use the same slot-success accounting the summary uses, or surface the specific `THRESHOLD_REASON` into the stall so it is visible.
2. **Treat an all-out-of-scope / zero-in-scope round as a successful (clean) review** rather than a panel failure, provided reviewers completed and produced parseable output. Zero in-scope findings is a normal outcome.
3. **Commit the panel-failed determination inputs** (`collector-results.env`, `review-core-threshold.env`, or a distilled `THRESHOLD_REASON` / per-slot status table) into the run log so a `panel-failed` is root-causable after Step 18 teardown.
4. **Make the `--merge` → `pr-created` downgrade explicit.** When stall recovery ships via `step8-shippr` after a review-panel stall, emit a loud operator warning (and/or distinct outcome label) so it is clear the requested auto-merge did not happen and the PR needs manual review/merge.
5. Investigate why `collector_success_count` was 0 while 7 OOS findings were aggregated — i.e. whether the collector dropped/blanked per-slot success records for output that contained only out-of-scope observations.
