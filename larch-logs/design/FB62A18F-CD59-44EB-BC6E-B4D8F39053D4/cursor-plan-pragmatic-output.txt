**1. `/implement` both-down hard-fail lacks a pinned routing contract** (`python/bootstrap.py:1359-1474`, risk-integration, blocking)

The plan pins `/design` termination via `STEP0_STATUS=degraded-both-down-hard-fail` and `DEGRADED_HARD_FAIL=true`, but the `/implement` section only says “hard-fail both-down in all modes” without naming the bootstrap stdout key or the Step 0 routing row. Today `_run_absorbed_continue_tail` can still write `.degraded-tools-gate-prompted` and continue to `1.r` when `both_down=true` and `non_interactive=true` (lines 1444-1450). That violates issue requirement #2.

**Suggested revision:** Add `DEGRADED_HARD_FAIL=true` (or `IMPLEMENT_BAIL_REASON=both-vendors-down`) to `ROUTING_KEYS`, emit it from the absorbed tail on both-down in every mode, and add an explicit implement SKILL Step 0 routing branch that stops before `1.r` (Step 18 or exit 2), parallel to design’s hard-fail status.

**2. Absorbed tail still auto-creates the continue sentinel** (`python/bootstrap.py:1437-1450`, correctness, important)

The plan’s edge cases require that only an explicit operator **Continue** may create `.degraded-tools-gate-prompted`, and that non-interactive one-down without a sentinel must not auto-proceed. Current bootstrap code still calls `_write_degraded_sentinel` on one-down non-interactive paths (lines 1441-1443). `design-step0-session.sh` has the same bug for one-down (lines 208-210: sentinel written before any prompt).

**Suggested revision:** In both `bootstrap.py` and `design-step0-session.sh`, delete sentinel creation from one-down/both-down detection branches. Create the sentinel only after operator **Continue**. For non-interactive one-down without a prior sentinel, fail closed instead of proceeding.

**3. Resume degraded gate must not consume stripped session-env presence** (`python/bootstrap.py:1371-1391`, correctness, important)

The plan’s approach says resume must not call the degraded gate with missing probe values from stripped session env, but the absorbed tail still binds `st.codex_present` / `st.cursor_present` from session data before calling `degraded-tools-gate`. After `session_env.py` stops persisting those keys, empty presence can trigger `PRESENCE_INPUT_EMPTY` or fail-safe “both down” and block runs where binaries exist.

**Suggested revision:** In the absorbed tail, rerun a private `check-reviewers` probe (same as initial Step 0) and pass that stdout’s `CODEX_PRESENT` / `CURSOR_PRESENT` into `agent degraded-tools-gate`. Use session env only for `CODEX_BINARY_FOUND` / `CURSOR_BINARY_FOUND`.
