# [Bug] Codex bail `protected-path-edit-required-out-of-scope` misclassified as `transient-infra`

### [Bug] Codex bail `protected-path-edit-required-out-of-scope` misclassified as `transient-infra`

## Context

Run `D0D24DD6-D277-4091-A967-DE35D3454893` (issue #4019): Codex bailed with `REASON=protected-path-edit-required-out-of-scope` because the implementation plan requires editing `.claude-plugin/plugin.json`, which Codex's sandbox explicitly forbids.

## Root cause

`stall-recovery-report.sh classify` maps `protected-path-edit-required-out-of-scope` to `FAILURE_CLASS=transient-infra` and `RESUME_HINT=step2-impl` (main agent implements inline). This classification is wrong: the protected-path restriction is a **permanent Codex sandbox policy** — it will never succeed on retry with the same Codex coder. It is not a transient network/infra failure.

The `step2-impl` hint causes the main agent to implement all changes inline. For large plans (100+ files), this consumes enormous context and is slow. The correct dispatch for a protected-path bail should instead be `RESUME_HINT=step2-impl` only when the plan does require protected-path edits that the main agent can make, but the classification should be more specific so operators know what's happening.

## Suggested fix

In `stall-recovery-report.sh` (or its allowlists TSV), add a distinct classification for `protected-path-edit-required-out-of-scope`:

- `FAILURE_CLASS=protected-path` (not `transient-infra`)
- `RESUME_HINT=step2-impl` (correct — main agent can edit protected paths)
- A warning displayed to the operator that Codex bailed on a protected path and main Claude will implement

This prevents the misleading "transient-infra" label while preserving the correct recovery dispatch. The retry cap for `protected-path` should be 1 (no point retrying Codex on a permanent ban), and the first-detection message should clarify the protected path name.
