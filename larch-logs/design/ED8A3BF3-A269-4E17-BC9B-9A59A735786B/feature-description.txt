# Redesign /implement OOS filing pipeline: post-ship-pr Python script, no PR-body…

## Summary

Three required changes to the `/implement` OOS filing pipeline, plus three additional bugs found during investigation of the silent-OOS-drop root cause.

---

## Required changes

### 1. Remove OOS URL weaving from PR body

Any existing path in `/implement` (or any helper it calls) that injects filed OOS issue URLs into the PR body must be removed. OOS always stays OOS — it is never folded into the current PR's body or referenced as "related work" in the PR description. This is a hard invariant.

Audit `scripts/compose-pr-summary.sh`, `python/pr_body.py`, and any path through `create-pr.sh` / `ship.py` that could include OOS URLs in the PR body.

### 2. Add a post-ship-pr Python step that files OOS issues

After `python/cli.py ship pr` returns `outcome=OK`, the orchestrator must hand off to a new Python script (not prompt-side `.md` instructions) that reads the accumulated OOS markdown files (`oos-accepted-review.md`, `oos-accepted-main-agent.md`) and files the accepted items as GitHub issues. The script should:

- Be callable standalone and testable
- Own the full OOS pipeline currently documented as prose in `SKILL.md` Steps 9a/9a.1 and `skills/implement/references/oos-pipeline.md`
- Live as a `python/cli.py oos file` subcommand (or similar)
- The Python ship driver (`python/ship.py`) is NOT modified — it remains a pure shipping machine with zero OOS knowledge

The orchestrator's Step 8+ Exit 0 handling for the Python path changes from "go to Step 16" to "check for accumulated OOS files; if present run `python/cli.py oos file`; then go to Step 16".

### 3. Add aggressive Codex-powered combining before filing

When accumulated OOS items total more than one, the Python OOS filer must invoke a Codex agent (before calling `/issue`) to aggressively combine the items into a smaller set — ideally one issue if reasonable. The combining step must be strongly biased toward merging: the prompt should instruct Codex to consolidate unless items are clearly unrelated. The combined output replaces the individual items as input to `/issue` batch mode.

This ensures OOS never generates unnecessary issue sprawl.

---

## Additional bugs found during investigation

### 4. Dead documentation path: `Exit 3: needs_user_reason=oos-filing`

`SKILL.md`'s Step 8+ Python driver selector documents `Exit 3: needs_user_reason=oos-filing` as triggering the OOS pipeline on the Python path. But `python/ship.py` and `python/config.py` have **zero** `oos-filing` code — grep returns no matches. This documented exit path is completely unimplemented and was presumably never wired up. The documentation should be cleaned up alongside the fix: remove the `oos-filing` branch from the SKILL.md Python exit-3 routing table, since the fix moves OOS filing to after `outcome=OK` (not as an Exit 3 handoff).

### 5. Misleading `OOS_PENDING=false` in state seed

The orchestrator seeds `OOS_PENDING=false` in the initial `ship-pr-state.sh` before calling ship.py. Since `ship.py` never reads this key (confirmed: zero OOS mentions in `python/ship.py`), the seeding is harmless but misleading — an operator might think setting it to `true` would trigger OOS filing, but it would not. The `OOS_PENDING` key in the state file is bash-path-only. On the Python path, accumulated OOS files should be detected directly by the post-ship-pr Python script.

### 6. `steps_ran={}` in committed manifest when OOS steps are skipped

When OOS steps never run (Python path, `OOS_PENDING` always false), the committed `manifest.json` emits `steps_ran: {}` (empty object) instead of explicit `"step9a1": false`. This violates the bail-time `steps_ran` invariant documented in SKILL.md: "write-final-report.sh records explicit `steps_ran.step9a1=false` ... for terminal non-merge outcomes." The empty object is ambiguous for downstream audit tooling (`audit-scan-run.sh` and `verify-run-log-completeness.sh` treat missing/null as the empty-object bail path, but the invariant still requires explicit false entries). Fix: ensure `write-final-report.sh` always emits `step9a1=false` when the OOS gate never ran.

---

## Root cause summary

On the Python ship path, `python/ship.py` has zero OOS knowledge. It goes straight from pr-prep to PR creation to CI to merge in one shot, with no pause point for OOS. The documented `Exit 3: oos-filing` path in SKILL.md was never implemented in ship.py. As a result, every `/implement` run on the Python path silently drops all accepted OOS items from the review panel.

## Affected files (approximate)

- `python/` — new OOS-filer script / `python/cli.py oos file` subcommand
- `python/file_oos.py` — extend with post-ship filing and Codex combine logic
- `python/cli.py` — add subcommand entry point
- `python/ship.py` — no changes (pure shipping machine)
- `skills/implement/SKILL.md` — update Step 8+ Exit 0 Python path; remove dead `oos-filing` Exit 3 branch
- `skills/implement/references/oos-pipeline.md` — retire or reduce to bash-path-only
- `scripts/write-final-report.sh` / `python/report.py` — emit `step9a1=false` when OOS gate never ran
- `scripts/compose-pr-summary.sh` / `python/pr_body.py` — audit and remove any OOS URL injection

## Acceptance

- After `python/cli.py ship pr` returns `outcome=OK`, accumulated OOS items are filed by a Python script, not by orchestrator prose.
- When there are 2+ accepted OOS items, a Codex agent combine pass runs first and reduces them to the smallest reasonable set.
- The PR body contains no references to filed OOS issue URLs.
- `manifest.json` emits `steps_ran.step9a1=false` (not `{}`) when the OOS gate does not run.
- The `oos-filing` Exit 3 branch is removed from SKILL.md Python routing.
- The new Python OOS filer has its own test coverage (`make lint` + `make py-test` pass).
- `/implement` runs that previously dropped OOS silently now file them.
