## Implementation Plan — #3209: drop-bump-commit.sh stall on dirty tree during CI+merge loop

Fix the spurious `run_rebase_rebump` stall two ways (Option A + B), without changing `drop-bump-commit.sh` or its guards.

- **Option A (catch-all at the stall site):** in `ship-pr.sh` `run_rebase_rebump`, commit leftover tracked files before `drop-bump-commit.sh` so Guard 1 cannot fire on a dirty tree.
- **Option B (root-cause hardening):** in `review-and-fix.sh` round mode, re-check the tracked tree after the round commit and commit once more if a pre-commit hook re-dirtied it.

## Approach

Defense in depth. Option A makes `run_rebase_rebump` self-healing for any dirty-tracked-tree precondition regardless of source (recovery agent, hook, or timing window) — this alone fixes the reported stall. Option B removes the most likely upstream source (a pre-commit hook leaving tracked files dirty after the round commit) so the dirty tree rarely reaches ship-pr in the first place. Both reuse `git-commit.sh` and the existing `git status --porcelain --untracked-files=no` idiom; neither introduces new flags, scripts, or abstractions.

Key decision: commit (not stash). Stashing then popping after `git rebase --onto` (the drop) or the rebase onto main can conflict against the rewritten tree; committing replays the leftovers cleanly and never loses them.

## Edge cases
- Clean tree at the drop site → Option A guard is false; no-op (the common case).
- Only staged changes (worktree clean, index dirty) → `git add -u` is a no-op but `git diff --cached --quiet` is false → fixup commit still lands.
- Deleted tracked files → `git add -u` stages the deletions → committed.
- New untracked files → excluded by both fixes (`--untracked-files=no`); Guard 1 already ignores them, so they never cause the stall.
- Option B, normal case (clean tree after round commit) → re-check is a no-op; `CODER_COMMIT_SHA` unchanged.
- Option B, findings mode (no `round_num`) → entire block skipped; parent-owned commit unchanged.

## Failure modes
1. **Fixup commit fails in Option A** (git error). Signal: non-zero from `git add -u`/`git-commit.sh`, captured to the rebase fail_file and recorded as a Warning. Mitigation: fall through to `drop-bump-commit.sh`, which stalls via Guard 1 exactly as before — no regression.
2. **Non-idempotent pre-commit hook in Option B** keeps re-dirtying the tree. Signal: tree still dirty after the single follow-up; `larch_err` warning. Mitigation: no retry loop (would spin); Option A catches the residue at the ship-pr drop site.
3. **Fixup commit alters bump classification.** Mitigation: the leftover changes are legitimately part of the in-flight branch and should affect classification; the distinct commit subject avoids the bump/changelog drop regexes, so drop/rebase logic is unaffected.

## Testing strategy
- New `test-ship-pr.sh` case: dirty tracked tree before `run_rebase_rebump` → no stall, fixup commit lands, bump dropped + re-bumped.
- New `test-review-and-fix.sh` case: pre-commit hook re-dirties a tracked file in round mode → clean tree after apply, follow-up commit lands, `CODER_COMMIT_SHA` is the follow-up.
- Run `make lint` (equivalently `bash scripts/relevant-checks.sh`) repo-wide; both new harnesses pass via their `make` targets (`test-ship-pr`, `test-review-and-fix`).
- No change to `drop-bump-commit.sh` or `test-drop-bump-commit.sh`.
