### DECISION_1: Claude tier delivery mechanism for the ship-pr.sh recovery waterfall

- **Chosen**: Add a NEW narrow `scripts/launch-claude-ci.sh` next to the existing `scripts/launch-cursor-ci.sh` and `scripts/launch-codex-ci.sh`. Three siblings, clean separation of read-only `launch-claude-subprocess.sh` (reviewer/voter infra) from write-capable Claude CLI invocations for recovery work.
- **Alternative**: Extend the existing `scripts/launch-claude-subprocess.sh` with an opt-in writer mode (e.g., `--mode writer` or `--role recover`) so there is exactly one Claude launcher, one redaction path, one auth flow, one timing-ledger contract. Drops the read-only prompt prefix when the new mode is set; preserves single-responsibility on the auth/canonicalization side.
- **Tension**: Pragmatic/Safety + Innovation + Edge-cases all prefer a new launcher to avoid widening the documented read-only contract of `launch-claude-subprocess.sh` (security/blast-radius framing — that script's read-only invariant is currently a load-bearing safety property). Architecture/Standards prefers extending the existing one to avoid ~200 lines of duplicated argv parsing, canonicalization, EXTRA_ROOTS validation, control-char checks, and timing-ledger wiring (single-launcher maintainability framing). The 3-vs-1 split on launcher count maps onto a tension between "additive surface area is the smaller blast radius" versus "single source of truth for Claude invocation contract".
- **Impact**: High
- **Affected files**: `scripts/launch-claude-ci.sh` (NEW under chosen path), `scripts/launch-claude-ci.md` (NEW), `scripts/test-launch-claude-ci.sh` (NEW), `scripts/launch-claude-subprocess.sh` (extended under alternative path), `scripts/launch-claude-subprocess.md` (touched under alternative), `scripts/test-launch-claude-subprocess.sh` (touched under alternative), `scripts/ship-pr.sh` (consumer either way), `scripts/lib-timing-kinds.sh` (allow-list addition either way).

### DECISION_2: Local-reproduction verification mechanism

- **Chosen**: Script-level mandatory post-tier verification. Run `run-relevant-checks-captured.sh` after each waterfall tier for checks-class phases (run_checks_phase, lint-fix-loop derivatives). For pr-create 9b where no failed-CI log is available locally, use dry-run probes: `git push --dry-run` to validate push viability + `gh pr view --json state` to validate PR-create outcome. Vendor prompts carry text-level guidance ("reproduce the failed CI job locally, fix, verify locally, only THEN push"), but enforcement is script-side, not prompt-text-side.
- **Alternative**: Machine-readable proof KV envelope emitted by the vendor (`REPRO_CMD=...`, `REPRO_FAILED_BEFORE=true`, `VERIFY_CMD=...`, `VERIFY_PASSED_AFTER=true`) that `ship-pr.sh` parses and requires before accepting the tier's output. ship-pr.sh runs an independent verify pass (same `run-relevant-checks-captured.sh`) anyway, but the KV is the contract signal that the vendor actually ran the reproduction loop.
- **Tension**: Innovation argues prompt text drifts and that machine-readable proof is the only robust signal that the vendor did the work; Pragmatic argues that the post-launch verify pass already enforces the invariant and the KV layer adds parser surface for marginal gain. Edge and Architecture agree the script-level verify is the load-bearing check, but neither rejects the KV proposal — Edge specifically notes that local reproduction is asymmetric per phase, so a uniform KV contract may be over-fit to checks-class sites.
- **Impact**: Medium
- **Affected files**: `scripts/launch-cursor-ci.sh`, `scripts/launch-codex-ci.sh`, `scripts/launch-claude-ci.sh` (or `scripts/launch-claude-subprocess.sh` depending on DECISION_1), `scripts/ship-pr.sh`, `scripts/ship-pr.md`.

### DECISION_3: Apply local-reproduction invariant to EXISTING run_ci_fix_vendor

- **Chosen**: Yes — the local-reproduction invariant (constraint A) applies to ALL CI fix paths, including the existing `run_ci_fix_vendor` 3-vendor-attempt cycle. Implementation: prompt-level addition to the existing vendor launcher calls (no argv-shape change to `launch-cursor-ci.sh` / `launch-codex-ci.sh`) plus post-launch verify via the existing `run_checks_with_lint_fix_loop` call already in place. This is additive, not a restructure.
- **Alternative**: Strict interpretation of constraint C ("Do not restructure the existing 3-vendor-attempt cycle"). Leave `run_ci_fix_vendor` exactly as-is; only enforce constraint A on the new waterfall paths (run_checks_phase, run_pr_prep_phase, run_pr_create_phase, run_rebase_rebump non-bump conflict tier). Existing CI fix work goes through with current prompts unchanged.
- **Tension**: User constraint A says the invariant applies universally; user constraint C says no restructure. They can co-exist if the change is prompt + post-launch validation (the chosen path), but Pragmatic's reading is more cautious: any change to existing CI fix risks regressions in a heavily-used path. Edge frames this as "small behavior shift on existing run_ci_fix_vendor" that orchestrator-side flag tables must learn.
- **Impact**: Medium
- **Affected files**: `scripts/launch-cursor-ci.sh` (prompt text only), `scripts/launch-codex-ci.sh` (prompt text only), `scripts/ship-pr.sh:run_ci_fix_vendor` (post-launch verify already exists; no structural change).

### DECISION_4: Per-tier rollback mechanism

- **Chosen**: Dirty-tree-baseline + revert-on-tier-fail. Before each waterfall tier, capture `git rev-parse HEAD` baseline plus the tracked/untracked dirty-paths via the existing `capture_tracked_dirty_paths` / `capture_untracked_dirty_paths` helpers. After tier completes (success or failure), run `run-relevant-checks-captured.sh` (or phase-appropriate verify). On tier-verify failure, revert that tier's edits via `git checkout -- <tracked_delta>` for tracked changes and `rm <untracked_delta>` for untracked files, mirroring `lint-fix-loop.sh`'s `post_dispatch_forbidden_revert` pattern. Assert `git rev-parse HEAD == baseline_head` post-tier; if the tier committed, hard-fail with `head-changed-after-dispatch` (mirrors `lint-fix-loop.sh:273-275`).
- **Alternative**: Innovation's "tier produces a patch file" idea. Each tier writes a unified diff to `$IMPLEMENT_TMPDIR/recovery-waterfall/<phase>/<tier>.patch`; ship-pr.sh applies it, verifies, commits + pushes. Tier launchers are read-only; no half-fixes can leak into the working tree.
- **Tension**: Patch-file approach is architecturally cleaner (centralized mutation, vendor launchers stay read-only) but invasive: it changes the vendor `--role fix` / `--role resolve-conflict` contract (today the vendor commits/pushes; under the alternative the vendor must emit a patch only). Pragmatic and Edge both lean toward the chosen rollback pattern because it matches existing conventions and doesn't require vendor-contract changes; Innovation flags the patch-file approach as "probably too much for this issue" itself.
- **Impact**: Medium
- **Affected files**: `scripts/ship-pr.sh` (new waterfall function + tier helpers), `scripts/launch-cursor-ci.sh` / `scripts/launch-codex-ci.sh` / `scripts/launch-claude-ci.sh` (no change under chosen; vendor contract change under alternative).

### DECISION_5: Mid-waterfall crash-recovery state

- **Chosen**: NO new state keys. If `ship-pr.sh` crashes mid-waterfall (host crash, signal, etc.), the resumed run restarts the recovery from the Cursor tier. Wall-time cost of one extra Cursor attempt is acceptable; complexity savings (no schema additions, no resume routing, no "did the previous tier complete or not?" ambiguity) are large.
- **Alternative**: Add `RECOVERY_TIER` (cursor|codex|claude|""), `RECOVERY_PHASE` (checks|pr-prep|pr-create|rebase-nonbump|""), and `RECOVERY_ATTEMPT_COUNT` keys to ship-pr-state.sh. Each tier writes the state before launching and clears on success. On resume, skip tiers whose `RECOVERY_TIER_<NAME>_RESULT=succeeded-pending-verify` was recorded.
- **Tension**: Edge argues crash recovery is required for reliability and that the new keys are cheap to add (all match `^[A-Z_][A-Z0-9_]*=.*$`, so `validate_state_syntax` still passes); the others lean toward simplicity (mid-waterfall crashes are rare; restart cost is acceptable; the chosen path keeps the state schema focused on phase-progression, not recovery-progression).
- **Impact**: Low
- **Affected files**: `scripts/ship-pr.sh` (state-file write/read) — additions only under the alternative path.
