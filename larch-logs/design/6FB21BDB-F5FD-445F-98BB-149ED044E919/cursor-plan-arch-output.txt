## Numbered findings

**1. Missing embedded loop re-encode (blocking, correctness)**  
`python/plan_review.py` lists `review-design-step3-loop.sh` in `_RETIRE_DESIGN_SKIPS`, so `plan-review run` always executes the gzip embedded body, not the on-disk file. The plan edits the on-disk loop only. Runtime will keep writing `.completed/step-3` before envelope persist and will never mint `step-3-terminal`, so the hook retarget and foreground probe cannot fix the incident.

**2. `design-step3-state.sh` has no on-disk source (important, completeness)**  
The plan’s `### UPDATED: skills/design/scripts/design-step3-state.sh` path does not exist in the repo. `step3_state()` delegates to `_run_legacy` on the embedded asset only. Stale-sentinel cleanup on `--direct-review-entry` / `--auto-continuation-entry` requires editing and re-encoding that blob in `python/plan_review.py`, with a documented regeneration recipe.

**3. Stale `step-3` survives wrapper relaunch (important, correctness)**  
Launch hygiene removes `step-3-terminal` but not `step-3` / `step-3.5`. Terminal failure paths still call `step3_loop_write_completed_step3()` before persist, and the EXIT trap still mints `step-3`. The updated SKILL keeps Step 3b routing keyed on `step-3` alone. A relaunch after a partial terminal path can leave a stale pause milestone and invite premature Step 3b progression while a new review wrapper is active.

**4. Embedded parity test not pinned (important, risk-integration)**  
`python/test_plan_review.py` already enforces `live == embedded` for the loop (`test_embedded_review_design_step3_loop_matches_live_script`). The plan’s testing section does not call this out. Without it, a hook-only change can look complete while the authoritative embedded loop stays stale until CI pytest fails.
