# [BUG] (URGENT) bg-poll-guard blocks all recovery after premature task-notification, forcing 180+ ps polls and 5-14x main-agent cost inflation

## Summary

During a `/design 4636` run, the `design-step3-review.sh` background task fired a premature `&lt;task-notification&gt;` (exit 0) before the review actually completed. The `.bg-wait-active` marker remained in place (the wrapper PID was still alive), so `hook-bg-poll-guard.sh` correctly blocked all subsequent TMPDIR-referencing Bash and Read tool calls. Recovery waiters launched as `run_in_background: true` were killed by the harness with exit code 144, leaving foreground `ps -p PID` polling as the only viable wait mechanism. The orchestrator ran approximately 180 foreground `ps` calls over ~70 minutes in a growing 1M-token context window, inflating the Claude main-agent bill to ~$83.91 — 5–14× the typical $7–17 for a 5-round design run.

A secondary latent bug was also found: `marker_step_completed` in `hook-bg-poll-guard.sh` checks for `.completed/step-5c-terminal` to release the `design-step5c` guard, but `design-step5c.sh` writes `.completed/step-5c` (no `-terminal` suffix). If step5c ever fires a premature notification, this mismatch would leave the guard permanently active until the wrapper's EXIT trap fires.

## Original report

User-observed during `/design 4636` (run ID `410AD75F-2779-4242-8F39-67115DD22D8C`):

## Root cause analysis

**Premature notification (uncertain root cause)**: The Claude Code task harness fires `&lt;task-notification&gt;` before the background bash process exits. The current theory is a harness-level race — either the `run_in_background: true` shell wrapper itself exits 0 after spawning the background script, or the harness fire condition is not "process exited" but something earlier. The exact mechanism is unknown without harness source access.

**Recovery waiter killed (exit 144)**: `run_in_background: true` background tasks are killed by the task harness (SIGURG / signal 16, exit 128+16=144) after some condition — possibly after the same task ID receives a prior completion notification, or after a harness-managed timeout shorter than `timeout: 21600000`. The recovery waiter processes do not appear in `ps aux` output from inside the background sandbox (PID namespace isolation), so `kill -0 PID` checks inside the waiter would immediately exit 0, causing `until ! ps -p PID` waiters to also exit immediately.

**`step-5c-terminal` mismatch (definite bug)**: `hook-bg-poll-guard.sh` line 84:
```
design-step5c)  sentinel="$dir/.completed/step-5c-terminal" ;;
```
But `design-step5c.sh` writes `.completed/step-5c` (verified by `ls .completed/` in the session). The `-terminal` suffix does not exist.

**Cost amplification**: Each of ~180 foreground `ps` tool calls in a conversation that had grown to hundreds of turns (252M tokens accumulated) consumed the full context window. At Sonnet 4.6 [1m] pricing, that drives main-agent cost from the typical ~$10 to $83.91.
