# [BUG] (URGENT) bg-poll-guard blocks all recovery after premature task-notification, forcing 180+ ps polls and 5-14x main-agent cost inflation

Latent `step-5c-terminal` bug reproduced by inspection: `grep "step-5c" scripts/hook-bg-poll-guard.sh` vs `grep "step-5c" skills/design/scripts/design-step5c.sh`.

## Expected behavior

1. After a background task's `&lt;task-notification&gt;` fires, the orchestrator should be able to verify the step sentinel (e.g., `.completed/step-3`) with a lightweight foreground Bash call without being blocked by `hook-bg-poll-guard.sh`.
2. OR: the premature notification should never fire while the wrapper PID is still alive.
3. Recovery waiters should not be killed (exit 144) by the task harness — they are the sanctioned mechanism for handling premature notifications.
4. `marker_step_completed` for `design-step5c` should match the sentinel that `design-step5c.sh` actually writes.

## Observed behavior

1. `&lt;task-notification&gt;` fires prematurely for `design-step3-review.sh`. The wrapper PID is still alive, so `hook-bg-poll-guard.sh` correctly keeps the guard active and blocks all TMPDIR reads/polls.
2. `run_in_background: true` recovery waiters (`until [ -f "step-3" ]; do sleep 30; done`) are killed by the harness (exit 144), making them useless as wait mechanisms.
3. The only unblocked poll is foreground `ps -p PID`, which does not reference the TMPDIR.
4. `marker_step_completed` in `hook-bg-poll-guard.sh` checks `.completed/step-5c-terminal` at line 84, but `design-step5c.sh` writes `.completed/step-5c` (no `-terminal` suffix) — a mismatch that leaves the guard permanently active if step5c ever fires a premature notification.

## Root cause analysis

**Premature notification (uncertain root cause)**: The Claude Code task harness fires `&lt;task-notification&gt;` before the background bash process exits. The current theory is a harness-level race — either the `run_in_background: true` shell wrapper itself exits 0 after spawning the background script, or the harness fire condition is not "process exited" but something earlier. The exact mechanism is unknown without harness source access.

**Recovery waiter killed (exit 144)**: `run_in_background: true` background tasks are killed by the task harness (SIGURG / signal 16, exit 128+16=144) after some condition — possibly after the same task ID receives a prior completion notification, or after a harness-managed timeout shorter than `timeout: 21600000`. The recovery waiter processes do not appear in `ps aux` output from inside the background sandbox (PID namespace isolation), so `kill -0 PID` checks inside the waiter would immediately exit 0, causing `until ! ps -p PID` waiters to also exit immediately.

**`step-5c-terminal` mismatch (definite bug)**: `hook-bg-poll-guard.sh` line 84:
```
design-step5c)  sentinel="$dir/.completed/step-5c-terminal" ;;
```
But `design-step5c.sh` writes `.completed/step-5c` (verified by `ls .completed/` in the session). The `-terminal` suffix does not exist.

**Cost amplification**: Each of ~180 foreground `ps` tool calls in a conversation that had grown to hundreds of turns (252M tokens accumulated) consumed the full context window. At Sonnet 4.6 [1m] pricing, that drives main-agent cost from the typical ~$10 to $83.91.

## Evidence

- **Premature notification**: Task `becmoiftm` output file had 1 line (empty) when first checked; `ps -p 54056` showed the process alive for 70+ minutes after the notification.
- **Recovery waiter killed**: Final `&lt;task-notification&gt;` for tasks `bdi537sba`, `bp9jne3ya`, `bqt6wo0gc` all reported `failed with exit code 144` (earlier premature notifications for same tasks showed exit 0).
- **`step-5c-terminal` mismatch** — hook source:

  design-step5c)  sentinel="$dir/.completed/step-5c-terminal" ;;

- **`marker_is_live` PID check** (line 113): `kill -0 "$pid"` kept the marker live because PID 54056 was the bash wrapper still running — the logic was correct for this case, it was the premature notification that was the problem.

## Affected files

- `scripts/hook-bg-poll-guard.sh` — `marker_step_completed` has the `step-5c-terminal` mismatch (line 84); also the premature-notification release logic at line 104 depends on the step sentinel being present, which creates a circular dependency when the sentinel hasn't been written yet.
- `skills/design/SKILL.md` — sanctioned recovery waiter form (`until [ -f ".../step-3" ]`) does not survive harness kills (exit 144); the SKILL.md only sanctions one recovery waiter and then requires waiting for the original notification, leaving no fallback.
- `skills/design/scripts/design-step5c.sh` — writes `.completed/step-5c`; does not write `.completed/step-5c-terminal` expected by the hook.

## Suggested fix(es)

**Fix 1 — `step-5c-terminal` sentinel mismatch (low effort, definite bug)**:
Change `hook-bg-poll-guard.sh` line 84 from:
```bash
design-step5c)  sentinel="$dir/.completed/step-5c-terminal" ;;
```
to:
```bash
design-step5c)  sentinel="$dir/.completed/step-5c" ;;
```
Or align `design-step5c.sh` to write `.completed/step-5c-terminal` before the EXIT trap fires, whichever is the intended contract.

**Fix 2 — Allow sentinel-check foreground probe after notification (medium effort)**:
Add a foreground-only allowance path: when the orchestrator has already received a `&lt;task-notification&gt;` for a background task but the step sentinel is still absent, allow a single foreground `[ -f "$DESIGN_TMPDIR/.completed/step-3" ] &amp;&amp; echo YES || echo NO` probe without blocking. The hook could whitelist this specific form (no sleep, no probe verb, just a file-test and echo) independently of `.bg-wait-active`.

**Fix 3 — Document or mitigate recovery-waiter harness kills (low effort)**:
Document in SKILL.md that recovery waiters (`run_in_background: true` `until` loops) can be killed by the harness (exit 144) and provide a fallback: after three consecutive killed recovery waiters, permit repeated foreground `[ -f "..." ] &amp;&amp; echo DONE || echo WAIT` sentinel checks (no sleep, no TMPDIR-referencing probe verb) as the recovery path, to avoid hundreds of `ps` calls.

**Fix 4 — Investigate premature notification root cause (separate)**:
Understand why `&lt;task-notification&gt;` fires before the background wrapper exits. If the harness fires on "shell process exited" and the shell wrapper forks the review script to background before exiting, either: (a) change `design-step3-review.sh` to never fork to background (keep the wrapper alive until children complete), or (b) report to Anthropic.
