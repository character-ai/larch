# Implementation plan

Confidence: high

## Approach

1. Add typed analytics models and pure helpers in `python/larch/issue/analyze_bugs.py`.
   - Map touched paths to stable zones.
   - Anchor trailing windows to the manifest `generated_at` value for deterministic tests and reruns.
   - Detect marker chains from titles and stripped issue bodies. Require a case-insensitive marker and an issue reference.
   - Detect file-intersection chains from newer fixes to prior fixes whose touched-file sets overlap within 14 days.
   - Deduplicate edges by detector kind and endpoint pair.
   - Compute file churn from unique fix commits in the trailing 7 days.
   - Mark zones chronic when they contain at least three bugs in 14 days, or at least two member bugs that are endpoints of any chain edge. Count an edge even when its other endpoint belongs to another zone.
   - Detect baseline extension only for files matching `python/*-baseline.json`.
   - Sum textual additions from git numstat output. Do not treat binary `-` entries as added lines.

2. Enrich coordinator-owned history without changing agent contracts.
   - During prefetch, derive fix time, added-line count, marker references, zones, baseline status, and existing touched-file data.
   - Keep these values out of the verifier bundle markdown and agent JSONL formats.
   - Extend `LedgerRecord` additively with the derived metadata needed across runs.
   - Preserve compatibility with existing ledger rows. Treat absent legacy fields as unavailable evidence rather than inventing timestamps or paths.
   - Merge active-run metadata with prior ledger records so the first run after the change can analyze all currently selected recent bugs and persist their metadata for later runs.
   - Continue using last-valid-record behavior for append-only ledger keys and the existing corrupt-line quarantine.

3. Build one deterministic analytics view for routing and reporting.
   - Use unique issues and fix commits to prevent repeated ledger entries from inflating counts.
   - Represent chain edges with stable issue endpoints and detector kinds.
   - Associate each issue with every zone touched by its fix.
   - Expose chronic-zone members, churned files, chain edges, and baseline-extending issues from the same view used by deep routing and report rendering.

4. Extend deep-queue routing.
   - Preserve existing mechanical and triage-doubt candidates.
   - Promote `FIXED_CLEAR` and `FIXED_LIKELY` issues when they are chain-linked, touch a chronic zone, cross from `python/` into `scripts/` or `skills/`, or add more than 300 lines.
   - Order risk promotions as chain-linked, chronic-zone, cross-language, then size.
   - Place deterministic calibration samples after risk-routed candidates and avoid duplicate issues.
   - Change the coordinator default for `--sample` from zero to three while preserving an explicit `--sample 0`.
   - Keep `--deep-max`. Persist dropped candidates with issue and routing reason, and emit the existing stderr warning rather than silently slicing the queue.
   - Keep whole-line stdout `KEY=value` names and shapes unchanged.

5. Add evidence-tier reporting.
   - Derive `DEEP` when a valid deep result supplies the final verdict.
   - Derive `TRIAGE` when verified triage supplies the final verdict.
   - Derive `MECH` when a mechanical result supplies the final verdict.
   - Add the tier column to the Issues table without changing final-verdict precedence.

6. Add report sections in the required order.
   - Render `Chronic zones` with zone, unique bug count, and member issues. Include churned-file detail within this section without creating an extra top-level section.
   - Render `Fix chains` with issue endpoints and detector kind.
   - Render `Baseline-extending fixes`.
   - Render `Since last run` with newly selected issues, newly verified issues, new chain edges, and zones entering or leaving chronic status.
   - Always render the sample size, sampled failures, and triage false-pass rate, including a zero denominator as `0.00%`.
   - When chronic zones exist, end the human-readable report with a suggestion to run `/learn-from-bugs` scoped to those zones.
   - Preserve the whole-line `ANALYZE_BUGS_COST_ESTIMATE=...` line unchanged and keep it as the final machine-readable report line.

7. Persist per-run delta state.
   - Write `run-state.json` inside each run directory after computing the report.
   - Store the run identity, selected issues, verified issues, chronic zones, and stable chain-edge identities.
   - Find the most recent valid prior snapshot under the same repository cache, excluding the active run.
   - Emit an explicit first-run state with empty deltas when no prior snapshot exists.
   - Make repeated report rendering for one run idempotent by comparing against another run’s snapshot, never the snapshot being rendered.
   - Validate snapshot shape and repository identity. Fail loudly on malformed coordinator-owned state rather than publishing a false delta.

## Edge cases

- Map `python/larch/<pkg>/...` to `python/larch/<pkg>`. Map other multi-component paths to their first two meaningful components, while `scripts/...` and `docs/...` remain `scripts` and `docs`. Keep root files stable as their own zones.
- Count each issue once per zone even when several touched files map to that zone.
- Ignore missing fix SHAs in commit-time, line-count, churn, and file-intersection calculations.
- Do not create self-edges when repeated records describe the same issue or commit.
- Allow marker edges to reference issues outside the selected set. Only selected or ledger-backed endpoints contribute member metadata.
- Preserve separate marker and file-intersection edges when both detectors support the same issue pair.
- Use strict trailing-window boundaries consistently and test fixes exactly 7 or 14 days old.
- A deep verdict overrides the earlier mechanical or triage evidence tier.
- An issue matching several promotion rules enters the queue once with its highest-priority reason.
- A calibration sample already selected by risk routing remains a risk candidate, not a second sampled queue row.
- Missing optional metadata in legacy ledger rows must not break loading or report rendering.

## Failure modes

- Git metadata probes can fail or return malformed timestamps or numstat rows. Keep the issue usable for existing verification, but omit unsupported analytics and record no fabricated values.
- Repeated ledger rows can inflate zone and churn counts unless analytics deduplicates by stable issue and fix identities.
- Using wall-clock time can change rerendered results. Use the manifest timestamp.
- Updating the durable snapshot before rendering succeeds can corrupt the next delta. Render and validate the current state before atomically writing `run-state.json`.
- Queue truncation can hide systemic risk. Persist every dropped candidate and its promotion reason.
- Report changes can move or alter the cost footer. Pin the exact `ANALYZE_BUGS_COST_ESTIMATE` grammar in the golden test.
