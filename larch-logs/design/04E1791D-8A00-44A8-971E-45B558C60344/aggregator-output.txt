### FINDING_1: delay=0 keychain lock release stays async and can self-contend
- **Reviewer(s)**: Cursor-Arch
- **Severity**: important
- **Concern**: Item 3 pins immediate keychain release via `external_startup_lock_release_after(state, delay=0)`, but that helper always schedules a `threading.Timer` release even when `delay` is 0. On `check_reviewers`, `cursor_auth_preflight` and `_cursor_probe_setup_chain` → `cursor_preread_service_token` can run back-to-back; the first call's async release can leave the lock held while the second acquire spins (up to `LARCH_EXTERNAL_STARTUP_LOCK_TRIES`), adding health-gate latency or timeout under load.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Arch: Pin synchronous release for `delay=0` (`rmdir` in `finally` before return) or hoist one lock around the combined Darwin keychain phase in `check_reviewers` and probe setup; add a test that back-to-back preflight+preread does not block on self-contention.

### FINDING_2: `_review_emit_launcher_result` composes failure diagnostics on success and duplicates on failure
- **Reviewer(s)**: Cursor-Innovation
- **Severity**: blocking
- **Concern**: The plan wires compose-before-classify into `_review_emit_launcher_result`, but that helper is invoked after successful Codex/Cursor review runs too (for example `launch_codex_review_main` and `launch_cursor_review_main`). On success (`launcher_exit == 0`), compose gathers non-empty sidecar/diag sections into `.failure-diag` even when the launcher succeeded, leaving a spurious failure-diag carrier that skews later resolver/diagnostic consumers. On failure, `_review_append_launch_failure` already calls `_compose_failure_diag` before logging; composing again inside `_review_emit_launcher_result` appends an "additional failure diagnostics" block when the carrier already exists, producing duplicated sections and an inflated `.failure-diag`.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Innovation: Gate compose to `launcher_exit != 0` inside `_review_emit_launcher_result`, matching `_review_append_launch_failure`. On success, only emit KVs from existing artifacts; do not compose.
  - From Cursor-Innovation: [SCOPE-REDUCTION] For Item 7, delegate `_review_failure_source` to `resolve_failure_diagnostic_source` and fix `_append_implement_launch_failure`; in emit, forward `stderr_sink` into the resolver only. Do not re-compose on paths where append already ran. Reserve compose-in-emit for preflight-only emit call sites that never call append.

### FINDING_3: Implement stderr-tail regeneration rule is underspecified
- **Reviewer(s)**: Cursor-Innovation
- **Severity**: important
- **Concern**: The plan says to regenerate `output.stderr-tail` when an existing tail came from a less-specific generic carrier, but gives no mechanical rule for detecting that case. Implementers can overwrite a correct tail, skip regeneration when sidecar stderr is still masked, or regenerate from the wrong source.
- **Suggested revisions (informational for voters; coder decides)**:

Pin this in `test_agents.py`.

### FINDING_5: Planned voter bounded-read regression test monkeypatches the wrong read API
- **Reviewer(s)**: Cursor-Pragmatic
- **Severity**: important
- **Concern**: The planned `_append_voter1_failure` regression monkeypatches `Path.read_bytes`, but the plan switches reads to `path.open("rb").read(limit)`. A whole-file read regression in `_append_voter1_failure` would not raise on `read_bytes`; the new test would still pass while large `.diag` / `.launcher-stderr` files load fully into memory again.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Pragmatic: Guard the bounded-read contract by monkeypatching `Path.open` (or a shared prefix helper) and asserting `read()` is called with limit 200/500, or assert `read_bytes` is never invoked on those paths.
