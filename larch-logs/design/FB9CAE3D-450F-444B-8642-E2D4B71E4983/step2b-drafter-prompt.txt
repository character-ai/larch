# Update /combine-issues dependency management: inherit source edges, audit open issues, OOS-blocked convention

## Problem

`/combine-issues --oos` (and the standard combine flow) does not validate or transfer dependency relationships when merging source issues into combined ones. After combination, the new host issue is an orphan: it carries none of the blocked-by or blocking edges that existed on its source issues, and it is not wired to any other open issues it may depend on or block.

The gap was exposed by the post-combination audit on 2026-06-12: all 10 source issues were found to have no registered dependencies, but that was only because the skill never checked whether the *newly created* combined issues had dependencies with the broader open-issue set.

## Desired Behaviour

### 1 — Inherit source-issue dependencies

When N source issues are merged into one combined issue, every dependency registered on any source issue must be re-registered on the new combined issue before the source issues are closed.

Concretely, for each source issue S and each edge `S blocked-by B` or `S blocks C`:
- Re-apply the same edge on the new combined issue using `/block-issue` / `issue add-blocked-by`.
- If both S1 and S2 contributed the same edge, deduplicate: register it once.

### 2 — Audit combined issues against all open issues

After all combined issues are created, run a dependency audit over the full open-issue set (including the newly created combined issues). For each pair (combined issue, open issue) where a dependency is detected:
- Express it via `/block-issue` / `python3 python/cli.py issue add-blocked-by`.
- The audit should cover both directions: combined-blocked-by-open and combined-blocks-open.

### 3 — Direction convention for OOS ↔ non-OOS edges

When a dependency exists between a newly combined `[OOS]` issue and an existing non-OOS issue:
- The OOS issue is the dependent (blocked) party.
- The non-OOS issue is the blocker (free to land first).
- Rationale: OOS items are deferred backlog; non-OOS issues should not be held up by OOS work.

Exceptions are permitted only when the OOS item introduces something a non-OOS issue genuinely requires. Exceptions must be surfaced to the operator as an explicit proposal before the edge is written.

## Implementation Sketch

The dependency management overhaul can be implemented as an additional phase inside the `--oos` flow (and optionally the standard flow), executed after the `combine-issues apply` calls complete:

1. **Inherit phase**: for each source issue, fetch its current dependencies, map them to the combined issue that absorbed it, and call `issue add-blocked-by` for each inherited edge.
2. **Audit phase**: fetch all open issues (using `issue list-issues`), run Tier-1 + Tier-2 reasoning over (combined issue, open issue) pairs to detect dependencies, and apply edges following the direction convention in §3 above.
3. **Exception gate**: before writing any non-OOS-blocked-by-OOS edge, surface it to the operator for approval.

The `combine-issues apply` CLI helper and the `python/combine_issues.py` module will need to expose the source→combined mapping so the inherit phase can walk it.

## Acceptance Criteria

- After a `/combine-issues --oos` run, every combined issue has its inherited source dependencies registered.
- After the audit phase, every dependency between a combined issue and any other open issue is expressed via GitHub's native blocker API.
- No existing non-OOS issue is blocked by a newly created OOS issue without explicit operator approval.
- The skill emits a dependency summary at the end of the run: edges inherited, edges added by audit, exceptions surfaced.

## Proposed Design Outline

### Goals
- After `--oos` combination, every combined issue inherits all blocked-by and blocking edges from its source issues.
- After combination, the skill detects and wires dependencies between combined issues and existing open issues.
- No non-OOS issue is blocked by a new OOS issue without explicit operator approval.

### Non-goals
- Standard (non-`--oos`) flow dependency management.
- Full LLM-based Tier-2 audit over all open-issue pairs (Tier-1 prose scanning is included; Tier-2 is best-effort via skill reasoning).
- Retroactive dependency audits of previously combined issues.

- Add `gh.issue_blocking_read` to `gh.py` (mirror of `issue_blocked_by_read` for the `blocking` endpoint).
- Add `combine-issues fetch-deps` verb to `combine_issues.py`: fetches blocked-by and blocking for a list of issues, outputs JSON.
