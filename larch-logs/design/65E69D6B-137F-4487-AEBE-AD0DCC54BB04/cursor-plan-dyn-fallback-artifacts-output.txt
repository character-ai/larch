## Findings

1. **[correctness]** `skills/design/SKILL.md:1094` — The planned MainAgent TSV exception is not reflected in orchestrator prose. Step 3 still tells the operator that re-tally produces a classification TSV where `voting_result` stays `rejected` for all rows, even though `tally-plan-review.sh` will preserve `accepted` for tagged scope-reduction blocks. That mismatch is exactly the kind of artifact/classification split the plan is trying to close.

2. **[correctness]** `skills/design/SKILL.md:1094` — The plan wires `--scope-anchor-file` through `plan-review-loop.sh` and tally for the first pass, but the orchestrator-owned MainAgent re-tally instruction only adds `--voter MainAgent:...` and `--findings-classification-out`. Without forwarding the originating issue path on re-tally, the new problem-first `[SCOPE-REDUCTION]` rubric in SKILL.md has no guaranteed anchor during the 0-judge path where it matters most.

3. **[risk-integration]** `skills/design/scripts/test-plan-review-loop.sh:1171-1192` — The existing brainstorm-merge regression expects merged brainstorm content in the dispatch `--feature-file`. The plan explicitly routes binding scope through unmerged `SCOPE_ANCHOR_FILE` while keeping brainstorm as optional context. That test is not listed among planned harness updates, so implementation is likely to break CI unless this case is rewritten or superseded by `test-plan-review-scope-anchor.sh`.

4. **[correctness]** `skills/design/scripts/plan-review-loop.sh:792-815` — Baseline capture is described as “round-1 entry plan once,” but the loop bullet does not say to write only on `round_num==1`. In multi-round mode the plan file is revised between rounds; overwriting `plan-review-baseline.txt` on later rounds would compare reviewers against the wrong baseline and weaken drift-based scope-reduction detection.

The core tally override, MainAgent TSV coercion narrow-fix, dedup marker preservation, and plan-mode aggregation fallback are otherwise aligned with the current pipeline: `aggregate-findings.sh` already leaves `findings-in-scope.md` unchanged on validation failure, and the TSV-to-Concern path at `plan-review-loop.sh:1011` preserves a leading `[SCOPE-REDUCTION]` marker for detection downstream.
