### 1. [correctness] Stale `larch:plan` in scope anchor (`skills/design/SKILL.md:469`, `skills/design/scripts/plan-review-loop.sh:119-134`)

The plan correctly splits brainstorm-merged `plan-review-feature-context.txt` from the binding anchor and threads `SCOPE_ANCHOR_FILE` through scout, panel, voters, tally, revise, and MainAgent handoff. The anchor source itself remains `feature-description.txt`, which Step 0b writes from full issue title+body (`skills/design/SKILL.md:469`) without removing embedded `larch:plan` content.

On replace or re-design runs, that file can carry a prior plan block from the issue body. Reviewers and voters would then treat bloated plan text as binding scope evidence, undermining the feature’s scope-reduction goal even when brainstorm merge is fixed.

**Suggested revision:** Compose the anchor from issue narrative with `larch:plan` stripped (e.g. via `plan-block-read.sh` on `$DESIGN_TMPDIR/issue-body.txt`), not from unfiltered `feature-description.txt`.

### 2. [architecture] Dynamic prompt `tail -n +2` contract (`skills/design/references/plan-review.md:7`, `skills/design/scripts/dispatch-plan-review-panel.sh:58-61`)

`append_shared_prompt_tail` strips only the first rendered line (`tail -n +2`); `plan-review.md` documents that line 1 must be the role line. The plan adds issue-anchor and baseline blocks to `render-plan-review-prompt.sh` but does not require they appear after that role line.

If implementation prepends multi-line anchor blocks before the role line, dynamic archetype slots (including `anchor-provenance`) and the generic Claude fallback would drop the first anchor line and may miss scope-anchor instructions entirely, while static slots still receive the full prompt.

**Suggested revision:** Document and test that `--feature-file` / `--baseline-plan-file` blocks emit only after the role line; keep `test-dispatch-plan-review-panel.sh` dynamic-path coverage for untrusted-data framing in rendered dyn prompts.
