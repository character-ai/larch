# Implementation Plan: anchor /design plan-review to the issue + protect scope-cut findings

## Goal

Stop the `/design` plan-review loop from ratcheting an over-scoped plan upward. Feed the originating issue into the scout, reviewers, and voters as the scope anchor; give reviewers the pre-review plan as a drift baseline; and let a scope-reduction finding win in the tally even when additions would normally outvote it. Both tiers, uniform. No Gate B / convergence / assessor-on-SIMPLE changes (sibling issues).

## Key design decisions

- **Scope-cut marker = in-band literal tag, not a new enum.** Reviewers prefix a scope-reduction finding's `what` text with the literal token `[SCOPE-REDUCTION]`. The TSV `scope` field stays `in_scope`, so `validate-research-output.sh` (which drops any row whose scope is not `in_scope`/`out_of_scope`, `scripts/validate-research-output.sh:375`) and the in-scope/OOS split (`plan-review-loop.sh:1080`) are untouched. Detection mirrors `is_security_block` (unfenced literal match).
- **Protected tally rule lives in design-only code.** `lib-vote-tally.sh` and `render-voter-prompt.sh` and `aggregate-findings.sh` are shared with `/review` and `/research`. All shared edits are additive and backward-compatible: a new detector function, a new optional flag, a plan-mode-only instruction. The accept-threshold override lives in `tally-plan-review.sh` (design-only).
- **Acceptance rule for scope-reduction blocks:** accepted when `YES >= 1` AND `YES >= NO`. A single advocate wins unless rejectors strictly outnumber advocates; EXONERATE is neutral. This is the structural protection — a scope cut needs one champion, not the usual two YES, so additions cannot drown it.
- **Baseline plan captured per-run by the loop.** `plan.txt-original` is written only on HARD (`design-postplan-emit.sh:457`), so `plan-review-loop.sh` snapshots its own round-1 entry plan to `plan-review-baseline.txt` for both tiers and passes it to reviewers. ## Approach

Five touch points, one per pipeline stage, all keyed on the same `[SCOPE-REDUCTION]` literal:

1. **Scout** reads the issue scope first (prompt re-anchor) so it stops naming specialists after plan bloat.
2. **Reviewers** receive the issue + baseline plan and are tasked to flag over-scope, tagging scope-cut findings' `what` with `[SCOPE-REDUCTION]`.
3. **Aggregator** preserves the tag in plan mode.
4. **Voters** receive the issue as scope anchor and judge scope-cut findings problem-first.
5. **Tally** detects the tag and applies the protected acceptance so a single advocate wins.

Shared-script edits stay additive (new flag, new function, plan-mode-gated instruction) so the three other voter/tally consumers are byte-unchanged when the new inputs are absent.

## Edge cases

- **Round 1, no drift**: baseline == current plan; the reviewer baseline block degrades to a no-op (paths equal). Reviewers still get the issue anchor.
- **SIMPLE tier**: `plan.txt-original` absent, but the loop writes its own `plan-review-baseline.txt`, so the baseline exists for both tiers.
- **Aggregator rewords the tag away**: the tally also matches the literal anywhere unfenced in the block, and the plan-mode preserve-instruction reduces the chance; if the tag is lost, the finding simply falls back to the standard threshold (fails safe, no crash).
- **0-judge MainAgent path**: override uses single-voter counts (`YES>=1 & YES>=NO`), so a lone main-agent YES still accepts a scope cut.
- **Other voter consumers** (`/research`, `/review`, `/implement`): no flag passed → identical behavior; `test-render-voter-prompt.sh` byte-equality guards this.

## Failure modes

- **Shared-script regression** (highest risk): a change to `render-voter-prompt.sh` or `lib-vote-tally.sh` leaks into `/review`/`/research`. Warning signal: `test-render-voter-prompt.sh` / `test-lib-vote-tally.sh` / `test-tally-code-votes.sh` diff. Mitigation: additive-only edits + byte-equality default-path assertions.
- **Tag not surviving aggregation**: scope-cut silently reverts to the hard threshold. Signal: the new regression test's "tagged" case fails. Mitigation: tally matches the literal in the final block + plan-mode preserve instruction; fail-safe fallback to standard tally.
- **Over-protection**: a frivolous "remove stuff" finding wins on one YES. Signal: reviewers/voters over-tag in practice. Mitigation: the `YES >= NO` guard lets any two rejectors kill it, and voters are told to judge the over-scope claim problem-first (real or not).

## Testing strategy

- New `test-plan-review-scope-anchor.sh`: end-to-end tally proof that a `[SCOPE-REDUCTION]` finding wins on `YES=1,NO=1` while an untagged finding does not (the issue's acceptance criterion), plus prompt-render assertions.
- Extend `test-lib-vote-tally.sh`, `test-tally-plan-review.sh`, `test-plan-review-prompt.sh`, `test-render-voter-prompt.sh`, `test-dispatch-plan-voters.sh` for the new surfaces and backward-compat byte-equality.
- `make lint` green (shellcheck, markdownlint, agent-lint S030 pins, script-md-sibling existence, focus-area enum check unaffected).

## Acceptance

- Scout, reviewer, and voter prompts each receive the originating issue as scope anchor; reviewers also receive the pre-review plan baseline.
- A reviewer/voter can raise and win a scope-reduction finding against an over-scoped plan, proven by new regression coverage.
- `/research`, `/review`, `/implement` voter/tally behavior is byte-unchanged (guarded by tests).
- Existing harnesses updated; `make lint` green.

This is one of three sibling issues addressing `/design` plan-review scope-creep. The other two cover the loop dynamics (no auto-apply + drift-aware convergence) and enabling the plan-quality assessor on SIMPLE.

## Problem

- **Reviewers lack the issue.** The external reviewer prompt (`render-plan-review-prompt.sh`) points only at `__PLAN_FILE__` and walks five focus areas; it does not embed the originating issue and never asks "is this plan larger than the issue requires?" Reviewers also never see the original (pre-review) plan, so cumulative drift is invisible. A defect-finder handed a detailed plan finds gaps to fill — i.e. **additions**.
- **Voters lack the issue entirely.** The ballot is literally `cat <findings> <oos> > ballot.txt` — findings only. `render-voter-prompt.sh` says "read the ballot… you may inspect the plan or repo files," and scores each finding on CORRECTNESS / SEVERITY / QUALITY. Its one proportionality escape ("EXONERATE if the change adds more complexity than **it** warrants") anchors on the finding's own concern, **not** the issue. So "is this in scope for the issue?" is not a question the voter can even ask.
- **The scout reads the drifting plan.** `scout-plan-archetypes-wrapper.sh` derives dynamic archetypes from the plan, so as the plan bloats it spins up specialists named after the bloat (in #3482: `admission-gate`, `result-env-chain`, `contract-sync`) — a self-fulfilling specialization into the creep.
- **Net: a one-way ratchet.** The scoring axes structurally favor additions (concrete, verifiable against the plan, actionable) over scope-reductions (need the issue as reference, vague, "remove stuff"). In #3482 a reviewer (`Codex-Requirements`) raised exactly the right finding — "plan expands beyond the requested simple rename reorder; restore the minimum" — and the panel **rejected** it, while accepting the additions.

## Proposed change (candidate directions — `/design` will choose)

- Feed the originating issue + approved outline into the scout, reviewer, and voter prompts as the scope anchor. For reviewers, also provide the original pre-review plan as a baseline so over-scope/drift is visible.
- Task reviewers explicitly to flag over-scope and unnecessary additions relative to the issue.
- Re-anchor the voter proportionality test to the issue ("more complex than **the issue** warrants"), and make scope-reduction / "this over-serves the issue" findings a first-class class that additions cannot structurally outvote.
- Scout dynamic archetypes from the issue rather than the drifting plan (or freeze the scout to round 1).

## Scope / acceptance

- `render-plan-review-prompt.sh`, `render-voter-prompt.sh`, the ballot construction in `plan-review-loop.sh`, and `scout-plan-archetypes-wrapper.sh` updated so each stage receives the issue anchor.
- A reviewer/voter can raise and win a scope-reduction finding against an over-scoped plan (new regression coverage).
- Existing harnesses (`test-plan-review-prompt.sh`, `test-dispatch-plan-voters.sh`, etc.) updated; `make lint` green.
