# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `blocker` or `major`. Single-YES `minor`, `nit`, `uncertain`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

Eight latent hardening gaps in larch's own lint, marker, parity-harness, and test infrastructure. Combined from three OOS sources (#6283, #6282, #6281) to run one `/design` + `/implement` cycle instead of three. Items 1-3 harden the bg-wait writer-parity lint and its Python marker writers; items 4-5 harden `write_tally` temp-file staging and its test; items 6-8 harden the hook clone-ownership parity harness.

Each item is independently shippable. No item is user-facing.

---

### Item 1 — `_has_clone_path_emission` is overly broad (latent lint false-negative)

**File**: `python/larch/lint/lint_bg_wait_writer_parity.py:41-48`

The helper accepts any non-comment line containing `CLONE_PATH=`, regardless of whether that line is inside a marker `printf`/write context. A future edit could remove `CLONE_PATH=` from the marker printf but introduce an unrelated `CLONE_PATH=` reference (log line, variable read, comment in another language) and still pass lint.

**Fix**: require `CLONE_PATH=` to appear in the same block or function as the `.bg-wait-active` write, or pair with `lint_bg_wait_coverage` discovery to cross-check that each writer's `CLONE_PATH=` token is structurally adjacent to `.bg-wait-active`.

---

### Item 2 — Python `run_step_checks_main` has no bg-wait marker arming (latent, legacy path)

**File**: `python/larch/implement/dispatch_commit_route.py:1108-1115` (registered as `cli.py implement run-step-checks`)

`run_step_checks_main` is the Python equivalent of `run-step-checks.sh`. It forwards to `checks run-relevant` but never calls `_write_bg_wait_marker`. Any caller invoking `cli.py implement run-step-checks --site step3` gets no `.bg-wait-active` marker and therefore no hook bg-wait denial coverage for Step 3.

The shell wrapper gained CLONE_PATH parity in #6276. The Python entrypoint was not updated. They should stay in sync.

**Fix**: add `_bg_wait_marker` context to `run_step_checks_main`, matching the same step/timeout as the checks-commit-route marker in `dispatch_commit_route.py`.

---

### Item 3 — Duplicate `_write_bg_wait_marker` in `step_7a.py` and `dispatch_commit_route.py` (maintenance risk)

**Files**: `python/larch/implement/step_7a.py:92-105`, `python/larch/implement/dispatch_commit_route.py:75-88`

Both modules define their own `_write_bg_wait_marker` (currently byte-identical field set and order: `PID`, `CLAUDE_PID`, `START_EPOCH`, `STEP`, `TIMEOUT_S`, `CLONE_PATH`; each also duplicates `_read_keepalive_clone_path`). The lint inventories both files and checks that each emits `CLONE_PATH=`, but it does not verify that the two implementations have identical field sets or field order. A future edit adding a field to one and forgetting the other produces a silent field-set divergence that the parity lint cannot catch.

**Fix**: extract a single shared `_write_bg_wait_marker` helper (e.g. in `python/larch/implement/bg_wait.py`) and have both modules import it, or at minimum add a cross-file field-set equivalence test.

---

### Item 4 — `write_tally_main` raw `log_root` parent assumption

**File**: `python/larch/review/voting.py:1471` (the `dir=` arg in `write_tally_main`)

`write_tally_main` passes `dir=Path(args.log_root).parent` to `NamedTemporaryFile`. This is correct when callers pass `&lt;impl_tmpdir&gt;/larch-logs` (parent = `impl_tmpdir`). But it is fragile for non-standard `--log-root` values: a root-relative path like `/larch-logs` would produce `Path("/larch-logs").parent == "/"`, causing `NamedTemporaryFile` to try staging in `/` and fail. No current caller triggers this, but the assumption is undocumented and a future caller could hit it silently.

**Fix**: validate `Path(args.log_root).parent` before passing it as `dir=`. Raise or fall back to a known-safe directory (only use the parent when it is a non-root, non-relative directory under `IMPLEMENT_TMPDIR`). Add a doc comment explaining the contract.

**Acceptance**: `write_tally_main` raises (or falls back gracefully) when `Path(args.log_root).parent` is not a usable directory.

---

### Item 5 — `dir=` fix in `voting.py` is untested in isolation

**File**: `python/tests/review/test_voting.py::test_write_tally_stages_record_under_log_root_parent`

The test sets `$TMPDIR` to a nonexistent path and asserts `write-tally` exits 0 and writes `code-review-tally.json`. It passes with or without the `dir=` fix in `voting.py`, because Python's `tempfile` falls back to a working default (e.g. `/tmp`) when `$TMPDIR` is broken. With only the `run_log_batch.py` fix in place, `NamedTemporaryFile` still creates the record under the fallback dir, `_rebase_under_tmpdir` returns the absolute path as-is, and `_redact_to_temp` reads it successfully. The current assertions (`returncode == 0`, record exists, malformed TMPDIR absent) do not flip when the `dir=` argument is removed, so the test does not isolate the fix.

**Fix**: add an assertion that the temp record was staged under `log_root.parent` (i.e. `tmp_path`), not under `/tmp` or the system default. This makes the test red when `dir=` is absent and green when it is present.

**Acceptance**: a test for `write_tally_main` is red without the `dir=` fix and green with it.

---

### Item 6 — awk `extract_function` stops early on nested `}` lines

**File**: `scripts/test-hook-clone-ownership-parity.sh:14-21`

`extract_function` uses:

```awk
in_fn &amp;&amp; $0 == "}" { exit }
```

This exits at the **first** standalone `}` line. Current compared functions (`canonical_dir`, `marker_value`, `marker_candidates`, `clone_paths_same`, `marker_foreign_clone`) use only `if/fi`, `for/done`, and `case/esac`, so extraction is correct today. But `marker_candidates` is already complex enough that a future `{ ...; } 2&gt;/dev/null` command group would truncate the extracted body silently and produce a false PASS.

**Fix**: accumulate a brace depth counter and exit only when the depth returns to zero after the opening brace.

**Acceptance**: `make test-hook-clone-ownership-parity` still passes; manually injecting a nested `{ }` block into a compared function body causes a FAIL.

### Item 7 — No parity coverage for the step-completion renamed pair

**Files**: `scripts/hook-bg-poll-guard.sh:146` (`marker_step_completed`), `scripts/hook-no-progress-guard.sh:132` (`is_step_completed`)

These are parallel helpers with different names. The harness does byte-identical comparison keyed on the same name, so it does not compare this renamed pair, and one-sided edits to step-completion detection logic go undetected.

**Fix**: add a semantic or structural comparison path for the intentionally renamed pairs, or document that they are explicitly excluded with a rationale comment in the harness.

**Acceptance**: the harness either verifies renamed-pair equivalence or carries an explicit documented exclusion comment explaining why.

**Files**: `scripts/hook-bg-poll-guard.sh:593` (`marker_is_live`), `scripts/hook-no-progress-guard.sh:195` (`is_marker_live`)

Same gap as item 7, for marker-liveness blocking behavior.

**Fix**: same as item 7.

**Acceptance**: same as item 7.
