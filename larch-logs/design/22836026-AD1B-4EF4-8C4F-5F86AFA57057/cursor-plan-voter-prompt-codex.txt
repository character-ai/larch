## Summary

The `/design` plan-review round Gantt chart ("Round N reviewer timing" in the final-summary output) renders a misleadingly large, unlabeled empty tail at the end of every round that has at least one accepted finding. The chart's declared window duration includes time spent on Gate B's plan-apply/dedup/postplan-validation work, but that work has no labeled bar of its own, so it renders as blank space after the last reviewer/voter bar.

## Original report

Surfaced during manual review of a completed `/design` run's final-summary output (issue #6061, run `F37028B8-64BD-4BB2-96DB-44ADEB6B87B0`). Both rendered Gantt charts ("Round 1 reviewer timing" and "Round 2 reviewer timing") showed a large empty region between the last labeled bar and the chart's declared right edge. Asked to root-cause why, given that "something happened that took a while but didn't end up in the diagram."

## Reproduction scenario

1. Run `/design` on any issue where at least one plan-review round produces one or more accepted in-scope findings (the common case; Gate B then applies them).
2. Let the run complete through Step 5c so `final-summary.md` renders.
3. Inspect the `### Round N reviewer timing` ASCII Gantt for that round.
4. Compare the chart's declared window span (e.g. `window 0:00-11:50 (710s)`) against the horizontal position where the last rendered bar (typically the last `*/vote` row) ends.

Concretely reproduced in run `F37028B8-64BD-4BB2-96DB-44ADEB6B87B0` (design of issue #6061), both rounds:
- Round 1: declared window `0:00-11:50 (710s)`. The last bar (`codex/vote`, 107s) ends well before the 11:50 mark by ASCII-column position, leaving roughly 4 minutes of unlabeled trailing space.
- Round 2: declared window `0:00-8:02 (482s)`. The last bar (`codex/vote`, 80s) similarly ends with roughly 3+ minutes of unlabeled trailing space before the window's right edge.

## Expected behavior

The "Round N reviewer timing" Gantt window should either:
(a) only span the time actually consumed by reviewer/aggregator/voter subprocesses, so the window's declared end lines up closely with the last rendered bar's end, or
(b) include a labeled bar/segment for any additional work counted inside that window, so the chart accurately attributes all the time it displays.

## Observed behavior

The window's declared duration is noticeably longer than the sum of rendered bar positions; a multi-minute unlabeled gap appears at the end of the chart in both rounds of the reproduction run.

## Root cause analysis

Verified by direct code reading (line numbers current as of `main` at investigation time; re-check before implementing, since the code may have moved):

- `python/larch/review/plan_review.py:479` calls `_write_design_round_meta(tmpdir=tmpdir, round_num=round_num)` inside the `"awaiting-continuation"` phase handler, gated on `$DESIGN_TMPDIR/.gate-b-postapply-ready-{round_num}` existing on disk. That marker is written only after Gate B has already applied every accepted finding to `plan.txt`, run `python/cli.py plan-review gate-b-dedup --snapshot-trailers` then `--dedup`, and validated the revised plan via postplan (`design step2b-postplan --site gate-b`).
- `_write_design_round_meta` (`plan_review.py:219-228`) runs `python/cli.py progress write-design-round-meta`, then calls `_record_design_round_timing_from_start_file` (`python/larch/review/plan_review_loop.py:549-558`), which stamps `end_s = int(time.time())` — literally whatever wall-clock moment this function happens to execute.
- The window's `start_s` comes from `plan-review/round-N/round-start-s`, stamped immediately before dispatch.
- Individual reviewer/aggregator/voter subprocess tasks each get their own Gantt bar via `record-vendor-task`, which writes a separate `v1 vendor` ledger row per task (`python/larch/report/timing.py:70-90`, invoked from e.g. `python/larch/agents/_claude_runner.py` and the Codex/Cursor launch equivalents). The round's own window is a distinct `v1 round` ledger row (`python/larch/report/timing.py:92-121`, `TimingLedger.record_round`) whose end boundary has no corresponding labeled bar.
- Net effect: whenever a round has at least one accepted finding, all the wall-clock time the main agent spends reading `accepted-plan-findings.md`, rewriting `plan.txt`, and running dedup + postplan validation between "last vote subprocess exits" and "round resumes at `awaiting-continuation`" is silently folded into that round's own "reviewer timing" Gantt window as unlabeled trailing space, even though none of that time was spent by reviewers or voters. The chart's label ("reviewer timing") is misleading about what the tail actually represents.
- Contrast case supporting this diagnosis: `plan_review.py:423` shows the other call site of `_write_design_round_meta`, reached when `accepted == 0` (nothing for Gate B to apply). On that path the round-close timing stamp happens immediately after tally with no Gate B apply work in between, so the same trailing gap should be much smaller or absent — this is a testable prediction if reproducing on a zero-findings round.

### Goals
- Attribute the unlabeled trailing gap in `/design` "Round N reviewer timing" Gantt charts to a visible, labeled Gate B span.

- Emit one labeled bar (e.g. `gate-b/apply`) as a `v1 vendor`-style ledger row spanning the Gate B apply + dedup + postplan work.

- Emit only on the accepted-findings path (`plan_review.py:479`, Gate B ran); the zero-findings path (`:423`) has no gap, so no bar.
- Confirm the existing Gantt renderer draws the new row inside the round window with no layout change.
