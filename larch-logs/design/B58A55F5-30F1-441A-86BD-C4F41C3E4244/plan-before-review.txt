## Approach

Implement the approved narrow fix in `progress_report.py`.

- Keep timing ledger format unchanged.
- Keep Top-reviewers fallback remap unchanged.
- In `_derive_progress_label`, compute the raw basename and the normalized basename with `_progress_normalize_output_base`.
- Look up labels by raw basename first, then normalized basename.
- Detect fallback rows when the normalized basename differs from the raw basename.
- Append ` (via fallback)` to the selected or derived label only for fallback rows.
- Do not append the suffix to special apply-task labels such as `codex/apply`, because those return before basename handling.

## Edge cases

- Raw manifest labels should still win when the exact basename exists.
- Fallback normalization can strip chained suffixes such as `-phase2-retry`; keep using the existing helper so behavior stays shared.
- A phase2 or phase3 row without a recognizable reviewer basename should still fall back to the existing unknown/vendor/kind logic, with the fallback suffix only when a label was actually derived.
- Row cap behavior can still drop rows when the chart exceeds `PROGRESS_GANTT_ROW_CAP`; this plan does not change cap policy.

## Failure modes

- If only `_progress_vendor_rows` changes, direct `_derive_progress_label` callers may still mislabel fallback rows.
- If normalization happens after `_progress_derived_label`, the chart can show `unknown/...phase2` labels.
- If the suffix is applied before special-kind handling, apply rows may become noisy or wrong.
- If the suffix is applied to primary rows, the chart will overstate fallback use.
