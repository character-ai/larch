## Plan

## Summary

Add a plan-size guardrail to `/design` that measures two new "fits in one implementer pass" signals — firm-heading count and distinct top-level surfaces touched — alongside the existing plan-body-line and diff-size signals, blocks an oversized single plan from finalizing by default, and lets the operator either decompose it (existing panel, unchanged) or record an explicit `oversize_override: operator` line in the plan block. Thresholds move into `python/larch/core/config.py` with calibration rationale anchored to the #6514 incident.

Reuses existing machinery: the Step 2b.5 `hard-trigger` action (`SIZE_TRIGGER_FIRED` routing is unchanged), optional-trailer preservation across the revise waterfall, and the decompose panel. Adds one new fail-closed enforcement point at Step 5c finalization to catch post-review plan growth so an oversized single plan cannot reach `/implement`.

## Approach

- Fold new signals into the existing detector. `check_plan_size_main` gains firm-heading and surface counting and folds `firm-headings` / `surfaces` reason tokens into `TRIGGER_REASONS` and `SIZE_TRIGGER_FIRED`. Because `step2b5_next_action_for` already routes `SIZE_TRIGGER_FIRED=true` to `hard-trigger`, the action decider needs no change.
- Override is a preserved optional trailer. `oversize_override: operator` is taught to the contiguous metadata-block parser (`parse_optional_metadata`) and added to `OPTIONAL_KEYS`, so the revise waterfall preserves it across review edits. When present it suppresses the size hard trigger (mirroring `mechanical_churn`), and the detector emits `OVERSIZE_OVERRIDE=operator`.
- Thresholds centralize in config. Existing literals (800/1500/2000) and the new thresholds (firm headings 25, surfaces 4) become `Final` constants in `python/larch/core/config.py` with a rationale comment; the detector references them (G-Cfg-1).
- Interactive Override at the block. The Step 2b.5 initial-site hard-trigger prompt gains an Override option; choosing it writes the trailer via a new `plan set-oversize-override` verb, then continues (Round 1 decision: interactive prompt only, no flag).
- Fail-closed finalization guard. `publish_core` re-checks size on the composed plan just after the existing review-provenance refusal; an oversized plan lacking the override is refused (`return 4`), so it cannot finalize. Step 5c surfaces a Decompose / Override / Cancel recovery.
- Decompose panel unchanged. The Split path files serial part issues with native blocked-by edges and per-part inventories as today; per-part reviewed `larch:plan` blocks are earned when each part is `/design`'d independently (Round 1 decision: boundaries + inventory, not inline per-part plans).

### Surface definition (judgment call, flagged for plan review)

For each firm heading's path: `python/larch/<pkg>` when the path is under `python/larch/<pkg>/...`; `python/larch` for a top-level file directly in that package; otherwise the first path segment (`skills`, `docs`, `scripts`, `python`, ...). Count distinct surfaces across firm headings only (MAY_UPDATE excluded). Note: larch's own multi-surface refactors (this very plan touches ~6 surfaces) trip `surfaces > 4`; the intended release valve is Override or decompose, and firm-heading count remains the primary fits-in-one-pass signal. This is the issue's proposed constant; recalibration is future work.

## Edge cases
- `oversize_override: operator` inside the contiguous metadata block must not break parsing of `diff_added:` / `mechanical_churn:` above it; the parser must accept it as a block line.
- The override must survive the revise waterfall (findings applied between 2b.5 and Step 5c); preserved via `OPTIONAL_KEYS` and a keys-preservation test.
- Post-review growth: a plan under threshold at 2b.5 that grows past it during review is caught by the Gate B `--with-plan-size` re-emit and, as the final backstop, the Step 5c guard.
- MAY_UPDATE headings are conditional and are excluded from firm-heading and surface counts.
- Mechanical-churn suppression stays orthogonal: it suppresses only the diff trigger; firm-heading / surface triggers still fire unless overridden.
- A plan with a valid override that is not actually oversized emits `OVERSIZE_OVERRIDE=operator` harmlessly (no trigger to suppress).
- `--skip-approve` cannot auto-approve past the Step 5c fail-closed refusal; the Decompose / Override / Cancel prompt still fires.

## Failure modes
1. Trailer-parser regression silently drops existing size trailers (diff estimates lost, mechanical_churn ignored). Earliest signal: `test_plan_quality` optional-trailer preservation cases. Mitigation: the recognition branch plus a preservation test that places `oversize_override` above other trailers.
2. Override not preserved across revision, so Step 5c refuses a legitimately overridden plan and blocks finalization. Signal: the revise-waterfall keys-preservation test with `oversize_override` in `OPTIONAL_KEYS`. Mitigation: `OPTIONAL_KEYS` membership plus a round-trip test.
3. Threshold too aggressive (`surfaces > 4`) false-positives on legitimate multi-surface plans, causing operator friction. Signal: this very plan trips it. Mitigation: Override is the documented release valve, the threshold is flagged as a calibration candidate, and firm-heading count remains the primary signal.

## Testing strategy
- Unit: detector (firm headings, surfaces, config-sourced thresholds, override suppression, new keys), parser (`oversize_override` recognition plus preservation), and `set_oversize_override_main` (insert / remove / idempotent / guards) in `test_plan_quality.py`.
- Integration: the Step 5c finalization guard in `test_design_publish.py`; postplan KV passthrough in `test_design_postplan.py` (conditional).
- `make py-lint`, `make py-test`, and the design script harnesses (`test-check-plan-size`, `test-gate-b-apply-mode`, `test-design-structure.sh`) pass.
