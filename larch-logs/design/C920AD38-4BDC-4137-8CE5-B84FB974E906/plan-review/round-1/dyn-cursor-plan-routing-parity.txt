## Findings

### 1. correctness — Missing `STEP2B5_NEXT_ACTION` vocabulary (`step2b5-rc-handling.md:13-17`, `SKILL.md:348-351`)

Settle actions are already frozen in `design-step35-settle.sh:119-131` (`gate-b-continue`, `gate-a-hard-size`, etc.). The plan moves Step 2b.5 routing to `STEP2B5_NEXT_ACTION` but never lists the canonical tokens for hard, partition, drift, no-trigger, rc2 warning, or internal-error. Without a frozen table, Python, markdown branch bodies, and tests can drift while still claiming parity.

### 2. correctness — Merged vs retained check-size rc `2` split (`design_postplan.py:281-291`, `design_step2b.py:218-221`, `design_step5c.py:51-83`)

Retained `step2b5_main` echoes check-size output and returns the child rc (tests at `test_design_lifecycle.py:2006-2017` cover rc `2` as warn-and-continue). Merged `postplan_emit_main` always `return 1` after any check-size failure (`design_postplan.py:281-291`), and `_postplan_decide` treats rc `1` as fatal (`design_step2b.py:220-221`). The issue acceptance calls for rc-matrix parity; the plan's shared helper does not say which side wins.

### 3. correctness — Incomplete settle envelope contract (`design-step35-settle.sh:286-302`, `settle-rc-dispatch.md:17-27`)

The bash table at `design-step35-settle.sh:119-131` pairs each `(POSTPLAN_RC, site)` with a fixed process exit (`0`, `10`, `12`, `13`). After Python owns dispatch, `SETTLE_EXIT_RC` must be required alongside `SETTLE_NEXT_ACTION`, and `settle-rc-dispatch.md` should document action↔exit pairs for the existing disagreement guard instead of only the POSTPLAN_RC diagnostics block.

### 4. risk-integration — Postplan emit may drop `STEP2B5_NEXT_ACTION` (`design_postplan.py:151-180`)

Direct-entry Gate A hard-size paths bind from `.design-postplan-emit-result.env` (`step2b5-rc-handling.md:5-6`). `flush()` only prints keys in its explicit loop (`design_postplan.py:153-178`); adding the action to `PHASE_RESULT_ENV_ALLOW_KEYS` alone does not put it on stdout or into the env file consumers read.

### 5. [OUT_OF_SCOPE] architecture — Helper placement in `design_session.py`

Dispatch tables fit better in a dedicated module than in `design_session.py`, which already owns wrapper-env and phase allowlists. Not required for correctness; optional scope reduction.
