## Findings

### 1. [correctness] `emit-tally` rejects promoted-only sinks (`review_tally.py:1207-1222`)

The plan keeps `OOS_ACCEPTED_COUNT` vote-only (correct for scoreboards), but `emit_tally` requires an exact match between that counter and non-security blocks in `oos-accepted-review.md`:

```1207:1212:python/larch/review/review_tally.py
    sink_count = _non_security_oos_count(oos_accepted_file)
    if oos_accepted_count > 0 and sink_count == oos_accepted_count:
        pass
    elif sink_count > 0 and sink_count != oos_accepted_count:
        print(f"emit-tally: OOS_ACCEPTED_COUNT={oos_accepted_count} but accepted sink has {sink_count} non-security block(s); refusing destructive rebuild", file=sys.stderr)
        return 1
```

The primary feature path (zero vote-accepted OOS, severity trigger fires, tally promotes pool items) produces `sink_count > 0` with `OOS_ACCEPTED_COUNT=0`, which hits the refusal branch. `test_emit_tally_refuses_destructive_oos_rebuild_mismatch` (`python/tests/review/test_review_tally.py:1719-1747`) encodes this strict equality. The plan does not list `emit_tally` under `### UPDATED:` or `### MAY_UPDATE:`.

**Suggested revision:** Add a narrow `emit_tally` relaxation (or companion KV) so tally-written promoted sinks are preserved when `sink_count >= OOS_ACCEPTED_COUNT`, and add a promotion-only emit test.

### 2. [correctness] Design promotion missing header normalization (`design_oos.py:22-24`, `plan_review_tally.py:794-833`)

`/implement` explicitly normalizes promoted chunks via `_normalize_oos_header_text` (`review_tally.py:451-452`). The plan edge case covers `/implement` FINDING→OOS headers but not `/design`.

Design filing only recognizes `### OOS_<n>:` blocks:

```22:24:python/larch/design/design_oos.py
_OOS_HEADER_RE = re.compile(r"^###\s+OOS_(\d+):[^\n]*\n", re.MULTILINE)
```

```74:87:python/larch/design/design_oos.py
def _extract_unfiled_blocks(text: str) -> str:
    indices: list[int] = [match.start() for match in _OOS_HEADER_RE.finditer(text)]
    if not indices:
        return ""
```

Latent and neutral-rescued in-scope findings are `FINDING_N` items routed to `oos.md` only today (`plan_review_tally.py:794-802`). Promoting them without reheadering leaves `oos-accepted-design.md` invisible to prepare, reproducing `skip-no-items` for the exact population this issue targets.

**Suggested revision:** Add design-side normalization and monotonic `OOS_N` allocation before `_accumulate_round_oos`, plus a plan-review tally test that promoted FINDING blocks reach `oos-combined.md`.

### 3. [correctness] Body-severity helper contract is inconsistent inside the plan (`plan_review_tally.py:112-122`)

The Approach requires lowercase normalization and `blocking`/`important`/`latent` classification. The `plan_review_tally.py` section says to use `_body_severity_for_block`, which returns raw text with no lowercasing:

```112:122:python/larch/review/plan_review_tally.py

    ...
            return re.sub(r"[ \t]+$", "", value)
    return ""
```

Reviewer output with `Important` or `BLOCKING` would not satisfy the trigger even when the issue intent is met.

**Suggested revision:** Point both tally modules at one new `_aggregate_trigger_severity(block)` helper; keep `_body_severity_for_block` for classification TSV only.

### 4. [risk-integration] Bug A retry action is not wired through Step 5b (`design_oos.py:790-797`, `design_step5b.py:254-257`)

Annotate already fails closed on empty stdout without writing `oos-issues-created.md`:

The plan adds a retry `NEXT_ACTION`, but only `MAY_UPDATE: design_lifecycle.py`. Prepare routing knows only `file-issues`, `label-only`, and skip statuses (`design_step5b.py:77-84`). Annotate failure prints `STEP5B_STATUS=annotate-failed` and the skill body still continues to 5b.5 (`finalize-step5.md:55`). The plan’s own failure mode warns about a dead retry status without lifecycle support.

**Suggested revision:** List `design_step5b.py` (annotate path) and finalize-step5 retry branching as firm updates; test the full prepare→issue→annotate retry loop.

### 5. [correctness] `/implement` `oos_seq` seeding may be insufficient for promoted reroutes (`review_tally.py:269-284`)

`_seed_oos_seq` reads `accumulated-oos.md` only. Post-loop promotion that reheaders `FINDING_N` blocks needs a seq beyond vote-accepted writes in the same round and any pre-existing session sink when `--session-env-path` differs from the round dir (called out in planned tests). Without seeding from existing accepted sinks, promoted headers can collide.

**Suggested revision:** Seed from max `OOS_N` in round and session accepted files before the post-loop promotion pass.
