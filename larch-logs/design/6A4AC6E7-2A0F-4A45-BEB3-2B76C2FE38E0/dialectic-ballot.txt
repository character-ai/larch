## Dialectic Ballot

You are a judge on a 3-panel adjudicating contested design decisions. For each `DECISION_N` below, read both Defense A and Defense B, then cast exactly one binary vote: `THESIS` or `ANTI_THESIS`. THESIS means the side labeled as defending the synthesis's `CHOSEN` option on that decision wins; ANTI_THESIS means the side defending the synthesis's `ALTERNATIVE` option wins. Judge on argument quality — not on which defense "sounds more confident." Vote on every decision. Do not modify files.

The tool that produced each defense is hidden (Defense A / Defense B labels are anonymous). Which side defends CHOSEN vs. ALTERNATIVE is disclosed on each decision's header because that information is semantic, not tool-attributive.

### DECISION_1: stdin redirection at lib-codex-launcher-common.sh vs setsid session detach

Defense A (defends CHOSEN — "Redirect background Codex subprocess stdin to /dev/null at the lib-codex-launcher-common.sh layer"):
<defense_content>
When a Family-B background Bash exits, its session teardown can close inherited file descriptors; `setsid` puts the Codex subprocess in a new session so the child keeps running even if the parent shell and its FD table vanish—a belt-and-suspenders fix beyond the specific `write_stdin` error.

Ship a shared Codex launch helper in `lib-codex-launcher-common.sh` that runs every background Codex subprocess with stdin redirected to `/dev/null`, because that directly fixes the documented failure mode without changing session or signal semantics.

Every Codex voter/reviewer path already funnels through `run-external-agent.sh`, which spawns the CLI with `"$@" &` and leaves stdin inherited (`scripts/run-external-agent.sh:205-211`), while callers pass the prompt on the argv tail after `codex exec` (e.g. `scripts/launch-review.sh:497-510`); run logs for #2962 show `write_stdin failed: stdin is closed for this session` when the parent shell exits mid-run—exactly what `< /dev/null` neutralizes.

`setsid` can still help if the subprocess or libc probes controlling-terminal state for reasons beyond stdin closure, or if some future spawn path forgets the redirect.

Larch never launches interactive Codex today: invocations are `codex exec` with `--output-last-message` and prompt argv, timeout already kills by PID in `run-external-agent.sh:220-226`, and `setsid` adds macOS/Linux behavioral divergence without addressing a failure mode that is explicitly stdin-shaped.

Background Codex voters keep inheriting a closing stdin from short-lived parent shells, reproduce empty ballots in Step 5 code-review voting, and #2973-class failures return within the next implement cycle.
</defense_content>

Defense B (defends ALTERNATIVE — "setsid (or exec setsid) session detach"):
<defense_content>
Redirecting Codex stdin to `/dev/null` attacks the observed "stdin is closed" failure directly with a narrow shell change and avoids changing process-session semantics for monitored external-agent runs. Because `run-external-agent.sh` already owns timeout, diagnostics, and sentinel behavior, preserving its current process model is a legitimate safety argument.

Ship `setsid` session detachment instead, because the stated requirement is parent-shell-exit survival, and stdin redirection is a symptom patch that leaves session coupling intact while pretending to be the root fix.

`scripts/lib-codex-launcher-common.sh:7` says the file only preserves `codex_launcher_*` wrapper names, and `scripts/lib-codex-launcher-common.sh:12` merely sources `lib-external-launcher-common.sh`; it is not currently the spawn layer. The actual launch point is centralized in `scripts/run-external-agent.sh:205-213`, where the command is backgrounded, while Codex call sites route through it at `scripts/launch-review.sh:497-510` and `scripts/launch-codex-implement.sh:324-338`. That makes session detachment a single lifecycle decision at the real process boundary, not a launcher-shim fiction.

The best opposing point is that `setsid` is broader than stdin redirection: it may affect controlling-terminal assumptions and platform behavior, while `< /dev/null` is easy to reason about and matches the observed error text.

That concession loses on proportionality because the current failure class is explicitly parent-shell lifetime coupling, not interactive input support; `run-external-agent.sh:150-152` and `scripts/run-external-agent.sh:223-226` still retain explicit PID cleanup for normal wrapper exits and timeouts, so detaching the session does not require abandoning monitored termination.

If this position loses, `/dev/null` may suppress today's stdin complaint while leaving the next parent-exit or controlling-terminal hangup failure to recur under a different symptom, forcing a second launcher change in the same fragile Step 5 path.
</defense_content>

### DECISION_2: voter `.done` wait granularity — single invocation vs per-launch-group

Defense A (defends ALTERNATIVE — "Wait per launch group: one wait after launch-claude-review.sh, then a second wait after dispatch-with-waterfall.sh"):
<defense_content>
A single `wait-for-reviewers.sh` call immediately before `check_and_retry_voter_parse_rate` gives one readiness gate aligned with tally consumption: one timeout budget, one stdout block to parse, and instant return when all three `.done` files already exist because `wait-for-reviewers.sh` scans sentinels before its first sleep.

Per-group waits match `dispatch-code-voters.sh`'s two launch phases and avoid paying for a redundant third poll on Codex/Cursor sentinels that `dispatch-with-waterfall.sh` already finalizes before parse-rate runs.

`dispatch-code-voters.sh` runs `check_and_retry_voter_parse_rate` at lines 215–217 with no prior `wait-for-reviewers.sh`, while `dispatch-with-waterfall.sh`'s `collect_phase` (lines 343–366) already `wait`s each background PID and calls `collect-agent-results.sh`, which internally invokes `wait-for-reviewers.sh` on each phase output before returning to the dispatcher.

One batched wait is easier to audit than two call sites and mirrors the voting-protocol pattern of listing every external sentinel in a single waiter invocation.

That audit win is mostly duplicate work here: the waterfall path already blocks on `.done` for voters 2–3, so a terminal three-sentinel wait mostly re-probes state that `collect-agent-results.sh` just validated, while deferring Claude readiness until after the entire Codex/Cursor waterfall finishes even though voter 1 launched and returned first at lines 103–113.

We ship a single-invocation design that adds another long-timeout poll without shortening the failure window, blurs which launch group timed out when stdout shows `TIMEOUT 2` vs `TIMEOUT 3`, and still leaves the Claude-only gap between `launch-claude-review.sh` return and waterfall start un-hardened if `.done` and output diverge.
</defense_content>

Defense B (defends CHOSEN — "Single wait-for-reviewers.sh invocation in dispatch-code-voters.sh immediately before parse-rate checks, covering all voter `.done` sentinels"):
<defense_content>
Per-launch-group waits fail closer to the launcher that hung, so a Claude-only stall and a Codex/Cursor stall are reported at the right boundary. That makes timeout diagnosis sharper than one aggregate wait.

Place one `wait-for-reviewers.sh` invocation in `scripts/dispatch-code-voters.sh` immediately before parse-rate checks, covering all voter `.done` sentinels.

`dispatch-code-voters.sh` already has the natural join point: it launches Claude at `scripts/dispatch-code-voters.sh:103`, falls back to a `.done` sentinel at `:113`, dispatches Codex/Cursor through waterfall at `:173`, then immediately checks parse rate at `:215-217`. `wait-for-reviewers.sh` is explicitly variadic and index-stable (`scripts/wait-for-reviewers.sh:4-16`, `:158-166`), while `review-core.sh` treats `dispatch-code-voters.sh` as the voter boundary before tally (`skills/review/scripts/review-core.sh:621-653`).

The opposing approach gives better fault localization: if Claude hangs, waiting after `launch-claude-review.sh` points directly at voter 1 instead of delaying that fact until all voter paths are known.

That precision is not worth splitting the synchronization contract because `dispatch-with-waterfall.sh` already performs phase waits (`scripts/dispatch-with-waterfall.sh:343-345`) and returns final output slots (`:551-559`), so the missing guard is specifically "do not parse or tally before every advertised voter sentinel exists."

If single-wait is wrong, Step 5 may still lose time to an aggregate timeout and require follow-up work to isolate hung launch groups without regressing the tally-before-output race.
</defense_content>
