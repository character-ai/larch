# Approach Synthesis — Issue #2973 voter failures

## Agreement points (all 4 sketches converge)

1. **Voter race is real**: tally reads voter outputs before all voter `.done` sentinels fire. Fix by explicit `.done` wait before tally.
2. **Reuse wait-for-reviewers.sh**: do not invent a second readiness primitive. It is already a general `.done` waiter.
3. **Cursor sidecar empty is benign for tally**: `tally-code-votes.sh` does not read sidecars (verified via grep). Sidecar population is a separate cleanup.
4. **Deeper root cause (out-of-scope for this PR)**: sentinel inheritance — nested Family-B scripts (`collect-agent-results.sh`, `dispatch-with-waterfall.sh`, `review-and-fix.sh`) inherit the orchestrator's `LARCH_DONE_SENTINEL` and `LARCH_BREADCRUMBS_SURFACED_FILE`, causing `breadcrumb-monitor.sh` to exit before `review-and-fix.sh` completes. Codex-Innovation and Codex-Pragmatic both identify this; Cursor-Edge cites the exact line. Per Round 1 Decision 1, this is filed as OOS in Step 5b.

## Resolved tradeoffs

- **Codex stdin fix surface area** → user-decided: all background-Codex launches (not voter-only). Landing site: `scripts/lib-codex-launcher-common.sh` (shared between `launch-review.sh` and `launch-codex-implement.sh`).
- **Voter wait integration** → user-decided: reuse `wait-for-reviewers.sh`. Codex-Innovation's "voter-finalization manifest" rejected for over-scope.
- **Cursor sidecar fix** → user-decided: include sidecar population fix in same PR (Round 1 Decision 5).
- **Verification bar** → user-decided: offline regression tests only. No live `/implement` re-run required.

## Contested decisions (for dialectic)

1. **Codex stdin fix mechanism**: stdin redirection (`< /dev/null`) vs `setsid` session detach vs pty wrapper. The user's "all background-Codex launches" decision raises the stakes — wider blast radius makes the simpler mechanism more attractive, but a future `codex exec --interactive` could break under stdin redirection.
2. **Voter wait scope**: wait for all voter `.done` sentinels in one collect-style invocation, vs wait per launch group (Claude alone, then waterfall). The first is simpler; the second produces faster failure signal if one slot hangs.
