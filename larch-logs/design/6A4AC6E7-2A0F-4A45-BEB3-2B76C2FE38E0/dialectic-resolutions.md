## Dialectic Resolutions

### DECISION_1: stdin redirection at lib-codex-launcher-common.sh vs setsid session detach
**Resolution**: Redirect background Codex subprocess stdin to `/dev/null` at the `lib-codex-launcher-common.sh` layer.
**Disposition**: voted
**Vote tally**: THESIS=3, ANTI_THESIS=0
**Thesis summary**: Ship a shared Codex launch helper that runs every background Codex subprocess with stdin redirected to `/dev/null`; this directly fixes the documented `write_stdin failed: stdin is closed for this session` error without changing session or signal semantics, and matches the observed failure mode tracked in #2962 run logs.
**Antithesis summary**: `setsid` session detach is the broader proportional fix because the underlying coupling is parent-shell lifetime, not interactive input — `< /dev/null` is a symptom patch that leaves session-level coupling intact and may push the next failure into a different surface.
**Why thesis prevails**: All three judges agreed the documented failure is explicitly stdin-shaped (`write_stdin failed: stdin is closed for this session`) and the `< /dev/null` fix matches the error byte-for-byte while leaving signal propagation, timeout-by-PID, and macOS/Linux portability untouched. The antithesis's strongest concession — that future controlling-terminal probes could still fail — remains speculative against the concrete present failure; the thesis's evidence at `scripts/run-external-agent.sh:205-211` (background spawn with inherited stdin) and `scripts/launch-review.sh:497-510` (Codex invocations) shows the fix lands at the smallest correct layer for the present bug. The antithesis's risk-if-wrong (next surface-level failure) is real but not yet tracked; this design intentionally scopes to the documented failure mode.

### DECISION_2: voter `.done` wait granularity — single invocation vs per-launch-group
**Resolution**: Wait for ALL voter `.done` sentinels in one `wait-for-reviewers.sh` invocation, placed in `dispatch-code-voters.sh` immediately before parse-rate checks.
**Disposition**: voted
**Vote tally**: THESIS=2, ANTI_THESIS=1
**Thesis summary**: Place one `wait-for-reviewers.sh` invocation in `scripts/dispatch-code-voters.sh` immediately before parse-rate checks, covering all three voter `.done` sentinels — the natural join point that matches the tally callsite without splitting the synchronization contract.
**Antithesis summary**: Per-group waits match the dispatcher's two launch phases and avoid paying for a redundant third poll on sentinels that `dispatch-with-waterfall.sh` already finalizes via its `collect_phase` (lines 343-366), while localizing timeouts to the launch group that actually stalled.
**Why thesis prevails**: A 2-1 split between judges. The thesis correctly identifies that the missing guard is specifically "do not parse or tally before every advertised voter sentinel exists" (the actual failure mode from issue #2973 Voter B/C) — a single terminal wait directly addresses this without splitting the contract. The antithesis's concern about fault-localization granularity (knowing whether voter 1 or 2/3 timed out) is legitimate but a diagnostic-quality argument, not a correctness argument; the existing `--timeout` exit-on-timeout grammar from `wait-for-reviewers.sh` already produces per-sentinel TIMEOUT lines on stdout, so single-wait does not hide which slot timed out. The antithesis's strongest point — that `collect-agent-results.sh` already waits on Codex/Cursor sentinels inside the waterfall — is correct as an observation but does not eliminate the need for a single barrier covering ALL three sentinels (including Claude), since the race in the issue is the gap between `launch-claude-review.sh` return and the tally read of `voter_1_path`. **Note**: this is a close 2-1 split; Step 3.5 still-contested criterion may surface this for Round 2 discussion if the user enters Gate B(c).
