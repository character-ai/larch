# Implementation Plan — /design plan-size gate: split add/delete thresholds, relax mechanical churn (#3175)

## Summary

Make the `/design` Step 2b.5 hard plan-size gate key on estimated ADDED lines instead of total churn. Deletions never trip it. A self-declared `mechanical_churn: true` trailer downgrades the diff gate to a soft advisory. The change is additive and backward compatible: the required final `diff_lines: <N>` trailer and its ~41 consumers are untouched, and plans without the new trailers reproduce today's behavior byte-for-byte.

Settled directions (Step 1c/1d):
- New OPTIONAL trailers `diff_added: <N>`, `diff_deleted: <N>`, `mechanical_churn: true`, placed in the final contiguous metadata block immediately ABOVE the still-required last-line `diff_lines: <N>`.
- Hard diff trigger fires on `diff_added > 2000` (strict `>`) when `diff_added` is present; otherwise legacy `diff_lines > 1500`.
- Deletions (`diff_deleted`) are informational only — never a trigger, no cap.
- `mechanical_churn: true` suppresses the diff hard trigger and emits a SOFT advisory instead (no Split/Cancel).
- `plan_lines > 800` plan-body hard trigger is UNCHANGED and is NOT affected by `mechanical_churn` or deletions (out of scope per Round 1).
- Optional size trailers do not consume plan-body budget: `PLAN_LINES` is computed as physical plan lines before the final metadata block, excluding `diff_added`, `diff_deleted`, and `mechanical_churn` trailers immediately above final `diff_lines:`. Legacy plans without optional trailers keep today's `PLAN_LINES` byte-for-byte.

## Edge cases

- `diff_deleted` present without `diff_added`: deletions are informational, so the gate uses the legacy `diff_lines` fallback; `diff_deleted` never affects the trigger.
- `diff_added` present, `diff_deleted` absent: fine — additions-keyed trigger applies; `DIFF_DELETED=` emitted empty.
- `mechanical_churn: true` with the diff already under threshold: `soft_advisory=0` (nothing to downgrade); advisory line not printed.
- `mechanical_churn: true` + `plan_lines > 800`: plan-body hard trigger still fires; the diff side may also set `SOFT_ADVISORY=true`. Both surfaces are coherent (hard prompt + advisory line that explicitly says the plan-body gate still requires Split/Cancel, not “proceeding”).
- Malformed optional trailer (`diff_added: 12x`, tab, double space): rejected by the anchored regex, treated as absent → legacy fallback. No exit-code change.
- Optional trailer text in prose/code blocks: ignored unless it appears in the final contiguous metadata block immediately above `diff_lines:`.
- Optional trailer text separated from the final metadata block by a blank line is ignored as metadata; the blank stops scanning, and the separated trailer-looking line remains part of `PLAN_LINES`.
- Multiple `diff_added:` lines inside the final metadata block: the last full-line match in file order, closest to `diff_lines:`, wins, mirroring the `diff_lines` last-line robustness (harness case 11 analog).
- A plan with exactly 800 body lines plus three recognized optional metadata trailers remains under the plan-body hard gate; malformed trailer-looking lines are body text, are not subtracted, and can still contribute to `PLAN_LINES`.

## Failure modes

1. **Silent gate bypass via stale parser.** If SKILL.md Step 2b.5 is not updated to parse `SOFT_ADVISORY`/`DIFF_ADDED`, the advisory is computed but never surfaced, so operators lose the signal. Earliest signal: advisory never prints on a known mechanical-churn plan. Mitigation: update Step 2b.5 parse + advisory print in the same change; `test-design-structure.sh` keeps the EMIT_PLAN→check-plan-size ordering honest.
2. **Backward-compat regression for the ~41 `diff_lines` consumers.** A grammar/last-line change would break `emit-plan.sh` and legacy plans. Earliest signal: `test-check-plan-size.sh` cases 1-13 or `test-emit-plan.sh` fail. Mitigation: keep `diff_lines:` last-line-required and lines 1-90 byte-stable; legacy cases stay green; do not touch `emit-plan.sh`.
3. **Retired-key collision.** Reintroducing `SOFT_TRIGGER_FIRED`/`FILES_COUNT` would clash with the harness retired-key asserts (and any drift lint). Earliest signal: `assert_no_key` failures. Mitigation: use `SOFT_ADVISORY`; leave the retired-key asserts in place.
4. **Revision-flow trailer loss.** Gate B or waterfall revision rewrites can preserve only `diff_lines:` and drop the optional trailers, converting a deletion/mechanical plan back into a legacy hard trigger. Earliest signal: a revised `mechanical_churn: true` plan returns `plan-size-trigger`. Mitigation: update revision prompts/contracts and add a focused preservation regression or spot-check.
5. **Plan-body spoofing.** Prose or code samples containing `mechanical_churn: true` could suppress the diff gate if the parser scans the whole file. Earliest signal: spoof-resistance regression fails. Mitigation: parse only the final contiguous metadata block above `diff_lines:`.
6. **Metadata scan crosses block boundary.** A scanner that skips blank lines could parse a separated body `diff_added:` line or subtract it from `PLAN_LINES`. Earliest signal: blank-separated trailer regression fails. Mitigation: stop upward scanning on any non-matching line, including blanks.
7. **Duplicate-key inversion.** Implementing "last wins" as last encountered while scanning upward would choose the farthest value from `diff_lines:` and can invert the hard trigger. Earliest signal: duplicate optional-key regression fails. Mitigation: collect the final block in file order or only overwrite as iteration proceeds toward `diff_lines:`.
8. **Metadata false positive on plan-body gate.** Adding three optional trailers to an 800-line body could create a hard trigger if `PLAN_LINES` remains the raw line count. Earliest signal: 800-body-plus-trailers regression fails. Mitigation: subtract recognized optional metadata trailer lines from `PLAN_LINES` after parsing the final block; malformed lines remain body text.
9. **Unified-diff revision bypass.** If preservation validation is attached only to file-replacement parsing, the default waterfall unified-diff path can remove optional trailers and still pass `ACTION=EMIT_PLAN`. Earliest signal: default unified-diff preservation regression fails or a plan-review-loop revised mechanical plan returns `LOOP_STATUS=plan-size-trigger`. Mitigation: validate the resulting `plan.txt` after every successful candidate apply before `run_emit_plan_gate`, restore on failure, and add both unified-diff and file-replacement regressions.

<feature>
/design plan-size gate: split add/delete thresholds, relax mechanical churn

## Motivation

The `/design` Step 2b.5 hard plan-size trigger (`skills/design/scripts/check-plan-size.sh`) fires on a single `diff_lines: <N>` total-churn estimate with a fixed `> 1500` threshold and offers only **Split / Cancel** (no Continue — hard triggers are non-downgradeable). This conflates two very different kinds of large change:

- **Deletion-heavy rip-outs** — a plan that mostly *removes* code is large by line count but low in review complexity.
- **Trivial mechanical modifications** — large rename / mechanical-substitution churn that is high line count but low complexity.

Concrete trigger case: issue #3118 ("Breadcrumbs Deprecation Stage 3: Monitor contract removal") produced a ~4700-line plan that is overwhelmingly *deletions* (deleting `lint-foreground-markers.sh` ~1037 lines + `test-lint-foreground-markers.sh` ~1721 + `test-breadcrumb-monitor.sh` ~902, plus plumbing removal). The hard gate fired and offered only Split/Cancel on a leaf partition piece (already piece 3 of a 5-way split) where neither fit; the operator had to use the `AskUserQuestion` "Other" escape to override and proceed.

## Proposed change

1. Have `check-plan-size.sh` distinguish **added** vs **deleted** line estimates instead of one `diff_lines` total. Either accept separate trailers (e.g. `diff_added: <N>` / `diff_deleted: <N>`) or derive the add/delete split from the plan, and key the hard trigger primarily on **additions / net new complexity**, not raw total churn.
2. Allow **basically arbitrary-size deletions** — deletions should not trip the hard trigger (or only at a very high, separate cap). Large removals are low-risk.
3. **Strongly relax** the limit for **trivial mechanical modifications** even when the count is very large (e.g. mechanical rename / substitution churn), so high-count-but-low-complexity changes are not forced into Split/Cancel.
4. Consider giving the hard trigger a Continue/override affordance for these low-complexity-large cases, or reclassifying them as soft (advisory) rather than hard.
