# [BUG] (URGENT) /implement and /design orchestrators use Monitor for one-shot completion, creating one turn per log line

## What happened

During `/implement` run BC8DDA64 (issue #3678), the orchestrator spawned 6–8 concurrent `Monitor` tool calls to watch Codex and Step 3 check progress. Each `Monitor` fires **one conversation turn per matching log line**, creating ~30+ spurious turns and burning tokens on pure waiting.

The same mistake can occur in `/design` whenever it needs to wait for an external process to finish.

## Root cause

### Primary: Monitor misused for one-shot completion

`Monitor` is designed for **event streams** ("fire on every occurrence, indefinitely"). The correct tool for "tell me when this process is done" is `Bash run_in_background` with a condition-based exit — which fires **exactly one** `&lt;task-notification&gt;` when the command exits.

AGENTS.md is explicit:
&gt; "Don't spawn a Monitor or a Bash `run_in_background` polling loop (`for`/`while`/`until` + `sleep`) to watch another job finish... **Use Monitor only for logs, external polling, or event streams.**"

`/implement` SKILL.md NEVER #8 is also explicit:
&gt; "For long-running helper scripts (≥ 30s; e.g., `run-step-checks.sh`, `run-step5-review.sh`...), set `run_in_background: true` on the Bash tool call (immediate-background mode) and rely on `&lt;task-notification&gt;` for one-shot completion."

Both rules were violated.

### Trigger: premature background task notification

`run-step2-dispatch.sh` was launched via `Bash run_in_background`. The task notification fired with empty stdout while the Codex process tree (PIDs 50005/50035/50202/50275/50952/50968) was still running. This left the orchestrator without a valid task handle.

**Correct recovery:** re-launch **one** `Bash run_in_background` task with `until &lt;completion-condition&gt;; do sleep 60; done` → wait for its single completion notification.

**Actual recovery:** spawned multiple `Monitor` calls watching different log files and PID-exit conditions simultaneously.

### Compounding: redundant monitors

At peak, 7 monitors ran simultaneously, several watching the same sources (e.g., two separate monitors on `codex-impl.log`). Each produced its own turn stream.

## Suggested fix (covering both `/implement` and `/design`)

### 1. Add an explicit prohibition to AGENTS.md (covers all skills)

Add to the "Conventions" section, next to the existing anti-polling rule:

&gt; **NEVER use the `Monitor` tool for one-shot completion tracking in any skill.** `Monitor` fires one turn per log line — it is for event streams only (indefinite watching of errors, CI events, live log tails). For "tell me when this is done," use `Bash run_in_background` with a condition-based exit (`until &lt;condition&gt;; do sleep N; done`), which fires exactly one `&lt;task-notification&gt;`. This applies even when a prior background task's notification fired prematurely with empty output — re-launch a single condition-exit task, do NOT fall back to Monitor.

### 2. Add NEVER #N to `/implement` SKILL.md

Add to the NEVER list (as an extension of NEVER #8):

&gt; **NEVER use the `Monitor` tool anywhere within the `/implement` orchestrator.** When a background task notification fires prematurely (empty stdout, underlying process still running), re-launch exactly one `Bash run_in_background` task with `until &lt;completion-condition&gt;; do sleep 60; done`. Do NOT spawn multiple monitors watching the same condition.

### 3. Add equivalent rule to `/design` SKILL.md

Same prohibition, scoped to `/design`.

### 4. Add structural test

Add an assertion to `scripts/test-implement-anti-polling-rule.sh` (and an equivalent for design) that scans `skills/implement/SKILL.md` for any `Monitor` tool call and fails if found.

- `skills/implement/SKILL.md` — NEVER list extension of #8
- `skills/design/SKILL.md` — same prohibition
