## Approach

Add a new read-only ledger verb:

```bash
python3 python/cli.py skill-closure ledger [--root ROOT] [--window N | --since-tag TAG] [--summary]
```

Use direct git history of `python/skill-closure-baseline.json`.

Key choices:

- Keep `lint_skill_closure_growth.py` unchanged except for reusing its `BASELINE_RELPATH` constant.
- Put historical parsing in a new sibling module with lenient rules.
- Treat each target's first appearance as an initial value, not a delta.
- Parse PR numbers only from commit subjects ending in `(#N)`. Do not call GitHub.
- Mark any positive per-target delta with a visible `raise` field.
- Exit 0 for successful reads even when raises exist. This is not a gate.

**Default selection and display** (FINDING_1): `--window` and `--since-tag` choose which commits are in scope; `--summary` independently chooses detailed vs. aggregate display; any combination is valid.
- No `--window` and no `--since-tag`: select the full history of commits touching the baseline file. This is not a truncation default; different invocations without a range flag always see the same complete history.
- No `--summary`: print detailed per-commit rows (the default). With `--summary`, print only the aggregated per-target totals for the selected range (e.g. full history + `--summary` prints one aggregate for the whole file history).

**Predecessor and first-seen rule** (FINDING_4, applies to both detailed and summary modes): compute the full oldest-to-newest per-target value sequence over the *complete* history first, before any `--window`/`--since-tag` filtering. Every selected commit's delta is the difference against the nearest earlier touching revision in that full sequence, even when that earlier revision falls outside the selected range (a `--window 2` or `--since-tag` selection still uses the immediately preceding untouched-by-filter revision to compute its first included delta). A target's first-ever appearance in the full history is never a delta — it seeds that target's tracked value — and is excluded from every summary aggregate and from the `raise` marker, even if the first-appearance commit itself falls inside the selected range.

## Files to modify/create

### NEW: python/larch/lint/skill_closure_ledger.py

Implement the ledger logic and CLI main.

Suggested structure:

- Frozen dataclasses:
  - `BaselineSnapshot`
  - `BaselineRevision`
  - `TargetDelta`
  - `SummaryRow`
- A lenient parser:
  - Accept top-level JSON arrays.
  - Read only rows with `skill: str` and `closure_estimated_tokens: int`.
  - Ignore missing historical fields, extra fields, and targets not present in a revision.
  - Reject invalid JSON and non-array payloads with a clear stderr error.
- Git-backed history loading:
  - Ask `larch.git.git` for commits touching `BASELINE_RELPATH`, oldest to newest.
  - Use `git.show_file()` for each `commit:path`.
  - Compare each revision to the previous revision in history (see Predecessor and first-seen rule above).
- Window filtering:
  - `--window N` selects the last `N` commits that touched the baseline.
  - Compute each selected commit's delta against its immediate previous touching revision, even if that previous revision sits outside the window.
- Tag filtering (FINDING_2, FINDING_1-round-3):
  - `--since-tag TAG` first validates the ref with `git rev-parse --verify '<TAG>^{commit}'`, run with `cwd` set to the resolved `--root` (never the process's ambient working directory), so tag resolution and the subsequent history walk always agree on which repository they read. A ref that does not resolve to a commit exits 2 with a clear stderr message naming the tag.
  - Select commits with the rev-range `<TAG>..HEAD -- <path>` (same resolved `--root` as `cwd`) so git itself computes ancestry (commits reachable from HEAD but not from the tag), rather than a hand-rolled position/date comparison.
- Summary mode:
  - Aggregate selected detailed deltas by target, honoring the Predecessor and first-seen rule above.
  - Print start value, end value, net delta, raise count, largest raise commit, and largest raise delta.
- Output:
  - Detailed TSV header:
    `commit\tpr\tsubject\ttarget\tprevious\tcurrent\tdelta\traise`
  - First-seen rows use empty `previous` and `delta`, with `raise=false`.
  - Summary TSV header:
    `target\tstart\tend\tdelta\traises\tlargest_raise_commit\tlargest_raise_delta`
  - Use short or full SHAs consistently. Prefer full SHA in output for auditability.
- CLI behavior:
  - `--root` defaults to the repository root (same `Path(__file__).resolve().parents[3]` convention as `skill-closure report`) and must be an existing directory, validated the same way as `report`'s `--root`; exits 2 with a stderr message when it is not a directory (FINDING_3). The resolved root is passed as `cwd` to every `log_path_commits()` and `show_file()` call so history reads always target the intended tree, not the process's ambient working directory.
  - `--window` must be a positive integer.
  - `--window` and `--since-tag` are mutually exclusive.
  - Successful reads return 0.
  - Bad args return 2 through argparse.
  - Git, JSON, or history errors return 2 with stderr.

## Edge cases

- Historical rows with missing `review` or `panel-tier` targets must not fail.
- Historical rows with missing content-token or conditional fields must not fail.
- A target appearing for the first time must not show a large false raise.
- A selected first commit still needs the previous touching revision for a real delta.
- Commit subjects without `(#N)` should leave the PR column empty.
- Empty history for the baseline path should fail clearly.
- Deleted or unreadable baseline blobs should fail clearly.
- A `--since-tag` value that does not resolve to a commit should fail clearly (FINDING_2).
- An unresolvable or non-directory `--root` should fail clearly, matching `skill-closure report` (FINDING_3).

## Failure modes

- A strict parser would break on older baseline schemas.
- Window summaries can be wrong if they drop the prior revision needed for the first selected delta.
- Raise markers can create false alarms if first-seen targets are treated as growth.
- Git output parsing can corrupt subjects if delimiters are weak.
- Adding the verb to lint or CI would violate the no-gate scope.
