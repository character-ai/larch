## Findings

### 1. Conditional loads need `require_near` pins (architecture / correctness)

The plan’s **Failure modes** section (plan.txt:156) calls out branch pointers that load too late and says to guard with harness needles near branch bullets. The **Testing strategy** block (plan.txt:133-145) never specifies `require_near`, even though `scripts/test-implement-structure.sh` already uses that API for every-run reads:

```298:305:scripts/test-implement-structure.sh
cleanup_read = '**MANDATORY — READ ENTIRE FILE**: Read `${CLAUDE_PLUGIN_ROOT}/skills/implement/references/step18-cleanup.md` completely.'
require_near(
    skill,
    cleanup_read,
    'bash "$IMPLEMENT_TMPDIR/larch-run.sh" skills/implement/scripts/step-18.sh --phase gate',
    'Step 18 cleanup read before gate fence',
    900,
)
```

Without analogous pins, substring `require()` on the new reference paths is not enough to enforce lazy-load correctness on `oos-pipeline`, `ci-fix`, or eligible Step 18a.5.

### 2. `ship-pr-exit-matrix` duplicate guards are incomplete (correctness)

The plan moves two substantial bodies currently at:

```90:117:skills/implement/references/ship-pr-exit-matrix.md
## OOS checkpoint router
...
## autonomous main-agent CI-fix sub-procedure
...
```

The harness section (plan.txt:139-144) only forbids the old **headings** in `ship-pr-exit-matrix.md`. Unlike Step 18a.5, where `compose-report --report-kind escalation-success` is already a pinned needle in `scripts/test-implement-structure.sh:486`, there are no existing body needles for the OOS router or CI-fix procedure to move. A partial implementation can strip headings and still leave distinctive body tokens in the every-run file.

The branch bullet at `skills/implement/references/ship-pr-exit-matrix.md:46` still says “run the OOS checkpoint router” without naming `ship-pr-oos-checkpoint-router.md`; the plan’s UPDATED section covers the intent but does not require a harness pin on the updated bullet text.
