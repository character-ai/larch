# [BUG] /design leaves lingering shell after completion: plan-review loop round-2 auto-continuation writes stale LOOP_STATUS=complete before session cleanup kills in-flight wait-reviewers

## Context

After every `/design` run that triggers the plan-review loop's **automatic round-2 continuation**, Claude Code reports "1 shell still running" at session end. The lingering shell outlives the session by up to 31 minutes (the `--timeout 1860` given to `agent wait-reviewers`). The bug is confirmed live on the session that produced design run `ED7EA236-294D-49F3-98E3-1EE27DE04DE0` (issue #3690 design, 2026-06-14).

## Symptoms

- `"1 shell still running"` notice in the Claude Code harness after `/design` completes.
- `ps aux` after the session shows a chain of processes that outlive the session tmpdir cleanup:

```
PID 68978  design-step3-review.sh  (blocked on `wait 69006`)
PID 69006  python3 cli.py plan-review run --mode loop  (blocked on subprocess)
PID 69014  run-step3-review.sh --mode loop  (blocked on plan-review-loop.sh)
PID 72798  plan-review-loop.sh --round-num 2  (blocked on cmd substitution)
PID 91811  plan-review-loop.sh subshell  (cmd substitution fork)
PID 91812  collect-agent-results.sh --paths-file ... (blocked on WAIT_OUTPUT=$(...))
PID 91824  collect-agent-results.sh subshell  (cmd substitution fork)
PID 91825  python3 cli.py agent wait-reviewers --timeout 1860 \
             .../cursor-plan-arch-output.txt.done \
             .../cursor-plan-innovation-output.txt.done \
             .../cursor-plan-pragmatic-output.txt.done \
             .../cursor-plan-requirements-output.txt.done \
             .../codex-plan-generic-output-phase3.txt.done
```

- The four Cursor `.done` files no longer exist — they were deleted by Step 6 `session cleanup-tmpdir` before `agent wait-reviewers` found them.
- `agent wait-reviewers` polls every 5 s, never finds the files, and runs until its 1860 s timeout.

## Root Cause (confirmed by live process inspection)

### Step 1 — Round 1 completes and writes `.step3-review-result.env`

Inside `run-step3-review.sh --mode loop`, `run_step3_round_body` calls `plan-review-loop.sh` and, at the end of the body, `phase_driver_write_result_env "$RESULT_ENV"` writes:

```
LOOP_STATUS=complete
ROUNDS_COMPLETED=1
REVIEW_ROUND_COUNT=1
```

to `$DESIGN_TMPDIR/.step3-review-result.env`.

### Step 2 — The continuation heuristic immediately starts round 2

`run_design_step3_loop()` in `review-design-step3-loop.sh` calls `step3_loop_run_continuation`, which invokes `plan-review-continuation.sh`. Because round 1 accepted 5 findings, `PLAN_REVIEW_CONTINUE=true` is returned. The loop then executes:

```bash
round_num=$((10#$round_num + 1))
continue   # ← top of while true; dispatches round 2
```

At this point `.step3-review-result.env` **already exists** with `LOOP_STATUS=complete`, but round 2 has not been written yet.

### Step 3 — The orchestrator's completion waiter fires on the stale file

The SKILL.md explicitly warns: *"NEVER poll `.step3-review-result.env` with a sleep loop … It can leave the task registered as running. It can block session exit until `TaskStop`."*

However, when `design-step3-review.sh` sent a spurious `<task-notification>` (see § Contributing factors below), the orchestrator launched the sanctioned one-time completion waiter:

```bash
until [ -f .../claude-design-larch1-6j3blpuz/.step3-review-result.env ]; do sleep 30; done
```

This waiter fired on the **stale round-1 result**. The orchestrator read `LOOP_STATUS=complete` and proceeded past Step 3, through Steps 3b → 4 → 4b → 5b → 5c → **6 (cleanup)**.

Meanwhile, `python3 cli.py plan-review run --mode loop` (PID 69006) is still in the middle of round 2: it has already dispatched Cursor reviewers and launched `collect-agent-results.sh`, which launched `agent wait-reviewers --timeout 1860` polling for the four Cursor `.done` files.

### Step 4 — Session cleanup deletes the `.done` files that round 2 needs

`design-step6-cleanup.sh` runs `session cleanup-tmpdir`, which deletes the entire session tmpdir `claude-design-larch1-6j3blpuz/`. This removes:

- `cursor-plan-arch-output.txt.done`
- `cursor-plan-innovation-output.txt.done`
- `cursor-plan-pragmatic-output.txt.done`
- `cursor-plan-requirements-output.txt.done`

`agent wait-reviewers` (PID 91825) continues polling `Path(sentinel).is_file()` for up to 1860 seconds, but the files will never reappear. The entire chain — `design-step3-review.sh` → `plan-review run --mode loop` → `run-step3-review.sh` → `plan-review-loop.sh --round-num 2` → `collect-agent-results.sh` → `agent wait-reviewers` — stays blocked until the 1860 s timeout expires.

`design-step3-review.sh` (PID 68978) is the process Claude Code tracks as the background task (`bsdgsb8ri`). It is still alive. Hence the "1 shell still running" message.

## Contributing Factors

1. **Spurious `<task-notification>`** for `design-step3-review.sh` (task `bsdgsb8ri`) fired while round 1 was still in progress. This caused the orchestrator to fall into the sanctioned-waiter exception (SKILL.md: "exactly one `Bash run_in_background` task with `until <completion-condition>; do sleep N; done`").

2. **Wrong completion sentinel**. The waiter used `.step3-review-result.env` existence as the condition. This file is written after each round's body — not only at final loop exit. The correct sentinel for "loop fully done" is `.completed/step-3`, which `step3_loop_write_completed_step3` writes **only** in `step3_loop_emit_envelope complete` at the final iteration.

3. **`session cleanup-tmpdir` does not kill in-flight processes before deleting the tmpdir**. `kill_session_background_processes` is called from `design-step3-review.sh`'s cleanup trap, but that trap only runs *after* `wait "$_loop_pid"` returns. Since the loop is blocked waiting for round 2's collect, the trap never fires before cleanup.

## Suggested Fix (two independent approaches; either one suffices)

### Fix A — Correct the completion sentinel (minimal, recommended)

In `SKILL.md` and the sanctioned completion waiter exception path, change the polling condition from `.step3-review-result.env` to `.completed/step-3`:

```bash
# WRONG (used today):
until [ -f "$DESIGN_TMPDIR/.step3-review-result.env" ]; do sleep 30; done

# CORRECT:
until [ -f "$DESIGN_TMPDIR/.completed/step-3" ]; do sleep 30; done
```

`.completed/step-3` is written by `step3_loop_write_completed_step3()` inside `step3_loop_emit_envelope`, which runs only at the loop's terminal iteration. It is not written on round-N intermediate completions. This matches the orchestrator's intended "Step 3 is truly done" semantic.

Additionally, document that `design-step3-review.sh`'s expected exit — which produces the `<task-notification>` — should also be the production signal, and the waiter is only a recovery path.

### Fix B — Clear `.step3-review-result.env` before starting round 2 (defensive, belt-and-suspenders)

In `run_design_step3_loop()` in `review-design-step3-loop.sh`, before `round_num=$((round_num + 1)); continue`, delete or rename the result env:

```bash
rm -f "$DESIGN_TMPDIR/.step3-review-result.env" 2>/dev/null || true
round_num=$((10#$round_num + 1))
continue
```

This prevents any waiter from mis-triggering on a stale round-1 result. Round 2 will overwrite the file when it completes.

### Fix C — Kill in-flight processes before session cleanup (deeper, orthogonal)

In `session cleanup-tmpdir` (or in `design-step6-cleanup.sh` before calling it), call `python3 cli.py session kill-background-processes --design-tmpdir "$DESIGN_TMPDIR"` **before** deleting the directory. This ensures `agent wait-reviewers` processes are terminated before their files are removed, regardless of how the orchestrator behaved.

This is complementary — it would prevent the zombie-chain even when Fixes A and B are applied, as a safety net.

## Files Involved

- `skills/design/scripts/review-design-step3-loop.sh` (embedded in `python/plan_review.py`) — Fix B
- `skills/design/SKILL.md` Step 3 sanctioned waiter exception — Fix A
- `skills/design/scripts/design-step6-cleanup.sh` — Fix C
- `python/finalize.py` `kill_session_background_processes` — Fix C (verify it runs before tmpdir deletion)

## Definition of Done

- After a `/design` run that triggers round-2 auto-continuation, no lingering shell is reported.
- The completion waiter (when needed) triggers only when `step3_loop_write_completed_step3` has run, not on intermediate round writes.
- `session cleanup-tmpdir` kills in-flight processes before deleting files (or the waiter no longer uses a sentinel that goes stale).
