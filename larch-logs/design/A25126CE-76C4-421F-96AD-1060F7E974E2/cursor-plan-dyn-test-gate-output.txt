### Findings

1. **correctness** — `python/test_finalize_bash_parity.py:64-68`: The proposed fail-closed sentinel cannot live in the same module as `pytestmark = pytest.mark.skipif(...)`. Pytest applies module marks to every test in the file, so any future broad skip condition (the current script-exists pattern at lines 19–22) would skip the guard as well and `make py-test` would stay green without running parity. Put the guard in a separate always-collected module.

2. **correctness** — `python/test_run_logs.py:483-497`: The plan rewrites `load_or_recover_manifest` recovery semantics in `python/run_logs.py` but does not list `test_run_logs.py`. Today, a missing manifest with no run directory falls through to `init_run()` (lines 343–344) without `recovery_reason`; existing tests would not catch absent-run-dir recovery or `recovery_ok=false` propagation to teardown/ship.

3. **correctness** — `python/ship.py:425-435`: The `pr_closed` / flush gating fix is production-critical, yet the testing strategy names only `test_finalize.py`, `test_finalize_bash_parity.py`, and `test_ci_monitor.py`. `test_ship.py` already exercises postmerge ordering with mocked `postmerge` (lines 147–175) but nothing asserts flush suppression for OK-but-not-closed skip paths.

4. **risk-integration** — plan parity approach vs `scripts/test-implement-finalize.sh:134-140`: The plan points at the implement-finalize sandbox, which stubs `local-cleanup.sh` and emits canned KVs. After porting cleanup inline to `_local_cleanup`, that parity shape never exercises the orphan flush-reset logic guarded in `scripts/local-cleanup.sh:77-110`, which `scripts/test-local-cleanup.sh` covers with real git repos. Stub-leaf parity would not catch the plan’s own “cleanup reset safety” failure mode.

5. **architecture** — plan.txt:64-66: Side-by-side parity requires bash stdout KVs and Python `FinalizeResult` fields to reflect the same stubbed git/gh world. The plan does not define a shared scenario/fixture builder; bash subprocess env stubs and `RecordingRunner` response queues must be maintained independently, which is a common source of false-green parity.
