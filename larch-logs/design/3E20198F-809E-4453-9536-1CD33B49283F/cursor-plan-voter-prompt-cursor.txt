# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `blocker` or `major`. Single-YES `minor`, `nit`, `uncertain`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

After a successful merge + local cleanup (`git checkout main`), the `/implement` final-summary section "Architectural guidelines" always displays "The architectural guideline note was dropped because HEAD drifted after staging." even though the note WAS correctly included in the PR body. The root cause is that `_architectural_guidelines_section` in `final_report.py` calls `note_consumable(head_sha=&lt;current HEAD&gt;)`, but after `git checkout main` in `finalize.py`'s `_local_cleanup`, the current HEAD is the `main` tip — which never equals the feature-branch-tip SHA stored as `HEAD_SHA` in the durable note. The mismatch triggers `_persist_drop_notice_and_invalidate`, which clears the durable note and records the spurious drop notice.

## Original report

&gt; The architectural guideline note was dropped because HEAD drifted after staging.

This message appeared in the `## Architectural guidelines` section of the `/implement` final summary on a run that merged cleanly with no CI fix, no rebase, no conflict resolution, and a valid assessment that was staged during Phase A.

## Reproduction scenario

## Root cause analysis

`note_consumable` (in `architectural_guidelines.py`) enforces `metadata.get("HEAD_SHA") == head_sha`. This strict equality check is correct during the ship loop — it prevents showing a stale note when the implementation branch has advanced. However, it is too strict for the **post-merge final report context**, where:

- The ship driver has already pinned the note at HEAD = B and embedded it in the PR body.
- The local cleanup switched to `main`, making HEAD ≠ B.
- `_architectural_guidelines_section` in `final_report.py` calls `note_consumable` with the now-different HEAD and concludes (incorrectly) that the note was never valid.

The `_local_cleanup` function in `finalize.py` (`git checkout main`, line 236) is the proximate cause of the HEAD change. This is expected behavior. The bug is that `_architectural_guidelines_section` does not account for the post-merge HEAD change.

## Evidence

- `note_consumable` (`architectural_guidelines.py:588-595`): returns `True` only when `metadata.get("HEAD_SHA") == head_sha`.
- `_local_cleanup` (`finalize.py:236`): runs `git checkout main` during postmerge, changing the working-tree HEAD.
- `_architectural_guidelines_section` (`final_report.py:218-244`): enters `_persist_drop_notice_and_invalidate` when `has_guideline_artifacts and not consumable`, which is always `True` after local cleanup.
- The ship driver's `_pin_and_load_guidelines_note` at line 1988 in `ship.py` runs BEFORE `git checkout main`, so it succeeds when called with the feature-branch HEAD. The PR body correctly includes the note. The problem is only in the final-report rendering step.
- Confirmed: in the triggering run, breadcrumbs show only `pr-prep: postbump/Flush+Push` — no rebase, no CI fix, so `_invalidate_guidelines_note` was never called. The durable note was intact; only the HEAD check failed.
- `ARCHITECTURAL_GUIDELINES_PIN_STATUS=skipped` in step-16-17 output confirms that `pin_note_from_staged` returned `False` when called on main HEAD (fingerprint of empty diff on main ≠ implementation diff fingerprint).

## Affected files

- `python/larch/report/final_report.py` — `_architectural_guidelines_section` is the primary fix site; it should not treat a post-merge HEAD change as a genuine "drift" condition.
- `python/larch/core/architectural_guidelines.py` — `note_consumable` and optionally a new `note_readable_post_merge` variant that skips the HEAD_SHA equality check.

## Suggested fix(es)

**Option A (minimal):** In `_architectural_guidelines_section`, before calling `_persist_drop_notice_and_invalidate`, check whether the durable note is present and a `post-merge-sentinel` file exists in `implement_tmpdir`. If post-merge, read the durable note directly regardless of HEAD_SHA mismatch; skip `_persist_drop_notice_and_invalidate`. This scopes the fix to the one context where the HEAD change is expected.

**Option B (slightly broader):** Add a `note_readable_any_head(implement_tmpdir) -&gt; bool` helper that checks only `STATUS == "present"` without the HEAD_SHA check. Use it in `_architectural_guidelines_section` as a fallback when `not consumable and durable_present` to read and display the note anyway. Keep `note_consumable` unchanged so it still guards the ship-loop "is this note still valid for the current diff?" question.

Either option should avoid calling `_persist_drop_notice_and_invalidate` when the only reason for non-consumability is post-merge HEAD drift (local checkout to main), not genuine implementation change.
