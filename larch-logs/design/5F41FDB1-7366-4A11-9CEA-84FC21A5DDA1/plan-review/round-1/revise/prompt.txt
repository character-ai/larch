# [BUG] Step 5c publish validator: false missing-script for consumer-repo scripts

## Summary

`/design` Step 5c composed-plan validation emits false-positive `missing-script` defects (`VALIDATE_STATUS=defects-found`, `PUBLISH_RC=4`) for repo-relative plan-command scripts that **exist in the consumer repo** but are absent from the version-pinned plugin cache. The publish tail `python/design_publish.py` validates `composed-plan.md` with `--repo-root str(plugin_root)`, so the validator's dual-root existence check never sees the consumer repo where the scripts live.

This is the **Step 5c publish-tail site** of the #4490 family, and it is **still broken after #4847**. #4847's fix (#4863, shipped in 51.1.10) covered only the plan-review-loop site (`python/plan_review.py`); it did **not** touch `design_publish.py`, even though a comment on #4847 ("Second manifestation: Step 5c publish validation") documented this exact site and said a complete fix "should cover **both** sites." So this is an incomplete-fix recurrence: the same `_consumer_repo_root()` correction that `design_postplan.py` already carries was never applied to `design_publish.py`.

## Original report

the root cause of Step 5c composed-plan validation reported 2 `missing-script` defects for `scripts/test-implement-anti-polling-rule.sh` and `skills/fluff-analysis/scripts/test-fluff-analysis.sh`.

(Observed on a live `/design` run on issue #4865, larch 51.1.10, plugin loaded from the version-pinned cache.)

## Reproduction scenario

1. Install/load larch as a plugin from the version-pinned cache (e.g. `~/.claude/plugins/cache/.../larch/&lt;version&gt;/`), so the cache lacks consumer-repo files added after the release was cut. Confirmed for this run: the cache lacked both scripts and was not even a git repo.
2. Run `/design &lt;issue&gt;` in a consumer repo (here, the larch source tree) whose plan's `## Testing strategy` fence references existing repo scripts, e.g.:
   ```bash
   bash scripts/test-implement-anti-polling-rule.sh
   bash skills/fluff-analysis/scripts/test-fluff-analysis.sh
   ```
3. Step 2b drafter validation: `VALIDATE_STATUS=ok` (clean — `design_postplan.py` carries the fix).
4. Approve at Gate C; Step 5c publish runs.
5. Step 5c composed-plan validation reports `VALIDATE_STATUS=defects-found`, `VALIDATE_DEFECT_COUNT=2` (both `kind=missing-script`), `PLAN_WRITE_OK=false`, `PUBLISH_RC=4`, `STEP5C_STATUS=validator-defects`, blocking the `larch:plan` write until the operator Overrides (`design-step5c.sh --skip-validate`).

The two scripts exist in the consumer repo, so the defects are false positives.

## Expected behavior

Step 5c composed-plan validation should resolve repo-relative plan-command scripts against the **consumer repo** (with the plugin cache as the secondary dual-root for plugin-only scripts), exactly as the Step 2b postplan does. A plan referencing existing consumer-repo scripts should validate clean at Step 5c, identical to Step 2b. No spurious `defects-found` / `PUBLISH_RC=4` / operator Override.

## Observed behavior

Step 5c validation checks only the plugin root. Because the plugin cache lacks the consumer repo's test scripts, existing scripts resolve as `missing-script`, producing `defects-found` and blocking publish. Auto-repair is actively harmful here: the only way a vendor can make the false positive "pass" is to delete the valid `bash …test-*.sh` commands from the plan, so the operator must Override instead.

## Root cause analysis

`python/design_publish.py` `publish_core` validates `composed-plan.md` by invoking `python/cli.py plan validate` with `--repo-root str(plugin_root)`:

```python
# python/design_publish.py (composed-plan validation block, ~line 244-256)
"plan", "validate",
"--plan-file", str(composed_plan),
"--source-kind", "composed",
"--design-tmpdir", str(design_tmpdir),
"--repo-root", str(plugin_root),   # &lt;-- PLUGIN root, not consumer repo
```

`python/plan_quality.py` `_resolve_repo_script(script, repo, plugin)` builds its roots from `repo` (= the passed `--repo-root`) then `plugin` (= `_plugin_root`, resolved from `CLAUDE_PLUGIN_ROOT`). When `--repo-root` is the plugin root, both roots collapse to the plugin cache, so the consumer repo is never checked and a consumer-only script returns `missing-script`. The #4490 dual-root existence check is defeated because the consumer repo is absent from the roots list.

`python/design_postplan.py` (Step 2b postplan) does this correctly:

```python
# python/design_postplan.py:215-227
validate_env["CLAUDE_PLUGIN_ROOT"] = str(root)
repo_root_arg = _consumer_repo_root() or root   # git toplevel of cwd = consumer repo
... "--repo-root", str(repo_root_arg), env=validate_env
```

`_consumer_repo_root()` (`design_postplan.py:26`) returns the git toplevel of cwd (the consumer repo) and its docstring cites #4490 verbatim. `design_publish.py` has no equivalent — it passes `str(plugin_root)` unconditionally, so the same class of false positive recurs at the publish gate.
