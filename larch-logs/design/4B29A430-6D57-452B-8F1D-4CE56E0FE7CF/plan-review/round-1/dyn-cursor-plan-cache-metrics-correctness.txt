## Findings

**1. [correctness / risk-integration]** `python/larch/report/tokens.py:1307-1308`, `python/larch/report/report_tokens_scan.py:290-302`, proposed `measure_cache_efficiency()`

The plan reuses `report_tokens_scan.scan()` for inputs (git-resolved consumer repo) but follows existing `measure_*_main` wrappers that resolve output relative to `tokens._repo_root()` (`Path(__file__).resolve().parents[3]`). `/report-tokens` already uses `ScanResult.repo_root` for scan-backed work (`report_tokens_cli.py:69-69`). A scan-backed measure command that writes via `_repo_root()` will read consumer `larch-logs` and emit `larch-logs/measure-cache-efficiency/<date>.tsv` under the plugin tree in normal installs.

**Suggested revision:** Resolve the output directory from the first `scan()` result’s `repo_root`; print `WROTE\t<relpath>` against that same root. Update `test_measure_cache_efficiency_main_prints_relative_path` to assert that contract instead of monkeypatching `_repo_root()`.

**2. [correctness]** `python/larch/report/tokens.py:436-448`, `529-531`; plan `_cache_create_effective`

Split-bucket fallback is under-specified. `_totals()` always adds `cache_create_5m` / `cache_create_1h` keys to per-step totals, often as zero, while vendor `claude_sub` ledger rows only populate `cache_create` (`_TOKEN_FIELDS` at `tokens.py:26`). `RunRecord.claude_sub` from scan can show `cache_create_5m=0` with `cache_create>0` because `_totals()` in `report_tokens_scan.py:95-99` prefers an explicit zero in `totals` over `BUCKETS_*` (`report_tokens_scan.py:101-106`). If `_cache_create_effective` sums splits whenever keys exist, `claude_sub` create volume becomes zero, all-zero rows vanish, and zero-read / nonzero-create `inf` outliers on that lane are lost.

**Suggested revision:** `effective = (cache_create_5m + cache_create_1h) if (cache_create_5m + cache_create_1h) > 0 else cache_create`. Document this for vendor `claude_sub` per-step rows, not only legacy reports missing split keys.

**3. [correctness]** Proposed `_measure_cache_efficiency_records`; `python/tests/report/test_tokens.py` (planned tests)

Per-step ranking should reflect corpus-level create/read imbalance per `(skill, step, lane)`. The plan sums buckets across runs but does not require ratio-after-aggregation. Averaging per-run ratios or ranking intermediate rows would change order versus `sum(create_eff)/sum(read)`, which is what the issue asks for when flagging recurring bad steps.

**Suggested revision:** Sum cache fields in the aggregator, compute ratio once on aggregated totals, then rank. Add one assertion that two runs with different per-run ratios produce the aggregated ratio from summed numerators/denominators.

---

**What looks sound (no finding):** Local `report_tokens_scan` import avoids the `tokens.py` import cycle (`report_tokens_scan.py:16`). `resolve_repo=False` keeps measurement free of `gh` (`report_tokens_scan.py:288-291`). Reading `raw_report[<lane>]["per_step"]` instead of `phase_rows` is required because `PhaseRow` omits split buckets (`report_tokens_scan.py:152-159`). Ranking rules (all-zero exclusion, zero-read `inf` first, stable tie-break) match the stated goal. Scope stays measurement-only; no capture-path or CI creep.
