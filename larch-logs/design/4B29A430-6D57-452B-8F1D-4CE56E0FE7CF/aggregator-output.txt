### FINDING_1: Merged scan records must carry scan-origin skill
- **Reviewer(s)**: Cursor-Arch, Codex-Arch, Cursor-Innovation, Cursor-Pragmatic, Codex-Pragmatic, Cursor-Requirements
- **Severity**: important
- **Concern**: `RunRecord` stores issue metadata and vendor totals but not skill; `report_tokens_scan._workflow` always returns `""`. The plan concatenates design and implement `ScanResult.records` and groups per-step rows by `(skill, step, lane)`, yet helper signatures omit a `skill` argument and `measure_cache_efficiency()` only says to concatenate records. A flat merge loses which scan produced each record, so per-run `skill` cells can be blank or wrong and homonymous steps (e.g. design `3` vs implement `3`) fuse across skills. That corrupts `runs`, summed buckets, and outlier ranks in both TSV sections.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Arch: Mirror `report_tokens_cli.py`: iterate each `scan(runner, skill=..., resolve_repo=False)` separately and thread `skill` into `_cache_efficiency_step_rows_for_record` / `_measure_cache_efficiency_records` (e.g. `(skill, record)` pairs). Emit per-run `skill` from that binding, not from `RunRecord`. Add a unit test with the same step name in design and implement asserting separate per-step rows.
  - From Codex-Arch: Carry records as `(skill, RunRecord)` pairs, or an equivalent small wrapper, from each scan through `_measure_cache_efficiency_records`.
  - From Cursor-Innovation: Iterate each scan with its skill label (for skill, scan_result in (("design", design_scan), ("implement", implement_scan)): for record in scan_result.records: ...) or build list[tuple[Skill, RunRecord]] before _measure_cache_efficiency_records; pass skill into per-run and per-step builders. Add a unit assertion that design and implement records with the same step name stay in separate per_step groups.
  - From Cursor-Pragmatic: When merging scans, bind each record with the `skill` argument passed to `report_tokens_scan.scan()` (e.g. `list[tuple[Skill, RunRecord]]`); thread that `skill` through `_cache_efficiency_step_rows_for_record`, per-run row construction, and per-step aggregation; add a unit test with the same step label under both skills asserting two distinct per-step rows.
  - From Codex-Pragmatic: Carry the scan skill with each record, for example list[tuple[Skill, RunRecord]], and build both per-run rows and per-step aggregation keys from that preserved skill.
  - From Cursor-Requirements: In `measure_cache_efficiency()`, iterate `for skill in ("design", "implement")`, scan each skill, and accumulate tagged pairs such as `(skill, record)` (or an internal row type carrying `skill`). Pass `skill` into `_cache_efficiency_step_rows_for_record` and per-run row builders so every emitted row and bucket key includes the scan-origin skill before `(skill, step, lane)` aggregation.

### FINDING_2: Per-step effective-create aggregation drops legacy combined creates in mixed groups
- **Reviewer(s)**: Codex-Arch, Codex-Innovation, Codex-Requirements
- **Severity**: important
- **Concern**: The plan sums raw `cache_create`, `cache_create_5m`, and `cache_create_1h` across runs in a `(skill, step, lane)` group, then applies `split_sum if split_sum > 0 else cache_create` on the grouped totals. Committed reports can mix split-bucket rows and legacy combined-only `cache_create` rows for the same skill, step, and lane. Once `split_sum > 0`, legacy combined-only create tokens from other runs in that group are discarded from the ratio numerator, so mixed-history groups are under-ranked.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Codex-Arch: Sum raw TSV columns as planned, but also accumulate an effective-create contribution per per-step record using `_cache_create_effective`; compute the grouped ratio from `sum_effective_create / sum_cache_read`.
  - From Codex-Innovation: For per-step groups, accumulate an effective_create_sum by applying _cache_create_effective to each contribution before adding it. Keep raw bucket sums for TSV columns. Compute ratio and sort from effective_create_sum over summed cache_read. Update the aggregate test to mix one split row with one legacy combined-only row.
  - From Codex-Requirements: Keep summing raw bucket columns for TSV output, but add a separate effective_cache_create_sum accumulator. For each per-step contribution, compute split_sum if split_sum > 0 else cache_create, add that to the accumulator, and compute the per-step ratio from effective_cache_create_sum divided by summed cache_read. Extend the aggregation test with one split contribution plus one legacy combined-only contribution in the same group.

### FINDING_3: Per-step bucket reads must use each item's nested totals mapping
- **Reviewer(s)**: Cursor-Innovation
- **Severity**: important
- **Concern**: Committed reports store `per_step` entries as `{"step": "...", "totals": {...}}` (see `tokens._per_step_json` and `report_tokens_scan._phase_rows`). The plan points at `raw_report[lane]["per_step"]` but does not require drilling into `totals`. Passing the row object into `_cache_lane_totals_from_mapping` yields zero cache fields and drops or mis-ranks every per-step outlier.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Innovation: In _cache_efficiency_step_rows_for_record, read step from item["step"] and pass _as_mapping(item.get("totals")) into _cache_lane_totals_from_mapping; skip rows with missing/non-object totals. Extend the per-step aggregation test to use nested totals dicts.
