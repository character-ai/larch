Pre-existing latent defects in design-log-publish flush path (surfaced during #3413 review)

## Summary

Four pre-existing latent defects surfaced during code review of #3413 (re-enable `/design` run-log flush + fix `--admin` merge gate). These are independent of the #3413 changes and require separate follow-up.

---

### FINDING_17: `design-publish.sh` may trust `PUBLISH_OK=true` despite non-zero publish exit

**Concern**: If `design-log-publish.sh` exits non-zero while stdout still contains `PUBLISH_OK=true`, the envelope parsing in `design-publish.sh` may accept it as success and proceed to rename/cleanup — bypassing the failure branch.

**Suggested fix**: explicitly check the exit code alongside the `PUBLISH_OK=true` envelope, or pipe `design-log-publish.sh` through a wrapper that enforces fail-closed on non-zero exit before publishing `PUBLISH_OK`.

**Vote tally**: YES=2 NO=0 EXON=1 (accepted)

---

### FINDING_11: direct `design-log-publish.sh --repo` argument lacks `validate_repo`

**Concern**: Direct invocations of `scripts/design-log-publish.sh --repo OWNER/REPO` bypass the stricter `validate_repo` function used upstream in `design-publish.sh`, so a malformed repo argument could silently target the wrong repository.

**File**: `scripts/design-log-publish.sh` (repo argument validation at entry)

**Suggested fix**: add `validate_repo`-style validation at the entry of `design-log-publish.sh` to match the strictness of its callers.

**Vote tally**: YES=3 NO=0 EXON=0 (accepted)

---

### FINDING_25: step registry advances past publish failure

**Concern**: `design-publish.sh` writes `.completed/step-5c` when `PLAN_WRITE_OK=true` even if `PUBLISH_OK=false`. This allows pause/resume flows to advance past the publish step rather than retrying it.

**File**: `skills/design/scripts/design-publish.sh` (step completion registry)

**Suggested fix**: gate `.completed/step-5c` write on `PUBLISH_OK=true`, or use a separate registry key so failed publishes can be retried on resume without advancing the orchestrator state.

**Vote tally**: YES=3 NO=0 EXON=0 (accepted)

---

### FINDING_4: missing `SESSION_ID` renders approved summary

**Concern**: When `SESSION_ID` is empty, the publish step is skipped entirely, but the post-publish `render-final-summary.sh --post-publish-only` call can still render an "approved" summary — potentially confusing operators who see approval without any actual publish completing.

**File**: `skills/design/scripts/design-publish.sh`, `skills/design/scripts/render-final-summary.sh`

**Suggested fix**: pass a `--publish-skipped` / `failed-publish` variant flag to `render-final-summary.sh` when `SESSION_ID` is missing so the rendered summary reflects the actual publish outcome.

**Vote tally**: YES=3 NO=0 EXON=0 (accepted)

---
