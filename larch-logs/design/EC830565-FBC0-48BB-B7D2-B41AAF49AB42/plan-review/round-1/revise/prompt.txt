# bug-treadmill [FEATURE] Shared lint engine for python/larch/lint rule modules

​#### Problem

Every custom lint is a standalone application. As of 2026-07-11:

- `python/larch/lint/` holds 43 Python modules totaling ~15.9k lines.
- The three lints added by #6873 are `lint_markdown_heading_fence_state.py` (873 lines), `lint_unreachable_branch.py` (820), and `lint_self_disarmable_gate.py` (552). All three define their own `argparse` CLI and their own `--baseline` / `--write-baseline` handling. Spot-checks of `lint_unreachable_branch.py` and `lint_markdown_heading_fence_state.py` show no imports from the `larch.lint` package at all.
- `lint_common.py` exists (114 lines) but the newest lints do not use it.
- 15 modules implement their own baseline I/O against sibling `python/*-baseline.json` files.
- Four more standalone lints landed the same week: #6619 (monkeypatch facade binding), #6622 (lifecycle prefix literal), #6750 (suppression reason), #6675 (two regression ratchets).

The cost is double. Each new prevention proposal from `/learn-from-bugs` lands as 550-900 lines instead of ~100. And plumbing duplicated 40+ times is the same defect class as #6632 / #6672 (one grammar, two diverging parsers): suppression grammar, baseline schema, discovery scope, and output format can each drift per module.

​#### Goal

A new lint rule is a detect function plus a registration entry, roughly 100-250 lines including tests hooks, instead of 550-900.

​#### Required design

Create `python/larch/lint/engine.py` following the repo's guidelines (frozen dataclasses per G-Py-1, injected Runner per G-Py-7, fail loudly per G-Py-4):

1. Data model.
   - `Finding`: frozen dataclass with `path`, `line`, `rule_id`, `message`, optional `qualified_symbol`, optional `metric`.
   - `SourceFile`: frozen dataclass with `path`, `text`, `lines`, and a lazy `ast` property for `.py` files. Syntax-error policy is a rule option: `fail` (emit a finding) or `skip`.
   - `LintRule`: frozen dataclass with `rule_id`, `description`, `pathspecs` (git pathspecs), `detect(SourceFile) -&gt; Iterable[Finding]`, optional `pragma_token` override, `syntax_error_policy`.
2. Discovery. Enumerate files with `git ls-files -- &lt;pathspecs&gt;` through the injected Runner. No `os.walk`.
3. Suppression. One canonical same-line pragma: `# lint-&lt;rule-id&gt;: ok &lt;reason&gt;`. A non-empty reason is required for the suppression to count. `pragma_token` lets a ported rule keep its previously documented token for back-compat.
4. Baselines. One loader/writer supporting the two existing shapes: symbol-metric entries (`{file, code, qualified_symbol, metric}`, the complexity style) and generic finding-key entries. Stable sort order on write so diffs stay minimal. A finding absent from the baseline fails. A baseline entry with no matching finding is reported as stale (warning by default; `--strict-stale` fails). Rules without a baseline are supported.
5. CLI. `run_rule(rule, argv) -&gt; int` handling `--paths`, `--baseline`, `--write-baseline`, `--strict-stale`. Output one finding per line: `path:line: RULE_ID message`. Diagnostics go to stderr. Exit 0 clean, 1 findings, 2 usage.
6. Registration stays as-is. Each rule module keeps a thin `main(argv)` that calls `run_rule`, keeps its `("lint", "&lt;name&gt;")` entry in `python/larch/cli.py`, and keeps its `lint-&lt;name&gt;` / `test-lint-&lt;name&gt;` Makefile pair. No CI workflow changes.
