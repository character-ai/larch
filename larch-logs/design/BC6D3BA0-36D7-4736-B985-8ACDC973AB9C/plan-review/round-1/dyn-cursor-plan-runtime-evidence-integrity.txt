## Findings

### 1. Harness coverage gaps must be manifest-wide (major, correctness)

The plan stores orchestration gaps per selected fix in `RuntimeResult`, but `render_report` already walks every manifest bundle when building the Issues table (`python/larch/issue/analyze_bugs.py:2604-2620`). With `--runtime-max` default 10, only those fixes get runtime rows. Issues 11–200 with unmapped orchestration touches would never appear in the coverage-gap list, which breaks acceptance criterion 2.

**Suggested revision:** compute `Harness coverage gaps` from all bundles’ `touched_files` at report time; use runtime rows only for executed pytest/harness evidence.

### 2. Budget pool should exclude zero-executable fixes (major, correctness)

The plan sorts by newest `fix_time` among fixes with `fix_sha` but does not exclude fixes with no pytest files and no mapped harness targets. Those fixes would consume budget slots with absent-only evidence while newer executable fixes are skipped, without ever earning `RUNTIME`.

**Suggested revision:** define eligibility as fixes with at least one executable check before applying `--runtime-max`.

### 3. Pin per-invocation timeout default (major, correctness)

`config.py` defines `SUBPROCESS_DEFAULT_TIMEOUT_SEC = 1800` (`python/larch/core/config.py:155`). The plan adds a runtime timeout constant but no numeric default. Inheriting 1800s per pytest/harness call is unsafe for a coordinator running up to 10 fixes.

**Suggested revision:** add a smaller `ANALYZE_BUGS_RUNTIME_TIMEOUT_SEC` (or similar) and classify timeouts via `PROC_TIMEOUT_EXIT_CODE` (124).

### 4. Tie-break key unspecified (minor, correctness)

Analytics already uses `(fix_time, issue)` for deterministic ordering at `python/larch/issue/analyze_bugs.py:1751`. The plan requires deterministic ties but does not name the secondary key for runtime selection.

**Suggested revision:** document `(-fix_time, issue_number)` before truncation.

### 5. Mapped harness required for promotion (minor, correctness)

Promotion text focuses on “discovered checks” but not on required harness targets when mapped prefixes match touched paths. That leaves room to promote on pytest alone while skipping a mapped `make` target.

**Suggested revision:** require all resolved harness targets to pass when any touched path matches `HARNESS_MAP`.

---

**Contracts the plan gets right:** failures/timeouts become `SUSPECT` evidence without aborting later fixes; stale identity via issue/cache key/SHA; path safety with pytest `--` and constant-owned make targets; timeout classification via `PROC_TIMEOUT_EXIT_CODE`; absent/skipped execution must not grant `RUNTIME`; malformed artifacts fail loudly while command failures do not fail the runtime CLI.
