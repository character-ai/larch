## Approach

Add a coordinator-only runtime stage after ledger/deep processing and immediately before the single final report. Do not render or persist an interim report before runtime evidence exists.

Select the newest eligible **unique fix SHAs** by `fix_time`, up to `--runtime-max`. Execute each selected SHA once, then fan its shared result out to every matching manifest issue/cache-key binding.

For each selected fix SHA:

- Discover added or modified `python/tests/` files from the fix commit.
- If validated discovered test paths are nonempty, run exactly those files together with `python3 -m pytest -p no:cacheprovider --basetemp &lt;run-dir-owned-path&gt; -- &lt;paths&gt;`, using a timeout and option-safe argv. Never invoke pytest without paths.
- If no runnable discovered tests remain, record test evidence as absent without running pytest.
- Resolve touched orchestration paths against a declarative prefix-to-make-target map.
- Run each deduplicated mapped target with `make` and a timeout.
- Persist bounded pass, fail, timeout, or absent evidence in `runtime-results.jsonl`.

Bind every result to all current manifest issue identities, cache keys, and the unique fix SHA. The report must reject runtime evidence from stale bindings and never reuse it for a current bundle.

A runtime failure overrides static and deep-truncation handling: it produces verdict `SUSPECT`, tier `RUNTIME`, and a bounded, single-line evidence reason. A passing runtime execution promotes an otherwise qualifying static verdict to tier `RUNTIME`. Absence does not crash the run or claim runtime verification. Unmapped orchestration zones remain at their static tier and appear in a harness coverage-gap section. A fix may retain a coverage-gap annotation even when another runtime source passes.

Runtime `SUSPECT` and every other non-certifying runtime outcome must be excluded from verified-issue accounting, newly-verified deltas, confirmed-fixed counts, and snapshots.

The final report runs once after runtime verification so its rendered output, ledger hydration, run state, sweep state, and snapshot all use runtime-adjusted verdicts. `--runtime-max 0` disables execution and writes an empty current runtime artifact.

## Edge cases

- A fix has no resolved SHA or no runtime-relevant files.
- Multiple manifest bundles share one fix SHA.
- A discovered test was later deleted from `main`.
- A selected fix has no runnable discovered tests and must not collect the full suite.
- Several touched paths resolve to the same make target.
- A fix touches both mapped and unmapped orchestration zones.
- Runtime output contains newlines, pipes, control characters, or excessive text.
- A prior runtime artifact belongs to another manifest, cache key, or older fix SHA.
- Deep-truncation handling coexists with runtime failure evidence.
- The budget exceeds eligible unique SHAs or is zero.

## Failure modes

- Git discovery or runtime artifact corruption fails loudly because the coordinator cannot trust the evidence.
- Pytest failures, harness failures, missing tests, and timeouts become recorded evidence rather than coordinator errors.
- A report never grants `RUNTIME` from absent checks, stale rows, skipped SHAs, or a no-path pytest invocation.
- Runtime `SUSPECT` never contributes to verified accounting or snapshots.

# bug-treadmill [FEATURE] analyze-bugs: runtime evidence tier for verified fixes

#### Problem

All verification today is reading. Triage and deep verdicts conflate "the diff reads right" with "the behavior is verified". Runtime breaks pass static review: #6946 crashed every `/implement --merge` PR CI-failure route in the affected release, and the fix verdict machinery would have accepted the causing diff. The report cannot distinguish a fix whose tests ran from a fix nobody executed.

#### Required design

Coordinator-side only; the read-only agents stay read-only.

1. For each fix commit under verification, identify test files the commit added or modified (paths under `python/tests/`). Run exactly those files with pytest through the repo's Python conventions, with a per-run timeout. Record pass, fail, or absent.
2. Harness map: a declarative constant (module-prefix to make-target pairs, e.g. the Step 8 assessment offline harness and the bash32/halt-rate harnesses) maintained in `python/larch/issue/analyze_bugs.py` or a sibling JSON. For a fix touching a mapped module prefix, run the mapped target with a timeout. Extending the map is a one-line change.
3. Verdict tiers: a fix whose commit tests and mapped harnesses pass gets tier `RUNTIME` in the report's evidence-tier column (which the analytics sibling introduces). A fix in an orchestration zone with no mapped harness is annotated `UNVERIFIED_RUNTIME: no harness covers &lt;zone&gt;`; the report aggregates these into a harness-coverage-gap list (input for the close-criteria sibling).
4. Budget: `--runtime-max M` (default 10) newest fixes; skipped fixes keep their static tier; log the skip count.
5. Failures are evidence, not errors: a failing test run downgrades the verdict to `SUSPECT` with the pytest tail in the reason, and never crashes the run.

#### Tests

Harness-map resolution tests; test-file discovery from fixture commits; timeout and failure-downgrade paths; report tier rendering; budget cap with logged skips.

#### Non-goals

No live GitHub or vendor-CLI calls; no authoring of new harnesses (close-criteria sibling drives that); no change to agent read-only contracts.

#### Acceptance criteria

1. A fixture fix commit with a passing test file gets tier `RUNTIME`; with a failing test file it downgrades to `SUSPECT` with evidence.
2. A fixture fix in an unmapped orchestration zone produces the `UNVERIFIED_RUNTIME` annotation and appears in the coverage-gap list.
3. `.claude/skills/analyze-bugs/SKILL.md` documents the tier semantics and `--runtime-max`.

#### Backing evidence

The failure domain of this repo's bugs is recovery paths, vendor CLIs, and multi-process orchestration; CI-green carries near-zero signal for that class, and static reading has the same blind spot. Part of the `bug-treadmill` umbrella; blocked by the analytics, verdict-depth, and sweep siblings (file this last; it builds on their report and ledger surfaces).
