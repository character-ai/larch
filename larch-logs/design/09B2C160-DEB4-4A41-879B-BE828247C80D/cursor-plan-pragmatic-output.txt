**1. `git apply` vs session tmpdir (correctness)**  
`session-setup.sh` creates `SESSION_TMPDIR` with `mktemp` (typically under `/tmp` or the cache), not inside the larch git worktree. The plan’s unified-diff path depends on `git apply` for validate and apply. That command requires a git repository, so the approach will not work in real `/design` sessions or in hermetic harness dirs unless the plan adds a non-git apply strategy.

**2. Launcher argv contract (correctness)**  
`dispatch-with-waterfall.sh` always passes `--prompt-file` (or `--agent-file`) to `launch-review.sh` / `launch-claude-review.sh`. Both launchers reject invocations with only `--description-text`. The plan composes `prompt.txt` but step (b) does not wire it via `--prompt-file`, so launches will fail before any patch is produced.

**3. Emit-plan path mismatch (correctness)**  
`emit-plan.sh` hard-codes `PLAN_FILE="$DESIGN_TMPDIR/plan.txt"`. Revisions mutate `--plan-file`. Without a canonical-path rule or sync, a successful patch on a non-canonical path can still fail the emit gate (or pass against a stale file).

**4. `set -e` vs “always exit 0” contract (risk-integration)**  
Finalize requires unconditional `REVISE_*` KVs and exit 0 for logical failures. With `set -euo pipefail` (as in sibling scripts), a failed `git apply`, piped `design-driver`, or launcher can terminate the script before finalize. The tier loop needs explicit `set +e` / rc handling.

**5. `invalid-patch` vs `apply-failed` (correctness)**  
Step (d) assigns validator failures to `invalid-patch`. Case 5 and the `.md` validator describe `git apply --check` failure as `apply-failed`. That split will break the harness and the `failed-validation` vs `failed-apply` aggregator unless the plan picks one status for pre-apply check failures.
