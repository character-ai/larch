# [BUG] /implement --merge: client pre-commit hook aborts run-log commit; ship stalls pre-PR and step8-shippr recovery deadlocks on pre-terminal 'stalled' label

## Summary

Each reship re-renders `final-summary.md` with the `stalled` heading, then refuses its own run-log commit via the pre-terminal guard, then stalls again. The loop repeats to the retry cap. No PR is ever created.

In the observed run the code fix was correct and reviewed clean; only shipping failed. The operator merged by hand.

## Required fix (operator-approved direction)

### Fix 1: hook-tolerant run-log commit (Part A)

In `_commit_run` (`python/larch/report/run_log_commit.py`): when `git commit` exits non-zero, re-run the commit tail (`git add` → `git diff --cached --quiet` → `git commit`) exactly once.

- Rationale: file-modifying hooks leave their fixes in the worktree and are idempotent, so the retry adopts the fixes and passes. Checking-only hooks (secret scanners, commit-msg policy) fail the retry identically and surface as today.
- Keep the retry unconditional on non-zero commit rc. Do not parse hook output to decide whether to retry. One retry also heals transient races (for example `index.lock`).
- If the retry's `git diff --cached --quiet` reports nothing staged (the hook restored HEAD content), return the existing unchanged/success shape.
- **Do not use `git commit --no-verify`.** It would commit hook-unclean files into the client repo (client CI running `pre-commit run --all-files` then fails on their mainline) and would bypass client checking hooks such as secret scanners. Larch is a guest in the client repo; adopting the client's hook fixes is the correct behavior and also keeps committed logs hook-clean by that client's own rules.
- The fix lands once in `_commit_run` and covers all consumers (fact 1). Leave `_larch_log_commit` unchanged after verifying it has no live callers, or align it; do not fork behavior between the two.

### Fix 2: de-terminalize state at ship-driver re-entry (Part B)

At drive re-entry in the Python ship driver, after the `ResumePlan` is derived from existing state (`python/larch/implement/ship_resume.py` reads `PHASE` / `RESUME_PHASE`; the reset must not disturb those inputs) and before the first `run_logs.flush_logs_pre` of the drive:

- If `ship-pr-state.sh` has `PHASE=stalled`, write a normal non-terminal ship state (reuse the `_write_ship_state` non-terminal path per fact 6): `PHASE` set to the drive's next in-progress phase value (do not invent a new label), `STALL_TRACKING=false`, terminal-only keys cleared.
- Neutralize the stale terminal overlay in `finalize-state.sh` written by `_write_terminal_finalize_if_terminal`. Deleting the file restores the documented mid-flight contract (`finalize-state.sh` exists only on terminal outcomes); rewriting `STALL_TRACKING=false` is acceptable if deletion breaks a consumer. The invariant: after the reset, `_stall_signal_is_terminal` returns false for the resumed drive, and `normalized_outcome_values` yields the neutral `shipping` outcome for a pre-PR reship.
- Emit a breadcrumb recording the de-terminalization and the prior label.
- The reset lives in the Python driver only. Prompt-side orchestrator code must never write `finalize-state.sh` or session env (AGENTS.md).
- **Do not modify the guard.** `_check_preterminal_commit_blocked`, `_preterminal_outcome_commit_blocked`, and `config.PRETERMINAL_FORBIDDEN_OUTCOME_LABELS` stay as they are. No bypass flag. After the reset, the refresh re-renders a non-terminal summary and the guard passes naturally. If the reshipped drive stalls again, `_write_terminal_state` re-marks both files; convergence stays bounded by the existing reship caps.

### Fix 3: distinct refresh-skip reason for the pre-terminal refusal (observability only)

`_preterminal_outcome_refresh_skip` (`run_log_flush.py:710`) currently reports reason `commit-failed`, which masked the deadlock as a hook failure in the observed run.

End-to-end shape, as far as the existing ship test harness models it: a simulated first stall at `pr-create-guideline-outcome-refresh` followed by a reship converges to the PR-create path instead of the deadlock.
