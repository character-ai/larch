## Edge cases

- **Non-empty lock:** Do not remove it; surface diagnostic with lock path.
- **Live git process:** Do not remove the lock.
- **Process probe failure:** Fail closed and keep the lock.
- **Lock disappears before unlink:** Treat as not removed; return original failure with diagnostic.
- **Retry fails after removal:** Return the retry result; do not loop.
- **Worktrees:** Resolve lock via `git rev-parse --absolute-git-dir`, not repo-root `/.git`.
- **Pathspec commits:** Retry the exact same argv so `--only`, `--pathspec-from-file`, and `--pathspec-file-nul` keep current semantics.
- **Duplicate staging removed:** `_stage_and_commit_round` and `commit_fixes --stage-all` must not pre-add; `commit_main()` is the sole staging owner for those paths.
- **Staging failure before commit:** Lock cleanup must run on `git add` failures, not only on `git commit` failures.
- **Mid-transaction lock:** Preemptive sweep handles pre-existing stale locks; wrapped add/commit handles locks encountered at invocation time.

## Failure modes

- A conservative live-git probe may refuse cleanup when an unrelated git process exists. That is safer than deleting an active lock. Diagnostics must name the lock path and reason.
- Removing duplicate raw `git add` calls changes call order slightly (single staged add inside `commit_main`). Behavior should remain equivalent because `commit_main` already re-staged the same pathspec file.

# [BUG] Stale .git/index.lock makes Step 5 review coder commit fail as coder-failed stall

## Summary

A stale `.git/index.lock` makes the `/implement` Step 5 review-and-fix coder commit fail with git exit 128, which surfaces as an opaque `coder-failed` stall. The review-and-fix commit path has **no** stale-lock detection or cleanup (the Step 2 dispatcher at least *detects* `index.lock`, but only to bail). The documented `step5-review` stall-recovery retry would re-hit the same lock without clearing it, so the run cannot make progress until an operator manually removes the lock.

## Original report

Investigate the "stall root cause" of an `/implement --merge` run (issue #4641, sh-to-py G12) that stalled at Step 5 code review with `STALL_REASON=coder-failed` after round 3.

## Reproduction scenario

1. Run `/implement --merge &lt;issue&gt;` such that Step 5 review runs at least one round that applies + commits a fix via an external coder.
2. Have a stale `.git/index.lock` present at the moment the coder commits — e.g., a 0-byte lock left by an interrupted/killed prior `git commit`.
3. Observe the coder commit fail and the Step 5 loop return `STEP5_REVIEW_STATUS=stall` / `STALL_REASON=coder-failed` / `CODER_STATUS=failed`.

Observed directly in this run during Step 18a stall recovery: the recovery commit (`python/cli.py review-and-fix commit-fixes --stage-all`) failed with **exit 128** and `fatal: Unable to create '&lt;repo-root&gt;/.git/index.lock': File exists`. A **0-byte** `.git/index.lock` was present (timestamped at the round-3 failure time); no git process was operating on the repo. Removing the lock (`rm -f .git/index.lock`) and re-running the commit returned `COMMITTED=true` immediately.

## Expected behavior

A stale `.git/index.lock` (0-byte and not held by any running git process — consistent with larch's single-runner invariant) should be detected and safely cleared, or at minimum produce a distinct, actionable diagnostic, so the review coder commit can proceed instead of an opaque `coder-failed` stall. Stall recovery for a lock-induced `coder-failed` should clear the stale lock before retrying, otherwise the retry cannot succeed.

## Observed behavior

- Step 5 round 3 returned `coder-failed`, which the loop converted to `stall`.
- The round-3 fix was correctly applied to the working tree but left **uncommitted** (the commit was blocked by the lock).
- The stall classified as `transient-infra` / `MATCHED_CLASSIFIER_PATTERN=transient-output`, `RESUME_HINT=step5-review` (re-run the review loop) — but re-running would re-hit the same lock because nothing clears it.
- Manual lock removal was required to recover.

## Root cause analysis

Inferred root cause: an interrupted/failed `git commit` (by the round-3 review coder) left a 0-byte `.git/index.lock`. The leftover lock then makes every subsequent commit fail with `git exit 128: Unable to create '.git/index.lock'`.

The Step 5 review-and-fix coder commit path (`apply_findings_with_coder` in `python/review_and_fix.py`) maps any non-zero, non-4 coder return code directly to `coder-failed` (`python/review_and_fix.py:2961`) with no `index.lock` awareness and no cleanup. By contrast, the Step 2 dispatcher (`python/implement_dispatch.py:1443-1448`) checks `index.lock` as part of its `dirty-state-after-timeout` guard — but it only *detects and bails*; it does not clean up. The Step 18a stall-recovery commit path likewise hit the lock directly (exit 128), confirming the lock as the proximate cause. Net effect: a leftover lock yields an opaque `coder-failed` stall, and the documented recovery (re-run review) cannot make progress.

Observation vs. inference: the 0-byte lock, the exit-128 error, and the successful commit after `rm` are **observed**. That the round-3 coder's own interrupted commit created the lock is **inferred** (from the 0-byte size and matching timestamp), not directly observed.

## Affected files

- `python/review_and_fix.py` — `apply_findings_with_coder` and the round coder commit path; no stale-lock detection/cleanup; maps the failure to `coder-failed` at line ~2961. Primary gap.
- `python/git.py` — the `git commit` entrypoint (`commit` / `commit_main`); could surface a distinct stale-lock error or offer guarded cleanup so all commit paths benefit.
- `python/implement_dispatch.py` (lines 1443-1448) — has partial lock awareness (detect-and-bail) shown here for contrast/parity.
- `python/stall_recovery.py` / Step 18a — a lock-induced `coder-failed` classified `transient-infra` with `RESUME_HINT=step5-review` retries without clearing the lock.

## Suggested fix(es)

- Add a guarded stale-`.git/index.lock` sweep around the review coder commit: remove the lock only when it is 0-byte **and** not held by any running git process (respecting the single-runner invariant), then retry the commit once. Prefer centralizing this in `python/git.py` so the dispatcher, review-and-fix, and stall-recovery commit paths share one safe policy.
- Alternatively/additionally, surface a distinct diagnostic (e.g., `coder-failed: stale .git/index.lock`) and have the `step5-review` recovery clear a detected stale lock before retrying, so the documented recovery path can actually succeed.

## Open questions

- Was the lock left by the coder's own interrupted commit, or by a concurrent external git process? Evidence points to the former, but it was not directly observed.
