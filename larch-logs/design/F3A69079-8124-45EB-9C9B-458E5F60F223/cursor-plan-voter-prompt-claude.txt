# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `major`. Single-YES `minor`, `nit`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

The Claude Code platform fires `&lt;task-notification&gt;` events on every assistant-turn-end while a background task is pending, not only on completion. Each notification triggers a classification Read (empty output), a silent yield, and a turn end. The turn end triggers the next notification. This creates an infinite feedback loop. Recent fixes (#5240, #5478, #5639) prevent bad actions but do not break the loop because they cannot prevent the platform from firing the next notification after each turn ends.

## Original report

During a `/design` run that reached Step 3 plan review (`design-step3-review.sh` launched via `run_in_background: true`), the orchestrator received 8+ `&lt;task-notification&gt;` events in rapid succession while the background task was genuinely still running (plan reviewers: Cursor and Codex). Each notification's classification Read returned empty/unchanged task output. The fixes from #5240 (silent yield on empty output), #5478 (sentinel probe clamp), and #5639 (no-progress circuit breaker) did not stop the loop within the session window before the user intervened manually.

## Reproduction scenario

1. Start a `/design` run on any non-trivial issue.
2. When Step 3 plan review launches, the background task (`design-step3-review.sh`) starts long-running external reviewer processes (Cursor, Codex).
3. While the reviewers run, the plan-review driver writes nothing to the background task's stdout (all progress goes to FD 3 or stderr).
4. The platform fires `&lt;task-notification&gt;` at the end of each assistant turn.
5. The orchestrator does: classification Read (empty) → silent yield → end turn.
6. Turn end fires another `&lt;task-notification&gt;`.
7. Loop repeats until the circuit breaker at threshold=5 arms, or the user interrupts.

## Expected behavior

After the first empty-output classification Read, the orchestrator silently yields. The platform fires at most one or two more notifications before the circuit breaker blocks further notifications. The user sees at most 2-3 notification turns before things go quiet until the real completion arrives.

## Observed behavior

The orchestrator receives 8+ spurious `&lt;task-notification&gt;` events in rapid succession. Each triggers a new turn. The circuit breaker (threshold=5) did not arm before the user intervened (they intervened at ~turn 4). Additionally, the orchestrator emitted prose output ("Silent yield — task output still empty. Waiting.") during supposedly-silent yields, amplifying user frustration.

## Root cause analysis

Two layers:

**Layer 1 (platform behavior):** Claude Code fires a `&lt;task-notification&gt;` at the end of every assistant turn where pending background tasks exist, regardless of whether the task has produced new output. This is consistent with the SKILL.md statement "the backgrounded /design task reliably re-fires a `&lt;task-notification&gt;` on completion (current evidence indicates it does)." But in practice, the platform fires the notification much more aggressively: on every turn-end, not only on true completion. This means "silent yield → end turn" immediately queues the next spurious notification.

**Layer 2 (circuit breaker gap):** The no-progress circuit breaker (`hook-no-progress-guard.sh`) increments a counter on each Stop event (assistant turn-end) and blocks on UserPromptSubmit after threshold=5. Two gaps:

1. **Threshold too high:** With rapid spurious notifications, 5 turns takes seconds. Users notice 2-3 spurious turns already. The threshold should probably be 2-3, not 5.
2. **Scope mismatch:** The circuit breaker arms via Stop (which fires on task-notification turns) but fires via UserPromptSubmit (which fires on human-typed messages). If `&lt;task-notification&gt;` is delivered as a system message rather than a UserPromptSubmit hook event, the armed circuit breaker never fires on notifications; it only fires on the next real human message. This inverts the design intent: the breaker blocks real human messages but leaves the notification loop intact.

**Layer 3 (orchestrator prose leak):** The "silent yield" contract says "no further probe, parse, or prose tools." But the orchestrator was emitting text narration ("Silent yield — task output still empty. Waiting.") on each spurious turn, which violates the contract and is visible to the user.

## Evidence

- `hook-no-progress-guard.sh`: Stop event increments `no-progress-turns.count`; UserPromptSubmit checks `no-progress-circuit-breaker-armed`. If task-notifications are not UserPromptSubmit events, the block never fires.
- `hook-bg-poll-guard.sh` `marker_step_completed` for `design-step3-review`: requires both `$dir/.completed/step-3-terminal` AND `$dir/.step3-terminal-persisted-this-run` to release the guard. Both are absent while the task runs. This is correct, but does not stop the notification loop.
- The tasks output file `/private/tmp/claude-501/.../&lt;id&gt;.output` remained at 1 line (blank) across all 8+ notification turns, confirming the background task had not written any output yet (plan reviewers were still running).
- The `hook-bg-poll-guard.sh` correctly blocked Bash probe attempts (`deny_if_needed`), confirming it is working. But it explicitly allows Read of `tasks/*.output` ("write-once classification artifact"), so the classification Read always succeeds regardless of how many times it has already returned empty.
- The circuit breaker `THRESHOLD` default is 5. The user intervened after ~4 turns, so the breaker had not armed yet.

## Affected files

- `scripts/hook-no-progress-guard.sh` — circuit breaker threshold and block event (UserPromptSubmit vs task-notification scope)
- `scripts/hook-bg-poll-guard.sh` — task-output Read is explicitly always allowed; no mechanism to deny after N empty reads
- `skills/shared/design-background-wait.md` — documents the silent yield contract; the orchestrator violated the no-prose rule

## Suggested fix(es)

Two complementary fixes:

**Fix 1 (threshold):** Lower `LARCH_NO_PROGRESS_GUARD_THRESHOLD` from 5 to 2 or 3. Even if there is a gap in what events it blocks, arming sooner limits the loop depth.

**Fix 2 (classification Read rate-limit):** In `hook-bg-poll-guard.sh`, track how many times a specific `tasks/&lt;id&gt;.output` file has been Read during the current bg-wait and returned unchanged (or empty). After N reads (e.g., 2), deny subsequent Reads of that file until the task output actually changes or the bg-wait marker is removed. This forces the orchestrator to end the turn with no tool calls, which may reduce the notification rate or at least make the loop invisible (no tool calls = no visible output).

**Fix 3 (clarify event scope):** Investigate whether `&lt;task-notification&gt;` triggers UserPromptSubmit hook events. If it does not, redesign the circuit breaker to fire on Stop events directly (block immediately when counter exceeds threshold, by injecting a stop-continuation directive).

**Fix 4 (orchestrator contract enforcement):** Reinforce in SKILL.md and design-background-wait.md that "silent yield" means ZERO prose output and ZERO tool calls. The orchestrator should not emit any text on spurious-notification turns.

## Open questions

2. Why does the platform fire `&lt;task-notification&gt;` on every turn-end vs only on true task completion? Is this Claude Code's documented behavior or a platform bug?
3. Is there a way to see the hook invocation log for the current session to confirm the Stop counter increments on notification turns?
