# [OOS] /design Step 3 plan-review & log-publish drift + bugs — 7 items

Combined from #4214, #4272, #4248 by `/combine-issues --oos`. Drift, latent timing, and merge-idempotency gaps in the `/design` Step 3 plan-review loop and the `/design` log-publish flow.

### Item 1 — Normative design docs still cite retired plan-quality script basenames
- **Location**: `skills/design/scripts/lib-plan-optional-trailers.md`, `docs/workflow-lifecycle.md`, `skills/design/scripts/test-trailer-awk.md`, `skills/design/scripts/test-design-postplan-emit.md`
- **Source**: #4214
- **Severity**: latent
- **Description**: Normative design docs still cite the retired `check-plan-size.sh` and `revise-plan-with-waterfall.sh` basenames after the C3a2 cutover to `python/cli.py plan check-size`. Verify each citation against the current Python surface before editing; some test-contract docs may describe historical behavior intentionally.

### Item 2 — Map design-clarify.sh / design-clarify.md in scripts/relevant-checks.sh
- **Location**: `scripts/relevant-checks.sh`
- **Source**: #4214
- **Severity**: latent
- **Description**: `relevant-checks.sh` does not map `design-clarify.sh` / `design-clarify.md` to `test-design-clarify` like other design wrappers (`test-design-publish`, `test-design-step2b-drafter`). The wrapper, its `.md`, and `test-design-clarify.sh` all exist, so the structure check is unwired.

### Item 3 — Missing-row fail-safe may run a second terminal postplan fence on drafter-success
- **Location**: `skills/design/SKILL.md` (drafter-success path)
- **Source**: #4214
- **Severity**: important
- **Description**: Acceptance calls for one Bash call through postplan on success; a silent second postplan can re-validate and rewrite sentinels after a partial internal handoff. Confirm the drafter-success path fences postplan exactly once.

### Item 4 — Structure pins only grep for literal tokens, not teardown behavior
- **Location**: `scripts/test-design-structure.sh`
- **Source**: #4214
- **Severity**: latent
- **Description**: The `contains` checks for `_loop_pid=`, `set -m`, and `kill -- -"$_loop_pid"` can pass while cleanup ordering is wrong (trap left armed after `wait`, `_loop_pid` cleared too late, or `set -e` restored before trap clear), which would not be caught before production.

### Item 5 — Success awaiting-continuation uses loop-local round_start_s
- **Location**: `skills/design/scripts/review-design-step3-loop.sh` (awaiting-continuation success path)
- **Source**: #4272
- **Severity**: latent (3 votes, OOS accepted)
- **Description**: The success path for `awaiting-continuation` uses loop-local `round_start_s` (reset each iteration) instead of `step3_loop_read_round_start_s`, while the failure path already uses the resume-aware reader. On resumed phases the success-path timing record uses a resume-time start rather than the actual round start, potentially narrowing the Gantt window and hiding reviewer rows. Fix: apply `step3_loop_read_round_start_s` on the success path (and consider the `panel-failed` path). Final-report Gantt uses min/max across round rows so impact may be limited when an earlier row exists, but success-vs-failure timing semantics remain inconsistent on resumed phases.

### Item 6 — design-log-publish.sh: no origin-default fetch before merge-base check
- **Location**: `scripts/design-log-publish.sh`
- **Source**: #4248
- **Severity**: latent
- **Description**: No fetch of the origin default branch before the merge-base check. A stale `origin/<default>` ref can miss an already-merged branch and skip the idempotent short-circuit.

### Item 7 — Merged-branch harness may not match squash production semantics
- **Location**: `scripts/test-design-log-publish.sh`
- **Source**: #4248
- **Severity**: latent
- **Description**: The harness merges a log branch into main while keeping the remote ref. Unless it simulates squash-merge plus ref behavior, it may not exercise the production idempotency short-circuit it is meant to cover.
