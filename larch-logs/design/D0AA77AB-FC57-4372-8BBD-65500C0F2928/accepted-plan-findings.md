### FINDING_1: Edge-case prose about marker clearing is incorrect
- **Concern**: The plan's edge-case section states "Operators who want to clear the marker can let any lifecycle rename do it; no manual cleanup is required." This is **wrong**. After `strip_round_trip_prefix` and `has_round_trip_prefix` are deleted (correctly per acceptance #2), the compose path no longer recognizes the `[ROUND-TRIP] ` token — the bracket sequence survives in `USER_TAIL` as inert prose. For an existing title `[DONE] [ROUND-TRIP] Foo`, a future rename will produce `[IN PROGRESS] [ROUND-TRIP] Foo` (the leftover bracket persists). Operators who want a clean title must `gh issue edit --title` manually. Acceptance #2 forbids re-adding a literal `[ROUND-TRIP]` strip step, so this residue is unavoidable. The misleading prose would set wrong operator expectations.
- **Proposed resolution**: Replace the second sentence of the edge-case bullet with: "After this change, the marker grammar is no longer recognized — it survives in the user-tail prose of titles that already carry it until an operator manually clears them via `gh issue edit --title`. New renames neither add nor preserve the marker, and the lifecycle prefix logic still composes correctly around the leftover bracket text (idempotency is preserved because the canonical comparison treats the residue uniformly on both sides)."
