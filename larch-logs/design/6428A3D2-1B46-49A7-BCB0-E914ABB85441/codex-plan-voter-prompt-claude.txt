# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For

## Summary

During `/implement` stall recovery, `python/cli.py stall-recovery record-escalation` fails with `reason: failure-detail-log-invalid`, recorded as a `## Tool Failure: record-escalation` execution issue. The escalation reporting path rejects its own `--failure-detail-log` (the lint-fix checks log) at exactly the moment a run is already stalling, so the auto-filed failure report and ledger entry are degraded. The `failure-detail-log-invalid` token is generic: `validate_failure_detail_log` collapses five distinct rejection causes into one reason, emitting the specific cause only to stderr (which is not captured into the execution issue), so the true cause is not diagnosable from committed logs.

## Original report

In `/implement` runs the stall-recovery escalation reporting path fails with a `Tool Failure: record-escalation ... reason: failure-detail-log-invalid`.

Source: `python/larch/state/stall_recovery.py` `record_escalation_main` calls `validate_failure_detail_log(tmpdir, path)` on the `--failure-detail-log` argument and, when it returns `False`, returns `hard_fail("failure-detail-log-invalid")`. So the escalation path rejects its own failure-detail log exactly when a run is already stalling/escalating, degrading stall recovery and the auto-filed failure report.

Observed in 5 of the last 100 `/implement` runs, versions 52.0.6 through 52.1.2 (reaches newest/main). `python/larch/state/stall_recovery.py` is untouched since the `v52.1.2` release tag, so the defect is present in `main`.

## Reproduction scenario

1. Run `/implement` on a change whose post-apply lint-fix loop fails (for example a large diff that leaves many lint violations, as happens after a packaging move), so Step 5 / Step 7a escalates via the stall-recovery path.
2. Observe the `record-escalation` invocation that passes `--failure-detail-log &lt;lint-fix checks log&gt;`.
3. Inspect the committed `execution-issues.ndjson` for the `## Tool Failure: record-escalation` entry.

Not reproduced synthetically in this investigation. The evidence is from committed run logs plus source inspection of HEAD. A targeted reproduction is to call `stall-recovery record-escalation --tmpdir &lt;T&gt; --failure-detail-log &lt;P&gt;` where `&lt;P&gt;` is a real file but (a) larger than 64KiB, or (b) not resolvable under `&lt;T&gt;`, and confirm the run-visible reason is the generic `failure-detail-log-invalid`.

## Expected behavior

When the lint-fix loop escalates, `record-escalation` should accept the failure-detail log it was handed and record a complete escalation ledger / failure report. If the detail log genuinely cannot be attached (too large, wrong location), the recorded reason should name the **specific** cause (oversize, outside-tmpdir, missing, symlink, non-absolute) rather than the generic `failure-detail-log-invalid`, and the escalation itself should still succeed (the detail log is optional evidence, not a hard precondition).

## Observed behavior

`record-escalation` returns `hard_fail("failure-detail-log-invalid")` and the run records:

```
## Tool Failure: record-escalation
- helper: python/cli.py stall-recovery record-escalation
- reason: failure-detail-log-invalid
```

The specific rejection cause is printed only to stderr inside `validate_failure_detail_log` and is not surfaced into the execution issue, so the operator cannot tell which of the five validation conditions failed.

## Root cause analysis

Uncertain on the precise trigger; two hypotheses, both consistent with the code.

`validate_failure_detail_log` (`python/larch/state/stall_recovery.py`) returns `False` (→ `failure-detail-log-invalid`) when the path is non-absolute, is a symlink, resolves outside the `--tmpdir`, is not a regular file, or exceeds `MAX_OPTIONAL_EVIDENCE_BYTES` (64KiB). The implement-side detail log is the lint-fix checks log: `python/checks.py` sets `ledger_failure_detail_log=str(log_path)` where `log_path = _resolve_checks_log_path(candidate=checks_log, allowed_root=allowed_root)`.

- **Hypothesis A (most likely): oversize.** A lint-fix failure log for a large/broken diff (for example the recent `larch.*` packaging move that left many files failing lint) can easily exceed 64KiB, so the optional-evidence cap rejects it.
- **Hypothesis B: tmpdir-containment mismatch.** If the checks-log path (`allowed_root` / `run_parent` resolution) is not under the `--tmpdir` that `record-escalation` validates against, `relative_to(tmpdir)` raises and the log is rejected as "outside implement tmpdir".

Either way, a second, independent defect compounds it: the run-visible reason is the generic `failure-detail-log-invalid`, because the five distinct stderr messages all map to the single `hard_fail` token. That makes post-hoc root-causing from committed logs impossible.

## Suggested fix(es)

- Make the failure-detail log strictly optional in `record-escalation`: when `validate_failure_detail_log` fails, record the escalation **without** the detail log (and note `detail-log-skipped: &lt;specific-reason&gt;`), instead of `hard_fail`. The escalation/ledger is more valuable than the optional evidence attachment.
- Propagate the **specific** validation cause into the recorded reason (`failure-detail-log-oversize`, `failure-detail-log-outside-tmpdir`, `failure-detail-log-missing`, etc.) rather than the single generic `failure-detail-log-invalid`.
- If oversize is confirmed (Hypothesis A), truncate or tail the lint-fix detail log to the 64KiB cap before attaching, rather than rejecting it.
- If containment is confirmed (Hypothesis B), align the checks-log root with the `--tmpdir` passed to `record-escalation`.
