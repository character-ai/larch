# [BUG] Architectural assessment lacks a fallback waterfall for transient tool failures

## Summary

The Step 8 architectural assessment runs on a single tool lane: `claude --print --model claude-sonnet-4-6`. When that subprocess returns empty or unparseable stdout, the coordinator retries the same lane a few times, then declares the assessment `unavailable`. That routes `/implement` ship to `operator-bail` and blocks the run, even when the change is clean and CI is green. The assessment has no cross-tool fallback waterfall, unlike the implementer, reviewer panel, and CI-fixer. A single transient empty response is enough to stall an otherwise-mergeable PR.

## Original report

Filed after `/implement` reproduced this failure while shipping the fix for #7057.

Request: give the architectural assessment a fallback waterfall, like the implementer (Codex to Cursor to Claude), the reviewer panel (Claude plus Codex plus Cursor), and the Step 8 CI-fixer (multi-tier). When the primary assessment tool returns empty or unparseable output, the backup must kick in and try an alternate tool or model before declaring `unavailable`. The backup should trigger on exactly this failure mode (a transient empty or unparseable response that currently yields `unavailable`), not only when the primary tool binary is missing. Route to `operator-bail` only after the full waterfall is exhausted across tools.

## Reproduction scenario

1. Run `/implement --merge &lt;issue-N&gt;` on a HARD-tier issue so the Step 8 assessment gate runs.
2. Let the run reach the assessment gate at least twice (for example, a CI-fix moves HEAD and the ship driver re-triggers the assessment on the new diff).
3. On one of those attempts, have the `claude --print --model claude-sonnet-4-6 ... --allowedTools Read --permission-mode plan` subprocess return empty stdout (observed transiently in a real run).

Observed in run `DA867F05-EAD1-4115-8D27-5526693C083E` (PR #7094, issue #7057):
- First assessment succeeded: `invariants:clean, guidelines:deviation`.
- After the CI-fixer moved HEAD, the re-assessment returned `unavailable` for both kinds.
- The `unavailable` receipts carried `"detail": "Expecting value: line 1 column 1 (char 0)"`, i.e. the subprocess returned empty stdout and JSON parsing failed.
- The same session succeeded once and failed once, so this is transient, not a systematic environment misconfiguration.

## Expected behavior

When the primary assessment lane returns empty or unparseable output, a backup lane should run automatically. The backup should try an alternate tool or model (for example Codex or Cursor, or a retry against a different model) and produce a real assessment. The run should only fall to `operator-bail` with `architectural-assessment-unavailable` after every lane in the waterfall has been tried and exhausted. A single transient empty response from one tool should not stall a clean, CI-green PR.

## Observed behavior

The coordinator retries the single `claude` lane only. `run()` loops up to 3 attempts, and `_launch_assessment` adds a same-lane empty-stdout retry. All retries hit the same tool and model. When they exhaust, `_persist_unavailable` records `outcome=dropped, reason=unavailable`, `ASSESSMENT_RESULTS=invariants:unavailable,guidelines:unavailable` is returned with `ASSESSMENT_STATUS=complete`, and `ship route-exit` emits `NEXT_ACTION=operator-bail`. There is no alternate-tool lane. The run stalls and needs a manual takeover (push plus admin-merge) to land.

## Root cause analysis

The assessment is single-lane by construction. `python/larch/implement/architectural_assessment.py` binds one model (`_MODEL = "claude-sonnet-4-6"`) and one launcher command (`"claude", "--print", "--model", _MODEL, ...`). `run()` retries that same command up to 3 times, and `_launch_assessment` retries transient exit-0 empty stdout within the same lane. Any empty stdout, non-zero exit, `TimeoutExpired`, or `JSONDecodeError` that survives those same-lane retries reaches `_persist_unavailable`. The Bash adapter `skills/implement/scripts/step-8-assessment.sh` layers its own attempt-1 / attempt-2 retry and timeout-to-unavailable handling, but it also re-runs the same assessment lane; it has no Codex or Cursor branch. So neither layer switches tools. This differs from the implementer dispatcher and the Step 8 CI-fixer, which both waterfall across tools on failure.

The fix merged for #7057 (main commit `100c7881`) makes this failure visible by propagating the sanitized diagnostic (`Expecting value: line 1 column 1 (char 0)`) into the outcome sidecars and the `ASSESSMENT_UNAVAILABLE_DETAIL` operator-bail handoff. It does not prevent the failure and adds no fallback. This issue tracks the resilience gap: a backup waterfall that recovers from a transient single-tool failure automatically.
