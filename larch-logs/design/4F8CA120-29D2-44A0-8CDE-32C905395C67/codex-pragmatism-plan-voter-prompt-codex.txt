# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed"). A red or flapping default-branch CI counts as actively
   blocking verification for every run: restoring or stabilizing default-branch CI clears this
   gate. The `/implement` orchestrator, not reviewers, owns executing that repair.

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `major`. Single-YES `minor`, `nit`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

The Step 8 architectural assessment runs on a single tool lane: `claude --print --model claude-sonnet-4-6`. When that subprocess returns empty or unparseable stdout, the coordinator retries the same lane a few times, then declares the assessment `unavailable`. That routes `/implement` ship to `operator-bail` and blocks the run, even when the change is clean and CI is green. The assessment has no cross-tool fallback waterfall, unlike the implementer, reviewer panel, and CI-fixer. A single transient empty response is enough to stall an otherwise-mergeable PR.

## Original report

Filed after `/implement` reproduced this failure while shipping the fix for #7057.

Request: give the architectural assessment a fallback waterfall, like the implementer (Codex to Cursor to Claude), the reviewer panel (Claude plus Codex plus Cursor), and the Step 8 CI-fixer (multi-tier). When the primary assessment tool returns empty or unparseable output, the backup must kick in and try an alternate tool or model before declaring `unavailable`. The backup should trigger on exactly this failure mode (a transient empty or unparseable response that currently yields `unavailable`), not only when the primary tool binary is missing. Route to `operator-bail` only after the full waterfall is exhausted across tools.

## Reproduction scenario

1. Run `/implement --merge &lt;issue-N&gt;` on a HARD-tier issue so the Step 8 assessment gate runs.
2. Let the run reach the assessment gate at least twice (for example, a CI-fix moves HEAD and the ship driver re-triggers the assessment on the new diff).
3. On one of those attempts, have the `claude --print --model claude-sonnet-4-6 ... --allowedTools Read --permission-mode plan` subprocess return empty stdout (observed transiently in a real run).

Observed in run `DA867F05-EAD1-4115-8D27-5526693C083E` (PR #7094, issue #7057):
- First assessment succeeded: `invariants:clean, guidelines:deviation`.
- After the CI-fixer moved HEAD, the re-assessment returned `unavailable` for both kinds.
- The `unavailable` receipts carried `"detail": "Expecting value: line 1 column 1 (char 0)"`, i.e. the subprocess returned empty stdout and JSON parsing failed.
- The same session succeeded once and failed once, so this is transient, not a systematic environment misconfiguration.

## Expected behavior

When the primary assessment lane returns empty or unparseable output, a backup lane should run automatically. The backup should try an alternate tool or model (for example Codex or Cursor, or a retry against a different model) and produce a real assessment. The run should only fall to `operator-bail` with `architectural-assessment-unavailable` after every lane in the waterfall has been tried and exhausted. A single transient empty response from one tool should not stall a clean, CI-green PR.

## Observed behavior

The coordinator retries the single `claude` lane only. `run()` loops up to 3 attempts, and `_launch_assessment` adds a same-lane empty-stdout retry. All retries hit the same tool and model. When they exhaust, `_persist_unavailable` records `outcome=dropped, reason=unavailable`, `ASSESSMENT_RESULTS=invariants:unavailable,guidelines:unavailable` is returned with `ASSESSMENT_STATUS=complete`, and `ship route-exit` emits `NEXT_ACTION=operator-bail`. There is no alternate-tool lane. The run stalls and needs a manual takeover (push plus admin-merge) to land.

## Root cause analysis

The assessment is single-lane by construction. `python/larch/implement/architectural_assessment.py` binds one model (`_MODEL = "claude-sonnet-4-6"`) and one launcher command (`"claude", "--print", "--model", _MODEL, ...`). `run()` retries that same command up to 3 times, and `_launch_assessment` retries transient exit-0 empty stdout within the same lane. Any empty stdout, non-zero exit, `TimeoutExpired`, or `JSONDecodeError` that survives those same-lane retries reaches `_persist_unavailable`. The Bash adapter `skills/implement/scripts/step-8-assessment.sh` layers its own attempt-1 / attempt-2 retry and timeout-to-unavailable handling, but it also re-runs the same assessment lane; it has no Codex or Cursor branch. So neither layer switches tools. This differs from the implementer dispatcher and the Step 8 CI-fixer, which both waterfall across tools on failure.

The fix merged for #7057 (main commit `100c7881`) makes this failure visible by propagating the sanitized diagnostic (`Expecting value: line 1 column 1 (char 0)`) into the outcome sidecars and the `ASSESSMENT_UNAVAILABLE_DETAIL` operator-bail handoff. It does not prevent the failure and adds no fallback. This issue tracks the resilience gap: a backup waterfall that recovers from a transient single-tool failure automatically.

## Suggested fix(es)

1. Add a fallback waterfall to the assessment lane. When the primary `claude` lane returns empty stdout, non-zero exit, timeout, or unparseable JSON after its same-lane retries, try an alternate lane (for example Codex, then Cursor) or an alternate model before declaring `unavailable`.

3. Only emit `architectural-assessment-unavailable` and route to `operator-bail` after every lane in the waterfall is exhausted. Preserve the #7057 diagnostic so the final handoff still reports the last lane's failure detail.
4. Reuse the existing tool availability and selection machinery from the implementer dispatcher or the Step 8 CI-fixer where possible, rather than adding a parallel tool-selection path.
5. Keep the invariant-violation and genuine `dropped` semantics unchanged. The waterfall applies to unavailability (no parseable assessment produced), not to a produced assessment that reports a violation.

## Proposed Design Outline

### Goals
- Give the Step 8 architectural assessment a bounded cross-tool fallback waterfall so a transient empty/unparseable response from one tool no longer stalls a clean, CI-green PR.
- Waterfall order for every assessment: Cursor/Composer-2.5 -&gt; Codex/Terra -&gt; Claude/Sonnet-4-6; advance one lane on any unavailable-class failure; emit `unavailable`/operator-bail only after the last lane is exhausted (per-kind).

- Extend the coordinator `run()` in `architectural_assessment.py` to iterate a fixed ordered lane list instead of retrying one hardcoded `claude` command.

- Reuse Cursor/Codex launch + availability helpers (the reviewer/dispatcher read-only path); a lane whose binary is unavailable is skipped, not fatal.
