## Problem

- `python/ship.py::run_ship()` seeds CI-loop counters to zero on each invocation, so exit-3/exit-6 handbacks reset session-wide caps.
- `_write_ship_state()` persists counters, but entry does not restore them, and terminal/open-PR state writes can overwrite restored counters with zero.
- Re-entry always restarts at checks/postbump/PR creation, causing redundant work against an existing PR.
- Reviewer findings require the resume path to avoid stale/no-state classification, verify the checked-out branch/PR head, preserve PR identity through repo-unavailable `ensure_pr`, refresh `postmerge`/`done` state on merged resume, handle `PHASE=done` idempotently, avoid premature manifest-DONE routing, explicitly refuse unsupported rebase-continuation handbacks without erasing handoff markers, and keep bash cap ordering by observing pass/already-merged before cap stalls.

## Approach

Add a best-effort resume reconciliation at the top of `run_ship()`. The persisted state file is the floor for session-wide counters only for validated non-fresh resumes; `fresh` always uses literal zero counters.

Compute `_resume_plan()` immediately after repo/tmpdir validation and before any `_write_ship_state(...)` call. Only the `fresh` path may emit the entry `phase="checks"` write. Non-fresh paths must never pass through a pre-resume write with default-zero counters.

Resume starts:

- `blocked-rebase-continuation` — state indicates `RESUME_PHASE=ship-pr-rrr-phase14`. This has highest precedence after reading state/counters: classify it before branch/PR validation, before `done`, before `merged`, and before `open-pr`. Do not silently resume incorrectly; return `NEEDS_USER_INPUT` with a clear unsupported Python-driver continuation detail. Do not call `_write_ship_state()` / `_write_terminal_state()` on this path unless the write explicitly preserves original `PHASE`, `RESUME_PHASE`, and `CALLER_KIND`; the preferred implementation is to leave `ship-pr-state.sh` untouched so the bash continuation token survives repeated invocations.
- `fresh` — no state file; invalid/missing PR identity where one is required; checked-out branch cannot be verified; branch/head mismatch; closed-not-merged PR; normal-repo `gh.pr_view` failure; or any failed validation except the blocked-rebase marker above. Run full checks/postbump/PR/CI path with zero counters.
- `open-pr` — state file exists, PR identity is valid, current checkout matches the expected branch, and either:
  - `gh` is reachable and reports an open PR whose head matches the current branch; or
  - `gh` is intentionally skipped because `repo_unavailable`, `forked`, or `forked_target`, and state `BRANCH_NAME` matches the current branch.
  Skip checks/postbump, hydrate context before any PR-state write, preserve restored counters through every pre-CI `_write_ship_state`, then either reuse the existing PR-only/forked/draft/repo-unavailable early exit or enter CI with restored counters.
- `merged` — state file exists, current checkout validates, PR identity validates, and merged predicates hold. Write `phase="postmerge"` before postmerge with restored counters, run postmerge, then write `phase="done"` on OK.
- `done` — state `PHASE=done` and branch validation passes. Return success idempotently without checks/postbump/ensure/CI/postmerge.

Resume validation rules:

1. If `ctx.state_file` is falsy, return `fresh`. Do not classify from argv/env-only `ctx.pr_number`.
2. Read state phase, resume phase, caller kind, branch, PR identity, PR URL, merge result, and counters.
3. If `RESUME_PHASE=ship-pr-rrr-phase14`, return `blocked-rebase-continuation` immediately, before branch/PR validation or any fresh fallback.
4. Verify the actual checked-out branch with a non-raising probe (`git.try_current_branch` or an equivalent wrapper around existing helpers). Detached HEAD, git errors, or mismatches return `fresh`.
5. Parse `PR_NUMBER` from state first. Fallback to `ctx.pr_number` only when a state file exists and state `PR_NUMBER` is absent/empty, not malformed. Accept only positive base-10 integers.
6. Skip `gh.pr_view` only when `repo_unavailable`, `forked`, or `forked_target`; otherwise call it and treat exceptions as `fresh`.
7. For `open-pr`, require `gh` state `OPEN` and `head_ref` matching the current branch when `gh` is reachable. When `gh` is intentionally skipped, require state `BRANCH_NAME` to match the current branch.
8. For `merged`, accept `gh` state `MERGED`; or state `PR_CLOSED=true`; or state `MERGE_RESULT` in `config.POST_MERGE_MERGE_RESULTS`; or state `PHASE=postmerge`. Treat manifest `DONE` as merged only when state phase/closed/merge-result already agrees. Do not let manifest `DONE` alone force postmerge from an active/open state.
9. Default missing/empty invalid merged `merge_result` to `config.MERGE_RESULT_DRIVER_ALREADY_MERGED`.

Cap-order rule:

- Remove or move the outer pre-monitor iteration-cap stall so `ci_monitor.monitor` / decision logic can observe pass or already-merged outcomes at the cap first. Non-merge/non-pass cap exhaustion should still stall once the decision sees the cap reached.

### Part A — Implementation: persist CI-loop counters + idempotent phase resume (was #3444)

In `python/ship.py`, the CI-loop counters `iteration`, `rebase_count`, `fix_attempts`, and `transient_retries` are function-local to each `run_ship()` invocation, so exit-3/exit-6 handbacks to the orchestrator reset them. This diverges from bash's session-wide 50/20/10 caps and can either bypass the caps across reinvocations or exhaust them too early within a single run. Re-invoking `run_ship()` after a handback also restarts checks/postbump/PR-prep even when a PR already exists or the OOS/CI phases were completed, causing redundant rebase/push/CI churn against an open PR. Port bash's ground-truth phase detection: derive the resume point and caps from `gh`/`git` ground truth plus the run-log manifest (PR exists? merged? OOS filed?) so re-entry resumes near the current phase and the iteration/rebase/fix/transient budgets are session-wide rather than per-process.
