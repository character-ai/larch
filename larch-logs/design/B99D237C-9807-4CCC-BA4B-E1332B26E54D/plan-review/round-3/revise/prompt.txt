## Problem

- `python/ship.py::run_ship()` seeds CI-loop counters to zero on each invocation, so exit-3/exit-6 handbacks reset session-wide caps.
- `_write_ship_state()` persists counters, but entry does not restore them, and terminal/open-PR state writes can overwrite restored counters with zero.
- Re-entry always restarts at checks/postbump/PR creation, causing redundant work against an existing PR.
- Reviewer findings require the resume path to avoid stale/no-state classification, verify the checked-out branch/PR head, preserve PR identity through repo-unavailable `ensure_pr`, refresh `postmerge`/`done` state on merged resume, handle `PHASE=done` idempotently, avoid premature manifest-DONE routing, explicitly refuse unsupported rebase-continuation handbacks, and keep bash cap ordering by observing pass/already-merged before cap stalls.

## Approach

Add a best-effort resume reconciliation at the top of `run_ship()`. The persisted state file is the floor for session-wide counters only for validated non-fresh resumes; `fresh` always uses literal zero counters.

Resume starts:

- `fresh` — no state file; invalid/missing PR identity where one is required; checked-out branch cannot be verified; branch/head mismatch; closed-not-merged PR; or any failed validation. Run full checks/postbump/PR/CI path with zero counters.
- `open-pr` — state file exists, PR identity is valid, current checkout matches the expected branch, PR is open and head matches when `gh` is reachable, or state `BRANCH_NAME` matches when `gh` is intentionally skipped. Skip checks/postbump, hydrate context before any PR-state write, preserve restored counters through every pre-CI `_write_ship_state`, then enter CI with restored counters.
- `merged` — state file exists, current checkout validates, PR identity validates, and merged predicates hold. Write `phase="postmerge"` before postmerge, run postmerge, then write `phase="done"` on OK.
- `done` — state `PHASE=done` and branch validation passes. Return success idempotently without checks/postbump/CI/postmerge.
- `blocked-rebase-continuation` — state indicates `RESUME_PHASE=ship-pr-rrr-phase14`. Do not silently resume incorrectly; return `NEEDS_USER_INPUT` with a clear unsupported Python-driver continuation detail while preserving restored counters.

Resume validation rules:

1. If `ctx.state_file` is falsy, return `fresh`. Do not classify from argv/env-only `ctx.pr_number`.
2. Read state phase, resume phase, branch, PR identity, PR URL, merge result, and counters.
3. Verify the actual checked-out branch with existing git helpers. If the current branch cannot be read or does not match the expected branch/state branch, return `fresh`.
4. Parse `PR_NUMBER` from state first. Fallback to `ctx.pr_number` only when a state file exists and state `PR_NUMBER` is absent/empty, not malformed. Accept only positive base-10 integers.
5. Skip `gh.pr_view` when `repo_unavailable`, `forked`, or `forked_target`; otherwise wrap it in `try/except`.
6. For `open-pr`, require `gh` state `OPEN` and `head_ref` matching the current branch when `gh` is reachable. When `gh` is skipped, require state `BRANCH_NAME` to match the current branch.
7. For `merged`, accept `gh` state `MERGED`; or state `PR_CLOSED=true`; or state `MERGE_RESULT` in `config.POST_MERGE_MERGE_RESULTS`; or state `PHASE=postmerge`. Treat manifest `DONE` as merged only when state phase/closed/merge-result already agrees. Do not let manifest `DONE` alone force postmerge from an active/open state.
8. Default missing/empty invalid merged `merge_result` to `config.MERGE_RESULT_DRIVER_ALREADY_MERGED`.

Cap-order rule:

- Remove or move the outer pre-monitor iteration-cap stall so `ci_monitor.monitor` / decision logic can observe pass or already-merged outcomes at the cap first. Non-merge/non-pass cap exhaustion should still stall once the decision sees the cap reached.
