# [BUG] ship.py postmerge does not write finalize-state.sh; step-18-finalize.sh restore fallback triggers instead

## Context

Observed during `/implement` run `EAE67F5C-3248-4944-A02B-E4C5F941485D` (issue #4103, PR #4172, merged `admin_merged`). The Python `ship.py` driver completed the merge successfully and exited with `outcome=OK`. However, `finalize-state.sh` was absent when `step-18-finalize.sh` ran in Step 18.

## Symptoms

1. `step-18-finalize.sh` reached line 51 (`elif [ ! -f "$IMPLEMENT_TMPDIR/finalize-state.sh" ]`) and found the file missing → `_restore_finalize=true`.
2. `session restore-finalize-state` rebuilt `finalize-state.sh` from `ship-pr-state.sh`.
3. `implement-finalize.sh teardown` then ran successfully: issue renamed to `[DONE]`, tmpdir deleted.
4. The first invocation of `step-18-finalize.sh` (through `larch-run.sh`) exited with code **144** and no output — an unusual exit code suggesting a signal or kill-related exit during teardown.
5. A second direct invocation of `step-18-finalize.sh` emitted `implement-finalize.sh: --state-file must exist and be readable` because by that point teardown from the first invocation had already deleted the tmpdir.

## Root Cause Analysis

`run_postmerge_phase` in `python/ship.py` (line 1162) calls `_write_terminal_finalize_if_terminal(state_ctx, Outcome.OK, "")` which should write `finalize-state.sh` to `$IMPLEMENT_TMPDIR`. The function has two early-return guards:

- `result in {Outcome.TRANSIENT, Outcome.NEEDS_USER_INPUT}` — not triggered by `Outcome.OK`
- `not _tmpdir_under_allowed_root(ctx.tmpdir)` — should pass for a `~/.cache/larch/sessions/` path

The write uses `_write_finalize_text_safely` which does an `O_CREAT|O_EXCL` atomic write to a `.tmp` file followed by `tmp.replace(target)`. If either the initial `write_finalize_state` or the subsequent `write_finalize_state_merged` call raises `ShipError` or `OSError`, the exception propagates. A `ShipError` would be caught by `run_ship`'s `except (NeedsUserInput, ShipError, ...)` → returns `STALLED`. An `OSError` would reach `main()`'s `except Exception` → `INTERNAL_ERROR`. Neither happened — the driver returned `outcome=OK`.

**The write path has no code-level explanation for the absence.** All traced conditions point to the file being written. The most likely cause is one of:

1. **Silent OS-level write failure not surfaced as a Python exception** — e.g., a filesystem flush/sync gap on the atomic rename that left the `.tmp` file orphaned without completing the rename to `finalize-state.sh`. Python's `tmp.replace(target)` can succeed from the Python perspective while the kernel defers the inode update on macOS (APFS), though this is atypical.

2. **`kill_session_background_processes` sent SIGTERM to a process in the step-18-finalize.sh bash chain** before teardown fully flushed. The bash function (implement-finalize.sh line 1040) kills processes whose argv contains `$IMPLEMENT_TMPDIR`. The path `$IMPLEMENT_TMPDIR/finalize-state.sh` appears as an argument to `implement-finalize.sh teardown`, and `step-18-finalize.sh` itself is running as a parent process. The function skips `my_pid` (implement-finalize.sh's bash) and `ppid` (its immediate parent) but does NOT skip grandparent processes in the chain. If a grandparent process had `$IMPLEMENT_TMPDIR` in its argv, it would be sent SIGTERM — which would explain exit code 144 (128 + signal 16 = SIGURG, or possibly 128 + SIGTERM=15 with a macOS process-accounting off-by-one).

3. **Timing/race with another process** cleaning up the sessions directory between the Python write and the bash check — e.g., a concurrent `larch cleanup` or orphaned session-gc run. Less likely since the tmpdir was live and actively in use.

## Impact

The run completed successfully. `restore-finalize-state` is the designed fallback for this case (step-18-finalize.sh lines 48–71). Issue renamed to `[DONE]`, tmpdir cleaned up, PR merged. No data loss.

## What to Investigate

- Whether `_write_terminal_finalize_if_terminal` should log a breadcrumb on success so future runs can confirm the write completed.
- Whether `kill_session_background_processes` in `implement-finalize.sh` (line 1040) should also skip grandparent PIDs (not just `my_pid` and `ppid`) to avoid accidentally signaling the step-18-finalize.sh bash chain.
- Whether exit code 144 from the first `step-18-finalize.sh` invocation came from `kill_session_background_processes` sending a signal to a process in the bash lineage, and whether that is related to `finalize-state.sh` being absent (i.e., a prior teardown attempt that terminated mid-write).
