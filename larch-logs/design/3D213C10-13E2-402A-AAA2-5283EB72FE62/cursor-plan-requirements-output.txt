## Findings

1. **[correctness]** `scripts/run-external-agent.sh:150-254` / `scripts/write-session-env.sh:189-216` — Production session-env wiring does not activate the gate in `/implement`.

   The plan’s Decision 2 (“on in production via session-env writers”) assumes persisting `LARCH_EXTERNAL_HEALTH_CHECK_TIMEOUT` in session env is enough. That holds for `/design`, where `write-design-current-env.sh` emits sourceable `export` lines and every Bash block sources `current-design-env-$PPID.sh`. It does not hold for `/implement`: `write-session-env.sh` writes a non-sourceable `KEY=VALUE` file, and `skills/implement/SKILL.md` rehydrates only `LARCH_TOKEN_SESSION_ID`, `LARCH_CLAUDE_SOURCE_FILE`, and `LARCH_TIMING_LEDGER` from `$IMPLEMENT_TMPDIR/session-env.sh` — not the new timeout key. Because `run-external-agent.sh` gates only on process environment, production `/implement` launches (Step 2 coder, Step 5 review, `lint-fix-loop.sh`, etc.) would still run with the gate OFF despite the new session-env default.

   **Suggested revision:** At the chokepoint (in `run-external-agent.sh` or `external_launch_health_gate`), when process env lacks a positive integer, read `LARCH_EXTERNAL_HEALTH_CHECK_TIMEOUT` from `$IMPLEMENT_TMPDIR/session-env.sh` using `read-session-env-key.sh`. That matches the single-chokepoint design and avoids touching dozens of SKILL rehydration sites. Optionally add one integration assertion that a stub unhealthy probe fast-fails when the key exists only in `session-env.sh`, not in the process env.
