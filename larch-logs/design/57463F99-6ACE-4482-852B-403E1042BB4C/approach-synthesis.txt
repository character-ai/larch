### Rule body content (architectural intent only — exact wording is a Step 2b detail)
- Front-matter `paths:` listing as above.
- Title `# gh ... --body / --notes — file-backed only`.
- The forbidden pattern (single short example fence): `gh pr create --body "$(cat <<'EOF' ... EOF)"` — failure-mode: heredoc tokens inside `$()` get corrupted by the surrounding shell when the body contains markdown backticks.
- The required pattern: Write the body to `$IMPLEMENT_TMPDIR/pr-body.md` (or another local tmpdir path), then `gh pr create ... --body-file <path>`; or use `scripts/create-pr.sh --title T --body-file F` for PR creation in this repo.
- Coverage clause: same rule applies to `gh issue create --body[-file]`, `gh issue comment --body[-file]`, `gh pr comment --body[-file]`, `gh release create --notes[-file]`. Out of scope: `git commit -m`, `--title` text, any `gh` command without `--body`/`--notes`.
- One brief sentence pointing at companion `BASH_AUTHORING.md §2` ("Bash Quoting Hygiene") so readers know where the broader heredoc/quoting context lives.

### Tradeoffs
- Trigger coverage vs. noise: narrow `paths:` keeps the rule out of unrelated edits. Will not fire for future files that invoke `gh ... --body` — accepted per Round 1 #3.
- Mechanism strength: declarative rule only (no PreToolUse hook) means the rule relies on the model. Accepted per Round 1 #2.
- Consistency at landing: fixing the one inline-`--body` violation in `design-log-publish.sh` is in-scope for the PR; deferring it would leave the rule's prescriptive tone contradicted at landing.
