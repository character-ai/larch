Implement this as a single new path-triggered rule, probably `.claude/rules/gh-body-file.md`. The rule should be prescriptive, not advisory: never compose multiline or generated GitHub text inline with `gh ... --body` or `--notes`; write the content to a temp/body file first, then pass `--body-file` or `--notes-file`. For `gh pr create` in this repo, the rule should route through `scripts/create-pr.sh --title ... --body-file ...`, since that wrapper already owns push semantics, tmpdir redaction, diagnostics, and existing-PR handling. This extends the existing `BASH_AUTHORING.md` quoting guidance into the GitHub CLI surface that actually caused the failure.

I would add only the new rule file under `.claude/rules/`, with narrow `paths:` frontmatter covering PR/body-adjacent surfaces: `AGENTS.md`, `BASH_AUTHORING.md`, `scripts/create-pr.{sh,md}`, `scripts/ship-pr.{sh,md}`, `scripts/gh-pr-body-update.{sh,md}`, `scripts/design-log-publish.{sh,md}`, `scripts/tracking-issue-write.{sh,md}`, `scripts/clarify-comment-post.{sh,md}`, `scripts/plan-block-write.{sh,md}`, `skills/implement/SKILL.md`, `skills/issue/SKILL.md`, `skills/design/SKILL.md`, and `skills/design/scripts/decompose-file-issues.{sh,md}`. Those are the surfaces I found that either create/update PR bodies, issue bodies/comments, or contain prompt-side examples of `gh issue comment` / PR lifecycle behavior.

The main tradeoff is trigger coverage versus noise. A narrow rule avoids injecting GitHub CLI guidance while editing unrelated docs, but it will not fire for every future file that happens to add `gh ... --body`; that is acceptable given the user’s rule-only decision and “PR-adjacent only” scope. The other risk is wording drift with wrappers: `create-pr.sh` and `gh-pr-body-update.sh` already enforce file-backed bodies, while `scripts/design-log-publish.sh` currently has a short inline `gh pr create --body`; the rule should make that an obvious future cleanup target without requiring a hook or immediate mechanical enforcement.
