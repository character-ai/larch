## Findings

**1. risk-integration — `python/oos_filer.py:788-792` (blocking, in_scope)**  
The plan only lists `python/file_oos.py` for algorithm, caps, and atomic CLI output. `python/oos_filer.py` already calls `file_oos.file_conflict_deps(combined)` in-process at lines 788-792 and only handles `OSError`. That is a second Step 9a.1 consumer beside the CLI path in `skills/implement/references/oos-pipeline.md:43-46`. Porting caps into `file_conflict_deps()` without updating `oos_filer.py` will either hard-fail OOS filing on global-cap exceed (violating degraded-continue) or skip caps on the Python ship path.

**Suggested revision:** Add `### UPDATED: python/oos_filer.py` with a narrow catch of the same global-cap error the CLI maps to exit 1; keep existing warning-plus-continue behavior.

**2. correctness — `skills/implement/scripts/oos-file-conflict-deps.sh:284-289` (important, in_scope)**  
Bash adds one candidate edge per item pair, then `break`s. The plan says “build candidate conflict edges” and “union-find” but not this cap on pair multiplicity. Duplicate rows change `cluster_edges` counting used for `OOS_FILE_CONFLICT_CLUSTER_CAP` at lines 311-316, so Tier-1/Tier-2 behavior can diverge from fixtures case-j, case-k, and case-s.

**Suggested revision:** State explicitly in the `python/file_oos.py` section: at most one candidate edge per `(i,j)` pair.
