# /design plan-size guardrail: split oversized plans into serial part issues before /implement

#### Problem

`/design` finalized a single HARD plan for #6514 with roughly 85 firm `NEW:`/`UPDATED:` headings and `diff_lines: 4800`. `/implement` hands the whole plan to one external implementer invocation (single one-shot by contract). No single one-shot reliably lands an 85-file cross-cutting migration, and this one did not: 25 files landed, 61 were left untouched, and the remainder had to be hand-filed afterward as #6524. The plan review loop scored plan quality and clarity but nothing evaluated whether the plan fits inside one implementer pass.

#### Proposal (for /design to refine)

1. Add mechanical plan-size signals at plan finalization: count of firm `NEW:`/`UPDATED:`/`REWRITTEN:` headings (excluding `MAY_UPDATE:`), declared `diff_lines`, and count of distinct top-level surfaces touched (`skills/`, `python/larch/&lt;pkg&gt;`, `scripts/`, `docs/`). Emit them in the plan block or plan-quality output.
2. Add thresholds in `python/larch/core/config.py`, calibrated from committed run logs (`/report-tokens` and `/difficulty-calibration` data), with initial values on the order of: firm headings above 25, or `diff_lines` above 1500, or surfaces above 4. Exceeding any threshold marks the plan oversized.
3. An oversized plan cannot finalize as a single issue by default. `/design` must either decompose it into serial part issues (part 1..N) with native blocked-by edges, per-part firm-heading inventories, and per-part acceptance criteria, or record an explicit operator override in the plan block (an `oversize_override: operator` line adjacent to `diff_lines:`), so the choice is visible to `/implement` preflight and in the run log.
4. Reuse existing machinery where it fits: the plan grammar already carries `diff_lines:`; plan-quality checks already run at finalization (`python/cli.py plan-quality` surfaces); the `/design` decompose panel machinery may be reusable for proposing the part boundaries. Decomposition must preserve the clarify round-trip and `larch:plan` wire format per `docs/issue-anchored-plan.md`.
5. Part issues get the same review rigor: each part's plan block carries its own `review_status` and `rounds_completed` provenance so `/implement` preflight admission works unchanged per part.

The companion issue filed alongside this one makes `/implement` fail closed on such gaps; this issue prevents the oversized single plan from reaching `/implement` at all.
