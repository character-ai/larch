**1. [correctness]** `skills/implement/references/stall-recovery.md:41-47` — Dedup normalization keeps indexed keys instead of mapping to consumer keys.

The plan’s step-4 rewrite says to map `ISSUE_1_NUMBER`/`ISSUE_1_URL` on create, and on dedup to “also persist `ISSUE_1_DUPLICATE_OF_NUMBER` and `ISSUE_1_DUPLICATE_OF_URL`.” That wording stores indexed duplicate keys under their `/issue` names, not under `ISSUE_NUMBER`/`ISSUE_URL`.

On dedup, batch `/issue` emits only indexed duplicate keys — no `ISSUE_1_NUMBER`:

```332:337:skills/issue/SKILL.md
- If `ITEM_<i>_VERDICT=DUPLICATE` with `DUPLICATE_OF=<N>`: emit
  - `ISSUE_<i>_DUPLICATE=true`

```

Step 8’s only reader loads `ISSUE_NUMBER` from `stall-recovery-issue.env`; nothing reads `ISSUE_1_DUPLICATE_OF_*`:


**Scenario:** Dedup fires on first-detection filing → env file contains `ISSUE_1_DUPLICATE_OF_NUMBER=…` but no `ISSUE_NUMBER` → terminal `gh issue comment` misses the recovery issue (same failure mode #3568 targets).

**Suggested revision:** Make step 4 explicit: if `ISSUE_1_DUPLICATE=true`, write `ISSUE_NUMBER`/`ISSUE_URL` from the `DUPLICATE_OF_*` lines; else write them from `ISSUE_1_NUMBER`/`ISSUE_1_URL`. Match the OOS batch pattern at `skills/implement/references/oos-pipeline.md:48-49` (“Treat both created URLs and duplicate-of URLs as valid disposition URLs”).
