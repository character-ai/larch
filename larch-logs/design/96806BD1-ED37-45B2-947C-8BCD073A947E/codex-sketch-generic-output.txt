I’d put the rating capture at the tally boundary, not in the main `/design` orchestrator. `plan-review-loop.sh` already owns round number, ballot creation, voter dispatch, and calls [tally-plan-review.sh](<OPERATOR_REPO_PATH>/skills/design/scripts/tally-plan-review.sh), while [lib-vote-tally.sh](<OPERATOR_REPO_PATH>/scripts/lib-vote-tally.sh) already provides anchored vote parsing. Extend that layer with a shared parser, either as `scripts/parse-judge-vote-and-rating.sh` plus a small sourced function, or directly in `lib-vote-tally.sh` if reuse with `/review` is expected. The parser should keep today’s vote behavior stable, then extract optional `CORRECTNESS=... SEVERITY=... QUALITY=... UNCERTAIN=...`; missing rating keys become `uncertain/uncertain/uncertain/true` or `uncertain/.../false` depending on the exact contract chosen. `tally-plan-review.sh` should write one row per ballot block, using `reviewer_for_block` for `reviewer_slots`, existing `classify_result` for `voting_result`, and the three voter files positionally for `v1_*` through `v3_*`. Since `plan-review-loop.sh` already has `ROUND_NUM`, it should pass an explicit output path such as `$DESIGN_TMPDIR/plan-review/round-$ROUND_NUM/findings-classification.tsv` into tally rather than making tally infer round state.

Files to modify would be [skills/shared/scripts/render-voter-prompt.sh](<OPERATOR_REPO_PATH>/skills/shared/scripts/render-voter-prompt.sh) for the runtime voter format, [scripts/dispatch-plan-voters.sh](<OPERATOR_REPO_PATH>/scripts/dispatch-plan-voters.sh) only if it needs a plan-only renderer flag or retry-prefix changes, [skills/design/references/plan-review.md](<OPERATOR_REPO_PATH>/skills/design/references/plan-review.md) for the normative prompt contract, [scripts/lib-voter-parse-rate.sh](<OPERATOR_REPO_PATH>/scripts/lib-voter-parse-rate.sh) so retry text does not ask for the old shorter format, [skills/design/scripts/tally-plan-review.sh](<OPERATOR_REPO_PATH>/skills/design/scripts/tally-plan-review.sh) for TSV emission, and likely [skills/design/scripts/plan-review-loop.sh](<OPERATOR_REPO_PATH>/skills/design/scripts/plan-review-loop.sh) to pass the round-aware output path. Add harness coverage beside the existing tally and prompt tests: extend `test-tally-plan-review.sh`, `test-render-voter-prompt.sh`, `test-dispatch-plan-voters.sh`, and add the requested classification-focused harness. `design-log-publish.sh` currently stages only depth-1 design tmpdir files plus `render-cache/`, so nested `plan-review/round-N/` publishing either depends on #2666 or needs a recursive allowlist update here. `docs/run-logs.md`, `docs/linting.md`, and `Makefile` should be updated for the new artifact and test target.

Main risk is prompt/parser drift. The voter renderer is shared with code review, so the rating instructions should be gated to plan review, or code review voters will suddenly be asked for fields no downstream code consumes. Another risk is degraded or malformed voter output: existing parse-rate logic accepts `ID: VOTE ...`, but its retry prose and diagnostics still describe the old exact shape. The implementation should distinguish a missing judge, which gets empty TSV columns, from a present judge that omitted a ballot item, which should remain visible as a parse error rather than silently becoming an “uncertain” rating. The log publishing dependency is the other practical risk: producing the TSV in the tmpdir is straightforward, but proving it lands under committed `larch-logs/design/<RUN_ID>/plan-review/round-<N>/` requires either #2666’s recursive staging or a targeted publish change in this issue.
