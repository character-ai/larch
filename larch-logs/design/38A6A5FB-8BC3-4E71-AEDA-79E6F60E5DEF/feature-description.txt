# [BUG] (URGENT) Multiple failures caused /design plan review to silently skip and still publish [DESIGNED]

## Summary

A `/design 4168` run in larch3 encountered a chain of failures that caused the plan-review panel to be silently skipped and the design to publish successfully anyway (wrote `larch:plan` to the issue, renamed to `[DESIGNED]`). The operator had to manually detect the failure, rename the issue back, and re-run. This documents every problem observed, their root causes, and required hardening.

- **Session**: `E6F4D92C-008D-4687-99F3-7575EC2A12AC`
- **Issue**: #4168 (Results collector and retry contracts)
- **Repo**: larch3 (`character-ai/larch`)

## Bugs observed

### Bug 1 — Codex drafter emitted `mechanical_churn: 1100` (integer instead of boolean)

**Symptoms:**
- `design-step2b-drafter.sh` returned exit 1 with: `**⚠ 2b: post-plan emit failed (plan-size-failed); repair plan.txt before Step 2b.5 / Step 3.**`
- `execution-issues.md` recorded: `PLAN_SIZE_STATUS=invalid-mechanical-churn`
- The orchestrator had to manually edit `plan.txt` to change `mechanical_churn: 1100` → `mechanical_churn: true` before continuing

**Root cause:**
The Codex drafter wrote `mechanical_churn: 1100` (the actual churn line count as a numeric estimate) instead of the required boolean `mechanical_churn: true`. The `plan check-size` validator treats `mechanical_churn:` as a strict boolean and rejects non-`true`/`false` values with `PLAN_SIZE_STATUS=invalid-mechanical-churn`.

**Required fix:**
- The drafter prompt (Step 2b inline instructions) must be clarified to state that `mechanical_churn:` accepts only `true` or `false`, never a number.
- `plan check-size` should emit a clearer error distinguishing "wrong type" from "wrong value" so operators know to fix the trailer, not the plan body.
- Consider whether the validator should accept `mechanical_churn: <N>` as a synonym for `mechanical_churn: true` to be resilient to this drafter error.

### Bug 2 — `plan-review-scope-anchor.txt` absent from DESIGN_TMPDIR after Step 3 ran

**Symptoms:**
- After `design-step3-review.sh` returned `panel-failed`, inspection of DESIGN_TMPDIR confirmed `plan-review-scope-anchor.txt` did not exist.
- The `plan-review/` directory was created but was completely empty (no `round-1/` subdirectory).
- `ROUNDS_COMPLETED=1`, `DEGRADED_PANEL=0`, but zero reviewers were launched.

**Root cause:**
The embedded plan-review bash loop (`run-step3-review.sh` → `plan-review-loop.sh`) expects `$DESIGN_TMPDIR/plan-review-scope-anchor.txt` as a required input to scope reviewer prompts. The scope anchor creation runs inside the embedded loop during Step 3 initialization (before `round-1/` is created). If scope anchor creation fails — for example, because `python3 cli.py plan-block strip-body` returns an error or empty output for the issue body — the loop exits before creating any round directory, writing `panel-failed` to the result env.

The scope anchor was never created and never appears in DESIGN_TMPDIR, confirming the loop aborted during initialization, not during reviewer dispatch.

**Contributing factor:**
Issue #4168 originally had a placeholder `larch:plan` block body `(needs /design — operator runs /design on this issue after partition lands.)`. The `plan-block strip-body` command strips this block from the issue body to form the scope anchor. If the stripped result was empty or the command failed silently, the scope anchor could be empty or missing, causing the loop to exit.

**Required fix:**
- `design-step3-entry.sh` (or `design-step3-entry-state.sh`) must create and validate `plan-review-scope-anchor.txt` **before** launching `design-step3-review.sh`. If the scope anchor is absent or empty after the entry script completes, abort with a clear error before the background job is launched.
- Add a guard in `design-step3-review.sh`: if `plan-review-scope-anchor.txt` does not exist at launch time, exit immediately with a recoverable error (not `panel-failed`) so the operator can diagnose the missing prerequisite.
- The embedded `plan-review-loop.sh` / `run-step3-review.sh` should emit a clear diagnostic when the scope anchor is missing, not silently translate the failure to `panel-failed`.

### Bug 3 — `panel-failed` is treated as a degradation path; `/design` succeeds and publishes `[DESIGNED]`

**This is the most critical bug.**

**Symptoms:**
- `STEP3_REVIEW_LOOP_STATUS=panel-failed` was returned by `design-step3-review.sh`.
- The SKILL.md orchestrator treated this as a Gate B bypass → proceeded to Step 3b (arch diagram) → Step 4 (rejected findings) → Gate C → Step 5 (plan write) → Step 6 (cleanup).
- The `larch:plan` block was written to issue #4168.
- The issue was renamed `[DESIGNED]`.
- Gate C was presented as `"Approve final design"` with no visible indication that zero reviewers had run.
- The operator approved Gate C without knowing the review panel had never executed.

**Root cause:**
The SKILL.md design encodes `panel-failed`, `tally-error`, and `degraded-empty-collector` as **non-terminal degradation statuses** that bypass Gate B but continue the full design flow to Gate C and plan publication. This is correct when the panel fails after launching reviewers (e.g., all reviewers timeout). It is incorrect when the panel fails before launching any reviewers (scope anchor missing, initialization error), because zero review coverage was provided.

The current behavior makes no distinction between:
- "Panel ran, all reviewers failed or returned empty" (degraded but some coverage existed)
- "Panel never launched any reviewers" (zero coverage)

Both produce `panel-failed` and both succeed through Gate C.

**Required fix:**
- `panel-failed` with `DEGRADED_PANEL=0` and no `round-1/` directory must be treated as a **hard stop**, not a degradation path.
- A new status should distinguish "panel launched but all failed" (current `panel-failed` semantics) from "panel never launched" (new: `panel-init-failed` or similar).
- Gate C must be blocked (or at minimum display a mandatory warning requiring explicit acknowledgment) when `panel-failed` is the review outcome, regardless of degradation level.
- The SKILL.md orchestrator must refuse to proceed to Step 5 (plan write) when the review panel produced zero findings because zero reviewers ran.

### Bug 4 — `/implement` Preflight does not verify that plan review ran

**Symptoms:**
- Not directly observed in this run, but a consequence of Bug 3: an `/implement` run on issue #4168 (now `[DESIGNED]`) would have proceeded without any plan review having occurred.

**Root cause:**
The `larch:plan` block in a `[DESIGNED]` issue carries no metadata about whether plan review succeeded, degraded, or was skipped. The `/implement` Preflight only validates that a `larch:plan` block exists and is structurally valid; it does not check review provenance.

**Required fix:**
- The `larch:plan` block written in Step 5c should include a `review_status:` field capturing the outcome (`complete`, `cap-hit`, `panel-failed`, `panel-init-failed`, `panel-skipped`, etc.) and `rounds_completed: N`.
- `/implement` Preflight must read `review_status:` and refuse to proceed when `review_status` is `panel-init-failed`, `panel-skipped`, or any status indicating zero reviewers ran.
- Alternatively (or in addition), larch must refuse to write a `larch:plan` block or rename to `[DESIGNED]` when `panel-failed` with zero reviewers ran.

### Bug 5 — Design log publish failed due to stale worktree

**Symptoms:**
- Step 5c reported: `design log publish failed; recovery metadata: recovery branch larch-log-design-E6F4D92C-008D-4687-99F3-7575EC2A12AC`
- The design-log-publish failure log contained: `design-log-publish: branch larch-log-design-E6F4D92C... is already checked out in another worktree; concurrent or stale publish for this RUN_ID`

**Root cause:**
A prior attempt (the first `design-step5c.sh` call, which ran as an immediate-background task) may have begun the log publish before the orchestrator ran it synchronously for recovery. The RUN_ID-keyed branch was left checked out in a worktree from that first attempt.

**Required fix:**
- `design-log-publish.sh` should detect and clean up stale same-RUN_ID worktrees from previous failed publish attempts before retrying.
- The recovery path should automatically retry publish after cleaning up the stale worktree, rather than requiring operator intervention.

### Bug 6 — `feature-description.txt` absent from DESIGN_TMPDIR on the `already-planned→replace` path

**Symptoms:**
- After choosing "Replace via full flow" from the already-planned prompt and running `design-step0-init.sh`, `feature-description.txt` was not written to DESIGN_TMPDIR.
- The file is listed as an input for Step 2b and Step 3 processing but was absent throughout the run.

**Root cause:**
`design-step0-init.sh` (the Sub-step 6 init wrapper) writes `feature-description.txt` only when `ROUTE=proceed`. On the `already-planned` path, even when the operator chooses "Replace via full flow", the route is still `already-planned` internally — the wrapper may not treat the replacement branch as equivalent to `proceed` for the purposes of writing `feature-description.txt`.

**Required fix:**
- The `already-planned→replace` path must be treated as functionally identical to `proceed` for the purposes of DESIGN_TMPDIR initialization. `design-step0-init.sh` must write `feature-description.txt` on this path.
- Add a guard: if `/design` proceeds past Step 0 to Step 1c/1d/2b without `feature-description.txt`, emit a clear error rather than silently continuing with a missing input.

### Bug 7 — Failure reporter returned `compose-status-missing`; no bug issue was auto-filed

**Symptoms:**
- `design-failure-report.stdout.log` contained: `DESIGN_FAILURE_REPORT_DECISION=fallback-print-required DESIGN_FAILURE_REPORT_REASON=compose-status-missing`
- No bug issue was automatically filed despite the `panel-failed` escalation.

**Root cause:**
The `design-failure-report.sh` gate requires `COMPOSE_STATUS` metadata to decide whether to file an issue. When `panel-failed` happens without the full compose flow completing (because the publish was also attempted and failed), `COMPOSE_STATUS` was not populated, causing the reporter to fall back to `print-only` mode.

**Required fix:**
- The failure reporter should not require `COMPOSE_STATUS` to file a `panel-failed` issue — panel failure is a terminal, always-escalating condition regardless of publish outcome.
- `panel-init-failed` (zero reviewers launched) must always trigger an auto-filed issue, not a fallback print.
