# [py-code-quality] Re-enable complexity linters as warnings on new/changed code

**Problem.** ruff currently ignores `C901`, `PLR0911`, `PLR0912`, `PLR0913`, `PLR0915` (complexity, returns, branches, args, statements). Pragmatic during the bash-to-Python migration, but it removed the guardrail, so new god-functions keep landing: `python/ship.py:run_ship` spans ~749 lines; `python/review_pipeline.py:review_core` ~350; `python/design_lifecycle.py:failure_report_core` ~355.

**Proposed change.** Add a ratchet: re-enable these rules as warnings (or errors scoped to changed files) so existing debt is grandfathered but new/refactored code is held to a complexity budget. Options: per-file ignores removed as modules are cleaned, or a changed-files lint lane. Pick the lowest-friction mechanism that stops the bleeding.

**Out of scope.** Do not fix existing violations here (that is the god-function-split item).

**Acceptance.** New code over the thresholds is flagged in CI / `make py-lint`; existing files stay green via grandfathering; mechanism documented in `docs/linting.md`.

**Effort / risk.** Low / low. One config + docs change.

**Dependencies.** Root (no blockers). Independent.
