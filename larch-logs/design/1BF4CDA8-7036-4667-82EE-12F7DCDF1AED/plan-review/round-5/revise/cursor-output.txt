## Plan

## Approach

- Re-enable `C901`, `PLR0911`, `PLR0912`, `PLR0913`, and `PLR0915` as hard ruff errors for `python/`.
- Grandfather current production violations with `[lint.per-file-ignores]` entries generated at implement time from live ruff JSON output so the main `ruff check .` pass stays green on the existing tree.
- Add a **baseline-comparison ratchet** so grandfathered production modules are not fully blind: a dedicated audit pass (without production per-file grandfather entries) compares live violations to a committed baseline manifest keyed by **stable qualified function identity plus observed metric**, not raw line numbers or message-local bare names.
- Exempt pytest-facing code by adding the same five codes to:
  - the existing `"test_*.py"` block, and
  - dedicated entries for pytest harness modules outside that glob: `conftest.py`, `test_support.py`, and `review_test_support.py`.
- Keep scope to config, one small lint module, baseline manifest, Makefile wiring, and docs. Do not refactor existing Python logic.
- Do not embed a frozen per-file inventory in the plan or transcribe a stale file list during implementation.

**Ratchet model (two layers):**

1. **Main ruff (`make py-lint-main`)** — production per-file ignores suppress listed complexity codes for entire grandfathered modules so CI stays green on known debt. This layer primarily blocks **new production modules** (or new violation types not yet listed for a partially grandfathered file).
2. **Baseline audit (`python/cli.py lint complexity-baseline`)** — runs ruff with test/harness exemptions only (no production per-file grandfather entries), compares output to `python/complexity-baseline.json`, and fails on:
   - any new `(file, code, qualified_symbol)` identity not present in the baseline, or
   - any existing `(file, code, qualified_symbol)` whose **observed metric increased** above the baselined value.

Per-file production ignores are cleanup bookkeeping; the baseline manifest is the enforcement backstop for growth inside grandfathered files. Docs must state both behaviors explicitly and must not imply refactors inside grandfathered modules are automatically budgeted.

**Stable baseline identity (addresses line-number churn, PLR message shape, and name collisions):**

- Do **not** key the baseline on `line`. Innocent edits above a grandfathered function shift ruff's reported line while complexity is unchanged; line-keyed baselines would false-fail normal refactors in modules such as `ship.py`, `review_pipeline.py`, and `design_lifecycle.py`.
- Do **not** key the baseline on the bare function name parsed from ruff messages alone. PLR rules (`PLR0911`–`PLR0915`) emit messages such as `Too many return statements (18 > 6)` with **no** backtick-quoted symbol; using message text for PLR identity would fail closed on the existing tree. A single production file can also contain multiple callables with the same simple name (for example three `run` definitions in `proc.py`: module-level `run`, `Runner.run`, and `ProcRunner.run`).
- Parse each ruff JSON violation into:
  - `file`: repo-relative path under `python/` (normalize away leading `./` and optional `python/` prefix; use forward-slash paths)
  - `code`: rule code (`C901`, `PLR0911`, etc.)
  - `qualified_symbol`: dot-separated qualified name resolved from source at ruff's reported line via `ast` (innermost enclosing `FunctionDef` / `AsyncFunctionDef`, prefixed by enclosing class names when present; nested functions become `outer.inner`)
  - `metric`: observed count parsed from the message's `(observed > limit)` clause (first integer)
- Baseline comparison index: `(file, code, qualified_symbol) -> metric`.
- **Pass** when every live violation's key exists in the baseline and `live.metric <= baseline.metric`.
- **Fail** on a new `(file, code, qualified_symbol)` or on metric growth for an existing key.
- **Fail closed** (exit 2) when any production violation cannot be resolved to `qualified_symbol` and `metric`, when baseline JSON is missing/malformed, or when baseline generation or loading detects duplicate `(file, code, qualified_symbol)` keys (no last-wins overwrite).
- **Residual edge case (documented):** renaming or moving a function changes `qualified_symbol`; cleanup requires shrinking the baseline and per-file ignores intentionally. Swapping two function bodies without renaming is out of scope for this ratchet.

**Ruff audit subprocess exit semantics:**

- Audit runs use `ruff check ... --output-format json`. When production violations exist, ruff exits **1** while still printing valid violation JSON on stdout.
- Treat ruff exit **0** (no violations) and **1** (violations present) as success paths when stdout JSON parses.
- Reserve audit-tool exit **2** for ruff spawn failure, ruff exit **>= 2**, empty/unparseable JSON, unparseable violations, missing/malformed baseline, or duplicate keys.
- Reserve audit-tool exit **1** for baseline regressions (`find_regressions` non-empty).
- The manual baseline-derivation command below also expects exit **1** when violations exist; parse stdout JSON regardless.

### NEW: `python/complexity-baseline.json`

- Committed baseline manifest generated at implement time from the audit-config scan (not from the main config scan that includes production per-file ignores).
- **Top-level wire shape (normative):** a JSON **array** of violation records, sorted stably by `(file, code, qualified_symbol)`. No wrapper object and no alternate top-level keys.
- Each record object has exactly these keys:

```json
[
  {
    "file": "proc.py",
    "code": "PLR0913",
    "qualified_symbol": "ProcRunner.run",
    "metric": 8
  },
  {
    "file": "ship.py",
    "code": "C901",
    "qualified_symbol": "run_ship",
    "metric": 42
  }
]
```

- Derive `qualified_symbol` and `metric` with the same parser used at audit time (see `python/lint_complexity_baseline.py` below). Do **not** store `line`.
- Include every production violation from the initial audit scan. Exclude exempt test/harness paths using the same exclusion rules as production per-file grandfather generation.
- During generation, **fail closed** if two violations collapse to the same `(file, code, qualified_symbol)`; do not emit a manifest with silent overwrites.
- Regenerate only when intentionally shrinking debt (remove entries when violations are fixed) or when the audit contract changes.

## Edge cases

- The production baseline must exclude `test_*.py` and the three pytest harness modules listed above, because those paths are intentionally exempt.
- If ruff reports a production file during the post-change acceptance scan, add it only from the live JSON output for the current tree. Do not guess codes or filenames.
- Harness modules such as `review_test_support.py` must never be treated as production grandfather targets; they belong in the harness exemption block.
- Production per-file ignores and the baseline manifest must be generated from the same initial audit scan so they stay consistent; do not maintain one from a stale embedded list.
- A new complexity violation in a grandfathered file must fail the baseline lint even when per-file ignores would suppress it in the main ruff pass.
- Adding branches/returns/statements inside an already-violating function must fail when ruff's reported `metric` increases, even if the definition line is unchanged.
- Innocent edits that shift ruff's reported line but leave `qualified_symbol` and `metric` unchanged must pass the baseline audit.
- Intentional baseline shrink (after fixing debt) requires editing both the per-file ignore entry and `complexity-baseline.json`.
- Function rename or move changes `qualified_symbol` and leaves an orphaned baseline row until cleanup; the new qualified name is treated as new complexity debt.
- Multiple violations in one file with the same simple name (for example several `run` callables) must produce distinct `qualified_symbol` values or baseline generation must fail closed.
- Ruff audit scans with violations present exit **1**; parsers must consume stdout JSON anyway. Only exit **>= 2** indicates tool/config failure.
- Ruff JSON `filename` values may vary (`ship.py`, `./ship.py`, `python/ship.py`) when `cwd=python/`; normalization must keep generation and comparison on the same canonical `file` key.
- Do not add threshold settings. Ruff defaults are the intended budget.
- Do not add a changed-files lint lane, extra Makefile target beyond wiring into `py-lint-main`, or CI workflow change beyond what existing `python-lint` / `python-tests` jobs already run.
- Pytest for this feature must not require installing ruff in `python/requirements-test.txt`; subprocess stays mocked and helpers are tested with fixture JSON plus small inline Python source fixtures for AST resolution.

## Failure modes

- If a production violation is missed during baseline generation, `make py-lint` will fail on the existing tree (main ruff pass and/or baseline comparison).
- If a global ignore remains for any of the five codes, new code will not be guarded.
- If broad globs are used for production files, the ratchet will not stop new violations in those modules.
- If the implementer transcribes a stale embedded file list instead of regenerating from ruff JSON, harness or production modules can be omitted and CI will fail before any new code lands.
- If only production per-file ignores are added without the baseline audit, grandfathered modules such as `ship.py`, `review_pipeline.py`, and `design_lifecycle.py` remain whole-file blind spots for the listed codes; new over-threshold functions added there would still pass main ruff until the per-file entry is edited during cleanup.
- If `ruff-complexity-audit.toml` accidentally includes production per-file grandfather entries, the baseline ratchet becomes a no-op for growth inside existing violators.
- If the baseline manifest drifts from live debt without intentional cleanup, CI fails until the manifest is regenerated or violations are fixed.
- If baseline keys use raw line numbers, normal refactors inside grandfathered modules false-fail until manual JSON rebaseline.
- If baseline keys use bare message-local names, PLR violations are unparseable and `make py-lint` cannot go green; duplicate simple names can false-pass growth or false-fail as spurious new identities.
- If duplicate `(file, code, qualified_symbol)` rows last-wins during generation, the audit can compare against the wrong callable and miss metric growth.
- If `complexity-baseline.json` uses an undocumented wrapper shape or invalid JSON, loader/tests disagree and the first CI run fails with exit 2.
- If baseline keys omit `metric`, complexity growth inside an existing violating function can pass undetected when ruff keeps reporting the same qualified identity.
- If the audit tool treats ruff exit **1** as failure, `make py-lint-main` stays red on the unchanged tree despite valid violation JSON.
- If `file` paths are not normalized, `./ship.py` vs `ship.py` splits baseline keys and causes spurious `(new)` regressions.
- If `py-lint-main` invokes `python/cli.py` from inside `cd python`, the target breaks with `python/python/cli.py` not found.
- If pytest spawns real ruff without adding it to `python/requirements-test.txt`, the `python-tests` CI job fails on missing binary.

## Testing strategy

- Before editing config, run the audit-config baseline derivation command and confirm JSON output includes only expected production violators plus any exempt paths you intend to ignore separately; confirm ruff exit **1** is expected when violations exist.
- After editing `python/ruff.toml`, run the main-config acceptance command and confirm exit 0.
- Generate `python/complexity-baseline.json` from the audit-config scan using the stable top-level array schema `{file, code, qualified_symbol, metric}`; confirm generation fails closed on duplicate keys and that `python/cli.py lint complexity-baseline` exits 0 on the unchanged tree.
- Run `make py-lint`.
- Run `python3 -m pytest python/test_lint_complexity_baseline.py` (fixture/subprocess-mock tests only; no ruff install required in `python-tests`).
- Run `make lint` because docs changed.
- No full `make py-test` is required unless implementation adds Python logic beyond the new lint module and its tests (run targeted pytest for the new module regardless).
