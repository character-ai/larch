## Approach

1. Grow `larch.review.review_types` into the sole Python owner of the FINDING/OOS block grammar.
   - Add a frozen block value type that exposes the item ID, kind, title, and complete block text.
   - Add `parse_blocks()` for canonical `### FINDING_<number>:` and `### OOS_<number>:` headings.
   - Require exactly three heading hashes. Ignore heading-like text inside fenced code blocks.
   - Preserve the existing boundary choices where consumers stop at any level-three heading versus the next FINDING/OOS heading.
   - Keep `parse_findings()` and `parse_findings_text()` as compatibility surfaces backed by the shared parser.
   - Add shared heading and ID parsing operations needed by validation, normalization, and reporting consumers.

2. Move security classification into `review_types.py`.
   - Preserve recognition of `focus-area=security`, explicit heading tags, and focus-area fields.
   - Preserve case-insensitive matching and the current treatment of fenced and inline-code examples.
   - Expose `is_security_block_text()` as the sole classifier.
   - Keep failure-sensitive callers responsible for validating that the classifier returned a boolean.

3. Add `count_non_security_blocks(text)`.
   - Segment through `parse_blocks()`.
   - Count FINDING and OOS blocks that are not security-tagged.
   - Return zero for empty text and text without canonical blocks.

4. Move `_finding_dedup_key` unchanged into `review_types.py` as `finding_dedup_key`.
   - Preserve the existing Location and Concern extraction, normalization, and fallback behavior.
   - Replace private imports and local copies with the public helper.

5. Migrate each in-scope consumer.
   - Replace independent block segmentation and heading/ID extraction with `parse_blocks()` or the compatibility finding parser.
   - Replace copied security classifiers and non-security counters with the shared helpers.
   - Retain regexes for distinct grammars such as vote lines, generated output, field extraction, and deliberate malformed-heading diagnostics.
   - Where a consumer rewrites or validates a heading, parse the canonical heading through the owner and keep the consumer-specific policy local.

6. Extend `lint_shared_convention_regex.py`.
   - Detect literal regexes that parse canonical FINDING/OOS Markdown headings or segment their blocks.
   - Scan supported `re` calls and module-level pattern assignments, not only `re.compile`.
   - Allow only `larch/review/review_types.py` to own this grammar.
   - Keep the detector narrow enough to permit vote-line syntax, output strings, field regexes, and malformed-input diagnostics.
   - Preserve reason-bearing line suppressions for intentional exceptional matches.

## Edge cases

- Ignore `### FINDING_1:` and `### OOS_1:` examples inside fenced code blocks.
- Do not accept one, two, four, five, or six hash heading depths.
- Do not widen canonical IDs beyond uppercase `FINDING_<digits>` and `OOS_<digits>`.
- Preserve titles containing colons, brackets, or security labels.
- Preserve the distinction between stopping at the next item heading and stopping at any level-three heading.
- Treat empty, preamble-only, and malformed input as zero parsed blocks rather than a parser failure.
- Do not classify security tokens shown only inside code examples as real tags.
- Ensure a security-tagged FINDING and a security-tagged OOS receive the same result.
- Keep malformed-heading detection available to aggregator validation without making malformed input part of the canonical grammar.
- Avoid flagging regexes for vote rows, classification IDs, generated headings, field labels, or explicit malformed-input diagnostics in the lint.

## Failure modes

- A boundary change could absorb unrelated Markdown sections into a block or truncate valid fields.
- An overbroad lint detector could reject unrelated FINDING/OOS identifiers and output templates.
- An underbroad detector could leave another parser copy outside the owner.
- Security-classification drift could publish a security OOS item or incorrectly hold a public item.
- Replacing validation regexes indiscriminately could remove diagnostics for malformed reviewer output.
- Importing from higher-level issue or review modules could create cycles. Keep `review_types.py` leaf-like and free of consumer imports.
- Consumers may rely on whitespace or trailing-newline details. Preserve their current rendered output when adapting parsed block text.
