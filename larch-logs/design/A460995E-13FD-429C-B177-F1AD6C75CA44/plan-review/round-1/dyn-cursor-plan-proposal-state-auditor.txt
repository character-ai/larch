### 1. [correctness] Default-mode marker timing (`skills/learn-from-bugs/SKILL.md:108-142`)

The planned flow builds a reconciled proposals JSONL after the adoption section and new residuals are known, then passes it to `write-state`. The existing default-mode subsection still writes and commits the marker immediately after printing the report, with no `--proposals-file`. On the default path, checked statuses and new `proposed` entries would not persist, which breaks the core feature.

**Suggested revision:** Move the `write-state` / `git commit --only` fences to the end of Step 4, after reconciled JSONL exists, and require `--proposals-file` in both default and filing marker paths.

### 2. [correctness] Filed-issue `stateReason` granularity (`python/larch/issue/learn_from_bugs.py` — planned `check_proposals`)

The approach says a closed completed issue is `adopted` and closed not planned is `orphaned`, but it does not require `stateReason==COMPLETED` before adopting. Elsewhere the repo already treats `NOT_PLANNED` specially (`python/larch/issue/analyze_bugs.py:512-513`). A bare `CLOSED` issue with empty, `DUPLICATE`, or other reasons could be misclassified as adopted.

**Suggested revision:** Adopt only on `CLOSED` + `COMPLETED`; orphan on `NOT_PLANNED`; keep `pending` or fail closed for other closed reasons and missing `stateReason`.

### 3. [correctness] Filing-mode dedup mapping (`skills/learn-from-bugs/SKILL.md` — filing mode; `skills/issue/SKILL.md:334-346`)

The plan parses `ISSUE_N_NUMBER` but `/issue` dedup rows emit `ISSUE_i_DUPLICATE=true` and `ISSUE_i_DUPLICATE_OF_NUMBER` instead of a created number. Without explicit mapping, deduped batch items cannot attach `filed_issue`, which triggers the plan's own "do not advance on ambiguous mapping" rule and loses filing history.

**Suggested revision:** For each batch index `i`, accept `ISSUE_i_NUMBER` or, when `ISSUE_i_DUPLICATE=true`, bind `filed_issue` from `ISSUE_i_DUPLICATE_OF_NUMBER` for all proposals in that batch item.

### 4. [correctness] `ANALYSIS_ROOT` vs `$PWD` (`skills/learn-from-bugs/SKILL.md:36-67,121`)

`ANALYSIS_ROOT` drives prepare and the planned adoption checks, but `write-state` still uses `--root "$PWD"`. When the operator passes `--root PATH` for a foreign checkout, adoption evidence and marker persistence target different trees.

**Suggested revision:** Bind `--root "$ANALYSIS_ROOT"` for `check-proposals`, `write-state`, and marker commit/rollback fences.

### 5. [correctness] Hook target contract (`python/larch/issue/learn_from_bugs.py` — planned hook check; `hooks/hooks.json:1-34`)

`hooks/hooks.json` stores matcher plus command paths, not named hook IDs. The plan requires parsing the file and matching a "named hook entry" without defining what the proposal `target` field contains.

**Suggested revision:** Specify hook `target` as command script path or matcher string and match against parsed hook entries; cover with present/absent fixture trees.

### 6. [security] Root-confined target reads (`python/larch/issue/learn_from_bugs.py` — planned `check_proposals`)

The SKILL delta treats prior proposal content as untrusted, but the Python plan does not require repository targets to resolve under `root` before reads.

**Suggested revision:** Reject absolute paths and `..` escapes when resolving lint, invariant, guideline, test, and hook targets from marker JSON.
