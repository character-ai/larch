## Approach

Extend the existing durable marker and workflow without adding a second state store.

1. Model proposal records as validated, frozen domain objects.
2. Read schema v1 markers as schema v2 state with no proposals.
3. Write only schema v2 markers.
4. Check prior proposals after preparation and before clustering.
5. Render a deterministic adoption summary for the report.
6. Carry checked prior proposals into the next marker.
7. Add each residual proposal once. Reuse a pending record when its stable ID matches.
8. In filing mode, attach each created issue number before writing the marker.
9. Preserve the existing marker-only commit contract.

Use conservative status transitions:

- A matching repository artifact is `adopted`.
- An open filed issue or an unlanded target is `pending`.
- A filed issue closed as not planned is `orphaned`.
- A previously adopted repository target that later disappears is `orphaned`.
- A closed completed issue is `adopted`.
- A `fix` without a filed issue remains `pending`.
- A failed or malformed `gh` result stops the check. It must not manufacture a status.

## Edge cases

- A v1 marker has no proposal history and must not be rewritten until the normal successful marker boundary.
- Proposal IDs may match while other fields conflict. Stop rather than silently merging distinct proposals.
- Multiple proposals may map to one filed issue. Preserve separate proposal records with the same issue number.
- A proposal may remain pending for many runs. Keep its original `run_date` so age remains meaningful.
- Invalid or future schema versions remain unusable.
- Empty proposal history renders a useful adoption section without division by zero.
- Future dates produce age zero rather than a negative age.
- Repository targets may contain heading-like text inside fenced examples. Ignore those examples.
- A missing target does not prove removal unless prior state shows that target had been adopted.
- A filed issue result takes precedence over a coincidental local target match.
- Filing output that cannot map issue numbers back to proposal groups blocks marker advancement.

## Failure modes

- Fail before report generation when checked state cannot be trusted.
- Fail before marker mutation when proposal JSONL is malformed or inconsistent.
- Fail filing mode when `/issue` reports partial failure or lacks required issue-number records.
- Do not downgrade a GitHub read failure to pending.
- Do not overwrite the prior marker when adoption checking or report generation fails.
- Do not commit report files, checked-proposal scratch files, or filing scratch files with the marker.
- Preserve the existing accurate stop behavior when the marker-only commit fails.
