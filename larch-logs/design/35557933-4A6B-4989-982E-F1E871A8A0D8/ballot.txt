### FINDING_1: CI enforcement gap — `make lint` is not run in CI
- **Concern**: The plan claims that composing `lint-foreground` into `Makefile` `lint:` makes pre-commit / CI enforce the rule. CI's `lint` job actually runs `make lint-only` (pre-commit hooks only), not `make lint`, and PR harness coverage runs through sharded `make test-harnesses-N`. The new lint can pass locally while never gating PRs.
- **Suggested resolution**: Either register a `.pre-commit-config.yaml` local hook for `scripts/lint-foreground-markers.sh` (`always_run: true, pass_filenames: false`, matching the `lint-skill-invocations` shape) AND/OR append `test-lint-foreground-markers` to one `test-harnesses-N` shard. Revise plan prose that claims `lint:` composition alone is sufficient.
- **Reviewers**: Cursor-Arch, Cursor-Edge, Cursor-Innovation, Cursor-Pragmatic, Cursor-Requirements, Codex-Arch, Codex-Edge, Codex-Pragmatic, Codex-Requirements (9 of 10).

### FINDING_2: New harness not assigned to a `test-harnesses-N` shard
- **Concern**: `scripts/test-harness-shards-coverage.sh` enforces that every non-carved-out `test-*` recipe target appear in exactly one `test-harnesses-N:` prerequisite list and in `.PHONY`. The plan adds `test-lint-foreground-markers` but does not place it on a shard line, so `make test-harnesses` will fail until it lands somewhere.
- **Suggested resolution**: Append `test-lint-foreground-markers` to `.PHONY` and exactly one `test-harnesses-N:` line (mirror `test-lint-bash32` placement in `test-harnesses-16`).
- **Reviewers**: Cursor-Arch, Cursor-Edge, Cursor-Innovation, Cursor-Pragmatic, Cursor-Requirements, Codex-Arch, Codex-Edge, Codex-Pragmatic (8 of 10).

### FINDING_3: Leading-command detection misses command-substitution invocations
- **Concern**: Existing Family B call sites include assignment-wrapped command substitutions like `_plan_review_dispatch=$("${CLAUDE_PLUGIN_ROOT}/scripts/dispatch-with-waterfall.sh" ...)` in `skills/design/SKILL.md` and `_plan_voter_dispatch=$("${CLAUDE_PLUGIN_ROOT}/scripts/dispatch-plan-voters.sh" ...)` in `skills/design/references/plan-review.md`. A scanner that matches only the leading shell word will silently pass these as unmarked.
- **Suggested resolution**: Extend the fence parser to recognize denylisted basenames anywhere in executable shell syntax inside fences — assignments, command substitutions (`$(...)`, backticks), env prefixes (`VAR=value cmd`), quoted `${CLAUDE_PLUGIN_ROOT}` paths, `bash script.sh` wrappers, `if`/`while` tests. Add fixtures pinning each shape.
- **Reviewers**: Codex-Arch, Codex-Edge, Codex-Innovation, Codex-Pragmatic, Codex-Requirements (all 5 Codex archetypes).

### FINDING_5: Banner/comment window ambiguity (`±20` vs `above` vs `±5`)
- **Concern**: Plan prose alternates between "within 20 lines above the fence" (one-sided), "±20 lines above fence" (bidirectional ambiguity), and the inline comment window stated as both "immediately above" and "±5". Implementers and the linter author may diverge on semantics.
- **Suggested resolution**: Pin a single directional rule everywhere — banner canonical line must appear within the **20 markdown lines IMMEDIATELY BEFORE** the opening fence; inline comment must appear within the **5 source lines IMMEDIATELY BEFORE** the invocation line, INSIDE the fence. Make `scripts/lint-foreground-markers.md` byte-match the implemented algorithm.
- **Reviewers**: Cursor-Arch, Cursor-Edge, Cursor-Innovation, Cursor-Pragmatic, Cursor-Requirements (5 of 10).

### FINDING_9: Family A regression spot-check absent from testing strategy
- **Concern**: The hard constraint requires Family A invocations (e.g., `launch-review.sh`, `launch-codex-implement.sh`, `launch-cursor-implement.sh`) keep `run_in_background: true` and their collector pairing. The plan's testing strategy validates Family B markers but does not explicitly verify Family A blocks remain unchanged. A bulk marker-insertion pass could accidentally edit nearby Family A prose.
- **Suggested resolution**: Add a regression check (grep-based or fixture-based) verifying that known Family A launch fences still carry `run_in_background: true` after the audit. Either a harness fixture or a one-time pre-/post-audit grep diff.
- **Reviewers**: Cursor-Requirements (1 of 10).

### FINDING_10: Marker-only lint cannot catch contradictory `run_in_background: true` co-occurrence
- **Concern (latent)**: A future SKILL.md edit could add the canonical banner + inline comment near a Family B basename AND still use `run_in_background: true` in the Bash tool metadata (or `&` shell backgrounding in the fence). Markdown-only lint cannot inspect Bash tool metadata; the invariant could be violated while the lint stays green.
- **Suggested resolution**: Optional — extend the lint to additionally reject same-fence co-occurrence of a denylisted basename with `& ` or `nohup` patterns inside the fence. Bash tool metadata is out of scope (not in `.md` files). Add fixtures for the negative case.
- **Reviewers**: Codex-Edge (1 of 10, latent severity).

### FINDING_12: `review-and-fix.sh` prose invocation in `skills/review-and-fix/SKILL.md` remains uncovered
- **Concern**: The feature acceptance requires "every Family B invocation in `skills/**/SKILL.md`" be marked. If `skills/review-and-fix/SKILL.md` has only a prose "Run `review-and-fix.sh`" instruction (not a fenced bash block), the plan's "prose-only mentions are not flagged" rule (Decision 5/6) leaves it uncovered, contradicting acceptance #3.
- **Suggested resolution**: Either (a) convert the prose instruction to a fenced bash block and apply markers, or (b) explicitly revise the acceptance scope language to "every FENCED Family B invocation" (matches the discussion-round1.md decision that prose mentions are intentionally excluded). Pick one; document the choice in the plan.

### FINDING_14: Canonical banner not pinned as byte-identical literal
- **Concern**: The plan describes the canonical banner phrase but does not pin it as the byte-identical required literal that `lint-foreground-markers.sh` must regex-match. Without an exact-match requirement, lint can have false negatives (legacy bespoke ⚠ paragraphs whose first line is semantically equivalent but not byte-identical) or false positives (canonical phrase under-specified).
- **Suggested resolution**: Copy the exact banner line from issue #2641 binding decisions into both the plan and `scripts/lint-foreground-markers.md` verbatim; require the linter to match that literal byte-for-byte (or a documented normalization, e.g., strip leading `> ` blockquote prefix).
- **Reviewers**: Cursor-Requirements (1 of 10).

### FINDING_15: Multi-line invocation handling underspecified
- **Concern**: Wrapped invocations with `\` continuation lines (e.g., the existing `ship-pr.sh` Invoke block spanning ~20 lines) are not clearly addressed. Ambiguous whether the inline comment goes above the basename line or above the entire invocation block (the basename and its continuations).
- **Suggested resolution**: Spell in `scripts/lint-foreground-markers.md` that the comment must be on the LAST non-comment line BEFORE the line containing the basename token (anchor on the basename line, not the entire wrapped invocation). Add a fixture pinning multi-line invocation behavior.
- **Reviewers**: Cursor-Innovation (1 of 10).

### FINDING_16: Fence parser must be data-only (security latent)
- **Concern (latent, security focus)**: Markdown fence parser in `scripts/lint-foreground-markers.sh` must extract fence content as data only — any accidental `eval` or `source` of extracted fence bodies would execute skill examples (which include real script invocations) as shell.
- **Suggested resolution**: Specify and implement parse-only scanning using string operations or `awk` extraction; never `eval`, `source`, `bash -c`, or `sh -c` on fence content. Add a code comment to that effect and a harness fixture with a fence containing a deliberate "side-effecting" command that the parser must NOT execute.
- **Reviewers**: Cursor-Arch (1 of 10, security focus, latent severity).
