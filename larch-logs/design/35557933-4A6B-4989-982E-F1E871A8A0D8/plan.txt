# Plan — Fixes #2641: Foreground-by-default for blocking script calls

## Approach

Treat this as a **documentation + lint** change, not an orchestration refactor. The skill prose already contains scattered "Do NOT set `run_in_background: true`" warnings at specific sites; this work establishes the single normative rule, makes the per-site markers uniform, adds a CI-enforced lint, and revises a small set of canonical operator-facing docs so future drift fails fast.

Execution sequence:
1. Establish the rule (BASH_AUTHORING.md §4 + AGENTS.md cross-reference + `docs/linting.md` row + `.pre-commit-config.yaml` header reconciliation).
2. Build the linter (`scripts/lint-foreground-markers.sh` + sibling `.md` + harness + harness sibling `.md` + Makefile target + `test-harnesses-N` shard wiring + `agent-lint.toml` exclusion + pre-commit local hook entry).
3. Run the linter against the current tree, capture the full list of failing sites (the lint output IS the authoritative checklist), and apply canonical markers at each. Existing bespoke ⚠ banners are preserved; the canonical leader is added as the first paragraph line (Decision 1, leading-line match).
4. Verify `make lint`, `make test-harnesses-${shard}` for the chosen shard, `make lint-only` (pre-commit hooks), and Family A regression spot-check all pass.

## Canonical marker literals (pinned byte-for-byte; FINDING_14)

**Banner** (must appear as the leading prose line of a paragraph within the 20 markdown lines IMMEDIATELY BEFORE the opening fence; strip `> ` blockquote prefix before match):

```
**⚠ Foreground required — do NOT set `run_in_background: true`.**
```

**Inline comment** (must appear on at least one of the 5 source lines IMMEDIATELY BEFORE the line containing the denylisted basename token, INSIDE the same fence):

```
# Foreground required: see BASH_AUTHORING.md §4
```

Linter regex matches the banner phrase verbatim after stripping a leading `> ` (one-level blockquote prefix); no other normalization. Matches the comment via a Bash 3.2-compatible substring scan that requires the literal `# Foreground required: see BASH_AUTHORING.md §4` on a comment line (`^#` after leading whitespace) preceding the basename anchor.

## Detection algorithm (FINDING_3, FINDING_5, FINDING_15)

For each `.md` file in scope:

1. Walk markdown line-by-line. Track fenced shell blocks: enter on a line matching `^```\s*(bash|sh|shell)\s*$`; exit on a closing `^```\s*$`. Track nesting depth = 0 (no nested fences in markdown; the closing fence at depth 0 ends the block).
2. Within each fenced block, identify **invocation anchor lines** — non-comment lines (`^\s*[^#\s]`) whose textual content contains any denylisted basename token via the following match positions (matched as **whole-path tokens**: the basename appears either as the leading shell word, after a path prefix `${CLAUDE_PLUGIN_ROOT}/scripts/`, `${CLAUDE_PLUGIN_ROOT}/skills/*/scripts/`, a quoted variant, or inside a `$(...)` / `\`...\`` command substitution):
   - Leading shell word: `^\s*(bash\s+)?(["']?)(\S*\/)?BASENAME\b`
   - Assignment-wrapped command substitution: `=\$\(["']?(\S*\/)?BASENAME\b`
   - Env-prefixed invocation: `^\s*(\w+=\S+\s+)+(bash\s+)?(["']?)(\S*\/)?BASENAME\b`
   - `if`/`while` test: `\b(if|while|until|elif)\s+(["']?)(\S*\/)?BASENAME\b`
   - Quoted path expansion: `"\$\{?CLAUDE_PLUGIN_ROOT\}?/\S*\/BASENAME\b`
   The match operates on the full **line text** (not byte position), so a wrapped invocation with `\` continuations matches on the line that physically contains the basename token; continuation lines without the token are not anchors.
3. For each invocation anchor line, assert BOTH:
   - **Banner**: the canonical banner phrase appears on at least one of the 20 markdown lines IMMEDIATELY BEFORE the opening fence (one-sided, before-only; `> ` blockquote prefix stripped before match).
   - **Comment**: the canonical inline comment appears on at least one of the 5 source lines IMMEDIATELY BEFORE the anchor line (one-sided, before-only; inside the same fence; comment lines `^\s*#` only).
4. On any failure, emit `FILE:ANCHOR_LINE: missing <banner|comment> for <BASENAME>` to stdout and increment a violation counter. Exit non-zero (1) when violations > 0; exit 0 when no violations.

**Parse-only safety (FINDING_16)**: extraction is string-based (`awk` / `while IFS= read -r`); the linter NEVER `eval`s, `source`s, `bash -c`s, or otherwise executes fence content. The script has an explicit code comment near the fence-parse loop stating this invariant. A harness fixture contains a fence with a deliberate side-effecting command (e.g., `: > /tmp/foreground-marker-poison.$$`) and asserts the file does not exist after the lint run.

## Edge cases

- **Bespoke long banners (e.g., `ship-pr.sh`, Step 5)**: leading-line match per Decision 1. The canonical phrase is prepended as the first paragraph line of the existing ⚠ blockquote; the bespoke state-machine context / `--resume-phase` recovery prose stays intact below. The linter strips `> ` blockquote prefixes during banner match; the lint regex matches the canonical phrase byte-for-byte after that strip.
- **Multi-Family-B fence**: one banner above the fence covers the entire fence; one inline comment per Family B anchor line inside the fence. The harness pins this (fixture 4).
- **Prose-only basename mentions**: not flagged. Lint scans ```bash / ```sh / ```shell fences only.
- **Commented-out invocations** (`# foo.sh ...` inside a fence): not flagged — the anchor-line scanner requires `^\s*[^#\s]`.
- **Family A allowlist**: not enforced by this lint (per "Out of scope"). Family A basenames simply aren't on the denylist, so they pass implicitly.
- **`heavy-worker.md`** foreground-collector paragraph that mentions `run_in_background: true` in prose (no fence): not flagged.
- **`review-and-fix.sh` prose-only invocation**: not flagged (FINDING_12 resolution: acceptance is "every FENCED Family B invocation").
- **Bash 3.2 portability**: linter uses newline-delimited temp files, `while IFS= read -r ...`, avoids associative arrays / namerefs / `mapfile`. `make lint-bash32` covers this.

## Failure modes

1. **Lint surface drift from a renamed or split blocking script**: if a future PR renames `ship-pr.sh` or splits `review-and-fix.sh` into two scripts, the denylist in `scripts/lint-foreground-markers.sh` falls behind. Earliest signal: a future incident where backgrounding the renamed/split script suppresses breadcrumbs and `make lint-foreground` stays green. Mitigation: the linter's denylist is the single source of truth and is referenced from `scripts/lint-foreground-markers.md`; any blocking-script rename PR must update both. Add a one-time grep at landing time: walk `scripts/*.sh` and `skills/*/scripts/*.sh`, flag any blocking-pattern script (CI/merge state machine, collector, dispatcher, wait loop) not on the denylist.

2. **Linter false-positives on an unusual fence shape**: a Family B invocation inside a `bash` heredoc inside a `bash` fence, or a fence labelled `console` / language-tag-less, may misclassify. Earliest signal: a `make lint-foreground` failure pointing at a site that looks unfixable by adding markers. Mitigation: the harness covers heredoc / indented / unusual-language-tag fences (fixtures 7, 8). If the audit surfaces a site the linter can't reason about cleanly, prefer false negatives (relax the detector) over forcing contorted marker placement; document the carve-out in `scripts/lint-foreground-markers.md`.

3. **Marker insertion accidentally drifts existing semantic prose, breaking other lints**: even though banner + comment are inert, editing many SKILL.md files raises the risk of accidentally re-flowing surrounding paragraphs and breaking `agent-lint` / `markdownlint` / existing structure tests. Earliest signal: `make lint` fails on an existing structure test after a marker-insertion batch. Mitigation: insert markers via `Edit` (precise old/new strings) rather than `Write` (full-file replacement); run `make lint` after each batch of marker insertions; never touch the same line as a load-bearing structure-test anchor (FINDING_4 fix: don't rely on the stale `(28g)` example — use the harness's real `grep -Fq` contract strings as the actual structure-test anchors when validating).

- **Regression**: `make lint` must remain green. `lint-bash32` covers shell portability of the new lint script. `agent-lint` / `markdownlint` / existing `test-design-structure.sh` / `test-implement-structure.sh` must remain green after marker insertion.
- **CI enforcement (FINDING_1)**: the new `.pre-commit-config.yaml` `local` hook for `lint-foreground-markers.sh` (with `always_run: true, pass_filenames: false`) is what gates PRs through the existing CI `lint` job (which runs `make lint-only`). The `test-harnesses-N` shard wiring is what gates PRs through the existing CI harness matrix job. Both paths catch drift; pre-commit catches the lint contract immediately, harness catches lint-script regressions on every PR.
- **End-to-end**: after marker insertion, run `make lint-foreground` against the modified tree and confirm exit 0. Then introduce a deliberate violation (delete a banner) in a throwaway fixture-style commit, confirm exit 1 with a clear `FILE:LINE: missing banner for BASENAME` message, then revert.
