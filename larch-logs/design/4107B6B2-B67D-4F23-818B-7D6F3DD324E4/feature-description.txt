# [BUG] ship-pr classifies merge-conflict-at-merge-time as review-required, blocking auto-recovery

## Symptoms

During a `/implement --merge` run (run ID: `5E9A232E-F58E-482B-A680-F65B461A08EC`, PR #4247), the ship PR state machine:

1. Created PR #4247
2. `ship.py` detected a stale branch and did an internal rebase (`ship.py: rebase: Flush+Push`)
3. CI ran and passed after the rebase (~2.5 minutes, 13 polls)
4. `ship.py: merge` was attempted
5. GitHub API returned: `"PR requires approving review; admin merge failed: GraphQL: Pull Request has merge conflicts (mergePullRequest); fallback merge failed: X Pull request character-ai/larch#4247 is not mergeable: the merge commit cannot be cleanly created."`
6. ship.py classified this as `needs_user_reason=review-required` and returned **exit 3 (NEEDS_USER_INPUT)**

Operator had to manually rebase, resolve conflicts, and re-invoke ship.py to complete the merge.

## Root cause

The merge failure had **two components** in the GitHub API error message:

1. "PR requires approving review" — review gate
2. "Pull Request has merge conflicts" / "not mergeable" — actual merge blocker

These are a **race condition**: between ship.py's rebase-push and the merge attempt (~2.5 min of CI runtime), new commits landed on `origin/main` that conflicted with the branch. Specifically:

- Our branch had a Codex CI-fix commit removing unused shell variables from `test-stall-recovery-report-2.sh` and `test-stall-recovery-report-3.sh`
- Main received `perf(test): split test-stall-recovery-report.sh (168s) into 3 parallel shards` (#4242) which reorganised those same files

The bug: ship.py's merge error parser hit the `"requires approving review"` phrase first and classified the whole error as `review-required`, without checking for the "merge conflicts" / "not mergeable" substring. Had it detected the latter signal, it could have retried with a rebase instead of surfacing as a user-input stall.

## Suggested fix

In `python/ship.py` (or `scripts/merge-pr.sh`), when a merge attempt fails:

1. Check for "merge conflicts" or "not mergeable" in the error detail **independently** of whether "requires approving review" also appears.
2. If a merge-conflict signal is detected and `REBASE_COUNT` is within budget, attempt a rebase+push+CI+retry cycle before returning `review-required`.
3. Only surface as `review-required` when the branch is confirmed up-to-date with main (post-rebase) and the failure is purely a review gate.

Alternative: `merge-pr.sh`'s fallback merge path could probe for "not mergeable" vs "requires review" and emit a distinct `BAIL_REASON` (e.g. `merge-conflict-race`) that the ship driver maps to a rebase retry rather than a user-stall.

## Context

- **Run ID**: `5E9A232E-F58E-482B-A680-F65B461A08EC`
- **PR**: #4247
- **Conflicting files**: `skills/implement/scripts/test-stall-recovery-report-2.sh`, `skills/implement/scripts/test-stall-recovery-report-3.sh`
