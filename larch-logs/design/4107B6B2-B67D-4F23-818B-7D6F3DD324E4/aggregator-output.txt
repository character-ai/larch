### FINDING_1: MAIN_ADVANCED may loop merge without rebase when BEHIND persists
- **Reviewer(s)**: Cursor-Innovation
- **Severity**: important
- **Concern**: Remapping merge-time conflict errors to `MERGE_RESULT_MAIN_ADVANCED` in `merge.py` may not trigger a rebase in `ship.py`. After that remap, `ship.py` increments iteration and continues to `ci-initial` rather than entering the rebase path. `ci_monitor.decide()` can return `merge` when CI is pass, `behind_count > 0`, and `conflicted=False` (see `python/ci_monitor.py:148-150`). In the reported race, admin-eligible PRs can stay `BEHIND` during merge while GitHub may not flip to `DIRTY` before the next poll, so ship re-enters merge without rebasing and may repeat the same failure until `SHIP_MERGE_LOOP_MAX_ITERATIONS`. Bash `ship-pr.sh` already special-cases admin failures with "Base branch was modified" via `run_rebase_rebump` (`scripts/ship-pr.sh:2992-2994`); Python has no equivalent for conflict diagnostics.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Innovation: Extend the plan with a minimal ship.py branch: when merge_pr returns MAIN_ADVANCED and outcome.error matches the conflict tuple, route to the existing rebase path (or set goto_rebase) before the ci-initial continue. Alternatively document and test that GitHub always transitions to DIRTY post-failure; if not guaranteed, merge.py-only remap is incomplete for auto-recovery.
