**1. [correctness] `RESUME_PHASE` / `CALLER_KIND` cleared on every merge write** (`python/ship.py:223-224`)

The plan’s merge preserves orchestrator-only keys, but the overlay set is still today’s `fields` map, which hard-codes `RESUME_PHASE=""` and `CALLER_KIND=""`. Any `--state-file` refresh after the orchestrator seeds handoff tokens will wipe them. That breaks Python-path `ship_pr_pre_push` / conflict flows that depend on those keys surviving between selector re-invokes (plan FINDING_10 assumes classification evidence in merged `ship-pr-state.sh`).

**2. [correctness] NEEDS_USER_INPUT / TRANSIENT exclusion not wired to `_write_terminal_state` call sites** (`python/ship.py:175-181`, `307-308`, `380-385`)

FINDING_3 correctly narrows terminal finalize writes, but the proposed helper `_write_terminal_state` still runs for all non-OK outcomes (`checks_result.outcome is not Outcome.OK`, `monitor.result.outcome is not Outcome.OK`). CI-monitor and checks already emit `Outcome.NEEDS_USER_INPUT` (e.g. `first-fixer-non-health`). That writes `finalize-state.sh` today and would contradict FINDING_6 / edge-case “no finalize on mid-loop exit 3”, causing Step 18 to skip `restore-finalize-state.sh` when finalize exists but is not terminal.

**3. [correctness] Flush-skip stall refresh vs unconditional `PHASE=done` ship write** (`python/ship.py:266-271`, `468-476`)

FINDING_5 adds stall-shaped finalize after flush skip inside `run_postmerge_phase`, but `run_ship` always calls `_write_ship_state(working, phase="done")` before returning `post.outcome` even when `post` is `Outcome.STALLED`. That can leave `ship-pr-state.sh` without stall overrides while `finalize-state.sh` was just refreshed—undermining the Step 18 gate that only re-runs restore on `STALL_TRACKING` / `BAIL_NEEDS_USER_INPUT` / `STALL_STEP` divergence in **ship-pr-state**.
