A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature

## Summary

Two compounding defects cause `checks-child-failed EXIT_CODE=-15` (SIGTERM from the checks wrapper timing out) to exit the run as a terminal unrecoverable failure instead of a retryable transient event. First, the stall recovery Step 18a procedure does not pass `--in-memory-stall-tracking` to `stall-recovery classify`, so `any_stall=False` and the classifier returns `no-stall` without even inspecting the bail reason. Second, `_classify_text` has a blanket early-return for `step in {"3", "6"}` that classifies every step-3 stall as `contract-failure / step-contract` regardless of whether the bail reason signals a timeout (SIGTERM), making the run terminal even when the checks genuinely pass standalone.

## Original report

stall-recovery classify returns FAILURE_CLASS=unrecoverable for checks-child-failed EXIT_CODE=-15 (SIGTERM) instead of transient-infra, preventing automatic retry when the test runner is killed by timeout

## Reproduction scenario

1. Run `/implement` on a large PR where the test suite takes &gt;450 seconds (e.g. a 4-module split touching 4,000+ tests).
2. The `checks-commit-route --checks-site step3` subprocess is killed by SIGTERM before the test runner finishes.
3. `checks-repair-loop` sees no `REDACTED_LOG_FILE` → routes to stall with `STALL_TRACKING=true` in memory.
4. Step 18a orchestrator calls `stall-recovery classify --stall-step 3 --phase checks --bail-reason checks-child-failed --exit-code -15` — without `--in-memory-stall-tracking true`.
5. Result: `MATCHED_CLASSIFIER_PATTERN=no-stall FAILURE_CLASS=unrecoverable RESUME_HINT=none` → terminal.
6. Even if `--in-memory-stall-tracking true` is passed, `_classify_text` returns `("contract-failure", "none", "step-contract")` at line 125-126 for any step-3 stall.

Standalone `python/cli.py checks run-relevant --site step3` in the same tree: `RELEVANT_CHECKS_OK=true SITE=step3 COVERAGE=full`. The checks pass; only the wrapper timed out.

## Expected behavior

`checks-child-failed` with a negative exit code (SIGTERM) at step 3 should be classified as `transient-infra` with a retryable resume hint (e.g. `step3-checks`), so the stall recovery procedure retries the checks rather than terminating the run.

At minimum, the `no-stall` path should not fire when `STALL_TRACKING=true` was set in memory; the stall-recovery Step 18a procedure should pass `--in-memory-stall-tracking "${STALL_TRACKING:-false}"`.

## Observed behavior

- Bug 1 (immediate): `stall-recovery classify` receives no `--in-memory-stall-tracking` flag. `any_stall=False`. Returns `MATCHED_CLASSIFIER_PATTERN=no-stall FAILURE_CLASS=unrecoverable` without evaluating bail reason.
- Bug 2 (structural): Even with `--in-memory-stall-tracking true`, `_classify_text` line 125-126 returns `("contract-failure", "none", "step-contract")` for any step 3 bail, including SIGTERM timeouts.
- Combined: run terminates as a filed stall issue rather than retrying.

## Root cause analysis

**Bug 1 — missing `--in-memory-stall-tracking` argument** (stall-recovery.md / orchestrator):

The stall-recovery.md Step 3 directive says "Classify. Pass any validated BAIL_FAILURE_DETAIL_LOG." It does not instruct the orchestrator to pass `--in-memory-stall-tracking`. But `any_stall` at `_classify.py:211` requires at least one truthy source. When STALL_TRACKING=true is only in-memory (not yet written to disk state files), all disk sources read `false`, so `any_stall=False` → line 218 returns `no-stall` unconditionally.

**Bug 2 — blanket step-3 contract-failure** (`python/larch/state/_classify.py:125-126`):

```python
if step in {"3", "6"}:
    return "contract-failure", "none", "step-contract"
```

This fires before any bail-reason inspection. `checks-child-failed EXIT_CODE=-15` (SIGTERM) is a transient infrastructure event, not a step-contract violation. A step-contract violation means the orchestrator or wrapper misbehaved; a SIGTERM means the operating system killed the process due to timeout. They warrant different treatment.

Additionally, `_resume_hint_for` at line 100-101 returns `"none"` for `safe_step in {"3", "6"}` even for classes like `transient-infra`, meaning there is currently no retry path for step-3 transient failures at all.
