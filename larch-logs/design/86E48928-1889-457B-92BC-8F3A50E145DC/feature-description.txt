# Cross-round findings ledger to suppress duplicate review suggestions (reviewers + judges)

**Build a per-invocation findings ledger so reviewers and judges stop re-processing duplicate suggestions across review rounds.**

## Problem

In `/design` plan review, `/implement` Step 5 code review, and `/review` diff mode, the review loop runs up to 5 rounds. Reviewers and judges carry no memory of prior rounds:

- **Reviewers re-review the diff fresh each round.** The prompt renderers (`render_specialist`, `render_reviewer` in `python/rendering.py`) inject the diff and a rubric, never prior-round findings.
- **Judges vote on the current ballot only.** The voter archetypes are static text; the ballot is the current round's findings, neutralized to `anonymous`.
- **Dedup is within-round only.** `python/review_aggregate.py` merges one round's findings; nothing compares across rounds.

Result: the same suggestion gets raised, adjudicated, then raised again round after round. That wastes reviewer dispatch, voting, and fix-loop tokens, which is the costliest part of the pipeline.

The raw data already exists. `findings-classification.tsv` (per round) records every finding with outcome (accepted / neutral / rejected / OOS), scope, and vote cells. `write_rejected_findings_aggregate` in `python/review_and_fix.py` already collects rejected findings across `round-*/` dirs. It is just never read back into prompts or compared across rounds.

## Goal

Maintain a per-invocation **findings ledger** of every suggestion made in prior rounds, tabulated as accepted / neutral / rejected / OOS, and use it to stop duplicates from being re-processed:

- Reviewers read the ledger and skip duplicates before submitting.
- Judges read the ledger and short-circuit duplicates to NO.
- Near-exact rejected duplicates are auto-suppressed before the ballot, so they cost no voting tokens.

## Design

Two layers. v1 is cheap and reversible. v2 adds the bigger token win.

### v1: deterministic ledger + prompt injection

**Build the ledger deterministically. No separate agent.** The ledger is a projection of `findings-classification.tsv`, which the tally step already writes. Append each round's classified findings to a running ledger file at end of round, inside the existing tally path (`review tally-code-votes` / `review emit-tally`). No LLM, no parallel "ledger-updater," no extra orchestration barrier. A deterministic file append costs ~0 tokens and has no latency to hide, so running it parallel to the fixer buys nothing.

- **Location**: one `findings-ledger.tsv` in the review tmpdir (`$REVIEW_TMPDIR` / `$IMPLEMENT_TMPDIR`), appended at end of each round. Persists across rounds within one skill invocation, which is exactly the scope of the duplicate problem.
- **Columns**: round, finding id, title, file:line, outcome (accepted / neutral / rejected / oos), vote tally, one-line reason.
- **Anonymized**: entries shown to voters carry no proposer labels, consistent with the neutralized ballot. Proposer attribution stays out of band in `proposer-map.tsv`.

**Inject the ledger path into reviewer and voter prompts** (`render_specialist`, `render_reviewer`, `render_voter`), with the bucket-specific rules below. Reviewers and judges read the file directly.

### v2: auto-suppress near-exact rejected duplicates at aggregation

In `review aggregate-findings` (`python/review_aggregate.py`), after merging the current round's findings, compare them against the ledger with the existing embedding/dedup machinery. Drop a new finding before it reaches the ballot only when both hold:

- it is a near-exact match (high similarity plus same file:line) to a prior **rejected** entry, AND
- the cited location was not changed by fixes in the intervening rounds.

If the area changed, let it through; the rejection may no longer hold. This keeps v2 conservative: it removes only repeats that are provably the same and provably un-rebutted. Everything borderline still reaches the ballot.

## Duplicate-handling policy

- **Rejected duplicates**: suppress, absent materially new evidence. This is the core win. v2 auto-suppresses the near-exact, unchanged-location subset before voting.
- **Accepted duplicates**: do NOT suppress. Accepted means a fix was applied; a re-raise usually means the fix was incomplete, which is signal worth keeping. Annotate instead: "previously fixed in round N; if still present, the fix may be incomplete."
- **Neutral duplicates** (≥1 YES but below threshold): treat like rejected (suppress absent new evidence). Keep this behind a single policy knob so neutrals can be re-surfaced if that turns out to matter.
- **OOS duplicates**: suppress re-raising as new OOS. Already tracked.

## Where it plugs in

Build at the shared `review core` / tally / aggregation layer so all three consumers inherit it:

- `/design` plan review rounds
- `/implement` Step 5 code review rounds
- `/review` diff-mode rounds

Surfaces:

- **Ledger write**: tally path (`review tally-code-votes` / `review emit-tally`), reading `findings-classification.tsv`.
- **Reviewer injection**: `render_specialist` / `render_reviewer` in `python/rendering.py`.
- **Judge injection**: `render_voter` in `python/rendering.py`.
- **v2 suppression**: `review aggregate-findings` / `python/review_aggregate.py`.

## Validation

- Unit tests for the ledger writer (append, anonymization, outcome mapping) and the v2 gate (suppresses near-exact rejected, preserves accepted re-raise, respects the changed-location guard).
- Measure round-over-round dup-rate reduction from committed run-logs. `/fluff-analysis` already analyzes which suggestions get rejected / deferred / accepted and is the natural home for a repeat-rate metric.

## Open questions for /design

- Similarity threshold and the "location changed since rejection" computation for v2.
- Whether to also emit a human-readable markdown ledger (for run-logs / PR body) alongside the TSV.
- Cross-invocation persistence: currently none. The duplicate problem is within-invocation, so this is likely unnecessary.
