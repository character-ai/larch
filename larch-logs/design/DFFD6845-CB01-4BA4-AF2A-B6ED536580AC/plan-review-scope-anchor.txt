Delegate /design plan drafting to a strong model; Fable voter; fix model pins

## Summary

Preliminary plan proposal — **decisions baked in during a refinement discussion**. The formal design (running `/design` to produce the vetted `larch:plan`) is intentionally deferred to a **separate session** so the design tier/model can be chosen deliberately. This issue records the agreed direction so a later `/design <this-issue>` starts from settled scope.

**Goal:** get strong-model quality on the two quality-sensitive parts of `/design` — plan drafting and the always-on Claude voter — **without** paying to run the whole orchestrator on a strong model. Today, cost pressure forces running `/design` under a cheap session model (e.g. Sonnet), which degrades the drafted plan.

## Decisions locked in

- **Scope of drafting delegation: DRAFT ONLY.** Only the Step 2b plan draft moves to a strong model. Review (Step 3), Gate B revision-application, Gate C, and the `larch:plan` write all stay on the orchestrator exactly as today.
- **Drafter model: configurable, default `claude-fable-5`** via env var `LARCH_DESIGN_PLAN_MODEL` (also accepts an Opus id).
- **Voter model: configurable, default `claude-fable-5`** via env var `LARCH_VOTER_MODEL`.
- **Fallback-reviewer model: `claude-sonnet-4-6`** (cheap) — NOT Opus, NOT Fable. Rationale: the fallback reviewers (used only when both externals are down) are numerous, so the backup must stay cheap.
- **Presentation: summary + full.** The orchestrator DOES read and present the draft (the earlier "main agent never reads it" idea was retracted). When the plan is large it shows a summary; when small, the full plan; full plan always available on demand.

## Component 1 — Delegate Step 2b plan drafting to a configurable strong model

- At `/design` Step 2b, instead of the orchestrator drafting the plan inline, spawn a headless Claude sub-process pinned to a configurable model (default `claude-fable-5`) via the existing `scripts/launch-claude-subprocess.sh` (the same launcher used for voters and the dynamic-archetype scout, and which already supports `--model`).
- The sub-process does the codebase research **in its own context** — so the dozens of file reads never touch the orchestrator's context (the real context win) — and writes two files:
  - `plan.txt` (full — the canonical artifact reviewers and gates consume),
  - `plan-summary.md` (summary for display).
  It returns only a short status string (line counts), **not** the plan body, so the proposal does not bloat the orchestrator on return.
- The orchestrator reads/presents the **summary when the plan is large, full when small**, reusing the existing large-plan summary-mode threshold already present at the Step 2b print, the Step 3 pre-vote preview, and Gate C.
- Config knob `LARCH_DESIGN_PLAN_MODEL` (default `claude-fable-5`; accepts an Opus id). **Automatic fallback** to today's inline orchestrator drafting if the sub-process spawn fails, times out, or returns empty — keep `/design` robust.
- The drafting prompt must carry the existing Step 2b contract so the plan still parses downstream: per-file `### NEW:` / `### UPDATED:` / `### REWRITTEN:` headings, the trailing `diff_lines:` line (plus optional `diff_added` / `diff_deleted` / `mechanical_churn`), `skills/design/references/readability-style.md`, and the SIMPLE/HARD tier emphasis.
- Inputs to pass to the sub-process: `feature-description.txt`, `approach-synthesis.txt`, `discussion-round1.md`, `design-outline.md` (when approved), `brainstorm.md`, `dialectic-resolutions.md`.

## Component 2 — Always-on Claude voter → Fable (both /design and /implement)

- The voting-panel **Voter 1** (Claude, always launched — the floor) currently runs `claude-sonnet-4-6` by default, because neither `scripts/dispatch-plan-voters.sh` (`/design` plan review) nor `scripts/dispatch-code-voters.sh` (`/implement` Step 5 / `/review` code review) passes a model arg, so `launch-claude-review.sh` → `launch-claude-subprocess.sh` falls through to the launcher's `claude-sonnet-4-6` default.
- Change the always-on Claude voter to Fable via a **role-based default in `scripts/launch-claude-review.sh`**: when `--role voter` and no `--model` is supplied, use `LARCH_VOTER_MODEL` defaulting to `claude-fable-5`. Both voter dispatchers already pass `--role voter`, so this is a **single change point** covering `/design` and `/implement`.

## Component 3 — Fix model-pin discrepancies found during refinement

- **(3a)** `skills/shared/voting-protocol.md` (Voter Panel Composition) documents the code voter as "Claude opus — via `launch-claude-subprocess.sh --model claude-opus-4-7`", which never matched the code (the actual default was `claude-sonnet-4-6`) and names a stale Opus generation. Update the prose to reflect the new reality (the always-on Claude voter is Fable, `claude-fable-5` by default), keeping it model-name-agnostic where existing guidance already warns against hardcoding model names in voter columns.
- **(3b)** The `/design` fallback-reviewer Claude slots in `skills/design/scripts/dispatch-plan-review-panel.sh` and `skills/design/scripts/decompose-panel-dispatch.sh` pin `--model claude-opus-4-7` (a stale Opus generation). Change these to `claude-sonnet-4-6` — these are the both-externals-down fallback reviewers and there are many reviewer slots, so the backup reviewer must stay cheap (Sonnet, not Opus or Fable). This also aligns `/design`'s fallback reviewer model with `/implement`'s, which already defaults to `sonnet-4-6`.

## Proposed Design Outline

### Goals
- Delegate Step 2b plan drafting to a strong-model subprocess (default `claude-fable-5`) via a new write-capable launcher, keeping orchestrator context free of codebase research reads.
- Route always-on Claude voter model through `LARCH_VOTER_MODEL` (default `claude-fable-5`) in `launch-claude-review.sh`, covering both `/design` and `/review`.
- Fix two stale `--model claude-opus-4-7` fallback-reviewer pins and update `voting-protocol.md` prose to match.

### Non-goals
- No changes to external reviewer panels (Cursor/Codex remain primary reviewers).
- No upgrade of fallback reviewer slots beyond the required `claude-sonnet-4-6` fix.
- No changes to `/implement` orchestration, code-review flow, or skill dispatch logic beyond voter model default.

### Approach sketch
- Create `scripts/launch-claude-drafter.sh` (new): write-capable subprocess launcher using `--allowedTools "Read,Write,Edit"` and `--add-dir` for session dir and repo root; handles `.done` sentinel, token accounting, timing, same patterns as `launch-claude-subprocess.sh`.
- Update `skills/design/SKILL.md` Step 2b: add pre-draft block that generates prompt, launches drafter, waits for `.done`, checks `plan.txt`, presents summary/full via existing threshold logic; falls back to inline drafting on failure.
- Update `scripts/launch-claude-review.sh`: after arg parsing, when `ROLE=voter` and `MODEL=""`, set `MODEL="${LARCH_VOTER_MODEL:-claude-fable-5}"`.
- Update `skills/design/scripts/dispatch-plan-review-panel.sh` and `decompose-panel-dispatch.sh`: one-line model change each (`claude-opus-4-7` → `claude-sonnet-4-6`).
- Update `skills/shared/voting-protocol.md` Voter 1 code-review line to reflect Fable via `LARCH_VOTER_MODEL`.
- Add `LARCH_DESIGN_PLAN_MODEL` and `LARCH_VOTER_MODEL` docs to `docs/configuration-and-permissions.md`.
