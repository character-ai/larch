## Umbrella

Two `/design` Step 3 plan-review reviewer-slot handling bugs centered on `python/agents.py`, combined because they touch the same file, the same plan-review reviewer panel, and the same launcher test harnesses (`python/test_launch_review.py` / `python/test_agents.py`).

- **#4886** — a clean no-issues reviewer is misclassified `NOT_SUBSTANTIVE` and dropped when narration precedes the `{"no_issues_found": true}` sentinel, because both salvage layers require a *leading* sentinel. Primary fix site is the tool-agnostic `python/research_eval.py::validate_structured_reviewer_output`; the Cursor-only `python/agents.py::_review_cursor_normalize_no_issues` needs parallel hardening. (This issue already absorbed duplicate #4885; #4885's extra live-run evidence lives in #4886's comments.)
- **#4888** — `agent launch-review` hardcodes the reviewer-failure site string to the literal `"review Step 2"` for every launch failure, so `/design` Step 3 launch failures are mislabeled and disagree with the collector path's `design Step 3` label for the same panel.

Shared surfaces: `python/agents.py` (`_review_cursor_normalize_no_issues` and the launch-review failure logger), `python/research_eval.py`, `python/collect_results.py`, `python/test_launch_review.py` / `python/test_agents.py`. Both source issues' full content is preserved verbatim below.

## Source: #4886 — [BUG] Plan-review validator marks a clean no-issues reviewer NOT_SUBSTANTIVE when…

_Originally filed as #4886; preserved verbatim below._

## Summary

The plan-review / review collector marks a reviewer slot `NOT_SUBSTANTIVE` (dropped, logged as a failure) when the reviewer correctly finds no issues but emits the `{"no_issues_found": true}` sentinel **after** narration prose instead of as the first line. Both salvage layers only recognize the sentinel when it **leads** the output, so a recoverable trailing sentinel is treated as a failed slot rather than a clean no-findings pass. Observed in a live `/design` plan-review run (issue #4775, round 4). It was harmless that run, but it can misclassify a genuinely-clean sole-reviewer round as `degraded-empty-collector`.

**Relationship to #4790 / #4789 (related but distinct; still reproducing).** Those issues fixed the primary `\x1f`-vs-`KEY=VALUE` collector-parse bug. Their comments separately flagged `STATUS=NOT_SUBSTANTIVE` with `FAILURE_REASON="structured records not found after repair"` on the same `cursor-requirements` slot as a *secondary* defect that "deserves a parity audit / hardening." #4790's merged fix targeted the `\x1f` parser, not this salvage scope, and #4790 is now CLOSED. This exact failure still reproduces on v51.1.10 (run A6E6687D, 2026-06-20, after #4790 closed 2026-06-19). Failure modes differ: #4790's secondary cases were findings-bearing `JSON_PARSE_FAIL` (real findings dropped); this issue is the **no-issues clean pass** mislabeled as a failure. This issue pinpoints one precise root cause of that flagged-but-deferred work: the no-issues-sentinel salvage is first-line / leading-`{` only.

## Original report

A `/design` plan-review run (run A6E6687D-A9BC-44D9-ACC9-84FB3BC22E83, issue #4775, round 4) logged a reviewer slot failure for `cursor-plan-requirements`. Inspection of the collector record showed `STATUS=NOT_SUBSTANTIVE`, `EXIT_CODE=0`, `FAILURE_REASON=structured records not found after repair`. The reviewer's actual output was a correct clean pass: two short paragraphs confirming the plan matched scope, followed by the literal sentinel `{"no_issues_found": true}` on a later line. `round-4/reviewer-status.tsv` shows the slot as `failed`, and the failure was appended to `execution-issues.md` under "External Reviewer Issues". The reviewer did its job (found nothing wrong) but was recorded as a failure and earned no scoreboard credit.

This is the benign-this-time cousin of #4790 ("Plan-review panel silently drops all reviewer findings"): here only one slot in one round was dropped, and the round had a second reviewer, so the run outcome was unaffected.

## Reproduction scenario

Deterministic, offline. Feed the structured-reviewer validator an output that puts narration before the no-issues sentinel:

```bash
printf '%s\n' \
  'Reading the plan and tracing cited codebase paths.' \
  'No material gaps found.' \
  '' \
  '{"no_issues_found": true}' > /tmp/reviewer-out.txt

python3 python/cli.py eval validate-research-output \
  --structured-reviewer-mode --write-structured /tmp/sidecar.tsv /tmp/reviewer-out.txt
echo "exit=$?"
```

Observed: prints `structured records not found after repair`, `exit=5` (→ the collector marks the slot `NOT_SUBSTANTIVE`).
Expected: `exit=0` (a clean no-findings pass; empty structured sidecar).

A sentinel-first file (`{"no_issues_found": true}` on line 1) correctly returns `exit=0`, confirming the trigger is the leading prose.

Live evidence path: `larch-logs/design/A6E6687D-A9BC-44D9-ACC9-84FB3BC22E83/plan-review/round-4/cursor-plan-requirements-output.txt` and `.../execution-issues.md` (currently in design-log PR #4874; not yet on `main`).

## Expected behavior

A reviewer that emits a recoverable standalone `{"no_issues_found": true}` sentinel (the documented no-findings contract) should be classified as a **clean no-findings pass** with an empty structured sidecar, even when non-conforming narration precedes the sentinel. The slot should not be marked `NOT_SUBSTANTIVE`, should not be logged as an external-reviewer failure, and should count as an effective (clean) reviewer.

## Observed behavior

When narration precedes the sentinel, the slot is classified `NOT_SUBSTANTIVE` ("structured records not found after repair"), dropped, recorded as `failed` in `reviewer-status.tsv`, and appended to `execution-issues.md`. The clean pass is lost.

## Root cause analysis

Two independent salvage layers each require the no-issues sentinel to **lead** the output, so neither recovers a trailing sentinel:

1. **Collect-time validator (tool-agnostic, primary):** `python/research_eval.py::validate_structured_reviewer_output` (called by `python/collect_results.py` in `--structured-reviewer-mode`). It tests `_json_no_issues("\n".join(lines))`, and `_json_no_issues` → `_first_json_object` does `stripped = text.lstrip(); if not stripped.startswith("{"): return None`. With prose first, the joined text starts with a letter, so the sentinel is not detected; it then finds no JSONL/TSV records and emits `structured records not found after repair` (exit 5). It also accepts a bare leading `NO_ISSUES_FOUND` only as `lines[0]`.
2. **Cursor launch postprocess (Cursor-only, secondary):** `python/agents.py::_review_cursor_normalize_no_issues` only inspects the **first** non-blank line (`first = ...; re.search(r'\{[^{}]*"no_issues_found"[^{}]*\}', first)`); a trailing sentinel after prose is never collapsed to the canonical single-line form, so it cannot pre-fix the input for layer 1.

The reviewer prompt (`python/rendering.py`) deliberately requires zero preamble and warns that any leading prose "risks your entire slot being salvaged or dropped". So the reviewer violated the output contract. The bug is that the **salvage path is too narrow**: when there are no structured records, a standalone recoverable `{"no_issues_found": true}` line is the strongest possible signal of a clean pass and should be honored rather than treated as a failure.

Confidence: high for the mechanism (traced end to end and reproduced offline). The product decision (how lenient salvage should be) is open; see Suggested fixes / Open questions.

## Evidence

- `python/research_eval.py:44-58` — `_first_json_object` returns `None` unless `text.lstrip()` starts with `{`; `_json_no_issues` depends on it.
- `python/research_eval.py:138-150` — `validate_structured_reviewer_output`: only `lines[0] == "NO_ISSUES_FOUND"` or leading-`{` sentinel returns 0; otherwise emits `structured records not found after repair` and returns 5.
- `python/collect_results.py:746` — `_run_validator(["--structured-reviewer-mode", "--write-structured", sidecar, record.reviewer_file])`; lines ~727-769 perform the `NOT_SUBSTANTIVE` classification and drop.
- `python/agents.py:4521-4538` — `_review_cursor_normalize_no_issues` only scans the first non-blank line.
- `python/review_pipeline.py:1257` and `:1318` — sentinel detection / validator invocation on the review pipeline side.
- Live run: `larch-logs/design/A6E6687D-A9BC-44D9-ACC9-84FB3BC22E83/execution-issues.md` (record: `STATUS=NOT_SUBSTANTIVE|EXIT_CODE=0|FAILURE_REASON=structured records not found after repair`) and `.../plan-review/round-4/cursor-plan-requirements-output.txt` (prose then `{"no_issues_found": true}`); `.../plan-review/round-4/reviewer-status.tsv` shows `Cursor-Requirements	failed`.
- Prior art: #4790 / #4789 comments document the same `FAILURE_REASON="structured records not found after repair"` on the same `cursor-requirements` slot (and several dynamic slots), flagged as a fragile structured parse+repair path that "deserves a parity audit / hardening"; #4790's merged fix targeted the `\x1f` parser, not this salvage scope.

## Affected files

- `python/research_eval.py` — primary, tool-agnostic salvage. `_first_json_object` / `_json_no_issues` / `validate_structured_reviewer_output` only honor a leading sentinel. This is the most general fix site (covers Cursor and Codex collect paths).
- `python/collect_results.py` — consumes the validator exit code to classify `NOT_SUBSTANTIVE`; no change needed if the validator is fixed, but it is where the drop happens.
- `python/agents.py` — `_review_cursor_normalize_no_issues`, Cursor-only first-line normalizer; broaden for parity so Cursor output is collapsed before collection.
- `python/review_pipeline.py` — shares the sentinel-detection / validator-invocation surface.
- `python/rendering.py` — reviewer prompt that defines the no-preamble contract (do not weaken the findings-format gate).

## Suggested fix(es)

- In `python/research_eval.py::validate_structured_reviewer_output`, when no structured JSONL/TSV records are recovered, also treat the output as a clean no-findings pass if **any** single non-blank line is exactly the `{"no_issues_found": true}` sentinel (or a bare `NO_ISSUES_FOUND` line), not only `lines[0]`. Keep returning an empty structured sidecar and exit 0. Only widen the **no-issues** salvage; do not relax findings parsing.
- For parity, broaden `python/agents.py::_review_cursor_normalize_no_issues` to detect a standalone trailing sentinel line (not just the first line) and collapse it to the canonical single-line form.
- Keep the strict leading-format gate for **findings** output unchanged (the prompt still demands zero preamble); this change only rescues the unambiguous no-issues case.
- Add regression tests: prose-then-sentinel returns 0 in `python/test_research_eval.py`; the Cursor normalizer collapses a trailing sentinel in `python/test_launch_review.py` / `python/test_agents.py`; a collector-level test that a prose-prefixed no-issues slot is treated as a clean effective reviewer, not `NOT_SUBSTANTIVE`.
- Check Codex-path parity per `.claude/rules/external-tool-launcher-parity.md`: the failing live slot was Cursor, but the collect-time validator is shared, so fixing `research_eval.py` covers both; confirm no Codex-only normalizer needs the same change.

## Open questions

- Should salvage accept a sentinel anywhere in the output, or only when it is the sole non-blank non-prose line (to avoid masking a reviewer that emitted partial findings plus a stray sentinel)? Recommendation: accept only when no valid structured records exist AND exactly one sentinel line is present.
- Should a recovered-after-narration clean pass still emit a low-severity warning (so reviewers/prompts that drift toward preamble remain visible) while no longer being counted as a failure?
- Does `/research` (the other `validate_structured_reviewer_output` consumer) rely on the current strict-leading behavior in any way that a broadened no-issues salvage would change? Expected no, since the change only fires when zero structured records are found.
- Is this the unaddressed remainder of #4790's flagged secondary defect (structured parse+repair hardening), or a separate recurrence? Either way, since #4790 is closed, this issue can serve as the dedicated tracking vehicle for the no-issues-sentinel salvage scope.

## Source: #4888 — [BUG] agent launch-review hardcodes reviewer-failure site to 'review Step 2'

_Originally filed as #4888; preserved verbatim below._

## Summary

The shared reviewer-launch failure logger in `python/agents.py` hardcodes the `run-log append-failure` site string to the literal `"review Step 2"` for every `agent launch-review` launch failure, regardless of which skill/step actually launched the reviewer. In a `/design` Step 3 plan-review run, reviewer-launch failures are therefore logged under `review Step 2` while collector failures from the same panel are correctly logged under `design Step 3`, so the same panel's failures appear under two conflicting site labels in `execution-issues.md`.

## Original report

Root-caused from a live `/design` run (run `63E3CB35-CEB6-4AEE-A979-02B9ACF24B86` on issue #4678).

`python/agents.py`, in the launch-review failure logger (the function that appends to `execution-issues.md` when a reviewer launch exits non-zero), hardcodes the failure site to the literal `"review Step 2"`:
- `python/agents.py:4135` passes `--site` `"review Step 2"` to `run-log append-failure`.
- `python/agents.py:4154` calls `_append_vendor_failure_diagnostics(source, site=f"review Step 2 {tool}-review", ...)`.

This logger is the shared launch-failure path used by `agent launch-review` for all consumers (`/design` Step 3 plan-review, `/implement` Step 5 code review, `/review`). The site is not derived from the actual calling skill/step; it is a constant.

A separate nearby site argument at `python/agents.py:4931` uses `--site "2"` for the `/implement` Step 2 path; it is a possible sibling instance to check, but the primary defect is the hardcoded `"review Step 2"`.

## Reproduction scenario

1. Run `/design <issue>` so Step 3 launches the plan-review panel with Cursor present.
2. Force or observe a reviewer-launch failure (e.g., a Cursor slot that cannot reach the Cursor API, exit 1).
3. Inspect the run's `execution-issues.md` under `larch-logs/design/<RUN_ID>/`. The launch-failure entry header reads `Step review Step 2 — <tool>-review failed ...`, even though the launch occurred in `/design` Step 3.
4. Compare with a collector failure in the same run (e.g., a `NOT_SUBSTANTIVE` slot): its header correctly reads `Step design Step 3 — collect-results ...`.

Not reduced to a unit repro here, but the constant site string is directly visible in source and in the published run log.

## Expected behavior

Reviewer-launch failures should be logged with a site/step label that reflects the actual caller (e.g., `design Step 3` for a `/design` plan-review launch, the matching step for `/implement` Step 5 and `/review`). Launch-failure and collector-failure entries for the same panel should agree on the site label.

## Observed behavior

All `agent launch-review` launch failures are logged under the constant site `review Step 2`. In a `/design` run this disagrees with the collector-failure path (which logs `design Step 3`), so the same panel's failures are split across two site labels.

## Root cause analysis

The launch-review failure logger (around `python/agents.py:4124-4154`) does not accept or thread a caller-provided site/step label. It passes the constant `"review Step 2"` to `run-log append-failure` (`python/agents.py:4135`) and to `_append_vendor_failure_diagnostics` (`python/agents.py:4154`). The collector path (`python/cli.py agent collect-results`, invoked by the caller with `--site "design Step 3"`) is parameterized by the caller and is correct; only the launch-failure logger is hardcoded. The likely original intent was a `/review`-flavored "Step 2" label that was never generalized when the same logger became shared across `/design` Step 3, `/implement` Step 5, and `/review`.

This is low severity (failures are still logged and visible), but it degrades the site/step attribution signal that audits and triage rely on to find review-process problems.

## Evidence

- `python/agents.py:4135` — literal `"review Step 2"` passed as `--site` to `run-log append-failure`.
- `python/agents.py:4154` — `_append_vendor_failure_diagnostics(source, site=f"review Step 2 {tool}-review", ...)`.
- `python/agents.py:4931` — nearby `--site "2"` for the `/implement` Step 2 launch-failure path (possible sibling instance of the same hardcoding pattern).
- Run `63E3CB35-CEB6-4AEE-A979-02B9ACF24B86` (issue #4678), `larch-logs/design/63E3CB35-CEB6-4AEE-A979-02B9ACF24B86/execution-issues.md`:
  - 3 launch failures logged as `Step review Step 2 — cursor-review failed (exit 1 ...)`.
  - 2 collector failures (round 4 `NOT_SUBSTANTIVE`) logged as `Step design Step 3 — collect-results cursor NOT_SUBSTANTIVE failed (exit 0)`.
- Collector path site correctness reference: `skills/design/references/plan-review.md` (Failure logging contract) and SKILL.md Step 3 use `--site "design Step 3"` for collector failures.

## Affected files

- `python/agents.py` — the launch-review failure logger (around lines 4124-4154) holds the hardcoded site; `python/agents.py:4931` is a likely sibling for the `/implement` Step 2 path.
- `python/test_launch_review.py` and/or `python/test_agents.py` — launcher harnesses that should pin the site label is caller-derived (per `.claude/rules/launcher-argv-test-coverage.md`).

## Suggested fix(es)

- Thread the caller's site/step label into the launch-review failure logger instead of the hardcoded `"review Step 2"`. For `/design` Step 3 the site should be `design Step 3`; for `/implement` Step 5 it should match that step; etc. Mirror the site string the collector-failure path already uses for the same panel so launch and collector failures agree.
- Audit `python/agents.py:4931` (`--site "2"`) and any other hardcoded launch-failure site for the same fix.
- Add or extend a regression assertion pinning that the launch-failure `--site` reflects the caller-provided step, not a constant (`.claude/rules/launcher-argv-test-coverage.md`).
- Check parity across the Codex/Cursor launcher family per `.claude/rules/external-tool-launcher-parity.md`.

## Open questions

- What is the cleanest way to pass the caller site into the launcher? Options: a new `--site`/`--step-label` arg on `agent launch-review` threaded to the failure logger, or deriving it from an existing env/context the launcher already receives. The coder should pick the minimal-change path consistent with the collector contract.
- Should the `/implement` Step 2 `--site "2"` at `python/agents.py:4931` be normalized to a descriptive label (e.g., `implement Step 2`) in the same change, or tracked separately?

## Approved direction (outline)

## Proposed Design Outline

### Goals
- Fix #4886: a clean no-issues reviewer whose `{"no_issues_found": true}` sentinel follows narration is recovered as a clean pass, not dropped as `NOT_SUBSTANTIVE`.
- Fix #4888: reviewer launch-failure logs use a caller-derived site label so launch and collector failures for the same panel agree.

### Non-goals
- Do not weaken the strict zero-preamble gate for findings output.
- Do not change reviewer prompts (`rendering.py`) or `/research`'s own validation path.
- Do not add a Codex-only normalizer (none exists; the shared validator covers Codex).

### Approach sketch
- `research_eval.py::validate_structured_reviewer_output`: after structured parse yields nothing, salvage a clean pass only when exactly one standalone sentinel line is present; emit a low-severity, non-failure warning.
- `agents.py::_review_cursor_normalize_no_issues`: collapse a standalone trailing sentinel (not just the first line), keeping the `schema_version` findings guard.
- `agents.py`: thread a caller `site` into `_review_append_launch_failure` via a new `agent launch-review --site`; normalize the sibling `_append_implement_launch_failure` site `"2"` -> `"implement Step 2"`.
- `collect_results.py`: surface the recovered-pass warning without classifying the slot `NOT_SUBSTANTIVE`.

### Surfaces in scope
- `python/research_eval.py`, `python/agents.py`, `python/collect_results.py`, plan-review panel dispatch (caller that passes the site).
- `python/review_pipeline.py` sentinel detection — confirm parity need during drafting.
- Tests: `python/test_research_eval.py`, `python/test_launch_review.py`, `python/test_agents.py`, `python/test_implement_dispatch.py`, and a collector-level assertion.

### Open questions
- Exact warning channel: validator stdout marker consumed by the collector vs collector-side detection.
- Whether `review_pipeline.py:1257` needs the same trailing-sentinel broadening for parity.
