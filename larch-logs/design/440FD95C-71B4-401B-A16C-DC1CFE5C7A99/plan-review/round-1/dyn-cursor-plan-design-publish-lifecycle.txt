The plan’s terminal helper uses `_is_terminal_publish_outcome` for every `cancelled-*` and `failed-*` outcome. That collides with clarify, which already owns log publish on several of those outcomes.

Happy clarify calls this with `outcome="cancelled-clarify"` (lines 1233-1241). Comment-post and label-remove failures call it with `outcome="failed-clarify"` (lines 1188-1196, 1218-1226). The orchestrator then runs the Final summary block for the same `SUMMARY_OUTCOME` values.

A second `log_publish_main` on the same run id targets the same branch name (`design_log_publish_flow.py` lines 306-317). The first successful publish often leaves that branch on the remote; a second `worktree add -b` commonly fails. With the plan’s fail-closed terminal rule (no `.completed/step-final-summary` on publish failure), clarify success can lose its terminal sentinel even when clarify publish and disk upsert succeeded.

**Minimum-change fix:** Mirror the approved / Step-5c split: clarify keeps centralized log publish + disk upsert; Final summary for `cancelled-clarify` (and `failed-clarify` when clarify already published) should use local render from `final-summary.md`, not `_publish_terminal_final_summary`. Gate republish on `.design-log-publish-metadata.env` or prior `design-log-publish` stdout when `failed-clarify` needs a first publish (e.g. fetch-only failures with no prior publish).
