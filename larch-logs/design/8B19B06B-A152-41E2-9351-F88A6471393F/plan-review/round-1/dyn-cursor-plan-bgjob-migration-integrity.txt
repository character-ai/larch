## Findings

### 1. Step 5 merge-env path mismatch (correctness)

The plan routes parent mode through `bgjob adapt`, but `adapt._prepare_launch_spec` always sets merge env to `bgjob/{step}.merge.env`:

```291:313:python/larch/bgjob/adapt.py
def _merge_env_path(*, spec: model.JobSpec) -> Path:
    root = model.bgjob_dir(spec.tmpdir)
    return root / f"{model.validate_slug(spec.step, label='step')}.merge.env"


def _prepare_launch_spec(spec: model.JobSpec) -> model.JobSpec:
    ...
    merge_env = _merge_env_path(spec=spec)
    ...
    larch_io.trusted_atomic_write(path=merge_env, text="", root=root, mode=0o600)
    command = (*spec.command, "--bgjob-child", "--merge-result-env", str(merge_env))
```

Step 5 today uses a different merge file, and `review-and-fix` writes only there:

```219:222:skills/implement/scripts/step-5-review.sh
MERGE_RESULT_ENV="$IMPLEMENT_TMPDIR/.step5-review-result.env"
...
: >"$MERGE_RESULT_ENV"
```

```137:320:python/larch/review/review_and_fix.py
_STEP5_REVIEW_RESULT_ENV = ".step5-review-result.env"
...
    return tmpdir / _STEP5_REVIEW_RESULT_ENV
```

The plan does not list `adapt.py` or `review_and_fix.py` as updates. Without an explicit merge-path contract, daemon publication can miss Step 5 KVs and break the grammar in `step-5-review.md`.

### 2. Checks identity pre-seed vs adapt truncate (correctness)

Step 6 and `run-step-checks` seed `CHECKS_INPUT_*` into merge env before `bgjob start`:

```327:335:skills/implement/scripts/step-6-entry.sh
MERGE_RESULT_ENV_TMP="$(mktemp "${MERGE_RESULT_ENV}.tmp.XXXXXX")" || exit 2
{
    printf '%s\n' "CHECKS_INPUT_HEAD_SHA=${LAUNCH_HEAD}"
    ...
} >"$MERGE_RESULT_ENV_TMP"
...
mv -f "$MERGE_RESULT_ENV_TMP" "$MERGE_RESULT_ENV"
```

`adapt` truncates that file to empty on every fresh launch (`adapt.py:309`). Live rejoin calls `classify_live_seed`; an empty merge env yields `incomplete` / `missing-identity` (`checks_result_identity.py:224-232`), and parents fail closed when `STATE != matching` (`step-6-entry.sh:283-286`). The plan names the edge case but does not say how identity seeding survives `start_or_reattach`.

### 3. Step 5 canonical result reuse (risk-integration)

Generic adapt reuse only checks `BGJOB_RC` and `STEP` (`adapt.py:167-184`). Step 5 requires a richer envelope and stall semantics:

```88:132:skills/implement/scripts/step-5-review.sh
required_keys = {
    "STEP5_REVIEW_STATUS",
    ...
}
...
if rows.get("BGJOB_RC") == "0" and status == "complete" and required_keys.issubset(rows):
    print("complete")
...
if status == "stall" and required_keys.issubset(rows):
    print("stall")
```

The plan says “validate completed results before reuse” but does not require porting this classifier before calling adapt. A partial result env could be emitted as `BGJOB_STATUS=DONE`.

### 4. Step 5 liveness AND vs adapt daemon policy (risk-integration)

Step 5 registry probe requires both processes live:

```75:76:skills/implement/scripts/step-5-review.sh
    if registry.child_liveness(entry).live and registry.daemon_liveness(entry).live:
```

`adapt` reattaches when the daemon is live (`adapt.py:415-429`), even if the child is not. That conflicts with acceptance “behave identically” unless the plan documents this as an intentional policy change.

### 5. CI-fixer successful finalize lineage (correctness)

Successful `--finalize` always appends a lineage row:

```152:152:skills/implement/scripts/step-8-ci-fixer.sh
  printf '%s\t%s\t%s\t%s\t%s\t%s\n' "$ATTEMPT" ... >>"$LINEAGE"
```

The next `--start` derives `ATTEMPT` from lineage row count (`step-8-ci-fixer.sh:195`). Repeated finalize on the same step can double-count. Crash finalization has dedup in `ci_fixer_lane.py:949-1013`; the plan’s “lineage deduplication” should cover the successful path explicitly in `ci_fixer_adapter.py`.
