## Dialectic Resolutions

### DECISION_1: Fix-dispatch path for per-job inner loop
**Resolution**: Wrap `scripts/lint-fix-loop.sh` and widen its `--site` enum to accept new per-job values (e.g., `ship-pr-ci-per-job`) for the new per-job CI repair loop. Do NOT pass per-job local-CI logs through `run_ci_fix_vendor`'s full 3-tier waterfall (which is reserved for the broader post-CI-fail recovery and includes rollback / first-fixer bail / un-conditional `run_checks_with_lint_fix_loop` re-verify semantics that do not match a single-job retry).
**Disposition**: voted
**Vote tally**: THESIS=1, ANTI_THESIS=2
**Thesis summary**: Reuse `run_ci_fix_vendor`'s existing 3-tier launcher waterfall directly, passing each captured local-job log as `--failure-log`. The CI launchers already accept `--failure-log` and are prompt-shaped for GitHub Actions logs; `lint-fix-loop.sh`'s prompt template is hard-wired to making `scripts/relevant-checks.sh` pass.
**Antithesis summary**: Wrap `lint-fix-loop.sh` with a widened `--site` enum so the per-job retry is a small local-command-retry loop (cap-3) shaped exactly like the existing post-vendor `run_checks_with_lint_fix_loop` invocation. Reusing `run_ci_fix_vendor` imports phase-level CI recovery, rollback, launcher-tier policy, token recording, and `run_checks_with_lint_fix_loop` re-entry — all unnecessary for a single mapped local job.
**Why antithesis prevails**: Both external judges (and Step 2b will follow them) found that per-job repair semantically matches `lint-fix-loop.sh`'s cap-3-local-retry contract, not `run_ci_fix_vendor`'s phase-level CI recovery. Reusing run_ci_fix_vendor would unconditionally re-enter `run_checks_with_lint_fix_loop` (`scripts/ship-pr.sh:1437-1439`) after every per-job fix and re-run the relevant-checks gate, which is wasteful and adds rollback / first-fixer-bail semantics designed for the broader recovery path. The thesis's strongest concession (lint-fix-loop's prompt is wired to relevant-checks) is engaged by treating the prompt template as a localized `--site`-conditional concern — exactly the surface that the widened enum will parameterize.
**Plan consequence**: the new per-job loop in ship-pr.sh dispatches via `lint-fix-loop.sh` with a new `--site` value, **not** through `run_ci_fix_vendor`. `lint-fix-loop.sh`'s `compose_prompt` function must be extended to emit a CI-job-shaped prompt body when `--site` matches the new per-job pattern (instead of always saying "make relevant-checks.sh pass").

### DECISION_2: Whether to factor a reusable "run captured cmd → dispatch fixer → rerun up to 3" helper in ship-pr.sh
**Resolution**: Factor a private inline helper in `scripts/ship-pr.sh` (e.g., `run_captured_cmd_then_fix_loop`) that encapsulates the shared mechanics: capture local-run log to a tmp file, redact via `redact-secrets.sh`, dispatch `lint-fix-loop.sh` (the per-job dispatcher resolved in DECISION_1), re-run the captured command, repeat up to per-job cap. Both the new per-job loop AND the existing `run_checks_with_lint_fix_loop` call site can share the primitive; specialized side-effects (delta-path tracking, `record_failure` category strings, `LAST_LINT_FIX_DELTA_PATHS_FILE` etc.) are preserved at the call site via callbacks or status outputs rather than inlined into the helper.
**Disposition**: voted
**Vote tally**: THESIS=2, ANTI_THESIS=1
**Thesis summary**: A shared private helper avoids drift between two near-identical loops (capture-log + redact + dispatch + re-run + count). Specialized handling can stay at call sites with callbacks; only the invariant loop mechanics are factored.
**Antithesis summary**: `run_checks_with_lint_fix_loop` (scripts/ship-pr.sh:795-871) is not a bare retry loop — it has specialized staging semantics (vendor_dirty_paths_file, LAST_LINT_FIX_DELTA_PATHS_FILE, delta-path merging, `record_failure` coupling, downstream `git add` logic at 1445-1456). Forced abstraction across two contexts often reintroduces complexity as conditional branches.
**Why thesis prevails**: Both external judges accepted the thesis's middle-path framing — extract only the invariant loop mechanics (capture, redact, dispatch, rerun, count) and preserve specialized side-effects (delta-path tracking, record_failure category strings, downstream `git add` coupling) at the call site via callbacks or status returns. The antithesis's strongest concession is that drift is manageable with tests; the judges found this is precisely the argument that justifies factoring once and locking the contract via a single regression harness, rather than relying on review discipline alone. The factoring must be conservative: do NOT inline staging behavior into the helper; the helper exposes status / log paths and the call site owns staging.
**Plan consequence**: introduce the helper, refactor `run_checks_with_lint_fix_loop` to use it (keep all delta-path / record_failure side-effects at the call site), and use the same helper from the new per-job loop. Update `scripts/test-ship-pr.sh` and `scripts/test-ship-pr-fix-loop-2632.inc.sh` assertions to cover the factored helper directly.
