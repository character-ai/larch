## Dialectic Ballot

You are a judge on a 3-panel adjudicating contested design decisions. For each `DECISION_N` below, read both Defense A and Defense B, then cast exactly one binary vote: `THESIS` or `ANTI_THESIS`. THESIS means the side labeled as defending the CHOSEN option on that decision wins; ANTI_THESIS means the side defending the ALTERNATIVE option wins. Judge on argument quality — not on which defense "sounds more confident." Vote on every decision. Do not modify files.

The tool that produced each defense is hidden (Defense A / Defense B labels are anonymous). Which side defends CHOSEN vs. ALTERNATIVE is disclosed on each decision header because that information is semantic, not tool-attributive.

### DECISION_1: Fix-dispatch path for per-job inner loop

**CHOSEN**: Reuse run_ci_fix_vendor 3-tier waterfall directly with --failure-log set to local-job log. No changes to lint-fix-loop.sh.
**ALTERNATIVE**: Wrap lint-fix-loop.sh with widened --site enum and route per-job fixes through it.

Defense A (defends CHOSEN):
<defense_content>
<steelman>
Centralizing every fix in `lint-fix-loop.sh` by widening `--site` would reuse one battle-tested loop (tmpdir wiring, `LINT_FIX_STATUS`, delta paths, and the existing three-attempt driver in `run_checks_with_lint_fix_loop`) instead of growing another parallel orchestration surface in `ship-pr.sh`.
</steelman>
<claim>
For per-job CI remediation, `ship-pr` should call the same `run_ci_fix_vendor` tier-A→tier-B→tier-C waterfall, passing each captured local job log as `--failure-log`, and should not extend `lint-fix-loop.sh`’s `--site` enum for that purpose.
</claim>
<evidence>
In [`scripts/ship-pr.sh`](scripts/ship-pr.sh), `run_ci_fix_vendor` iterates tiers `tier-A`, `tier-B`, `tier-C` and, when a redacted capture exists, passes `--failure-log` into each launcher’s `--role fix` invocation (`1375:1397:scripts/ship-pr.sh`). In contrast, [`scripts/lint-fix-loop.sh`](scripts/lint-fix-loop.sh) frames the task as making `scripts/relevant-checks.sh` pass from a checks log (`40:48:scripts/lint-fix-loop.sh`), and its usage string hard-limits `--site` to `step3|step5|step6|ship-pr-ci-initial|ship-pr-ci-merge` (`22:23:scripts/lint-fix-loop.sh`), which matches the post-vendor `run_checks_with_lint_fix_loop` path (`813:829:scripts/ship-pr.sh`) rather than arbitrary GitHub Actions job output.
</evidence>
<strongest_concession>
Widening `--site` could keep all “LLM fixes repo from a log file” flows behind one script, reducing the chance that a new per-job path diverges from session-env, redaction, or commit-staging conventions that `lint-fix-loop.sh` already encodes.
</strongest_concession>
<counter_to_opposition>
Those conventions are still needed after a vendor fix—`run_ci_fix_vendor` already ends by calling `run_checks_with_lint_fix_loop` for exactly that relevant-checks-shaped pass (`1437:1439:scripts/ship-pr.sh`)—so per-job CI log repair belongs in the launchers that already advertise `--failure-log` for fix roles (`32:32:scripts/launch-tier-A-ci.sh`, `28:28:scripts/launch-tier-B-ci.sh`, `31:31:scripts/launch-tier-C-ci.sh`), not by overloading a prompt whose success criterion is wired to `relevant-checks.sh`.
</counter_to_opposition>
<risk_if_wrong>
If the waterfall is wrong here, fixes that only make sense against full Actions metadata would misfire on trimmed local-job logs, wasting tiers and still landing in `BAIL_REASON=ci-local-unfixable:…` without improving the PR, while a tailored `lint-fix-loop` site might have steered the model with job-specific instructions.
</risk_if_wrong>
</defense_content>

Defense B (defends ALTERNATIVE):
<defense_content>
<steelman>
The thesis is strongest where it says CI launchers already accept `--failure-log` and are prompt-shaped for GitHub Actions logs, so reusing `run_ci_fix_vendor` avoids teaching `lint-fix-loop.sh` about non-relevant-checks failures. It also preserves the existing tier-A/tier-B/tier-C waterfall without another dispatch abstraction.
</steelman>
<claim>
The proportional implementation is to wrap and slightly widen `lint-fix-loop.sh`, because the requested per-job inner loop is a local-command retry loop, not the full ship-pr CI vendor recovery path.
</claim>
<evidence>
`scripts/ship-pr.sh:827-840` already implements the exact cap-3 fix-then-rerun loop around `lint-fix-loop.sh`, while `scripts/lint-fix-loop.sh:195-202` shows the only site coupling is a small enum/label switch. By contrast, `scripts/ship-pr.sh:1375-1397` runs a three-launcher CI waterfall, `scripts/ship-pr.sh:1402-1422` adds rollback and first-fixer bail semantics, and `scripts/ship-pr.sh:1437-1439` unconditionally re-enters `run_checks_with_lint_fix_loop`, which is unnecessary and potentially wrong for a single mapped local job.
</evidence>
<strongest_concession>
The opposing point is real: `scripts/lint-fix-loop.sh:45-48` currently tells the fixer to make `scripts/relevant-checks.sh` pass, while `scripts/launch-tier-B-ci.sh:82-119` validates and embeds a failure log directly for CI-fix prompts.
</strongest_concession>
<counter_to_opposition>
That mismatch is a localized prompt/site-label problem, whereas reusing `run_ci_fix_vendor` imports phase-level CI recovery, rollback, launcher-tier policy, token recording, and whole-relevant-checks verification into a job-local loop whose contract is only “run this mapped command, fix, retry up to three times, mark unfixable.”
</counter_to_opposition>
<risk_if_wrong>
If the wrapper path loses, ship-pr’s per-job repair can become coupled to broad CI-vendor semantics, making unfixable-set handling and per-job retry accounting harder to reason about and easier to break when the existing waterfall changes for unrelated CI recovery reasons.
</risk_if_wrong>
</defense_content>

### DECISION_2: Whether to factor a reusable run-captured-cmd-then-fix-waterfall helper in ship-pr.sh

**CHOSEN**: Factor out a private helper in ship-pr.sh shared by both the new per-job loop AND a refactored run_checks_with_lint_fix_loop.
**ALTERNATIVE**: Keep run_checks_with_lint_fix_loop as-is and duplicate ~80% of the structure in a separate per-job loop.

Defense A (defends ALTERNATIVE):
<defense_content>
<steelman>
Factoring a single `run_captured_cmd_then_fix_waterfall` keeps one authoritative implementation of capture, redaction, vendor dispatch, re-run, and attempt counting, so any correction to that spine fixes both the existing CI merge-path and the new per-job path and avoids silent divergence when one copy is updated and the other is not.
</steelman>
<claim>
Given current requirements, leaving `run_checks_with_lint_fix_loop` untouched and adding a separate per-job loop that repeats the capture-or-dispatch skeleton is the proportionate choice because it avoids refactoring behavior that is already regression-locked and materially more specialized than a generic waterfall wrapper.
</claim>
<evidence>
In [`scripts/ship-pr.sh`](scripts/ship-pr.sh), `run_checks_with_lint_fix_loop` (lines 795–871) is not a bare retry loop: it snapshots vendor dirty paths before the loop (`capture_dirty_paths` into `vendor_dirty_paths_file` at 825–826), merges lint-fix delta paths into `ALL_LINT_FIX_DELTA_PATHS_FILE`, sets `LAST_LINT_FIX_DELTA_PATHS_FILE` on success (844–848), and treats `no-changes` as an immediate failure with `record_failure` (851–853), while `run_ci_fix_vendor` wires this function as the post-waterfall verification gate at 1437–1439; that coupling is exactly where a shared helper can accidentally change staging semantics that downstream `git add` logic in the same file depends on (1445–1456).
</evidence>
<strongest_concession>
A duplicated loop really can drift if someone edits the per-job path’s redact-or-rerun sequencing without mirroring `run_checks_with_lint_fix_loop`, producing inconsistent caps or logging behavior between the two flows.
</strongest_concession>
<counter_to_opposition>
Drift is manageable with tests and code review, whereas a forced abstraction across two contexts that already differ—lint-fix-loop’s `LINT_FIX_STATUS` / delta-path side effects versus a future per-job path driven by `run_ci_fix_vendor` and job-scoped failure logs—usually reintroduces complexity as conditional branches or extra parameters that are harder to reason about than two explicit, locally similar blocks.
</counter_to_opposition>
<risk_if_wrong>
If the anti-thesis loses, the only real downside is maintaining two parallel implementations of the same mechanical steps, which increases the chance a bugfix lands in one loop but not the other until a test or production failure exposes the gap.
</risk_if_wrong>
</defense_content>

Defense B (defends CHOSEN):
<defense_content>
<steelman>
Keeping the existing lint-fix loop intact avoids refactoring code that already has focused tests and phase-specific behavior. A separate per-job loop can be easier to reason about initially because CI job repair may need semantics that differ from relevant-checks repair.
</steelman>
<claim>
The plan should factor a private helper in `scripts/ship-pr.sh` so the new per-job CI loop and `run_checks_with_lint_fix_loop` share the capture, redaction, fixer dispatch, rerun, and attempt-count primitive.
</claim>
<evidence>
`scripts/ship-pr.sh:813-870` already performs the repeated structure: capture checks, extract/resolve the redacted log, call `run_lint_fix_loop_capture`, rerun checks, and cap attempts at three. `scripts/ship-pr.sh:1357-1363` separately redacts CI failure logs before `run_ci_fix_vendor` passes them into the waterfall at `scripts/ship-pr.sh:1391-1397`, showing the same log-to-fixer contract the new per-job loop would otherwise duplicate.
</evidence>
<strongest_concession>
The strongest opposing point is that `run_checks_with_lint_fix_loop` has important details beyond the generic loop, including `record_failure` category handling and `LAST_LINT_FIX_DELTA_PATHS_FILE` staging behavior at `scripts/ship-pr.sh:844-849`.
</strongest_concession>
<counter_to_opposition>
That argues for a narrow helper with explicit callbacks or status outputs, not duplication: preserve phase-specific recording and delta-path handling at the call site while centralizing only the invariant loop mechanics that are already shared with per-job CI repair.
</counter_to_opposition>
<risk_if_wrong>
If this position loses, two near-identical retry engines will diverge: one may update redaction, retry caps, or terminal status handling while the other silently keeps old behavior, making remote-CI repair unreliable and harder to test over the next month.
</risk_if_wrong>
</defense_content>
