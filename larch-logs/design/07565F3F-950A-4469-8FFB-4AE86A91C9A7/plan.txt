# Implementation Plan: /design files OOS issues directly via /issue (with [OOS] prefix) + Step 5 breadcrumb split

## Summary

This change relocates **design-phase** OOS issue filing from `/implement` Step 9a.1 upstream into `/design`. After the user picks **Approve final design** at Step 4b Gate C, `/design` runs the same combine + file-conflict-deps pipeline that `/implement` currently runs, then calls `/larch:issue` in batch mode with `--title-prefix "[OOS]"` to file each accepted (non-security) OOS as a public GitHub issue. Filed URLs are annotated back into `$DESIGN_TMPDIR/oos-accepted-design.md` per-block, and also written to a sentinel file `$DESIGN_TMPDIR/oos-issues-created.md` for `/implement` carry-forward. `/implement` Step 9a.1 reads the design-phase OOS file and **skips re-filing items whose `Filed URL` field is populated**, but continues to file Step-5 review OOS and main-agent dual-write OOS as before. The `oos-disposition-gate.sh` is extended to count design-phase Filed URLs against the non-security OOS block count.

Secondary scope: the misleading `🔶 /design 5: cleanup` breadcrumb is fixed by splitting today's Step 5 into **Step 5 (finalize)** — covers reviewer-status notes, OOS filing (new), `larch:plan` write, design-log publish, and `[DESIGNED]` rename — and **Step 6 (cleanup)** — covers the `cleanup-tmpdir.sh` call. `step-name-registry.tsv` and SKILL.md breadcrumb prints update in lock-step.

## Approach

### Filing trigger placement

The new OOS-filing sub-step fires inside the new Step 5 (finalize), **before** the `larch:plan` block write. This sequencing means the filed URLs are available to be optionally embedded in the `composed-plan.md` (e.g., a `## Filed Out-of-Scope Issues` section); however, this plan does **not** add such an embedding — Filed URLs live in the local `oos-accepted-design.md` artifact only. Embedding into the plan block is out of scope for this PR.

### Idempotency

Re-invocation of `/design` on the same issue (e.g., user invokes `/design` again after a clean exit) MUST NOT double-file. The `$DESIGN_TMPDIR/oos-issues-created.md` sentinel is the deterministic guard: at the top of Step 5b, if the file exists and is non-empty, recover URLs from it and skip the entire pipeline (cap, deps, /issue call). This parallels `/implement` Invariant #2 (Step 9a.1 OOS Sentinel Idempotency) — see `skills/implement/SKILL.md` NEVER #5 for the rationale.

Note that `/design` re-runs across distinct sessions create a fresh `$DESIGN_TMPDIR` each time, so the sentinel cannot cross sessions. Cross-session protection relies on `/larch:issue`'s own LLM dedup (Phase 1/2 against the existing repo issues). For `--trivial` scope, this is acceptable; cross-session sentinel persistence is out of scope.

### Gate C re-run loop and Step 3 re-runs

Step 4b Gate C option (c) "Re-run review panel" jumps back to Step 3. When Step 3 re-runs, the tally script overwrites `$DESIGN_TMPDIR/oos-accepted-design.md` with the new run's accepted-OOS blocks. **The Step 5b sentinel does NOT exist yet at this point** (Gate C has not approved yet), so the overwrite is safe. Step 5b only runs after Gate C Approve, by which point the latest run's `oos-accepted-design.md` is the canonical input. There is no risk of filing OOS items from a discarded prior review run.

### Helper sharing strategy

The plan reuses `skills/implement/scripts/oos-issue-cap.sh` and `oos-file-conflict-deps.sh` from /design unchanged. Both helpers accept `--input-file` / `--output` paths and do not hardcode `/implement` tmpdirs (verified: `oos-file-conflict-deps.sh:43` falls back to `IMPLEMENT_TMPDIR` only when neither flag is set, and the design helper passes `--output` explicitly). No code changes to the helpers; only the calling site differs. The script-md-siblings rule's "caller surface" clause is satisfied because the new caller (`file-design-oos.sh`) is documented in the new helper's sibling .md.

### Tracking-issue summary projection

The current tracking-issue summary comments are written by `/implement` (`larch:final-summary` marker) and include the filed OOS URL list. After this change, `/implement`'s final summary still aggregates filed URLs from both /design's pre-filed URLs (via `$DESIGN_TMPDIR/oos-issues-created.md` carry-forward) and /implement's own Step 9a.1 filings. No `/design`-owned new marker comment is introduced; this keeps the comment-marker surface unchanged (per `skills/implement/references/summary-comment-template.md`).

### Disposition gate adaptation

The disposition gate is the safety net that ensures no accepted OOS is silently dropped. With /design pre-filing, the gate's `filed` counter must include URLs from `oos-accepted-design.md`'s `- **Filed URL**:` lines (or equivalent). The chosen mechanism: extend the gate to accept **multiple** `--filed-urls-file` arguments, and have /implement Step 9a.1 pass both `$IMPLEMENT_TMPDIR/oos-issues-created.md` (own filings) and `$_oos_design_path` (the design-phase accepted-OOS file — which contains Filed URL lines that the existing URL regex `https://github\.com/.../issues/[0-9]+` will match). This adds one CLI parser change and one shared-helper call-site update; no new helper.

### Privacy guardrail

OOS Descriptions are filed as **PUBLIC** GitHub issues by `/larch:issue`. Now that `/design` files them upstream (rather than `/implement`), the same privacy constraint that lives at `skills/implement/SKILL.md:568` applies equally to the design phase: reviewer-supplied `path:line` hints in OOS Descriptions become public on filing. The new Step 5b block in `skills/design/SKILL.md` MUST include a "Privacy guardrail" paragraph mirroring the /implement wording — reviewers should follow `SECURITY.md` and avoid naming high-risk paths or pasting secret-adjacent material in OOS Descriptions; the prose anchor is the design-mindset hint that catches reviewer-prompt regressions before they reach public filing. The `redact-secrets.sh` pipe inside `create-one.sh` is the mechanical backstop, but the prose anchor is the documentation-level guard against future-edit regressions in the reviewer prompts. Cross-reference SECURITY.md's outbound-redaction subsection from the new Step 5b paragraph.

## Edge cases

- **Empty `oos-accepted-design.md`**: Step 5b prints `⏩ 5b: oos filing — no accepted-OOS items` and proceeds to 5c (plan write). No /issue call.
- **All blocks are security-tagged**: per existing `plan-review.md:128`, security-tagged blocks are never written to `oos-accepted-design.md` in the first place. The file may still contain non-security blocks; only those are filed. (Sanity check: count non-security blocks via `oos-non-security-block-count.awk` before invoking /issue.)
- **`/larch:issue` returns `ISSUES_FAILED > 0`**: the helper exits non-zero; SKILL.md catches it, surfaces a `**⚠ 5b: oos filing — N items failed**` warning, appends a `Tool Failures` entry to `$DESIGN_TMPDIR/execution-issues.md`, and **continues** to 5c (plan write). Filing failure does NOT block the larch:plan write — operators inspect the warning and manually re-file or escalate. Partial filing (some succeeded, some failed) IS reflected in the per-block Filed URL annotation (only successful items get the field).
- **`oos-issue-cap.sh` exits non-zero (Tier-2 cap exceeded, parser failure)**: fatal — the run cannot continue without a valid working batch. Emit `**⚠ /design: oos filing aborted (cap helper failed)**`, log to execution-issues, and skip to 5c. Operator triage required.
- **`oos-file-conflict-deps.sh` exits non-zero**: graceful-degrade — invoke `/larch:issue` WITHOUT `--intra-batch-deps-file`, log a `**⚠ /design: oos-file-conflict pre-pass failed**` warning matching the /implement Step 9a.1 fallback (SKILL.md:564), and continue. /issue's Phase-2 LLM dep-analysis still runs as the sole dep source.
- **Sentinel exists from prior run in same session**: idempotency path — recover URLs from `$DESIGN_TMPDIR/oos-issues-created.md`, skip the pipeline, and re-annotate `oos-accepted-design.md` to be safe (the annotation pass is idempotent: it only adds Filed URL when missing for a matching OOS_N block).
- **`/implement` running on a /design output that pre-existed this change**: backward compatibility — if `oos-accepted-design.md` lacks `Filed URL` fields, /implement Step 9a.1 treats every block as unfiled (current behavior). Only the disposition gate gains the multi-file accommodation; the parser-side skip is opt-in via field presence.
- **Step 5 breadcrumb numbering on resume / log replay**: any tooling that parses `🔶 /design 5: cleanup` literally must be updated. Audit search: `grep -rn "design 5: cleanup\|5\\\\tcleanup" docs/ skills/ scripts/`.

## Failure modes

The three most likely architectural/systemic failure paths and their mitigations:

1. **Disposition gate false-negative (URL miscounting)**. The shared `count_filed_urls_union_files` regex matches **any** GitHub issue URL in any input file. If a reviewer's OOS Description contains a URL like "see also #1234" referencing a related issue, the gate would over-count and miss a real disposition gap. **Earliest warning signal**: the URL count exceeds the actual filed-issue count by a margin visible in the gate's stderr `non_security_oos=X filed_urls=Y` line. **Mitigation**: tighten the regex used when scanning `oos-accepted-design.md` to require the `- **Filed URL**:` prefix on the same line (a new helper `count_filed_url_field_lines`). Defer to a follow-up PR if the simpler union approach proves false-negative-prone in practice; for `--trivial` scope, accept the small risk in exchange for minimal code change.

2. **Step 5b → Step 5c ordering regression**. If a future edit re-orders the new finalize sub-steps so the larch:plan write happens BEFORE OOS filing, a /design run that fails OOS filing would still have published the plan to the issue (claiming `[DESIGNED]`), leaving stale state. **Earliest warning signal**: a /design run that prints `**⚠ 5b: oos filing — N items failed**` AND `[DESIGNED]` rename succeeded for the same session. **Mitigation**: a structural assertion in `scripts/test-design-structure.sh` pinning the sub-step order (5a → 5b OOS filing → 5c plan write → 5d rename → Step 6 cleanup), plus a SKILL.md anti-pattern bullet documenting the ordering invariant.

3. **`/design` session re-run drops sentinel and double-files**. If a future edit moves `cleanup-tmpdir.sh` from Step 6 back into Step 5, OR if the sentinel write fails silently and the cleanup proceeds anyway, a second `/design` invocation on the same issue would not find the sentinel and would file duplicate issues. **Earliest warning signal**: two `/design` runs on the same `ISSUE_NUMBER` produce two sets of filed-OOS URLs in GitHub for the same observations. **Mitigation**: the `file-design-oos.sh` helper writes the sentinel **before** the in-place rewrite of `oos-accepted-design.md` completes (via temp-file + atomic mv ordering), so the sentinel always exists when the artifact has Filed URL annotations. Also: /issue's LLM dedup catches obvious title duplicates as a soft backstop.
