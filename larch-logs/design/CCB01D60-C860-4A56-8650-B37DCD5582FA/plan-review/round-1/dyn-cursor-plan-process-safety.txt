### 1. Registry key must include run-id (`python/larch/bgjob/cli.py`, proposed)
The binding issue requires `~/.cache/larch/daemons/<run-id>-<step>.env`. The plan’s `registry.py` / `cli.py` sections describe registry storage but never wire `--run-id` or `LARCH_RUN_ID` into the filename. Same `STEP` names are reused across lanes and retries, so concurrent runs can clobber one registry entry and misroute `wait`/`reap`.

### 2. Missing-leader kill path is not recycled-PGID-safe (`python/larch/core/process_identity.py:216-299`)
Existing termination logic that bgjob is told to wrap already has a weak branch when the leader PID is absent:

```216:234:python/larch/core/process_identity.py
def _validated_missing_leader_members(
    *,
    recorded: RecordedProcessIdentity,
    runner: proc.Runner,
) -> tuple[int, ...] | None:
    descendants = collect_process_group_members(pgid=recorded.pgid, runner=runner)
    if not descendants:
        return None
    validated_members: list[int] = []
    for child in descendants:
        child_identity = read_process_identity(
            pid=child,
            runner=runner,
            expected_signature=recorded.expected_signature,
        )
        if child_identity is None or child_identity.pgid != recorded.pgid:
            return None
        validated_members.append(child)
    return tuple(validated_members)
```

That path never compares `start_time` or full `command_signature`, yet still reaches `os.killpg(recorded.pgid, …)` (lines 285-299). The plan’s edge-case line (“Recycled PID or PGID must never be killed”) does not require fixing or bypassing this branch. Extend identity checks or restrict `reap` to registry deletion unless full leader identity validates.

### 3. Double-fork needs an explicit registry handshake (`python/larch/bgjob/daemon.py`, proposed)
`dispatch_leg.py` already shows the safe pattern: capture stable identity with `_read_stable_process_identity(..., require_pgid_match=True)` before persisting (`114-125`). The plan does not say whether the foreground `start` parent or the post-`setsid` daemon writes the registry, or how `start` knows identity is stable before printing `BGJOB_STATUS=STARTED`. Without that contract, the first registry row can record the wrong process.

### 4. `reap` must be spelled out as signal-only-on-full-match (`python/larch/bgjob/registry.py`, proposed)
Acceptance criterion 2 is explicit, but implementation files only say “identity-verified stale jobs.” Pin: full four-field validation before any signal; mismatch → unlink registry + refusal log, no `killpg`. `kill_active_leg` already refuses on failed validation (`dispatch_leg.py:337-348`); `reap` should follow the same fail-closed rule.
