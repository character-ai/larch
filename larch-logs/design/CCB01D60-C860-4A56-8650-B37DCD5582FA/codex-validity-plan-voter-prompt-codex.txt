# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `major`. Single-YES `minor`, `nit`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Problem

Every long-running larch step (plan review, code review, checks, ship-pr, research lanes) is launched today via Bash `run_in_background: true` and waits on `&lt;task-notification&gt;` for completion. That primitive is undocumented, fires before process exit, re-fires on every turn-end, cannot be suppressed (upstream anthropics/claude-code#18544, closed not-planned), and cannot be intercepted by any hook (anthropics/claude-code#39027). We have shipped ~20 mitigation PRs since 2026-06-13 (#5240, #5478, #5511, #5610, #5635, #5638, #5639, #5684, #5780, #5781, #5927, #6268, #6309, #6448, #6478, #6493, #6508 …) and incidents still recur daily, because the defense layers can only reduce probability, quiet turns, and bound loops — never reach zero. Full analysis: consolidated upstream report anthropics/claude-code#74982.

This issue removes the dependency on `run_in_background` and `&lt;task-notification&gt;` entirely. Issue 2 (filed separately, blocked on this one) deletes the obsolete defense stack.

## Verified platform facts this design relies on (Claude Code 2.1.201, tested 2026-07-06)

1. Foreground-to-background auto-conversion fires at the call's **effective timeout** (the `timeout` param, else 120s default), not at a fixed threshold: a 130s command with `timeout=300000` completed in the foreground; the same command with no param converted at 120s.
2. A raised `BASH_MAX_TIMEOUT_MS` is honored at validation **and runtime**: a 630s command under `BASH_MAX_TIMEOUT_MS=700000` with `timeout=660000` completed in the foreground.
3. With `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, `run_in_background` is removed from the tool schema (InputValidationError if passed) and timeout expiry is a clean SIGTERM kill (exit 143) instead of a conversion.
4. Bare foreground `sleep N &amp;&amp; …` is blocked pre-execution by the harness; wrapped helpers are not.

## New machinery (normative behavior contracts; module layout may be refined by /design)

New Python package, proposed `python/larch/bgjob/`, exposed as `python3 python/cli.py bgjob {start,wait,status,reap}`. Stdlib-only, per repo convention.

### `bgjob start --step NAME --tmpdir DIR --budget-s N [--log-dir DIR] -- CMD [ARGS…]`

Runs as a short foreground call (&lt; 2s) from the step wrapper or orchestrator:

- Double-fork + `setsid` the real command into its own session/process group. The daemon is never a child of the Bash tool process, so the harness has nothing to track, notify about, or auto-background.
- Record in a registry entry (`~/.cache/larch/daemons/&lt;run-id&gt;-&lt;step&gt;.env`): PGID, PID **plus process start-time identity** (never bare PID — #6213 lesson: PID wraparound), START_EPOCH, BUDGET_S, TMPDIR, CLONE_PATH, owning-session identity.
- Daemon stdout/stderr go to log files under `--log-dir` (default `$TMPDIR/bgjob/`). The daemon writes **nothing** to any harness-visible stream.
- On child exit: write `$TMPDIR/bgjob/&lt;step&gt;.result.env` atomically (`tmp` + `mv`) containing `BGJOB_RC`, `BGJOB_ELAPSED_S`, and the step's existing KV result block; then remove the registry entry. During the transition the daemon also keeps writing the step's existing terminal sentinel (e.g. `.completed/step-5-terminal`) so downstream routing is untouched; sentinel retirement is issue 2's audit.
- **Budget self-expiry (primary orphan containment)**: at `BUDGET_S`, kill own process group, write result with `BGJOB_RC=timeout`.
- **Dead-man switch (secondary)**: every 60s verify the owning session is alive (PID + start-time identity match); if gone for a 120s grace window, kill own group and write `BGJOB_RC=orphaned`.
- Print exactly one stdout line: `BGJOB_STATUS=STARTED STEP=&lt;name&gt; PGID=&lt;n&gt;`.

### `bgjob wait --step NAME --tmpdir DIR --max-wait-s 270`

Foreground call, invoked with Bash `timeout: 330000`:

- Poll the result file every 1–2s. Return immediately with `BGJOB_STATUS=DONE` + the full result KV block when it exists.
- Each poll cross-checks daemon liveness (PGID + identity): daemon gone with no result → return `BGJOB_STATUS=DEAD BGJOB_DIAG=…` immediately (include a redacted stderr-log tail), never hang.
- At `--max-wait-s` (270s), return `BGJOB_STATUS=WAIT ELAPSED_S=&lt;n&gt;`.
- Internal `SIGALRM` hard deadline at max-wait + 30s: a wedged wait can never outlive its own tool call. 270s &lt; 300s prompt-cache TTL &lt; 330s tool timeout &lt; 600s harness cap — auto-backgrounding is structurally unreachable (fact 1 above).
- Exit 0 for DONE/WAIT/DEAD (status is in stdout KV); exit 2 with `BGJOB_ERROR=…` only for internal invariant failures.

### `bgjob status` / `bgjob reap`

- `status`: list registry entries with liveness verdicts (for `/larch:status` and debugging).
- `reap`: kill + clean identity-verified orphans past budget or with dead owners (tertiary containment). Wire into `scripts/cleanup-sessionstart.sh` and `/cleanup`.

### Orchestrator contract (replaces the premature-notification recovery labyrinth)

One shared doc, proposed `skills/shared/bgjob-wait.md`, referenced by all migrated call sites:

&gt; Launch the step with `bgjob start` (foreground). Print the step breadcrumb. Then call `bgjob wait --max-wait-s 270` with `timeout: 330000` in a loop: on `WAIT`, call it again with no other tool call, no Read, and no prose in between; on `DONE`, parse the printed KV block and continue the step; on `DEAD`, route to the step's existing failure handling. Never launch the step with `run_in_background`, never use Monitor or TaskOutput for it, and never sleep between waits.

Optional cost refinement (decide in /design, not required for correctness): a cheap waiter-subagent mode where the orchestrator delegates the wait loop to a minimal foreground agent so chunk polls re-read a ~3k-token context instead of the orchestrator's full context. Direct-loop mode is the baseline and the fallback.

### Enforcement (prevents regression to run_in_background)

- New small PreToolUse hook (~80 lines, replaces nothing yet — issue 2 removes the old guards): deny any Bash call with `run_in_background: true` while a larch run is active in the owning clone. Unlike task-notifications, tool calls are reliably interceptable by hooks.
- Repurpose `lint bg-wait-coverage` into its inverse: fail if `run_in_background` appears in `skills/` outside an explicit allowlist doc. (Old lint retirement is issue 2.)
- Optional, documented for operators in `docs/configuration-and-permissions.md` (not forced by the plugin): `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` for dedicated autonomous runner sessions makes "no background task can exist" schema-level (fact 3). Must only be suggested once this migration is complete, and noting it also disables background subagents and Ctrl+B.
