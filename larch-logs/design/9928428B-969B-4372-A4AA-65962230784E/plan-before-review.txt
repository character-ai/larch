## Approach

Scope the fix to `/design` plan review only.

Add progress breadcrumbs inside `python/larch/review/plan_review_round.py::execute_round` for these sub-steps:

1. `launching reviewers`
2. `collecting reviewer outputs`
3. `aggregating reviewer findings`
4. `dispatching 3 voters`
5. `tallying votes`

Use the same side channel as the code-review path:

- import `progress_file`
- add `_progress_note(step, text)`
- call `progress_file.append_breadcrumb(Path.cwd(), "design", step, text)`
- ignore the boolean return value

Do not change `_emit(...)`, stdout `KEY=value` rows, status-line rendering, or progress-file format.

## Edge cases

- If panel dispatch fails, only `launching reviewers` should appear.
- If collection is skipped because the paths file is empty, `collecting reviewer outputs` should not appear unless the code actually enters collection.
- If aggregation fails, `dispatching 3 voters` and `tallying votes` should not appear.
- If voter dispatch fails, `tallying votes` should not appear.
- Breadcrumb append failure must stay silent.

## Failure modes

- Changing `_emit(...)` or printed stdout can break callers that parse `KEY=value`.
- Using skill label `implement` or step `5` would make `/design` status lines wrong.
- Adding changes to `/implement` or `/review` violates the resolved scope.
- A test that asserts every early-return branch can become brittle. Cover the normal sequence and rely on code placement for branch behavior.

If time is tight, at minimum run the targeted pytest file because this change is isolated to plan-review round behavior.
