Zero-turn typed-keyword progress hook (p/progress): UserPromptSubmit → skill/step-aware progress_report.py

Problem: /implement long-running phases (Step 5 review rounds, Step 8+ ship-pr) run for hours as single foreground Bash calls that the harness auto-backgrounds after ~10 minutes, after which all stdout ceases to appear in chat. The user has no visibility into progress (review rounds can each take 30-60+ min, round cap 5; CI watch can run for hours).

Goal: typed-keyword on-demand progress report served entirely harness-side — **zero model turns, zero API calls, zero context growth** — backed by a skill/step-aware report engine. The decisions below are settled with the operator; design should refine mechanics, not reopen them.

**Entry point — UserPromptSubmit hook (the only entry point; no `!` shell form, no PATH install):**

1. Thin bash shim `scripts/hook-progress-report.sh` registered for `UserPromptSubmit` in `hooks/hooks.json` (`type: command`, `${CLAUDE_PLUGIN_ROOT}`-anchored path — same shipping vehicle as the existing block-submodule-edit guard; hooks stay bash per the #3780 convention). It parses the harness stdin JSON (`prompt`, `cwd`, `session_id`, `transcript_path`) with at most one `jq` invocation, applies the trigger match, and only on match invokes the Python engine.
2. Trigger (settled): the submitted prompt, trimmed, **exactly** matches one of two verbatim lowercase entries: `p` or `progress`. Case-sensitive anchored exact match; anything else → instant silent exit 0 passthrough.
3. Match + live run found: run the engine and emit `{"decision": "block", "reason": "<report>"}` with exit 0. Documented UserPromptSubmit semantics: the prompt is blocked and erased, the reason is displayed to the user, and the model is never invoked.
4. Match + no live run: silent exit 0 passthrough — typing `p` outside a run reaches the model normally.
5. **Fail-open is critical**: any internal error → silent exit 0 passthrough. The hook runs on *every* prompt submission in *every* repo the plugin is loaded in: the no-match path must be a few milliseconds, and a defect must never block or alter normal prompts. The matched path may take ~1s (engine); the default 60s hook timeout is ample.

**Report engine — `python/progress_report.py` (skill- and step-aware):**

6. New stdlib-only module `python/progress_report.py` exposed as `python3 "${CLAUDE_PLUGIN_ROOT}/python/cli.py" progress report` (repo cli.py convention; aligns with the sh-to-py direction). The engine determines **which skill is live and which step it is in**, then dispatches to a per-(skill, step) renderer that constructs the progress-so-far report.
7. Live-run discovery (settled): session pointer files under `~/.cache/larch/sessions/` — the new /implement pointer (item 11) plus the existing `current-design-env-$PPID.sh` — selected by matching each pointer's recorded repo cwd against the hook's stdin `cwd` (unique per repo by the single-runner invariants), falling back to the newest pointer whose tmpdir still exists; no match → "no live run". Intentional side effect: typing `p` in a *second* claude session in the same repo also reports the run.
8. Step determination (settled: **derive-only for v1** — no new instrumentation in the long-running scripts): timing ledger (latest started step), `ship-pr-state.sh` (`PHASE=`), round staging dirs, `finalize-state.sh`. Within-round progress is also derived: `panel-manifest.ndjson` lists dispatched reviewer slots and the round dir accumulates collected outputs, enabling e.g. `round 2: 9/14 reviewers returned, 41m elapsed`. A component-written `progress.txt` liveness line is a future option, not v1.
9. v1 renderer registry (settled):
   - implement **Step 5 (flagship)**: liveness header (current round, within-round reviewer counts, elapsed, last-artifact mtime) + rounds-so-far table. The per-round data **already exists mid-run**: `round-meta.json` is flushed per round (`review-and-fix.sh` `flush_round_log_after_coder` → `larch-log.sh write-round`) into `$IMPLEMENT_TMPDIR/larch-logs/implement/$RUN_ID/round-<N>/` alongside `panel-manifest.ndjson` + `timing-ledger.tsv`. The table is produced by **shelling out to `scripts/render-review-phase-detail.sh`** (#3774, path fix #3794) for guaranteed parity with the final report; native Python rendering is deferred to the sh-to-py B3/C2 ports.
   - implement **Step 8+ (ship-pr)**: phase report from `ship-pr-state.sh` — current PHASE, PR number/URL, CI iteration/status.
   - **Generic fallback** (any other step): current step + start time + elapsed + last-artifact mtime.
   - **/design**: same dispatch architecture from day one, minimal v1 renderer (generic fallback keyed off the design pointer); richer /design renderers are follow-up work.

**Live-run pointer + done marker:**

10. /implement Step 0 writes a pointer file under `~/.cache/larch/sessions/` (PID-suffixed filename for cross-session uniqueness, twin of `current-design-env-$PPID.sh`) via the sanctioned `python/cli.py session` writer machinery — never prompt-side writes. Records `IMPLEMENT_TMPDIR`, the repo root cwd, and the skill kind; cleared at run teardown; stale pointers (tmpdir gone) are skipped by the engine and reaped by /cleanup.
11. `$IMPLEMENT_TMPDIR/progress/done` marker written when the Step 5 loop exits on any path — scoped to the Step 5 loop solely so the #3878 Monitor watcher can self-exit; run-level "done" is simply the pointer being cleared at teardown. Files only; the FD3 quiet contract (`scripts/lib-quiet.md`) is untouched.

**Discoverability:**

12. Print one line at run start and again at the Step 5 launch banner: `progress: type p (or progress) at any time`.

**Design-time verification items (explicit early checks — do these first):**

13. (a) Block-reason display fidelity and any length limit — the Step 5 report is ~50-80 plain-text lines; keep the layout plain/monospace-friendly and determine the truncation strategy if a limit exists. (b) Whether `UserPromptSubmit` fires at type-time or at delivery-time for a prompt typed while a model turn is mid-flight — if delivery-time, the report appears late in that narrow window (the common case — idle orchestrator awaiting a task-notification — is unaffected).

**Tests/lint:**

14. Offline hook harness (fixture stdin JSON: match → block JSON; no-match / no-pointer / internal-error → silent exit 0 passthrough), pytest coverage for `progress_report.py` (skill/step dispatch + renderers over fixture tmpdirs/staging dirs), Makefile target registration, Bash 3.2 + shellcheck for the hook, `make py-lint` / `py-test` green. Update `SECURITY.md` per editing rules (new always-on prompt-path hook surface).

**Decision record**: an earlier revision specified a `! r` shell-prefix entry point with a `~/.local/bin` launcher; it is **removed, not demoted to fallback** — the hook needs no install and adds zero context (the `!` form puts the report bytes into conversation context). A `?` trigger was considered and rejected (collides with genuine "?" prompts and TUI key handling). Do not resurrect either at design time.

**Prior art / anti-pattern guard (from /issue dedup pass)**: FD3 progress breadcrumbs (#2416) and the bash breadcrumb-monitor architecture (#2749) were deliberately ripped out (#3111, #3118) after incidents (#2996). This issue is file-artifact + read-side only and must not resurrect that machinery.
