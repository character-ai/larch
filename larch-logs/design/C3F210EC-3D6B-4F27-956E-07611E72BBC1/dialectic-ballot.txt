## Dialectic Ballot

You are a judge on a 3-panel adjudicating contested design decisions. For each `DECISION_N` below, read both Defense A and Defense B, then cast exactly one binary vote: `THESIS` or `ANTI_THESIS`. THESIS means the side labeled as defending the synthesis's CHOSEN option on that decision wins; ANTI_THESIS means the side defending the ALTERNATIVE option wins. Judge on argument quality — not on which defense "sounds more confident." Vote on every decision. Do not modify files.

The tool that produced each defense is hidden (Defense A / Defense B labels are anonymous). Which side defends CHOSEN vs. ALTERNATIVE is disclosed on each decision's header because that information is semantic, not tool-attributive.

### DECISION_1: Chat-bound display loop mechanism — Monitor tool vs foreground polling loop

Feature context: propagate breadcrumbs from long-running larch helper scripts to the user's main chat when the Claude Code harness randomly backgrounds them. Round 1 binding: flip 9 currently-foreground-required scripts to always-background + propagate (BASH_AUTHORING.md §4 retired/repurposed); inline display in chat; nested-script transparency; redaction via redact-secrets.sh; model-actionable structured format; preserve lib-quiet.sh FD-3 contract.

Defense A (defends CHOSEN — Monitor tool for near-real-time per-line streaming; completion via background Bash <task-notification>):
<defense_content>
The foreground polling loop is easier to reason about because Bash owns the tail state, sentinel, sleep cadence, and final flush in one portable process. It also avoids betting on Monitor behavior for an actively appended file, which is less directly proven in this repository.

Monitor should be the chat-bound breadcrumb display path, with Bash task notification reserved for completion, because the repository already distinguishes log/event streaming from completion watching.

AGENTS.md explicitly says not to use Monitor or polling loops to watch a background job finish, but then carves out Monitor for "logs, external polling, or event streams" at AGENTS.md:56. BASH_AUTHORING.md makes the same distinction: Family B foreground rules protect completion coupling, while "Monitor-style tailing of external logs" is out of scope at BASH_AUTHORING.md:52-56. `emit_breadcrumb` already provides a gated breadcrumb stream and FD routing in scripts/lib-quiet.sh:114-124, so a redacted breadcrumb file is a log/event stream, not the completion mechanism.

The polling loop is the more mechanically predictable implementation: it can be tested with ordinary Bash 3.2 semantics and does not depend on Monitor correctly following appended lines in near real time.

That predictability solves the wrong layer: a sleep loop occupies a foreground Bash call for the whole run and reintroduces the same class of runner-watching machinery AGENTS.md warns against, while Monitor can be limited to streaming already-redacted breadcrumb records and leave terminal status to the existing task notification.

If Monitor cannot reliably stream append-only breadcrumb files, users will see stale or missing progress during long helper runs, and the design will need a fallback tail harness with explicit flush, dedupe, and completion reconciliation.
</defense_content>

Defense B (defends ALTERNATIVE — foreground bash "until DONE_SENTINEL; sleep 30; emit-new-lines" polling loop with trap EXIT sentinel installed via larch_quiet_install_done_sentinel):
<defense_content>
Monitor has the cleanest UX target: if breadcrumbs are an event stream, AGENTS.md explicitly leaves Monitor available for logs and event streams, and it can display lines with less artificial delay than a 30-second loop. Keeping completion on the existing background task notification also avoids making the tailer responsible for process lifecycle.

Ship the foreground polling loop because it satisfies the current breadcrumb requirement with ordinary Bash, existing quiet-stream contracts, and fewer new tool semantics than validating Monitor as a file-streaming substrate.

`scripts/lib-quiet.sh:114`-`120` already routes `emit_breadcrumb` either to `LARCH_QUIET_BREADCRUMB_FD` or to caller-visible output, and `scripts/lib-quiet.md:20`-`25` documents that inherited FD path for nested visibility. `AGENTS.md:56` permits Monitor for logs/event streams but also warns against using Monitor or a Bash polling loop to watch completion; the polling design can respect that by using `<task-notification>` for completion and the sentinel only to stop the display loop. `skills/implement/SKILL.md:1611` already sanctions an in-turn foreground 30-second sleep retry, showing the runtime model is accepted when scoped.

The best opposing point is latency: Monitor better matches "ideally, instantly," while a sleep-based loop can show breadcrumbs up to 30 seconds late and occupies a foreground Bash call for the duration.

That latency is a bounded UX cost, not architectural necessity; the repo already values turn-coupled Bash behavior heavily, while Monitor would require proving active file-follow semantics, redaction ordering, cancellation, and nested propagation under a less documented path.

If polling loses, the feature may work faster but ship a broader, less verified orchestration surface; if Monitor behaves differently under appended redacted files, breadcrumbs can silently disappear or require another design pass.
</defense_content>

### DECISION_2: Wrapper shape — single foreground wrapper vs explicit skill-level pairing

Feature context: same — 9 denylisted scripts flipped to always-background + propagate. This decision concerns where the background/foreground boundary lives.

Defense A (defends ALTERNATIVE — single scripts/run-with-breadcrumbs.sh wrapper that the skill always calls foreground; the wrapper internally backgrounds the long script and streams the redacted breadcrumb file out on its own stdout):
<defense_content>
Explicit pairing makes the orchestration topology visible in SKILL.md: the long task is visibly backgrounded and the paired foreground consumer is visibly what preserves turn coupling. It also gives lint a direct invariant to enforce at authoring time.

Ship the single foreground wrapper because it preserves the current foreground contract while avoiding new two-call boilerplate and a harder cross-call structural lint.

BASH_AUTHORING.md:52-54 says the load-bearing requirement is foreground completion coupling, ordered breadcrumbs/stdout/stderr, and avoiding asynchronous task notifications after the model ends the turn; a foreground `run-with-breadcrumbs.sh` satisfies that from the skill author's perspective. The repo already has the internal-background wrapper pattern: scripts/run-external-agent.sh:143-155 writes a sentinel on exit, scripts/run-external-agent.sh:205-213 launches the child in the background, and scripts/run-external-agent.sh:217-238 polls it while the wrapper itself remains the foreground call.

The best opposing point is that explicit pairing makes the hidden background process obvious to a SKILL.md reader and can force authors to acknowledge the live stream consumer beside every long-running launch.

That visibility is not worth duplicating orchestration at every callsite: scripts/lint-foreground-markers.sh:18-28 already centralizes the denylist, and scripts/lint-foreground-markers.sh:294-303 already enforces a per-anchor authoring rule, so requiring one blessed wrapper invocation is simpler than teaching lint same-message pairing semantics across launch and consumer calls.

If the wrapper abstraction is wrong, failures concentrate in one script and can obscure which child process or breadcrumb stream broke, while explicit pairing would expose those pieces in the skill transcript.
</defense_content>

Defense B (defends CHOSEN — explicit skill-level pairing: skill issues run_in_background:true for the long script, then immediately issues a foreground consumption call in the same message; enforced as a structural invariant by repurposed lint):
<defense_content>
The single-wrapper approach gives skill authors one stable foreground command while centralizing sentinel files, exit-code propagation, redaction, and breadcrumb streaming in one tested script. That reduces repeated callsite ceremony and may make operational behavior more uniform.

Explicit background launch plus immediate foreground breadcrumb consumption should ship because the bg/fg contract is an orchestrator-level invariant, not merely a shell implementation detail.

The existing lint already proves this repository enforces orchestration shape in Markdown: `scripts/lint-foreground-markers.sh:62-69` enumerates skill/rule authoring files, `scripts/lint-foreground-markers.sh:294-302` flags denylisted script anchors missing required nearby structure, and `BASH_AUTHORING.md:52-54` ties that structure to turn-boundary correctness. `skills/implement/SKILL.md:1018-1031` shows the current contract is readable at the callsite, including the script invocation and the operational rule around backgrounding.

The wrapper's strongest point is real: centralized code is easier to test for redaction, sentinel cleanup, nested exit propagation, and stderr-tail failure UX than repeating paired launch/consume blocks across several skill files.

That centralization does not justify hiding topology from the only layer that can accidentally end the turn early: the orchestrator prompt. Since the existing linter already detects script anchors and nearby structural requirements, repurposing it to require "launch plus paired consumer" keeps violations visible in the same surface where authors create them.

If explicit pairing loses to the wrapper, SKILL.md readers and structural lint mostly see a foreground wrapper call while the true background lifecycle moves into an implementation file, making it easier for future edits to bypass or misunderstand breadcrumb consumption and completion coupling.
</defense_content>
