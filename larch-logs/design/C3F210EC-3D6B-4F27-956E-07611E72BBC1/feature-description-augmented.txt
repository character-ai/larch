# Feature: Propagate breadcrumbs from long-running helper scripts back to the calling skill (periodically or, ideally, instantly)

## Original issue (character-ai/larch #2749)

Skills such as /implement and /design rely on helper scripts that take a long time. They are carefully designed to be mostly silent (to avoid voluminous stdout from bloating main agent context), but they emit periodic breadcrumb messages on stdout, so the caller can be updated with some reasonable frequency with where the script is at.

Despite valiant efforts to prevent claude harness from backgrounding these scripts, due to a known existing bug in claude harness, it randomly backgrounds these. The difference between them running in foreground and background is that in foreground the breadcrumbs are shown in real time by the harness (grayed out and in a tiny window, but still), whereas in background they stay completely silent. Since it's impossible (until claude code issue is fixed) to prevent this backgrounding, we have to come up with a way to mitigate it, so the user sees breadcrumbs, if not immediately, at least with some periodic refresh. These helper scripts can run >> 10 minutes.

Tools we have:
1) The script is run from inside a skill launched by claude code harness, so the harness may have instruments that could be used to "pipe" the stdout of the process to the chat
2) The script stdout is redirected to a file in a temp directory (for subsequent run logs flushing), so the breadcrumbs do get logged there in real time
3) We instruct claude to always background these scripts (which it does provide mechanism for), instead of trying to (unsuccessfully) to direct it to NEVER do so, and set up a timer wherein periodically, say, once a minute or once/30 seconds, we check the log file of the script, and everything that we did not display last time that got added to the tail since then we grab and display for user in the chat. This wait loop should be terminated, of course, once the script exits, successfully or not. I like this approach the least, because I have bad experience with claude harness timers (they tend to hang around and not be very reliable), but I suspect this may be our only resort.

Brainstorming a solution is needed here as the first step.

## User-resolved scope constraints (Round 1 — binding for the design)

1. **Coverage**: Broad. Apply uniformly to all long-running larch scripts (the codebase has 209 scripts sourcing `scripts/lib-quiet.sh` and 19 emitting via `emit_breadcrumb`). Prefer a shared mechanism, not per-skill custom code.

2. **Latency target**: Open — the design may pick either near-real-time per-line streaming or periodic batch (~30-60s). Trade off reliability vs immediacy.

3. **Display target**: Inline in the main chat transcript (visible in conversation scrollback). NOT a side-channel-only solution. Side channels may be additive but cannot replace inline chat output.

4. **Foreground duplication**: When a script does happen to run in foreground (and the harness already streams its FD-3 lines inline as gray text), the propagation layer MUST NOT re-print the same lines into the main chat — avoid double output.

5. **Foreground-marker contract for the 9 denylisted scripts (BASH_AUTHORING.md §4)**: **FLIP to always-background + propagate.** The 9 scripts currently lint-required to be launched foreground (ship-pr.sh, ci-wait.sh, collect-agent-results.sh, dispatch-plan-voters.sh, dispatch-with-waterfall.sh, run-step5-review.sh, run-step2-dispatch.sh, step2-implement.sh, review-and-fix.sh) are explicitly retired from the foreground-only contract. The propagation layer becomes authoritative. `scripts/lint-foreground-markers.sh`, the `**⚠ Foreground required**` banners, the `# Foreground required: see BASH_AUTHORING.md §4` comment markers, and BASH_AUTHORING.md §4 itself are all in-scope for retirement or repurposing as part of this design.

6. **Failure UX**: On non-zero exit, propagate the exit code AND a stderr/log tail (last N lines, e.g., 20-40) into the main chat. Do not leave failure surfacing to the harness task notification alone.

7. **Refactor budget**: Maximum. SKILL.md / orchestrator code, `lib-quiet.sh`, the 9 denylisted scripts, and new helper scripts are ALL in-scope for modification.

8. **Model-actionable propagation**: The breadcrumb format should be **deliberately model-actionable** — Claude (the assistant orchestrator) should be able to recognize patterns (e.g., stuck > N minutes on phase X, repeated retry failures) and take adaptive action (cancel, retry, escalate). Reactive-policy surface is in-scope.

9. **Nested-script propagation**: Transparent at any depth. When `plan-review-loop.sh` calls `dispatch-plan-review-panel.sh` which calls Cursor/Codex launchers, breadcrumbs from inner scripts must bubble up to the user's chat. Likely threads via `LARCH_QUIET_BREADCRUMB_FD` or a shared log.

## Implicit hard constraints (from codebase exploration)

- `lib-quiet.sh` FD-3 machine-readable stdout contract (callers parse `KEY=VALUE`, `STATUS=`, `EXIT_CODE=` lines) must continue to work. `emit_kv`/`emit` are unchanged in behavior.
- Existing `emit_breadcrumb`, `LARCH_QUIET_BREADCRUMBS=1`, `LARCH_QUIET_BREADCRUMB_FD` opt-in surface remain functional (additive evolution, not replacement).
- Harness primitives available: `Bash` `run_in_background: true`, `Monitor` (endorsed by AGENTS.md for "logs, external polling, or event streams"), `ScheduleWakeup` (user reluctant — flaky in their experience).
- Bash 3.2 portability (BASH_AUTHORING.md §3) applies to any new shell scripts.
- Output redaction (`scripts/redact-secrets.sh`) must apply to anything propagated to chat that may contain secrets.

## Out of scope

- Fixing the upstream Claude Code harness backgrounding bug itself.
- Replacing the `lib-quiet.sh` FD-3 / `emit_kv` contract.
- Side-channel-only displays (must be inline-in-chat at minimum).
