## Findings

### 1. Per-coder loop missing explicit return semantics (correctness)

The plan restructures `apply_findings_with_coder` into a Cursor→Codex loop. It states outcomes clearly, but only the **no-changes** branch uses the word **return**:

```234:247:<TMPDIR>/plan.txt
- For each attempt:
  ...
  - On `False`: if cleanup fails, `_finalize_failed_cleanup` then `CoderResult(2, ...)`; else continue.
  ...
  - **No-changes**: when `_collect_round_stage_paths(round_dir)` is empty, return `CoderResult(0, tool, "no-changes", ...)`.
  - When `round_num > 0` and stage paths non-empty: `_stage_and_commit_round`; on empty commit sha, cleanup and continue waterfall.
  - On success: `CoderResult(0, tool, "applied", ..., commit_sha)`.
- After all attempts exhausted cleanly: `CoderResult(4, "none", "main-agent-required", ...)`.
```

**Applied**, **rc=2 cleanup failure**, and **rc=3 submodule-violation** do not say **return**. Without that, a literal reading lets the loop continue after a successful Cursor commit and run Codex on an already-mutated tree. That would regress the core bug fix and violate the outline goal that commit failure should fall through only after cleanup, not after success.

**Suggested revision:** Add one bullet: return immediately from the loop on `applied`, `no-changes`, rc=2 (post-`_finalize_failed_cleanup`), and rc=3; only failed edit/commit paths with verified cleanup may `continue`.
