## Findings

### 1. Step 5c orchestrator will mis-route the new refusal (major, correctness)

The plan returns `publish_rc=4` and targets Gate C re-entry, but the live contract in `skills/design/references/finalize-step5.md:88` and `skills/design/SKILL.md:648-650` only special-case oversize refusals before the review-provenance branch. Anything else with `VALIDATE_STATUS=defects-found` and an empty `VALIDATE_LOG_FILE` is treated as review-provenance failure and sends the operator back to Step 3, not Gate C.

If the implementer avoids `defects-found` to dodge that branch, `VALIDATE_STATUS=ok` skips review-provenance and falls into `validator-autofix` on `composed-plan.md` (`skills/design/references/validator-failure.md:13-20`). That is also wrong for a missing Gate C artifact.

The plan lists `approval-gates.md` as MAY_UPDATE only. The required fix is firm updates to `finalize-step5.md` and `SKILL.md` with a `PUBLISH_REFUSE_REASON=missing-guideline-assessment` branch modeled on the oversize special case.

### 2. Refusal emitter must not reuse `_emit_publish_refusal` (major, correctness)

```390:410:python/larch/design/design_publish.py
def _emit_publish_refusal(*, reason: str, kvs: list[tuple[str, str]], result_env: Path) -> None:
    ...
        _replace_kv(rows=kvs, key="PUBLISH_REFUSE_REASON", value=reason)
    kvs[1] = ("VALIDATE_STATUS", "defects-found")
    kvs[2] = ("VALIDATE_DEFECT_COUNT", "1")
```

The plan’s KV list does not define `VALIDATE_STATUS` behavior. Reusing this helper guarantees collision with existing Step 5c special cases. A dedicated refusal path should emit the `ARCH_GUIDE_*` rows, set `PUBLISH_REFUSE_REASON=missing-guideline-assessment`, write `.design-publish-result.env`, print a Gate C re-entry warning, and return `4` before `redact` / `named-block write` (currently at `design_publish.py:867-895`).

Note: `design_step5c.py:642-645` captures publish stdout to a temp file; the operator-visible message must come from the SKILL/finalize prompt body, not only a `publish_core` print.

### 3. Run-log completeness needs an explicit approved filter (minor, correctness)


`_design_publish_reached` only checks that `final-summary.md` exists (`run_log_manifest.py:418-427`). The plan requires the assessment only for approved runs, but the `_required_design_artifacts` section does not pin how to detect `: approved` in the summary heading. Tests mention non-approved exemption; the implementation section should require the same explicit check to avoid false completeness failures on `failed-plan-write` or cancelled runs that still flushed a summary.

## What the plan gets right

- **Gate placement in `publish_core`**: After validation (`design_publish.py:822-865`) and before redaction/plan-block write/rename/log-publish (`867+`) matches the irreversible-action boundary.
- **Degraded path hook**: `design_log_publish_flow.py:644-649` calls `_render_final_summary_before_copy` before tree copy; inserting a check for `outcome == "approved"` there covers direct/resume log-publish (`design_terminal.py:993-1020`) while pause/clarify paths pass non-approved outcomes.
- **Absent/invalid guidelines**: `read_guidelines()` returns `absent`/`invalid` without requiring an artifact (`architectural_guidelines.py:338-353`, `persist_design_assessment` at `1813-1817`); the plan’s `required=false` for those statuses aligns.
