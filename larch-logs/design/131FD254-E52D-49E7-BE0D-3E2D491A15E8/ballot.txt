# Ballot — Plan Review for Issue #2683

Plan under review: `$DESIGN_TMPDIR/plan.txt` (the implementation plan
written by Step 2b and updated mid-design to add large-plan summary
mode). Vote YES / NO / EXONERATE on each finding. Use the
proportionality rubric (EXONERATE when the concern is legitimate but
the proposed change introduces more complexity than the issue
warrants).

The plan itself targets only two files: `skills/design/SKILL.md` (new
Step 3 entry print + tightened Step 4b body) and
`skills/design/references/approval-gates.md` (strengthened Gate C
Presentation + Prompt sections). The plan introduces a sentinel file
`$DESIGN_TMPDIR/.step3-entry-plan-printed` for first-time-only gating
and an env var `LARCH_DESIGN_PLAN_SUMMARY_THRESHOLD` (default 120) for
the large-plan summary mode.

### FINDING_1: Asymmetric enforcement — Step 3 has Bash, Gate C has prose
- **Concern**: The plan adds a mechanical fenced Bash block at Step 3 entry that emits `## Plan Candidate for Review` and applies the threshold/outline logic deterministically. Gate C, however, stays prose-only ("**MUST** read and print..." in `SKILL.md` Step 4b + strengthened wording in `approval-gates.md`). Reviewers (12 across both vendors and all five static archetypes) flag this asymmetry as drift-prone: the threshold/outline/bold-note logic can diverge between the two sites, or Gate C can still be skipped by an inattentive executor despite the MUST language.
- **Proposed resolution**: Add a parallel fenced Bash block in SKILL.md Step 4b immediately before the Gate C AskUserQuestion that emits `## Final Design Plan` and applies the same threshold/outline logic as Step 3 (header literal differs; no sentinel because Gate C re-prints on every entry). Keep `approval-gates.md` as the prose normative source for the contract; Step 4b's Bash block is the mechanical enforcement of that contract.

### FINDING_2: Numeric threshold guard missing from canonical Bash snippet
- **Concern**: The plan's Approach section shows a Bash block that uses `_summary_threshold="${LARCH_DESIGN_PLAN_SUMMARY_THRESHOLD:-120}"` followed immediately by `[ "$_plan_lines" -gt "$_summary_threshold" ]`. The Edge cases section promises a `case "$_summary_threshold" in (''|*[!0-9]*) _summary_threshold=120 ;; esac` guard for non-numeric env values, but that guard does not appear in the canonical fenced block. An implementer copy-pasting the Approach block ships without the guard and a non-numeric env var triggers a Bash arithmetic abort.
- **Proposed resolution**: Inline the `case "$_summary_threshold" in (''|*[!0-9]*|0) _summary_threshold=120 ;; esac` guard (including `0` as invalid per FINDING_16's concern) directly inside the canonical fenced block in both the Step 3 entry block and the new Step 4b block. Remove duplication between Approach and Edge cases — the Bash snippet IS the contract.

### FINDING_3: approval-gates.md "exactly three options" conflicts with Other opt-in
- **Concern**: `approval-gates.md` Gate C Prompt section says "`AskUserQuestion` with exactly three options" but the new design relies on the `Other` free-form path for full-plan retrieval. Implementers reading the existing normative line may strip `Other` to comply with "exactly three options".
- **Proposed resolution**: Reword `approval-gates.md` Gate C Prompt section from "exactly three options" to "three primary options plus the host's standard `Other` free-form channel". Explicitly document that picking `Other` and requesting the full plan triggers `cat $DESIGN_TMPDIR/plan.txt` + re-fire of the same three-option AskUserQuestion; the three primary outcomes (Approve / Discuss / Re-run) are unchanged. Add one sentence noting that this Gate C `Other` behavior is distinct from the Step 0 tier gate's `Other` (which is a terminal cancel) — Gate C `Other` never cancels.

### FINDING_4: Step 3 large-plan opt-in is not actionable before reviewer launch
- **Concern**: The plan's Step 3 entry bold note tells users they can "ask to see the full plan if you wish" before voting begins. But Step 3 has no AskUserQuestion before reviewers launch — the orchestrator immediately proceeds to scout + dispatch under the anti-halt rule. A user reading a large-plan summary cannot reliably interrupt to request the full plan before 10+ reviewers begin reading the plan. Four reviewers (Codex-Arch, Cursor-Innovation, Cursor-Pragmatic, Codex-Requirements) flagged this.
- **Proposed resolution**: When the Step 3 entry summary mode fires (plan exceeds threshold), add a small **blocking** AskUserQuestion with exactly two options: **Begin review** (proceed to scout/dispatch with summary already displayed) and **Show full plan first** (orchestrator emits full `plan.txt` content under a `## Full Plan Candidate` header, then re-fires the same two-option prompt). The prompt fires ONLY when summary mode fires; small plans skip the prompt. Note: this prompt is at Step 3 entry only, not at Gate C — Gate C already has a 3-option AskUserQuestion that the user can answer with `Other` to request the full plan.

### FINDING_5: Step 3 bold note says "Other on next prompt" but Gate C is not next
- **Concern**: The plan's Step 3 entry bold note says "Reply 'show full plan' (or pick 'Other' on the next prompt and ask for it)". But the next prompt is not Gate C — Gate C is many sub-steps later (after voting, Gate B, arch diagram, rejected findings). The "Other on the next prompt" wording is misleading at Step 3.
- **Proposed resolution**: Rewrite the Step 3 entry bold note to reference only the blocking AskUserQuestion from FINDING_4 (if accepted), or only free-form "show full plan" interrupt language. Reserve `Other` wording for the Gate C bold note where `Other` is genuinely the next prompt.

### FINDING_6: DESIGN_TMPDIR unset guard missing in proposed Bash block
- **Concern**: The proposed Bash block starts with `[ -f ~/.cache/larch/sessions/current-design-env-$PPID.sh ] && source ...`. If the source file is missing (e.g., interrupted Step 0, stale session), `DESIGN_TMPDIR` is unset; the subsequent `[ ! -e "$DESIGN_TMPDIR/.step3-entry-plan-printed" ]`, `wc < "$DESIGN_TMPDIR/plan.txt"`, and `touch "$DESIGN_TMPDIR/.step3-entry-plan-printed"` all resolve to root-relative paths (`/.step3-entry-plan-printed`). 3 reviewers flagged.
- **Proposed resolution**: Immediately after the source prelude, add `if [ -z "${DESIGN_TMPDIR:-}" ] || [ ! -d "$DESIGN_TMPDIR" ]; then printf '%s\n' '**⚠ 3: DESIGN_TMPDIR missing or invalid; cannot present plan candidate for review**'; else ... fi` wrapping the rest of the block. Apply the same guard at the new Step 4b Bash block (if FINDING_1 is accepted).

### FINDING_7: touch exit status not checked
- **Concern**: `touch "$DESIGN_TMPDIR/.step3-entry-plan-printed"` is unconditional. Transient FS or permission errors silently leave no sentinel; every Step 3 re-entry re-prints the entire plan candidate (or the summary). This is latent — `touch` failures are rare but the cost of failure is high (re-print spam).
- **Proposed resolution**: Capture the `touch` exit status; on failure, print `**⚠ 3: sentinel write failed (touch exit N); plan candidate may re-print on Step 3 re-entry**` and continue. Document the fallback in the plan's Edge cases.

### FINDING_8: grep includes headers from fenced code blocks
- **Concern**: `grep -E '^#{2,3} ' "$DESIGN_TMPDIR/plan.txt"` matches H2/H3 lines anywhere in the file, including inside fenced code regions. A plan with a `## Example` heading inside an example markdown code block produces a misleading outline. 3 reviewers flagged.
- **Proposed resolution**: Either (a) document the limitation in the plan as acceptable best-effort behavior ("the outline is best-effort and may include headers from fenced code blocks"), or (b) use a small awk-based fence-aware extractor. Option (a) is simpler and matches the plan's "no new scripts" constraint; (b) is more correct.

### FINDING_9: Step 2b doesn't require H1/H2/H3 markdown structure
- **Concern**: The summary mode assumes a first-line title + H2/H3 outline. Step 2b's plan-writing instructions do not require Markdown headings — a plan written with bullets, bold labels, or plain paragraphs would produce an empty outline and the bold note alone, hiding almost all plan content. Latent because Step 2b plans currently produce headings in practice, but not enforced.
- **Proposed resolution**: When the outline grep returns zero lines, fall back to `head -n 30 "$DESIGN_TMPDIR/plan.txt"` so the user still gets meaningful content. Document the fallback in the contract. Do NOT tighten Step 2b — that would be a separate scope expansion.

### FINDING_10: Bold note prints absolute $DESIGN_TMPDIR/plan.txt paths
- **Concern**: The bold note interpolates `$DESIGN_TMPDIR/plan.txt`, which expands to `<OPERATOR_REPO_PATH>/larch/sessions/claude-design-...`. This leaks host username and cache layout into chat transcripts and any published design log artifacts. Latent security/privacy concern.
- **Proposed resolution**: Replace the absolute path with a relative reference like `the plan file in this run's $DESIGN_TMPDIR` (no expansion), since operators who care about the path can resolve `$DESIGN_TMPDIR` from the environment anyway. Keep the operator-facing breadcrumb path conventions unchanged elsewhere.

### FINDING_11: docs/configuration-and-permissions.md update missing for new env var
- **Concern**: AGENTS.md points at `docs/configuration-and-permissions.md` as the canonical env-var documentation surface (LARCH_PROBE_TTL_SECONDS, LARCH_CODEX_EFFORT, LARCH_TOKEN_RATE_PER_M live there). The plan introduces `LARCH_DESIGN_PLAN_SUMMARY_THRESHOLD` but explicitly says "no docs/ updates needed" and only mentions CHANGELOG.md. 8 reviewers flagged.
- **Proposed resolution**: Add `docs/configuration-and-permissions.md` to the Files-to-modify list. Document `LARCH_DESIGN_PLAN_SUMMARY_THRESHOLD`: default `120`, positive-integer semantics (0 or non-numeric falls back to 120), strict greater-than line comparison, scope (both Step 3 entry and Gate C presentation). Update the plan's Documentation impact section to reflect this.

### FINDING_12: CHANGELOG.md missing from Files-to-modify
- **Concern**: The plan's Documentation impact section mandates a CHANGELOG.md PATCH entry for the new env var, but the Files-to-modify section lists only two markdown files. An implementer following the file list can ship without the CHANGELOG entry. 7 reviewers flagged.
- **Proposed resolution**: Add `CHANGELOG.md` to Files-to-modify with the same one-line PATCH note already described in Documentation impact.

### FINDING_13: Dual-authority — Step 4b prose contradicts approval-gates.md
- **Concern**: The plan adds MUST-level Gate C print language directly to SKILL.md Step 4b while also adding the `Other` → cat → re-fire loop to approval-gates.md. Two co-normative authorities for the same Gate C behavior can drift; an implementer reading only Step 4b sees "emit summary + 3-option prompt" with no Other handling, while approval-gates.md says "Other triggers full plan + re-prompt". 1 reviewer (Codex-dyn-dual-authority) flagged but high-impact.
- **Proposed resolution**: Keep SKILL.md Step 4b as a brief delegation ("Execute the Gate C body in `approval-gates.md` — the executor MUST emit `$DESIGN_TMPDIR/plan.txt` under `## Final Design Plan` (or the summary form for large plans) before firing the AskUserQuestion. See `approval-gates.md` for the full Other handling.") with the mechanical Bash block from FINDING_1. Make `approval-gates.md` the single normative source for Gate C behavior (Presentation, Prompt, Other-handling, large-plan summary mode).

### FINDING_14: PATCH classification rationale wrong (docs/scripts-only vs skills/ runtime)
- **Concern**: The plan cites "docs/scripts-only → PATCH" from AGENTS.md, but `skills/design/SKILL.md` is part of the runtime surface defined in AGENTS.md. The PATCH classification is still correct under `.claude/skills/bump-version/SKILL.md`'s "default for everything else" rule (no SKILL.md added/deleted/renamed; no description/name/argument-hint change), but the cited rationale is wrong.
- **Proposed resolution**: Revise the CHANGELOG section in the plan to cite the correct rationale: PATCH under the default-for-existing-skills-edits rule, not the docs/scripts-only rule.

### FINDING_15: Sentinel persists across Step 6 cleanup-skipped preservation paths
- **Concern**: The plan claims "Step 6 cleanup removes the sentinel implicitly", but Step 6 has skip conditions (plan-block-write failure, publish failure, standalone-heavy failure). On preserved-tmpdir paths, the sentinel stays in `$DESIGN_TMPDIR/.step3-entry-plan-printed`. Operators retrying within the preserved tmpdir do not see the Step 3 entry re-print.
- **Proposed resolution**: Update the plan's Edge cases section to describe the preservation paths explicitly: "On Step 6 cleanup-skipped paths (plan-block-write failure, publish failure, standalone-heavy failure), the sentinel persists with the preserved tmpdir. Operators retrying from the same `$DESIGN_TMPDIR` should `rm -f "$DESIGN_TMPDIR/.step3-entry-plan-printed"` first if they want the Step 3 entry re-print to fire again." No code change needed.

### FINDING_16: Threshold guard should reject 0 too
- **Concern**: The `case "$_summary_threshold" in (''|*[!0-9]*)` pattern accepts `0`. A 0 threshold makes every plan summarize (since `wc -l` is always ≥ 0), which silently hides all plan content. Latent UX issue.
- **Proposed resolution**: Treat `0` as invalid: extend the pattern to `case "$_summary_threshold" in (''|0|*[!0-9]*) _summary_threshold=120 ;; esac`. Folded into FINDING_2's proposed resolution.

### FINDING_17: Testing strategy lacks non-numeric threshold test
- **Concern**: The plan's Testing strategy section covers low (10) and high (999999) numeric values but not invalid values. The non-numeric guard from FINDING_2 needs a corresponding test.
- **Proposed resolution**: Add to Testing strategy: "Set `LARCH_DESIGN_PLAN_SUMMARY_THRESHOLD=abc` and run `/design` on any plan; verify the summary mode either falls back to the 120 default (no Bash arithmetic error) or is bypassed entirely. Verify the warning if any is printed."
