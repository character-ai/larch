### Item 14 — design/implement secret-rotation warning inert because run-log commit emits `SECRET_SCRUB_VIOLATIONS=0`
- **Location**: `python/run_logs.py` `_commit_run` (~L2167, the existing `WARN: larch-log flush scrubbed secret-shaped values` check); `python/design_publish.py` rotate warning; `python/design_log_publish_flow.py` `log_publish_main`; `python/redact.py` `main_scrub_log_secrets`
- **Source**: #4799 (Main agent; auto-filed per policy). Phase: implement.
- **Severity**: latent (risk-integration)
- **Description**: `python/run_logs.py` `_commit_run` initializes `violations = 0` and never reassigns it, so every `run-log commit` emits `SECRET_SCRUB_VIOLATIONS=0`. The operator secret-rotation warning is therefore currently inert on BOTH the implement path (`run_logs.py` ~L2167, the existing `WARN: larch-log flush scrubbed secret-shaped values` check) and the design publish path restored in #4782 (`design_publish.py` rotate warning, fed by `design_log_publish_flow.py` `log_publish_main`). The design path additionally pre-redacts each file via `redact secrets` in `_copy_tree_redacted` before `run-log commit`, so even if `_commit_run` counted, the post-redaction tree would report 0. The real violation counter (`scrub_log_directory` producing `LARCH_SECRET_SCRUB_VIOLATIONS`) lives in `redact.py` `main_scrub_log_secrets` and is not wired into `_commit_run`. Suggested fix: thread the real scrub-violation count from `_copy_tree_to_repo` / `_scrub_run_tree` (or a dedicated `redact scrub-log-secrets` pass) into `_commit_run`'s `SECRET_SCRUB_VIOLATIONS=` output so both warnings fire when a secret is scrubbed; alternatively, if the count is intentionally vestigial (gitleaks-in-CI is the real gate per #3379 / #3380), document that and drop the inert warnings. Out of scope for #4782, which is scoped to the two design publish files and must not modify `run_logs.py` or the implement path.
