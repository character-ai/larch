# [BUG] (URGENT) /combine-issues --oos closes 0 sources when blockers are closed

## Summary

In the `/combine-issues --oos` dependency-inheritance phase, an inherited `blocked_by` edge whose **blocker issue is closed** is classified as `unknown`, which marks the contributing source issue **ineligible for closure**. Because a closed blocker can never reappear in `list-open`, the oos-6c refresh cannot reclassify it. A single satisfied (closed) dependency therefore permanently blocks that source's closure. When every consumed source happens to inherit such an edge, the run **closes zero sources while still creating the combined issues** — a net **increase** in open-issue count that inverts the skill's entire purpose.

This is fail-closed behavior applied to a case where the dependency is already **satisfied** (the blocker is done), not genuinely unresolved.

## Impact

- **Severity**: important. A correct, fully-approved combine run can silently close nothing and leave more open issues than it started with.
- **Observed live (2026-06-14)**: combining 16 `[OOS]` issues into 3 (#4301, #4302, #4303). `plan-inherited` returned **12 unknown edges, all pointing at closed `[DONE]` blockers** (11 distinct: #4068, #4069, #4213, #4216, #4217, #4234, #4237, #4243, #4256, #4268, #4277). `per_source_initial_eligibility` marked **all 14 sources** ineligible with `unknown_inherited_classification`. Strict execution would have produced **3 new combined issues + 16 still-open sources = 19 open** vs. the 16 we started with. The run only completed correctly because the operator manually verified each blocker was closed and filtered those moot edges out of the deps input.

## Reproduction

1. Have an open issue `S` with a native `blocked_by` edge to another issue `B`, where `B` is **closed**.
2. Run `/combine-issues --oos` so `S` is consumed into a combined issue.
3. `fetch-deps` reports `S.blocked_by = [B]` (it does not filter by state).
4. `plan-inherited` classifies edge `(combined, B)` as `unknown` ("missing issue metadata"), so `S` is ineligible.
5. `list-open` refresh (oos-6c) does not include `B` (it is closed), so the edge stays `unknown`.
6. `close-eligible` keeps `S` ineligible; `close-sources` never closes it.

## Root cause (precise)

File: `python/combine_issues.py`.

1. **`_metadata(open_rows, combined_rows)`** (def at line 313) builds the lookup `meta` from **`combined_rows + open_rows` only**. `open_rows` come from `combine-issues list-open`, which calls `gh api repos/{repo}/issues?state=open` (`list_open_main`, ~line 632) and filters to `state == open` (~line 647). **Closed issues are never in `meta`.**

2. **`_classify_edge(edge, meta, combined_oos)`** (def at line 338):
   - Lines 342-343: `if client_meta is None or blocker_meta is None: return "unknown", "missing issue metadata"`. A closed blocker is absent from `meta`, so `blocker_meta is None` → **this is the branch that fires** for closed blockers (matches the observed reason string).
   - Lines 346-347: `if str(blocker_meta.get("state") ...).lower() != "open": return "unknown", "blocker issue is not known open"`. Even if closed-blocker metadata *were* injected, this second guard would still force `unknown`. Both guards conspire to fail-closed on any non-open blocker.

3. **`plan_inherited_main`** (line 366): for each `unknown` edge it sets every contributing source `eligible = False` with reason `unknown_inherited_classification` (lines 436-440).

4. **`close_eligible_main`** (line 509): for each `unknown_edges` entry it appends `unknown_inherited_classification:<edge>` to each source's reasons (lines 568-573); any source with reasons becomes ineligible (lines 601-611).

5. **oos-6c refresh is structurally unable to help**: it re-runs `list-open` + `plan-inherited`, but closed blockers are never returned by an `state=open` query, so the blocker stays absent and the edge stays `unknown` indefinitely. The SKILL prose ("Keep unresolved and still-unknown inherited edges close-blocking") therefore traps closed-blocker edges as permanent close-blockers.

The conceptual defect: **a `blocked_by` edge to a closed issue is a *satisfied* dependency** (imposes no ordering constraint) and should be neither inherited (writing a `blocked_by` to a closed issue is pointless) nor treated as close-blocking. The code conflates "blocker closed → moot" with "blocker metadata unavailable → risky."

## Suggested fix (preferred: explicit `satisfied` bucket)

1. **Enrich blocker state in `plan_inherited_main`.** For blocker issue numbers referenced by `blocked_by`/`blocking` that are absent from `open_rows`, resolve their state once (a bounded `gh issue view <n> --json state,title` per missing blocker, or a single batched `gh api` call) and add them to `meta` with their real `state`. Keep it bounded and fail-open (a read failure stays `unknown`).

2. **Add a `satisfied` classification in `_classify_edge`.** When `blocker_meta` exists and `state` is `closed` (case-insensitive), return a new bucket `("satisfied", "blocker issue already closed (dependency satisfied)")` instead of `unknown`. Genuine missing metadata (read failure / transient) must still return `unknown` to preserve fail-closed safety.

3. **Emit `satisfied_edges` in the plan output** (a list parallel to `safe_edges`), and do **not** write them (like `safe` but skip the `add-blocked-by` call — writing a `blocked_by` edge to a closed issue is a no-op at best).

4. **In `close_eligible_main`, do not add a reason for `satisfied` edges.** A source whose only inherited complication is satisfied/closed blockers must be eligible.

5. **SKILL.md (oos-6 / oos-6c / oos-7) prose**: document the `satisfied` bucket so the prompt side no longer needs a manual closed-blocker workaround; state explicitly that satisfied (closed-blocker) edges are not written and not close-blocking, while genuinely-unknown edges remain close-blocking.

### Lighter alternative (if the team prefers minimal change)

Filter closed blockers at `fetch_deps_main` time: resolve each `blocked_by`/`blocking` target's state and drop the closed ones before they reach the planner (this is exactly the manual workaround used in the observed run). Simpler, but it loses the audit trail that a satisfied dependency existed and silently changes `fetch-deps` semantics.

## Tests to add (`python/test_combine_issues.py`)

- `plan-inherited`: a source whose `blocked_by` points at a **closed** issue → edge classified `satisfied` (not `unknown`); source stays eligible; edge absent from `safe_edges`/`exception_edges`/`unknown_edges`; present in new `satisfied_edges`.
- `close-eligible`: a source whose only inherited edge is `satisfied` → **eligible** (regression for the observed all-sources-ineligible failure).
- **Fail-closed regression guard**: a source whose blocker is genuinely unreadable (read failure, `read_ok=false` or unresolved state) stays `unknown` / ineligible — the closed-blocker fix must not weaken fail-closed handling of truly-unknown blockers.

## Additional work items discovered in the same run

These are separate gaps in the `/combine-issues --oos` machinery surfaced by the same live run. They can land in this issue or be split out; they share the dependency/closure surface with the primary bug.

### A. No sanctioned mechanism to close a fully-stale source issue (important)

The actuality check (oos-2) can mark **every** item of a source issue stale (already fixed). In this run that happened to #4253 and #4224 (both fully stale). The OOS closure path only closes sources that are **consumed into a combined issue** (`apply --defer-close --source-issues` + `close-sources`, which requires a combined host). A fully-stale issue contributes no items to any combined body, so:
- It cannot be listed in `close-sources` (no combined host owns it).
- Listing it in `apply --source-issues` would misrepresent that its (stale) content is preserved in the combined body, violating "NEVER discard actionable content from source issues."

There is no `combine-issues close-stale` verb. I worked around it with a direct `gh issue comment` + `gh issue close --reason "not planned"`, which bypasses the skill's helper layer. **Suggested fix**: add a `combine-issues close-stale --issues <csv> --reason <text> [--comment-file <path>]` verb (redaction-aware, mirroring `close-sources`), and document the all-items-stale branch in oos-2/oos-5 so the prompt side does not improvise raw `gh` calls.

### B. `fetch-deps` is blocker-state-blind (data half of the primary bug)

`fetch_deps_main` (`python/combine_issues.py`, def ~line 244) returns `blocked_by`/`blocking` issue numbers with no state annotation, so the planner cannot tell a live blocker from a satisfied (closed) one without a second lookup. Whichever layer owns the fix (`fetch-deps` annotating blocker `state`, or `plan-inherited` enriching it — see primary fix step 1), the state data must reach `_classify_edge`. **Suggested fix**: have `fetch-deps` emit each blocker's `state` (one batched `gh api` call), or drop closed-blocker references with a logged, audit-preserving note.

### C. oos-6c "refresh" cannot resolve closed-blocker unknowns; SKILL prose overstates it

The oos-6c step ("Refresh Inherited Unknowns") re-runs `list-open` + `plan-inherited` and is described as reclassifying previously-unknown edges. But `list-open` only ever returns open issues, so a closed-blocker edge stays `unknown` across every refresh — the refresh is structurally incapable of resolving the most common unknown cause. **Suggested fix**: once B/the primary fix lands (closed blockers → `satisfied`, not `unknown`), update `skills/combine-issues/SKILL.md` oos-6c prose to state plainly that the refresh resolves *combined-issue-metadata* races (newly created hosts), not closed-blocker edges, and that closed blockers are terminal-satisfied rather than terminal-unknown.

### D. `apply` does not emit a source→combined mapping (minor, ergonomics + correctness risk)

The dependency phases require `source-to-combined.json` and `combined-issues.json`, but `combine-issues apply` emits only `COMBINED_ISSUE` / `SOURCE_ISSUES` per call. The orchestrator must hand-assemble those JSON state files across multiple `apply` invocations, which is error-prone (a mis-keyed source→combined map silently corrupts inheritance and closure partitioning). **Suggested fix**: have `apply` emit a machine-readable mapping fragment (e.g. `SOURCE_TO_COMBINED_JSON_FRAGMENT={...}`) per invocation, or add a `combine-issues record-apply` helper that accumulates the state files, so the prompt side does not hand-build them.
