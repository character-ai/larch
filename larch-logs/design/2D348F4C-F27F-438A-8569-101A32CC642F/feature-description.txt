# [DESIGNING] ship-pr Recovery-depth asymmetry between run_ci_fix_vendor and the new ship-pr.sh recovery

Recovery-depth asymmetry between run_ci_fix_vendor and the new ship-pr.sh recovery waterfall paths. As implemented in #2395, the new run_recovery_waterfall hooks (run_checks_phase, run_pr_prep_phase, run_pr_create_phase, run_rebase_rebump non-bump conflicts) use a 3-tier cascade Cursor -> Codex -> Claude (one try per tier, with launch-claude-ci.sh as the third tier). The existing run_ci_fix_vendor (scripts/ship-pr.sh:1216-1307) continues to use only Cursor-or-Codex with 3 launch attempts and no Claude tier in the evaluate-failure loop. This is inconsistent recovery depth between the CI-eval path and the new stall waterfalls. Either (a) extend run_ci_fix_vendor to include a Claude tier when both vendor attempts exhaust, matching the new waterfall depth; or (b) document the asymmetry explicitly in scripts/ship-pr.md with a justification (likely: CI-fix work is a tight inner loop where Claude's higher per-call cost outweighs the marginal recovery benefit).
