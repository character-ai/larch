### Agreements / synthesis direction
1. **Inline 3-tier loop in `run_ci_fix_vendor`, NOT a call to `run_recovery_waterfall`.** The CI-fix verifier model is fundamentally different: vendor success is only the *handoff* into the existing post-success flow (`append-token-record.sh`, dirty-path capture, `run_checks_with_lint_fix_loop`, staging, commit, log refresh, push) which decides whether the phase really recovered. `run_recovery_waterfall` runs an in-tier verifier (`run-relevant-checks-captured.sh` or per-phase re-run). Mixing those two verifier semantics would muddy the model and risk regression in the post-success path that Round 1 declared must stay byte-identical.
2. **Tier ordering: Cursor → Codex → Claude.** Each tier with `--role fix`, identical argv (`--output`, `--run-id`, `--repo`, optional `--plan-file`, `--timeout 1800`). Break on first `rc=0` into the existing post-success flow at line 1244+. After all three fail, `return 1` (unchanged from today).

4. **Inter-tier rollback adopted narrowly**: between tier attempts, restore/remove only paths the failed tier dirtied (quoted `--` sentinel + `while read -r` loop), mirroring the post-#2395 waterfall safety style. Rationale: success should be attributable to the tier that returned success; the existing post-success dirty-path capture should only see the successful tier's changes plus lint-fix changes. The tradeoff (losing partial work from a failed tier) is correct for a recovery waterfall.
5. **`--failure-log` injection for every tier.** Source = the `gh-run-logs.sh` capture already written by `run_evaluate_failure` (the `failed_run` log) — this is the *primary* context that explains why CI failed. An optional lightweight `command -v claude` skip is acceptable only if `launch-claude-ci.sh` does not already fail cleanly. Crucially, Claude tier is NOT conditional on Cursor/Codex availability — it's always tried if its prior tiers failed.
