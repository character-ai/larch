# Implementation plan

confidence: high

## Approach

- Add `bgjob adapt` as an additive command. Do not convert step scripts or change assessment and ship token vocabularies.
- Reuse `JobSpec`, registry identity checks, daemon startup, result-env parsing, and atomic `larch.io` helpers.
- Resolve the adapter inputs from explicit flags and existing session environment defaults. Accept the child command after `--`.
- Serialize each run-and-step decision with a confined lock. Hold it through registry inspection and daemon startup so simultaneous calls cannot launch duplicate children.
- Implement this state machine:
  1. Return the existing result through the `BGJOB_STATUS=DONE` contract when a valid result env already exists.
  2. Start a new daemon when no registry entry exists.
  3. Clear malformed registry state before a fresh start.
  4. Re-attach to a valid, in-budget entry when `child_liveness(entry).live OR daemon_liveness(entry).live`. Emit `BGJOB_STATUS=STARTED STEP=<step> PGID=<pgid>`.
  5. Fail closed without unlinking or restarting when a valid, in-budget entry has no live child or daemon.
  6. Clear and restart an expired entry only when both recorded processes are dead. Fail closed if an expired entry still has a live recorded process.
- Document why OR is correct: the daemon may remain live while it finalizes a child result, and the child may remain observable during daemon transition or failure.
- Derive and validate the adapter merge-env path under the bgjob tmpdir. Reject symlinks and non-regular files. Initialize it with an atomic, mode-restricted write before a fresh launch.
- Add the adapter-owned child flags and merge-env path to the child argv. Rehydrate `CLAUDE_PLUGIN_ROOT` from persisted session state before daemon launch so the child inherits the runtime plugin root.
- Keep the user-facing entry point at `python3 python/cli.py`. Register the command in the canonical `python/larch/cli.py` dispatcher because `python/cli.py` is only a shim.

## Edge cases

- The daemon can outlive the child while it writes the final result. Treat that entry as live.
- A child can still validate while the daemon identity has disappeared. Treat that entry as live and re-attach.
- A result may appear between the first check and registry classification. Re-check it under the lock before clearing or failing.
- A registry row may be malformed, symlinked, expired, or replaced during inspection. Revalidate paths and identities at use time.
- A live expired process must not be silently orphaned or duplicated.
- Existing merge or result paths may be symlinks, directories, or other special files. Refuse them.
- Repeated calls must preserve the same STARTED or DONE wire grammar.

## Failure modes

- Fail closed when process identity cannot prove that a valid registry entry is safely reusable or safely stale.
- Do not unlink a valid dead entry merely to make the next launch succeed.
- Do not start a child if lock acquisition, plugin-root rehydration, merge-env initialization, or registry inspection fails.
- Preserve daemon startup errors as non-zero adapter failures with a machine-readable `BGJOB_ERROR`.
- Never signal a persisted PID or PGID from this new path.

## Testing strategy

- Run the new focused suite:
  - `python3 -m pytest python/tests/bgjob/test_bgjob_adapt.py`
- Run existing bgjob regression suites to detect wire or lifecycle regressions:
  - `python3 -m pytest python/tests/bgjob`
- Run the accepted Python checks:
  - `make py-lint`
  - `make py-test`
- Confirm existing step scripts remain byte-unchanged and still call `bgjob start`.
