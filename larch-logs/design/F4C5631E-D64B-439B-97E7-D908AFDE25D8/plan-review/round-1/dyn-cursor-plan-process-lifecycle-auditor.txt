## Findings

### 1. [correctness] Missing lock-guarded result re-check before launch

**Location:** `python/larch/bgjob/daemon.py:276-279` (existing hazard); plan state machine / edge cases (gap)

The plan’s edge case covers re-checking the result env under lock before **clearing or failing**, but not before **`start_daemon`**. Fresh launches always unlink the result file first:

```276:279:python/larch/bgjob/daemon.py
    result = model.result_env_path(tmpdir=spec.tmpdir, step=spec.step)
    result.parent.mkdir(parents=True, exist_ok=True)
    with contextlib.suppress(OSError):
        result.unlink()
```

If caller A probes “no result” outside the lock, then the job finishes and writes a result while A waits for the lock, A can still reach `start_daemon` and wipe that result while starting a duplicate child.

**Suggested revision:** Under the held per-run-and-step lock, re-read the result env immediately before stale clearing and before any call to `start_daemon`. Return `BGJOB_STATUS=DONE` when it is present and readable. Add a concurrency test for “result appears between first probe and locked start.”

---

### 2. [correctness] Merge-env init must not run on re-attach

**Location:** `python/larch/bgjob/adapt.py` (planned NEW module)

The approach limits merge-env initialization to fresh launch, but the module bullets do not branch-guard it. On OR-live re-attach (state 4), truncating merge env would destroy rows the live daemon still merges via `write_result` (`daemon.py:145`).

**Suggested revision:** Only atomically create/truncate merge env on the fresh-start branch. Skip merge-env mutation on DONE and re-attach paths. Test that a second OR-live invocation leaves merge-env content unchanged.

---

### 3. [correctness] Lock must block, not fail-fast

**Location:** `python/larch/implement/dispatch_step2.py:137-141` (counterpattern); planned `adapt.py` lock

The plan says “serialize” but does not require blocking acquisition. Non-blocking flock causes concurrent callers to error instead of waiting and re-attaching, which conflicts with acceptance (“re-attaches on a second call”).

**Suggested revision:** Use blocking `fcntl.flock(lock_fd, fcntl.LOCK_EX)` without `LOCK_NB`. Hold through registry classification and through `start_daemon` return. Concurrency test: second caller gets `STARTED`, not a lock failure.

---

### 4. [correctness] Re-attach PGID must come from validated child identity

**Location:** `python/larch/bgjob/daemon.py:317-358`

State 4 emits STARTED with PGID but does not specify the source. Fresh starts use the **child** PGID (`os.getpgid(child.pid)` at line 317, emitted at line 358). Using daemon PGID or a cached pre-lock value breaks wire parity.

**Suggested revision:** After lock acquisition, re-read the registry entry, re-run OR liveness at use time, and emit PGID from `entry.child.pgid`. Test the dead-daemon / live-child OR case explicitly (already listed in the plan’s test matrix; pin expected PGID source there).
