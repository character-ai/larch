## Approach

Implement a report-only, retroactive OOS reconciler in `python/analyze_issues.py`.

Keep `python/voting.py::classify_result` and live OOS scoring unchanged. Accepted OOS still earns provisional `+1` at vote time.

- Scan committed `larch-logs/{design,implement}/` evidence.
- Find filed OOS issue URLs and legacy issue-number references.
- Join each filed issue to the current GitHub issue dump fetched by `/analyze-issues`.
- Classify the issue fate.
- Report provisional points, fate-adjusted points, and docked counts per reviewer.

Use this fate policy:

- **Open issue**: keep provisional `+1`.
- **Closed by PR**: keep `+1` when `closedByPullRequestsReferences` is non-empty.
- **Closed unfixed**: dock to `0` when `stateReason` is `NOT_PLANNED`, or labels/body indicate wontfix or not planned.
- **Combined away**: dock to `0` when a combined-away marker or legacy `Combined into #N` close comment is present.
- **Closed ambiguous**: leave provisional and report as unknown, rather than docking without evidence.

Teach `/combine-issues` to write a durable combined-away marker in the close comment for future source closures. Preserve the human-readable `Combined into #<target>` text.

Suggested marker:

`<!-- larch:combined-away source=#<source> target=#<target> -->`

Keep the bulk `gh issue list` fetch lean. Add `stateReason` and `url` to the list JSON when supported. Do **not** bulk-fetch `comments` on the full issue list. After log evidence collection, dedupe filed OOS issue numbers and fetch close-comment / marker fields only for that candidate set via per-issue `gh issue view` (pattern from `python/issue_create.py`). Merge view results into an in-memory issue index keyed by number before fate classification. If targeted comment fetch fails for an issue, classify from `stateReason`, labels, and body first; treat combined-away as unknown unless another marker is present; record per-issue fetch failures in a degraded bucket and continue the overall `/analyze-issues` run.

### Stable ID normalization (implement join contract)

Production `oos-issues.ndjson` rows use artifact-prefixed stable ids from `oos_filer._stable_identifier` (e.g. `oos-accepted-review:OOS_1`, `oos-accepted-main-agent:OOS_1`, `oos-accepted-review:<16-char-hash>`). Same-run collisions are possible when multiple artifacts each carry `### OOS_1:` under different source keys, and when multiple rounds reuse the same heading id.

Reuse `oos_filer._stable_source_key` (Path.stem) and `_stable_identifier(title, body, source_key=...)` for hash alias generation. Do **not** delegate FINDING joins to unmodified `oos_filer._issue_covers_stable_id` alone; its `_bare_oos_suffix` matches only `OOS_\d+`.

Add analyze-local cover helpers (or a small shared public matcher in `oos_filer.py` if the implementer prefers one source of truth):

- `_bare_oos_item_suffix(stable_id) -> str | None` matching both `OOS_\d+` and `FINDING_\d+` after optional `source_key:` prefix.
- `_stable_ids_cover(issue_stable_id, block_lookup_keys) -> bool` applying source-key rules equivalent to `oos_filer._issue_covers_stable_id` but using the widened suffix matcher and block index keys below.

When indexing accepted markdown blocks, compute:

- `heading_id`: bare `OOS_N` or `FINDING_N` from the `###` heading.
- `canonical_stable_id`: `f"{source_key}:{heading_id}"` when heading id is present.
- `hash_stable_id`: `oos_filer._stable_identifier(title, body, source_key=source_key)` for ndjson hash joins.
- `artifact_relpath`: path relative to the run directory (e.g. `round-1/oos-accepted-review.md`).

Index each block under all of:

- namespaced heading key (`source_key:OOS_N` / `source_key:FINDING_N`);
- hash alias (`source_key:<digest>`);
- secondary bare heading suffix (`OOS_N` / `FINDING_N`) only for legacy lookup when source key is known on the ndjson side;
- round-qualified key `(artifact_relpath, heading_id)` for disambiguation.

When matching ndjson `Stable ID` lines to blocks, try hash alias, namespaced heading id, then widened cover logic. When a bare legacy id matches multiple same-run blocks across rounds or artifacts, do not pick arbitrarily: prefer the match whose `artifact_relpath` is cited in ndjson body/path evidence when present; otherwise mark reviewer attribution `unknown` and keep scoring by stable id / URL when possible, or skip with an `ambiguous_stable_id` bucket.

### Log evidence model

Evidence collection is run-scoped for implement logs and design-run-scoped for design logs.

1. **Per run directory** under `log_root/{design,implement}/*/`:
   - Recursively collect `**/oos-accepted-*.md` (implement evidence lives under `round-N/`; a shallow glob misses almost all implement OOS blocks).
   - Read run-root `oos-issues.ndjson` and `oos-issues-created.md` when present.

2. **Within each implement run directory**, join round markdown to ndjson before scoring:
   - Parse accepted blocks from `**/oos-accepted-*.md` with `source_key = path.stem` and `artifact_relpath` relative to the run root.
   - Build block index keyed by hash alias, namespaced heading id, round-qualified `(artifact_relpath, heading_id)`, plus secondary bare-suffix keys for legacy lookup.
   - For each `oos-issues.ndjson` record, parse `Stable ID` lines (multiple per record allowed), `Filed URL`, `Filed as #N`, and legacy `Filed OOS issue #N` / `Filed OOS issue: <url>` body forms.
   - When `Stable ID` lines are absent (legacy bodies), extract cited `OOS_N` / `FINDING_N` tokens from disposition prose, markdown table cells, and bullet excerpts in the filed section only; join each extracted id to same-run markdown blocks via widened cover logic and round/path disambiguation rules above.
   - Attach each ndjson stable id to the matching accepted block's `Reviewer` / `Reviewer(s)` from the same run when unambiguous.
   - Map `oos-accepted-main-agent` stable ids with prefix `oos-accepted-main-agent:OOS_N` (or bare `OOS_N` matched only through main-agent source rules) to reviewer label `Main agent` when no round markdown block exists.

3. **Cap-rollup expansion** (implement runs only):
   - Expand only when `_is_cap_rollup_record(record)` is true: ndjson title/body indicates `Aggregated rollup` (cap-rollup from `file_oos._aggregate_block`) **or** the record body / `Stable ID` lines explicitly cite member `OOS_N` / `FINDING_N` / namespaced stable ids.
   - Fan out one score record per cited member block joined from same-run markdown via rollup prose excerpt list or explicit stable-id citations.
   - Do **not** fan out a single filed URL to every unattached same-run block when the record is not an aggregated rollup and does not cite member ids; score only joined or cited items and report other same-run blocks as unjoined or skipped.
   - Docking the rollup issue zeros adjusted points for every expanded member row, not just the single ndjson stable id.

4. **Design runs** do not use the ndjson join path. Parse `oos-issues-created.md` and `oos-accepted-design.md` at the design run root (plus recursive `oos-accepted-*.md` if present). Join `OOS_FILE_MAP\t<N>\t<url>` rows to `### OOS_N:` blocks in `oos-accepted-design.md` using `design_oos._block_range` semantics (mirror or import). Prefer block `Reviewer` / `Reviewer(s)` and inline `Filed URL` when present; fall back to map URL only when block fields are absent.

5. **Scoring unit**: emit one score record per distinct OOS item identity when available. Primary dedupe key for implement markdown evidence: `(run_id, artifact_relpath, heading_id)` when heading id is known; when only hash stable id is known, use `(run_id, hash_stable_id)`; when namespaced heading id is known without round collision, `(run_id, canonical_stable_id)` is acceptable but must not collapse distinct round-local blocks sharing the same stem and heading id. Fall back to `(reviewer_label, issue_url)` or `(reviewer_label, issue_number)` only when item identity is unavailable. Multiple canonical stable ids sharing one filed URL each receive the joined issue fate independently.

6. **Reviewer attribution**: split `Reviewer` / `Reviewer(s)` with `python/voting.py::tokenize_finding_reviewers` (or `grow_attribution_labels` over known reviewer labels mined from the run) and emit one provisional point row per reviewer token before item-level dedupe. Treat comma-lists like live OOS scoring: each co-proposer gets `+1` for the same filed item.

## Edge cases

- Historical OOS records may lack `Filed URL`. Join by `Filed OOS issue #N` / `Filed as #N` when present; otherwise skip and count in a skipped bucket.
- Historical source issues may have no comments in the targeted view fetch. Treat combined-away as unknown unless `stateReason`, labels, body, or legacy close text provides another signal.
- A closed issue can have no PR link and no not-planned signal. Keep it provisional and report `closed_unknown`.
- Multiple log records can point at the same filed issue. Score each distinct item identity separately; dedupe only exact duplicate evidence keys.
- A single filed issue may aggregate several OOS items. Count each canonical / round-qualified item once per reviewer token derived from its accepted block.
- Security-held OOS without a public issue URL must not be scored as filed OOS.
- Legacy code-review OOS blocks use `FINDING_N` ids; ndjson stable ids may be hash-based; joins must use hash alias and widened suffix rules, not bare suffix equality alone.
- `oos-accepted-main-agent` items use `Main agent` when ndjson stable id matches main-agent source rules and no round markdown block exists.
- Cap-rollup ndjson may list only one stable id while round markdown retains many member blocks; expansion scores only cited rollup members, not every unattached block.
- Same-run `OOS_1` in multiple artifacts or rounds must never share reviewer attribution through stem-only or bare-suffix-only indexing.
- Design `oos-issues-created.md` map rows without `oos-accepted-design.md` blocks still contribute URL fate rows with reviewer `unknown`.

## Failure modes

- If `gh issue list --json stateReason` is unsupported, `fetch_main` retries without optional fields and fate detection degrades for not-planned closes.
- If targeted `gh issue view` comment fetch fails for some filed OOS issues, continue with list/view body data, mark those issues `degraded_comment_fetch`, and avoid docking combined-away without evidence.
- If the fate section itself raises, print a short warning and continue the rest of `/analyze-issues`.
- If `larch-logs` is missing, render `No filed OOS run-log evidence found.` and continue.
- If an issue URL points outside the fetched repo, skip it and count it as skipped.
- If implement ndjson exists without any accepted markdown in the same run, attribute reviewer as `unknown` but still score by stable id or URL when possible; cap-rollup expansion may still recover multiple rows from explicit rollup prose alone.
