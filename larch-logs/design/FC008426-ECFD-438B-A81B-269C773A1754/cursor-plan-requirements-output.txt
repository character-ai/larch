**1. [correctness] Detached HEAD guard missing from `evaluate_failure`**

The plan ports `run_evaluate_failure`’s outer loop (`evaluate_failure`, lines 44–45 of the plan) but does not mention the per-attempt detached-HEAD check in `scripts/ship-pr.sh:2525-2530`. Phase-1 already exposes `git.current_branch` in `python/git.py:37-44`. Without an equivalent guard, fix/vendor work can proceed on a detached HEAD and surface the wrong terminal status.

**Suggested revision:** At the top of each outer attempt in `evaluate_failure`, verify a named branch; on failure return immediately with a stall-class outcome (map to `StepResult`/`STALLED` with detached-head detail), and add a stubbed unit test.

---

**2. [correctness] `poll_ci` three-strike semantics vs `ci-wait.sh`**

`ci-wait.sh` treats three consecutive **unparseable** `ci-status.sh` outputs as bail-worthy (`201-211`), while `ci-decide.sh` bails immediately on `status=error` (`80-84`). The plan’s `poll_ci` line and testing bullet (“3 consecutive `error`”) conflate these paths.

**Suggested revision:** Document and implement a counter only for empty/invalid `gather_status` results (intermediate `pending`), and immediate `bail` when `decide()` sees `error`; align `test_ci_monitor.py` with that split.

---

**3. [architecture] `rebase_then_evaluate` — fix timing after rebase**

The plan correctly forbids fixing **before** rebase (`did_fixing=False`, acceptance line 133). Bash still runs **`run_evaluate_failure` immediately after rebase** in the same action handler (`3547-3549`), without another `ci-wait.sh` poll. The proposed `monitor()` always re-enters through `poll_ci`, which can sit in `wait` while bash would already be in the fix path.

**Suggested revision:** Either document an explicit Phase-7 driver obligation (rebase → call `evaluate_failure` with saved `failed_run_id`, no poll), or extend the Phase-6 API for a post-rebase fast path; fix the misleading parity citation.
