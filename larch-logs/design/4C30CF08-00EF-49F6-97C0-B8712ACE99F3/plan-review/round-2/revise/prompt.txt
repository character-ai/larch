# [BUG] /design review re-entry rejoins stale bgjob result env; re-review after a plan edit returns the pre-edit verdict without re-running

## Summary

When `/design` revises `plan.txt` after Step 3 review and re-enters review (Gate A "Ready for review" or Gate C "Re-run review panel", i.e. `design-step3-entry.sh --reentry`), the Step 3 review launcher rejoins the **stale** prior-round bgjob result env instead of running a fresh review. The panel returns the pre-edit verdict and the Step 4 tail's Gate C preview shows the pre-edit plan — no reviewer ever sees the revised plan. The same gap exists for the Step 4 tail. Because publish review-provenance checks only review status plus the `.completed/step-3` sentinel (not a plan fingerprint), a stale-reviewed plan can still publish.

## Original report

Discovered while running `/design` on issue #6621. After Step 3 review completed, the plan was revised (a reviewer-flagged heading-format fix) and review was re-entered via `design-step3-entry.sh --reentry` followed by `design-step3-review.sh`. The launcher returned `BGJOB_STATUS=DONE` instantly with a `BGJOB_ELAPSED_S` identical to the prior round and no fresh `plan-review/round-*` artifacts — it had rejoined the previous round's result env rather than launching a new review. The Step 4 tail (`design-step3b-tail.sh`) exhibited the same behavior: `gatec-preview.md` still showed the pre-edit plan. Manually deleting the stale bgjob result envs and relaunching produced a genuine fresh round.

## Reproduction scenario

1. Run `/design` on any issue through Step 3 until review completes (this writes `$DESIGN_TMPDIR/bgjob/design-step3-review.result.env`).
2. Revise `$DESIGN_TMPDIR/plan.txt` and re-validate it (settle/postplan).
3. Re-enter review: `design-step3-entry.sh --reentry`, then `design-step3-review.sh`.

Observed: `design-step3-review.sh` returns `BGJOB_STATUS=DONE` immediately (rejoined the stale result env) instead of `BGJOB_STATUS=STARTED`; no new round runs; `plan-review/round-*` mtimes stay at the prior round. Then `design-step3b-tail.sh` likewise rejoins its stale `design-step4-tail.result.env` and regenerates nothing, so `gatec-preview.md` shows the pre-edit plan.

## Expected behavior

After `--reentry`, the next `design-step3-review.sh` (and `design-step3b-tail.sh`) invocation should start a fresh run (`BGJOB_STATUS=STARTED`) that reviews the current `plan.txt` and regenerates the Gate C preview from it. Re-entry is explicitly for re-reviewing a changed plan, so the prior round's result env must not be reused.

## Observed behavior

The relaunch rejoins the stale result env and returns the prior round's verdict/preview. The revised plan is never reviewed. The eventual round (when one is forced) does write `.completed/step-3`, so review-provenance passes and the stale-reviewed plan publishes.

## Root cause analysis

The re-entry state handler clears the completion sentinels but not the bgjob result envs, and the launchers rejoin on result-env presence before reaching their own fresh-start cleanup:

- `python/larch/review/plan_review_loop.py:453` `_step3_clear_downstream_sentinels(tmpdir)` unlinks `.completed/step-3`, `.completed/step-3.5`, `.completed/step-3-terminal`, `.step3-terminal-persisted-this-run`, `.completed/step-3b`, `.completed/step-4`, `.completed/step-4b`, and `.gate-b-postapply-ready-*` (lines 455-465). It does **not** unlink `bgjob/design-step3-review.result.env` or `bgjob/design-step4-tail.result.env`. It is called by `step3_state()` on both the re-entry path (`--direct-review-entry`, line 507) and the `--auto-continuation-entry` path (line 493).
- `skills/design/scripts/design-step3-review.sh:323`: `if [ -f "$_result_env" ]; then exec … bgjob wait --step design-step3-review --max-wait-s 0` rejoins any existing bgjob result env. Its own fresh-start `rm -f …/design-step3-review.result.env` at line 346 is never reached on this path.
- `skills/design/scripts/design-step3b-tail.sh:153`: identical rejoin for `bgjob/design-step4-tail.result.env`; its fresh-start `rm -f` (with `.completed/step-4`) at line 170 is unreached.

So after `--reentry` the stale result envs survive, and the launchers return `DONE` (rejoin) rather than `STARTED` (fresh launch). This is a state-clearing omission — the re-entry clears "downstream sentinels" but forgot the bgjob result envs that gate the launchers' rejoin-vs-fresh decision.

## Evidence

- Verified on branch `main`, HEAD `453be2b91`, larch 52.5.10.
- `plan_review_loop.py:453-465`: unlink list contains the `.completed/step-*` sentinels and `.gate-b-postapply-ready-*` only — no `bgjob/*.result.env`.
- `plan_review_loop.py:493` and `:507`: both `--auto-continuation-entry` and `--direct-review-entry` call `_step3_clear_downstream_sentinels`.
- `design-step3-review.sh:323-346`: rejoin guard precedes the fresh-start `rm -f` of the result env.
- `design-step3b-tail.sh:153-170`: same shape for the Step 4 tail.
- Live symptom during #6621: relaunch returned `BGJOB_STATUS=DONE BGJOB_ELAPSED_S=445` (identical to the prior round) with no fresh round artifacts; after `rm -f bgjob/design-step3-review.result.env` the relaunch returned `BGJOB_STATUS=STARTED` and ran a genuine round that wrote fresh `plan-review/round-2` artifacts and `.completed/step-3`.

## Affected files

- `python/larch/review/plan_review_loop.py` — `_step3_clear_downstream_sentinels()` (line 453); the clearing omission is the root cause and the cleanest single-point fix.
- `skills/design/scripts/design-step3-review.sh` — Step 3 review launcher rejoin guard (line 323).
- `skills/design/scripts/design-step3b-tail.sh` — Step 4 tail launcher rejoin guard (line 153).
- `python/design_publish.py` — `review_provenance()` checks status + `.completed/step-3` only; relevant to the defense-in-depth open question below.

## Suggested fix(es)

1. Add `bgjob/design-step3-review.result.env` and `bgjob/design-step4-tail.result.env` to the unlink set in `_step3_clear_downstream_sentinels()` so both the `--direct-review-entry` and `--auto-continuation-entry` paths clear them. (Alternatively, clear them in the `--reentry` block of `design-step3-entry.sh`, but the shared helper is the DRY locus and also covers auto-continuation.)
2. Add a regression test asserting that after a re-entry the bgjob result envs are absent, so the launchers take the `STARTED` (fresh) path rather than rejoining.
3. Defense-in-depth (optional): have `review_provenance` bind the reviewed plan's content fingerprint so a plan edited after review cannot publish against a stale review even if a future re-entry path regresses.
