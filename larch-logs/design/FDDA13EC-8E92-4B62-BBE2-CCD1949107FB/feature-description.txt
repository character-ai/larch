[BUG] cursor_auth_preflight single-shot keychain read permanently excludes Cursor on transient macOS keychain lock

## Summary

`cursor_auth_preflight` in `scripts/lib-cursor-auth.sh` performs a single-shot `security find-generic-password` call with no retry. On transient macOS keychain lock (e.g., while Cursor is rotating its access token), this call returns non-zero, `cursor_auth_preflight` exits 2, and the `check-reviewers.sh` probe immediately writes `false` to the stamp (`/tmp/larch-cursor-present-<user>.stamp`, 60s TTL) — short-circuiting the entire probe. The live `cursor agent` probe (which has up to 5 retries via `MAX_AUTH_RETRIES`) never runs. Because `CURSOR_PRESENT=false` is persisted into `session-env.sh` at bootstrap, Cursor is excluded from the **entire** multi-hour `/implement` run even though the underlying issue resolved within seconds.

## Context (observed incident)

During larch run `C89A55AC-0F01-4348-B594-CD4DBC4E2378` (issue #3675, PR #3946, ~3h06m), the session bootstrap at Step 0 reported:

```
**⚠ Cursor not healthy for this session (runtime probe failed, skipped probe, auth error, or timeout). Using Claude replacement.**
```

`degraded-tools-gate.sh` confirmed `CURSOR_STATE=probe-failed`, `BOTH_DOWN=false`. All 5 code-review rounds ran with 3 Codex slots and 0 Cursor slots — reviewer panel diversity was reduced for the entire run. Running `check-reviewers.sh` interactively after the run completed showed `CURSOR_PRESENT=true` immediately, confirming the failure was transient.

## Root Cause

`cursor_auth_preflight` (Darwin path, `lib-cursor-auth.sh:154`) is:

```bash
if security find-generic-password -a cursor-user -s cursor-access-token >/dev/null 2>&1; then
    rc=0
else
    rc=1
fi
if [ "$rc" = "0" ]; then
    return 0
fi
# ... logs actionable message
return 2
```

One call, no retry. Return code 2 is the "auth not present" signal consumed by `check-reviewers.sh`:

```bash
_pf_rc=0
cursor_auth_preflight || _pf_rc=$?
if (( _pf_rc == 2 )); then
    CURSOR_PRESENT=false
    larch_write_bool_stamp "$(larch_stamp_path cursor)" "$CURSOR_PRESENT" || true
    # <-- exits the entire cursor probe block; live probe never runs
```

The macOS Keychain briefly holds a write lock when Cursor's desktop app rotates its `cursor-access-token` credential. A single `security find-generic-password` during that window returns non-zero. Duration is typically <200ms, but that is long enough to hit when:
- Cursor app just launched (initial keychain write)
- A session-token refresh happens to coincide with bootstrap
- macOS sleep/wake cycle triggers a keychain lock

The live `larch_run_one_cursor_probe` function already handles transient failures correctly — it has a retry loop up to `MAX_AUTH_RETRIES=5` and classifies auth failures (exit code 2) for retry. `cursor_auth_preflight` sits upstream of that loop and bypasses it entirely.

**Secondary amplifier**: the `false` stamp has a 60-second TTL, which means that even a second bootstrap attempt within 60 seconds would read the cached `false` without re-probing. And since `session-env.sh` persists the `CURSOR_PRESENT=false` result, all subsequent skill invocations in the same session inherit the exclusion permanently.

## Files

- `scripts/lib-cursor-auth.sh` — `cursor_auth_preflight` (lines ~154–210)
- `scripts/check-reviewers.sh` — consumes preflight exit code, writes stamp

## Fix Suggestion

**Option A (minimal — preferred)**: add a short retry loop (2–3 attempts, 100–300ms sleep) around the `security find-generic-password` call inside `cursor_auth_preflight`:

```bash
cursor_auth_preflight() {
    # ... existing CURSOR_API_KEY fast-path ...

    local attempt max_attempts
    max_attempts=3
    for attempt in 1 2 3; do
        if security find-generic-password -a cursor-user -s cursor-access-token >/dev/null 2>&1; then
            return 0
        fi
        if (( attempt < max_attempts )); then
            sleep 0.2   # wait for keychain write lock to clear
        fi
    done
    # ... existing actionable message + return 2 ...
}
```

This keeps the preflight fast (≤600ms extra in the worst case) while surviving a momentary keychain write-lock. The retry count should be bounded and small — this is a cheap read operation and the window is typically <200ms.

**Option B (defense-in-depth)**: in `check-reviewers.sh`, when `cursor_auth_preflight` exits 2, do not immediately write `false` to the stamp and bail. Instead, run one live probe attempt anyway. If it succeeds, the keychain entry is present despite the preflight miss; write `true` and set `CURSOR_PRESENT=true`. Only write the `false` stamp if the live probe also fails.

The downside of Option B alone is that it bypasses the preflight's purpose of preventing the `Security process exited with code: 45` error from leaking to the user. Option A + B together provide the best coverage.

**Option C (stamp TTL reduction for `false` stamps)**: reduce the negative stamp TTL (or eliminate it — don't cache `false` at all). A `true` stamp is safe to cache for 60s; a `false` stamp from a transient failure is not. Separate `LARCH_PROBE_NEGATIVE_TTL_SECONDS` from `LARCH_PROBE_TTL_SECONDS` and default it to 0 or a very short value (5s).

## Recommended Fix

Option A in `lib-cursor-auth.sh` (3 attempts, 200ms sleep) + Option C (set negative TTL to 0 by default so failed probes are never cached). Option B as a bonus hardening layer. Add a regression test to `test-lib-cursor-auth.sh` covering the retry path.
