### MVP-1: composed-plan.md prose-only rewrite, single LLM call, no validator

The simplification step runs exactly once at Step 5c — between `compose composed-plan.md` and `redact-secrets.sh` — and rewrites only the prose paragraphs of `composed-plan.md`. A single LLM call receives the composed plan with a Strunk & White + short-sentence (<20 words) + simpler-vocabulary prompt, plus an explicit byte-identity contract for fenced code blocks, backticked tokens, the `### NEW:/UPDATED:/REWRITTEN:` subsection grammar, and the trailing `diff_lines: <N>` line. **IN**: composed-plan rewrite, hard fall-back to original on any non-zero / malformed output, one `Warnings` entry on failure. **CUT**: no separate OOS body rewrite (assumption: OOS issues are mostly title + a 1-2 line description that already reads cleanly, and rewriting them needs a second LLM call), no `plan.txt`-level rewrite (assumption: chat display already renders from the composed plan / `larch:plan` block downstream), no structural validator beyond byte-equality grep of preserved tokens. **Biggest risk if we cut too far**: the rewriter silently mangles a backticked function-name or shell flag inside prose that the simple byte-equality check doesn't catch (e.g., changes `--no-edit` to `–no-edit` with an en-dash), and `/implement` later reads a subtly-broken reference. **Cost**: small.

### MVP-2: MVP-1 plus a structural diff guard but still skip OOS

Same single-call rewrite on `composed-plan.md` only, but add a mechanical pre-write guard that extracts and compares the set of fenced code blocks, backticked tokens, `### NEW:/UPDATED:/REWRITTEN:` headings, and the `diff_lines: <N>` tail line from input and rewriter output. If any token differs, fall back to the original plan and log a `Warnings` entry naming the mismatched token class. **IN**: MVP-1 surface plus the structural guard plus a single regression fixture under `skills/design/scripts/fixtures/`. **CUT**: still no OOS bodies, no `plan.txt`, no semantic comparison (assumption: byte-equality of the precision-contract tokens is enough for `/implement` safety; semantic drift in prose is the *desired* effect of the step). **Biggest risk**: false positives where the guard rejects every rewrite (because the LLM stripped a code-fence newline) and the feature ships always-fall-back — i.e., looks deployed but never actually simplifies. **Cost**: small-medium.

### MVP-3: Two artifacts, two calls — composed-plan + OOS bodies

Run the rewriter at Step 5c on `composed-plan.md` as in MVP-1 **and** at Step 5b on each accepted-OOS Description field *before* `/larch:issue` files it. Each artifact gets its own LLM call; OOS bodies use a stricter dyslexia-friendly prompt because they tend to be denser. **IN**: prose rewrite of both surfaces, per-artifact fall-back (one failing OOS body falls back to its own original, doesn't poison the others), one combined `Warnings` entry if any artifact fell back. **CUT**: still no `plan.txt`-as-source rewrite (assumption: `plan.txt` and `composed-plan.md` derive from the same source and rewriting downstream once is the only canonical surface), no validator beyond byte-identity check. **Biggest risk**: doubling the LLM-call surface doubles the latency budget and the failure-mode matrix; if OOS filing fails *because* of a rewriter timeout we've added a new Step 5b failure path that the design SKILL.md branch-handling didn't previously have to enumerate. **Cost**: medium.

### MVP-4: Rewrite `plan.txt` at the source, let everything else inherit

Insert the rewriter step at the *earliest* in-pipeline point where `plan.txt` is canonical — right after Step 2b finalize-plan and before Step 3 plan-review — so that the simplified text flows through the reviewer panel, Gate B/C chat displays, OOS extraction, composed-plan build, and `larch:plan` write without further intervention. **IN**: a single `simplify-plan.sh` helper invoked from `finalize-plan.sh` (or via a new `ACTION=SIMPLIFY_PLAN` record in `design-driver.sh`), writing `plan.simplified.txt` and atomically renaming over `plan.txt` after the byte-identity guard passes. **CUT**: no separate Step 5c rewrite, no separate OOS rewrite (assumption: rewriting the source artifact rewrites every downstream consumer for free). **Biggest risk**: the reviewer panel now critiques the simplified plan, not the engineer-authored plan — reviewers may surface "this prose is too terse" findings that the engineer didn't write and can't fix, polluting the review signal. Re-running `/design` over an already-simplified plan also has fewer rollback knobs because the un-simplified source no longer exists in tmpdir. **Cost**: medium.

### MVP-5: Two-pass with cheap deterministic pre-pass + optional LLM polish

Pass 1 is a deterministic shell/awk pre-pass that does the *mechanical* dyslexia-friendly transforms a script can do safely: split any `.`/`;`-terminated sentence over 20 words into bullets, collapse double-blank-lines, demote long paragraphs to bulleted lists when they exceed N lines. Pass 2 is an LLM Strunk & White pass *only* over prose that survived pass 1 unchanged — i.e., short paragraphs the script couldn't safely split. Both passes preserve fenced code, backticks, and the `### NEW:/UPDATED:/REWRITTEN:` grammar by operating outside them via the same anchor regex `check-plan-size.sh` already uses. **IN**: a deterministic pre-pass plus an LLM polish pass plus byte-identity guard on the merged output. **CUT**: OOS bodies (assumption: same as MVP-1), no validator on pass 1 because it's deterministic. **Biggest risk**: the deterministic pass over-splits a code-adjacent sentence and breaks markdown structure in a way the LLM pass can't repair, or — converse risk — the pass 1 makes such conservative edits that pass 2 still does the bulk of the work and we paid the complexity without saving the LLM budget. **Cost**: medium-large.

### MVP-6: Always-on rewrite, fail-open with NO validator and NO byte-identity guard

The leanest possible interpretation of the user's "always-on, fall-back on failure" decisions: a single LLM call at Step 5c with a strong precision-contract prompt, no programmatic guard at all, and the only failure detector is "did the rewriter return non-empty output that still contains the required `## Plan` / `## Acceptance` / `diff_lines: <N>` anchors". If those anchors are present, the rewrite is used as-is; if not, fall back to the original. **IN**: minimal helper, minimal prompt, minimal contract check, single `Warnings` entry on fallback. **CUT**: structural diff, fenced-code byte check, OOS bodies, `plan.txt` source rewrite — everything (assumption: the precision contract belongs to the *prompt*, not the runtime; downstream consumers will surface real precision regressions as bugs we then fix). **Biggest risk**: a silent precision regression ships to `/implement`, the engineer doesn't notice because the plan still *reads* well, and the LLM-introduced bug is discovered downstream during implementation or review — exactly the failure mode the "Preserve every fact and code reference verbatim" decision was meant to prevent. **Cost**: small.
