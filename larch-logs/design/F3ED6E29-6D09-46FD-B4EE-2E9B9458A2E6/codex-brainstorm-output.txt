**Minimal: Pre-Review In-Place Helper**
After Step 2b writes `plan.txt`, run a new helper that rewrites `plan.txt` in place before Step 2b.5, Step 3 preview, reviewers, Gate B/C, and Step 5c composition. Step 5b gets a separate narrow pass over accepted OOS Description fields before `file-design-oos.sh prepare` hands them to `/larch:issue`. IN: one inline LLM helper script, in-place canonical rewrite, re-run `ACTION=EMIT_PLAN`, validator checks for fenced-code byte equality, `diff_lines` preservation, `### NEW/UPDATED/REWRITTEN` grammar, and unchanged backticked/code-reference tokens. OUT: sibling artifacts, external agents, new skill abstraction. Tradeoff: lowest implementation cost and best alignment with “one canonical simplified plan,” but highest pressure on the helper’s precision because it mutates the artifact reviewers and `/implement` consume.

**Moderate: Structured Protected-Span Rewriter**
Add a simplification helper that first tokenizes protected spans, replaces them with sentinels, rewrites only unprotected prose, then restores the original bytes. Fire it after every settled `plan.txt` write: initial Step 2b, Gate B plan revision, and post-plan discussion re-emits; also fire inside Step 5b for OOS Description fields. IN: deterministic protected-span extraction plus LLM prose rewrite, in-place `plan.txt`, no separate final-only pass, validators comparing all protected spans before/after. OUT: rewriting composed-plan independently, reviewer subagents, late-only publication cleanup. Tradeoff: more implementation work than the minimal helper, but precision risk drops because the LLM never sees mutable code references as editable text. Constraint risk: idempotency needs care so repeated Gate B/Gate C loops do not keep shortening already-simple prose.

Constraint risk is mostly around preserving OOS block headings and security-token filtering so public filing behavior does not change.
