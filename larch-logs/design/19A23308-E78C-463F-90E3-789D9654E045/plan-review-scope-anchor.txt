## Summary

Issue #6591 ("Step 3 checks bgjob `implement-step3-checks` orphaned after ~123s on second launch") was closed WONTFIX as "transient system kill suspected." That disposition is very likely wrong. The symptom is the same ~123s bgjob-orphan root cause as #6595 and #6580, both of which were accepted as real defects and fixed on shared code that the Step 3 path also uses. So #6591 is probably already fixed incidentally, but the tracker records a misleading "transient" conclusion, and no test reproduces the Step 3 second-launch orphan scenario specifically. This bug asks to confirm coverage, add a targeted regression test, and correct the #6591 disposition.

## Original report

Filed as a follow-up from a 24-hour bug-spike audit (repo `character-ai/larch`, main at `ce93288bf`).

The recurring "orphaned at ~123s" signature in the newly-introduced `bgjob` background-job transport (landed 2026-07-07 via #6514/#6521) was filed three times:

- #6595 — Step 5 review bgjob orphaned at ~123s — **fixed** (daemon owner-validation hardening).
- #6580 — Step 5 review bgjob orphaned at ~123s — **fixed** (stable `LARCH_CLAUDE_PID` propagated from the launcher).
- #6591 — Step 3 checks bgjob (`implement-step3-checks`) orphaned after ~123s on second launch — **closed WONTFIX / not_planned**, rationale "transient system kill suspected (contract-failure at 3)."

There is no hardcoded `123` in the bgjob code. ~123s is approximately the Claude Code harness's ~120s foreground-tool kill, so "transient system kill" and "bgjob orphan on harness kill" are the same event, not two different things. The concern: #6591 was triaged as environmental noise while its Step 5 siblings were triaged as real code defects, even though Step 3 runs through the same launcher and daemon that #6580 and #6595 repaired.

## Reproduction scenario

Not reproduced directly (would require driving a full `/implement` run and forcing the harness ~120s kill of the Step 3 checks wrapper on a second launch). The claim here is based on static code-path analysis showing Step 3 shares the fixed code, plus the issue-tracker history. A faithful reproduction would:

1. Run `/implement` to Step 3 so `run-step-checks.sh --site step3` launches the `implement-step3-checks` bgjob.
2. Trigger a second launch where the transient foreground wrapper is killed near ~120s (the harness kill #6591 attributes to a "transient system kill").
3. Observe whether the daemon reports `BGJOB_RC=orphaned` (pre-fix behavior) or survives via the stable owner pid and consecutive-failure grace (post-fix behavior).

## Expected behavior

- The Step 3 (`implement-step3-checks`) bgjob should not be declared orphaned when the transient foreground wrapper is killed by the harness while the stable session owner is still alive, identical to the fixed Step 5 behavior.
- The issue tracker should record the true root cause (bgjob owner-validation on harness kill), not "transient system kill," so the same signature is not re-triaged as noise in future.

## Observed behavior

- #6591 is closed as `not_planned` with rationale "transient system kill suspected," implying no code defect and no fix.
- Its Step 5 siblings (#6595, #6580) were treated as real defects and fixed on code shared with the Step 3 path.
- No regression test reproduces the Step 3 second-launch orphan scenario, so if the shared fix ever regresses on the Step 3 path it would not be caught, and the "transient" label would make a recurrence look like noise again.

## Root cause analysis

Likely root cause (inferred from code paths, not from a live repro): the `bgjob` transport declared the job orphaned when the harness killed the transient foreground wrapper whose pid had been used as the owner. The Step 5 fixes addressed exactly this:

- #6580 made the shared launcher export a stable `LARCH_CLAUDE_PID` so the owner pid no longer dies with the transient wrapper (`python/larch/state/session_env.py:930`, `_implement_run_launcher_text`).
- #6595 hardened the daemon owner-validation loop (consecutive-failure threshold before starting the grace timer, bounded `ps` probe) in `python/larch/bgjob/daemon.py` and `python/larch/core/process_identity.py`.

Step 3 uses both: `skills/implement/scripts/run-step-checks.sh:150` launches the `implement-step3-checks` bgjob with `--owner-pid "${LARCH_CLAUDE_PID:-$PPID}"`, and the SKILL.md Step 3 fence invokes it through the same shared `implement-run-$PPID.sh` launcher (generated by `_implement_run_launcher_text`). So the Step 3 path inherits both fixes and #6591 is probably already resolved in behavior. What remains is (1) a wrong tracker disposition and (2) a missing Step-3-specific regression test.

Uncertainty is explicit: this has not been reproduced end-to-end. It is possible the Step 3 second-launch path has a distinct trigger not covered by the Step 5 fixes; the confirmation step below exists to settle that.
