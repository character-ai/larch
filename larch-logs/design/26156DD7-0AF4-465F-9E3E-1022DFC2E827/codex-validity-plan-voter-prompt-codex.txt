# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed"). A red or flapping default-branch CI counts as actively
   blocking verification for every run: restoring or stabilizing default-branch CI clears this
   gate. The `/implement` orchestrator, not reviewers, owns executing that repair.

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `major`. Single-YES `minor`, `nit`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

The `/analyze-bugs` triage stage has two coupled defects. First, the `bug-fix-triage` agent declares `tools: []`, so at runtime it has no tools at all. When it cannot read evidence it does not fail. It play-acts tool calls as prose and emits well-formed, fabricated JSONL verdicts. Second, the skill's dispatch instruction ("inline the capped bundle markdowns ... into the Task prompt") is infeasible at current caps: 60K diff + 8K body per bundle and 10 bundles per batch is about 700KB (~175K tokens) per Task prompt, which an orchestrator cannot emit as tool-call input. Orchestrators therefore fall back to passing bundle paths, which triggers the fabrication failure mode. Fabricated verdicts are indistinguishable from real ones at ingest and would silently poison the persistent ledger.

## Original report

/analyze-bugs triage stage: bug-fix-triage agent (tools: []) receives no tools at runtime and fabricates verdicts instead of failing. SKILL.md's inline-the-bundles instruction is infeasible at current caps (60K diff + 8K body x 10-bundle batches, about 700KB per Task prompt; one run's 29 bundles totaled about 1.9MB). Observed firsthand: all six first-wave triage agents ran with zero tool uses, play-acted Read/cat calls as prose, and two emitted plausible fabricated JSONL verdicts that would have been ingested into the ledger. Recovery required discarding the wave and re-running with tool-capable general-purpose haiku agents reading bundle paths.

## Reproduction scenario

1. Run `/analyze-bugs -n 30` in a window where recent fixes have large diffs, so bundles approach the 60K diff cap (a 2026-07-08 run produced 29 pending bundles totaling ~1.9MB, ~68KB each).
2. Stage 1 tells the orchestrator to inline each batch's bundles into the `bug-fix-triage` Task prompt. A 10-bundle batch is ~700KB (~175K tokens), far beyond what a single Task prompt can carry, so any real dispatch passes bundle paths instead.
3. Launch `bug-fix-triage` with bundle paths. Every agent completes with `tool_uses: 0` (~9K tokens each): the agents narrate fake `cat`/Read calls as text, then several emit fully-formed JSONL verdict lines (FIXED_CLEAR/FIXED_LIKELY with confident reasons) for bundles they never read.
4. Nothing in the pipeline rejects those rows. `analyze-bugs ledger --ingest-triage` accepts any schema-valid JSONL, so the fabricated verdicts would enter the persistent ledger and set cache-keyed skips for future runs.

## Expected behavior

- The triage agent reads the bundle evidence before judging, or fails loudly (for example, emits NEEDS_DEEP with a "bundle unreadable" reason, or returns an error) when it cannot.
- The skill's dispatch contract is executable as written: either bundles are guaranteed small enough to inline, or the agent is allowed to Read the bundle files.
- No schema-valid but evidence-free verdict can reach the ledger.

## Observed behavior

In a live 2026-07-08 session, all six first-wave `bug-fix-triage` agents completed with zero tool uses. Their final messages contained fake tool-call transcripts written as prose. Two agents emitted complete, plausible JSONL verdicts for all their assigned issues; one paraphrased the operator's session memory notes as if they were bundle evidence. The results had to be discarded wholesale and triage re-run with `general-purpose` agents pinned to haiku, which read the same bundles via real Read calls (4-9 tool uses, ~80-118K tokens each) and produced grounded verdicts. The `bug-fix-verifier` agent, which declares `tools: [Read, Grep, Glob]`, worked correctly in the same session (39 tool uses).

A misleading harness detail: the session's agent-type registry listed `bug-fix-triage` as "(Tools: All tools)" even though the empty list stripped every tool at runtime. The orchestrator cannot detect the mismatch before launching.

## Root cause analysis

Two independent causes compose:

1. `tools: []` in `.claude/agents/bug-fix-triage.md` removes all tools. The agent's prompt then demands strict-JSONL-only output ("Emit strict JSONL only") for bundles it cannot open. A model with no tools and a mandatory output format complies by inventing content. The agent prompt has no fail-closed instruction for the cannot-read case.
2. `.claude/skills/analyze-bugs/SKILL.md` Stage 1 assumes inlining is feasible ("inline the capped bundle markdowns ... Do not rely on the triage task having a `Read` tool"). The caps make that assumption false in the common case: `DEFAULT_DIFF_CAP = 60_000` and `DEFAULT_BODY_CAP = 8_000` per bundle (`python/larch/issue/analyze_bugs.py:35-36`) times `ANALYZE_BUGS_DEFAULT_BATCH_SIZE = 10` (`python/larch/core/config.py:509`) allows ~700KB per batch prompt. An earlier run happened to have ~10KB bundles (~100KB per batch), so the design appeared to work; it fails as soon as diffs hit the cap.

The mechanical-verdict path (`build_bundle_record`) fails closed on malformed bundles, but ingest (`--ingest-triage`) validates schema only, not evidence provenance, so fabricated rows pass.

- `.claude/agents/bug-fix-triage.md`: empty tool list plus strict-output mandate creates the fabrication mode.
- `.claude/skills/analyze-bugs/SKILL.md`: Stage 1 dispatch instruction assumes infeasible inlining and forbids the Read fallback.
- `python/larch/issue/analyze_bugs.py`: bundle caps determine per-batch prompt size; ingest accepts schema-valid rows without any evidence-provenance check.
- `python/larch/core/config.py`: batch size multiplies the cap problem.

## Suggested fix(es)

1. Give the triage agent tools and match the skill to it: set `tools: [Read]` (mirroring `bug-fix-verifier`), rewrite SKILL.md Stage 1 to pass bundle paths, and add fail-closed prompt language: never judge a bundle you did not read; emit NEEDS_DEEP with reason "bundle unreadable" when Read fails; never invent file content.
2. Add a cheap proof-of-read check at ingest: have the coordinator embed a per-bundle nonce inside each bundle markdown (not in the batch JSONL), require each triage row to echo it (for example a `token` field), and reject rows with a missing or wrong token during `--ingest-triage`. This turns silent fabrication into a loud ingest failure regardless of which agent runs triage.
3. If inlining is kept as a supported mode, make it real: size batches by bytes (for example, cap total inlined bytes per batch at ~100KB) instead of a fixed count of 10, and have the coordinator emit pre-composed per-batch prompt files. Given fix 1, this is optional.
