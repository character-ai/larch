# [BUG] bg-poll-guard cross-clone block: foreign session's live .bg-wait-active denies…

# Cross-clone bg-poll-guard denials

## Summary

A live `.bg-wait-active` marker written by a `/implement` run in one repo clone (larch7) caused `scripts/hook-bg-poll-guard.sh` in a **different** clone's session (larch8, mid-`/design` for #6090) to deny that session's read of its **own just-completed background task output**. The victim session obeyed the deny text ("end the turn and wait for `<task-notification>`") for a notification that had already been delivered, so it hard-stalled until operator intervention. Root cause is two compounding defects: (1) the victim session was pinned at session start to the 52.2.6 plugin root, whose hook still matched `*tasks/*.output*` unconditionally (fixed by #6080 in v52.2.8, installed 21 seconds before the fatal denial but invisible to already-running sessions); (2) at current HEAD, several deny branches remain ungated by clone correlation, including the two that blocked the victim's self-diagnosis, so any future cross-clone false positive again becomes an undiagnosable hard stall. Fix the class: clone-gate marker collection itself, allow reading the marker file, and make every deny reason self-identifying.

## Original report

Operator report (condensed): "We have been plagued lately by this nightmarish bug of some hook in one session of claude running a larch skill (usually /implement or debug) blocking another session. We have made a number of fixes to squash this, but another instance just occurred. This one is in larch8, wherein a session is completely blocked by a hook seemingly from a session in larch7."

The blocked larch8 session self-reported: mid-`/design` for issue #6090, plan reviewed and Gate C approved, filing one accepted OOS finding via `/larch:issue`. "Every Bash call I make right now, even a harmless cat/stat/ls, is being denied by a hook with 'An immediate-background wait is active. End the turn and wait for `<task-notification>`.' I did already receive that task's completion notification. I found the marker file causing this: `<TMPDIR>/.bg-wait-active`. That's from a different session (larch7, not this larch8 clone). The hook appears to be scanning all sessions rather than just the current one. I can't even read the file's contents right now to confirm its age, because the hook denies that read too."

Note: the session's "stale leftover" hypothesis was wrong. The marker was a live, legitimate wait. The "scanning all sessions" observation was correct.

## Reproduction scenario

Deterministic shape (verified against 52.2.6's hook code; timestamps below are from the real incident):

1. Clone A (`larch7`) runs `/implement`; its Step 5 review wrapper writes `~<TMPDIR><suffix>/.bg-wait-active` with `STEP=implement-step5-review` and holds it for the duration of the review (here 07:44Z to 08:28Z).
2. Clone B (`larch8`) runs a long-lived `/design` session started while plugin 52.2.6 was current, so its `CLAUDE_PLUGIN_ROOT` stays pinned to `plugins/cache/larch-local/larch/52.2.6` even after later upgrades.
3. Clone B launches any `run_in_background` Bash task (here the `/larch:issue` title-snapshot task `bop06zc0j`), receives its completion `<task-notification>`, then reads the output: `wc -l .../tasks/bop06zc0j.output; head -3 ...`.
4. The 52.2.6 hook globs all sessions (`find "$HOME/.cache/larch/sessions" -maxdepth 2 -name .bg-wait-active`), finds clone A's live marker, and `bash_has_probe_target()` matches `*tasks/*.output*` unconditionally: deny.
5. Clone B ends the turn per the deny text and waits forever (its notification already arrived). Follow-up diagnosis probes (`cat`/`stat`/`ls` of the marker path; `Read` of the marker file) are denied by the still-unconditional `*"$dir"*` Bash branch and `path_under_dir` Read branch. Those two diagnosis denials reproduce at HEAD as well.

The step-4 denial itself does not reproduce at HEAD (v52.2.8 clone-gated the Bash `tasks/*.output` branch), but any session started on <= 52.2.7 keeps the vulnerable hook until restarted, and the step-5 diagnosis denials reproduce on every version including HEAD.

## Expected behavior

- A `.bg-wait-active` marker should only ever gate the session/clone it belongs to. A live wait in larch7 must never deny tool calls in a larch8 session.
- A session that received its task's completion notification must be able to read that task's output.
- If a deny does fire, the reason should identify the triggering marker (path, STEP, owning session dir) and hook version so the orchestrator and operator can immediately distinguish "my wait" from "someone else's wait" and spot stale pinned hooks.
- A session must be able to read a marker file itself to diagnose; reading the one-line marker is not progress polling.

## Observed behavior

- 08:07:33Z: larch8's `wc -l .../tasks/bop06zc0j.output; head -3 ...` denied with "An immediate-background wait is active. End the turn and wait for `<task-notification>`; do not poll progress artifacts." The only live marker on the machine was larch7's `implement-step5-review` marker.
- The larch8 orchestrator ended the turn and stalled; the `/design` run for #6090 blocked until the operator intervened, and the session escalated with questions instead of finishing (file OOS issue, Step 5c publish, Step 6 cleanup all pending).
- 08:11:51Z: larch8's diagnosis probe (`cat`/`stat`/`ls` of the larch7 marker path) denied by the same hook; an earlier `Read` of the marker file was also denied.
- `bg-poll-guard-denials.count` in the larch7 session dir reads `2` (mtime 08:11:51Z), matching exactly the two denials: cross-clone denials are attributed to the marker owner's dir, further confusing attribution.

## Root cause analysis

Two compounding defects, high confidence (code read at both versions, transcript-verified):

1. **Version-pinned hook missing the #6080 gate.** In 52.2.5 through 52.2.7, `bash_has_probe_target()` (52.2.6 hook line 682-684) is `case "$cmd" in *"$dir"*|*tasks/*.output*) return 0 ;; esac`, with a comment wrongly claiming both alternatives are "already dir-specific". Task outputs live under the session's own scratchpad (`/private/tmp/claude-501/<project>/<session-uuid>/tasks/*.output`) and have no relation to any marker dir, so any live marker anywhere on the machine denied any Bash touching any `tasks/*.output` path. #6080 (commit 4d38b1dc5, PR #6097) clone-gated it behind `bash_probe_target_dir_plausible`; first shipped in v52.2.8 (tagged 08:06:27Z, installed 08:07:12Z, 21 seconds before the fatal denial). Hooks execute from the session's pinned `CLAUDE_PLUGIN_ROOT`, so already-running sessions kept the 52.2.6 hook. This rollout lag is why the class keeps "recurring after we fixed it": #5925, #5948, and #6080 each only protect sessions started after the upgrade, while `/design` and `/implement` sessions run for many hours.
2. **Diagnosability defect, present at HEAD.** Two deny branches remain unconditional (no clone gating): the Bash `*"$dir"*` branch in `bash_has_probe_target` (`scripts/hook-bg-poll-guard.sh:764`) and the Read `path_under_dir` branch (`scripts/hook-bg-poll-guard.sh:870`). Any probe-verb Bash command whose text contains a foreign live marker dir path, and any `Read` under a foreign live marker dir, are denied. So the victim of a cross-clone false positive cannot read the marker to learn it is foreign, and the generic deny reason names no marker. A scoping false positive therefore converts into a hard, user-visible stall.

Design history context: `marker_is_live()` deliberately dropped CLAUDE_PID scoping (#5684 comment at `scripts/hook-bg-poll-guard.sh:466`) because hook input carries no session identifier, relying on "per-session tmpdir" for isolation. That isolation only exists on the branches that were later explicitly clone-gated (#5925 tmpdir-var refs, #5948 Read task-output plus Monitor/TaskOutput, #6080 Bash task-output). The remaining ungated branches are the residue of that decision.

## Suggested fix(es)

1. **Structural, kills the class:** hoist clone ownership filtering into the live-marker collection loop so markers from non-matching clones never enter `live_dirs_file`/`live_markers_file` and can never deny anything in the session: Bash, Read, Monitor, TaskOutput, waiter denials, or probe clamps. This also fixes the sole-live-dir clamp binding and the cross-clone attribution of `bg-poll-guard-denials.count`. Two candidate ownership signals: (a) the existing `bash_probe_target_dir_plausible` cwd-tag vs marker-dir-tag correlation (`scripts/hook-bg-poll-guard.sh:721-743`), which retains the accepted #5684/#5925 same-basename collision; (b) stronger: the `.larch-keepalive` `CLONE_PATH` comparison that the #5927 fix already added to `hook-no-progress-guard.sh` as `marker_foreign_clone()` (lines ~78-95, applied on its Stop and UserPromptSubmit paths) — path equality has no same-basename collision, the sidecar already exists in session dirs (verified present in the larch7 incident dir), and fail-safe semantics for missing/unparsable keepalive are already worked out there. Prefer (b) with (a) as fallback, or share one helper across both hooks.
2. **Diagnosability:** exempt the `.bg-wait-active` marker file itself from Bash/Read denial (reading a five-line marker is not progress polling), and append the triggering marker path, its `STEP`, and the hook's plugin version to every `permissionDecisionReason` (`json_deny`, `json_deny_monitor`, `json_deny_probe`). Static-printf constraint from #5610 still holds: build the string with printf formatting, not jq.
3. **Rollout gap:** document that guard-hook fixes reach only sessions started after the upgrade (pinned `CLAUDE_PLUGIN_ROOT`), and surface a version-skew breadcrumb, at minimum the hook version in deny reasons from (2), optionally a `sessionstart-health` comparison of the session's plugin root against `installed_plugins.json`.
4. **Tests** in `scripts/test-hook-bg-poll-guard.sh`: (a) foreign-clone marker never denies Bash containing the foreign dir path from a non-matching cwd; (b) foreign-clone marker never denies Read under the foreign marker dir; (c) marker-file read allowed under a live same-clone marker; (d) deny reason contains marker path and STEP; (e) probe clamps never bind the sole live dir across clones; (f) same-clone denials still fire (no regression on the guard's core purpose).

## Open questions

- Collection-time gating fail-open semantics: when hook-input `cwd` is empty or uncorrelatable, plausibility is false and collection-time filtering would drop all markers, disabling the guard for that call. Today's gated branches already behave this way. Confirm `cwd` is always present in PreToolUse input, or keep the current per-branch behavior for the empty-cwd case.
- Should the marker-read exemption cover only basename `.bg-wait-active`, or also `.completed/*` sentinels for foreign clones? Under fix (1) foreign-clone reads are allowed wholesale, so the exemption mainly matters for same-clone self-diagnosis.
- Should both hooks converge on one ownership mechanism (`marker_foreign_clone()` `.larch-keepalive` `CLONE_PATH` comparison, per #5927) instead of `bg-poll-guard` keeping the weaker basename-tag heuristic? If yes, does the shared helper live in each hook (contract-bearing hooks stay self-contained per `BASH_AUTHORING.md`) or is duplication acceptable here?
- Is there any legitimate cross-clone coordination pattern (e.g. `/design` in clone A intentionally inspecting clone B's run) that fix (1) would newly allow and that should instead stay denied? None identified in skills, but confirm during design.
