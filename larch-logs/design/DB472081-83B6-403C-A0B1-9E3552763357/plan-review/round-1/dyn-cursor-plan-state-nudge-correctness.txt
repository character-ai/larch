### 1. correctness — `skills/learn-from-bugs/SKILL.md`

The plan’s edge case (“Dirty tree during marker commit: commit only the marker path”) matches a real failure mode. The repo already isolates single-path commits via `python/cli.py git commit --only` (see `docs/linting.md` `make test-git-commit-only` and `SECURITY.md` malformed-manifest recovery). The plan only says “commit only that path” without naming that helper, so a default `git add && git commit` can still ship unrelated staged work.

**Suggested revision:** Pin the skill to `python3 "${CLAUDE_PLUGIN_ROOT}/python/cli.py" git commit --only` with a single path argument for `config.LEARN_FROM_BUGS_STATE_RELPATH`.

### 2. completeness — `skills/learn-from-bugs/SKILL.md:60`

`run_prepare` in `python/larch/issue/learn_from_bugs.py` currently emits keys like `ISSUES_SELECTED` and `REPO` (lines 279–296). The plan adds `HIGHEST_CLOSED_ISSUE_NUMBER_SCANNED` for `write-state`, but the shipped skill’s Step 2 KV list at line 60 does not include it. Without that binding, `write-state --highest-closed-issue-number-scanned` may be omitted and the marker loses required audit context.

**Suggested revision:** Extend the Step 2 parse list and document retention through Step 4.

### 3. completeness — `skills/learn-from-bugs/SKILL.md:86-99`

Acceptance requires “A `/learn-from-bugs` run updates the committed marker.” The plan’s Step 4→5 addition is prose-only: no fence showing `write-state` arguments (`--repo`, `--search`, `--state`, `--selected-count`, `--highest-closed-issue-number-scanned`, `--root`) sourced from Steps 1–2, and no commit fence. Other larch skills use explicit Bash blocks for mechanical steps; this gap makes incomplete markers or wrong commits likely.

**Suggested revision:** Add two consecutive fences after Step 4 report print: `learn-from-bugs write-state …` with full argv bindings, then isolated `git commit --only`, with hard stop before Step 5 on failure.

### 4. risk-integration — `.claude/skills/audit-runs/SKILL.md:346-365`

Report-contamination controls are good (“Do not modify audit counters…”, “chat-only”, non-fatal `gh` failure). The plan wires `bugs-backlog-nudge` “after scan results exist and before report filing” but does not update the **Revised Orchestrator Flow** ASCII block (lines 348–365), which still jumps from `scan-run` to `compute-counters` with no nudge step. That gap can cause the nudge to run too late, be skipped on some branches, or be conflated with report authoring despite the chat-only rule.

**Suggested revision:** Add one line to the flow diagram: `python/cli.py audit-runs bugs-backlog-nudge` after all `scan-run` calls and before `compute-counters`, plus an anti-pattern bullet: never include nudge stdout in the filed audit-report body.
