After the bgjob migration (blocking issue; see "Replace run_in_background/task-notification waits with larch-owned daemons"), nothing in larch launches Bash `run_in_background` tasks, so the entire defense stack built against spurious `&lt;task-notification&gt;` storms is dead weight: ~2,240 lines of guard hooks, ~2,310 lines of their harnesses, the writer-parity lint (the coverage lint was repurposed in place as the permanent inverse guard and stays; see the section C correction), four sidecar state files, and several thousand words of orchestrator prose that ride along in every session. This issue removes all of it. The blocking issue deliberately leaves this stack in place (inert) so the two PRs are independently revertable.

Everything below is enumerated from a repo audit on 2026-07-06; paths are repo-relative. Where a file is dual-use, the split is stated explicitly.

&gt; **NEVER wait on harness background tasks.** **Why**: Bash `run_in_background` task-notifications are undocumented, fire before process exit, re-fire on turn-end, and cannot be intercepted or suppressed by hooks (anthropics/claude-code#74982), which produced the #5240/#6478/#6508 token-burning loop family; larch therefore waits only on its own daemons. **How to apply**: launch long steps only through `python3 python/cli.py bgjob start` and wait only by looping `python3 python/cli.py bgjob wait` exactly as specified in `skills/shared/bgjob-wait.md`, with no other tool call, Read, sleep, or prose between wait calls; never pass `run_in_background: true`, and never use Monitor, TaskOutput, or `ScheduleWakeup` to await step completion. **CI-backed**: yes — the run_in_background skills lint and the bgjob-wait harness pin this rule.

&gt; - **Long-running steps run as larch-owned daemons, never as harness background tasks.** Launch with `python3 python/cli.py bgjob start` and wait by looping `python3 python/cli.py bgjob wait` per `skills/shared/bgjob-wait.md`; make no other tool call and print no prose between wait calls.
