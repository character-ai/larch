# [BUG] repair-loop exhaustion emits NEXT_ACTION=stall instead of main-agent-edit;…

## Summary

When `checks repair-loop` exhausts its helper repair iterations and returns `LOOP_STATUS=exhausted`, it emits `NEXT_ACTION=stall` instead of `NEXT_ACTION=main-agent-edit`. The stall-recovery classifier then classifies step3/step6 stalls as `FAILURE_CLASS=contract-failure / RESUME_HINT=none`, so the main agent never gets a repair opportunity. The main agent can often fix trivial lint violations (missing blank lines, unused variable warnings, path format errors) in seconds using Edit calls. Helper phases must not be the final stall decider.

## Original report

repair-loop should never return STALL; main agent must always get a repair opportunity. Only main agent can declare STALL, never a helper.

Context: during /implement run F608FD97 (issue #6806), `checks repair-loop --site step3` ran for 1170 seconds, returned `LOOP_STATUS=exhausted NEXT_ACTION=stall`. The checks failures were trivially fixable lint violations (MD012 double blank lines, SC2034 unused vars, S030 wrong path format in comment). The stall-recovery classifier then produced `FAILURE_CLASS=contract-failure / RESUME_HINT=none`, so no main-agent repair attempt was ever made. The main agent could have fixed all three issue types in seconds with Edit calls.

Desired behavior: repair-loop exhaustion should return `NEXT_ACTION=main-agent-edit` (not `NEXT_ACTION=stall`). Main agent then inspects the failures, applies inline edits, and re-runs the checks composite. Only if the main agent itself cannot fix the failures does it declare STALL. Helper phases (repair-loop, lint-fix) must never be the final stall decider.

## Reproduction scenario

1. Run `/implement &lt;issue-N&gt;` on a branch that has trivially fixable lint violations (MD012, SC2034, S030).
2. Step 3 emits `NEXT_ACTION=checks-failed`; the Checks Failure Entry Macro invokes `checks repair-loop --site step3`.
3. The lint-fix agents run for several minutes, make some changes, but fail to fully resolve all lint errors.
4. `run_check_fix_loop` exhausts its iteration cap; `loop.status = "exhausted"`.
5. `_repair_loop_action` falls through to `return "stall"` because "exhausted" matches none of the early-return branches.
6. The repair loop emits `NEXT_ACTION=stall LOOP_STATUS=exhausted`.
7. The main agent seeds `STALL_TRACKING=true` and enters Step 18.
8. `stall-recovery classify` is called; since `STALL_STEP=3`, `_classify_text` returns `("contract-failure", "none", "step-contract")` immediately.
9. No main-agent edit attempt is ever made.

## Expected behavior

After `run_check_fix_loop` exhausts its iterations (status `exhausted`), `_repair_loop_action` should return `"main-agent-edit"` (same as for `"no-changes-stale"` on supported sites). The main agent then reads the failure log, applies inline edits to fix the remaining lint violations, and re-runs the checks composite. Only if the main agent itself cannot clear the checks failures does it declare STALL and enter Step 18.

## Observed behavior

`_repair_loop_action` in `python/larch/implement/checks_lint_fix.py` returns `"stall"` for `LOOP_STATUS=exhausted` because the function only catches `"ok"` (continue), `"main-agent-required"` (main-agent-edit), and `"no-changes-stale"` on supported sites (main-agent-edit). The `"exhausted"` status falls through to the unconditional `return "stall"` at line 276.

The stall-recovery classifier (`python/larch/state/_classify.py`, `_classify_text`) compounds this: any stall with `step in {"3", "6"}` immediately returns `("contract-failure", "none", "step-contract")` before inspecting the failure text, so even if the repair loop did reach stall legitimately, the classifier gives no resume path.

## Root cause analysis

**Primary root cause**: `_repair_loop_action` in `python/larch/implement/checks_lint_fix.py` lines 258-276 has no branch for `loop.status == "exhausted"`. The existing "no-changes-stale" branch (via `_populate_no_changes_stale_ledger`) only fires when the fixer made no changes at all. When the fixer made partial changes but checks still fail after all iterations, the status is `"exhausted"` and the function returns `"stall"` unconditionally.

**Contributing factor**: `_classify_text` in `python/larch/state/_classify.py` lines 171-172 hard-codes `step in {"3", "6"}` to `"contract-failure"`. This means any stall routed through step3/step6 is declared unrecoverable before the failure text is examined, so legitimate helper-exhaustion stalls on step3 get the same classification as genuine contract violations.

The `_NO_CHANGES_STALE_MAIN_AGENT_SITES` frozenset already includes `"step3"`, `"step5-self-review"`, `"step5-mav"`, and `"step6"`, showing the design intent that those sites should route exhausted helpers to the main agent. The `"exhausted"` status is simply missing from the routing logic.
