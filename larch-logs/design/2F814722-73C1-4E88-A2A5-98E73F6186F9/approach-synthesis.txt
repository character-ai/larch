### Agreement
Both sketches agree on **bug location**: the prune logic in `upgrade-larch.sh` (lines ~258-358) sorts cached versions by semver ascending and drops the lowest — which is incorrect when install order does not match version order.

### Divergence (contested decision)
**DECISION_1: Source of truth for "installed"**
- **Chosen**: cache directory state itself (per Round 1 user resolution: "Installed == Present in Cache"). Use cache-directory **mtime** as the recency signal; do NOT introduce a new persistent history file.
- **Alternative (Codex)**: persistent `installed-history` text file, append-only, consulted during prune.
- **Tension**: a separate history file would track install events explicitly and survive cache state changes, but it adds new persistent state, a migration path, and corner cases (stale entries, history-vs-cache divergence, file corruption, multi-user systems). The user's Round 1 clarification was emphatic: no separate concept; the cache IS the source of truth.
- **Impact**: High — sets the entire data-model direction of the fix.
- **Affected files**: `skills/upgrade-larch/scripts/upgrade-larch.sh`, possibly `scripts/write-session-env.sh`, `skills/upgrade-larch/scripts/test-upgrade-larch-prune.sh`.
- **Resolution direction (user-bound from Round 1)**: mtime-based, no history file. The Codex history-file proposal is rejected; the user has already considered and refused that direction in Round 1.

### Architectural decisions (synthesis)
1. **Prune eviction order**: change the trim loop in `upgrade-larch.sh` from version-asc to mtime-asc (oldest mtime evicted first). All existing protection pins (LATEST_STABLE, executing cached PLUGIN_ROOT, active-session-pinned versions) stay in force.
2. **Newer-than-LATEST_STABLE auto-prune**: keep current behavior unchanged (still drops cache entries with version > LATEST_STABLE, modulo session pins).
3. **Mtime refresh on session boot**: when `write-session-env.sh` (or a session-setup helper) writes `LARCH_CLAUDE_PLUGIN_ROOT=<value>` to `session-env.sh`, also `touch` the corresponding cache directory so its mtime reflects the most recent use. This makes "actually-used older versions" naturally protected from prune.
4. **Cap stays at 8** — no change.
5. **First-run / fresh-install behavior**: mtime ordering Just Works on first run because every cache directory has some mtime (set when `claude plugin install` created it). No bootstrap migration needed — no history file means no bootstrap problem.

### Tradeoffs and risks
- **Cross-platform stat**: mtime extraction needs both BSD (macOS) and GNU (Linux) variants. Use `ls -t` (sorts by mtime descending across both) or a portable `stat` wrapper. Failure mode: silent stat failure produces wrong ordering — must add a guard.
- **Test determinism**: regression tests seeding mtimes need to use `touch -t YYYYMMDDhhmm` or similar; cases that previously relied on version-asc order will need explicit mtime seeding.
- **Session-boot side effect**: touching the cache directory from `write-session-env.sh` adds a filesystem write on every session start. Cheap, but new code path — must not fail the session-setup on touch error (best-effort with stderr warning).
- **Concurrency** (low risk): if two sessions start simultaneously, both touch the same cache dir; idempotent.
- **Mtime resolution**: filesystem mtime is typically 1-second granularity; two sessions starting within the same second can have indistinguishable mtimes for different directories. Edge case, not a real problem since the cap is 8 (collisions only matter if exactly the 9th entry shares a second with the 8th).
- **No history file** means we cannot distinguish "version downloaded by marketplace cache" from "version actually run". Per user's Round 1 resolution, this distinction is collapsed: anything in cache counts as installed, ranked by mtime.
