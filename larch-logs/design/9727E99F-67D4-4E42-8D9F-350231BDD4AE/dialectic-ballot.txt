### DECISION_2: DEFERRED phase guard for `phase_coder_select`

Defense A (defends ALTERNATIVE — keep existing strict guard that skips coder phase on DEFERRED=true):
<defense_content>
Widening `should_run_post_tracking_phase` so `phase_coder_select` runs whenever plan materialization would run fixes a real regression: after the SKILL.md waterfall is deleted, `DEFERRED=true` paths that still materialize `plan.txt` (POSTED=false metadata defer, forked-target with plan) would otherwise emit empty `coder=` while `run-step2-dispatch.sh` requires `--coder`, matching the Phase 3 rationale that deferred tracking must not block Step 2 inputs.

Keep `should_run_post_tracking_phase` strict (DEFERRED still skips `phase_coder_select`) and resolve implementer choice in the collapsed Step 0 KV routing table from keys bootstrap already emits, instead of reclassifying DEFERRED as a coder-phase trigger.

`scripts/implement-bootstrap.md` documents an intentional Phase 3 vs Phase 4 split: permissive `should_run_phase_plan_materialize` allows `DEFERRED=true` so Step 2 gets plan files, while stricter `should_run_post_tracking_phase` also skips when `DEFERRED=true` (`scripts/implement-bootstrap.md:97`). `should_run_post_tracking_phase` is only consumed by `phase_coder_select` (`scripts/implement-bootstrap.sh:184-188`, `1085-1098`), and `B4-all` locks the contract that DEFERRED runs skip Phase 4 without stub bail overwrite (`skills/implement/scripts/test-implement-bootstrap.sh:801-803`).

[tool]-Edge is correct that deleting the prompt-side waterfall without any replacement leaves `coder=` empty on DEFERRED-but-implementing runs while Step 2 still calls `run-step2-dispatch.sh` with `--coder "$coder"` (`skills/implement/SKILL.md:885-887`, `skills/implement/scripts/run-step2-dispatch.sh:58`).

That gap does not require widening the guard: `emit_final_tail` already ships `codex_available` / `cursor_available` on every path (`scripts/implement-bootstrap.sh:935-936`), so collapsed Step 0 can add one routing row—if `coder=` is empty and `IMPLEMENT_BAIL_REASON` is empty, map from those KV lines (or forward `--coder` argv into bootstrap only when `should_run_post_tracking_phase` is true)—without changing phase-skip semantics, rewriting the Phase-skip section, or extending `B4-all` to assert coder population inside bootstrap on DEFERRED.

If DEFERRED paths reach Step 2 with neither bootstrap `coder=` nor a routing-table fallback, dispatch fails at `--coder is required` and fork/POSTED=false implement runs stall despite valid `plan.txt`.
</defense_content>

Defense B (defends CHOSEN — widen `should_run_post_tracking_phase` to permissive predicate matching plan-materialize; DEFERRED no longer skips coder):
<defense_content>
Keeping the strict guard is the lowest-change path because `DEFERRED=true` currently means post-tracking phases should not run, and changing that meaning could make metadata-deferred runs perform more work than operators expect. The orchestrator could instead treat `DEFERRED=true` as a Step 2 short-circuit and preserve existing phase-guard semantics.

`should_run_post_tracking_phase` should be widened to match `should_run_phase_plan_materialize` so every deferred-but-implementing path that materializes a plan also resolves a non-empty `coder` before Step 2 dispatch.

The current guard skips on `DEFERRED=true` at `scripts/implement-bootstrap.sh:184-188`, while plan materialization explicitly ignores `DEFERRED` and only checks bail, stall, and repo availability at `scripts/implement-bootstrap.sh:190-194`; the `coder` and `all` phase paths then call `phase_coder_select` only through the stricter guard at `scripts/implement-bootstrap.sh:1082-1098`. The contract documents the mismatch: Phase 3 allows forked targets and `POSTED=false` defers so Step 2 receives plan files, but Phase 4 still skips on `DEFERRED=true` at `scripts/implement-bootstrap.md:95-97`. Step 2 then unconditionally invokes `run-step2-dispatch.sh --coder "$coder"` at `skills/implement/SKILL.md:885-887`, and the B4-all deferred test currently asserts plan materialization without asserting any populated coder at `skills/implement/scripts/test-implement-bootstrap.sh:794-820`.

The opposition is right that widening the guard changes runtime semantics for `DEFERRED=true`, and that is not a purely mechanical stub replacement.

That semantic change is exactly where the ownership should move: once Step 0 owns coder selection end-to-end, leaving `DEFERRED=true` as a coder-skip trigger creates a split-brain contract where bootstrap prepares Step 2 inputs except the one required dispatcher argument.

If this position loses, deferred-but-implementing paths can leave `coder` empty after successful plan materialization, pushing a preventable Step 2 dispatch failure into prompt-side handling and tests that do not pin the required invariant.
</defense_content>
