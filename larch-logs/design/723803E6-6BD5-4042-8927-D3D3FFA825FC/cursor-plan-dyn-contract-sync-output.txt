### Findings

1. **correctness** — `scripts/test-design-structure.sh:59-61` (plan § `test-design-structure.sh`): The new structural assertion `publish_upsert_line < publish_rename_line < publish_log_line` conflicts with the real tail order `upsert → design-log-publish --scrub-only → rename → design-log-publish (full)`. `publish_log_line` is already defined at line 634 as the **first** `design-log-publish.sh` match (scrub-only), so rename will sit **after** that line, not before it. Revise the pin to compare rename against the **last** publish invocation (or a separate `publish_scrub_line`).

2. **correctness** — `skills/design/scripts/test-design-publish.sh:246-254` (plan § happy-path ordering): The harness still treats the first `design-log-publish` log line as `publish_pos`. With two calls, that is `--scrub-only`, so the planned `plan→upsert→rename→publish→marker` check will fail on correct code (`rename_pos` > first `publish_pos`). Use the **last** `design-log-publish` entry (full flush) for `publish_pos`, or filter out `--scrub-only`.

3. **correctness** — `skills/design/scripts/design-publish.sh:326-367` + plan `render-final-summary.sh` bullet (~87-89): The plan tells `append_failed_publish_notes` to read `RENAMED` from `.design-publish-result.env`, but `design-publish.sh` calls `render-final-summary.sh` **before** `write_result_env_and_emit` (lines 326-330 vs 367). On `failed-publish` after a successful early rename, the summary cannot see `RENAMED=true` from the result env. Export `RENAMED` into the environment (same pattern as `DESIGN_LOG_*`) immediately before render, and document/test that path—not result-env read alone.

4. **risk-integration** — `skills/design/scripts/test-design-publish.sh:78-91` (plan § `SCRUB_OK=false` / happy path): The publish stub does not implement `--scrub-only` or `SCRUB_OK=`. The new driver will invoke scrub-only first; without stub support, happy-path rename gating and the new negative case are untested or falsely red. Extend `write_stubs` so `--scrub-only` emits `SCRUB_OK=true|false` without treating the call as a full flush.

5. **latent** — `scripts/test-design-structure.sh:1328-1329`: The existing `(25)` check `publish_log_line < publish_marker_line` will also anchor on the **first** `design-log-publish.sh` line after this change, so it no longer proves the reentry marker runs only after the **full** flush. When touching `(25)`, consider pinning `tail -1` (full publish) `< publish_marker_line` so marker placement cannot regress between scrub and flush.
