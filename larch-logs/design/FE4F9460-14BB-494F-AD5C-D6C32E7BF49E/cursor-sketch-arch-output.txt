Reviewing the aggregator script, its docs, tests, and how `/review` invokes it.
## Architecture review: guarded aggregator containment relaxation

### 1. Key architectural decisions

The right place for this change is the **preflight path contract** in `aggregate-findings.sh`, not in `review-core.sh`, `plan-review-loop.sh`, or `dispatch-with-waterfall.sh`. Containment is enforced today in one early block: canonicalize `--review-tmpdir`, reject symlinked `--findings-file`, canonicalize the findings path, then prefix-match against `REVIEW_TMPDIR_CANON` (lines 46–62). That matches how larch scripts usually layer security: **argv-visible, default-off escape hatches** alongside env-based ones like `LARCH_AGGREGATOR_DISABLED` (documented in `aggregate-findings.md`).

Reuse the existing **boolean `true|false` flag pattern** used for `--codex-present` / `--cursor-present`: parse in the `while` loop, default `ALLOW_FINDINGS_OUTSIDE_TMPDIR=false`, validate after required args, and gate only the `case "$_findings_canon"` rejection branch while keeping canonicalization. Symlink rejection at line 50 should stay **before** flag-gated logic and stay unconditional — that preserves the script’s “regular file, not a symlink” invariant without opening traversal via links.

Keep the **asymmetric containment model**: relax **input** (`--findings-file`) only; leave dispatch **output** containment at lines 735–744 unchanged (`_cand_canon` must still resolve under `--review-tmpdir`). That fits the multi-round layout from R4/FINDING_2: `findings-in-scope.md` can live at `round-N/` while `agg-in-scope/` is the aggregator scratch dir, without letting vendor output land outside the review tmpdir. No shared library is needed; the repo already uses inline `pwd -P` + prefix `case` (e.g. stall-recovery, token/timing ledgers). The discoverability suffix on the rejection message is the right audit surface given the explicit choice of **no** stderr breadcrumb or `execution-issues.md` entry when relaxation is active.

### 2. Files/modules to modify (and layering)

| Surface | Role | Why here |
|--------|------|----------|
| `skills/review/scripts/aggregate-findings.sh` | Implementation | Single owner of input path policy, argv contract, and merge pipeline |
| `skills/review/scripts/aggregate-findings.md` | Contract doc | Documents CLI next to `LARCH_AGGREGATOR_DISABLED`; line 8 already states findings “under `$REVIEW_TMPDIR`” — update that and add an “Escape hatch” bullet for the new flag |
| `skills/review/scripts/test-aggregate-findings.sh` | Regression | First coverage of outside-tmpdir reject/allow (none exists today) |

**Out of scope (by design):** `review-core.sh` (always passes `findings.md` under `REVIEW_TMPDIR`), `plan-review-loop.sh` (today passes `findings-in-scope.md` under `DESIGN_TMPDIR` — still valid), future multi-round callers that will opt in later. That respects single responsibility: path policy stays in the aggregator; orchestrators only pass paths.

**Layering check:** No SRP violation if you resist widening the flag to dispatch output or symlink rules. `aggregate-findings-phrases.inc.bash` and the embedded `aggregate-validate.py` heredoc should stay untouched — validation semantics are unrelated to where the ballot file lives on disk.

**Suggested test shape:** two cases in the existing harness style — `mktemp` sibling dirs, ballot outside `review-tmpdir`, stub `AGGREGATE_DISPATCH_SH` so preflight is the variable under test; assert exit `2` + hint without flag, and preflight success (or reach stub dispatch) with `--allow-findings-outside-tmpdir=true`. Optionally assert symlink rejection still fails even with the flag.

### 3. Tradeoffs: maintainability vs convenience

**Flag vs staging:** Staging `findings-in-scope.md` into each `agg-*` dir would preserve today’s contract without a new flag but duplicates artifacts and complicates two-pass OOS round-trips. The explicit flag trades a small CLI surface for a stable per-round directory layout; default-off preserves byte-equivalent behavior for all current `/review` call sites (`review-core.sh` lines 517–522 never pass the flag).

**Explicit flag vs env var:** A `LARCH_*` env would match `LARCH_AGGREGATOR_DISABLED` but is easier to inherit accidentally across subprocesses. Required argv `true|false` makes opt-in visible in logs and tests — aligned with “the flag is the audit signal.”

**Relax input only:** Convenient for multi-round partition 2; maintainers must remember output paths are still confined. Document that asymmetry in `aggregate-findings.md` so future callers do not assume “outside tmpdir” applies to dispatch artifacts.

**No runtime warning when relaxed:** Keeps stderr/execution-issues noise down but shifts burden to code review and `/design` wiring when `plan-review-loop.sh` (or a future loop driver) starts passing the flag. A follow-on partition should add the flag only where the directory layout requires it.

**Canonicalization without containment:** When the flag is `true`, paths outside tmpdir are still resolved to absolute form — good for consistent `mv` back to `FINDINGS_FILE`, but callers must ensure the ballot is a regular file in a trusted tree (symlink guard remains the main filesystem hardening on input).
