## Plan

Add `rebase-failed` to the stall classifier's recognized STALL_STEP token set so that a rebase conflict during ship-pr routes to `RESUME_HINT=step8-shippr` rather than falling through to `unrecoverable` / `none`.

### Root cause (confirmed from code)

`python/finalize.py:postbump()` returns `status="rebase-failed"` when `_rebase_no_push()` returns `"failed"`. `python/ship.py:run_ship()` writes `STALL_STEP=rebase-failed` and `PHASE=rebase-failed` to state files. Then:

1. `safe_step_value("rebase-failed")` → `unknown` (not in the closed enum)
2. `classify_from_evidence("rebase-failed", ...)` → `unrecoverable` (no heuristic pattern matches the raw step token)
3. `resume_hint_for("unrecoverable", ...)` → `none` immediately (class check short-circuits before step routing)

Result: terminal failure with no retry dispatch, even though the operator could resolve the conflict and re-ship.

### Auto-dispatch and same-cause-repeat safeguard

After the fix, `rebase-failed` classifies as `transient-infra` / `step8-shippr`. Step 18a will attempt one auto-dispatch back to Step 8. If the conflict is not yet resolved, postbump will fail again with the same signature. The existing `same-cause-repeat` check in `stall-recovery.md` Step 5 ("only after classification produces the same sanitized signature again does it become `same-cause-repeat`; that follow-up classification emits `RESUME_HINT=none`, so do not redispatch the same step automatically") caps this at 1 wasted retry. The primary value of the fix is enabling operator-driven retry: after the operator manually resolves the conflict and the branch is rebased, the step8-shippr retry succeeds. Without the fix, `RESUME_HINT=none` makes no retry possible even after operator resolution.
