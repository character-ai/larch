# [BUG] /design Step 5c: anti-poll violation skips final-summary.md generation

## Context

During a `/design` run for issue #3686 (sh-to-py C5: research/eval pipeline), `final-summary.md` was not generated and `.design-publish-result.env` was absent after `design-step5c.sh` completed (background task, exit code 0). The design had 5 review rounds; the issue was renamed to `[DESIGNED]`, the `larch:plan` block was written, and design log PR #4212 was created — the publish succeeded.

## Symptoms

1. `final-summary.md` absent when Step 6 ran.
2. `.design-step5c-status.env` absent at Step 6 time.
3. `.design-publish-result.env` absent immediately after background task launched.
4. Task output file was 0 bytes.
5. Step 6 printed "missing Step 5c status sidecar; preserving tmpdir for recovery" and skipped cleanup.

All three artifacts were written correctly ~6 minutes after launch when `design-publish.sh` completed:
- `.design-step5c-status.env`: `PUBLISH_OK=true`, `PUBLISH_RC=0`, `CLEANUP_ELIGIBLE=true`
- `.design-publish-result.env`: `PLAN_WRITE_OK=true`, `PUBLISH_OK=true`

## Root Cause

**Anti-poll violation.** SKILL.md Step 5c specifies:

> **Immediate-background wait rule**: After the `Command running in background` ack, print only the permitted breadcrumb/status table. Then **END THE TURN**. `<task-notification>` is the only resume trigger.

The orchestrator violated this rule. Immediately after the `run_in_background: true` launch ack for `design-step5c.sh`, it ran foreground Bash tool calls to check the result:

1. Read `.design-publish-result.env` → absent (`design-publish.sh` still running).
2. Checked task output → 0 bytes (no output yet).
3. Ran `design-step6.sh` → saw missing status sidecar → preserved tmpdir.

`design-publish.sh` takes several minutes: it runs `design-log-publish.sh` which performs git operations (clone worktree, branch, commit, push, PR create). The `<task-notification>` for the task arrived ~6 minutes after launch, during the user's next turn — confirming the task was still running when Step 6 executed.

The premature reads found empty/missing files not because publish failed but because `design-publish.sh` had not yet written them. Step 6 treated this as a publish failure and preserved the tmpdir.

## Suggested Fix

### 1. Orchestrator behavioral fix (no code change needed)

SKILL.md already has the correct rule. The orchestrator must end the turn after the `run_in_background: true` launch ack for `design-step5c.sh` and not read any tmpdir files until the `<task-notification>` fires.

### 2. Defensive guard in `design-step6-prelude.sh` (low-effort code change)

When `.design-step5c-status.env` is missing, check whether the background task marker `.bg-wait-marker-design-step5c` is still present. If so, emit a hard error instead of silently treating it as a failed publish:

```
**⚠ Step 6: design-step5c.sh appears still in-flight (.bg-wait-marker-design-step5c present);
   do not proceed until <task-notification> fires — re-run /design from this step.**
```

This makes the anti-poll violation visible rather than silently misclassifying a running task as a failed publish.

### 3. Test coverage

Add a test case for `design-step6.sh` that asserts: when `.design-step5c-status.env` is absent AND `.bg-wait-marker-design-step5c` is present, the prelude emits the in-flight error (not the "missing sidecar; preserving" message).

## Reproduction

1. Run `/design <large-issue>` (multiple review rounds, 900+ line plan).
2. In Step 5c, launch `design-step5c.sh` with `run_in_background: true`.
3. Before `<task-notification>` fires, run any foreground Bash call reading from DESIGN_TMPDIR.
4. Proceed to Step 6.

**Result**: Step 6 prints "missing Step 5c status sidecar; preserving tmpdir" even though the publish ultimately succeeds when the task completes.
