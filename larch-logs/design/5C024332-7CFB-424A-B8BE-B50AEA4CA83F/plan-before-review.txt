## Approach

Build a small, side-effect-free lint pipeline around frozen domain models and the existing `larch.core.proc.Runner` protocol.

1. Define the public scan models:
   - `Finding` with `path`, `line`, `rule_id`, `message`, optional `qualified_symbol`, and optional `metric`.
   - `SourceFile` with repository-relative `path`, decoded `text`, immutable `lines`, and a lazy cached Python AST.
   - `LintRule` with the approved `rule_id`, `description`, `detect`, `syntax_policy`, and `suppression_token` fields.
2. Discover tracked files through the injected runner with `git ls-files --cached`, using the validated repository root as `cwd`.
3. Normalize and validate discovered paths before reading them. Reject absolute paths, traversal, containment escapes, malformed discovery output, and entries that do not resolve to regular files inside the repository.
4. When `paths` is supplied, validate each requested file or directory and filter the tracked-file result. Always run git discovery first. Match files exactly and directories by repository-relative descendants.
5. Load source as strict UTF-8. Preserve `splitlines()` output for line-based checks and same-line suppression.
6. Parse Python only when a detector first accesses the source AST. Cache either the parsed tree or the syntax failure so repeated access does not reparse.
7. Apply the rule syntax policy:
   - `fail`: convert a Python `SyntaxError` into a deterministic rule finding at the reported line.
   - `skip`: omit that source without invoking further AST-dependent work.
8. Validate every detector result before suppression or rendering. Require a `Finding`, a positive in-range line, the current source path, the active rule ID, a non-empty single-line message, and coherent optional symbol and metric values. Treat detector exceptions and invalid output as scan errors.
9. Apply suppression only on the finding's exact source line. Require the configured suppression token and a non-empty trailing reason. Treat an empty reason as an error rather than silently suppressing the finding.
10. Sort accepted findings by stable repository-relative fields, then render each as `path:line: RULE_ID message`.
11. Buffer the scan result before writing streams. Print findings to stdout only after the full scan validates. Print operational, path, decoding, detector, and suppression errors to stderr.
12. Return `0` for a clean scan, `1` for valid findings, and `2` for validation or execution errors. Do not write files.

## Edge cases

- Git may return duplicate entries, blank records, separators, or paths that become unsafe after resolution. Reject malformed paths and deduplicate valid tracked paths before loading.
- Requested directories may contain tracked and untracked files. Include only files present in git discovery.
- An empty requested directory match is a valid clean scan, not a discovery failure.
- A detector may return duplicate findings. Preserve a deterministic result while defining and testing whether exact duplicates collapse or render once.
- `SyntaxError.lineno` may be absent or outside the loaded line range. Normalize it to a deterministic valid line for rendering.
- A final source line may lack a newline. Same-line suppression must still inspect it.
- Messages, symbols, paths, and rule IDs must not inject extra rendered lines.

## Failure modes

- Invalid root or path input returns `2` before any source scan.
- Git discovery failure returns `2` with the runner's bounded diagnostic on stderr.
- UTF-8 decoding or file-read failure returns `2`.
- A syntax failure follows the active rule policy rather than becoming an uncaught exception.
- A detector exception, malformed finding, or malformed suppression returns `2`.
- Errors win over findings. Buffer output so an invalid later source cannot leave misleading partial findings on stdout.
- No error path writes a baseline, cache file, or repository artifact.
