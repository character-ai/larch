   ```python
   def split_all_blocks(text):
       parts = re.split(r"(?m)^(?=### (?:FINDING|OOS)_[0-9]+:)", text)
       fins, oos = [], []
       for p in parts:
           p = p.strip()
           if not p:
               continue
           m = re.match(r"^### (FINDING|OOS)_[0-9]+:", p)
           if not m:
               continue
           (fins if m.group(1) == "FINDING" else oos).append(p)
       return fins, oos
   ```

## Approach

The bug is localized to two lines (`fins = split_blocks(raw, "FINDING")` / `oos = split_blocks(raw, "OOS")`) and one helper definition (`split_blocks(text, prefix)`). Option A from the issue body is preferred over Option B (trim trailing content per block) because (a) the diff is smaller (one helper replaces one), (b) the unified splitter eliminates the asymmetry between FINDING and OOS handling at the source rather than patching it twice, and (c) the unified regex `(?m)^(?=### (?:FINDING|OOS)_[0-9]+:)` is a faithful structural match — every block boundary is now an actual heading boundary, not a prefix-conditional one.

Downstream code paths (LLM aggregator on `findings-in-scope.md`, ballot composition, tally, voting) require no changes: they consume the dedup output, and once the dedup produces well-formed blocks, the bug is closed at the source.

## Edge cases

- **Empty input** (`raw` is empty or whitespace-only): `re.split` with a lookahead on empty string returns `['']`; the loop's `if not p: continue` and the `re.match` guard collectively drop empty/non-heading chunks. `fins` and `oos` both end up empty — same behavior as the current code.
- **Single heading with no body**: the chunk `### OOS_1:\n` passes `re.match`, body is empty, classified into the right list. Renumbering at line 466 still works (acts on the heading line only).
- **Mixed FINDING and OOS interleaved in a single reviewer's contribution**: the unified splitter breaks at every heading regardless of kind, so each block is cleanly bounded by the next-heading lookahead. Each block carries only its own heading + body.
- **Leading blank-line padding** (from `_findings_tmp` concatenation): `re.split` with `(?m)^` matches at line start; the leading whitespace is captured into the preceding chunk (or the prefix-before-first-heading) and discarded by `p.strip()`.
- **Dedup merging across reviewers**: the existing `dedup()` runs on cleanly-bounded blocks now, so its Jaccard similarity check on `what_text` operates on the correct concern text rather than on multi-block tails. This may legitimately collapse semantically-duplicate findings across reviewers, which is the intended behavior (and was already happening for the FINDING side; the OOS side now joins that behavior cleanly).

## Failure modes

- **Risk: the new regex over-matches a literal `### FINDING_5:` inside fenced code** — out-of-scope: the dedup input is reviewer-emitted markdown from controlled TSV emission (Python `emit_finding` / `emit_oos` at lines 305-324), which never wraps headings in code fences. Mitigation: continue trusting the TSV emitter contract.
- **Risk: aggregator (LLM step at lines 513+) re-introduces duplicates downstream** — the aggregator runs on `findings-in-scope.md` (extracted via the already-correct regex at lines 499-504). Even on the buggy code today, the aggregator's global renumbering masks any leaked FINDING duplicates. The fix removes the leak at the source, so the aggregator never sees duplicates either.
- **Risk: regression test passes against current buggy code if FINDING dedup happens to work** — guarded by also asserting OOS heading uniqueness (the explicit failure mode in #2764).
