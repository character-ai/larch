### Summary

Add an additive `--with-plan-size` mode to `design-postplan-emit.sh` that runs
`check-plan-size.sh` after a successful emit and maps the merged
emit + validate + plan-size verdict to thin-fence **action exit codes**. The
three prompt-side fences that today run `design-postplan-emit.sh` then a
standalone `check-plan-size.sh` collapse to one driver call plus a thin
`call → echo → case rc` fence. `check-plan-size.sh` keeps its current logic and
stays standalone-callable.

### Approach

- The driver, with `--with-plan-size`, after the existing emit → optional
  HARD snapshot → validate sequence:
  - On `VALIDATE_STATUS=defects-found`: exit **10** and **skip** the plan-size
    check (defects must be resolved first; size is re-evaluated on Fix-and-retry
    re-emit or on Override via the retained standalone Step 2b.5).
  - Otherwise run `check-plan-size.sh` and map its verdict:
    - hard trigger (`HARD_TRIGGER_FIRED=true`) → exit **12**.
    - partition route (`partition_requested=true` and no hard trigger) →
      exit **13**.
    - clean → exit **0**.
- Output discipline (matches the Step 3.6 thin-fence pilot): in
  `--with-plan-size` mode the driver writes all KVs to
  `.design-postplan-emit-result.env` (diagnostics) and emits **display** lines
  via `emit` on FD 3 — the soft mechanical-churn advisory line, the
  under-threshold breadcrumb, the `## Plan Size — Hard Trigger` /
  `## Plan Size — Partition requested` sections, and any `WARN` bodies. It does
  **not** mirror KVs to FD 3, so the orchestrator's `echo "$out"` shows display
  only (no `KEY=VALUE` noise).
- The driver reads `partition_requested` from `run-params.json` with the
  existing `json_scalar_or_sed` helper (default `false` when absent).
- Pause in `--with-plan-size` mode returns exit **11**; the orchestrator's thin
  fence `exec`s `design-pause-save.sh` (the Step 3.6 convention — a cleaner halt
  than the legacy in-subshell `exec`). The non-flag pause checkpoints are left
  unchanged.
- `check-plan-size.sh` exit 2/3 inside `--with-plan-size` is **non-fatal**: the
  driver appends a `WARN`, treats the plan as under threshold, and exits 0
  (mirrors the current standalone Step 2b.5 "proceed without threshold check").
- The driver invokes `check-plan-size.sh` via
  `${PLUGIN_ROOT}/skills/design/scripts/check-plan-size.sh`, consistent with how
  it already calls `design-driver.sh`, `snapshot-plan-round.sh`, and
  `invoke-plan-validator.sh`. The offline harness symlinks the real script (and
  its libs) into the fake plugin tree so the genuine threshold logic runs.
- Backward compatibility: without `--with-plan-size`, the driver behaves exactly
  as today — exit codes `{0,1,2}`, `defects-found` exits 0, KVs mirrored to
  FD 3, legacy in-subshell pause. No non-flag caller changes.

### Failure modes

1. **Exit-code mis-map at a site**: a fence treats an action rc as failure (or
   vice versa) → false abort or a skipped prompt. Earliest signal: harness rc
   assertions and `assert_thin_fence`. Mitigation: per-site rc-arm anchors in
   `test-design-structure.sh` and explicit rc cases in the offline harness.
2. **KV noise leaking to chat**: if `--with-plan-size` still mirrors KVs to

   Override → Step 2b.5 prose plus a `test-design-structure.sh` anchor; the
