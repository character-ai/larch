# [BUG] design-step3b-tail.sh: elif command grep under set -e aborts on macOS bash 3.2

## Summary

`skills/design/scripts/design-step3b-tail.sh` reads `skip_approve_requested` from `run-params.json` with a jq-less fallback shaped `elif command grep -Eq ... ; then` under `set -euo pipefail`. On macOS system bash 3.2.57, `command grep` inside an `if`/`elif` condition loses the `set -e` exemption: a non-zero grep exit aborts the whole script. No-match is the common case (`skip_approve_requested` is usually false), so any jq-less macOS host aborts the Step 4b tail wrapper. This is the same class as closed #3935 and #3899, and no committed-script lint enforces the sanctioned `( command grep ... )` form, so the class can recur.

## Reproduction scenario

On a macOS host with system bash 3.2.57 and **no `jq` on PATH**, run any `/design` flow that reaches the Step 4b tail (`design-step3b-tail.sh`) with `skip_approve_requested` absent or false in `$DESIGN_TMPDIR/run-params.json`. The `elif command grep -Eq ...` probe exits 1 (no match), `set -e` fires, and the wrapper aborts before `design dialectic-gatec`.

Minimal shape repro (from the #3935 investigation; macOS system bash only):

```
/bin/bash -c 'set -euo pipefail; if command grep -q nomatch /dev/null 2>/dev/null; then echo hit; fi; echo done'
```

On bash 3.2.57 `done` never prints; on bash 4+ it does. Not reproduced live in this run: the dev host has `jq`, so the fallback branch is unreachable here.

## Expected behavior

The jq-less fallback evaluates the grep probe as an ordinary `if`/`elif` condition: no match means `_skip_approve_requested_gatec` stays `false` and the script continues to the Gate C call.

## Observed behavior

Would-abort (latent): on bash 3.2.57 with jq absent, the script exits at line 154 with a non-zero status on the common no-match case. Nothing in CI or lint catches the pattern; the two prior incidents of this class (#3935 in `tally-plan-review.sh`, #3899 in `tally-code-votes.sh`) were found only by live-run stalls.

## Root cause analysis

Two layers:

1. **Site defect.** `design-step3b-tail.sh:154` uses the exact shape `BASH_AUTHORING.md` §1 marks unsafe: "on macOS bash 3.2.57, `if command grep ...; then` triggers `set -e` when grep exits non-zero. For `if` probes, use `( command grep PATTERN FILE )`". The script declares `set -euo pipefail` at line 4. The #3935/#3899 fixes swept their own files but not this sibling (the file may postdate those sweeps).
2. **Enforcement gap.** `lint-bash32` forbids feature tokens (associative arrays, namerefs, `mapfile`, case conversion, `&>>`, coprocs) but has no rule for `if`/`elif` `command grep`. `lint-bare-grep-probe` covers orchestrator-facing Markdown fences, not committed scripts. So the class has no mechanical backstop.

The harness sites (`test-lint-awk-multibyte-regex.sh:58` `if ! command grep -Fq ...`, `:87` `if command grep -Fq ...`) are stated with lower confidence: the file toggles `set -e` inside its assert helpers, and whether the negated `if !` form triggers the 3.2 divergence needs a repro.

## Suggested fix(es)

1. Rewrite `design-step3b-tail.sh:154` to the sanctioned subshell form: `elif ( command grep -Eq '...' "$DESIGN_TMPDIR/run-params.json" ) 2>/dev/null; then`. Apply the same form to the two `test-lint-awk-multibyte-regex.sh` sites if the bash-3.2 repro confirms them (or unconditionally, since the subshell form is safe on both shells and costs one fork).
2. Extend `lint-bash32` (or add a sibling committed-script lint) to flag `if command grep`, `elif command grep`, and `if ! command grep` (grep-family: `grep`, `egrep`, `fgrep`, `rg`) in committed shell scripts, with the standard `# lint-bash32: ok <reason>` suppression and a regression fixture covering the `elif` and negated forms.

3. Lint home: extend `lint-bash32` versus a new `lint-command-grep-in-if` script lint; the fix owner should match whichever keeps the suppression-pragma story consistent.
