Key architectural decision: keep the assessor separate from the per-finding voter path. `scripts/dispatch-plan-voters.sh` and `skills/shared/scripts/render-voter-prompt.sh` are tightly shaped around `FINDING_N` / `OOS_N` ballots, so a sibling holistic assessor is the cleaner boundary. I would still simplify the proposed shape: make the assessor a “best-so-far guard” rather than only `previous vs current`. Store `plan-original`, every `round-N/plan-after.txt`, and an optional `best-plan-round.txt`; assessors compare current against both previous and best-known, with output like `ASSESSMENT: IMPROVED|REGRESSED|TIE` plus `LOST_REQUIREMENTS:`. That catches the subtle failure mode where round 2 is slightly better than round 1, round 3 is slightly better than round 2, but both drift away from the original intent.

The right modification points are `skills/design/SKILL.md` around Step 2b, Step 3, Step 3.5, and Gate C(c), plus `skills/design/references/approval-gates.md` for loop semantics. Keep `skills/design/scripts/plan-review-loop.sh` mostly untouched except for honoring dynamic `--round-num`; it already has a clear single-pass responsibility. Add design-local scripts for snapshot, assessor orchestration, tally, and rollback, but consider collapsing `dispatch-plan-assessors.sh` and `assess-plan-round.sh` unless the repo’s sibling-doc/testing convention strongly favors one script per concern. Update `scripts/lib-timing-kinds.sh`, `scripts/test-design-structure.sh`, and `Makefile` because this repo pins orchestration structure aggressively.

Main tradeoff: the proposed implementation is robust but heavy. Six new scripts plus six harnesses is defensible for a shipping plugin, but it adds another review/vote subsystem to maintain. A leaner alternative is to run a single holistic “regression scout” in Claude first and launch the 3-assessor panel only when the scout sees risk. The crazy-but-plausible idea is to stop treating plan text as the state of truth: model each accepted finding as a reversible patch transaction, keep a “plan diff ledger,” and ask assessors to judge the cumulative patch set before it is committed to `plan.txt`. That would prevent death by cuts earlier, but it is a bigger conceptual shift than the current feature needs.
