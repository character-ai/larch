### DECISION_1: Where the multi-round loop controller lives
- **Chosen**: Extend the existing launcher `scripts/run-step5-review.sh` to default to multi-round dispatch (a new `--mode loop` or `--all-rounds` flag), and add the actual loop function `run_implement_loop` next to `run_implement_round` inside `skills/review-and-fix/scripts/review-and-fix.sh`. The launcher's role stays the same (resolve context, choose dispatch mode). The round primitive and the loop live in the same script, sharing helpers.
- **Alternative**: Create a brand-new wrapper script `scripts/run-step5-review-loop.sh` that reuses the launcher's context-resolution helpers (likely by sourcing or re-running them) but is otherwise an independent surface. The existing `run-step5-review.sh` stays purely per-round; the new wrapper iterates it.
- **Tension**: Codex-Innovation floated the new-wrapper option as the "cleaner" path because it isolates the new behavior in a removable file and avoids touching the existing launcher's contract. Codex-Pragmatic preferred extending the existing launcher and co-locating `run_implement_loop` next to `run_implement_round`, citing minimal surface area and the fact that the loop reuses the round primitive's helpers directly. Cursor sketches did not produce content on this question. The deeper tension: a new wrapper script keeps the dispatch architecture more "removable" (feature-flag-style) but introduces a third script (round + launcher + loop-launcher) that maintainers must learn; extending in place keeps surface minimal but bundles the new mode into already-load-bearing files.
- **Impact**: Medium
- **Affected files**: `scripts/run-step5-review.sh`, `skills/review-and-fix/scripts/review-and-fix.sh`, `scripts/run-step5-review.md`, and (Alternative only) a new `scripts/run-step5-review-loop.sh` plus sibling `scripts/run-step5-review-loop.md`
