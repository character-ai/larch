## Plan

### Approach

- Split CI Python linting into two parallel jobs to cut `python-lint` wall time. Root cause: pylint runs single-process (`-j1`) on Linux CI (~100s of the ~166s job); ruff is ~0.1s and pyright is ~36s.
  - **`python-lint`**: ruff + pylint, with pylint forced to all cores.
  - **`python-pyright`** (new): pyright only.
- Restructure the Makefile so CI runs the halves separately while local `make py-lint` stays the unchanged superset:
  - `py-lint: py-lint-main py-typecheck` (umbrella; local-dev entry, same output and order).
  - `py-lint-main`: ruff + pylint.
  - `py-typecheck`: pyright.
  - Keep the `PYLINT_JOBS ?= $(shell ...)` sysconf auto-detect unchanged (local fallback).
- Force pylint to all cores on CI only via job-level `env: PYLINT_JOBS: "0"` on `python-lint`; `make`'s `?=` keeps the env value, so local behavior is untouched.
- Move `actions/setup-node` from `python-lint` (no longer runs pyright) to `python-pyright`.
- Register `python-pyright` as a first-class fixable job (drift guard + `/implement --merge` replay) using `make` targets, so replay honors the Makefile `PYLINT_JOBS` fallback locally while CI overrides via env.
- Keep `python-lint-duplicate-code` untouched (separate in-flight design issue; must stay `-j1`).
- Update `docs/linting.md` prose describing the `python-lint` job.

### Edge cases

- Branch protection may still require only the old `python-lint` status. Add `python-pyright` as a required check in GitHub settings (outside this repo), or pyright stops gating merges.
- Keep all lint commands rooted in `python/` so `.pylintrc` and `pyrightconfig.json` resolve.
- `make py-lint` remains the local superset (ruff + pylint + pyright); only CI jobs and replay use the narrower sub-targets.
- Do not split ruff into its own job; it runs ~0.1s.
- Do not touch `python-lint-duplicate-code` (separate in-flight design issue; must stay `-j1`).

### Failure modes

- YAML indentation errors can break the workflow; run `actionlint` locally.
- If a CI runner cannot do pylint multiprocessing, forcing `PYLINT_JOBS=0` could make `python-lint` fail rather than speed up. Standard `ubuntu-latest` supports it; the `env` override is trivially revertable, and the Makefile sysconf fallback still protects local/restricted hosts.
- If `python-pyright` is omitted from any mapping surface (`config.py` / `ci-failed-jobs.sh` / `test-ci-failed-jobs.sh`), `make test-ci-failed-jobs` fails and/or `/implement --merge` mis-classifies pyright failures.
- If `test_ci_monitor.py` stubs are not fully retargeted from `("make", "py-lint")` to `("make", "py-lint-main")`, `make py-test` fails across `run_ci_fix` / `verify_job_locally` / `evaluate_failure` even when production replay is correct.

### Testing strategy

- Run `make lint`, `make py-lint`, and `make py-test`.
- Run the full `python3 -m pytest python/test_ci_monitor.py` module to catch stale `("make", "py-lint")` stubs and missing `python-pyright` replay entries.
- Run `make test-ci-failed-jobs` (or its harness shard) to confirm the drift guard passes with `python-pyright`.
- If available, run `actionlint .github/workflows/ci.yaml`.
- Validate on CI:
  - `python-lint` no longer runs pyright and completes in roughly half or less of the prior ~166s.
  - `python-pyright` runs and fails independently on type errors.
  - Combined coverage still includes ruff, full pylint, duplicate-code pylint, pyright, and tests.
