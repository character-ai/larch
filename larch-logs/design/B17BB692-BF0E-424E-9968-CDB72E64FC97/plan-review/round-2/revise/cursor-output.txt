## Plan

### Approach

- Split CI Python linting into two parallel jobs to cut `python-lint` wall time:
  - **`python-lint`**: ruff + pylint only.
  - **`python-pyright`**: pyright only.
- Keep local **`make py-lint`** unchanged (still runs ruff, pylint, and pyright).
- Keep **`python-lint-duplicate-code`** untouched.
- Set **`PYLINT_JOBS=0`** at the `python-lint` job level so GitHub-hosted Linux uses all available cores.
- Remove **`actions/setup-node`** from `python-lint`; add it to **`python-pyright`** (pyright still needs Node).
- Keep **`python/requirements-dev.txt`** installation in both jobs.
- Register **`python-pyright`** in the hard-coded CI failure / local-replay surfaces so harness lint and `/implement --merge` CI-fix do not treat it as unmapped.
- Narrow **`python-lint`** local-replay and toolchain prep to ruff + pylint only (matching CI), not the full `make py-lint` superset.
- Define one canonical replay argv tuple per job in **`python/ci_monitor.py`** (or a tiny shared helper) and mirror it in **`python/test_ci_monitor.py`** via module-level constants so production wiring and every `RecordingRunner` stub stay aligned.

### Edge cases

- Branch protection may still require only the old **`python-lint`** status.
  - Add **`python-pyright`** as a required check in GitHub settings outside this repo.
- Keep commands rooted in **`python/`** so `.pylintrc` and `pyrightconfig.json` resolve correctly.
- Do not split ruff into its own job; it is too fast to justify another job.
- Do not touch **`python-lint-duplicate-code`**; its single-process pylint mode is intentional.
- **`make py-lint`** remains the local superset; only CI job replay / agentic-fix paths narrow to job-specific commands.
- Replay argv strings must match **exactly** between `per_job_command()` and test constants (quoting / `PYLINT_JOBS` default included) or `RecordingRunner` keyed lookups fail despite correct production behavior.

### Failure modes

- YAML indentation errors can break the workflow.
- If **`PYLINT_JOBS=0`** behaves unexpectedly on the runner, **`python-lint`** may fail instead of speeding up.
- If branch protection is not updated, pyright still runs in CI but may not gate merges.
- If **`python-pyright`** is omitted from the failure-mapping surfaces, `make test-ci-failed-jobs` fails and `/implement --merge` CI-fix bails on pyright-only failures as no-local-equivalent.
- If only `test_per_job_command_table` / `prepare_python_toolchain` are updated but other `RecordingRunner` stubs still key on `("make", "py-lint")`, `make py-test` fails across `run_ci_fix` / `verify_job_locally` / `evaluate_failure` integration tests even when production replay is correct.

### Testing strategy

- Run **`make lint`**.
- Run **`make py-lint`** and **`make py-test`**.
- Run the **full** **`python3 -m pytest python/test_ci_monitor.py`** module (not only `test_per_job_command_table` / toolchain cases) to catch stale `("make", "py-lint")` stubs and missing **`python-pyright`** replay entries.
- If available locally, run **`actionlint .github/workflows/ci.yaml`**.
- Run **`make test-ci-failed-jobs`** (or the harness shard that includes it) to confirm workflow drift guard passes with **`python-pyright`**.
- Validate on CI:
  - **`python-lint`** no longer runs pyright.
  - **`python-pyright`** runs and fails independently on type errors.
  - **`python-lint`** completes in about half or less of the prior ~166s wall time.
  - Combined coverage still includes ruff, full pylint, duplicate-code pylint, pyright, and tests.
