## Decision 1: Consolidate `parse-argv` into the new mechanized flag-parsing verb rather than adding a parallel verb
- **Question**: Should `python/cli.py design parse-flags` replace/retire the existing `design parse-argv` verb, or coexist alongside it as a separate surface?
- **Resolution**: Retire `parse-argv` and repoint `SKILL.md`'s Step 0-pre call site to the new verb in the same commit. `docs/python-migration.md`'s hard-cutover / no-shims convention ("once a domain is registered in cli.py, all consumers are repointed in the same commit; no forwarding-stub duplicates") argues against leaving two parallel argv-parsing surfaces built on the same underlying state machine. `parse-argv`'s existing behavior-matrix guarantees (`python/tests/design/test_design_argv.py`) carry forward onto the new verb.
- **Source**: codebase (`docs/python-migration.md` decision log; consistent with the just-shipped `#5983` precedent, which fully replaced `approval-gates.md`'s literal prompt copy with a Python renderer rather than keeping a parallel prompt source).

## Decision 2: `flags.md`'s non-argv sections (plan-size thresholds, Step 3 review env vars, plan-command validator summary, legacy branch-info/step-prefix notes) stay untouched in content; only the force-read directive and the file's own normative self-description change
- **Question**: The issue leaves open whether `flags.md` "becomes a conditional reference for edge-case prose OR shrinks accordingly" — does this issue's scope include rewriting or relocating `flags.md`'s non-flag-parsing sections?
- **Resolution**: Out of scope for content changes. Those sections' *operational* dispatch semantics are already owned by sibling files that remain independently force-read at their own point of use (`step2b5-rc-handling.md` for plan-size actions, `validator-failure.md` for validator defects, `plan-review.md` for Step 3). `flags.md`'s copies of threshold values are background reference only — no runtime orchestrator path reads `flags.md` for them. This issue removes `flags.md`'s Step 0-pre force-read and updates the file's own header (currently: "single normative source for flag validation rules" / "This file is authoritative for validation and dispatch") since that claim becomes false once `parse-flags` owns validation and error-string generation — but leaves the substantive threshold/validator prose in place as optional background reading.
- **Source**: codebase (direct comparison of `flags.md` against `step2b5-rc-handling.md` and `validator-failure.md`; confirmed neither delegates back to `flags.md` for threshold values).
