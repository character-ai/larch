### DECISION_1: Internal reuse pattern between rebase-checkpoint-probe.sh and phantom-probe-with-warn.sh

Defense A (defends CHOSEN = "Library-based reuse via new scripts/lib-phantom-probe.sh — both wrappers source the library and call a phantom_probe_with_warn shell function"):
<defense_content>
Delegating to `phantom-probe-with-warn.sh` as a subprocess keeps a single executable as the behavioral contract, so tests and reviewers need only one argv/stdout surface, and the rebase wrapper stays a thin orchestrator that merges KVs without owning append/warn edge cases. Duplicating the probe block inline in both wrappers is also straightforward for Bash contributors who prefer copy-paste clarity over designing a sourced function's contract.

Shipping `scripts/lib-phantom-probe.sh` with a shared `phantom_probe_with_warn` function sourced by both wrappers is the right compromise because it preserves one implementation of probe+warn+append-failure logic while avoiding subprocess breadcrumb/KV plumbing and per-macro fork/exec cost.

The implement skill still embeds the full Rebase Checkpoint Macro as inline bash calling `rebase-push.sh` (for example the M1 fence at skills/implement/SKILL.md lines 129-136), while scripts/lib-quiet.sh lines 97-112 show `emit_kv` writing machine-readable lines to FD 3 when `LARCH_QUIET_PID` matches the current shell — so a sourced library function in the same process can emit phantom KVs into the wrapper's quiet session without spawning a second script entrypoint. Peer sourced libraries such as scripts/lib-dirty-tree-sidecar.sh lines 1-5 already use an idempotent `LARCH_LIB_*_LOADED` guard, matching the repo's established pattern for non-executable `scripts/lib-*.sh` modules.

A subprocess call reuses the existing top-level script shape of scripts/check-phantom-dirty.sh (lines 6-9: `source` `lib-quiet.sh` then `larch_quiet_init`), so behavior stays encapsulated behind a shebang entrypoint rather than a new internal API with implicit globals and ordering constraints between callers and the library.

Subprocess reuse forces either a second `larch_quiet_init` boundary and an extra `emit_breadcrumb` at the child's entry (colliding with the wrapper's own single-breadcrumb design) or ad hoc flags to suppress that, plus stdout parsing and KV merge logic that can drift from the wrapper's terminal block; a sourced function keeps exactly one quiet session and one breadcrumb while still deduplicating the phantom logic.

If the plan instead ships duplicated probe+warn bodies, a fix to append-failure handling or STATUS/REASON edge cases will need to land twice and can diverge silently; if it ships subprocess delegation without rigorous merge rules, orchestrators may mis-parse combined output or see misleading double breadcrumbs when debugging `/implement` runs.
</defense_content>

Defense B (defends ALTERNATIVE = "Inline duplication of the phantom probe + warn + append-failure logic in both wrappers (or subprocess delegation between them)"):
<defense_content>
A shared `scripts/lib-phantom-probe.sh` would centralize the probe, warning append, and KV emission contract so both wrappers cannot drift when phantom handling changes. It also avoids subprocess parsing and nested breadcrumb problems while keeping each wrapper's entry breadcrumb independent.

Library reuse is disproportionate here because the existing durable boundary is already `check-phantom-dirty.sh`, and the remaining warn-and-forward glue is too small and wrapper-specific to justify a third new runtime file.

scripts/check-phantom-dirty.sh:56 through scripts/check-phantom-dirty.sh:98 already encapsulates the substantive phantom status detection and KV output, while skills/implement/SKILL.md:467 through skills/implement/SKILL.md:496 shows the remaining caller work is parse four fields, append one of two warning bullets, and continue. Existing peer libraries are materially broader or compatibility-driven: scripts/lib-quiet.sh:37 through scripts/lib-quiet.sh:125 defines a process-wide FD/logging contract, and the existing launcher-common helper at scripts/lib-codex-launcher-common.sh:7 through scripts/lib-codex-launcher-common.sh:22 is an explicit wrapper shim preserving existing launcher call-site names. In this checkout, `scripts/rebase-checkpoint-probe.sh`, `scripts/phantom-probe-with-warn.sh`, and `scripts/lib-phantom-probe.sh` are absent, so the library choice creates an extra new shipped runtime artifact before there are even two established callers.

The best opposing point is that duplicate append-failure handling can drift, and phantom warnings are user-visible enough that a one-line mismatch between wrappers could confuse operators or tests.

That risk is better controlled by focused harness assertions for both wrappers than by introducing a sourced helper whose contract must now include caller-owned `set -e` behavior, quiet FD state, return semantics, and KV naming. Because the core probe is already centralized, duplicating the thin append branch is a smaller maintenance burden than documenting, testing, and shipping a new shell library.

If inline duplication loses, the feature ships with one more library boundary that future maintainers must understand before editing a simple two-wrapper flow, and bugs may migrate from obvious local branches into subtler source-time coupling around quiet output and caller state.
</defense_content>
