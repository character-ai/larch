## Findings

### 1. [correctness] Filing-mode durable artifacts vs clean-worktree (`skills/learn-from-bugs/SKILL.md:264-288`)

Filing mode must persist retry artifacts under `larch-logs/shared/learn-from-bugs-filing/` before marker work, then commit only the state marker. `python/cli.py pr create` delegates to `assert_clean_worktree`, which fails on any remaining porcelain changes (`python/larch/git/push.py:34-42`). After a successful `/issue` pass, the three filing files stay dirty and publication should fail with `PR_STATUS=push_failed`.

**Suggested revision:** Add an explicit filing-mode strategy in the shared publication fragment: commit filing artifacts on the state branch, use a worktree for marker-only work, or defer copying into `ANALYSIS_ROOT` until after merge.

### 2. [correctness] `git -C` vs shell cwd for `pr create` (`python/larch/git/pr.py:322-330`)

The plan keeps `git -C "$ANALYSIS_ROOT"` for the marker commit but runs `pr create` from the caller directory. `create_pr_parity` compares `branch` to `git.try_current_branch` with `cwd=None`, so the checkout used for branch detection is the shell PWD, not `ANALYSIS_ROOT`. Publication fails even when the marker commit succeeded on the state branch.

**Suggested revision:** Require `(cd "$ANALYSIS_ROOT" && …)` around branch creation, commit, `pr create`, and `gh pr merge`; assert this in `_structure_learn_from_bugs_specialized.py`.

### 3. [risk-integration] Scope-disposition gate on `pr create` (`python/larch/git/pr.py:471-507`)

`cli.py pr create` is not a standalone git helper. With `IMPLEMENT_TMPDIR` exported and implement artifacts present, it can return `PR_STATUS=needs-user` without pushing. The plan does not document this refusal path.

**Suggested revision:** Add stdout parsing and operator guidance for `needs-user` / `halt-scope-disposition`; do not advance durability or clear pending filing state on that path.

### 4. [risk-integration] Post-commit, pre-PR failure recovery (`skills/learn-from-bugs/SKILL.md:286-288`)

The plan forbids rolling back after a PR exists but does not define recovery when the marker commit succeeded and push or PR creation failed. That orphans a feature branch, leaves `main` stale, and same-day branch names collide on retry.

**Suggested revision:** Preserve the branch, report the failed stage, and reuse an existing open PR for the branch when identity parses cleanly (aligned with `design_log_publish_flow.py:450-484`).

### 5. [correctness] Stale contract exception (a) (`skills/learn-from-bugs/SKILL.md:28`)

Exception (a) still treats the marker as durable after Step 4 without a PR. That conflicts with the plan’s durability definition and can let default mode continue to Step 5 while `main` still has the old marker.

**Suggested revision:** Reword exception (a) to match PR-created plus merge or manual-handoff durability.

### 6. [correctness] PR KV success predicate (`python/larch/git/pr.py:498-501`)

Parsing `PR_NUMBER` / `PR_STATUS` without rejecting `push_failed`, `error`, `needs-user`, or `PR_NUMBER=0` could reach `gh pr merge` with invalid input.

**Suggested revision:** Pin an allowlist of success statuses and require positive `PR_NUMBER` plus non-empty `PR_URL` before merge or durability claims.
