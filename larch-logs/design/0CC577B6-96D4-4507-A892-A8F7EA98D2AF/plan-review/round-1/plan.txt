# Plan: ship-pr.sh — rebase + rebump + lint inside the CI-fix path before pushing

Re-sequence the `/implement` CI-fix path so a fix is pushed already-rebased,
re-bumped, and lint-clean in one shot. Reuse existing helpers only; no new
rebase / rebump / behind-count / lint-fix / push implementations (issue #3210
hard constraint). Decisions from Round 1: guard-only (no ci-decide rework),
rotate the vendor start tier per attempt, cover both fix-push paths via one
shared helper.

### NEW: `scripts/ci-behind-count.sh`
Extract the behind-count computation that currently lives inline at
`ci-status.sh:177` (`git rev-list "HEAD..$BASE_TARGET" --count`) into a small,
reusable script so both `ci-status.sh` and `ship-pr.sh` call one source (no
duplicated `git rev-list HEAD..<base> --count`).
- Args: `--base-remote` (default `origin`), `--base-ref` (default `main`),
  `--no-fetch` (skip the `git fetch`; caller already fetched).
- Behavior: optional `git fetch "$BASE_REMOTE" "$BASE_REF" --quiet`, then
  `BEHIND_COUNT=$(git rev-list "HEAD..${BASE_REMOTE}/${BASE_REF}" --count)`.
- Output (FD-3/stdout KV via `lib-quiet.sh`): `BEHIND_COUNT=<n>`. Same input
  validation regex on `--base-remote`/`--base-ref` as `ci-status.sh:64`.
- Exit 0 on success; non-zero on argv error. On a failed `git rev-list`, emit
  `BEHIND_COUNT=0` (fail-open: never block a push on a count error) and a
  Warnings-class diagnostic on stderr.

## Approach

The fix-push order becomes: **commit fix → check behind → (if behind) rebase +
rebump with push deferred → re-verify failed jobs + lint on the rebased tree →
push (force-with-lease if rebased, else plain).** This matches the issue's
required order (rebase → rebump → lint → push) while reusing `run_rebase_rebump`
wholesale; the only change to the rebase machinery is a `defer_push` flag that
suppresses its terminal force-push so the caller can re-verify first.

Guard-only reconciliation (Round 1 Decision 1): `ci-decide.sh` / `run_ci_phase`
routing is untouched. After the post-fix path rebases, the next `ci-wait` poll
computes `BEHIND_COUNT=0`, so `ci-decide.sh` returns `wait`/`evaluate_failure`
rather than `rebase` — the deferred-rebase path is a natural no-op fallback, not
a double rebase.

Both fix-push paths are covered because the logic lives in the shared
`_stage_and_push_ci_fixes` (Round 1 Decision 3); the vendor path and the per-job
local-fix path both call it.

## Edge cases

- **Not behind:** behind-check returns 0 → no rebase, plain `git-push.sh`
  (today's behavior, unchanged).
- **Fork target:** base resolves to `upstream/main`; rebase uses the existing
  fork handling already present in `run_rebase_rebump` and the `ACTION=rebase`
  fork branch.
- **Rebase conflict:** reuses `run_rebase_rebump`'s vendor conflict-resolution
  (launch-*-ci.sh `--role resolve-conflict`, Phase 1-4) and its `exit_stall`
  behavior — no new conflict path.
- **Lint delta after rebase:** committed with the existing
  `collect_ci_stage_paths` staging block before the force-push.
- **Claude tier unavailable / Codex down (current degraded run):** the rotated
  waterfall keeps the same per-tier availability guards (1869) and waterfall
  fallbacks; rotation only changes the starting index.
- **`HAS_BUMP=false` repos:** `_run_rebase_rebump_from_step3` already skips the
  rebump when `HAS_BUMP=false`; deferred-push mode preserves that.

## Failure modes

1. **Re-verify fails after a deferred rebase (unpushed local rebase).** The
   branch is rebased+rebumped locally but not pushed; `_verify_failed_jobs_locally`
   may `exit 3` or return 2/4. Mitigation: `CI_FIX_REBASE_PENDING=true` persists
   so the eventual retry push uses `git-force-push.sh` (avoids a
   non-fast-forward rejection from a plain push against the diverged remote).
   Map post-rebase re-verify `rc=2` to `exit_stall` (head moved) and `rc=4` to a
   `_stage_and_push_ci_fixes` failure return so the outer `_max_fix` loop
   retries; do not push an unverified tree. Earliest signal: a plain-push
   non-fast-forward error in CI logs. Simplest mitigation: the pending-flag →
   force-with-lease selection above.
2. **Double-rebase regression with `ci-decide.sh`.** If the post-fix rebase and
   the next-poll `ACTION=rebase` both fire, churn returns. Signal: `REBASE_COUNT`
   climbing without CI converging. Mitigation: the post-fix path leaves the
   branch up to date, so the next poll sees `BEHIND_COUNT=0`; covered by a
   regression test asserting no second rebase when already current.
3. **`REBASE_COUNT` undercount on the bail-before-push path.** A rebase that
   bails before `_run_rebase_rebump_from_step3`'s counter bump is not counted,
   weakening the max-rebases storm guard. Signal: more than `_max_rebases`
   effective rebases. Mitigation: increment the counter when the deferred rebase
   completes, independent of the deferred push.
