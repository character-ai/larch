Tally classifier: fold "neutral" into "rejected" (3 outcome buckets, not 4)

## Problem

The voting tally classifier in `skills/shared/voting-protocol.md` emits **four** finding-outcome buckets (`accepted`, `neutral`, `exonerated`, `rejected`) from a **three-choice** voter ballot (YES / NO / EXONERATE). The `neutral` bucket is counter-intuitive: operators see a 4th term in the final report that maps to no vote choice, and the basic question "was the finding applied?" doesn't get a clean answer.

Concrete example from the `/implement 2620` final report (May 22, 2026):

```
- 2 review rounds, 14 accepted findings (0 rejected), 12 exonerated, 3 neutral
```

29 findings total, bucketed into 4 categories. Operator confusion: what is "3 neutral"? Where in the YES/NO/EXONERATE ballot vocabulary did "neutral" come from?

## Current classifier (background)

Voter ballot choices are YES, NO, EXONERATE — three options per voter per finding. The tally classifier in `skills/shared/voting-protocol.md:60-62` derives one of FOUR outcomes per finding using these tie-breaks (after the acceptance-threshold check fails):

```
accepted   ← YES >= threshold (2+ YES in a 3-voter panel; unanimous in 2-voter; etc.)
neutral    ← YES > 0 AND YES == NO                       (e.g., 1Y/1N/0E or 1Y/1N/1E)
exonerated ← YES > 0 AND NO == 0 AND EXONERATE > 0       (e.g., 1Y/0N/1E or 1Y/0N/2E)
rejected   ← everything else                              (e.g., 0Y/3N/0E, 0Y/0N/3E, 0Y/1N/2E)
```

The `neutral` bucket flags a panel split — at least one voter wanted to apply the finding AND at least one voter rejected it. The carve-out exists so the Reviewer Competition Scoreboard at `voting-protocol.md:198-210` can distinguish two cohorts that both score 0 points but mean different things:

- **Neutral** (`1Y/1N/...`) — panel disagreement: one reviewer was right enough to be voted in, another was confident the finding should be dismissed.
- **Exonerated** (`1Y/0N/1+E`) — panel consensus: the concern is legitimate but not worth fixing in this PR.

For action purposes (was the finding applied to the code?) both are equivalent — neither is applied. For competition scoring, both award 0 points to the reviewer who proposed the finding. The only operational use of the distinction is informational: which reviewers produce contentious findings vs. consensus-OOS findings.

## Costs of the carve-out

1. **Cognitive load** — the operator-facing final report shows a 4-term breakdown that doesn't match the 3-term ballot vocabulary. The mental model "voters choose A/B/C; outcomes are A/B/C" breaks.
2. **Final report clutter** — `/implement` and `/design` summary lines have to mention all four (or selectively elide some, which is itself confusing). The May 22 example above is the canonical case: "0 rejected, 12 exonerated, 3 neutral" makes the reader stop and think.
3. **No action-level distinction** — neutral and exonerated findings are treated identically by the coder (neither is applied) and by the lint/checks pipeline (no follow-up). The distinction is purely scoreboard-internal.
4. **Inconsistent scoring at the boundary** — a `1Y/1N/0E` "neutral" scores 0 (same as exonerated). A `0Y/1N/0E` "rejected" scores -1. The discontinuity at 1Y vs 0Y is sharp but invisible in the report.

## Proposal (outline only — `/design` to refine)

**Fold `neutral` into `rejected`** at the report level. Findings that did not meet the acceptance threshold ARE rejected for the purpose of "what happens to this finding in this PR" — neither applied nor surfaced for follow-up via OOS. The carve-out for scoring (0 vs -1 points) stays inside the scoreboard logic but is not surfaced as a separate finding-outcome term.

**New finding-outcome vocabulary** (3 terms, matching the ballot vocabulary 1-to-1):

```
accepted   ← YES >= threshold                         → finding applied; reviewer +1
rejected   ← did not meet threshold (everything else) → finding not applied
exonerated ← subset of rejected; YES > 0 AND NO == 0  → finding not applied; legitimate concern noted
                    AND EXONERATE > 0                    (informational classification within rejected)
```

`exonerated` is reported alongside `rejected` as a **sub-classification** — every exonerated finding is also a rejected finding. The final-report wording becomes:

```
K accepted, N rejected, P exonerated
```

where K + N = total findings, and P ≤ N (every exonerated finding is also counted in the rejected total). The example above re-renders as:

```
2 review rounds, 14 accepted findings, 15 rejected (12 exonerated)
```

The split is now self-consistent: total = 14 + 15 = 29, exonerated ≤ rejected (12 ≤ 15 ✓).

**Scoring** (for the Reviewer Competition Scoreboard) — preserve the existing point allocation, but route through the new vocabulary:

- accepted: +1 (unchanged)
- exonerated (subset of rejected): 0 (unchanged)
- rejected that was previously classified as "neutral" (`1Y/1N/...`): 0 (unchanged — these don't cost points because at least one voter validated the finding)
- rejected that was previously classified as "rejected" (`0Y/...`): -1 (unchanged — unanimous dismissal)

The classifier still computes the underlying vote pattern; only the OUTCOME LABEL changes from 4 buckets to 3. Internal data structures may keep a fine-grained outcome (e.g., `rejected.neutral` vs `rejected.true_rejected` vs `rejected.exonerated`) for the scoreboard, but the operator-facing final report uses only 3 terms.

**Validation invariant**: `P (exonerated count) <= N (rejected count)` must hold always. If a future change breaks this (e.g., starts counting exonerated outside rejected), the tally test must fail loud. Add an assertion in `scripts/tally-*` tests and in the structure tests.

- `skills/shared/voting-protocol.md` — drop the `neutral` outcome from the classifier text; rewrite the outcome matrix as 3 buckets with exonerated as a sub-classification; update the scoreboard columns (collapse "Neutral (1 YES)" + "Exonerated (0 YES, 1+ EXON.)" into a single "Exonerated (subset of rejected, scored 0)" column with an internal-only `rejected.neutral` accounting for scoring).
- `skills/review/scripts/tally-code-votes.sh` — change `_OUTCOME` emission: instead of `neutral`, emit `rejected` with an internal sub-flag (e.g., `_REJECTED_SUBTYPE=neutral`); preserve scoring math.
- `skills/review/scripts/emit-tally.sh` — drop the "Neutral findings: N" bullet (line ~85); update the final-summary template to "K accepted, N rejected, P exonerated"; assert `P <= N`.
- `scripts/tally-plan-review.sh` (if it has analogous logic for `/design` plan review) — same change.
- `skills/review-and-fix/scripts/review-and-fix.sh` — keep `NEUTRAL_COUNT` as an internal accounting key if needed for scoring fidelity, but stop surfacing it in the final per-round summary (the line near `emit_kv NEUTRAL_COUNT` and `flush_review_batches` invocations).
- `scripts/render-run-summary.sh` and `skills/implement/scripts/write-final-report.sh` — update the final-report wording to the 3-term format with the exonerated sub-count.
- All test fixtures that assert `NEUTRAL_COUNT=N` in tally outputs — update to assert the new shape.
- Any prose in `/implement` SKILL.md, `/design` SKILL.md, or `/review` SKILL.md that mentions "neutral" as a finding outcome — rewrite.

## Acceptance (high level — `/design` to detail)

1. `skills/shared/voting-protocol.md` outcome matrix lists exactly 3 finding-outcome terms (`accepted`, `rejected`, `exonerated`), with `exonerated` documented as a sub-classification of `rejected`.
2. All operator-facing summary lines (`/implement` final report, `/design` plan-review tally, `/review` round summary) use the format `K accepted, N rejected, P exonerated` (or equivalent prose). NO operator-facing surface mentions "neutral" as a finding outcome.
3. The invariant `P <= N` (exonerated count ≤ rejected count) is asserted by at least one structure test.
4. Reviewer Competition Scoreboard scoring is preserved: findings that previously scored 0 still score 0; findings that previously scored -1 still score -1.
5. Internal data structures may retain `NEUTRAL_COUNT` / `_REJECTED_SUBTYPE=neutral` for accounting fidelity, but these are not surfaced in operator-facing reports.
6. `make lint` and `bash scripts/relevant-checks.sh` pass cleanly.
7. Backward compat for run-log JSONL fields: existing `neutral_count` field in `review-and-fix-summary.json` and `code-review-tally` batches may be preserved (set to 0 going forward) OR removed with a schema_version bump; `/design` to decide based on downstream consumer impact (e.g., `/larch:report-tokens` or audit-runs harnesses that read the field).

## Out of scope

- Changing the voter ballot choices (YES/NO/EXONERATE stays as-is — 3 options).
- Changing the scoring point values (+1/0/-1 stays).
- Adding new outcomes or vote choices.
- Changing the acceptance threshold (still 2+ YES in a 3-voter panel, unanimous in 2-voter, etc.).
- Re-rendering historical run-log batches in place. New format applies forward; existing logs keep the 4-term shape they were emitted with.

## Notes for `/design`

- This change touches the report layer + scoreboard layer + classifier-emit layer, but NOT the voter ballot, voter prompt, or scoring math. Scope should be tightly bounded; resist the temptation to also revisit the YES/NO/EXONERATE vocabulary or the threshold rules.
- The "rejected vs exonerated" sub-classification within "rejected" matches the existing distinction; this issue is primarily a re-labeling + report-format change with light data-structure cleanup.
- Verify whether any audit tooling (`/larch:report-tokens`, `scripts/audit-runs.sh`, `skills/audit-runs/*`) reads `neutral_count` from run-log batches. If so, decide whether to keep the field zero-filled for backward compat or bump the schema version.

Severity: medium (operator confusion in the final report; no incorrect behavior, just a counter-intuitive vocabulary).
