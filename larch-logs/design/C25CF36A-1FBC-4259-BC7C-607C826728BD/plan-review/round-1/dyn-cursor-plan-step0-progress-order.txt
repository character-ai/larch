## Review summary

The plan matches the current Step 0 shape: parse KVs stay before `session setup`, `repo_root` is already computed once via `consumer_repo_root(Path.cwd())` (design_step0.py:191), `progress activate` is registered (`python/larch/cli.py:383`), and `_run_best_effort` already fail-softs subprocess failures (design_step0.py:56-58). Moving the session-setup `timing mark` after activation is the right fix because `_append_progress_mark` writes progress breadcrumbs (`python/larch/report/timing.py:688-731`).

**What is already well pinned**

- Explicit `--run-id` vs `SESSION_ID` fallback via `parsed.get("run_id", "") or session_id`
- Fail-soft activation through `_run_best_effort`, not checked `subprocess.run`
- Repo-root reuse by reusing the same `repo_root` variable
- Command-based ordering intent and a degraded-gate success failure path

**Findings**

1. **Ordering test gap (major)** — The implementation section requires removing the pre-setup timing call at design_step0.py:166. The test section only asks for activate-before-timing ordering. That is not enough to catch the most likely regression: leaving the old call and adding a new one. Tighten the test to prove the pre-setup mark is gone, or that activate precedes every session-setup timing mark.

2. **Nested repo-root gap (minor)** — Plan edge cases require nested-working-directory parity for activation, and an existing test already covers nested `write-design-env` repo-root threading. Extend that test for `progress activate` rather than duplicating the nested fixture.

**No other in-scope defects**

- Scope stays within the two firm files; no implement Step 0 or writer migration creep.
- Piece 1 dependency is acknowledged; this piece only wires `progress activate`.
