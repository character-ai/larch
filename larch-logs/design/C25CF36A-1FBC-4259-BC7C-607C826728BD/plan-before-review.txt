## Approach

Implement the minimum Step 0 wiring for the run-scoped progress pointer.

- Keep parse output before session setup.
- After `session setup` yields `SESSION_TMPDIR` and `SESSION_ID`, compute the active progress run id:
  - use parsed `run_id` when non-empty
  - otherwise use `SESSION_ID`
- Reuse the same `repo_root` value for both `write-design-env` and `progress activate`.
- Call `python3 python/cli.py progress activate --repo-root <repo_root> --run-id <active_run_id>` through the existing best-effort helper.
- Move the visible `timing mark "design Step 0: session setup"` call so it runs after activation.
- Do not let activation failure change Step 0 outcome.
- Do not expand scope into progress layout, statusline reading, implement Step 0, or writer migration. Those belong to other pieces.

## Edge cases

- Empty parsed `run_id` must not produce an empty active pointer. It must fall back to `SESSION_ID`.
- Activation can fail because the run id is invalid, the cache path is hostile, or the progress CLI is absent on a dependency-skewed branch. Step 0 must continue.
- The repo root passed to activation must be the same resolved root used for `write-design-env`, including nested-working-directory cases.
- Timing must not run before activation, because the timing mark appends the first visible progress breadcrumb.

## Failure modes

- If Piece 1 is absent and `progress activate` is not registered, this plan is blocked. Do not implement a replacement progress subsystem in this piece.
- If activation is checked instead of best-effort, a pointer write failure can abort `/design` before Step 0 finishes.
- If the timing mark stays before activation, the first Step 0 breadcrumb can write to the stale or wrong progress surface.
- If tests match command strings too loosely, they may confuse `token mark`, `timing mark`, and `progress activate`.
