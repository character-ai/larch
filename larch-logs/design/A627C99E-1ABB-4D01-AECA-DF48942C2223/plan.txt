## Edge cases

- Preserve the `LARCH_TEST_LAUNCH_CLAUDE_SUBPROCESS` override. It must still bypass `_PY_CLI` for the launcher command.
- Keep warnings bounded so subprocess stderr cannot flood run logs.
- Do not warn on successful subprocess returns.
- Do not change the `summary-metadata.md` contents except restoring the real plugin version when the CLI call succeeds.
- All new diagnostic output stays on stderr; stdout remains reserved for `_emit_kv` and other machine-parseable contracts.

## Failure modes when non-trivial

- If `_PY_CLI` is wrong again, tests should fail because the path does not exist or argv points outside `python/cli.py`.
- If the CLI exists but a subprocess returns nonzero, callers still degrade as before, but stderr now shows the failed site.
- If warning assertions are too brittle, narrow them to stable site labels such as `plugin read-version` and `upsert-summary` in `.err` only.
- If the diagram argv test leaves git subprocesses live, it may fail before reaching the launch assertion; the full-chain `fake_run` prevents that flake.

## Testing strategy

- Run `python3 -m pytest python/test_pr_body.py`.
- Run `make py-test` only if the targeted test exposes broader coupling.
- Run `make py-lint` if imports, private constant access, or stderr formatting triggers lint concerns.
