## Summary

`/implement` Step 7a code-flow diagram generation always fails with `rc=2` because `python/larch/git/pr_body.py` builds the larch CLI path as `Path(__file__).resolve().parent / "cli.py"`, which resolves to the nonexistent `python/larch/git/cli.py` instead of the real entrypoint `python/cli.py`. ## Original report

Code-flow diagram generation in `/implement` Step 7a always fails with `rc=2`: `can't open file '&lt;root&gt;/python/larch/git/cli.py': [Errno 2] No such file or directory`.

Root cause: `python/larch/git/pr_body.py` `generate_code_flow_diagram` computes `plugin_root = Path(__file__).resolve().parent` (which is `python/larch/git/`), then invokes `[sys.executable, str(plugin_root / "cli.py"), "agent", "launch-claude-subprocess"]`. The real CLI entrypoint is `python/cli.py`. After the VCS modules moved into the `larch.git` package (issue #5168), this relative path was never updated; sibling modules correctly use `Path(__file__).resolve().parents[2] / "cli.py"` (e.g. `python/larch/state/bootstrap.py`, `python/larch/state/closeout.py`).

The same broken idiom appears at two more sites in the same file: the `plugin read-version` call and the `tracking-issue upsert-summary` call, both `Path(__file__).resolve().parent / "cli.py"`. These fail silently because they run with `check=False` (plugin version degrades to `unknown`; the `larch:metadata` tracking-issue comment upsert is skipped).

Observed in 21 of the last 100 `/implement` runs, every 52.1.1 and 52.1.2 run. `pr_body.py` is untouched since the `v52.1.2` release tag, so the bug is present in `main`/HEAD.

## Root cause analysis

`pr_body.py` lives at `python/larch/git/pr_body.py`. `Path(__file__).resolve().parent` is therefore `python/larch/git/`, and `parent / "cli.py"` is `python/larch/git/cli.py`, which does not exist (the CLI entrypoint is `python/cli.py`). The correct relative computation, used by sibling modules in the same package tree, is `Path(__file__).resolve().parents[2] / "cli.py"` (git -&gt; larch -&gt; python). This is a path-resolution regression from the packaging move that relocated VCS code into `larch.git` (issue #5168) without updating these three relative-path computations.

## Evidence

- `python/larch/git/pr_body.py:860`: `plugin_root = Path(__file__).resolve().parent`.
- `python/larch/git/pr_body.py:865`: `launch_cmd = [sys.executable, str(plugin_root / "cli.py"), "agent", "launch-claude-subprocess"]` (loud failure: the code-flow diagram).
- `python/larch/git/pr_body.py:733`: `subprocess.run([sys.executable, str(Path(__file__).resolve().parent / "cli.py"), "plugin", "read-version"], ..., check=False)` (silent: version -&gt; `unknown`).

- Correct sibling idiom: `python/larch/state/bootstrap.py:26` and `python/larch/state/closeout.py:20`: `_PY_CLI = Path(__file__).resolve().parents[2] / "cli.py"`.
- `git log v52.1.2..HEAD -- python/larch/git/pr_body.py` is empty: untouched since release, so HEAD still has the defect.
- Run-log incidence: 21 of the last 100 `/implement` runs, present in every 52.1.1 and 52.1.2 run, e.g. committed `final-summary.md` and `execution-issues.ndjson` Step 7a warnings.

## Affected files

- `python/larch/git/pr_body.py` — the three broken `cli.py` path computations (lines 733, 746, 860/865). This is the only file that needs changing.
- `python/test_pr_body.py` — should gain coverage asserting the resolved CLI path equals `&lt;repo&gt;/python/cli.py` (and exists), so the regression cannot recur silently.

## Suggested fix(es)

Prefer a single module-level constant (mirroring `_PY_CLI` in `larch/state/bootstrap.py` / `closeout.py`) reused by all three call sites rather than three inline computations.
- Add a regression test in `python/test_pr_body.py` that asserts the constructed argv points at an existing `python/cli.py`.
- Consider making the diagram path assert-or-log loudly if the CLI path does not exist, so a future packaging move fails fast instead of degrading silently.
