## Findings

### 1. [correctness] Probe stamp cache not keyed to review-role probe (`python/larch/agents/_auth.py:223-254`, `398`)

The plan switches the Codex probe to the `review` role (`gpt-5.6-luna`) but leaves `_codex_probe_stamp_kind()` as `codex-login` / `codex-env-key` only. Stamps store a bare `true`/`false` with a 60s TTL (`_read_fresh_probe_stamp`, lines 231-251). A recent successful **default**-model probe can cache `codex_present=true` and skip the new luna probe entirely.

That recreates the original bug during rollout: Step 0 and `/status` can green-light Codex while Step 2 still launches `gpt-5.6-sol` (`python/larch/core/config.py:741`) and hits the vendor CLI gate. Stale gate-detail persistence is coupled to the same gap: when the stamp short-circuits, no probe runs to clear an old gate-detail file per the plan’s “clear after non-gate result” rule.

**Suggested revision:** Bump or partition the stamp kind for the review-role probe, invalidate on role/model change, and ensure a detected gate forces `codex_present=false` even if a stale positive stamp exists.

### 2. [correctness] Gate probe failures must use the no-retry RC (`python/larch/agents/_auth.py:440-464`)

The plan says a CLI gate is non-transient and must not consume transient retries. Today `_run_one_codex_probe` returns `1` on generic failure, and `_run_codex_probes` retries `rc == 1` up to `_max_transient_probe_retries()` (lines 460-464). `_PROBE_NO_RETRY_RC` (3) already exists for one-shot failures (`python/larch/agents/_types.py:78`; tested at `python/tests/agents/test_agents.py:1633-1655`).

Without an explicit gate → `_PROBE_NO_RETRY_RC` mapping, operators still wait through retry loops before seeing the upgrade message.

**Suggested revision:** Return `_PROBE_NO_RETRY_RC` when the shared detector fires; add a gate analogue of `test_check_reviewers_probe_no_retry_rc_one_shot`.

### 3. [risk-integration] Dispatch stdout contract conflicts with `REASON` on `claude_fallback` (`skills/implement/references/step2-dispatch.md:57`)

The plan’s clean-tree path emits `STATUS=claude_fallback` with an actionable `REASON`. The authoritative dispatch contract still states `REASON=<token> # set ONLY when STATUS=bailed`. That mismatch risks harness drift and violates the edit-in-sync list at `step2-dispatch.md:115-120`, which the plan does not include in its firm file set.

**Suggested revision:** Add `skills/implement/references/step2-dispatch.md` as `### UPDATED:` and document optional `REASON` on `claude_fallback` for the CLI-upgrade path only.

### 4. [correctness] `/status` gate message delivery path is incomplete (`skills/status/SKILL.md:25-29`, `python/larch/agents/_auth.py:744-779`)

The plan preserves `check-reviewers` / `status check` KV keys (correct), and extends `degraded_tools_result` for Step 0. But `/status` step 2 renders Codex solely from `CODEX_STATE`, mapping every `probe-failed` to the generic runtime phrase. `CODEX_STATE` alone cannot distinguish CLI-gate failure from other probe failures.

**Suggested revision:** Either emit the actionable gate text on stderr from `status_check_main` (KV unchanged), or add an explicit gate-detail file read in status step 2 before choosing the Codex line.

### 5. [correctness] Step 2 diagnostic scan should follow the launcher failure pipeline (`python/larch/implement/dispatch_step2.py:270-273`, `603-628`)

Gate detection is planned before mapping to `codex-runtime-failure` vs `claude_fallback`. `_run_launcher` only parses stdout KVs and drops combined stderr (third return value unused at line 603). Implement launch failures consolidate diagnostics into transcript-sidecar artifacts via `_append_implement_launch_failure` (`python/larch/agents/_ci_launcher.py:772-793`), not only `codex-impl.log`.

**Suggested revision:** Scan `resolve_failure_diagnostic_source(st.transcript_path, sink=str(st.sidecar_log))`, sidecar, and capped launcher stdout—not sidecar alone—before branching.

---

**Note on intentional scope:** The plan’s choice to probe `luna` only and leave `sol`/`terra` as launch-time checks is a deliberate minimum-change tradeoff aligned with the issue’s “consider probing role model” wording; it is not flagged as over-scope. The stamp-cache and no-retry gaps above are what would leave Step 0/`/status` falsely healthy within TTL.
