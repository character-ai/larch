# [BUG] /design log flush: stale-base re-publish creates conflicting dup PRs

## Summary

`/design` run-log flushing chronically produces `chore(larch-logs)` PRs that get stuck with `add/add` merge conflicts, even though each run directory is unique. The conflict is **not** between the stuck PRs. **Each stuck PR re-publishes a run directory that is already on `main`.** On 2026-06-13, three were stuck at once: #4241 and #4244 (both run `37B0D250-CC1B-42B2-BA64-FF06B44448CB`) and #4212 (run `01E58E95-4FF1-47C2-9D09-C996604F6341`).

This is about the design-log PR being **unmergeable (conflicted)** and **duplicated**, not about the merge mechanism.

## Intended design (for reference — not in scope for change)

- `/implement` run logs are folded into the implementation ("business") PR; there is no separate log PR.
- `/design` run logs get their **own** PR (`chore(larch-logs): ... design run <RUN_ID>`), which runs CI and is **merged with `--admin`** when admin merge is available. This admin merge is **intended**: `--admin` bypasses the review gate only; CI still gates the merge. It is the sanctioned path and is **not** to be removed.
- "Directly to main" is prohibited only in the raw sense: larch must never `git push origin main`, nor commit to local `main` and push, without going through a PR.

## Evidence (2026-06-13)

| Stuck PR | Run | Already flushed to main by | State |
|---|---|---|---|
| #4241 | `37B0D250` | #4238 (merged 19:32, 150 files) | DIRTY / add-add |
| #4244 | `37B0D250` | #4238 (same run) | DIRTY / add-add |
| #4212 | `01E58E95` | #4210 (merged 17:03, 114 files) | DIRTY / add-add |

- Every conflict is `CONFLICT (add/add)`: the same path is added on both the PR branch and `main` with different content.
- Each stuck branch's merge-base with `main` **predates its own run's first flush**: the `37B0D250` branches base at #4221 (17 commits behind main); `01E58E95` bases 21 commits behind. The first flush (#4238 / #4210) is **not** an ancestor of the re-flush branch.
- **#4241 and #4244 are byte-identical** (same run, same 17-file delta) — two re-publishes of one run, so they could never both merge.
- The re-flushes carry the run's **final** snapshot; the first flush committed an **earlier** one. Example: #4212 adds `final-summary-notes.md`, `review-findings-full.jsonl`, `review-phase-detail.md`, and `token-report-final.json` (114 → 122 files); the `37B0D250` delta finalizes `plan.txt` (+186 lines) and review round 5.

## Root cause

**RC-1 — same RUN_ID is published more than once (trigger).** The three `37B0D250` publishes carry distinct manifest `started_at` values (19:28, 19:33, 19:36) across two branch prefixes (`larch-log-design-` twice, `larch-log-design-recovery-` once). Inference (from artifacts, not traced live): the `/design` publish step (`design-step5c.sh` → `design-publish.sh` → `design-log-publish.sh`) ran multiple times for one run via re-entry or recovery. Overlaps #4234 RC-3.

**RC-2 — worktree based on a stale `origin/<default>` that is never refreshed (conflict mechanism).** `scripts/design-log-publish.sh` sets `WT_BASE_REF="origin/$ORIGIN_DEFAULT"` (~line 275) and `git worktree add ... "$WT_BASE_REF"` (~line 279). For the default `--reason final`, nothing fetches `origin/$ORIGIN_DEFAULT` first; the only fetch is of the log branch `$WT_BRANCH`, and only under `--reason pause` (~line 243). So the base is whatever stale `origin/main` the clone last fetched. Because the repo merges constantly, the base goes stale within minutes.

**RC-3 — no rebase before push.** The push (`git push ... "$WT_BRANCH"`, ~line 964) sends the branch built on the stale base; there is no `fetch` + `rebase origin/<default>` between worktree creation and push. So the branch re-adds the entire run directory. The first publish merges cleanly (the dir is not yet on main); every later publish of the same run hits `add/add` because the dir is already on main with different content.

**RC-4 — the empty-porcelain idempotency guard misses this case.** The guard (~lines 860–890) no-ops only when re-staged content is byte-identical to what is already committed. Re-entry changes `manifest.json` timestamps and finalizes `plan.txt`, so `git status --porcelain` is non-empty and a conflicting PR is opened anyway.

**RC-5 — the `--admin` merge is correct; it is not the bug.** `scripts/design-log-publish.sh` delegates the merge to `python/cli.py ship design-log` → `python/design_log_ship.py::run_design_log_ci_merge` → `gh.pr_merge(..., merge_method="squash", admin=True, delete_branch=True)`. `--admin` bypasses the review gate only; CI still gates the merge, and the merge correctly refuses to land a **conflicted** PR. That refusal is exactly why the stale-base conflicts (RC-2 / RC-3) leave these PRs stuck instead of auto-merging. Removing the admin merge is **not** the fix.

## Still present on local main? YES

Verified on local `main` (clean tree, latest fetch): no `fetch origin "$ORIGIN_DEFAULT"` before the worktree base (RC-2); no rebase before `git push` (RC-3). These two gaps are the live defect.

## Relationship to #4234 (related; do not fold in)

#4234 ([IMPLEMENTING], URGENT) targets a different symptom: a concurrent second publish overwrites the first's `PUBLISH_OK=true`, producing a false `failed-publish` report. Its planned fix adds a `REASON=final` idempotent-skip (probe whether `larch-logs/design/<RUN_ID>` is already on the refreshed default branch; if so emit `PUBLISH_OK=true` and skip the PR) plus a write-once result env.

#4234's idempotent-skip handles the "run already fully on main → don't open another PR" dedup. The **net-new** contribution of this issue is **rebase-right-before-push (Fix B)**, which #4234 does not do — it fetches the default branch only for the idempotent probe, early in the script, leaving a multi-minute window (staging, redaction, CI registration) during which `main` advances and the base goes stale again. Note also: #4234's idempotent-skip alone would **drop the final-snapshot delta** when the first flush committed an early snapshot (the #4212 / #4241 case); Fix C below reconciles that.

## Suggested fix

**Fix B (primary) — rebase on latest main immediately before push (RC-2 / RC-3).** Right before `git push`, run `git fetch origin <default>` and rebase the worktree branch onto `origin/<default>` (or rebuild the commit on a fresh `origin/<default>` base), then push. This removes `add/add` conflicts from both the stale initial base and `main` advancing during the publish window, so the PR is clean and the existing `--admin` CI-gated merge can complete. Refreshing only at worktree-add time is insufficient because staging, redaction, and CI registration take minutes.

**Fix C — make re-publish idempotent and incremental (RC-1 / RC-4), coordinated with #4234.** When the run dir is already on `main`, do not open a second conflicting PR; but do not silently skip and lose a newer snapshot. If the session produced a more complete snapshot, publish only the delta on a freshly-rebased branch. Reconcile with #4234's idempotent-skip so the early-snapshot-then-final-snapshot case still captures the final state.

**Fix D — guard repeated publish invocations for one RUN_ID (RC-1).** Overlaps #4234 RC-3: add a published-sentinel / idempotency check in `design-step5c.sh` / `design-publish.sh` so a re-entry does not blindly re-run a full publish.

**Fix E (minor, optional) — graceful fallback when `--admin` is unavailable.** Today an org that forbids admin merges yields `PUBLISH_OK=false` and leaves the branch behind. Keep `--admin` as the default (use it whenever available); when it is unavailable, fall back to a non-admin merge or leave the PR open for a human rather than failing closed. Precedent: #1083.

## Out of scope (corrected)

Removing the `--admin` merge is **out of scope** — the design-log PR's `--admin` merge after green CI is the intended mechanism. An earlier revision of this issue incorrectly proposed removing it; that framing is withdrawn (see RC-5 and Intended design above).
