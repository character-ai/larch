**3. [correctness] `dispatch-plan-voters` fence shape in `plan-review.md`**  
The voter-dispatch reference fence (lines 157–170) runs `dispatch-plan-voters.sh` inside `$(...)` synchronously, then `eval`, then the monitor. The plan’s canonical contract assumes `writer &` then `IDENT=$!`. Without restructuring, a naïve `wait` on `$!` would not wait on the long-running dispatcher, and the orphan bug can persist for plan-review voting.

**4. [correctness] Shell `&` not explicit in sweep rules**  
Post-change fences in `skills/implement/SKILL.md` (e.g. Step 2 dispatch ~883–894, Step 5 ~1147–1158, ship-pr ~1452–1475) use Tool JSON `run_in_background: true` but no shell `&` on the writer line. Issue #2996’s root cause and the plan’s worked example both require backgrounding in the wrapper shell; `$!` only binds to the writer when that line ends with `&`. Failure modes §1 says “warn (not fail) on missing `&`”, which conflicts with making `$!`+`wait` reliable. The sweep should require `&` and the linter should fail closed on missing `&` for top-level Family B anchors.

**5. [architecture] Shell-script lint path misdescribed**  
The plan says to wire the new helper into “the existing shell-file scan path” around line 496, but the shell loop at lines 702–705 only calls `scan_shell_file_for_unset_before_nested_child`. Decision 5 requires pid/wait enforcement in shell scripts, not only Markdown fences—add an explicit new shell scanner (or extend the shell loop) rather than assuming the fence scanner already covers `.sh` files.

**6. [architecture] Lint contract docs omitted**  
`docs/linting.md` (line 17) and `scripts/lint-foreground-markers.md` still describe the pre-wait Family B contract. With Decision 5, these should be updated in the same change set as `BASH_AUTHORING.md` and the linter.

**7. [correctness] Regression harness scope vs Decision 6**  
Decision 6 asks for a harness that simulates early monitor exit and proves the parent waits for the background PID. The plan’s harness description ends by verifying only the positive (`wait` present) case.
