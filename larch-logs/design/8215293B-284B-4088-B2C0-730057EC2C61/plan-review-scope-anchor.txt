# Delegate /implement Step 8 architectural assessments to a bgjob lane, once per run

Delegate /implement Step 8 architectural guidelines/invariants assessment out of the main agent, via a bgjob lane, authored once per run.

## Operator decisions (2026-07-10)

1. **Once per run.** The assessment is authored **once** per `/implement` run, not re-authored after every HEAD change. Post-assessment HEAD movement (rebases, CI-fix commits) triggers only the deterministic pre-filter re-check described below — re-authoring happens only if the new commits bring previously-untouched paths into a guideline/invariant scope.
2. **bgjob lane, not an Agent-tool sub-agent.** The authoring runs as a background job (claude_sub or codex subprocess under the documented bgjob start/wait contract, same shape as review and ship-pr), so its tokens land outside the main-agent lane and its reasoning stays out of main-agent context. Do not use an in-session Agent-tool sub-agent.
3. **Mechanical pre-filter approved.** A cheap deterministic pre-filter skips authored assessment entirely when the diff cannot intersect any guideline/invariant scope.

## Context

Step 8 compose-time gating exits the Python ship driver with NEXT_ACTION=assessments; the main agent then loads skills/implement/references/architectural-guidelines-present.md (and architectural-invariants-present.md when applicable), reads $IMPLEMENT_TMPDIR/architectural-guideline-materialized-diff.txt, authors the assessment draft in its own context, runs append-deviation-note / step-architectural-guidelines-write-compose.sh helpers, and relaunches Step 8 through the bgjob pair. Reassessment currently repeats after any HEAD change. /design Gate C does the analogous invariant+guideline assessment inline (design is inline-only).

## Measured cost (committed larch-logs, July 2026)

Guideline-assessed runs without CI issues show Step 8 claude-lane mean 7.44M tokens vs 6.12M for runs without a guideline outcome (median 4.30M vs 3.32M) — roughly 1.0-1.3M tokens (~$0.5-0.7 at Opus rates, ~2x at Fable) of marginal main-agent cost per run, or about 10% of the July per-run main-agent mean (12.26M). 103/186 July runs wrote architectural-guideline-outcome.json (trending toward 100% now that knowledge files exist); 94 of 103 outcomes were clean, 6 deviation — most authored assessments conclude "no deviations identified." CI-fix runs (12% of July runs; Step 8 mean 14.7M when combined with assessments) currently pay the reassessment multiple times. The materialized diff plus assessment reasoning also stay in main-agent context for the rest of the run (context bloat).

## Required change

1. **Pre-filter (deterministic, first).** Before any authoring, a mechanical check maps the materialized diff's paths (and optionally hunk symbols) against guideline/invariant scopes. No intersection → write the deterministic clean note and outcome JSON without any model call. 94/103 clean July outcomes suggest a high skip rate.
2. **bgjob authoring lane.** When the pre-filter finds an intersection, the ship driver (or a thin CLI verb it calls) starts a bgjob that authors the assessment from the materialized diff + ARCHITECTURAL_GUIDELINES.md / ARCHITECTURAL_INVARIANTS.md. The driver validates the result (HEAD-match, schema) and persists the durable note + outcome JSON. The main agent's only involvement is the existing bgjob start/wait + Step 8 relaunch; it never reads the diff or authors assessment prose.
3. **Once-per-run semantics.** The authored (or deterministic-clean) assessment is recorded with the diff fingerprint it covered. Later HEAD changes in the same run re-run only the pre-filter against the incremental diff (new commits vs the assessed fingerprint): no new scope intersection → keep the existing note; new intersection → one re-author via the same bgjob lane. This replaces the current unconditional reassessment-on-HEAD-drift.

## Proposed Design Outline

### Goals
- Add a thin bgjob start/wait/rejoin adapter that runs Piece 2's `architectural-assessment run` CLI off the main-agent lane, once per identity (requested kind set plus covered fingerprint).
- Emit and validate canonical result KVs: `BGJOB_RC`, step identity (`implement-step8-assessment`), requested kinds, covered fingerprint, and completion status.
- Add a harness that covers fresh start, live rejoin, completed rejoin, deterministic skip, authored success, stale rejection, timeout fallback, invalid-output fallback, and required KVs.

### Non-goals
- Do not change `skills/implement/SKILL.md`. Do not activate the Step 8 route (Piece 4, #6837).
- Do not duplicate Piece 2 logic (materialization, pre-filter, authoring, persistence, HEAD-drift).
- No main-agent inline authoring as a fallback.

### Approach sketch
- Mirror the `step-8-ship.sh` adapter shape: check registry liveness, check completed-rejoin, else clear stale envelope and `bgjob start` a child that delegates to `architectural-assessment run`.
- Identity gate: compute one covered-fingerprint digest over the requested kind set and each kind's materialization identity (`HEAD_SHA`, `BASE_REF`, `DIFF_FINGERPRINT`). Rejoin live or completed work only on an exact kind-set and digest match.
- On bgjob timeout (exit 124) or Piece 2 invalid/failed output, re-launch once, then fail closed via a fail-closed result KV.
- Result env carries `STEP`, `BGJOB_RC`, `REQUESTED_KINDS`, `COVERED_FINGERPRINT`, `ASSESSMENT_STATUS`, and per-kind completion.
- The `.md` pair documents the step contract and the harness scenarios. Keep shell Bash 3.2-safe with the same symlink and path guards as `step-8-ship.sh`.
