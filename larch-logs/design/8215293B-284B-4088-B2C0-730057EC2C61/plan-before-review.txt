## Approach

Add a thin Bash 3.2-compatible bgjob envelope around `python3 python/cli.py architectural-assessment run`.

The adapter will:

1. Read the requested assessment kinds from `$IMPLEMENT_TMPDIR/.ship-route-exit-handoff.env`, following the existing `DETAIL` and `DETAIL_FILE` handoff grammar.
2. Normalize, deduplicate, and order the kind set with Piece 2's `normalize_kinds` contract. Reject empty, duplicate, or unsupported tokens.
3. Validate each requested kind's current materialization through Piece 2's validation code.
4. Build a stable covered-fingerprint digest from the normalized kind set and each kind's `HEAD_SHA`, `BASE_REF`, and `DIFF_FINGERPRINT`.
5. Rejoin a live or completed `implement-step8-assessment` job only when both the normalized kind set and covered fingerprint match.
6. Clear stale merge-result, result, and launch-identity state before starting fresh work.
7. Delegate all assessment work to `architectural-assessment run`. Do not reproduce materialization, pre-filter, authoring, persistence, or HEAD-drift logic.
8. Retry once after a timeout, non-zero child result, malformed output, missing required KVs, or output whose kind coverage or fingerprint does not match the launch identity.
9. Mark the second failed attempt as fail-closed. Never author an assessment in the foreground agent.
10. Publish canonical result KVs through the bgjob result-env contract. Include `STEP`, `BGJOB_RC`, normalized requested kinds, covered fingerprint, completion status, attempt state, and Piece 2's per-kind results.

Use an attempt-aware merge-result envelope. Preseed the second attempt with a fail-closed completion status so daemon-owned timeout results still carry the terminal failure state. A successful child replaces that provisional status with the validated completion state.

## Edge cases

- `DETAIL` is empty, contains an unknown token, repeats a token, or contains only separators.
- `DETAIL_FILE` is missing, outside `$IMPLEMENT_TMPDIR`, symlinked, non-regular, or contains malformed data.
- One requested kind has valid materialization while another is missing or stale.
- A job is live but its launch identity differs from current inputs.
- A registry row is dead while its stale result env remains.
- The child completes while `HEAD` moves and Piece 2 updates materialization identity.
- Piece 2 reports success but omits a requested kind or returns an extra kind.
- A timeout leaves only preseeded merge-result KVs.
- Attempt 1 fails, then inputs change before attempt 2.
- Cleanup encounters a symlink or non-regular path.
- A merge-result value contains a newline or carriage return.

## Failure modes

- Fail with exit 2 on unsafe paths, malformed handoff data, invalid materialization identity, or registry inspection errors.
- Treat input mismatch as stale work, not successful completion.
- Retry one execution failure at the bgjob level.
- Preserve the daemon's non-zero or timeout `BGJOB_RC` after the retry is exhausted.
- Emit a terminal fail-closed assessment status after the second failed attempt.
- Never fall back to inline assessment authoring.
- Never consume a result whose identity differs from the current requested kind set and materialized diff.
