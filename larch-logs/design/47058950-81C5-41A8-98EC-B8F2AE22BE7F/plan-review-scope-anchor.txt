## Summary

Architectural assessments (invariants and guidelines) consistently return `unavailable` during `/implement` runs. The operator-bail message shows `NEEDS_USER_REASON=architectural-assessment-unavailable` with `DETAIL=invariants,guidelines`, but provides no diagnostic about WHY the assessment failed. The detail captured by `_persist_unavailable` is stored only in a receipt file that is not committed to larch-logs, and the outcome files (`architectural-*-outcome.json`) carry `"detail":""` even when a non-empty failure reason was available.

## Original report

Architectural assessment (invariants + guidelines) returns unavailable on every attempt during /implement runs, routing to operator-bail instead of completing. Root-cause: the `step-8-assessment.sh` bgjob launcher times out or the assessment adapter fails silently. The operator-bail message says "assessment unavailable" with detail "invariants,guidelines" but no actionable failure reason is surfaced. The adapter should either surface the specific error or retry more aggressively.

## Reproduction scenario

1. Run `/implement --merge <issue-N>` on any HARD-tier issue.
2. The `step-8-assessment.sh` adapter runs.
3. It launches `python/cli.py architectural-assessment run --kind invariants --kind guidelines`.
4. That command calls `claude --print --model claude-sonnet-4-6 --add-dir ... --allowedTools Read --permission-mode plan`.
5. If the `claude` subprocess returns empty stdout (or a non-zero exit), `_persist_unavailable` is called for each pending kind.
6. Both outcome files get `"detail":""` and `"outcome":"dropped"`.
7. The ship driver exits 3 with `needs_user_reason=architectural-assessment-unavailable`.
8. Operator-bail message shows only the kind list; no diagnostic about the subprocess failure.

Observable in committed run log `BD267D84-8B70-4E30-9FC7-E60E4328D5FE`:
- `larch-logs/implement/BD267D84-8B70-4E30-9FC7-E60E4328D5FE/architectural-invariant-outcome.json`: `"outcome":"dropped","reason":"unavailable","detail":""`
- `larch-logs/implement/BD267D84-8B70-4E30-9FC7-E60E4328D5FE/architectural-guideline-outcome.json`: `"outcome":"dropped","reason":"unavailable","detail":""`

## Expected behavior

The operator-bail message (or the outcome file) should include the specific failure reason, e.g.:
- "assessment launcher returned empty stdout after 3 attempts"
- "launcher exited 1"
- `subprocess.TimeoutExpired` with the timeout duration

The operator should know whether to retry immediately or investigate the `claude` CLI availability.

## Observed behavior

The operator sees only:
```
NEEDS_USER_REASON=architectural-assessment-unavailable
DETAIL=invariants,guidelines
```

No information about what caused the `claude` subprocess to fail.

## Root cause analysis

The detail captured by `_persist_unavailable` (`python/larch/implement/architectural_assessment.py:663`) is:
1. Passed to `_safe_detail()` and written to the receipt file (`architectural-assessment-unavailable-{kind}.json`).
2. NOT written to the outcome file via `_write_outcome()`.
3. NOT propagated into `ASSESSMENT_RESULTS` or any field that reaches `ship route-exit`.
4. The outcome file schema (`InvariantsGateResult` / `GuidelinesGateResult`) does not carry a `detail` field at all.

As a result, `"detail":""` in both outcome files even when the actual failure reason is `"assessment launcher returned empty stdout after 3 attempts"` (memory #6973 root cause: `json.JSONDecodeError: Expecting value: line 1 column 1` from an empty-body Claude response).

The receipt file (`$IMPLEMENT_TMPDIR/architectural-assessment-unavailable-{kind}.json`) does carry the detail but is not committed to larch-logs during teardown.

## Evidence

- `python/larch/implement/architectural_assessment.py:658-660`: `_safe_detail()` redacts and truncates the detail; the detail is then written only to the receipt file, not to the outcome file.
- `python/larch/implement/architectural_assessment.py:671`: `_write_outcome` is called with a `result` object whose `assessment` is `"Architectural assessment unavailable."` — no detail.
- `python/larch/implement/architectural_assessment.py:674-685`: Receipt file carries `detail`, but receipt files are not in larch-logs.
- `python/larch/implement/architectural_assessment.py:786-790`: `ValueError("assessment launcher returned empty stdout after 3 attempts")` is the most common empty-stdout path.
- `python/larch/implement/architectural_assessment.py:825-830`: All pending kinds get `unavailable` on any `OSError/TypeError/ValueError/JSONDecodeError` from the launch-and-parse path.
- Committed outcome files from run `BD267D84-8B70-4E30-9FC7-E60E4328D5FE` confirm `"detail":""` even after a failure.

## Affected files

- `python/larch/implement/architectural_assessment.py`: `_persist_unavailable`, `_write_outcome`, `run` — the detail is captured but not propagated.
- `python/larch/state/ship_guidelines.py` (or equivalent): outcome schema `InvariantsGateResult` / `GuidelinesGateResult` — no `detail` field.
- `python/larch/implement/ship.py` (or equivalent): `route-exit` handler for `architectural-assessment-unavailable` — does not surface detail from receipt file.
- `skills/implement/scripts/step-8-assessment.sh:711`: Child error is only printed to stderr, not captured in merge-result-env.

## Suggested fix(es)

1. **Surface detail in outcome files**: Add a `detail` field to `InvariantsGateResult` / `GuidelinesGateResult`. Populate it from `_persist_unavailable` via `_write_outcome`. This makes the detail visible in committed run logs.
2. **Propagate detail to operator-bail**: Extend `ship route-exit` to read the `detail` field from outcome files and include it in `.ship-route-exit-handoff.env` as `ASSESSMENT_UNAVAILABLE_DETAIL`. Display it in the operator-bail message.
3. **Commit receipt files to larch-logs**: Include `architectural-assessment-unavailable-{kind}.json` in the larch-logs flush so operators can read the detail from committed logs.
4. **Surface child stderr**: In `step-8-assessment.sh:run_child`, capture stderr from the child assessment command and write it to the merge-result-env so the parent adapter can include it in diagnostic output.

## Open questions

- Is `claude --print --model claude-sonnet-4-6 --allowedTools Read --permission-mode plan` the correct invocation for the CI environment? Does the `claude` CLI require an interactive session that is not available in the bgjob context?
- Should the adapter surface a warning when the `claude` CLI is not available or not authenticated, rather than silently retrying?
