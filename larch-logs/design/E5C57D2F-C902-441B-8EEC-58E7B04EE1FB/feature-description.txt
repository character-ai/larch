# [BUG] (URGENT) ship-pr.sh exits undocumented code 2 when local CI harness confirms failure

## Problem

During an `/implement --merge` run for issue #3243, `ship-pr.sh` exited with code **2** after printing:

```
⚠ ship-pr: running local CI job test-harnesses-12
SHIP_PR_EXIT=2
```

Exit code **2** is not in `ship-pr.sh`'s documented orchestrator exit table, which only covers: 0, 3, 4, 5, 6. The orchestrator has no handler for it and falls out of the normal state machine.

## Root Cause

`ship-pr.sh` has an autonomous CI-fix path: when it detects a CI failure it runs the corresponding local harness (e.g. `make test-harnesses-12`) to confirm the failure is locally reproducible before attempting a fix. If that local harness exits non-zero — confirming the failure — `ship-pr.sh` exits with code **2**, propagating the harness's exit code directly without translating it to a documented orchestrator code.

The `ship-pr-state.sh` on this path has `STALL_TRACKING=false` and `BAIL_REASON=` (empty), so none of the normal recovery branches (stall, bail, conflict) match.

## Impact

- Orchestrator receives exit 2 with no handler → manual recovery required: read `ship-pr-state.sh` for `PHASE`, re-invoke `ship-pr.sh` without `--resume-phase` to continue from persisted state.
- In the incident run (PR #3265, run `0B6CCD67-F8AC-4EA2-9375-7134D5D8AE4C`) the CI failure was a genuine regression in the PR. The main agent diagnosed it and applied a fix inline, then re-invoked `ship-pr.sh` successfully — but this required manual orchestrator recovery that should have been automated.
- Any future run where the local harness confirms a real CI failure will require the same manual intervention until this is fixed.

## Suggested Fix (outline)

The "local harness confirmed failure" path should exit with a documented code rather than propagating the raw harness exit. The natural mapping is:

**Exit 3 with `BAIL_REASON=first-fixer-non-health`** — this is the existing orchestrator path for "Cursor CI-fix launcher reports `LAUNCHER_FAILURE_CLASS=other`." It triggers the **autonomous main-agent CI-fix sub-procedure** in `SKILL.md` Step 8+, which:
1. Captures fresh CI logs via `gh-run-logs.sh`
2. Uses Claude tool calls to apply a minimal fix
3. Runs `run-relevant-checks-captured.sh` to validate
4. Commits and pushes
5. Re-invokes `ship-pr.sh`

This is exactly the right flow when a local harness confirms the failure. The details are TBD, but the conceptual change: when `ship-pr.sh`'s local-harness-run exits non-zero, write `BAIL_REASON=first-fixer-non-health` and `FAILED_RUN_ID=<CI run id>` to `ship-pr-state.sh`, then exit 3.
