## Plan

## Approach

Create a standalone pre-`/design` `/triage` skill that investigates an existing issue, produces a bounded analysis, and only updates a non-security, eligible issue after fail-closed checks.

Keep model-led diagnosis in `skills/triage/SKILL.md`. Put all deterministic GitHub mutation, outbound sanitization, protected-state checks, snapshot comparison, and postcondition verification behind typed Python CLI helpers.

`--report-only` is a hard no-mutation path: it renders the evidence, diagnosis, verdict, missing evidence, and fix outline before terminal machine keys, but never invokes mutation, dependency, or follow-up filing paths. `/triage` never edits repository files or authors a `/design` plan.

### NEW: skills/triage/SKILL.md

- Define `/triage <issue-number> [--repo OWNER/REPO] [--report-only]`.
- Validate one positive issue number, the optional repository slug, and known flags before any scratch allocation.
- Fetch the target issue’s title, body, comments, state, URL, labels, `updatedAt`, and pull-request discriminator using read-only GitHub calls. Wrap the issue payload, every content-bearing evidence artifact, Git output, and probe output using the existing `python/cli.py untrusted file-block` convention before model inspection.
- Add two mandatory security gates mirroring `/bug`:
  - Immediately after the initial issue fetch and before scratch allocation or investigation.
  - Immediately before any mutation, dependency operation, or `/issue` invocation.
  - If the issue or gathered evidence is security-sensitive, or classification is uncertain, disarm the Write hook, print the existing `SECURITY.md` responsible-disclosure guidance, emit `TRIAGE_VERDICT=inconclusive`, `ISSUE_UPDATED=false`, and `TRIAGE_FAILURE=security-sensitive`, and stop. Never publish a verification comment, body update, close action, dependency edge, or follow-up for that issue.
- Resolve the checkout origin slug once. When `--repo` differs from the checkout:
  - Do not inspect local `main`, local code, local logs, or make symbol/fix claims from the checkout.
  - Do not create a temporary checkout or fetch arbitrary repositories.
  - Restrict analysis to issue-linked GitHub metadata and explicitly validated cited refs; label all repository-code conclusions as unverified.
  - End as `inconclusive` with `ISSUE_UPDATED=false`; do not mutate the issue, wire dependencies, or file follow-ups.
- Create a canonical `/tmp` scratch directory only after the first security and repository-target gates pass. Add a token-scoped `Write` hook using the `triage` activation token; permit scratch artifacts only under that directory and remove the activation sentinel on every terminal path.
- Before proposing a mutable verdict, reject protected lifecycle state:
  - Call `python3 python/cli.py issue title-eligibility` and refuse mutation when `LIFECYCLE_REJECT=true`.
  - Refuse mutation when the issue has the clarify label or a valid or malformed `larch:plan`, pause, design, implement, or other protected lifecycle control block.
  - Permit replacement only of a syntactically validated helper-owned triage block; treat any other existing or malformed `<!-- larch:` control marker as protected state.
  - Render the refusal in report-only output and otherwise emit `TRIAGE_VERDICT=inconclusive`, `ISSUE_UPDATED=false`, and a stable protected-state failure value.
- Investigate inline with a bounded evidence budget:
  - Prioritize explicitly cited run logs and files.
  - Inspect `execution-issues.ndjson`, `final-summary.md`, `manifest.json`, outcome, handoff, and cited code only when relevant.
  - Allow cited unmerged-branch inspection only through a deterministic helper using the fixed checkout remote, a validated full commit SHA or `refs/pull/<positive-number>/head`, and argument-vector execution.
  - Accept only validated repo-relative code paths and canonical `larch-logs/` paths; reject absolute paths, traversal, symlinks, option-like values, and paths outside the bounded allowlist.
  - Cap full neighbor bodies, log artifacts, code-file reads, and command output. Record every omitted, unavailable, rejected, truncated, or unflushed source instead of inferring its contents.
- Verify whether behavior remains on current `main`, whether a later change fixed it, and whether cited paths, symbols, and line references still resolve. Label each conclusion as an observation or inference.
- Never execute issue-supplied reproduction commands verbatim. Route feasible reproduction through a deterministic `triage probe` helper that accepts only named, allowlisted, argument-validated, credential-free, non-networked probes; reject shell syntax, expansions, redirects, arbitrary executables, authenticated calls, and arbitrary destinations. Otherwise report the proposed reproduction as unexecuted evidence.
- Snapshot open issues, shortlist plausible overlaps, inspect only bounded candidates, and classify each dependency as near-certain or uncertain.
- Compose a design-ready triage section for `valid` findings. Preserve the original report and all non-triage body content byte-for-byte; replace only a validated helper-owned triage section. The generated section contains summary, verified behavior, corrected root cause, evidence, reproduction, scope split, missing evidence, and fix outline. Do not create a `larch:plan` block.
- Sanitize every copied or generated outbound section before scratch write and again in the mutation helper: redact secrets, internal URLs, PII, and temporary paths; neutralize all user-controlled `<!-- larch:` markers; permit only a separately synthesized, validated triage marker.
- Map verdicts as follows:
  - `valid`: append or replace the helper-owned sanitized triage section and leave title and state unchanged.
  - `already-fixed` or `invalid`: add a sanitized verification comment, restore only shared lifecycle title prefixes, and close as `NOT_PLANNED`.
  - `duplicate`: add a sanitized comment naming a verified different canonical issue, restore lifecycle title prefixes, and close as `NOT_PLANNED`.
  - `inconclusive`: make no GitHub mutation and state the evidence gap or safety gate.
- Outside `--report-only`, invoke `python3 python/cli.py triage apply --operator-invoked` with the fetched `updatedAt` timestamp and required artifact paths. Never call it for `inconclusive`.
- Apply only near-certain dependencies after the primary issue update verifies. Invoke `/block-issue <issue> <blocker> --repo "$REPO"` with the selected repository slug, then require an exact read-back of the blocked-by edge. Treat missing, malformed, or unverifiable relationship data as a triage failure and do not print a success summary. Keep uncertain edges only as recommendations in the triage section.
- File any follow-up issue only through `/issue ... --operator-invoked`; never file public security findings.
- Emit rendered analysis before terminal machine keys. Use exactly:
  - `TRIAGE_VERDICT=<valid|already-fixed|duplicate|invalid|inconclusive>`
  - `ISSUE_UPDATED=<true|false>`
  - `TRIAGE_FAILURE=<none|security-sensitive|protected-state|foreign-repository|insufficient-evidence|validation|authorization|stale-snapshot|redaction|mutation|postcondition|dependency-postcondition>`
- Avoid success claims when any mutation, verification, or dependency read-back fails.

## Edge cases

- The issue changes between fetch, body edit, comment, title restoration, close, or dependency application.
- The issue is closed, deleted, transferred, or is a pull request.
- `--repo` differs from the checkout origin.
- The report is security-sensitive or security classification is uncertain.
- Cited logs exist only on an unmerged branch, are missing, truncated, rejected by path validation, or were never flushed.
- A cited line moved while its symbol still exists.
- A reproduction suggestion contains shell syntax, an authenticated request, a network destination, or an unallowlisted executable.
- Multiple plausible duplicates exist without one canonical match.
- A dependency is plausible but not near-certain.
- The body contains a valid or malformed lifecycle machine block, untrusted larch marker, or prior helper-owned triage section.
- The body already contains the proposed triage section or a prior triage comment exists.
- A lifecycle prefix is absent, repeated, or mixed with a bug prefix.
- The canonical duplicate equals the triaged issue.
- Redaction or marker neutralization changes the proposed content.
- A GitHub mutation succeeds but its read-back, timestamp, close reason, or dependency edge does not confirm the postcondition.

## Failure modes

- Fail before mutation when validation, authorization, security, repository-target, lifecycle-state, snapshot freshness, redaction, ref/path validation, or safe-probe checks fail.
- Stop the mutation sequence after any failed command, timestamp mismatch, or failed read-back.
- Preserve the scratch directory for actionable mutation diagnostics, but disarm the Write hook.
- Do not claim design readiness when evidence is insufficient, the target repository cannot be verified, or a valid triage-section update cannot be verified.
- Do not close an issue when the verification comment, title restoration, canonical duplicate check, or pre-mutation snapshot check fails.
- Treat a missing or unverifiable dependency edge as failure without a success summary.
- Report missing evidence and residual uncertainty without inventing a root cause.
