### FINDING_1: **risk-integration** `.claude/skills/rebalance-tests/scripts/rebalance.py` — Post-PR verification triggering not tied to Python kinds

The plan extracts shared “verification-run triggering” helpers and documents Python fail-closed verification parsing, but the Verification block never states that `n_verify_runs` workflow_dispatch must run whenever the Python leg is selected. On `--kind python`, skipping triggers leaves verification with no fresh `python-tests` logs and the new fail-closed path becomes a false failure.

**Suggested revision:** Document that one shared post-PR dispatch/wait loop runs for any kind that needs verification data, then branch into harness wall-clock vs Python duration-sum checks.

### FINDING_2: **correctness** `.claude/skills/rebalance-tests/SKILL.md` — Harness-only 12-step workflow survives rename

The hard-rename goal requires accurate operator docs. The plan’s SKILL.md rewrite lists flags, gates, and library modules but does not instruct removal/replacement of the existing harness-only steps 1–12. Those steps contradict `--kind python` and default `--kind all`.

**Suggested revision:** Make the SKILL.md task explicitly replace the numbered workflow with kind-aware steps (or per-kind subflows) through asymmetric verification.

### FINDING_3: **correctness** `python/pytest_ci_timing.py` — Missing stateful `shard_total` propagation in `parse_log`

The approved edge case requires `observed_shard_count` to return `4` when logs say `of 4` even if shard 4 has no `call` rows. Duration rows typically lack `of N` on the same line; only step headers carry it. The parse spec covers per-line regex, job-name shard fallback, and attempt banners, but not carrying `shard`/`shard_total` context into each emitted row.

**Suggested revision:** Add explicit within-job-slice context tracking to the `parse_log` contract so planned tests and runtime shard-count validation stay aligned.
