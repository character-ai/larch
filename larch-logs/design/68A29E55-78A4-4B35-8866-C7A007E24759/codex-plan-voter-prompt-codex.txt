# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

## Summary

When the Claude voter subprocess in `/design` Step 3 plan-review fails transiently (e.g., "No messages returned from query"), `dispatch_voters_main` in `plan_review_panel.py` sets `DISPATCH_OK=false` and exits with code 1 — even though Codex and Cursor voters both produced substantive, non-empty vote output. The round-loop gate in `plan_review_round.py` then skips the tally entirely and marks the round as `panel-failed`, silently discarding all aggregator findings regardless of majority-vendor agreement.

## Original report

User invoked `/design 5619`. The plan-review panel returned `NEXT_ACTION=step3b-bypass` with `STEP3_REVIEW_LOOP_STATUS=panel-failed`, `ACCEPTED_COUNT=0`, and `DEGRADED_PANEL_WARNING="2/3 effective judges produced substantive vote output"`. Six important findings with `YES` votes from both Codex and Cursor were dropped.

## Reproduction scenario

1. Run `/design &lt;issue&gt;` so Step 3 plan-review launches.
2. During the voter-dispatch phase, the Claude voter subprocess fails (e.g., "Error: No messages returned from query" — a transient Claude CLI error).
3. Codex and Cursor voters complete normally with non-empty, substantive output.
4. Observe `NEXT_ACTION=step3b-bypass`, `TALLY_PLAN_REVIEW_STATUS=panel-failed`, `ACCEPTED_COUNT=0` — all findings dropped.

## Expected behavior

When 2 out of 3 voters produce substantive output (effective ≥ 1), the tally should run using only the available voter files. The round may complete with a degraded-panel warning, but findings with majority support from effective voters should be accepted and applied.

## Observed behavior

`DISPATCH_OK=false` is set because voter_1 (Claude) failed, regardless of voter_2 (Codex) and voter_3 (Cursor) health. `dispatch_voters_main` returns exit code 1. `plan_review_round.py` interprets returncode != 0 as panel-failed and skips the tally, dropping all 6 aggregated findings.

From `claude-vote-output.txt.failure-diag`:
```
Error: No messages returned from query
```

From `claude-vote-output.txt` (voter_1): 0 bytes.
From `codex-vote-output.txt`: 1883 bytes — valid votes.
From `cursor-vote-output.txt`: 2116 bytes — valid votes.

**The voter failure is not visible in the reviewer-status table.** `reviewer-status-table.txt` shows all reviewers green because it tracks the collector phase (reviewers), not the voter phase. Operators monitoring the reviewer table see no signal that the voter round is degraded.

## Root cause analysis

In `python/larch/review/plan_review_panel.py`, the full-panel voter dispatch path (line ~1054):

```python
dispatch_ok = "false" if voter_1_status == "failed" else "true"
_emit(key="DISPATCH_OK", value=dispatch_ok)
return 0 if dispatch_ok == "true" else 1
```

`DISPATCH_OK` and the exit code are gated **solely on voter_1 (Claude)** regardless of vendor voter health. This causes any transient Claude CLI failure to abort the tally even when Codex and Cursor both succeeded.

In `python/larch/review/plan_review_round.py`, line ~965:

```python
if voter.returncode != 0 or voter_kv.get("DISPATCH_OK", "false") != "true":
    # panel-failed — tally skipped, all findings dropped
    return 1, values
```

The tally itself (`plan-review tally`) already handles partial voter participation — it only includes `--voter` args for non-failed slots (line ~991-993). So fixing the DISPATCH_OK gate to allow degraded-but-functional dispatch should be sufficient; no tally changes are needed.

**Secondary: why does the Claude voter fail?** The voter is invoked as:

```
claude --print --output-format json --model claude-sonnet-4-6 \
  --add-dir &lt;design_tmpdir&gt; --allowedTools Read --permission-mode plan
```

Exit code 124 is the Claude CLI's own code for "No messages returned from query." A contributing factor may be the `--permission-mode plan` flag: when `ANTHROPIC_API_KEY` is set, the CLI also emits `⚠ claude.ai connectors are disabled because ANTHROPIC_API_KEY or another auth source is set and takes precedence over your claude.ai login`. Whether this warning path interacts with `--permission-mode plan` to produce empty API responses is unknown and worth investigating as a separate hardening item.

## Suggested fix(es)

In `plan_review_panel.py`, change the DISPATCH_OK assignment in `dispatch_voters_main` (full-panel path) from:

```python
dispatch_ok = "false" if voter_1_status == "failed" else "true"
```

to:

```python
dispatch_ok = "true" if effective &gt; 0 else "false"
```

where `effective` is the integer already computed by `effective_judges_main` at line ~1000. This keeps the tally running whenever at least one voter has substantive output, while still propagating the `DEGRADED_PANEL_WARNING`.

Also add a test: voter_1 fails, voter_2+voter_3 succeed, assert DISPATCH_OK=true and tally proceeds.
