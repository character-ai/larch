# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed"). A red or flapping default-branch CI counts as actively
   blocking verification for every run: restoring or stabilizing default-branch CI clears this
   gate. The `/implement` orchestrator, not reviewers, owns executing that repair.

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `major`. Single-YES `minor`, `nit`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.

necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

## Summary

`scripts/test-design-structure.sh` can emit a false-negative `cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design &lt;verb&gt;` failure. The harness captures the `_DESIGN_LIFECYCLE_STDOUT_KEYS` block once with a `$(awk ...)` command substitution, then reuses that single capture across a per-verb loop. When the command substitution truncates transiently, later verbs drop out of the reused block, so the check fails even though the key is present in the file. This produces spurious `main` CI failures.

## Original report

test-design-structure.sh emits a false-negative "cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design &lt;verb&gt;" failure when its once-captured awk block truncates, causing spurious main-branch CI failures. Discovered during `/implement` of #6604 (PR #6606, merged); the root cause was fully investigated during that run, so no separate re-reproduction was performed.

## Reproduction scenario

The failure is transient and hard to force deterministically. It was observed once in CI:

1. Push a merge commit to `main`.
2. `main` CI runs the `test-harnesses` shard that executes `bash scripts/test-design-structure.sh`.
3. Under transient I/O or memory pressure, the `$(awk ...)` capture at line 319 truncates mid-output.
4. The per-verb loop then fails with `cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design &lt;verb&gt;` for a verb whose entry is actually present.

Running the harness locally passes deterministically (`EXIT=0`, `test-design-structure: ok`). Re-running the failed CI job on the same commit also passes.

## Expected behavior

The check reads the `_DESIGN_LIFECYCLE_STDOUT_KEYS` block reliably. It fails only when a `("design", "&lt;verb&gt;")` entry is genuinely absent. A transient read or truncation does not produce a "missing key" verdict.

## Observed behavior

A transient truncation of the once-captured block yields `cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design &lt;verb&gt;` for a verb that is present in the file. The verdict is misleading and non-reproducible on re-run.

## Root cause analysis

`scripts/test-design-structure.sh` (around line 319) captures the block once:

```
stdout_keys_block="$(awk '/^_DESIGN_LIFECYCLE_STDOUT_KEYS:/{flag=1;next}/^\)/{if(flag){flag=0}}flag' "$CLI_PY")"
```

It then reuses `$stdout_keys_block` across a per-verb loop (around lines 320-324) and at two additional sites (around lines 404 and 685):

```
printf '%s' "$stdout_keys_block" | grep -Fq "(\"design\", \"$verb\")" || fail "cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design $verb"
```

If the command substitution truncates (transient CI I/O, or `awk` killed mid-output under memory pressure), the reused block is missing later verbs, and the loop fails on the first absent verb. Nothing guards that the extracted block is complete or non-empty, so a truncated read is indistinguishable from a genuinely missing key.

Secondary observation: the awk stop pattern `/^\)/` matches only a line that starts with `)`. The frozenset closes with `})` (starts with `}`), so the extraction over-captures past the frozenset into later definitions. This does not cause the false-negative, but it shows the extraction logic is loose.

## Evidence

- `main` CI run `28930228453` (push event, merged SHA `014e8614393cf87bcc28986ad1fe39ec8cd19e69`) failed `test-design-structure` with `cli _DESIGN_LIFECYCLE_STDOUT_KEYS missing design step0c`.
- `("design", "step0c")` is present at `python/larch/cli.py:615`, inside the `_DESIGN_LIFECYCLE_STDOUT_KEYS` frozenset.
- Re-running the same failed job on the same commit passed (`conclusion=success`).
- The full harness passes deterministically locally (`EXIT=0`, `test-design-structure: ok`).
- In the failing run, the whole-file check `contains "$CLI_PY" '("design", "step0c")'` passed, and the loop only reached `step0c` because the 8 preceding verbs passed their block-grep. So the reused block held verbs through line 614 but was truncated right before line 615 (step0c). The file content is byte-identical, so `awk` did not logically stop; the `$(awk ...)` capture truncated.

## Affected files

- `scripts/test-design-structure.sh`: the once-captured `stdout_keys_block` (around line 319) and its reuse sites (around lines 323, 404, 685). This harness produces the false-negative.

## Suggested fix(es)

- After capturing `stdout_keys_block`, validate it is non-empty and contains a known terminal sentinel, such as the last frozenset entry `("plan", "step1-log")`.
- If the block is truncated or empty, either re-extract with bounded retries to self-heal a transient truncation, or `fail` with a distinct `block extraction incomplete` diagnostic so it is not misreported as a genuinely missing key.
- Apply the guard at all reuse sites.
- Optionally tighten the awk stop pattern `/^\)/` so it stops at the frozenset close (`})`) instead of over-capturing into later definitions.

## Open questions

- Should the guard self-heal (re-extract with bounded retries) or fail loudly with a distinct diagnostic? A distinct loud failure is best for auditability; a bounded retry then a distinct failure may be the right hybrid.
- Is the transient truncation driven by CI resource limits on the `test-harnesses` shard? If so, a shard resource adjustment may also reduce recurrence.
