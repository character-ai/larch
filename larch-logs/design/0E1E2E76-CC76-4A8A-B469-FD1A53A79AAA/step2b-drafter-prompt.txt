## Bug 1: BEFORE table uses `current_shards` instead of `new_shards`

**Location:** `rebalance.py` line 474


`current_shards` is the **old** shard layout (read before rebalancing). The BEFORE table shows estimated totals for old shards while AFTER shows measured totals for new shards. This makes the comparison misleading:

## Bug 2: No feasibility preflight — CI runs triggered for an impossible threshold

**Data from the 2026-06-13 run:**

- Total test load: ~1631s across 301 targets
- Ideal shard time: 1631 / 20 = **81.6s**
- Heaviest single target: `test-stall-recovery-report` = **167.8s** (consistent across all 5 baseline runs AND all 3 verification runs)
- Balance threshold: 15s
- Required: heaviest shard &lt;= 81.6 + 7.5 = **89.1s** — but `test-stall-recovery-report` alone is 167.8s

No packing algorithm can satisfy this. LPT correctly placed `test-stall-recovery-report` alone in shard 1 (it is the slowest target; it goes first), but a shard containing only this test already exceeds the threshold by 86s.

The script triggered 3 verification CI runs (~5 minutes each) before discovering this.

**Verification variance was negligible** (median per-shard spread across the 3 runs was 6.3s, max 26.3s), confirming the 146s gap is structural, not noise.

**Per-run shard 1 data:**
- Run 1: 172.2s
- Run 2: 165.8s
- Run 3: 168.6s

**Fix:** After computing baseline medians and before triggering any CI runs, check:

```python
max_target_time = max(medians.values(), default=0.0)
ideal_shard = sum(medians.values()) / n_shards
if max_target_time &gt; ideal_shard + args.balance_threshold / 2:
    print(
        f"Warning: heaviest target ({max_target_time:.1f}s) exceeds "
        f"ideal shard time ({ideal_shard:.1f}s) + threshold/2 ({args.balance_threshold/2:.1f}s). "
        f"The {args.balance_threshold}s threshold cannot be met without splitting or speeding up "
        f"the heaviest test targets. Continuing anyway — the rebalancing may still improve spread."
    )
```

Consider also printing the top-N heaviest targets so the operator knows what to split.
