# [BUG] (URGENT) /rebalance-test-harnesses: BEFORE table compares wrong shards; no feasibility check before triggering verification CI runs

## Summary

Two bugs caused the 2026-06-13 rebalance (PR #4232) to falsely report "balance FAILED" and waste 3 verification CI runs:

1. **BEFORE table uses old shard layout** — comparison is meaningless
2. **No feasibility preflight** — the 15s threshold was geometrically impossible; the script spent ~5 min triggering CI to discover this

---

## Bug 1: BEFORE table uses `current_shards` instead of `new_shards`

**Location:** `rebalance.py` line 474

```python
# WRONG — current_shards is the OLD layout
_print_shard_table("BEFORE (estimated from baseline medians):", current_shards, medians)
```

`current_shards` is the **old** shard layout (read before rebalancing). The BEFORE table shows estimated totals for old shards while AFTER shows measured totals for new shards. This makes the comparison misleading:

| Shard | BEFORE (old layout) | AFTER (new layout) | Interpretation |
|-------|--------------------|--------------------|----------------|
| 1 | 0.8s (`test-implement-bootstrap`) | 168.6s (`test-stall-recovery-report`) | Looks 200x worse — but both numbers are correct for their respective shards |
| 6 | 273.4s (`test-stall-recovery-report` + others) | 77.4s (different tests) | Looks great — but old/new shards have entirely different contents |

**Same bug at lines 403-406:** `baseline_spread` is computed from `current_shards`, so the "before spread" in the PR body (272.6s) also refers to the old layout, not the new layout's estimated spread.

**Fix:** Replace `current_shards` with `new_shards` on line 474 and in the `baseline_spread` computation (lines 403-406). The BEFORE column should show estimated totals for the **new** shard assignments so BEFORE vs AFTER compares the same shard indices.

---

## Bug 2: No feasibility preflight — CI runs triggered for an impossible threshold

**Data from the 2026-06-13 run:**

- Total test load: ~1631s across 301 targets
- Ideal shard time: 1631 / 20 = **81.6s**
- Heaviest single target: `test-stall-recovery-report` = **167.8s** (consistent across all 5 baseline runs AND all 3 verification runs)
- Balance threshold: 15s
- Required: heaviest shard <= 81.6 + 7.5 = **89.1s** — but `test-stall-recovery-report` alone is 167.8s

No packing algorithm can satisfy this. LPT correctly placed `test-stall-recovery-report` alone in shard 1 (it is the slowest target; it goes first), but a shard containing only this test already exceeds the threshold by 86s.

The script triggered 3 verification CI runs (~5 minutes each) before discovering this.

**Verification variance was negligible** (median per-shard spread across the 3 runs was 6.3s, max 26.3s), confirming the 146s gap is structural, not noise.

**Per-run shard 1 data:**
- Run 1: 172.2s
- Run 2: 165.8s
- Run 3: 168.6s

**Fix:** After computing baseline medians and before triggering any CI runs, check:

```python
max_target_time = max(medians.values(), default=0.0)
ideal_shard = sum(medians.values()) / n_shards
if max_target_time > ideal_shard + args.balance_threshold / 2:
    print(
        f"Warning: heaviest target ({max_target_time:.1f}s) exceeds "
        f"ideal shard time ({ideal_shard:.1f}s) + threshold/2 ({args.balance_threshold/2:.1f}s). "
        f"The {args.balance_threshold}s threshold cannot be met without splitting or speeding up "
        f"the heaviest test targets. Continuing anyway — the rebalancing may still improve spread."
    )
```

Consider also printing the top-N heaviest targets so the operator knows what to split.

---

## What actually happened (the packer was correct)

The rebalance correctly improved overall spread:
- **Old layout estimated spread:** 272.6s
- **New layout measured spread:** 146.4s (a real ~47% improvement)

The packer placed `test-stall-recovery-report` (167.8s) alone in shard 1 because it is the global maximum — this is exactly what LPT should do. The "balance FAILED" message was a threshold misconfiguration, not a packer defect.

The old shard 6 (which contained `test-stall-recovery-report` among 19 other tests) estimated to 273.4s. Under the new layout those 19 other tests are distributed across other shards, and shard 1 holds only `test-stall-recovery-report`.
