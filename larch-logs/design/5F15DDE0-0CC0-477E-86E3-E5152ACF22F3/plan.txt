## Plan

### Approach

Change only the final report assembly order. Keep all existing section content and formatting intact.

Build the final body as:

1. review phase detail, when present
2. exec issue and warning detail, when present
3. architectural invariant and guideline sections for `/implement`, when present
4. the existing run summary block last

Use simple section joining that strips only boundary newlines. Do not alter the summary renderer, the detail renderers, degraded fallback text, or tracking issue upsert logic.

### Edge cases

- No review detail: output should remain the compact summary.
- No issue detail: review detail should still precede the summary.
- No prefix sections at all: output should equal the summary body with normal trailing newline behavior.
- Review renderer raises: keep the summary and continue.
- Architectural note rendering fails: keep the summary and continue.
- Degraded fallback summary exists: enrichment should still place added detail before that summary.

### Failure modes when non-trivial

- A naive prepend can add leading blank lines. Use section lists and `strip("\n")` on section boundaries.
- Changing `pr_body.render_run_summary` would affect other callers. Do not change it.
- Moving detail after summary in only one renderer would leave `/design` and `/implement` inconsistent.
- Tracking issue upsert could publish stale ordering if it reads before the rewritten file. Keep the existing write-before-upsert sequence.
- Implement tests that only check review-detail ordering can miss exec-issues regressions. Use `str.index` ordering checks on every path that emits exec detail.
