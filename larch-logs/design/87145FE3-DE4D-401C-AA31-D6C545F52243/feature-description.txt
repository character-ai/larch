# Restore OOS voting + always file one unifying OOS issue (/implement + /design)

## Summary

Out-of-scope (OOS) findings surfaced during `/implement` code review are no longer filed as GitHub issues. They are stripped from the ballot **before** the code-review panel votes, so they never become "accepted OOS" and the filer never sees them; they are only *surfaced* in a "Dropped OOS candidates" list for manual filing. This is a regression.

The fix: restore OOS to the vote in `/implement`, **loosen** the acceptance standard to "legitimacy" in both skills, and file **every** vote-accepted OOS item into a **single unifying `[OOS]` issue per run** — no post-vote filing criteria — in both `/implement` and `/design`.

> Line numbers below are anchors as of current `main`; they drift — the symbol names are the durable reference.

## Symptom (observed)

A `/implement` run surfaced 7 OOS items under a `## Dropped OOS candidates` section in its final summary but filed **no** unifying `[OOS]` issue for them. Asked to self-diagnose, that run concluded the #6028 fix was "present and working as designed" (it surfaces dropped candidates for manual filing) — which is true, but stops one layer short of *why accepted OOS was empty in the first place*. Separately, `[OOS]` issues from `/design` had become rare.

## Root cause

### `/implement` — a real regression (pre-vote OOS gate)

A **pre-vote OOS gate** removes every `[OUT_OF_SCOPE]`/`[OOS]`-tagged finding from the ballot **before the code-review panel votes**:

- `_apply_pre_vote_oos_gate` — `python/larch/review/review_core_body.py:305`. Splits the ballot into `dropped_blocks` (OOS-tagged, via `_is_oos_ballot_block` at `:265`, matching titles that start with `[OUT_OF_SCOPE]`/`[OOS]`) and `kept_blocks` (everything else). It writes the OOS blocks to `oos-dropped-before-vote.md` (`:306`, `:321`) and **rewrites the ballot `findings.md` to `kept_blocks` only** (`:327`).
- Invoked via `_prune_nit_then_pre_vote_gate` (`:520`, gate call at `:535`) from all three review branches: normal (`:786`), validation-exhausted (`:727`), and empty-merge (`:770`).
- **Ordering proof**: `_prune_nit_then_pre_vote_gate` rewrites `findings.md` to the non-OOS remainder, and *then* the tally votes on `findings.md`. So the panel never sees OOS.

Because OOS never reaches the vote, it never becomes accepted OOS, `oos-accepted-review.md` stays empty, and the filer (`python/cli.py oos file`, invoked at `python/larch/implement/dispatch_ship.py:424`; reads `oos-accepted-review.md` via `file_oos.py:160`) files nothing.

**The surrounding machinery is intact but decapitated** — the gate silently kills a pipeline that everything else still expects to run:

- Voter prompts still instruct judges how to vote on `[OUT_OF_SCOPE]` items using the rubric — `python/larch/rendering/rendering.py:1226-1230` — now dead instructions.
- Reviewers are still prompted to *generate* OOS proposals (capped at 3 each) — `rendering.py:857-862` — so the cost is still paid.
- OOS still participates in panel scoring — `rendering.py:919` ("Accepted OOS earns provisional +1... rejected OOS -1").
- The tally still writes `oos-accepted-review.md` — `python/larch/review/review_tally.py:736`.
- `python/cli.py oos file` still reads it and still rolls accepted OOS into one issue.

Net effect: 100% of the generation cost, 0% of the value, and the materiality rubric — the very tool meant to separate a real out-of-scope bug from noise — is **never run**.

**The #6028 "Dropped OOS candidates" section only surfaces these for manual filing.** `render_dropped_oos_candidate_section` (`python/larch/report/review_phase_detail.py:127`) reads `round-*/oos-dropped-before-vote.md` into the final summary. `docs/run-logs.md` calls it "a manual filing queue." It does not file anything.

Note: the prune-nit step can also *demote* in-scope findings to `[OUT_OF_SCOPE]` (`review_core_body.py:534`), and those get swept into the same pre-vote drop.

**Introduced by:** #5462 / PR #5496, commit `f8bffba74` — "Add pre-vote OOS gate to review core / Drop OOS-prefixed findings before code-review voters see the ballot." (Later moved into `review_core_body.py` by the #5772 module split; the logic originates in #5462.)

### `/design` — NOT a code regression

The plan-review path has **no** pre-vote gate. It votes on OOS and files accepted items:

- OOS rides the ballot: `_is_oos_scope` (`plan_review_round.py:236`), retained under `PER_REVIEWER_OOS_PROPOSAL_CAP = 3` (`:27`, `:507`), rendered as `oos_md` (`:535`) and folded into the ballot (`:714`, `:928`).
- Panel votes; accepted non-security `OOS_N` items are appended to `oos_accepted_chunks` (`plan_review_tally.py:888`) and accumulated into `oos-accepted-design.md` (`:809`, path at `:661`).
- Step 5b readies filing: `file_oos_prepare_main` (`python/larch/design/design_oos.py:552`) reads `oos-accepted-design.md`, extracts unfiled non-security blocks, and emits `FILE_DESIGN_OOS_STATUS=ready` (or `skip-no-items` at `:601`).
- The issue is created by **`/larch:issue`** (batch mode) from the `file-issues` branch — `skills/design/SKILL.md:574` (helpers at `:687`). Annotate then writes `- **Filed URL**:` back to avoid double-filing.

**Verification against committed run logs:** across **711** `/design` run logs, **144 filed an OOS issue** (`oos-issues-created.md` present); 193 had OOS proposed, 111 had accepted OOS. So the design path fires when the panel accepts OOS. The scarcity of design `[OOS]` issues is the **strict rubric rejecting proposals**, not a broken path — which the "loosen to legitimacy" change below fixes.

A prior partial fix (#6291) added an aggregate-severity promotion pool to design OOS (`_promote_aggregate_oos_pool` / `_aggregate_trigger_fires`, `design_oos.py:165`/`:176`) — a supplement, not a replacement for the direct path, and it did not touch `/implement`.

## Key distinction: pre-vote-dropped ≠ voted-and-rejected

This is the crux of the bug. The "Dropped OOS candidates" are items that **never reached the voters** — the materiality rubric was never applied to them; they were dropped blind, purely for carrying an `[OOS]` tag. That is different from items **voted on and rejected** (which land in `rejected-findings.md` after the panel applied the rubric and said NO). The former is silent, un-adjudicated loss; the latter is a legitimate decision.

## Design decision & rationale

Three coherent options were considered:

- **(A) Drop entirely.** Only coherent if we *also* stop generating and instructing OOS. As-is it is the worst of both worlds: we pay to generate OOS, ship voter instructions and tally/filer machinery, then drop everything before the one gate that separates signal from noise — permanently losing genuine correctness/security follow-ups with no recourse.
- **(B) File everything surfaced.** Noise/spam; high triage cost. Rejected.
- **(C) Vote, then file survivors as one issue.** What the machinery was built for.

**Decision: (C), with a loosened voting standard.** The judges vote on OOS; everything accepted by the standard panel thresholds is filed into **one** unifying `[OOS]` issue, **regardless of the issue's contents or size** — the "filing criteria" (any post-vote materiality/count gate) is removed. Acceptance uses the standard thresholds: **2+ YES in a 3-judge panel, 1+ in a 2-judge panel, unilateral in a 1-judge panel.**

**Voting standard is loosened to "legitimacy"** (not the strict default-deny materiality gate): judges accept any genuine, concrete, non-duplicate OOS observation, and still auto-reject pure style/polish/noise and speculative/hypothetical items with no concrete trigger. Rationale: restoring the vote under the *current strict* rubric ("would this beat the median item in a busy maintainer's backlog?") would still reject most OOS, so the user would keep seeing few `[OOS]` issues. Loosening to legitimacy is what actually makes OOS follow-ups appear again while still filtering noise.

## Desired behavior

1. **Vote on OOS in both skills.** Remove/neutralize the `/implement` pre-vote OOS gate so `[OUT_OF_SCOPE]` findings ride the ballot and are voted on across the normal, validation-exhausted, and empty-merge review paths. `/design` already votes on OOS — no gate to remove there.
2. **Loosen the acceptance standard to "legitimacy"** in `skills/shared/oos-acceptance-rubric.md`: accept any genuine, concrete, non-duplicate OOS observation; still auto-reject pure style/polish/noise and speculation with no concrete trigger. Applies to both code-review (implement) and plan-review (design) voters.
3. **Always file one unifying `[OOS]` issue.** Every item accepted by the standard panel thresholds (2+/3, 1+/2, unilateral/1) is filed into a single `[OOS]` issue for the run, regardless of contents, size, or severity — no post-vote materiality or count gate. This already works via `OOS_ISSUES_PER_RUN_CAP=1` rollup in `file_oos.py` (`issue_cap` / `_aggregate_block`); ensure nothing suppresses a small or single-item batch.
4. **Empty accepted set → file nothing** (no empty issue). Keep semantic dedup so re-runs don't create duplicate `[OOS]` issues.
5. **Repurpose the "Dropped OOS candidates" final-summary section** (`review_phase_detail.py:127`) to list **voted-and-rejected** OOS as an audit trail, since nothing will be dropped pre-vote in `/implement` anymore.

- Docs: `docs/run-logs.md` (the "manual filing queue" wording), `docs/voting-process.md`, `skills/shared/voting-protocol.md`.

## Acceptance criteria

- A `/implement` run where reviewers surface OOS files exactly one `[OOS]` issue containing all vote-accepted OOS items; none are silently dropped before the vote.
- A `/design` run with vote-accepted OOS files one unifying `[OOS]` issue.
- Under the loosened rubric, a genuine, concrete OOS observation (non-style) is accepted at or above the panel threshold and lands in the unifying issue.
- Pure style/noise OOS is still rejected and appears only in the rejected-OOS audit list.
- No empty `[OOS]` issue is filed when nothing is accepted; re-runs dedup instead of creating duplicates.
