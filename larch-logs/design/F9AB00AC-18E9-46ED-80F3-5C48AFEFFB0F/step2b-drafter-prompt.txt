# [Bug] /design Step 3 poll loop leaves background task registered, blocks session exit

## Context

During a `/design` run for issue #4077, `design-step3-review.sh` was launched with `run_in_background: true` (task ID `brldnoktv`). After launching it, the orchestrator spawned a polling loop instead of waiting for `&lt;task-notification&gt;`:

```bash
for i in $(seq 1 40); do
  if ls "$DESIGN_TMPDIR/.step3-review-result.env" 2&gt;/dev/null; then
    echo "Review result ready!"; break
  fi
  sleep 15
done
```

The loop found `.step3-review-result.env`, the design proceeded normally, and `/design` finished. But the background task handle (`brldnoktv`) was never consumed through the task notification mechanism. Claude Code kept it registered as running, preventing session exit until `TaskStop` was called manually.

## Root cause

The polling loop bypasses Claude Code's task lifecycle. Claude Code tracks background tasks by waiting for the subprocess to exit and firing `&lt;task-notification&gt;`. When the orchestrator polls a result file and proceeds without receiving that notification, the task remains registered as in-flight indefinitely.

The prohibition is documented in AGENTS.md:

&gt; Don't spawn a Monitor or a Bash `run_in_background` polling loop (`for`/`while`/`until` + `sleep`) to watch another job finish. For long helpers, rely on Bash `&lt;task-notification&gt;` for one-shot completion.

And repeated in `skills/design/SKILL.md` Step 3:

&gt; Wait for `&lt;task-notification&gt;` before parsing stdout or reading `.step3-review-result.env`.

Both instructions exist; the orchestrator violated them anyway.

The trigger was impatience: the task appeared stuck (output file showed 0 bytes for several minutes), so a polling loop was introduced to unblock forward progress. This is precisely the anti-pattern the rule targets.

## Suggested fix

Two complementary mitigations:

**1. Strengthen the consequence statement in SKILL.md Step 3.**

The current instruction says "Wait for `&lt;task-notification&gt;`" but does not explain *why*. Adding the consequence makes the cost concrete and harder to rationalize away:

&gt; **⚠ NEVER poll `.step3-review-result.env` with a sleep loop. Polling bypasses Claude Code's task lifecycle and leaves the task registered as running, blocking session exit until `TaskStop` is called manually. Wait for `&lt;task-notification&gt;` unconditionally.**

**2. Add to `skills/shared/orchestrator-never.md` (or the existing NEVER list in SKILL.md) an explicit entry:**

&gt; **NEVER poll a `run_in_background` result file with a Bash sleep loop.** The task stays registered as running until `&lt;task-notification&gt;` fires. Polling that finds the result file first leaves a dangling task handle that blocks session exit.

The fix does not require code changes — both mitigations are documentation/instruction updates only.
