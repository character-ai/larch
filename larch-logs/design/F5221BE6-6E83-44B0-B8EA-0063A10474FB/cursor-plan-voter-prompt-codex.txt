# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope

## Summary

`/implement`'s "Bash block prelude" contract (`skills/implement/SKILL.md:97-105`) requires every post-Step-0 fence to be a single physical line of the form `bash "$IMPLEMENT_TMPDIR/larch-run.sh" &lt;script&gt; ...`, relying on `$IMPLEMENT_TMPDIR` already being an exported shell variable. The same section states the Bash tool does not preserve shell state between calls. Because each Bash tool invocation starts a fresh shell, `$IMPLEMENT_TMPDIR` is empty on the very first post-Step-0 fence, so the launcher path resolves to `/larch-run.sh` and `bash` fails with exit 127 before `larch-run.sh` ever runs.

## Original report

"the cause of the above failure \"Background command \"Dispatch Step 2 implementation to Codex\" failed with exit code 127\""

This was reported immediately after a live `/implement --merge 6071` run's Step 2 dispatch fence failed in the background with exit code 127.

## Reproduction scenario

1. Run `/implement &lt;issue-N&gt;` through Step 0 in one Bash tool call. Step 0 bootstrap succeeds and exports `IMPLEMENT_TMPDIR` (and `CLAUDE_PLUGIN_ROOT`) only within that call's shell.
2. Issue the Step 2 fence from `skills/implement/SKILL.md:310` verbatim, as its own separate Bash tool call, without re-exporting `IMPLEMENT_TMPDIR` first:
   ```bash
   bash "$IMPLEMENT_TMPDIR/larch-run.sh" python/cli.py implement run-dispatch --implement-tmpdir "$IMPLEMENT_TMPDIR" --coder "$coder"
   ```
3. Observe: the new shell has no `IMPLEMENT_TMPDIR`, so `"$IMPLEMENT_TMPDIR/larch-run.sh"` expands to `/larch-run.sh`. `bash` cannot find that file and exits 127 with `bash: /larch-run.sh: No such file or directory`, before `larch-run.sh`'s own body (including its self-derivation fallback) ever executes.

Reproduced live in this session: the first Step 2 dispatch attempt failed exactly this way. Re-running with `export IMPLEMENT_TMPDIR=&lt;literal-tmpdir&gt;` (and `export coder=codex`) prepended in the same Bash call succeeded.

## Expected behavior

Every post-Step-0 fence in `/implement` (roughly 21 occurrences of this pattern in `skills/implement/SKILL.md` alone, spanning Steps 2 through 18) should reliably resolve and invoke `$IMPLEMENT_TMPDIR/larch-run.sh` from a fresh Bash tool call, without the orchestrating agent needing to break the "exactly one nonblank, noncomment physical line" / "no inline shell logic" rule to reconstitute missing environment state.

## Observed behavior

The first post-Step-0 fence issued as its own Bash tool call fails with exit code 127 (`bash: /larch-run.sh: No such file or directory`) because `$IMPLEMENT_TMPDIR` is empty in the new shell. `larch-run.sh`'s internal self-derivation fallback never gets a chance to run, because the failure happens while the calling `bash` process is still trying to locate the script file, before any of the script's own text is interpreted.

## Root cause analysis

`skills/implement/SKILL.md:97-105` ("Bash block prelude") states plainly: "The Claude Code Bash tool does NOT preserve shell state between calls," matching the Bash tool's documented behavior (only cwd persists across separate invocations; exported variables do not). Despite stating this, the same section mandates that every post-Step-0 fence be a single physical line referencing `"$IMPLEMENT_TMPDIR/larch-run.sh"`, and explicitly forbids sourcing an env file, using continuations, or adding "inline shell logic" — which would include a plain `export IMPLEMENT_TMPDIR=...` line to work around the missing variable.

`python/larch/state/bootstrap.py`'s `_write_larch_run_sh` (line 144) writes a self-healing fallback into the generated `larch-run.sh` (line 151: `IMPLEMENT_TMPDIR="${IMPLEMENT_TMPDIR:-$(cd "$(dirname "${BASH_SOURCE[0]}")" &amp;&amp; pwd -P)}"`), which would correctly re-derive `IMPLEMENT_TMPDIR` from the script's own on-disk location once the script starts running. That fallback is unreachable in this failure mode: `bash "$IMPLEMENT_TMPDIR/larch-run.sh" ...` with an empty `IMPLEMENT_TMPDIR` resolves the launcher's own path to the literal string `/larch-run.sh` before `bash` ever opens or interprets the file, so it fails at the "no such file" stage rather than reaching line 151 of the generated script.

The fallback solves "the script can't find its own tmpdir once it's running," but not "the caller can't find the script in the first place" — the actual failure mode whenever a fresh Bash tool call has no exported `IMPLEMENT_TMPDIR`.

No shell profile on this machine (`~/.zshrc`, `~/.bashrc`, `~/.bash_profile`, `~/.zprofile`) sources any larch session-env file, so nothing else re-establishes `IMPLEMENT_TMPDIR` automatically in a new shell.

**This is the fourth time this problem area has surfaced, and the current gap traces directly to the fix that was supposed to close it:**

- #2071 (DONE) fixed `CLAUDE_PLUGIN_ROOT` not being rehydrated in Bash blocks, establishing the "every post-Step-0 block re-derives its env vars" pattern — but only for `CLAUDE_PLUGIN_ROOT`, not `IMPLEMENT_TMPDIR` itself.
- #2195 (DONE) fixed a Step 18 bug where `IMPLEMENT_TMPDIR` was assigned a literal value but not `export`-ed, so a **child process** (`capture-session-transcript.sh`) couldn't see it. Its root-cause writeup states plainly: "All other Step 0–17 Bash blocks in SKILL.md include `export IMPLEMENT_TMPDIR`." That is a different failure layer than this report — #2195 assumes the fence itself already has the correct value as a local shell variable; this report is about the value being absent from the fence's own shell in the first place.
- #4037 (DONE, URGENT) fixed a Step 18 fence that used an unguarded `. "$IMPLEMENT_TMPDIR/plugin-root.env"` source with no `-f` test, crashing when the tmpdir had already been cleaned up by a prior successful teardown. Its "Structural fix" note says: "Issue #4011 (`/implement: collapse Bash-fence rehydration preludes via a session launcher script`) replaces ALL post-Step-0 fences with a single `bash "$IMPLEMENT_TMPDIR/larch-run.sh" &lt;script&gt;` call that handles its own rehydration inside the launcher, eliminating the copy-drift hazard entirely."
- **#4011 (DONE) is the issue that introduced the exact `larch-run.sh` launcher pattern this report is about.** Its plan explicitly lists, as the launcher's first responsibility: "1. Set `IMPLEMENT_TMPDIR` from the environment, or from the launcher directory if unset" — i.e. it anticipated `IMPLEMENT_TMPDIR` being unset and designed a self-derivation fallback for exactly that case (this is the `${IMPLEMENT_TMPDIR:-$(cd "$(dirname "${BASH_SOURCE[0]}")" &amp;&amp; pwd -P)}` line in `bootstrap.py:151`). But #4011's own acceptance criteria pin the caller-side fence shape as `bash "$IMPLEMENT_TMPDIR/larch-run.sh" &lt;script&gt;` — which still requires `$IMPLEMENT_TMPDIR` to already be set *at the calling shell*, before the launcher (and its self-derivation fallback) ever starts running. The self-derivation branch can only ever fire once the launcher is already executing, so it never covers the case reproduced here: a brand-new Bash tool call, right after Step 0, with nothing yet exported.

So this is not a fresh problem in a new area — it is a specific, still-open gap in the exact fix (#4011) that was supposed to eliminate this whole class of bug, in the exact way #4011 anticipated (an unset `IMPLEMENT_TMPDIR`) but did not fully close (the caller can't reach the fallback if it can't find the launcher first).
