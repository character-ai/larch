# [BUG] (URGENT) OOS gate silently drops accepted [OUT_OF_SCOPE] review findings

[BUG] (URGENT) OOS gate silently drops accepted [OUT_OF_SCOPE] review findings

## Summary

The OOS disposition gate that guards PR creation/merge in the ship driver counts only `### OOS_`-headed blocks as non-security accepted OOS. Accepted out-of-scope review findings emitted under the **legacy `### FINDING_N: [OUT_OF_SCOPE]` header** (which `tally-code-votes.sh` explicitly supports and writes verbatim) are counted as **zero**, so the disposition gate trivially passes and the findings are **never filed** — a silent drop that violates the `/implement` orchestrator's NEVER #14 ("NEVER silently drop a voted-in OOS finding").

Discovered during the `/implement` run for #3432 (PR #3549, merged): 3 voted-accepted `[OUT_OF_SCOPE]` review findings (tallies YES=3, YES=3, YES=2/EXON=1) were dropped; the run's final summary reported `OOS filed: 0`.

## Affected paths

- **Producer**: `skills/review/scripts/tally-code-votes.sh` (~lines 505-587). It accepts BOTH `### OOS_*` and legacy `### FINDING_* [OUT_OF_SCOPE]` headers (`if [[ "$id" == OOS_* ]] || head -n1 "$block" | grep -Fq '[OUT_OF_SCOPE]'`) and copies the block **verbatim** (`cat "$block" >> "$OOS_ACCEPTED_OUT"`), preserving the original `### FINDING_N:` header.
- **Counter (bash)**: `scripts/oos-non-security-block-count.awk` — matches `^###[[:space:]]+OOS_` only.
- **Counter (python port)**: `python/oos.py` — `_OOS_HEADER_RE = re.compile(r"^###\s+OOS_", re.MULTILINE)`; `_count_non_security` skips any file lacking a `### OOS_` header, returning 0.
- **Gate consumer**: `python/ship.py` `_oos_gate` (and the analogous bash `ship-pr.sh` path) — `count_non_security == 0` ⇒ `disposition_ok` trivially true ⇒ proceed to pr-create/merge without emitting `oos-filing` (`NEEDS_USER_INPUT`).
- **Downstream filing parser**: `skills/issue/scripts/parse-input.sh` OOS mode also keys on `### OOS_N:`.

## Root cause

A **format-contract mismatch** between the OOS producer and the OOS counter/gate:

- `tally-code-votes.sh` intentionally supports two accepted-OOS header formats (`### OOS_N:` and legacy `### FINDING_N: [OUT_OF_SCOPE]`) and copies the block verbatim. So when reviewers tag a finding `[OUT_OF_SCOPE]` (instead of assigning an `OOS_N` id), the `### FINDING_N:` header survives into `oos-accepted-review.md` / `accumulated-oos.md`.
- The counter (`oos-non-security-block-count.awk`, and its faithful Python port in `python/oos.py`) recognizes **only** `### OOS_`, so it counts these blocks as 0.

This is **pre-existing in the bash ship path** — `python/oos.py`'s `count_non_security` docstring is literally "Port oos-non-security-block-count.awk block counting", so the Python ship driver (#3462 soak) reproduces the gap exactly rather than introducing it. The soak run merely surfaced it under close observation.

## Reproduction

Minimal:

```
printf '### FINDING_1: [OUT_OF_SCOPE] x\n' > f.md   # count_non_security -> 0  (BUG: should be 1)
printf '### OOS_1: x\n'                  > g.md   # count_non_security -> 1
```

End-to-end:
1. Run `/implement <issue>` on a change whose review panel emits ≥1 accepted `### FINDING_N: [OUT_OF_SCOPE]` finding (no `OOS_N` id).
2. `oos-accepted-review.md` then contains `### FINDING_N: [OUT_OF_SCOPE]` blocks with `Result=accepted`.
3. `python3 -c "import oos,sys; print(oos.count_non_security(('oos-accepted-review.md',)))"` → `0`.
4. Ship driver merges with `OOS filed: 0`; no issue created for the accepted findings.

## Impact

- **Silent drop of voted-in OOS findings** (NEVER #14) on any run whose accepted review OOS use the `[OUT_OF_SCOPE]` FINDING header rather than an `OOS_N` id.
- Affects both the bash `ship-pr.sh` and Python `ship.py` gates equally.
- Directly relevant to #3462 (ship.py default cutover) and #3132 (ship.py umbrella): the cutover must not ship a gate blind to legacy-header OOS.

## Suggested fix

**Preferred (normalize at the producer — single fix point):** in `skills/review/scripts/tally-code-votes.sh`, when appending an accepted `[OUT_OF_SCOPE]` block whose header is `### FINDING_N:`, **rewrite the header to `### OOS_<k>:`** (fresh sequential index) before writing to `oos-accepted-review.md` / `OOS_ACCEPTED_OUT`, preserving the original finding title text after the id. This makes every downstream consumer — the counter, the disposition gate, and the `/issue` batch parser — see the canonical `### OOS_` schema. (Mirror the same normalization in `oos-accepted-main-agent.md` / design OOS producers if they can emit the FINDING header.)

**Alternative / defense-in-depth (align the readers):** extend `scripts/oos-non-security-block-count.awk` and `python/oos.py` `_OOS_HEADER_RE` to also match `^###\s+FINDING_\d+:\s*\[OUT_OF_SCOPE\]`. This is insufficient alone, because `skills/issue/scripts/parse-input.sh` still needs `### OOS_N:` to actually create the issues — so producer normalization is required regardless; reader alignment is a backstop.

**Regression coverage:** add a fixture `oos-accepted-review.md` containing only `### FINDING_N: [OUT_OF_SCOPE]` accepted blocks and assert `count_non_security > 0`, that the gate emits `oos-filing`, and (end-to-end) that an issue is actually filed. Cover both the Python gate (`python/test_oos*.py` / `python/test_ship*.py`) and the bash gate harness (`skills/implement/scripts/test-oos-disposition-gate.sh`).

- `count_non_security` (Python + awk) counts `[OUT_OF_SCOPE]`-tagged accepted blocks.
