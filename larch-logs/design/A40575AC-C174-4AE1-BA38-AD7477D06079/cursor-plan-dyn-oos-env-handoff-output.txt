**1. [correctness] `emit-tally.sh` else-branch can still wipe tally output (`skills/review/scripts/emit-tally.sh:153-159`)**

The plan’s skip guard targets only the `oos-serialize.sh` invocation. Today’s control flow is:

```153:159:skills/review/scripts/emit-tally.sh
if [[ -n "$OOS_FILE" && -f "$OOS_FILE" ]]; then
    oos_args=(--findings-file "$OOS_FILE" --output-file "$OOS_ACCEPTED_FILE")
    [[ -n "$SESSION_ENV_PATH" ]] && oos_args+=(--session-env-path "$SESSION_ENV_PATH")
    "$SHARED_DIR/oos-serialize.sh" "${oos_args[@]}" >/dev/null || true
else
    : > "$OOS_ACCEPTED_FILE"
fi
```

If `OOS_ACCEPTED_COUNT > 0` but `oos.md` is absent, the else branch still truncates `$OOS_ACCEPTED_FILE`. On the nested `/implement` path, `review-core.sh` then `copy_to_parent`s that file over the parent `oos-accepted-review.md` tally already wrote via `OOS_ACCEPTED_OUT`, undoing normalization even when the tally env says accepted OOS exist. The plan should guard the **whole** if/else, not only the serialize arm.

**2. [correctness] Missing numeric coercion for `OOS_ACCEPTED_COUNT` (`skills/review/scripts/emit-tally.sh:58-81`)**

`count_from_tally` returns an empty string when a key is missing (`END { if (!found) print "" }`). `ACCEPTED_COUNT` / `REJECTED_COUNT` / `EXONERATED_COUNT` are coerced to `0` at lines 79–81; `OOS_ACCEPTED_COUNT` is not. The plan cites “default `0` when absent” but does not specify the same coercion before `> 0` comparison. That matters for legacy or zero-judge tally env files that lack the key.

**3. [correctness] Counter write timing vs normalization (`skills/review/scripts/tally-code-votes.sh:583-592,776-792`)**

The plan correctly increments per accepted block and relies on the existing end-of-script env append. It should state explicitly that `OOS_ACCEPTED_COUNT` in `review-tally.env` is written **once, after** all normalized appends complete, and that increments stay in the non-security append branch only. Current structure already does this; making it normative prevents a partial implementation from emitting the counter mid-loop.

**4. [testing] `test-emit-tally.sh` preservation case is byte-only (`skills/review/scripts/test-emit-tally.sh`)**

The proposed case checks that a pre-seeded canonical block survives emit. It should also assert `OOS_ACCEPTED_COUNT` remains `1` in the tally env **and** that `oos-non-security-block-count.awk` returns `> 0` on the preserved file, so the test validates semantic preservation rather than only `cmp` equality.

**Verified (no finding): skip guard vs legacy `FINDING_` headers**

The guard keys on `OOS_ACCEPTED_COUNT > 0`, not header shape. After producer normalization, a tally run that accepted legacy `### FINDING_N: [OUT_OF_SCOPE]` or scope-drift bare `### FINDING_N:` blocks will set `OOS_ACCEPTED_COUNT > 0` even though the on-disk headers were legacy before normalization. That matches the intended production fix.

**Verified (no finding): re-tally with zero accepted after a prior preserved file**

`tally-code-votes.sh` truncates `oos-accepted-review.md` (and the parent mirror when paths differ) at lines 105–116 before processing. A re-tally that accepts zero OOS writes `OOS_ACCEPTED_COUNT=0` and an empty accepted file; emit-tally correctly falling through to serialize/truncate is intended, not a bypass of the guard.

**Verified (no finding): `count_from_tally` when the tally **file** is absent**

`emit-tally.sh` requires `--tally-file` to exist (line 46) and exits before `count_from_tally` runs. “Default 0” applies to a **missing key**, not a missing file.
