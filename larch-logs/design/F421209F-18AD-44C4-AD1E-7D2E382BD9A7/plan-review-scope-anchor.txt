### Item 1 — Ship pre-fix-rebase / phase14 guard hardening (from #6367)

- **Location**: `python/larch/implement/ship.py` (`ship pre-fix-rebase` / phase14 paths; `_ship_route_phase14_reship_pending`, `rebase_and_push`, `_ship_pre_fix_write_conflict_state`, `_write_ship_state`, `_ship_pre_fix_patch_handoff`).
- **Severity**: important.
- **Concern**: The `ship pre-fix-rebase` / phase14 paths can return `NEXT_ACTION=continue` before checking for an in-progress rebase, conflict metadata, branch/repo/protected-branch guards, or an explicit freshness sentinel. A stale handoff flag can green-light `ci-fix` or `reship` on the wrong checkout, skip conflict routing for a paused rebase, or let generated-file `ci-fix` repairs run without a mechanical successor to the removed step-6 merge-ref rebase guard. Successful pre-fix rebases also do not update `REBASE_COUNT`, so the CI monitor can allow more physical rebases than the configured cap. The in-progress conflict path may omit a `PHASE=rebase` state write, and the pre-push conflict handoff write-failure path lacks regression coverage.
- **Suggested revisions**:
  - Run in-progress-rebase, conflict-metadata, branch/repo, and protected-branch checks before any phase14 skip or `NEXT_ACTION=continue`.
  - Do not key the skip solely on flag presence; limit it to the no-checks-observed phase14 case, distinguish flag content/reason, and unlink or use a separate marker for conflict handoffs from `_write_handoff_flag`.
  - Mirror `_ship_route_phase14_reship_pending` where appropriate.
  - After a successful `rebase_and_push` with `result.rebased` true, increment and persist `REBASE_COUNT`, or centralize counter updates inside `rebase_and_push` for all callers.
  - Reuse `_ship_pre_fix_write_conflict_state` or `_write_ship_state(phase=rebase)` on the in-progress conflict path.
  - Write a tmpdir sentinel from `ship_pre_fix_rebase_main` and fail closed in `ci-fix` when `PRE_FIX_REBASE_REQUIRED=true` but the sentinel is absent.
  - Add a monkeypatch regression test forcing `_ship_pre_fix_write_conflict_state` or `_ship_pre_fix_patch_handoff` to raise; assert `rc != 0` and no `NEXT_ACTION=`.

### Item 2 — Derive the step3 bg-wait 15600s marker timeout from the shared constant (from #6339)

- **Location**: `python/larch/implement/dispatch_commit_route.py:88`.

## Proposed Design Outline

### Goals
- Harden the ship pre-fix-rebase / phase14 paths: add missing guards, fix REBASE_COUNT tracking, add regression test.
- Deduplicate the step3 checks timeout (10800s) and commit-route marker timeout (15600s) to a single source of truth.
- Fix execution-issue artifact precedence so tmpdir markdown entries are not silently dropped when run-dir NDJSON also exists.
- Wire `test-write-final-report` into a CI shard and fix the SECURITY.md truncation-marker mismatch.

### Non-goals
- No restructuring of the ship.py state machine beyond the targeted guard additions.
- No changes to the CI runner, check engine, or final-report rendering beyond the artifact-precedence fix.
- No new public API surface beyond the one constant rename in `dispatch_leg.py`.

### Approach sketch
- In `dispatch_ship.py`: run branch/repo/in-progress-rebase checks before the phase14 flag skip; increment REBASE_COUNT after a successful rebase; write `.phase=rebase` state on the in-progress conflict path; write a pre-fix-rebase sentinel; add a monkeypatch test.
- In `dispatch_leg.py`: expose `_CHECKS_DEADLINE_MS` as a public constant.
- In `dispatch_commit_route.py`: derive both hardcoded timeouts (10800, 15600) from the named constants; update the existing test assertion for TIMEOUT_S.
- In `run-step-checks.sh`: derive TIMEOUT_S from a Python constant at startup to eliminate duplication.
- In `exec_issue_detail.py`: change `prefer_run_dir` semantics so tmpdir markdown takes precedence when non-empty, even if NDJSON exists; update the affected test.
- In `Makefile`: append `test-write-final-report` to one `test-harnesses-N` shard.
- In `SECURITY.md`: update the truncation-marker example text from the em-dash form to the colon form.
