# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

## Summary

The `/implement` Step 3 checks `.bg-wait-active` marker writer is the only one of nine bg-wait-marker writers that does not stamp a local `CLONE_PATH=` line on the marker (and it does not read `.larch-keepalive` at all). The recent cross-clone hook-scoping remediation (#5925 / #5927 / #6108 / #5948) resolves a marker's owning clone from its own `CLONE_PATH` stamp first, falling back to the sibling `.larch-keepalive` `CLONE_PATH`. Because the Step 3 marker never carries the direct stamp, its clone identity depends entirely on the keepalive fallback. If that keepalive is ever missing or unreadable, this marker's clone identity becomes unknown and can, under a narrow additional condition, cause a sibling clone's Step 3 tool calls to be falsely denied — the same cross-clone false-denial class as #5925 / #5927 (denial-only; this is not a process-kill path). Step 3 checks runs on every `/implement`, so this is the most frequently-live marker in the codebase, and no test guards the omission.

## Original report

Found during a correctness/completeness audit of the recent cross-session process-death fixes (the #6213 / #6237 kill cluster and the #5925 / #5927 / #6108 / #5948 / #6137–#6141 cross-clone hook-denial cluster).

Independent enumeration of every `.bg-wait-active` writer showed eight of nine writers read `.larch-keepalive` and stamp `CLONE_PATH=%s` on the marker, while `skills/implement/scripts/run-step-checks.sh` (STEP=`implement-step3-checks`) writes only five fields and omits the stamp. The two guard hooks were confirmed to gate every deny/count/block decision through the deduped `marker_foreign_clone` clone-ownership helper (byte-identical across both hooks, CI-parity-tested), so cross-clone scoping is otherwise sound; this writer is the one site the CLONE_PATH remediation did not reach.

## Reproduction scenario

Direct field reproduction is difficult because it requires the keepalive fallback to be unavailable, which is off the normal path. The gap itself is confirmed statically:

1. Start any `/implement` run and let it reach Step 3 checks (the site invoked with `run_in_background: true`). Observe the written marker:
   `cat "$IMPLEMENT_TMPDIR/.bg-wait-active"` → contains `PID`, `CLAUDE_PID`, `START_EPOCH`, `STEP=implement-step5-review`-style `STEP=implement-step3-checks`, `TIMEOUT_S`, but **no `CLONE_PATH=` line**.
2. Compare against the Step 5 marker written by `step-5-review.sh`, which includes a trailing `CLONE_PATH=&lt;repo path&gt;` line.

Cross-clone denial requires the additional, off-normal-path condition below (keepalive missing/unreadable **and** a sibling clone whose leaf-dir basename sanitizes to the same clone-tag), so it is a latent exposure rather than a routinely-reproducible failure.

## Expected behavior

The Step 3 checks marker should carry the same `CLONE_PATH=` stamp every other bg-wait writer applies, so `marker_foreign_clone()` can resolve this marker's owning clone directly from the marker itself, without depending on the `.larch-keepalive` fallback. Clone scoping for this marker should be as robust as it is for Step 5, Step 6, Step 7a, Step 8, the checks-commit-route marker, and the design markers.

## Observed behavior

The Step 3 checks marker carries no `CLONE_PATH` stamp. `marker_foreign_clone()` falls back to `.larch-keepalive`'s `CLONE_PATH`. In the normal case the keepalive is present and scoping still holds. But when the keepalive is missing or unreadable, this marker's clone identity is unknown, so it drops into the #6138 "unknown identity keeps the marker conservatively" fail-closed path plus the basename clone-tag heuristic (`bash_probe_target_dir_plausible`). Under those conditions a sibling clone whose cwd leaf-dir basename sanitizes to the same clone-tag can have its own Step 3 Bash probes / `Monitor` / `TaskOutput` / prompt falsely denied by this foreign marker.

## Root cause analysis

`skills/implement/scripts/run-step-checks.sh:72-73` writes the marker with a five-field `printf` and no keepalive read:

```
printf 'PID=%s\nCLAUDE_PID=%s\nSTART_EPOCH=%s\nSTEP=implement-step3-checks\nTIMEOUT_S=10800\n' \
  "$$" "$_step3_claude_pid" "$_step3_start" &gt;"$IMPLEMENT_TMPDIR/.bg-wait-active" 2&gt;/dev/null || true
```

Every other writer first reads `.larch-keepalive` `CLONE_PATH` (guarding against a symlink) and appends `CLONE_PATH=%s`. The clone-ownership remediation (#5925 / #5927) added the stamp to those writers but this one was missed. No lint or test asserts that every `.bg-wait-active` writer stamps `CLONE_PATH`; the existing parity test (`scripts/test-hook-clone-ownership-parity.sh`) only compares the two hook scripts' helper functions, not the marker writers, so the omission is unguarded.

Severity is low: the keepalive fallback covers the normal case, the failure mode is a false tool-call denial (not a process kill), and it requires a basename clone-tag collision to actually cross-block. But it is a genuine completeness gap in the cross-clone remediation, on its highest-exposure marker.
