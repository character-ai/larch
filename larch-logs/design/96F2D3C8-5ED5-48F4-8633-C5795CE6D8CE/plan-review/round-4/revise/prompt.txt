# [BUG] Committed run-log final-summary/manifest misrecord merged runs as bailed/partial

## Summary

Committed `/implement` run-log artifacts misrecord successfully **merged** runs as failed. For a run that merged its PR, the committed `larch-logs/implement/&lt;run-id&gt;/final-summary.md` records `Outcome: bailed` and `manifest.json` records `status: partial` with `steps_ran.step8=false`. The live end-of-run summary and the GitHub tracking-issue comment are correct ("merged"); only the committed run-log tree is wrong. This corrupts the historical run-log dataset that `audit-runs` / `verify-completeness` and other committed-log analyzers read, causing them to classify clean merges as bails. Observed across 5 consecutive recent runs, so it is systemic rather than run-specific.

**This is a regression of the already-closed #2524** ("/implement bailed outcome shipped despite successful merge"), whose post-merge fix was subsequently banned by NEVER #16 and never replaced with a pre-merge equivalent. See Root cause analysis.

## Original report

committed-log bailed/partial misrecording.

Discovered during `/implement --merge 4678` (PR #4897, merged via `admin_merged`). The live run reported `outcome=OK`, `merge_result=admin_merged`, and the Step 17 summary block rendered `— merged`. But after the merge landed on `main`, the committed run-log artifacts for that run read as a failed/partial run. Cross-checking other recent run-log directories showed the same pattern on every merged run inspected.

## Reproduction scenario

1. Run `/implement --merge &lt;issue-N&gt;` to completion so the PR merges (CI passes, `merge_result=merged` or `admin_merged`).
2. After merge, check out `main` and inspect the committed run log:
   - `head -3 larch-logs/implement/&lt;run-id&gt;/final-summary.md`
   - `python3 -c "import json; d=json.load(open('larch-logs/implement/&lt;run-id&gt;/manifest.json')); print(d['status'], d['steps_ran'])"`
3. Observe `final-summary.md` first line ends with `— bailed` and `Outcome: bailed`, and `manifest.json` shows `status=partial`, `steps_ran={'step8': False, ...}`, despite the PR having merged.

No special setup required; this reproduces on the normal `--merge` happy path.

## Expected behavior

For a run whose PR merged, the committed run-log snapshot should reflect a non-failure outcome. Either:

- the committed `final-summary.md` / `manifest.json` record `merged` (the design-blessed speculative pre-squash flush described in `skills/implement/SKILL.md` NEVER #16), or
- at minimum a neutral non-terminal outcome (e.g. `pr-created`) rather than the terminal-failure token `bailed`, with `manifest.status` not equal to `partial` and `steps_ran.step8` consistent with `final-summary.md` actually being present.

This mirrors #2524's accepted acceptance criterion: for any run whose parent-issue PR is merged when the final-summary is written, the committed outcome must be one of `{merged, succeeded, …}` and never bare `bailed`.

## Observed behavior

Confirmed merged run `2396BA29-A4E2-4C78-B6B1-0C3CBE380897` (issue #4678, PR #4897):

- live ship driver returned `outcome=OK`, `merge_result=admin_merged`; `git log` on `main` has `829aeb158 Fixes #4678 ... (#4897)`.
- committed `final-summary.md` line 1: `## /implement run 2396BA29-... — bailed`; line 3: `- **Outcome**: bailed`.
- committed `manifest.json`: `status=partial`, `steps_ran={'step8': False, 'step9a1': True}`, `stalled_at_step=null`.

Same pattern across the 5 most recent committed run-log directories (all `final-summary` = `bailed`, all `manifest` = `status=partial`, `step8=false`). One older dir additionally showed the fully-degraded `status=None`, `steps_ran={}` empty-object variant.

## Root cause analysis

The committed run-log artifacts are flushed at the **pre-PR-create** point (`pr-prep`, before `python/cli.py pr create`), and NEVER #16 forbids re-committing corrected artifacts after the squash-merge. So the committed snapshot freezes whatever outcome was computable before the PR existed.

At that pre-PR moment `ship-pr-state.sh` has neither `PR_NUMBER` nor `MERGE_RESULT`, so `stall_recovery.normalized_outcome_values` (python/stall_recovery.py:659-674) falls through its cascade:

```
elif merge_result in {"merged", "admin_merged"}: outcome = "merged"
elif merge_result == "already_merged":          outcome = "force-merged-externally"
elif pr_number ... and draft:                   outcome = "pr-created-draft"
elif pr_number ... and not draft and not merge:  outcome = "pr-created"
else:                                            outcome = "bailed"   # &lt;-- pre-PR snapshot lands here
```

With no `PR_NUMBER` and no `MERGE_RESULT`, and not a fork/design-only/stall path, the `else` branch assigns `bailed`. `final_report.write_final_report` consumes that value, so the committed `final-summary.md` says `bailed`. `final_report._stamp_skipped_steps_for_terminal_report` (python/final_report.py:387-434) then stamps `steps_ran.step8=false` for any non-`merged` outcome when `final-summary.md` / `version-bump-reasoning.md` are absent, and the manifest status becomes `partial`.

The live Step 17 re-render (post-merge, in-tmpdir) and the API-only `final-report write --comment-only` tracking-issue refresh both compute `merged` correctly because by then `MERGE_RESULT=admin_merged` is in state. But that corrected state is never committed (NEVER #16), so the squash-merge tree keeps the pre-PR `bailed`/`partial` snapshot.

**Regression lineage (key context for the fix):**

- **#2524** ("[DONE] /implement bailed outcome shipped despite successful merge", closed 2026-05-21) fixed this exact symptom in the old bash `scripts/ship-pr.sh` by adding a **post-merge** `write-final-report.sh` + `larch-log.sh commit` in `run_postmerge_phase`, gated by `LARCH_LOG_COMMIT_POSTMERGE_SHIP_PR=1`.
- **#2182** / **#2552** then established NEVER #16 ("never commit larch run logs after the PR merges") and explicitly removed the `LARCH_LOG_COMMIT_POSTMERGE_SHIP_PR=1` bypass (#2552 notes PR #2530 reintroduced it). That ban deleted #2524's mechanism.
- The subsequent sh-to-py ship migration (`python/ship.py`) did not re-implement the alternative the NEVER #16 contract itself describes (write speculative `OUTCOME=merged` into `final-summary.md` before the squash-merge so it rides into the merged tree).
- Net: the post-merge fix was correctly banned, but no pre-merge replacement was added, so the original #2524 symptom regressed.

Prior related closed fixes in the same area: **#1955** / **#1937** (manifest never finalized after merged run), **#2568** (run-statistics missing, `steps_ran={}`), **#2364** (`final-summary.md` written before create-pr, captures `PR: N/A`), **#2253** (run-log/manifest contract completeness).

The code-path and artifact claims are observation-backed; "affects every merged run" is an inference from the consistent 5-run pattern plus the code analysis.

## Suggested fix(es)

Candidate directions (not yet validated; `/design` should choose and scope). Note that the obvious "just commit after merge" fix is **forbidden** by NEVER #16 — that is precisely what regressed #2524, so do not reintroduce it.

1. **Implement the design-blessed speculative pre-squash flush** (NEVER #16): for `--merge` runs, after CI passes and merge is imminent, write speculative `OUTCOME=merged` into `final-summary.md` (and stamp the manifest accordingly) and fold it into the final pre-merge log-flush commit so it rides into the squash-merge tree; roll back on merge failure. This lands accurate merged-outcome data without any post-merge commit.
2. **Avoid the `bailed` default for a pre-terminal snapshot.** When the committed snapshot is taken before a terminal outcome is known, record a neutral non-terminal token (e.g. `pr-created` once `PR_NUMBER` exists, or a dedicated `in-progress`/`pr-pending` value) instead of falling through to terminal `bailed`. Re-sequencing the committed flush to occur after `pr create` (so `PR_NUMBER` is populated) already upgrades `bailed` → `pr-created`.
3. **Reconcile `manifest.steps_ran.step8` with on-disk reality.** Ensure stamping in `_stamp_skipped_steps_for_terminal_report` runs after `final-summary.md` is written into `run_dir`, so a present `final-summary.md` is never stamped `step8=false`.
4. **Make downstream audit tooling tolerant** as a stopgap: treat a committed run-log dir whose PR merged (derivable from the merge commit / PR linkage) as `merged` regardless of the stale `final-summary` token.

Pick (1) or (2) as the primary fix; (3) is a likely-required companion; (4) is optional defense-in-depth.
