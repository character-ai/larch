**1. `already_merged` belongs outside `merge.py` parity (correctness)**  
`merge-pr.sh` documents eight `MERGE_RESULT` values and never emits `already_merged`:

```29:29:scripts/merge-pr.sh
#   MERGE_RESULT=merged|admin_merged|main_advanced|ci_not_ready|version_already_published|admin_failed|policy_denied|error
```

`already_merged` is set in `ship-pr.sh` when `ci-wait` returns `ACTION=already_merged`, or when `version_already_published` pairs with a merged PR (`scripts/ship-pr.sh` ~3504–3505, ~3551–3552). The plan’s nine-variant table and `test_merge_bash_parity.py` “identical classification” goal conflict with that split.

**2. `stage_accepted_oos` is scope creep without a bash port (architecture)**  
The gate script only validates disposition (`oos-disposition-gate.sh`); accepted OOS filing is owned by `/issue` in `skills/implement/SKILL.md`. `python/gh.py` has `issue_comment` / `issue_edit` but no `issue_create`, so the proposed staging API has no seam or parity target.

**3. Fork-aware push is not in `git-push.sh` (architecture / minimum change)**  
`git-push.sh` always runs plain `git push` with retries. Fork/base-remote selection lives in `ship-pr.sh` (`FORKED_TARGET` → `upstream` for CI, `rebase-push.sh` for rebase), not in the script the plan names as the port source.

**4. `upsert_token_report` lacks a live bash counterpart (architecture)**  
`write-final-report.sh` upserts only `larch:final-summary` via `tracking-issue-summary.sh`. `larch:token-report` appears in `tracking-issue-read.sh` for parsing, not as an active upsert in the implement path—adding `upsert_token_report` in Phase 5 risks unused code unless the plan names a real caller.
