## Approach

Apply a layered fix at the ship driver and stall classifier.

1. In `run_postmerge_phase`, distinguish the expected `preterminal-outcome` skip from a real post-merge flush failure.
2. When the PR has a terminal merge result and the skip reason is `config.REFRESH_SKIP_PRETERMINAL_OUTCOME`, keep the warning breadcrumb and finish with `Outcome.OK`.
3. Preserve the existing stalled path for other skip reasons, including `commit-failed`.
4. In `classify()`, short-circuit a recorded post-merge stall after a terminal merge to `operator-action` / `none` / `postmerge-flush-expected`.
5. Keep `_ship_refresh_preterminal_stall()` unchanged so the pre-push guideline-refresh path still requests `step8-shippr`.

## Edge cases

- A successful merge with `commit-failed` or another unexpected flush reason must remain stalled.
- A `postmerge` label alone is insufficient. The merged state must contain a terminal merge result.
- `already_merged` must receive the same protection as `merged` and `admin_merged`.
- A pre-push `preterminal-outcome` remains recoverable through `step8-shippr`.
- Stale textual evidence containing `preterminal-outcome` cannot override durable post-merge success state.

## Failure modes

- An overly broad ship-driver condition could hide a real run-log flush failure. Match the intentional skip reason exactly.
- An overly broad classifier guard could suppress recovery before merge completion. Require both `phase == "postmerge"` and a terminal merge result.
- Omitting the pattern allowlist update would emit `MATCHED_CLASSIFIER_PATTERN=redacted`, weakening diagnostics and regression assertions.
- Leaving `operator-action` to generic resume-hint inference could reintroduce reship routing for an unrecognized stall step.
