## Context

`shard_totals_per_run` (`python/harness_ci_timing.py:145-163`) and its helper `_split_shard_attempts` (`python/harness_ci_timing.py:122-142`) carry the retry-dedupe logic for CI shard timings. Two behaviors are load-bearing:

- **Retry dedupe**: a retried matrix job replays the shard from its first target. The opening target reappears non-consecutively, which starts a new attempt. Only `attempts[-1]` is summed, so retried targets are not double-counted.
- **Multi-bash summing**: multi-bash Makefile targets emit consecutive rows with the same label. A consecutive repeat is NOT a retry; every row in the attempt is summed.

Today only `test_shard_totals_per_run_basic` (`python/test_harness_ci_timing.py:131-139`) exercises this function, and it covers neither retries nor multi-bash. A branch-order swap or removal of latest-attempt selection in `_split_shard_attempts` would pass CI silently. This change adds regression coverage. Test-only; production code is unchanged.

## Approach

Add 3 test functions to the existing `shard_totals_per_run` section of `python/test_harness_ci_timing.py`, inserted after `test_shard_totals_per_run_basic` (ends line 139) and before the `median_shard_totals` section header (line 142). Use plain `TimingRow` construction only. No new helpers or fixtures. `TimingRow` and `shard_totals_per_run` are already imported (`python/test_harness_ci_timing.py:5-13`); no import changes.

Each test asserts exact float equality (matching the existing `== 15.0` style). All seconds are small integer-valued floats whose sums are exact, so `==` is safe.

**Expected totals, hand-traced:**

- **Retried shard** (`test-a`, `test-b`, then `test-a`, `test-b`): attempt 1 = `[a10, b5]`, attempt 2 = `[a12, b8]`. `attempts[-1]` sum = **20.0**. Regression sentinel (both attempts summed) = 35.0.
- **Multi-bash** (`test-multi` x3 consecutive, then `test-other`): single attempt `[m1, m2, m3, o4]`, sum = **10.0**. This also guards branch order: the repeated target is the *first* target, so a swapped check (first-target before prev-target) would wrongly split attempts and yield sentinel 7.0.
- **Retry + multi-bash** (`test-a` x2, `test-b`; then `test-a` x2, `test-b`): attempt 2 = `[a4, a5, b6]`, sum = **15.0**. Regression sentinel (all six rows) = 21.0.

```python
def test_shard_totals_per_run_retried_shard_uses_latest_attempt() -> None:
    # A retried matrix job replays the shard from its first target, so the
    # opening target reappears non-consecutively.  Only the latest attempt
    # counts; summing both attempts would double the total to 35.0.
    rows = [
        TimingRow(run_id=1, shard=1, target="test-a", seconds=10.0),
        TimingRow(run_id=1, shard=1, target="test-b", seconds=5.0),
        TimingRow(run_id=1, shard=1, target="test-a", seconds=12.0),
        TimingRow(run_id=1, shard=1, target="test-b", seconds=8.0),
    ]
    per_run = shard_totals_per_run(rows)
    assert per_run[1][1] == 20.0


def test_shard_totals_per_run_multi_bash_rows_all_summed() -> None:
    # Multi-bash targets emit consecutive rows with the same label; a
    # consecutive repeat of the first target is NOT a retry, so every row
    # in the single attempt is summed (1+2+3+4 == 10.0).
    rows = [
        TimingRow(run_id=1, shard=1, target="test-multi", seconds=1.0),
        TimingRow(run_id=1, shard=1, target="test-multi", seconds=2.0),
        TimingRow(run_id=1, shard=1, target="test-multi", seconds=3.0),
        TimingRow(run_id=1, shard=1, target="test-other", seconds=4.0),
    ]
    per_run = shard_totals_per_run(rows)
    assert per_run[1][1] == 10.0


def test_shard_totals_per_run_retried_shard_with_multi_bash() -> None:
    # Retry + multi-bash combined: each attempt repeats a multi-bash target.
    # Only the latest attempt's rows count (4+5+6 == 15.0), not all six.
    rows = [
        TimingRow(run_id=1, shard=1, target="test-a", seconds=1.0),
        TimingRow(run_id=1, shard=1, target="test-a", seconds=2.0),
        TimingRow(run_id=1, shard=1, target="test-b", seconds=3.0),
        TimingRow(run_id=1, shard=1, target="test-a", seconds=4.0),
        TimingRow(run_id=1, shard=1, target="test-a", seconds=5.0),
        TimingRow(run_id=1, shard=1, target="test-b", seconds=6.0),
    ]
    per_run = shard_totals_per_run(rows)
    assert per_run[1][1] == 15.0
```

## Edge cases

- **Branch-order subtlety**: the consecutive-repeat check must run before the first-target check. Test 2 puts the multi-bash target as the *first* target precisely to pin this ordering; a swap yields 7.0, not 10.0.
- **Retry detection**: only a non-consecutive reappearance of the first target starts a new attempt. Tests 1 and 3 cover this; test 2 confirms consecutive repeats do not.
- **Float equality**: all sums are exact in float (integer-valued operands), so `==` assertions are stable. No tolerance needed.

## Failure modes

- Removing latest-attempt selection (summing all attempts) → test 1 fails (20.0 vs 35.0), test 3 fails (15.0 vs 21.0).
- Swapping the branch order in `_split_shard_attempts` → test 2 fails (10.0 vs 7.0).
- These are genuine regression guards, not tautologies: each distinguishes correct output from a specific plausible bug.
