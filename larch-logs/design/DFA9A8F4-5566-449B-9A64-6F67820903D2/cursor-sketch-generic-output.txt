## Architectural Sketch: Unified OOS Voter-Prompt Rendering

### (1) Core Architecture: Shared Helper and Prompt Composition

The solution introduces a new shared helper script `skills/shared/scripts/render-voter-prompt.sh` that encapsulates the complete voter-prompt body generation logic, eliminating the hand-written duplication currently split between `scripts/dispatch-plan-voters.sh::make_prompt_file()` and `scripts/dispatch-code-voters.sh::make_voter_prompt_file()`. This helper will be a pure stdout-emitting Bash script (strict-mode compliant: `set -euo pipefail`) that takes skill-specific deltas as flags and outputs the assembled prompt text to stdout. The two dispatcher scripts will call the helper once during initialization, capture its output, and write it to the appropriate temp file (e.g., `${DESIGN_TMPDIR}/voter-prompt.txt` for `/design`, `${REVIEW_TMPDIR}/voter-prompt.txt` for `/review`).

Flags passed to the helper will control the minimal variance across the two skills: `--ballot-id-grammar FINDING_ONLY|FINDING_AND_OOS` to select ballot ID example blocks (FINDING_N vs both FINDING_N and OOS_N); `--context-file-type plan|diff` to customize the "read from path" prose (ballot vs ballot+diff+plan context); `--panel-role` to inject the skill-specific role introduction ("senior engineer on a voting panel" vs "scrupulous senior code reviewer"). The helper will also accept `--include-all-findings-rule true|false` to control whether the general "do not vote NO solely because you dislike the proposed fix" rule appears (true for unified output; `/design` plan voters currently lack it). The unified prompt will carry three layers of instruction: the panel-role intro, the general fix-proposals-informational rule applied to all FINDING items, and an explicit, emphatic OOS-specific problem-vs-solution clause. The OOS clause wording will be canonicalized as: "For items prefixed with [OUT_OF_SCOPE]: vote based on whether the **problem described** is real and worth filing as a GitHub issue. Treat any suggested remedy in the item body as *informational only* — do not vote NO because you disagree with the proposed fix. The implementer of the future OOS issue chooses the actual remedy." This exact wording will be embedded verbatim in `skills/shared/voting-protocol.md` (with a comment marker pointing to the helper as the runtime authority) and inlined into the Step 3 MAV paragraph of `skills/design/SKILL.md` (line ~598) and the Step 5 MAV paragraph of `skills/implement/SKILL.md` (line ~1238), ensuring all three filing surfaces—plan-review voters, code-review voters, and main-agent fallback in both `/design` and `/implement`—emit identical guidance.

### (2) Implementation Scope: Files to Modify and Rationale

**Create new files:**
- `skills/shared/scripts/render-voter-prompt.sh` — the core helper, ~120 lines including header/usage/strict-mode, sourcing `lib-quiet.sh` and emitting structured kv pairs per the `emit` / `emit_kv` contract used by sibling scripts.
- `skills/shared/scripts/render-voter-prompt.md` — sibling documentation per the script-md-siblings rule, covering purpose, flags (--ballot-id-grammar, --context-file-type, --panel-role, --include-all-findings-rule), output contract, invocation examples, and a note that this is the single source of truth for voter-prompt text.
- `scripts/test-render-voter-prompt.sh` — dedicated harness for the helper, exercising both `FINDING_ONLY` and `FINDING_AND_OOS` modes, asserting the presence of the canonical OOS clause, and verifying the general all-findings rule appears when requested. ~80–100 lines following existing harness patterns.

**Refactor existing dispatchers:**
- `scripts/dispatch-plan-voters.sh` — replace the entire `make_prompt_file()` function body with a call to the new helper: `render-voter-prompt.sh --ballot-id-grammar FINDING_AND_OOS --context-file-type plan --panel-role "senior engineer on a voting panel deciding which proposed plan modifications should be accepted" --include-all-findings-rule true`. Remove the per-tool loop and store the single rendered prompt in a shared location. Update `make_plan_voter_retry_prompt_file()` similarly. No caller-facing behavior change; the final prompt content becomes identical to today's except for the addition of the all-findings rule and the expanded OOS clause.
- `scripts/dispatch-code-voters.sh` — replace `make_voter_prompt_file()` body with a helper call: `render-voter-prompt.sh --ballot-id-grammar FINDING_ONLY --context-file-type diff --panel-role "scrupulous senior code reviewer on a 3-judge voting panel deciding which proposed code-review findings should be accepted" --include-all-findings-rule true`. The `/review` voters already have the general fix-proposals rule; the helper will preserve it as-is and add the explicit OOS clause.

**Update test harnesses:**
- `scripts/test-dispatch-plan-voters.sh` — add an assertion that the composed prompt contains the canonical OOS clause text (e.g., `grep -Fq 'the problem described is real and worth filing' "$prompt_file"`) and verify both FINDING and OOS example blocks are present.
- `scripts/test-dispatch-code-voters.sh` — add similar assertion that the OOS clause and the all-findings rule both appear in the final prompt.

**Update documentation and SKILL.md:**
- `skills/shared/voting-protocol.md` (line ~93, the "For items prefixed with [OUT_OF_SCOPE]" section) — replace the existing OOS prose with the canonical clause verbatim, prefixed with a comment: `<!-- Canonical text generated by scripts/shared/scripts/render-voter-prompt.sh; changes must be synchronized there. -->`. This keeps the doc in sync without tight coupling.
- `skills/design/SKILL.md` (Step 3 main-agent-vote-required prose, line ~598) — inject the canonical OOS clause inline, with surrounding prose clarifying that the main agent uses the same rubric as the voting panel for OOS items.
- `skills/implement/SKILL.md` (Step 5 main-agent-vote-required prose, line ~1238) — similarly inject the canonical OOS clause inline, with the same framing.

### (3) Tradeoffs and Risks

The primary tradeoff is **coupling vs. drift prevention**. Centralizing voter-prompt generation in a single helper script eliminates future hand-written duplication and the silent drift that has already occurred (`/design` lacks the fix-proposals rule, OOS clause wording varies). The cost is that any bug in the helper affects both dispatchers simultaneously, and skill-specific prose must be carefully parameterized (via flags) rather than freely varied. This is acceptable because the voter prompts are already constrained by the voting protocol; parameterization captures the intentional deltas, and ad-hoc prose divergence is the defect being fixed. **Risk of altered voter behavior:** changing the panel-role intro or the fix-proposals rule could shift the panel's voting patterns if the new wording is semantically different from the old. The design minimizes this by (a) preserving `/review`'s existing prose exactly, (b) applying the same general rule to `/design` plan voters (they should already be voting this way; the rule is a guardrail, not a behavior change), and (c) making the OOS clause explicit and emphatic rather than vague (reinforcement, not reframing). **Test fixture compatibility:** existing harnesses have captured prompts or snapshots; updating the dispatchers will invalidate those snapshots. The new dedicated harness for the helper uses synthetic inputs (no file dependencies), so it is resilient. The dispatcher harnesses will need new assertions (canonical-clause-presence checks) rather than exact-match snapshots; this is more maintainable anyway. **Byte-preservation vs. normalization:** the helper will use the same `printf` idiom as today's dispatchers to keep formatting and whitespace consistent where possible, but prose formatting may normalize slightly (e.g., line breaks when the helper separates logical sections). This is acceptable because voters are instructed to ignore narrative text anyway; what matters is the structural presence of the rules, not the exact spacing.
