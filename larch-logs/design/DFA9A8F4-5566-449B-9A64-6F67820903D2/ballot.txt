### FINDING_1: Drift guard only covers 2 of 4 canonical OOS clause copies

- **Concern**: The plan declares 4 byte-synced canonical OOS clause copies (`render-voter-prompt.sh` output, `skills/shared/voting-protocol.md`, `skills/design/SKILL.md` Step 3 MAV at ~line 598, `skills/implement/SKILL.md` Step 5 MAV at ~line 1238). The proposed drift guard (`scripts/test-render-voter-prompt.sh::case_canonical_text_drift_guard`) only greps the helper output and `voting-protocol.md` — both SKILL.md MAV copies are unguarded by CI. An edit to either SKILL.md copy in isolation passes all planned CI targets while silently diverging from the runtime prompt.
- **Proposed resolution**: Extend `case_canonical_text_drift_guard` to grep the exact canonical clause string in **four** places: rendered helper output, `skills/shared/voting-protocol.md`, `skills/design/SKILL.md`, and `skills/implement/SKILL.md`. Update `render-voter-prompt.md` and the `voting-protocol.md` HTML comment to state CI explicitly guards all 4 copies.
- **Reviewers**: 13 (Codex-Arch, Codex-Innovation, Codex-Edge, Codex-Pragmatic, Codex-Requirements, Codex-dyn-sync-invariant, Cursor-Arch, Cursor-Edge, Cursor-Innovation, Cursor-Pragmatic, Cursor-Requirements, Cursor-dyn-sync-invariant; aggregator counted ~13)
- **Severity**: important

### FINDING_6: Helper stdout payload conflicts with lib-quiet conventions

- **Concern**: The plan specifies that `render-voter-prompt.sh` sources `scripts/lib-quiet.sh` (matching sibling-script conventions). But `larch_quiet_init` redirects raw `printf` output to the quiet-log channel — so if the helper follows the standard pattern, the dispatcher captures empty prompt files via `> "$prompt_file"`, leaving voters with no instructions.
- **Proposed resolution**: Document explicitly in `render-voter-prompt.sh` that the helper either (a) does NOT call `larch_quiet_init` because its stdout IS the payload, OR (b) saves/restores fd1 around the prompt emission, OR (c) uses `emit` after init. Add a harness assertion under quiet-active context that rendered prompts are non-empty.
- **Reviewers**: 2 (Codex-Edge, Codex-Innovation)
- **Severity**: important

### FINDING_7: New .sh file executable mode unspecified while callers execute it directly

- **Concern**: The plan's dispatcher wrappers invoke the helper as `"$PLUGIN_ROOT/skills/shared/scripts/render-voter-prompt.sh"` — a direct executable call. If the new file lands with non-executable mode (which it would under default `git add` of a freshly-Written file without `chmod +x`), both dispatchers fail at runtime with permission-denied before the waterfall.
- **Proposed resolution**: Either (a) explicitly note in the plan that `render-voter-prompt.sh` and `test-render-voter-prompt.sh` must be `chmod +x`'d (and add an `-x` assertion in the harness), OR (b) invoke via `bash "$PLUGIN_ROOT/.../render-voter-prompt.sh"` from both dispatchers (no executable bit required).
- **Reviewers**: 2 (Codex-Arch, Codex-Requirements)
- **Severity**: important

### FINDING_8: OOS clause parenthetical "(or OOS_N: items in plan review)" leaks irrelevant grammar to /review voters

- **Concern**: The plan's canonical OOS clause contains `(or OOS_N: items in plan review)`. `--id-grammar finding-only` (used by /review) suppresses the OOS_N example block but NOT the clause text containing the OOS_N parenthetical. A /review voter handling a `FINDING_7 [OUT_OF_SCOPE]` ballot item could be nudged into emitting `OOS_7: YES`, which `vote_for_id` will NOT match for FINDING_7 and counts as JUDGE_ERROR. The two dynamic dyn-grammar-clause-scope reviewers both flagged this.
- **Proposed resolution**: Make the OOS clause text **grammar-conditional**. For `--id-grammar finding-only`, emit only `For items prefixed with [OUT_OF_SCOPE]: ...`. For `--id-grammar finding-oos`, emit `For OOS_N: items in plan review (or items prefixed with [OUT_OF_SCOPE] in code review): ...`. Add a finding-only harness assertion that no `OOS_N` substring appears in the rendered prompt. Update the canonical text in `voting-protocol.md` and the two SKILL.md MAV paragraphs to reflect a single doc-style wording (which need not match the runtime grammar-specific helper output verbatim — the drift guard then asserts each consumer's expected text).
- **Reviewers**: 2 (Codex-dyn-grammar-clause-scope, Cursor-dyn-grammar-clause-scope)
- **Severity**: important

### FINDING_13: Free-form --panel-role is a prompt-injection surface

- **Concern**: `--panel-role STRING` is free-form. A future caller could pass role text with newlines or contradictory instructions and still get a syntactically valid voter prompt, bypassing intended prompt shapes. While the panel-role is currently hardcoded in the two dispatchers (not user-controllable), the helper's API exposes a free-form sink that could be exploited if a future caller wires it to untrusted input.
- **Proposed resolution**: Replace `--panel-role STRING` with a fixed enum `--prompt-kind design-plan|code-review` (the helper internalizes both panel-role strings). Alternatively, validate the input: reject control characters and newlines; reject non-ASCII; cap length.
- **Reviewers**: 1 (Cursor-Innovation)
- **Severity**: latent
