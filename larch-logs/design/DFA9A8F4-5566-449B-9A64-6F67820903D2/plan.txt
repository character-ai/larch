Add an explicit, emphatic OOS problem-vs-solution clause. Backport the canonical OOS clause text to `skills/shared/voting-protocol.md` and inline it into the `main-agent-vote-required` (MAV) prose in `skills/design/SKILL.md`, `skills/implement/SKILL.md`, and the /design Voter 1 instruction in `skills/design/references/plan-review.md`. Add a documentation note in `skills/review/SKILL.md` explaining /review's MAV adjudication delegation.

1. **`skills/shared/scripts/render-voter-prompt.sh`** (~170 LOC) — the canonical voter-prompt renderer. Bash 3.2-compatible, `set -euo pipefail`. **Does NOT call `larch_quiet_init`** (per FINDING_6 resolution): the helper's stdout IS the payload, so lib-quiet's stdout redirection would silently empty the rendered prompt. The script body therefore omits the standard `source lib-quiet.sh; larch_quiet_init` opener and writes its payload directly via `printf`. A leading comment block documents this divergence and points at the harness case that pins it. **Must land with executable mode** (`chmod +x`) per FINDING_7 resolution.

   Required flags:
   - `--ballot-file PATH` — substituted into the "Read the ballot from this path: …" line.
   - `--panel-role STRING` — the skill-specific panel-role intro tagline.
   - `--id-grammar finding-oos|finding-only` — controls (a) whether the `OOS_N` example block is emitted alongside `FINDING_N`, AND (b) the wording of the OOS-specific clause (grammar-conditional, per FINDING_8 resolution).
   - `--verification-context plan|diff-plan` — controls the verification-context sentence emitted in the "Read the ballot" block (per FINDING_2 resolution, the `plan` branch preserves the existing "may silently inspect the plan or referenced repo files for verification" allowance).

   Output (stdout) structure, byte-preserved from current dispatcher prose where possible:

   Common body (always emitted):
   ```
   You are a {PANEL_ROLE}.
   Vote EXONERATE rather than YES when the concern is legitimate but the proposed change introduces more complexity than it warrants.
   Do NOT vote NO solely because you dislike or distrust the proposed fix — fix proposals are informational; the coder decides the exact change. Vote NO only when the stated problem is not real or not worth raising.
   ```

   Then the **grammar-conditional OOS clause** (per FINDING_8):

   - For `--id-grammar finding-only` (`/review` code voters; ballot has only `FINDING_N:` with `[OUT_OF_SCOPE]` prefix on OOS rows):
     ```
     For items prefixed with `[OUT_OF_SCOPE]`: vote based on whether the **problem described** is real, concrete, and worth filing as a GitHub issue. Treat any suggested remedy in the item body as *informational only* — do not vote NO because you disagree with the proposed fix. The future implementer of the OOS issue chooses the actual remedy.
     ```
   - For `--id-grammar finding-oos` (`/design` plan voters; ballot has both `FINDING_N:` and `OOS_N:` headings):
     ```
     For `OOS_N:` items in plan review (or items prefixed with `[OUT_OF_SCOPE]` in code review): vote based on whether the **problem described** is real, concrete, and worth filing as a GitHub issue. Treat any suggested remedy in the item body as *informational only* — do not vote NO because you disagree with the proposed fix. The future implementer of the OOS issue chooses the actual remedy.
     ```

   Then:
   ```
   Do NOT modify files. Do NOT commit. Do NOT push.

   Read the ballot from this path: {BALLOT_FILE}
   ```

   Then **verification-context branch** (per FINDING_2):
   - For `--verification-context plan` (`/design` plan voters):
     ```
     **Verify silently** — do not produce narrative output, reasoning explanations, or status updates before, between, or after the vote lines. You may read the ballot file and silently inspect the plan or referenced repo files for verification, but do not invoke planning/status tools.
     ```
   - For `--verification-context diff-plan` (`/review` code voters):
     ```
     Use the ballot path and any provided diff/plan context files to verify the ballot claims before voting.
     **Verify silently** — do not produce narrative output, reasoning explanations, or status updates before, between, or after the vote lines. You may read the ballot file and any provided diff/plan context files for verification, but do not invoke planning/status tools or any other tools beyond those file reads.
     ```

   Then the vote-line schema:
   ```
   For every ballot item, output exactly one line using the same ID from the ballot heading:
     FINDING_N: YES
     FINDING_N: NO -- one-line reason
     FINDING_N: EXONERATE -- one-line reason
   ```

   And for `--id-grammar finding-oos` only, append the OOS_N example block:
   ```
     OOS_N: YES
     OOS_N: NO -- one-line reason
     OOS_N: EXONERATE -- one-line reason
   ```

   Then:
   ```
   You must vote on every item. Do NOT skip any.
   **Output ONLY vote lines.** Lines that do not start with the exact ballot ID from the ballot heading followed by YES, NO, or EXONERATE are silently ignored.
   ```

   Exit codes: `0` on success; `2` on argument error (missing/invalid flag); flags validated against fixed enums via `case` statements.

## Approach

The unification is **mechanical refactoring** with explicit guards against the regressions surfaced by plan review:

1. The helper is **stdout-emitting and does NOT call `larch_quiet_init`** (FINDING_6) — its stdout IS the payload; lib-quiet's stdout redirection would silently empty the rendered prompt. The leading comment in the helper documents this divergence and points at the harness case.
2. The helper **must land with executable mode** (FINDING_7); `case_executable_bit` in the harness asserts `[ -x ... ]` so a future patch dropping the mode bit fails CI immediately.
3. The OOS clause is **grammar-conditional** (FINDING_8): finding-only emits the `[OUT_OF_SCOPE]` variant (no `OOS_N` substring anywhere); finding-oos emits the `OOS_N: items in plan review` variant. A finding-only harness assertion (`grep -v 'OOS_N'`) guards against future regressions.
4. The verification-context plan branch **preserves the existing /design plan/repo inspection allowance** (FINDING_2). `case_finding_oos` in the new harness asserts the wording; `scripts/test-prompt-template-invariants.sh:134-137` continues to pass unchanged.
5. The test harness `PLUGIN_ROOT_STUB` is **augmented to copy the new helper + lib-quiet.sh** (FINDING_3) so the dispatchers can resolve the helper at runtime.
6. The /design Voter 1 prompt (in plan-review.md) gains the canonical OOS clauses (FINDING_4); the drift-guard greps it.
7. /review's MAV adjudication is documented as delegated to /implement Step 5 (FINDING_5).
8. Sibling .md docs for all 4 modified scripts are updated (FINDING_9).
9. agent-lint.toml + docs/linting.md updated for the new harness (FINDING_10, FINDING_11).
10. The HTML drift comment lives in **Markdown prose adjacent to** the fenced Voter Prompt Template in voting-protocol.md, not inside it (FINDING_12). The comment is mechanically followed by the canonical OOS clause text.

The canonical OOS clause text lives in **four doc/SKILL.md copies + two helper grammar variants = six logical locations**. The drift-guard case (`case_canonical_text_drift_guard`) mechanically asserts the **finding-only variant** (the lowest-common-denominator wording) is present byte-for-byte in the four doc/SKILL.md locations:
- `skills/shared/voting-protocol.md`
- `skills/design/SKILL.md`
- `skills/implement/SKILL.md`
- `skills/design/references/plan-review.md`

The two helper grammar variants share the same canonical core (the `vote based on whether the problem described is real...` body); they differ only in the leading prefix (`For items prefixed with [OUT_OF_SCOPE]:` vs `For OOS_N: items in plan review (or items prefixed with [OUT_OF_SCOPE] in code review):`). The drift guard's hard-coded canonical string matches the shared body, not the prefix, so both grammar variants satisfy the same drift assertion.

The /design Voter 1 prompt embeds the **finding-oos variant** because Voter 1 votes on `OOS_N:` items in /design plan review; this matches the helper's finding-oos output that Voters 2/3 receive. The drift guard greps the shared body, so the byte-match is preserved.

Existing harnesses (`scripts/test-prompt-template-invariants.sh`, `scripts/test-dispatch-code-voters-retry-*.sh`) remain unchanged. Their continued green status acts as a regression guard.

## Edge cases

- **`--ballot-file` argument**: validated as a readable path string; embedded in the prompt via `printf '%s'`.
- **`--panel-role` argument**: free-form string; validated for non-empty but no other constraint (the FINDING_13 prompt-injection concern was EXONERATEd by the voting panel — callers are hardcoded).
- **Empty enum value for `--id-grammar` / `--verification-context`**: `case` validation rejects with exit 2.
- **Bash 3.2 portability**: no associative arrays, no `mapfile`, no `${var,,}`; `make lint-bash32` runs in CI.
- **Helper invoked with no flags**: prints usage to stderr (without using `larch_err` from `lib-quiet.sh` since we do not source it; use a plain `printf >&2`) and exits 2.

## Failure modes

The 3 most likely architectural / systemic failure paths:

1. **Drift between the canonical OOS clause copies** (helper output × 2 grammar variants / `voting-protocol.md` / `/design` SKILL.md MAV / `/implement` SKILL.md MAV / Voter 1 in plan-review.md). Earliest warning: `scripts/test-render-voter-prompt.sh::case_canonical_text_drift_guard` fails in CI. Mitigation: the drift-guard hard-codes the shared canonical-body string and greps **all four** doc/SKILL.md locations. `render-voter-prompt.md` documents the edit-in-sync rules and lists the five logical copy locations.

2. **Retry-prompt rendering regression** — `make_plan_voter_retry_prompt_file()` and `make_voter_retry_prompt_file()` prepend a parse-rate-prefix to the rendered prompt; the plan explicitly leaves them UNCHANGED. Earliest warning: existing `scripts/test-dispatch-code-voters-retry-*.sh` harnesses fail on regression.

3. **Voter-behavior shift from prompt-text normalization** — if the helper output normalizes whitespace or word choices materially, voter panels might vote differently. Mitigation: byte-preserve existing prose where possible; intentional content changes (general rule for /design, grammar-conditional OOS clause for both) are additions, not rewrites. The PLUGIN_ROOT_STUB-augmented dispatcher harnesses assert composed-prompt presence of canonical text rather than exact-match snapshots, so trivial whitespace tweaks don't cascade into harness churn.
