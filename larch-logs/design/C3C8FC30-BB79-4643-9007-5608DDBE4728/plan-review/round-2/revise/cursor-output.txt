Reviewing the codebase to align the revised plan with existing Step 5b routing and OOS filing patterns.
## Plan

## Approach

Add a shared high-risk OOS priority helper, then wire it into implement Step 9a.1 filing and design Step 5b annotate labeling.

- Treat `focus-area: correctness` and `focus-area: regression` (and equivalent `Focus area` / `focus area` forms) as high-risk public OOS signals.
- Reuse the existing label name `oos-correctness` for both correctness- and regression-tagged filed issues (label name unchanged; scope broadened).
- Auto-create the label with `gh label create oos-correctness --force` before applying it.
- Apply the label only to filed issue(s) whose accepted or post-cap combined OOS item carries a high-risk focus-area signal.
- Mirror `file_oos._FOCUS_AREA_LINE_RE` / `oos._FOCUS_AREA_FIELD_RE` line normalization so indented rollup bodies (4-space embedded source blocks under cap) are detected.
- OR priority across normalized-title duplicates before filing so a later duplicate cannot drop a retained block's high-risk flag.
- Add a design label-only retry path when filing succeeded but labeling failed, without re-invoking `/larch:issue`.
- Wire label-only retry through Step 5b lifecycle routing (`design_lifecycle.py`) so prepare status `label-only-retry` reaches annotate without `unknown-oos-status` repair stops.
- Keep security routing unchanged.
- Do not change inline review acceptance, OOS-vs-accept routing, SLA reporting, `/deps`, or `/combine-issues`.
- Do not label `risk-integration` or private security-routed OOS.

## Edge cases

- **Duplicate filing result**: apply `oos-correctness` to the duplicate target issue too.
- **Normalized-title dedup**: OR high-risk priority from skipped same-title duplicates into the retained block via `dataclasses.replace` before combine/cap.
- **Cap or rollup**: label the filed rollup issue when any embedded source body was high-risk or indented focus-area lines match inside the aggregate block.
- **Missing label**: auto-create it before filing or before post-file edit.
- **Missing repo in implement path**: use the same repo resolution already available in Step 9a.1. If unavailable, fail the priority label operation rather than silently filing an unmarked high-risk OOS issue.
- **Design retry after label failure**: preserve `oos-issues-created.md` and `.oos-priority-label-pending`; a subsequent `/design` run uses label-only retry to finish labeling without re-filing.
- **Design retry after label success**: `prepare` keeps `skip-sentinel` behavior when pending marker is absent.
- **Label-only annotate**: empty `oos-issue.stdout.txt` is expected; lifecycle must not treat it as sequencing error.
- **Mixed-batch label failure**: non-priority filed issues survive; only failing priority creates are eligible for cleanup.
- **Security OOS**: keep excluded from public filing. Do not label private security sidecar items.
- **risk-integration OOS**: out of scope for this MVP; no priority label.

## Failure modes

- **`gh label create --force` fails**: fail only priority-tagged OOS in the batch; record the command output; do not roll back unrelated non-priority filings.
- **`gh issue edit --add-label` fails**: fail after recording filed URLs for the affected priority item(s). On design, write pending marker for label-only retry. On implement, clean up only priority-tagged creates that lack verified labels; leave successful non-priority issues and duplicate targets intact.
- **Step 5b routing mismatch**: if `label-only-retry` is not mapped to routable `NEXT_ACTION`, prepare stops for repair; add lifecycle tests to prevent regression.
- **Analyze issue dump lacks labels**: render an empty high-risk section rather than guessing from issue bodies.
- **Analyze issue dump lacks `createdAt`**: sort those rows last and print `unknown` for date or age.
