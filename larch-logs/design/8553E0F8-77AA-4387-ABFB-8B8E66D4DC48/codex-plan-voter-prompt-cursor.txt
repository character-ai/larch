# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.

## Summary

When `/design` Step 3 (`design-step3-review.sh`) runs via `run_in_background: true`, Claude Code fires a premature `&lt;task-notification&gt;` ("completed exit code 0") roughly 319 seconds into a 14-minute review while the script is still blocked on `wait $_loop_pid`. At that moment the task output file is empty (nothing is written to the wrapper's stdout until `normalize-status` runs at the very end). The hook (`hook-bg-poll-guard.sh`) simultaneously blocks every tool call because the `.bg-wait-active` marker is legitimately live. Crucially, the hook also blocks reads of the task output file via `path_is_task_output + bash_probe_target_dir_plausible`, so the orchestrator cannot verify whether the notification is spurious (empty output rule: "end the turn without probing"). The result is a locked turn loop — 28 denied probes over 518 seconds — until the task truly completes, the EXIT trap removes the marker, and a user message starts a fresh turn.

## Original report

Premature `run_in_background` task notification deadlocks `/design` Step 3 review for ~8 min: Claude Code fires "completed" notification when background task stdout goes silent (before actual exit), hook blocks all tool calls including task-output reads, orchestrator cannot confirm empty-output spurious notification rule, accumulates 28 denied probes with no escape until task truly exits and EXIT trap clears the marker.

One of the following should hold:

## Root cause analysis

**Two compounding factors cause the deadlock:**

**Factor 1 — Premature notification (Claude Code side):**
`run_in_background: true` fires the "completed" task notification after a period of stdout inactivity, while the bash wrapper (`design-step3-review.sh`) is still blocked on `wait $_loop_pid`. The script produces no stdout output between marker creation (line 299) and `wait` (line 617) in the normal path. After ~5 minutes of silence, Claude Code's background-task tracking apparently interprets the quiet stdout as completion and fires the notification. This is a different class of spurious notification from #5240 (which was bash `set -m` job-control emitting sub-job exit events); there is no `set -m` here.

**Factor 2 — Hook blocks task output reads (larch side):**
After a `&lt;task-notification&gt;` fires, AGENTS.md instructs the orchestrator: "when task output is empty, end the turn without probing (spurious notification, #5240)." To follow this rule the orchestrator must read the task output file. However `hook-bg-poll-guard.sh` denies `Read` on `tasks/*.output` when (a) a live `.bg-wait-active` marker is present AND (b) `bash_probe_target_dir_plausible` correlates the marker's clone tag to the cwd (which it does whenever the design session matches the repo name). This was partially addressed by #5925 (added the plausibility gate to prevent foreign-clone false positives), but it still denies same-clone reads. A task output file is a write-once completion artifact, not a polling artifact; blocking its read prevents the only mechanism by which the orchestrator can distinguish spurious from genuine notifications.

**The resulting deadlock is self-reinforcing:** notification arrives → orchestrator tries to probe/read → hook denies → orchestrator ends turn → notification re-fires → repeat. The only exits are (a) the task truly completes and the EXIT trap removes the marker, or (b) the timeout in `marker_is_live` exceeds `TIMEOUT_S + 60 = 21660 s`, which would take 6 hours.

**Note:** The #6268 fix (`_step3_review_guarantee_post_loop_exit` removing `.bg-wait-active` at line 377) is present in 52.4.17 and functioned correctly — the marker was removed at true completion (15:14:47). This bug is not a regression of #6268.

## Suggested fix(es)

**Fix A (larch, minimal change):** In `hook-bg-poll-guard.sh`, remove the `path_is_task_output` block from the Read denial logic (lines 1140-1154). Task output files are write-once completion artifacts; the orchestrator reading them is not polling. The existing Bash-probe denial already blocks sentinel polling. Risk: if Claude Code writes task output incrementally (before process exit), an early read would return partial data; add a note in AGENTS.md that empty task output means spurious.

**Fix B (larch, documentation):** Update AGENTS.md and `design-background-wait.md` to state explicitly that task output file reads are denied during a live wait and that the empty-output rule must be applied based on sentinel absence alone, not by reading the file. Update the hook deny message to include whether the read target is a task output file, to aid diagnostics.

**Fix C (workaround, larch):** In `design-step3-review.sh`, write a keepalive heartbeat to stdout at the start of the Python launch (e.g., `printf 'REVIEW_RUNNING=1\n'`). This prevents Claude Code's inactivity timeout from firing a premature notification for the 14-minute silent window.

**Fix D (upstream):** File a report with the Claude Code team (Anthropic) about the `run_in_background` notification firing prematurely based on stdout inactivity rather than actual process exit. The "completed" notification should only fire when the tracked process (the bash PID) has actually exited.

Fix A or Fix C would address the larch-visible symptom. Fix D would address the root trigger in Claude Code. Fix B is needed regardless to clarify the AGENTS.md contract.
