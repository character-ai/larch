## Approach

The change is structurally simple: one new shared helper (`upsert-diagrams-comment.sh`), three call-site additions/refactors (/design Step 5c.5; /implement step-7a.sh; ship-pr.sh deletions), one marker-shape change in two reader/writer call sites plus docs. The dominant complexity sits in (a) the merge-and-preserve logic inside the new helper and (b) the doc-prose sweep across all files that currently mention the per-run diagrams marker.

The helper is the single source of truth for parsing and composing the comment body. /design calls it with `--architecture-file`; /implement calls it with `--code-flow-file`; either side can re-run idempotently. The helper internally fetches the existing comment, parses the existing top-level H2 sections with an awk state-machine that tracks mermaid-fence nesting (so a fenced literal `## Architecture Diagram` line inside a diagram body does not confuse the splitter), and composes the new body section by section. Sections that have neither a new file nor a preserved prior body are omitted from the composed output (no "not available" placeholders, which would defeat the joint-ownership contract).

The shared marker `&lt;!-- larch:diagrams v1 --&gt;` is the load-bearing rollout decision. Existing per-run `&lt;!-- larch:diagrams v1 runid=... --&gt;` comments stay on the issue as orphans (Round 1 decision 5). `tracking-issue-read.sh` keeps both marker shapes in its skip-filter so issue-context dumps continue to ignore the legacy orphans alongside the new stable ones.

Roll the rename and the new helper together as ONE merged change. A staggered rollout (helper first, then call-sites later) would temporarily produce comments with mismatched markers that neither side would update, defeating the shared-comment contract during the gap.

## Edge cases

- /design Step 3b skipped (non-architectural plan): `$DESIGN_TMPDIR/architecture-diagram.md` is absent. Step 5c.5 detects the absent file and skips the upsert entirely (no `Warnings`, just a `⏩` breadcrumb). The /implement run later still upserts Code Flow with no Architecture section in the body.
- /implement runs before /design: /implement's helper call finds no `&lt;!-- larch:diagrams v1 --&gt;` comment, posts a code-flow-only body. /design later runs and the helper finds /implement's comment; preserves the Code Flow section while writing the Architecture section. Both orderings produce the same final body.
- Concurrent /design + /implement upserts (mid-flight race): single-runner invariants reduce the window. Last-writer-wins. Because both sides always read-merge-patch before writing, the loser's content is preserved if its section heading is intact in the winning patch's input — which it is, because the winner read after the loser committed. The only failure mode is two writers reading the same baseline and both committing; one section is then lost. Accept the residual risk (matches today's `larch:plan` race semantics).
- Reruns of /design (Already-planned path): /design Step 5c.5 re-upserts; Architecture section is replaced, Code Flow preserved. Same for /implement reruns.
- Mermaid fence body containing H2 lines that look like section headings: the awk splitter tracks ```mermaid ... ``` fence depth and ignores `##` lines inside any open fence.
- Empty architecture-diagram.md (Step 3b candidate sanitizer-rejected and deleted before promotion): file absent; helper treats as section-not-provided.
- Comment fetch fails (gh API outage): helper exits with `UPSERT_STATUS=failed`; both call sites map to the existing best-effort `Warnings` log path. The plan-block-write succeeded and the rest of Step 5c proceeds.
- Duplicate stable-marker comments (operator error): helper fails with the same error semantics as `tracking-issue-summary.sh` (matches the `paste -sd,` joined ID list pattern).
- Legacy runid-bearing comment plus a new stable comment coexist on one issue: helper ignores the legacy comment entirely (only matches the exact stable marker). The legacy comment remains as a frozen artifact of an older run.

## Failure modes

1. **Section parser confuses mermaid-fence prose for a section heading**, dropping Architecture or Code Flow content silently on the next upsert. Earliest signal: a diffless-looking `gh api PATCH` that nevertheless loses content. Mitigation: the test harness must include at least one comment body where a mermaid fence contains the literal substring `## Code Flow Diagram` so the fence-state-machine is exercised end-to-end.
2. **Marker rollout drift** — one of /design, /implement, or `tracking-issue-read.sh` filter still references `&lt;!-- larch:diagrams v1 runid=` while the others use the stable form. Earliest signal: an /implement run after /design produces a SECOND `larch:diagrams` comment (different marker) instead of updating the first. Mitigation: ship all marker call-site edits in one commit and run `make lint` plus a fresh end-to-end probe before merging; final pre-merge grep `grep -rn 'larch:diagrams v1 runid' .` must return zero hits outside `tracking-issue-read.sh`'s historical filter and any docs that explicitly call out the legacy orphan handling.
3. **Redaction chain regression** — the shared helper must reproduce the existing `redact-tmpdir-paths.sh | redact-secrets.sh` pipeline that `tracking-issue-summary.sh` already runs internally. If the helper bypasses one of them, a path or secret could leak into the public comment. Mitigation: have the helper call `tracking-issue-summary.sh upsert-summary` as the final step (do NOT re-implement the upsert HTTP path) so redaction is centralized.
