# bug-treadmill [FEATURE] Complexity-baseline debt ratchet: repeat-bump gate + debt report

​#### Problem

28 fix commits extended `python/complexity-baseline.json` between 2026-07-08 and 2026-07-11. The pattern: the complexity lint fires on a fix, the fix baselines it away, and the same functions keep growing. Entries added in this window include `launch_codex_implement_main` and `launch_cursor_implement_main` at metrics in the 50s, sibling launcher entries at 77 and 82, and `_launch_slot` branch entries. The guardrail yields every time, so dispatch hot spots accrete a lane or guard branch per fix and never get refactored.

A hard ban on baseline extensions was considered and rejected: it would block urgent fixes at the worst moment. This design never blocks a first extension. It binds only on repeat accretion, which is where the evidence shows the pathology.

​#### Required design

1. Schema. Extend complexity-baseline entries to:

   ```json
   {
     "file": "larch/x.py",
     "code": "PLR0915",
     "qualified_symbol": "f",
     "metric": 55,
     "added_at": "2026-07-12",
     "source_issue": 1234,
     "reason": "<one sentence>",
     "history": [{"date": "2026-07-12", "metric": 55}],
     "operator_override": {"reason": "<one sentence>", "issue": 1240}
   }
   ```

   `source_issue`, `reason` metadata, and `operator_override` are optional keys; `operator_override` is absent by default. Grandfather existing entries with a one-shot migration: `added_at: "legacy"`, `history: []`.
2. Writer. The `--write-baseline` path in `larch/lint/lint_complexity_baseline.py`:
   - keeps `added_at` stable across rewrites,
   - appends `{date, metric}` to `history` on any metric increase,
   - requires a non-empty `reason` for any new entry or metric increase,
   - stamps dates as UTC dates,
   - never emits `operator_override`. Per invariant I-Gate-1 (a gate never disarms on data authored by the gated entity), the override enters only by manual operator edit.
3. Gate (repeat-bump rule, enforced by the same lint that validates the baseline):
   - First-ever entry, or first metric increase for a symbol: allowed. Urgent fixes always ship.
   - A second metric increase for the same `qualified_symbol` within 14 days (computed from `history` dates only, no git archaeology, so it works in shallow CI clones): FAIL. The failure message names the function, its bump history, and the three exits: simplify the function, split it, or add an operator override.
   - An `operator_override` with a non-empty reason and a positive linked `issue` silences the gate for that entry. The lint still lists all active overrides in its output so they stay visible.
4. Debt report. `python3 python/cli.py lint complexity-debt --report` prints: entry count, entries by age bucket, top 10 by metric, symbols with 2 or more bumps in 30 days, and all active overrides. Not wired into CI; it is the operator-facing burn-down view. Surfacing it in `/larch-size` or the analyze-bugs report is an explicit follow-up, not this issue.

​#### Alternatives considered

- Hard ban on baseline extensions in fix PRs: rejected. It blocks emergency fixes and invites bypass.
- Report-only, no gate: rejected. 28 extensions in 4 days show that visibility alone does not bind.
- The chosen design binds exactly where chronic accretion is proven (second bump within 14 days) and nowhere else.

​#### Tests

- Migration round-trip: legacy entries preserved and grandfathered.
- Writer: appends history on increase, keeps `added_at`, requires reason, refuses to emit `operator_override`.
- Gate: passes on first bump; fails on second bump inside the window; passes on second bump outside the window; override with reason and issue silences; override missing reason or issue still fails.
- Stable serialization ordering.

​#### Non-goals

- No changes to the C901 / PLR0912 / PLR0915 thresholds themselves.
- No policy for the other `python/*-baseline.json` files in this issue. The schema generalizes; a follow-up

## Proposed Design Outline

### Goals
- Implement the metadata-preserving `--write` mode with `--reason TEXT`, history appending on metric increase, and UTC date stamping in `lint_complexity_baseline.py`
- Add the repeat-bump gate in check mode (second increase within 14 days = fail, with failure message and three exits) plus active-override listing
- Add `lint_complexity_debt.py` with `--report`, register it in `cli.py`, extend tests, and update `docs/linting.md` + `Makefile`

### Non-goals
- No changes to complexity thresholds (C901, PLR0912, etc.) or `ruff.toml`
- `--report` not wired into CI or `/larch-size` (explicit follow-up in issue)
- No schema changes to other `python/*-baseline.json` files

### Approach sketch
- Rewrite `_run_write` to load existing baseline, merge live records (preserve metadata, append history on increase, stamp UTC date, require `--reason` on new entry or increase), write merged result
- Add gate check in `_run_check`: for each record whose history shows 2+ increases within 14 days and no `operator_override`, emit failure message with three exits; always list active overrides at end
- New `lint_complexity_debt.py`: load baseline, print five sections (entry count, age buckets, top-10 by metric, symbols with 2+ bumps in 30 days, active overrides)
- Register `("lint", "complexity-debt")` in `cli.py`; update `Makefile` comment on `regen-complexity-baseline` target and add `make lint-complexity-debt` check
