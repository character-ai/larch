# /design leaves orphan background processes after skill completes

/design leaves orphan background processes after skill completes

After a `/design` run finishes and the final-summary is emitted, Claude Code's status bar continues showing "N active shells" referencing the completed session's tmpdir. The processes belong to this session (confirmed by `--design-tmpdir` args), not to any other session. They stay alive until their `--timeout 1860` (31 min) expires or until the operator kills them manually.

## Observed processes left alive after task-notification

From a concrete run (session `claude-design-larch8-4s8d_c2c`, issue #3685, round-1 review completed, `LOOP_STATUS=complete` written):

```
plan-review-loop.sh        --round-num 2   (32 min elapsed)
run-step3-review.sh        --mode loop     (49 min elapsed)
dispatch-plan-voters.sh    --ballot-file … (26 min elapsed)
dispatch-with-waterfall.sh --slots-file …  (26 min elapsed)
collect-agent-results.sh   --timeout 1860  (22 min elapsed)
collect-agent-results.sh   --timeout 1860  (22 min elapsed, duplicate)
python/cli.py agent wait-reviewers --timeout 1860 … (22 min elapsed)
```

Additionally, a `run_in_background: true` Bash tool call that tried to expand a large variable (`$PLAN_CONTENT`, ~600 lines) inside a heredoc (`cat > file << COMPOSED_EOF`) got stuck; its three subshell copies also stayed alive until manually killed.

## Root cause

`design-step3-review.sh` (and its child `run-step3-review.sh --mode loop`) launch background processes with `&` inside bash functions and sub-scripts. When the loop determines it is "done" — writing `.step3-review-result.env` with `LOOP_STATUS=complete` — the top-level wrapper exits. This fires the Claude Code `<task-notification>`. But the children do not receive a signal: they were spawned in sub-shells or from sourced functions, so they are not in the same process group as the parent and `kill -TERM $$` (or implicit SIGHUP on parent exit) does not reach them.

Specific surviving subtrees observed:

1. **Voter collection tree** — `dispatch-plan-voters.sh` → `dispatch-with-waterfall.sh` → `collect-agent-results.sh` → `python/cli.py agent wait-reviewers`. These block waiting for `*.done` sentinel files that were already written. They time out at 1860 s.

2. **Round-2 check** — `plan-review-loop.sh --round-num 2` was apparently started by the loop for a continuation check. The loop wrote `LOOP_STATUS=complete` (stopping the logical flow) but did not kill the already-launched round-2 subprocess.

3. **Heredoc large-variable expansion** — a Bash tool call containing `cat > file << EOF\n${LARGE_VAR}\nEOF` hung. Claude Code spawned 3 subshell copies (the snapshot + eval pattern); the cat+heredoc combination apparently blocks when the variable expansion is very large. The `run_in_background: true` call never fired a task-notification until the subshells were killed externally (it fired only after `kill -TERM`).

## Impact

- "N active shells" stays non-zero in the status bar after `/design` completes, confusing operators.
- Each orphan holds open file descriptors to the session tmpdir, potentially blocking cleanup.
- At scale (many parallel `/design` runs), orphans accumulate until 1860 s timeout, consuming CPU and file descriptors.
- Operators who check "what is running" get misleading information (as happened in this session).

## Suggested fixes

**Fix 1 — Process-group kill on exit (primary fix)**

In `design-step3-review.sh` and `run-step3-review.sh`, set a process group on entry and kill it on exit:

```bash
# At the top of the script (after set -euo pipefail):
set -m   # enable job control / process groups

# Add an EXIT trap that kills the entire process group:
_PGID=$(ps -o pgid= -p $$ | tr -d ' ')
trap 'kill -- -"$_PGID" 2>/dev/null || true' EXIT
```

Or use `setsid bash script.sh` at the launch site so the script runs in its own session, then send `kill -TERM -<pgid>` before the wrapper exits.

**Fix 2 — Explicit child-PID tracking in plan-review-loop.sh**

`plan-review-loop.sh` could collect PIDs of every background subprocess it spawns (`dispatch_pid=$!`) and kill them in an EXIT trap:

```bash
_child_pids=()
start_some_subprocess & _child_pids+=($!)
trap 'kill "${_child_pids[@]}" 2>/dev/null || true' EXIT
```

**Fix 3 — Avoid large-variable heredoc in Bash tool calls**

The `cat > file << EOF\n${LARGE_VARIABLE}\nEOF` pattern with `run_in_background: true` is fragile when the variable is large. The SKILL.md (or BASH_AUTHORING.md) should note this anti-pattern and direct implementers to use the Write tool instead for composing files with large variable content. The `btvdcpdyr` shell was the `composed-plan.md` write — using `Write` would have been safer and avoided the stuck subshell entirely.

**Fix 4 — kill_session_background_processes at loop exit**

`finalize.py` already implements `kill_session_background_processes(runner, ctx)` which scans for processes referencing the tmpdir path. This could be called from within `run-step3-review.sh` (or its Python replacement) before the wrapper returns, using `python3 python/cli.py session kill-background-processes --tmpdir "$DESIGN_TMPDIR"`.

## Reproduction

Run `/design` on any issue, wait for the plan-review round to complete, observe `LOOP_STATUS=complete` in `.step3-review-result.env`, then check:

```bash
ps aux | grep "$(basename $DESIGN_TMPDIR)" | grep -v grep
```

Processes with elapsed time > 0 after the task-notification fired are orphans.
