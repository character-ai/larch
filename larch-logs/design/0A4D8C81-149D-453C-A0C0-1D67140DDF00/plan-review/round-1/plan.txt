## Implementation Plan — per-review-round timing in timing-report.json (#3488)

SIMPLE tier: smallest change that adds a per-round `rounds` sub-array to the
Step 5 (implement code review) and Step 3 (design plan review) `per_step`
entries in `timing-report.json`, with per-round `duration_seconds`,
`accepted`, and `rejected` for both skills, plus `oos` for design.

### Goal (binding scope, from Round 1)
- Per-round `duration_seconds` AND `accepted`/`rejected` counts are mandatory for both skills (hard-required).
- `/design` rounds additionally carry an `oos` count.
- JSON + run-log flush + tests only. No markdown `## Per-Step Durations` change; no `/report-tokens` or other analysis-tool change; no new flush site; no backfill.
- `rounds` is purely additive; no existing field renamed/removed.

### Architecture (key facts established by codebase research)
- `timing-report.json` is rendered from the session timing-ledger TSV by `scripts/timing-report.sh` (`refresh-run-logs.sh:78` runs `timing-report.sh --full --format json`, then `larch-log.sh --batch timing-report` commits it). So per-round data must live in the **ledger** to reach the committed batch. No new flush site is needed.
- Ledger rows are fixed at **13 tab-columns**; `timing-report.sh row_ok()` skips any row with `NF != 13` and dispatches by column 2 (`mark`/`vendor`/`workflow`). A new `round` row kind must be exactly 13 columns and is naturally ignored by the markdown path.
- The implement Step 5 round loop is `run_implement_loop` in `review-implement-step5-loop.sh` (sourced by `review-and-fix.sh`); it calls `_implement_round_body` once per round. `_implement_round_body` already computes `accepted_count`/`rejected_count` (from review-core `ACCEPTED_COUNT`/`REJECTED_COUNT`).
- The design Step 3 round loop is `while (( round_num <= ROUND_CAP ))` in `plan-review-loop.sh`; `_run_plan_review_round` is the round body. Per-round accepted/rejected counts come from `$DESIGN_TMPDIR/accepted-plan-findings.md` and `rejected-findings.md` (same greps as ~1456–1457). Per-round **accepted OOS** counts come from `voting-tally.md` Findings rows (`grep -cE '^\| OOS_[0-9]+ \|'` with `[[ -f ... ]]` guard) so security-accepted OOS that never land in `oos.md` are included; do **not** count `oos.md` (rejected-OOS prose) for `--oos`.
- Parent step marks: implement `Step 5 — code review` (`step-telemetry-mark.sh` before `run-step5-review.sh`; re-emitted when `--starting-round` > 1 — see below); design `design Step 3 — plan review`. JSON attachment requires **skill + recorded `round_step` label + interval**: `emit_round_array(skill, step, s, e)` keeps a row only when `round_skill == skill`, `round_step == step`, and `round_start ∈ [s,e)`. Prevents resumed Step 5 rounds or Step 7 intervals from stealing rows. Gate-C re-entry still yields distinct parent-mark intervals per pass.
- `design-publish.sh` calls `design-log-publish.sh` before `render-final-summary.sh`, which today renders `$DESIGN_TMPDIR/timing-report-final.json` post-publish; publish copies top-level tmpdir files, so Gate-C must render timing JSON **immediately before** `design-log-publish.sh` when `SESSION_ID` is set (`LARCH_TIMING_SKILL=design timing-report.sh --full --format json --output …/timing-report-final.json`; best-effort `|| true`). `render-final-summary.sh --post-publish-only` remains for chat/summary only.
- Backward compat verified: timing-report batch validation is `none`; `measure-realized-cost.sh` and `python/report_tokens_scan.py` read timing-report.json via `.get()` and tolerate the additive field.

## Approach
Place per-round timing+counts in the ledger as a new 13-column `round` row kind, emitted once per round by the two existing review loops at the points where counts are already available. `timing-report.sh` attaches by skill + recorded step label + interval; implement resumes re-mark Step 5 when `--starting-round` > 1. Counts: implement from `IRF_LAST_*`; design accepted/rejected from plan-review artifacts; design OOS from `voting-tally.md` Findings rows. Design durations end after revise/post-apply when those run. Gate-C renders `timing-report-final.json` before publish so committed design logs include round rows. Emission is strictly best-effort (`|| true`; ledger is already non-fatal) so a telemetry write never disturbs an in-flight review.

## Edge cases
- `end_s < start_s` (clock skew): clamp `duration_s` to 0 in `record-round` (mirrors vendor rows).
- No round rows for a step: `emit_round_array` prints nothing, so the per_step entry is byte-identical to today (backward compatible).
- Parent step mark absent: round rows match no interval and are silently omitted from JSON (they still exist in the ledger). The emitters use the canonical parent labels and interval matching to minimize this.
- Gate-C re-entry: distinct parent-mark intervals; pre-publish timing render picks up all ledger rows through Step 5c.
- Step label mismatch / wrong interval: triple-match drops orphan round rows rather than attaching to Step 7 or another skill interval.
- Resumed implement Step 5 (`--starting-round` > 1): without re-mark + `round_step`, round 2+ could fall into Step 7's interval — mitigated by `run-step5-review.sh` mark + `emit_round_array` step equality.
- Implement round rows never carry `oos`; the report omits the field for them.
- Design timing emit must not run before revise on paths that will revise (under-counts wall time); early emit only on skip-revise branches.
- Design `_emit_round_timing_row` must not grep bare artifact basenames or `oos.md` for accepted OOS; use `voting-tally.md` with `[[ -f ... ]]` guards.
- Markdown / `--summary` / `--terse` unaffected: `round` rows are not `mark`/`vendor`/`workflow`, so those code paths ignore them.

## Failure modes
1. **Round row attached to wrong `per_step`** (skill-only interval match) → Step 5 rounds appear under Step 7 or another interval. Signal: `rounds` on unexpected step. Mitigation: `round_step` column + `emit_round_array(skill, step, …)`; implement resume re-mark; fixture with Step 5 / Step 7 / Step 5.
2. **Count drift** (artifact heading format changes) → wrong accepted/rejected/oos. Signal: per-round counts disagree with `voting-tally.md` / `review-tally.env`. Mitigation: accepted/rejected greps + OOS from `| OOS_N |` tally rows; tests assert counts.
3. **Design duration under-count** → sum of `rounds[].duration_seconds` < parent Step 3 duration. Signal: rounds emitted before revise/post-apply. Mitigation: late `_round_end` on revise paths only.
4. **Stale timing JSON in published design logs** → committed `timing-report-final.json` missing late Step 4/5 marks and round rows. Signal: publish artifact predates final ledger. Mitigation: pre-publish render in `design-publish.sh`.
5. **Telemetry failure aborts the loop** → would break `/implement` or `/design` mid-review. Mitigation: `|| true` on every `record-round` and timing-report render; never gate loop control flow on telemetry.
