## Edge cases
- `end_s < start_s` (clock skew): clamp `duration_s` to 0 in `record-round` (mirrors vendor rows).
- No round rows for a step: `emit_round_array` prints nothing, so the per_step entry is byte-identical to today (backward compatible).
- Parent step mark absent: round rows match no interval and are silently omitted from JSON (they still exist in the ledger). The emitters use the canonical parent labels and interval matching to minimize this.
- Gate-C re-entry: distinct parent-mark intervals; pre-publish timing render picks up all ledger rows through Step 5c.
- Step label mismatch / wrong interval: triple-match drops orphan round rows rather than attaching to Step 7 or another skill interval.
- Resumed implement Step 5 (`--starting-round` > 1): without a timing-only re-mark + `round_step`, round 2+ could fall outside any Step 5 interval or into Step 7's interval — mitigated by `run-step5-review.sh` timing mark + `emit_round_array` step equality.
- Implement round rows never carry `oos`; the report omits the field for them.
- Design timing emit must not run before revise on paths that will revise (under-counts wall time); early emit only on skip-revise branches.
- Design OOS counting must not grep bare artifact basenames, must not count `oos.md`, and must not count every `OOS_N` row; parse `voting-tally.md` with `[[ -f ... ]]` guards and require Result = `accepted`.
- Main-agent-vote-required rounds must not append preliminary rows; append-only telemetry cannot correct stale `0/0/oos` rows later.
- Pre-publish design timing render must remove stale output or use a fresh temp before `design-log-publish.sh`; otherwise an old post-publish summary artifact could be committed after a failed render.
- Markdown / `--summary` / `--terse` unaffected: `round` rows are not `mark`/`vendor`/`workflow`, so those code paths ignore them.

## Failure modes
1. **Round row attached to wrong `per_step`** (skill-only interval match) → Step 5 rounds appear under Step 7 or another interval. Signal: `rounds` on unexpected step. Mitigation: `round_step` column + `emit_round_array(skill, step, …)`; implement resume re-mark; fixture with Step 5 / Step 7 / Step 5.
2. **Count drift** (artifact heading format changes or OOS result parsing wrong) → wrong accepted/rejected/oos. Signal: per-round counts disagree with `voting-tally.md` / `review-tally.env`. Mitigation: accepted/rejected greps + accepted-only OOS Result-column parsing; tests assert accepted, rejected, and exonerated OOS cases.
3. **Round duration under-count** → `rounds[].duration_seconds` misses checks/lint or revise/post-apply time. Signal: round duration much smaller than wall-clock review work. Mitigation: late `_round_end` immediately before each terminal/continue path after post-round work.
4. **Stale MAV counts** → main-agent-vote-required round records `0/0/oos` before synthetic adjudication. Signal: ledger row predates main-agent voter/re-tally artifacts. Mitigation: persist start, defer emission, append one row only after final re-tally.

<feature>
Add per-review-round timing to timing-report (implement + design), flush with run logs

## Summary

`timing-report.json` currently records the entire `/implement` Step 5 code review (and `/design` plan review) as a single opaque timing bucket — no per-round breakdown. This makes it impossible to tell whether a slow review was caused by one pathologically-slow round vs. five uniformly slow rounds, and impossible to detect per-round regression over time.

Surfaced during investigation of user-visible slowness in `/implement` reviews (June 2026). The analysis required manually correlating across runs because no per-round elapsed data existed.

## Current state

- `timing-report.json` `per_step` has one entry: `"step": "Step 5 — code review", "duration_seconds": 11014` — no sub-breakdown.
- No per-round timing exists in larch-log batches either (`code-review-tally`, `review-findings-full`, `timing-report` all lack round-level elapsed fields).
- Same gap exists for `/design` Step 3 plan-review rounds (the `plan-review-tally` batch has no per-round timing).

## Proposed changes

### 1. `review-and-fix.sh` — emit per-round timing marks

At the start and end of each `_implement_round_body` call (or equivalent), call `timing-ledger.sh mark "review round N start"` / `"review round N end"` (or integrate with the existing step-telemetry pattern) so wall-clock per round is recorded in the timing ledger.

### 2. `timing-report.sh` / timing-report batch

Aggregate per-round marks into a `rounds` sub-array in the `per_step` entry for Step 5 (implement) and Step 3 (design). Shape:

```json
{
  "step": "Step 5 — code review",
  "duration_seconds": 11014,
  "rounds": [
    {"round": 1, "duration_seconds": 2203, "accepted": 21, "rejected": 9},
    {"round": 2, "duration_seconds": 2198, "accepted": 17, "rejected": 9},
    ...
  ]
}
```

Accepted/rejected counts are already available from `review-tally.env` per round; the only missing piece is elapsed seconds.

### 3. Flush with run logs

`larch-log-flush.sh` / `refresh-run-logs.sh` already flush `timing-report` at Step 7a and on CI retries. The per-round data should be included in those flushes — no new flush site needed, only a richer report format.

### 4. `/design` plan-review parity

Apply the same per-round timing instrumentation to `plan-review-loop.sh` / `dispatch-plan-review-panel.sh` so `/design` runs also show per-round elapsed in the committed plan-review-tally batch.
