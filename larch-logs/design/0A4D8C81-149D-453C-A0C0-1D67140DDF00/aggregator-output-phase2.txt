### FINDING_1: `_emit_round_timing_row` uses bare filenames without DESIGN_TMPDIR guards
- **Reviewer(s)**: Cursor-Edge, Cursor-Innovation
- **Severity**: important
- **Concern**: The proposed `_emit_round_timing_row` helper greps bare `accepted-plan-findings.md`, `rejected-findings.md`, and `oos.md` instead of `"$DESIGN_TMPDIR/..."` paths. Under `set -euo pipefail`, `grep` runs in the caller’s cwd (not `DESIGN_TMPDIR`), so missing files can make `grep` exit 1 and abort the plan-review loop before any `record-round` `|| true` shim; even when the loop continues, counts may be zero or wrong and per-round ledger/JSON fields can be bogus or fail `is_uint` on empty values. Existing tally code at `plan-review-loop.sh` ~1347–1348 already uses `$DESIGN_TMPDIR`-qualified paths with `[[ -f ... ]]` guards.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Edge: Mirror existing tally paths: grep -cE on "$DESIGN_TMPDIR/accepted-plan-findings.md", "$DESIGN_TMPDIR/rejected-findings.md", and "$DESIGN_TMPDIR/oos.md" with [[ -f ... ]] guards and 2>/dev/null || true (same pattern as lines 1347-1348)
  - From Cursor-Innovation: Pin the helper to "$DESIGN_TMPDIR/accepted-plan-findings.md", "$DESIGN_TMPDIR/rejected-findings.md", and "$DESIGN_TMPDIR/oos.md" (same paths as existing ACCEPTED_COUNT grep at plan-review-loop.sh:1348)

### FINDING_2: Rejected-finding grep pattern mismatches tally output schema
- **Reviewer(s)**: Cursor-dyn-ledger-schema-match
- **Severity**: important
- **Concern**: `tally-plan-review.sh` writes in-scope rejected findings in `rejected-findings.md` as `### [Plan Review] FINDING_N` headers, not `### FINDING_N:`. If `_emit_round_timing_row` greps rejected rows with the same `^### FINDING_[0-9]+:` pattern used for accepted findings, the pattern never matches and per-round `rejected` stays 0 in ledger/JSON despite real rejections.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-dyn-ledger-schema-match: Grep ^### \[Plan Review\] FINDING_[0-9]+ on rejected-findings.md, or read rejected_count from tally output (tally-plan-review.sh:497-502) instead of mirroring the accepted heading pattern

### FINDING_3: `emit_json_child_steps` parent vs. child interval ambiguity
- **Reviewer(s)**: Cursor-dyn-emit-step-caller-coverage
- **Severity**: important
- **Concern**: In `scripts/timing-report.sh` (`emit_json_child_steps`, ~372–381), parent-window `start`/`end` parameters share names with loop-local child bounds `s`/`e`. An implementer may pass the parent implement-window `start,end` into downstream emission instead of each child mark’s interval from `skill_mark_ts` / `skill_interval_end`. Because `emit_round_array` matches only on `round_skill` and `round_start`, design `round` rows from an earlier child mark in the same parent slice can attach to a later `per_step` entry (e.g. a second `design Step 3 — plan review` after Gate-C re-entry, or another design sub-step under the same implement step).
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-dyn-emit-step-caller-coverage: State explicitly that the `emit_json_step(..., s, e)` call inside `emit_json_child_steps` must use the loop-local child `s` and capped `e` from `skill_mark_ts` / `skill_interval_end` (current lines 374-377), not the function’s parent-window `start`/`end` parameters; add a fixture with two same-label design marks and disjoint round rows to `scripts/test-timing-report.sh`
