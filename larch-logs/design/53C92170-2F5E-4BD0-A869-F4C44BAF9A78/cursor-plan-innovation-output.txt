### Findings

1. **[architecture]** `python/run_logs.py:851-879` — O1 re-architects flushes as publish-then-restore/clean with a repo-wide porcelain gate. That is heavier than needed for SIMPLE tier: the soak churn is timestamp-only refresh sidecars in the tmpdir tree. Classifying allowlisted deltas **before** `_publish_run_tree_to_repo` and skipping publish entirely avoids worktree mutation and matches the minimum-change goal better than mirroring `larch-log.sh` reset lines after the fact.

2. **[correctness / risk-integration]** `python/run_logs.py:875-877` — The plan’s volatile-only path adds restore/clean, but the existing no-commit branch (`git add` then cached `diff --quiet`) still returns success while leaving staged paths under `rel`. That staged-leak path remains reachable on non-volatile flushes and can still trip `rebase._force_push_branch`’s full-repo dirty check (`python/rebase.py:234-238`). Extend unstage/restore/clean (and the empty-porcelain check) to **all** no-commit returns, not only the new volatile-only classifier.

3. **[correctness]** `python/run_logs.py:851-879` — The plan requires repo-wide `git status --porcelain` to be empty after volatile-only restore/clean but does not specify failure behavior when it is not. Implementers may choose assert, bare traceback, or inconsistent `CommandResult` handling. Specify fail-closed semantics (non-zero commit result / `REFRESH_SKIP_COMMIT_FAILED` / `ShipError`) and test the failed-cleanup path.

4. **[architecture]** `python/config.py:190-198` — `REFRESH_SKIP_VOLATILE_ONLY` in `REFRESH_SKIP_MERGE_OK` conflicts with the proposed success contract (`_larch_log_commit` returns 0 → `flush_logs_pre` returns `skipped=False`). The constant appears unused unless skip-reason emission is added; drop it or wire it through `flush_logs_pre`, not both.
