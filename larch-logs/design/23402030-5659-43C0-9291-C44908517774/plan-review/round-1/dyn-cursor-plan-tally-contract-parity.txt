## Findings

### 1. Plan-review dual pass breaks single-owner policy (architecture)

`plan_review_tally.py` adjudicates in `_Tally._render` (`797-886`) but writes classification and ledger in a later pass (`437-553`, `757`). Each pass calls `voting.neutral_high_severity_rescue_to_oos` again with independently gathered votes. That contradicts the plan goal of computing `fileable_oos`, `neutral_rescued`, score kind/result, and OOS routing once per item. Tests such as `test_tally_plan_review_rescues_high_severity_neutral_findings_to_oos` assert classification `scope`/`voting_result` and ledger `outcome` stay aligned with OOS artifacts (`test_plan_review.py:2226-2232`). A refactor that only replaces the `_render` loop leaves two other policy owners.

### 2. Code-review pre-engine normalization missing from hook contract (correctness)

Before adjudication, code review sets `is_oos` from `OOS_` prefixes, `[OUT_OF_SCOPE|OOS]` heading tags, and `_scope_drift`, then may replace `result` with `voting.classify_oos_result` (`review_tally.py:916-921`). The plan lists scope-drift as an intentional family difference but does not require a family hook for heading-tag OOS detection or post-drift `classify_oos_result`. Shared engine logic keyed only on item id would regress ballots like `FINDING_3: [OUT_OF_SCOPE]` in `test_review_tally.py` classification fixtures.

### 3. [SCOPE-REDUCTION] Avoid canonical score-row unification (architecture)

The plan asks for “canonical score rows,” but the families already diverge in representation: code review accumulates `(reviewer, kind, result, weight)` and applies `bonus_by_reviewer` later (`review_tally.py:414-437`); plan review stores bonus inside 5-tuples (`plan_review_tally.py:70-104`). Unifying tuple shape is extra surface area without policy benefit. The engine should own adjudication outputs; families should keep their existing score projections.

### 4. Main-agent TSV override and duplicated scoring must survive extraction (correctness)

Plan review forces classification `voting_result` to `rejected` when `main_agent_voter` is set (`plan_review_tally.py:448`) while `_render` still scores through `_record_plan_review_score_rows`, which recomputes `neutral_rescued` (`80-84`). The plan’s edge case (“Main-agent fallback must not be scored as an external panel”) and the UPDATED section’s “remove duplicated … scoring” conflict unless the adapter preserves the TSV-only override and removes rescue recomputation from the score helper.

### 5. Security holdback needs per-family classifier inputs (risk-integration)

Security routing must stay fail-closed and sidecar-only. Today code review classifies security from the block file (`_security_block` → `voting.is_security_block`); plan review classifies from restored artifact text (`is_security_block_text`). Collapsing those inputs in the shared engine risks changing which bucket receives an item, with regression coverage in `test_tally_security_oos_holdback` and related tests.

### 6. Adapter-level byte-parity tests should cover the dual-pass hazard (risk-integration)

Fake family hooks in `test_tally_engine.py` can prove policy math in isolation but will not catch plan-review’s second pass re-deriving different classification or ledger rows from the same ballot. The plan should require real adapter fixtures against existing suites (`test_review_tally.py`, `test_plan_review.py`, `test_plan_review_round.py`) for neutral rescue, non-fileable OOS, security holdback, and co-proposer cases.

## Out-of-scope (tracked follow-ups)

**[OUT_OF_SCOPE]** `python/larch/review/review_tally.py:481-494` vs `python/larch/review/plan_review_tally.py:1008-1024`: public OOS pool dedup uses different identity algorithms today. Harmonizing dedup is a behavior change beyond the stated convergence goals; keep family artifact writers owning pool accumulation.
