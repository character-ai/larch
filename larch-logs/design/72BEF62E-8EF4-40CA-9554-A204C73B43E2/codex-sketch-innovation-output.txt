I would make `plan-review-loop.sh` a narrow transaction driver, not a thin wrapper around `/review`’s `review-core.sh`. The reusable pieces are already below that layer: `dispatch-plan-review-panel.sh`, `collect-agent-results.sh`, `aggregate-findings.sh`, `dispatch-plan-voters.sh`, and `tally-plan-review.sh`. `review-core.sh` has code-review-specific artifacts, round summaries, diff/OOS semantics, and implement log promotion, while `/design` needs session-root artifacts and must not revise `plan.txt` in Step 3. The clean shape is: scout, dispatch panel, collect, convert collected output into `$DESIGN_TMPDIR/ballot.txt` / findings format, optionally aggregate, dispatch all voters, tally, emit `LOOP_STATUS`, `ACCEPTED_COUNT`, `DEGRADED_PANEL`, `ROUNDS_COMPLETED`.

I would keep `dispatch-plan-voters.sh` and extend it to own Voter 1 via `launch-claude-review.sh`, matching `dispatch-code-voters.sh` instead of moving voter launch back into [SKILL.md](<OPERATOR_REPO_PATH>/skills/design/SKILL.md:634). Deleting it and inlining voter dispatch into the new loop is tempting, but it would bury parse-rate retry, fallback accounting, and `VOTER_PATHS_FILE` behavior inside an already-large orchestration script. A unified `dispatch-voters.sh --kind plan|code` is the “right” longer-term abstraction, but it is too much blast radius for a no-behavior-change refactor. The files I would touch are exactly the issue’s list, with special attention to [dispatch-plan-voters.sh](<OPERATOR_REPO_PATH>/scripts/dispatch-plan-voters.sh:1), [tally-plan-review.sh](<OPERATOR_REPO_PATH>/skills/design/scripts/tally-plan-review.sh:1), [dispatch-plan-review-panel.sh](<OPERATOR_REPO_PATH>/skills/design/scripts/dispatch-plan-review-panel.sh:1), and [plan-review.md](<OPERATOR_REPO_PATH>/skills/design/references/plan-review.md:1), because those are the real contracts SKILL currently paraphrases.

Main tradeoff: moving the 0-judge branch fully into shell exposes that the old “main-agent adjudication” was not script-native. I would avoid pretending otherwise: with Voter 1 now a Claude subprocess, 0-judge should mean “all launched judges failed,” and the loop should either emit `LOOP_STATUS=main-agent-vote-required` for a tiny remaining SKILL shim or run a clearly labeled synthetic Claude subprocess fallback. For aggregator rollback, do not invent a new flag unless product wants a design-specific kill switch; [aggregate-findings.sh](<OPERATOR_REPO_PATH>/skills/review/scripts/aggregate-findings.sh:1) already supports `LARCH_AGGREGATOR_DISABLED=1`, so `plan-review-loop.sh` can honor `LARCH_DESIGN_USE_AGGREGATOR=false` only as a convenience wrapper around that. The “crazy but might work” idea is to treat the loop as an append-only event log: every phase writes `plan-review-loop.env` plus artifacts, and future multi-round work only replays phases by round number. I would still keep the public API to `--round-num <N>` for now; a richer `--phase` interface is premature until convergence and per-round promotion are actually designed.
