## Findings

### 1. Growth matching must stay pair-scoped (correctness)

**Location:** `python/larch/lint/duplicate_code.py:438-464`

The plan ties identity to sorted module pair plus content hash, but the growth rule only says to match a stored hash in equal-length windows inside a longer live block. It never says the baseline row must share the live observation's module pair.

That opens cross-pair allowance inheritance: a new `(C,D)` cluster could pass if its longer normalized text embeds a window matching `(A,B)`'s baselined hash, without being the same duplicate relationship.

**Suggested revision:** Restrict exact and growth matching to baseline rows with the same sorted module pair as the live observation. Never match on hash alone across pairs.

### 2. Normalized-block extraction contract is missing (correctness)

**Location:** `python/larch/lint/duplicate_code.py:110-114`

`DuplicateCluster` today holds only `lines` and source spans. Nothing retains Pylint's stripped duplicate text:

```110:114:python/larch/lint/duplicate_code.py
@dataclass(frozen=True)
class DuplicateCluster:
    lines: int
    spans: tuple[tuple[str, int, int], ...]
```

The plan requires hashing normalized common-block text and stable identity across unrelated line shifts, but does not name the pylint 4.0.5 extraction surface. Reimplementing strip logic beside symilar risks hashes that disagree with what R0801 actually compares.

**Suggested revision:** Pin extraction to pylint symilar's own normalized block bytes (per commonality, from canonical `LineSet`s). Fail closed on API drift. Do not hash raw file slices or a custom normalizer.

### 3. Multi-span expansion needs per-pair text, not one cluster hash (correctness)

**Location:** `python/larch/lint/duplicate_code.py:453-464`

Merged clusters aggregate many spans with one line count and no text:

```453:464:python/larch/lint/duplicate_code.py
def _clusters_from_sims(sims: Sequence[tuple[int, set[Any]]]) -> list[DuplicateCluster]:
    clusters: list[DuplicateCluster] = []
    for line_count, couples in sims:
        spans = tuple(
            sorted(
                (str(lineset.name), int(start_line), int(end_line))
                for lineset, start_line, end_line in couples
            )
        )
        clusters.append(DuplicateCluster(lines=int(line_count), spans=spans))
    return sorted(clusters, key=lambda cluster: cluster.spans)
```

The plan says to derive identities after merge and then expand to module pairs. One cluster-level hash for all pairs can let `(A,C)` inherit `(A,B)`'s allowance inside a transitive group, or collapse two same-pair duplicates that share line count.

**Suggested revision:** Emit baseline observations from canonicalized `_find_common` commonalities (one normalized text per sorted pair). Reject duplicate live `(pair, hash)` like `engine.py` does for live identities (`python/larch/lint/engine.py:1302-1307`). Keep merged clusters for digest/reporting only.

### 4. Growth ambiguity needs an explicit fail-closed rule (correctness)

**Location:** `python/larch/lint/duplicate_code.py:321-349`

Parallel canonicalization fixes `LineSet` identity for dedup (`python/larch/lint/duplicate_code.py:321-349`), but the plan's growth rule does not say what to do when:

- two same-pair baseline rows both match one live block (different historical duplicates), or
- one live block has multiple equal-length windows matching the same baseline hash.

The general "ambiguity must fail closed" edge case does not define growth tie-breaking. First-match logic could grant the largest allowance.

**Suggested revision:** If more than one same-pair baseline row qualifies for a live observation, exit `2` with an explicit ambiguous-growth diagnostic. Only then compare live line count to the single matched row's allowance.

### 5. Module path format for identities is unspecified (correctness)

**Location:** `python/larch/lint/duplicate_code.py:248-249`

Scanned files are recorded as pylint filepaths (`fileitem.filepath` at line 248). Spans use `lineset.name` at line 458. The plan requires sorted module names but not a canonical repo-relative form. Other baselines use `python/`-prefixed paths (`python/larch/lint/engine.py:951-968`).

Unpinned naming can make the 115-row bootstrap look stale after regen even when duplicate content is unchanged.

**Suggested revision:** Specify one canonical module string format for identity, JSON rows, and diagnostics; add a test that regen is stable across the chosen normalization.
