## Approach

Extend the existing parallel Pylint runner. Keep its detection semantics and pair enumeration unchanged.

Represent each baseline row with:

- The sorted module pair.
- A 16-character SHA-256 prefix of the normalized common block.
- The allowed line count.
- A non-empty reason.

Derive the hash from Pylint's stripped common-block text, not source positions. For growth detection, match the stored block hash against equal-length windows within a longer live block. This catches growth at either edge. Treat changed blocks as a new live identity plus a stale baseline identity.

Use exit code `0` when every live cluster is grandfathered at or below its allowance. Return `1` for new, grown, or stale clusters. Return `2` for malformed, missing, unreadable, ambiguous, or unsafe baseline state.

`--write` regenerates canonical sorted JSON. It preserves reasons for exact identities, removes stale rows, and requires `--initial-reason` for identities without a preserved reason.

## Edge cases

- Unrelated line movement must not change an identity.
- Identifier or code changes inside a common block may change its hash and must fail as new plus stale.
- A longer block may extend before or after the old block. Search normalized equal-length windows rather than checking only a prefix.
- Multiple clusters between the same modules remain distinct through their content hashes.
- Hash-prefix or live-identity ambiguity must fail closed.
- Routine regeneration must not invent reasons for changed identities.
- Manual and push-triggered workflow runs may overlap. Concurrency and exact-title verification prevent duplicate tracking issues.
- A closed prior issue must not be reopened implicitly. Create a new open tracking issue.

## Failure modes

- Pylint API drift or unavailable normalized text returns the existing tool-error class.
- Invalid baseline data returns `2` before evaluating findings.
- New, grown, or stale rows return `1` with regeneration guidance.
- Baseline regeneration refuses unreasoned new identities.
- GitHub query, mutation, or read-back failure leaves the workflow red and visible in Actions.

## Testing strategy

- Run `python3 -m pytest python/tests/lint/test_duplicate_code.py -q`.
- Bootstrap a temporary baseline through the CLI, rerun the check, then exercise new, grown, and stale fixtures.
- Run `make regen-duplicate-code-baseline` and inspect the canonical diff and row count.
- Run `make py-lint-duplicate-code` against the committed baseline.
- Run `actionlint .github/workflows/duplicate-code.yaml`.
- Run the repository JSON lint against `python/duplicate-code-baseline.json`.
- Use `workflow_dispatch` after merge to confirm the 25-minute budget and failure-issue path without adding PR-time coverage.
