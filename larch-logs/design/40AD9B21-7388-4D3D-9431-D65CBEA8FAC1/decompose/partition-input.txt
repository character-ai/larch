# Revive duplicate-code (R0801) enforcement as a shrink-only baseline ratchet

## Summary

The only mechanical duplication detector is switched off, and main is red under it. `.github/workflows/duplicate-code.yaml` lost its `push: main` trigger in #5110 (2026-06-22) and now runs only on manual `workflow_dispatch`. A full run on 2026-07-15 found 115 duplicate clusters at the configured threshold, 97 of them production-to-production. Revive the check as an always-on, shrink-only baseline ratchet per G-Enf-2.

Full root-cause analysis: #7460. Prompt-layer companion: #7464.

## Measured state (2026-07-15, local runs of `make py-lint-duplicate-code`)

- Exit: pylint refactor status (make Error 8); findings exist on main.
- 115 clusters of 2 similar blocks at the configured `min-similarity-lines=8` (`python/.pylintrc`).
- Breakdown: 97 production-to-production, 3 production-to-test, 15 test-to-test.
- Concentration: 78 of the 97 production pairs are inside the `python/larch/lint/lint_*.py` family (`lint_env_via_config_constant`, `lint_subprocess_via_runner`, `lint_layering`, `lint_tempfile_dir`, `lint_lifecycle_prefix_literal`, `lint_monkeypatch_facade_binding`, `lint_renderer_golden_tests`, and siblings). The largest cluster is 33 lines (`lint_layering` vs `lint_subprocess_via_runner`). Each new lint module was evidently written by copying a sibling; the enforcement layer itself is the biggest copy-paste nest.
- Notable non-lint pairs: `larch.design.design_publish` vs `larch.design.design_step5c` (16 lines), `larch.calibration.calibration_replay` vs `larch.report.run_log_batch` (15 lines), `larch.implement.checks_lint_fix` vs `larch.implement.step_7a` (14 lines).
- Wall time: 14m22s cold, 5m32s on an immediate rerun (pylint `persistent=yes` cache warm). Both are too slow to gate every PR (issue #4480's conclusion stands), and a cold run exceeds the disabled workflow's `timeout-minutes: 10`.

## Proposed change

1. Baseline ratchet (load-bearing): add a shrink-only, reason-bearing baseline to `python/cli.py lint duplicate-code` (host: `python/larch/lint/duplicate_code.py`, the existing custom parallel runner). Add `python/duplicate-code-baseline.json` per G-Enf-2: new clusters and grown clusters fail; stale rows fail so the baseline only shrinks; every row carries a reason. Key clusters by durable content per G-Det-1: the sorted module pair plus a normalized content hash of the common block, not line numbers, so unrelated line shifts do not force rebaselining.
2. Re-enable `.github/workflows/duplicate-code.yaml` on `push: main` with `timeout-minutes` raised above the cold-run cost, running the baseline-aware check. Make failure actionable: file or update one tracking issue on failure. A red result with no owner is how the check died the first time (#4763 moved it post-merge, then #5110 disabled it).
3. Optional follow-up, PR-time coverage: extend the runner with a changed-files mode that compares only changed files against the full corpus. The runner already enumerates explicit pair combinations, so restricting pairs to those touching changed files is a natural extension and would bring the cost down to PR scale. Keep it a separate step; the main-push ratchet is the priority.

## Alternatives considered (G-Prevent-1 host naming)

- Re-enable the workflow with no baseline: main is red today, so the job fails on every push and gets ignored or re-disabled again.
- Exclude tests to go red/green without a baseline: 97 production pairs remain, so exclusion does not make main green.
- PR CI as-is: 5 to 14 minutes of wall time; rejected in #4480 and confirmed by this measurement.
- Host: no new lint module. Extend `duplicate_code.py` and reuse the existing baseline conventions (reason-bearing rows, guarded `make regen-*` refresh, stale-row failure). No new `python/lint-module-manifest.json` entry is needed unless a new `lint_*.py` module is created.

## Acceptance

- With the committed baseline, `python3 python/cli.py lint duplicate-code` e
