# Implementation Plan: PID-keyed `/design` session-env symlink

## Goal

Eliminate the machine-wide `~/.cache/larch/sessions/current-design-env.sh` singleton that causes concurrent `/design` runs (across working-tree clones on the same machine, including nested-under-`/implement` runs) to silently clobber each other's session env, by keying the stable symlink name on the **Claude Code parent process id** so each Claude session owns its own slot.

## Approach

The Claude Code Bash tool spawns a fresh `bash` subshell per Bash-tool call. Inside any such subshell, `$PPID` resolves to the Claude Code process itself, and that value is **stable for the entire Claude session** (every Bash call within one `/design` run sees the same `$PPID`). Different Claude sessions, including concurrent ones in different working-tree clones, have **different** PPIDs.

**Empirically verified on Claude Code (Opus 4.7) during quick-mode self-review**: from inside a Bash-tool subshell, `$PPID` resolves directly to Claude's PID (parent process name = `claude` — observed `claude --model claude-opus-4-7[1m] --effort high`), and is **identical across separate Bash tool calls in the same Claude session** (two consecutive Bash tool calls in this `/design 2599` run both reported `PPID=870`). The PID-keying mechanism is therefore directly grounded in observed runtime behavior, not on inferred process-tree assumptions.

**Cross-skill audit** (grep + `ls scripts/write-*-current-env.sh` performed during Step 0c): only `/design` uses a machine-wide env symlink. `/implement`, `/research`, `/review`, and other skills use other handoff patterns (explicit `SESSION_ENV_PATH` arg, per-session tmpdir paths passed by absolute path) and are **unaffected** by this bug. The fix is scoped to `/design` and its writer.

Therefore:

1. The orchestrator's Step 0 Bash block captures `$PPID` (= Claude's PID) and passes it to the writer as `--claude-pid "$PPID"`.
2. The writer scopes the symlink filename to that PID: `~/.cache/larch/sessions/current-design-env-${CLAUDE_PID}.sh`.
3. Every prelude line in `skills/design/SKILL.md` becomes `[ -f ~/.cache/larch/sessions/current-design-env-$PPID.sh ] && source ~/.cache/larch/sessions/current-design-env-$PPID.sh`. Subshells spawned inside Bash blocks inherit `$PPID` (it is the parent shell's parent, i.e. Claude), so the same value resolves at every prelude.

The actual session env file still lives under `$DESIGN_TMPDIR/source-env.sh` (per-session, no change). Only the **symlink name** is keyed by Claude's PID. The conditional `[ -f ... ] &&` guard is preserved so missing/stale symlinks degrade to a silent no-op (existing semantics).

### Parallelism model — N concurrent `/implement` + `/design` sessions

The fix must hold under arbitrary numbers of concurrent `/implement` and `/design` sessions. Walk-through:

- **Multiple `/design` across different clones (e.g., `~/larch1`, `~/larch5`)**: each clone is a separate Claude Code process; each has a unique PID. Each writer creates a uniquely-named symlink (`current-design-env-<PID1>.sh`, `current-design-env-<PID5>.sh`, …). Every prelude resolves to its own session. ✓
- **Multiple `/implement` across clones**: `/implement` does not use the machine-wide symlink (it threads `SESSION_ENV_PATH` explicitly to nested skills via env var and tmpdir paths). N concurrent `/implement` does not race on the symlink at all. ✓
- **`/implement` invoking nested `/design`** (Skill-tool call within the same Claude process): the nested `/design`'s Step 0 runs in the same Claude session, sees the same `$PPID` as the surrounding `/implement`, and creates the symlink under that PID. Another concurrent `/implement` in a **different** Claude process has a different PID and a different symlink. ✓
- **One Claude session sequentially running multiple `/design`** (e.g., the user pattern that produced this very bug — running `/design 2596`, then aborting, then `/design 2599`): both `/design` invocations share the SAME `$PPID`, so they write to the SAME symlink slot — but they run **sequentially**, not concurrently, so the second invocation correctly overwrites the symlink to point at its own session's source-env. The first session's stale symlink is naturally replaced. ✓
- **Same Claude session, concurrent `/implement` and `/design`?**: not a real shape — a single Claude session runs one skill at a time. Even if a nested `/design` is in flight under `/implement`, the outer `/implement` is paused waiting for the Skill tool to return. Concurrent slash-commands within one Claude session do not exist. ✓
- **PID reuse after a Claude process exits**: a long-dead Claude PID can be reassigned by the OS to an unrelated process. If a future Claude session happens to receive the same PID and runs `/design`, it would source what may be a **dangling** symlink (the prior session's tmpdir was likely cleaned up at Step 5). The conditional `[ -f ... ] &&` guard turns this into a silent no-op; subsequent prelude consumers fail loudly with `DESIGN_TMPDIR: unbound variable`. If a tmpdir was preserved (Step 5 skipped on failure), the prelude would source a stale env — detectable by SESSION_ID / ISSUE_NUMBER mismatch and surfaced operationally; not silent corruption. Documented as a known operational risk in `write-design-current-env.md`.

### Why not other options

- **Per-CWD symlink (`$PWD/.larch/current-design-env.sh`)**: requires `.gitignore` change in every consumer repo; still races inside one repo if a user runs two `/design` from the same checkout (rare but possible). PID keying solves both naturally.
- **Embed `DESIGN_TMPDIR` into each Bash block at SKILL render time**: requires a build/render step that the runtime does not have today.
- **Crawl the process tree inside the writer (`ps -o ppid= -p $PPID`)**: fragile across platforms; the writer's own parent is the orchestrator-side bash subshell, not Claude. Passing `--claude-pid "$PPID"` from the orchestrator side is the cleaner hop.

## Edge cases

- **`$PPID` inside `(...)` subshells**: Bash parenthesized subshells inherit `$PPID` from the parent shell unchanged. Subsequent `source` inside a subshell resolves the same symlink. ✓
- **`bash -c '...'` wrappers**: a new `bash` invocation would change `$PPID` to the outer bash's PID, breaking the assumption. Current SKILL.md does not wrap the prelude in `bash -c`. The new `scripts/test-design-structure.sh` probe (`--claude-pid "$PPID"` literal in Step 0a) is a guard against future authors introducing such a wrapper.
- **PID reuse after Claude exit**: see Parallelism model above. The conditional `[ -f ... ] &&` guard handles dangling symlinks gracefully.
- **Pre-upgrade in-progress `/design` runs**: the prelude is conditional. A pre-upgrade run uses the old unkeyed path and will silently no-op on missing files, then fail loudly with `DESIGN_TMPDIR: unbound variable`. Same failure shape as the current pre-upgrade story, no worse.
- **Stale symlink accumulation**: each Claude session leaves one `current-design-env-<PID>.sh` symlink behind. Targets get cleaned up by Step 5, but symlink names persist (cheap, ~50 bytes each). Documented as cosmetic clutter with an operator-runnable cleanup snippet; out-of-scope for the runtime fix itself.
- **Test isolation under real-machine PIDs**: harness uses fake high-numbered PIDs that cannot collide with running processes (e.g., `999900 + counter`).

## Failure modes

1. **Wrong PID captured (e.g., future `bash -c` wrapping)**. If a future SKILL.md edit nests the Step 0 writer call inside `bash -c '...'`, the writer would receive the outer bash's PID, not Claude's, and subsequent preludes would source a non-existent symlink. **Earliest warning signal**: every Bash block from Step 1c onward fails immediately with `DESIGN_TMPDIR: unbound variable` (the conditional source no-ops, then `set -u` trips). **Mitigation**: the new `test-design-structure.sh` probe asserts `--claude-pid "$PPID"` appears literally in the Step 0a writer call site.
2. **`$PPID` is `0` or empty**. Defense-in-depth in the writer: reject non-positive-integer `--claude-pid` values with explicit error before the symlink update.
3. **Symlink race under filesystem stress**. `ln -sfn` is atomic at the inode level on POSIX, so two simultaneous writes from the same PID would still yield a coherent symlink (one of the two targets, deterministically the last writer). Concurrent writes from the same PID are not possible by construction (sequential Bash blocks within one Claude session), but the `ln -sfn` atomic guarantee provides defense in depth.

- **Concurrent regression** (manual, deferred): the bug originally manifested across `larch1`…`larch6` clones. A scripted reproducer (spawn two `/design` from two clones; assert each writes only to its own tmpdir) would be the gold-standard regression — recorded as a follow-up issue, **not** wired into `make lint` (requires real Claude Code processes; not portable).
- **`make lint` and `make test-harnesses`** must pass after all changes.
