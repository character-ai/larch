## Findings

### 1. [correctness] Legacy migration path is not covered by the planned tests
**Location:** `python/tests/lint/test_lint_complexity_baseline.py` (planned coverage); `python/larch/lint/lint_complexity_baseline.py:migrate_baseline`

The plan’s testing strategy describes migration round-trip as loading and reserializing the **already migrated** checked-in `python/complexity-baseline.json`. That validates `serialize_baseline` canonical ordering and metadata preservation on the post-migration artifact, but it does **not** exercise `migrate_baseline` or `--migrate` on legacy four-field rows.

Because the PR depends on a one-shot `--migrate` run (`Approach` / `UPDATED: python/complexity-baseline.json`), a broken migration implementation could be masked if the committed JSON is migrated manually while CI only runs the post-migration round-trip. That weakens the acceptance criterion that identities and metrics are unchanged across migration.

**Suggested revision:** Add a dedicated test on a synthetic legacy fixture that calls `migrate_baseline` (or `main --migrate`), checks grandfather fields on every row, and asserts unchanged `(file, code, qualified_symbol) → metric` projections.

### 2. [correctness] `migrate_baseline` must bypass strict `load_baseline`
**Location:** `python/larch/lint/lint_complexity_baseline.py:migrate_baseline` (planned); current `_validate_record` at ```186:217:python/larch/lint/lint_complexity_baseline.py```

The plan says migration “reads the existing baseline JSON,” which implies the right behavior, but it never states the constraint explicitly. Today `_validate_record` requires exactly `BASELINE_KEYS` (four fields). After Piece 1, strict load will reject legacy shapes. If an implementer routes migration through `load_baseline`, `--migrate` will fail on the file it is supposed to upgrade.

**Suggested revision:** Add one explicit plan line: `migrate_baseline` parses raw JSON (or a legacy-only helper) and must not call `load_baseline` on the pre-migration file.
