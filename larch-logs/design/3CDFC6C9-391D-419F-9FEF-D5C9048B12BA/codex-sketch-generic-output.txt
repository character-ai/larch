The main edits should be in `scripts/dispatch-code-voters.sh`, `scripts/dispatch-code-voters.md`, `skills/review/scripts/tally-code-votes.sh`, and `skills/review/scripts/tally-code-votes.md`. `tally-code-votes.sh` already has the right per-block loop and knows `reviewer_slots`, `voting_result`, effective voters, `JUDGE_ERROR`, OOS handling, and degraded panels, so it is the right place to append TSV rows. `review-core.sh` likely only needs to surface a `FINDINGS_CLASSIFICATION_TSV_FILE` KV if callers need it, because `/implement` round publishing already uses `larch-log.sh write-round --source-dir "$REVIEW_TMPDIR"`. `scripts/larch-log.sh` must add `findings-classification.tsv` to `round_artifact_included`; standalone `/review` logging likely needs a new flat batch or an extension to `log-phase.sh`/batch registry if the TSV must land under `larch-logs/review/<RUN_ID>/`, since standalone review currently writes named flat batches rather than per-round directories.

The main risk is semantic drift between current code-review OOS representation and the issue text: the current tally docs say code review mainly uses `FINDING_N` with `[OUT_OF_SCOPE]`, while shared ballot splitting also supports `OOS_N`. The implementation should support both in prompt, parsing, parse-rate checks, and TSV rows. The other risk is accidentally making rating parsing affect vote quorum; keep classification observational and preserve existing `YES/NO/EXONERATE/JUDGE_ERROR` behavior.
