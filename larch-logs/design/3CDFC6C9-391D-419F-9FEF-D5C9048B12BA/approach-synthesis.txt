## Approach Synthesis (sketch_budget=2 quick mode: Cursor-Generic + Codex-Generic)

Both sketches converge on the same architecture; Cursor's sketch is terse and Codex's is comprehensive. There are no contested decisions.

### Agreements

1. **TSV ownership lives in `tally-code-votes.sh`**. The script already loops per ballot block, knows `reviewer_slots` / `voting_result` / effective voters / `JUDGE_ERROR` / OOS handling, and writes the existing `YIELD_TSV_FILE` (`scout-archetype-yield.tsv`). The new `findings-classification.tsv` is appended in the same loop.

2. **`dispatch-code-voters.sh` only changes the judge prompt contract**. Extend `make_voter_prompt_file()` (and the retry prompt prefix `VOTER_PARSE_RATE_RETRY_PREFIX`) to instruct judges to emit `CORRECTNESS=`, `SEVERITY=`, `QUALITY=`, `UNCERTAIN=` tokens on the same line. No change to parse-rate retry behavior or vote quorum.

3. **Reuse L2's `scripts/parse-judge-vote-and-rating.sh`** (per Round 1 Decision 1 — L6 blocks on L2 #2671). L6 implementation does not start until that helper lands.

4. **Lenient parsing** (per Round 1 Decision 2). A recognized vote token is sufficient for the existing tally machinery; missing/unparseable rating tokens become `UNCERTAIN=true` with empty axis values. Existing `JUDGE_ERROR` triggers and vote thresholds are unchanged.

5. **`scripts/larch-log.sh` `round_artifact_included` allowlist must include `findings-classification.tsv`** (Cursor specifically). Without an entry, `larch-log.sh write-round` skips the TSV when publishing `/implement` review rounds to `larch-logs/implement/<RUN_ID>/round-<N>/`.

### Codex-only extras (Cursor did not contradict)

6. **Standalone `/review` log path is flat**. `/review` writes flat batch slugs under `larch-logs/review/<RUN_ID>/` (per `skills/review/scripts/log-phase.md`), not per-round subdirectories. Decision: add a new flat batch in `log-phase.sh` (e.g., `review-findings-classification`) rather than extend the implement-style round dir into /review. Keeps the existing flat scheme intact.

7. **`OOS_N:` vs `FINDING_N: [OUT_OF_SCOPE]` disambiguation**. `dispatch-code-voters.sh` currently handles `[OUT_OF_SCOPE]` semantics inside `FINDING_N:`, but the shared ballot also supports `OOS_N:`. Both forms must be covered by the extended prompt and TSV emission (issue body: "All ballot finding entries — `### FINDING_N:` AND `### OOS_N:`").

8. **`review-core.sh` surfaces `FINDINGS_CLASSIFICATION_TSV_FILE` KV**. When `tally-code-votes.sh` writes the TSV, it emits a `FINDINGS_CLASSIFICATION_TSV_FILE=<path>` line; `review-core.sh` re-emits it so the standalone `/review` wrapper loop can publish via `log-phase.sh`. Mirrors the existing `YIELD_TSV_FILE` plumbing.

9. **Harness coverage** spans:
   - `test-tally-code-votes.sh` — TSV writes per ballot block.
   - `test-dispatch-code-voters.sh` — extended judge prompt body.
   - `test-larch-log-write-round.sh` — allowlist entry.
   - `test-log-phase.sh` — new flat batch slug (standalone /review).
   - New `skills/review/scripts/test-findings-classification.sh` — integration test across both consumers via fixture.

### No contested decisions

Both sketches agreed on the high-level architecture (script ownership, prompt contract, allowlist update). The "extras" in Codex's sketch are details Cursor did not address but did not contradict either; they are taken as the synthesis position with no dialectic debate required.
