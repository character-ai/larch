## Findings

### 1. Classification `scope` not updated for rescued neutrals (plan-review + code-review parity)

**Focus:** correctness  
**Plan:** `### UPDATED: python/larch/review/review_tally.py`, `### UPDATED: python/larch/review/plan_review_tally.py`  
**Location:** `python/larch/review/review_tally.py:159-187`, `python/larch/review/plan_review_tally.py:336-370`

The plan routes rescued in-scope neutrals to `oos.md` and increments `OOS_REJECTED_COUNT` in code-review KVs, but it only says to keep `voting_result=neutral` in classification. It does not change the `scope` column.

Both tally writers still emit `scope=in_scope` for `FINDING_*` items:

```187:187:python/larch/review/review_tally.py
    row.append("oos" if is_oos else "in_scope")
```

```369:369:python/larch/review/plan_review_tally.py
            row.append("oos" if item_id.startswith("OOS_") else "in_scope")
```

Downstream, `progress_report._parse_classification_tsv` counts in-scope `FINDING_*` with `voting_result=neutral` as **NEUTRAL_COUNT**, not **OOS_REJECTED_COUNT**:

```1987:1993:python/larch/report/progress_report.py
        if in_scope and re.fullmatch(r"FINDING_[0-9A-Za-z_]+", item):
            if result == "accepted":
                accepted += 1
            elif result == "rejected":
                rejected += 1
            elif result == "neutral":
                neutral += 1
```

That breaks parity: code-review stdout/env KVs will show `OOS_REJECTED_COUNT=1`, but implement/design `round-meta.json` (from classification TSV) will still show `NEUTRAL_COUNT=1` and `OOS_REJECTED_COUNT=0`.

**Suggested revision:** When rescue fires, write classification `scope=oos` while keeping `voting_result=neutral`. This matches the existing #4882 scope-aware canonical pattern without touching `progress_report.py`.

### 2. `_record_tally` per-item rows will still mark rescued neutrals as rejected

**Focus:** correctness  
**Plan:** `### UPDATED: python/larch/review/review_tally.py` (Failure modes mention accepted-OOS sink only)  
**Location:** `python/larch/review/review_tally.py:412-420`, `python/larch/review/review_tally.py:1022-1026`

The plan updates aggregate `NEUTRAL_COUNT` / `OOS_REJECTED_COUNT` / `REJECTED_COUNT`, but not per-finding tally env rows. `_record_tally` always writes `_OUTCOME=rejected` for any non-accepted item, including neutrals:

```412:420:python/larch/review/review_tally.py
def _record_tally(*, tally_file: Path, item_id: str, accepted: bool, outcome: str) -> None:
    prefix, number = item_id.split("_", 1)
    _append(path=tally_file, text=f"{prefix}_{number}_ACCEPTED={'true' if accepted else 'false'}\n")
    if outcome == "accepted":
        _append(path=tally_file, text=f"{prefix}_{number}_OUTCOME=accepted\n")
    else:
        _append(path=tally_file, text=f"{prefix}_{number}_OUTCOME=rejected\n")
        subtype = "true_rejected" if outcome == "rejected" else "neutral"
        _append(path=tally_file, text=f"{prefix}_{number}_REJECTED_SUBTYPE={subtype}\n")
```

Later, `emit-tally` rebuilds compact `rejected-findings.md` from every `_OUTCOME=rejected` line. A rescued major neutral in `oos.md` could still land in compact rejected output, contradicting the plan test that `FINDING_1` must not appear in `rejected-findings.md`.

**Suggested revision:** Add a rescued-neutral branch in `_record_tally` (e.g. `OUTCOME=oos`, no `REJECTED_SUBTYPE`) and teach `emit-tally` to ignore those rows when building compact rejected output.

### 3. Code-review ledger is recorded before rescue is decided

**Focus:** correctness  
**Plan:** `### UPDATED: python/larch/review/review_tally.py` ("record the ledger outcome as `oos`")  
**Location:** `python/larch/review/review_tally.py:770-780` vs artifact routing at `799-814`

`_record_classification_and_ledger` runs with `outcome="oos" if is_oos else result` before the finding artifact branch that the plan extends for rescue. If only the artifact branch is updated, the ledger can remain `neutral` while `oos.md` and KV counts say OOS.

Plan-review avoids this because `_write_findings_ledger` runs after `_render` and the plan explicitly updates it. Code-review does not have that ordering guarantee today.

**Suggested revision:** Compute `neutral_high_severity_rescue_to_oos(...)` before `_record_classification_and_ledger`, and pass `outcome="oos"` into `_ledger_entry` when rescue fires.

- Plan-review regression assertions (ledger `outcome=oos`, artifact placement) are directionally correct once classification `scope` and ledger ordering are fixed.
