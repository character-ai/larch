# Problem

We file OOS issues liberally. `/implement` and `/design` drop anything they notice into `[OOS]` issues, on the logic that `/combine-issues --oos` deduplicates and filters later. Better to over-file than to miss something useful.

Today `/combine-issues --oos` filters on **actuality** only: is the referenced file or code still present, and is the concern unfixed (`.claude/skills/combine-issues/SKILL.md` step `oos-2`). It never judges **merit**: whether the item is worth doing at all. So real-but-not-worth-it items survive and get promoted into combined issues that spend `/design` + `/implement` cycles.

`/combine-issues` is the right chokepoint. Killing a low-merit item here is the cheapest kill: it skips the whole downstream cost. It also runs on a smart model, so the judgment is reliable.

# Proposal

Add a second per-item gate after the actuality check: a **merit** ("is this a good idea?") judgment. Keep items that pass both gates. Propose the rest for rejection.

Scope is prompt-side only, in `.claude/skills/combine-issues/SKILL.md` step `oos-2`. The Python module (`python/larch/issue/combine_issues.py`) is mechanical (fetch/apply/close/deps) and needs no new verb. The actuality check is already prose-only; merit is the same shape.

# Merit rubric (ground it in the repo's own principles)

Do not free-float "common sense." Judge each item against documented values so every rejection is citable:

- Speculative feature, single-use abstraction, unrequested flexibility, or defensive code for impossible states (`KARPATHY_CLAUDE.md` §2).
- Refactors unbroken code (§3).
- Pure nitpick or style preference with no real impact.
- Large or risky change for a trivial gain (lopsided cost/benefit).
- Contradicts a documented decision (strongest signal): the item says "do X" where a rule says "we deliberately don't do X."

**Cite a concrete reason or keep.** Default-keep bias, stronger than the actuality check's, because merit is a judgment and a wrong rejection silently loses a good improvement. No specific reason tied to code read or a documented principle means keep the item.

# Operator confirmation of rejections (one batch gate)

Merit is a judgment, so rejections are never auto-applied. Hold every proposed rejection and surface them **all at once** as one consolidated list at the `oos-4` approval gate. Give each rejected item a 1-3 sentence statement of the cause of rejection:

```
Rejected items (merit):
  A (#<N>) — <1-3 sentence cause of rejection>
  B (#<M>) — <1-3 sentence cause of rejection>
  C (#<P>) — <1-3 sentence cause of rejection>
approve?
```

One confirmation covers the batch. The operator can approve all rejections, or reply in **free prose** to keep any subset (for example, "keep A and C" or "keep the caching one, it is actually load-bearing"); the named items are rescued and the rest are rejected. The operator can also cancel. Do not prompt per item.

Stale (actuality) discards stay auto-applied and reported as today. Only merit rejections need this confirmation, because only merit is a judgment call.

# Reporting and closure

- Extend the `oos-2` summary to count merit rejections separately, for example: `<K> kept, <M> stale, <P> low-merit (rejected pending confirmation)`.
- Generalize "fully stale source" to "fully discarded source": a source emptied by stale discards plus confirmed merit rejections closes as `not planned`. Make the close comment honest ("items discarded as stale or out of line with repo principles"), not just "stale."
- Closure happens only after the operator confirms the rejections.

# Non-goals

- Keep the gate binary (keep or reject). No third "low-value, tagged" tier: that gold-plates the filter the gate exists to be.
- Do not tighten the filing side (`/implement`, `/design` OOS emission). Filing stays liberal; combine does the judging. Double-filtering is out of scope.

# Acceptance criteria

- `oos-2` applies a merit gate after actuality, with the rubric above and a default-keep bias.
- Proposed merit rejections are held, not auto-discarded.
- All proposed rejections appear in one consolidated list at `oos-4` for a single batch confirmation, each with a 1-3 sentence cause of rejection. The operator can approve all, reply in free prose to keep any subset, or cancel.
- The `oos-2` summary counts merit rejections separately.
- A source fully emptied by stale plus confirmed merit rejections closes as `not planned` with an honest close comment.
- No new Python verb. The change is confined to `SKILL.md` prose, plus any test that pins the `oos-2` summary text.

## Proposed Design Outline

### Goals
- Add a merit ("worth doing?") judgment gate to `oos-2` that fires after actuality check per item.
- Surface all proposed merit rejections in one batch at `oos-4` for operator confirmation.
- Generalize "fully stale source" to "fully discarded source" so stale + confirmed merit rejections together qualify a source for `not planned` closure.

### Non-goals
- No new Python verb or module change.
- No third "keep-tagged" tier; judgment is binary (keep or reject).
- No tightening of the OOS filing side in `/implement` or `/design`.

### Approach sketch
- Edit `oos-2` in `.claude/skills/combine-issues/SKILL.md`: after marking an item actual, apply the five-point merit rubric from the issue body; if low-merit, add to a "proposed merit rejections" list with a 1-3 sentence cause.
- Update `oos-2` summary line to report kept, stale, and low-merit counts separately.
- Edit `oos-4` to prepend the consolidated merit-rejection list before the combination scheme prompt; the operator confirms all in one batch (approve all, free-prose keep-subset, or cancel).
- After confirmation, treat confirmed merit rejections the same as stale discards for source-closure eligibility ("fully discarded source").
- Update the close comment text to say "discarded as stale or out of line with repo principles" when merit rejections contributed.
