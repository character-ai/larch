<steelman>
Keeping every initial-state key as adjacent `printf` lines inside `write_initial_state()` keeps the cold-start picture in one contiguous block and avoids adding another sourced module to trace when debugging a malformed `ship-pr-state.sh`.
</steelman>
<claim>
Given `ship-pr.sh` already sources `lib-finalize-state-keys.sh` for the same class of contract, extracting an ordered ship-pr initial-state key list into `scripts/lib-ship-pr-state-keys.sh` is the proportionate choice: it matches established practice instead of growing an already enormous script with another hand-maintained key sequence.
</claim>
<evidence>
[`scripts/ship-pr.sh`](scripts/ship-pr.sh) lines 18–19 source `lib-finalize-state-keys.sh`; [`scripts/ship-pr.sh`](scripts/ship-pr.sh) lines 239–297 define `write_initial_state()` with many hard-coded keys yet omit keys the SKILL and tests treat as part of the state surface (e.g. `NO_LOGS_COMMIT` appears in [`scripts/lib-finalize-state-keys.sh`](scripts/lib-finalize-state-keys.sh) lines 10–31 as `LARCH_FINALIZE_STATE_KEYS`, while `BAIL_FAILURE_DETAIL_LOG` is exercised in [`scripts/test-ship-pr-fix-loop-2632.inc.sh`](scripts/test-ship-pr-fix-loop-2632.inc.sh) line 62); [`scripts/lib-finalize-state-keys.md`](scripts/lib-finalize-state-keys.md) lines 1–3 document the “keys live in a small sourced lib + stub MD” split.
</evidence>
<strongest_concession>
A dedicated lib file forces reviewers to flip between two files to see defaults and ordering, which is a real navigation cost compared to one long function body.
</strongest_concession>
<counter_to_opposition>
That navigation cost is already paid for finalize-state keys in this same script path, and the drift risk is concrete: tests grep for keys absent from the current `printf` sequence, so a single ordered array plus a writer loop is simpler to extend safely than renumbering dozens of format lines by hand.
</counter_to_opposition>
<risk_if_wrong>
If the argv-only direction removes most `ship-pr-state.sh` composition from `ship-pr.sh`, a standalone keys library could become redundant churn until deleted or folded back.
</risk_if_wrong>
