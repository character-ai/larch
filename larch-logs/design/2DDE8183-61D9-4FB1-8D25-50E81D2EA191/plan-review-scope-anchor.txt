## Summary

Four backgrounded fences in `/implement` and `/design` run with no `.bg-wait-active` marker, so the two notification-storm hook guards are inert during them. Extend marker coverage to all four, and add a structural guard so `/review` (foreground today) cannot silently regress into an uncovered backgrounded fence.

## Root cause

Both guards fire only while a live `.bg-wait-active` marker exists, and the hooks recognize a closed STEP allowlist (`marker_step_completed` in `scripts/hook-bg-poll-guard.sh`; `is_step_completed` in `scripts/hook-no-progress-guard.sh`): `design-step3-review`, `design-step5c`, `design-step-final-summary`, `implement-step3-checks`, `implement-step5-review`. Any backgrounded fence outside that list runs with Monitor/TaskOutput denial **and** the #5639 circuit breaker both disabled. See the companion ship-pr issue for the full root cause.

## Fix

For each fence: write `.bg-wait-active` on entry (`PID`/`START_EPOCH`/`TIMEOUT_S`/`STEP=<new value>`), remove on all exits, and register the new STEP + its terminal sentinel in both hooks' release functions (`marker_step_completed` + `reset_probe_counter_for_step` in `hook-bg-poll-guard.sh`; `is_step_completed` in `hook-no-progress-guard.sh`). Fail-open throughout.

Specifics:

- **Step 7a** (Python): write/remove the marker in the `step-7a` entrypoint via `try`/`finally`, like the design final-summary Python port (`SKILL.md:218`). Terminal sentinel e.g. `.completed/step-7a-terminal`.
- **Step 6 / Step 5-resume** (composites): write the marker at the **outer composite boundary** (`checks-commit-route` / `checks-step5-resume`), **not** inside `run-step-checks.sh` per check pass. These composites re-invoke checks in a repair loop; a per-pass marker would thrash on/off. Terminal sentinels e.g. `.completed/step-6-terminal`, `.completed/step-5-resume-terminal`.
- **design Step 4 tail**: `.completed/step-4` is already the fence's terminal sentinel; reuse it. Write/remove the marker in `design-step3b-tail.sh` (`STEP=design-step4-tail`). Because `/design` recovery uses a foreground probe, **also** add `step-4` to the foreground-probe allowlist + clamp in `bash_is_terminal_sentinel_foreground_probe` / `probe_sentinel_name` (its regex currently lists only `step-3-terminal`/`step-5c-terminal`/`step-final-summary`) and to the `skills/shared/design-background-wait.md` contract. Otherwise the live marker makes `hook-bg-poll-guard.sh` deny the sanctioned `[ -f "$DESIGN_TMPDIR/.completed/step-4" ]` probe via the generic bracket-file-test rule.
- **Step 7a / 6 / 5-resume are notification-only** (`/implement` recovery is notification-only per NEVER #8): no foreground-probe allowlist change needed; the marker only needs the two release registrations.

## /review coverage

`/review` and `/review-and-fix` dispatch the reviewer panel (`review core`) and the Cursor/Codex fix applier (`review-and-fix apply-findings`) as **foreground** `python/cli.py` calls. No `run_in_background`, no `<task-notification>`, so no spurious-notification exposure and no marker needed today. The only backgrounded review path is `/implement` Step 5, already covered by `implement-step5-review`.

To keep it that way, add a structural lint/test asserting every `run_in_background: true` launch directive in `skills/{design,implement,review,review-and-fix}/**` maps to a fence that arms `.bg-wait-active` (allowlist-backed). This generalizes the invariant and forces any future backgrounded review fence to add a marker. It covers `/review` by construction.

## Proposed Design Outline

### Goals
- Arm `.bg-wait-active` markers on all four currently uncovered backgrounded fences so hook guards protect them from notification storms.
- Register new STEP values and terminal sentinels in both hook release functions, and extend the foreground-probe allowlist for design Step 4.
- Add a structural lint that enforces `run_in_background: true` → `.bg-wait-active` pairing across all four skills, covering `/review` by construction.

### Non-goals
- No changes to marker format, hook decision logic, or guard thresholds beyond adding new STEP registrations.
- No changes to fences that already carry markers (`design-step3-review`, `design-step5c`, `design-step-final-summary`, `implement-step3-checks`, `implement-step5-review`, `implement-step8-ship`).
- No restructuring of the companion ship-pr issue's scope; hook edits in this issue are additive only.
