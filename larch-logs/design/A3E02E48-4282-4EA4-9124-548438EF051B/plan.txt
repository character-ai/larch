### UPDATED: python/larch/report/run_logs.py

Add a new `larch_log_validate_run_id_main(argv: list[str]) -> int` near the existing `larch_log_*_main` entry points.

Implementation shape:
- Parse `--run-id` as a required argument.
- Print exactly `VALID=true` when `validate_run_id_slug(args.run_id)` returns true.
- Print exactly `VALID=false` when it returns false.
- Return `0` for both valid and invalid values.
- Return a usage-style nonzero code only for malformed CLI usage, such as missing `--run-id`.

Do not use `_parse_common`, because it validates run IDs as an error path. This verb must be a check-only predicate.

## Approach

1. Add the new Python main as a thin wrapper over `validate_run_id_slug`.
2. Wire it through the central dispatcher and machine-stdout key set.
3. Update `/review` Step 4 to consume the new predicate, and change every Step 4 `--run-id` argparse CLI call (validator, log-phase, capture-transcript, commit) to the `=` form so dash-leading values parse correctly everywhere, not only at the new guard.
4. Fix `review_tally.py`'s internal `log-phase` subprocess forwarding to use the same `=` form.
5. Add unit tests before broader lint.
6. Keep `skills/implement/scripts/post-tracking-issue.sh` out of scope. It has a distinct behavior gap and was explicitly excluded by discussion round 1.

## Edge cases

- Empty `RUN_ID` must be `VALID=false` with return code `0`, so `/review` can skip log writes without aborting.
- Invalid but present values like `..`, `a..b`, `bad/slash`, and `bad\slash` must be false, not usage errors.
- A dash-leading but otherwise valid slug (for example `-abc123`) must be `VALID=true`, and every later Step 4 call that receives it (log-phase, capture-transcript, commit, and `review_tally.py`'s internal forwarding) must still succeed, not just the validator call.
- Quiet-mode inheritance must not suppress the `VALID=` line.
- The SKILL.md guard should parse an exact `VALID=true` line, not a loose substring.
- Avoid reintroducing the regex or `..` checks in SKILL.md prose.

## Failure modes

- If invalid run IDs return nonzero, `set -e` or `pipefail` contexts can turn a skipped log write into a Step 4 abort.
- If the verb is not marked machine stdout, the guard may fail under quiet larch contexts.
- If SKILL.md keeps the rule in prose, the duplicate source of truth remains.
- If only the new validator call uses the `=` form while log-phase, capture-transcript, commit, or `review_tally.py` keep the two-token form, a dash-leading run-id passes the guard but still breaks the actual larch-log write.
- If review skill closure grows, prefer tightening nearby wording. Update the closure baseline only if the growth is intentional and unavoidable.
