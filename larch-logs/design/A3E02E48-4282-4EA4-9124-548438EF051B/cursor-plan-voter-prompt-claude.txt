# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `blocker` or `major`. Single-YES `minor`, `nit`, `uncertain`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.
After the first review round, a finding that no prior round raised is suspect: if it were
necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

Anchor. Judge necessity against the spec, not against the finding text. For /design plan review,
the spec is the originating issue scope (the staged scope anchor / feature description). For
/implement and /review code review, the spec is the implementation plan (plan fidelity).

## Summary

The Step 4 `RUN_ID` slug-validation guard added to `skills/review/SKILL.md` by PR #6105 (issue #6089) reimplements `run_log_batch.validate_run_id_slug`'s non-empty / no-`..` / no-`/` / no-`\` / `^[A-Za-z0-9._-]+$` check as inline Bash glob/regex matching (`review_run_id_valid`) instead of calling a Python CLI helper. This duplicates validation logic that already has a single Python source of truth, violating `ARCHITECTURAL_GUIDELINES.md` guideline G-Skill-2: "logic lives in Python behind `cli.py`; SKILL.md and Bash stay thin."

## Original report

Bug filed via `/bug` with the argument `G-Skill-2 (logic lives in Python behind cli.py; SKILL.md and Bash stay thin)`. This names the specific `ARCHITECTURAL_GUIDELINES.md` entry that was violated; it was surfaced by the `/implement` Architectural Guidelines Phase A step during the run that implemented issue #6089 (PR #6105), which flagged the deviation described below as a non-blocking Warning.

## Reproduction scenario

Not a runtime bug; it is a static code-organization issue visible by reading the source:

1. Open `skills/review/SKILL.md` around lines 84-89.
2. Observe the inline Bash block that computes `review_run_id_valid` by hand.
3. Compare against `python/larch/report/run_log_batch.py` lines 141-144, which implements the identical rule as `validate_run_id_slug`.
4. Search `python/larch/cli.py`'s `("run-log", ...)` verb table (around lines 427-444): no verb exposes `validate_run_id_slug` to callers outside the `larch.report` package.

## Expected behavior

Per G-Skill-2, the RUN_ID slug-validity check that gates Step 4 review larch-log writes should be a Python-owned check invoked through `cli.py` (for example a `run-log validate-run-id` verb, or reuse of an existing verb with a check-only mode), with `skills/review/SKILL.md` staying a thin caller that branches on that check's result. This matches the pattern used elsewhere in this skill for logic that belongs in Python.

## Observed behavior

`skills/review/SKILL.md` Step 4 instead recomputes the slug rule directly in Bash:

```bash
review_run_id_valid=false
if [[ -n "${RUN_ID:-}" &amp;&amp; "$RUN_ID" != *..* &amp;&amp; "$RUN_ID" != */* &amp;&amp; "$RUN_ID" != *\\* &amp;&amp; "$RUN_ID" =~ ^[A-Za-z0-9._-]+$ ]]; then
  review_run_id_valid=true
fi
```

This mirrors `validate_run_id_slug`'s behavior byte-for-byte but lives in a second, independently-maintained location. `python/larch/cli.py`'s `("run-log", ...)` verb registry has no `validate`-style entry, so `skills/review/SKILL.md` has no CLI call to delegate to instead of re-deriving the predicate inline.

## Root cause analysis

Issue #6089's plan (implemented by PR #6105) added this RUN_ID validity guard to close an OOS finding from #5976, and explicitly named `run_log_batch.validate_run_id_slug` as the rule to match: "Add a Step 4 `RUN_ID` validity guard matching `run_log_batch.validate_run_id_slug`." Two `/design` review rounds and the round-1 `/implement` code-review panel did not flag that the guard could delegate to a Python CLI call instead of duplicating the Bash. The `/implement` Architectural Guidelines Phase A step (which compares the diff against `ARCHITECTURAL_GUIDELINES.md` after code review) is the one place that caught it, but per `AGENTS.md` that phase's deviations "are warnings only and never block PR creation," so the PR merged with the duplication intact.

## Evidence

- `skills/review/SKILL.md:84-89` — the new inline Bash slug guard (`review_run_id_valid=...`), also referenced in prose at lines 75 and 117.
- `python/larch/report/run_log_batch.py:141-144` — `validate_run_id_slug`, the Python source of truth for this exact rule.
- `python/larch/cli.py:427-444` — the `("run-log", ...)` verb registry; no `validate`/slug-check entry exists. `validate_run_id_slug` is called only internally, from `run_log_manifest.py`, `run_log_commit.py:314`, and `run_log_flush.py:965,1007` — never from outside the `larch.report` package.
- Flagged during the `/implement` run for issue #6089 (PR #6105, merged to `main` as commit `cf0d33786`) by the Architectural Guidelines Phase A step, logged as a non-blocking Warning in that run's final summary.

## Affected files

- `skills/review/SKILL.md` — carries the duplicated Bash validation logic; would become a thin caller of a new or reused Python check.
- `python/larch/report/run_log_batch.py` — houses `validate_run_id_slug`, the logic that needs a CLI-facing entry point.
- `python/larch/cli.py` — would gain a new `(domain, verb)` registry entry if a dedicated verb is added.

## Suggested fix(es)

Expose `validate_run_id_slug` (or an equivalent thin check) as a `cli.py` verb, e.g. `python3 cli.py run-log validate-run-id --run-id "$RUN_ID"` returning a `VALID=true|false` KV (or a plain exit code). Change `skills/review/SKILL.md` Step 4's guard to call that verb and branch on its result instead of re-deriving the glob/regex predicate inline in Bash. No behavior change should be required; this is a structural move of one existing rule into one place.

## Open questions
