## Goal

Move `/review` Step 4 `RUN_ID` validation behind `python/cli.py` while keeping Step 4 behavior unchanged.

## Files to modify/create

### UPDATED: python/larch/report/run_logs.py

Add a new `larch_log_validate_run_id_main(argv: list[str]) -> int` near the existing `larch_log_*_main` entry points.

Implementation shape:
- Parse `--run-id` as a required argument.
- Print exactly `VALID=true` when `validate_run_id_slug(args.run_id)` returns true.
- Print exactly `VALID=false` when it returns false.
- Return `0` for both valid and invalid values.
- Return a usage-style nonzero code only for malformed CLI usage, such as missing `--run-id`.

Do not use `_parse_common`, because it validates run IDs as an error path. This verb must be a check-only predicate.

### UPDATED: python/larch/cli.py

Register the new verb:
- `("run-log", "validate-run-id"): ("larch.report.run_logs", "larch_log_validate_run_id_main")`

Add the same key to `_MACHINE_STDOUT_KEYS`, because callers consume `VALID=true|false` as machine stdout and must not inherit quiet-mode suppression.

### UPDATED: skills/review/SKILL.md

In Step 4:
- Replace the prose that spells out the slug rule with prose that says the guard calls `python3 "${CLAUDE_PLUGIN_ROOT}/python/cli.py" run-log validate-run-id`.
- Keep the statement that all Step 4 review larch-log writes, standalone transcript capture, and standalone commit are gated on that guard.
- Replace the inline `[[ ... =~ ^[A-Za-z0-9._-]+$ ]]` block in the exact `review-scout-manifest` pattern with a thin CLI call.
- Pass `--run-id` using the `=` form (`--run-id="${RUN_ID:-}"`), not a separate argv token. A separate token lets a dash-leading slug value be misread as another option by argparse; the `=` form assigns the value unambiguously regardless of its leading character.

Preferred guard shape:
review_run_id_valid=false
if python3 "${CLAUDE_PLUGIN_ROOT}/python/cli.py" run-log validate-run-id --run-id="${RUN_ID:-}" | grep -qx 'VALID=true'; then
  review_run_id_valid=true
fi

Keep the rest of the `jq`, `review log-phase`, transcript capture, and commit prose unchanged except where it refers to the duplicated rule.

## Approach

1. Add the new Python main as a thin wrapper over `validate_run_id_slug`.
2. Wire it through the central dispatcher and machine-stdout key set.
3. Update `/review` Step 4 to consume the new predicate, passing `--run-id` with the `=` form so dash-leading values parse correctly.
4. Add unit tests before broader lint.
5. Keep `skills/implement/scripts/post-tracking-issue.sh` out of scope. It has a distinct behavior gap and was explicitly excluded by discussion round 1.

## Edge cases

- Empty `RUN_ID` must be `VALID=false` with return code `0`, so `/review` can skip log writes without aborting.
- Invalid but present values like `..`, `a..b`, `bad/slash`, and `bad\slash` must be false, not usage errors.
- A dash-leading but otherwise valid slug (for example `-abc123`) must be `VALID=true`; the SKILL.md call passes it with `--run-id=` so argparse cannot mistake it for another option.
- Quiet-mode inheritance must not suppress the `VALID=` line.
- The SKILL.md guard should parse an exact `VALID=true` line, not a loose substring.
- Avoid reintroducing the regex or `..` checks in SKILL.md prose.

## Failure modes

- If invalid run IDs return nonzero, `set -e` or `pipefail` contexts can turn a skipped log write into a Step 4 abort.
- If the verb is not marked machine stdout, the guard may fail under quiet larch contexts.
- If SKILL.md keeps the rule in prose, the duplicate source of truth remains.
- If review skill closure grows, prefer tightening nearby wording. Update the closure baseline only if the growth is intentional and unavoidable.
