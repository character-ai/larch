# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

## Summary

`/design` Step 3 plan-review runs as a `run_in_background` Bash fence that enables bash monitor mode (`set -m`) so teardown can reap the whole reviewer process group. As a side effect, bash emits job-control messages (`[1] &lt;pid&gt;` on launch, `[1]+ Done` on every subprocess exit) that the Claude Code harness converts into empty-output `&lt;task-notification&gt;` events. Because the plan-review fence runs for a long time (median ~1h, max 2:26:02 across committed logs; 83/91 runs exceed 10 minutes), `set -m` fires a spurious notification on every reviewer subprocess exit over that window. Each notification re-invokes the orchestrator (a full-context turn), producing the "dozens if not hundreds" of money-burning turns the operator observed before intervening. This issue eliminates the SOURCE: drop `set -m` and give the worker its own process group from inside Python via `os.setsid()`, so `kill -- -PGID` still works with zero job-control output.

## Original report

The operator reported repeated episodes where the `/design` (and possibly `/implement`) main agent went into a furious loop processing spurious task-notifications from the review process, each notification costing a turn and therefore money, with dozens to hundreds of turns before manual intervention. Investigation traced the `/design` notifications to bash `set -m` job-control output, not to fabrication by the main agent. The notifications are real harness events triggered by job-control stderr leaking into the background task's output stream.

This issue targets the `/design` SOURCE of those notifications. The complementary `/implement`-side defense and a universal turn circuit-breaker are filed separately.

## Reproduction scenario

1. Run `/design` on any non-trivial issue that exercises the full plan-review panel (Codex + Cursor + Claude reviewers, multiple rounds).
2. Step 3 launches `skills/design/scripts/design-step3-review.sh` with `run_in_background: true`. The script runs `set -m` (line ~393) before backgrounding `python3 cli.py plan-review run`.
3. Over the review window (commonly ~1 hour; up to ~2.4 hours observed), each reviewer subprocess that starts and exits causes bash to emit a job-control message.
4. Each job-control message that reaches the task output stream causes the harness to fire an empty-output (1-line / near-zero-byte) `&lt;task-notification&gt;`.
5. The orchestrator is re-invoked on each notification. Even when it correctly makes no tool call, the turn still re-reads the full context as input tokens.

Cannot be deterministically triggered by a single command; the spurious notification count scales with the number of reviewer subprocess exits, which varies by plan size, round count, and panel composition.

## Expected behavior

Exactly one `&lt;task-notification&gt;` per Step 3 plan-review fence, fired on true completion or bail/cap-hit. This matches the operator's mental model that the review process should notify only on completed or bailed. Zero empty-output job-control notifications.

## Observed behavior

Multiple empty-output `&lt;task-notification&gt;` events fire over the review window, one per reviewer subprocess lifecycle event. Prior mitigations reduced the per-notification cost and the catastrophic probe loop, but the notifications still fire, so each still costs one orchestrator turn. Over a multi-hour wait this accumulates into a large, recurring, avoidable token cost.

## Root cause analysis

`set -m` (bash monitor mode) is enabled in `design-step3-review.sh` (line ~393) SOLELY to place the backgrounded plan-review loop in its own process group, so teardown can call `kill -- -"$_pid"` (line ~363) to reap the entire reviewer subtree. Monitor mode is what makes a backgrounded job a process-group leader. The unavoidable side effect of monitor mode in a non-interactive shell is job-control notification output on subprocess launch and exit.

All prior fixes are mitigation, not source elimination:

- #5240 / #5510 / #5511 (source-side): redirect job-control stderr to `bash-job-control.log`. The current code wraps the whole monitor-mode critical section in `{ ... } 2&gt;"${DESIGN_TMPDIR}/bash-job-control.log"` (line ~465). This is fragile: it depends on bash deferring each deferred job notice to a command boundary that stays inside the redirect scope. When a notice escapes that scope, it reaches the task output stream and fires a notification.
- #5478 / #5506 / #5610 (orchestrator-side): instruct the orchestrator to end the turn without probing on empty-output notifications.
- #4688 / #4725 (hook-side): `hook-bg-poll-guard.sh` denies repeated probes and background recovery waiters.

None of these stop the notifications from FIRING. The only way to drive the count to ~1 is to remove monitor mode. The long review duration is what makes this expensive: committed `timing-ledger.tsv` data shows the plan-review fence runs a median of ~1 hour (max 2:26:02), so the per-subprocess-exit notification count over a single fence is high.

## Suggested fix(es)

Eliminate the notification source by replacing monitor-mode process-group isolation with in-process `os.setsid()`:

1. In `run_main` (`python/larch/review/plan_review.py`), call `os.setsid()` at startup, guarded by a `--new-process-group` flag or env var so unit tests and other callers are unaffected. The worker is launched via `&amp;` from bash, so it is not already a process-group leader and `os.setsid()` cannot raise `EPERM`. After `setsid`, the worker leads its own group and its reviewer children inherit that group id.
2. In `design-step3-review.sh`, drop `set -m` (and the `_step3_review_monitor_was_enabled` / `_step3_review_monitor_enabled_by_wrapper` / `set +m` machinery). Launch the worker with the new flag/env. `$!` is then the worker pid, which equals its process-group id, so `kill -- -"$!"` still reaps the whole reviewer subtree on teardown, cap-hit, and bail.
3. Remove the `monitor-mode-unavailable` hard-fail path (lines ~407-409) since monitor mode is no longer required.
4. Drop the job-control rationale for the wide stderr redirect at line ~465. Keep the dedicated `plan-review-loop-stderr.log` so reviewer-child stderr never reaches the task stream.
5. Verify: exactly one notification per review fence; reviewer subtree fully reaped (no orphan codex/cursor processes) on normal completion, cap-hit, and bail; macOS bash 3.2 process-group semantics hold.

This both removes the entire empty-output notification class at the source and simplifies the script.
