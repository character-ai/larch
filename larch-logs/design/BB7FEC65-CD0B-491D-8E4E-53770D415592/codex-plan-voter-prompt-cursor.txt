# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).

## Summary

The `PostToolUse` anti-read-poll hook keys its **generic-read** counter file by cwd hash only — `state-${cwd_hash}.tsv` (`scripts/hook-anti-read-poll.sh:356`) — while its **task-output** counter is keyed by session hash *and* cwd hash — `state-taskout-${session_hash}-${cwd_hash}-${task_id}.tsv` (line 309). `session_hash` is already computed (line 50) but is not used in the generic key. When two Claude Code sessions share the same cwd, they share the single generic-read counter file, which can (a) **suppress** a legitimate anti-poll reminder for a session that really is polling — letting the model keep polling and burn turns/tokens — and (b) **misfire** a spurious reminder against a session that was not polling. Low severity and narrow (it cannot happen across distinct repo clones), but a genuine token-cost bug, filed on that basis.

## Original report

Surfaced while auditing the recent cross-session hardening work. A prior review flagged this counter's session-scoping omission as "spurious reminder only." On closer inspection the more significant vector is **suppression**, not misfire: because the generic counter increments only on a matching consecutive path+offset and otherwise resets, a foreign same-cwd session's interleaved reads reset the shared counter, so a genuinely-polling session never crosses the fire threshold and its polling is never nudged — which is exactly the token burn the hook exists to prevent.

## Reproduction scenario

Static analysis; the concrete misbehavior requires two Claude Code sessions with the same cwd, which is off larch's normal single-runner-per-repo path. To demonstrate the mechanism:

Suppression (the token-burn vector):
1. Two sessions A and B run with the same cwd (same `cwd_hash`), so both use `state-${cwd_hash}.tsv`.
2. A polls file X (reads `X@offset0` repeatedly, intending to wait for it to change). Left alone, A's count would reach 3 within 30s and fire the reminder.
3. Between A's reads, B reads any different path Y. That write stores `(Y, …, count=1)` — resetting the shared counter (`else` branch, lines 374-377).
4. A's next read of X sees `last_path=Y`, so it too resets to count=1. A never reaches the exact-match fire guard `[ "$count" -eq "$POLL_THRESHOLD" ]` (line 389). A keeps polling un-nudged → continued turns/tokens.

Misfire:
1. Same setup; A and B both read the identical `X@offset0` interleaved.
2. The shared counter climbs across the two sessions and hits 3 while neither read X three times on its own; the reminder fires (mis-attributed) on whichever session's read hit count==3 → one spurious `[system-reminder]` injected.

The existing regression test `scripts/test-hook-anti-read-poll.sh:262` ("distinct session_id buckets do not share counters") demonstrates the intended isolation — but exercises only the task-output path.

## Expected behavior

The generic-read poll counter should be scoped per session (as the task-output counter already is), so one session's reads can neither reset nor advance another session's consecutive-read streak. Each session's anti-poll reminder should fire based solely on that session's own reads.

## Observed behavior

The generic-read counter is shared by all sessions with the same cwd. A concurrent same-cwd session can reset the streak (suppressing a deserved reminder, so real polling continues) or advance it (firing a spurious reminder). The task-output counter does not have this problem because its key includes `session_hash`.

## Root cause analysis

`handle_generic_read_poll` builds `state_file="$state_dir/state-${cwd_hash}.tsv"` (line 356), omitting the `session_hash` that is computed at line 50 and used by the task-output path (line 309). The counter stores only the last `(path, offset, count, first_ts)` and increments only when the new read matches that stored `path+offset` (line 366), resetting to 1 otherwise (lines 374-377). With a shared file, interleaved reads from a second same-cwd session perturb the streak. This is a straightforward keying inconsistency, not a subtle logic error; the fix is to add `session_hash` to the key.

Reachability bound (observation, high confidence): the key still includes `cwd_hash`, and distinct larch clones are separate checkouts at distinct paths, so their `cwd_hash` values differ and their state files are disjoint. The bug therefore cannot occur across distinct clones — only between two sessions sharing one cwd (e.g., two Claude Code sessions started in the same clone directory). larch's single-`/implement` and single-`/design` invariants discourage that, but they are detected, not serialized.

## Token-burn bounds (honest)

- Advisory `additionalContext` only — no deny, no forced turn. A misfire costs roughly one reminder line (~50 tokens).
- The exact-match fire guard limits firing to once per polling burst; it cannot spam every turn.
- The suppression vector's downside (uncaught polling that keeps costing turns) is partially backstopped by the separate `PreToolUse` `hook-bg-poll-guard.sh`, which hard-denies progress/task-output polling during background waits. anti-read-poll is the softer, generic backstop this bug degrades.
- Zero possibility across distinct clones.
