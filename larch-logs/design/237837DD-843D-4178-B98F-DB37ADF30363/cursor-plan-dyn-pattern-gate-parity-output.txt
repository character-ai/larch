**1. [correctness] Empty-merge attestation incompatible with pattern gate**

The plan threads `'^[[:space:]]*### FINDING_[0-9]'` into `dispatch-with-waterfall.sh` ([plan.txt](file:///Users/zhupanov/.cache/larch/sessions/claude-design-larch2-c6yhoD/plan.txt) step 2). The dispatcher applies it with `grep -Eq` on `STATUS=OK` files ([scripts/dispatch-with-waterfall.sh:278-288](scripts/dispatch-with-waterfall.sh)). The orchestrator template explicitly allows successful output with **no** `### FINDING_N:` blocks when the file ends with `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` ([agents/orchestrator-aggregator.md:45-59](agents/orchestrator-aggregator.md)). That attestation-only payload cannot satisfy the proposed pattern, so every phase fails the gate, `DISPATCH_OK` becomes false ([scripts/dispatch-with-waterfall.sh:360-368](scripts/dispatch-with-waterfall.sh)), and step 3 maps to `REASON=dispatch-failed`. `review-core.sh` only stalls on `validation-exhausted` ([skills/review/scripts/review-core.sh:514-558](skills/review/scripts/review-core.sh)), so the `/implement` Tool Failures path is lost for the “all tools agree on empty merge” scenario that today ends in `validation-exhausted` after narrow-trigger validation ([skills/review/scripts/aggregate-findings.sh:793-833](skills/review/scripts/aggregate-findings.sh)).

**Parity checks that did not yield findings**

- **ERE / BRE**: `dispatch-with-waterfall.sh` documents and implements `--require-result-pattern` as ERE via `grep -E` ([scripts/dispatch-with-waterfall.sh:63-75](scripts/dispatch-with-waterfall.sh), [scripts/dispatch-with-waterfall.md:35](scripts/dispatch-with-waterfall.md)). The proposed character classes are valid ERE; this is a correct port of the **mechanism** used by decompose-aggregator, not a copy of the same literal pattern (Recommendation vs FINDING is intentional).
- **FINDING_10+**: `[0-9]` after `FINDING_` still matches `### FINDING_10:` because `grep -Eq` only requires one digit at that position; production logs include FINDING_10+ headings. Not a single-digit-only trap in practice.
- **Agent template leading whitespace**: [agents/orchestrator-aggregator.md:27-28](agents/orchestrator-aggregator.md) shows column-0 `### FINDING_N:`; the validator already `lstrip`s before `_STRICT_FINDING_HEADING` ([skills/review/scripts/aggregate-findings.sh:292-295](skills/review/scripts/aggregate-findings.sh)). Optional `[[:space:]]*` on the gate is decompose-style, not template-required.
- **Cursor narration-only (#2881 motivation)**: Output without `### FINDING_[0-9]` correctly fails the gate and routes through internal phases, matching [scripts/test-dispatch-with-waterfall.sh:300-323](scripts/test-dispatch-with-waterfall.sh).

**[OUT_OF_SCOPE]** Pre-existing mismatch: embedded Python uses `[0-9]+` for block parsing ([skills/review/scripts/aggregate-findings.sh:183-189](skills/review/scripts/aggregate-findings.sh), [246](skills/review/scripts/aggregate-findings.sh)) while `count_finding_blocks` uses a single `[0-9]`; the plan does not claim to fix that and it predates #2881.
