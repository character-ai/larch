## Edge cases

- A reviewer with 3 OOS rows and later in-scope rows must keep the later in-scope rows.
- A reviewer with 4+ OOS rows must not leave numbering gaps among retained rows.
- Two reviewers with 4 OOS rows each should retain 6 total OOS rows (3 per slot/label).
- External reviewer file suffixes like `-phase2`, `-phase3`, and `-retry` still normalize to one reviewer label in `/implement`.
- `/design` cap identity uses manifest slot names, not display labels, so two slots with similar human labels do not collide.
- Prompt-side cap in `rendering.py` / agent bodies and collector-side cap must use the same numeric limit and materiality bar so reviewers are not told to emit rows that will be discarded.

## Failure modes

- Partial `reviewer-templates.md` edits leave three generated agents still uncapped; `generate check` or contradictory prompts follow.
- Hand-maintained agents still saying "report every issue" while also capping OOS at 3 causes vendor token waste until collection drops overflow.
- Updating templates/agents but not `rendering.py` / `_dynamic_agent_body` leaves live external prompts uncapped; mechanical truncation then keeps the first three sidecar rows, not necessarily the most material.
- Counting skipped OOS before the cap can leak incorrect `OOS_COUNT` or sparse `FINDING_N` numbering.
- Capping after writing `findings_file` forces voters to evaluate overflow OOS rows.
- Tests that omit the post-OOS in-scope row can pass while a broken `continue`/`break` drops later in-scope findings.
