## Findings

### 1. Orchestrator-substituted counts are not deterministic (in-scope, important, correctness)

The plan correctly replaces hardcoded `--accepted 0 --rejected 0` and adds durable `self-review-accepted.md`, but Step 8.5 still requires the main agent to grep, compute, and paste integer literals into the Bash fence. `write_self_review_tally()` already accepts arbitrary counts and only forwards them:

```2459:2490:python/review_and_fix.py
    parser.add_argument("--accepted", default="0")
    parser.add_argument("--rejected", default="0")
    ...
        "--accepted", str(accepted),
        "--rejected", str(rejected),
```

The issue root cause is agent non-compliance with SKILL literals (evidence: run `9E341CD7` reported `1/1` while most runs show `0/0`). Swapping literals without server-side counting does not close that gap.

**Minimum-change revision:** count headings inside `write_self_review_tally()` from the two tmpdir artifacts (small Python change, unchanged single-line fence). That removes Step 8.5 orchestrator arithmetic and better matches the issue’s “deterministic accounting” goal.

### 2. No mechanical link between fixes committed and accepted headings (in-scope, important, risk-integration)

Step 4 asks for heading appends; Step 7 commits fixes; Step 8.5/tally only sees headings, not git state. If the agent fixes code but skips `self-review-accepted.md`, the run still completes with `accepted_count=0`.

The plan lists this failure mode but mitigates only with prompt wording. That is the same under-reporting class the issue reports.

### 3. fluff-analysis remains blind to self-review findings ([OUT_OF_SCOPE], latent)

`fluff-analysis.py` loads implement findings exclusively from `review-findings-full.jsonl`, not from `code-review-tally.json`. The plan’s tally-only carve-out (empty JSONL) fixes aggregate tallies and `final-summary.md` for non-zero counts (via existing `_derive_review_line` `accepted+rejected>0` path in `pr_body.py`), but not per-finding fluff analysis. This matches the approved outline non-goals; worth tracking separately if fluff visibility matters.

**Not flagged:** `pr_body.py` self-review zero branch (`"self-review: 0 findings"`) is correct for genuine zero totals; non-zero totals already render as `N/M accepted` without plan changes. Fence-shape constraints (`||` banned in launcher fences) explain why inline `$(grep -c ...)` is awkward, which strengthens the case for Python-side counting rather than orchestrator substitution.
