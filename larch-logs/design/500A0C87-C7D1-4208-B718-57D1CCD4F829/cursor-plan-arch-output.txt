## Findings

**1. [correctness] Missing route-state file is not a read failure** (`skills/design/scripts/design-clarify.sh:78-97`, planned `python/clarify.py`)

Bash only attempts the sidecar when `REPO` is empty and the file exists. A missing `.design-step0-route-state.env` is a no-op, not `route-state-read-failed`. The plan describes failure tokens but does not pin this guard. `phase_driver_read_result_env` raises on a missing path (`python/design_lifecycle.py:45-46`), so a naive port can treat absence as terminal clarify failure.

**2. [architecture] Read path should reuse `phase_driver_read_result_env`** (planned `python/clarify.py`)

`read-result-env.sh` is already a thin delegate to `design read-result-env` → `phase_driver_read_result_env`. New `_load_route_state_repo` / `_read_result_env` parsers in `clarify.py` duplicate tested trust boundaries. Reuse the existing helper; keep a local `_write_result_env` only for writes (as the plan already distinguishes from `design_postplan._write_result_env`).

**3. [correctness] `DESIGN_TMPDIR` must be a directory** (planned `python/clarify.py`)

The plan requires absolute and existing paths but not `is_dir()`. Bash fails on `cd` when the path is a file. Add an explicit directory check before fetch/publish.

**[OUT_OF_SCOPE] 4.** Drop `_build_delegate_pause_args` from the planned helper list; pause argv belongs at the single `pause_save_main` call site.

**[OUT_OF_SCOPE] 5.** Prefer `design_lifecycle._append_failure` over a new `_append_clarify_failure` for staging-warning append parity.
