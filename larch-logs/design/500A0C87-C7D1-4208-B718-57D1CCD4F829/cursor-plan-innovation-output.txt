**1. Fetch failure tokens vs in-process API (correctness)**  
The plan moves fetch to direct `clarify_state()` / `clarify_comment_fetch()` calls. In Bash, `state-read-failed` and `fetch-read-failed` only fire when `read-result-env.sh` cannot parse subprocess stdout (`design-clarify.sh:219-258`). Direct calls raise exceptions or return structs instead. The plan still lists all six fetch failure tokens and tests require each, but gives no mapping from API failures to tokens. That invites wrong statuses or fake parse-failure branches.

**2. DESIGN_TMPDIR canonicalization (correctness)**  
Bash canonicalizes with `pwd -P`. Other design ports use `_require_design_tmpdir` → `resolve()`. The plan only requires an absolute existing directory. Symlinked tmpdir paths can produce non-canonical paths in handoff env files.

**3. stage_failed_clarify vs step0_clarify_hard_halt_main (architecture)**  
These are not interchangeable: different log basenames and different exit semantics (`step0_clarify_hard_halt_main` always returns 0). The plan’s subprocess staging is right; it should explicitly forbid the hard-halt CLI shortcut.

**4–5. [SCOPE-REDUCTION] Reuse existing helpers**  
`phase_driver_read_result_env` and `_append_failure` already cover route/request env reads and warning append. New parallel helpers add ~100+ lines without new behavior.

**6–7. Out of scope**  
Unused `_build_delegate_pause_args` is plan clutter. Missing SESSION_ID warning is minor UX parity, not a ship blocker.
