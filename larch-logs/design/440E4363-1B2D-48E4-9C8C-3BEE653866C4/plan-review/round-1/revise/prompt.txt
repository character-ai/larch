# [BUG] CI fixer lane crashes on every post-reship lineage: stale fixer-rounds.tsv trips the foreign-identity guard (BGJOB_RC=1, operator-bail missing-result)

## Summary

During `/implement` of issue #7000 (run `F438D8FB-D306-4235-8BC8-D201830D887C`, PR #7048), the second Codex CI fixer bgjob (`implement-step8-ci-fixer-1-codex-82ed6c40d30d5a96`) exited with `BGJOB_RC=1` without writing `$BGJOB_DIR/$STEP.merge.env` or a fresh `ci-fixer/fixer-status.env`. `step-8-ci-fixer.sh --finalize` then returned `RESULT=operator-bail REASON=missing-result`, and the operator fixed CI manually.

Code tracing has confirmed the root cause. `fixer-rounds.tsv` persists across fixer lineages, but `_read_rounds` in `python/larch/implement/ci_fixer_lane.py` rejects any row whose run id differs from the current lane's run id. After any fixer round that ends in `reship`, a new CI failure gets a new failed run id, so the next lane's `_persist` deterministically raises `LaneClosedError("rounds file contains duplicate or foreign identity")`. The crash-recovery persist in `main()` hits the same guard, prints `STATUS=closed-failure`, and exits 1. Every multi-lineage CI recovery therefore ends in `operator-bail`, which defeats the autonomous CI-fix loop that the in-run checks design explicitly delegates to (`checks_run_relevant.py:519-534`).

Three secondary defects compound it: the orchestrator contract has no route for `BGJOB_RC != 0`, teardown destroys the crash diagnostics, and the crashed lane had already salvage-committed a real Codex fix that it then failed to report.
