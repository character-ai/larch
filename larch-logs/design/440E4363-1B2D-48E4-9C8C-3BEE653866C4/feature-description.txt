# [BUG] CI fixer lane crashes on every post-reship lineage: stale fixer-rounds.tsv trips the foreign-identity guard (BGJOB_RC=1, operator-bail missing-result)

## Summary

During `/implement` of issue #7000 (run `F438D8FB-D306-4235-8BC8-D201830D887C`, PR #7048), the second Codex CI fixer bgjob (`implement-step8-ci-fixer-1-codex-82ed6c40d30d5a96`) exited with `BGJOB_RC=1` without writing `$BGJOB_DIR/$STEP.merge.env` or a fresh `ci-fixer/fixer-status.env`. `step-8-ci-fixer.sh --finalize` then returned `RESULT=operator-bail REASON=missing-result`, and the operator fixed CI manually.

Code tracing has confirmed the root cause. `fixer-rounds.tsv` persists across fixer lineages, but `_read_rounds` in `python/larch/implement/ci_fixer_lane.py` rejects any row whose run id differs from the current lane's run id. After any fixer round that ends in `reship`, a new CI failure gets a new failed run id, so the next lane's `_persist` deterministically raises `LaneClosedError("rounds file contains duplicate or foreign identity")`. The crash-recovery persist in `main()` hits the same guard, prints `STATUS=closed-failure`, and exits 1. Every multi-lineage CI recovery therefore ends in `operator-bail`, which defeats the autonomous CI-fix loop that the in-run checks design explicitly delegates to (`checks_run_relevant.py:519-534`).

Three secondary defects compound it: the orchestrator contract has no route for `BGJOB_RC != 0`, teardown destroys the crash diagnostics, and the crashed lane had already salvage-committed a real Codex fix that it then failed to report.

## Confirmed root cause

All anchors verified on current `main`.

1. Each fixer lane persists one row into a shared ledger: `_persist` writes `fixer-rounds.tsv` in the handoff dir (`python/larch/implement/ci_fixer_lane.py:547`, `config.CI_FIXER_ROUNDS_FILE` at `python/larch/core/config.py:847`). The handoff dir is the run-wide `$IMPLEMENT_TMPDIR/ci-fixer` (`skills/implement/scripts/step-8-ci-fixer.sh:76`). Nothing clears or rotates the file, and `ci_fixer_lane.py` is its only consumer.
2. `_read_rounds` (`ci_fixer_lane.py:495-511`) raises `LaneClosedError("rounds file contains duplicate or foreign identity")` when any existing row's run id (column 3) differs from the lane's run id (line 507).
3. Lineages are keyed by `(MODE, RUN_ID)` (`step-8-ci-fixer.sh:166-167`). A `reship` whose CI fails again always yields a new failed run id, hence a new lineage whose attempt 1 reads the previous lineage's rows. Both observed lanes were `ATTEMPT=1` with different step suffixes, which matches exactly.
4. `_persist` calls `_read_rounds` before writing anything (`ci_fixer_lane.py:552`), so the lane dies after `_dispatch` completed, including after `_salvage_uncommitted_fixer_edits` already committed the fixer's edit (`ci_fixer_lane.py:414-453`, salvage-reship path at `:485-490`).
5. The `except` block in `main()` (`ci_fixer_lane.py:622-640`) retries `_persist` with an `operator-bail` result. The retry hits the same guard, so the lane prints `STATUS=closed-failure` and returns `config.EXIT_INTERNAL_ERROR` (= 1, `config.py:20`).
6. The bgjob daemon is not at fault: `_monitor` reaps the child and always writes the bgjob result env with `BGJOB_RC=1` (`python/larch/bgjob/daemon.py:237-270`). The lane-owned `$STEP.merge.env` and a fresh `fixer-status.env` were never written, so `--finalize` fails the guard at `step-8-ci-fixer.sh:105` and emits `RESULT=operator-bail REASON=missing-result`.

The literal `closed-failure` stdout line cannot be re-read because teardown deleted the bgjob logs (work item 3), but every observable matches this path and no other path produces this signature. A daemon budget timeout writes `BGJOB_RC=timeout` and an owner-orphan kill writes `BGJOB_RC=orphaned` (`config.py:259-260`), so `BGJOB_RC=1` is the child's own exit code. A pre-dispatch `LaneClosedError` would have persisted an `operator-bail` result and exited 0 with artifacts present.

## Corrections to the original analysis

- `scripts/bgjob-daemon.sh` does not exist. The daemon is `python/larch/bgjob/daemon.py`, and it behaved correctly.
- `python/larch/implement/ship.py` does not own `fixer-status.env`. `ci_fixer_lane._persist` writes it (`ci_fixer_lane.py:543-588`).
- The complexity-baseline check is not CI-only. `make py-lint` runs it locally via `py-lint-checks-fast` (`Makefile:47-66`). What skips it is the in-run `/implement` composite: `checks_run_relevant.py:519-534` intentionally scopes local checks to ruff/pyright and delegates heavy lints to CI, "handled by the autonomous CI-fix loop". That design makes this crash worse: the CI fixer is the designed owner of exactly this failure class.
- The fixer prompt already directs baseline-ratchet regeneration: `python/larch/agents/_ci_launcher.py:208` tells the fixer to run `python3 python/cli.py lint <lint-name> --write` for ratchet failures and to edit source only for genuinely new violations. A prompt gap is secondary, not primary (work item 4).
- "Retry with the next tier automatically" alone would not have recovered. A fresh `--start` recomputes the identical identity (lineage B is empty, same head and fingerprint, so codex attempt 1 again with the same `STEP`), and the relaunched lane crashes on the same guard. The routing fix depends on the persistence fix.

## Deterministic reproduction

Unit-level: create a handoff dir whose `fixer-rounds.tsv` contains one valid row with run id A; build a lane identity with run id B; call `_persist` (or `main()` with stubbed launchers). Observe `LaneClosedError` from `_read_rounds`, then `STATUS=closed-failure` and exit 1 from `main()`.

End-to-end shape: any `/implement` whose first fixer round ends `reship` and whose reshipped CI fails again. The second lane always crashes; finalize always returns `operator-bail missing-result`.

## Work items

1. **Fix cross-lineage rounds poisoning (primary).** Make prior-lineage rows non-fatal in `_read_rounds` / `_persist` (`ci_fixer_lane.py:495-511`, `:543-588`). Options: filter rows to the current run id while keeping duplicate-attempt rejection within that run id, or scope the ledger per lineage (`fixer-rounds-<lineage-key>.tsv`, mirroring `lineage-$LINEAGE_KEY.tsv` at `step-8-ci-fixer.sh:167`). Preserve the integrity intent: same-run-id duplicate attempts and malformed rows still fail closed. The `main()` recovery persist must succeed in the same situation. Fix the input contract rather than adding a reason-string special case: the ledger is cross-lineage history that the guard treats as single-lineage state.
2. **Define the `BGJOB_RC != 0` route.** `skills/implement/references/ship-pr-ci-fix.md` waterfall item 5 requires `BGJOB_RC=0` before finalize and says nothing about non-zero, so the orchestrator improvises (here it called finalize and got `operator-bail missing-result` despite untried tiers). Decide and document the route, for example: finalize gains a crashed-lane mode that records the crashed attempt in the lineage and emits `RESULT=retry-next-tool` while tiers remain, or item 5 gains an explicit non-zero branch. Keep the single-wait-owner and no-evidence-reads rules intact.
3. **Preserve crash diagnostics.** The daemon captured the lane's output at `$IMPLEMENT_TMPDIR/bgjob/<step>.stdout.log` / `.stderr.log` (`python/larch/bgjob/model.py:126-135`, `daemon.py:280-297`), but `implement-finalize teardown` deletes the tmpdir and no flush copies fixer artifacts into the committed run log; run `F438D8FB` contains none. Preserve a bounded, redacted diagnostic (log tails plus the launch envelope) on any non-`reship` lane outcome. Constraint: `ship-pr-ci-fix.md` forbids the main agent from reading lane transcripts and evidence, so preservation must be an automated copy inside the Python path, not orchestrator reads.
4. **Optional prompt hardening.** Evaluate naming `complexity-baseline` in the `_ci_launcher.py:208` ratchet examples, since metric-bump regressions like this incident are mechanically fixed by `make regen-complexity-baseline` (`Makefile:89-92`). Low priority: with item 1 fixed, the waterfall reships and the next lineage sees a shard-1-only failure with the generic regen guidance already in the prompt.
