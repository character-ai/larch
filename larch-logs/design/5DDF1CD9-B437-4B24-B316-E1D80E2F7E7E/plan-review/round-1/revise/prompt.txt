# [BUG] Ship driver initial CI wait still hangs ~30 min silently when no CI run starts

## Summary

The `/implement` ship driver's **initial** CI wait (and other `empty_checks_grace=0` poll paths) can still hang silently for ~30 minutes when no CI run ever starts for the PR head. PR #4872 (issue #4867) fixed the analogous hang only for **head-changing** monitor re-entries (after a CI-fix or rebase push); the very first CI wait after PR creation, and any `ci wait` / `ci status` CLI invocation, still poll the full `CI_WAIT_TIMEOUT_SEC` (1800s) budget with no `&lt;task-notification&gt;` and no state advance when checks stay empty.

## Original report

&gt; 30 minute silent hang

Reported immediately after #4867 / PR #4872 landed. That fix bounded the post-fix-push re-entry with `CI_WAIT_POST_FIX_EMPTY_CHECKS_GRACE_SEC` (120s) but deliberately scoped out the initial CI wait, leaving the same 30-minute silent-hang failure mode reachable on the first poll.

## Reproduction scenario

Primary (environment-dependent, like #4867):
1. Run `/implement --merge` so the ship driver creates a PR and enters the merge loop at `PHASE=ci-initial`.
2. If GitHub does not start a CI run for the new PR head (e.g. the `pull_request: opened` workflow is dropped / skipped / never registers checks — the same GitHub-side flakiness #4867 observed for `synchronize`), `gh pr checks` returns zero checks.
3. The first `ci_monitor.monitor()` call uses `empty_checks_grace=0` (see Root cause), so zero checks classify as `pending` and `poll_ci` polls the full ~30-min budget before bailing `poll-budget-exhausted`, emitting no `&lt;task-notification&gt;` and not advancing `ship-pr-state.sh`.

Synthetic (monitor half, deterministic): drive `python/ci_monitor.poll_ci(..., empty_checks_grace=0)` (or `python/cli.py ci wait` with its default `--empty-checks-grace 0`) against a branch head that has zero associated check runs; confirm it classifies `pending` and polls to `CI_WAIT_BAIL_POLL_BUDGET_EXHAUSTED` rather than detecting "no run will start". Contrast with `empty_checks_grace&gt;0`, which yields `NO_CHECKS` after one grace sleep.

## Expected behavior

- The initial CI wait should confirm a CI run actually started for the PR head within a short bounded window before committing to the long poll loop, mirroring the post-fix-push path from #4867.
- If no run appears in that window, fail loudly to a recoverable stall (or re-trigger) rather than polling a non-existent run for the full budget.
- In all cases the CI-monitor/ship path should emit a `&lt;task-notification&gt;` / advance `ship-pr-state.sh` so the orchestrator is never left silently blocked for ~30 minutes.

## Observed behavior

- On the first merge-loop iteration of a fresh run, `_seed_last_monitored_head` returns the current HEAD, so `current_head == last_monitored_head` and `post_push_grace` evaluates to `0`.
- With `empty_checks_grace=0`, `_resolve_checks_status` returns `pending` (not `NO_CHECKS`) for an empty rollup, so `decide` returns `wait` and `poll_ci` loops up to `max_polls` (1800/10 = 180).
- The only output during the wait is per-poll `ci_monitor: poll N/180 pending ...` lines written to stderr (captured by the background task, not surfaced as a notification). After ~30 minutes the loop bails `poll-budget-exhausted`.

## Root cause analysis

The #4867 fix activates the bounded `NO_CHECKS` grace **only** when the head changed since the last poll: `post_push_grace = CI_WAIT_POST_FIX_EMPTY_CHECKS_GRACE_SEC if last_monitored_head and current_head and current_head != last_monitored_head else 0`. On the initial wait there is no prior head to differ from (the seed equals the current HEAD), so grace is `0`. `_resolve_checks_status` only returns `NO_CHECKS` when `empty_checks_grace &gt; 0`; otherwise empty checks are indistinguishable from `pending`, and `poll_ci` polls to the full timeout. The same `grace=0` default applies to the `ci wait` / `ci status` CLI (`python/ci.py` `--empty-checks-grace default=0`), so those paths share the failure mode.

This is intentional scoping from #4867 (the initial wait legitimately needs patience for the first run to attach, so a blunt bounded grace risks false bails). The residual is that the initial wait has **no** bounded "did a run start at all?" detection and **no** periodic operator-visible signal, so a genuinely runless head hangs the full budget silently.

## Evidence

- `python/ship.py` `_seed_last_monitored_head` returns `current` (entry HEAD) on a fresh run (no persisted `LAST_MONITORED_HEAD`, `fix_attempts==0`, not `ci_fix_rebase_pending`); the merge loop then computes `post_push_grace = 0` because `current_head == last_monitored_head`.
- `python/ci_monitor.py` `_resolve_checks_status` returns `("pending", None)` for an empty rollup when `empty_checks_grace == 0`, and `("NO_CHECKS", None)` only when `empty_checks_grace &gt; 0`.
- `python/ci_monitor.py` `poll_ci` loops to `max_polls = ceil(CI_WAIT_TIMEOUT_SEC / CI_WAIT_POLL_INTERVAL_SEC) = 180` and only `_warn_stderr`s each poll; the NO_CHECKS early-bail at the top of the loop is unreachable with `grace=0`.
- `python/config.py`: `CI_WAIT_TIMEOUT_SEC = 1800`, `CI_WAIT_POLL_INTERVAL_SEC = 10` (→ ~30 min), `CI_WAIT_EMPTY_CHECKS_GRACE_SEC = 0`.
- `python/ci.py`: both `ci wait` and `ci status` argparsers set `--empty-checks-grace default=0`.
- Prior art / context: issue #4867, PR #4872 (`b02bf3b44`), which bounded only the post-push re-entry and persists `LAST_MONITORED_HEAD` for resume.

## Affected files

- `python/ship.py` - the merge loop's initial CI wait passes `empty_checks_grace=0`; needs a bounded initial-run-start window (or a startup-grace seed) and a guaranteed signal on no-run.
- `python/ci_monitor.py` - `poll_ci` / `_resolve_checks_status` treat empty checks as `pending` (poll to timeout) whenever `grace=0`; could surface a distinct time-bounded "no run started" condition independent of the caller's grace, and emit a periodic completion/stall signal.
- `python/ci.py` - `ci wait` / `ci status` default `--empty-checks-grace 0`, so manual/cron callers share the hang.
- `python/config.py` - houses the budget/grace constants; a dedicated initial-start window constant may belong here.

## Suggested fix(es)

- Apply a bounded "did the initial run start?" window to the first ship-driver CI wait too (a separate, possibly longer, initial-start grace than the 120s post-fix value, since first runs may take longer to attach), then fail loudly to a recoverable stall (or re-trigger) if none appears.
- Alternatively, have `ci_monitor` distinguish "zero checks across a bounded startup window" from "pending" regardless of the caller's `empty_checks_grace`, and bail/signal on it.
- Ensure `poll_ci` emits a periodic operator-visible progress/stall signal (or advances `ship-pr-state.sh`) during long waits rather than only stderr breadcrumbs, so a 30-min wait is never fully silent.
- Consider a non-zero default `--empty-checks-grace` (or an explicit `--require-run-start` window) for the `ci wait` CLI.

## Open questions

- Should the initial-start window re-trigger CI automatically or stall to the operator with a clear message (same open question as #4867, but the initial-wait tradeoff differs: false bails here abort a PR that simply had slow CI startup)?
- What initial-start grace value balances "first run may take a minute or two to attach" against "detect a truly runless head quickly"? Should it be larger than `CI_WAIT_POST_FIX_EMPTY_CHECKS_GRACE_SEC`?
- Should the `ci wait` / `ci status` CLI default change, or stay opt-in to avoid surprising existing callers?
