Reviewing the ship merge loop and CI monitor code to draft a revised plan that addresses the accepted findings.
## Plan

Implement a bounded initial CI startup window in the ship merge loop only, using **poll-based** empty-check detection so the happy path keeps 10s polling while runless heads bail within ~300s.

Do not pass the 300s window through `empty_checks_grace` blocking sleep. That would sleep once on the first empty rollup and delay detection of slow-starting checks. Add a separate startup-deadline parameter in `ci_monitor` instead.

Use the existing `NO_CHECKS` bail path. Do not add periodic progress signals. Do not change CLI defaults.

## Approach

- Add `CI_WAIT_INITIAL_EMPTY_CHECKS_GRACE_SEC = 300` in `python/config.py`.
  - Name matches the post-fix constant family.
  - Semantics are a **poll-based startup deadline**, not a blocking `gather_status` sleep.
- In `python/ci_monitor.py`, add `empty_checks_startup_deadline_sec: int = 0` to `poll_ci()` and `monitor()`.
  - When `> 0`, keep calling `gather_status(..., empty_checks_grace=0)` on the normal `CI_WAIT_POLL_INTERVAL_SEC` loop.
  - On each `pending` result, probe whether the checks rollup is still empty (via existing `checks_status(..., empty_checks_grace=0)` or equivalent).
  - If checks appear, disable the startup deadline for the rest of that monitor call and continue normal polling.
  - If the rollup stays empty and elapsed time reaches `empty_checks_startup_deadline_sec`, bail `NO_CHECKS` with `CI_WAIT_BAIL_NO_CHECKS_OBSERVED`.
  - Leave `_resolve_checks_status` blocking-sleep behavior unchanged for `empty_checks_grace > 0` (post-fix path).
- In `python/ship.py`, compute monitor params once per loop iteration:
  - **Head changed:** `empty_checks_grace = CI_WAIT_POST_FIX_EMPTY_CHECKS_GRACE_SEC`, `empty_checks_startup_deadline_sec = 0`.
  - **First bounded-empty-checks opportunity:** `empty_checks_grace = 0`, `empty_checks_startup_deadline_sec = CI_WAIT_INITIAL_EMPTY_CHECKS_GRACE_SEC`.
  - **Otherwise:** both `0`.
- Track a merge-loop-local one-shot flag `initial_startup_deadline_available`.
  - Initialize `True` when `iteration == rebase_count == fix_attempts == transient_retries == 0` at merge-loop entry (covers fresh runs and zero-counter cold resumes).
  - Clear it to `False` immediately after each `ci_monitor.monitor()` return, regardless of outcome.
  - Do not key ongoing eligibility on all-zero counters alone. `evaluate_failure` / `ci-still-in-progress` can return `OK` without incrementing counters.
- Replace inline `post_push_grace` with a helper (for example `_empty_checks_params_for_monitor(...)`) that returns `(empty_checks_grace, empty_checks_startup_deadline_sec)`.
  - Bind both values once.
  - Pass them to `monitor()`.
  - Reuse the **same bindings** in the `NO_CHECKS` `terminal_last_head` guard:
    - `bounded_empty_checks = empty_checks_grace > 0 or empty_checks_startup_deadline_sec > 0`
    - Keep persisting `pre_monitor_head` when bail detail is `no-ci-checks-observed` and `bounded_empty_checks` is true.
- Keep `python/ci.py` unchanged.
  - `ci wait` and `ci status` keep `--empty-checks-grace default=0`.
  - No new CLI flag for the startup deadline in this change.
- Preserve #4867 behavior.
  - Head-changing re-entries still use the 120s post-fix blocking grace.
  - `LAST_MONITORED_HEAD` resume seeding for post-push `NO_CHECKS` stalls stays intact.

## Edge cases

- **Post-fix push:** Keep 120s blocking grace when HEAD changed; startup deadline `0`.
- **Initial open PR / zero-counter cold resume:** First monitor call only gets the 300s poll-based startup deadline.
- **Monitor returns OK without counter bumps:** Second and later monitor calls get no initial deadline because the one-shot flag cleared.
- **Slow but present checks:** Checks appearing within the window are detected on the next 10s poll; no full-window blocking sleep.
- **Truly runless head:** Bails `NO_CHECKS` within ~300s instead of ~30 min silent poll exhaustion.
- **Manual CLI callers:** No behavior change; defaults stay `0`.
- **Other `empty_checks_grace=0` callers:** No behavior change unless they opt into the new kwarg.

## Failure modes

- If startup-deadline logic lives in `_resolve_checks_status` instead of `poll_ci`, happy-path latency regresses to one long sleep. Keep deadline accounting in the poll loop.
- If the one-shot flag is omitted or keyed only on all-zero counters, later monitor calls may repeat the 300s window after benign `OK` returns. Clear the flag after every monitor call.
- If the `NO_CHECKS` guard still references `post_push_grace` after rename, expect `NameError` or lost `LAST_MONITORED_HEAD` seeding. Reuse the same helper bindings for monitor and terminal guard.
- If terminal `LAST_MONITORED_HEAD` handling narrows to post-fix grace only, #4867 resume after post-push stalls can regress. Preserve and test `pre_monitor_head` persistence.

- Run `python3 -m pytest python/test_ci.py` to confirm CLI defaults unchanged.
