# [BUG] code-review-tally.json reports only round 1 for multi-round /implement runs

## Summary

The committed `larch-logs/implement/&lt;RUN_ID&gt;/code-review-tally.json` reports `rounds: 1` and an `accepted_count` equal to **round 1's** accepted total, even when the `/implement` Step 5 review loop actually ran multiple rounds. The per-round `round-*/` directories are committed correctly and show the true multi-round results, so the committed run log is internally inconsistent: the round directories say N rounds, the summary tally says 1. The multi-round review loop itself works correctly. This is a reporting/accounting bug only. It propagates into `final-summary.md` ("Code review: X/Y accepted") and any consumer that reads the tally (`audit-runs`, `/fluff-analysis`, token/cost summaries), under-reporting how much review work happened. This bug directly caused a misdiagnosis that the `/implement` review panel was producing near-zero accepted findings, when multi-round review was in fact accepting tens of findings per run.

## Original report

Regular `/implement NNNN` runs appear to do only a single review round, and the committed code-review tally shows very low or zero accepted counts. Investigation of committed run logs shows the review loop actually ran multiple rounds with many accepted findings, but `code-review-tally.json` records `rounds: 1` and only round 1's `accepted_count`. The regression appears to start around v50.1.x: every 50.1.x and 51.x regular run records `rounds: 1` regardless of how many `round-*` directories were committed, while older versions recorded multi-round counts correctly.

## Reproduction scenario

1. Run a regular (non-`--emergency`, non-`--self-review`) `/implement &lt;issue&gt;` where Step 5 code review runs 2+ rounds (round 1 accepts findings, coder applies them, the loop continues).
2. After the run, inspect the committed run log under `larch-logs/implement/&lt;RUN_ID&gt;/`:
   - Count `round-*` directories (each holds `findings-classification.tsv`, `voting-tally.md`, `review-round-summary.md`).
   - Read `code-review-tally.json` `rounds` and `accepted_count`.
3. Observe: number of `round-*` directories is greater than `code-review-tally.json.rounds` (which is `1`), and `accepted_count` equals round 1's accepted total rather than the cumulative across rounds.

Concrete already-committed example: run `03510CED-5FA7-400E-A0E7-568786249E7B` (issue #4533, larch 51.0.0) has five `round-*` directories but `code-review-tally.json` says `rounds: 1, accepted_count: 14`.

## Expected behavior

`code-review-tally.json` should be consistent with the committed `round-*` directories:

- `rounds` equals the total number of review rounds run (= number of committed `round-*` dirs).
- `accepted_count` / `rejected_count` reflect the documented cumulative-across-rounds semantics (or, if final-round semantics are intended, that should be documented and consistent), not round 1 only.
- `final-summary.md` "Code review: X/Y accepted" should reflect the same totals.

## Observed behavior

For multi-round regular runs since ~v50.1.x, `code-review-tally.json` is frozen at round 1: `rounds: 1` and `accepted_count` = round 1's accepted total, regardless of how many rounds actually ran. The `round-*` directories committed in the same run log contradict it.

## Root cause analysis

Located but not fully traced (stated as inference where uncertain):

- `python/review_and_fix.py` `flush_review_batches()` writes `code-review-tally.json` via `voting write-tally --rounds &lt;rounds&gt; --accepted &lt;derived_accepted&gt; ...` with `--mode replace`. `derived_accepted` is computed by `_derive_code_review_tally(findings_file)` over the composed `review-findings-full.jsonl`.
- The per-round flush inside `_run_round()` calls `flush_review_batches(..., round_num, total_accepted, total_rejected, ...)` every round.
- The symptom (committed tally frozen at round 1) indicates that rounds 2..N flushes do **not** update the committed `code-review-tally.json`, even though `flush_round_log_after_coder()` commits each `round-*` directory correctly each round. The most likely cause is a flush/commit-ordering interaction: the tally batch is staged in `$IMPLEMENT_TMPDIR/larch-logs` and only the round-1 version lands in the committed repo log, while the round directories are committed incrementally through a different path. This may be compounded by the known in-progress committed-snapshot behavior (runs commit a pre-final snapshot). The exact "which flush lands in the committed log" needs confirmation by tracing the commit path for the tally batch versus the round directories.

## Evidence

- Run `03510CED-5FA7-400E-A0E7-568786249E7B` (issue #4533, larch 51.0.0). Five committed round directories, each with real findings + `voting-tally.md`:
  - round-1: 30 findings, 14 accepted, 3 rejected
  - round-2: 43 findings, 8 accepted, 5 rejected
  - round-3: 27 findings, 11 accepted, 9 rejected
  - round-4: 29 findings, 11 accepted, 5 rejected
  - round-5: 25 findings, 15 accepted, 2 rejected
  - Total: ~59 accepted across 5 rounds. But `code-review-tally.json` says `rounds: 1, accepted_count: 14` (= round 1 only).
- Other recent committed runs (tally `rounds` vs actual `round-*` dir count): issue #4170 = 3 dirs but `rounds=1`; #4016 = 2 dirs but `rounds=1`; #4427 = 2 dirs but `rounds=1`. Issue #4503 = 2 dirs and `rounds=2` (correct), so it is not 100% always wrong.
- Regression window (distribution of `code-review-tally.json.rounds` for regular runs, by version era; "multi-round %" = share of runs with `rounds &gt; 1`):
  - `&lt;=40`: 48%, `42-45.x`: 40%, `47.x`: 57%, `49.x`: 53%, `50.0.x`: 30%
  - `50.1.x`: 0% (9 runs, all `rounds=1`), `51.x`: 8% (only 1 of 12 with `rounds &gt; 1`)
  - Older eras reported multi-round correctly; starting ~v50.1.x the field is effectively pinned at 1. Bisecting commits landing in v50.1.0 / v50.1.x that touched the Step 5 tally flush path is the fastest way to localize.

## Affected files

- `python/review_and_fix.py` — `flush_review_batches()` (writes `code-review-tally.json`), the per-round flush calls inside `_run_round()`, and the terminal Step 5 flush callers. Primary suspect for the round-count and accepted-count freezing.
- `python/voting.py` — `write-tally` verb (records `rounds`/`accepted`/`rejected` into the tally JSON). Consumer of the (incorrect) `--rounds` / `--accepted` values.
- `docs/run-logs.md` — `code-review-tally.json` `rounds` / `accepted_count` semantics; should be made explicit (cumulative vs final-round) so the fix has a contract to satisfy.
- `skills/implement/scripts/write-final-report.md` / final-summary rendering — reads the tally and prints "Code review: X/Y accepted"; inherits the under-report.

## Suggested fix(es)

- Ensure the terminal Step 5 flush re-writes `code-review-tally.json` with the cumulative `rounds_completed` and cumulative accepted/rejected, and that this terminal flush is the copy that lands in the committed log (re-commit the tally batch after the loop completes, not only after round 1).
- Add a regression assertion: for a 2+ round run, committed `code-review-tally.json.rounds` equals the number of committed `round-*` directories, and `accepted_count` matches the cumulative round summaries.
- Decide and document the intended `accepted_count` semantics for multi-round runs (cumulative across rounds vs final round) in `docs/run-logs.md`, then make the writer conform.

## Open questions

- Intended semantics of `accepted_count` for multi-round runs: cumulative across all rounds, or the final round only? The fix and the regression test depend on this decision.
- Is the freeze caused by the per-round flush staging vs the commit path (tally batch not re-committed after round 1), or by a stale `rounds` argument passed at the terminal flush? Needs a trace of one live multi-round run to confirm.
- Does the same round/accepted under-reporting affect `/review` (standalone) tallies, or only `/implement` Step 5?

## Proposed Design Outline

### Goals
- Report true multi-round results in `code-review-tally.json`: `rounds` = committed `round-*` count; `accepted_count` / `rejected_count` = cumulative across rounds.
- Stop the tally write from silently freezing at round 1.
- Document the cumulative semantics as a shared contract.

### Non-goals
- Backfilling already-committed historical tallies.
- Changing tally consumers (`audit-runs`, `/fluff-analysis`, token/cost summaries).
- A separate standalone `/review` test (the shared-writer fix covers it).
- Touching the `review-findings-full.jsonl` path (already correct).

### Approach sketch
- Root cause: `voting write-tally` calls `_die` on code-review body header-validation failure before writing; the body is discarded for code-review, so the gate only harms.
- Make code-review tally-body validation non-fatal: warn, then write the record. Keep the existing cumulative count derivation and the explicit round count.
- Leave the plan-review tally path untouched (it stores and uses its body).
- Add a 2+ round regression test: written tally `rounds` == round-dir count and counts == cumulative, even when a body line trips the old gate.

### Surfaces in scope
- `python/voting.py` — `write_tally_main` code-review validation gate.
- `docs/run-logs.md` — cumulative-semantics contract.
- `python/test_voting.py`, `python/test_review_and_fix.py` — regression coverage.

### Open questions
- None.
