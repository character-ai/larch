# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed").

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more
flexible / future-proof," "best practice," "while we're here," "defensive in case," refactors,
renames-for-clarity, added configurability, broadened error handling for inputs the feature
cannot produce, performance / micro-optimization claims (e.g. "redundant I/O", "avoid an extra
call/scan", "micro-cache this") when the feature already meets its stated performance
requirement, and cross-shell / cross-OS / tool-version portability speculation for shells,
platforms, or tool versions the project does not target.

Out-of-Scope is the safe harbor, not the trash. A real finding that fails the necessity gate
belongs on the Out-of-Scope list, where it can still be accepted as a tracked GitHub issue.
Deferring a good idea is the correct outcome, not a loss.

Severity interaction. A Nit can never clear the necessity gate (a Nit is by definition optional).
Neutral rescue is not inline acceptance. A neutral finding with one YES vote is routed to OOS artifacts only when the YES severity is `blocker` or `major`. Single-YES `minor`, `nit`, `uncertain`, missing, or invalid severities stay dropped. Rescued neutrals keep vote-table `Result=neutral`, but classification records `scope=oos`.

necessary, the plan or code would not have passed the earlier round — hold it to gate 2 or 3
(Correctness or Introduced-regression) only.

## Summary

`design-step3-review.sh` fires a `&lt;task-notification&gt;` with valid output (including `LOOP_STATUS=complete`) before the process fully exits and before `_step3_review_guarantee_post_loop_exit` removes `.bg-wait-active`. During the gap between the notification and the process exit, the hook blocks every probe attempt, causing repeated task-notification re-deliveries and wasted turns. The v52.4.9 fix (#6268) ensures `.bg-wait-active` is removed on process exit, resolving the loop when the review completes. However, the early notification creates a window where the loop runs continuously until exit, which can be very long if the review itself is still in progress.

## Original report

root cause of spurious notifications problems, and why the fix we merged just today did not work. Was it not in the larch version running this session?

## Reproduction scenario

1. Start `/design &lt;issue&gt;` that reaches Step 3 plan review with Cursor + Codex active.
2. Step 3 launches `design-step3-review.sh` with `run_in_background: true`.
3. Within ~30 seconds the orchestrator receives `&lt;task-notification&gt;` with the current task output. At this point the review may still be running (Cursor/Codex reviewers active, `plan-review run` not yet done).
4. The orchestrator attempts to probe `.completed/step-3-terminal`; the hook denies access because `.bg-wait-active` is present and PID is alive.
5. Each turn end re-fires the same `taskId` notification.
6. The loop continues until the process exits and `_step3_review_guarantee_post_loop_exit` removes `.bg-wait-active` and writes the sentinel.

In a 14-minute run (Cursor reviewer active for 7+ minutes) this produced 10+ notification re-deliveries and ~6 ScheduleWakeup recovery cycles, burning ~500–1000 tokens.

## Expected behavior

The task notification fires only after the process has fully exited and `.bg-wait-active` has been removed. No re-notification loop occurs during the review.

## Observed behavior

- Task notification fires while the review is still running (confirmed: PIDs 3572/3601/3605/3630 alive at 13+ minutes elapsed when notification shows valid `LOOP_STATUS=complete` output).
- Each turn end re-delivers the same notification (`taskId: byqc6dgqk`).
- Hook denies all probes while `.bg-wait-active` is present and PID is alive.
- Loop continues for the full review duration (~14 minutes in this run).
- Once the process exits, the v52.4.9 fix works correctly: `.bg-wait-active` is removed, `step-3-terminal` sentinel is written, hook releases, and the orchestrator can advance.

## Root cause analysis

**Two-phase timing gap.** The `run_in_background: true` task notification fires when the bash task's stdout is flushed — not strictly when the process exits. In `design-step3-review.sh`, `plan-review normalize-status` writes to stdout while the process is still alive (not yet at the `exit` call). Claude Code's task framework captures that stdout flush and fires the notification. The process then runs `_step3_review_guarantee_post_loop_exit` (the v52.4.9 new trap), removes `.bg-wait-active`, writes the sentinel, and exits. The gap between the stdout flush (notification fire) and the process exit (cleanup completion) is normally very small — but if the review itself is still running when the notification fires, the gap can span the entire review duration.

**How the early notification fires.** `normalize-status` runs and writes its output to the bash process's stdout. The task output file receives `LOOP_STATUS=complete` etc. Claude Code sees the file updated and fires the notification. However, `design-step3-review.sh` hasn't executed the EXIT trap yet (it calls `exit "$_step3_normalize_rc"` after `rm -f "$_plan_review_stdout_file"`). `.bg-wait-active` is still present. The hook blocks all probes.

**Why the v52.4.9 fix (#6268) did work.** The fix added `_step3_review_guarantee_post_loop_exit` as the post-loop EXIT trap, which removes `.bg-wait-active` and writes the sentinel. This ran correctly when the process exited, breaking the loop. Confirmed: `.bg-wait-active` gone, `step-3-terminal` present after exit.

**Why it appeared "not to work" during the live run.** The fix applies at process exit. During the ~14-minute review, the process was alive, the marker correctly present, and probes correctly blocked. The fix couldn't run until the review completed. This gave the appearance of the fix failing, but it was actually waiting for the review to finish.

**The remaining gap.** There is a brief window between `normalize-status` writing stdout (notification fires) and the process exit (cleanup runs). For fast reviews this window is milliseconds. For slow reviews (Cursor taking 7+ minutes), the window equals the remaining review time. The re-notification loop during this window is an efficiency bug, not a correctness bug — it resolves correctly when the process exits.

## Suggested fix(es)

1. **No code change needed for correctness.** The v52.4.9 fix resolves the loop at process exit. For fast reviews the window is negligible.

2. **Efficiency improvement (optional).** To reduce token burn during the wait window, the hook could distinguish "process alive, review in progress" (normal wait — end turn silently) from "process dead, marker stale" (the pre-v52.4.9 bug — probe allowed). If `kill -0 $PID` fails, the hook could allow a single probe even if `.bg-wait-active` is present. But this may already be done by the hook's liveness check.

3. **Document the expected loop duration.** Add a note to `design-background-wait.md` that the re-notification loop during a long review is expected behavior; the orchestrator should end turns silently on repeated identical notifications (per the `#5418` fingerprint rule) rather than scheduling wakeups, which can compound the turn count.
