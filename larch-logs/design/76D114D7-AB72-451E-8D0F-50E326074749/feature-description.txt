[DESIGNING] [BUG] Cursor aggregator emits self-contradicting output, repair-phase synthesizes empty attestation, losing all input findings and stalling review with `round-failed-complete`

## Symptom

In an `/implement --merge 2395` run on `sergey-zhupanov/similar-to-issue-2382-try-to-have-ship-p-2395` (RUN_ID `996FF59E-D201-42A5-BE34-92CB639A9F2A`), Step 5 review wrapper returned:

```
STEP5_REVIEW_STATUS=stall
STALL_TRACKING=true
STALL_REASON=round-failed-complete
ROUNDS_COMPLETED=1
FINAL_ROUND_NUM=1
FINAL_REVIEW_AND_FIX_STATUS=complete
CODER_STATUS=skipped
EFFECTIVE_ROUND_CAP=5
```

The round structurally completed with 0 accepted / 0 rejected / 0 exonerated, **despite the six static Cursor specialists producing 28 raw findings collectively**. Run was forced down the stall path → Step 16 → Step 17 → Step 18 with `[STALLED]` rename. No PR created; no merge attempted.

## Root cause

The Cursor aggregator (single slot, `cursor` tool) was handed an `aggregator-prompt.md` containing 29 input `### FINDING_N:` blocks under `## Raw reviewer findings (input)`. The prompt's output contract requires either:

1. Emit one or more `### FINDING_N:` merged blocks (no attestation token), or
2. When all input findings are subsumed / duplicates: emit optional preamble + final line `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` (machine-readable empty-merge marker).

The aggregator model's actual `aggregator-output.txt` was a **self-contradicting** 2-paragraph file:

```
Aggregating the supplied reviewer slots into merged findings. We have multiple `### FINDING_N:` blocks, so we do not include `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED`.



LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED
```

The preamble explicitly **claims** finding blocks are present (so the attestation token must not appear), then the body emits the attestation token anyway and contains **zero** `### FINDING_N:` blocks.

The repair pass (`aggregator-repair.sh` / `aggregate-validate.py`) detected the broken state and emitted `ATTESTATION_SYNTHESIZED=true unique_input_reviewers=5 input_slots=5 input_findings=28` — i.e., it **synthesized an empty-merge attestation as recovery**. This destroys the 28 input findings: voting tallied them as zero, scout reported `validation-failed`, and the wrapper marked the round `round-failed-complete`.

## Impact

Empty attestation synthesis on a degenerate aggregator output is **incorrect recovery** because:

- The aggregator's preamble explicitly asserted "we have FINDING_N blocks" — which is the model's own claim that this is NOT an empty-merge case. Synthesizing the empty-merge marker contradicts the model's stated intent and the input data (28 actual findings).
- At least one of the lost findings in this run flagged a **real bug in the implementation under review**: `cursor-specialist-correctness-output.txt` reported `with_transient_retry` returns on rc=0 before consulting the merge envelope predicate, breaking acceptance criterion #3 (envelope-aware retry) in the issue's plan. That finding was silently discarded by the synthesis, then the wrapper stalled the run rather than failing it loudly.
- This converts a recoverable reviewer-output-format problem into a session-terminating stall with no actionable diff to retry on.

## Suggested fix directions (one of)

1. **Reject the output instead of synthesizing.** In the repair pass, detect "input had ≥1 `### FINDING_N:` block AND output has 0 blocks AND output preamble does not match empty-merge intent" → treat as `aggregation-failed` and re-prompt the aggregator with a stricter "your previous output contradicted itself; emit the FINDING_N blocks" framing. Re-prompt budget could be 1 retry.
2. **Strict empty-merge intent check.** Before synthesizing attestation, require the aggregator's preamble (or absence thereof) to be consistent with empty-merge (e.g. preamble must not contain the substring `### FINDING_N:` as a claim of presence). On mismatch, return `aggregator-output-malformed` and let the wrapper fail-loudly rather than synthesize a falsely-empty result.
3. **Carry inputs through on degenerate output.** As a last-resort recovery, when the aggregator output is degenerate and the repair phase cannot fix it, pass the input `### FINDING_N:` blocks through unchanged (skipping merge) so voting and Step 5 can still operate on the raw findings. This trades aggregator deduplication for run-completion when aggregation itself is the failure point.

Option 1 is the cleanest because it preserves the "aggregator must produce valid output" invariant; Option 3 trades quality for liveness; Option 2 is a structural assertion gate that hardens against this exact pathology.

## Acceptance criteria for the fix

1. Given an aggregator output where preamble claims FINDING_N blocks are present but body contains zero FINDING_N blocks, the repair pass must NOT synthesize `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED`. Instead it must either re-prompt the aggregator (Option 1), surface an explicit `aggregator-output-malformed` failure (Option 2), or pass input findings through (Option 3).
2. The Step 5 wrapper's `round-failed-complete` stall reason must not fire when the underlying issue is an aggregator output format problem with recoverable input findings; either the round succeeds with the input findings carried through, or it fails loudly with a distinct stall reason naming the aggregator pathology.
3. New regression test exercising the degenerate-aggregator-output path (input has FINDING blocks → aggregator emits attestation token + contradictory preamble → repair must not silently synthesize empty attestation).
4. No regression: legitimate empty-merge cases (aggregator's input had 0 finding blocks, or all were genuinely duplicates) still synthesize attestation correctly.
