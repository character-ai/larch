## Approach

Confidence: high, based on direct inspection of the dispatcher, launchers, token report builder, and cost analysis tests.

The root cause is in the live external-launcher path. `run-dispatch` no longer emits the token mark for external Codex or Cursor when the binary is expected, and `launch_codex_implement_main` / `launch_cursor_implement_main` do not emit it either. Restore the mark in both launchers after the token-budget preflight passes and before the external tool can record usage.

Keep the mark best-effort. If the mark command fails, continue the launch, but write a warning to the launcher sidecar and the implement execution issues log when `IMPLEMENT_TMPDIR` is available. Do not mark on `cap_hit`, because no implementer launch occurs.

Ownership split stays explicit:

- Dispatcher `_maybe_mark_step2_telemetry` continues to emit the Step 2 **token** mark only on Claude fallback and binary-missing external routes via `_step2_token_mark_eligible`.
- External launchers own the Step 2 **token** mark when `CODEX_BINARY_FOUND=true` or `CURSOR_BINARY_FOUND=true`.
- Dispatcher timing-mark behavior is unchanged.

Also harden consumers. Treat `raw=codex_implement` and `raw=cursor_implement` ledger rows as explicit Step 2 implementer rows when a Step 2 mark is absent or misplaced. This keeps new token reports and cost analysis from silently folding coder work into Step 0.

## Edge cases

- If `IMPLEMENT_TMPDIR` is missing, do not fail the launcher. Record a local warning in the sidecar.
- If the token ledger cannot be resolved or written, keep launching. The user requested best-effort marks, not dispatch aborts.
- If a valid Step 2 mark already encloses implementer rows, do not synthesize a duplicate Step 2 row.
- If historical committed reports are already wrong, leave them unchanged. This is fix-forward only.
- If a Codex row has no implementer raw label and no Step 2 mark, keep existing behavior. Do not guess.
- When `CODEX_BINARY_FOUND=true` or `CURSOR_BINARY_FOUND=true`, dispatcher token marks must stay absent even if the launcher mark fails best-effort; consumer fallback and launcher warnings carry the repair signal.

## Failure modes when non-trivial

- Double counting can occur if synthetic Step 2 rows do not remove raw-labeled implementer rows from their enclosing Step 0 slice.
- Double marking can recur if dispatcher tests only cover binary-missing paths and launcher tests only cover launch success without argv assertions.
- A best-effort mark helper can become silent again if tests only assert launch success. Assert the exact token-mark argv and call order.
- Importing new constants from the wrong layer can trip layering lint. Keep shared literals in `larch.core.config`.
- Over-broad raw-label fallback can misclassify review or CI fixer rows. Match exact raw labels only.
