Four distinct risks; no merges. Each needs a different fix or targets a different failure surface.

### FINDING_1: Pre-launch panel-failed envelope omits standard keys
- **Reviewer(s)**: Cursor-Arch
- **Severity**: important
- **Concern**: The planned pre-launch monitor-mode failure helper is specified to persist only `STEP3_REVIEW_LOOP_STATUS`, `LOOP_STATUS`, and `REASON`. Other `panel-failed` exits use `step3_loop_persist_envelope`, which writes a wider key set (`REVIEW_ROUND_COUNT`, `ACCEPTED_COUNT`, `DEGRADED_PANEL`, `TALLY_PLAN_REVIEW_STATUS`, and related fields). A fresh pre-launch abort can therefore leave `.step3-review-result.env` and downstream `read-result-env.sh` / wrapper stdout out of sync with every other panel-failed path, breaking resume or handoff consistency.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Arch: Reuse the same persisted key list as `step3_loop_persist_envelope` for panel-failed with `REASON=monitor-mode-unavailable` or call a shared helper instead of ad-hoc three-key writes

### FINDING_2: Process-group kill may not reach nested reviewer jobs
- **Reviewer(s)**: Cursor-Pragmatic
- **Severity**: important
- **Concern**: With `set -m` enabled, `dispatch-with-waterfall.sh` backgrounds each reviewer (`&`). Under job control those jobs can become separate process-group leaders. `kill -- -"$_loop_pid"` only signals the loop driver's process group (the backgrounded `run-step3-review.sh` PID), so external reviewers launched inside the loop may keep running and writing outputs after the wrapper reaps the loop driver. That matches the incident's late `cursor-plan-requirements-output.txt` write even when the loop driver has exited. The plan's broader "no child subprocess" acceptance criteria may be unmet by wrapper-only PG kill while `run-step3-review.sh` stays unchanged.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Pragmatic: Narrow acceptance criteria to "no `run-step3-review.sh --mode loop` process survives wrapper exit" (external reviewers already in flight remain a documented non-goal), or extend teardown inside `run-step3-review.sh` to reap its job table before exit. The plan explicitly leaves `run-step3-review.sh` unchanged, so the wrapper-only PG kill cannot meet the broader "no child subprocess" wording.

### FINDING_3: Pre-launch abort must emit terminal stdout KVs before EXIT cleanup
- **Reviewer(s)**: Cursor-Pragmatic
- **Severity**: important
- **Concern**: The monitor-mode pre-launch `panel-failed` path can exit before the existing post-wait `read-result-env.sh` parse and the terminal KV emit block. The orchestrator learns the Step 3 outcome from immediate-background stdout on `<task-notification>`. If the pre-launch helper writes only `.step3-review-result.env` or omits `STEP3_REVIEW_LOOP_STATUS` on stdout, the orchestrator can mis-route (wrapper hard failure vs gate-b-bypass) even though the loop never launched.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Pragmatic: Name the required stdout keys explicitly in the plan: at minimum `STEP3_REVIEW_LOOP_STATUS=panel-failed`, `LOOP_STATUS=panel-failed`, and optional `REASON=monitor-mode-unavailable`; print them before any `exit 0` that can invoke `_step3_review_cleanup`.

### FINDING_4: EXIT trap must be disarmed before post-loop failure exits
- **Reviewer(s)**: Cursor-Pragmatic
- **Severity**: important
- **Concern**: The EXIT-trap cleanup must not run on the successful path after the trap is cleared, but `_loop_pid` must be cleared and the trap disarmed before any post-loop `exit 1`. On the `postplan-failed` branch (current line 228), if `_loop_pid` is still set or the EXIT trap is still armed, cleanup could kill a resumed loop or turn a handled postplan failure into an ambiguous wrapper exit. The plan orders teardown, `_loop_pid=""`, `trap - EXIT`, then `set +m`, but does not restate that `postplan-failed` and `run-step3-review.sh` rc-2 handling happen only after disarm.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Pragmatic: Keep the ordered disarm sequence as a hard invariant in the implementation: after `wait`, final PG teardown, set `_loop_pid=""`, `trap - EXIT`, restore monitor mode, then run env parse and allow `exit 1` only on `postplan-failed` / rc 2.
