# [BUG] (URGENT) design-step3-review.sh exits without killing run-step3-review.sh: orphan loop modifies plan.txt post-completion

## Incident

During design run `AE50793A-D663-44C2-AF1C-68722B596BBA` (issue #4157, larch 50.0.4, today), `plan.txt` was silently modified **after** the design run completed and the `larch:plan` block had been written to the tracking issue. The modification was detected via a `system-reminder` notifying of an unexpected file change.

Timeline:
- `18:22` — background task `b1hhexwp2` (`design-step3-review.sh`) completed, exit 0. Notification received. All 8 reviewer output files were empty (`degraded-empty-collector`). Orchestrator moved to Step 3b, finalized, ran Step 4, Gate C, Step 5, Step 6.
- `18:30` — `design-publish.sh` completed; `larch:plan` written to #4157; issue renamed `[DESIGNED]`.
- `19:18` — `cursor-plan-requirements-output.txt` written (2065 bytes), 56 minutes after launch. The Cursor requirements reviewer had been "still running (1m elapsed)" at collection time.
- `19:23` — `.step3-review-result.env` appeared, `review-round-count.txt` advanced, `plan-pre-apply-round-4.txt` created.
- `19:25` — `plan.txt` modified (11 608 → 25 481 bytes). Files `.gate-b-postapply-ready-4`, `.gate-b-optional-trailer-keys`, `.step3-round-4.phase` written. `dispatch-plan-review-panel.sh --round-num 5` observed live in the process list.

## Root cause

`design-step3-review.sh` is the immediate-background wrapper that Claude Code launches as a background task. Internally it invokes `run-step3-review.sh --mode loop` (a separate child subprocess).

When round 1 returned with `LOOP_STATUS=degraded-empty-collector` (all collector outputs empty), `design-step3-review.sh` exited with code 0 and issued the `<task-notification>`. **However it did not kill or wait for `run-step3-review.sh` (PID 32154) before exiting.** The child continued as an orphan, owning the full multi-round loop lifecycle.

The orphan:
1. Waited for the still-running Cursor requirements reviewer (which eventually wrote 2065 bytes at 19:18).
2. Processed its findings, applied them to `plan.txt` via `revise-plan-with-waterfall.sh --patch-format file-replacement`.
3. Dispatched rounds 2–5 normally, modifying `plan.txt` and all associated artifacts.

The process was confirmed live via `ps aux | grep dispatch-plan-review-panel` at 19:25.

## Impact

- The `larch:plan` block in the tracking issue contains the pre-review plan (4 layers). The post-review `plan.txt` in the session tmpdir has reviewer-applied improvements (5 layers, additional files). These are now divergent.
- Any operator running `/implement` will work from the unreviewed plan, missing the reviewer-applied changes.
- The orphan ran the full review loop (rounds 2–5) against the already-published plan, which is work that cannot be recovered by the orchestrator.
- This is the reverse of the #4157 busy-wait bug: instead of the orchestrator polling while waiting for a live background task, the background task exits early and leaves a ghost that modifies files the orchestrator considers settled.

## Root cause in code

`design-step3-review.sh` likely has structure like:

```bash
# sources env, checks pause, then:
run-step3-review.sh --mode loop ... &
LOOP_PID=$!
# ... or: exec run-step3-review.sh --mode loop ...
```

If it uses `exec`, the wrapper PID is replaced and there is no child to kill. If it uses `&` + `wait $LOOP_PID`, an early-exit path (e.g. `degraded-empty-collector` signalled via a file/env rather than exit code) may bypass the `wait`. If it runs `run-step3-review.sh` synchronously but the loop itself forks sub-loops, those sub-forks survive the parent exit.

The exact mechanism needs confirmation by reading `design-step3-review.sh` and `run-step3-review.sh` directly.

## Suggested fix

**Option A (preferred): kill-on-exit trap in the wrapper.**

In `design-step3-review.sh`, capture the loop PID and install an EXIT trap:

```bash
run-step3-review.sh --mode loop ... &
LOOP_PID=$!
trap 'kill -- -$LOOP_PID 2>/dev/null || true' EXIT
wait $LOOP_PID
_loop_rc=$?
trap - EXIT
```

`kill -- -$LOOP_PID` sends SIGTERM to the process group rooted at `$LOOP_PID` so all grandchild Cursor/Codex processes are also terminated.

**Option B: always `wait` before exiting.**

If the wrapper uses a pattern where `run-step3-review.sh` exits by writing a result file and the wrapper polls or is otherwise notified, replace that with a blocking `wait` so the wrapper never exits before the loop PID is reaped.

**Option C: process-group isolation.**

Launch `run-step3-review.sh` in its own process group (`setsid` or `set -m` + `(run-step3-review.sh &)`) and kill the entire group on wrapper exit. This is a stronger guarantee when the loop spawns its own reviewers.

## Acceptance criteria

- After `design-step3-review.sh` exits (for any reason: complete, degraded-empty-collector, cap-reached, panel-failed), no child subprocess of that wrapper continues to run.
- `plan.txt` and other session artifacts are not modified after the orchestrator receives `<task-notification>` for the background task.
- A structure-test pin confirms the kill/wait pattern exists in `design-step3-review.sh`.
- `make lint` passes.
