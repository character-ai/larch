**1. Security — do not `source` the new result env** (`skills/design/SKILL.md`, planned fence)

The plan’s UPDATED `SKILL.md` section says the orchestrator should **source** `$DESIGN_TMPDIR/.step3-review-result.env`. That conflicts with `SECURITY.md`, which treats `.step3-plan-review-result.env` as untrusted data and requires allowlisted parsing. The live Step 3 driver fence already uses a read loop, not `source`, for that file.

**2. Correctness — subprocess loses `IMPLEMENT_TMPDIR` for `--feature-file`** (planned `run-step3-review.sh`)

Today’s inline fence passes `--feature-file "${IMPLEMENT_TMPDIR:-$DESIGN_TMPDIR}/feature-description.txt"`. `write-design-current-env.sh` exports `CODEX_PRESENT` / `CURSOR_PRESENT` / `CLAUDE_PLUGIN_ROOT`, but not `IMPLEMENT_TMPDIR`. A separate `run-step3-review.sh` process will not see `IMPLEMENT_TMPDIR` unless the plan requires exporting it, passing `--feature-file`, or re-reading session state. The plan’s argv list omits this; `run-step3-review.md` “derived sources” is named but not specified in the plan body (unlike `run-step2-dispatch.md`).

**3. Correctness — `test-step3-review-cap.sh` extraction strategy** (`skills/design/scripts/test-step3-review-cap.sh:14-28`)

The cap harness pulls bash blocks from `SKILL.md` via markdown anchors. After the refactor, cap logic lives in `run-step3-review.sh`. The plan lists harness updates but does not require replacing `extract_block` with script invocation. That is the highest-risk harness gap called out in Failure modes, and it needs an explicit approach in the plan.
