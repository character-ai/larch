[BUG] /design Step 3 aggregator emits empty-merge attestation when 57 raw FINDING inputs are present, causing tally rc=2 and zero ballot blocks

## Summary

The /design Step 3 plan-review aggregator (LLM-driven, Cursor on this run) emitted the literal sentinel `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` despite being given 57 raw `### FINDING_N:` blocks plus a non-empty OOS section as input. The aggregator's own prompt explicitly forbids that attestation when `### FINDING_N:` blocks are present in the supplied input. As a result, `aggregator-output.txt` carries only a 244-byte intent preamble plus the attestation token, `findings-in-scope.md` is overwritten by that 244-byte output (no FINDING blocks survive), and `tally-plan-review.sh` rejects the resulting `ballot.txt` with rc=2 because the only content there is duplicate `### OOS_1:` blocks from the pre-existing OOS-numbering bug (issue #2764).

Reproduced on character-ai/larch at SHA e07e4e5d during a "Replace via full flow" replay of /design --simple 2671 (run id A248746F-0EB2-44E0-91F7-52F4DCAFDC84). The same plan + feature description ran successfully on the prior /design invocation earlier in the same conversation (run 96806BD1-ED37-45B2-947C-8BCD073A947E, which produced PR #2771 + tracking design at #2671). Only this replay hit the empty-merge attestation.

## aggregator-output.txt full content (run gaF6T6)

```
Aggregating 57 raw inputs into merged findings: no repo reads required (inputs are self-contained). Calling CreatePlan to satisfy plan-mode, then providing the full structured finding list in the reply.



LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED
```

The aggregator narrated an intent ("then providing the full structured finding list in the reply"), called `CreatePlan` to satisfy plan-mode (Cursor agent shape), and then emitted the empty-merge attestation **instead of** the promised structured finding list. Plan-mode satisfaction appears to have terminated the response before the finding list was written.

## Root cause hypothesis

The aggregator prompt at `skills/review/scripts/aggregate-findings.sh` (and its downstream Cursor invocation) instructs the LLM:

> "Because there is at least one `### FINDING_N:` block, the empty-merge attestation line must **not** appear."

The Cursor agent shape includes a `CreatePlan` tool call that, per the agent's narration, was invoked "to satisfy plan-mode" before the finding list emission. When `CreatePlan` returns / completes, Cursor may have ended the turn prematurely without continuing to emit the finding-list payload — collapsing the response back to the default tail (the empty-merge attestation). This is a Cursor model behavior, not a larch helper failure: `aggregate-findings.sh` correctly dispatched the prompt; the validator (`aggregator-validate.py`) is fail-open on `STATUS=ok` + non-zero return, which is appropriate for non-truncation cases.

Evidence pointing at Cursor specifically:
- `aggregator-dispatch.env` records `ALL_OUTPUT_TOOLS=cursor` (this was a Cursor-aggregated run).
- The intent-announcement style ("Calling CreatePlan to satisfy plan-mode") is a Cursor agent narration pattern.
- The same input set under Codex aggregation in the prior run produced a fully populated `aggregator-output.txt` (26513 bytes, 21 FINDING blocks).

## Concrete impact

1. `findings-in-scope.md` is overwritten by the 244-byte aggregator output (the in-scope file is written via the `_agg_out=$_agg_in` redirection pattern in `plan-review-loop.sh`). The Python-deduped 57 FINDING blocks from `findings.md` are still on disk, but never reach the ballot.
2. `ballot.txt = cat aggregator-output.txt findings-oos.md` = 949 bytes total: 244 bytes of aggregator intent preamble + 2 duplicate `### OOS_1:` blocks from the unfixed Python-dedup-splitter bug (issue #2764).
3. `tally-plan-review.sh --voter-files claude-vote-output.txt codex-vote-output.txt cursor-vote-output.txt` exits rc=2 with "duplicate or malformed FINDING/OOS headings in ballot" (triggered by the two duplicate `OOS_1` blocks, but the *real* problem upstream is the empty-merge attestation).
4. `LOOP_STATUS=complete TALLY_PLAN_REVIEW_STATUS=tally-error ACCEPTED_COUNT=0` is the loop's final state. No accepted/rejected/oos artifacts produced.

## Suggested fix

Two layers to consider:

**Layer 1 — aggregator-output validation (larch-owned, deterministic)**:

`scripts/aggregator-validate.py` (or its calling shell wrapper) should refuse an aggregator output that:

1. Contains `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` AND the original `findings-in-scope.md` input contained one or more `### FINDING_N:` blocks (the empty-merge attestation is structurally invalid when inputs were non-empty).
2. Contains zero `### FINDING_N:` blocks while the input contained one or more.

On detection, fall back to either (a) the pre-aggregator Python-deduped findings (so voting proceeds against the raw deduped list, which is noisier but correct) OR (b) a retry with the alternate aggregator tool (Codex when Cursor failed; Claude as final retry).

Suggested validator pseudocode addition near the existing structural checks:

```python
input_finding_count = count_finding_blocks(agg_input_path)
output_finding_count = count_finding_blocks(agg_output_path)
has_empty_attestation = "LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED" in agg_output_text
if input_finding_count > 0 and (has_empty_attestation or output_finding_count == 0):
    sys.stderr.write(
        "aggregator-validate: invalid empty-merge attestation; "
        f"input had {input_finding_count} FINDING blocks, output has {output_finding_count}\n"
    )
    sys.exit(2)
```

**Layer 2 — plan-review-loop fallback when aggregator output is structurally empty**:

`skills/design/scripts/plan-review-loop.sh` already has `_agg_out=$_agg_in` default. When the aggregator validator returns non-zero (Layer 1 above), the loop should set `_agg_out=$DESIGN_TMPDIR/findings-in-scope.md` from a **pre-aggregator snapshot** (cp before the aggregator runs) so the raw deduped findings reach the ballot. Add a `WARN=plan-review-aggregator: empty-merge-attestation detected; using raw deduped findings` emit so operators see the degraded path.

Both layers together let /design recover gracefully from this Cursor failure mode without losing the panel-review output entirely.

## Acceptance

- `aggregator-validate.py` (or equivalent helper) rejects an aggregator output that emits `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` (or zero FINDING blocks) when the input `findings-in-scope.md` had one or more FINDING blocks.
- `plan-review-loop.sh` falls back to the pre-aggregator Python-deduped findings on validator rejection, emitting a `WARN=` so the degraded path is observable in run logs.
- Regression fixture in `skills/design/scripts/test-plan-review-loop.sh` (or aggregator-validate.sh test): aggregator emits empty-merge attestation while input has N FINDING blocks → validator rejects, loop falls back to deduped findings, tally still produces a populated ballot.
- A successful follow-on /design run on a previously-failing replay produces a non-empty `voting-tally.md` and a non-empty `accepted-plan-findings.md` even when one aggregator tool degrades to empty-merge-attestation.
