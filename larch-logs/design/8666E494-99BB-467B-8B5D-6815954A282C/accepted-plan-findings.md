Also bump `diff_lines:` to account for the new edit (+~10 lines).

### FINDING_2: Plan must decide whether `empty_merge_from_nonempty_input` progresses the outer waterfall
- **Concern**: `aggregate-findings.sh` line 717 progresses the outer aggregation waterfall (Cursor → Codex → Claude) by setting `MERGE_PIPELINE_RC=1` *only* on the specific stderr token `AGGREGATOR_VALIDATION_FAILED=preamble_finding_substring`; all other validation failures use `MERGE_PIPELINE_RC=2` (terminal — no retry with the next external). The bug report explicitly states "The same input set under Codex aggregation in the prior run produced a fully populated `aggregator-output.txt` (26513 bytes, 21 FINDING blocks)" — i.e., Codex would have succeeded on the same input that Cursor failed on, but only if the waterfall progresses. The plan introduces a new validation-failed token (`empty_merge_from_nonempty_input`) without specifying whether the waterfall should treat it like the preamble case (progress, try next external) or like a generic terminal failure (no retry). Leaving this ambiguous risks the implementer picking the wrong default and either (a) silently re-introducing the bug under Codex+Claude failure, or (b) over-retrying on legitimate noise inputs.
- **Proposed resolution**: Add an explicit sub-decision under **Approach** stating the waterfall behavior. Recommended: progress the outer waterfall on `empty_merge_from_nonempty_input` (treat it like `preamble_finding_substring`) — this directly matches the bug report's observed recovery pattern (Codex succeeded where Cursor failed) and bounds the worst case to "all three externals fail similarly, then findings.md remains the raw deduped findings via the existing terminal `validation-exhausted` path." Update the wrapper's grep clause at line 717 from `'^AGGREGATOR_VALIDATION_FAILED=preamble_finding_substring'` to match either token (e.g., extend to `'^AGGREGATOR_VALIDATION_FAILED=(preamble_finding_substring|empty_merge_from_nonempty_input)$'`). Bump `diff_lines:` to account for the one-line grep change. Also add a corresponding test case asserting outer-phase progression behavior (next-phase attempt observable via the `PHASES_ATTEMPTED` emit).
