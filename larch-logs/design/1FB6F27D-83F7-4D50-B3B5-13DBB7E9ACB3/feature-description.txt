# [py-code-quality] Add typed Finding (+parser) and a single Manifest representation

**Problem.** Domain data is stringly-typed where plumbing is strongly typed. Measured tree-wide: 211 `dict[str, Any]` + 320 `dict[str, str]` annotations and 119 `cast()`, against ~1 Enum despite 151 dataclasses (124 frozen).

**Evidence.**
- A review finding has no type: it is a `### FINDING_N:` markdown block re-parsed by regex at every hop (`python/review_pipeline.py:1245`), carried as `list[tuple[str,str,str]]` and even a positional 6-tuple `(str,str,str,str,str,str|None)` (`python/review_tally.py:628`).
- Statuses/votes/severities are bare strings (`core_status` flows through ~15 string literals in `python/review_and_fix.py:2418`).
- The `Manifest` dataclass exists but is bypassed via `_dict_to_manifest`/`_manifest_to_dict` round-trips, with an 18-key exclude-set literal duplicated at `python/run_logs.py:734` and `:925` (will drift).

**Proposed change.** Add a `Finding` dataclass + one `parse_findings(path) -> list[Finding]` replacing the per-hop regex re-scans. Make `Manifest.from_json`/`to_json` the sole representation; retire the dict round-trips and the duplicated exclude-set. Convert internal-only statuses/votes/severities to `StrEnum` (keeps the string on the wire, adds type safety + exhaustiveness).

**Out of scope / don't-touch.** Keep the markdown finding-file layout and `KEY=value` wire formats. Change in-memory representation only; serialize from the types.

**Acceptance.** One `Finding` type + one parser used by review_and_fix/review_aggregate; `Manifest` is the only manifest representation; key internal status sets are `StrEnum`; parity/units green.

**Effort / risk.** Medium / low-medium. Biggest readability/safety win.

**Dependencies.** Root (no blockers). Blocks the god-function-split item and the packaging item. Wired via `/block-issue`.
