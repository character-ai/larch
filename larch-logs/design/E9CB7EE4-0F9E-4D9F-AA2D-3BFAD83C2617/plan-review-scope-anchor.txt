## Summary

`/design` Step 5c can fail to publish an otherwise fully-approved plan with a spurious `kind=difficulty-metadata` validator defect. Root cause: the Step 2b **external-vendor drafter** path never writes `$DESIGN_TMPDIR/design-difficulty-rating.raw.json`, and the fallback resolution path (`difficulty.plan_difficulty()`) cannot find the plan's `difficulty:` trailer once `/design` auto-composes `composed-plan.md` from `plan.txt`, because the compose step's own appended `diff_lines:` line separates the true trailing metadata block from the plan's original `difficulty:`/`confidence:` trailer with an intervening `## Acceptance` section.

## Original report

Surfaced as a side observation while running `/design` for issue #6188 (a test-coverage fix unrelated to this bug). Step 2b's plan drafting used the external-vendor "drafter subprocess" path (`design step2b-drafter`, vendor=Codex), which produced a valid `plan.txt` with a correctly formatted `difficulty: MODERATE` trailer line. The plan was reviewed, Gate B applied one accepted finding, and Gate C auto-approved (`--skip-approve`). Step 5c then failed on its first attempt:

```
**⚠ Step 5c: composed-plan.md was absent; auto-composed from plan.txt**
PUBLISH_RC=4
PLAN_WRITE_OK=false
VALIDATE_STATUS=defects-found
VALIDATE_DEFECT_COUNT=1
```

`validate-plan-commands.log` showed `DEFECT plan kind=difficulty-metadata` — despite `plan.txt`'s trailer containing a syntactically valid `difficulty: MODERATE` line the whole review process had already seen and approved.

Workaround used to unblock the run: manually created `$DESIGN_TMPDIR/design-difficulty-rating.raw.json` with the same `predicted_tier`/`confidence` already present in the approved plan, then re-ran the Step 5c launcher (`design-step5c.sh`). That let `_resolve_publish_difficulty_rating` find a valid rating directly, `rewrite_plan_difficulty` correctly inserted `difficulty: MODERATE` into the true trailing block, and republish succeeded (`PLAN_WRITE_OK=true`, `PUBLISH_OK=true`).

## Reproduction scenario

1. Run `/design <issue>` where Step 2b plan drafting uses the external-vendor drafter subprocess path (`design step2b-drafter`, Codex or Cursor), not the inline main-agent drafting fallback. The drafter writes `plan.txt` with a valid `difficulty: <TIER>` trailer line (per the prompt built in `python/larch/design/design_step2b.py:405-436`), but — confirmed by grepping every reference to `difficulty.DESIGN_RAW_RATING_BASENAME` across `python/larch/` — nothing in the drafter-subprocess code path ever writes `$DESIGN_TMPDIR/design-difficulty-rating.raw.json`. Only the *inline* (main-agent, prose-driven) Step 2b path is documented in `skills/design/SKILL.md` to write that sidecar via the `Write` tool, so any drafter-subprocess run skips it structurally.
2. Reach Step 5c at a point where `$DESIGN_TMPDIR/composed-plan.md` does not yet exist, so the Step 5c driver auto-composes it from `plan.txt` (observed banner: `composed-plan.md was absent; auto-composed from plan.txt`). The composer emits `## Plan` (verbatim `plan.txt` body, including its own `difficulty:`/`confidence:`/`diff_lines:` trailer) followed by `## Acceptance`, then appends its own fresh trailing `diff_lines: <N>` line at the true end of the document (per `docs/`/`skills/design/references/finalize-step5.md`'s compose contract), producing two `diff_lines:` occurrences in the file.
3. `design_publish.py`'s Step 5c body (around line 733) has non-empty `review_status`/`rounds_completed` from `.step3-review-result.env`, so it calls `_splice_plan_provenance` (design_publish.py:292-336). That function computes `existing_difficulty = difficulty.plan_difficulty(text)` (line 302) **before** splicing — at that point `difficulty.trailing_plan_metadata_lines()` (difficulty.py:566-572, via `_trailing_metadata_span` at difficulty.py:552-563) only sees the composer's lone trailing `diff_lines:` line, because `_PLAN_TRAILER_LINE_RE` stops matching at the first non-trailer line walking backward, and the actual `difficulty:`/`confidence:` pair sits earlier in the document, separated by `## Acceptance` and prose. `existing_difficulty` therefore returns `""`.
4. Because `existing_difficulty` is falsy, `provenance` only gets `review_status:`/`rounds_completed:` (difficulty.py:303-308 in the caller — no `difficulty:` line is carried forward), and the splice logic (design_publish.py:322-336) inserts those two lines immediately before the trailing `diff_lines:`, leaving the original `difficulty: MODERATE`/`confidence: high` pair stranded mid-document.
5. `_resolve_publish_difficulty_rating` (design_publish.py:109-129) then checks for `$DESIGN_TMPDIR/design-difficulty-rating.raw.json`; since the drafter subprocess never wrote it (step 1 above), it falls back to `difficulty.plan_difficulty(plan_text)` — the same trailing-block scan — which also returns `""` for the same reason. `design_rating` resolves to `None`.
6. Because `design_rating is None`, `rewrite_plan_difficulty` (difficulty.py:515-533) never runs, so the composed plan's trailing block ends up with `review_status:`/`rounds_completed:`/`diff_lines:` only — no `difficulty:` anywhere in it.
7. The Step 5c validate subprocess call (design_publish.py:750-768) sets `LARCH_REQUIRE_PLAN_DIFFICULTY=1`. `validate_plan_main` (`python/larch/design/_plan_quality_commands.py:853-905`, specifically the check at lines 876-877) treats a missing trailing `difficulty:` as a hard defect (`kind=difficulty-metadata`) whenever that env var is set, producing `VALIDATE_STATUS=defects-found`, `PUBLISH_RC=4`, `PLAN_WRITE_OK=false` — even though the plan has a perfectly valid `difficulty:` line, just not in the position the scan requires.

## Expected behavior

A plan that was rated, reviewed, and approved with a valid `difficulty: <TIER>` trailer should publish through Step 5c without a validator defect, regardless of whether Step 2b drafting went through the external-vendor drafter subprocess or the inline main-agent path, and regardless of whether `composed-plan.md` needed to be auto-composed from `plan.txt` at Step 5c time.

## Observed behavior

Step 5c fails with `PUBLISH_RC=4`, `VALIDATE_STATUS=defects-found`, `kind=difficulty-metadata`, blocking publish of `larch:plan` to the tracking issue and blocking the `[DESIGNED]` rename, even though the plan's difficulty metadata was valid and already approved through Gate C. No `AskUserQuestion` or automated recovery in the current `/design` flow resolves this defect; per `skills/design/references/validator-failure.md`, the only prescribed recovery is the composed-plan.md auto-repair vendor-edit path or an operator picking Fix-and-retry / Override / Cancel — none of which target the actual root cause (the missing sidecar / the trailing-block scan losing a mid-document `difficulty:` line).

## Root cause analysis

Two independent, compounding defects:

1. **Missing writer**: `$DESIGN_TMPDIR/design-difficulty-rating.raw.json` (`difficulty.DESIGN_RAW_RATING_BASENAME`, difficulty.py:27) has five read call sites across the codebase (`design_publish.py:110`, `design_publish.py:856`, `design_summary.py:178`, `design_summary.py:194`, `design_postplan.py:78`, `plan_review_common.py:90`) and **zero** write call sites in `python/larch/`. The only place this file is documented to be written is `skills/design/SKILL.md`'s Step 2b prose ("Write `$DESIGN_TMPDIR/design-difficulty-rating.raw.json` with `predicted_tier`, `confidence`, and bounded `rationale`"), which only the inline main-agent drafting path follows directly via the `Write` tool. The drafter-subprocess path (`design step2b-drafter`, `python/larch/design/design_step2b.py`) asks the external vendor to embed a `difficulty:` line in the plan body text (design_step2b.py:405-436) but has no code that extracts that line back out into the JSON sidecar.
2. **Fallback resolution is structurally blind to a valid mid-document difficulty line**: `difficulty.plan_difficulty()` / `trailing_plan_metadata_lines()` / `_trailing_metadata_span()` (difficulty.py:507-512, 552-572) only recognize a *contiguous* run of trailer-shaped lines at the literal end of the text. Whenever the Step 5c composer appends its own `diff_lines:` line after `## Acceptance` (per the compose contract in `skills/design/references/finalize-step5.md`), the plan's original `difficulty:`/`confidence:` pair — still present and valid — becomes unreachable to this scan. This affects both `_splice_plan_provenance`'s `existing_difficulty` lookup (design_publish.py:302) and `_resolve_publish_difficulty_rating`'s fallback branch (design_publish.py:117), so even a manually-authored plan without a raw-rating sidecar would hit the same failure once auto-composed.

Uncertain: I did not trace why `composed-plan.md` was absent at Step 5c time in this run (the driver auto-composed it transparently rather than treating the absence as a hard defect requiring Fix-and-retry, which is what `skills/design/references/finalize-step5.md`'s prose for "missing or empty composed-plan.md" describes) — that may be expected/intended behavior for a first-time Step 5c entry, or it may itself be a second, separate gap between documented and actual behavior. I have not verified which.

## Affected files

- `python/larch/design/design_publish.py` — `_resolve_publish_difficulty_rating`, `_splice_plan_provenance`, and the Step 5c body that sequences them; likely needs a repaired trailing-block-independent way to recover a plan's original difficulty tier, or the drafter path needs to guarantee the sidecar exists before this code runs.
- `python/larch/design/design_step2b.py` — drafter-subprocess path; currently has no code writing `design-difficulty-rating.raw.json` from vendor-produced plan text.
- `python/larch/calibration/difficulty.py` — `plan_difficulty` / `trailing_plan_metadata_lines` / `_trailing_metadata_span`; the shared scan that both call sites in `design_publish.py` rely on and that cannot see a difficulty line separated by intervening document sections.
- `skills/design/SKILL.md` — documents the raw-rating-sidecar contract only for the inline drafting path; the drafter-subprocess path has no equivalent documented contract for this artifact.

## Suggested fix(es)

No single fix identified as clearly correct; two independent angles, either or both may be warranted:

1. Make the drafter-subprocess path (`design step2b-drafter` / `design_step2b.py`) parse the vendor's own `difficulty: <TIER>` trailer line out of the drafted plan text and write `$DESIGN_TMPDIR/design-difficulty-rating.raw.json` itself, the same way the inline path is documented to, so `_resolve_publish_difficulty_rating`'s primary (reliable) path always has data regardless of which Step 2b path produced the plan.
2. Make `difficulty.plan_difficulty()` (or a new helper) scan the *entire* document for the last well-formed `difficulty: <TIER>` line rather than only the literal trailing contiguous metadata block, so a difficulty line stranded mid-document by compose-time restructuring is still found. This would need care not to pick up a stale/superseded difficulty line if a plan is revised more than once, so ordering/precedence rules would need explicit design.

## Open questions

- (Resolved via dedup search against #5422) The "composed-plan.md absent → transparently auto-composed" behavior observed at Step 5c is intended — #5422 fixed exactly this by making the driver auto-compose when the file is missing, rather than treating absence as a hard abort. That part of this run's behavior is not a separate gap.
- Should the raw-rating sidecar be considered a required Step 2b artifact enforced by a structural check (so a missing sidecar surfaces immediately after drafting, rather than three steps later at publish time), independent of which fix from Suggested fix(es) is chosen?

## Approved direction (outline)

## Proposed Design Outline

### Goals
- Lock in today's correct behavior with a regression test: a drafter-subprocess plan whose `difficulty:` trailer gets stranded mid-document by Step 5c's auto-compose must still publish cleanly (proving the #6064 side-effect fix holds).
- Close the still-latent whole-document blind-scan gap in `difficulty.py` as defense-in-depth, so `plan_difficulty()` finds a valid `difficulty:` line anywhere in the document when the trailing-span scan finds none.

### Non-goals
- Not re-implementing `_write_design_difficulty_sidecar` — it already exists in `design_postplan.py` and already covers both the drafter-subprocess and inline Step 2b paths.
- Not adding a new Step 2b hard-fail structural check for a missing sidecar — dropped per Round 1 Decision 2; it would fight the documented, deliberate "stay graceful at Step 2b, enforce at Step 5c" design.
- Not changing where `rewrite_plan_difficulty` inserts/replaces its line (stays within the trailing metadata span) — a composed document's embedded `## Plan` copy of the original trailer is expected content, not a defect to clean up.

### Approach sketch
- Add a whole-document fallback scan to `python/larch/calibration/difficulty.py`, reached only when the existing trailing-span scan (`_trailing_metadata_span`) finds no `difficulty:` line, preserving current behavior for the common case.
- Feed that fallback through both existing callers (`_splice_plan_provenance`'s `existing_difficulty` and `_resolve_publish_difficulty_rating`'s fallback in `design_publish.py`) so both benefit without call-site changes beyond the shared helper.
- Add regression coverage exercising the drafter-path + compose + publish chain (function-level, mirroring the scenario already verified empirically this session).
