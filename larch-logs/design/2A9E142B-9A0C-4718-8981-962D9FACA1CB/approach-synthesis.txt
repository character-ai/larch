## Approach Synthesis

### Agreement (both sketches)

Replace the Step 2b.5 Split-path body in `skills/design/SKILL.md` with a real decomposition procedure. All 3 sprawl-trigger sources (Step 2b.5 mechanical thresholds + `-p`/`--partition`, Step 1c sprawl heuristic, Step 1d sprawl heuristic) already converge on this body, so a single replacement covers all triggers.

The procedure runs an 8-slot fanout (4 archetypes × 2 vendors: Cursor + Codex per archetype) using existing reviewer machinery: `scripts/dispatch-with-waterfall.sh` for Cursor → Codex → Claude per-slot waterfall, `scripts/collect-agent-results.sh` for output collection, and `scripts/aggregate-findings.sh` (or analog) for the optional aggregator path. Mirror the shape of `skills/design/scripts/dispatch-plan-review-panel.sh`. Emit a `DEGRADED_PANEL` flag; fail only when zero usable proposals return.

After collection, the prompt-side `/design` flow presents the 4 archetype proposal bundles (each bundle = Cursor + Codex output for that archetype) plus options for: aggregator-picked optimal split, refine plan manually (return to caller — Step 1e Gate A on 1c/1d entry, or Step 2b on 2b.5 entry), and cancel. After the user picks a proposal (or aggregator delivers one), run a topological-sort cycle check on the dependency graph; refuse to file on cycle and re-prompt. On user-approved split, file N issues via `/larch:issue` batch mode with `--input-file` + `--intra-batch-deps-file` for inter-piece dependency edges. Close the original issue with a #2644-style cross-reference comment listing each new issue with state marker, scope sentence, and blocked-by chain. Exit `/design` cleanly (operator runs `/design` on each new piece independently).

### File layout (new helpers under `skills/design/scripts/`)

- `decompose-panel-dispatch.sh` (+ sibling `.md`) — renders 8 archetype × vendor prompts, builds NDJSON slot manifest, invokes `dispatch-with-waterfall.sh`. Mirrors `dispatch-plan-review-panel.sh` shape.
- `decompose-prompts/` directory — four archetype prompt templates: `decomposition-specialist.txt`, `dependency-analyst.txt`, `scope-minimalist.txt`, `risk-isolation.txt`. Each instructs the reviewer on the "independently mergeable" constraint, the soft 2-5 piece cap with justification for >5, and the structured Markdown output schema from the issue body (Recommendation / Pieces / per-piece Scope, Dependencies, Diff_lines estimate, Why independently mergeable).
- `decompose-aggregator.sh` (+ sibling `.md`) — wraps `aggregate-findings.sh` (or builds an analog) for the optimal-split delegation. Takes the 4 archetype proposal bundles as input; returns one canonical partition.
- `decompose-file-issues.sh` (+ sibling `.md`) — stages a `/larch:issue` batch input file from the chosen partition (one block per piece per the `/larch:issue` parse-input format), generates the intra-batch dependency TSV, invokes `/larch:issue` from the prompt side, captures the `ISSUE_*`/`ISSUES_*` stdout, validates outcomes, then posts the close-comment + closes the original issue. Idempotent via a sentinel file in `$DESIGN_TMPDIR/.decompose-issues-filed`.
- `decompose-cycle-check.sh` (+ sibling `.md`) — small helper that runs topological-sort cycle detection on the chosen partition's dependency graph (in-memory; no GitHub calls).
- Harnesses: `test-decompose-panel-dispatch.sh`, `test-decompose-aggregator.sh`, `test-decompose-file-issues.sh`, `test-decompose-cycle-check.sh`.

### Architectural notes from sketches

1. **Panel input artifact is dynamic** (Cursor): when Step 1c/1d sprawl triggers the panel, there is no `plan.txt` yet. The panel prompts must read from `feature-description.txt` + `discussion-round1.md`. When Step 2b.5 triggers (post-plan), prompts read `plan.txt` + `discussion-round1.md`. `decompose-panel-dispatch.sh` accepts both modes; the prompt template includes a `Plan: <available|not-yet-written>` marker driven by an input flag.
2. **`/larch:issue --no-dedup` is mutually exclusive with `--intra-batch-deps-file`** (Codex; verified in `skills/issue/SKILL.md:59`). Plan: keep dedup enabled (no `--no-dedup`); dedup fails open and rarely false-positives on uniquely-named partition pieces. This overrides the Round 1 default that said "force --no-dedup".
3. **Idempotent close** (Codex): write a sentinel `$DESIGN_TMPDIR/.decompose-original-closed` after the original-issue close succeeds. On re-run, skip close if sentinel exists. Similar sentinel for issue-creation completion (`$DESIGN_TMPDIR/.decompose-issues-filed`).

### Main tradeoffs and risks

- **Risk: contract drift between "8 reviewer invocations" and "4 raw proposals"** (Codex). Mitigation: bundle outputs per archetype (Cursor + Codex per archetype → one proposal bundle). The `AskUserQuestion` shows 4 bundles, not 8. The reviewer prompt itself produces an archetype's recommended split; Cursor and Codex run the same prompt and we show both — the user picks an archetype, not a vendor.
- **Risk: degraded panel still gates user choice**. If 2 archetypes return only 1 of 2 vendors, surface that in the option description ("decomposition-specialist [Codex only, Cursor failed]"). If an entire archetype has 0 successful slots after waterfall, drop it from the choice list and surface that as a `**⚠ archetype <name> unavailable**` line before the AskUserQuestion.
- **Risk: cycle check false-positive blocks user-approved partitions**. Mitigation: cycle check runs ONLY on the user's final picked partition (not on every reviewer's proposal). The check is in-memory, deterministic, and cheap; reviewers are not auto-rejected for cycles.
- **Risk: filed pieces accidentally inherit dependencies the user didn't intend**. Mitigation: the intra-batch deps TSV is generated mechanically from the chosen partition's "Dependencies: blocked-by Piece N" lines; emit a preview to chat before calling `/larch:issue`.
