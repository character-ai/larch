## Findings

1. **correctness** `python/duplicate_code.py:34-44` — The plan’s numbered ingestion path is `set current module → tokenize → process_tokens → SimilaritiesChecker.process_module`, but `process_module` in pylint 4 expects an astroid `nodes.Module` built from the discovered file. Without an explicit parse step (or a delegated `PyLinter` per-file check), implementers can wire the checker incorrectly while still intending “pylint parity.” **Revision:** Document and implement astroid module construction in the same order pylint uses, or run pylint’s own per-file pipeline with only similarities enabled.

2. **correctness** `plan.txt:241-249` — The merge-blocking parity gate only requires `LEGACY_RC == NEW_RC`. That is necessary but not sufficient for the issue’s “equivalent findings” goal: both tools can exit `1` for different duplicate clusters. **Revision:** Add a cluster-set comparison (normalized file pairs / line ranges) to the pre-cutover gate.

3. **architecture** `plan.txt:12-13,64-69` — **[SCOPE-REDUCTION]** The plan asks for a maintained `_compute_sims`-equivalent plus `close()`-equivalent layer on top of parallel `_find_common` calls. That is the largest long-term drift surface and works against minimum-change. **Revision:** Feed merged pairwise results back through pylint’s pinned `_compute_sims` / `SimilaritiesChecker.close()` instead of reimplementing reportability rules.

4. **risk-integration** `python/duplicate_code.py:55-59` — Parallelism is specified at a high level (`ProcessPoolExecutor`, fork when available) but not at the worker IPC boundary (picklable return values, top-level worker function, `mp_context`, spawn rebuild). This is a common failure point when moving from single-process pylint to a pool. **Revision:** Add an explicit worker contract section covering serialization and the non-fork fallback.
