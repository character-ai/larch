Architecturally, I would keep `scripts/implement-bootstrap.sh` as the Step 0 phase dispatcher and replace only the `phase_plan_materialize` stub, rather than adding another orchestration layer. The new phase should be a mechanical sequence with small local helpers: validate/read `$PREFLIGHT_TMPDIR/plan-from-issue.txt`, copy it to `$IMPLEMENT_TMPDIR/plan.txt`, compose `feature-description.txt` via `gh issue view`, bind `workflow-path HARD`, persist run flags, run the dirty-tree checkpoint, optionally derive/create the branch, capture the canonical branch via `git-current-branch.sh`, write plan log/tally artifacts, and upsert the `larch:plan` summary. I would add stable globals for `BRANCH_NAME`, `BRANCH_ACTION`, and `PLAN_FILE`, then emit them in `emit_final_tail` instead of hard-coded empty values.

The main code changes belong in `scripts/implement-bootstrap.sh`, with `scripts/implement-bootstrap.md` updated to document the new phase mapping, output keys, breadcrumbs, and new bail reasons: `run-flags-persist-failed`, `dirty-tree`, and `branch-create-failed`. The harness in `skills/implement/scripts/test-implement-bootstrap.sh` should extend the sandbox stubs for `gh`, `persist-implement-run-flags.sh`, `check-mid-run-dirty-tree.sh`, `git-current-branch.sh`, `run-step1-plan-log.sh`, `write-tally.sh`, and `tracking-issue-summary.sh`, then add the requested B6/B7 bail cases plus slug derivation edge cases. `skills/implement/SKILL.md` should then collapse the Step 0 prose so the single bootstrap Bash block runs through `--up-to-phase plan` or whatever boundary Phase 3 standardizes, leaving only the implementer waterfall outside.

The main risk is control-flow compatibility: current `should_run_post_tracking_phase` treats `DEFERRED=true` as a hard stop, but existing prose says some deferred metadata paths continue to plan materialization. Phase 3 should probably split “may materialize plan” from “may continue later phases” so repo-unavailable, closed issue, PR issue, and tracking-init failure still skip, while intended deferred paths behave correctly. The other risks are shell quoting and slug parity: preserve the exact `tr | sed | cut` behavior in a helper so tests can lock uppercase, punctuation, empty-ish, and 40+ char titles. Finally, branch creation failure semantics need to be narrow and observable: branch-exists exit 1 should stall with `branch-create-failed`; other helper failures should be documented explicitly so the orchestrator does not silently continue with an ambiguous branch state.
