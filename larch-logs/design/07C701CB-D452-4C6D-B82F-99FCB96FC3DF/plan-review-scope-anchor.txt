## Summary

During an `/implement` run for issue #6289, the orchestrator launched a background `grep -r` over the user's entire home directory (`/Users/...`) instead of the intended plugin python directory. The path was constructed from `$IMPLEMENT_TMPDIR/../../../..`, which resolves 4 levels above the session tmpdir to the home directory. The process ran for ~38 minutes, produced at least 64 MB of captured output (preview message claimed 2.5 GB), and was eventually killed with SIGURG (signal 16, exit code 144). The task notification arrived mid-Step-18 finalize, ~38 minutes after launch.

## Original report

Background command "Find valid escalation token values" failed with exit code 144

## Reproduction scenario

During `/implement` Step 18a stall recovery (coder=codex external-api-down), the orchestrator called `stall-recovery record-escalation` and got a token-validation error. To find valid token values, the orchestrator ran:

```bash
( command grep -r "record.escalation\|record_escalation\|COMMON_TRIGGERS\|escalation.*site\|escalation.*trigger" \
  "$IMPLEMENT_TMPDIR/../../../.." 2>/dev/null ) || \
( command grep -rn "COMMON_TRIGGERS\|record_escalation" \
  "/path/to/plugin/python/" --include="*.py" -l 2>/dev/null )
```

With `run_in_background: true`. The path `$IMPLEMENT_TMPDIR/../../../..` resolves to the user home directory (not the plugin directory as intended), launching a massive recursive scan.

## Expected behavior

The grep produces a small result set from the plugin directory and completes in seconds. If the path expression is wrong, the harness or orchestrator detects the oversized search before 38 minutes elapse.

## Observed behavior

- The grep scanned the entire home directory.
- The process ran for ~38 minutes.
- The persisted output file grew to at least 64 MB (harness preview said 2.5 GB total).
- The process was killed with SIGURG (signal 16), exit code 144.
- A task-notification for the failed command arrived during Step 18 finalize, long after the orchestrator had moved on.

## Root cause analysis

Two factors combined:

1. **Path construction error**: `$IMPLEMENT_TMPDIR/../../../..` resolves to the home directory when `IMPLEMENT_TMPDIR` is at depth 4 below home (e.g., `~/.cache/larch/sessions/<id>`). The intent was to reach the plugin root or python directory, but the relative ascent was wrong. This is an orchestrator-level mistake in the Bash command, not a larch code defect.

2. **No output/runtime guard for background Bash**: The harness did not terminate the runaway process until SIGURG was delivered ~38 minutes later. There is no early-abort mechanism for background commands that exceed an output-size or wall-clock threshold in a way that surfaces an actionable error quickly.

The exit code 144 (128 + 16 = SIGURG) is consistent with the harness sending `kill -SIGURG` to clean up a long-running background process, though the exact harness kill policy is not documented in committed scripts.

## Evidence

- Session tmpdir: `<TMPDIR>`
- Path expansion: `$IMPLEMENT_TMPDIR/../../../..` → `/Users/zhupanov` (confirmed by `os.path.realpath`)
- Background task ID: `bwpu5pwj4`
- Persisted output file size: 64 MB (harness preview: 2.5 GB estimate)
- File timestamp: ~38 minutes after command launch
- Exit code: 144 = 128 + SIGURG (signal 16, confirmed via Python `signal.Signals`)
- Task notification arrived during Step 18 finalize of the same `/implement` run

## Affected files

- `skills/implement/SKILL.md` — Step 18a stall recovery section; no path-validation guidance for Bash probes
- `BASH_AUTHORING.md` — covers grep wrapper trap and background stdin hangs, but does not address relative-path ascent hazards or output-size limits for background jobs

## Suggested fix(es)

1. **Orchestrator guidance**: Add a rule in `BASH_AUTHORING.md` or `AGENTS.md` that background grep probes must use absolute paths or paths anchored to a known-bounded root (e.g., `$CLAUDE_PLUGIN_ROOT/python/`), never relative `../` ascents from a tmpdir.
2. **Harness output limit**: If the Claude Code harness can enforce a per-task output cap (e.g., 10 MB for background Bash jobs), surface an `output-limit-exceeded` error quickly rather than letting the process run for 38 minutes before SIGURG.
3. **Larch stall-recovery probe**: The specific investigation probe could be replaced with a direct `python3 $CLAUDE_PLUGIN_ROOT/python/cli.py stall-recovery record-escalation --help` call, which is bounded and avoids filesystem search entirely.

## Open questions

1. What is the harness kill policy for background Bash commands — is SIGURG intentional, and at what threshold is it sent?
2. Should `scripts/lint-bare-grep-probe.sh` be extended to flag grep probes that use `../` relative paths resolving above a known safe root?

## Proposed Design Outline

### Goals
- Prevent background grep probes from scanning unbounded directories by documenting a new `../` ascent prohibition in `BASH_AUTHORING.md` and `stall-recovery.md`.
- Enforce the prohibition mechanically by extending `scripts/lint-bare-grep-probe.sh` to flag grep-family path arguments containing `../`.

### Non-goals
- Harness-level output-size or wall-clock limits (out of larch's control).
- Fixing any historical probe that already ran; guidance applies prospectively.
- Touching Python code, `cli.py`, or any non-Bash/markdown surface.

### Approach sketch
- Add a "Bounded search root" subsection to `BASH_AUTHORING.md` §1 forbidding `../` ascents from tmpdir variables in background grep probes.
- Add a one-sentence note to `stall-recovery.md` sub-step 5 (retry dispatch) referencing the `BASH_AUTHORING.md` rule.
- Extend the token-analysis loop in `lint-bare-grep-probe.sh` to detect when a path argument contains `../` and emit a new violation class; add a `# lint-bare-grep-probe: ok` suppression path for intentional uses.
- Update `lint-bare-grep-probe.sh` comments and `BASH_AUTHORING.md` to document the new suppression path.
- Add test fixtures to `skills/design/scripts/` (or the existing test harness) covering the new lint check.
