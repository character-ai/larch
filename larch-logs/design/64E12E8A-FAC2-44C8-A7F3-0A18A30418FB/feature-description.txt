### Item 1 — Step 3 composite path arms bg-wait before stale cleanup (latent) — CONFIRMED LIVE

**File**: `python/larch/implement/dispatch_commit_route.py` (`checks_commit_route_main` → `_optional_bg_wait_marker`)

The live Step 3 composite path arms the bg-wait marker through `checks_commit_route_main` / `_optional_bg_wait_marker` without first clearing the stale `.completed/step-3-terminal` sentinel or the `bg-poll-guard-probe-denials.step-3-terminal.count` probe-denial counter. `run_step_checks_main` (fixed in #6321) clears both before arming; the composite route should do the same so a resumed tmpdir does not release hook denial early. With a leftover sentinel, `marker_step_completed` treats the new wait as already finished and hook denial can stay off on resume.

**Fix**: in `checks_commit_route_main` (or `_optional_bg_wait_marker`), clear `.completed/step-3-terminal` and `bg-poll-guard-probe-denials.step-3-terminal.count` before arming the step-3 marker, matching `run_step_checks_main` and `design_core._bg_wait_marker_context`.

*(Duplicate source #6305 — "Live Step 3 composite still skips FINDING_5 pre-arm cleanup" — is fully covered by this item.)*

### Item 2 — Step 3 timeout semantics differ by entrypoint (latent) — CONFIRMED LIVE

**Files**: `python/larch/implement/dispatch_commit_route.py` (`checks_commit_route_main` uses `TIMEOUT_S=15600`; `run_step_checks_main` uses `TIMEOUT_S=10800`), `skills/implement/scripts/run-step-checks.sh`

`checks_commit_route_main` uses `TIMEOUT_S=15600`; `run_step_checks_main` and `run-step-checks.sh` use `TIMEOUT_S=10800`. The hook bg-wait timeout depends on which entrypoint arms the marker, making timeout behavior inconsistent.

**Fix**: align `checks_commit_route_main`'s step-3 marker timeout with `run_step_checks_main` and `run-step-checks.sh` (`TIMEOUT_S=10800`), or document the intentional difference.

**File**: `scripts/test-hook-clone-ownership-parity.sh`
