## Findings

### 1. Per-step `--budget-s` mapping (correctness)

The plan moves killing authority into `bgjob` daemons (`python/larch/bgjob/daemon.py` `_monitor`, lines 110–139) but does not pin `--budget-s` per migrated step. Today’s timeouts live in marker `TIMEOUT_S` fields and `dispatch_commit_route.py`:

```87:93:python/larch/implement/dispatch_commit_route.py
def _checks_commit_route_marker(checks_site: str) -> tuple[str, int, str] | None:
    if checks_site == "step3":
        return config.CHECKS_COMMIT_ROUTE_MARKER_STEP3, CHECKS_COMMIT_ROUTE_OUTER_TIMEOUT_MS // 1000, ".completed/step-3-terminal"
    if checks_site == "step5-self-review":
        return config.CHECKS_COMMIT_ROUTE_MARKER_STEP5_SELF_REVIEW, 14700, ".completed/step-5-self-review-terminal"
```

Step 8 and Step 3 design review use 21600s (`skills/implement/scripts/step-8-ship.sh:114-115`, `skills/design/scripts/design-step3-review.sh:168`). Step 5 resume uses 32700s (`dispatch_commit_route.py:943-947`). Without a budget table in the plan, wrappers can easily under-budget long steps and produce `BGJOB_RC=timeout` (`python/larch/core/config.py` `BGJOB_RC_TIMEOUT`), which must not reach success routing.

**Suggested revision:** Add one normative budget table to `skills/shared/bgjob-wait.md` (or Approach), sourced from existing constants rather than new magic numbers.

---

### 2. Step 6 in-flight must use liveness, not registry presence (correctness)

The plan updates `python/larch/design/design_step6.py` but current `_step6_in_flight` only checks `.bg-wait-active` (lines 49–65). The replacement logic must call `registry.daemon_liveness` / `registry.child_liveness` (`python/larch/bgjob/registry.py:162-173`), not `registry.read_for` file existence alone.

`python/tests/design/test_design_lifecycle.py` `test_step6_in_flight_signal_matrix` (4765+) covers marker/sentinel/sidecar cases but not a **dead** registry row. After `bgjob wait` returns `DEAD`, a stale registry file could falsely block Step 6 if implementation only checks path presence.

**Suggested revision:** Implement liveness via a shared helper in `design_core.py`; extend `test_design_lifecycle.py` with dead-registry → not-in-flight.

---

### 3. Step 8: gate `route-exit` on `BGJOB_RC=0` (risk-integration)

`python/larch/bgjob/wait.py` returns `BGJOB_STATUS=DONE` whenever a result env exists (52–56), including `BGJOB_RC=timeout` and `BGJOB_RC=orphaned` written by `_monitor` (`daemon.py:121-132`). The plan says keep `ship route-exit` byte-compatible, but Step 8 orchestration still describes handoff probing via `.step-8-ship-handoff.rc` after `<task-notification>` (`skills/implement/SKILL.md:604-641`).

**Suggested revision:** In `skills/implement/SKILL.md` Step 8 and `ship-pr-exit-matrix.md`, document the ordered gate: `bgjob wait` → `BGJOB_STATUS=DONE` **and** `BGJOB_RC=0` → read `.step-8-ship-handoff.rc`/`.json` → `ship route-exit`. Never call `route-exit` on `timeout`, `orphaned`, or `DEAD`.

---

### 4. Step 5: do not parse review KVs without `BGJOB_RC=0` (correctness)

Step 5 is the other high-risk lifecycle surface. The plan removes `.step5-wrapper-detached` re-entry (`skills/implement/scripts/step-5-review.sh`, `test-step-5-review.sh`) and delegates owner death to the daemon (`test_daemon.py` `test_monitor_uses_recorded_child_identity_on_orphan`). That produces `BGJOB_RC=orphaned` in the result env, surfaced as `DONE` by `wait.py`.

Implement SKILL still says to parse `STEP5_REVIEW_STATUS` after notification (488–495). Without an explicit `BGJOB_RC` gate, a timed-out or orphaned review could be treated as `complete` and violate NEVER #4.

**Suggested revision:** Add a Step 5-specific branch in `skills/implement/SKILL.md` and `self-review.md`: parse `STEP5_REVIEW_STATUS` only after `BGJOB_RC=0`; route `timeout`/`orphaned`/`DEAD` to stall or Step 18 without entering Step 6.

---

### 5. `bgjob wait` exit code vs stdout (correctness)

`cli.wait_main` returns exit 0 for `DONE`, `WAIT`, and `DEAD` (`python/larch/bgjob/cli.py:69-87`). The shared contract in `skills/shared/bgjob-wait.md` focuses on stdout KVs but does not warn that exit 0 is not success.

**Suggested revision:** One sentence in `bgjob-wait.md` and a harness assertion: only `BGJOB_STATUS=DONE` with `BGJOB_RC=0` (plus required step KVs) authorizes continuation.

---
