## Edge cases

- `BGJOB_STATUS=WAIT` must cause the next identical `bgjob wait` with no intervening prose or tools.
- `BGJOB_STATUS=DEAD` must not parse stale step stdout as success.
- `DONE` with `BGJOB_RC=timeout` or `BGJOB_RC=orphaned` must route to failure or stall.
- `bgjob wait` shell exit 0 on `WAIT` or `DEAD` must not advance the step.
- Existing sentinels may exist from prior attempts. Result env plus identity-checked registry state must decide current completion.
- Stale merge-result env from a prior attempt must not satisfy required KVs after a fresh start; truncate before each `bgjob start`.
- Step 6 must not treat Step 5c as idle when the terminal sentinel is absent and a live identity-valid `design-step5c` registry row exists; dead registry rows must not block Step 6.
- Step 5 re-entry must rejoin a live registry row via `bgjob wait` and must not launch a second loop daemon.
- Step 8 must write handoff rc/json before any route-exit handling sees the result.
- Recycled PID or PGID must never be signaled. Use identity-checked helpers only.
- Retained legacy hooks must remain functional for #6516, but migrated paths should not trip them.

## Failure modes

- Wrapper stdout gains banners and breaks harness parsing.
- A prompt path continues on `DONE` without checking `BGJOB_RC`.
- A result env omits a required legacy KV, causing false success or false stall.
- Stale merge-input env satisfies KVs after `BGJOB_RC=0` without fresh child output.
- Step 3 normalize still reads `.step3-review-result.env` and misses `BGJOB_RC` or fresh loop status.
- Step 5 detach sidecars are removed before bgjob owner-death and re-entry tests cover the replacement.
- Step 5 resume path remains on legacy direct launch because `step-5-resume.sh` or `step5-review-branches.md` were not migrated.
- Checks repair-loop still relaunches bare composites and bypasses bgjob wait.
- Step 6 treats dead registry presence as in-flight and blocks cleanup forever.
- Step 8 handoff sidecar ordering changes and breaks `ship route-exit`.
- `test-design-structure.sh` still pins notification-recovery literals and fails CI after skill migration.
- Allowlist shrinks before all skill prose is migrated, causing lint failure.
- Hook tests are over-pruned and accidentally delete #6516 compatibility coverage.

# Migrate remaining run_in_background call sites to bgjob start/wait (part 2)

## Context

PR #6522 (closed #6514) landed part 1 of the bgjob migration: the `python3 python/cli.py bgjob {start,wait,status,reap}` transport (`python/larch/bgjob/`), the PreToolUse deny hook `scripts/hook-deny-run-in-background.sh`, the inverse `lint bg-wait-coverage` with the reason-bearing allowlist `python/larch/lint/bg_wait_allowlist.txt`, the shared wait contract `skills/shared/bgjob-wait.md`, and session-start reaping in `scripts/cleanup-sessionstart.sh`.

Part 1 deliberately did not convert the call sites. Every long-running larch step still launches via Bash `run_in_background: true` and waits on `&lt;task-notification&gt;`. The 13 allowlist entries carry that legacy prose, and the legacy marker/notification machinery is still live in 11 Python modules. This issue converts all of it to `bgjob start` plus chunked `bgjob wait`.

Issue #6516 (delete the spurious-task-notification defense stack) assumes this migration is complete ("nothing in larch launches Bash `run_in_background` tasks"). #6516 must stay blocked on this issue. Part 1 left the defense stack functional but inert so this PR and #6516 stay independently revertable; this issue must also leave it functional.

## Binding contract per migrated site

`skills/shared/bgjob-wait.md` is the single normative wait contract. Apply it uniformly:

- Wrapper bodies keep their names, rehydrate and arm step preconditions, then `exec` the real work under `bgjob start --step &lt;name&gt; --tmpdir "$TMPDIR" --budget-s &lt;n&gt; -- &lt;command...&gt;`. Harness-visible wrapper stdout is exactly the one `BGJOB_STATUS=STARTED STEP=&lt;name&gt; PGID=&lt;n&gt;` line. Banners and breadcrumbs move to orchestrator prose or daemon logs.
- Orchestrator prose replaces every "immediate-background + wait for `&lt;task-notification&gt;`" instruction with: foreground `bgjob start`, then loop `bgjob wait --max-wait-s 270` with tool timeout `330000`. On `WAIT`, the next action is another identical `bgjob wait` with no prose, `Read`, `TaskOutput`, `Monitor`, or sleep between waits. On `DEAD`, route through the step's existing failure or stall handling. On `DONE`, continue only when `BGJOB_RC=0` and the step's required KVs are present; `BGJOB_RC=timeout`, `BGJOB_RC=orphaned`, any other non-zero value, or missing required KVs route through the step's existing failure or stall handling.
- Each step's existing result KV block merges into `$TMPDIR/bgjob/&lt;step&gt;.result.env` (the `--merge-result-env` input to `bgjob start`), and the result env is the completion source of truth.
- Existing terminal sentinels keep being written during this issue (`.completed/step-3-terminal`, `.completed/step-5-terminal`, `.completed/step-5c-terminal`, `.completed/step-4`, `.completed/step-final-summary`, `.completed/step-7a-terminal`, `.step-8-ship-handoff.rc` / `.json`). Routing contracts stay byte-compatible; sentinel retirement belongs to #6516.
