# Scope progress breadcrumbs per run ID so each run starts with empty statusline

## Problem

The statusline feature landed via #6624 (PR #6664) with deliberate per-clone scoping. This issue upgrades that scoping decision after live operator experience.

The statusline breadcrumb log is scoped per clone but shared across runs. The path is `~/.cache/larch/progress/&lt;sha256(clone-root)[:16]&gt;.log`. Writes are append-only. No run start ever resets the file.

Result: when the operator starts a new `/design` or `/implement`, the statusline tails the previous run's final breadcrumb. Example: `larch 21:12: [implement 5] reviewers 7/12 done (stale 41m)`. A fresh run at Step 0 renders as if it were mid-review. The stale state survives Claude Code restarts because it lives on disk, keyed by clone path.

Worse: the live-bgjob bypass in `_age_suffix` (`python/larch/report/statusline.py:92-104`; the bgjob check at lines 99-100 runs before the hide threshold) strips the `(stale Nm)` marker as soon as the new run spawns its first background job. Prior-run leftovers then render as live progress.

## Requirements (operator, hard)

1. The breadcrumb log must be private to the unique run ID within a particular clone. Different run IDs in the same clone must not share a log. Different clones already do not share one.
2. Each run's log starts empty. This follows from requirement 1.
3. Layout: the breadcrumb file lives under a unique run-id subdirectory. No flat clone-level log file.

## Current mechanics

- Writers call `append_breadcrumb(Path.cwd(), skill, step, text)`. Call sites: `python/larch/review/review_core_body.py`, `python/larch/review/review_and_fix.py`, `python/larch/review/plan_review.py`, `python/larch/implement/ship_merge.py`, and ship_state. The path comes from `progress_file.progress_path` (`python/larch/report/progress_file.py:50-55`) via `consumer_repo_root`.
- Reader: `cli.py progress statusline` (`python/larch/report/statusline.py`) resolves the session cwd from the Claude Code stdin payload and tails the clone-hash file. Installed launcher: `~/.cache/larch/statusline.sh`, refreshInterval 2.
- Cleanup: day-scale retention only (`cleanup_old_progress_files`; `/cleanup` skill).

## Proposed design (for /design to vet)

Prefer the explicit-key option over mtime heuristics.

- New layout: `~/.cache/larch/progress/&lt;clone-hash&gt;/&lt;run-id&gt;/breadcrumbs.log`. Each run owns a subdirectory; the log lives inside it. Future per-run progress artifacts can join it, and removing one directory cleans a whole run.
- Add a per-clone pointer file `~/.cache/larch/progress/&lt;clone-hash&gt;/current` holding the active run ID. Write it atomically (temp file plus rename) at run start in Step 0 of `/design` and `/implement`. The run ID already exists there (session-env / tmpdir key).
- Writers keep their signature. `append_breadcrumb` resolves the clone-hash dir from cwd, follows the pointer, and appends inside the active run-id subdirectory. Missing pointer: best-effort no-op. This preserves the fail-silent contract and needs no run-id plumbing through review or ship call sites.
- Reader follows the pointer to `&lt;clone-hash&gt;/&lt;run-id&gt;/breadcrumbs.log`. Missing pointer, subdirectory, or file renders nothing. Keep file-mtime age and the clone-filtered bgjob liveness check. Both become run-scoped because prior runs' files are never selected.
- `cli.py progress note` gains an optional `--run-id` override for pointer-independent writes.
- Update the retention sweep to reap aged run-id subdirectories. The reader ignores legacy flat `&lt;clone-hash&gt;.log` files; retention reaps them too.
- Rejected alternative: storing the log in the run's session tmpdir. That reintroduces tmpdir discovery in the reader, the #4661 bug class that #6624 deliberately retired.
- Update `docs/progress-reporting.md`, `python/tests/report/test_progress_statusline.py`, and the sessionstart/bootstrap install tests as needed.
