# [BUG] Unify per-tool Codex/Cursor startup serial locks into one shared mutex (macOS…

## Summary

The Darwin external-CLI startup serial lock is **per-tool**, but the resource it protects (the macOS Keychain) is **shared across tools**. `external_serial_lock_acquire(tool)` builds a lock path that embeds the tool name, so Codex and Cursor acquire two independent mutexes (`/tmp/larch-codex-serial-$USER.lock` and `/tmp/larch-cursor-serial-$USER.lock`). The lock therefore serializes only same-tool startups (codex-vs-codex, cursor-vs-cursor) and provides **zero** serialization for the cross-tool case (codex-vs-cursor) that the larch panels create on every round. Request: unify the per-tool locks into one shared, tool-independent startup mutex and clean up the surrounding code, docs, and tests.

## Original report

unify and clean up the above mutex locking

Context (from the investigation that prompted this report): the per-tool serial lock surfaced while root-causing reviewer-scheduling anomalies in a `/design` plan-review run (one Codex slot hitting the 1860s timeout in round 1; a Codex generic reviewer running a serial auth-retry after its first attempt in round 2). The serial lock itself is not the primary cause of those, but inspecting it revealed the per-tool-vs-shared mismatch documented here.

## Reproduction scenario

The race is probabilistic, so this is a "make it likely," not a deterministic repro.

1. On macOS (Darwin), with both Codex and Cursor configured.
2. Run any flow that launches Codex and Cursor external CLIs concurrently at startup. The most direct is the `/design` Step 3 plan-review panel, whose `dispatch-with-waterfall.sh` phase 1 launches all present-tool reviewer slots in parallel (round 1: 4 Cursor + 4 Codex; round 2: 4 Cursor + 1 Codex-generic). `/review` and `/implement` reviewer panels launch the same way.
3. Observe that `/tmp/larch-codex-serial-$USER.lock` and `/tmp/larch-cursor-serial-$USER.lock` can be held simultaneously, i.e., a Codex startup and a Cursor startup run their auth/Keychain-touching startup at the same instant.
4. Under load this surfaces as Cursor "Security process exited with code: 45" startup failures and/or empty-startup failures that trip the bounded auth-startup retry wrapper.

Deterministic confirmation of the lock topology does not need the race: inspect the two lock paths in the code (below) and confirm the tool name is in the path.

## Expected behavior

One **shared, tool-independent** startup mutex so that **any** two external-CLI startups serialize against each other, regardless of tool or launcher implementation. Because the macOS Keychain is a single per-user resource, a Codex startup and a Cursor startup that both touch it must not run concurrently. A single lock (e.g. `/tmp/larch-external-serial-$USER.lock`) also makes the Python launcher (`python/agents.py`) and the Bash launcher (`scripts/lib-external-launcher-common.sh`) serialize against each other for the cross-tool case, which per-tool paths never do today.

## Observed behavior

Two independent per-tool locks. Codex and Cursor startups never serialize against each other. The lock only serializes same-tool concurrency. The cross-tool Keychain race the lock was introduced to prevent is left unguarded, which is exactly the concurrency the reviewer panels create.

## Root cause analysis

The lock path embeds the tool name in both implementations:

- Python `external_serial_lock_acquire` (`python/agents.py`): `lock_path = Path(f"/tmp/larch-{tool}-serial-{user}.lock")`.
- Bash `external_serial_lock_acquire` (`scripts/lib-external-launcher-common.sh`): `lock_path="/tmp/larch-${tool}-serial-${USER:-larch}.lock"`.

The introducing commit (#1986, "Generalize external CLI startup serialization") is internally inconsistent: it chose **per-tool** locks ("Add shared external launcher helpers for Darwin **per-tool serial locks**") yet justified them by a **shared** resource ("Apply external_serial_lock_acquire/release_after to codex **and** cursor probe spawns … **so concurrent health probes do not race the macOS keychain**"). A per-tool lock cannot serialize a shared resource across tools.

**Inference vs. observation.** Observed: the lock is per-tool; Cursor reads the Keychain via `security find-generic-password -a cursor-user -s cursor-access-token`; Cursor's auth-failure regex includes `keychain` / `Security (process exited with code|command failed)`; Codex's auth-failure regex does **not** mention the Keychain (Codex auth is `OPENAI_API_KEY` env-key or file-based `CODEX_HOME`). Inference: whether the per-tool split is an active bug or merely redundant hinges on whether the **codex binary itself** touches the login Keychain at startup. The introducing commit's author explicitly assumed it does (they wrapped Codex spawns "so concurrent health probes do not race the macOS keychain"). If Codex does touch the Keychain, per-tool locks are a real bug; if Codex never touches it, the Cursor lock alone already serializes the sole Keychain client and the split is harmless-but-redundant. Either way, the design's own stated intent calls for one shared lock, and unifying is strictly safer.

## Evidence

- `python/agents.py` — `external_serial_lock_acquire(tool)` builds `f"/tmp/larch-{tool}-serial-{user}.lock"`; `external_serial_lock_release_after` schedules `rmdir` after `LARCH_EXTERNAL_SERIAL_LOCK_DELAY` (default 0.5s), so the lock is a startup/spawn guard, not a whole-run lock. Acquired at 7 call sites (cursor probe, codex probe, `_run_external_agent_with_auth_retries`, codex/cursor negotiation, and the review launch path).
- `scripts/lib-external-launcher-common.sh` — `external_serial_lock_acquire` builds `"/tmp/larch-${tool}-serial-${USER:-larch}.lock"` (mkdir-based mutex, TTL 30s, up to 300 tries); `external_serial_lock_release_after` disowns a delayed `rmdir`. Mirrors the Python path token-for-token (`larch-${tool}-serial`).
- Both implementations use the identical per-tool template, so a Python-launched tool and a Bash-launched **same** tool do serialize, but **no** combination of Codex+Cursor ever serializes.
- Commit #1986 message: "per-tool serial locks" + "so concurrent health probes do not race the macOS keychain."
- `SECURITY.md` ("External CLI startup locks"): the lock "only reduces concurrent CLI startup/auth races" and is "a reliability mechanism, not an authorization boundary." (Confirms purpose; confirms this is a reliability bug, not a security issue.)
- Cursor Keychain access: `python/agents.py` `cursor_auth_preflight` / `cursor_preread_service_token` call `security find-generic-password -a cursor-user -s cursor-access-token`.
- Auth-failure classification (`_AUTH_RE` in `python/agents.py`): the `cursor` pattern includes `keychain.*(not found|failed)` and `Security (process exited with code|command failed)`; the `codex` pattern does not.
- The reviewer panels launch tools concurrently: `scripts/dispatch-with-waterfall.sh` phase 1 backgrounds every present-tool slot, so Codex and Cursor startups overlap in `/design` Step 3, `/review`, and `/implement`.

## Affected files

- `python/agents.py` — implementation: `external_serial_lock_acquire`, `external_serial_lock_release_after`, and the 7 acquire call sites. Primary fix site (drop `{tool}` from the path).
- `scripts/lib-external-launcher-common.sh` — Bash twin of the lock. Must change in lockstep with the Python path and stay byte-identical so cross-impl/cross-tool startups serialize.
- `scripts/lib-external-launcher-common.md` — `.md` contract for the Bash library; documents the lock helpers; update wording.
- `python/checks.py`, `python/review_and_fix.py` — consumers that invoke the serial-lock-guarded launch paths; verify no per-tool assumptions leak in.
- `python/test_agents.py`, `python/test_launch_review.py`, `python/test_review_and_fix.py`, `python/test_implement_dispatch.py`, `scripts/test-dispatch-with-waterfall.sh` — harnesses that pin lock behavior / set `LARCH_EXTERNAL_SERIAL_LOCK_*`; update path expectations and add a cross-tool serialization assertion.
- `.claude/rules/external-tool-launcher-parity.md` — names the "serial-lock spawn site" as a parity surface; the lock change must apply to both lanes and is covered by this rule.
- `SECURITY.md`, `docs/configuration-and-permissions.md` — document the lock path / `LARCH_EXTERNAL_SERIAL_LOCK_*` env vars; update prose to the unified path.

## Suggested fix(es)

1. **Unify the lock path.** Replace the per-tool template with a single tool-independent path in both implementations, kept byte-identical:
   - Python: `f"/tmp/larch-external-serial-{user}.lock"`.
   - Bash: `"/tmp/larch-external-serial-${USER:-larch}.lock"`.
   Keep the `tool` argument in the function signatures for now (callers pass it; it still gates the Darwin/`{codex,cursor}` guard) but stop using it in the path. Optionally rename to `external_startup_lock_*` for clarity as part of "clean up."
2. **Keep the spawn-guard semantics.** TTL (30s), tries (300), and the delayed release (0.5s) are unchanged; only the path key changes. A single lock slightly increases cross-tool startup serialization (intended), bounded by the same release delay.
3. **Tests.** Update the path literals in the harnesses and add an assertion that a Codex acquire blocks a concurrent Cursor acquire (and vice versa) on Darwin, which would have caught this.
4. **Docs.** Update `SECURITY.md`, `docs/configuration-and-permissions.md`, and `scripts/lib-external-launcher-common.md` to the unified path and the "shared across tools" rationale.
5. **Clean up.** Reconcile the commit-#1986 "per-tool" wording wherever it persists in comments; ensure the `noqa: S108` parity comment and the `.md` contract reflect the single shared path.

## Open questions

- Does the Codex CLI binary touch the macOS login Keychain at startup in larch's invocation (env-key `OPENAI_API_KEY` and/or file-based `CODEX_HOME`)? If empirically no, the unification is a safe simplification rather than a correctness fix. A quick confirmation: `sudo fs_usage -w -f filesys codex` (or dtrace) on a Codex spawn and check for `login.keychain-db` access.
- Should the lock be scoped per `$USER` only (current) or also per host boot session? Current age-based stale recovery (TTL 30s) is probably sufficient; confirm it does not over-serialize when many slots launch in one panel.
- Should the function/env-var names (`external_serial_lock_*`, `LARCH_EXTERNAL_SERIAL_LOCK_*`) be renamed to reflect "shared startup lock," or kept for backward compatibility with operator-set env vars and existing docs?

## Proposed Design Outline

### Goals
- Replace the per-tool Darwin startup lock with one shared, tool-independent mutex so any two external-CLI startups (Codex vs Cursor) serialize against each other.
- Full rename to "startup lock": helpers `external_startup_lock_*`, env vars `LARCH_EXTERNAL_STARTUP_LOCK_*`, path `/tmp/larch-external-startup-$USER.lock` (byte-identical across Python + Bash).
- Add cross-tool serialization regression coverage and update the docs/comments to the unified path + "shared across tools" rationale.

### Non-goals
- No backward-compat shim for the old `LARCH_EXTERNAL_SERIAL_LOCK_*` env vars (hard rename; breaking change accepted).
- No live macOS Keychain tracing (`fs_usage`/dtrace); proceed as a strictly-safer change.
- No change to lock semantics (TTL 30s, 300 tries, 0.5s delayed release) or to per-`$USER` scoping.

### Approach sketch
- `python/agents.py`: drop `{tool}` from the path; rename functions + env-var reads; keep the `tool` arg (still gates the `Darwin` + `{codex,cursor}` early-return guard).
- `scripts/lib-external-launcher-common.sh`: mirror token-for-token so the path literal stays byte-identical to Python; rename functions + env-var reads; update `python/checks.py`'s generated snippet.
- Update remaining call sites/consumers (`review_and_fix.py`, the ~7 acquire sites) for the renamed symbols.
- Tests: swap path/env-var literals everywhere; add a Codex-acquire-blocks-Cursor (and vice versa) Darwin assertion.
- Docs/comments: `SECURITY.md`, `docs/configuration-and-permissions.md`, `.md` contract, parity rule; reconcile the "#1986 per-tool" wording.

### Surfaces in scope
- `python/agents.py`, `python/checks.py`, `python/review_and_fix.py`
- `scripts/lib-external-launcher-common.sh` + `scripts/lib-external-launcher-common.md`
- Harnesses: `python/test_agents.py`, `python/test_launch_review.py`, `python/test_review_and_fix.py`, `python/test_implement_dispatch.py`, `python/test_agent_waterfall.py`, `scripts/test-dispatch-with-waterfall.sh`
- Docs/rules: `SECURITY.md`, `docs/configuration-and-permissions.md`, `.claude/rules/external-tool-launcher-parity.md`

### Open questions
- None. All three issue open questions resolved in Round 1 (full rename, per-`$USER` scope, strictly-safer with no empirical gating).
