The recommended approach is to **route the vendor fallback through the same per-job verification harness** that already exists in `run_per_job_local_fix_loop`, so any code dispatched by `run_ci_fix_vendor` is re-validated locally against the originally-failed CI jobs before `_stage_and_push_ci_fixes` is allowed to push. Concretely, plumb the already-parsed `ci_failed_tsv` (built at `run_evaluate_failure` line ~2085) into `run_ci_fix_vendor` as a new positional argument and persist the same fixable-jobs subset (filtered through `_per_job_argv` so only locally-reproducible jobs gate the push). After the winning tier returns at line ~1865, but before the call to `_stage_and_push_ci_fixes` at line 1870, invoke a new `_verify_failed_jobs_locally` helper that iterates the fixable-jobs list and runs `_run_per_job_command_once` per job; on any non-zero, feed that job's redacted log back into `run_captured_cmd_then_fix_loop` (re-using the existing `_run_per_job_command_capture` rerun callback and `ship-pr-ci-per-job` site label) so we get a local fix/test loop that mirrors the per-job loop, then re-verify. Only when every originally-failed fixable job passes locally does control fall through to `_stage_and_push_ci_fixes`. This is preferable to "widen verification beyond originally-failed jobs" (would amplify wall-clock cost and re-trigger `relevant-checks.sh` work already done) and to "pre-push hook inside `_stage_and_push_ci_fixes`" (which lacks the TSV in its signature and would either need a global or duplicate the classification — both worse coupling). It also avoids the empty-TSV gap by short-circuiting: when `ci_failed_count=0` or the TSV is empty we still call vendor, but `_verify_failed_jobs_locally` becomes a no-op-with-warning that delegates to `relevant-checks.sh` only (the current behavior, now explicit), so we don't silently miss verification when we have job names.

The main tradeoffs and risks center on three vectors. First, **regression of #2909/PR #2941**: the head-changed-routing chain runs `lint-fix-loop.sh:322 → ship-pr.sh:147 → run_per_job_local_fix_loop return 2 → exit_stall 10-head-changed / 12-head-changed`; the new `_verify_failed_jobs_locally` MUST mirror that exact return-2 propagation to its caller `run_ci_fix_vendor` and `run_ci_fix_vendor` must in turn translate that into a return code that distinguishes head-changed from generic failure (proposal: vendor returns 2 on head-changed, and `run_evaluate_failure` at line 2127 keys off it identically to the per-job rc=2 branch already at lines 2113-2116) — the alternative (collapsing to rc=1) would silently re-enter the vendor loop and re-introduce the #2909 bug. Second, **wall-clock bound**: with `_RCC_MAX_ITER_LOCAL=6` inner × `_max_fix=3` outer × up to 3 vendor tiers × N fixable jobs, worst-case fixable-job count must be bounded; mitigate by (a) capping `N` implicitly via the existing `ci-failed-jobs.sh` classifier (only 8 fixable job kinds in the case statement at lines 30-32), (b) breaking out of `_verify_failed_jobs_locally` on the first `head-changed` or `main-agent-required`, and (c) preserving the existing jittered backoff at lines 2140-2147 only on outer iterations (not adding a new inner sleep). Third, **partial-fix masking**: if the vendor edits one job's surface but the local re-verify catches a second job still failing, the current code would push anyway after `relevant-checks.sh` passes; the proposed verifier prevents that, but it also means a vendor that fixes 7 of 8 jobs and gets stuck on the 8th now keeps the work locally without pushing — escalation should land via the same `BAIL_REASON=ci-local-unfixable` path that `run_per_job_local_fix_loop` already uses at lines 2024-2033, so the main agent gets the same bail surface and operators see a uniform escalation contract. Finally, do not modify `relevant-checks.sh` (out of scope per Round 1) — the new verifier is additive, leaving `_stage_and_push_ci_fixes`'s `run_checks_with_lint_fix_loop` call at line 1724-1728 as the baseline gate it already is.
