## Root cause analysis

Three causes, in priority order.

**RC1: no writer records a manual recovery (data corruption, primary).** The thin recovery verbs write nothing the report reads. `pr create` emits `PR_NUMBER` only as a stdout KV (`python/larch/git/pr.py:493-498`). `merge pr` touches GitHub PR state only (`python/larch/git/merge.py`). The values the report needs are all written exclusively by the ship driver's postmerge phase, which never ran: `MERGE_RESULT` and `PR_NUMBER` in `ship-pr-state.sh`, the `post-merge-sentinel` file (`python/larch/implement/ship_pr.py:320-322`), the manifest flush to `status=done` plus `pr_number`, and the driver's own `final-report write`. Consequences chain:

- `normalized_outcome_values` keeps returning `shipping` (`python/larch/state/_normalize.py:251`), so every render before and after the merge says `shipping`.
- `_outcome_with_manifest_only_backstop` (`python/larch/report/final_report.py:636`) cannot correct it: it requires both state files to be empty and the manifest to be `done` with a `pr_number`; neither holds here.
- `_reconcile_manifest_for_terminal_report` (`python/larch/report/final_report.py:809-810`) then re-asserts `status=in-progress` because the outcome is `shipping`, cementing the wrong manifest.

**RC2: the operator-bail contract does not order recovery against Steps 16-18.** `skills/implement/SKILL.md:725` and `skills/implement/references/ship-pr-exit-matrix.md:48` end with "resume ship or merge manually" and say nothing about when Steps 16-18 may run. In this run Steps 16/16a/17 ran before recovery, and the post-merge re-render was byte-identical (still `shipping`), so `should_emit_updated_body` stayed false (`final_report.py:1040-1048`). `EMIT_BODY=false` was correct behavior given identical bytes. Had the merge been recorded before the post-merge render, the body would have changed to `merged`, `snapshot_changed` would be true, and Step 18 would have emitted the refreshed body itself.

**RC3: terminal emission does not survive a turn boundary.** The orchestrator must emit the cached Step 17 body as its final chat text (SKILL.md:830 precedence; NEVER #17 at SKILL.md:76). A user message arriving between finalize and that emission loses the emission permanently. No rule directs the orchestrator to emit the cache at the start of the next turn.
