# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature
   introduces, AND the test is proportionate to the behavior's risk and size. A test that could
   merely exist, restates existing coverage, broadens an unrelated harness, or is
   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.
   **Plan-mandated deliverable carve-out:** a test, doc, generated file, cleanup task, or
   other artifact explicitly required by the supplied implementation plan is in-scope when omitted
   from the diff. This is not a license to require optional tests or docs the plan did not mandate.
   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished
   or shipped until this is fixed"). A red or flapping default-branch CI counts as actively
   blocking verification for every run: restoring or stabilizing default-branch CI clears this
   gate. The `/implement` orchestrator, not reviewers, owns executing that repair.

Default-deny. If you are unsure whether a finding clears a gate, it does not. Unsure => Out-of-Scope
or reject => never an in-scope accept.

Out-of-Scope signals, NOT acceptance signals (real, possibly worth a future issue — never an
in-scope change here): "cleaner," "more robust," "more idiomatic," "more consistent," "more

## Summary

Typing `p` or `progress` at the Claude CLI prompt no longer prints the zero-cost progress report while a long larch phase runs. The plugin machinery still works: `scripts/hook-progress-report.sh` and `python3 python/cli.py progress report` behave correctly whenever the `UserPromptSubmit` hook fires. The regression is structural. The bgjob migration (PR #6522, 2026-07-07) replaced turn-ending `run_in_background` waits with chunked foreground `bgjob wait` fences, so the orchestrator turn stays active for the entire phase. The CLI never returns to an idle prompt, typed input is queued as mid-turn steering, and the hook never intercepts it. The feature is now unreachable exactly when it mattered most.

## Original report

The operator reports (paraphrased, details preserved): typing `p` (or `progress`) in the Claude CLI used to make the harness intercept the prompt and print, in yellow, the progress report generated and updated by the running phase job. It worked in all phases and was especially helpful for long-running ones. Key advantage: no context increase and no extra turns; the LLM was never involved. After a long string of spurious background-task notification bugs, the repo switched decisively to the bgjob library (long-running phases spawn as daemons). The spurious notifications appear gone, but the progress report feature stopped working too, most likely but not certainly due to the bgjob switch. Request: investigate, root cause, and file a detailed bug with proposed fix.

## Reproduction scenario

1. On current main (`6d32d492c`), start a long phase, for example `/implement` Step 5 code review or `/design` Step 3 plan review.
2. While the phase runs, the orchestrator repeats foreground `python3 .../cli.py bgjob wait --step &lt;step&gt; --tmpdir ... --max-wait-s 270` fences. The session shows one continuous active turn.
3. Type `p` and press Enter.
4. No yellow report appears. The CLI queues the input as a mid-turn message.

Control (verified 2026-07-08): with no active turn, the path works end to end. A synthetic live run (fake `current-implement-env-999999.sh` pointer, tmpdir, and one `v1 mark` timing-ledger row) plus `{"prompt":"p","cwd":...}` piped to `scripts/hook-progress-report.sh` produced the correct `{"decision":"block","reason":"implement: Step 5 — code review: started 0s ago\n..."}`.

## Expected behavior

Typing `p` or `progress` during a long-running phase prints the live progress report in the terminal with no context growth, no extra turn, and no model involvement, as it did before the bgjob migration.

## Observed behavior

During bgjob-migrated phases, no report prints. The typed `p` is queued and delivered mid-turn as steering when the current tool call completes; it may then land in model context instead of being blocked (inference, see below). At best a report could appear minutes late at a chunk boundary; the operator observes the feature as fully stopped. When the CLI is idle the hook still fires. In this clone an idle `p` currently renders a stale report ("Ship-PR phase: checks / stall step: 5") from a leftover `current-implement-env-*.sh` pointer whose tmpdir persists; `_discover_live_run` ranks by activity mtime and never checks run liveness. That staleness is pre-existing and minor, not a bgjob regression.

## Root cause analysis

The feature's trigger channel was the idle prompt, and the bgjob transport removed idle time during phases.

- Pre-bgjob: long phases launched via Bash `run_in_background: true`. The orchestrator turn ended right after launch, so the CLI sat idle for the whole phase. Every typed `p` was a fresh prompt submission: `UserPromptSubmit` fired, blocked, and printed at zero cost.
- Post-bgjob: phases run as detached daemons while the orchestrator holds the turn open with an unbroken chain of foreground `bgjob wait --max-wait-s 270` calls. The skill contract is explicit: on `BGJOB_STATUS=WAIT`, "the next action is the identical wait command with no intervening prose or tools". The CLI therefore never reaches an idle prompt during a phase.
- Claude Code (docs v2.1.204, checked 2026-07-08) queues input typed while the assistant works and delivers it when the current tool call completes ("Type a correction and press Enter... Claude reads it as soon as the current action completes"). The hooks documentation says `UserPromptSubmit` fires "when you submit a prompt, before Claude processes it" but is silent on queued mid-turn messages.
- Inference (upstream behavior undocumented): the queued `p` is injected into the live turn as steering text without an effective `UserPromptSubmit` block. No report prints, and the `p` consumes model context mid-wait-fence, the exact cost the feature existed to avoid.

This is a harness-interaction regression, not a defect in the hook, discovery, or rendering code. The feature loss was an unstated side effect of #6514/#6521; do not revert bgjob, since the spurious-notification fix must stand (upstream anthropics/claude-code#18544, anthropics/claude-code#39027).
