## Edge cases

- **Truncated logs:** the detector reads the same bounded tail style used for prompts. The failing command and regression rows should be near the end of a failed make target.
- **Multiple relevant targets:** if `make py-lint` stops at `complexity-baseline`, later targets do not run. The fast-fail should not claim all checks are fixed.
- **Tool failures:** missing ruff, bad JSON, bad baseline files, or baseline loader errors should not use the regression fast path unless a regression row is also present.
- **All complexity codes:** regressions on `PLR0911`, `PLR0913`, or `PLR0915` must fast-fail the same as `C901` / `PLR0912`.
- **Qualified symbols:** class-nested symbols with dots in stdout must match; bare function names must still match.
- **Nested file paths:** repo-relative paths with `/` in `{file}` (e.g. `larch/core/proc.py`) must match; flat basenames must still match.
- **No tools installed:** complexity-baseline regressions must still escalate with `complexity-baseline-regression` and `exit_code=1`, not the no-tools early return.

## Failure modes

- An overly broad regex could skip external fixers for mechanical lint failures.
- An overly narrow regex (wrong codes, missing `(new)`, slash-restricted `{file}`, or bare-name-only symbols) could miss valid complexity regression rows and preserve the current 600s timeout.
- Running the detector after the no-tools branch would drop the planned failure reason and ledger exit code on tool-less hosts.
