# [BUG] /design review-phase output hygiene: suppress already-satisfied 'Unimplemented' suggestions + remove stale reviewer breadcrumb

## Umbrella

Two `/design` review-phase output-hygiene bugs, combined because both make the `/design` review phase report accurately to the operator (the operator should never see misleading review-phase output).

- **#4884** — Step 4 "Unimplemented Plan Review Suggestions" re-lists reviewer concerns the plan already implements, because the #4849 filter dedups only by finding-identity and misses concern-level overlap satisfied by a differently-worded accepted finding. Report-side fix in `python/plan_review.py`, plus optional higher-leverage source-side reviewer-prompt hardening.
- **#4838** — a static reviewer-panel breadcrumb (`📊 Reviewers: | Cursor-Arch: ⏳ | ...`) is printed *before* the review panel launches, so it cannot reflect the real panel composition, is stale, and adds no value; remove it and audit `/design` and `/implement` for other stale breadcrumbs like it.

Different files (`python/plan_review.py` + `skills/design`; `skills/design` and `skills/implement` SKILL.md/scripts), shared goal. Both source issues' full content is preserved verbatim below.

## Source: #4884 — [BUG] /design Unimplemented Plan Review Suggestions re-lists concerns already satisfied by earlier-round applies

_Originally filed as #4884; preserved verbatim below._

## Summary

`/design` Step 4 "Unimplemented Plan Review Suggestions" lists reviewer concerns the plan **already implements**. In a real run, 5 of 7 reported "unimplemented" suggestions were already present in the plan by round 4. The #4849 fix is in place but only dedups by **finding-identity** (a rejected block whose key matches an *accepted* finding), so it misses the common case: a later-round finding that re-raises a concern already satisfied by a **different** accepted finding. The operator reads a "not done" list full of done things.

## Original report

Observed during a real `/design` run on issue #4773 (run `58D5F692-9355-4F5F-9ADF-8788AD790BF5`; design-log PR #4876, merged to main).

At Step 4 the run reported 7 "Unimplemented Plan Review Suggestions" (round 5's rejected findings, `FINDING_1`..`FINDING_7`). Cross-checking each against `plan-pre-apply-round-5.txt` (the plan after rounds 1-4, before round 5) showed 5 of the 7 were already addressed:

- `FINDING_1` asserts "the plan only removes the design-only fallback; it does not fix the unconditional jsonl-first `_top_reviewers` call." The pre-round-5 plan already contains `Remove design-only gate` plus the `_classification_tsv_available` branch. The finding factually mis-states the current plan.
- `FINDING_5` ("inline scoreboard Score ignores `accepted_weight`") — already present: `Score = sum(accepted_weight) + oos_accepted - rejected - oos_rejected`.
- `FINDING_4` ("OOS scope computed after classification row; reorder") — already present: `Reorder main tally loop: compute is_oos ... before _classification_row`.
- `FINDING_6` ("design tally comma-splits co-proposer") — already present: `split_classification_attribution(..., column="finding_reviewers", ...)`.
- `FINDING_2` ("operator copy still flat accepted-suggestion counts") — already present: the `accepted-point score` relabel.

`#4849` ("`/design` Step 3 reports already-applied findings as Unimplemented Suggestions") is marked DONE and is in the running 51.1.10 plugin (verified via `git merge-base --is-ancestor`), yet it did not prevent this.

## Reproduction scenario

Hard to reproduce deterministically (depends on a multi-round review where a later round re-raises a concern an earlier round already applied via a differently-worded finding). Observed organically; the committed run-log makes it inspectable without a re-run:

1. Read `larch-logs/design/58D5F692-9355-4F5F-9ADF-8788AD790BF5/rejected-findings.md` (the round-5 not-accepted set surfaced as "Unimplemented Plan Review Suggestions").
2. Read `larch-logs/design/58D5F692-9355-4F5F-9ADF-8788AD790BF5/plan-pre-apply-round-5.txt` (the plan after rounds 1-4).
3. Grep the pre-round-5 plan for each rejected finding's claimed-missing fix; 5 of 7 are present.

Synthetic reproduction for a regression test: build a `.step3-applied-finding-keys.tsv` ledger plus a `rejected-findings.md` where a rejected block re-states a concern whose **accepted** counterpart has a different dedup key, and assert the rejected block is still emitted (current behavior) — then assert it should be suppressed or annotated (desired).

## Expected behavior

The Step 4 "Unimplemented Plan Review Suggestions" report should not present concerns that the final plan already satisfies. A rejected finding whose concern is already implemented (by any accepted finding, regardless of wording) should be suppressed, or clearly annotated as "already addressed by the plan," so the label "Unimplemented" only ever means a genuine, deliberately-unaddressed gap.

## Observed behavior

Rejected findings that re-raise already-implemented concerns are emitted verbatim under "Unimplemented Plan Review Suggestions." The panel itself behaves correctly (it votes these down because they are redundant); the defect is purely in the **report**: voted-down-because-already-done findings are mislabeled as unimplemented gaps.

## Root cause analysis

Two compounding causes; primary is the report filter.

**1. Identity-keyed filter misses concern-level overlap (primary).** The #4849 fix lives in `python/plan_review.py`:

- `emit_rejected_findings` (around line 1216) reads `rejected-findings.md` and filters it through `_filter_rejected_findings_body`.
- `_filter_rejected_findings_body` (around line 1193) drops a block only when `_finding_dedup_key(block)` is in the `applied` set.
- `applied` comes from `_read_all_applied_finding_keys` (around line 1150), which is the cumulative ledger of **accepted** finding keys (`.step3-applied-finding-keys.tsv`).

So the filter suppresses a rejected block **only when the same finding identity was accepted in some round**. When a later-round reviewer re-raises a concern that an earlier round already implemented via a **different, differently-worded** finding, the rejected block's `_finding_dedup_key` differs from the accepted finding's key, is not in `applied`, and is emitted. `_finding_dedup_key` is a per-finding normalized key, not a semantic/concern match, so cross-wording overlap is invisible to it.

**2. Reviewers re-flag completed work (contributing).** Later-round reviewers raised findings that mischaracterize the current plan (`FINDING_1` claims the plan "only removes the design-only fallback" when it demonstrably does the full `_classification_tsv_available` branch). They appear to review against a stale or misread plan and flag already-done work, which is what generates the redundant rejected findings in the first place. Worth confirming later-round reviewers receive the latest `plan.txt` and adding a prompt instruction to verify a concern is not already addressed before raising it.

## Evidence

- Verified ancestry: `git merge-base --is-ancestor <Fixes #4849 commit> HEAD` → true; #4849 fix is in 51.1.10.
- `python/plan_review.py` lines ~1150-1264: `_read_all_applied_finding_keys`, `_filter_rejected_findings_body`, `emit_rejected_findings`. The filter predicate is `key and key in applied`, where `applied` = accepted-finding keys only.
- Run `58D5F692-9355-4F5F-9ADF-8788AD790BF5` committed artifacts on main: `rejected-findings.md` (the 7 surfaced findings) and `plan-pre-apply-round-5.txt` (already contains the `FINDING_1/2/4/5/6` fixes).
- Review Phase Detail for the run: rounds accepted 7, 8, 5, 2, 1 (round-sum 23 vs ~10 distinct), 5 rounds to the cap, plan grew 172 → 370 lines — consistent with the re-raise churn dynamic of #4808/#4809 feeding redundant findings into the rejected report.

## Affected files

- `python/plan_review.py` — `emit_rejected_findings`, `_filter_rejected_findings_body`, `_read_all_applied_finding_keys`, `_finding_dedup_key`. The Step 4 report filter that under-suppresses.
- `skills/design/SKILL.md` Step 4 and `skills/design/scripts/design-step3b-tail.sh` / `.md` — the wrapper that emits the rejected body between `---LARCH-REJECTED-BEGIN---` / `---LARCH-REJECTED-END---`.
- Per-round reviewer prompt / latest-plan handoff in the plan-review loop (`python/plan_review.py` round dispatch) — the source of the redundant re-raised findings.
- `python/test_plan_review.py` — add regression coverage for concern-level (not just identity-level) suppression.

## Suggested fix(es)

- **Report-side (primary):** broaden Step 4 suppression beyond identity match. Options: suppress any rejected finding whose concern is covered by the current plan, or annotate such findings as "already addressed" rather than "Unimplemented." A purely mechanical fix is hard (semantic overlap), so consider: (a) suppress rejected findings that were voted down with a "already done / redundant" rationale, (b) only surface a rejected finding as "Unimplemented" when it was *newly raised* and the plan does not already mention its target surface, or (c) relabel the whole section to make clear these were considered-and-not-applied, not gaps.
- **Source-side (contributing):** confirm later-round reviewers get the latest `plan.txt`; add a reviewer-prompt instruction to verify the concern is not already addressed in the current plan before raising it. This reduces redundant re-raises at the source and is the higher-leverage fix.
- Add `python/test_plan_review.py` coverage: a rejected block whose concern is satisfied by a different accepted finding (different dedup key) must not appear in the Step 4 emit.

## Open questions

- For `/design`, is the right fix report-side suppression, source-side reviewer-prompt hardening, or both? Source-side likely has higher leverage (it also reduces wasted review rounds and cost).
- Should "Unimplemented Plan Review Suggestions" be relabeled to avoid implying a real gap when the entries are considered-and-rejected redundancies?
- Is the round-sum churn (23 accepted across 5 rounds, plan doubling, run to cap) a separate issue worth filing under #4808's umbrella, or is it the same root re-raise dynamic? (Noted here as context; not the focus of this bug.)
