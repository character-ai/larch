## Approach

1. Persist publish progress after each irreversible phase:
   - Initialize the result env for the current attempt before publish work starts.
   - Rewrite it after the plan write, tracking-issue rename, and log-publish attempt.
   - Record `PLAN_WRITE_OK`, `RENAMED`, `LOG_PUBLISH_ATTEMPTED`, `LOG_PUBLISH_COMPLETED`, `PUBLISH_OK`, and known issue, branch, and PR fields.
   - Ensure every returned rc-5 path leaves current state. Let result-env write failures surface instead of silently retaining an earlier attempt.

2. Distinguish rc-5 sources:
   - Emit `PUBLISH_RC_SOURCE=returned` when `publish_core` returns rc 5.
   - Emit `PUBLISH_RC_SOURCE=exception` before printing a mapped exception traceback.
   - Preserve the first traceback line and bounded stdout and stderr tails under `DESIGN_TMPDIR`.

3. Build one bounded failure-detail artifact:
   - Include the exit code, rc source, latest publish phase, progress flags, first traceback line, and stderr tail.
   - Keep separate bounded stdout and stderr tail files for committed run-log diagnosis.
   - Reject unsafe paths and line-oriented env values.
   - Keep all public output behind existing sensitive-corpus and redaction checks.

4. Stage accurate terminal state:
   - Read the current allowlisted result env even for terminal rc values.
   - Copy validated progress and identity fields into terminal state.
   - Write `.design-step5c-status.env` through the existing guarded writer and verify the non-empty status contract.
   - Preserve the rc-4 assessment refusal and retry behavior unchanged.

5. Classify publish-tail failures from structured state:
   - Add a specific publish rc-5 and `publish-tail-failed` classifier pattern.
   - Use `recoverable` with resume hint `design-rename-log-flush` when `PLAN_WRITE_OK=true`.
   - Keep failures before plan write terminal unless another existing classifier applies.
   - Thread tracking issue, recovery branch, PR, progress, and rc-source fields into the classification and report.

6. Reconcile a later salvage in the same run:
   - Use the approved terminal reporting pass in `design_terminal.py` as the reconciliation hook.
   - Before the existing terminal-sentinel skip, detect a prior `failed-publish-tail` report from the same `DESIGN_TMPDIR`.
   - Require current, validated evidence that the plan wrote, the issue reached `[DESIGNED]`, and log publish completed.
   - If the sentinel records a newly filed report issue, post a bounded marker-keyed recovery comment, close it, and re-read its state.
   - Record reconciliation success in a durable sentinel so re-entry is idempotent.
   - Do not close an unrelated issue found through dedup. Record a recovery comment only when the existing report contract identifies it safely.
   - On reconciliation failure, keep the design outcome successful, append an execution issue, and leave the report open for operator review.

## Edge cases

- A new attempt fails before creating its first checkpoint. The fresh initial state must still replace any stale refusal env.
- The plan writes, but the process raises before rename. Classification is recoverable with both remaining phases in the hint.
- Rename succeeds but emits incomplete stdout. Record only validated rename evidence.
- Log publish creates a recovery branch or PR and then returns nonzero. Preserve those identifiers with `PUBLISH_OK=false`.
- Result-env persistence itself fails. Keep the captured exception diagnostic and do not trust the old env.
- Captured output contains secrets, control characters, invalid UTF-8, or tmpdir paths. Bound local files and require redaction before egress.
- A later approved pass sees a terminal report but lacks all recovery markers. Leave the report open.
- The terminal report was a dedup comment on a pre-existing issue. Do not close that issue as if this run created it.
- Reconciliation runs twice. The durable reconciliation sentinel prevents duplicate comments and closes.
- GitHub reports a successful close but the follow-up read shows the issue open. Record the mismatch and retain retryable local evidence.

## Failure modes

- If tail persistence fails, append a bounded execution issue and retain the generic terminal detail rather than suppressing the original publish failure.
- If terminal-state validation rejects a new field, fall back to the existing safe report path and expose the validation failure.
- If sensitive-corpus population or redaction fails, do not file, amend, close, or publish diagnostic text.
- If salvage reconciliation cannot resolve the report issue number or repository, keep the report open and record the reason.
- Do not convert reporting failures into `/implement` retries or alter design publish retry caps.
