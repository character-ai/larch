## Approach

1. Persist current publish state throughout every attempt:
   - Initialize a fresh result env before publish work starts so prior rc-4 refusal state cannot survive into a new rc-5 attempt.
   - Rewrite it after each completed or attempted publish phase, including plan write, difficulty-label sync, rating persistence, diagram upsert, tracking-issue rename, and run-log publish.
   - Record `PLAN_WRITE_OK`, per-phase progress, `RENAMED`, `LOG_PUBLISH_ATTEMPTED`, `LOG_PUBLISH_COMPLETED`, `PUBLISH_OK`, `PUBLISH_RC_SOURCE`, and known issue, branch, and PR fields.
   - Ensure every returned rc-5 path leaves current state. Result-env write failures must surface to Step 5c rather than silently retaining an earlier attempt.

2. Preserve diagnostics from both the publish driver and nested subprocesses:
   - Emit `PUBLISH_RC_SOURCE=returned` when `publish_core` returns rc 5 and `PUBLISH_RC_SOURCE=exception` before printing a mapped exception traceback.
   - Preserve the first traceback line and bounded Step 5c stdout and stderr tails under `DESIGN_TMPDIR`.
   - At nested tracking-issue rename and design log-publish failure sites, persist bounded, phase-named stderr artifacts or relay their bounded diagnostic content into the Step 5c captured diagnostic stream before returning rc 5.
   - Keep separate bounded stdout and stderr tail files for committed run-log diagnosis, with safe filenames and redaction-eligible contents.

3. Build one bounded, structured failure-detail artifact:
   - Include exit code, rc source, latest publish phase, all validated progress flags, first traceback line, Step 5c stderr tail, and available failing-phase stderr tail.
   - Reject unsafe paths and line-oriented env values.
   - Keep public output behind the existing sensitive-corpus and redaction checks; raw diagnostics remain local unless scrubbed successfully.

4. Stage accurate terminal state without breaking dedicated URL and branch validation:
   - Read the current allowlisted result env even for terminal rc values.
   - Copy validated progress and identity fields into terminal state.
   - Validate branch and PR URL fields through their dedicated validators before raw-value rejection, or explicitly exempt those structured keys from the blanket raw-value check while retaining safe-token and GitHub URL-shape validation.
   - Write `.design-step5c-status.env` through the existing guarded writer and verify the non-empty status contract.
   - Preserve the rc-4 assessment refusal and retry behavior unchanged.

5. Classify publish-tail failures from structured state:
   - Add a specific publish rc-5 and `publish-tail-failed` classifier pattern.
   - Add that exact pattern to every safe matched-pattern allowlist so the classifier emits the named pattern rather than `redacted`.
   - Use `recoverable` only when validated plan-write evidence exists, with a resume hint that reruns the complete idempotent post-plan publish tail, including required label, rating, diagram, rename, and log-publish work.
   - Do not use `design-rename-log-flush` unless a future implementation records and validates completion of every required pre-rename post-plan phase.
   - Keep failures before plan write terminal unless another existing classifier applies.
   - Thread tracking issue, recovery branch, PR, progress, phase, and rc-source fields into classification and reporting.

6. Defer post-success report reconciliation:
   - Do not add GitHub report comments, report closure, remote close verification, or reconciliation sentinels in this diagnostics fix.
   - Preserve existing terminal-report dedup and escalation behavior.
   - Record later-report amendment or closure as a follow-up only if it becomes explicitly required; this change must not introduce new remote mutations after a successful salvage.

## Edge cases

- A new attempt fails before creating its first checkpoint. The fresh initial state must still replace any stale refusal env.
- The plan writes, but a later required post-plan phase fails. Classification is recoverable only through the complete idempotent post-plan resume operation.
- A required phase succeeds but its checkpoint persistence fails. Surface that persistence failure and do not trust stale progress.
- Rename succeeds but emits incomplete stdout. Record only validated rename evidence.
- A rename or log-publish subprocess returns rc 5 with an empty outer stderr capture. Preserve its bounded phase stderr artifact when available.
- Log publish creates a recovery branch or PR and then returns nonzero. Preserve those identifiers with `PUBLISH_OK=false`.
- Captured output contains secrets, control characters, invalid UTF-8, or tmpdir paths. Bound local files and require redaction before egress.
- Valid GitHub PR URLs and safe branch names must survive terminal-state validation; arbitrary URL-shaped or unsafe values must not.
- The named classifier pattern must remain visible only when it is an allowlisted structured token.
- Existing terminal reports remain unchanged after a later successful salvage; no report issue is commented on or closed by this change.

## Failure modes

- If tail persistence fails, append a bounded execution issue and retain the generic terminal detail rather than suppressing the original publish failure.
- If nested-phase capture fails, preserve available outer diagnostics and record the bounded capture failure without replacing the original publish failure.
- If terminal-state validation rejects a new field, fall back to the existing safe report path and expose the validation failure.
- If sensitive-corpus population or redaction fails, do not file, amend, close, or publish diagnostic text.
- Do not convert reporting failures into `/implement` retries or alter design publish retry caps.
- Do not add reconciliation or issue-mutation fallback behavior as part of this change.
