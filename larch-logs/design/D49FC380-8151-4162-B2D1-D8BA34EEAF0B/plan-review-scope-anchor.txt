## Defects

**1. Exit-5 publish diagnostics are lost.**
- `_step5c_invoke_publish_core` maps any exception from `publish_core` to rc 5 and prints the traceback to the captured stderr stream (`python/larch/design/design_step5c.py:331-340`).
- That stream goes to `tempfile.mkstemp(prefix="larch-publish-stderr.", dir=$TMPDIR)` (`design_step5c.py:567-572`), which is never copied into `$DESIGN_TMPDIR` and never flushed. The traceback (or the failing subprocess output) is unrecoverable after the fact; it was already gone during this investigation.
- The failure detail log written for the report is a single line, `design-publish.sh failed (exit 5)` (`design_step5c.py:208-210`), and that is all the auto-issue carried.
- The failure classifier has no rc-5 pattern, so classification fell through to `fallback`.

**2. The result env goes stale on rc-5 paths and errors are swallowed.**
- Most `return 5` sites in `publish_core` do not rewrite `.design-publish-result.env`, so the env on disk after the terminal failure was the *previous* attempt's rc-4 refusal env (`PLAN_WRITE_OK=false`, `missing-guideline-assessment`), misdescribing a run whose plan write had succeeded.
- On the one rc-5 site that does write it (`python/larch/design/design_publish.py:818-823`), `_write_result_env` swallows `OSError` and the caller ignores the result (`design_publish.py:57-62`), so a failed rewrite is silent.
- `publish_core` records no progress markers between phases, so post-mortems cannot tell how far an attempt got without the kind of forensics done here (plan-splice fingerprint, label sync, upsert artifacts, rename events).
- Minor related anomaly: `.design-step5c-status.env` was flushed as 0 bytes even though `_step5c_write_status` (`design_step5c.py:583-591`) writes 7 rows on this path.

**3. Terminal reports overstate failure and are never amended.**
- The report declared `unrecoverable` and `Attempts: none` for a failure whose remaining work was one rename plus one log flush; the same session completed both within 4 minutes, but nothing updated or closed the auto-issue.
- Branch/PR were reported `unknown` although the flush machinery knew the issue number and later produced PR #6846.

## Where attempt 2 died (bounded, not exact)

The lost stderr file is the only artifact that could pin the line. Evidence bounds it to `design_publish.py` after the diagrams upsert writes (`:1163-1173`, present with `UPSERT_STATUS=ok`) and before a successful `[DESIGNED]` rename (`:1198`, no rename event until 20:17:45). Consistent candidates: an exception in that window (e.g., subprocess spawn failure under the 3-concurrent-runs load that afternoon) mapped to rc 5, or a silently failed rename (check=False) followed by a failed `design log-publish` leg returning 5 at `:823` with the env rewrite swallowed. Both candidates are cured by the same diagnostics fixes.

## Fix directions (for /design to weigh)

1. On terminal publish rc in Step 5c, copy bounded tails of the `larch-publish-stdout.*`/`larch-publish-stderr.*` captures into `$DESIGN_TMPDIR` (so they flush) and include the stderr tail in `design-publish-tail.failure.log` and the auto-issue failure-detail section.
2. Distinguish exception-mapped rc 5 from returned rc 5, e.g. emit `PUBLISH_RC_SOURCE=exception|returned` plus the first traceback line from `_step5c_invoke_publish_core`.
3. Write phase-progress markers from `publish_core` (post-plan-write, post-rename) into the result env or a sidecar so a crash leaves accurate state instead of a stale refusal env; stop discarding `_write_result_env` failures silently.
4. Make the terminal reporter consume that progress state: when the plan write already succeeded, report class `recoverable` with a resume hint (rename + log flush), and populate branch/PR/issue fields from known state.
5. Add an rc-5 classifier pattern so these stop matching `fallback`; optionally amend/close the auto-issue when a later salvage in the same session succeeds.

## Proposed Design Outline

### Goals
- Preserve publish-failure diagnostics: keep bounded stdout/stderr tails and the exception traceback so they flush and reach the auto-issue.
- Report salvageable exit-5 runs correctly: class recoverable with a resume hint when the plan already wrote.
- Keep accurate on-disk state after a crash so post-mortems and the reporter agree.

### Non-goals
- Do not change the publish logic, retry counts, or the rc-4 fail-closed assessment gate.
- Do not change /implement retry_policy caps or auto-retry behavior.
- Do not alter the run-log flush PR machinery.

### Approach sketch
- In design_step5c.py, copy bounded publish stdout/stderr tails into DESIGN_TMPDIR before unlinking the temp captures; feed the stderr tail into design-publish-tail.failure.log; emit PUBLISH_RC_SOURCE=exception|returned plus the first traceback line.
- In design_publish.py publish_core, add phase-progress markers (post-plan-write, post-rename, log-publish leg), rewrite the result env on every rc-5 path, and surface _write_result_env failures.
- In _classify.py add a publish/rc-5/publish-tail-failed pattern; thread plan-write success into the terminal state so the reporter reports recoverable with a rename+log-flush resume hint and populates branch/PR/issue.
- Amend or close the auto-filed issue when a salvage later succeeds in the same session.
