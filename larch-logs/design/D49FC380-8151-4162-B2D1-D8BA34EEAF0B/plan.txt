## Approach

1. Make every Step 5c publish attempt state-isolated before invoking `publish_core`:
   - Invalidate or remove the prior `.design-publish-result.env` through an atomic, fail-closed operation before creating publish captures or invoking the driver.
   - If invalidation fails, do not invoke publish and do not read the prior result env; surface a visible Step 5c diagnostic and stage a safe terminal failure without publish-progress evidence.
   - Have `publish_core` atomically create a fresh baseline result env before its first publish operation. A failure to initialize or checkpoint state must propagate as a visible failure rather than leave an earlier attempt eligible.
   - Write every result-env checkpoint atomically, with the current attempt’s identity and progress values, so interrupted writes cannot leave partial or stale trusted state.

2. Route publish exit code 5 through a dedicated Step 5c terminal-failure path:
   - Keep rc 2 on the existing configuration-error early-exit behavior.
   - Change the current early-exit guard so rc 5 does not bypass `_step5c_safe_publish_env`, tail persistence, failure-detail rendering, enriched status writing, or terminal-state staging.
   - For returned rc 5, emit `PUBLISH_RC_SOURCE=returned`; for exceptions mapped to rc 5, emit `PUBLISH_RC_SOURCE=exception` before capturing the mapped traceback.
   - On rc 5, persist bounded stdout and stderr tails under `DESIGN_TMPDIR`, read only the current validated result env, render `design-publish-tail.failure.log`, write and verify `.design-step5c-status.env`, then stage terminal state.
   - Preserve rc-4 assessment refusal and documented persist-and-retry behavior unchanged.

3. Persist accurate publish progress and nested diagnostics:
   - Record `PLAN_WRITE_OK`, `PUBLISH_OK`, `RENAMED`, `LOG_PUBLISH_ATTEMPTED`, `LOG_PUBLISH_COMPLETED`, latest phase, rc source, and known issue, branch, PR, diagram, and summary fields.
   - Rewrite state after each completed or attempted phase: plan write, difficulty-label sync, rating persistence, diagram upsert, tracking-issue rename, and run-log publish.
   - Set `LOG_PUBLISH_ATTEMPTED` before `_run_log_publish_after_capture`; set `LOG_PUBLISH_COMPLETED` only after successful completion.
   - At nested tracking-issue rename and design log-publish failures, capture bounded, phase-named stderr artifacts in deterministic safe paths under `DESIGN_TMPDIR`, or relay bounded content into the outer captured stream before returning rc 5.
   - Stop swallowing `_write_result_env` failures. Preserve the original publish failure where possible, but append a bounded state-persistence diagnostic and prevent stale progress from being trusted.

4. Build one bounded structured failure-detail artifact:
   - Include exit code, rc source, latest phase, validated progress flags, first traceback line, Step 5c stderr tail, and available nested failing-phase stderr tails.
   - Keep separate bounded stdout and stderr tail files for committed run-log diagnosis, with safe filenames and redaction-eligible contents.
   - Reject unsafe paths, symlinks, multiline env values, and unvalidated artifact references.
   - Keep raw diagnostics local. Public output remains behind the existing sensitive-corpus and redaction checks and fails closed if scrubbing cannot prove safety.

5. Stage terminal state from validated current-attempt data:
   - Read the allowlisted result env on terminal rc paths only after Step 5c’s pre-invocation invalidation and only when current-attempt initialization/checkpoint provenance is valid.
   - Copy validated progress, issue, branch, PR, rc-source, and failure-detail fields into terminal state.
   - Validate branch and PR URL fields through their dedicated validators before blanket raw-value rejection, or explicitly exempt those structured keys while retaining branch-token and GitHub URL-shape validation.
   - Write `.design-step5c-status.env` through the guarded writer and verify the non-empty status contract.
   - If state validation or persistence fails, retain a generic safe terminal report path and expose the validation or persistence failure without upgrading recoverability.

6. Wire structured publish-tail classification into the actual `/design` generic profile:
   - In `_classify_generic_from_terminal_state`, branch before `_classify_text` when validated terminal state has `TRIGGER=publish-tail-failed` and `EXIT_CODE=5`.
   - Use the structured publish-tail classifier to emit the named allowlisted pattern, `recoverable`, and the complete idempotent post-plan resume hint only when validated current-attempt `PLAN_WRITE_OK=true` evidence exists.
   - Otherwise retain the generic fallback and unrecoverable behavior; stale, malformed, incomplete, or unproven progress must not upgrade the failure.
   - Do not use `design-rename-log-flush` unless a future implementation records and validates completion of every required earlier post-plan phase.
   - Thread tracking issue, recovery branch, PR, phase, rc source, and progress into classification and report rendering.

7. Reconcile a later salvage in the same run:
   - Use the approved terminal reporting pass in `design_terminal.py` as the reconciliation hook.
   - Before the existing terminal-sentinel skip, detect a prior `failed-publish-tail` report from the same `DESIGN_TMPDIR`.
   - Require current, validated evidence that the plan wrote, the issue reached `[DESIGNED]`, and log publish completed before acting.
   - If the sentinel records a newly filed report issue, post a bounded marker-keyed recovery comment, close it, and re-read its state.
   - Record reconciliation success in a durable sentinel so re-entry is idempotent.
   - Do not close an unrelated issue found through dedup. Record a recovery comment only when the existing report contract identifies it safely.
   - On reconciliation failure, keep the design outcome successful, append an execution issue, and leave the report open for operator review.

## Edge cases

- A new attempt fails before creating its first publish checkpoint. Step 5c invalidation and publish-side initialization must ensure the prior refusal env cannot be read as current state.
- Step 5c cannot invalidate the prior result env. It must not invoke publish or classify any prior progress as recoverable.
- `publish_core` cannot atomically initialize the fresh env. It must surface a visible failure and leave no stale state eligible.
- The plan writes, but a later required post-plan phase fails. Classification is recoverable only through the complete idempotent post-plan resume operation.
- A required phase succeeds but checkpoint persistence fails. Surface that persistence failure and do not trust stale progress.
- Rename succeeds but emits incomplete stdout. Record only validated rename evidence.
- A rename or log-publish subprocess returns rc 5 with an empty outer stderr capture. Preserve its bounded phase stderr artifact when available.
- Log publish creates a recovery branch or PR and then returns nonzero. Preserve those identifiers with `PUBLISH_OK=false`.
- Captured output contains secrets, control characters, invalid UTF-8, or tmpdir paths. Bound local files and require redaction before egress.
- Valid GitHub PR URLs and safe branch names must survive terminal-state validation; arbitrary URL-shaped or unsafe values must not.
- The named classifier pattern remains visible only when it is an allowlisted structured token.
- A later approved pass sees a terminal report but lacks all recovery markers. Leave the report open.
- The terminal report was a dedup comment on a pre-existing issue. Do not close that issue as if this run created it.
- Reconciliation runs twice. The durable reconciliation sentinel prevents duplicate comments and closes.
- GitHub reports a successful close but the follow-up read shows the issue open. Record the mismatch and retain retryable local evidence.

## Failure modes

- If prior-result invalidation or fresh result-env initialization fails, do not consume a prior env; stage a generic safe terminal failure with the invalidation or initialization diagnostic.
- If tail persistence fails, append a bounded execution issue and retain the generic terminal detail rather than suppressing the original publish failure.
- If nested-phase capture fails, preserve available outer diagnostics and record the bounded capture failure without replacing the original publish failure.
- If terminal-state validation rejects a new field, fall back to the existing safe report path and expose the validation failure.
- If sensitive-corpus population or redaction fails, do not file, amend, close, or publish diagnostic text.
- Do not convert reporting failures into `/implement` retries or alter design publish retry caps.
- If salvage reconciliation cannot resolve the report issue number or repository, keep the report open and record the reason.
