# [BUG] [URGENT] design-log-publish.sh: concurrent second invocation overwrites successful first run's PUBLISH_OK result, causing false failed-publish report

## Summary

When `/design` Step 5c (`design-step5c.sh`) is invoked a second time while the first invocation is still running, the concurrent-publish guard fires in `scripts/design-log-publish.sh` and the **second run overwrites the first run's successful `.design-publish-result.env`** with `PUBLISH_OK=false`. The operator sees a `failed-publish` final summary even though the design log was successfully pushed and merged, and the issue was renamed to `[DESIGNED]`.

## Reproduction

1. `/design` reaches Step 5c.
2. `design-step5c.sh` is launched as a background task.
3. Before the first invocation finishes (e.g. while it is waiting for CI checks after pushing the branch), a second `design-step5c.sh` (or `design-step5c.sh --skip-validate`) is launched.
4. The second invocation's `design-log-publish.sh` hits the concurrent-worktree guard at line 248: `git worktree list | grep -Fq " [$WT_BRANCH]"` → true → `emit_publish_result false` → `PUBLISH_OK=false`.
5. The second invocation writes `.design-publish-result.env` with `PUBLISH_OK=false`.
6. The first invocation finishes, merges the PR, renames the issue — but its own (correct) `.design-publish-result.env` was already overwritten.
7. The orchestrator reads `PUBLISH_OK=false` and shows a `failed-publish` final summary.

Observed in session `D3795C0A-A7C8-470A-AAF0-92EFF2B10F40` on 2026-06-13: logs were merged as PR #4228; issue #4217 was renamed to `[DESIGNED]`; yet final summary reported `failed-publish`.

## Root Causes

### RC-1 (primary): Concurrent-guard emits result to a shared file with no write-once protection

`design-log-publish.sh` writes its result to `$DESIGN_TMPDIR/.design-publish-result.env` (via `persist_design_log_metadata`). There is no write-once or compare-and-swap guard on that file. A concurrent second invocation overwrites a successful first invocation's result.

### RC-2 (secondary): Concurrent guard does not emit `RECOVERY_BRANCH` for `--reason final`

Lines 248–254 in `scripts/design-log-publish.sh`:

```bash
if git -C "$REPO_ROOT" worktree list | grep -Fq " [$WT_BRANCH]"; then
    larch_err "design-log-publish: branch $WT_BRANCH is already checked out in another worktree; concurrent or stale publish for this RUN_ID"
    emit_publish_result false
    if [[ "$REASON" == "pause" && "$REMOTE_BRANCH_EXISTS" == true ]]; then
        emit_kv RECOVERY_BRANCH "$WT_BRANCH"
    fi
    exit 0
fi
```

`REMOTE_BRANCH_EXISTS` is only fetched/checked when `REASON=pause` (lines 241–247). For `REASON=final` (the default for all non-pause runs), `REMOTE_BRANCH_EXISTS` is always `false`, so `RECOVERY_BRANCH` is never emitted even when the branch was already pushed by the first run. The operator cannot identify the recovery branch from the failure output alone.

### RC-3 (contributing): `design-step5c.sh` has no idempotency guard

`design-step5c.sh` does not check whether the design logs were already published (e.g. by testing `git ls-remote origin $WT_BRANCH` or reading a published-sentinel file) before invoking `design-log-publish.sh`. A naive re-invocation always triggers a full publish attempt.

## Suggested Fixes

### Fix for RC-2 (minimal, low risk)

Extend the remote-branch check to always run (not just for `REASON=pause`), and emit `RECOVERY_BRANCH` unconditionally when the remote branch exists:

```diff
-REMOTE_BRANCH_EXISTS=false
-if [[ "$REASON" == "pause" ]]; then
-    git -C "$REPO_ROOT" fetch origin "$WT_BRANCH:refs/remotes/origin/$WT_BRANCH" >/dev/null 2>&1 || true
-    if git -C "$REPO_ROOT" show-ref --verify --quiet "refs/remotes/origin/$WT_BRANCH"; then
-        REMOTE_BRANCH_EXISTS=true
-    fi
-fi
+REMOTE_BRANCH_EXISTS=false
+git -C "$REPO_ROOT" fetch origin "$WT_BRANCH:refs/remotes/origin/$WT_BRANCH" >/dev/null 2>&1 || true
+if git -C "$REPO_ROOT" show-ref --verify --quiet "refs/remotes/origin/$WT_BRANCH"; then
+    REMOTE_BRANCH_EXISTS=true
+fi
 if git -C "$REPO_ROOT" worktree list | grep -Fq " [$WT_BRANCH]"; then
     larch_err "design-log-publish: branch $WT_BRANCH is already checked out in another worktree; concurrent or stale publish for this RUN_ID"
     emit_publish_result false
-    if [[ "$REASON" == "pause" && "$REMOTE_BRANCH_EXISTS" == true ]]; then
+    if [[ "$REMOTE_BRANCH_EXISTS" == true ]]; then
         emit_kv RECOVERY_BRANCH "$WT_BRANCH"
     fi
     exit 0
 fi
```

### Fix for RC-1 (medium risk)

Add a write-once guard to `persist_design_log_metadata`: if `.design-publish-result.env` already contains `PUBLISH_OK=true`, refuse to overwrite it with a failure result. This prevents a concurrent failure from masking a prior success.

### Fix for RC-3 (medium risk)

Add an idempotency check to `design-step5c.sh` (or `design-publish.sh`): before calling `design-log-publish.sh`, test whether the remote branch already exists AND has already been merged into main (e.g. `git merge-base --is-ancestor origin/$WT_BRANCH origin/main`). If so, skip the log publish and emit `PUBLISH_OK=true`.

## Files

- `scripts/design-log-publish.sh` — lines 241–254 (RC-2 fix), `persist_design_log_metadata` (RC-1 fix)
- `skills/design/scripts/design-step5c.sh` or `design-publish.sh` — idempotency guard (RC-3 fix)
- `scripts/design-log-publish.md` — update contract to document `RECOVERY_BRANCH` emission on concurrent-final path
