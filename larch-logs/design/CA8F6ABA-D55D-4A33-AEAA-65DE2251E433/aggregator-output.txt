**Four distinct findings** — same concurrent-publish theme, but different code paths and fixes. No merges applied.

### FINDING_1: Write-once eligibility flag scope is ambiguous
- **Reviewer(s)**: Cursor-Arch
- **Severity**: important
- **Concern**: `PUBLISH_RESULT_WRITE_ONCE_ELIGIBLE` may be set only for SESSION_ID publish-tail handling and not kept true through the terminal `write_result_env_and_emit` at script exit. An implementer can clear the flag after `design-log-publish` returns while `PUBLISH_OK=false` remains in memory; the terminal write can then overwrite an on-disk `PUBLISH_OK=true`, and RC-1 fails.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Arch: Pin explicitly: set the flag true before publish-tail entry and keep it true until the terminal `write_result_env_and_emit` completes; only false when SESSION_ID is empty or PLAN_WRITE_OK is still false.

### FINDING_2: Write-once skip can leave stdout `PUBLISH_OK=false` while disk stays true
- **Reviewer(s)**: Cursor-Arch
- **Severity**: important
- **Concern**: When write-once skips the disk write, stdout can still emit `PUBLISH_OK=false` while the on-disk result env keeps `PUBLISH_OK=true`. If any caller treats captured stdout as authoritative on exit 0, a concurrent failure path can surface failed-publish semantics despite a preserved result env. `design-step5c.sh` parses file-first on exit 0, but the stdout/disk contract is underspecified.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Arch: Inside `write_result_env_and_emit` after a locked re-read decides to skip the disk write, also coerce emitted `PUBLISH_OK` and reload PR metadata before the stdout KV block, or document and test that exit 0 consumers must ignore publish stdout when the primary result env exists.

### FINDING_3: Concurrent guard persists metadata before `RECOVERY_BRANCH` is known
- **Reviewer(s)**: Cursor-Innovation
- **Severity**: important
- **Concern**: On the concurrent-worktree path, `emit_publish_result false` calls `persist_design_log_metadata` before `_PUBLISH_META_RECOVERY_BRANCH` is set. `.design-log-publish-metadata.env` can lack `DESIGN_LOG_RECOVERY_BRANCH` even when stdout emits `RECOVERY_BRANCH`.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Innovation: Mirror `emit_publish_failure`: set `_PUBLISH_META_RECOVERY_BRANCH` before persist, or `emit_kv RECOVERY_BRANCH` then call `persist_design_log_metadata` again

### FINDING_4: Publish-tail can render failed-publish after peer records success
- **Reviewer(s)**: Cursor-Pragmatic
- **Severity**: important
- **Concern**: The plan re-checks `result_env_publish_ok_is_true` before assigning `SUMMARY_OUTCOME` and staging failed-publish, but `render-final-summary.sh` runs outside the result-env lock. A fast second `design-publish.sh` can pass the re-check; the first invocation can write `PUBLISH_OK=true` before the second reaches render. The second still emits failed-publish and can overwrite an approved `final-summary.md` even though write-once later preserves the result env.
- **Suggested revisions (informational for voters; coder decides)**:
  - From Cursor-Pragmatic: Hold the result-env lock from the pre-summary re-check through `SUMMARY_OUTCOME` selection and `render-final-summary` invocation (or re-read under the lock immediately before render and skip failed-publish when `PUBLISH_OK=true`); add a concurrent interleaving regression where publish-tail B passes the re-check then A writes success before B renders
