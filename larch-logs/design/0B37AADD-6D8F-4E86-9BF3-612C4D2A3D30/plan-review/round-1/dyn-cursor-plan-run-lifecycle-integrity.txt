## Findings

### 1. code-quality / architecture — bgjob `run_id` ≠ progress `run_id` (`python/larch/bgjob/model.py:76-79`, `python/larch/report/statusline.py:85-96`, `skills/design/scripts/design-step3-review.sh:358-364`)

Approach 3 says to match registry `entry.run_id` to the active progress run. In production those IDs live in different namespaces. Bgjob `default_run_id` hashes the tmpdir (`python/larch/bgjob/model.py:76-79`). Launchers such as `design-step3-review.sh` never pass `--run-id`, so registry rows carry the hash slug. Progress activation uses the session UUID or an operator `--run-id` (`python/larch/design/design_step0.py:200-209`).

**Scenario:** Step 3 review is live. SessionStart runs with `source=resume`. The new predicate finds no registry row whose `run_id` equals the UUID in `current`, so reset clears the pointer while work continues. Reproduction item 4 in the plan (preserve B when B's bgjob is live) fails in real runs.

**Suggested revision:** Match on tmpdir-derived progress identity (read `session-id` / `LARCH_RUN_ID` from `entry.tmpdir`) or thread the activated progress run id into all `bgjob start` calls.

### 2. code-quality / correctness — `[SCOPE-REDUCTION]` resume/compact reset (`python/larch/report/statusline.py:24-25`, `python/larch/report/statusline.py:129-139`, `python/larch/report/progress_file.py:127-129`)

The plan expands `RESET_SESSION_SOURCES` to include `resume` and `compact`, replacing today's no-op behavior tested at `python/tests/report/test_progress_statusline.py:901-912`. Preservation requires a matching live in-budget bgjob. Foreground steps before the first bgjob only write via `append_breadcrumb`, which returns false when `current` is missing (`python/larch/report/progress_file.py:127-129`).

**Scenario:** Operator runs `/design`, hits context limit, and restarts with `--continue` during Step 1d (no bgjob yet). SessionStart `source=resume` clears `current`. The statusline stays blank until a new run activates, even though the same run is still active.

**Suggested revision:** Do not reset on `resume`/`compact`, or require a stronger in-progress signal than bgjob liveness. Lifecycle deactivate at terminal boundaries already addresses finished-run stale status on resume (issue scenario 2) with less surface area.

### 3. code-quality / correctness — pause `RUN_ID` vs custom `--run-id` (`python/larch/design/design_pause.py:195-209`, `python/larch/design/design_step0.py:200-209`)

Pause-save sets `RUN_ID` from `SESSION_ID` in `source-env.sh`. Step 0 may activate a different `--run-id`. Compare-and-clear deactivation then fails to clear the pointer the run actually activated.

**Suggested revision:** Resolve the pause/deactivate run id from the same persisted activation source Step 0 uses, not `SESSION_ID` alone.

### [OUT_OF_SCOPE] Finalize kill order (`python/larch/state/finalize.py:744-748`)

Teardown kills session background processes before tmpdir removal. A post-kill "preserve live bgjob" branch in finalize would never fire on the success path. Low impact if deactivation always runs on terminal outcomes.
