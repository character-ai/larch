# Review Acceptance Rubric (Necessity Gate)

A proposed change is **in-scope-acceptable only if the feature would be incomplete, broken, unverifiable, or regressed without it.** If a finding is real, or even valuable, but the feature
ships correctly without it, it is **not in-scope** — route it to Out-of-Scope (file a tracked
issue). To be accepted in-scope, a finding must clear at least one of these gates:

1. Completeness — the change is a required part of the specified feature; without it,
   functionality the issue explicitly asked for is missing or only partially delivered.
2. Correctness — as written, the plan or implementation would fail to deliver the feature as
   specified: a real defect on the feature's own execution path (wrong behavior, inverted logic,
   a missing case the spec requires).
3. Introduced regression or harm — the change itself introduces a security vulnerability, a
   data-loss or data-corruption path, or a breaking change to an existing caller, contract, or
   CLI/wire surface — even if the new feature works. (You do not ship a regression and file an
   issue about it.)
4. Necessary test — **Default a test finding to Out-of-Scope.** It clears this gate as in-scope
   only if it covers a new, currently-uncovered, risk-bearing execution path that THIS feature

   red-green-TDD-after-the-fact is a Nit → Out-of-Scope, never in-scope.

   Before applying this carve-out, internally map the finding to the exact plan requirement, or
   conclude that no matching requirement exists. Do not include that mapping in voter output.
5. Unblock a pre-existing condition — a pre-existing defect that actively blocks completing,
   building, or verifying the feature (overlaps 1-2; the test is "the feature cannot be finished

## Original report

The architectural guideline note was dropped because HEAD drifted after staging.

## Reproduction scenario

Run `/implement --merge &lt;issue&gt;` on this repo (any issue whose plan touches files covered by `ARCHITECTURAL_GUIDELINES.md`) while other PRs are actively landing on `origin/main` — the routine case here, per #5969's own frequency audit and #6059's observed concurrent-merge conditions.

1. Step 7a's "Architectural guidelines (Phase A — staging)" stages a clean assessment (e.g. "Consulted ARCHITECTURAL_GUIDELINES.md; no deviations identified.").
2. Step 8+ (`ship pr`) creates the PR; `_compose_pr_body_for_pr_create` successfully pins the note via `_pin_and_load_guidelines_note` (this path is the one #5969/#6059 already hardened). The PR body includes the note.
3. While `ship.py`'s CI-monitor loop is waiting on CI, `origin/main` advances (routine on this repo). `monitor.goto_rebase` fires, and `_ship_rebase_phase` (or, on the phase-14 force-push-gate path, `_ship_phase14_rebase`) runs `rebase.rebase_and_push(...)`, then immediately calls `_invalidate_guidelines_note(working.tmpdir)` — no pin/refresh attempt at all.
4. By the time Step 16-17 (or a later `closeout.py` re-pin attempt) runs, the staged assessment and durable note are already gone; only the generic drop-notice placeholder survives.

Step 16-17's mechanical re-pin attempt logged `ARCHITECTURAL_GUIDELINES_PIN_STATUS=skipped`, and the final summary showed only the generic drop notice — matching the exact symptom in #5754/#5969/#6021/#6034/#6059, but with all of those specific root causes already fixed in the tree at the time of this run.

`command grep -rn "dropped because HEAD drifted" larch-logs/` shows this message recurring across many `larch-logs/implement/&lt;run-id&gt;/final-summary.md` files, including several dated after #6062's fix — consistent with a still-open gap.

## Expected behavior

A mid-CI-loop rebase that doesn't touch the feature branch's own files should not need to drop the note at all: `pin_note_from_staged_for_current_head` (already used by the two other call sites) is designed to re-stage the same assessment text against a freshly recomputed live diff/HEAD without new LLM judgment. The rebase-phase handlers should attempt this before falling back to invalidate, exactly as `_compose_pr_body_for_pr_create` and (post-#6021/#6062) `closeout.py` already do.

## Observed behavior

`_ship_rebase_phase` (`ship_merge.py:219`) and `_ship_phase14_rebase` (`ship_merge.py:251`) call `_invalidate_guidelines_note(working.tmpdir)` unconditionally immediately after every successful `rebase_and_push`, with no attempt to re-pin first. `_invalidate_guidelines_note` correctly persists the generic drop notice before wiping the staged/durable artifacts (via `maybe_persist_dropped_note_before_invalidate` + `invalidate_implement_note`), so nothing is silently lost from an auditability standpoint — but a still-valid assessment is discarded even when nothing about the underlying diff changed.

Two related call sites show the same *shape* of unconditional invalidate-without-pin-attempt and may warrant the same fix, though I have not traced whether they're reachable without an orchestrator round-trip the way `ship_merge.py`'s is:
- `python/larch/implement/ci_monitor.py:1625` (`_invalidate_guidelines_before_push`, inside the pending-CI-fix-rebase retry path).
- `python/larch/implement/ci_agentic_fix.py:101`.

Separately (does not affect the primary finding, but sits in the exact code I read while investigating): `python/larch/implement/ship.py:848`'s `if monitor.did_fixing: _invalidate_guidelines_note(...)` is dead code — `MonitorResult.did_fixing` is hardcoded `False` at all 8 of its construction sites in `ci_monitor.py` (`grep -rn "did_fixing=True" python/larch/` returns zero matches repo-wide), and a docstring on `run_ci_monitor_iteration` (~`ci_monitor.py:1977`) confirms the inline-fix behavior that used to set it was removed.
