# Implementation Plan — ship-pr loop: skip waterfall on first-fixer non-health failure (issue #2682)

## Canonical KV tokens (single source of truth)

The classification grammar is pinned by name in this plan and enforced by structural tests so future renames trigger CI failures rather than silent drift (per `.claude/rules/drift-prone-prose-in-docs.md` and `.claude/rules/timing-task-kind-allowlist.md` patterns).

- `LAUNCHER_FAILURE_CLASS` enum: exactly one of `none` / `health` / `other`.
- `LAUNCHER_FAILURE_REASON` enum: exactly one of `auth` / `binary-missing` / `health-probe` / `timeout` / `parse` / `refusal` / `unknown` (empty string on `LAUNCHER_FAILURE_CLASS=none`).

The literal token `parse` is used everywhere; the testing strategy that previously wrote `parse-error` is corrected. The reason for auth failure after the in-launcher retry exhausts is `auth` (the existing `append_launch_failure` token `auth-retries-exhausted` is a separate diagnostics string emitted to `${OUTPUT}.diag`; it is NOT one of the canonical reason tokens). The token `binary-missing` is the canonical reason when the launcher cannot resolve the underlying CLI binary; mechanism for detection is documented under Edge case #10 below.

`no-action` and `refusal` outcomes that occur on `LAUNCHER_EXIT=0` are EXPLICITLY OUT OF SCOPE for this issue — they require post-exit-0 detection (empty-diff baseline comparison or output pattern matching) that the launchers do not perform today. A follow-up issue will be filed separately to extend `LAUNCHER_FAILURE_REASON` with `no-action` / `refusal` tokens and add the detection mechanism. This issue's mechanics cover launcher-detectable failures only: timeout, parse, refusal-by-CLI-exit-code (when the CLI itself returns a refusal status), generic non-zero. Note that the enum still includes `refusal` because the underlying CLI may itself return a refusal exit code (e.g., codex's safety stop); detecting refusal CONTENT post-exit-0 is what is deferred.

## Files to modify/create

- `scripts/lib-external-launcher-common.sh` — add a launcher-shared helper (working name `external_classify_launch_failure`) that consumes inputs the launchers already have (`LAUNCHER_EXIT`, sidecar log path, and the existing `external_auth_verdict` output) and prints two KV lines on stdout: `LAUNCHER_FAILURE_CLASS=<token>` and `LAUNCHER_FAILURE_REASON=<token>` using the canonical enums above. Health-classed reasons are exactly: `binary-missing`, `auth` (after the in-launcher auth retry exhausts), and `health-probe`. Every other launcher-detectable failure (timeout, parse, generic non-zero CLI exit, `refusal` from CLI exit code) is `other`. On `LAUNCHER_EXIT=0` the helper emits `LAUNCHER_FAILURE_CLASS=none LAUNCHER_FAILURE_REASON=`. Binary-presence is sourced from the launcher's existing `command -v <binary>` precondition (see Edge case #10 below); a missing binary means the launcher fails to start the spawn — the helper recognizes this signal via an explicit caller-passed argument (e.g. `--binary-found false`) so the existing `command -v` early-exit path can still emit the KVs before exiting.

The pre-spawn `die()` argv-validation path (e.g., `launch-cursor-ci.sh:33-36`) is NOT part of this issue — argv mismatches are coding bugs in callers, not first-fixer failures, and the existing exit-2 behavior is preserved unchanged.

## Approach

The core insight is that the waterfall fallback chain (`cursor → codex → claude`) is justified ONLY when the first fixer was actually unable to attempt the fix (binary missing, login expired, health probe failed). When the first fixer DID run but failed for an in-band reason (timeout, parse error, generic non-zero), all three vendor tiers share the same context and the same root cause is likely; retrying through codex and claude is expected-low-yield and burns wall time and tokens.

Mechanics:

1. **Classification belongs at the launcher boundary** because launchers already own auth/retry/sidecar interpretation via `external_auth_verdict` in `lib-external-launcher-common.sh`. Adding a `ship-pr.sh` pre-flight probe would duplicate that work.
2. **Two new KVs (additive, not an overload of `LAUNCHER_EXIT`)** preserve the existing exit-code grammar that other consumers and `test-ship-pr.sh` already depend on.
3. **Bail via the existing `run_ci_phase` `bail)` envelope** (return non-zero from `run_ci_fix_vendor`, let outer flow route through the standard exit-3 sequence) per FINDING_5 — direct `exit 3` from inside the helper was the original plan and skipped the envelope; the revised plan threads through the existing path.
4. **A new BAIL_REASON via existing exit 3** keeps `needs_user_bail_reason` and `/implement` Step 8+ Exit 3 as the integration points. The new path is strictly additive.
5. **Policy fires only at the first tier (cursor)** per Round 1 Decision 3. Non-first tiers keep current waterfall behavior.
6. **Infinite-loop guardrail (sentinel + counter, fail-closed write-before-attempt order)** ensures `/implement` ↔ `ship-pr.sh` cannot ping-pong.
7. **Fork / unavailable-repo gate** prevents the autonomous fix path from attempting commit + push on runs where those operations are invalid.
8. **CI log capture with redaction** ensures the main-agent gets the actual CI failure (not just launcher diagnostics) AND that secrets stay out of Claude's context.
9. **Refresh-run-logs parity** with the existing ship-pr.sh CI-fix push path ensures larch-log token/timing artifacts remain consistent.

Interaction with **issue #2669** (already filed as `BLOCKED_BY` on issue #2682): #2669 tracks the exit-3-vs-exit-4 discrepancy when vendor CI fix agents exhaust. The current plan reuses exit 3 with a new BAIL_REASON token, structurally compatible with the existing exit-3 taxonomy. The blocker relationship is preserved so the new `first-fixer-non-health` token name can be aligned with whatever final taxonomy #2669 settles on; if #2669 lands first with a different exit-3 reason-token scheme, this plan's token will be renamed in a follow-up PR. No production rollback is required because the consumers are internal to ship-pr.sh + `/implement`. The previous wording's tension between "must land first" and "forward-compatible" (FINDING_13) is resolved by framing the dependency as "lands first to allow token alignment," not "lands first to avoid breakage."

## Edge cases

1. **Cursor success** — `LAUNCHER_EXIT=0`, classifier emits `LAUNCHER_FAILURE_CLASS=none`. No waterfall, no policy. Sanity-case in tests.

2. **Missing or malformed `LAUNCHER_FAILURE_CLASS` in `$fail_file`** — the guard parses the file with `awk -F=` (mirroring the existing `LAUNCHER_EXIT` parser style). When the parsed value is empty or unrecognized, default to the safer fallback `health` so the existing waterfall behavior is preserved. The bail-to-main-agent path is taken ONLY when the KV explicitly says `other`. This protects against rollback risk and against scenarios where the launcher fails before reaching its emit-block.

3. **wrapper_rc=2 (launcher argv validation `die()`)** — the launcher exits before reaching its KV emit-block; `LAUNCHER_FAILURE_CLASS` is absent in `$fail_file`. Per Edge case #2 the missing value defaults to `health`, and the existing `wrapper_rc=2` rollback + continue-to-next-tier behavior is preserved unchanged. The policy does NOT fire on argv validation errors — those are coding bugs in callers, not first-fixer failures. (FINDING_1)

4. **Auth retry succeeded inside the launcher** — the launcher already retries auth once; if the retry succeeds, classification proceeds against the post-retry result. If the retry exhausts, the classifier emits `health/auth`. Keep waterfall.

5. **`/implement` main-agent fix succeeds, ship-pr.sh re-run succeeds** — sentinel persists in `$IMPLEMENT_TMPDIR`; cleanup happens with the tmpdir at the end of the `/implement` run.

6. **`/implement` main-agent fix succeeds locally but CI still fails** — second `ship-pr.sh` invocation either has the same first-fixer non-health failure (sentinel blocks a second main-agent attempt → falls back to user-bail), or the first fixer succeeds and the fix lands.

7. **Counter cap semantics (resolved)**: counter is incremented BEFORE the attempt. The policy fires on read values `0`, `1`, `2` (corresponding to attempts 1, 2, 3). A 4th arrival sees counter `3` and falls through to the user-bail path. (FINDING_7)

8. **Sentinel or counter write failure**: fail-closed — abort the autonomous path, log a `Tool Failures` entry, fall through to user-bail. The new path is opt-in; the existing user-bail path is the safe default.

9. **FORKED_TARGET / REPO_UNAVAILABLE state at start of `/implement` Step 8+ Exit 3 procedure**: skip the autonomous path entirely (FINDING_12). The user-bail flow handles fork dry-runs and unavailable-repo runs as today.

10. **Binary-missing detection** (FINDING_10): the launcher's existing `command -v <binary>` precondition is the source of truth. When `command -v` fails, the launcher emits `LAUNCHER_FAILURE_CLASS=health LAUNCHER_FAILURE_REASON=binary-missing` before exiting; the helper documents this contract. No new probe is added.

## Failure modes

1. **Classification drift toward `other`**: a future change misclassifies a transient health failure (e.g., a transient network outage during auth) as `other`. The waterfall would skip when it shouldn't, hitting the user-bail more often. *Earliest signal*: a sudden spike in `first-fixer-non-health` bails in `/implement` run logs after a launcher / `lib-external-launcher-common.sh` change. *Mitigation*: keep the `health` set narrowly enumerated; Edge case #2 defaults unrecognized class to `health`; structural tests pin the canonical tokens.

2. **Infinite re-invocation between `/implement` Step 8+ and `ship-pr.sh`**: the sentinel + counter design closes this, but only with the fail-closed write-before-attempt ordering. *Earliest signal*: a run log with `>3` cycles of `ship-pr.sh exit 3 → main-agent attempt → ship-pr.sh exit 3`. *Mitigation*: the mock-harness asserts the 4th cycle falls through to user-bail; sentinel writes happen before any repo edit.

3. **Main-agent fix uses wrong diagnostic input**: addressed in /implement Step 8+ sub-step 5 by capturing fresh gh-run-logs.sh output (with redaction). *Earliest signal*: main-agent fixes that don't address the actual CI error. *Mitigation*: gh-run-logs.sh is the primary diagnostic input; BAIL_FAILURE_DETAIL_LOG is supplemental.
