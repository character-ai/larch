I would treat this as a small lifecycle extension plus a new `/design` “publish logs” tail, but I’d avoid embedding raw `gh pr create/merge/delete` choreography directly in [skills/design/SKILL.md](<OPERATOR_REPO_PATH>/skills/design/SKILL.md:789). First add `planned` to [scripts/tracking-issue-write.sh](<OPERATOR_REPO_PATH>/scripts/tracking-issue-write.sh:110), its docs/tests, and [scripts/lib-title-markers.sh](<OPERATOR_REPO_PATH>/scripts/lib-title-markers.sh:1) so `[PLANNED]` becomes a first-class lifecycle marker. Note the wording says “append `[PLANNED]` prefix”; mechanically this should be a leading prefix, consistent with `[IN PROGRESS]`, `[DONE]`, and `[STALLED]`. In Step 5, after `plan-block-write.sh` succeeds, call `tracking-issue-write.sh rename --state planned`, then publish logs before `cleanup-tmpdir.sh`.

For logs, the obvious path is extending [scripts/larch-log.sh](<OPERATOR_REPO_PATH>/scripts/larch-log.sh:413) so `commit` can accept something like `--message "chore(larch-logs): flush design run $RUN_ID [skip ci]"`, then have `/design` initialize/write a `design` run directory from `$DESIGN_TMPDIR` and commit it under `larch-logs/design/<run-id>/`. The less fragile variant is a new helper, maybe `scripts/design-log-publish.sh`, that owns: generate/validate run id, copy/redact the full `DESIGN_TMPDIR`, commit with `[skip ci]`, call [scripts/create-pr.sh](<OPERATOR_REPO_PATH>/scripts/create-pr.sh:1), call [scripts/merge-pr.sh](<OPERATOR_REPO_PATH>/scripts/merge-pr.sh:1) or a lighter logs-only merge helper, then call [scripts/local-cleanup.sh](<OPERATOR_REPO_PATH>/scripts/local-cleanup.sh:1). I’d prefer the helper because Step 5 is already prompt-heavy; moving git/GitHub side effects into a tested shell script gives one contract to harness and keeps resume/idempotency sane.

Main tradeoff: reusing `merge-pr.sh` preserves safety gates but conflicts with the requested “bypass CI” behavior, because it currently requires checks to pass before `--admin`. Either add an explicit logs-only `--skip-ci-admin` mode with very tight guards that diff paths are only `larch-logs/design/<run-id>/`, or create a dedicated helper that does the same guard then runs `gh pr merge --squash --admin --delete-branch`. The “crazy but might work” alternative is to skip PRs entirely and store design logs as a GitHub issue attachment/comment artifact, but that fights the repo’s committed-run-log direction. The other unconventional option is to make `larch-log.sh commit` produce a Git bundle or patch artifact first, then have a publisher script import it onto the branch, which would make recovery cleaner if PR creation succeeds but merge fails. I would still add a `SESSION_ENV_PATH`/nested safeguard despite the prompt saying no nested guard: this repo explicitly supports `/design` nested under `/implement`, and an unguarded PR/merge from nested Step 5 would be a bad surprise.
