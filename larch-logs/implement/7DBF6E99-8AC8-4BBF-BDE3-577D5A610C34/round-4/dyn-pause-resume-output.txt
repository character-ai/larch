Reviewing pause/resume integration in the branch diff, focusing on Step 3.6 sentinels, Gate-B bypass, and rc=11 handoff.
### In-Scope Findings

- **risk-integration** `scripts/design-pause-load.sh:128-288`, `skills/design/scripts/design-route.sh:237-242` — Resume routing trusts the frozen `STEP=` value from the pause marker and never reconciles it against the newly introduced Step 3.6 sentinel. Before this branch, a pause after Gate B (step-3.5 complete, no step-3.6 yet) correctly saved `STEP=3b`. After merge, those in-flight markers still route `resume@3b`, which jumps straight to the architecture diagram and permanently skips the new HARD-only assessor even when `design_classification=HARD` and `.completed/step-3.6` is absent in the restored snapshot. **Suggested fix:** On load/route, upgrade `STEP=3b` → `STEP=3.6` when step-3.5 is complete, step-3.6 is missing, and classification resolves HARD (leave bypass runs alone: they already write step-3.6 before 3b). Add a pause/resume harness case with a legacy marker (`STEP=3b`, sentinels `{step-3, step-3.5}` only) and assert `resume@3.6`.

- **risk-integration** `scripts/design-pause-save.sh:82-87` — Step inference treats “step-3.6 present, step-3b absent” as always meaning “resume at 3b”, without requiring step-3.5. If an orchestrator ever writes only the step-3.6 sentinel (partial Gate-B-bypass failure, manual tmpdir repair, or corrupted restore), pause-save emits `STEP=3b` and resume skips Gate B entirely. **Suggested fix:** Require step-3.5 (and ideally step-3) before the step-3.6→3b shortcut; if step-3.6 exists but step-3.5 does not, fall back to `STEP=3.5` or fail closed with a diagnostic instead of advancing to 3b.

- **risk-integration** `skills/design/scripts/test-design-pause-resume.sh:228-258` — The plan’s acceptance criterion (“a later pause after Step 3b does not resume into skipped Gate B/assessor work”) is not covered. Current tests only pause while bypass sentinels `{step-3, step-3.5, step-3.6}` are set and assert `STEP=3b`; they never advance to 3b, write `step-3b`, pause again, and assert the next resume is Step 4 (or at least not 3/3.5/3.6). **Suggested fix:** Add a case: complete bypass sentinels → mark `step-3b` (or simulate post-3b progress) → save → assert `STEP=4` (or next incomplete step), and optionally load/route to confirm no re-entry into 3.5/3.6.

- **risk-integration** `skills/design/SKILL.md:1187-1244` — On WORSE-majority (`rc=10`), the step-3.6 completion sentinel is deferred until the operator chooses Continue; a pause before that choice leaves `{step-3.5}` complete but no `step-3.6`, so pause-save correctly stores `STEP=3.6`, but resume reruns the full HARD assessor (including write-after/dispatch) rather than restoring the pending Continue/Stop decision. That can change the WORSE verdict and duplicate external assessor work. **Suggested fix:** Either persist a “pending WORSE prompt” artifact at rc=10 (round + validated trailer) and short-circuit resume to the Continue/Stop branch, or document that mid-WORSE pause intentionally re-runs assessment and add harness coverage for the duplicate-run behavior.
