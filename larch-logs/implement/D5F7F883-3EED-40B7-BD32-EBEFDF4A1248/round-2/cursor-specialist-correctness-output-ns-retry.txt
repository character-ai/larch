### In-Scope Findings

- **correctness** `scripts/compose-review-findings.md:31` — **Important.** The `category` contract now says the field is “empty when absent or when the extracted token is not a recognized tag (OOS strict mode only allows the five tags),” which misstates real behavior: for non–`out_of_scope` rows `strict_cat=0`, a `## NonCanonical: path` line still emits `NonCanonical` as `category`, while a single-colon `### FINDING_…: NonCanonical` line emits an empty `category`, and strict mode applies to OOS for both `##` and `###`, not only OOS for the “unrecognized tag ⇒ empty” rule. **Suggested fix:** Rewrite the `category` sentence so it distinguishes (1) `##` vs `### FINDING_…` parsing, (2) `out_of_scope` strict canonical-only behavior for both shapes, and (3) the extra restriction that `### FINDING_…` only fills `category` for canonical tags unless there is a second `:` so the first segment is unambiguously the category token.

- **correctness** `.claude/skills/audit-runs/scans.tsv:5` — **Latent.** The new `rej-category-blank` `test("### FINDING_[0-9A-Za-z_]+:")` regex requires exactly one ASCII space between `###` and `FINDING_`, while `extract_category` matches `/^###[[:space:]]+FINDING_/`, so multiple spaces (e.g. `###  FINDING_1: architecture: …`) still fail category extraction but do not satisfy the scan predicate; a `jq -e` check on synthetic JSON shows `true` for one space and `false` for two spaces with the same header content, so the audit scan can miss a blank-category regression that the parser also misses. **Suggested fix:** Align the scan regex with the parser (e.g. `###[[:space:]]+FINDING_[0-9A-Za-z_]+:` in `test`, or an equivalent `\\s+` pattern jq accepts) so both paths treat the same heading shapes as “FINDING triple-hash present.”

- **correctness** `scripts/compose-review-findings.sh:63-112` — **Latent.** The implementation plan called for applying the same strict/non-strict whitelist behavior as the existing `##` branch, but the new `### FINDING_…` branch treats `strict=0` more narrowly: with two colons after the `FINDING` id, any first-segment token is accepted, yet `### FINDING_1: performance: foo.sh` yields `category=""` because the second `:` is not in the remainder after the first split, `startswith`-style logic differs from “split on first body colon after the id,” and non-canonical two-part titles are handled differently from `## performance: foo.sh`, which would still return `performance`. **Suggested fix:** Either document this intentional asymmetry in the plan/feature notes and the contract doc, or change parsing so the first “payload” segment after `### FINDING_<id>:` uses the same colon-splitting rules as the `##` branch when `strict=0`, if non-canonical REJ categories must round-trip like `##` lines.
