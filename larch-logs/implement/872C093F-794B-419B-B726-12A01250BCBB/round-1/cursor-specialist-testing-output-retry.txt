### In-Scope Findings

- **risk-integration** `skills/review/scripts/test-review-core.sh:140-186` — The tally stub never emits `FINDINGS_CLASSIFICATION_TSV_FILE`, so none of the new `review-core.sh` pass-through branches (zero-findings ~451–491, normal ~634–637, main-agent ~687, completion ~733) are exercised in CI. A regression that drops or misnames the KV would not fail `make test-review-core` while Step 4 log publishing (per `skills/review/SKILL.md` and plan FINDING_7) would silently skip forensic TSV batches. **Suggested fix:** Extend the tally stub to echo `FINDINGS_CLASSIFICATION_TSV_FILE` (and optionally create a header-only fixture TSV) on zero-findings and at least one normal path; assert `FINDINGS_CLASSIFICATION_TSV_FILE=` in `test-review-core.sh` stdout for `TEST_FINDINGS=0` and `TEST_FINDINGS=1` cases.

- **risk-integration** `skills/review/scripts/test-findings-classification.sh:130-144` — Fixture F only compares `parse-judge-vote-and-rating.sh` to `vote_for_id` on a static file; it does not run `tally-code-votes.sh`’s `parse_vote_rating_for` loop (plan FINDING_14 / single-parse invariant). A future refactor could reintroduce `vote_for_id` for tally while keeping the parser for TSV without failing CI. **Suggested fix:** Add a fixture that drives `tally-code-votes.sh` with rated voter lines and asserts per-column votes match both `vote_for_id` and parser output for every ballot id (mirror design harness `assert_parser_vote_matches_vote_for_id` usage through tally).

- **risk-integration** `skills/design/scripts/test-findings-classification.sh:299-322` (plan) — The design harness includes a stub-parser “malicious output / TSV sanitization” case (`FINDING_8`); the new review harness has no equivalent for `write_classification_tsv_row` / `sanitize_*_cell` in `tally-code-votes.sh`. Tab-injected or out-of-enum axis values could leak into committed `larch-logs/.../findings-classification*.tsv` without a regression signal. **Suggested fix:** Port the stub-parser pattern to `test-findings-classification.sh` (or extend `test-tally-code-votes.sh`) asserting enum-only cells and `vN_uncertain=true` when axes are invalid.

- **risk-integration** `skills/review/scripts/test-tally-code-votes.sh:325-337` — The existing “3 voters, 1 YES, 2 JUDGE_ERROR” case still uses bare `FINDING_1: YES` lines and asserts only vote markdown / counts, not classification TSV columns. Plan required injecting ratings and asserting `FINDINGS_CLASSIFICATION_TSV_FILE` + schema in this harness; partial coverage exists only in case 1. **Suggested fix:** Add rated voter fixtures for the JUDGE_ERROR case and assert `v2_vote`/`v3_vote` are `""` or `JUDGE_ERROR` per documented semantics, with empty axis columns and `vN_uncertain=true` as appropriate.

- **risk-integration** `skills/review/scripts/test-findings-classification.sh:63-83` (plan) — Fixture B checks `voting_result==accepted` and lenient `v2_correctness`/`v2_uncertain` but does not assert “vote tally unaffected vs no-ratings baseline” (plan Fixture B / FINDING_19). A bug that changed `classify_result` inputs while keeping ratings columns could slip through. **Suggested fix:** Capture baseline `ACCEPTED_COUNT` / `FINDING_1_OUTCOME` from a duplicate tally run with fully rated lines, or hard-code expected tally KVs alongside classification assertions.

- **latent** `Makefile:412-417` — `test-findings-classification` (shard 9) and `test-review-findings-classification` (shard 8) both run `skills/review/scripts/test-findings-classification.sh`, so full `make lint` executes the same integration harness twice (~2× CI time for that script). **Suggested fix:** Run the review harness from only one target/shard (keep the combined design+review target on shard 9, or drop the duplicate from shard 8).

- **nit** `skills/review/scripts/test-tally-code-votes.sh:42-45` — Ballot still models OOS via `FINDING_3: [OUT_OF_SCOPE]` rather than `### OOS_N:` headings now supported in tally/prompts. Integration fixture A covers `OOS_1`, but the long-lived tally regression suite does not exercise `OOS_N` env keys (`OOS_1_ACCEPTED` from `record_tally_outcome` prefix change in `tally-code-votes.sh`). **Suggested fix:** Add one tally case with `### OOS_1:` ballot block and assert `OOS_1_OUTCOME` / classification row.
