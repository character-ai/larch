The implementation largely matches the plan: voter prompts, shared parser reuse, per-round TSV emission, log-batch registration, and a solid integration harness. The issues below are edge-case / failure-recovery gaps that can lose forensic data or mislead downstream consumers.

### In-Scope Findings

1. **Important** — **risk-integration** `skills/review/SKILL.md:61-63` — Step 4 runs once after the multi-round Step 3 loop, but line 61 only binds `FINDINGS_CLASSIFICATION_TSV_FILE` from the final `review-core.sh` return. Line 63 says “for each round,” yet nothing in Step 3 persists per-round classification paths for Step 4 to iterate. A literal Step 4 run publishes at most the last round’s TSV to `larch-logs/review/<RUN_ID>/`, while earlier `findings-classification-round-1.tsv` … `round-(N-1).tsv` files remain only in `$REVIEW_TMPDIR`. That breaks the acceptance criterion for multi-round standalone `/review --diff` even though Fixture E proves tally + `log-phase` work in isolation. **Suggested fix:** Log inside the Step 3 loop (or at Step 4 loop `r=1..round_num`) with `--batch review-findings-classification-round-${r}` and `--payload-file "$REVIEW_TMPDIR/findings-classification-round-${r}.tsv"`; mirror the same in `heavy-worker.md` (return per-round paths or instruct the parent to scan tmpdir).

2. **Important** — **correctness** `skills/review/scripts/tally-code-votes.sh:70-74` — Path selection uses `[[ -n "$SESSION_ENV_PATH" || -n "${IMPLEMENT_TMPDIR:-}" ]]` to pick the flat `findings-classification.tsv` name. That is correct when `$REVIEW_TMPDIR` is an `/implement` per-round directory, but wrong when a standalone `/review` session inherits `IMPLEMENT_TMPDIR` or `SESSION_ENV_PATH` while reusing one `$REVIEW_TMPDIR` across rounds: every round overwrites the same flat file instead of writing `findings-classification-round-${ROUND_NUM}.tsv`. Harnesses avoid this with `IMPLEMENT_TMPDIR=""`; production agents often do not. **Suggested fix:** Key off nested layout (e.g. `SESSION_ENV_PATH` set *and* `$REVIEW_TMPDIR` under `$(dirname "$SESSION_ENV_PATH")/round-*`) or add an explicit `--classification-tsv-mode implement|standalone` flag from `review-core.sh` instead of inferring from ambient env.

3. **Important** — **correctness** `skills/review/scripts/tally-code-votes.sh:440-446` + `skills/review/scripts/test-findings-classification.sh:130-144` — Tally counts empty `PARSED_VOTE` as `JUDGE_ERROR` in the scoreboard (`case "$vote" in … *) judge_error`), but `sanitize_vote_cell` writes `vN_vote=""` for the same cases. `vote_for_id` returns `JUDGE_ERROR` for missing/unparseable lines; Fixture F only checks well-formed lines, so parser/`vote_for_id` tally parity is guarded but TSV semantics are not. Downstream forensic tooling can read blank votes while `voting-tally.md` shows JERR > 0. **Suggested fix:** Map empty parser votes to `JUDGE_ERROR` in TSV when the voter file is non-empty and the ballot id exists, or document that `""` means “contributed to JERR” and add a harness case with a prose-only voter line.

4. **Latent** — **architecture** `skills/review/scripts/tally-code-votes.sh:373-377` — On `EFFECTIVE_VOTERS==0`, every ballot row is written with `voting_result=rejected` and empty `vN_*` columns (Fixture C codifies this). No judges voted, so “rejected” is a placeholder, not an outcome; this can skew offline analytics that treat `voting_result` as ground truth. **Suggested fix:** Use a sentinel such as `main-agent-required` / empty `voting_result`, or document in `docs/run-logs.md` and `tally-code-votes.md` that 0-judge rows are schema placeholders only.

5. **Latent** — **risk-integration** `skills/review/references/heavy-worker.md:94` — The example footer exposes a single `FINDINGS_CLASSIFICATION_TSV_FILE=…round-1.tsv`. Combined with the Step 4 gap, `--subagent` multi-round runs are especially likely to drop round ≥2 classification artifacts from committed logs. **Suggested fix:** Extend the heavy-worker contract to list all per-round TSV paths (or require the parent to glob `$REVIEW_TMPDIR/findings-classification-round-*.tsv` before Step 4 logging).

6. **Nit** — **architecture** `skills/review/scripts/tally-code-votes.sh:333-337` — `record_tally_outcome` now emits `OOS_N_ACCEPTED` / `OOS_N_OUTCOME` keys, but `skills/review/scripts/tally-code-votes.md:34` still documents only `FINDING_N_*`. **Suggested fix:** Update the sibling `.md` so env-file consumers know OOS ids use the `OOS_` prefix.
