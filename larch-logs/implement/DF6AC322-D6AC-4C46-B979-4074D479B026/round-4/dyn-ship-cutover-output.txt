### In-Scope Findings

- **architecture** `python/ship.py:559-562` — The Python driver always cold-starts the merge loop with `iteration`, `rebase_count`, `fix_attempts`, and `transient_retries` at zero and never hydrates them from `ship-pr-state.sh` on re-entry, while `skills/implement/SKILL.md` Step 8+ Exit 0/6 explicitly re-invokes the full `ship.py` fence whenever `PHASE` is not `done`/`postmerge`. Each orchestrator re-entry therefore resets the in-process cap even though bash `ship-pr.sh` persists and resumes `ITERATION` across invocations. A long-running `--merge` run can bypass `SHIP_MERGE_LOOP_MAX_ITERATIONS` and related retry budgets across multiple Step 8+ re-entries. **Suggested fix:** On `run_ship()` entry, read `ITERATION`, `REBASE_COUNT`, `FIX_ATTEMPTS`, and `TRANSIENT_RETRIES` from `ctx.state_file` when present (mirroring bash `read_state`), seed the merge-loop locals from those values, and add regression tests that simulate orchestrator re-invocation after `PHASE=ci-initial` to prove the cap is cumulative across driver restarts.

- **architecture** `skills/implement/references/stall-recovery.md:24,41` — Stall recovery’s `step8-shippr` dispatch and safety constraints still hard-require `${CLAUDE_PLUGIN_ROOT}/scripts/ship-pr.sh`, but Step 8+ now selects `python/ship.py` when `LARCH_SHIP_PR_IMPL=python` and documents a different control-flow contract (stdout JSON, `finalize-state.sh` stall keys, no `PHASE` consumption). A Python-path stall that classifies to `step8-shippr` will switch drivers mid-run, losing JSON routing, dual-file stall semantics, and the `no-logs-commit` / version-guard behavior wired into the Python fence. **Suggested fix:** Teach `stall-recovery.md` (and any dispatch prose in `skills/implement/SKILL.md` Step 18a) to branch on `LARCH_SHIP_PR_IMPL` the same way Step 8+ does—re-invoke `python/ship.py` with the documented foreground argv on the Python path—and extend `test-stall-recovery-report.sh` with a Python-selector fixture so recovery cannot silently fall back to bash.

- **architecture** `skills/implement/scripts/stall-recovery-report.sh:203-278`, `scripts/restore-finalize-state.sh:110-125`, `python/ship.py:1207-1216` — The branch introduces dual stall writers (`_write_terminal_state` / `_persist_stall_metadata_if_needed` write `STALL_TRACKING` into both `finalize-state.sh` and `ship-pr-state.sh`) but recovery success still clears stall only in `ship-pr-state.sh` via `clear-stall`, while `restore-finalize-state.sh` deliberately preserves existing `finalize-state.sh` `STALL_TRACKING=true` over `ship-pr-state.sh` `STALL_TRACKING=false`. If recovery clears `ship-pr-state.sh` before a successful driver pass rewrites `finalize-state.sh` with `STALL_TRACKING=false`, Step 18b restore can resurrect a stale stall and teardown will still treat the run as `[STALLED]`. **Suggested fix:** Make stall clearing symmetric: either extend `clear-stall` to also clear `STALL_TRACKING`/`STALL_STEP` in `finalize-state.sh` (without violating NEVER #11’s prompt-side ban—do it inside the helper), or change `restore-finalize-state.sh` to prefer a post-recovery `ship-pr-state.sh` `STALL_TRACKING=false` over preserved finalize stall metadata, with harness cases covering “recovery cleared ship-pr, finalize still true”.

### Out-of-Scope Observations

- **plan-fidelity** `scripts/larch-log.sh:93` — The new dynamic Codex allow clause uses the catch-all glob `dyn-*-codex-output-*.txt`, which the attached plan explicitly forbids in favor of narrow `dyn-*-codex-output-phase*.txt` / retry shapes only. Earlier deny clauses currently block the tested negative fixtures (`.prompt`, `*-vote-prompt.txt`, `.events.jsonl`), but the catch-all still widens the committed surface beyond the documented contract and could admit other `dyn-*-codex-output-<suffix>.txt` artifacts if deny ordering changes.

- **architecture** `python/finalize.py:350-365` — `write_finalize_state_merged()` emits keys in sorted order, while `write_finalize_state()` and `restore-finalize-state.sh` use the canonical `lib-finalize-state-keys.sh` ordering. This is unlikely to break readers today but leaves three different on-disk shapes for the same contract file and makes byte-level parity tests harder to maintain.
