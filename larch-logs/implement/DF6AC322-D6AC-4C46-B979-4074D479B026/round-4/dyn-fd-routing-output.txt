### In-Scope Findings

- **risk-integration** `scripts/larch-log.sh:93` — The new dynamic-Codex allow clause uses the catch-all pattern `dyn-*-codex-output-*.txt` (and matching sidecar globs), but `scripts/larch-log.md:35-36` and the attached plan both state there must be no catch-all suffix glob. Today, `*-vote-prompt.txt` / `*.prompt` denies still run first, so negative tests pass, but the matcher is wider than documented and depends on deny-order remaining stable; a future reorder could commit prompt-shaped names such as `dyn-api-contract-codex-output-vote-prompt.txt` to public run logs. **Suggested fix:** Replace `dyn-*-codex-output-*.txt` with the narrow shapes only (`dyn-*-codex-output.txt`, `dyn-*-codex-output-phase*.txt`, and `dyn-*-codex-output-retry*.txt` if retry artifacts exist), mirror that in docs/tests, and keep the ordering regression pin.

- **risk-integration** `python/logging_util.py:106-117`, `python/logging_util.py:151-155`, `python/ship.py:727-735` — After `quiet_init()`, contract JSON is written to fd 3 via `contract_stream()`, while fd 1 is redirected to the quiet log. That works when fd 3 is dup’d from the subprocess stdout pipe, but when the child inherits a parent-quiet fd layout (`exec 3>…` / `larch_quiet_init`), `fd3_inherited` stays true and contract output stays on inherited fd 3, not captured stdout. `test_quiet_init_preserves_inherited_fd3_contract_stream` shows `completed.stdout == ""` while contract lands elsewhere; `/implement` Step 8+ documents parsing “stdout JSON,” so a quiet-parent → `python3 ship.py` spawn can yield quiet-log bytes on stdout and no parseable contract for the orchestrator. **Suggested fix:** Either require the Python invoke fence to establish fd 3 as the caller contract stream (bash parity: `exec 3>&1` before `python3 ship.py`), or teach `emit_result()` to fall back to the original stdout pipe when inherited fd 3 is not the harness capture fd; add an integration test that runs ship.py under a quiet-init’d bash parent and asserts the orchestrator-readable stream still receives exactly one JSON line.

- **risk-integration** `python/ship.py:737-748` — On contract-stream write failure, `emit_result()` only runs the fd 3 fallback when `result.outcome is not Outcome.INTERNAL_ERROR`. If the driver is already returning `INTERNAL_ERROR` (top-level exception path) and fd 3/contract emission also fails, `emitted_contract` stays false and the code only logs `"INTERNAL_ERROR contract may be incomplete"` to the quiet log—no fd 3 fallback and no stdout JSON. The orchestrator then sees a non-contract exit with empty or log-only stdout, breaking Step 8+ outcome routing. **Suggested fix:** Attempt `_emit_contract_fallback()` for all failed primary emits (including when the original outcome is already `INTERNAL_ERROR`), or emit a minimal error JSON to fd 3 before exit; add a test that forces both `run_ship` exception and a broken `contract_stream()` and asserts stdout/fd 3 still delivers parseable JSON.

### Out-of-Scope Observations

- **risk-integration** `python/logging_util.py:175-177` — `BreadcrumbWriter.emit()` sets `routed = True` after `os.write(4, …)` even when the write is suppressed by `OSError`, so with `LARCH_QUIET_ACTIVE` set but fd 4 not wired, breadcrumbs can be dropped silently instead of falling back to stderr. This pattern predates the branch’s quiet work; the branch amplifies reliance on fd 4 routing but does not introduce the `routed = True` logic itself.
