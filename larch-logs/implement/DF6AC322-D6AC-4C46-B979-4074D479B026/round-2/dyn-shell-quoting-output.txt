### In-Scope Findings

- **security** `scripts/restore-finalize-state.sh:84-104` — This branch adds POSIX single-quote escaping in `python/finalize.py` (`_shell_single_quote`) and unquoting in `scripts/implement-finalize.sh`, but `restore-finalize-state.sh` still rebuilds `finalize-state.sh` with bare `printf '%s=%s\n' "$key" "$value"`. On the Python ship path, Step 18 always runs restore before teardown, so Python-quoted values (including GitHub-sourced `PR_TITLE`, `PR_URL`, `BRANCH_NAME`) are rewritten unquoted from `ship-pr-state.sh`. A value containing an embedded newline (possible in some external metadata, or any crafted `ship-pr-state.sh`) makes `printf` emit extra `KEY=value` lines and can flip booleans such as `STALL_TRACKING` or add spoofed keys; metacharacters like `$(…)` remain literal today because nothing sources the file, but the asymmetry reopens the state-integrity hole Python quoting was meant to close. **Suggested fix:** Reuse the same single-quote writer on the bash side (small shared helper mirroring `_shell_single_quote`), reject `\n`/`\r` in every value before write, and add harness cases for newline/metacharacter `PR_TITLE`/`BAIL_REASON` round-tripping through restore → `implement-finalize.sh teardown`.

- **risk-integration** `scripts/read-session-env-key.sh:96-104`, `skills/implement/scripts/stall-recovery-report.sh:56-66`, `skills/implement/scripts/write-final-report.sh:88-98` — Python writers now emit quoted booleans (e.g. `STALL_TRACKING='true'`), and only `implement-finalize.sh` unquotes them (`unquote_state_value`). Step 18a stall recovery and final-report logic still read `finalize-state.sh` via `read-session-env-key.sh` / `kv_get` and compare raw strings (`truthy` accepts `true` but not `'true'`; `write-final-report.sh` uses `[ "$STALL_TRACKING" = "false" ]`). On the Python path, a quoted finalize file can therefore be read as non-stalled until restore rewrites unquoted `STALL_TRACKING=true`, weakening stall detection, rename/sentinel behavior, and outcome reporting for the window before restore. **Suggested fix:** Centralize finalize-state reads through the same unquote helper used in `implement-finalize.sh` (or teach `read-session-env-key.sh` an optional `--unquote-shell` mode), extend `truthy` to accept quoted `'true'`/`'false'`, and add regression tests for Python-quoted `finalize-state.sh` consumed by stall-recovery and write-final-report without an intervening restore.

### Out-of-Scope Observations

- **security** `scripts/ship-pr.sh:842-855` — Pre-existing: bash `write_finalize_state()` also uses unquoted `printf '%s=%s\n'` with no newline rejection; the branch does not change this path. Same newline/spoofed-key risk as restore, independent of the new Python quoting.

- **security** `python/finalize.py:327-347` vs `scripts/implement-finalize.sh:168-177` — Pre-existing latent parser divergence: Python `read_finalize_state()` uses `shlex.split` (handles double quotes/escapes), while bash `unquote_state_value` only strips POSIX single-quoted literals. Current writers only emit single-quoted values, so this is not an active defect today, but hand-edited or future double-quoted state files would parse differently across Python and bash consumers.

- **security** `scripts/larch-log.sh:69-95` — The dynamic Codex allow-list changes are pure glob matching with no shell evaluation; no security issues identified in that portion of the diff.
