Reviewing the shell–Python bridge: checking quiet-mode stdout capture, REPO guard reachability, and test coverage.
### In-Scope Findings

- **risk-integration** `python/test_design_log_ship.py:307-345` — The plan requires a `main()` test that sets inherited `LARCH_QUIET_ACTIVE` / `LARCH_QUIET_PID` and asserts `PUBLISH_OK=` is visible on captured stdout, but no such test exists. `python/conftest.py` autouse-fixtures force `LARCH_QUIET_DISABLE=1` on every pytest run, so the three `main()` tests only exercise the non-quiet path where `logging_util.emit_kv` writes to real stdout; they never validate the production subprocess contract where `design_log_ship.main()` calls `quiet_init()` and routes `PUBLISH_OK=` through fd 3 after redirecting fd 1/2 to the quiet log. **Suggested fix:** Add a subprocess-based test (mirroring `python/test_ship.py` `test_quiet_init_routes_contract_and_breadcrumb_fds`) that unsets `LARCH_QUIET_DISABLE`, sets inherited parent quiet env vars, runs `cli.py ship design-log` with `capture_output=True` (or a bash `out=$(...)` wrapper), and asserts `PUBLISH_OK=` appears in the captured stream while diagnostics stay out of it.

- **risk-integration** `scripts/test-design-log-publish.sh:6` — The shell harness globally exports `LARCH_QUIET_DISABLE=1`, so every bridge test runs with parent and child quiet routing disabled. Production `scripts/design-log-publish.sh:27` always calls `larch_quiet_init`, and the Python bridge at `scripts/design-log-publish.sh:1106-1122` depends on the child re-initializing quiet mode and emitting `PUBLISH_OK=` on the contract stream (fd 3 duplicate of the command-substitution pipe, per `scripts/lib-quiet.sh:53-57` and `python/logging_util.py:80-85,98-105`). The harness therefore never exercises the integration path that motivated the bridge change, while `scripts/test-design-log-publish.md:37` claims quiet-capture coverage. **Suggested fix:** Add a dedicated harness case that unsets `LARCH_QUIET_DISABLE`, runs publish inside a parent with `larch_quiet_init` active, captures `_dlship_out` via the same `$(python3 ... 2>&1)` pattern, and asserts `PUBLISH_OK=` is parsed successfully without replaying child diagnostics to stderr.

### Out-of-Scope Observations

- **code-quality** `scripts/design-log-publish.sh:1101-1103` — The inner `if [[ -z "${REPO:-}" ]]` guard inside the `checks_registered=true` branch is unreachable: the outer gate at `scripts/design-log-publish.sh:1022-1024` already sets `merge_rc=2` and skips registration when `REPO` is empty, and nothing clears `REPO` between those lines. Harmless dead code, not an integration regression.

- On the quiet-routing mechanism itself: `design_log_ship.main()` calls `logging_util.quiet_init()` before `emit_kv` (`python/design_log_ship.py:302-310`), and Python’s quiet init mirrors bash’s “child must re-init so fd 3 captures the command-substitution pipe” rule (`scripts/lib-quiet.sh:53-57`, `python/logging_util.py:80-85`). I did not find a definite production routing bug from static review alone; the main risk introduced by this branch is the untested quiet subprocess contract described above.
