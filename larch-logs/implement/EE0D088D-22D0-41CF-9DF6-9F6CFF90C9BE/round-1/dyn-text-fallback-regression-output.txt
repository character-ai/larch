Reviewing `_classify_checks_text` and its tests for regressions on the `required=False` path.
### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:328-346` — The expanded `fail_re` and `pending_re` patterns are applied before any `required` branch, so `required=False` (default ship-pr / `gather_status` / `poll_ci` / `ci wait`) no longer matches the plan’s “default behavior unchanged” guarantee or `scripts/ci-status.sh` text-fallback parity (`\bfail` and `pending|in_progress|queued` only). Optional-check text containing `cancelled`, `skipping`, `unknown`, `neutral`, `stale`, `action required`, `error`, or `timed out` now returns `"fail"` instead of `"pass"`, and `waiting` / `requested` / `expected` now return `"pending"` instead of `"pass"`. That can stall or mis-route `/implement` ship CI when JSON classification is unavailable and text fallback is used — the exact degraded path this helper is meant to cover. **Suggested fix:** Gate the broad `fail_re` / `pending_re` behind `required=True` (keep legacy `\bfail` + narrow pending regex for `required=False`), or split into `_classify_checks_text_required` vs `_classify_checks_text_optional` so ship-pr optional semantics stay aligned with `ci-status.sh` and pre-change behavior.

- **risk-integration** `python/ci_monitor.py:297-346` — For `required=False`, JSON and text classifiers now disagree on the same PR state: `_classify_checks_json` still treats `cancelled` / `skipping` / `unknown` / missing bucket as `"pass"` (see `python/test_ci_monitor.py:2143-2144`), while `_classify_checks_text` treats the same status tokens in `gh pr checks` text output as `"fail"`. Outcome depends on whether `_resolve_checks_status` takes the JSON path or the text-fallback path (`python/ci_monitor.py:383-403`), so a flaky `gh pr checks --json` call can flip ship-pr between green and blocked without any CI change. **Suggested fix:** Make optional-mode text classification mirror optional JSON rules (only explicit `fail` bucket / `\bfail` status lines block; treat cancelled/skipping/unknown/neutral as pass), and add an integration test that asserts JSON-empty/text-fallback and JSON-array paths agree for the same optional-check fixtures.

- **risk-integration** `python/ci_monitor.py:328-330` — The shared `fail_re` uses bare `\bskip(?:ped|ping)?\b` and `\berror\b`, which match substrings in common check names (e.g. `skip-changelog`, `error-handler`) even when the status column is `pass`, turning green optional checks into false `"fail"` on the text-fallback path. `scripts/ci-status.sh:172-182` and the old classifier only keyed on `\bfail`, so this is a new false-positive surface for ship-pr, not just stricter handling of real failures. **Suggested fix:** Anchor classification on the status column (tab/whitespace-delimited fields) or require failure tokens only in a trailing status field; at minimum exclude name-only matches and add regression tests with passing checks whose names contain `skip`, `fail`, or `error`.

- **risk-integration** `python/test_ci_monitor.py:2139-2144` — Coverage guards the JSON optional path (`test_default_optional_json_classifier_unchanged_for_unknown_bucket`) and required-mode text ambiguity (`test_required_text_fallback_ambiguous_output_is_not_pass`), but there is no equivalent test proving `required=False` text fallback still classifies cancelled/skipping/neutral optional output as `"pass"` and still uses the legacy fail/pending heuristics. The branch therefore ships a documented ship-pr regression risk without a pin. **Suggested fix:** Add `test_default_optional_text_classifier_unchanged_for_cancelled_and_skipping` (and pending-behavior cases) asserting old optional semantics, plus a JSON-fail → text-fallback harness test through `checks_status(required=False)`.

### Out-of-Scope Observations

- `scripts/merge-pr.sh:199` and `python/gh.py:673-675` already treat `cancelled|skipping` as blocking in their own text helpers, so tightening optional text classification would align `_classify_checks_text` with `ci-status.sh` / historical `ci_monitor` behavior, not necessarily with every other script in the repo. That pre-existing split is worth reconciling separately, but the regression vs the plan and `ci-status.sh` parity target is introduced by this branch’s unconditional regex expansion in `python/ci_monitor.py`.
