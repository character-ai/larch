### In-Scope Findings
- **architecture** `skills/review/scripts/review-core.sh:856-881` — The code-review pre-filter runs immediately after `collect-findings.sh`, but code collector output does not preserve reviewer severity as a standalone `- **Severity**:` line: `skills/review/scripts/collect-findings.sh:498-503` writes only Reviewer/Concern/Suggested revision, and TSV severity is folded into prose at `skills/review/scripts/collect-findings.sh:406-413`, while `skills/review/scripts/prune-nit-findings.sh:59-61` only matches standalone severity lines. As wired, real collected code-review nits will usually bypass pruning and still reach aggregation/voting. **Suggested fix:** Either preserve severity as a first-class field in `collect-findings.sh` before pruning, or move the code-path prune step after `aggregate-findings.sh`, where severity lines are guaranteed; add a review-core fixture using inline TSV/nit input to prove the nit is routed out before voting.
- **architecture** `skills/review/scripts/review-core.sh:983-1010` — Pruned code nits are appended only to `oos.md` by `skills/review/scripts/prune-nit-findings.sh:118-151`, but code voters and tally are invoked with `findings.md` only, and `skills/review/scripts/tally-code-votes.sh:103-107` truncates `$REVIEW_TMPDIR/oos.md` at startup. Any nit that is successfully pruned is removed from the in-scope ballot and then erased rather than remaining an OOS proposal eligible for filing. **Suggested fix:** Build a combined voting ballot from aggregated in-scope findings plus OOS-tagged pruned items, or teach `tally-code-votes.sh` to ingest/preserve preexisting `oos.md` before truncation; add an end-to-end test asserting a pruned nit appears in OOS artifacts/classification, not only disappears from `findings.md`.
- **architecture** `skills/review/scripts/prune-nit-findings.sh:132-153` — The helper claims fail-open leaves files unchanged, but it renames the rewritten in-scope file before appending moved blocks to the OOS file; if the OOS append fails, `fail_open()` emits `STATUS=skipped` after nits have already been removed from `findings.md`. Callers such as `skills/review/scripts/review-core.sh:863-879` treat that as nonfatal, so an I/O failure can silently drop findings. **Suggested fix:** Stage both destination contents first and commit with rollback/backups, or at minimum append/persist OOS successfully before removing blocks from in-scope; add a harness case that forces OOS write failure and verifies both files remain unchanged.
