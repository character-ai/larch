### In-Scope Findings

1. **Latent** (`security`) — [scripts/harness-timer.sh:12](scripts/harness-timer.sh): `elapsed` is computed with `python3 -c "print(f'{max(0.0, $end - $start):.2f}')")`, so `$start` and `$end` are expanded by the shell into the Python source string. Today they come only from trusted `time.time()` output, so normal misuse of `harness-timer.sh` does not feed attacker-controlled text there. If that ever changed (e.g. alternate clock source, captured stderr merged into the substitution, or a compromised `python3` printing crafted stdout), this pattern is strictly weaker than passing numbers as `argv`/`stdin` after a numeric sanity check. **Concrete scenario:** a malicious or replaced `python3` prints `0);import os;os.system('id'` as “start”; the next `python3 -c` line becomes attacker-influenced Python source (RCE as the invoking user), whereas the old `date +%s` + `$((…))` path did not embed clock strings into a `-c` program. **Suggested fix:** compute elapsed in one Python invocation, or use `python3 -c 'import sys; …'` with `"$start"` and `"$end"` as arguments and validate with a tight regex before use.

2. **Nit** (`risk-integration`) — [scripts/test-harness-timer.sh:83-120](scripts/test-harness-timer.sh): The delivered harness includes a fourth case (backward-clock clamp + shim counter) beyond the three cases called out in the original feature description (`sleep 0.5`, `sleep 2`, `false`). This is reasonable hardening but is a small requirements/traceability drift vs the stated prompt. **Suggested fix:** Align the tracking issue / feature text with the fourth case, or call it out explicitly in the PR body so reviewers do not treat it as scope creep.
