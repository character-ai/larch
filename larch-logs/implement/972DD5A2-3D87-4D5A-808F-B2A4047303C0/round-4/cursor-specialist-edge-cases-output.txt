### In-Scope Findings

1. **Important** (`correctness`, `failure recovery`) — [`scripts/harness-timer.sh:8-13`](scripts/harness-timer.sh) — The wrapper intentionally omits `set -e`, so a failing or missing `python3` on the start/end/elapsed probes does not abort the script. If `start`/`end`/`elapsed` end up empty or the third `python3 -c` errors, `printf` can still emit a `LARCH_HARNESS_TIMING` line with a malformed or empty duration token while the exit code still mirrors the inner command. Downstream shard analytics then ingest a “successful” failure sample with a broken timing field, which is easy to misread as a real zero or to drop silently depending on parser strictness. **Suggested fix:** After each `python3` probe, validate non-empty numeric `start`/`end` and non-empty `elapsed`, or use a single Python helper that prints both timestamps and elapsed in one invocation so failure is atomic; on probe failure, print a distinct stderr diagnostic and either skip the line or exit non-zero so CI does not record garbage contract rows.

2. **Important** (`correctness`, `risk-integration`) — [`scripts/test-harness-timer.sh:60-67`](scripts/test-harness-timer.sh) — The `sleep 2` assertion requires `^[12]\.[0-9]{2}s$`, so any wall time in the 3.xx–9.xx second range (heavily loaded CI runner, VM stall, laptop sleep, I/O blocking) fails even though the harness behaved correctly. That produces flaky CI unrelated to the timer change. **Suggested fix:** Widen the pattern (for example allow leading digit 1–9 with a sane upper cap), or assert a numeric range with `awk` like `timing_in_range` (e.g. `>= 1.80 && <= 15.00`) instead of pinning the leading digit to 1 or 2 only.

3. **Latent** (`risk-integration`) — [`scripts/test-harness-timer.sh:85-105`](scripts/test-harness-timer.sh) — The backward-clock test’s shim only intercepts `python3 -c` when the second argument is exactly `import time; print(time.time())`. Any harmless refactor of those one-liners in `harness-timer.sh` (quoting, semicolons, `from time import time`, etc.) bypasses the shim: the “backward clock” scenario may no longer run, and the counter assertion can fail even though clamp logic is still correct. **Suggested fix:** Document the coupling beside the shim, or assert clamp behavior without string-matching the inner Python source (for example inject timestamps via env vars read by a tiny dedicated code path used only under test).

4. **Latent** (`correctness`) — [`scripts/harness-timer.sh:12`](scripts/harness-timer.sh) / [`scripts/harness-timer.md:213-218`](scripts/harness-timer.md) — `max(0.0, end - start)` makes `0.00s` indistinguishable in logs from a true sub-10 ms run rounded to two decimals. The doc explains backward-clock clamping but not this ambiguity. **Suggested fix:** Note in the contract that `0.00s` may mean clamp, rounding, or an extremely fast run, or reserve a separate sentinel for clamp if consumers need to disambiguate.

5. **Nit** (`code-quality`) — [`scripts/test-harness-timer.sh:9-20`](scripts/test-harness-timer.sh) — The failure counter variable `fail` and the function `fail()` share a name; it works in typical Bash but slows reading and risks mistakes if someone adds `fail` as a command or refactors arithmetic. **Suggested fix:** Rename the function to `record_fail` or the counter to `failures`.
