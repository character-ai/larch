Primary security concern is **bash re-expansion** of captured timestamps when building the nested `python3 -c` string.

### In-Scope Findings

1. **Latent** (`security`) — [`scripts/harness-timer.sh:12`](scripts/harness-timer.sh)

   **Issue:** `elapsed=$(python3 -c "print(f'{max(0.0, $end - $start):.2f}')")` expands `$start` and `$end` inside **double quotes** in the parent shell before the outer `python3` runs. Those values came from earlier command substitutions; if they ever contain shell metacharacters or command substitutions (e.g. `$(cmd)`), the parent shell can execute them during that expansion.

   **Concrete scenario:** A **malicious or trojaned `python3`** on `PATH` (or a wrapper) prints crafted stdout for `print(time.time())` (for example a line that embeds `$(id)`), populating `start`/`end` with hostile text. When the `elapsed=` line runs, bash parses the expanded string and can run the injected command as the same user running the harness.

   **Suggested fix:** Do not embed captured stdout into a double-quoted shell string. For example: use a **single-quoted** `python3 -c` that reads `sys.argv[1]`/`sys.argv[2]` after validating with a strict `^[0-9]+(\.[0-9]+)?$` regex in bash, or export sanitized values and read them in Python via `os.environ`, or compute elapsed in one Python invocation. Honest CPython output for `time.time()` is numeric-only; the gap is **trust in `python3` stdout being safe for bash parsing**.
