### In-Scope Findings

1. **Nit** (`code-quality`) [scripts/test-harness-timer.sh:10-11](scripts/test-harness-timer.sh) — The helper function is named `fail` while the failure counter is also `fail`. Bash resolves the arithmetic update to the variable in practice, but this shadows the name and is harder to read than peers that use names like `bump_fail` / `record_fail` / `fail_case`, and it may trip maintainers or static analysis. **Suggested fix**: Rename the function (or the counter) so the two are distinct.

2. **Latent** (`correctness`) [scripts/test-harness-timer.sh:27-33](scripts/test-harness-timer.sh) — The `sleep 2` assertion allows only `^[12]\.[0-9]{2}s$`, so a wall time of `3.00s` or higher (slow/overloaded CI) fails even though the timer is correct. **Scenario**: Shard host stalls; measured elapsed crosses 3s → harness fails despite valid behavior. **Suggested fix**: Loosen the upper bound (e.g. allow `2\.`–`4\.` or a bounded range) or assert a minimum near 2s plus a generous ceiling.

3. **Latent** (`correctness`) [scripts/test-harness-timer.sh:18-25](scripts/test-harness-timer.sh) — The `sleep 0.5` window is `0.40s`–`0.69s` via `^0\.[4-6][0-9]s$`. A fast finish around `0.38s`–`0.39s` is unlikely but possible relative to nominal 500ms. **Scenario**: Scheduler returns early vs expectation → flake. **Suggested fix**: Widen the lower tenths digit (e.g. include `3`) or document/encode a slightly wider tolerance.

4. **Nit** (`code-quality`) [scripts/harness-timer.sh:8-12](scripts/harness-timer.sh) — Each invocation starts three separate `python3` processes for timing. Matches the attached implementation plan and is correct; it is just heavier than a single `python3 -c` that records start, runs the inner command via `os.exec`/`subprocess` (not requested). **Suggested fix**: Optional consolidation if cold-start cost matters on large harness matrices.

5. **Nit** (`risk-integration`) [scripts/test-harness-timer.sh:18-29](scripts/test-harness-timer.sh) — The first two cases only assert the timing token, not that `harness-timer.sh` exited 0 when the inner `sleep` succeeds. A hypothetical regression that still printed a plausible timing line with a non-zero wrapper exit would not be caught. **Suggested fix**: Capture and assert `rc=0` for the sleep cases similarly to the `false` case.

No **Important** or **blocking** issues identified; `harness-timer.sh`’s `printf` + `f'{...:.2f}'` with bash-expanded `$start`/`$end` is consistent with typical `time.time()` string output and preserves the prior exit-code mirroring pattern.
