### In-Scope Findings

1. **Latent**, **security**, [`scripts/harness-timer.sh:12`](scripts/harness-timer.sh): `elapsed` is computed by expanding `$start` and `$end` into a `python3 -c "print(f'{$end - $start:.2f}')"` string before Python sees it. Today both values are produced by `print(time.time())`, so they should stay numeric, but this pattern couples shell parsing to Python source and would become dangerous if a future edit ever fed unsanitized or attacker-influenced text into the same template. **Concrete scenario:** a later change sets `start` from an environment variable or file without validation; a crafted value could break out of the f-string or alter the `-c` program. **Suggested fix:** keep literals and data separate, e.g. pass both timestamps as arguments and parse in Python (`python3 -c 'import sys; ...' "$start" "$end"`) or compute elapsed in one Python process.

2. **Latent**, **correctness**, [`scripts/test-harness-timer.sh:27-33`](scripts/test-harness-timer.sh): The `sleep 2` assertion uses `^[12]\.[0-9]{2}s$`, which rejects any duration ≥ `3.00s`. On a heavily loaded CI host, wall time after `sleep 2` can exceed three seconds, producing a **false test failure** even when `harness-timer.sh` behaves correctly. **Suggested fix:** widen the pattern (e.g. allow a leading digit 1–9), cap a maximum, or assert a lower bound with a generous upper bound.

3. **Nit**, **correctness**, [`scripts/test-harness-timer.sh:18-25`](scripts/test-harness-timer.sh): The `sleep 0.5` window (`0.4x`–`0.6x` seconds) is tight; extreme scheduler delay could slip past `0.69s` and fail intermittently. **Suggested fix:** slightly widen the regex or use a tolerance-based check if flakes appear.
