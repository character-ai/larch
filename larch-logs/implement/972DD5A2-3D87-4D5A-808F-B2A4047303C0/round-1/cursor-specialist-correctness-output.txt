### In-Scope Findings

1. **Latent**, `correctness` (requirements), [scripts/test-harness-timer.sh](scripts/test-harness-timer.sh):27-33 — The `sleep 2` case only accepts `^[12]\.[0-9]{2}s$`. Wall time can exceed 3.0s on a saturated runner even after `sleep 2`, so the harness can report `3.02s` and fail the test despite correct timer behavior. **Suggested fix:** Widen the pattern (for example allow `3\.` or match `^[0-9]+\.[0-9]{2}s$` with explicit numeric min/max checks in the shell).

2. **Latent**, `correctness` (requirements), [scripts/test-harness-timer.sh](scripts/test-harness-timer.sh):18-25 — The `sleep 0.5` window is `0.40s`–`0.69s` via `^0\.[4-6][0-9]s$`. Values like `0.70s` are plausible under scheduling jitter. **Suggested fix:** Extend the tens digit class (e.g. include `7`) or assert a numeric range instead of a tight character class.

3. **Nit**, `code-quality` (plan), [scripts/test-harness-timer.md](scripts/test-harness-timer.md):9 — The stub says “±100 ms slop” while the regex allows `0.69s`, i.e. up to ~190 ms above 0.5s, so the written slop does not match the enforced contract. **Suggested fix:** Align the prose with the regex (or tighten the regex to match “±100 ms”).

4. **Nit**, `risk-integration` (plan), [scripts/test-harness-timer.sh](scripts/test-harness-timer.sh):7-11 — The implementation plan called out `REPO_ROOT` / `cleanup_tmpdir` like other harnesses; this script is intentionally minimal and omits them (no tmpdirs here). **Suggested fix:** Either add the usual scaffolding for consistency or drop that sentence from future plans for stateless harnesses.
