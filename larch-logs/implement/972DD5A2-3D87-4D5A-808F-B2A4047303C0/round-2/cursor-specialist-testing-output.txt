### In-Scope Findings

1. **Important** `risk-integration` `scripts/test-harness-timer.sh:44-51` — The `sleep 2` case only checks a wide numeric band (`1.90`–`4.99` via `timing_in_range`) and never enforces the acceptance shape from the feature/plan (`^[12]\.[0-9]{2}s$`, i.e. whole seconds must be `1` or `2`). A broken timer that prints `3.00s` or `4.00s` after `sleep 2` would still pass, so the regression test can miss gross duration bugs that the specified regex would reject. Tighten the upper bound to something just above expected wall time (or add an explicit `^[12]\.[0-9]{2}s$` check in addition to a narrow slop band).

2. **Nit** `risk-integration` `scripts/test-harness-timer.sh:35-42` — For `sleep 0.5`, the plan/feature called for `^0\.[4-6][0-9]s$` (tenths digit `4`–`6`). The harness instead accepts any `N.NNs` in `0.40`–`0.79`, which includes values like `0.78s` that the specified regex would reject. Impact is smaller than the `sleep 2` gap but the test is still looser than the stated contract. Align the assertion with the regex or document the deliberate relaxation.

3. **Latent** `risk-integration` `scripts/harness-timer.sh:258-266` (per diff; current file `scripts/harness-timer.sh` timing block) — Each wrapped harness now forks `python3` three times per invocation (`start`, `end`, `elapsed`), which slightly inflates wall time versus the old `date` approach and can shift per-test timings used for shard rebalancing; unlikely to fail current tests but it changes measurement semantics. Accept as trade-off for sub-second resolution or collapse to one Python snippet if noise becomes an issue.
