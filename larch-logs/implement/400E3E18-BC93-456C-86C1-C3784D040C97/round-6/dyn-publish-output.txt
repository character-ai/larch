### In-Scope Findings

- **risk-integration** `skills/design/scripts/design-publish.sh:217-229` — On `mktemp` failure in `render_fresh_timing_report_for_publish`, the function returns before the stale-artifact cleanup at lines 233–236 runs. Any pre-existing `$DESIGN_TMPDIR/timing-report-final.json` (for example from an earlier in-session render or a restored pause snapshot) is left in place, and `design-log-publish.sh` still runs immediately afterward. The new `timing-report-final.failure.log` is excluded from staging, but a stale JSON file is not, so a failed pre-publish render can still flush outdated per-round timing into committed run logs while only emitting a warning. **Suggested fix:** Mirror `design-pause-save.sh` by deleting all `$DESIGN_TMPDIR/timing-report-final.*` at the start of the helper and again on every failure path (including `mktemp`), so publish never stages timing JSON unless the current render succeeded validation.

- **risk-integration** `scripts/design-log-publish.sh:274-400` — For `--reason pause` when the remote recovery branch already exists, the worktree is checked out from `origin/$WT_BRANCH`, so `$RUN_DEST/timing-report-final.json` from a prior pause snapshot remains on disk. The new pause/final pre-render helpers remove failed renders from `$DESIGN_TMPDIR` only; when re-render fails, the top-level staging loop copies nothing and does not delete the inherited worktree copy, so the next pause commit can retain and republish stale timing JSON without any fresh per-round data. **Suggested fix:** Before top-level staging (or specifically when timing re-render failed / no validated JSON is present in the tmpdir), explicitly `rm -f` excluded timing sidecars and `timing-report-final.json` under `$RUN_DEST`, or overwrite/remove them whenever the tmpdir lacks a validated replacement.

- **risk-integration** `skills/design/scripts/design-publish.sh:259-281` — Pre-publish validation requires a Step 3 row with a `rounds` array; if `timing-report.sh` returns otherwise-valid JSON without that field (partial round-telemetry failure, interval mismatch, or missing parent mark), the helper quarantines all `timing-report-final.*` artifacts and continues to `design-log-publish.sh` with `PUBLISH_OK=true`. The run log is then committed without any timing report, even though aggregate step timing may exist in the ledger, which violates the acceptance goal of having per-round data in the committed `timing-report` batch and makes timing loss look like a successful publish. **Suggested fix:** Relax validation to accept base timing JSON without `rounds` (warn-only), or fail closed on missing `rounds` when Step 3 marks/round ledger rows exist; alternatively skip log publish when fresh timing render fails if timing data is required for the batch.

### Out-of-Scope Observations

- **risk-integration** `skills/design/scripts/render-final-summary.sh:87-88` — After a successful pre-publish render and log flush, `--post-publish-only` unconditionally deletes and re-renders `timing-report-final.json` for the final-summary duration line. That does not republish stale data (publish already ran), but it means the tmpdir copy can diverge from what was committed; pre-existing behavior, now more visible because publish depends on a separate pre-flush render.
