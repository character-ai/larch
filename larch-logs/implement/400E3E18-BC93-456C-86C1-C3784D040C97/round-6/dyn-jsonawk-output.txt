Reviewing the branch diff and commit history, focusing on timing-report JSON emission correctness.
### In-Scope Findings

- **correctness** `skills/design/scripts/record-plan-review-round-timing.sh:42-55` — When `plan-review/round-N/` already exists (created early for `round-start-s`, `findings-classification.tsv`, etc.) but `_snapshot_round_dir` has not yet copied session-root tally artifacts into it, the helper unconditionally switches `artifact_root` to the round directory and then reads `accepted-plan-findings.md`, `rejected-findings.md`, and `voting-tally.md` only from that path. Missing files leave `accepted`/`rejected`/`oos` at 0 even though the live session-root tally files already hold the final counts. That wrong data is written to `round` ledger rows and rendered into `timing-report.json` `rounds` arrays. This hits the common terminal paths that emit before snapshot (`plan-review-loop.sh` `_snapshot_terminal_exit_preserving_status` at `440-446`, legacy single-pass complete at `1432-1433`, and deferred MAV emission from `skills/design/SKILL.md`), while non-terminal multi-round continuation (`1592`, after snapshot at `1557`) and panel-failed-with-successful-snapshot (`1485`) are unaffected. **Suggested fix:** Only prefer `plan-review/round-N/` when the needed tally files are present and non-empty there; otherwise fall back to `$DESIGN_TMPDIR` session-root artifacts (or emit after snapshot / pass the loop’s already-computed `ACCEPTED_COUNT`/`REJECTED_COUNT` into the helper). Add a harness case where the round dir exists without snapshotted tally files but session-root files have non-zero counts, and assert the ledger/`timing-report.json` `rounds` entry matches.

- **correctness** `scripts/timing-report.sh:381-411` — `emit_round_array` deduplicates multiple ledger `round` rows with the same `(skill, step, interval, round)` by silently keeping the last row (`match_idx[round_match_pos[rkey]] = i`), so a duplicate emission with a later `duration_seconds` overwrites the earlier one with no signal. Idempotent guards usually prevent double-writes, but if a warn-only helper retry or a partial failure produces two rows for the same round inside one Step 5 / Step 3 interval, the JSON can show the wrong duration/counts. **Suggested fix:** Either reject/ warn on duplicate `(skill, step, round, interval)` rows during aggregation, or deterministically prefer the row whose `[start_s, end_s)` best matches the parent step interval instead of last-wins.

### Out-of-Scope Observations

- **correctness** `scripts/timing-report.sh:384` — Round attachment uses only `round_start ∈ [step_start, step_end)`; `round_end` and stored `duration_seconds` are not checked against the parent step bounds. A deferred handoff row can therefore report wall time that extends past the Step 5 mark while still attaching to that step. That matches the current plan (defer before Step 7 commit), but it means `rounds[].duration_seconds` is not strictly bounded by the parent `per_step.duration_seconds`; consumers should treat it as wall-clock for the round, not a partition of the step total.

- The `timing-report.sh` JSON construction itself (comma placement, nested child intervals, absent-parent omission, markdown unchanged, `jq` parsing) looks sound for the fixtures in `scripts/test-timing-report.sh`; the main design-side correctness gap is upstream ledger row content, not the awk emitter.
