### In-Scope Findings

- **correctness** `scripts/timing-report.sh:381-415` — `emit_round_array` uses two awk global arrays (`round_match_pos`, `match_idx`) as call-scoped temporaries and cleans them up at the end. The cleanup loop `for (i = 1; i <= mc; i++) { delete round_match_pos[round_num[match_idx[i]] + 0]; delete match_idx[i] }` runs only when `mc > 0`; the early-return on `mc == 0` skips cleanup entirely. This is correct because no entries are added to either array when `mc == 0`. However, the sort rearranges `match_idx[1..mc]` in place, so the cleanup iterates the sorted order. After dedup, `round_match_pos` holds keys = unique round numbers of matched entries; cleanup deletes each via `round_num[match_idx[i]]` post-sort. This is correct because sort only swaps (never adds/removes) array slots, so all unique round numbers appear exactly once in `match_idx[1..mc]`. No bug, but the cleanup is fragile: if a future refactor increments `mc` for duplicate rounds (breaking the invariant that `mc` = unique-round count), cleanup would silently leave orphaned entries in `round_match_pos` that would corrupt subsequent `emit_round_array` calls within the same awk process. **Suggested fix:** Add a local clear at the start: `delete round_match_pos; delete match_idx` (both are awk global arrays used only here), which makes the function self-contained regardless of invariants on `mc`. This is the canonical awk pattern for function-scoped scratch arrays; the current cleanup-at-end approach works only because `mc` is the strict unique count after dedup.

- **correctness** `skills/design/scripts/record-plan-review-round-timing.sh:54-56` — The OOS awk parser uses `$7` as the `Result` column, hardcoded to the 6-column voting-tally format `| Item | YES | NO | Exon | JERR | Result |`. When a tally table has a different number of columns (e.g., a 5-column variant `| Item | YES | NO | Exon | Result |`), `$7` would be the empty trailing field, the `result == ""` fallback triggers, `result=$NF` = `$7` = still empty, so no accepted OOS is counted at all. The `NF >= 7` guard does not discriminate between 5-column (NF=7, trailing field empty) and 6-column (NF=8) tables. In practice the standard tally is always 6-column, but plan-review-loop.sh writes this file and no schema version field exists to guard against future changes. **Suggested fix:** Use `$NF` as the primary Result field (last non-empty pipe-separated token), trimmed, instead of hardcoding column 7. `result=$NF; gsub(/^[[:space:]]+|[[:space:]]+$/, "", result)` makes the OOS counter format-agnostic and avoids the 5-column silent-zero regression.
