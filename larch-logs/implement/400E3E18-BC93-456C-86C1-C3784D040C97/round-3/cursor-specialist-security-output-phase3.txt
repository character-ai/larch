### In-Scope Findings

1. **correctness** `scripts/timing-report.sh:381-415` — `emit_round_array` uses two global awk arrays (`round_match_pos`, `match_idx`) that are not listed as local parameters and are cleaned up only in the tail of the function. Because the `match_idx` deduplication rebases duplicate-round-number rows with `match_idx[round_match_pos[rkey]] = i` (updating in place), this works correctly for the last-wins dedup case. However, because `mc` is local and the cleanup loop runs `delete match_idx[i]` for `i in 1..mc`, if a prior call left stale keys in `round_match_pos` (e.g., from a different step label whose cleanup somehow failed), those stale keys could cause a duplicate round to be silently dropped rather than a new match recorded. In practice awk has no exceptions and the cleanup always runs, but the use of globals for inter-call state makes the contract implicit. **Suggested fix:** Move `round_match_pos` and `match_idx` into the function's local-variable parameter list (add trailing dummy params), eliminating the need for explicit cleanup and making cross-call isolation guaranteed.

2. **correctness** `skills/review-and-fix/scripts/review-implement-step5-loop.sh:121-125` — The in-process guard variable `STEP5_ROUND_${round_num}_TIMING_EMITTED` is set only after an awk probe confirms the ledger row is present with matching `start_s` and `end_s`. If `timing-ledger.sh`'s `sanitize_field` transforms the step label (e.g., collapses the em-dash U+2014 in `"Step 5 — code review"`) differently than the literal the awk probe expects, the probe never matches, the guard never sets, and a second call writes a duplicate round row to the ledger. The deferred helpers (`record-implement-review-round-timing.sh`, `record-plan-review-round-timing.sh`) have ledger-level idempotency and are immune to this; only the in-loop function is affected. **Suggested fix:** Match the awk probe in `_emit_implement_round_timing_row` against the sanitized form actually written by `timing-ledger.sh`, or simplify by setting the guard unconditionally after `timing-ledger.sh` exits 0 (the `|| true` means the exit code is always 0, so gating the guard on the awk probe is the only check).

3. **nit** `skills/design/scripts/design-publish.sh:217-230` — In the `mktemp`-failure branch of `render_fresh_timing_report_for_publish`, the code creates `$DESIGN_TMPDIR/timing-report-final.failure.log`, passes it to `append-tool-failure.sh` as `--output-file`, then immediately removes all `timing-report-final.*` with `rm -f`. This create-use-delete cycle within a single failure path is correct but unusual; a later change that reorders the `rm -f` before `append-tool-failure.sh` would cause `append-tool-failure.sh` to receive a missing file path silently. **Suggested fix:** Write the failure content directly to a temp path inside `$_tmp_dir` (where the directory creation failed, so `$_tmp_dir` is unset — use a different fixed temp path or `$DESIGN_TMPDIR/execution-issues.md` directly), avoiding the create-then-delete dance on `$DESIGN_TMPDIR`.

4. **nit** `skills/design/scripts/record-plan-review-round-timing.sh:58-62` — The OOS result fallback (`result=$NF`) is used when `$7` is empty or dashes. For a standard 6-column Markdown pipe table, `$7` is correctly the Result column. But if a `voting-tally.md` row has extra trailing pipe characters (e.g., from a tool that appends an alignment column), `$NF` would not be the Result, potentially causing the `result == "accepted"` comparison to silently produce wrong OOS counts. Since `voting-tally.md` is larch-generated, this is very unlikely in practice. **Suggested fix:** Remove the `$NF` fallback; when `$7` is empty or dashes, treat the result as missing/unknown and skip the row (i.e., `next` instead of the fallback assignment). A missing result should not default to the last field of an unpredictable row.
