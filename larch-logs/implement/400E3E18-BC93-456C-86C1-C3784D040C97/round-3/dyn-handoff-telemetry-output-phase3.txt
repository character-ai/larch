### In-Scope Findings

- **risk-integration** `skills/implement/SKILL.md:761-836` — The MAV and `coder-main-agent-required` terminal-stall prose instructs the main agent to "invoke `record-implement-review-round-timing.sh` per the deferred timing block below before leaving Step 5", but the code block immediately below contains `git add -A` followed by `commit-review-fixes.sh`. On a terminal stall after lint (i.e., the checks/lint repair exhausted its attempts), the main agent should only emit the timing row and then skip to Step 16 — it must NOT commit. A main agent that executes the whole "deferred timing block" on the stall path would produce a phantom commit before the Step-16 stall, violating the ordering invariant that deferred round `end_s` must land before `commit-review-fixes.sh`'s Step 7 mark. The success path naturally separates into three distinct fenced code blocks (record-timing, commit, re-invoke), but the stall path redirects to the same block containing commit commands. **Suggested fix:** Hoist the timing-emit snippet into a standalone fenced block labelled "deferred timing emit (both success and stall)" and place the `git add -A` / `commit-review-fixes.sh` in a separate block labelled "success path only — stage and commit". The stall-path prose should reference only the timing block, eliminating any ambiguity about whether the commit step applies.

- **correctness** `skills/design/scripts/plan-review-loop.sh:403-418` — `_emit_plan_round_timing_row` sets the idempotency guard variable (`PLAN_ROUND_N_TIMING_EMITTED=true`) unconditionally as its first action, before validating `start_s` and `end_s`. If `${_round_start:-}` is empty at the first call (which is possible when a terminal exit is triggered from a code path that never set `_round_start`), the guard is permanently set to `true` without writing any row, and subsequent calls with valid timestamps are silently suppressed. By contrast, `_emit_implement_round_timing_row` in `review-implement-step5-loop.sh` only sets its guard after confirming the row exists in the ledger. The design path uses `|| return 0` guards but those are unreachable after the guard is already set. **Suggested fix:** Validate `start_s` and `end_s` before setting the guard, or move the `printf -v "$guard_var"` assignment to after the helper invocation and a successful ledger probe, consistent with the implement version's pattern.

- **risk-integration** `skills/review-and-fix/scripts/review-implement-step5-loop.sh:248-265` — `_emit_implement_round_timing_row` does not set the one-shot guard variable until after the ledger write AND the awk verification both succeed. Between the `timing-ledger.sh record-round` call (`|| true`) and the awk check, if `timing-ledger.sh` writes the row but awk fails to read it back (e.g., due to a mid-write file lock timeout), the guard stays unset and a second call — if it occurred — would write a duplicate row. The `timing-report.sh` `emit_round_array` deduplicates by keeping the last row per round number, so a duplicate row for the same `(round, start_s, end_s)` tuple would be harmless, but a second call with a different `end_s` (e.g., after a delay) would silently overwrite the first row's duration. In practice the loop exits immediately after the first call, but the inconsistency compared to the design-path guard leaves a latent correctness hole. **Suggested fix:** Set the guard before the write (matching the design path) and rely on `record-implement-review-round-timing.sh`'s ledger-based idempotency for the deferred-emit case, or add a pre-write guard set followed by an early-exit check, eliminating the window between write and verify.

### Out-of-Scope Observations

- **code-quality** `skills/design/scripts/design-publish.sh:214-297` — `render_fresh_timing_report_for_publish` calls `append-tool-failure.sh` for the missing-`jq` case with `--exit-code 127` (command-not-found). If `jq` is present but the render itself fails (exit non-zero), the outer failure path also passes `"${_render_rc:-1}"` which may be 0 if only the `jq -e` validation failed (render succeeded but produced invalid JSON). The effective exit code logged to `execution-issues.md` would be `0` in that scenario, making the failure appear as a success. This is a pre-existing design risk amplified by the new render path but not introduced by it.
