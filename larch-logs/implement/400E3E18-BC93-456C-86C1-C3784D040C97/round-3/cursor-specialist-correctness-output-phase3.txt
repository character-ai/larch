### In-Scope Findings

1. **correctness** `skills/design/scripts/plan-review-loop.sh:423-437` — `_emit_plan_round_timing_row` sets the one-shot guard (`printf -v "$guard_var" '%s' true`) on line 429 **before** the `start_s`/`end_s` numeric-validation checks on lines 430–431. If the first call for a given round has an empty or non-numeric timestamp (e.g., `_round_start` unset due to an unexpected `date` failure), the guard is permanently set and all future calls for that round are silently skipped — no row is ever written. The plan specifies "emit rows only when final counts and wall time are known" and the plan's failure-mode section says "failed telemetry must never abort `/implement` or `/design`" but also implicitly that the row should still be written on the next valid call. The implement-side `_emit_implement_round_timing_row` in `review-implement-step5-loop.sh:101-126` correctly sets its guard only after the ledger write is confirmed via an awk probe. In practice `date +%s` rarely fails on macOS/Linux, so this is latent rather than immediate, but the asymmetry with the implement side is a correctness defect vs. the stated design. **Suggested fix:** Move `printf -v "$guard_var" '%s' true` to after the call to `record-plan-review-round-timing.sh` succeeds (or mirror the implement-side awk ledger-confirmation guard).

2. **correctness** `skills/review-and-fix/scripts/test-record-implement-review-round-timing.sh:20-21` — The test for the grep-n fallback path (round 2, `rejected-findings.md` containing `FINDING_1_OUTCOME=rejected` and `9:FINDING_2_OUTCOME=rejected`) only asserts the duration field (`$9 == 5`). It does not assert `$10 == 2` (accepted count from `accepted-findings.md`) or `$11 == 2` (rejected count from the grep-n fallback). If the `'^([0-9]+:)?FINDING_[0-9]+_OUTCOME=rejected$'` pattern silently matched only one row instead of two, or the `'^### FINDING_[0-9]+:'` accepted count was wrong, this test would still pass. The plan explicitly lists "rejected fallback counts `FINDING_N_OUTCOME=rejected` with and without `grep -n` line-number prefix" as a test requirement, but the assertion does not verify the counts. **Suggested fix:** Add `$10 == 2 && $11 == 2` to the awk filter on line 21.

4. **correctness** `skills/implement/SKILL.md` (MAV handoff, diff context) — The SKILL.md prose for `main-agent-vote-required` instructs re-running `tally-code-votes.sh` with `--review-tmpdir "$IMPLEMENT_TMPDIR/round-$FINAL_ROUND_NUM"` to populate `review-tally.env` before calling `record-implement-review-round-timing.sh`. However, `record-implement-review-round-timing.sh` reads the tally env from `$round_dir/review-tally.env` using exact key names `ACCEPTED_COUNT` / `ACCEPTED` and `REJECTED_COUNT` / `REJECTED`. If the actual key names written by `tally-code-votes.sh --review-tmpdir` differ from these (e.g., they use different key names), the deferred helper falls back to the grep-based accepted/rejected-file counts rather than the post-MAV tally, silently undercounting. The SKILL.md prose and the helper both assume the same key convention, but no test verifies that `tally-code-votes.sh` actually writes `ACCEPTED_COUNT` / `REJECTED_COUNT` into `review-tally.env` when invoked with `--review-tmpdir`. **Suggested fix:** Add a test fixture in `test-record-implement-review-round-timing.sh` that explicitly puts `ACCEPTED_COUNT=N` in `review-tally.env` and verifies the tally-env path takes priority — this already exists for round 3/4, but a comment explicitly documenting the MAV re-tally assumption would help.

5. **correctness** `skills/design/scripts/plan-review-loop.sh:1413-1422` (multi-round MAV path) — In the multi-round loop's `main-agent-vote-required` branch (`if [[ "$loop_status_override" == "main-agent-vote-required" ]]`), the code calls `_snapshot_terminal_exit_preserving_status` which calls `_persist_plan_round_start "$round_num" "${_round_start:-}"`. But `_round_start` was captured at the **top** of the while loop (line ~1450), before `_run_plan_review_round`. The MAV branch checks `loop_status_override` **before** the `_round_rc != 0` (panel-failed) guard, meaning `_round_start` is fresh. However the template says "no-clobber semantics so the original start timestamp is retained" — `_persist_plan_round_start` correctly uses `if [[ ! -e "$path" ]]` for no-clobber. But if a previous (Gate C) re-run had already written a `round-start-s` for the same `round_num` (SKILL.md notes "Each Step 3 entry clears plan-review/round-*/ before launch"), then no-clobber would preserve the stale timestamp from the previous entry — not the current run's `_round_start`. This is consistent with the design ("preserve original start timestamp") but could produce inflated round durations across entries. This is a pre-existing design trade-off rather than an introduced bug, but worth noting since the `round-start-s` persistence is new in this diff. **Suggested fix:** Document this edge-case in the `plan-review-loop.md` cross-entry forensic limitation note.
