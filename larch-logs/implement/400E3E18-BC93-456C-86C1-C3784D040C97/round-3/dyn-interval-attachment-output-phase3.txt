### In-Scope Findings

- **correctness** `scripts/timing-report.sh:381-415` — `emit_round_array` uses `round_match_pos` (a global awk array) as a dedup map keyed by round number. The cleanup loop at the end of the function (`delete round_match_pos[round_num[match_idx[i]] + 0]`) correctly removes only entries added in that call. However, the cleanup uses the array index stored in `round_match_pos[rkey]` implicitly via `match_idx` — it iterates `i = 1..mc` and reads `round_num[match_idx[i]]` to find the key to delete. After a dedup overwrite (`match_idx[round_match_pos[rkey]] = i`), `round_match_pos[rkey]` still holds the original position (not updated). The deletion then deletes based on `round_num` looked up from the overwritten `match_idx` position, which still has the correct `round_num` (both duplicates share the same round number). This works, but only because the overwritten entry still carries the same `round_num`. If a future change reuses `match_idx` positions across different round numbers (e.g., by compacting after dedup), the cleanup would delete the wrong key. As written this is logically correct but fragile — the reliance on both duplicates sharing the same `round_num` is an implicit invariant not enforced by the code or tests. **Suggested fix:** Reset `round_match_pos` explicitly at the start of each call (`delete round_match_pos` in gawk, or iterate and delete all entries before the fill loop) rather than relying on caller-side cleanup, eliminating the cross-call stale-state risk entirely.

- **correctness** `skills/design/scripts/plan-review-loop.sh:404-420` — `_emit_plan_round_timing_row` sets the one-shot guard variable (`printf -v "$guard_var" '%s' true`) **before** calling `record-plan-review-round-timing.sh`, so if the helper fails (e.g., transient `mktemp` or `flock` error that exits 0 via `|| true` without writing), the guard is already set and prevents retry within the same process. By contrast, `_emit_implement_round_timing_row` (`review-implement-step5-loop.sh:220-233`) sets the guard **only after** verifying the row was written (awk ledger check), enabling retry on failure. A design round emitted via `_emit_plan_round_timing_row` that fails silently will never retry, silently dropping the timing row. Both paths are best-effort, but the asymmetry is surprising and means design runs are more likely to lose timing data under transient failures than implement runs. **Suggested fix:** Move the `printf -v "$guard_var" '%s' true` to execute after calling the helper (with a ledger-verification awk check), matching the implement-side pattern. Alternatively, document the intentional difference and add a comment explaining why pre-set is acceptable for the design path.

- **correctness** `scripts/test-timing-report.sh:70-103` (fixture lines) — The test for "Step 5 re-mark attaches later round to the second Step 5 entry" includes round 4 (`round_start=35`, step="Step 5 — code review") written between the Step 7 mark (ts=30) and the re-mark (ts=45). The test verifies round 4 does NOT appear in either Step 5 entry via exact-equality `|.rounds == [...]` assertions. However, the test does NOT assert that round 4 produces NO orphan warning or that no `per_step` entry gains an unexpected `rounds` key. If a future refactor attaches orphaned rows to the enclosing implement step (by relaxing the step-label filter to interval-only matching), the `jq` assertions on specific arrays would still pass but an unintended `rounds` key would appear on Step 7. The fixture is comprehensive for current behavior but does not add a negative check (`has("rounds") | not`) on ALL entries except the two expected Step 5 entries. **Suggested fix:** Add `all(.per_step[]; if .step == "Step 7 — commit" or .step == "Step 5 — code review" and .duration_seconds == 20 or .step == "Step 5 — code review" and .duration_seconds == 15 then true else has("rounds") | not end)` (or an equivalent check) so orphaned round 4 never silently inflates an unexpected entry.

### Out-of-Scope Observations

- **code-quality** `skills/design/scripts/plan-review-loop.sh:381-416` — `_snapshot_terminal_exit_preserving_status` was modified to call `_emit_plan_round_timing_row` before `_snapshot_round_dir`. For the `main-agent-vote-required` branch, it calls `_persist_plan_round_start` instead. This is correct by intent, but `_emit_plan_round_timing_row` silently no-ops when `_round_start` is empty (the `[[ "$start_s" =~ ^[0-9]+$ ]] || return 0` guard). If `_round_start` is ever unset due to a code path that bypasses the assignment (pre-existing: the legacy single-pass path sets `_round_start` but the multi-round path has it in the loop body), the row would be silently dropped without any log message. This is a pre-existing structural risk that the new emission points inherit.
