Reviewing the branch diff and commit history for correctness issues in the timing-ledger and timing-report changes.
### In-Scope Findings

- **correctness** `skills/design/scripts/plan-review-loop.sh:423-437` — `_emit_plan_round_timing_row` arms the per-round `PLAN_ROUND_N_TIMING_EMITTED` guard when `record-plan-review-round-timing.sh` exits 0, but that helper (and `timing-ledger.sh` via `main … || true; exit 0`) never verifies that a `round` row actually landed in the ledger. If `append_tsv_line` fails closed (for example `flock` contention), the guard still flips to `true` and every later emission site for that round becomes a no-op, so `timing-report.json` can permanently omit a design round despite the loop believing timing was recorded. **Suggested fix:** Mirror the implement loop helper: after calling `record-plan-review-round-timing.sh`, confirm the expected row exists in `$DESIGN_TMPDIR/timing-ledger.tsv` (match on skill/step/round and ideally `start_s`/`end_s`) before setting `PLAN_ROUND_N_TIMING_EMITTED`, and leave the guard unset when verification fails so a later terminal/deferred hook can retry.

- **correctness** `scripts/timing-report.sh:381-392` — `emit_round_array` attaches a `round` row to a `per_step` entry using only `round_start ∈ [step_start, step_end)`; it does not bound `round_end` or the stored `duration_s` to that same interval. If a deferred implement row is recorded after `commit-review-fixes.sh` has already emitted the `Step 7 — commit review fixes` mark (violating the Step 5 ordering in `skills/implement/SKILL.md`), the row still attaches to Step 5 because `start_s` predates the Step 7 mark, but `duration_seconds` can span Step 7 wall time and exceed the parent Step 5 `duration_seconds` without any warning. **Suggested fix:** Either enforce ordering mechanically (helper refuses/fails when a later Step 7 mark already exists) or tighten attachment by requiring `round_end` (or `round_start + duration_s`) to also fall inside `[step_start, step_end)`, dropping or clipping rows that span the next step mark.

- **correctness** `scripts/timing-report.sh:384-391` — When more than one `round` ledger row for the same `(skill, step, round)` falls inside the same step interval, `emit_round_array` silently keeps only the last file-order match. The fixture in `scripts/test-timing-report.sh` depends on this behavior, but production double-writes (for example a partial in-loop row plus a deferred handoff row) would publish only the last row with no stderr signal, hiding incorrect earlier telemetry. **Suggested fix:** Treat duplicate `(skill, step, round)` matches within one interval as an error in tests and emit a `timing-report.sh: WARNING` when duplicates are detected, or deterministically prefer the row with the latest `end_s` only after logging the collision.

### Out-of-Scope Observations

- `scripts/timing-ledger.sh:314-315` — `main` forces exit 0 even when `cmd_record_round` returns failure; this is consistent with existing `mark`/`vendor` best-effort telemetry but means callers cannot distinguish validation/append failures without ledger scraping (pre-existing pattern extended by `record-round`).
- `skills/review-and-fix/scripts/record-implement-review-round-timing.sh:83-87` — Idempotent dedupe keys only on `(skill, step, round)`, so a bad first row blocks later correction; normal MAV/coder paths avoid double emission, but the dedupe policy is brittle if a malformed row is ever written first.
