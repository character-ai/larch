### FINDING_5: Stale timing-report-final deletion order diverges between design-publish.sh and design-pause-save.sh

**File:** `skills/design/scripts/design-publish.sh` ~line 1379  
**Severity:** minor  
**Category:** edge-cases

**Observation:**

`render_fresh_timing_report_for_publish()` in `design-publish.sh` performs the stale-file deletion loop *after* the `mktemp` call succeeds:

```bash
tmpdir=$(mktemp -d ...)          # ← mktemp first
# ... stale deletion loop here (inside mktemp-success path)
"$PLUGIN_ROOT/scripts/timing-report.sh" ... > "$tmpdir/timing-report-final.json"
```

By contrast, `render_fresh_timing_report_for_pause_publish()` in `design-pause-save.sh` deletes stale files *before* calling `mktemp`:

```bash
# stale deletion loop first
tmpdir=$(mktemp -d ...)          # ← mktemp second
```

The consequence: if `design-publish.sh` exits between the `mktemp` call and the stale-deletion loop (e.g., `set -euo pipefail` firing on an intermediate command), the stale `timing-report-final.*` files survive and a subsequent run may serve the old report. More practically, the two functions now diverge silently in a way that creates maintenance confusion — a developer reading `design-pause-save.sh` and expecting the same pattern in `design-publish.sh` will not find it.

There is no race window where a *reader* picks up the stale file between deletion and replacement (publish is single-process), so this is a maintenance/correctness-under-abort concern rather than a live race.

**Suggested fix:** Move the stale deletion loop to before the `mktemp` call in `design-publish.sh` to match `design-pause-save.sh`. This makes the two functions structurally identical and eliminates the abort window.

## Out-of-Scope Observations

### OOS_1: Rejected-count fallback grep uses `$'\r'`-sensitive line anchor

**File:** `skills/review-and-fix/scripts/record-implement-review-round-timing.sh`

The rejected-count fallback pattern:

```bash
grep -cE '^([0-9]+:)?FINDING_[0-9]+_OUTCOME=rejected'
```

uses `^` as a line-start anchor. On files with Windows CRLF line endings (`\r\n`), the `\r` remains before the newline, so lines are `FINDING_1_OUTCOME=rejected\r`. The `^` anchor matches the start of the logical line, but the pattern matches the full field content up to the newline — the trailing `\r` is after the `d` in `rejected`, so `rejected\r` ≠ `rejected` and the pattern does not match. The accepted-count grep (`^### FINDING_[0-9]+:`) has the same exposure. In practice these files are written by larch scripts on Unix and the risk is low, but the failure mode is silent (count becomes 0 rather than an error), which makes it hard to detect if a CRLF file ever appears.

This is out of scope for this review (CRLF handling was not part of the stated feature).

### OOS_2: `round_end` array populated in timing-report.sh but never consumed by emit_round_array

**File:** `scripts/timing-report.sh`

The round-row parsing block populates `round_end[i]` from `$8`, and `emit_round_array` accepts `start, end` parameters — but inside the function, only `round_start[j]` is used for the `[step_start, step_end)` interval filter; `round_end[j]` is never read. The emitted JSON object also does not include an `end_s` field (only `start_s`, `duration_s`, `accepted`, `rejected`, `oos`). The `round_end` array is allocated, maintained, and never used. This is dead state — not harmful, but wasteful and potentially confusing during future maintenance.

This is out of scope for this review (the field was present in a prior design iteration and its removal or inclusion is a feature decision).
