Reviewing `lint-codex-exec-auth.sh` and related changes for correctness of its suppression mechanisms.
### In-Scope Findings

- **correctness** `scripts/lint-codex-exec-auth.sh:205-212` — The markdown scanner uses a single `in_fence` flag with no nesting depth. Any line inside an open `bash`/`sh`/`shell` fence that matches `^[[:space:]]*```[[:space:]]*$` clears `in_fence`, even when that closing fence belongs to nested markdown/heredoc content still inside the outer fence. Later `codex exec` lines in the same outer block are then skipped, so unwired dispatch in skill/reference fences can slip through undetected. **Suggested fix:** Track fence depth (increment on open, decrement on bare close) or only treat a closing fence as valid when depth returns to zero; add a harness fixture with a bash fence containing an inner ` ``` ` example and a trailing raw `codex exec`.

- **correctness** `scripts/lint-codex-exec-auth.sh:119-121` — Allowlisting is basename-only (`basename "$rel"`) before the per-line scan. Under the in-scope glob `skills/*/scripts/*.sh`, any file named `launch-codex-exec.sh`, `launch-review.sh`, etc. is exempt for the whole file, not just the canonical `scripts/` launcher. That is exact string equality, not substring matching, but a future or mistaken copy under `skills/*/scripts/` would be fully ignored. **Suggested fix:** Restrict basename allowlisting to `scripts/*.sh` (top-level only), or require an exact relative-path allowlist for `skills/review-and-fix/scripts/review-and-fix.sh`; keep pragma/line rules for everything else.

- **correctness** `scripts/lint-codex-exec-auth.sh:135-141,189-195` — Detection is limited to the contiguous literal `codex[[:space:]]+exec`. Static lines that dispatch via a variable command word (`"$CODEX_BIN" exec …`, `"${CODEX_BIN:-codex}" exec` only when `codex` is not immediately adjacent to `exec`, `exec "$codex_bin"`, etc.) never match, so unwired call sites can evade the guard while still running Codex. Path-qualified `/path/to/codex exec` is caught; variable-qualified forms are not. **Suggested fix:** Extend the matcher (or add a second rule) for common alternate spellings such as `"$…" exec` / `exec` immediately after a Codex-path variable when paired with Codex flags (`--full-auto`, `--sandbox`, `-C`, `--output-last-message`), and pin bypass cases in `scripts/test-lint-codex-exec-auth.sh`.

### Out-of-Scope Observations

- **correctness** `scripts/run-external-agent.sh` — Still a generic `"$@"` wrapper with no `external_prepare_codex_auth` wiring; callers must supply auth-aware argv. That matches the plan (launcher layer owns auth), but it remains the path used by `launch-codex-exec.sh` and was called out in the attached OOS as a surface that does not itself enforce env-key auth.

- The env-prefix skip regex at `scripts/lint-codex-exec-auth.sh:140,194` correctly handles chained prefixes (`CODEX_HOME=… OTHER=1 codex exec …`; covered by `scripts/test-lint-codex-exec-auth.sh:90-92`), and lines with no assignment prefix are still checked on the full line first (`135-137`). The post-strip pass is effectively redundant whenever `codex exec` appears contiguously on the raw line; that does not create a false-negative for chained env prefixes.

- Pragma suppression (`129-130`, `184-185`) correctly honors trailing `codex exec … # lint-codex-exec-auth: ok …` and rejects embedded string pragmas (`scripts/test-lint-codex-exec-auth.sh:55-57`). Pragma on a separate continuation line without joining via `\` does not suppress a prior `codex exec` line — correct.
