Reviewing the round-cursor state machine: reading the diff and key implementation files.
Checking whether `write-cursor` failures are handled elsewhere and verifying the leading-zero arithmetic edge case:
### In-Scope Findings

- **correctness** `skills/design/SKILL.md:1023-1027` — Step 3 advances the in-shell `ROUND_NUM` and passes it to `plan-review-loop.sh` immediately after calling `write-cursor`, but never checks the script’s exit status. The Step 3 bash fence does not run under `set -e`, so a failed `write-cursor` (disk full, permission error, invalid tmpdir) leaves `plan-review-round-cursor.txt` at *N* while `ROUND_NUM` becomes *N+1* in the same fence. `plan-review-loop.sh` then runs with an inflated `--round-num`, while Step 3.6 (separate fence) re-reads the cursor file and stays on *N*, so `write-after`, assessor inputs, and the WORSE/Stop UX can disagree with the review round that actually ran. **Suggested fix:** After `write-cursor`, require exit 0 (or re-read via `read-cursor` and set `ROUND_NUM` only from the file). Do not assign `ROUND_NUM=$_next_cursor` unless the cursor file was updated successfully.

- **correctness** `skills/design/scripts/snapshot-plan-round.sh:31-46` — `parse_cursor_file` treats any all-digit string (e.g. `008`) as valid and returns it unchanged, but `skills/design/SKILL.md:1024` uses `$((ROUND_NUM + 1))` without a `10#` base prefix. In Bash, `008` triggers `value too great for base`, which can abort cursor advancement mid–Step 3 while `plan-after-round-<N>.txt` already exists, leaving the cursor file and snapshots inconsistent. `write-cursor` already normalizes with `10#`; `read-cursor` does not. **Suggested fix:** Normalize in `parse_cursor_file` (e.g. `printf '%s' $((10#raw))` after validation) or reject leading-zero forms as malformed per FINDING_13; mirror the same `10#` rule in SKILL.md’s `_next_cursor` arithmetic.

- **correctness** `skills/design/SKILL.md:1151-1161` — Step 3.6 calls `write-after --round "$ROUND_NUM"` only when `ROUND_NUM` is already set in the shell, and skips `read-cursor` in that case. `assess-plan-round.sh` always reads `plan-review-round-cursor.txt` independently (`assess-plan-round.sh:24-33`, `87-95`). If `ROUND_NUM` leaks across fences (or from a failed Step 3 advance above), `write-after` can target the wrong round (including write-once `plan-after-round-<wrong>.txt`) while the assessor compares `plan-after-round-<cursor-1>.txt` vs `plan.txt` for the file cursor—skipping the gate, firing it on the wrong baseline, or poisoning later snapshot-existence checks. **Suggested fix:** Always call `read-cursor` at the start of Step 3.6 and use that value for both `write-after` and operator messaging; optionally parse `ROUND_NUM=` from `assess-plan-round.sh` stdout for Stop/`ASSESSOR_ROUND_NUM` instead of the shell local.
