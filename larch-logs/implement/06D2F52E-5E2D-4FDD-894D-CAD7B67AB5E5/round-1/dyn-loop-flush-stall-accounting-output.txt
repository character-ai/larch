Analyzing the diff and `flush_review_batches` behavior for stall-path correctness.

### In-Scope Findings

- **correctness** `review-implement-step5-loop.sh:136-288` — After a successful `_implement_round_body` (`post_exit` 0), `review-and-fix.sh` already calls `flush_review_batches` with the real `total_exonerated` / `total_neutral` (and composed findings when available) at `review-and-fix.sh:1413-1422`. Many stall branches in `run_implement_loop` then call `flush_review_batches "$IMPLEMENT_TMPDIR" "$RUN_ID" "$rounds_completed" 0 0 0 0` again. `code-review-tally` is a **replace** batch per `scripts/larch-log-batches.sh:17`, so this is not an append-only duplicate row problem, but the second write still re-runs `write-tally.sh` with `exonerated`/`neutral` taken from the **literal** `0`/`0` arguments (`review-and-fix.sh:669-680`), while accepted/rejected in the record are driven by `derived_*` from the recomposed JSONL. That can **overwrite** a correct tally JSON with **zeroed exonerated/neutral metadata** (and refresh `--rounds` to `$rounds_completed`) even though the round actually produced non-zero exonerations/neutrals, corrupting run-log semantics for any consumer that trusts those JSON fields. **Suggested fix:** Drop the redundant stall-path `flush_review_batches` whenever the inner round already flushed successfully (`post_exit==0` and the round’s `flush_review_batches` path ran), or thread the last round’s `total_exonerated`/`total_neutral` (and optional composed path) through `IRF_LAST_*` / `review-and-fix.env` and pass those through on any genuine “flush once more” path instead of hardcoded zeros.

- **correctness** `review-implement-step5-loop.sh:102-105` — On entry, if `round_num` already exceeds `effective_round_cap` (MAV resume past cap), the loop emits `mav-resume-past-cap` and calls `flush_review_batches` with `"${rounds_completed:-0}"` while `rounds_completed` is still the initial `0` because `_implement_round_body` never ran. That issues another **replace** `code-review-tally` write with `ROUNDS=0` and `exonerated=neutral=0`, which can clobber a previously correct tally from earlier Step 5 work in the same `RUN_ID` / log root. **Suggested fix:** Skip this flush entirely on the pure “resume past cap with no new round” path (log consumers already have prior batches), or flush using the last known round index and tallies read from disk (`round-(N)/review-and-fix.env` / composed artifacts) instead of `0`.

### Out-of-Scope Observations

- The original concern about append-only duplicate **zero-count** tally **rows** is mitigated by batch mode `replace` for `code-review-tally` and `review-findings-full` in `scripts/larch-log-batches.sh:17-18`; the regression risk from this branch is **metadata overwrite** on the second flush, not unbounded duplicate JSONL lines.
