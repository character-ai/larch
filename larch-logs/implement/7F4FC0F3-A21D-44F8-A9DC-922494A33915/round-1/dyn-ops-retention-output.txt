### In-Scope Findings

- **risk-integration** `docs/configuration-and-permissions.md:284` — The updated `LARCH_CLEANUP_RETENTION_DAYS` blurb states that `/cleanup` removes matching `/tmp` larch patterns “only when no file within a bounded scan (`find -maxdepth 5`) was modified inside the retention window,” but runtime only applies that nested-activity gate to **directories**; stale `/tmp` **files** matching patterns (e.g. `larch4-review.diff`) are deleted on top-level `-mtime +N` alone (`skills/cleanup/scripts/cleanup.sh:106-108`). Operators tuning retention from this env-var doc may assume loose `/tmp` artifacts get the same nested-activity protection as session directories. **Suggested fix:** Split the sentence: cache and `/tmp` **directories** require the bounded nested scan; `/tmp` **files** are removed on top-level age plus pattern match only. Point to `skills/cleanup/scripts/cleanup.md` / `SECURITY.md` for the full split model.

- **risk-integration** `docs/skills.md:47` — The catalog blurb applies the nested-scan removal rule uniformly to “An entry,” which overstates protection for `/tmp` files (same directory-vs-file asymmetry as above) and omits operator-relevant failure semantics that this branch now documents in `SECURITY.md` and `skills/cleanup/scripts/cleanup.md`: scan `find` failure warns and skips that entry (fail-safe), top-level enumeration `find` failure is silent fail-open (`CACHE_REMOVED=0`, exit 0), and the `/tmp` pass pre-filters by top-level `-mtime +N` while the cache pass does not. **Suggested fix:** Mirror the `SECURITY.md` split: directories vs files, cache vs `/tmp` enumeration, depth-5 tradeoff, and the two failure modes; keep the existing “≤ 5 levels” retention wording.

- **risk-integration** `skills/cleanup/SKILL.md:9` — The shipped skill prompt (what agents relay at invoke time) was updated to nested-activity language but still omits the depth-bound tradeoff (activity deeper than five levels does not protect), scan fail-safe, enumeration fail-open, and cache-vs-`/tmp` enumeration asymmetry that `SECURITY.md:234` and `skills/cleanup/scripts/cleanup.md:9-13` now treat as part of the deletion contract for session state that may hold secrets. An operator relying on `/cleanup` Step 1 output alone can misread `CACHE_REMOVED=0` + exit 0 as “nothing stale” rather than possible silent enumeration failure or per-entry scan skip. **Suggested fix:** Add one short paragraph or bullet list to `SKILL.md` covering depth-5 limit, fail-safe vs fail-open, and cache vs `/tmp` path differences, with a pointer to `SECURITY.md` for auditors.
