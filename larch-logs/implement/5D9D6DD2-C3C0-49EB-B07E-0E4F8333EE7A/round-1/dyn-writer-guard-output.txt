Reviewing the writer-guard security boundary: reading the diff, commit history, and `session_env.py` implementation.
### In-Scope Findings

- **security** `python/session_env.py:216-239,270-278` — `_atomic_write` creates its temp file with `tempfile.mkstemp` and does not set `O_NOFOLLOW`, while the plan called for mirroring `finalize._write_finalize_text_safely` (`python/finalize.py:636-662`), which opens the temp path with `O_CREAT|O_EXCL|O_NOFOLLOW`. On main, `write_finalize_state_merged` used that safe helper; after the move into `session_env.py` it now calls `_atomic_write`, so merge writes to `finalize-state.sh` no longer get the stronger symlink-refusal guarantees that ship already documents for state-file writes. A same-UID attacker who swaps a parent directory or temp target to a symlink can redirect the temp+replace sequence. **Suggested fix:** Port the `O_EXCL|O_NOFOLLOW` open-and-replace logic from `_write_finalize_text_safely` into `_atomic_write` (or have `write_finalize_state_merged` call `_write_finalize_text_safely` again), and add pytest coverage for symlinked destination/temp parents.

- **security** `python/session_env.py:725-750,847-884` — `persist-run-flags` and `restore-finalize-state` enforce per-writer key allowlists and CR/LF rejection on KV payloads, but neither verb validates `--implement-tmpdir` with `_writer_target_allowed` before writing `run-flags.sh`, `finalize-state.sh`, or `final-bail-reason.txt`. A mistyped or attacker-influenced `--implement-tmpdir` (e.g. `/etc`, `$HOME`) can therefore create or overwrite session-state files outside the temp/cache session roots that `write-env` and `write-design-env` are restricted to (`python/session_env.py:453-456,576-577`). This gap is amplified by the new `SECURITY.md` claim that session writers “limit session-content destinations to temp/cache session roots” (`SECURITY.md:289`). **Suggested fix:** Require `_writer_target_allowed(Path(args.implement_tmpdir))` (and `_safe_output_parent` on the parent of each output file) in both verbs before any `_atomic_write`, with rejection tests mirroring `test_write_env_writer_guard_and_plugin_root_only`.

- **security** `python/session_env.py:573-633` — `write_design_env_main` checks `_writer_target_allowed(out_path)` but never calls `_safe_output_parent`, which `write_env_main` applies at `python/session_env.py:455-456`. If `--output`’s parent is a symlink, `_atomic_write` still runs `mkstemp(dir=str(path.parent))` and `replace()` against that parent, so the validated absolute `out_path` string does not guarantee the bytes land where the guard intended. That weakens the highest-risk `write-design-env` surface called out in the plan (sourceable env + `~/.cache` symlink refresh). **Suggested fix:** Reject symlinked output parents with `_safe_output_parent(out_path)` before `_atomic_write`, and add a pytest that places the parent under a symlink and expects failure.

- **security** `python/session_env.py:634-642,541-543` — The design current-env symlink refresh builds `symlink_path` via `_design_symlink_path` but has no dedicated validator that the symlink location is exactly `Path.home() / ".cache" / "larch" / "sessions" / "current-design-env-$PPID.sh"` with non-symlink ancestors, as the plan and `SECURITY.md:289` describe (“explicit carve-outs with their own validators”). `symlink_path.parent.mkdir(...)` and `tmp_link.replace(symlink_path)` follow symlinked `~/.cache` or `sessions` components without refusal, so a same-UID layout that symlinked those directories can redirect the stable design rehydration symlink outside the intended hardcoded tree. **Suggested fix:** Add a `_validate_design_symlink_location(path: Path) -> None` that resolves parents, rejects symlinked ancestors, and asserts the final path matches the hardcoded `~/.cache/larch/sessions/current-design-env-{pid}.sh` pattern before `mkdir`/`symlink_to`/`replace`.

- **security** `python/session_env.py:881-884` — `restore_finalize_state_main` runs `_validate_no_newlines` on the 20-key `finalize-state.sh` payload but writes `BAIL_REASON` from `ship-pr-state.sh` straight to `final-bail-reason.txt` with no CR/LF check. Untrusted or corrupted `ship-pr-state.sh` bytes can therefore inject arbitrary multiline content into a downstream artifact that may be fed to `larch-log.sh write` (`python/session_env.py:887-899`), while neighboring KV output is sanitized. **Suggested fix:** Reject `BAIL_REASON` values containing `\n` or `\r` before `_atomic_write`, or route bail text through the same value sanitizer used for KV writers, with a pytest fixture containing embedded newlines.

### Out-of-Scope Observations

- **security** `python/session_env.py:197-208` — `is_allowed_session_tmpdir` and `_writer_target_allowed` are separate entry points (cleanup vs write) but currently implement identical root sets; that matches the plan’s shared root list and does not let cleanup’s predicate bypass write guards, but the duplication could drift later without a shared helper or comment pinning the intentional split.

- **security** `python/session_env.py:697-717` — `write-id` and `write-run-params` also skip `_writer_target_allowed`; retired bash had the same behavior, so this is pre-existing trust in caller-supplied paths rather than a regression, though it remains outside the narrowed guard surface now documented in `SECURITY.md`.

- **security** `python/finalize.py:757-760` — Full `write_finalize_state` still uses `_write_finalize_text_safely` with `O_NOFOLLOW`; only the merged-write helper regressed in this branch.
