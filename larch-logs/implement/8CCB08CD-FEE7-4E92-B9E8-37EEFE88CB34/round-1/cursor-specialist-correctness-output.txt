### In-Scope Findings

1. **Important** `correctness` ([`scripts/sessionstart-health.sh`](scripts/sessionstart-health.sh) ~129–131) — **Plan-correctness / requirements (`both`)**: The feature asks to drive resolver session binding from the SessionStart JSON `session_id`, but the script only runs `[[ -n "$SID" ]] && export LARCH_TOKEN_SESSION_ID="$SID"`. If `session_id` is missing, null, or empty, any **inherited** `LARCH_TOKEN_SESSION_ID` in the hook process stays set; [`lib-resolve-implement-tmpdir.sh`](skills/implement/scripts/lib-resolve-implement-tmpdir.sh) then enforces session-id binding against the wrong value. **Concrete scenario:** `.larch-keepalive` has `SESSION_ID=session-A`, wrapper leaked `LARCH_TOKEN_SESSION_ID=session-B`, stdin is `{"cwd":"/clone"}`. No keepalive row matches `session-B` → resolver returns empty → **no boundary advisory** even with `design-export/manifest.env` and no `.boundary-gate-passed` (false negative vs “re-inject NEXT REQUIRED advisory”). **Suggested fix:** When `SID` is empty after jq, `unset LARCH_TOKEN_SESSION_ID` (or export an explicitly empty handling agreed with resolver) before calling `resolve_implement_tmpdir`, so “no signal in payload” cannot be overridden by stale env.

2. **Nit** `risk-integration` ([`scripts/merge-pr.sh`](scripts/merge-pr.sh), [`scripts/test-merge-pr.sh`](scripts/test-merge-pr.sh), plus log/version commits) — **Completeness w.r.t. plan / requirements**: The pasted `<implementation_plan>` and `<feature_description>` only cover SessionStart boundary detection and its tests/docs. The branch diff also contains merge-pr “flush-only divergence” recovery, harness changes, and `chore(larch-logs)` / version work. That is not a logic bug by itself, but it **contradicts** a narrow “SessionStart-only” reading of the plan text and complicates bisect/revert. **Suggested fix:** Treat as separate PR or document clearly in the PR body.

3. **Nit** `code-quality` (implementation plan text embedded in the run-log diff, not a runtime file) — **Completeness w.r.t. plan**: The plan says “test cases 12–16” while the harness adds 12, 12b, 13, 14, 14b, 15, 15b (no distinct “16”). Behavior matches the feature list; only numbering is off. **Suggested fix:** Align plan wording with case IDs.
