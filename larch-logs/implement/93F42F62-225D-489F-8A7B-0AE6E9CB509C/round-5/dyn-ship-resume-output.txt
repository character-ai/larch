### In-Scope Findings

- **risk-integration** `skills/design/scripts/design-route.sh:294-368` — WI3 keeps the pause marker on every `LOAD_OK=false` path, but `design-route.sh` still falls through to title/reentry/plan routing when load fails (contract in `design-route.md` line 31). Before WI3, many restore failures deleted the marker, so fallthrough could start a fresh `/design` without a resume pointer. Now a failed restore (e.g. `snapshot-not-found`, `missing-restored-artifact`) leaves the marker in place while routing may still reach `ROUTE=proceed`, so every `/design` invocation pays a failed `design-pause-load.sh` attempt first and the issue body carries a stale pause block alongside a new design run. That is the #3506 recovery tradeoff taken too far at the route boundary. **Suggested fix:** When a pause marker is present and `LOAD_OK=false`, stop fallthrough: emit `ROUTE=cancel-pause-load` (or a dedicated retry route) and abort until the snapshot is fixed or the operator clears the marker manually; reserve `ROUTE=proceed` only when no pause marker exists.

- **risk-integration** `scripts/design-pause-load.sh:310-327` — On success the loader installs via `cp -R` and reports `LOAD_OK=true` even when `clear_pause_marker` fails (`MARKER_CLEARED=false`, `WARN=marker-delete-failed`). A second `/design` on the same issue still sees the marker, re-runs pause-load, and overwrites `$DESIGN_TMPDIR` from the published snapshot again. Any in-session tmpdir progress after the first successful restore (before a re-pause) is lost silently. **Suggested fix:** Treat a stale marker after successful install as an operator-action item: either retry marker deletion before returning success, surface a loud Step 0b breadcrumb that re-invoking `/design` will clobber the live tmpdir, or skip re-load when `.resume-loaded` is already present in the target tmpdir for the same `RUN_ID`.

- **risk-integration** `scripts/design-pause-load.sh:25-28,276-304` — `emit_load_fail` now never clears the marker, including for non-retryable validation failures (`restored-issue-mismatch`, `restored-run-id-mismatch`, `invalid-restored-manifest`, marker field validation errors). Those errors cannot be fixed by retrying the same load, but the marker persists and `design-route.sh` does not cancel the route, so the operator is stuck in a fail-then-fallthrough loop until manual marker surgery. WI3 correctly keeps the marker for retryable extract failures; applying the same rule to permanent mismatches amplifies the route-integration gap above. **Suggested fix:** Split failure classes: keep the marker only for retryable tokens (`snapshot-not-found`, `snapshot-extract-failed`, `missing-restored-artifact`, install failures); delete (or route to `cancel-pause-load` with explicit guidance) for binding mismatches and corrupt marker payloads.
