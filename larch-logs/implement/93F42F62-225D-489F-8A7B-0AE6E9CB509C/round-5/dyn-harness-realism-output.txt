Reviewing the branch diff and test harnesses for correctness and realism.
### In-Scope Findings

- **correctness** `skills/design/scripts/test-design-pause-resume.sh:742-746` — The remote-recovery (`LOG_RECOVERY_BRANCH=larch-log-design-RUNPAUSE1` → `FETCH_HEAD`) case is the only ref path that exercises `rev-parse --verify FETCH_HEAD^{commit}` before extraction, but the harness throws away loader stdout and asserts only that `git fetch` and that `rev-parse` line appeared in stub logs. It never checks `LOAD_OK=true`, restored artifacts under `$TMP/restore-recovery`, or marker lifecycle. A regression that pins `FETCH_HEAD` correctly but then passes a mutable ref (or wrong SHA) into `git ls-tree`/`git show` would still pass this case while breaking real resume; this is exactly the highest-risk ref kind called out in the plan’s failure-mode #2. **Suggested fix:** Capture `out_recovery_load`, assert `LOAD_OK=true`, verify `manifest.json`/`plan.txt` (and `.resume-loaded`) in `$TMP/restore-recovery`, and assert marker delete-on-success; optionally add a stub-only negative where `ls-tree` is invoked with `FETCH_HEAD` instead of the pinned SHA and expect `snapshot-extract-failed`.

- **correctness** `skills/design/scripts/test-design-pause-resume.sh:130-156` — The rewritten git stub’s `ls-tree` arm lists files with `find` on the mutable `$SNAPSHOT_ROOT` working tree, and `show` reads the same filesystem paths. That is not equivalent to production, where enumeration and extraction both come from the same commit object via `git ls-tree … "$snapshot_sha"` and `git show "$snapshot_sha:$path"`. Stub-backed round-trips can stay green even if `ls-tree` and `show` disagree on blob identity, ordering, or missing blobs at the pinned SHA. The new real-git export-ignore subshell mitigates this for two ref kinds only (local recovery branch and `origin/main`), not the `FETCH_HEAD` fetch path. **Suggested fix:** Teach the stub to serve paths/blobs from a fixture commit (or a small in-stub object store keyed by `$STUB_SNAPSHOT_SHA`), and add a real-git case that fetches a remote recovery branch into `FETCH_HEAD` under `larch-logs/ export-ignore`.

- **correctness** `skills/design/scripts/test-design-pause-resume.sh:266-310` — The WI2 “real git export-ignore” reproduction proves `ls-tree`+`show` restore succeeds but never runs the negative control that motivated the bug (`git archive "$ref" "larch-logs/design/<RUN_ID>/"` producing an empty tar in this repo). Without that contrast, the test cannot detect a partial revert back to `git archive | tar` on the same fixture. **Suggested fix:** In the export-ignore subshell, assert `git archive … | tar -t` is empty (or fails to list `plan.txt`) while the loader path restores `plan.txt` and `.completed/step-1c`.

- **correctness** `skills/design/scripts/test-design-pause-resume.sh:772-774` — Local recovery (`larch-log-design-recovery-RUNPAUSE1`) load also discards stdout and only checks that `origin` was not fetched. It does not assert `LOAD_OK=true` or that `$TMP/restore-local-recovery` received snapshot files, so a broken local-branch restore path could slip through if fetch-behavior assertions alone pass. **Suggested fix:** Assert full loader success and artifact presence for the local-recovery branch, mirroring the round-trip block at lines 255–262.

That is intentional per `read_resume_counters`’ docstring, but the new ship-resume tests do not use realistic corrupt-state fixtures produced by a prior bash run.

This matches existing `test_ship.py` style and predates the pause/resume shell work; serde drift in real `gh pr view` output would still not be caught here.
