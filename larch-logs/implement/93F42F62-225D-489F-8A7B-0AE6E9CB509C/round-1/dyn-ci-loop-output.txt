Reviewing the branch diff and commit history for correctness issues in the pause/resume changes.
### In-Scope Findings

- **correctness** `python/ship.py:1237,1298` — The merge-loop safety cap uses `iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS` (strictly greater than 50), while the embedded CI decision logic in `python/ci_monitor.py:142` bails at `iteration >= config.CI_MONITOR_MAX_ITERATIONS` (greater-than-or-equal to 50), matching `scripts/ci-decide.sh:123`. In production, `poll_ci` usually stalls at 50 before the outer cap is reached, but the ship-level `> 50` check allows one additional outer-loop pass when `monitor()` returns `action="wait"` (as in `test_open_pr_resume_at_iteration_cap_wait_stalls_after_monitor`) and increments the counter to 51 before stalling. That is an off-by-one mismatch between the two cap layers and diverges from bash’s `-ge 50` semantics on the outer counter. **Suggested fix:** Align the merge-loop cap with `decide()` / bash by using `iteration >= config.SHIP_MERGE_LOOP_MAX_ITERATIONS`, or document and test that the outer cap is intentionally one step looser than the inner cap.

- **correctness** `python/ship.py:590-613,826-838` — `_fresh_resume_plan` always zeroes `ResumeCounters` even when called with persisted state counters (e.g. after transient `gh pr view` failure on an `open-pr` resume at `ITERATION=50`). The run restarts on the `fresh` path with `iteration=0`, effectively resetting merge-loop budget. `test_fresh_fallback_hydrates_modes_and_resets_counters` encodes this as intentional, but it means a flaky `gh` read can bypass iteration-cap enforcement that was already persisted in `ship-pr-state.sh`. **Suggested fix:** If parity with bash resume is required, preserve `read_resume_counters` on gh-failure fallbacks that still have a valid `PR_NUMBER` in state (route to `blocked` / retry rather than `fresh`), or at minimum preserve `iteration` when re-entering the merge loop for an existing PR.
