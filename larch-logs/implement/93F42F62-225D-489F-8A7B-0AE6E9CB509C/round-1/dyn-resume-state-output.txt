Reviewing the branch diff and commit history for risk-integration issues in resume-state handling.
### In-Scope Findings

- **risk-integration** `python/ship.py:1178-1192` — On `open-pr` resume the driver skips `_pending_oos_gate` / `_materialize_manifest_oos` (those run only when `resume.start == "fresh"`), so a persisted `OOS_PENDING=true` state is never re-checked before `ensure_pr` and downstream CI/merge. Tests (`test_open_pr_resume_skips_pending_oos_gate`, `test_open_pr_resume_skips_leftover_oos_artifacts`) lock this in: ship can return `Outcome.OK` while `OOS_PENDING=true` and accepted-OOS artifacts remain in the tmpdir. Bash `ship-pr.sh` still blocks at `run_pr_create_phase` when `OOS_PENDING=true` and routes back to `pr-prep` for disposition (`scripts/ship-pr.sh:1274-1277`), so Python resume can complete shipping without the mechanical OOS disposition checkpoint that the shell path enforces. **Suggested fix:** On any resume path where `OOS_PENDING=true` (or accepted-OOS / security-OOS artifacts are present), run the same disposition gate as the fresh `pr-create` path before `ensure_pr`; if disposition is incomplete, return `NEEDS_USER_INPUT` with `NEEDS_USER_OOS_FILING` instead of proceeding.

- **risk-integration** `python/ship.py:590-613,816-838` — `_fresh_resume_plan` always zeroes `ITERATION` / `REBASE_COUNT` / `FIX_ATTEMPTS` / `TRANSIENT_RETRIES` even when callers pass preserved counters after branch/repo safety checks pass. Transient `gh.pr_view` failure, PR head mismatch, invalid/missing `PR_NUMBER`, or closed-unmerged PR state all fall back to `start="fresh"` with counters reset (`test_fresh_fallback_hydrates_modes_and_resets_counters` asserts `ITERATION=0`). A run that already exhausted most of the merge-loop budget can therefore regain a full counter budget after a flaky resume classification, weakening the iteration-cap safety rail. **Suggested fix:** Either stall with a structured resume error when classification fails but counters are non-zero, or carry forward persisted counters on “degrade to fresh” paths instead of unconditionally resetting them in `_fresh_resume_plan`.

- **risk-integration** `python/ship.py:801-917` — In `gh_skipped` mode (`repo_unavailable`, `forked`, or `forked_target`), `_resume_plan` can return `open-pr` using only persisted `PR_NUMBER` / branch checkout, without `gh.pr_view` head-ref validation that the non-skipped path requires (`viewed.head_ref != branch_name` at `839-846`). A stale or hand-edited `PR_NUMBER` paired with a matching local branch can resume CI/merge against the wrong PR identity; `test_forked_target_main_resume_uses_pr_only_path` exercises main-branch fork resume without GH. **Suggested fix:** In `gh_skipped` mode, require an additional local anchor (e.g., persisted `PR_URL` match, `manifest.json` / `parent-issue.md` cross-check, or explicit operator `--pr-number` override) before classifying `open-pr`, or fail closed to `NEEDS_USER_INPUT` when PR identity cannot be corroborated.

- **risk-integration** `python/ship.py:879-905` — For `gh_skipped` resumes, `local_merged` can be true from `manifest_status(ctx) == "done"` alone (plus `pr_number is not None`), routing to the `merged` → `run_postmerge_phase` path without remote merge confirmation. A prematurely flushed or corrupted in-tmpdir manifest marked `done` could trigger post-merge finalization while the PR is still open upstream. **Suggested fix:** In `gh_skipped` mode, require at least two independent merge signals (e.g., `PR_CLOSED=true` **and** `MERGE_RESULT` in post-merge set, or manifest `done` plus `post-merge-sentinel`) before selecting `merged`; otherwise stay on `open-pr` or stall.

- **risk-integration** `scripts/design-pause-load.sh:3700-3712` — After a successful install (`LOAD_OK=true`), a failed `clear_pause_marker` only emits `WARN=marker-delete-failed` and still exits success. Operators and `design-route.sh` may treat the run as fully resumed while the issue body still carries `larch:design-pause`, inviting duplicate resume attempts or manual marker repair (the original #3529 pain point for post-success delete failures). **Suggested fix:** Treat marker-delete failure as a distinct orchestrator-facing outcome (e.g., `LOAD_OK=true` plus a dedicated `MARKER_CLEARED=false` KV, or escalate to a loud operator halt) so resume success is not conflated with pointer cleanup.

### Out-of-Scope Observations

- **risk-integration** `python/ship.py:1072-1078` — `resume.start == "done"` returns `Outcome.OK` immediately (`detail="already done"`) without re-running postmerge or verifying terminal artifacts; `test_done_merged_resume_is_idempotent_without_manifest_status` pins this. That is likely intentional idempotency, but a corrupt `PHASE=done` write could mask incomplete post-merge work. Not newly introduced ambiguity—the new classifier makes this path easier to hit.

- **correctness** `python/ship.py:1237,1298` — Merge-loop cap guard changed from `iteration >= MAX` to `iteration > MAX`, allowing one additional monitor cycle at the persisted cap (`test_open_pr_resume_at_iteration_cap_wait_stalls_after_monitor` expects iteration 50 to run once before stalling at 51). Appears deliberate; verify parity with any shell-side `ci-decide.sh` iteration limits if operators rely on exact cap semantics.

- **architecture** `python/run_logs.py:173-204` vs `python/ship.py:564-565` — Boolean parsing is duplicated (`_state_bool_or_default` vs `_state_bool` / `_state_bool_text`). Rejected-findings from the implement run already noted drift risk; no new mismatch was found in this pass, but hydration and write paths could diverge over time.
