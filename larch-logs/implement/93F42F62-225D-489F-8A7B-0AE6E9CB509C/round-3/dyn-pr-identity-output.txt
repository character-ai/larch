Reviewing the branch diff and changed files for risk-integration issues.
### In-Scope Findings

- **risk-integration** `skills/design/scripts/design-route.sh:321-354` — When `design-pause-load.sh` reports `LOAD_OK=true` but `MARKER_CLEARED=false` / `WARN=marker-delete-failed`, the route driver still emits `ROUTE=resume@<STEP>` as long as the step is registered. GitHub issue state (pause marker still present) then disagrees with local state (restore installed, `.resume-loaded` written). A later `/design` on the same issue re-enters pause detection first, reloads the published snapshot into a fresh tmpdir, and can resume an old step instead of `already-planned` / `proceed` — the exact stale-marker failure mode from #3506, now reintroduced when post-success `named-block-write.sh --delete` fails. **Suggested fix:** Treat `MARKER_CLEARED=false` as a hard integration gate before `ROUTE=resume@*` (fail closed with a loud operator-visible warning and manual marker-repair instructions), or have `design-route.sh` retry `clear_pause_marker` once before routing; at minimum, surface `**⚠ ... marker-delete-failed; clear larch:design-pause manually before continuing**` in the orchestrator resume path.

- **risk-integration** `scripts/design-pause-load.sh:203-229` — Snapshot restore binds `REPO_TOP` from the caller’s cwd (`git rev-parse --show-toplevel`) while `--repo` is used only for `gh issue view` / marker delete. `MARKER_REPO` / `CURRENT_REPO` are validated against each other, but not against the git remote that actually supplies `larch-logs/design/<RUN_ID>/`. Running `/design` with `--repo owner/consumer` from a different checkout (e.g. the larch plugin dev tree) can pass GitHub identity checks yet restore the wrong snapshot or emit `missing-restored-artifact`; the new `ls-tree`/`show` path makes correct cwd a silent prerequisite rather than an enforced contract. **Suggested fix:** After resolving `CURRENT_REPO`, compare it to the slug for `REPO_TOP`’s `origin` (or `git -C "$REPO_TOP" remote get-url origin` normalized) and fail with a dedicated `ERROR=repo-worktree-mismatch` when they diverge; document that restore always uses the cwd worktree, not `--repo`.

- **risk-integration** `python/run_logs.py:159-168`, `python/ship.py:830-854` — `parse_pr_number()` treats an empty/missing `PR_NUMBER` in `ship-pr-state.sh` as “fall back to `ctx.pr_number`.” On resume, bootstrap/context PR identity can disagree with persisted state that intentionally cleared `PR_NUMBER` (or never wrote it after a partial ship). The driver may then resume `open-pr`/`merged` paths against a stale context PR while local git branch/state reflect a different head. **Suggested fix:** Remove the `ctx_pr_number` fallback when a state file exists; require an explicit positive `PR_NUMBER` in state (or a fresh `ensure_pr` path) before any `gh.pr_view`-backed resume. If fallback is kept, only use it when `PHASE` indicates pre-PR creation.

- **risk-integration** `scripts/design-pause-load.sh:214-217,232-247` — For remote recovery branches (`larch-log-design-<RUN_ID>`), restore still pins `snapshot_ref="FETCH_HEAD"` immediately after `git fetch`. Any other fetch in the same worktree before `ls-tree`/`git show` can repoint `FETCH_HEAD`, so local git state may not match the branch named in `LOG_RECOVERY_BRANCH`. **Suggested fix:** Resolve and use an explicit ref (`refs/remotes/origin/$LOG_RECOVERY_BRANCH` or `git rev-parse FETCH_HEAD^{commit}` captured right after the intended fetch) instead of bare `FETCH_HEAD` for enumeration and `git show`.

### Out-of-Scope Observations

- **risk-integration** `python/ship.py:591-592` — `_write_ship_state()` validates `BRANCH_NAME`, `PR_URL`, and `MERGE_RESULT` on write but not `REPO`; corrupt `REPO=` values can be persisted and only fail later in `_resume_plan()`. Pre-existing pattern in the #3448 ship-driver work on this branch; worth hardening but not introduced by the pause/resume shell changes.

- **correctness** `scripts/design-pause-load.sh:39` — `clear_pause_marker` still redirects all `named-block-write.sh` stderr/stdout to `/dev/null`, so `WARN=marker-delete-failed` surfaces no `gh`/API reason. This complicates recovery of the stale-marker case above; diagnostic emission would help operators without changing control flow.
