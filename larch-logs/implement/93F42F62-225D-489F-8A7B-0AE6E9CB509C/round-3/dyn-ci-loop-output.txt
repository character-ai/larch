Reviewing the branch diff and commit history for correctness issues in the pause/resume changes.
### In-Scope Findings

- **correctness** `python/ship.py:1421-1430` — When `merge_pr` returns `ci_not_ready` or `main_advanced`, the merge loop `continue`s without incrementing `ITERATION` and without any sleep/backoff. `poll_ci` only sleeps while its decision is `wait`; on a `merge` decision it returns immediately, so a race where CI status still looks green but `merge-pr` rejects can spin `monitor → merge → continue` as fast as GitHub/API calls allow. `SHIP_MERGE_LOOP_MAX_ITERATIONS` never advances on this path, so the ship-layer cap does not bound the loop. Bash `ship-pr.sh` re-enters `ci-wait.sh`, which polls with sleeps between attempts (`scripts/ship-pr.sh` ~2968, `ci_monitor.py` ~438-445). **Suggested fix:** On `ci_not_ready` / `main_advanced`, either increment `iteration` (and persist it), or sleep/backoff before the next `monitor()` call, matching `ci-wait.sh` behavior so the loop is time-bounded and does not hot-spin.

- **correctness** `scripts/design-pause-load.sh:305-310` — Install is split across `cp -R`, `rm .pause-requested`, and writing `.resume-loaded`. Any failure after a successful `cp` still calls `emit_load_fail "restore-install-failed"`, reporting `LOAD_OK=false` while snapshot files are already in `$DESIGN_TMPDIR`, with no `.resume-loaded` and the pause marker kept. `design-route.sh` will not route `resume@*` on the next `/design`, leaving a half-restored tmpdir and a retryable marker with no automatic resume. **Suggested fix:** Treat post-`cp` sentinel cleanup as best-effort (warn on `rm`/`.resume-loaded` failure but still emit `LOAD_OK=true`), or install atomically into a staging dir and swap only after all success checks, so a late sentinel failure cannot produce “files present, load failed.”

### Out-of-Scope Observations

- **correctness** `python/run_logs.py:147-173` — `read_resume_counters` maps corrupt `REBASE_COUNT`/`FIX_ATTEMPTS` values to `0` (tested in `python/test_run_logs.py:149-157`). That fail-open behavior can silently reset sub-counters on a damaged state file; it appears intentional but weakens budget enforcement on resume.

- **correctness** `python/ship.py:1270-1273` — Only `resume.start == "open-pr"` restores persisted CI counters; a `"fresh"` resume that still carries non-zero counters in state writes them during pr-create, then zeroes them at merge-loop entry. Likely intentional for a new PR path, but worth confirming against bash resume semantics.
