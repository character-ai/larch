Reviewing the branch diff and commit history for resume-state correctness.
### In-Scope Findings

- **correctness** `python/ship.py:1270-1273` — When `_resume_plan` falls back to `start=="fresh"` (e.g. `gh pr view` failure, PR head mismatch, or non-resumable PR state), persisted `ITERATION` / `REBASE_COUNT` / `FIX_ATTEMPTS` / `TRANSIENT_RETRIES` are still written during the checks/pr-create preamble, but the merge loop initializes all four counters to **zero** unless `resume.start == "open-pr"`. A run that previously stalled near `SHIP_MERGE_LOOP_MAX_ITERATIONS` (50) can therefore re-enter the CI loop with a reset budget after a transient resume mis-route, defeating the cap that `test_open_pr_resume_at_iteration_cap_still_observes_monitor` protects on the `open-pr` path. **Suggested fix:** When entering the merge loop after a fresh fallback, seed `iteration` / `rebase_count` / `fix_attempts` / `transient_retries` from `resume.*` (the same values already persisted in `ship-pr-state.sh`), or refuse fresh fallback when `PHASE=ci-initial` and counters indicate an in-progress merge loop unless an explicit operator reset flag is set.

- **correctness** `python/ship.py:865-872` — `viewed.head_ref != branch_name` is evaluated **before** the `state == "MERGED"` branch. A legitimately merged PR whose GitHub head ref no longer matches the local checkout (common after branch rename/delete) is classified as `start=="fresh"` instead of `merged`/`done`, which reruns checks/postbump/`ensure_pr` and can open a duplicate PR while the original is already merged (`test_open_pr_resume_wrong_head_routes_through_fresh_checks` encodes this behavior). **Suggested fix:** For `viewed.state == "MERGED"`, route to `merged`/`done` regardless of head-ref mismatch (optionally emit a warning), and reserve head-ref mismatch fresh-fallback for `OPEN` PRs only.

- **correctness** `python/run_logs.py:147-151` — `read_resume_counters` maps any non-numeric `ITERATION` / `REBASE_COUNT` / `FIX_ATTEMPTS` / `TRANSIENT_RETRIES` value to `0` without surfacing corruption. A partially corrupted `ship-pr-state.sh` silently resets loop budgets and can reopen the same cap-bypass window as above. **Suggested fix:** Treat non-numeric counter fields as a blocked resume (similar to invalid `BRANCH_NAME` / `PR_URL` handling in `_resume_plan`) or emit a loud parse warning and refuse `open-pr` resume until state is repaired.

- **correctness** `scripts/design-pause-load.sh:312-325` — On successful restore, `LOAD_OK=true` is emitted before marker deletion; if `clear_pause_marker` fails, the pause marker remains in the issue body while artifacts are already installed. Every subsequent `/design` invocation with the same issue will hit `design-route.sh` resume detection again, repeat a full snapshot restore into a new session tmpdir, and surface only `WARN=marker-delete-failed` (non-fatal). That matches WI3’s stated trade-off but reintroduces the stale-marker operational failure mode from #3529 whenever `named-block-write.sh` delete fails. **Suggested fix:** Either treat post-success marker-delete failure as a hard operator gate (`LOAD_OK=false` with a dedicated `ERROR=marker-delete-failed` while keeping restored files), or have `design-route.sh` skip re-load when `.resume-loaded` is already present in the active tmpdir and the marker still exists.

### Out-of-Scope Observations

- **correctness** `python/ship.py:489` — `_write_terminal_state` now always persists `PHASE=stalled` on failure instead of the prior `step or "stalled"` value. `open-pr` resume still works via `gh pr_view`, but `gh_skipped` merged detection that keys off `state_phase == "postmerge"` may lose a signal after terminal stalls; worth monitoring in forked/`repo_unavailable` runs.
