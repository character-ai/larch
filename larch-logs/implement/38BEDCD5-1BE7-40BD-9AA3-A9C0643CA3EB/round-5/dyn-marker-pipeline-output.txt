### In-Scope Findings

- **correctness** `skills/design/scripts/plan-review-loop.sh:1321-1338` — When two `[SCOPE-REDUCTION]`-tagged FINDING blocks Jaccard-merge, the kept body is chosen only by token count (`choose_tagged_body`), not by whether the retained block still has a leading marker after `merge_reviewers`. If the longer block’s marker lives only in a field the detector ignores (e.g. `Proposed resolution`) while the shorter block has it on `- **Concern**:`, dedup can keep a block that `check-scope-reduction-marker.sh` no longer classifies as tagged; parity then falls back to `findings-in-scope.pre-dedup.md` (safe), but on a false-negative parity pass the ballot can reach voters without any tagged scope-cut. **Suggested fix:** After `choose_tagged_body`, assert the chosen body still exits 0 from `check-scope-reduction-marker.sh`; if not, prefer the other tagged body or force parity fallback.

- **correctness** `scripts/check-scope-reduction-marker.sh:46-48` — The detector only inspects markdown-bold `- **Concern**:` lines, not plain `- Concern:` lines. Plan-review collection emits bold Concern (`plan-review-loop.sh:1119`), but ballot/tally fixtures and some reviewer shapes use unbold `Concern:` (see `test-tally-plan-review.sh:89-92`). Any such block with `[SCOPE-REDUCTION]` only on a plain `Concern:` line is a false negative for dedup tag-preference, plan-mode aggregation split, and parity—so scope-cut findings can be LLM-merged away instead of verbatim-appended. **Suggested fix:** Extend the Concern matcher to accept both `- **Concern**:` and `- Concern:` (and mirror that in `problem_text` / parity helpers), with harness cases for each shape.

- **risk-integration** `skills/design/scripts/test-plan-review-loop.sh` (layout only at ~1324), `skills/design/scripts/test-plan-review-scope-anchor.sh` — The branch adds `findings-in-scope.pre-dedup.md` and marker plumbing, but there is no offline case that feeds tagged + untagged near-duplicate FINDING blocks through collect → dedup → parity → aggregation → ballot renumber and asserts the leading `[SCOPE-REDUCTION]` marker survives. Round 4 fixed a real both-tagged merge bug (`choose_tagged_body` in commit `afeb4ad17`), yet nothing in `test-plan-review-loop.sh` would catch a regression to keeper-first merge. **Suggested fix:** Add a stubbed-loop fixture with one tagged and one untagged overlapping FINDING, assert post-dedup/post-aggregation ballot text still matches `check-scope-reduction-marker.sh`, and assert parity fallback when a stub forces marker loss.
