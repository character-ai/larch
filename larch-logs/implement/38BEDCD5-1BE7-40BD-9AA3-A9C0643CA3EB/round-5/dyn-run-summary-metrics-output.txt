Reviewing the branch diff and commit history, focusing on risk-integration for PR line-count and related reporting paths.
Inspecting PR line-count implementation and its integration points.
### In-Scope Findings

- **risk-integration** `skills/implement/scripts/write-final-report.sh:118-153` — `ship-pr-state.sh` caches the first `LINES_STATUS=ok` block per `PR_NUMBER` and reuses it on every later `write-final-report.sh` call. `ship-pr.sh` invokes `--comment-only` right after PR creation (`scripts/ship-pr.sh:1366-1367`), so counts are usually snapshotted early. The post-merge final report (`scripts/ship-pr.sh:3167-3168`) reuses that cache instead of refetching, even after CI-fix pushes, review commits, or log flushes on the same PR. The terminal summary can therefore under-report (or otherwise mis-state) the merged PR diff. **Suggested fix:** Treat the cache as comment-only ephemeral data, or invalidate/refetch on post-merge / non-`--comment-only` runs (e.g. skip cache when `MERGE_RESULT` is set, or add a phase marker and only reuse cache within the same `write-final-report` invocation). Add a harness where an early cached snapshot differs from a later live `gh` response for the same PR number.

- **risk-integration** `scripts/compute-pr-line-counts.sh:59-66` — `gh api` stderr is redirected to `/dev/null`, and failures collapse to `LINES_STATUS=unavailable` / `REASON=gh-failed` with no captured diagnostic. Operators only see `- **Lines (PR diff)**: N/A` in the final summary, with no `execution-issues.md` breadcrumb distinguishing auth expiry, rate limits, wrong repo, and transient network errors. That makes production triage harder and can hide systemic `gh`/permissions regressions behind benign-looking `N/A`. **Suggested fix:** Capture `gh` stderr to a tmp file on failure, append a `Warnings` entry via `append-tool-failure.sh` from `write-final-report.sh` (or emit a `WARN=` KV from the helper), and optionally surface a short reason token beyond `gh-failed`.

- **risk-integration** `skills/implement/scripts/write-final-report.sh:144-158` — The helper invocation is wrapped in `set +e`, but an empty/missing `lines_blob` (non-executable/missing `compute-pr-line-counts.sh`, unexpected helper exit before KV emission, etc.) is not logged. Parsing yields empty `LINES_STATUS`, `LINES_DATA_OK` stays false, and the summary quietly shows `N/A` with no `execution-issues.md` warning. That can mask a broken plugin install, bad `chmod`, or packaging regression as “no line data” rather than infrastructure failure. **Suggested fix:** After the helper call, if `lines_blob` is empty or lacks `LINES_STATUS=`, append a `Warnings` / `Tool Failures` entry (mirroring `append_render_warning`) before falling back to `N/A`; add a harness with a non-executable helper stub.

### Out-of-Scope Observations

- **risk-integration** `scripts/compute-pr-line-counts.sh:78-84` — Awk coerces non-numeric `additions`/`deletions` with `$2 + 0` / `$3 + 0`, silently treating bad API fields as zero while still emitting `LINES_STATUS=ok`. Unlikely with GitHub’s schema, but it weakens validation compared with the integer guards in `write-final-report.sh` / `render-run-summary.sh`.

- **code-quality** `scripts/test-compute-pr-line-counts.sh:35-52` and `skills/implement/scripts/test-write-final-report.sh` — The `gh` PR-files shim/fixture is duplicated across harnesses. Fixture drift between the two tests is a maintenance hazard, though not a runtime defect by itself.
