Reviewing the branch diff and PR metrics integration paths (`compute-pr-line-counts`, `render-run-summary`, `write-final-report`).
### In-Scope Findings

- **risk-integration** `skills/implement/scripts/write-final-report.sh:104-147` — When `compute-pr-line-counts.sh` returns `LINES_STATUS=unavailable` / `REASON=gh-failed`, the final report still publishes successfully and renders `- **Lines (PR diff)**: N/A`, but nothing is written to `execution-issues.md` or stderr. That differs from the script’s own degraded-render path (lines 578–588), which always calls `append_render_warning` on renderer failure. A transient `gh` outage, auth/rate-limit error, or bad repo binding therefore disappears from the run audit trail; operators only see a bare `N/A` in the tracking summary with no breadcrumb to investigate. **Suggested fix:** On any non-`ok` / non-`skipped` `LINES_STATUS`, append a `Warnings` entry via `append-execution-issue.sh` or `append-tool-failure.sh` (include `REASON=` and, when safe, captured `gh` stderr). Optionally surface a one-line `**⚠ PR line counts unavailable (gh-failed)**` note in the summary body, mirroring the corrupt token-report warning pattern.

- **risk-integration** `scripts/compute-pr-line-counts.sh:49-85` — The helper always emits `LINES_STATUS=ok` after a zero-exit `gh api --paginate`, even when the GitHub PR files list is truncated (API hard cap of 3 000 changed files) or the TSV parse is incomplete. Those partial totals are forwarded as authoritative `code +…/-…, larch-logs +…/-…` counts in `render-run-summary.sh` (lines 216–221) with no “partial” or “truncated” indicator. Large PRs can therefore under-report diff size in final reports without any failure signal. **Suggested fix:** Detect truncation (compare paginated file count to API `Link`/`total_count` if available, or treat `3000` files as a suspect ceiling) and either emit `LINES_STATUS=partial` with a `REASON=truncated` KV, or append a visible partial-data warning while still rendering the summed counts.

- **risk-integration** `scripts/compute-pr-line-counts.sh:50` — `gh api` stderr is redirected to `/dev/null`, so even when the caller logs a warning, the underlying failure mode (401, 403, rate limit, network) is discarded at the source. That makes post-mortems of silent `N/A` line-count bullets depend on re-running `gh` manually outside the run. **Suggested fix:** Capture stderr to a tmp file on failure, emit a redacted snippet through `larch_err` / the proposed write-final-report warning path, and keep stdout KV-only for successful parses.

- **risk-integration** `scripts/test-render-run-summary-callsites.sh:8-18` — The callsite pin verifies `--claude-input-tokens` / `--cost-unavailable` and `--emergency-requested` forwarding for every `render-run-summary.sh` invocation, but it does not pin the new `--code-added` / `--code-deleted` / `--logs-added` / `--logs-deleted` wiring added in `write-final-report.sh:480-486`. A future edit could drop `${line_args[@]}` from one render branch while tests stay green, regressing final-report metrics without touching plan-review harnesses. **Suggested fix:** Extend `test-render-run-summary-callsites.sh` to assert that `write-final-report.sh` references all four line-count flags and that `run_body_render` passes them on both primary and fallback render paths when `LINES_DATA_OK=true`.
