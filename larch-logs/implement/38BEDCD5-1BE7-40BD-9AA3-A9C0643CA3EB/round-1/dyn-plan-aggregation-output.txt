### In-Scope Findings

- **correctness** `skills/review/scripts/aggregate-findings.sh:725-767` — In plan mode, a successful LLM merge is written to `--findings-file` (`mv` at lines 726–734) **before** tagged `[SCOPE-REDUCTION]` blocks are appended and validated. If the post-append marker gate fails (lines 745–767), the pipeline returns `MERGE_PIPELINE_RC=2` / `AGGREGATED=false` but **does not restore** the original in-scope input. The file left on disk is the untagged-only merge, so tagged scope-reduction findings are dropped from the ballot path even though `aggregate-findings.md` (line 57) and the design plan both require falling back to the original in-scope stream on marker loss. **Suggested fix:** Snapshot `FINDINGS_FILE` before the plan-mode `mv` (or defer the `mv` until after tagged append + marker validation succeed). On marker/renumber failure, restore the snapshot, emit `AGGREGATED=false`, and leave the caller with the pre-aggregation in-scope file unchanged.

- **correctness** `skills/review/scripts/aggregate-findings.sh:754-758` — Tagged-block preservation is validated by **count only** (`sum(tagged blocks in combined) >= block count in PLAN_TAGGED_FILE`), not by matching each pre-split tagged block to a post-merge block that still carries a leading marker. A combined stream can satisfy the count while individual tagged inputs were merged away or stripped earlier in the untagged LLM pass, especially when paired with the failure mode above (partial write with no restore). **Suggested fix:** After building the combined stream, require a one-to-one match from each block in `aggregate-scope-reduction-tagged.md` to a distinct combined block that `check-scope-reduction-marker.sh` still detects (reuse the parity-style normalized token overlap used in `plan-review-loop.sh`, or compare block bodies directly), and fail closed with full input restore when any tagged input is unmatched.

- **risk-integration** `skills/design/scripts/plan-review-loop.sh:1435-1451` — Final ballot renumbering runs under `set -euo pipefail` with no error handling. If the duplicate-heading guard raises `SystemExit('duplicate headings after renumber')`, the whole plan-review round aborts instead of falling back to `findings-in-scope.pre-dedup.md` or the pre-aggregation in-scope snapshot. That is a hard failure at the dedup→aggregation→ballot boundary rather than the conservative fallback the plan describes. **Suggested fix:** Wrap the ballot renumber step in explicit error handling: on duplicate-heading failure, log a warning, copy the parity fallback artifact (`findings-in-scope.pre-dedup.md`) or pre-aggregation backup into `findings-in-scope.md`, re-run renumber once, and only fail closed if the fallback stream is also invalid.

- **correctness** `skills/design/scripts/plan-review-loop.sh:1367-1394` — The post-dedup parity gate matches tagged pre-dedup blocks to post-dedup tagged blocks using token Jaccard ≥ 0.5 on Concern text only. The plan calls for **reviewer overlap plus** normalized problem-token overlap, and the gate does not verify that the matched post-dedup block still has a leading `[SCOPE-REDUCTION]` marker (it builds `post_tag` with `tagged()`, but a false token match against a different tagged block could mask marker loss on the intended block). **Suggested fix:** Require both reviewer-set overlap and normalized problem-token Jaccard when pairing pre/post tagged blocks, and treat “matched block lost leading marker” as parity failure so the pre-dedup snapshot is restored before aggregation.
