### In-Scope Findings

- **architecture** `skills/shared/scripts/render-voter-prompt.sh:71-96` — With `--scope-anchor-file` set, the prompt still emits the unconditional finding-relative EXONERATE rule (“more complexity than **it** warrants”) before the issue-scoped anchor block. That preserves the pre-anchor proportionality model the issue is trying to fix: voters can still treat an over-scoped addition as proportionate to the finding itself and EXONERATE scope-reduction challengers. **Suggested fix:** When a readable scope anchor is inlined, replace or qualify the global EXONERATE lines so proportionality is explicitly measured against the originating issue scope (mirror the `[SCOPE-REDUCTION]` problem-first rubric), and add a harness assertion that the finding-relative wording does not appear unchanged on the anchored path.

- **architecture** `skills/design/scripts/plan-review-loop.sh:1216-1318` with `scripts/check-scope-reduction-marker.sh:43` — Jaccard dedup runs `is_tagged()` on both `FINDING_*` and `OOS_*` blocks, and the canonical detector matches `OOS_*` headings. That gives tagged OOS rows marker-preserving merge behavior even though the plan contract limits marker semantics to in-scope `FINDING_*` blocks only. **Suggested fix:** Restrict dedup tagging to `FINDING_*` blocks (parity gate already does), and narrow `check-scope-reduction-marker.sh` to `FINDING_*` candidates—or add an explicit `FINDING-only` mode used by dedup/aggregation while keeping any broader detector out of the ballot path.

- **architecture** `skills/shared/scripts/render-voter-prompt.sh:87-99` — `--scope-anchor-file` is injected whenever the path is readable, with no guard on `--verification-context`. `dispatch-code-voters.sh` does not pass the flag today, but the shared renderer’s contract allows plan-review scope instructions to leak into `code` or `diff-plan` callers on mis-invocation. **Suggested fix:** Gate scope-anchor emission on `VERIFICATION_CONTEXT=plan` (fail closed or ignore the flag with a warning otherwise), document that invariant in `render-voter-prompt.md`, and add a negative harness case for `--verification-context code --scope-anchor-file …`.

- **architecture** `skills/design/scripts/plan-review-loop.md:34-49` vs `109-113` — `SCOPE_ANCHOR_FILE` is emitted on stdout and in `.step3-plan-review-result.env`, but the normative “Machine output” KV table omits it. Downstream parsers (`run-step3-review.sh`, orchestrator fence tests) were updated, but the driver contract doc is internally inconsistent, which raises integration risk for future Step 3 consumers. **Suggested fix:** Add `SCOPE_ANCHOR_FILE` to the machine-output table and the durable-handoff key list beside the existing scope-anchor section.

- **architecture** `scripts/lib-vote-tally.sh:73-80` with `scripts/lib-vote-tally.md:61` — `is_scope_reduction_block` is documented as part of the shared tally surface, but neither `tally-plan-review.sh` nor `tally-code-votes.sh` calls it; only dedup/aggregation and harnesses use the marker helper directly. That leaves a documented tally API with no production caller and blurs the “optional plan-review behavior, unchanged code-review defaults” boundary. **Suggested fix:** Either wire the helper only where needed (dedup/aggregation) and trim the lib-vote-tally export/docs, or document it explicitly as test-only until tally consumes it.
