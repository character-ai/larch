### In-Scope Findings

- **correctness** `skills/design/scripts/plan-review-loop.sh:1413-1427` — The post-dedup parity gate can pass when multiple pre-dedup `[SCOPE-REDUCTION]` FINDING blocks collapse into a single post-dedup tagged block. The loop marks each pre tagged `src` as “represented” if *any* post tagged `dst` has reviewer overlap and ≥0.5 token Jaccard on Concern text; it does not require one-to-one matching (no `used` set) and does not require `len(post_tag) >= len(pre_tagged)`. After dedup merges two tagged scope-cut findings (common once `[SCOPE-REDUCTION]` is stripped for comparison), both pre blocks can match the same surviving post block and parity succeeds while a scope-reduction finding is silently dropped from the ballot. **Suggested fix:** Mirror the aggregation guard in `skills/review/scripts/aggregate-findings.sh:767-779`: fail parity when `len(post_tag) < len(pre_tagged)`, and match each post tagged block to at most one pre tagged block (track `used` indices or require distinct `dst` per `src`).

- **correctness** `skills/design/scripts/plan-review-loop.sh:1298-1312` — When two tagged blocks merge (`tagged=True` and `kept_tagged[i]=True`), dedup always keeps the earlier keeper body (`merge_reviewers(kb, blk)`) and only merges reviewer attribution from the later block. The later block’s `[SCOPE-REDUCTION]` Concern text is discarded outright. That is safe only if the parity gate always fails closed; because of the many-to-one parity bug above, this merge path can delete a scope-reduction finding without triggering the pre-dedup fallback. **Suggested fix:** In the both-tagged merge branch, prefer the block whose canonical detector still sees a leading marker (or refuse to merge two tagged blocks), and add a harness case with two distinct `[SCOPE-REDUCTION]` findings that Jaccard-merge to one block.

- **correctness** `skills/design/scripts/plan-review-loop.sh:1237-1243` — If `check-scope-reduction-marker.sh` exits unexpectedly (helper missing, `python3` failure, exit 2), `is_tagged()` logs a warning and treats the block as untagged. A genuine `[SCOPE-REDUCTION]` finding can then merge with an untagged near-duplicate via the `tagged=False, kept_tagged=False` branch, keeping the untagged keeper and dropping the marker before tally. **Suggested fix:** Fail closed on helper `rc ∉ {0,1}` (abort dedup or force pre-dedup fallback), or treat helper failure as tagged for merge purposes so the tagged body is never discarded.

- **correctness** `scripts/check-scope-reduction-marker.sh:43-45` — The canonical detector also inspects `### OOS_*:` headings, but the plan contract limits marker preservation to `FINDING_*` only. A tagged `OOS_*` heading is detected as scope-reduction and receives tagged dedup merge behavior even though aggregation and tally intentionally do not special-case OOS. That creates inconsistent marker semantics across stages. **Suggested fix:** Restrict `candidates()` to `FINDING` headings only (or explicitly document and test OOS behavior if intentional).
