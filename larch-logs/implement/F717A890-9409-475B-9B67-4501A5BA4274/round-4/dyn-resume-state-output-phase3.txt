### In-Scope Findings

- **correctness** `python/ship.py:1273-1288` — Dead/unreachable post-monitor cap check. The `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS:` guard at line 1273 (inside `if monitor.action not in {"merge", "already_merged"}:`) can never fire because the pre-monitor guard at line 1211 uses the identical condition on the same `iteration` value before the monitor call. `iteration` is not modified between line 1211 and line 1273, so if `iteration > cap` is true at 1273, line 1211 would have already returned `STALLED`. The plan's stated intent was to move the cap check so monitor can observe pass/already-merged at the limit — the implementation changed `>=` to `>` (which does allow monitor to run at exactly `iteration == cap`) but kept the pre-monitor guard AND added the post-monitor guard, making the latter permanently dead. The tests pass only because the semantics of `>` vs `>=` matter, not because the post-monitor path fires. Any future intent to stall here on a consumed `iteration` increment will silently fail. **Suggested fix:** Remove the post-monitor cap block at lines 1273-1288 entirely; the pre-monitor check at line 1211 already handles all cases. If the intent is to let monitor run at exactly `cap` and stall in the same iteration on non-pass/non-merged outcome, move the ENTIRE cap check to after the monitor call inside the `if monitor.action not in {"merge", "already_merged"}:` block using `iteration` AFTER the increment (`iteration + 1 > cap` at the top of the block, before `_write_ship_state`), and delete the pre-monitor check.

- **correctness** `python/ship.py:_fresh_resume_plan` (diff hunk starting with `def _fresh_resume_plan(`) — `_fresh_resume_plan` accepts a `counters: run_logs.ResumeCounters | None = None` parameter but silently discards it with `_ = counters` and always seeds all-zero. Several call sites inside `_resume_plan` pass `counters=counters` explicitly (e.g., on invalid PR identity, on `gh.pr_view` exception, and on missing expected branch for non-gh-skipped repos), creating the impression that previously-accumulated counters are forwarded into fresh runs. They are not — they are discarded. This is semantically correct (fresh must seed zero), but the misleading parameter makes future callers or maintainers believe they can optionally restore counters for fresh paths. If `_resume_plan` ever gains a code path where caller intent and implementation diverge (e.g., a "forced-fresh-with-restored-caps" variant), this silent discard would be the root cause. **Suggested fix:** Remove the `counters` parameter from `_fresh_resume_plan` entirely. Call sites that currently pass `counters=counters` should just call `_fresh_resume_plan(durable, ...)` without it; the zero-seeding is unconditional by design.

- **correctness** `python/ship.py:1154-1165` — `open-pr` resume path calls `_pending_oos_gate`, which includes the security OOS file gate and full `_oos_gate`, despite the plan specifying "open-pr: skip checks, postbump, `_materialize_manifest_oos`, security OOS file gate, and `_oos_gate`." If a `security-oos-observations.md` file was created between the previous run's OOS-gate pass and this resume (e.g., by a parallel scan), the open-pr path will return `NEEDS_USER_INPUT` for OOS filing even though OOS work was already filed and the run was in CI. This silently re-blocks work that legitimately cleared the gate. The plan test description also states "Open-pr with restored counters plus leftover OOS artifacts still seeds monitor with restored values and never calls `_materialize_manifest_oos`, security OOS file gate, or `_oos_gate`" — the existing test `test_open_pr_resume_preserves_pending_oos_gate` contradicts this description by validating OOS-gate firing on open-pr. The counter-zeroing concern is mitigated by explicit counter threading, but the functional gate re-firing on resume is unintended. **Suggested fix:** Remove the `elif resume.start == "open-pr": oos_result = _pending_oos_gate(...)` block (lines 1154-1165). The security-oos and OOS-disposition checks were already cleared to allow CI entry on the previous run; re-running them on resume can only add false blocking. If OOS state changes between runs the driver will encounter it on the next fresh run. Update or remove `test_open_pr_resume_preserves_pending_oos_gate` to match.

### Out-of-Scope Observations

- **code-quality** `python/ship.py:_fresh_resume_plan` — The `counters` parameter uses `_ = counters` to suppress the "unused variable" lint warning, a pattern that in Python conventionally signals intentional discard. However, this convention is invisible to callers, who see a meaningful parameter name suggesting the value is used. A simple `del counters` or removing the parameter entirely would be clearer. This is pre-existing style but the dead parameter is newly introduced by this diff.
