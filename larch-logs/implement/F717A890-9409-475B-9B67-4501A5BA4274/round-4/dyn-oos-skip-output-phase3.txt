### In-Scope Findings

- **risk-integration** `python/ship.py` — The open-PR resume path still invokes `_pending_oos_gate` (which internally calls both the security OOS file gate and `_oos_gate`), directly contradicting the plan's acceptance criteria. The plan's OOS-skip requirement states: *"skip checks, postbump, `_materialize_manifest_oos`, security OOS file gate, and `_oos_gate`"* and the feature description acceptance test explicitly says *"never calls `_materialize_manifest_oos`, security OOS file gate, or `_oos_gate`"* for open-pr resumes. In the diff the `elif resume.start == "open-pr":` block (added in `run_ship()`) still calls `_pending_oos_gate`, so an open-pr resume with a leftover `security-oos-observations.md` file—or un-filed OOS artifacts from a previous run's scan that were already reviewed—will incorrectly block with `NEEDS_USER_INPUT` / `oos-filing` rather than proceeding to `ensure_pr`. The plan's rationale for skipping was that OOS helpers "can rewrite state with zero counters"; while counter threading now mitigates that risk, the gate itself is not supposed to re-evaluate OOS artifacts on resume at all. The companion test `test_open_pr_resume_preserves_pending_oos_gate` (added in `python/test_ship.py`) validates this incorrect behavior—it stubs `oos.disposition_ok` to return `ok=False` and asserts `Outcome.NEEDS_USER_INPUT` for the open-pr path, which would catch any future fix as a regression. Additionally, `test_open_pr_resume_restores_counters_and_validated_branch` stubs `oos.disposition_ok` to `ok=True` rather than asserting the OOS helper is never called (meaning the test passes regardless of whether the gate runs). **Suggested fix:** Remove the `elif resume.start == "open-pr":` block that calls `_pending_oos_gate`—open-pr resumes already passed the OOS gate before the PR was created and should proceed directly to `ensure_pr`. Update `test_open_pr_resume_restores_counters_and_validated_branch` to stub `ship._pending_oos_gate` or `ship.oos.disposition_ok` as `forbidden` (like `_materialize_manifest_oos` is already marked), verifying the gate is never invoked. Rework or remove `test_open_pr_resume_preserves_pending_oos_gate` so it no longer asserts that OOS blocks an open-pr resume.

### Out-of-Scope Observations

- **code-quality** `python/ship.py` — The CI loop contains a duplicate iteration-cap check: one at the top of the `while True:` loop (`if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS`) and a second identical check inside the `if monitor.action not in {"merge", "already_merged"}:` block, both firing with the *un-incremented* value of `iteration`. Because `iteration` is not changed between the two checks, the inner check can never observe a value that the outer check already passed, making it permanently dead code. **Suggested fix:** Remove the inner `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS:` block inside the non-merge action branch; the outer check at the top of the loop already provides the correct cap semantics.
