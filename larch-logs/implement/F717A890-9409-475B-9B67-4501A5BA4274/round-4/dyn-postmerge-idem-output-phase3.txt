### In-Scope Findings

- **architecture** `python/ship.py:1273-1288` — Dead second iteration-cap check. The guard `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS:` at line 1273 (inside `if monitor.action not in {"merge", "already_merged"}:`) can never fire: the identical guard at line 1211 already stalls the loop before `ci_monitor.monitor` is invoked for any `iteration > MAX`, and no increment occurs between lines 1211 and 1273. The result is unreachable dead code that misleads readers into thinking there are two enforcement sites. The test `test_open_pr_resume_at_iteration_cap_still_observes_monitor` exercises `iteration=50` with action `already_merged` (merge path), so it never reaches the second check, leaving the dead branch untested and invisible to CI. **Suggested fix:** Remove the duplicate cap block at lines 1273-1288 entirely; the sole enforcement point should remain at line 1211 where `iteration > MAX` is checked before every monitor call.

- **architecture** `python/ship.py:1154-1165` — Open-PR resume path calls `_pending_oos_gate` despite the plan acceptance criterion stating "open-PR resume skips checks/postbump/OOS helpers." The diff introduces this call for the `open-pr` branch (symmetric with the `fresh` branch at line 1139), meaning the security OOS file gate and `_oos_gate` both run on open-pr resume. This contradicts the acceptance criterion in the plan ("open-PR resume skips … OOS helpers") but is consistent with `test_open_pr_resume_preserves_pending_oos_gate` which explicitly tests the gate blocking open-pr resume. The consequence is that a leftover `security-oos-observations.md` or un-filed OOS artifact will block an open-pr resume even when the user already cleared it between invocations, requiring manual cleanup to unblock. The architecture contract between the plan and the tests is therefore ambiguous: the plan says skip, the test says run. **Suggested fix:** Align either the plan acceptance criteria or the test to be explicit about this behavior. If the OOS gate should run on open-pr to catch pending artifacts, update the plan wording; if it should be skipped, guard the `_pending_oos_gate` call at line 1154 behind `resume.start == "fresh"` only (matching the `_materialize_manifest_oos` guard already in place).

- **architecture** `python/ship.py:378-381` — `_write_terminal_state` silently discards the `step` parameter for the ship-state phase: it assigns `_ = step` after using `step` only for `finalize.write_finalize_state`'s `stall_step` field, then writes `phase="stalled"` regardless. All callers pass a descriptive step string (e.g. `"ci-monitor"`, `"pre-rebase"`, `"merge-loop-iteration-cap"`) expecting it to appear in `PHASE=` in `ship-pr-state.sh` for diagnostic or resume purposes. The change means any code that reads `PHASE` from the state file to determine *where* a stall occurred (e.g., external monitoring or future resume logic) loses that granularity. The `step` parameter is no longer vestigial in `finalize-state.sh`, but it is no longer reflected in `ship-pr-state.sh`, creating an inconsistency between the two state files. This diverges from the pre-existing bash driver behavior where `PHASE` carried the step name on stall. **Suggested fix:** Either explicitly document that `PHASE=stalled` is now canonical for all non-OK terminal states (remove the `step` parameter from the signature to avoid confusion), or restore `phase = "done" if result is Outcome.OK else step or "stalled"` to maintain diagnostic parity with the bash driver.
