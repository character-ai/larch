### In-Scope Findings

1. **Important** **correctness** `python/ship.py:1213-1224` — The `open-pr` resume branch calls `_pending_oos_gate` (which includes the security OOS file gate and `_oos_gate`). The plan is explicit: "open-pr: skip checks, postbump, `_materialize_manifest_oos`, security OOS file gate, and `_oos_gate`." Only `_materialize_manifest_oos` is gated to `fresh`; the remaining OOS helpers still execute on `open-pr`. This means an `open-pr` resume can be incorrectly blocked at OOS disposition when the plan intends it to flow directly to CI. Additionally, `test_open_pr_resume_preserves_pending_oos_gate` was written to test this non-compliant behavior (OOS gate fires on open-pr), and the plan-required test asserting "never calls security OOS file gate, or `_oos_gate`" on open-pr is absent. **Suggested fix:** Move `_pending_oos_gate` out of the `elif resume.start == "open-pr"` branch; for open-pr resume, skip directly to `ensure_pr`. Replace `test_open_pr_resume_preserves_pending_oos_gate` with a test that marks the gate as `forbidden` on open-pr.

2. **Important** **correctness** `python/test_ship.py` — The plan's test-plan section lists numerous required scenarios that are absent from the diff: (a) "State-present `main`/`master` on non-forked/non-forked_target checkout returns `NEEDS_USER_INPUT` even when state branch matches current branch" — only the allow case (forked-target) is tested, not the refuse case; (b) "Wrong PR head returns fresh for `OPEN`, `MERGED`, and attempted `done` routing" — no test; (c) "`CLOSED` non-merged routes fresh even with stale `PR_CLOSED=true`, merged-looking `MERGE_RESULT`, `PHASE=postmerge`, `PHASE=done`, or manifest `DONE`" — no test; (d) "`repo_unavailable` open-pr resume with blank/zero `PR_NUMBER` and empty `PR_URL` still reaches PR-only OK path without checks/postbump" — no test; (e) "Manifest `DONE` alone does not force merged when phase/open state disagrees" — no test; (f) "`RESUME_PHASE=ship-pr-rrr-phase14` repeats the same refusal across two invocations and preserves `PHASE`, `RESUME_PHASE`, `CALLER_KIND`, counters" — `test_rebase_continuation_wins_over_state_repo_mismatch` tests precedence only, not the repeat-invocation/marker-preservation invariant; (g) "Terminal handback preserves restored counters across two `run_ship()` invocations" — no round-trip invocation test. These gaps leave the stated acceptance criteria unverifiable. **Suggested fix:** Add dedicated tests for the absent scenarios, especially the main/master guard refuse case, wrong-head routing, CLOSED routing, and the two-invocation rebase-continuation preservation test.

3. **Latent** **correctness** `python/run_logs.py:147` — `manifest_status` uses `ctx.run_id` directly rather than `effective_run_id(ctx)` as the plan specifies: "Read-only probe of `Path(ctx.tmpdir) / "larch-logs" / "implement" / effective_run_id(ctx) / "manifest.json"`; match the `_manifest_path` contract." `effective_run_id` prefers the state file's `RUN_ID` over `ctx.run_id`; `test_manifest_status_read_only_uses_context_run_id_path` explicitly verifies the divergent behavior (state-run path does not work, only ctx-run path does). If the run_id in `ship-pr-state.sh` differs from `ctx.run_id`, `manifest_status` silently reads the wrong manifest path. **Suggested fix:** Use `effective_run_id(ctx)` in the path construction to match the `_manifest_path` contract, or update the plan/docstring to explicitly document why `ctx.run_id` is preferred.

4. **Nit** **code-quality** `python/ship.py:_write_terminal_state:473-474` — The implementation changes `phase = "done" if result is Outcome.OK else step or "stalled"` to always write `"stalled"` for non-OK outcomes, discarding the `step` parameter (via `_ = step`). The plan says only to "extend" this function with counter kwargs, not to change the phase-naming behavior. The test `test_terminal_state_uses_canonical_stalled_phase` was added to verify this new behavior, confirming it is intentional — but the plan does not document this behavior change. **Suggested fix:** Either document this normalization in the plan/changelog, or clarify that the plan authorized it during review rounds.

5. **Nit** **code-quality** `python/ship.py:_fresh_resume_plan:596-599` — Accepts `counters: run_logs.ResumeCounters | None = None` but immediately discards it with `_ = counters` and re-binds to `ResumeCounters(0, 0, 0, 0)`. All call sites pass actual restored counters that are silently dropped. The behavior is correct (fresh always zeros), but the API is misleading — a future refactor could mistakenly believe the parameter is honored. **Suggested fix:** Remove the `counters` parameter from `_fresh_resume_plan` since it is never used; update call sites to omit it.
