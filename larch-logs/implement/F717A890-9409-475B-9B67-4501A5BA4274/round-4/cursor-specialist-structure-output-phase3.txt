### In-Scope Findings

1. **Important** `code-quality` `python/ship.py:1344-1360` — The inner cap check `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS:` inside `if monitor.action not in {"merge", "already_merged"}:` is unreachable dead code. `iteration` is not modified between the outer cap check at the top of the `while` loop (line 1283) and this inner check — both test the identical `> max` condition on the same variable, so the outer check always preempts the inner one. The scenario this was presumably meant to catch (post-monitor, pre-increment cap enforcement) is actually handled correctly by the outer check on the next loop iteration; the inner check just adds confusion and an unreachable `_write_terminal_state` + `return` path. **Suggested fix:** Remove the inner `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS:` block (lines 1345–1360) entirely; the outer check already provides the required cap-before-monitor semantics.

2. **Important** `code-quality` `python/ship.py:1213-1224` — The `elif resume.start == "open-pr":` branch calls `_pending_oos_gate`, which wraps both the security OOS file check and `_oos_gate`. The plan explicitly states: "open-pr: skip checks, postbump, `_materialize_manifest_oos`, security OOS file gate, and `_oos_gate`." Skipping only `_materialize_manifest_oos` while leaving the security gate and `_oos_gate` running on open-pr resume diverges from the plan obligation. `test_open_pr_resume_preserves_pending_oos_gate` tests and validates this divergent behavior, but the plan required a full skip. If a stale `oos-accepted-review.md` exists on resume, this path blocks the resume unnecessarily. **Suggested fix:** Remove the `elif resume.start == "open-pr":` OOS gate block entirely; the counter-safe OOS path was already addressed by threading counters through `_pending_oos_gate` — but per plan the entire gate should be skipped on open-pr resume.

3. **Latent** `code-quality` `python/run_logs.py:143-158` — `manifest_status` uses `ctx.run_id` directly rather than `effective_run_id(ctx)` as specified in the plan ("match the `_manifest_path` contract"). The plan spec says `effective_run_id(ctx)` because that helper prefers the state file's `RUN_ID` over `ctx.run_id`. If the two diverge — e.g., after a session ID rotation — `manifest_status` looks in the wrong directory and silently returns `""` instead of the actual status. `test_manifest_status_read_only_uses_context_run_id_path` explicitly validates the `ctx.run_id` behavior, but this contradicts both the plan spec and the naming convention used by every other manifest lookup in the module. **Suggested fix:** Replace `ctx.run_id` on line 147 with `effective_run_id(ctx)` (the function is already in the same module), and update the test name/assertion to match.

4. **Nit** `code-quality` `python/ship.py:596-600` — `_fresh_resume_plan` accepts a `counters: run_logs.ResumeCounters | None = None` parameter that is immediately discarded with `_ = counters` and replaced unconditionally with `ResumeCounters(0, 0, 0, 0)`. Several call sites pass `counters=counters` (e.g., line 820), creating the false impression the restored counters are used. **Suggested fix:** Remove the `counters` parameter from `_fresh_resume_plan`'s signature and all call sites; always construct zeros inline. The parameter is a leftover from an earlier design where `fresh` might propagate counters.

5. **Nit** `code-quality` `python/ship.py:473` — `_ = step` appears immediately after `step` has already been used in the preceding `finalize.write_finalize_state(ctx.with_(..., stall_step=step), ...)` call. This makes `step` look like it's being discarded when it has already served its purpose. **Suggested fix:** Remove `_ = step`; the parameter is used above it and pyright should not warn about a parameter that appears in a function call.

6. **Nit** `code-quality` `python/ship.py:645-646` — `_state_bool_text(value)` is semantically identical to `run_logs._state_bool_or_default(value, default=False)`, which was just added in the same PR in `run_logs.py`. Both are private module helpers. **Suggested fix:** Either make `_state_bool_or_default` a public helper in `run_logs` (rename to `parse_state_bool`) and reuse it, or add a thin public wrapper — eliminating the duplication.

7. **Nit** `code-quality` `python/ship.py:722-760` — State format validation failures that have nothing to do with the git checkout (invalid `BRANCH_NAME` regex, invalid `PR_URL`, invalid `MERGE_RESULT`, repo slug mismatch) all route through `_invalid_state_plan` which produces `start = "blocked-checkout-mismatch"` and `needs_user_reason = "checkout-mismatch"`. A user who sees `needs_user_reason: checkout-mismatch` with `detail: state REPO does not match context repo` will reasonably conclude they are on the wrong branch, not that the state file has a mismatched repo. **Suggested fix:** Introduce a separate `blocked-state-invalid` start value (or at minimum a separate `needs_user_reason` string like `"state-invalid"`) for non-branch validation failures, keeping `"checkout-mismatch"` only for genuine branch/HEAD mismatches and the main/master guard.
