### In-Scope Findings

- **correctness** `python/ship.py:1344-1360` — The post-monitor iteration cap check uses strict `>` (`if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS`) identical to the pre-monitor top-of-loop check. At exactly `iteration == MAX` with a non-merge action (e.g., `"wait"`): the top check passes (allowing monitor to fire, which is correct), but the post-monitor check also passes without stalling — so the loop continues, `iteration` increments to `MAX+1`, a `_write_ship_state` with `MAX+1` is emitted, `continue` fires, and only the *next* iteration's top check (`MAX+1 > MAX`) triggers the stall. This contradicts the plan criterion "ITERATION=50 with non-pass/non-merged outcome stalls after observing monitor/decision" — it actually stalls one loop turn later, with a stale state write at `MAX+1` in between. No existing test catches this: `test_merge_loop_iteration_cap_stalls` only checks `Outcome.STALLED` (not iteration count or number of monitor calls), and `test_open_pr_resume_at_iteration_cap_still_observes_monitor` uses `already_merged` which bypasses the non-merge branch entirely. **Suggested fix:** Change the post-monitor guard to `if iteration >= config.SHIP_MERGE_LOOP_MAX_ITERATIONS` while leaving the top-of-loop guard as `>`. This makes iteration=MAX reach the monitor (via the `>` top check), then stall immediately in the same loop body via the `>=` post-monitor check before any counter increment or extra state write. The merge/already_merged path is unaffected since it doesn't enter the non-merge branch.

- **correctness** `python/ship.py:963-968` — `_monitor_persisted_counters` increments `rebase_count` when `monitor.goto_rebase` is `True`, even though this flag is only meaningful on the continue path (where the rebase was attempted). When monitor outcome is non-OK and `goto_rebase` is `True` simultaneously (a theoretically unusual but not impossible combination depending on `ci_monitor.monitor` internals), the terminal handback would overcount `rebase_count` by 1 without an actual rebase having occurred. The non-OK branch in the CI loop at line 1321-1343 unconditionally calls `_monitor_persisted_counters` and writes the result as the terminal counter state; there is no guard confirming a rebase was actually attempted before incrementing. **Suggested fix:** Only apply the `goto_rebase` increment in `_monitor_persisted_counters` when the monitor result is also OK (i.e., the rebase action was actually issued and the monitor did not terminate). For terminal non-OK outcomes, `goto_rebase` should be treated as inapplicable and `rebase_count` should be left unchanged, mirroring how `iteration` is not incremented on terminal handbacks.

### Out-of-Scope Observations

- **correctness** `python/ship.py:1448-1458` (merge-retry path) — When `merge.merge_pr` returns `MERGE_RESULT_CI_NOT_READY` or `MERGE_RESULT_MAIN_ADVANCED`, the loop writes state with the current (unchanged) `iteration` and continues without incrementing. This is intentional per `test_merge_retry_results_do_not_consume_iteration_budget`, but it creates an infinite-loop risk if the CI-not-ready condition is permanent: only `iteration`-consuming actions (wait/rebase/fix/transient) advance the cap, so a stuck `MERGE_RESULT_CI_NOT_READY` loop never stalls. This is pre-existing behavior amplified by the new selective-increment logic; worth adding a separate `merge_retry_count` cap or a maximum consecutive merge-retry guard.
