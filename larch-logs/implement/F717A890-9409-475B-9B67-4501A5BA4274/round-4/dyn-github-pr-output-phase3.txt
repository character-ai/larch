### In-Scope Findings

- **risk-integration** `python/ship.py:1150-1165` — The `open-pr` resume path calls `_pending_oos_gate` (which internally invokes both the security OOS file gate and `_oos_gate`), directly contradicting the plan specification: "open-pr: skip checks, postbump, `_materialize_manifest_oos`, security OOS file gate, and `_oos_gate`" and the test-plan bullet "never calls `_materialize_manifest_oos`, security OOS file gate, or `_oos_gate`." If a `security-oos-observations.md` file exists with non-zero content in `ctx.tmpdir`, or if OOS accepted-review files are present without a matching `oos-issues.ndjson` (e.g., after a partial tmpdir reconstruction), `_pending_oos_gate` returns `NEEDS_USER_INPUT` and blocks the open-pr resume indefinitely. The test `test_open_pr_resume_restores_counters_and_validated_branch` sidesteps this by monkeypatching `disposition_ok` to return True, so the gate is called but benign; there is no test verifying the gate is actually skipped. **Suggested fix:** Move the `_pending_oos_gate` call for `open-pr` behind a guard that returns early without calling the gate (matching the `_materialize_manifest_oos` guard that is correctly skipped), so the open-pr path proceeds directly from `_write_ship_state(phase="pr-create")` to `_pr_title`/`ensure_pr` without re-entering OOS checks.

- **risk-integration** `python/ship.py:1273-1288` — The post-monitor cap stall check (`if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS` at line 1273, inside `if monitor.action not in {"merge", "already_merged"}`) is dead code that can never evaluate True. At that point `iteration` has the same value as when the pre-loop guard at line 1211 evaluated False (i.e., `iteration <= cap`), and `iteration` is not incremented between lines 1211 and 1273. The stall therefore only fires on the following loop iteration via the pre-loop guard, meaning the final persisted `ITERATION` in state is `cap + 1` (not `cap`) when stalling on a non-merge action — and a plan scenario described as "ITERATION=50 with non-pass/non-merged outcome stalls after observing monitor/decision" would actually persist `ITERATION=51`. While the overall stall behavior is correct, the dead check conflates the two stall sites and could mislead future readers into believing both guards serve distinct purposes. **Suggested fix:** Remove the duplicate inner `if iteration > config.SHIP_MERGE_LOOP_MAX_ITERATIONS` block at lines 1273–1288; the outer pre-loop guard already enforces the cap correctly (changed from `>=` to `>` to allow one final monitor cycle at the cap).

### Out-of-Scope Observations

- **correctness** `python/run_logs.py:143-158` — `manifest_status` uses `ctx.run_id` directly rather than `effective_run_id(ctx)`, which prefers the run-id from the state file. The plan spec says to "match the `_manifest_path` contract" (which uses `effective_run_id`).
