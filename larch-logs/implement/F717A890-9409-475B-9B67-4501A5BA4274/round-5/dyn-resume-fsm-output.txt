Reviewing the branch diff and resume classification flow in `python/ship.py`.
### In-Scope Findings

- **architecture** `python/run_logs.py:171-175` — `manifest_status()` probes `ctx.run_id` directly, but the plan and `_manifest_path()` both require `effective_run_id(ctx)` (state-file `RUN_ID` first). On gh-skipped resumes where persisted `RUN_ID` and argv `ctx.run_id` diverge, merged routing via `local_merged` in `python/ship.py:849-853` can miss a real `DONE` manifest or consult the wrong run directory, misclassifying `merged` vs `open-pr`. **Suggested fix:** Resolve the manifest path with `effective_run_id(ctx)` (same helper `_manifest_path` uses), and add a regression test that writes `RUN_ID=state-run` in state with the manifest under that slug while `ctx.run_id` differs.

- **architecture** `python/ship.py:849-876` — Gh-skipped `local_merged` treats `manifest_status(ctx) == DONE` plus any valid `pr_number` as sufficient for the `merged` start, without requiring agreeing `PR_CLOSED`, `PHASE=postmerge`, or a post-merge `MERGE_RESULT`. That contradicts the plan’s precedence (“manifest `DONE` only when one of those state predicates already agrees”) and the edge case that manifest `DONE` alone must not force merged when phase/open state disagree; a session still at `PHASE=ci-initial` with an open PR can be routed into `run_postmerge_phase`. **Suggested fix:** Drop the standalone manifest clause from `local_merged`, or gate it behind the same agreeing state predicates (`PR_CLOSED`, `PHASE=postmerge`, valid `MERGE_RESULT`); align `test_gh_skipped_resume_uses_done_manifest_as_merged_signal` accordingly.

- **architecture** `python/ship.py:665-666` — The no-state-file path returns `fresh` immediately, with no current-branch probe and no main/master guard at the classifier boundary. Branch safety is deferred to `finalize.postbump()` (`python/finalize.py:56-61`), so a handback or first entry with a missing/uncreated state file can still run checks (and emit the entry `phase="checks"` write) on a protected or unverified checkout before postbump stalls. The plan requires fresh work to pass branch safety before checks/postbump. **Suggested fix:** After the absent-state-file check, probe the current branch and apply the same main/master guard used at `python/ship.py:759-770`; return `blocked-checkout-mismatch` (or refuse fresh) when the checkout cannot be verified, even when no state file exists yet.

- **risk-integration** `python/ship.py:691-723` — Corrupt persisted metadata (`BRANCH_NAME`, `PR_URL`, `MERGE_RESULT`, `REPO`) is folded into `blocked-checkout-mismatch` via `_invalid_state_plan()`, but `run_ship()` always surfaces `needs_user_reason="checkout-mismatch"` (`python/ship.py:1030-1035`) regardless of `resume.detail` (e.g. `"invalid state MERGE_RESULT"`). That collapses corrupt-state repair and real checkout mismatch into one orchestrator bucket, which can send recovery down the wrong path when the checkout is fine but state strings are invalid. **Suggested fix:** Introduce a distinct start/reason pair for corrupt-state refusal (or route those cases to `fresh` where the plan calls for it), and map it to a dedicated `needs_user_reason` so detail and reason stay aligned.

### Out-of-Scope Observations

- `python/test_run_logs.py:211-223` encodes `manifest_status` using `ctx.run_id` even when state carries a different `RUN_ID`; that test should be updated once `effective_run_id` is wired in.
- Plan acceptance calls for “missing `state_file` returns fresh even when `ctx.pr_number` is set”; no dedicated `test_ship.py` case was found for that scenario.
- `_fresh_resume_plan()` accepts a `counters` argument but always discards it (`python/ship.py:568-569`); harmless but dead API surface on an otherwise well-factored classifier.
