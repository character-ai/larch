Reviewing the branch diff and commit history for state-persistence and risk-integration issues.
### In-Scope Findings

- **risk-integration** `python/run_logs.py:171-186` — `manifest_status()` looks up `Path(ctx.tmpdir)/larch-logs/implement/{ctx.run_id}/manifest.json` and gates on `validate_run_id_slug(ctx.run_id)`, but the plan and `_manifest_path()` use `effective_run_id(ctx)` (state-file `RUN_ID` first). On orchestrator re-entry, a stale or empty argv `ctx.run_id` makes `manifest_status()` return `""` even when the run-log manifest under the persisted state `RUN_ID` is `DONE`, so gh-skipped `_resume_plan()` can miss `local_merged` and route to `open-pr` instead of `merged`/`done`. **Suggested fix:** Resolve the manifest path with `effective_run_id(ctx)` (same slug validation), and add a test where `state RUN_ID≠ctx.run_id` and the manifest lives only under the state run id.

- **risk-integration** `python/ship.py:519-523` — `_write_ship_state()` always writes `RUN_ID=ctx.run_id`, but `_hydrate_resume_context()` (891-905) never hydrates `run_id` from `ship-pr-state.sh`. The first open-pr/merged write can overwrite a persisted session `RUN_ID` with a stale argv value, breaking run-log/manifest correlation and amplifying the `manifest_status()` bug above. **Suggested fix:** Read `RUN_ID` from state during resume hydration (with slug validation and ctx fallback, like durable flags) and write the hydrated value; cover with an open-pr resume test that asserts `RUN_ID` survives when `ctx.run_id` disagrees.

### Out-of-Scope Observations

- **correctness** `python/ship.py:849-854` — For gh-skipped resumes, `manifest_status()==DONE` alone (with `pr_number` set) can force `local_merged` while `PHASE=ci-initial` and no `PR_CLOSED`/merge-result agreement. `test_gh_skipped_resume_uses_done_manifest_as_merged_signal` encodes this, but it conflicts with the plan edge case that manifest `DONE` alone should not force merged when phase disagrees; stale manifests could trigger premature postmerge in `repo_unavailable` mode.

- **risk-integration** `python/ship.py:788-837` — Normal-repo `gh.pr_view` failures intentionally route `fresh` and reset CI counters to zero (`test_fresh_fallback_hydrates_modes_and_resets_counters`). That matches the plan, but a transient `gh` flake after a handback can still wipe session-wide caps and restart checks/postbump; consider whether a safe-refuse or open-pr fallback is preferable when branch/PR identity in state are otherwise valid.
