### In-Scope Findings

- **correctness** `python/ship.py:600-616,881-920,1001-1004` — `_resume_plan()` routes several degraded cases to `start="fresh"` via `_fresh_resume_plan(..., counters=counters)`, so stale `ITERATION` / `REBASE_COUNT` / `FIX_ATTEMPTS` / `TRANSIENT_RETRIES` are written back into `ship-pr-state.sh` on every fresh-path `_write_ship_state` (checks, postbump, pr-create, terminal checks stall). Merge-loop locals are zeroed only at entry (`iteration = resume.iteration if resume.start == "open-pr" else 0`, same for the other three). That split means a fresh run that stalls before the first CI write leaves the old counters in state; the next `open-pr` resume reloads them and the monitor sees the pre-fresh budget again. The plan calls for fresh to use literal zero counters session-wide, and acceptance says stale `ITERATION=49` on a fresh path must seed the monitor at zero — monitor seeding is correct, but state can still carry 49 until CI starts, so cap accounting is inconsistent across handbacks. **Suggested fix:** When `resume.start == "fresh"`, pass zeros into all `_write_ship_state` / `_write_terminal_state` calls (or build `_fresh_resume_plan` without forwarding read counters except on explicit `open-pr` / `merged` / `done` resumes). Align `test_fresh_fallback_hydrates_modes_and_preserves_counters` with that contract if stale-counter preservation on gh-failure fresh was not intentional.

- **correctness** `python/ship.py:736-749,1028-1044` — `_monitor_persisted_counters()` only bumps `transient_retries` on terminal monitor handbacks; it does not mirror the continue-path updates for `fix_attempts` (`if monitor.did_fixing: fix_attempts += 1`) or `rebase_count` (`rebase_count += 1` after `goto_rebase`). That matches bash for unsuccessful fixes (`test_terminal_counter_persistence_does_not_count_failed_fixing`) and matches the current test suite, but it diverges from the plan note that terminal handbacks should persist consumed `did_fixing` increments. A successful fix (`evaluate_failure` → `pushed`, `Outcome.OK`, `did_fixing=True`) never hits this terminal path, so successful pushes still increment on the continue branch; the gap is failed-fix / stall exits where `did_fixing=True` but the attempt should still advance session budget before exit-3/exit-4. **Suggested fix:** If parity with bash is intended, document the asymmetry in `_monitor_persisted_counters` and keep tests; if the plan’s “consumed increments” language means all `did_fixing` cycles, increment `fix_attempts` (and persist `rebase_count` when `goto_rebase` completed) in `_monitor_persisted_counters` before `_write_terminal_state`, and extend tests beyond the current failed-fixing case.
