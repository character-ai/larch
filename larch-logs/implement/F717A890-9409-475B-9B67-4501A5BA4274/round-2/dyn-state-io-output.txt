Inspecting state I/O, path validation, and how persisted values flow into shell/subprocess calls.
### In-Scope Findings

- **security** `python/run_logs.py:134-156` / `python/ship.py:523-585` — Resume now treats durable flags in `ship-pr-state.sh` as authoritative over argv/`RunContext`, with no cross-check against the invoking session. A writer that can modify the session state file (same UID, shared tmpdir, or a race before `_state_file_under_tmpdir` runs) can set `REPO_UNAVAILABLE=true` or `FORKED_TARGET=true` and force the `gh_skipped` path, skipping `gh.pr_view` head verification and bypassing the non-forked `main`/`master` refusal when `FORKED_TARGET=true`. That can resume open-pr/merged work without the GitHub-authoritative checks this branch adds for normal repos. **Suggested fix:** Treat state durable flags as a cache, not sole truth: on non-fresh resume, require agreement with argv/`session-env.sh` (or a signed bootstrap nonce), or refuse resume when `ctx.forked_target`/`ctx.repo_unavailable` disagree with hydrated state unless `repo_unavailable` was explicitly established at session start.

- **security** `python/ship.py:530-614` / `python/ship.py:704-708` — `REPO` is hydrated from state (`state_repo = read_state_kv(..., "REPO") ...`) and propagated into `_hydrate_resume_context` for `gh.pr_view`, `ensure_pr`, and CI monitor calls, without owner/repo slug validation or a match check against `ctx.repo`. A tampered state file can redirect those operations to a different repository the operator’s `gh` token can access, while argv still names the intended repo. **Suggested fix:** Validate `REPO` with the same slug rules used elsewhere (e.g. `report_tokens_scan._valid_repo_slug`), reject values starting with `-`, and on resume require `state_repo == ctx.repo` (or safe-refuse) before any GitHub call.

- **security** `python/ship.py:414-441` / `python/ship.py:1112-1115` — `_write_ship_state` now round-trips `RESUME_PHASE` and `CALLER_KIND` from disk and accepts arbitrary `extra_fields` keys (notably `CONFLICT_FILES`) with only a newline/`\\r` check. Values are not allowlisted before being rewritten into the shell-style state file that bash orchestration later consumes via `read_state` and conflict-resolution handoff. A tampered `RESUME_PHASE`/`CALLER_KIND`/`CONFLICT_FILES` can persist across Python re-invocations; comma-containing or adversarial `CONFLICT_FILES` paths can mis-scope conflict resolution. **Suggested fix:** Allowlist `RESUME_PHASE`/`CALLER_KIND` on read (clear or refuse unknown values), validate `CONFLICT_FILES` as a comma-separated list of repo-relative paths without `..`, newlines, or commas in individual entries before write, and drop `extra_fields` on routine rewrites unless explicitly preserving a known handoff.

### Out-of-Scope Observations

This branch adds useful hardening: `_state_file_under_tmpdir` (`python/ship.py:752-760`), newline rejection on state writes (`python/ship.py:445-447`), strict numeric parsing for counters/PR numbers (`python/run_logs.py:96-168`), and `manifest_status` path construction via validated `effective_run_id` (`python/run_logs.py:171-184`). Pre-existing gaps not introduced here: bash `ship-pr.sh` already trusts `read_state REPO` without slug validation, and `ship-pr-state.sh` was already a writable trust boundary inside the session tmpdir.
