Examining resume classification and related logic in the implementation files.
### In-Scope Findings

- **correctness** `python/ship.py:347-356,320-339` — On `open-pr` resume with `OOS_PENDING=true`, `run_ship()` first writes restored counters at the `pr-create` boundary (lines 935–941), then calls `_pending_oos_gate()` / `_oos_gate()`, which call `_write_ship_state()` without `iteration`/`rebase_count`/`fix_attempts`/`transient_retries` (defaults are 0). A failed disposition therefore overwrites session-wide counters in `ship-pr-state.sh` before returning `NEEDS_USER_INPUT`. That breaks the stated goal of preserving counters across exit-3/exit-6 handbacks; a resume at `ITERATION=49` can be reset to 0 while still mid-CI. `test_open_pr_resume_preserves_pending_oos_gate` only checks the outcome, not counter fields. **Suggested fix:** Thread the active counter tuple into `_pending_oos_gate` / `_oos_gate` (or read it from the just-written plan) and pass it through every `_write_ship_state` call on those paths; add a test that seeds non-zero counters plus `OOS_PENDING=true` and asserts they survive the refusal.

- **correctness** `python/ship.py:415-437,557-562,601-607,881-921,1001-1004` — `_fresh_resume_plan()` carries `read_resume_counters()` values into `ResumePlan`, and the `fresh` branch writes `resume.iteration` / `resume.rebase_count` / etc. into state during `checks`/`pr-prep`/`pr-create` (e.g. when `gh.pr_view` fails or PR identity is invalid). CI locals are zeroed only later (`iteration = resume.iteration if resume.start == "open-pr" else 0`), so persisted state can show stale caps while the monitor starts at 0 in the same invocation, and a checks/postbump stall can leave non-zero counters that influence the next classification. That conflicts with the plan acceptance that `fresh` seeds zero and “fresh ignores stale counters.” **Suggested fix:** Force zero counters in `_fresh_resume_plan()` (or zero them at the start of the `fresh` branch) for all state writes on that path; keep counter restoration exclusively for validated `open-pr` / `merged` / terminal handback paths.

- **correctness** `python/ship.py:547-562` — For normal repos (`gh_skipped` false), resume validation treats an empty persisted `BRANCH_NAME` as non-fatal when `ctx.branch` / `ctx.branch_name` is set and matches the current checkout (`expected_branch = state_branch or ctx.branch_name or ctx.branch`; mismatch is skipped when `expected_branch` is falsy). Bash `run_ship_branch_guard` stalls when either persisted `BRANCH_NAME` or the probed current branch is empty (see `scripts/ship-pr.sh:1071-1076`). A state file can therefore resume on a feature branch with no durable branch anchor if argv/env happens to match, which weakens the “cannot bypass branch validation” guarantee. **Suggested fix:** After `blocked-rebase-continuation`, require a non-empty persisted `BRANCH_NAME` for any non-`fresh` resume (not only `gh_skipped`), and safe-refuse when it is missing or does not equal the probed current branch; do not fall back to `ctx.branch` for anchor validation once a state file exists.

### Out-of-Scope Observations

- `python/run_logs.py:171-184` defines `manifest_status()`, but `python/ship.py::_resume_plan` never calls it. Gh-skipped `merged` routing therefore ignores manifest `DONE` unless `PHASE`/`PR_CLOSED`/`MERGE_RESULT` already agree. That matches “manifest DONE alone does not force merged,” but it is unused surface relative to the plan’s gh-skipped merged predicates.

- Several plan-listed acceptance scenarios (wrong PR head → fresh, `RESUME_PHASE=ship-pr-rrr-phase14` repeat invocation, cap at `ITERATION=49`/`50`, terminal handback round-trip, missing `state_file` with `ctx.pr_number`) have no dedicated tests in the branch diff; `test_fresh_fallback_hydrates_modes_and_preserves_counters` explicitly expects stale counters on a `gh`-failure `fresh` path, which cuts against the plan’s “fresh seeds zero” wording.
