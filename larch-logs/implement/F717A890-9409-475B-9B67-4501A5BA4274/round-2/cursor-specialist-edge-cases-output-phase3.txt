### In-Scope Findings

1. **correctness** `python/run_logs.py` `read_durable_flags` — The `forked` derivation uses the wrong fallback when `FORKED_TARGET` is present with an invalid (non-`true`/non-`false`) value. `forked = forked_target if raw_forked_target.strip() else ctx.forked` — when `raw` is non-empty but invalid, `_state_bool_or_default` falls back to `ctx.forked_target` for `forked_target`, so `forked` ends up as `ctx.forked_target` instead of `ctx.forked`. If `ctx.forked=True, ctx.forked_target=False` and state contains `FORKED_TARGET=garbage`, `durable.forked=False`, `gh_skipped=False`, and the normal-repo `gh.pr_view` path is taken on a forked context; any exception routes to `fresh`, restarting checks/postbump against an already-open PR. The tests only exercise valid (`true`/`false`) and absent values — the invalid-value fallback path is not covered. **Suggested fix:** `forked = forked_target if raw_forked_target.strip() in {"true", "false"} else ctx.forked`

2. **correctness** `python/ship.py` `_pending_oos_gate` (diff line 297–306) and `_oos_gate` (diff line 287–294) — Both call `_write_ship_state(ctx.with_(oos_pending=...), phase="pr-create")` with default-zero counter kwargs. When an open-pr resume with `OOS_PENDING=true` invokes `_oos_gate` and the OOS check rejects, the terminal state is written with `ITERATION=0` (and all other counters at zero), overwriting the counters restored from the state file moments earlier. On the next open-pr re-entry (after user files OOS), the CI loop starts at iteration 0 rather than the session-accumulated value, silently resetting the session-wide cap. The test `test_open_pr_resume_preserves_pending_oos_gate` verifies the correct outcome but does not assert counter values in the output state file. **Suggested fix:** Thread `iteration`, `rebase_count`, `fix_attempts`, `transient_retries` as parameters through `_pending_oos_gate` and `_oos_gate`, and pass them to all `_write_ship_state` calls within those functions; the call site in `run_ship` already has `resume.iteration` etc. in scope.

3. **correctness** `python/ship.py` `_monitor_persisted_counters` (diff line 691–704) — The helper increments only `transient_retries` on terminal CI handback, not `fix_attempts`, even though the plan spec says "persist the same consumed increments as the OK/continue path, including `did_fixing` and `transient_rerun_attempted`." The OK/continue path at diff line 1137–1138 applies `fix_attempts += 1` when `did_fixing`, but the terminal path does not. A NEEDS_USER_INPUT exit when the monitor reports `did_fixing=True` leaves `fix_attempts` one below the actual consumed count. On subsequent open-pr resume, the session has one extra fix attempt before the cap fires. The test `test_terminal_counter_persistence_does_not_count_failed_fixing` explicitly validates the current behavior as intentional, creating a documented divergence from the plan spec; the test name should be audited against the cap-exhaustion semantics before the Phase-7 flip-to-python. **Suggested fix:** Add `fix_attempts=fix_attempts + (1 if monitor.did_fixing else 0)` as the third tuple element, or document in the helper that terminal handbacks intentionally do not count `did_fixing` and update the plan spec to match.
