Reviewing resume routing and GitHub integration in the changed files.
### In-Scope Findings

- **risk-integration** `python/ship.py:347-356,320-339` — On `open-pr` resume, the driver writes restored CI counters at `pr-create` (lines 935–941), but `_pending_oos_gate` / `_oos_gate` call `_write_ship_state(..., phase="pr-create")` with default counter kwargs (`0`), so an `OOS_PENDING=true` handback overwrites `ITERATION`/`REBASE_COUNT`/`FIX_ATTEMPTS`/`TRANSIENT_RETRIES` before returning `NEEDS_USER_INPUT`. That breaks the session-wide cap contract the branch is meant to add: a monitor handback at iteration 49 can re-enter at 0 after OOS filing, effectively resetting merge-loop budgets. `test_open_pr_resume_preserves_pending_oos_gate` only checks outcome, not persisted counters. **Suggested fix:** Thread the active counter tuple into `_pending_oos_gate` / `_oos_gate` (or have `_write_ship_state` read-and-preserve existing counter keys when callers omit them on non-`fresh` paths), and extend the open-pr + `OOS_PENDING` test to assert counters survive the gate write.

- **risk-integration** `python/ship.py:615-621,1001-1004` — When a normal repo has a persisted `PR_NUMBER` and checkout validation succeeds, any `gh.pr_view` failure is classified as `fresh`, and the CI loop seeds `iteration`/`rebase_count`/`fix_attempts`/`transient_retries` to zero (`resume.start == "open-pr"` is the only restore path). A transient GitHub/API flake therefore reruns checks/postbump and restarts the monitor budget instead of resuming near the open PR with restored counters or handing back `TRANSIENT`. That diverges from bash’s session-wide 50/20/10 caps and can both bypass caps across reinvocations and churn an already-open PR. **Suggested fix:** Distinguish `TransientNetworkError` (return `Outcome.TRANSIENT` without a full fresh pipeline) from permanent lookup failures; when state + branch are valid but `gh` is temporarily unreachable, prefer `open-pr` resume using persisted identity or a safe-refuse that preserves counters rather than `fresh` with zero-seeded CI locals.

- **risk-integration** `python/ship.py:615-622` — The `except Exception` around `gh.pr_view` also catches non-transient `ShipError` (404/403/invalid repo from `gh._raise_read_failure`), routing those into the same `fresh` path as network blips. That can rerun checks/postbump/`ensure_pr` against an existing PR when GitHub is reachable but rejecting the lookup, instead of stalling or requesting operator input with preserved resume metadata. **Suggested fix:** Catch `TransientNetworkError` separately for the handback above; map other `ShipError`/`ShipError`-family read failures to `NEEDS_USER_INPUT` or `STALLED` with explicit detail, leaving counters and `RESUME_PHASE` intact.

- **risk-integration** `python/ship.py:721-733,881-890` — `_hydrate_fresh_context` updates repo/branch/durable flags but leaves `ctx.pr_number` / `ctx.pr_url` untouched when `_resume_plan` degrades to `fresh` (wrong `head_ref`, closed PR, `gh` failure, etc.). The next `_write_ship_state(..., phase="checks")` can therefore persist stale PR identity from argv/env while the run is classified as fresh, until `ensure_pr` re-derives identity by branch. That creates a window where state and GitHub ground truth disagree and can confuse orchestrator resume logic on early exit. **Suggested fix:** Clear `pr_number`/`pr_url` (and optionally `merge_result`/`pr_closed`) in `_hydrate_fresh_context`, or hydrate them from the `ResumePlan` (`pr_number=None`, `pr_url=""`) whenever `start == "fresh"`.

### Out-of-Scope Observations

- The plan’s GitHub-authoritative acceptance matrix (wrong-head → `fresh`, stale local merged flags overridden by reachable `OPEN`/`CLOSED`, `RESUME_PHASE=ship-pr-rrr-phase14` precedence, cap 49/50 semantics, non-forked `main`/`master` refusal, repo-unavailable blank PR identity) is largely implemented in `_resume_plan()` but has little or no direct pytest coverage in `python/test_ship.py`; regression risk for the gh/fork/repo-unavailable routing surface remains high.

- `run_logs.manifest_status()` is added and unit-tested but never consumed by `python/ship.py` resume routing; gh-skipped merged detection ignores manifest `DONE` entirely (conservative vs. the plan’s qualified manifest predicate, not clearly wrong).

- Open-pr resume intentionally skips `_materialize_manifest_oos` and the security sidecar unless `OOS_PENDING` is set (lines 950–960); a leftover `security-oos-observations.md` from an interrupted fresh run can be bypassed on open-pr re-entry — likely plan-intended, but it is a shipping gate bypass worth tracking operationally.
