Reviewing the branch diff and resume-plan state machine implementation.
Examining the resume state machine and comparing it to the plan.
### In-Scope Findings

- **architecture** `python/ship.py:991-1007,1070-1071` — The new resume classifier only recognizes `blocked-rebase-continuation` when `ship-pr-state.sh` already contains `RESUME_PHASE=ship-pr-rrr-phase14`, but the CI-loop rebase path still raises `PrePushConflictHandoff` and the top-level handler converts it to a generic `STALLED` result without persisting `RESUME_PHASE`, `CALLER_KIND`, or conflict metadata to state. After a Python-native pre-push conflict handback, the next `run_ship()` sees an empty resume marker and can classify `open-pr`, skip checks/OOS, restore counters, and re-enter CI instead of refusing unsupported continuation — a worse failure mode than the old always-fresh restart because it silently bypasses the required bash handoff. **Suggested fix:** Catch `PrePushConflictHandoff` in `run_ship()` (or a dedicated terminal writer) and persist the handoff tokens plus counters to `ship-pr-state.sh` before returning; alternatively map it to the same `NEEDS_USER_INPUT` refusal path as `blocked-rebase-continuation` so re-entry cannot progress into CI.

- **architecture** `python/ship.py:419-420,829-836,868-875` — `_write_ship_state()` always rewrites `RESUME_PHASE=""` and `CALLER_KIND=""` on every call, so any non-blocked resume path (notably `open-pr`, which writes `phase=pr-create` before PR-only early exits) destroys bash continuation markers on the first state touch. The blocked-rebase branch correctly avoids writing, but the state machine assumes markers survive across orchestrator re-invocations; a single open-pr/CI write after bash set `ship-pr-rrr-phase14` erases the token and makes the next resume look like a normal open PR. **Suggested fix:** Read existing `RESUME_PHASE`/`CALLER_KIND` from disk and write them back unchanged unless the caller explicitly sets new values; do not blank handoff keys during routine phase/counter updates.

- **architecture** `python/ship.py:513-537,629-637` — For gh-skipped resumes (`repo_unavailable`, `forked`, `forked_target`), open-pr routing only requires `pr_number is not None or durable.repo_unavailable` and never enforces the plan’s “state `BRANCH_NAME` matches validated current branch” rule when both `BRANCH_NAME` and ctx branch hints are absent. In that case `expected_branch` is empty, branch-mismatch/main-master checks are skipped, and the classifier can return `open-pr` on an arbitrary checkout, hydrating PR identity from stale state and entering CI on the wrong branch. **Suggested fix:** For gh-skipped non-fresh routes, require a non-empty validated branch (from state or ctx) that matches the probed current branch; otherwise return `blocked-checkout-mismatch` instead of `open-pr`/`merged`/`done`.

### Out-of-Scope Observations

- `run_logs.manifest_status()` is added and unit-tested but never consulted by `_resume_plan()`; merged routing for gh-skipped contexts ignores manifest status entirely. That matches the plan’s “manifest DONE alone must not force merged” safety rule, but it also means manifest-assisted merged detection when state predicates agree is still unwired.

- The diff adds only a small subset of the plan’s acceptance matrix (e.g., no tests for `RESUME_PHASE=ship-pr-rrr-phase14` repeat refusal, GitHub-authoritative wrong-head/CLOSED routing, cap-at-50 semantics, or terminal counter round-trips). The state-machine branches above are therefore largely unguarded against regression despite being the core architectural change.
