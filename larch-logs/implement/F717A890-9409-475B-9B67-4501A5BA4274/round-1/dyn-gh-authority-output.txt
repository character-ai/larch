Reviewing the branch diff and commit history for GitHub-authoritative resume routing and head-ref validation.
Inspecting `_resume_plan`, `gh.pr_view`, and how tests cover GitHub-authoritative routing.
### In-Scope Findings

- **risk-integration** `python/ship.py:563` — `_resume_plan` calls `gh.pr_view(..., repo=ctx.repo)` using argv/context `ctx.repo`, not the persisted `REPO=` value written to `ship-pr-state.sh`. Bash `ship-pr.sh` consistently uses `read_state REPO` for `gh pr view`, merge, and CI helpers (e.g. around lines 3010–3013). On orchestrator re-entry with a stale or missing `--repo`, GitHub-authoritative resume can query the wrong repository while `PR_NUMBER`, branch, and counters come from state, yielding wrong PR state, a false `fresh` restart, or resume against another repo’s PR. **Suggested fix:** When `ctx.state_file` exists, read `REPO` from state (fall back to `ctx.repo` only if absent/empty), include it in `ResumePlan` / `_hydrate_resume_context`, and pass the hydrated repo into every non-fresh `gh.pr_view`, `ensure_pr`, and `ci_monitor` call.

- **risk-integration** `python/run_logs.py:154` / `python/ship.py:551,537` — With a state file present, `read_durable_flags` sets `forked=ctx.forked or forked_target`, so a stale argv/env `FORKED=true` can survive even when persisted state has `FORKED_TARGET=false`. That incorrectly sets `gh_skipped` and skips `gh.pr_view` plus head-ref validation for what should be a normal repo, and it widens the `main`/`master` carve-out beyond bash `run_ship_branch_guard`, which reads only `FORKED_TARGET` from state. **Suggested fix:** For resume routing, derive `forked` solely from hydrated `forked_target` (state-first); do not OR in `ctx.forked` when a state file exists.

- **risk-integration** `python/ship.py:513-525` — When a state file exists but `BRANCH_NAME` is empty and `ctx.branch` / `ctx.branch_name` are also empty, `_resume_plan` skips branch reconciliation (`expected_branch` is falsy) and proceeds with only `current_branch`, allowing `open-pr` / `merged` / `done` classification without any persisted branch anchor. Bash `run_ship_branch_guard` stalls when either persisted or current branch is empty. **Suggested fix:** Treat “state file present + no resolvable expected branch + no safe current-branch proof” as `blocked-checkout-mismatch` (mirror bash fail-closed behavior), not as a valid non-fresh resume.

### Out-of-Scope Observations

- `manifest_status()` is added in `python/run_logs.py` but never used in `_resume_plan`; gh-skipped merged routing ignores manifest `DONE`. That is stricter than the plan’s optional manifest signal and is not itself a regression.

- The plan mandates classifying normal-repo `gh.pr_view` failures as `fresh`; the broad `except Exception` at `python/ship.py:564-568` therefore trades orchestrator `TRANSIENT` (exit 6) handbacks for a full checks/postbump restart on transient network errors. That is an intentional design trade-off, not an accidental bug.

- Many plan-listed acceptance scenarios (wrong PR head, GitHub-authoritative stale merged flags, `gh` exception → `fresh`, cap-at-50 semantics, rebase-continuation idempotency, etc.) are not yet covered in `python/test_ship.py`; the branch adds only a small resume subset. That is a coverage gap, not evidence those paths are broken in code.
