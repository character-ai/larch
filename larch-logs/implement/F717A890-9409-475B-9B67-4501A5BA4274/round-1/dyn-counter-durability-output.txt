### In-Scope Findings

- **correctness** `python/ship.py:657-670` — `_monitor_persisted_counters` bumps `fix_attempts` whenever `monitor.did_fixing` is true, but `ci_monitor.monitor` sets `did_fixing=True` for several terminal outcomes that are not successful fix pushes (for example `first-fixer-non-health`, `fix-exhausted`, `local-unfixable`, and other evaluate_failure failures at `python/ci_monitor.py:1300-1338`). Bash only increments `FIX_ATTEMPTS` after a successful staged fix push (`scripts/ship-pr.sh` around `2236`). On exit-3/exit-6 handbacks, persisted state can over-count fix attempts and hit `fix-attempts-exhausted` early on the next resume. **Suggested fix:** Only add to `fix_attempts` when the monitor outcome reflects a consumed fix attempt (for example `fix.status == "pushed"`), or split `did_fixing` into “attempted” vs “pushed” and persist increments only for the latter; align the continue-path increment at `python/ship.py:1005-1006` with the same rule.

- **correctness** `python/ship.py:1007` — After every non-merge monitor cycle, the loop unconditionally does `iteration += 1` before `continue`. Bash only increments `ITERATION` on rebase completion (`scripts/ship-pr.sh:2688-2691`, `3052`), not after every `ci-wait.sh` return. Paths such as transient rerun (`ci_monitor` `no-changes` with `transient_rerun_attempted=True`) therefore inflate the session iteration counter in-process and can hit `SHIP_MERGE_LOOP_MAX_ITERATIONS` sooner than bash. **Suggested fix:** Increment `iteration` only when bash does (after a completed rebase / outer-cycle advance), or persist and restore `ITERATION` from monitor output using the same semantics as `record_ci_counters` in `scripts/ship-pr.sh:1404-1408`.

- **correctness** `python/ship.py:1012-1014` — On `merge_pr` returning `ci_not_ready` or `main_advanced`, the code increments `iteration` and `continue`s without writing counters to `ship-pr-state.sh`. Bash retries merge on `ci-merge` without bumping `ITERATION` (`scripts/ship-pr.sh:3005-3006`). In a single process this can over-count toward the cap; on orchestrator handback before the next loop write, the increment is lost and behavior diverges from both bash and the in-memory path. **Suggested fix:** Drop the `iteration += 1` for merge retry to match bash, or persist counters immediately when retrying merge if an iteration bump is intentional.

- **correctness** `python/ship.py:1002-1007` — `rebase_count`, `fix_attempts`, `transient_retries`, and `iteration` are updated in memory after rebase/fix handling, but the next `_write_ship_state` happens only at the top of the next loop (`904-910`). An orchestrator handback between those points leaves stale counters on disk even though the current cycle already consumed budget. **Suggested fix:** Write counters to state immediately after incrementing them (or after rebase returns), especially before any call that can hand back to the orchestrator.
