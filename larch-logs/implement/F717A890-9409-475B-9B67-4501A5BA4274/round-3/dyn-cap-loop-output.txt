### In-Scope Findings

- **correctness** `python/ship.py:1124-1140` — The merge loop still performs a **pre-monitor** `iteration >= SHIP_MERGE_LOOP_MAX_ITERATIONS` stall before calling `ci_monitor.monitor()`. That contradicts the plan’s cap-order rule (“remove or move the outer pre-monitor iteration-cap stall”) and diverges from bash: `scripts/ci-decide.sh` evaluates `pass` / `already_merged` **before** the iteration safety limit (lines 106–120 vs 122–127), so a call at `ITERATION=50` can still return `merge` when CI is green. On open-pr resume with persisted `ITERATION=50` (`test_open_pr_resume_at_iteration_cap_stalls_before_monitor`), the driver stalls immediately and never polls CI, so a later green CI / mergeable PR cannot complete even though bash would re-enter `ci-wait` and merge. **Suggested fix:** Drop the pre-monitor cap at loop entry (lines 1125–1140). Always invoke `monitor()` first; only stall on cap **after** a non-`merge` / non-`already_merged` decision (the post-monitor branch at 1187–1202 already does this). Let `ci_monitor.decide()` own pass/merge-at-cap semantics, matching `ci-decide.sh`.

- **correctness** `python/ship.py:1277-1303` — On `merge_pr` returning `ci_not_ready` or `main_advanced`, the driver increments `iteration` and may hit the merge-loop cap before retrying. Bash does **not** bump `ITERATION` on that path: `scripts/ship-pr.sh` lines 3005–3006 `return 0` and re-enters CI with the same counter. Python can therefore exhaust the session iteration budget during merge retries that bash would keep retrying at the same `ITERATION`, causing premature `merge-loop-iteration-cap` stalls and incorrect persisted `ITERATION` on resume. **Suggested fix:** Remove the `iteration += 1` (and the cap check tied to it) for `MERGE_RESULT_CI_NOT_READY` / `MERGE_RESULT_MAIN_ADVANCED`; `continue` back to `monitor()` without consuming an outer-loop iteration, mirroring bash’s `return 0` retry semantics.

- **correctness** `python/ship.py:839-852` — `_monitor_persisted_counters()` only applies `transient_rerun_attempted` on terminal monitor handbacks; it never mirrors the continue-path bumps for `did_fixing` (`fix_attempts += 1` at 1256–1257) or `goto_rebase` (`rebase_count += 1` at 1253). That is correct for failed-fix exits (`test_terminal_counter_persistence_does_not_count_failed_fixing`), but if a monitor cycle performs a successful fix push and then returns a non-OK outcome in the same invocation, bash increments `FIX_ATTEMPTS` on push (`scripts/ship-pr.sh` ~2236) while the terminal path leaves the pre-push value. A re-invoked `run_ship()` can then retry fixes beyond bash’s persisted budget. **Suggested fix:** Extend `_monitor_persisted_counters()` to apply the same conditional increments as the continue branch (`rebase_count` after a completed rebase leg, `fix_attempts` when `did_fixing` and the fix reached `pushed` / equivalent), or persist counters in-state on the continue path before any terminal return so handback state always reflects consumed work.

### Out-of-Scope Observations

- The plan’s acceptance matrix calls for explicit tests (`ITERATION=49` final cycle, pass/already-merged at cap, two-invocation terminal handback with consumed increments). The branch adds `test_open_pr_resume_at_iteration_cap_stalls_before_monitor` and `test_merge_loop_iteration_cap_stalls`, but not the finer cap-order / handback round-trip cases; those gaps make the pre-monitor stall regression easier to miss.

- `python/ship.py:754-760` routes normal-repo GitHub `MERGED` to `done` only when both `PHASE=done` **and** manifest `status=DONE`; otherwise it re-enters postmerge. That matches `test_legacy_done_merged_resume_retries_postmerge_without_done_manifest` but is stricter than the plan’s “`PHASE=done` ⇒ done” wording for gh-skipped vs GitHub-authoritative paths — worth tracking separately from cap-loop behavior.
