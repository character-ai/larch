Reviewing `_resume_plan` and related GitHub routing against the plan.
### In-Scope Findings

- **risk-integration** `python/ship.py:726-732` — For normal repos, `_resume_plan()` only classifies `start="done"` when GitHub reports `MERGED` with a matching head **and** `PHASE=done` **and** `manifest_status(ctx) == config.MANIFEST_STATUS_DONE`. The plan’s GitHub-authoritative rules require `MERGED` + matching head + `PHASE=done` ⇒ `done` with no manifest gate. If postmerge already succeeded (`PHASE=done`, GitHub `MERGED`) but the tmpdir manifest is absent, partial, or not yet `done`, resume routes to `merged` and re-runs `run_postmerge_phase()` instead of returning idempotent OK. That misroutes a completed GitHub state and can duplicate finalize/post-merge work. **Suggested fix:** Drop the manifest conjunct for normal-repo `done` classification (use `state_phase == "done"` with GitHub `MERGED` + head match only). Reserve manifest-only recovery for gh-skipped contexts, or gate `merged` only when `PHASE` is `postmerge`/non-terminal.

- **risk-integration** `python/ship.py:1124-1139` — The merge loop still pre-stalls when `iteration >= SHIP_MERGE_LOOP_MAX_ITERATIONS` **before** `ci_monitor.monitor()` runs. On open-pr resume with `ITERATION=50`, the driver never polls CI/GitHub, so it cannot observe `already_merged` or a passing CI outcome at the cap. That contradicts the plan’s cap-order rule and `test_open_pr_resume_at_iteration_cap_stalls_before_monitor` encodes the wrong behavior. An externally merged PR can remain stalled at the cap without a final GitHub/CI observation. **Suggested fix:** Remove the pre-monitor cap check at loop entry; keep cap enforcement only after monitor returns a non-pass/non-merged action (as at `python/ship.py:1187-1202`), so iteration 50 still gets one monitor cycle that can route to merge/postmerge/done.

- **risk-integration** `python/ship.py:709-716,984-992,1119-1123` — When `gh.pr_view()` fails on a normal repo, `_resume_plan()` returns `start="fresh"` but carries persisted counters into `ResumePlan`, and the fresh path writes those counters into `ship-pr-state.sh` while seeding the CI loop with `iteration=0` (`resume.start == "open-pr"` is the only path that restores monitor counters). A transient `gh` outage can therefore leave stale `ITERATION`/`FIX_ATTEMPTS` in state during a “fresh” restart; the next successful resume may restore inflated session-wide caps and bypass bash-parity limits. The plan requires `gh` exceptions ⇒ `fresh` with zero counters. **Suggested fix:** On any `start="fresh"` classification (including `gh pr view failed`, wrong head, CLOSED, invalid PR identity), force `ResumeCounters(0,0,0,0)` in `_fresh_resume_plan` / `_hydrate_fresh_context`, and write zeros in fresh-path `_write_ship_state` calls so state and monitor seeding stay aligned.

### Out-of-Scope Observations

- The plan’s acceptance matrix includes several GitHub-authoritative scenarios (wrong-head `OPEN`/`MERGED`, `CLOSED` non-merged with stale local merged flags, `OPEN` overriding stale `PR_CLOSED`/`PHASE=postmerge`, missing `state_file` with `ctx.pr_number` set, `ITERATION=49` vs `50` cap semantics with pass/already-merged at cap) that are not covered by dedicated tests in `python/test_ship.py` beyond the cases added in this branch. The routing logic appears intended to handle them, but the gaps leave regression risk outside the github-authority focus.
