Reviewing the branch diff and commit history for ship state persistence architecture.
Digging into state-write paths and resume classification for architectural inconsistencies.
### In-Scope Findings

- **architecture** `python/ship.py:241-242` — `_materialize_manifest_oos()` still calls `_write_ship_state(..., phase="pr-create")` without counter kwargs, so all four CI-loop counters default to `0`. On the fresh path this runs after earlier fresh writes already threaded `resume.iteration` / `resume.fix_attempts` / etc. through `_write_ship_state` (e.g. `pr-create` at ~1038–1044). A manifest that triggers the pre-materialize `oos_pending` write can therefore clobber session-wide counters mid-run, which is exactly the regression this branch is trying to eliminate. **Suggested fix:** Add the same counter parameters used by `_oos_gate()` / `_pending_oos_gate()` to `_materialize_manifest_oos()`, and pass `resume.*` counters from the fresh-path call site at ~1054.

- **architecture** `python/ship.py:477-539` — `_write_ship_state()` now preserves `RESUME_PHASE` and `CALLER_KIND` from the existing file on routine writes, but it still does a full-file rewrite and does not preserve `CONFLICT_FILES`. The new pre-push handoff path (~1241–1251) writes `CONFLICT_FILES` via `extra_fields`, yet any later routine `_write_ship_state()` (open-pr `pr-create`, `ci-initial`, terminal writes, etc.) silently drops that key. Re-entry only stays safe while `RESUME_PHASE=ship-pr-rrr-phase14` still routes to `blocked-rebase-continuation` before any write; if that marker is cleared or bypassed, conflict metadata is lost even though counters and phase may survive. **Suggested fix:** Mirror the `RESUME_PHASE`/`CALLER_KIND` pattern for `CONFLICT_FILES`—read and carry forward the existing value when `extra_fields` is omitted, or merge persisted extra keys instead of replacing the whole state surface.

- **architecture** `python/ship.py:1089-1123` — The fresh and open-pr paths now share one PR/CI entry block, but they use two different counter authorities. Pre-CI `_write_ship_state()` calls (~986–1026, 1038–1044, 1089–1095, 1104–1110) always persist `resume.iteration` / `resume.rebase_count` / `resume.fix_attempts` / `resume.transient_retries`, while the merge loop only restores counters when `resume.start == "open-pr"` and otherwise hard-seeds locals to `0` (~1120–1123). On fresh fallback (e.g. GitHub head mismatch or `gh.pr_view` failure), `ResumePlan` can carry non-zero counters from state, so `ship-pr-state.sh` may record stale budgets even though the monitor loop starts at zero; a PR-only fresh exit (~1102–1116) can leave those stale values in state for the next open-pr resume. That splits “authoritative counters” between persisted state and in-process CI locals and weakens the plan’s “fresh seeds zero” contract. **Suggested fix:** For `resume.start == "fresh"`, zero counters in both the CI locals and every `_write_ship_state()` on that path (or zero `ResumePlan` counters at fresh classification time), and only persist non-zero counters on validated `open-pr` / terminal handback paths.

### Out-of-Scope Observations

- Plan acceptance calls for explicit `ITERATION=49` / pass-at-cap coverage, but `python/test_ship.py` only pins the `ITERATION=50` pre-monitor stall (`test_open_pr_resume_at_iteration_cap_stalls_before_monitor`); the off-by-one “one final monitor cycle at 49” case is not directly tested.
- Merge/postbump failure branches still return without a terminal `ship-pr-state.sh` stall write (only `finalize-state.sh` in some paths). That predates this branch, though counter threading into the last successful write (~1309) is improved here.
