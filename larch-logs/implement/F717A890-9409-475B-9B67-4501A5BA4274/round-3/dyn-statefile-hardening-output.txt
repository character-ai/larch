Inspecting state-file read/write paths and how bash consumes them for injection and traversal risks.
### In-Scope Findings

- **security** `python/ship.py:726-731` — New merged-resume routing treats `manifest_status(ctx)` as authoritative for the `done` vs `merged` fork when GitHub reports `MERGED`, but `manifest_status` resolves the manifest via `effective_run_id()`, which prefers `RUN_ID` from the untrusted state file over `ctx.run_id` (`python/run_logs.py:306-318`, `171-184`). Unlike `REPO`, resume never requires state `RUN_ID` to match the caller context. A party who can edit `ship-pr-state.sh` under the session tmpdir can point `RUN_ID` at another slug under `tmpdir/larch-logs/implement/`, plant a `manifest.json` with `"status": "done"`, set `PHASE=done`, and get an idempotent `done` exit that skips `run_postmerge_phase` even though GitHub still shows a freshly merged PR. **Suggested fix:** For resume classification only, require `read_state_kv(..., "RUN_ID")` to match `ctx.run_id` when both are present and slug-valid (mirror the `REPO` cross-check), or pass an explicit validated run id into `manifest_status` instead of `effective_run_id()`; only honor manifest `done` when it belongs to the current run.

- **security** `python/ship.py:610-612,679,762-827` — `read_durable_flags()` hydrates `REPO_UNAVAILABLE`, `FORKED_TARGET`, `forked`, `MERGE`, and `DRAFT` from the state file before routing, and those hydrated values can force the gh-skipped path (`gh_skipped = durable.repo_unavailable or durable.forked or durable.forked_target`), which then classifies `done` / `merged` / `open-pr` from local `PHASE`, `PR_CLOSED`, and `MERGE_RESULT` without calling `gh.pr_view`. That is a deliberate argv-override feature, but it also means a tampered state file can disable GitHub ground-truth checks that the normal-repo path depends on, as long as the writer can reach the session tmpdir. **Suggested fix:** Treat gh-skipped resume as a privileged mode: require caller/context agreement for `REPO_UNAVAILABLE` and fork flags (e.g. refuse state-only overrides unless `ctx` already asserts the same flag), or document and enforce an integrity boundary (session ownership, sentinel file, or signed state) before honoring state-first durable flags for non-`fresh` resumes.

- **security** `python/ship.py:618-621,803-844` — Resume hydration copies `BRANCH_NAME`, `PR_URL`, and `MERGE_RESULT` from the state file into `RunContext` and rewrites them via `_write_ship_state()` (`python/ship.py:507-536`) with only newline rejection on write, not shell-safe charset validation on read. Bash `ship-pr.sh` later consumes the same keys through `read_state()` and command-line expansion (`scripts/ship-pr.sh:395-406`, `1290`, `1389-1390`). Python subprocess calls are argv-safe, but this branch amplifies trust in attacker-writable state and re-persists values for the bash cutover surface. **Suggested fix:** Validate resumed string fields at ingest with the same constraints used elsewhere (repo slug regex for `REPO`, git-ref-safe charset for `BRANCH_NAME`, URL parsing for `PR_URL`, allowlisted tokens for `MERGE_RESULT`), and refuse or strip values that fail before hydration or rewrite.

### Out-of-Scope Observations

- `python/run_logs.py:306-313` — `effective_run_id()` preferring state `RUN_ID` predates this branch and is covered by `test_effective_run_id_prefers_state_file`; the new risk is its use in resume routing, not the helper itself.
- `scripts/ship-pr.sh:379-388` — Bash validates state-file line syntax only; value-level charset checks for `BRANCH_NAME` / `PR_URL` are still absent on the production bash path and were not introduced here.
- This review did not execute `make py-test` / `make py-lint`; findings are from static diff and source inspection only.
