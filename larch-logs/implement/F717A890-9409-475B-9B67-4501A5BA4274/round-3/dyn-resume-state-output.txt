Reviewing the branch diff and commit history for resume-state correctness.
### In-Scope Findings

- **correctness** `python/ship.py:1124-1140` — The merge loop still pre-stalls when `iteration >= config.SHIP_MERGE_LOOP_MAX_ITERATIONS` before calling `ci_monitor.monitor()`. That violates the stated cap-order rule (“pass/already-merged at cap does not pre-stall before the success/merged path”) and duplicates the cap that `ci_monitor.decide()` already applies after checking `merged`/`pass` (`python/ci_monitor.py:132-146`). On open-PR resume with a restored counter already at the cap, the driver can stall without giving `decide()` a chance to observe `pass` or `already_merged`, so a mergeable PR can be incorrectly capped out. **Suggested fix:** Remove the loop-entry guard (and rely on the post-monitor stall at `python/ship.py:1186-1202` plus `decide()`’s ordering), or only stall after a monitor/decision cycle when the outcome is neither merge nor already-merged; update `test_open_pr_resume_at_iteration_cap_stalls_before_monitor` accordingly and add a pass/already-merged-at-cap regression case.

- **correctness** `python/ship.py:726-732` — For normal repos, GitHub `MERGED` with matching `head_ref` routes to `done` only when both `PHASE=done` **and** `manifest_status(ctx) == config.MANIFEST_STATUS_DONE`. The plan/acceptance require idempotent `done` when GitHub confirms `MERGED` and local phase is already `done`; the extra manifest gate forces a `merged`/postmerge retry whenever `PHASE=done` was written but the manifest was not flushed to `"done"` (see `test_legacy_done_merged_resume_retries_postmerge_without_done_manifest`). That can rerun post-merge work on an otherwise complete run. **Suggested fix:** Route `MERGED` + matching head + `PHASE=done` to `done` without requiring manifest `"done"`, and reserve manifest-only recovery for cases where phase is `postmerge` or merge-result flags disagree.

- **correctness** `python/ship.py:696-724,984-993,1120-1123` — `_fresh_resume_plan(..., counters=counters)` keeps persisted counter values on every `start="fresh"` fallback, and the fresh path writes those values into `ship-pr-state.sh` during checks/pr-prep/pr-create, but the CI loop re-seeds locals to zero unless `start == "open-pr"`. That splits “fresh” behavior: monitor/cap logic starts at zero while the state file may still carry stale session counters until the first CI write, so a handback during checks/postbump can restore inflated counters on the next resume even though the run was classified as fresh. **Suggested fix:** Zero `ResumePlan` counter fields whenever `start="fresh"` (including gh/head/identity fallbacks), and pass literal zeros into all fresh-path `_write_ship_state` calls; keep counter preservation only for validated `open-pr`/`merged`/`done` resumes.

- **correctness** `python/ship.py:623-626,610-614` — `_resume_plan()` raises `ShipError` on invalid or mismatched persisted `REPO`, but the plan requires resume classification to never raise on corrupt/untrusted state and instead degrade safely. Those exceptions bubble to `run_ship()`’s top-level handler and become `Outcome.STALLED` (`test_resume_rejects_state_repo_mismatch_before_github`), which is a different failure mode than checkout/identity safe-refuse and can abort resume work without the intended `NEEDS_USER_INPUT` handback shape. **Suggested fix:** Treat invalid/mismatched `REPO` like other resume validation failures—return a blocked/fresh `ResumePlan` with a descriptive `detail`, or a dedicated safe-refuse start—and avoid raising from `_resume_plan()`.
