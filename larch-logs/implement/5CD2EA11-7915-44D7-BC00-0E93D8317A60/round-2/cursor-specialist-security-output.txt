### In-Scope Findings

1. **Latent** (`security`) [`scripts/redact-tmpdir-paths.sh`](scripts/redact-tmpdir-paths.sh) (new `[[:alnum:]_.-]+/[[:alnum:]_.-]+` operator-repo expressions): The scrubber only matches ASCII-ish path segments and relies on POSIX character classes whose `[[:alnum:]]` behavior is locale-sensitive. A real macOS/Linux home or repo directory that contains non-ASCII characters (or other characters outside that class) may fail to match, so text that still contains a literal `/Users/...` or `/home/...` absolute path could cross the publish boundary unchanged despite the expanded `SECURITY.md` claim. Tighten the contract with explicit `LC_ALL=C` (if not already set by all callers), document the ASCII-segment assumption, or add a conservative fallback pass for `/Users`/`/home` prefixes that does not depend on a narrow segment alphabet.

2. **Latent** (`correctness`) [`scripts/ship-pr.sh`](scripts/ship-pr.sh) (`run_rebase_rebump` + `semver_lt`): `_origin_ver` is constrained with `^[0-9]+\.[0-9]+\.[0-9]+$`, but `new_version` from `classify-bump.sh` is not validated on the same path before `semver_lt "$new_version" "$_origin_ver"` and the numeric `[[ ... -lt ... ]]` comparisons inside `semver_lt`. Unusual or corrupted `NEW_VERSION` strings can make the regression test unreliable or, in edge cases, trip Bash’s integer parsing for `[[` under `set -euo pipefail`, aborting the rebase/re-bump flow mid-flight. Mirror the origin-version regex (or reuse a single strict semver gate) for `new_version` before any semver comparison.
