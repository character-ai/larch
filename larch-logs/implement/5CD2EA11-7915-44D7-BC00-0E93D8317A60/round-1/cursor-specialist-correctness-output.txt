### In-Scope Findings

1. **Important** (`correctness`, source: **plan + requirements**) — [docs/run-logs.md](docs/run-logs.md):71-73  
   The new sentence claims `status` in **committed** manifests is **always** `"in-progress"`, but `larch-log.sh manifest` allows arbitrary updates to `status` (it is not in the immutable-field list), and `scripts/test-larch-log.sh` already exercises `manifest --field status=done` followed by persistence checks. **Concrete scenario:** a caller runs `larch-log.sh manifest ... --field status=done` and later `larch-log.sh commit`; the committed `manifest.json` contains `"done"`, contradicting the doc. The same paragraph also sits next to line 71, which still says the manifest contains **“final run status”**, which reads like the opposite of “always in-progress in git.” **Suggested fix:** Rephrase to the normal `/implement` lifecycle (tmpdir may hold `done`, typical flush commits snapshot `in-progress`), qualify with “unless a later commit intentionally records another status,” and align line 71’s wording with that model.

2. **Important** (`correctness`, source: **requirements**) — [scripts/test-larch-log.sh](scripts/test-larch-log.sh):203-226  
   The new regression seeds the stale run only under the **staging** log root (`$_stale_staging/larch-logs/...`), not as a pre-existing **untracked sibling under the fake repo’s** `larch-logs/implement/`. The failure mode in the feature description is **`git add` pathspec widening** picking up orphan directories already present in the **consumer repo worktree**; `cp` from the fresh run’s staging dir never copies that sibling, so the test can pass even if pathspec logic were still wrong for repo-local orphans. **Concrete scenario:** With a skill-wide pathspec, an untracked `$_stale_repo/larch-logs/implement/stalerun-old999/` beside the freshly copied run would be staged; the harness never creates that layout. **Suggested fix:** After `git init` / first commit on `$_stale_repo`, `mkdir -p "$_stale_repo/larch-logs/implement/$_stale_run"` and drop a decoy file there before `larch-log.sh commit`, then assert it stays absent or unstaged.

3. **Latent** (`correctness`, source: **plan** as shipped in the same branch) — [scripts/ship-pr.sh](scripts/ship-pr.sh):1224-1234  
   `run_rebase_rebump` calls `semver_lt "$new_version" "$_origin_ver"` after only checking `_origin_ver` matches `^[0-9]+\.[0-9]+\.[0-9]+$`. `new_version` is not regex-validated first (unlike `apply-bump.sh` for `NEW_VERSION`). **Concrete scenario:** If `classify-bump.sh` output were ever malformed or partially parsed (unexpected `NEW_VERSION` string), bash integer comparisons inside `semver_lt` can mis-compare or trip `set -e` behavior on bad data, skipping correction or stalling the re-bump path unexpectedly. **Suggested fix:** Gate the regression branch with the same strict semver regex used for `_origin_ver` (and/or validate before `semver_lt`).

4. **Nit** (`code-quality`, source: **plan**) — [docs/run-logs.md](docs/run-logs.md):73  
   “no commit window after merge” is easy to misread as “no code path ever writes `done`,” while `ship-pr` / `implement-finalize` docs describe `status=done` updates in tmpdir post-merge. Tighten wording to “flush commits normally happen before that update” to avoid cross-doc confusion.
