Reviewing exit-site mapping in the checkpoint script and SKILL.md orchestrator.
### In-Scope Findings

- **correctness** `skills/implement/SKILL.md:1204-1214` — The orchestrator fallback `append-tool-failure.sh` always uses `--site step-8-oos-checkpoint-validation` even when `_oos_chk_rc` is `1`. That path runs only when neither site token appears in `execution-issues.md`, i.e. when `oos-disposition-checkpoint.sh`’s own `log_checkpoint_failure` did not persist a row (because `append-tool-failure.sh` failed and was swallowed by `|| true`, or the log file was missing/unwritable). In that scenario a real disposition gap (exit `1`) is logged under the validation site, contradicting the Step 8+ prose at lines 1187–1187 (exit `1` → disposition remediation; exit `2` → range/setup) and the helper contract in `skills/implement/scripts/oos-disposition-checkpoint.sh:189-190` / `oos-disposition-checkpoint.md:40-41`. The removed inline block branched `_oos_fail_site` on gate rc before appending. **Suggested fix:** Set fallback `--site` from `_oos_chk_rc` (`step-8-oos-checkpoint` when `_oos_chk_rc -eq 1`; `step-8-oos-checkpoint-validation` for `2` and other non-zero codes, matching the helper’s `log_checkpoint_failure` mapping). Optionally pass `--output-file` from `_gate_log` vs `_oos_chk_err` based on whether the gate ran.

- **correctness** `skills/implement/SKILL.md:1204-1206` — The “already logged” guard uses `grep -Fq 'step-8-oos-checkpoint'`, which also matches rows written with `step-8-oos-checkpoint-validation` because `append-tool-failure.sh` emits `- **Step %s —` (`scripts/append-tool-failure.sh:150`) and the shorter token is a substring of the longer one. After a prior validation failure is logged, a later checkpoint exit `1` whose helper append failed will skip the fallback entirely, leaving no `Tool Failures` row for the current disposition gap even though `_oos_chk_rc` is still `1`. The harness avoids this for exit-1 assertions (`skills/implement/scripts/test-oos-disposition-gate.sh:538-539` negates the validation token); the orchestrator guard does not. **Suggested fix:** Make the guard rc-specific: for `_oos_chk_rc -eq 1`, treat as logged only when a disposition-only header is present (e.g. `grep -Fq 'step-8-oos-checkpoint'` **and** `! grep -Fq 'step-8-oos-checkpoint-validation'`, or match the exact `Step step-8-oos-checkpoint —` header); for `_oos_chk_rc -eq 2`, require `step-8-oos-checkpoint-validation` only.

### Out-of-Scope Observations

- `skills/implement/scripts/oos-disposition-checkpoint.sh:19-30,53-58,189-195` — In-script rc→site mapping is consistent: rc `1` → `step-8-oos-checkpoint`, rc `2` and pre-gate failures → `step-8-oos-checkpoint-validation`; gate rc `3+` maps to validation via the final `log_checkpoint_failure` at line 195, aligned with SKILL.md “any other non-zero exit” prose.

- `skills/implement/scripts/oos-disposition-checkpoint.md:311-320` — Ndjson discovery intentionally diverges from the old inline block when `session-id` is non-empty but the keyed ndjson is missing (no `find` bind to a foreign run). That is a behavioral change outside exit-site mapping; it is documented and covered by `test-oos-disposition-gate.sh` (“stale RUN_ID” case).

- No harness exercises the SKILL.md fallback append path (append failure / empty `execution-issues.md` with rc `1`), so the mis-site fallback would not be caught by `make test-oos-disposition-gate`.
