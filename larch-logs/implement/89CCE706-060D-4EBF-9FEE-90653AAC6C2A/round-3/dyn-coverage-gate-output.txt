### In-Scope Findings

- **correctness** `skills/review/scripts/review-core.sh:466-473` — The file-based fallback in `static_archetype_coverage_ok` runs on every static output in `external_array`/`claude_array` and treats any non-empty file without a literal `NOT_SUBSTANTIVE` token as success, even when `collector-results.env` already recorded `STATUS=NOT_SUBSTANTIVE` for that basename. That diverges from `check-reviewer-failure-threshold.sh`, which puts every collector-adjudicated base into `COUNTED_BASES_FILE` and does not let the output-file pass override a failed collector status. In an 8-slot both-vendor panel, both peers for one archetype can be collector-downgraded to `NOT_SUBSTANTIVE` (only 2/8 threshold failures, so the round continues), yet the coverage gate can still credit that slug from non-empty narrative files and let the round proceed without any substantive static lens for that archetype — contradicting the plan’s per-archetype gate (“zero successful peer outputs … not-substantive”). **Suggested fix:** While parsing collector records, build a per-normalized-base status map (reuse `normalize_reviewer_output_base`). Only run the file fallback when there is no collector record for that base (Claude phase-2/3-only path), or optionally when the collector status is an explicit recoverable class such as `ERROR` with a substantive file; never file-fallback credit bases whose collector status is `NOT_SUBSTANTIVE`, `FAILED`, `TIMED_OUT`, etc. Add a harness where both vendor peers for one slug are `NOT_SUBSTANTIVE` in collector but files are non-empty, aggregate threshold passes, and coverage must fail.

- **correctness** `skills/review/scripts/review-core.sh:444-446,461-463` — `cap_hit` is treated the same as `OK` for archetype coverage. A deliberate budget skip means no review ran for that peer, yet the slug is marked covered. If both vendor peers for an archetype return `cap_hit`, the coverage gate passes even though no static lens executed, while the plan describes failure when peers are “failed/not-substantive” (and cap_hit is not a substantive success). **Suggested fix:** Decide explicitly whether cap_hit satisfies per-archetype coverage; if not, count `cap_hit` as non-success here (even if threshold still treats it as a non-failure slot-skip), or require at least one peer with `STATUS=OK` or a substantive file-backed fallback before crediting a slug.
