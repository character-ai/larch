### In-Scope Findings

- **risk-integration** `scripts/dispatch-with-waterfall.sh:444-448` — Under `--no-fallback`, any static slot that fails phase 1 sets `static_dispatch_ok=false` for the whole panel, even when the opposite-vendor peer for the same archetype (same manifest `slot`, different `tool`) succeeds and is collected. `review-core.sh` no longer hard-stops on that KV, but `dispatch-panel.sh` still re-emits `STATIC_DISPATCH_OK=false`, which contradicts the plan’s “partial drop ≠ total static dispatch failure” contract and can mislead operators or automation that still read dispatch stdout. **Suggested fix:** Either narrow waterfall’s `STATIC_DISPATCH_OK` to “all four archetypes lack a successful static peer” (mirror `static_archetype_coverage_ok`), or compute a separate KV in `dispatch-panel.sh` after parsing `DROPPED_SLOTS_FILE` + manifest/collector paths so `STATIC_DISPATCH_OK` stays true when each of `security|correctness|edge-cases|testing` has at least one surviving peer.

- **architecture** `skills/review/scripts/dispatch-panel.sh:94-98` — Static Cursor and Codex rows share the same manifest `slot` value (the archetype slug, e.g. `security`) and differ only by `tool`/`output`. `/design` uses distinct slot IDs per vendor (`cursor-plan-*` vs `codex-plan-*` in `dispatch-plan-review-panel.sh:181-197`). Current join logic (`collect_dropped_static_outputs`, dropped TSV) correctly matches `slot`+`tool`, but any future consumer that keys only on `slot` will mis-attribute drops or successes when both vendors run. **Suggested fix:** Align with design by emitting vendor-qualified static slots (e.g. `cursor-static-security` / `codex-static-security`) while keeping output basenames unchanged for tally compatibility, or document/enforce “always key on `(slot,tool)` or output path” in `dispatch-panel.md` and add a harness assertion that duplicate slug+distinct tool rows round-trip through `DROPPED_SLOTS_FILE`.

- **risk-integration** `skills/review/scripts/review-core.sh:544-624` — `DISPATCH_OK` / `STATIC_DISPATCH_OK` are no longer read after dispatch; panel fate is entirely threshold + coverage. That is intended for partial no-fallback drops, but it also means a round can continue when `DISPATCH_OK=false` only because optional dynamic slots failed, or when dispatch logging says static dispatch degraded while aggregate static failure rate stays ≤50%. Failures are mostly still caught by coverage, yet there is no degraded-round signal analogous to design’s `DEGRADED_ROUND` (`plan-review-loop.sh:898`). **Suggested fix:** After threshold/coverage, derive and emit something like `PANEL_DEGRADED=true` when `DISPATCH_OK=false`, `DYNAMIC_DISPATCH_OK=false`, or `STATIC_DISPATCH_OK=false` with partial static success, so `/implement` Step 5 run logs and execution-issues reflect “continued with holes” without reintroducing the old unconditional `dispatch-failed` short-circuit.
