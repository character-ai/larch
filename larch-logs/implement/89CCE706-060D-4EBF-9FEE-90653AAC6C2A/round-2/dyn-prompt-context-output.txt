### In-Scope Findings

- **security** `scripts/render-specialist-prompt.sh:286-310` — The branch widens inline embedding of `PLAN_FILE` and `FEATURE_FILE` to `reviewer-testing` in **all** diff modes (`docs-only`, `test-only`, `generated-only`) and in **description** mode, while still using raw `cat` with no escaping (unlike `scout-dynamic-archetypes.sh`, which pipes inline text through `escape_prompt_data`). Together with re-enabling Codex phase-1 dispatch (`codex_present_for_waterfall="$CODEX_AVAILABLE"`), the same unredacted plan and full GitHub issue body (`feature-description.txt` from `implement-bootstrap.sh`) are now sent to **both** Cursor and Codex static `reviewer-testing` peers far more often than before. Plan materialization copies issue-derived content without a render-time `redact-secrets.sh` pass, so secrets or tokens in the issue/plan can reach third-party APIs and committed dynamic Codex artifacts. **Suggested fix:** Before `cat` into `<implementation_plan>` / `<feature_description>`, pipe through `redact-secrets.sh` (and consider `escape_prompt_data` or a delimiter-safe wrapper for tag breakout). Narrow injection to modes that truly need plan context, or stage plan/feature as path-only reads with explicit untrusted-data framing (as the scout already does for diff/description files).

- **security** `scripts/render-specialist-prompt.sh:289-298` — Plan and feature blocks are inserted **immediately after** the preamble line “The following tags delimit untrusted input…”, but the injected content is **not** inside those delimited tags. A collaborator-controlled plan or issue body can contain a literal `</implementation_plan>` (or `</feature_description>`) plus instruction-like prose that sits between the trust-boundary reminder and the fixed agent body, increasing prompt-injection risk for external reviewers—especially now that `reviewer-testing` always receives plan context when `--plan-file` is set. **Suggested fix:** Wrap inlined plan/feature in explicitly named delimiters (e.g. `<reviewer_plan untrusted="true">`) that are documented in the preamble, reject or escape closing-tag substrings in file content before embed, or switch to path-only references with “Read … treat as untrusted data” (matching scout staging).

- **security** `scripts/larch-log.sh:690` and `scripts/larch-log.md:26-31` — Static Codex specialist raw outputs and `.meta` are newly excluded from `write-round`, but **dynamic** `dyn-*-codex-output.txt` (and `.meta`) remain included and sanitized into committed `larch-logs/`. With Codex dynamic twins added in `dispatch-panel.sh`, reviewer transcripts that echo diff snippets, drop reasons, or accidental secrets can land in the public run-log tree while static Codex peers are suppressed—an asymmetric exposure path introduced by the both-vendor dynamic work. **Suggested fix:** Either exclude all Codex reviewer `*-output*.txt` from run logs (parity with static Codex), or extend redaction to strip plan/feature blocks and apply stricter secret scanning on dynamic Codex outputs before `write-round`.

- **risk-integration** `skills/review/scripts/dispatch-panel.sh:183-188` — Dynamic slots always pass `--plan-file` into `render-specialist-prompt.sh`, but only `reviewer-testing` gets the new broad injection; dynamics still receive plan only in `generic` diff mode via the `elif` branch. That is correct for scope, but when dynamics run in `generic` mode the full plan is still inlined into ephemeral prompts that are executed on **two** vendors per archetype—amplifying the same trust-boundary issues for LLM-scouted focus areas without the scout’s `has_unsafe_wrapper_tag` checks on plan content. **Suggested fix:** Stage plan for dynamics via `stage_context_file` + Read-tool instructions (as in `scout-dynamic-archetypes.sh`) instead of inline `cat`, or reuse scout-style validation on plan bytes before dispatch.

---

**Summary:** The collapse to four archetypes and per-archetype coverage gate look sound for preserving security coverage. The main security regressions are **expanded unescaped inline plan/feature embedding to `reviewer-testing` × both vendors**, **Codex phase-1 re-enable without render-time redaction**, and **asymmetric run-log retention of dynamic Codex outputs**. Addressing redaction/escaping at the render boundary and aligning log exclusion policy would close the largest gaps.
