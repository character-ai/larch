Reviewing branch changes for waterfall slot-accounting consistency. Reading the diff and key implementation files.
### In-Scope Findings

- **correctness** `skills/review/scripts/check-reviewer-failure-threshold.sh:138-158` — `count_static_status_once` only upgrades a slot from failure to success (`!status_is_success(old) && status_is_success(new)`); it never downgrades when collector results say `OK`/`cap_hit` but the on-disk transcript passed via `--reviewer-output-files` is empty or non-substantive (`output_file_is_success` → `ERROR`). Because `review-core.sh` always passes the same dispatch output paths to both `collect-findings.sh` and `--reviewer-output-files`, a collector false-positive `OK` on an empty file can leave that static peer in `SUCCEEDED_SLOTS` while the file has no findings, weakening the >50% gate and diverging from the coverage gate (which only credits `STATUS=OK` in `static_archetype_coverage_ok`). **Suggested fix:** Extend `count_static_status_once` with a symmetric downgrade path (e.g. when `status_is_success(old)` and the new status is `ERROR`/`NOT_SUBSTANTIVE`, decrement `SUCCEEDED_SLOTS` and increment `FAILED_SLOTS`), or treat a failed `output_file_is_success` check as authoritative over collector `OK` for the same normalized base.

- **correctness** `skills/review/scripts/check-reviewer-failure-threshold.sh:208-227` — Dropped-static accounting increments `FAILED_SLOTS`/`DROPPED_STATIC_SLOTS` even when `dropped_base` is empty (unrecognized `_dropped_tool`), so a malformed `DROPPED_SLOTS_FILE` row can add a failure without adding a normalized base to `COUNTED_BASES_FILE`, inflating `FAILED_SLOTS` relative to `COUNTED_SLOTS` and the 8-slot denominator. **Suggested fix:** `continue` before incrementing when `dropped_base` is empty after the `codex|cursor` case, or increment only when a normalized base was newly recorded.
