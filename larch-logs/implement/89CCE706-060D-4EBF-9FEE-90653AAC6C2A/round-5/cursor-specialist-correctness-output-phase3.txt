### In-Scope Findings

**1. [Latent] [correctness] `check-reviewer-failure-threshold.sh:~2123` — `count_static_status_once` allows OK→ERROR downgrade from empty phase-N files**

`count_static_status_once` has an upgrade path (failure→success) and a symmetrical downgrade path (success→failure). The downgrade fires when the same normalized base appears twice: first as OK (from the collector), then as ERROR (from `--reviewer-output-files`). Concretely: if `cursor-specialist-security-output.txt` is STATUS=OK in the collector and an empty `cursor-specialist-security-output-phase3.txt` is also present in `external_array` (which `review-core.sh` passes wholesale via `--reviewer-output-files`), `output_file_is_success` returns false for the empty phase-3 file and `count_static_status_once` downgrades the base from OK to ERROR — incorrectly flipping a succeeded archetype to failed. Phase-1 success should be idempotent; a subsequent empty phase-N file for the same slot should not retroactively invalidate it. Add a guard: only upgrade, never downgrade, in `count_static_status_once` (the upgrade path already handles the informative case), or filter `--reviewer-output-files` in `review-core.sh` to exclude files whose normalized base is already OK in the collector.

**2. [Latent] [correctness] `skills/review/scripts/review-core.sh:~3096` / `check-reviewer-failure-threshold.sh:~2192` — threshold and coverage gate disagree on what counts as "success"**

`check-reviewer-failure-threshold.sh --reviewer-output-files` calls `output_file_is_success` (non-empty + no `NOT_SUBSTANTIVE` token) to upgrade collector-ERROR slots. `static_archetype_coverage_ok` uses a different path: it checks whether the normalized base is in `rejected_file` (built from collector ERROR entries) and blocks `$@` files whose base is there. This means a slot that `check-reviewer-failure-threshold.sh` upgrades from ERROR to OK (because the file has bytes) will still fail `static_archetype_coverage_ok` because its base is in `rejected_file`. The net effect: threshold passes (`THRESHOLD_OK=true`) but coverage gate fires with `panel-failed`. This is observable when the collector records a slot as ERROR but the underlying output file is non-empty. The `external-files-only` test confirms the inconsistency is present but treats it as intentional without documentation. At minimum, document the asymmetry and explain why a substantive file that passes threshold does not satisfy coverage.

**3. [Nit] [correctness] `skills/review/scripts/check-reviewer-failure-threshold.sh:~2068` / `review-core.sh:~2907` — `NOT_SUBSTANTIVE` regex fires on reviewer prose**

Both `output_file_is_success` and `claude_static_output_is_success` scan reviewer transcript files for `(^|[^A-Z_])NOT_SUBSTANTIVE([^A-Z_]|$)`. This pattern matches the string anywhere in the file, including in legitimate reviewer prose such as "this change is NOT_SUBSTANTIVE for performance reasons." A reviewer that writes `NOT_SUBSTANTIVE` as part of analysis text would be incorrectly classified as a failed slot, reducing threshold counts and potentially blocking coverage credit. Restrict the check to the `STATUS=NOT_SUBSTANTIVE` line format (e.g., `grep -Eq '^STATUS=NOT_SUBSTANTIVE$'`) to mirror what the collector actually emits.

**4. [Nit] [correctness] `skills/review/scripts/dispatch-panel.sh:~2427` — `synthesize_dynamic_slots` indentation regression**

The `local row name...` declaration and the `while IFS= read -r row` loop inside `synthesize_dynamic_slots` are indented at 8 spaces (two function levels) while the surrounding function body uses 4-space indent. The `mkdir -p` call before them is at 4 spaces. This is not a runtime bug but produces misleading structure that suggests the loop is inside a nested block that does not exist. Realign to 4-space indent matching the rest of the function.
