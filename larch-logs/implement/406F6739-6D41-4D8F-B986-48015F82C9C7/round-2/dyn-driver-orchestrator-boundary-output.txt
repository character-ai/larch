### In-Scope Findings

- **architecture** `skills/design/SKILL.md:878-880` — After sourcing `$DESIGN_TMPDIR/.step3-review-result.env`, the fence still forces `LOOP_STATUS=panel-failed` whenever `run-step3-review.sh` exits non-zero (except `main-agent-vote-required`). That contradicts the file-first contract in the post-loop matrix (`skills/design/SKILL.md:891`) and can overwrite a valid status already loaded from the result env. Today the driver almost always exits `0` on success paths (`skills/design/scripts/run-step3-review.sh:300`), and exit `1` is only used after cursor-advance failure where the env already records `panel-failed` (`run-step3-review.sh:177-189`), so the happy path is safe. The coupling is brittle: any future non-zero exit after `phase_driver_write_result_env` (or a `set -e` abort between write and `exit 0`, e.g. `emit_kv` returning `2` at `run-step3-review.sh:289-298`) would turn a file-resident `cap-reached` / `converged` / `complete` into `panel-failed` and route Gate B / Step 3b incorrectly. **Suggested fix:** Apply the rc override only when `LOOP_STATUS` is still empty after file + stdout ingestion, or only for argv failures (`rc=2`) / missing result env; keep trusting the normalized `.step3-review-result.env` when it was sourced successfully.

- **architecture** `skills/design/scripts/run-step3-review.md:43` vs `skills/design/SKILL.md:878-880` — The driver contract says exit `1` means “HARD round-cursor advance failure (orchestrator abort)”, but the orchestrator no longer aborts: cursor failure writes `panel-failed` to the result env, exits `1`, and the fence downgrades to `panel-failed` and continues the branch matrix. That is an improvement over the removed inline `exit 1` (`diff.txt` removed `skills/design/SKILL.md` cursor `exit 1`), but the driver/orchestrator boundary docs disagree on whether exit `1` is fatal to Step 3. **Suggested fix:** Align `run-step3-review.md` (and any harness comments) with actual orchestrator behavior—exit `1` is a controlled `panel-failed` handoff, not a hard stop—or have the driver exit `0` after writing the normalized failure env so the rc override is unnecessary.

- **architecture** `skills/design/SKILL.md:863-873` — The orchestrator allowlist loads `STEP3_REVIEW_ROUND_NUM` and `REVIEW_ROUND_COUNT` from the result env (and stdout fallback), but no Step 3 post-loop branch or later fence references those variables; round cap, persist, and rollback live entirely in `run-step3-review.sh` (`run-step3-review.sh:81-271`). The branch matrix keys off `LOOP_STATUS`, `TALLY_PLAN_REVIEW_STATUS`, and `ROUNDS_COMPLETED` only (`skills/design/SKILL.md:893-916`). This widens the orchestrator surface without giving the LLM layer anything to do with those KVs and blurs the stated driver/orchestrator split in `lib-phase-driver.md:7-8`. **Suggested fix:** Drop the unused keys from the orchestrator allowlist (keep them driver-internal), or add a one-line contract note that they are diagnostic-only if retained for logging.

### Out-of-Scope Observations

- **Stdout fallback is not dead** under the SKILL.md invocation pattern: `run-step3-review.sh` calls `larch_quiet_init`, and `emit_kv` writes to FD 3 dup’d from the child’s FD1 (`scripts/lib-quiet.sh:55-57`, `174-175`), which in `_plan_review_out=$(…)` is the command-substitution pipe. Harnesses already assert captured `LOOP_STATUS=…` in driver stdout (`test-run-step3-review.sh:150-151`). The fallback only runs when `LOOP_STATUS` is empty after the file read (`skills/design/SKILL.md:869-876`); the primary handoff is `.step3-review-result.env`, matching `lib-phase-driver.md:14-17`.

- **`emit_kv` omits `STEP3_REVIEW_ROUND_NUM`** even though the orchestrator allowlist accepts it for stdout fallback (`run-step3-review.sh:289-298` vs `SKILL.md:873`). Low impact while the orchestrator does not consume that key.

- **Pattern divergence from `run-step2-dispatch.sh`** is intentional: Step 2 dispatches KVs on stdout without quiet mode; Step 3 uses quiet + atomic result env. Not a defect if file-first remains authoritative.
