### FINDING_13: Multiline allowlisted values can bypass consumer allowlist via `printf -v`
- **Reviewer(s)**: dyn-allowlist-variable-injection-output.txt
- **Severity**: important
- **Concern**: At `run-step3-review.sh:221-224`, inner-env normalization uses bare `printf -v "$_key"` over lines from `phase_driver_read_result_env` stdout without a per-line `case` re-allowlist (regression vs pre-refactor / stdout-fallback / SKILL fence). `phase_driver_read_result_env` (`lib-phase-driver.sh:67-76`) re-emits `key=value` without rejecting embedded newlines; multiline allowlisted values split into extra physical lines that bypass the allowlist and reach `printf -v` with attacker-chosen names (including bash-sensitive variables). Inner `write_step3_result_env` in `plan-review-loop.sh` uses unguarded `printf` for file writes while stdout uses `emit_kv` newline guards.
- **Suggested revisions (informational for voters; coder decides)**:
  - From dyn-allowlist-variable-injection-output.txt: Restore the explicit `case "$_key" in …)` allowlist (matching the stdout-fallback block) before every `printf -v` at `221-224`, and harden `phase_driver_read_result_env` to refuse or strip values containing `\n`/`\r` (mirroring `emit_kv` in `scripts/lib-quiet.sh:166-172`) so the line-oriented KV protocol cannot be broken by multiline spill.
  - From dyn-allowlist-variable-injection-output.txt: Before emitting, reject lines whose value contains newline/carriage return (return failure or skip the line with `larch_err`), or emit via an encoding that cannot spill (e.g. base64) and decode only after allowlist confirmation; add a harness case in `test-lib-phase-driver.sh` for multiline rejection.
