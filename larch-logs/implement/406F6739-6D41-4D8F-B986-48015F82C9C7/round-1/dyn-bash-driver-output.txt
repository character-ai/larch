If `run-step3-review.sh` exits non-zero before `phase_driver_write_result_env` (e.g. HARD cursor `exit 1` at `skills/design/scripts/run-step3-review.sh:173-174`, argv/`fail` exit 2, or a failed atomic write), a **leftover** `.step3-review-result.env` from an earlier Step 3 entry (Gate C / Gate A re-run) can still be sourced and drive the post-loop matrix with stale `LOOP_STATUS` (e.g. prior `complete` while this pass never launched the panel). **Suggested fix:** At the start of `run-step3-review.sh`, remove or overwrite `.step3-review-result.env` (and on any non-zero exit before the final write, write a failure sentinel or unlink it). In `SKILL.md`, require `_plan_review_rc -eq 0` (and optionally a freshness marker) before sourcing; if the driver failed or the env is missing/symlink-refused, treat as `panel-failed` and do not trust a prior file.

- **correctness** `skills/design/SKILL.md:849-874` — Prose says “driver stdout KVs are fallback only,” but the fence never parses `_plan_review_out` into `LOOP_STATUS`, `TALLY_PLAN_REVIEW_STATUS`, etc. (unlike the removed inline block, which merged stdout after the inner result env).
