### In-Scope Findings

- **architecture** `skills/design/SKILL.md:849-868` — Step 3 wraps `run-step3-review.sh` in `_plan_review_out=$(…)` even though the driver calls `larch_quiet_init` and routes contract output (`emit` / `emit_kv`) to FD 3 (dup’d from the subprocess stdout at init). With command substitution that FD is the capture pipe, so cap warnings, normalization messages, and terminal `emit_kv` breadcrumbs land only in `_plan_review_out`, which the fence never prints or parses; orchestration relies solely on `.step3-review-result.env`. That breaks the documented “driver stdout KVs are fallback only” handoff and hides operator-facing prose that used to come from inline `printf` in a non-capturing fence. **Suggested fix:** Invoke the driver in the foreground without command substitution (keep `set +e` / `_plan_review_rc`), source `.step3-review-result.env` for state, and if fallback is still required, add an allowlisted KV parse of `_plan_review_out` when the result env is missing or a symlink.

- **architecture** `skills/design/SKILL.md:856-867` — When `.step3-review-result.env` is a symlink, the fence prints a warning and skips parsing, but unlike the removed inline Step 3 block it does not fall back to driver stdout (`_plan_review_out`). A symlinked result file therefore leaves `LOOP_STATUS` and related locals unset even though the driver may have emitted normalized KVs on FD 3 into the capture variable. **Suggested fix:** On symlink refusal, parse allowlisted keys from `${_plan_review_out}` (same key set as the file loop) before continuing the branch matrix, matching the prior `.step3-plan-review-result.env` “stdout fallback only” behavior.

- **architecture** `run-step3-review.sh:86-240` — Operator-facing warnings (`emit "**⚠ Step 3: …**"`, `emit '⏩ 3: plan review — cap reached; skipping'`, etc.) use `emit` after `larch_quiet_init`, so they go to the contract stream (FD 3), not `larch_err` on FD 4 as `scripts/lib-quiet.md` prescribes for user-visible diagnostics after quiet init. Together with the SKILL capture wrapper, those messages are easy to lose entirely; even without capture they mix markdown warnings into the KV stream. **Suggested fix:** Route human diagnostics through `larch_err` (or `printf` before `larch_quiet_init` for the few early paths), reserve `emit`/`emit_kv` for machine keys, and align `run-step3-review.md` with that split.

- **architecture** `run-step3-review.sh:219-231` — Inner `plan-review-loop.sh` `WARN=` lines are re-published with `emit_kv WARN` (FD 3). The old SKILL orchestrator printed `WARN=…` to ordinary stdout for the agent; the new fence never reads WARN from `.step3-review-result.env` or from `_plan_review_out`, so symlink/cleanup/tally warnings from the panel path can disappear from the Step 3 chat surface. **Suggested fix:** Either forward WARN lines with `larch_err`, persist them in `.step3-review-result.env` under an allowlisted key the orchestrator echoes, or restore orchestrator-side parsing of `WARN` from driver stdout when not using command substitution.

- **architecture** `skills/design/scripts/plan-review-loop.sh:757-766` — Collector stderr handling changed from live `2> >(tee -a "$_collect_err" >&${_collect_stderr_fd})` to buffering in `plan-review-collector.stderr` and a post-run `cat … >&${_collect_stderr_fd}`. Diagnostics still target FD 4 when `LARCH_QUIET_PID=$$`, but nothing reaches operator stderr until collection finishes, which weakens the quiet-io contract for long-running collects (`lib-quiet.md` expects progress via `larch_err` on FD 4 during long work). **Suggested fix:** Document the deferred flush in `plan-review-loop.md`, or stream stderr with a S041-safe path (e.g., line-at-a-time `larch_err` while appending to `plan-review-collector.stderr`) if live visibility is still required.
