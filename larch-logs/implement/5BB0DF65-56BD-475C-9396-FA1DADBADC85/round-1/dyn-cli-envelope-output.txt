Reviewing the branch diff and commit history, focusing on spawned Claude CLI JSON envelope handling and downstream risk.
### In-Scope Findings

- **risk-integration** `scripts/launch-claude-subprocess.sh:255-277` — On exit 0, if the CLI returns a valid JSON envelope but `.result` is empty or extraction fails, the launcher leaves the raw JSON in `${OUTPUT_FILE}` yet still emits `STATUS=OK` / exit 0. The fail-loud guard only catches zero-byte output, so a non-empty JSON wrapper no longer trips it. Review/voter/scout collectors expect prose or structured findings, not the CLI envelope; a slot can look successful while its artifact is unparsable. **Suggested fix:** Mirror the Cursor path in `scripts/launch-review.sh` (~1211–1216): when `(.result // "") == ""` after parse, write a dedicated sentinel (e.g. `CLAUDE_EMPTY_RESPONSE`) plus a `.diag` sidecar, set non-OK status / non-zero exit, and only promote prose when extraction succeeds.

- **risk-integration** `scripts/launch-claude-subprocess.sh:261-267` — `record-vendor claude_sub` runs whenever `.usage` parses, even if `.result` was not installed over `${OUTPUT_FILE}`. Cost is attributed while the collector-facing file may still be raw JSON, so token spend and operational outcome diverge. **Suggested fix:** Gate ledger writes on successful `.result` promotion (non-empty extract written to `${OUTPUT_FILE}`), matching the “collectors keep seeing prose” comment in the same block.

- **risk-integration** `scripts/launch-claude-ci.sh:243-245` — The legacy word-count `.token-record` fallback runs whenever `CL_TOTAL==0` and `$OUTPUT` is non-empty, without requiring `LAUNCHER_EXIT==0` or successful prose extraction. After `--output-format json`, a failed `.result` extraction leaves the JSON envelope in `$OUTPUT`; `wc -w` counts JSON syntax as “tokens” and writes a misleading `${OUTPUT}.token-record` (`RAW=claude_ci_fix`) that `ship-pr.sh` forwards via `append-token-record.sh`. **Suggested fix:** Restrict the fallback to `LAUNCHER_EXIT==0` with confirmed non-JSON prose (or skip when `jq -e . "$OUTPUT"` succeeds), and never word-count a failed JSON envelope.

- **risk-integration** `scripts/launch-claude-ci.sh:198-212` — Usage is parsed from the JSON sidecar even when `.result` extraction fails (lines 202–205), so `CL_TOTAL` can be >0 while `$OUTPUT` still holds raw JSON. The launcher then records accurate `claude_sub` ledger rows but CI-fix consumers reading `$OUTPUT` get the envelope, not the fix summary. **Suggested fix:** Only set `CL_*` / `CL_TOTAL` and call `record-vendor` after `.result` is successfully promoted into `$OUTPUT`; otherwise leave counts at zero and rely on stderr-based failure classification.

- **risk-integration** `scripts/launch-claude-subprocess.sh:249-277` — Neither launcher inspects `is_error` or `subtype` in the Claude JSON envelope (the Cursor reviewer path checks empty `.result` and emits diagnostics). A subprocess can exit 0 with `is_error:true` or an empty `result` while still carrying billable `.usage`; the launcher treats that as success. **Suggested fix:** After `jq -e .` validation, fail closed (or emit sentinel + non-OK status) when `.is_error == true` or `(.result // "") == ""`, optionally recording usage only if billing-on-error is an explicit product choice.

### Out-of-Scope Observations

- `scripts/launch-claude-ci.sh:254` always `exit 0` regardless of `LAUNCHER_EXIT`; that predates this branch but still means ship-pr must parse `LAUNCHER_EXIT=` from stdout rather than the process exit code.

- The mandatory no-double-count regression in `scripts/test-token-report.sh` (~548+) and the `claude_sub` vendor naming look correctly wired; no collision with the transcript-derived `claude` lane was found in the diff.

- Cache 5m/1h collapse into a single `cache_create` bucket is documented as an accepted v1 trade-off in the plan; not a new regression from this branch.
