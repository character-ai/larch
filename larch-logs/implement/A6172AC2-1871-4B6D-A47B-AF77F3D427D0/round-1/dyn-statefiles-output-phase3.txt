### In-Scope Findings

- **correctness** `python/ship.py:774-783` — `_first_present` short-circuits on any `int`, including `0`, returning `"0"` for a zero-valued `ctx.pr_number` or (theoretically) a zero-valued `result.pr_number`. `"0"` is truthy in Python, so `_fill_if_empty` writes `PR_NUMBER=0` to `finalize-state.sh` when it should have been treated as absent. The fill order intended by the plan is `ShipResult → state_file → ctx`, and `ctx.pr_number=0` (set by `_env_int` when `PR_NUMBER=0` is in the environment) correctly sits in position 3 — but if the first two slots are also empty/None, `_first_present(None, None, 0)` returns `"0"` and writes a non-existent PR number. More critically, if `result.pr_number=0` were ever set (the type admits it; no current call does, but nothing prevents a future caller), `_first_present(0, "44", ...)` would return `"0"` and silently block the canonical `state.get("PR_NUMBER")="44"`, violating the plan's "never let stale pre-run ctx block canonical state-file values" invariant. **Suggested fix:** Treat integer `0` as absent inside `_first_present`: change `if isinstance(value, int): return str(value)` to `if isinstance(value, int) and value != 0: return str(value)` (so `0` falls through the same as `None`). The test `test_persist_stall_metadata_uses_state_file_before_ctx` in `python/test_ship.py` only exercises `pr_number=None` and would not catch the `pr_number=0` case.

- **correctness** `python/finalize.py:333-337` — `read_finalize_state` applies `shlex.split` per line and then falls back to the raw right-hand-side text when the split produces more than one token (`data[key] = parsed[0] if len(parsed) == 1 else value`). The `value` here is the raw string after the first `=` character — i.e., unstripped. For a line like `PR_TITLE=Implement feature X`, `shlex.split("Implement feature X")` gives `["Implement", "feature", "X"]` (3 tokens), so the fallback stores `"Implement feature X"`. This roundtrips correctly when Python reads it back. However, `write_finalize_state_merged` writes this value back as `PR_TITLE=Implement feature X` — without shell quoting — which is invalid bash syntax. When `restore-finalize-state.sh` or `stall-recovery-report.sh` sources the file, only `PR_TITLE=Implement` is set and `feature` and `X` are interpreted as commands. This is a semantic defect in values containing spaces (PR titles, free-text stall steps). Note: the pre-existing `write_finalize_state` has the same unquoted-write pattern; this diff propagates it into the new merge writer. **Suggested fix:** Quote values that contain whitespace or special shell characters when writing. A minimal fix is `shlex.quote(value)` or a single-quote wrapper in `write_finalize_state_merged`: `f"{key}={shlex.quote(data[key])}\n"` (matching the `shlex.split`-based reader, which already handles quoted values). Apply the same fix to `write_finalize_state` for consistency.

### Out-of-Scope Observations

- **correctness** `python/finalize.py:338-341` — The post-parse newline check in `read_finalize_state` (`if "\n" in value or "\r" in value: raise ShipError`) is a dead code path for files read from disk: `splitlines()` strips every newline before parsing, so no value can contain one after splitting. The check is purely defensive for hypothetical in-memory use, but in practice raises a `ShipError` that propagates out of `_persist_stall_metadata_if_needed`'s `except (OSError, ShipError)` guard, suppressing the gap-fill with a warning breadcrumb rather than writing partial stall metadata. This pre-dates the diff; the diff does not worsen it.
