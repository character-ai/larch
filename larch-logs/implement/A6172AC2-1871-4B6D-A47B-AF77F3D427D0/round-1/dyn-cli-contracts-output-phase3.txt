### In-Scope Findings

- **risk-integration** `python/ship.py:863-889` — `emit_result(ctx, result)` on line 875 (argparse failure path) is nested inside the outer `try/except Exception as exc` envelope (lines 866–886). If `emit_result` raises after `print` has already flushed JSON to the contract stream — for example, `BrokenPipeError` from `stream.flush()` (line 719) when the caller closes the read end of the stdout pipe before `flush()` completes — the outer `except Exception` handler on line 882 catches the exception, sets a fresh `result = ShipResult(Outcome.INTERNAL_ERROR, ...)`, and falls through to the second `emit_result` call on line 888. The second call opens a new dup of fd 3 (via `contract_stream()`) and emits a second JSON line. Any caller parsing stdout as a single JSON document (e.g., `jq .`, `json.loads(output)`, or the orchestrator's `ship_json=$(...)` capture) receives two JSON objects and fails to parse. This regression is introduced by this diff's restructuring of `main()` — the original code placed argparse outside the outer try, so argparse-path emit failures could not feed the outer handler. **Suggested fix:** Wrap the argparse-failure `emit_result` call in its own `try/except Exception` that suppresses any re-throw (e.g., `try: emit_result(ctx, result)\nexcept Exception: pass`), or hoist the argparse `SystemExit` handler to a helper that runs before the outer `try` block so its `emit_result` call is never inside the `except Exception` envelope.

- **risk-integration** `python/ship.py:774-783` — `_first_present` (used by `_persist_stall_metadata_if_needed`) treats integer `0` as a valid non-empty value and returns `"0"`. For the `PR_NUMBER` slot (line 814), if `result.pr_number` is `None` but `ctx.pr_number` is `0` (set when `PR_NUMBER=0` is in the environment and parsed by `_env_int`), `_fill_if_empty` writes `PR_NUMBER=0` to `finalize-state.sh`. The orchestrator reading `PR_NUMBER=0` will interpret it as a valid (if non-existent) PR number rather than "no PR created", potentially confusing Step 18 recovery dispatch. The same applies to `ctx.pr_number=0` passed from env. **Suggested fix:** Add a zero-exclusion guard in `_first_present` for integers: `if isinstance(value, int) and value != 0: return str(value)`, or filter in `_fill_if_empty` before writing, so `0` is treated the same as `None` for PR_NUMBER gap-fill.
