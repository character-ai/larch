### In-Scope Findings

- **risk-integration** `python/ship.py:709-721` — `_close_contract_stream` is called in a `finally` block inside `emit_result`, but it has no exception suppression. If the dup'd-fd `TextIOWrapper.close()` raises (`BrokenPipeError`, `OSError`) — which it can, because Python's `TextIOWrapper.close()` calls an internal `flush()` that propagates `BrokenPipeError` — the exception escapes `emit_result`. `emit_result` is called at line 888 **outside** `main()`'s outer `try/except`, so the exception propagates to `__main__` and exits with a non-contract traceback and an undefined exit code, even though the JSON may have already been written. **Suggested fix:** Wrap `stream.close()` in `_close_contract_stream` with `with suppress(Exception): stream.close()`, or add `except Exception: pass` around the close call. A `finally`-block close must never propagate.

- **risk-integration** `python/ship.py:866-886` — The argparse `except SystemExit` path calls `emit_result(ctx, result)` at line 875 **inside** the outer `try` (lines 866–886). If that `emit_result` call raises for any reason (including the close-propagation described above), the outer `except Exception` at line 882 catches it, overwrites `result` with a new `INTERNAL_ERROR`, and then `emit_result` is called **again** at line 888 outside the try. This produces two JSON lines on the contract stream. The orchestrator, which expects exactly one JSON line, will fail to parse the second line or pick up the first as the result. **Suggested fix:** Either wrap the argparse-path `emit_result` call in its own `try/except` that returns after a best-effort emit, or restructure `main()` so that only one `emit_result` site exists (normalize the argparse result into `result` and let the unified bottom-of-function emit handle it).

- **risk-integration** `python/logging_util.py:67-83` — `quiet_init`'s failure-handling (`except OSError`) clears env vars and resets `_self_initialized_quiet`, but **does not restore fds 3 and 4** to their prior values after `os.dup2(1, 3)` and `os.dup2(2, 4)` have already succeeded. If the failure occurs after those two dup2s (e.g., `os.open(path, ...)` raises), fds 3 and 4 are left permanently overwritten — fd 3 now points to whatever fd 1 was at entry (typically the parent's quiet log when bash has already initialized quiet), and fd 4 likewise. Any child process spawned after this failed `quiet_init` inherits clobbered fds 3/4. More critically, in the bash-quiet-invocation scenario where the parent set fd 3 = orchestrator pipe, a partially-failed `quiet_init` destroys that mapping; if ship.py were then to call `quiet_init` successfully on retry or if any code assumes fd 3 is the orchestrator pipe, contract JSON is misrouted. **Suggested fix:** Before the dup2 calls, save the current fd 3 and fd 4 values (`saved3 = os.dup(3)` with a guard that fd 3 is open), and restore them in the except handler: `os.dup2(saved3, 3); os.dup2(saved4, 4); os.close(saved3); os.close(saved4)`. If saving fails (fd 3/4 not currently open), skip restore.

### Out-of-Scope Observations

- **risk-integration** `python/logging_util.py:90-97` — `contract_stream()` performs `os.dup(3)` each call and wraps it in a `TextIO` with `closefd=True`. The caller is responsible for closing the returned stream; `emit_result` does this correctly via `_close_contract_stream`. However, if `contract_stream()` is called anywhere else without a corresponding close (e.g., future callers in tests), each unclosed call leaks one fd. A context-manager wrapper around the returned stream would make ownership explicit and prevent future leaks, but this is a design nit rather than a current bug.
