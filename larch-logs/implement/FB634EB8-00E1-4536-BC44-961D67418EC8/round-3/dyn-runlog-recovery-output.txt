Reviewing manifest recovery and fail-closed run-log paths on this branch vs main.
### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:949-951` — After a CI-fix rebase, `stage_and_push` calls `run_logs.flush_logs_pre` inside `suppress(OSError, ShipError)`, so a `RefreshSkip` with `reason=manifest-recovery-failed` is ignored with no breadcrumb or execution-issues entry while the path still force-pushes. That weakens the new fail-closed recovery gate on a high-risk push path and can leave run logs unrefreshed without operator-visible signal. **Suggested fix:** Inspect the `RefreshSkip` return (same pattern as `ship.py` postbump refresh at `498-500`); on `REFRESH_SKIP_RECOVERY_FAILED`, emit a warning breadcrumb and optionally append to `execution-issues.md`, then continue or stall per bash `refresh-run-logs.sh || true` semantics.

- **risk-integration** `python/ship.py:632-642` — Pre-rebase `flush_logs_pre` explicitly does not stall when `reason == REFRESH_SKIP_RECOVERY_FAILED`, but unlike the postbump path (`498-500`) it logs no warning when recovery fails. The merge loop can proceed to `rebase_and_push` with a failed manifest recovery and no audit trail, which is inconsistent with the warning-only contract used elsewhere on the ship path. **Suggested fix:** When `pre_rebase.skipped` and `pre_rebase.reason == run_logs.REFRESH_SKIP_RECOVERY_FAILED`, call `_breadcrumb("warning", ...)` (and/or record a Warnings execution issue) before continuing, matching postbump refresh behavior.

- **risk-integration** `python/run_logs.py:626-630` — `flush_logs_pre` gates on `recovery_ok` at the top, but later calls `update_manifest`, which re-checks recovery and raises `ShipError` on failure; `_write_manifest` can also raise `OSError`. Neither is converted to `RefreshSkip`, so callers that only handle `RefreshSkip.skipped` (e.g. `ship.py:498-500`, `632-642`) can abort the ship driver instead of degrading warning-only. **Suggested fix:** Wrap the `update_manifest` / commit tail in `flush_logs_pre` with try/except for `ShipError` and `OSError`, mapping failures to `RefreshSkip(skipped=True, reason=REFRESH_SKIP_RECOVERY_FAILED)` or `REFRESH_SKIP_COMMIT_FAILED` as appropriate.

- **risk-integration** `python/ship.py:438-449` — The branch removes the `pr_closed=ctx.pr_closed or post.outcome is Outcome.OK` flush bug (good), but `python/test_ship.py` has no test that `run_postmerge_phase` skips `finalize_postmerge_logs` when `pr_closed=False` (draft/merge-false/bail) and does not write `post-merge-sentinel` in those cases. That was called out in the plan acceptance criteria; without it, the regression fix is unguarded. **Suggested fix:** Add tests that monkeypatch `finalize_postmerge_logs` and assert it is not called when `ctx.pr_closed=False` for skipped-OK postmerge outcomes, plus a positive test when `pr_closed=True` and merge succeeded.

### Out-of-Scope Observations

- **risk-integration** `python/merge.py:170-174` — `_post_flush` maps any skipped post-flush (including `manifest-recovery-failed`) to `MERGE_RESULT_ERROR`. That is intentional for `merge_pr(..., post_flush=True)` and covered by `test_merge_post_flush_manifest_recovery_failed_emits_error`; production `ship.py` uses `post_flush=False` and delegates post-merge logging to `run_postmerge_phase` with warning-only skips.

- **correctness** `python/run_logs.py:679-691` — `flush_logs_post` writes `status=done` before `_write_final_report`; a report/redaction failure leaves a done manifest with a skipped flush. This matches bash `ship-pr.sh:3146-3173` (manifest write before report, report failure warning-only), so it is parity, not a new divergence.
