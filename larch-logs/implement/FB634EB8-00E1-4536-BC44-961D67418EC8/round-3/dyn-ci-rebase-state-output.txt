### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:1227-1250` — On a resumed run with `ci_fix_rebase_pending=true`, `evaluate_failure` jumps straight into the pending fast path and passes `last_classified or ClassifiedJobs(0, (), (), ())`. After a process restart `last_classified` is always `None`, so `stage_and_push` skips the post-rebase local verify block (`classified.fixable` is empty) and can force-push without re-running failed-job checks. Bash still runs `_run_post_rebase_verify_gates` on pending retries (using the phase TSV or at least `run_checks_with_lint_fix_loop`). **Suggested fix:** Before the pending `run_ci_fix` call, reload and classify failed jobs from `run_id` (or read the persisted phase TSV from `IMPLEMENT_TMPDIR`, matching bash’s `_resolve_effective_failed_jobs_tsv`) and pass that `classified` into `stage_and_push`; add a restart test that asserts verify runs before any `--force-with-lease` push.

- **risk-integration** `python/ci_monitor.py:1493-1498`, `python/ship.py:657-658` — When a verified rebase fix fails force-push but should stay pending, `monitor` returns `Outcome.OK` with `did_fixing=True`. `run_ship` then increments `fix_attempts` on every failed pending-push cycle. Bash only bumps `FIX_ATTEMPTS` after a successful `_stage_and_push_ci_fixes` (`stage_rc=0`). After enough lease/transient push failures, Python can hit `fix-attempts-exhausted` and bail while bash would keep retrying. **Suggested fix:** Treat pending push-only retries as non-counting: return `did_fixing=False` for the `waterfall-failed` + `ci_fix_rebase_pending` branch, or increment `fix_attempts` only when `fix.status == "pushed"`.

- **risk-integration** `python/ci_monitor.py:940-955`, `python/ci_monitor.py:968` — If `origin/<branch>` cannot be resolved after fetch, `stage_and_push` returns `pending=True` without a successful verify+push attempt. That re-persists `CI_FIX_REBASE_PENDING` and the ship loop keeps retrying the same failing path (until `fix_attempts` exhausts via the bug above). Bash only sets pending after verify passes and `git-force-push.sh` fails. **Suggested fix:** Return `pending=False` (and surface a stall/error) when `expected_remote_oid` is missing or remote-check fails; only set `pending=True` after verify succeeded and the force-push attempt itself failed.

### Out-of-Scope Observations

- **risk-integration** `python/README.md:79-81` — Still documents `CI_FIX_REBASE_PENDING` as deliberately omitted (#3405), but this branch implements the full pending-rebase lifecycle. Stale doc can mislead operators about force-push/retry behavior during Phase 7 parity work.

- **code-quality** `python/ship.py:396-398`, `python/test_ship.py:670-717` — `CI_FIX_REBASE_PENDING_HEAD` is serialized but never read on hydration/resume, and `test_ci_fix_rebase_pending_survives_head_mismatch` only checks that the pending flag reaches the first monitor call, not any HEAD mismatch guard. Harmless vs bash (bash has no such key), but the test name overstates coverage.
