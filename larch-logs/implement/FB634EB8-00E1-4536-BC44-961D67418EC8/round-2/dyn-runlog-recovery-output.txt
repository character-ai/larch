Reviewing the branch diff and commit history for runlog-recovery and risk-integration issues.
### In-Scope Findings

- **risk-integration** `python/finalize.py:468-496` — Teardown log recovery still keys off `ctx.run_id` for the early bail-out and for the execution-issues safety-net `run_dir`, while manifest recovery/commit paths use `run_logs.effective_run_id(ctx)` (state-file `RUN_ID` wins). When `ctx.run_id` is empty or stale but `state_file` carries the authoritative `RUN_ID`, teardown can skip the whole flush path or append safety-net records under the wrong `larch-logs/implement/<id>/` tree while manifest recovery targets a different directory. **Suggested fix:** Gate teardown on `effective_run_id(ctx)` and build `run_dir` from that same helper everywhere in `_teardown_log_flush`, matching bash `read_state RUN_ID` and the postmerge flush fix in `ship._postmerge_should_flush`.

- **risk-integration** `python/run_logs.py:651-694` — `flush_logs_post` / `finalize_postmerge_logs` render `write-final-report.sh`, ledger reports, and token/timing batches before writing `status=done` and `pr_number` to `manifest.json`. Bash `ship-pr.sh` `run_postmerge_phase` does the opposite: it writes `status=done`/`pr_number` first and only calls `write-final-report.sh` when that manifest update succeeds (`manifest_ok=true`). On manifest write failure after report rendering, Python can leave `summary-final.md` / `final-summary.md` showing a merged outcome while `manifest.json` stays `partial`, breaking the coherent recovery → done-manifest → report contract the plan describes. **Suggested fix:** Reorder `flush_logs_post` to match bash: recover → write `status=done`/`pr_number` → render final report and auxiliary batches only if the manifest update succeeds; skip report rendering when recovery or manifest write fails.

- **risk-integration** `python/ship.py:437-441` — Post-merge sentinel creation is deferred until `finalize.postmerge` returns `Outcome.OK`, whereas bash writes `post-merge-sentinel` immediately on terminal merge success (`ship-pr.sh:2998-3003`) before `run_postmerge_phase`. After a successful merge, a postmerge stall or crash before the Python sentinel write leaves teardown’s best-effort `larch-log.sh commit` unblocked (no sentinel, and the branch gate in `_teardown_log_flush` may still pass on a feature branch), while bash would refuse that commit. That diverges from the NEVER #16 post-merge commit guard semantics bash enforces today. **Suggested fix:** Write the post-merge sentinel when `ctx.pr_closed` becomes true after a terminal merge result (mirroring bash merge-success sites), independent of postmerge cleanup outcome; keep postmerge log finalization warning-only on partial cleanup as planned.

- **risk-integration** `python/run_logs.py:368-379` — When the run directory is entirely absent, recovery synthesizes a bare partial manifest via `_write_manifest` instead of invoking the bash-equivalent `larch-log.sh init` path used in `ship-pr.sh:3114-3138` / `implement-finalize.sh:980-997`. The synthesized file omits `schema_version`, `issue_number`, and other init-time fields that committed-run-log validators expect, so recovery can appear `recovery_ok=true` while producing a manifest shape incompatible with the bash reference tree. **Suggested fix:** Route absent-run-dir recovery through the same init semantics as bash (shell `larch-log.sh init` wrapper or a Python helper that emits schema v2 init fields, including `issue_number` when available), then tag `status=partial` and `recovery_reason=manifest_lost_mid_run`.

- **risk-integration** `python/run_logs.py:669-670` — Postmerge finalization stores `pr_number` inside `steps_ran` as an integer. Bash `larch-log.sh manifest` restricts `steps_ran.*` values to `true`/`false` and stores `pr_number` as a top-level manifest field. Python also mirrors `pr_number` into `extra`, but the `steps_ran` copy violates the bash manifest contract and can confuse validators or jq probes that assume boolean step flags only. **Suggested fix:** Drop the `steps["pr_number"]` assignment; persist `pr_number` only as a top-level manifest field (via `extra` or a dedicated manifest field), matching bash `--field "pr_number=$pr_num"`.

### Out-of-Scope Observations

- **risk-integration** `python/finalize.py:487-489` — Teardown’s pre-commit branch gate checks only literal `main`/`master`, while `larch-log.sh` `current_branch_is_default()` also treats `origin/HEAD`’s default branch (e.g. `develop`) as refused. This predates the broader parity work but remains a latent default-branch refusal gap for non-`main` defaults.
