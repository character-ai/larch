Reviewing the branch diff against the bash reference scripts for architectural parity.
### In-Scope Findings

- **architecture** `python/finalize.py:545-595` — `teardown()` never ports `kill_session_background_processes()` from `scripts/implement-finalize.sh:853-885`, so a Python-driven Step 18 can leave Codex/Cursor/CI helper processes bound to `$IMPLEMENT_TMPDIR` alive after finalize completes. Bash always SIGTERM/SIGKILLs those PIDs before tmpdir cleanup; omitting that step breaks the full finalize lifecycle contract the branch claims to mirror. **Suggested fix:** Add a small Python helper (or subprocess wrapper) that reproduces the bash awk/`ps` scan and kill loop, invoke it from `teardown()` after the larch-log flush block and before the stall/cleanup branch, and cover it with a unit test using stubbed process lists.

- **architecture** `python/finalize.py:492-542` — `_teardown_log_flush()` sets `recovery_ok=False` when the best-effort larch-log **commit** fails, and that flag gates the stall-only `stalled_at_step` manifest write at `python/finalize.py:516-524`. Bash only clears `larch_recovery_ok` on manifest **init/recovery** failure (`scripts/implement-finalize.sh:975-1012`) and still writes `stalled_at_step` after a commit warning. On a stalled run with recovery success but commit failure, Python drops operator recovery metadata bash preserves. **Suggested fix:** Decouple commit failure from `recovery_ok`; keep `recovery_ok` for init/recovery paths only, log commit failure as warning-only, and still call `update_manifest(..., stalled_at_step=...)` when `ctx.stall_tracking` and recovery succeeded.

- **architecture** `python/finalize.py:395-430` — `_rename_issue()` refuses any rename when `gh issue view` reports a non-`OPEN` state, but bash Branch B (`scripts/implement-finalize.sh:925-931`) calls `rename_issue` to `[DONE]` without an OPEN precondition (Branch A alone checks OPEN at `scripts/implement-finalize.sh:918-924`). Successful-merge teardown can therefore skip the done-rename in Python while bash still attempts it, diverging tracking-issue lifecycle semantics. **Suggested fix:** Split rename helpers: keep the OPEN gate for Branch A (`stalled`), and use a Branch-B path that mirrors bash by calling `tracking_issue.rename` regardless of issue state (still handling rename failure as `failed`).

- **correctness** `python/finalize.py:376-384` — `postmerge()` verify-main logic requires a truthy `expected_title` before evaluating either prefix or suffix match, so when `ctx.pr_title` is empty but `ctx.pr_number` is set, Python always emits `verify_main_status=unexpected` even if HEAD ends with `(#N)`. Bash always builds `"$pr_title (#$pr_number)"` and `scripts/verify-main.sh:82-90` can still verify via the `(#N)` suffix fallback for admin-merge subjects. **Suggested fix:** Match bash matching order explicitly: compute `full_expected = f"{pr_title or ''} (#{pr_number})"` when `pr_number` is set, then set `title_ok = actual.startswith(full_expected) or (suffix and actual.endswith(suffix))` without short-circuiting on an empty title.

- **architecture** `python/test_finalize_bash_parity.py:1-188` — The rewritten parity module only subprocess-compares draft skip and postbump branch-mismatch; it does not side-by-side exercise the high-value decisions called out in the plan (`_local_cleanup` partial/success + fetch-non-fatal, verify-main prefix/suffix, postbump force-push outcomes, teardown rename A/B/C). The fail-closed gate in `python/test_finalize_bash_parity_gate.py` only proves tests are collected, not that those branches stay aligned with bash. **Suggested fix:** Extend `test_finalize_bash_parity.py` with sandboxed `implement-finalize.sh` invocations (stubbing `git`/`gh` like `test_merge_bash_parity.py`) for cleanup partial, verify-main admin suffix, postbump remote-check/force-push KVs, and teardown rename branches so architectural drift fails `make py-test`.
