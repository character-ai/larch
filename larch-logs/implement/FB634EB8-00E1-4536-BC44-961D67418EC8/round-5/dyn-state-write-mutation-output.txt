Reviewing state-write and CI_FIX_REBASE_PENDING lifecycle in the diff and key files.
### In-Scope Findings

- **correctness** `python/ship.py:366-408` — `_write_ship_state` now read-modifies-writes the existing `ship-pr-state.sh` and only overwrites its fixed key set; keys such as `STALL_TRACKING`, `STALL_STEP`, `BAIL_REASON`, `EXIT_CODE`, and `CI_PASSED` are never taken from `RunContext` and are not cleared on successful merge/postmerge transitions (unlike bash `clear_stall_keys_for_postmerge` / post-merge `state_set_many … STALL_TRACKING false` in `scripts/ship-pr.sh:807-808,2999`). A prior stalled or bailed run can therefore leave `STALL_TRACKING=true` or a non-empty `BAIL_REASON` in the file while Python writes `PHASE=done`, which is misleading for any resume/orchestrator logic that reads those KVs. **Suggested fix:** On each write, either replace the file with an explicit allowlist (restoring pre-branch fail-closed semantics) or mirror bash lifecycle clears by zeroing ephemeral stall/bail keys on merge/postmerge success and syncing `STALL_TRACKING`/`STALL_STEP` from `ctx` when present.

- **correctness** `python/ci_monitor.py:943-982` — `CI_FIX_REBASE_PENDING` persistence is broader than bash: `pending = (did_rebase or ci_fix_rebase_pending) and not pushed` sets pending on any failed force-push after a rebase/pending path, whereas bash only calls `_ci_fix_pending_set` when `verify_passed=true` (`scripts/ship-pr.sh:1708-1710`). When `classified.fixable` is empty, Python skips local verify and can still persist `CI_FIX_REBASE_PENDING=true` on push failure; bash may return before push if post-rebase checks fail (`_run_post_rebase_verify_gates`, `scripts/ship-pr.sh:1566-1584`). That can write a pending flag and enter the monitor retry loop when bash would not. **Suggested fix:** Track a `verify_passed` boolean through `stage_and_push` (including the checks-only path for empty fixable sets) and set `pending` only when `verify_passed and not pushed`, matching bash.

- **correctness** `python/run_context.py:27-38` — `_state_bool` returns the **first** `key=` line, but `_write_ship_state` loads state with **last** duplicate key wins (`python/ship.py:368-374`). A corrupted or hand-edited state file with duplicate `CI_FIX_REBASE_PENDING=` lines can hydrate `RunContext` differently from what the next state write emits, so resume can clear or set pending incorrectly relative to the on-disk tail value. **Suggested fix:** Use one rule everywhere (prefer last-wins, as bash `read_state` effectively does via `state_set`), or reject/normalize duplicate keys when reading.

- **correctness** `python/ship.py:478-550` — Pre-merge-loop `_write_ship_state` calls (`phase="checks"`, `"pr-prep"`, `"pr-create"`, `"ci-initial"`) pass default `rebase_count=0`, `fix_attempts=0`, `iteration=0`, and `transient_retries=0`, resetting those counters in the state file even when `CI_FIX_REBASE_PENDING` was hydrated true from a mid-run resume file. In-memory loop counters also start at zero (`python/ship.py:558-561`) and are not reloaded from state, so a resumed process can under-count attempts relative to the prior session while still carrying `CI_FIX_REBASE_PENDING=true`. **Suggested fix:** Hydrate loop counters from state in `RunContext.from_env` (or at `run_ship` entry) and pass them through every `_write_ship_state` call, matching bash `read_state` usage in the CI loop.
