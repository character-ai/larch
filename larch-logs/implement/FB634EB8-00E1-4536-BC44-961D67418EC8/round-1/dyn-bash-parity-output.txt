Reviewing the branch diff and key implementation files for bash-parity correctness.
### In-Scope Findings

- **correctness** `python/run_logs.py:648-688` — `finalize_postmerge_logs` documents recovery → `status=done` → report, but `flush_logs_post` still calls `_write_final_report` / ledger rendering before updating the manifest to `done` and `pr_number`. Bash `scripts/ship-pr.sh:3146-3173` writes `larch-log.sh manifest --field status=done` first and only re-renders `write-final-report.sh` when that succeeds. On a failed merge-result path or a partial manifest, Python can emit a final summary that does not match the post-merge manifest state bash would produce. **Suggested fix:** Reorder `flush_logs_post` to match bash: after `recovery_ok`, write `status=done` / `pr_number` to the manifest, then call `_write_final_report` only when that write succeeds; skip the report path when manifest update fails (warning-only for `ship.run_postmerge_phase`).

- **correctness** `python/test_finalize_bash_parity.py:1-103` — The module was renamed as “bash-present parity” but still never runs `scripts/implement-finalize.sh` (no `subprocess` calls; only Python `finalize.*` with mocks). That is unlike `python/test_merge_bash_parity.py`, which actually invokes bash. Status-token drift in `finalize.py` will not be caught until runtime. **Suggested fix:** Add side-by-side subprocess fixtures (stub `git`/`gh`, state file, KV parse) per the plan, modeled on `test_merge_bash_parity.py`, and assert Python `FinalizeResult` fields against bash `STATUS` / auxiliary KVs.

- **correctness** `python/ci_monitor.py:1020-1053`, `python/ship.py:588-599` — When a CI fix rebases and `stage_and_push` force-push fails, `run_ci_fix` returns `waterfall-failed` with `ci_fix_rebase_pending=True`, `monitor` maps that to `Outcome.STALLED`, and `run_ship` exits the CI loop immediately. Bash keeps the monitor alive: `scripts/ship-pr.sh:1710-1719` sets `CI_FIX_REBASE_PENDING`, and `2231-2256` retries push-only `_stage_and_push_ci_fixes` inside `run_evaluate_failure` before stalling. Python persistence of `CI_FIX_REBASE_PENDING` in ship state never gets a retry turn. **Suggested fix:** Treat `waterfall-failed` + `ci_fix_rebase_pending` as a continuable monitor outcome (`Outcome.OK`, `did_fixing=True`) so `ship.py` increments the loop and re-enters with hydrated pending; mirror bash’s push-only retry path in `evaluate_failure` when `ci_fix_rebase_pending` is already true.

- **correctness** `python/finalize.py:82-95` — Postbump checkpoint corruption uses `POSTBUMP_CHECKPOINT_MAX_BYTES = 4096`, while bash `read_postbump_checkpoint` in `scripts/implement-finalize.sh:354-358` rejects checkpoints larger than 64 bytes. An oversized but well-formed checkpoint is `postbump-state-corrupt` in Python but cleared as a legacy token in bash. **Suggested fix:** Change the Python limit to 64 (and align symlink/malformed handling with `read_postbump_checkpoint` / the legacy-clear branch in `implement-finalize.sh`).

- **correctness** `python/ci_monitor.py:894-907` — Post-commit defer-rebase runs whenever `HEAD..origin/main` (via `base_remote`/`base_ref`) is behind, without bash’s guard that failed-jobs TSV must be known (`scripts/ship-pr.sh:1670-1675`). Python can rebase after a CI fix even when job classification is empty/unknown. **Suggested fix:** Port the “behind main but failed-jobs unknown; skipping defer-rebase” gate before setting `did_rebase`, using the same failed-jobs inputs `run_ci_fix` already has.

- **correctness** `python/ci_monitor.py:1139-1209` — Inside `evaluate_failure`’s outer retry loop, `ci_fix_rebase_pending` passed to `run_ci_fix` is never updated from a prior attempt’s `FixResult.ci_fix_rebase_pending`. A push failure that sets `pending=True` is dropped on the next inner attempt. **Suggested fix:** At the bottom of each loop iteration, set `ci_fix_rebase_pending = fix.ci_fix_rebase_pending` (or break/return early into the push-only path when pending is true).

- **correctness** `python/ship.py:680-688` — After `run_postmerge_phase`, `phase=done` is written only when `post.outcome is Outcome.OK`. Bash `run_postmerge_phase` always calls `advance_phase "done"` (`scripts/ship-pr.sh:3177`) after `implement-finalize.sh postmerge`, regardless of cleanup partials. A Python postmerge `Outcome.STALLED` (e.g. `branch-invalid`) leaves ship state at `postmerge`, which can block resume semantics bash does not have. **Suggested fix:** Align with bash: advance to `done` when merge completed and postmerge subprocess-equivalent finished, or write an explicit terminal stall phase derived from `post.status` instead of leaving `postmerge` stuck.

With the parity module still smoke-only, `make py-test` can stay green while offering little bash coupling protection.

That is an acceptance/test-gap risk rather than a proven runtime bug in the snippets reviewed.
