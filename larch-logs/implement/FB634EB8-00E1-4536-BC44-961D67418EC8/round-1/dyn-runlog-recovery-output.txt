Reviewing branch changes for run-log recovery and fail-closed semantics.
### In-Scope Findings

- **correctness** `python/ship.py:611-616` — CI-loop pre-rebase refresh calls `flush_logs_pre`, which now returns `RefreshSkip(skipped=True, reason="manifest-recovery-failed")` when `load_or_recover_manifest_checked` cannot persist recovery. That reason is not in `config.REFRESH_SKIP_MERGE_OK` (`python/config.py:202-211`), so the ship driver stalls the run (`Outcome.STALLED`, `"pre-rebase flush skipped: …"`). Bash runs `refresh-run-logs.sh` with `|| true` (`scripts/ship-pr.sh:2755-2757`) and continues into rebase. Postbump refresh in the same file correctly only warns (`python/ship.py:483-485`). A transient manifest-recovery/write failure therefore blocks the Python ship path mid-CI in a way bash does not. **Suggested fix:** Treat `REFRESH_SKIP_RECOVERY_FAILED` like other non-fatal refresh skips for pre-rebase (add it to `REFRESH_SKIP_MERGE_OK`, or log a warning and continue rebase, matching bash and the postbump branch).

- **correctness** `python/ship.py:330-336` — `_postmerge_should_flush` gates on `ctx.run_id`, while `finalize_postmerge_logs` / `flush_logs_post` resolve the run directory via `effective_run_id(ctx)`, which prefers `RUN_ID` from `ctx.state_file` (`python/run_logs.py:208-215`). `RunContext.from_env` does not hydrate `run_id` from the state file (`python/run_context.py:90-106`). A caller that sets `SHIP_PR_STATE_FILE` / `--state-file` with `RUN_ID=` but leaves `ctx.run_id` empty will skip post-merge finalize entirely, even though bash postmerge flushes when `read_state RUN_ID` is set (`scripts/ship-pr.sh:3105-3107`). That can leave `status=done`, final report, and `pr_number` unwritten after a successful merge. **Suggested fix:** Gate flush on `effective_run_id(ctx)` (and align PR/repo checks with state-file reads the same way bash does).

### Out-of-Scope Observations

- `python/run_logs.py:668-687` — Post-merge ordering still renders `write-final-report.sh` before writing `status=done` to `manifest.json`; bash writes `status=done` first (`scripts/ship-pr.sh:3148-3167`). This predates the branch; a failed manifest write after a successful report can leave summary and manifest out of sync.

- Acceptance criteria call for tests that `recovery_ok=false` skips `status=done`, report, and merge post-flush propagation (`python/test_run_logs.py`, `python/test_merge.py`, `python/test_ship.py`). Only the happy-path absent-run-dir recovery test was added (`python/test_run_logs.py:145-152`); there is no regression that blocks `flush_logs_post` / `finalize_postmerge_logs` from promoting to `done` when recovery fails.
