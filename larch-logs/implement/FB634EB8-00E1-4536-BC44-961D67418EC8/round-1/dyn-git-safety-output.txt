Reviewing the branch diff and git-operation paths for risk-integration issues.
### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:903-916` — CI-fix `stage_and_push` runs a raw `git rebase` when behind base but does not call `git rebase --abort` on non-zero exit. A conflict or in-progress rebase leaves the worktree in a rebase state; the function then sets `did_rebase=False` and falls through to a normal `git push`, which can fail unpredictably or mask the real problem instead of stalling cleanly. Postbump’s `_rebase_no_push` in `python/finalize.py:118-122` already aborts on failure; this path does not. **Suggested fix:** On any failed defer-rebase, always run `git rebase --abort` (only when a rebase is in progress), return `waterfall-failed`/STALLED without attempting a plain push, and set `ci_fix_rebase_pending` only after a successful rebase when a subsequent force-push fails—matching `scripts/ship-pr.sh`’s `run_rebase_rebump` + `_stage_and_push_ci_fixes` behavior.

- **risk-integration** `python/ci_monitor.py:903-907` — Defer-rebase is triggered whenever `behind_count > 0` after the CI-fix commit, without bash’s failed-jobs precondition (`scripts/ship-pr.sh:1670-1675`). Bash skips rebase when the effective failed-jobs TSV is empty/unknown and logs “behind main but failed-jobs unknown; skipping defer-rebase”; Python can still rebase and then force-push via `git.force_push_recovery`. That diverges from the shipped bash gate and can force-push in situations bash deliberately avoids. **Suggested fix:** Port the `_resolve_effective_failed_jobs_tsv` / non-empty TSV guard (or call the same helper logic) before setting `did_rebase`; use `ci-behind-count.sh` semantics for the behind probe, not only `rev-list`.

- **risk-integration** `python/ci_monitor.py:908-910` — After a successful CI-fix rebase, Python goes straight to `git.force_push_recovery` and never runs bash’s `_run_post_rebase_verify_gates` (`scripts/ship-pr.sh:1685-1693`), which re-runs checks/lint and may commit post-rebase deltas before push. The branch can force-push rebased CI-fix commits without that verification layer, increasing the chance of pushing a broken or incomplete fix tree. **Suggested fix:** Extract or invoke the same post-rebase verify + optional delta-commit sequence (or an equivalent Python port wired to `run_checks_with_lint_fix_loop`) between rebase success and force-push; align `ci_fix_rebase_pending` with bash so it is set on push failure only when verify passed.

- **risk-integration** `python/finalize.py:112-114` — `_rebase_no_push` calls `git rebase --abort` when fetch fails, even though no rebase was started in that function. If another step left the repo mid-rebase (e.g. a stuck CI-fix rebase), postbump can abort that unrelated operation before returning `rebase-failed`. **Suggested fix:** Abort only when `git rev-parse --git-path rebase-merge` or `rebase-apply` exists (same guard pattern as `rebase-push.sh`), otherwise return `failed` without touching rebase state.

### Out-of-Scope Observations

- **risk-integration (improvement vs pre-branch Python)** — Postbump no longer uses `rebase.rebase_and_push(..., allow_conflict_fix=True)`; conflicts now go through `_rebase_no_push` with explicit abort. That is stricter than the prior Python path, even though CI-fix defer-rebase still needs the abort/verify parity called out above.

- **correctness** — `python/test_ci_monitor.py:1238-1239` still documents “no `CI_FIX_REBASE_PENDING` retry” for push failure, but `stage_and_push` now sets `ci_fix_rebase_pending` when a rebase occurred and force-push fails (`python/ci_monitor.py:915`). The test still passes because it does not mock a behind-main rebase path; coverage for the new pending-retry semantics is thin relative to the production change.
