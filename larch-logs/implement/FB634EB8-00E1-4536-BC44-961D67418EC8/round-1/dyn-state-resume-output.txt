Tracing `CI_FIX_REBASE_PENDING` and resume-state plumbing across the branch diff and implementation.
### In-Scope Findings

- **architecture** `python/ci_monitor.py:1139-1209` — The new `ci_fix_rebase_pending` argument is passed into every `run_ci_fix()` call from a loop-local variable that is never updated from `fix.ci_fix_rebase_pending`. After a rebase/force-push failure sets `pending=True` on the `FixResult`, a continued outer attempt still calls `run_ci_fix(..., ci_fix_rebase_pending=False)`, so the deferred-push path in `stage_and_push` (lines 894–908) is skipped on retry and the run re-enters the full vendor waterfall instead of a push-only retry. **Suggested fix:** At the top of each `evaluate_failure` loop iteration, set `ci_fix_rebase_pending = fix.ci_fix_rebase_pending` when a prior `fix` exists, or thread `pending` through the loop explicitly; mirror bash `run_evaluate_failure` by branching on `CI_FIX_REBASE_PENDING` before log collection/vendor dispatch (`scripts/ship-pr.sh:2231-2256`).

- **architecture** `python/ci_monitor.py:1095-1224` — Bash’s `CI_FIX_REBASE_PENDING` contract is a dedicated push-only retry inside `run_evaluate_failure` (skip commit/vendor, call `_stage_and_push_ci_fixes`, backoff, increment `FIX_ATTEMPTS`, return 0 on success). This branch adds hydration, `MonitorResult.ci_fix_rebase_pending`, and ship-state serialization but does not implement that control-flow entry. On force-push failure the monitor returns `Outcome.STALLED` and `run_ship` exits (`python/ship.py:588-599`), so persisted `CI_FIX_REBASE_PENDING=true` is never consumed in-process—unlike bash, which retries inside the same evaluate-failure loop. **Suggested fix:** Add an `evaluate_failure` fast path when `ci_fix_rebase_pending` is true that calls a push-only helper (no delta commit, optional post-rebase verify gates), retries with backoff, and only then returns; align terminal outcomes with bash (success continues CI loop, repeated failure exhausts fix attempts).

- **architecture** `python/ci_monitor.py:879-880` — When `ci_fix_rebase_pending` is true, bash still runs `_stage_and_push_ci_fixes` with `pending_retry=true` and reaches force-push even with no new delta (`scripts/ship-pr.sh:1649-1706`). Python returns immediately on empty `delta_paths` without attempting `git.force_push_recovery`, so a hydrated pending retry cannot recover an already-committed fix. **Suggested fix:** If `ci_fix_rebase_pending`, skip the early return, resolve branch/HEAD, run verify gates if parity requires them, then force-push; only treat empty delta as fatal when not in pending-retry mode.

- **architecture** `python/ci_monitor.py:1212-1224` — Terminal `FixResult` constructions for `fix-exhausted` and outer-cap `waterfall-failed` omit `ci_fix_rebase_pending`, so it defaults to `False` even when the last inner fix left `pending=True`. `monitor()` then propagates `pending=False` into `MonitorResult`, and `ship.py:577-579` can overwrite a true pending flag in `working` before `_write_ship_state`. **Suggested fix:** Carry `ci_fix_rebase_pending` from the last attempted fix (or keep a loop-local `pending` flag) on all terminal returns from `evaluate_failure`; only clear it after a successful push, matching bash `_ci_fix_pending_clear`.

- **architecture** `python/ship.py:352-393` — `_write_ship_state` still rewrites the entire state file from a fixed key list. Bash uses `state_set`/`awk` to update individual keys (`scripts/ship-pr.sh:774-788`). This branch adds `CI_FIX_REBASE_PENDING` to that rewrite, so every CI-loop persist can drop `STALL_TRACKING`, `STALL_STEP`, `BAIL_*`, `NO_LOGS_COMMIT`, `FAILED_RUN_ID`, and other keys bash requires on resume (`scripts/ship-pr.sh:3250-3264`). That breaks cross-layer resume and contradicts the plan’s “persist before next iteration” lifecycle. **Suggested fix:** Merge writes key-by-key (read existing file, update only supplied keys) or expand the written set to the full canonical bash key set; do not let partial Python snapshots replace orchestrator-seeded state.

- **architecture** `python/ci_monitor.py:914-915` vs `scripts/ship-pr.sh:1708-1710` — Python sets `pending = (did_rebase or ci_fix_rebase_pending) and not pushed` on any failed force-push after rebase. Bash sets `_ci_fix_pending_set` only when `verify_passed=true` before push; failed verify returns early without arming pending. Python has no equivalent post-rebase verify gate in `stage_and_push`, so pending can be armed when bash would not, changing retry/stall semantics. **Suggested fix:** Port `_run_post_rebase_verify_gates` behavior (or call the bash helper) before force-push when `did_rebase` or pending; set `ci_fix_rebase_pending` only when verify succeeded and push failed, matching bash.

### Out-of-Scope Observations

- **architecture** `python/README.md:79-81` — The Phase 6 note still states that `CI_FIX_REBASE_PENDING` is deliberately omitted (#3405), but this branch adds partial plumbing in `run_context.py`, `ship.py`, and `ci_monitor.py`. That documents a different architecture than the implementation plan and risks operators assuming pending retry is intentionally absent.

- **architecture** `python/test_ship.py` — The plan calls for `CI_FIX_REBASE_PENDING` hydration, writeback, and clear-only-after-success tests in `test_ship.py`, but the branch only adds `test_from_env_hydrates_ci_fix_rebase_pending_from_state` in `python/test_run_context.py`. The resume state machine is not integration-tested at the ship/monitor boundary, so the gaps above would not be caught by the acceptance criteria the plan lists.
