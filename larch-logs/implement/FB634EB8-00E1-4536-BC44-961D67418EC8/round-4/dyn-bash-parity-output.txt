Reviewing the branch diff and commit history for correctness issues against the bash parity plan.
### In-Scope Findings

- **correctness** `python/ci_monitor.py:906-939` — Post-CI-fix defer-rebase does not match bash `_stage_and_push_ci_fixes` / `_run_post_rebase_verify_gates` (`scripts/ship-pr.sh:1663-1693`). After a behind-main rebase, bash always runs post-rebase verification (failed-job local verify and/or `run_checks_with_lint_fix_loop`, plus optional lint-delta commit). Python only runs `verify_job_locally` when `classified.fixable` is non-empty, and never runs the lint-fix loop or post-rebase delta commit. A fix can be force-pushed without the checks bash requires. **Suggested fix:** Port `_run_post_rebase_verify_gates` (or call the same scripts) from `stage_and_push` whenever `did_rebase` or `ci_fix_rebase_pending` is true; gate force-push and `CI_FIX_REBASE_PENDING` on the same `verify_passed` semantics as bash (`scripts/ship-pr.sh:1708-1710`).

- **correctness** `python/ci_monitor.py:906-915,979` — Behind-main detection uses `git rev-list --count HEAD..origin/main` before `git fetch`, while bash uses `ci-behind-count.sh`, which fetches first then counts (`scripts/ci-behind-count.sh:52-67`). With stale remote-tracking refs, Python can skip defer-rebase when bash would rebase, or rebase when bash would not. **Suggested fix:** Fetch `base_remote`/`base_ref` before the behind count (or shell out to `ci-behind-count.sh`) so the defer-rebase gate matches bash.

- **correctness** `python/ci_monitor.py:979,1517-1523` — `CI_FIX_REBASE_PENDING` is set whenever `(did_rebase or ci_fix_rebase_pending) and not pushed`, without bash’s `verify_passed=true` requirement (`scripts/ship-pr.sh:1708-1710`). If post-rebase verification is skipped or fails without returning early, a failed force-push can still persist pending and the monitor returns `Outcome.OK` for `waterfall-failed` with pending, inviting retry loops bash would not treat as resumable. **Suggested fix:** Track an explicit `verify_passed` flag through `stage_and_push`; set `ci_fix_rebase_pending` only when verification succeeded and force-push failed, matching bash `_ci_fix_pending_set`.

- **correctness** `python/run_logs.py:2477-2500` — `flush_logs_post` writes `status=done` and `pr_number` to disk before `_write_final_report` / ledger rendering. If report rendering fails, callers get `RefreshSkip` but the manifest may already show `done` without an updated summary (covered by `test_flush_logs_post_writes_done_manifest_before_reports`). Bash only runs the report after a successful manifest write (`scripts/ship-pr.sh:3160-3173`), but still does not roll back `done` on report failure. **Suggested fix:** Either mirror bash exactly (write manifest, then report only if manifest write succeeded—already close), or defer `status=done` until after a successful report render so fail-closed recovery and operator state stay consistent when report steps fail.

- **correctness** `python/ship.py:2697-2705,2897-2901` — On non-OK `finalize.postmerge()` (e.g. `branch-invalid`), Python returns `ShipResult(STALLED)` and skips `phase=done`, while bash `run_postmerge_phase` records failures but always `advance_phase done` and exits 0 (`scripts/ship-pr.sh:3097,3177-3178`). For the Python ship driver, a postmerge finalize failure can leave phase state inconsistent with bash resume semantics. **Suggested fix:** Align terminal phase writes with bash: still advance to `done` when merge completed and PR closed, or map implement-finalize usage errors to warning-only postmerge like bash does for partial cleanup.
