### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:922-937` — The new defer-rebase path in `stage_and_push` invokes `rebase-push.sh --no-push --keep-on-conflict`, but on any non-zero exit it immediately returns `pushed=False` with `pending=False` and does not abort the in-progress rebase, run vendor/conflict resolution, or surface the bash `run_rebase_rebump` exit-4 handoff. Because `rebase-push.sh` deliberately leaves the rebase in progress on conflict, later CI-fix iterations can run against a conflicted or detached tree and burn outer-loop attempts instead of stalling with a recoverable push-pending state. **Suggested fix:** Mirror `scripts/ship-pr.sh:1677-2932`: on conflict, either route through the same conflict-resolution / `ship-pr-rrr-phase14` contract bash uses, or abort the rebase before returning; only treat `rc==0` as `did_rebase=True`, and preserve `ci_fix_rebase_pending` when verify passed but push could not complete.

- **risk-integration** `python/finalize.py:94-102` — `postbump_preflight` treats a failed/empty `git symbolic-ref` as “use `ctx.branch_name`” and can return `ok=True` while HEAD is detached or not on the feature branch. Bash `validate_postbump_state_branch(true)` fails closed in that situation (`scripts/implement-finalize.sh:314-320`), emitting `branch-mismatch` before rebase/push. Python may then attempt `_rebase_no_push` / `force_push_recovery` from the wrong HEAD and surface `rebase-failed` / `push-failed` instead of the expected `branch-mismatch`, obscuring operator recovery. **Suggested fix:** Require a live named branch that byte-matches `ctx.branch_name` (or `ctx.branch`); if `symbolic-ref` fails or `rev-parse --abbrev-ref HEAD` is `HEAD`, return `PostbumpPreflight(ok=False, status="branch-mismatch", ...)`.

- **risk-integration** `python/finalize.py:152-158` — `_remote_branch_state` calls `git ls-remote` once with no transient retry, while the bash reference wraps the same probe in `with_transient_retry` (`scripts/check-remote-branch.sh:56-61`). A transient auth/network flake is therefore classified as `error` → `remote-check-failed` and stalls postbump, whereas bash would retry and may proceed. That is a false-negative stall on an otherwise healthy branch during the force-push gate. **Suggested fix:** Wrap the `ls-remote` probe in `retry.with_transient_retry` (same predicate bash uses) before mapping to `present` / `absent` / `error`.

- **risk-integration** `python/finalize.py:287-294` — After live presence is confirmed, postbump sets `expected_remote_oid` only from `git.try_rev_parse("origin/<branch>")` and never falls back to parsing the `ls-remote` OID. The new CI-fix path in `python/ci_monitor.py:956-963` already does that fallback, so first-time or stale-tracking-ref postbump runs can enter `force_push_recovery` with `expected_remote_oid=None` and use a weaker lease than bash/`git-force-push.sh`, increasing lease-bypass risk on cutover. **Suggested fix:** Reuse the CI-fix logic: after `present`, parse OID from `ls-remote` when `origin/<branch>` is missing, then pass that OID into `git.force_push_recovery`.

- **risk-integration** `python/ci_monitor.py:956-966` — When a post-rebase force-push cannot resolve a lease OID (missing `origin/<branch>` and absent/empty `ls-remote` output), `stage_and_push` clears `ci_fix_rebase_pending` (`pending=False`). Bash still records push failure and, when verify gates passed, sets `CI_FIX_REBASE_PENDING=true` (`scripts/ship-pr.sh:1708-1710`), allowing a push-only resume. Python therefore drops durable pending state on the exact retry path this branch adds, so a later monitor iteration may re-run the full vendor waterfall instead of retrying the force-push. **Suggested fix:** Align with bash: if verify passed and the failure happened on the force-push path, return `pending=True` (and persist it through `monitor` / `_write_ship_state`) unless the remote branch is positively `absent`; only clear pending after a successful push.

### Out-of-Scope Observations

- **risk-integration** `python/ship.py:643-652` — CI `goto_rebase` still resolves conflicts inside `rebase.rebase_and_push(..., allow_conflict_fix=True)` rather than emitting bash’s `RESUME_PHASE=ship-pr-rrr-phase14` / exit-4 orchestrator handoff. Round 3 added `enable_pre_push_handoff=True`, but the Python driver still does not match the documented `ship_pr_pre_push` conflict contract; this predates the finalize parity work and is not introduced by the postbump/local-cleanup changes under review.

- **architecture** `python/ship.py:396-398` — `CI_FIX_REBASE_PENDING_HEAD` is written to ship state but never read during `RunContext.from_env` hydration (`python/run_context.py:98-101`). It is inert metadata today; no head-mismatch invalidation occurs on resume.
