Reviewing the branch diff and commit history, then tracing run-log recovery and fail-closed gates across call paths.
### In-Scope Findings

- **risk-integration** `python/finalize.py:467-507` — Teardown recovery and larch-log commit failures are silent: `_teardown_log_flush` returns `recovery.recovery_ok` without emitting the warning breadcrumbs bash prints in `scripts/implement-finalize.sh:984-989` and `1019`, and `teardown()` discards that return value at line 700. Operators lose execution-issues/manifest audit signal on the Step 18 safety-net path even though bash continues best-effort. **Suggested fix:** Mirror bash `warn_line` behavior for recovery init/tag failure, stall-manifest write failure, and commit failure; append to execution-issues or breadcrumbs before continuing with commit when recovery failure must not block commit.

- **risk-integration** `python/finalize.py:1633-1643` — The teardown execution-issues safety net is fail-open on compose/redaction errors: the outer `try`/`except (OSError, ShipError)` returns `False` and skips manifest recovery and `commit_larch_logs`, whereas bash `flush_execution_issues_safety_net` warns and continues (`scripts/implement-finalize.sh:223-225`, `243-244`). A redaction failure in `render_execution_issues_batch` can drop the entire teardown log flush, including unflushed `execution-issues.md` content. **Suggested fix:** Catch redaction/compose errors only around the safety-net render, log a warning, and still run recovery + gated commit like bash.

- **risk-integration** `python/finalize.py:483-490` — Stall teardown forces `status=partial` via `update_manifest`, but bash only adds `stalled_at_step` when recovery succeeded (`scripts/implement-finalize.sh:1007-1012`) and does not rewrite `status`. If a `status=done` manifest already exists (post-merge flush), Python can downgrade it to `partial` on stall teardown. **Suggested fix:** On stall teardown, update only `stalled_at_step` (and `recovery_reason` when recovering a missing manifest); do not set `status=partial` when the manifest is already `done`.

- **risk-integration** `python/run_logs.py:1096-1136` — `_larch_log_commit` (used by `flush_logs_pre` and `commit_larch_logs`) does not enforce bash `larch-log.sh commit` hard stops for post-merge sentinel presence or default-branch refusal (`scripts/larch-log.sh:501-508`). Teardown guards branch/sentinel at the caller (`python/finalize.py:492-496`), but pre-push `flush_logs_pre` has no default-branch check. A wrong cwd on `main` could commit run logs to the default branch, violating the post-merge cleanup contract bash enforces centrally. **Suggested fix:** Port sentinel and default-branch checks into `_larch_log_commit` (or a shared pre-commit gate) so every commit path matches bash regardless of caller.

- **risk-integration** `python/run_logs.py:688-716` — `flush_logs_post` now writes `status=done` before `_write_final_report` (ordering fix vs bash). On report/redaction failure it returns a skip after the manifest is already `done` (`python/test_run_logs.py:129-149`). Ship postmerge treats that as warning-only and still advances (`python/ship.py:448-451`), leaving a done manifest without a re-rendered final summary. Bash has the same ordering, but the branch makes this path more central via `finalize_postmerge_logs`. **Suggested fix:** Either gate `status=done` on successful report render (rollback manifest on report failure) or document and test the warning-only “done manifest, stale summary” state so resume/teardown tooling does not assume both are coherent.

### Out-of-Scope Observations

- **risk-integration** `python/merge.py:170-174` — `_post_flush` maps every `flush_logs_post` skip (including `manifest-recovery-failed`) to `MERGE_RESULT_ERROR`, while ship postmerge logs a warning and still returns `Outcome.OK`. That split matches the plan (merge fail-closed vs ship warning-only), but any caller using `merge_pr(..., post_flush=True)` on an already-merged PR can surface `error` instead of a merged noop when recovery fails. Production `ship.py` passes `post_flush=False`, so this is latent until broader Python cutover.

- **architecture** `python/run_logs.py:720-727` — `finalize_postmerge_logs` is a one-line alias to `flush_logs_post`; centralized postmerge ordering is correct, but there is no separate execution-issues render in the postmerge helper (bash `run_postmerge_phase` also only does manifest + final report). Late execution-issues still depend on teardown safety-net parity.
