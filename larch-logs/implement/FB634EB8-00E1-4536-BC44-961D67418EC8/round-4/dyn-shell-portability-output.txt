### In-Scope Findings

- **code-quality** `python/test_finalize_bash_parity.py:160-173` — `test_postbump_branch_mismatch_status_matches_bash_subprocess` invokes `scripts/implement-finalize.sh` via `subprocess.run` without pinning `cwd` to the repo root and without PATH stubs for `git`, while the Python half uses `cwd=Path(__file__).resolve().parents[1]` and a `RecordingRunner` that fakes git output. Bash `run_postbump()` always starts with a real `git rev-parse --show-toplevel` on the subprocess working directory; outside a git worktree (or with a different inherited cwd than the Python side), bash can emit `STATUS=postbump-cwd-not-repo` while Python still returns `branch-mismatch`, breaking side-by-side parity. `python/test_merge_bash_parity.py` already avoids this by passing `cwd=REPO_ROOT` and stubbing `git`/`gh` on `PATH`. **Suggested fix:** Match the merge-parity pattern: set `cwd` to the repo root for the bash subprocess, stub `git`/`gh` in an isolated `bin/` directory on `PATH`, and assert the full KV set (`STATUS`, `REBASE_STATUS`, `FORCE_PUSH_STATUS`, `LOG_WRITE_STATUS`) rather than only `STATUS`.

- **code-quality** `python/test_finalize_bash_parity_gate.py:33-34` — The fail-closed gate parses pytest’s human summary with `assert " skipped" not in output` and `assert "7 passed" in output`. That couples CI to exact test cardinality and pytest’s default `-q` wording; adding/removing one test, running with `-ra`/`-rs`, or using a plugin that changes the summary line will make `make py-test` fail even when parity tests themselves pass. **Suggested fix:** Assert on machine-readable signals instead (`pytest --collect-only -q` item count, `pytest -q` exit code, and zero `s`/`S` markers in `pytest -rN` output), or compare collected-vs-run counts without hard-coding `7 passed`.

- **code-quality** `skills/review-and-fix/scripts/record-implement-review-round-timing.sh:99-104` — The pre-write idempotency probe exits success when *any* `round` row exists for `(skill, step, round)`, ignoring `start_s`/`end_s`, while the post-write verification at `118-120` and the design sibling `skills/design/scripts/record-plan-review-round-timing.sh:91-96` key on the full timestamp tuple. A deferred Step 5 emit after a handoff can therefore be skipped silently if an earlier partial or differently timed row for the same round number is present, and the helper still exits 0. **Suggested fix:** Align the first probe with the design helper (match `start_s`/`end_s`, and ideally accepted/rejected too), or drop the round-only short-circuit and rely solely on the post-write ledger check.
