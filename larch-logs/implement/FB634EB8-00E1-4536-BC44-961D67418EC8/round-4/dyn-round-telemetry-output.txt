### In-Scope Findings

- **correctness** `scripts/timing-report.sh:381-384` — `emit_round_array` attaches a ledger `round` row to a per-step JSON interval when only `round_start` lies in `[start, end)`; it never checks `round_end`. That conflicts with `docs/run-logs.md:379`, which says the step interval must fully contain both start and end. Deferred Step 5 / Step 3 timing (early `round-start-s`, late `record-*-round-timing`) can land on the prior step while `duration_seconds` spans into the next mark, so `timing-report.json` can mis-attribute review time and make `rounds[].duration_seconds` exceed the parent step total. **Suggested fix:** Require full containment (e.g. `round_start >= start && round_end < end`, aligned with half-open step bounds), drop non-conforming rows, and add a harness case for a round whose end crosses the next step mark.

- **correctness** `python/run_logs.py:704-716` — `flush_logs_post` / `finalize_postmerge_logs` write `status=done` (and `pr_number`) to `manifest.json` before `_write_final_report`, `_render_ledger_reports`, and `_render_token_timing_batches`. If any of those later steps raise `ShipError`, the function returns `RefreshSkip` but leaves the manifest at `done`. The plan calls for an atomic recovery → done write → report path and skipping both done and report on failure; `ship.run_postmerge_phase` only logs a warning, so a merged run can look “done” in the manifest without a refreshed final report. **Suggested fix:** Build the done manifest in memory, run report/ledger/token rendering first, and commit the manifest only after the full bundle succeeds (or roll back / avoid the done write when any step fails).

- **correctness** `python/ci_monitor.py:964-966` — After a successful CI-fix rebase (`did_rebase=true`), if remote OID resolution fails the function returns with `ci_fix_rebase_pending=false`. Bash sets `CI_FIX_REBASE_PENDING` when verify passed but force-push failed (`scripts/ship-pr.sh:1709-1710`), preserving the force-push retry path. Python can lose that flag, so the next monitor iteration may use a plain `git push` on rebased history instead of `git-force-push.sh` parity. **Suggested fix:** When `did_rebase || ci_fix_rebase_pending` and push did not succeed, always return `pending=true` (and persist it via `ship._write_ship_state`), including the “remote OID unavailable” branch; only clear pending after a successful force-push.

- **correctness** `skills/review-and-fix/scripts/record-implement-review-round-timing.sh:99-104` — Idempotency treats any existing ledger row with the same `(skill, step, round)` as success and exits 0 without comparing `start_s` / `end_s`. A failed first `record-round` followed by a deferred orchestrator retry with corrected timestamps is silently dropped, so the round can be missing from `timing-report.json` even though review completed. **Suggested fix:** Match bash-style idempotency on the full tuple `(round, start_s, end_s)` (as design’s helper does), or upsert/replace the row for that round when start/end differ.

- **correctness** `python/test_finalize_bash_parity_gate.py:43` — The fail-closed gate asserts the substring `"7 passed"`, so adding or removing a parity test makes `make py-test` fail even when all parity tests pass and none are skipped. That undermines the gate’s purpose (detect all-skipped parity) with brittle coupling to test count. **Suggested fix:** Assert `run.returncode == 0`, no `"skipped"` in output, and a positive collected count (or parse pytest’s summary line for `N passed` with `N > 0`) instead of a hard-coded total.
