### In-Scope Findings

1. **Important** (`correctness`) [scripts/ship-pr.sh:1199-1247](scripts/ship-pr.sh): After the new regression guard rewrites `new_version`, the block that refreshes the `version-bump-reasoning` larch-log batch still passes the original `reasoning_file` from `classify-bump.sh`, whose body was generated for the pre-correction `NEW_VERSION`. In the stale-conflict scenario (e.g. classify argued `29.1.39`, you correct to `29.3.1`), the PR title and committed `plugin.json` can disagree with the reasoning batch the run logs as authoritative. **Suggested fix:** On the correction path, append a bounded correction stanza to the reasoning file (or regenerate it) before `larch-log.sh write`, or skip the reasoning overwrite when `new_version` was corrected.

2. **Important** (`code-quality`, source: plan + repo contract) [.claude/skills/bump-version/scripts/apply-bump.md:60-65](.claude/skills/bump-version/scripts/apply-bump.md): This PR updates `apply-bump.md` invariants but leaves **Edit-in-sync** siblings untouched—notably [.claude/skills/bump-version/SKILL.md](.claude/skills/bump-version/SKILL.md) still describes only the same-version `origin/main` probe and `fail()` text (around lines 53–59) and does not document the new `NEW_VERSION < ORIGIN_VERSION` rollback. **Suggested fix:** Extend the SKILL “How it works” bullets for `apply-bump.sh` to match the sibling contract.

3. **Important** (`code-quality`) [.claude/skills/bump-version/scripts/apply-bump.md:7,25](.claude/skills/bump-version/scripts/apply-bump.md): The **Purpose** sentence and the **exit 1** sentence still only mention the same-version duplicate-bump case, not the regression guard, so the primary contract doc is internally inconsistent with the updated Invariants. **Suggested fix:** Mention both probes in Purpose and in the failure exit list.

4. **Latent** (`risk-integration`) [scripts/ship-pr.sh:689-724](scripts/ship-pr.sh): `run_bump_phase` maps only `ERROR` values matching `origin/main has already bumped to*` to `exit 5` / `CALLER_KIND=step8b_same_version`. A `version regression:` failure from `apply-bump.sh` falls through to `exit_stall 8`, unlike the rebase path where `run_rebase_rebump` auto-corrects before `apply-bump.sh`. If regression ever appears on the initial bump path (no correction), recovery is a hard stall instead of the same-version-style sub-procedure. **Suggested fix:** Either mirror the regression correction in `run_bump_phase`, or extend the `case` to route regression errors to the same exit-5 handoff if that matches product intent.

5. **Nit** (`code-quality`) [scripts/ship-pr.sh:385-396](scripts/ship-pr.sh) and [.claude/skills/bump-version/scripts/apply-bump.sh:41-51](.claude/skills/bump-version/scripts/apply-bump.sh): Identical `semver_lt` implementations in two shipped scripts increase drift risk on any future semver edge-case fix. **Suggested fix:** Move one copy to a small sourced helper under `scripts/` (or similar) and call it from both.

6. **Nit** (`code-quality`, source: plan) [scripts/test-apply-bump.sh:103-106,312-315](scripts/test-apply-bump.sh): The plan specified `--new-version 2.9.9` for sub-test H; the harness still hardcodes `2.0.0` in `invoke_apply`, so the test is weaker as documentation of the intended edge (though it still exercises `NEW_VERSION < ORIGIN_VERSION`). **Suggested fix:** Pass `2.9.9` for case H only (e.g. a dedicated runner or optional argument).

7. **Nit** (`code-quality`) [.claude/skills/bump-version/scripts/apply-bump.sh:9-11,22](.claude/skills/bump-version/scripts/apply-bump.sh): The header comment and exit-code comment still describe only the same-version `origin/main` check, not the regression guard. **Suggested fix:** Align comments with the new pre-commit probe.
