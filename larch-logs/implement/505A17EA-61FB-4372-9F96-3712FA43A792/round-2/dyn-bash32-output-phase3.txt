### Out-of-Scope Observations
- **code-quality** `scripts/test-implement-structure.sh:assert_degraded_tools_gate_fence` — Two early `fail` exit paths do not clean up `$tmp` or `$tmp.region`. When `[[ -n "$region" ]] || fail "..."` fires (region empty), and when `[[ -s "$tmp" ]] || fail "..."` fires (fence not found), neither temp file is removed before `exit 1`. The per-needle `{ rm -f "$tmp" "$tmp.region"; fail "..." }` cleanup is correct, but the two region-guard calls above it lack matching cleanup. This follows the pre-existing harness style (e.g. `assert_step2a_entry_simple_guard` in `test-design-structure.sh` has the same pattern), so it is not a regression; the OS reclaims the files on test exit. **Suggested fix:** Add `trap 'rm -f "$tmp" "${tmp}.region"' EXIT` at the top of `assert_degraded_tools_gate_fence`, drop the per-exit-path `rm -f` calls, and clear the trap with `trap - EXIT` only at the successful `rm -f` line — matching the cleanup discipline used in `compute-pr-line-counts.sh`.

- **code-quality** `scripts/compute-pr-line-counts.sh:83-85` — The terminal `trap - EXIT; rm -f "$tsv_tmp"; exit 0` sequence is redundant: the EXIT trap already invokes `cleanup()` on every exit path, including this success path. The explicit `trap -; rm` pattern is the correct idiom when you want to *prevent* double-deletion after a manual remove, but here both `trap - EXIT` and `rm -f` are guarding a file that the trap also removes — the only functional effect is the `rm` runs slightly earlier. Not harmful, but slightly misleading to readers. **Suggested fix:** Replace the trailing three lines with `exit 0` alone, letting the EXIT trap handle the final cleanup, and remove the `# shellcheck disable=SC2317` comment (which suppresses the "unreachable" warning for `cleanup()` but may no longer be needed if the function is visibly reachable from the trap). If early-exit performance matters, keep the pattern with a comment explaining why the manual remove precedes the trap reset.
