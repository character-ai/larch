### In-Scope Findings

**correctness — [`scripts/ship-pr.sh:936-1019`](scripts/ship-pr.sh)**  
**Issue:** `run_pr_create_phase` no longer runs `larch-log.sh manifest --field pr_number=…` after `create-pr.sh`. That was the only place in `ship-pr.sh` that persisted `PR_NUMBER` into the run-log `manifest.json` during the PR-create / CI-wait window. `run_postmerge_phase` still sets `pr_number` when `PR_CLOSED=true` ([`scripts/ship-pr.sh:1592-1636`](scripts/ship-pr.sh)), so **merged** runs still get `pr_number` on disk before Step 18’s `capture-session-transcript.sh` commit ([`skills/implement/SKILL.md:1924-1943`](skills/implement/SKILL.md)). For runs that **create a PR** but never reach that postmerge branch (stall in CI, `merge=false` / draft handoff, bail before merge, etc.), the **committed** `larch-logs/implement/<RUN_ID>/manifest.json` can remain `pr_number: null` for the whole time the PR exists on GitHub — a regression versus the old post-create manifest write + commit + push.  
**Suggested fix:** If manifest parity with GitHub matters, reintroduce a **local-only** `larch-log.sh manifest --field pr_number=…` after `state_set_many` (no extra push), or explicitly accept the trade-off and document it (see next finding).

**correctness — [`docs/run-logs.md:69-73`](docs/run-logs.md)**  
**Issue:** This branch documents two-phase `larch:final-summary` and placeholder `final-summary.md`, but the **`manifest.json`** subsection is unchanged. It still says generically that the manifest contains “PR number (once created)” without clarifying that, after this change, **committed** `pr_number` may be absent until merge-side postmerge (and may stay null for non-merge outcomes). That undershoots the scout question about docs vs actual timing.  
**Suggested fix:** Add a short sentence describing when `pr_number` reliably appears in committed JSON vs when operators should read `ship-pr-state.sh` / GitHub.
