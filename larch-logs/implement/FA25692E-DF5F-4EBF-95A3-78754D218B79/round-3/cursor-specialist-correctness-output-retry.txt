### In-Scope Findings

1. **Latent** **correctness** (plan) `scripts/parse-codex-usage.sh:66-72` — The `cached_tokens > input_tokens` guard runs only on **stream-aggregated** sums after all events are added, not per event. **Concrete scenario:** JSONL line 1 has `input_tokens=5`, `cached_input_tokens=20`; line 2 has `input_tokens=1000`, `cached_input_tokens=0`, `output_tokens=10`. Aggregates pass (`20 ≤ 1005`), exit 0, emit `INPUT=985` / `CACHED_INPUT=20` / `TOTAL=1015`. Per-event bucket math (or fail-closed on line 1) would yield `INPUT=1000`, `CACHED_INPUT=5`, `TOTAL=1015` — wrong uncached/cached split and wrong per-bucket cost even though `TOTAL` matches. **Suggested fix:** In the jq `reduce`, skip or exit 1 when any event’s coalesced `input_tokens < cached_tokens` before accumulating; keep the aggregate check as a backstop.

2. **Latent** **correctness** (plan, both) `scripts/parse-codex-usage.sh:36-44` — The parser sums **every** JSON object that exposes a usage marker (no `type == "token_usage"` filter; filter was added in `552eaa72` then removed in `8aef0664`). **Concrete scenario:** If a future (or current) Codex `--json` stream emits per-`responses` usage on turn events **and** a final `token_usage` summary with run totals, all lines are summed and ledger/totals are roughly **2×** real usage — cost lines overstate Codex spend (different failure mode than the old blended-rate warning). The checked-in smoke fixture (`scripts/fixtures/parse-codex-usage/codex-events-0.125.jsonl`) has a single `token_usage` line, so this is not exercised in CI. **Suggested fix:** Confirm against a real `codex exec --json` capture whether both shapes appear; if so, restrict to `type=="token_usage"` and/or dedupe by event id, and extend the smoke fixture.

3. **Nit** **correctness** (plan) `scripts/test-launch-review.sh` (removed in `8aef0664`) — Round 2 dropped the harness case “usage parsing must stay disabled when the sidecar falls back to `/dev/null`.” Production code still skips parsing when `SIDECAR=/dev/null` (`scripts/launch-review.sh:560-582`), but there is no regression test for that plan contract. **Concrete scenario:** A future refactor always calls `parse-codex-usage.sh` and writes a ledger row in review-codex `/dev/null` mode, reintroducing unwanted accounting. **Suggested fix:** Restore a small stub test that forces `: > "$SIDECAR"` failure and asserts no vendor row / no parse call.
