### In-Scope Findings

1. **Important** `risk-integration` `scripts/launch-codex-implement.sh:358` and `scripts/launch-codex-ci.sh:230` — Parse failures are fully silenced (`2>/dev/null`), unlike `scripts/launch-review.sh:562-565`, which appends `parse-codex-usage.sh` diagnostics to the sidecar when the events file is non-empty. **Scenario:** After a Codex CLI upgrade, `${TRANSCRIPT_PATH}.events.jsonl` or `${OUTPUT}.events.jsonl` contains JSONL but the helper exits fail-closed (e.g. `cached_tokens exceeds input_tokens`, or a new usage shape that sums to zero). `/implement` or CI records **no** vendor row and emits **no** `BLENDED_WARN` (fail-closed removes aggregate fallback), so final cost lines show **zero Codex spend** with no breadcrumb in the sidecar. Operators may read that as “Codex wasn’t used” rather than “usage parse failed.” **Suggested fix:** Mirror the review launcher contract: capture stderr to a temp file and, on empty `_codex_usage` with `-s "$CODEX_EVENTS"`, append the diagnostic to `$SIDECAR_LOG` (or emit a single `larch_err` breadcrumb) so failure recovery is observable without reintroducing aggregate fallback.

2. **Latent** `correctness` `scripts/parse-codex-usage.sh:36-44` — Events that match the synthetic `usage` branch (`{}`) but carry no numeric token fields still increment `usage_count`. If the stream contains only such shells, the script exits with `no usage events` even though usage-shaped objects were present. **Scenario:** A future Codex event like `{"type":"token_usage","usage":{}}` repeated across a run yields exit 1 and no ledger row; logs mislabel the failure as “no usage” rather than “zero totals after usage detection.” **Suggested fix:** Either require at least one non-zero summed field before incrementing `count`, or split stderr messages (`no usage objects` vs `zero token totals`).

3. **Nit** `architecture` `scripts/launch-review.sh:572-579`, `scripts/launch-codex-implement.sh:364-371`, `scripts/launch-codex-ci.sh:236-243` — Launchers trust the four KV lines without verifying `TOTAL == INPUT + CACHED_INPUT + OUTPUT` (or non-negative integers) before `record-vendor` / `token-record` writes. **Scenario:** A regression in `parse-codex-usage.sh` stdout formatting could write internally inconsistent buckets; downstream `token-report` / `token-cost` would consume bad data without a launcher-level guard. **Suggested fix:** After the `while` loop, assert arithmetic and skip the ledger write when the identity fails (fail-closed).

### Out-of-Scope Observations

1. **Latent** `risk-integration` `skills/review-and-fix/scripts/review-and-fix.sh:256-257`, `scripts/lint-fix-loop.sh:188-190` — These Codex invocations still use combined `2>&1` logging and do not call `parse-codex-usage.sh` or `exec --json`. **Why out of scope:** Not modified by this branch; plan scoped only the three runtime launchers. **Scenario:** `/review-and-fix` or lint-fix Codex work can still produce missing or aggregate-only token telemetry, so `BLENDED_WARN` or zero-bucket Codex rows may persist on those paths even after this fix lands.

2. **Nit** `code-quality` `scripts/launch-codex-ci.sh:254` — `launch-codex-ci.sh` always `exit 0` while setting `LAUNCHER_EXIT` in KV output. **Why out of scope:** Pre-existing contract, not introduced by per-bucket capture. **Scenario:** Callers that only check shell exit code may treat a failed Codex CI fix as success; token-record fail-closed behavior is correct but exit semantics remain ambiguous.
