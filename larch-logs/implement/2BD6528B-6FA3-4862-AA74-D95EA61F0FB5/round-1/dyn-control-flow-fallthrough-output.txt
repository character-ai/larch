Tracing control flow in `run_evaluate_failure` and related helpers. Reading the diff and key source sections.
### In-Scope Findings

- **correctness** `scripts/ship-pr.sh:1792-1805` — When `gh_logs_rc` is 0, `ci-failed-jobs.sh` reports failed jobs, and `run_per_job_local_fix_loop` completes successfully, a non-zero return from `_stage_and_push_ci_fixes` does **not** end the attempt. Control falls through to `run_ci_fix_vendor` on line 1802 because that call sits outside the inner `if _stage_and_push_ci_fixes …; then return 0; fi` block and is only gated by the outer `elif [ "$gh_logs_rc" -eq 0 ]` branch. That contradicts the plan wiring (“if per-job returns 0, **skip** `run_ci_fix_vendor` and proceed directly to the shared push helper”) and the happy-path test, which only asserts “no launcher” on success. After per-job repair, the working tree typically already contains lint-fix-loop edits (and possibly a local `Fix CI failure` commit if staging/commit succeeded before `git-push.sh` failed). `run_ci_fix_vendor` then snapshots a **post-per-job** baseline and may run up to three vendor launchers against the same failure log, then `_stage_and_push_ci_fixes` again with `run_checks_with_lint_fix_loop` — a second, broader recovery pass on a tree that is not in the “fresh failure, vendor-only” state the waterfall assumes. **Suggested fix:** After a successful `run_per_job_local_fix_loop`, treat `_stage_and_push_ci_fixes` failure like other push failures: `return 1` from `run_evaluate_failure` (or `continue` the outer `_fix_attempt` loop) **without** calling `run_ci_fix_vendor`. Only invoke `run_ci_fix_vendor` when the per-job path was not taken (zero fixable jobs, `ci-failed-jobs.sh` degrade, or per-job never ran). Add a harness case (e.g. stub `git-push.sh` to fail once after per-job success) that asserts launcher calls stay absent and the vendor waterfall is not entered.

- **correctness** `scripts/ship-pr.sh:1734` — `run_per_job_local_fix_loop` uses `exit 3` for the `ci-local-unfixable` bail. That **does** propagate correctly: it terminates the `ship-pr.sh` process and is not swallowed by the `while [ "$_fix_attempt" -lt "$_max_fix" ]` loop in `run_evaluate_failure` (lines 1766–1823), which only continues when the script is still running. No change required for bail propagation; document this explicitly so future edits do not replace `exit 3` with `return 3` inside the function.
