Reviewing control-flow wiring in `run_evaluate_failure`: reading the diff and tracing branch paths.
Checking whether `run_ci_fix_vendor` propagates `_stage_and_push` failures and scanning the diff for related control-flow changes.
### In-Scope Findings

- **correctness** `scripts/ship-pr.sh:1792-1805` — When `gh_logs_rc=0`, `ci-failed-jobs.sh` reports failed jobs, and `run_per_job_local_fix_loop` completes successfully (Phase A + Phase B verification), a failed `_stage_and_push_ci_fixes` does **not** stop the attempt: control falls through to `run_ci_fix_vendor` at line 1802. That contradicts the plan/acceptance text (“if the per-job loop returns 0, **skip** `run_ci_fix_vendor` and proceed directly to the shared push helper”) and the happy-path test, which only asserts the vendor waterfall is skipped on full success. A push-only failure (network, permissions, `git-push.sh`) after locally green CI jobs will still launch the 3-tier vendor waterfall, re-run `relevant-checks` on the vendor path, and may roll back or layer additional launcher edits on top of per-job fixes. **Suggested fix:** After `run_per_job_local_fix_loop` returns 0, treat `_stage_and_push_ci_fixes` as the terminal step for that branch: on success `state_set_many TRANSIENT_RETRIES 0 FIX_ATTEMPTS …` and `return 0`; on failure `return 1` (or `record_failure` + continue the outer `_fix_attempt` loop) **without** calling `run_ci_fix_vendor`. Reserve `run_ci_fix_vendor` for `ci_failed_rc≠0`, `FAILED_JOBS_COUNT=0`, or when the per-job path was never entered.

- **correctness** `scripts/ship-pr.sh:1575-1577` — `run_ci_fix_vendor` invokes `_stage_and_push_ci_fixes` but never tests its exit status before the function ends. Bash returns the helper’s status implicitly, so `run_evaluate_failure` usually sees failure, but a future edit that adds commands after `_stage_and_push_ci_fixes` would silently turn push/staging failures into success. The per-job branch at 1794 does check the helper explicitly, so the two recovery paths are inconsistent. **Suggested fix:** Add `if ! _stage_and_push_ci_fixes "$phase" "${ci_fix_out_base}.${winning_tier}.token-record" "$checks_site"; then return 1; fi` (or `return $?` immediately after the call) so vendor and per-job paths share the same explicit contract.

### Out-of-Scope Observations

- **architecture** `scripts/ship-pr.sh:870-946` — The plan called for refactoring `run_checks_with_lint_fix_loop` onto `run_captured_cmd_then_fix_loop`; the helper exists (lines 119–177) but is only used from `run_per_job_local_fix_loop`. The two loops still differ on `no-changes` handling (helper re-runs until two consecutive empty failures; `run_checks_with_lint_fix_loop` bails after one `no-changes` rerun at 926–928), so a blind refactor would change behavior.

- **correctness** `scripts/ship-pr.sh:1700-1719` — Phase B verification failures re-enter `run_captured_cmd_then_fix_loop` with a fresh `_RCC_MAX_ITER=3` per job; this is not coupled to `run_evaluate_failure`’s outer `_fix_attempt` counter at 1766, despite the plan edge-case note that verification should count against the outer cap.

- The final `elif run_ci_fix_vendor` at 1806–1808 is **reachable** for `gh_logs_rc=1` (hard `gh-run-logs` failure) and is not dead; `gh-run-logs.sh` only documents exits 0, 1, and 3.

- `FIX_ATTEMPTS` / `TRANSIENT_RETRIES` resets at 1795–1796, 1803–1804, and 1807–1808 cover all successful exit paths that were inspected; the gap is the per-job-success / push-failure path, which never increments `FIX_ATTEMPTS` and then incorrectly enters the vendor path above.
