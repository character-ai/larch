### In-Scope Findings

- **correctness** `scripts/ship-pr.sh:1706-1707` — On `exhausted` or `dispatch-failed` from `run_captured_cmd_then_fix_loop`, `run_per_job_local_fix_loop` returns **1** immediately instead of adding the job to `unfixable` and continuing. The plan and `scripts/ship-pr.md:84-86` say cap-exhausted per-job repairs should end in `exit 3` with `BAIL_REASON=ci-local-unfixable:…`. In a multi-job failure, the first exhausted job aborts the whole per-job pass and never runs remaining fixable jobs. **Suggested fix:** On `exhausted`/`dispatch-failed`, append the job token to `unfixable` and `continue` (or return only after Phase A finishes and the tail bail runs). Reserve `return 1` for statuses that should degrade to `run_ci_fix_vendor` (e.g. `main-agent-required` only), and document that split in `run_evaluate_failure`.

- **correctness** `scripts/ship-pr.sh:1723-1724` — Phase B calls `return 4` on the first verification failure. The plan says re-enter the per-job fix loop for that job within the outer budget, then add the job to `unfixable` if still failing. The implementation only sets `per_job_verification_retry=true` in `run_evaluate_failure:1826-1827` and retries the **entire** outer attempt; after three failures the run stalls with **exit 4** (`test-ship-pr.sh` verify-regression case), not `exit 3` / `ci-local-unfixable`. That diverges from the documented bail contract. **Suggested fix:** On verification failure, re-run `run_captured_cmd_then_fix_loop` for that job (or loop Phase B failures back into Phase A) until the shared cap is exhausted, then add the job to `unfixable` and `exit 3`; use `return 4` only if you intentionally want stall semantics and align `ship-pr.md` with that.

- **correctness** `scripts/ship-pr.sh:1822-1829` — `run_evaluate_failure` handles `per_job_rc` **0**, **2**, and **4** explicitly; **1** is not in the `case` and falls through to `run_ci_fix_vendor`. That matches the **main-agent-required** harness (`ci_per_job_main_agent_required`), but it also routes **`exhausted`** and **`dispatch-failed`** to the broad vendor waterfall, which conflicts with the per-job bail design above. The fall-through is easy to misread as accidental. **Suggested fix:** Split return codes (e.g. `1` = degrade to vendor for `main-agent-required` only; `3` or internal bail for unfixable exhaustion) or add an explicit `case "$per_job_rc" in 1) …` branch with a comment and tests per status.

- **correctness** `scripts/ship-pr.sh:873-948` — `run_checks_with_lint_fix_loop` was **not** refactored onto `run_captured_cmd_then_fix_loop` (plan DECISION_2 / acceptance). Per-job fixes use the shared helper; the push gate still uses a separate loop. Empty-output / `no-changes` / exhaustion behavior can drift between the two paths (plan called for byte-identical behavior and `T-refactored-checks-loop-byte-identical`; that test is not in the branch). **Suggested fix:** Refactor `run_checks_with_lint_fix_loop` to call `run_captured_cmd_then_fix_loop` with a `run_relevant_checks_capture` callback, or add an explicit regression test that pins both paths to the same exhaustion semantics.

- **correctness** `scripts/test-ship-pr.sh` — Plan cases **`T-per-job-cap-exhausted`** and **`T-per-job-no-changes-after-fail`** are absent (grep finds no matches). Without them, the `exhausted` → `return 1` → vendor path and the two-strike empty-log path in `run_captured_cmd_then_fix_loop:137-139` are not regression-locked. **Suggested fix:** Add harness cases: always-failing mapped command → `exit 3` + `ci-local-unfixable:<job>`; empty log after fail → `_RCC_STATUS=exhausted` and the intended parent routing (bail vs vendor), per the chosen design.
