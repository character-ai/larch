2. **Nit** (`code-quality`) — [.claude/skills/bump-version/scripts/apply-bump.md](.claude/skills/bump-version/scripts/apply-bump.md) (~invariants, first bullet): the opening invariant still says the worktree “must be clean” before the next bullet admits tolerated internal untracked files, which reads contradictory on a quick skim. **Suggested fix:** rephrase the first bullet to “must have no disallowed dirty entries” (or fold tolerance into that single bullet).

3. **Nit** (`code-quality`) — [scripts/git-push.sh](scripts/git-push.sh), [scripts/rebase-push.sh](scripts/rebase-push.sh), [scripts/ship-pr.sh](scripts/ship-pr.sh) (`run_evaluate_failure`): the jitter/backoff arithmetic is copy-pasted with the same integer-truncation quirks (`_base/4` is `0` for small `_base`, so the documented “±25%” is only approximate for early sleeps). **Suggested fix:** one tiny shared shell helper (e.g. `scripts/lib-backoff.sh`) or a short comment block copied from a single canonical comment to reduce drift.

4. **Latent** (`risk-integration`) — [scripts/ship-pr.sh](scripts/ship-pr.sh) (`run_evaluate_failure` / `run_rebase_rebump` stall paths): `exit_stall` now emits `10-max-retries`, `12-max-retries`, `10-detached-head`, and `12-detached-head` where vendor/rebump exhaustion or detached HEAD used to map to coarser step tokens (`10` / `12c` in the evaluate-failure exhaust path). In-repo references mostly treat stall text opaquely, but any out-of-repo operator automation that keyed on the old `STALL_STEP` strings could mis-classify stalls after upgrade. **Suggested fix:** mention the new stall tokens in the operator-facing contract ([scripts/ship-pr.md](scripts/ship-pr.md) already partially does) and in release notes if consumers exist.

5. **Nit** (`correctness`) — [scripts/rebase-push.sh](scripts/rebase-push.sh) (force-push retry block): lease-race recovery refreshes `git fetch "$BASE_REMOTE" "$CURRENT_BRANCH"` and compares `HEAD` to `"$BASE_REMOTE/$CURRENT_BRANCH"`, while `git push --force-with-lease` uses the branch’s configured push remote. In the common `BASE_REMOTE=origin` case this matches; in exotic multi-remote setups where `BASE_REMOTE` is not the push remote, the “already landed” shortcut may fail to notice a successful push and waste retries (not a regression vs no-fetch, but the new early `exit 0` path is keyed off that ref). **Suggested fix:** if this matters for fork workflows, refresh the same remote/ref the push uses (or drop the optimistic `exit 0` unless both refs agree).
