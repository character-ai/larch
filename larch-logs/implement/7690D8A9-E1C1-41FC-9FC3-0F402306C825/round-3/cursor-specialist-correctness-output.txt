### In-Scope Findings

1. **Important** (`correctness`, source: **both** — plan wording vs actual behavior) — [`scripts/git-push.sh`](scripts/git-push.sh):26-52 — The retry loop runs after **any** failed `git push`, not only transient non-fast-forward races. The contract in [`scripts/git-push.md`](scripts/git-push.md) calls out NFF-style contention, but the code has no exit-code or message gating. **Concrete scenario:** a deterministic failure (e.g. hook exits 1, `protected branch hook declined`, or auth `403`) still performs up to three push attempts with sleeps in between, multiplying hook side effects and delaying the eventual stall. **Suggested fix:** only sleep/retry when the failure matches an allowlist (e.g. non-fast-forward / rejected / transient classifier), otherwise exit with the first push’s status.

2. **Latent** (`risk-integration`, source: **requirements** + **plan** interpretation) — [`scripts/ship-pr.sh`](scripts/ship-pr.sh):1195-1345 vs [`scripts/rebase-push.sh`](scripts/rebase-push.sh):239-284 — `run_rebase_rebump` runs `rebase-push.sh` with `--no-push`, then force-pushes through [`scripts/git-force-push.sh`](scripts/git-force-push.sh), which still has the older “one 5s retry” policy. The new lease snapshot + three-try jitter loop in `rebase-push.sh` therefore **does not run** on the primary non-fork rebump path (only the separate `git-push.sh` path used after CI-fix commits picks up the new plain-push retries). **Concrete scenario:** repeated `--force-with-lease` races during rebump remain bounded by `git-force-push.sh` only, so the main “rebase storm” push leg is not materially improved by the `rebase-push.sh` change. **Suggested fix:** move the same lease snapshot + capped retry policy into `git-force-push.sh` (or restructure rebump to use the pushing mode of `rebase-push.sh` once).

3. **Latent** (`correctness`, source: **plan**) — [`scripts/rebase-push.sh`](scripts/rebase-push.sh):253-262 — `EXPECTED_REMOTE_OID` comes from `git rev-parse "$BASE_REMOTE/$CURRENT_BRANCH"` after a best-effort fetch; if that remote ref does not exist yet, `EXPECTED_REMOTE_OID` is empty and the push becomes `git push --force-with-lease=refs/heads/<branch>:` with nothing after the colon. Git’s parsing of an empty expected OID is version- and configuration-sensitive and can diverge from the historical plain `git push --force-with-lease` behavior. **Concrete scenario:** first-time publication of a branch name through `rebase-push.sh` (push mode) when the remote has no `refs/heads/<branch>` yet may fail or behave unlike the pre-change script. **Suggested fix:** if `EXPECTED_REMOTE_OID` is empty, fall back to plain `--force-with-lease` (or explicitly document and implement the “expect missing ref” zero-OID form supported by your minimum Git version).

4. **Nit** (`code-quality`, source: **plan**) — [`scripts/git-push.md`](scripts/git-push.md):5-6 vs [`scripts/git-push.sh`](scripts/git-push.sh):26-52 — Documentation says retries target “transient non-fast-forward rejections,” but the implementation retries all push failures. Tighten the doc to match the code, or add the gating suggested in finding 1.
