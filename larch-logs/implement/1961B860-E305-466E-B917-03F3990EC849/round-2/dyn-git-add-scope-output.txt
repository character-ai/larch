### In-Scope Findings

- **correctness** `skills/review-and-fix/scripts/review-and-fix.sh:461-472` — The new follow-up path is gated by `git status --porcelain --untracked-files=no` (tracked dirt only) but stages with `git add -A`, which also picks up any untracked paths present at follow-up time (e.g. artifacts a pre-commit hook wrote during the primary round commit, or files created between the two commits). That contradicts the tracked-only guard and Option A’s `git add -u` in `scripts/ship-pr.sh:2857-2871`, and can silently commit scratch or generated files that were deliberately left untracked. **Suggested fix:** Change the follow-up staging to `git add -u` (and update `skills/review-and-fix/scripts/review-and-fix.md:56` to match); keep `git add -A` only on the primary round commit at `review-and-fix.sh:438` where the orchestrator already owns full-tree staging.

- **correctness** `skills/review-and-fix/scripts/review-and-fix.sh:470-485` — After the follow-up `git-commit.sh` runs, pre-commit hooks can execute a second time and re-dirty tracked files (the regression test hook is idempotent after the first run, so it does not exercise this). When the second `git status --porcelain --untracked-files=no` check is still non-empty, the script only `larch_err` warns and then falls through to emit `CODER_STATUS=applied` with `CODER_COMMIT_SHA` set (`review-and-fix.sh:478-485`), violating the branch acceptance criterion that round mode must not return `applied` with uncommitted tracked changes and recreating the upstream stall class at `ship-pr` time instead of failing closed in Step 5. **Suggested fix:** On persistent tracked residue after follow-up, write `CODER_STATUS=failed` to `$result_file` and `return 2` (as in the uncommitted working-tree revision at `review-and-fix.sh:482-493`); optionally re-run `post_dispatch_submodule_revert` after a successful follow-up commit when using `git add -u`.

- **correctness** `scripts/ship-pr.sh:2857-2871` — Option A performs a single fixup commit before `drop-bump-commit.sh`; `git-commit.sh` on that fixup can trigger the same pre-commit hooks that motivated Option B. If a hook re-modifies tracked files on that commit, there is no second pass in the committed code, the tree remains dirty, and `drop-bump-commit.sh` Guard 1 (`scripts/drop-bump-commit.sh:90-93`) still returns `DROPPED=false` → the original `run_rebase_rebump` stall. **Suggested fix:** Mirror the two-pass pattern already drafted in the working tree (`scripts/ship-pr.sh:2874-2890`): after a successful fixup commit, re-check tracked porcelain and attempt one more `git add -u` + fixup commit; bump `--max-depth` when a fixup commit was inserted so the bump walk still reaches the version commit.
