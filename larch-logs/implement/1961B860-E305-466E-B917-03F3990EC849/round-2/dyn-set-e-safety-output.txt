Reviewing the branch diff and `set -e` behavior in `run_rebase_rebump` vs `review-and-fix.sh`.
### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:2853-2888` — Option A’s pre-rebase fixup is written for best-effort fallthrough (`git add -u` / `git-commit.sh` fail → `record_failure` → continue to `drop-bump-commit.sh`), but `ship-pr.sh` does not run with a globally disabled errexit. The script starts with `set -uo pipefail` and an explicit “no `set -e`” policy (`scripts/ship-pr.sh:4-7`), yet every `larch_err` goes through `larch_quiet_redact_diagnostic_stream`, which ends with `set -e` (`scripts/lib-quiet.sh:113-116`). `run_rebase_rebump` calls `larch_err` before the new block (`scripts/ship-pr.sh:2801`), so errexit is typically active at `git add -u > "$fail_file" 2>&1` / `"$SCRIPT_DIR/git-commit.sh" ...` (`2859-2885`). Under `set -e`, a non-zero `git add -u` or `git-commit.sh` exits the shell before `rc=$?` and before `record_failure`, so the documented Warning + fallthrough path is bypassed (hard abort instead of Guard 1 stall). That is the opposite of the plan’s “only improve, never regress” contract and differs from Option B, which correctly uses `if git add -u && git-commit.sh` inside `review-and-fix.sh` where `set -euo pipefail` is intentional (`skills/review-and-fix/scripts/review-and-fix.sh:4,461-465`). **Suggested fix:** Wrap the fixup git steps in an errexit-safe idiom: `set +e` … capture `rc` … `set +e` (or restore prior `-e` with the `had_errexit` pattern used in `run_lint_fix_loop_capture` at `scripts/ship-pr.sh:100-108`), or use `if ! git add -u …; then record_failure …; elif ! git diff --cached --quiet; then if ! git-commit.sh …; fi` so failures are evaluated inside `if`/`!` contexts where errexit does not trigger. Apply the same pattern to both passes in the block.

### Out-of-Scope Observations

- **risk-integration** `scripts/ship-pr.sh:1500-1503` — `run_pr_prep_phase` runs `set +e` for the OOS gate, then `set -e` and never `set +e` again in that process; a single long-lived `ship-pr.sh` invocation that went through `pr-prep` keeps errexit on for all later phases (pre-existing, but it widens the blast radius of the finding above).
- **risk-integration** `scripts/ship-pr.sh:1796-1813` — `_stage_and_push_ci_fixes` uses the same bare `git add` / `rc=$?` shape as the new fixup block (pre-existing; not introduced by this branch).
- On **stale `rc`**: after the fixup block, `drop-bump-commit.sh` immediately reassigns `rc=$?` (`scripts/ship-pr.sh:2907-2908`), so a successful fixup does not leave a stale code affecting the `DROPPED=false` stall logic; the main failure mode here is abort-before-`rc=$?`, not stale `rc` at drop time.
