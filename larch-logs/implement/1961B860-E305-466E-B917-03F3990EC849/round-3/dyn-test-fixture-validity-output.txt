### In-Scope Findings

- **code-quality** `scripts/test-ship-pr.sh:2567-2574` — The `rebump_dirty_tracked_fixup` case only greps the full log for the fixup subject and `Bump version to 1.2.4`; it never asserts that the fixup commit actually captured the seeded dirty change (`dirty tracked residue` in `sentinel-fix.txt`). A broken implementation that commits some other tracked dirt (or an empty index edge case) could still satisfy the subject-line checks while leaving the regression scenario unexercised. **Suggested fix:** Resolve the fixup commit SHA (e.g. `git log --format=%H --grep='chore: pre-rebase working-tree fixup (#3209)' -n 1`) and assert `git show "$sha":sentinel-fix.txt` contains `dirty tracked residue`, mirroring the content-level assertion in the plan acceptance criteria.

- **code-quality** `scripts/test-ship-pr.sh:2649-2653` — The `rebump_hook_redirty_second_fixup` case uses `fixup_count -ge 2`, so three or more fixup commits would still pass; it also does not verify that hook-induced residue (`hook re-dirty`) landed in either fixup commit. **Suggested fix:** Tighten to `[[ "$fixup_count" -eq 2 ]]` and add a `git log -1 -p --grep='chore: pre-rebase working-tree fixup (#3209)'` (or per-SHA `git show`) check that `sentinel-fix.txt` contains both `initial dirty` and `hook re-dirty`.

- **code-quality** `skills/review-and-fix/scripts/test-review-and-fix.sh:399-405` — The round-mode hook-residue test infers a single follow-up via `HEAD~1` parentage and subject grep, but never asserts an exact commit count (init → primary → one follow-up) or that `hook residue` appears in the follow-up commit’s `src/main.py` diff. A regression that emitted two follow-ups with the wrong parent chain could slip through if the final tree were clean. **Suggested fix:** Capture `initial_head` before the run, assert `git rev-list --count "${initial_head}..HEAD" -eq 2`, and `git show HEAD:src/main.py | grep -Fq 'hook residue'` (or equivalent diff against the primary commit).

For the pre-commit hook stamp at `skills/review-and-fix/scripts/test-review-and-fix.sh:372`, `${GIT_DIR:-.git}` is reliable in this harness: `run_review_and_fix` `cd`s to the work repo root (`test-review-and-fix.sh:276`), and `git-commit.sh` invokes plain `git commit`, which runs hooks with `GIT_DIR` set to the repo’s `.git` directory. The fallback `.git` resolves correctly from that cwd. An empty-string `GIT_DIR` would mis-resolve (bash parameter expansion treats `""` as set), but git’s hook invocation path does not do that in normal use here.
