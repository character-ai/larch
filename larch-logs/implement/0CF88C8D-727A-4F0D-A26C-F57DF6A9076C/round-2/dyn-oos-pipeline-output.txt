### In-Scope Findings

- **risk-integration** `scripts/lib-vote-tally.sh:67-72`, `skills/review-and-fix/scripts/review-and-fix.sh:203-225` — This branch broadens security detection in `lib-vote-tally.sh` (used by `tally-code-votes.sh` and `oos-serialize.sh`) to also match `- **focus-area**: security` and header-level `security` tokens, but `review-and-fix.sh` keeps its own narrower `is_security_block` that only matches `focus-area\s*=\s*security`. On the coder-`SKIPPED` path, a finding with canonical `- **focus-area**: security` is therefore held locally during tally yet normalized and appended to `accumulated-oos.md` / `oos-accepted-review.md` after skip, publicizing security-routed OOS that tally and serialize would have suppressed. **Suggested fix:** Deduplicate security classification into one shared helper (or source `lib-vote-tally.sh` from `review-and-fix.sh`) and apply the exact same predicate everywhere accepted OOS is written; add a skipped-routing harness case using `- **focus-area**: security` (not prose `focus-area = security`) and assert the block stays out of `oos-accepted-review.md`.

- **risk-integration** `skills/review/scripts/emit-tally.sh:171-177`, `skills/shared/scripts/oos-serialize.sh:62-69` — When `OOS_ACCEPTED_COUNT > 0` but the accepted sink is empty, emit-tally falls back to rebuilding from `oos.md` via `oos-serialize.sh` and exits 0 even on partial recovery. `oos-serialize.sh` only emits blocks whose header/body carry `[OUT_OF_SCOPE]` / `[OOS]`, so scope-drift reclassifications that tally accepted as bare `### FINDING_N:` (the #3550 production failure mode) are still dropped in this desync path while `OOS_ACCEPTED_COUNT` remains positive. The new `exit 1` guard only covers the no-`oos.md` case, so a tally/write desync can still ship with fewer accepted-OOS blocks than the tally counter claims. **Suggested fix:** Treat rebuild incompleteness as failure when `oos_accepted_count > 0` and post-serialize `oos_sink_count` is still zero or still below the non-security portion of `OOS_ACCEPTED_COUNT` (excluding held-security blocks), or fail closed instead of `|| true` on serialize failure; extend `test-emit-tally.sh` with a scope-drift-only `oos.md` desync fixture that must not exit 0 with an empty accepted sink.

- **risk-integration** `skills/review/scripts/emit-tally.sh:161-170`, `skills/review/scripts/tally-code-votes.sh:608` — The preserve branch keys only on `oos_accepted_count > 0 && oos_sink_count > 0` and logs a warning when `oos_sink_count != oos_accepted_count`, but `OOS_ACCEPTED_COUNT` counts security-held accepted OOS while `oos_sink_count` counts only non-security blocks in the sink. A round with one held-security and one public accepted OOS therefore preserves with a permanent count mismatch and no hard failure, making sink/gate divergence harder to detect operationally and masking partial-write regressions where the warning is the only signal. **Suggested fix:** Compare `oos_sink_count` against a non-security expected count (e.g. derive expected non-security blocks from `oos.md` / tally env, or subtract held-security accepted blocks before comparing) and fail closed when the sink is short rather than only emitting `larch_err` warnings.

- **risk-integration** `scripts/lib-vote-tally.sh:70`, `skills/shared/scripts/oos-serialize.sh:48` — The new header heuristic `^###...(?:\[security\]|\bsecurity\b)` classifies any `### FINDING_N:` title containing the word “security” as security-routed before accepted-OOS normalization runs. Legitimate non-security `[OUT_OF_SCOPE]` items about security documentation or hardening can be withheld from the public accepted sink (and thus never reach `/issue`), which is the same class of silent disposition loss this branch fixes, only on the tally/serialize path instead of the gate path. **Suggested fix:** Drop the header `\bsecurity\b` heuristic and rely on the dedicated `- **focus-area**: security` field line plus existing `focus-area = security` token detection, matching `oos-non-security-block-count.awk`; add a regression where an `[OUT_OF_SCOPE]` title contains “security” in prose but lacks a security focus-area field and must still be normalized and counted.
