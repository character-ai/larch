### In-Scope Findings

- **architecture** `skills/review/scripts/emit-tally.md:5` — The contract says emit-tally is a no-op on `oos-accepted-review.md` whenever `OOS_ACCEPTED_COUNT > 0`, but `emit-tally.sh:161-183` only preserves when **both** `oos_accepted_count > 0` and `oos_sink_count > 0` (sink blocks counted via `oos-non-security-block-count.awk`). If the tally env reports a positive count but the sink is empty or unreadable, the script either rebuilds from `oos.md` or exits 1; those branches are not described in the contract doc. **Suggested fix:** Update `emit-tally.md` to match runtime: preserve when tally count and awk sink count are both positive (with the mismatch warning), document the `oos.md` rebuild fallback when count>0 but sink==0, and document hard exit when count>0, sink==0, and `oos.md` is absent; align acceptance wording in the plan/issue accordingly.

- **architecture** `skills/shared/scripts/oos-serialize.md:7-9` — The contract still says the serializer “treats all OOS blocks in the input file as accepted,” but `oos-serialize.sh:55-59` now filters on `Result=accepted` and rewrites headers inline (`### OOS_<seq>:`). That is a behavioral and schema change not reflected in the doc, and the doc does not note that scope-drift blocks (bare `### FINDING_N:` without `[OUT_OF_SCOPE]`/`[OOS]`) are never emitted because `oos` stays false. **Suggested fix:** Rewrite `oos-serialize.md` to document the `Result=accepted` gate, canonical header normalization on output, scope-drift non-recovery from `oos.md`, and extend `test-oos-serialize.sh` to assert `^### OOS_1:` and rejected-block exclusion so the contract and harness stay aligned.

- **architecture** `skills/shared/scripts/normalize-oos-block-header.md:5` / `skills/shared/scripts/oos-serialize.sh:55-58` — The shared helper is documented as the single canonical normalization contract for tally and review-and-fix, but `oos-serialize.sh` implements a parallel inline `sub()` on the full block string instead of calling `normalize-oos-block-header.sh`. That creates a third normalization surface (different call site, no `NR==1` doc cross-reference, separate seq ownership) and will drift if the helper regex or semantics change. **Suggested fix:** Either delegate `oos-serialize.sh` flush to `normalize-oos-block-header.sh --seq N --block-file` (per-block temp file) and list it as a caller in `normalize-oos-block-header.md`, or extract one shared awk snippet sourced by both paths and document all three consumers explicitly.

- **architecture** `skills/review-and-fix/scripts/review-and-fix.md:108` / `skills/review-and-fix/scripts/review-and-fix.sh:630-633` / `skills/review/scripts/tally-code-votes.sh:127-128` — Docs say sequence continuation uses the existing `accumulated-oos.md` **non-security block count**, but both producers initialize `OOS_WRITE_SEQ` with a bespoke awk that counts any `^### (OOS_|FINDING_[0-9]+:)` line, including bare `FINDING_` headers the disposition gate intentionally does not count.
