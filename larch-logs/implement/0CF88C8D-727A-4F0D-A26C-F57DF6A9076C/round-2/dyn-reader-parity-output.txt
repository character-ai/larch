Comparing Python and awk OOS readers for semantic parity — reading the diff and both implementations.
### In-Scope Findings

- **correctness** `python/test_oos.py` / `skills/implement/scripts/test-oos-disposition-gate.sh` — The branch extends legacy-header counting in both `python/oos.py` (`_OOS_HEADER_RE` at `python/oos.py:32-35`, `_count_non_security_markdown` at `python/oos.py:60-81`) and `skills/implement/scripts/oos-non-security-block-count.awk:10-14`, and adds parallel unit tests (`test_count_non_security_counts_legacy_*` in `python/test_oos.py:187-242`, legacy cases in `skills/implement/scripts/test-oos-disposition-gate.sh:228-262`), but there is no golden-file harness that runs the same markdown fixtures through **both** counters and asserts identical totals. Elsewhere in this repo, bash/Python cutover surfaces use explicit parity tests (e.g. `python/test_redact.py`, `python/test_merge_bash_parity.py`); with `python/ship.py` calling `oos.count_non_security` while `oos-disposition-gate.sh` / `emit-tally.sh` use the awk script, a one-sided regex tweak could make the Python and bash gates disagree without CI catching it. **Suggested fix:** Add a small parity module (e.g. `python/test_oos_bash_parity.py` or a shared fixture table in `test_oos.py`) that parametrizes canonical `### OOS_`, leading-tag `### FINDING_N: [OUT_OF_SCOPE]`, trailing-tag `### FINDING_N: title [OUT_OF_SCOPE]`, bare `### FINDING_N:`, security `- **focus-area**: security`, and multi-block markdown, running each fixture through `oos.count_non_security(...)` and `awk -f skills/implement/scripts/oos-non-security-block-count.awk` and asserting equal counts.

### Out-of-Scope Observations

- **Reader logic appears aligned on the branch diff.** For the cases the fix targets, `python/oos.py` and `oos-non-security-block-count.awk` use the same state machine (new block on `### OOS_` or tagged `### FINDING_<digits>:` with a literal `[OUT_OF_SCOPE]` on the header line; bare `FINDING` headers ignored; security excluded via the same `- **focus-area**: security…` line shape). Python’s `FINDING_\d+:.*\[OUT_OF_SCOPE\]` and awk’s `index($0, "[OUT_OF_SCOPE]")` both accept leading- and trailing-tag headers on line 1, which the new tests cover (`python/test_oos.py:197-206`, `test-oos-disposition-gate.sh:246-262`).

- **Rejected-marker disposition still keys only on `OOS_<n>`** in both stacks (`python/oos.py:27`, `_count_rejected_markers` at `python/oos.py:169`; `scripts/oos-disposition-shared.inc.bash:97`). Explicit rejection rows that keep legacy `### FINDING_N:` / `FINDING_N` text in the ndjson rejected section will not increment `rejected_markers` even though `non_security` now counts legacy accepted headers. Bash and Python remain in parity here; the limitation is shared and pre-existing, but it is slightly more visible now that accepted legacy headers are counted.

- **`review-and-fix.sh` / `tally-code-votes.sh` sequence initialization** (`review-and-fix.sh:1446`, `tally-code-votes.sh:127`) uses an inline `awk` that counts any `^### (OOS_|FINDING_<digits>:)` header, while the gate counter requires `[OUT_OF_SCOPE]` for `FINDING` lines. That can inflate `OOS_WRITE_SEQ` relative to gate-visible blocks if bare `FINDING` headers ever remain in `accumulated-oos.md`; producer normalization is meant to prevent that, so this is a sequencing concern rather than a Python/awk gate split.
