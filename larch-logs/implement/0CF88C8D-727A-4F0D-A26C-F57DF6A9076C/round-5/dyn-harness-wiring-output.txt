### In-Scope Findings

- **risk-integration** `skills/review/scripts/test-emit-tally.sh:76-109` — The new preserve/fail-closed cases always seed `OOS_ACCEPTED_COUNT=1` as a clean integer, but `emit-tally.sh:82-83` coerces absent or non-numeric values to `0`, which routes back through serialize/truncate and can wipe tally-normalized `oos-accepted-review.md` — the exact #3550 failure mode if `review-tally.env` drifts from tally stdout. `test-tally-code-votes.sh` guards the producer append, yet nothing in `test-emit-tally.sh` exercises malformed/missing `OOS_ACCEPTED_COUNT` with a pre-populated normalized sink. **Suggested fix:** Add emit-tally cases where the sink already holds a normalized `### OOS_1:` block but `OOS_ACCEPTED_COUNT` is missing, blank, or non-numeric (`1a`); assert fail-closed or preserve behavior explicitly, not silent truncate/serialize.

- **risk-integration** `python/test_oos.py:295-411`, `skills/implement/scripts/test-oos-disposition-gate.sh:254-301` — Legacy-header coverage is split across separate Python (`make py-test`) and bash gate (`test-harnesses-5`) harnesses with no mechanical awk↔Python parity runner (unlike `python/test_merge_bash_parity.py` / `python/test_redact.py`). The plan’s failure mode #5 calls out awk/python drift, and the counters were both extended on this branch, but CI only runs isolated assertions per language. **Suggested fix:** Add a small bash-present parity harness (shared fixture markdown files) that runs `oos-non-security-block-count.awk` and `python -c "import oos; …"` on the same vectors — inline `[OUT_OF_SCOPE]`, trailing tag, `[OOS]` shorthand, bare `FINDING`, and security exclusions — and wire it into `test-harnesses-5` or `make py-test`.

- **risk-integration** `skills/review/scripts/test-tally-code-votes.sh:77-78`, `skills/review/scripts/test-emit-tally.sh:123-125,212-214`, `skills/review-and-fix/scripts/test-review-and-fix.sh:1524-1530` — New regression checks use file-wide `grep -Eq '^### FINDING_'` to prove canonical headers, but `skills/shared/scripts/test-normalize-oos-block-header.sh:37-43` documents that line-2+ `### FINDING_N:` citations in block bodies must survive normalization. A valid OOS block citing another finding on its own line would fail these greps even when production output is correct, yielding false CI failures or discouraging realistic fixtures. **Suggested fix:** Drop file-wide FINDING greps in favor of first-line-only checks (e.g., `awk '/^### /{print; exit}'`) or rely solely on `oos-non-security-block-count.awk` plus explicit `^### OOS_` header assertions; add one fixture with a body citation line to lock the contract.

- **risk-integration** `skills/implement/scripts/test-oos-disposition-gate.sh:600-617` — Gate-level #3550 cases cover legacy `### FINDING_N: [OUT_OF_SCOPE]` headers (lines 254-301), but the checkpoint disposition-gap case still uses only `### OOS_1:` in `oos-accepted-main-agent.md`. Because `oos-disposition-checkpoint.sh` is the Step 8+ mechanical gate consumed before `OOS_PENDING` clears, a regression that breaks legacy counting only on the checkpoint argv path would not be caught by the new gate tests alone. **Suggested fix:** Mirror the gate legacy-header gap fixture in the checkpoint section (expect exit 1 + Tool Failures log) and add a companion proceed case with a filed URL, matching the gate cases at 254-301.
