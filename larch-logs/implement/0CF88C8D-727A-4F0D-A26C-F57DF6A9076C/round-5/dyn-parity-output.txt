### In-Scope Findings
- **architecture** `skills/implement/scripts/test-oos-disposition-gate.sh:219-301` — The branch extends legacy-header counting in both `skills/implement/scripts/oos-non-security-block-count.awk` and `python/oos.py`, but cross-runtime parity is only asserted once (unbulleted `focus-area` security exclusion). Legacy fixtures for prefix/trailing `[OUT_OF_SCOPE]`, `[OOS]` shorthand, bare `### FINDING_N:`, and security-excluded legacy headers are covered in `python/test_oos.py` and bash gate exit-code cases without any shared `awk_count == py_count` loop on the same files. With `ship-pr.sh`/`oos-disposition-gate.sh` still authoritative on awk and `python/ship.py` on `oos.count_non_security`, future regex drift on these new surfaces would not be caught by CI. **Suggested fix:** Add a small shared fixture table (the legacy cases already in `python/test_oos.py`) to `test-oos-disposition-gate.sh` (or a dedicated `test-oos-counter-parity.sh`) that runs both counters on each fixture and fails on mismatch, mirroring the existing unbulleted-security parity block at lines 219–225.

- **architecture** `skills/review/scripts/emit-tally.sh:155-183`, `python/ship.py:362`, `skills/review/scripts/test-emit-tally.sh:216-241` — The review→ship pipeline now has two counting authorities: `emit-tally.sh` decides preserve vs rebuild from `oos_sink_count` produced only by awk, while the default Python ship driver later gates on `python/oos.py::count_non_security` over the same `oos-accepted-review.md`. Chained tally→emit integration tests assert awk counts on normalized sinks but never compare Python’s count on those same artifacts before ship. **Suggested fix:** In `test-emit-tally.sh` chained cases (and/or a ship integration test), after preserve/rebuild, assert `awk_count == py_count` on the final `oos-accepted-review.md`; optionally have `emit-tally.sh` log both counts in desync-rebuild warnings during the Python cutover soak.
