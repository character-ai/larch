Reviewing the audit-scan migration to `reviewer_signals[]` — reading the diff and relevant implementation files.
### In-Scope Findings

- **architecture** `.claude/skills/audit-runs/scripts/audit-scan-run.sh:438-441` — `scan_ns_retry_sidecars` returns `skip` as soon as `_audit_reviewer_signals_jq` reports `unavailable`, so the orphan sidecar loop at `456-465` never runs on legacy runs that still have committed `*-ns-retry*.txt` files but no `reviewer_signals`. Re-auditing the existing `larch-logs` corpus therefore loses fail detection for those runs (skip + zero counter delta), even though the hybrid path was clearly meant to preserve file-presence semantics when signals exist but `ns_retry_reason` is empty. **Suggested fix:** When signals are unavailable, fall back to the pre-migration file-glob path (count sidecars directly) and reserve `skip` for runs that lack both signals and sidecar files; keep the signal+orphan hybrid only as an enhancement on top of that fallback.

- **architecture** `.claude/skills/audit-runs/scripts/audit-compute-counters.sh:124-127` — Counter aggregation reads `ns-retry-sidecars` `.count // 0` without checking `result`, so a migrated `skip` line (no `count` field) contributes `0` to `NS_RETRIES_DELTA`. That makes skipped legacy runs look metrically clean in cumulative audit reports even though the per-run NDJSON says `skip`, which is the “false-clean” behavior at the dashboard layer the scout notes warn about. **Suggested fix:** Only add to `delta_ns_retries` when `result=="fail"` (or emit an explicit `partial_data`/`skipped_runs` counter for `result=="skip"` and teach report writers to surface it).

- **architecture** `.claude/skills/audit-runs/scripts/audit-scan-run.sh:158-176` — `_audit_reviewer_signals_jq` gates availability on “any round has a non-empty `reviewer_signals` array,” then runs `jq -sc` over **all** `round-*/round-meta.json` files. One corrupt or non-JSON meta in a multi-round run causes the slurp to fail, yielding empty output that callers treat like unavailability (`skip`), even though other rounds have valid signals. That is fragile for partial/copied logs. **Suggested fix:** Pre-filter to parseable metas (or slurp per-round and merge in shell) so one bad file cannot zero out signals for the whole run; distinguish `error` from `skip` in NDJSON when aggregation fails.

- **architecture** `.claude/skills/audit-runs/scripts/audit-scan-run.sh:540-555` vs `158-176` — `codex-generalist-waste` and `trailing-content-no-issues-found` use different unavailability contracts: codex reads only `round-1/round-meta.json` and skips when the `codex-generalist-output.txt` slot is absent, while trailing-content uses the global `_audit_reviewer_signals_jq` gate. A transitional run can therefore `skip` codex-waste while still evaluating trailing-content (or vice versa) on the same log tree, which breaks the “single concise carrier” architecture the plan describes. **Suggested fix:** Route all three migrated scans through one shared helper that defines availability consistently (round-1 slot missing vs global signals missing vs corrupt meta) and emits distinct `detail` tokens for each case.

- **architecture** `scripts/larch-log.sh:647-656` + `.claude/skills/audit-runs/scripts/audit-scan-run.sh:432-437` — On new concise logs, NS-retry detection depends entirely on the flush-time producer populating `ns_retry_reason` in `reviewer_signals`; committed sidecars are excluded by default, and the audit scan has no on-disk fallback when signals exist but `ns_retry_reason` is empty. A producer miss (meta path drift, flush error swallowed by `python3 … || true`) yields `pass` with `count:0`, not `skip`. **Suggested fix:** Treat “signals present, every `ns_retry_reason` empty, round had reviewer outputs” as `informational`/`fail` pending verification, or add a round-meta `signals_complete` flag set only when meta sidecars were successfully scanned at flush time.

- **architecture** `.claude/skills/audit-runs/scripts/audit-scan-run.md:41` + `.claude/skills/audit-runs/SKILL.md:72-80` — Operator-facing audit docs still describe file-glob/`*.meta` semantics for `ns-retry-sidecars`, `codex-generalist-waste`, and `trailing-content-no-issues-found`, while `scripts/larch-log.md:29-30` still claims NS-retry sidecars remain committed for audit. The branch changes both the flush contract and scan inputs without updating these canonical references, which will mislead future scan/counter changes (the SKILL itself lists five coordinated edit sites). **Suggested fix:** Update `audit-scan-run.md`, `SKILL.md`, and `larch-log.md` in the same change to document `reviewer_signals[]` as the primary carrier, file fallback rules (if any), and the `skip` semantics for legacy logs.

- **architecture** `.claude/skills/audit-runs/scripts/test-audit-runs.sh:914-938` — Test 24 still validates an inline reimplementation of the **old** first-pass grep logic and is not wired to `scan_trailing_content_no_issues_found` or `reviewer_signals`; the plan’s D15 requirement for pass/fail/skip coverage of all three migrated scans without raw files is only partially met (Test 35 exercises ns-retry signals path only). **Suggested fix:** Add hermetic `audit-scan-run.sh` fixtures for trailing-content and codex-generalist pass/fail/skip via `round-meta.json`, plus a legacy sidecar-only fixture asserting fallback or explicit skip behavior, and retire or repoint Test 24 to the real scan function.

### Out-of-Scope Observations

- **architecture** `.claude/skills/audit-runs/scripts/audit-scan-run.sh:459` — Orphan `output_base` derivation uses `${basename%-ns-retry.txt}.txt`, which matches the canonical `${ORIG_OUTPUT%.txt}-ns-retry.txt` pattern from `scripts/collect-agent-results.sh` but not arbitrary test names like `panel-ns-retry-sidecar.txt`; low risk in production but worth a comment or shared normalizer if non-canonical sidecar names exist in the wild.

- **correctness** `scripts/larch-log.sh:570-586` vs legacy grep scan — The `trailing_content()` producer skips leading blank lines and uses `result_kind()` normalization, while the removed grep scan used raw line 1 `NO_ISSUES_FOUND`; intentional per plan but means pre/post concise logs are not strictly comparable on that scan.
