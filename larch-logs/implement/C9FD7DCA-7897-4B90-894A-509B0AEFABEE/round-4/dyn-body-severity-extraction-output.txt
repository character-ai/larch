Reviewing the compose-review-findings extraction helpers and their call sites in the diff and source files.
### In-Scope Findings

- **correctness** `scripts/compose-review-findings.sh:152-160`, `skills/fluff-analysis/scripts/fluff-analysis.py:348-350` — `extract_body_severity()` keeps the entire remainder of the matched line (after stripping trailing whitespace), but `fluff-analysis.py` treats any non-empty `body_severity` as authoritative and does not fall back to `find_severity(prose)`. A line like `- **Severity**: minor note` yields `body_severity="minor note"`, `normalize_severity()` returns `(none)`, and the prose regex path (which would capture `minor` → `latent` via `([a-zA-Z-]+)`) is never used. That is a regression versus pre-carrier behavior for any finding whose severity line has trailing text, and it directly affects per-tier / accepted-low-value metrics the branch is meant to fix. **Suggested fix:** In the compose helper, trim the extracted value to the first canonical token (same `important|latent|nit` vocabulary as `aggregate-findings.sh` / `prune-nit-findings.sh`, case-insensitive), and/or in `fluff-analysis.py` fall back to `find_severity(prose)` when `normalize_severity(body_severity)` is `(none)` despite a non-empty carrier.

- **correctness** `scripts/compose-review-findings.sh:152-160`, `skills/review/scripts/aggregate-findings.sh:321`, `skills/review/scripts/prune-nit-findings.sh:69` — The new awk pattern matches `**Severity**` case-sensitively, while `aggregate-findings.sh` and `prune-nit-findings.sh` use `(?m)^-\s*\*\*Severity\*\*:…` with `re.IGNORECASE`. A reviewer line such as `- **severity**: nit` can be classified as nit for pruning but produce an empty `body_severity` in composed JSONL; with truncated `prose_body`, `find_severity()` also misses it (`\*\*Severity\*\*` is case-sensitive), so fluff analysis records `(none)` instead of `nit`. **Suggested fix:** Align compose extraction with the aggregate/prune pattern (case-insensitive label, require leading `-`, restrict value to `important|latent|nit`), or normalize the line before matching.

- **correctness** `scripts/compose-review-findings.sh:163-171`, `skills/fluff-analysis/scripts/fluff-analysis.py:348-349` — `extract_focus_area()` has the same full-line remainder behavior, and `focus_area = data.get("focus_area", "") or find_focus(prose)` blocks the `find_focus()` fallback whenever the carrier is non-empty. `find_focus()` only captures the first `[a-zA-Z-]+` token (`fluff-analysis.py:148-150`), so a line like `- **Focus area**: security — see rubric` stores `security — see rubric` in JSONL while the legacy path would record `security`, breaking focus-area aggregates for concise logs. **Suggested fix:** Trim `focus_area` to the first canonical focus token in compose (or apply the same first-token regex as `find_focus()`), and/or fall back when the stored value is not a known focus area.

### Out-of-Scope Observations

- **Ordering is correct:** In `emit_record` (`scripts/compose-review-findings.sh:200-205`), `extract_body_severity` / `extract_focus_area` run on the full redacted body before `${body_redacted:0:2000}`; the regression test at `scripts/test-compose-review-findings.sh:494-515` exercises markers placed after a 2100-character concern line.

- **`[[:space:]-]*` is intentional:** The hyphen matches markdown list bullets (`- **Severity**:`); the same idiom is used in `extract_reviewer_from_body`, `extract_category`, and `skills/design/scripts/tally-plan-review.sh:407-408`.

- **Empty-string vs absent field is consistent:** `emit_record` always emits `body_severity` / `focus_area` keys via `jq` (`scripts/compose-review-findings.sh:216-220`); `fluff-analysis.py` uses `data.get("body_severity", "") or ""` and treats both absent and `""` as “no carrier,” then falls back to prose parsing (`348-350`).

- **Herestring / silent empty:** `<<<"$1"` with a quoted argument does not expand shell metacharacters in the body; when no line matches, awk prints nothing and exit status stays 0, so an empty carrier is expected—not a silent awk failure. Very large bodies are already passed whole to `extract_category` the same way (`148`); that is a pre-existing argument-size constraint, not introduced by these helpers alone.
