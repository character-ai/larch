## Accepted Findings

### FINDING_9: **correctness** `python/design_lifecycle.py:732-828,885-890,1263-1300` — After `quiet_init`, the ported `*_core` helpers report validation and usage errors with `print(..., file=sys.stderr)`. That writes only to fd 2, which `quiet_init` redirects into the quiet log. The retired shell helpers used `larch_err`, which mirrored diagnostics to both fd 2 and fd 4 (the pre-redirect stderr). CLI callers such as `skills/design/scripts/design-step5c.sh:159-172` and `skills/design/references/decompose-panel.md:58-70` still redirect subprocess stderr into `design-stage-terminal-state.stderr.log` and pass that file to `run-log append-failure` on non-zero exit. On a post-`quiet_init` core failure, those stderr logs stay empty while the message lands only in `larch-quiet-*.log`, so failure capture and operator-visible stderr contracts regress. In-process capture via `_capture_contract_stream_to_paths` is unaffected because it redirects fd 2 into the artifact stderr log. **Suggested fix:** Add a small core-side diagnostic helper that mirrors bash `larch_err`: when quiet routing is active, write the same sanitized line to both the current stderr stream (fd 2) and the saved original stderr (fd 4) via `logging_util.diagnostic` or equivalent `os.write(4, ...)`, and use it for all `*_core` error paths (`unknown option`, `_CoreUsageError`, `ValueError`, and `traceback.print_exc` in `step_final_summary_core`). Keep pre-`quiet_init` `*_main` tmpdir validation on plain stderr.
