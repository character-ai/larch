### In-Scope Findings

- **correctness** `aggregate-findings.sh:92-96,231-233,312-386` — The new empty-merge path treats “no Python-parseable `### FINDING_N:` blocks” (`output_blocks` / `input_blocks`) as success when `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` is present, but persistence and attestation stripping branch on `count_finding_blocks`, which uses `grep '^### FINDING_[0-9]'` and does not require the colon or the same heading shape Python enforces. Vendor text can therefore contain a line that increments the grep count (for example a malformed heading without `:` or with a space before `:`) while Python still sees zero blocks; validation returns 0, yet the bash path takes the non-empty branch (`awk` copy), so the attestation line may remain in the rewritten ballot and `MERGED_COUNT` can disagree with the validator’s notion of structured output—whereas previously `not blocks` always failed validation. **Suggested fix:** Use one shared definition of “structured FINDING block” for validation, strip, and counts (for example tighten `count_finding_blocks` to match the Python lookahead/`re.match` contract, or additionally require `count_finding_blocks "$cand" -eq 0` before accepting an attested empty merge and before stripping the token).
