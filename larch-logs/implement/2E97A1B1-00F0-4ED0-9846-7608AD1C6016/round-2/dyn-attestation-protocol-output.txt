### In-Scope Findings

- **correctness** `skills/review/scripts/aggregate-findings.sh:311-322` — When merge output has no `### FINDING_N:` blocks, the validator returns success without an empty-merge attestation if `input_blocks(intext)` is empty (`return 0` at line 312–313), but bash already decided to aggregate using `count_finding_blocks` on `^### FINDING_[0-9]`, which does not require a colon after the id the way `input_blocks` / `output_blocks` do (`### FINDING_[0-9]+:`). Two malformed headings that satisfy the grep count but not the Python split can therefore reach this branch with zero output blocks and no `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED`, yet validation passes and `findings.md` can be replaced—undermining the new attestation contract and risking loss of the ballot. **Suggested fix:** Remove the `if not input_blocks(intext): return 0` shortcut (fail closed unless attested), or pass the bash-derived `INPUT_COUNT` into the validator and require `EMPTY_MERGE_ATTESTATION` whenever that count is at least 2, after aligning the heading grammar between `count_finding_blocks` and the Python parser.

- **correctness** `agents/orchestrator-aggregator.md:36-40` — The instructions require a “final line exactly” equal to `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED`, but the exemplar line in the prompt is written as Markdown inline code (backticks around the token), while the implementation only accepts a stripped full line equal to the bare string (`aggregate-findings.sh:314`). Models often copy delimiter characters from the prompt, so output like `` `LARCH_AGGREGATOR_EMPTY_MERGE_ATTESTED` `` or bullet-prefixed lines would fail attestation despite intent to comply. **Suggested fix:** Document the line as plain text only (for example a fenced `text` block showing the line with no backticks, or explicit wording such as “no backticks, bullets, or surrounding markdown”), matching the predicate the script uses.
