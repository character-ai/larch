### In-Scope Findings
- **risk-integration** `python/report_tokens_issue.py:29-48` — `_trim_sections()` treats any `redact.redact()` output under 65536 UTF-8 bytes as postable, but `gh.issue_create()` runs the body through `_fail_closed_redacted()` in `python/gh.py:141-146`, which raises `ShipError` when the redacted text contains the PEM fail-closed marker `[content truncated`. A report can therefore pass trimming and the byte gate in `post_issue()` yet still fail at issue-create time with a redaction error instead of a size-limit error, so the trim path does not guarantee a body that GitHub posting will accept. **Suggested fix:** Use the same fail-closed redaction helper (or an equivalent shared “postable body” function) inside `_trim_sections()` for measurement and early-exit, and treat fail-closed redaction failures like oversize bodies—continue dropping low-priority sections or fail with an explicit “unpostable after trim/redaction” error before calling `gh issue create`.

- **risk-integration** `python/test_report_tokens_issue.py:1-51` — The plan and acceptance criteria call for tests covering post-redaction byte trimming, banner immutability, oversize-after-trim failure, and `ShipError` propagation, but the module only checks tmpdir scrubbing and a single non-zero `gh` path. With no automated coverage of the 65536-byte trim loop or the post-trim hard failure at `python/report_tokens_issue.py:64-67`, regressions could reintroduce silent or misleading issue-post failures (the bugs this migration explicitly targets). **Suggested fix:** Add focused unit tests that build oversized `ReportSection` fixtures, assert sections drop in `SectionPriority` order with the truncation banner, verify fail-closed on still-oversize bodies, and pin stderr/exception behavior for `gh.issue_create()` failures.

### Out-of-Scope Observations
- **Observability regression:** The removed bash path printed `Analysis report issue created: <url>` on success; `post_issue()` / `report_tokens_cli.py` no longer emit the created issue URL, so operators must infer success from exit code alone.
- **Stdout vs issue redaction:** `report_tokens_cli.py` prints the full analysis (including the `Cache JSON:` temp path) before issue posting; only the GitHub issue body goes through `redact.redact()`. That matches local-analysis intent but differs from the fully scrubbed issue surface.
- **Partial success semantics:** On issue-post failure the CLI returns `EXIT_BAIL` (4) after stdout already contains the analysis; this is documented in `run-analysis.md` and is stricter than the old always-zero exit when issue creation failed.
