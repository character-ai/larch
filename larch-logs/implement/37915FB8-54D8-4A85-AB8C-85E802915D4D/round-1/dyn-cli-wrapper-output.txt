Reviewing the branch diff and key entrypoint files for risk-integration issues.
### In-Scope Findings

- **risk-integration** `Makefile:33-34` — The branch adds `skills/report-tokens/scripts/test-run-analysis-quiet.sh` as the mitigation for quiet-mode stream restoration (plan failure mode #4), but that harness is not registered in `Makefile`, `.pre-commit-config.yaml`, or any `test-harnesses-N` shard. CI only runs `make py-test` (`cd python && pytest`), so a regression that drops `exec 1>&3 2>&4` or breaks FD restore would ship with green checks. **Suggested fix:** Add a `test-run-analysis-quiet` Makefile target (mirroring other `skills/*/scripts/test-*.sh` harnesses) and wire it into an existing harness shard so CI exercises the wrapper under inherited `LARCH_QUIET_*` env.

- **risk-integration** `python/report_tokens_cli.py:61-68` — When the scan succeeds but finds zero parseable runs, the CLI prints “No parseable token reports found.” and returns `EXIT_OK` without attempting issue creation, even if `--no-issue` was not passed and `LARCH_REPORT_TOKENS_NO_ISSUE` is unset. The legacy embedded analyzer always called `create_report_issue(records, analysis_text)` after printing analysis unless `LARCH_REPORT_TOKENS_NO_ISSUE` was set, including for empty `records`. Automation that treats exit 0 as “report issue filed” will silently stop getting empty-state report issues. **Suggested fix:** On the empty-records path, either post a minimal skill-prefixed issue (matching prior behavior) or fail loudly / emit an explicit stderr notice and non-zero exit when issue posting was requested.

- **risk-integration** `python/report_tokens_cli.py:95-98` — Repo-slug and `gh issue create` failures now return `config.EXIT_BAIL` (4), while the old wrapper used `exit 1` for “could not resolve GitHub repo owner/name” (`run-analysis.sh` pre-migration). Callers or wrappers that key off exit code 1 for operator errors will misclassify these failures. **Suggested fix:** Use exit 1 (or document and test the new code) for repo-resolution and issue-posting failures in `report_tokens_cli.py`, keeping `EXIT_BAIL` for ship-pr semantics only if that constant is shared intentionally.

- **risk-integration** `python/report_tokens_scan.py:52-65` and `python/report_tokens_cli.py:58-60` — With issue posting enabled, a failed `gh repo view` no longer aborts before scanning (old bash validated `REPO` upfront and exited 1). The CLI now continues: `--no-issue` forces `repo_override="unknown/unknown"` and skips `gh`; otherwise scan emits an ERROR to stderr but still builds records with `https://github.com/unknown/unknown/issues/<N>` URLs (`report_tokens_scan.py:164-168`), prints full analysis, and only then fails at `post_issue` with exit 4. Operators get misleading issue links in stdout before the terminal failure. **Suggested fix:** When issue posting is requested and `_repo_slug` returns `None`, fail immediately after scan (before render/plot) with the same stderr message and a stable exit code; reserve the `unknown/unknown` placeholder strictly for `--no-issue` / `LARCH_REPORT_TOKENS_NO_ISSUE`.

- **risk-integration** `python/report_tokens_scan.py:52-54` — `LARCH_REPORT_TOKENS_REPO` values without a `/` are treated as invalid and become `None` with no format-specific stderr warning, unlike the old bash check `[[ "$REPO" != */* ]]`. A typo like `LARCH_REPORT_TOKENS_REPO=myorg-myrepo` produces the same late “could not resolve GitHub repo owner/name” error as a transient `gh` outage, making misconfiguration harder to diagnose in CI. **Suggested fix:** When an override is present but lacks `owner/repo` shape, print an explicit stderr error naming `LARCH_REPORT_TOKENS_REPO` and exit before scan/render.
