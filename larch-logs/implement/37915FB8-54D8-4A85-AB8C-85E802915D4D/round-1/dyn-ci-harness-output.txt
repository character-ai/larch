Reviewing CI/harness integration for the report-tokens migration: reading the diff and checking workflow, Makefile, and harness wiring.
### In-Scope Findings

- **risk-integration** `skills/report-tokens/scripts/test-run-analysis-quiet.sh:1-39` — The plan calls this harness out as the mitigation for failure mode #4 (quiet wrapper swallowing stdout/stderr) and the testing strategy says it should run via `make py-test` or harness registration, but the script is never wired: there is no `test-run-analysis-quiet` Makefile target, it is absent from all `test-harnesses-N` shards (including shard 5, which already runs `test-lib-quiet`), and `make py-test` only runs `cd python && pytest`, so CI’s `python-tests` job never executes it. A regression in `run-analysis.sh`’s `exec 1>&3 2>&4` restore (lines 77–81) can ship while unit tests stay green. **Suggested fix:** Add a `test-run-analysis-quiet` target wrapped with `scripts/harness-timer.sh`, register it on an appropriate shard (shard 5 beside `test-lib-quiet` is a natural fit), and extend `scripts/relevant-checks.sh` so edits under `skills/report-tokens/scripts/run-analysis.sh` or this harness trigger that target.

- **risk-integration** `Makefile:372-373` — `test-merge-parity` runs `python3 -m pytest python/test_merge_bash_parity.py` from the repo root, while `py-test` uses `cd python && pytest` with `python/pyproject.toml` `pythonpath = ["."]` (`Makefile:33-34`, `python/pyproject.toml:6-7`). That split means harness shard 5 and the `python-tests` job can disagree on import/config discovery if pytest layout changes, recreating the “parity regression only caught in one gate” risk this branch’s harness pytest pin was meant to close. **Suggested fix:** Align `test-merge-parity` with the `py-test` shape, e.g. `cd python && python3 -m pytest test_merge_bash_parity.py`, so both gates share one entrypoint.

- **risk-integration** `skills/report-tokens/scripts/test-run-analysis-quiet.sh:23` — The git shim falls back to `exec /usr/bin/git "$@"` when the stubbed `rev-parse` path is not taken. Ubuntu 24.04 CI images provide that path today, but the harness is not portable to environments where `git` lives elsewhere (and the harness is currently unrunnable in CI anyway). **Suggested fix:** Resolve git via `command -v git` (with a clear skip/fail if missing) instead of hardcoding `/usr/bin/git`, especially once the harness is added to the matrix.
