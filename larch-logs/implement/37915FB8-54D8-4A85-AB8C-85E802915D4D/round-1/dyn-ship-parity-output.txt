### In-Scope Findings

- **risk-integration** `skills/implement/SKILL.md:955,1020-1040` and `python/ship.py` (no `ship-pr-state.sh` writes) — Phase 7 documents a Python Step 8+ path that must not use `ship-pr-state.sh` for routing, but the detailed Exit 0/6 matrix still tells the orchestrator to read `PHASE` (and related keys) from that file. `python/ship.py` only writes `finalize-state.sh` via `finalize.write_finalize_state()` and never advances `PHASE`. After a successful `ship.py` exit 0, an agent following the Exit 0 bullet can still see `PHASE=checks` from the pre-ship seed and re-invoke **bash** `ship-pr.sh` instead of continuing to Step 16; transient Exit 6 retries also bucket on a stale phase name. **Suggested fix:** Add an explicit Python-path Exit 0/6 carve-out in `skills/implement/SKILL.md` (JSON `outcome`/`merge_result` is authoritative; skip `PHASE`-based re-invoke), and/or have `ship.py` emit a stable `phase` field and mirror minimal `ship-pr-state.sh` updates for keys the orchestrator still reads (`PHASE`, `OOS_PENDING`, `PR_CLOSED`).

- **risk-integration** `python/ship.py:33-91,411-416` — The stdout JSON contract exposes `outcome`, `needs_user_reason`, and `failed_run_id` but not the ship phase name. Step 8+ Exit 6 retry budgeting uses per-phase files (`ship-pr-net-retries-$PHASE.count` per `skills/implement/SKILL.md:1040`). With `LARCH_SHIP_PR_IMPL=python` and instructions not to read `ship-pr-state.sh`, there is no reliable phase token for those counters, so unrelated transient failures can share one bucket or retries can target the wrong phase. **Suggested fix:** Extend `ShipResult` / `to_json_dict()` with a `phase` (or `transient_phase`) string set at each terminal return, document it beside the Python driver selector, and map it to the existing counter filename grammar.

- **risk-integration** `python/report_tokens_cli.py:58-59` and `python/report_tokens_scan.py:164` — When `--no-issue` is set and `gh repo view` fails, the CLI sets `repo_override = "unknown/unknown"`. Scan then builds issue links like `https://github.com/unknown/unknown/issues/N` in tables such as `_top_runs` (`python/report_tokens_render.py:91`). That contradicts the plan’s “fail loud / don’t fabricate slugs” posture and produces plausible-but-wrong GitHub URLs in stdout. **Suggested fix:** Only use a real slug from `gh`/`LARCH_REPORT_TOKENS_REPO`; when slug resolution fails, omit hyperlinks (issue number only) and keep stderr errors—do not inject `unknown/unknown` for URL construction.

- **risk-integration** `python/report_tokens_scan.py:40-49,200-212` — On `git rev-parse` failure, scan root falls back to `Path.cwd()` with only a stderr warning. Running `/report-tokens` outside the intended repo (or during a transient git failure) can scan the wrong `larch-logs/` tree or find nothing while still exiting 0 for an empty scan, which is a silent integration risk for cost reporting. **Suggested fix:** Treat an unresolvable repo root like slug failure: exit non-zero with a clear stderr message unless the operator sets an explicit repo root override env var documented in `run-analysis.md`.
