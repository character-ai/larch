Reviewing issue-posting paths: reading the diff and key files for risk-integration findings.
### In-Scope Findings

- **risk-integration** `python/report_tokens_cli.py:97-110`, `python/report_tokens_issue.py:74-97` — Successful `gh issue create` no longer prints the created issue URL to stdout. The removed bash path printed `Analysis report issue created: <url>` on success (see diff removal around old `run-analysis.sh` ~7835); the new `post_issue` path only emits stderr on failure and returns silently on success. Operators and automation that relied on stdout to locate the filed report get no durable pointer unless they parse `gh` output themselves. **Suggested fix:** After a zero exit from `gh.issue_create`, print the trimmed URL from `result.stdout` to stdout (same contract as before), e.g. `Analysis report issue created: …`, and add a CLI test that asserts the line appears when posting is enabled.

- **risk-integration** `python/report_tokens_issue.py:39-40`, `62-66`, `81-87`, `python/gh.py:149-163`, `829-842` — Issue bodies are redacted up to three times: `_posting_body` calls `redact.redact()` twice, then `gh.issue_create` runs `_fail_closed_redacted()` (another `redact.redact()`) before writing `--body-file`. The implementation plan requires measuring and trimming on the single final redacted UTF-8 string that will be posted. Extra passes are redundant for most content (tests show idempotency for tmpdir paths) but break the contract: trim budgets against a double-redacted string while GitHub receives a third pass, and any PEM edge case that injects `[content truncated — unterminated PEM block…]` during redaction can pass trim yet make `gh.issue_create` raise `ShipError` via `_fail_closed_redacted`, failing the run after trimming. **Suggested fix:** Redact exactly once in `report_tokens_issue` (e.g. `_posting_body` → single `redact.redact`), measure/trim that string, and either pass it to `gh.issue_create` with a `body_pre_redacted=True` flag that skips `_fail_closed_redacted` in `_body_file_args`, or move trim after the same `_fail_closed_redacted` helper `gh` uses so measurement matches the posted file bytes.

### Out-of-Scope Observations

- **risk-integration** `python/report_tokens_render.py:212` — Stdout analysis still appends an unredacted `Cache JSON: {temp_path}` line; that predates the issue-posting change and is outside the filed-issue contract, but it can leak session tmpdir paths to the terminal transcript.

- **correctness** `python/config.py:84` — The GitHub cap is enforced as UTF-8 byte length (`65536`); if GitHub’s API limit is character-based, very wide Unicode could diverge slightly; the plan explicitly chose bytes, so this is a known modeling choice rather than a branch regression.
