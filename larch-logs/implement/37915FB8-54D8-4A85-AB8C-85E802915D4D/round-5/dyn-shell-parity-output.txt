Reviewing the branch diff for shell-parity and risk-integration issues, focusing on Python vs shell contract alignment.
### In-Scope Findings

- **risk-integration** `python/merge.py:137-142` — After head-OID checks, the Python merge path calls `_attempt_merge` directly and never runs the same-version bump gate that `scripts/merge-pr.sh` still executes (`origin/main` fetch, `Bump version to X.Y.Z` subject scan, `version_already_published` / `main_advanced` short-circuits at `scripts/merge-pr.sh:328-365`). `_version_race_gate` is a no-op stub (`python/merge.py:362-369`), and `test_merge_pr_ignores_obsolete_version_race_gate` locks that in, while `test_merge_bash_parity.py` still only pins the bash path for the staleness scenario (`test_behind_staleness_safety_emits_main_advanced`). With `LARCH_SHIP_PR_IMPL=python`, release-bump branches can reach `gh pr merge` where bash would have stopped with `version_already_published` or `main_advanced`. **Suggested fix:** Either port the bash gate into `merge_pr` before `_attempt_merge`, or remove/guard the bash gate and document that both paths intentionally skip it post–#3364; extend `test_merge_bash_parity.py` with a paired Python-vs-bash case so the harness cannot drift silently.

- **risk-integration** `python/run_context.py:88` — `RunContext.from_env()` sets `merge=_env_bool(source, "MERGE", default=True)`, so a missing `MERGE` env var enables the merge/CI loop. Default `/implement` runs use `merge=false` unless `--merge` is set; `ship-pr.sh` passes `--merge "$merge"` explicitly (`skills/implement/SKILL.md:1002-1007`), but `MERGE` is not written into `session-env.sh`. Any `python3 …/ship.py` invocation that omits `--merge` (manual runs, partial tests, or a thin wrapper that only exports `IMPLEMENT_TMPDIR`) will treat merge as enabled and drive CI/merge/postmerge. **Suggested fix:** Change the default to `False` to match orchestrator semantics, or require an explicit `--merge` argv and fail closed when it is absent; add a CLI test that env-only startup without `MERGE` leaves `ctx.merge` false.

- **risk-integration** `python/run_logs.py:587-594` — `flush_logs_post` catches every `ShipError` and returns `RefreshSkip(skipped=True, reason="redaction-failed")`, but `_write_final_report` raises `ShipError("write-final-report.sh failed")` on non-zero exit (`python/run_logs.py:500-505`). Post-merge refresh failures are mislabeled as redaction failures, which steers `ship.py` postmerge (`python/ship.py:268-271`) and merge `_post_flush` down the wrong remediation path. **Suggested fix:** Catch redaction failures explicitly (e.g. only from `_redact_batch_payload` / `"[content truncated"` paths) and propagate distinct skip reasons such as `final-report-failed` vs `redaction-failed`; add a unit test where a failing `write-final-report.sh` stub surfaces the correct reason.

- **risk-integration** `scripts/restore-finalize-state.sh:77-83` — The new early return skips rebuilding `finalize-state.sh` from `ship-pr-state.sh` when finalize already has `PR_NUMBER` but ship state does not. That avoids clobbering a good PR number, but it also skips merging other finalize keys (`STALL_TRACKING`, `MERGE_RESULT`, `NO_LOGS_COMMIT`, etc.) from ship state into the file Step 18 `implement-finalize.sh teardown` reads. A partial Python postmerge write plus an empty/partial `ship-pr-state.sh` can leave teardown with an incomplete `finalize-state.sh`. **Suggested fix:** Merge ship state into finalize field-by-field (ship wins only where ship has a non-empty value) instead of all-or-nothing skip, or require the full key set in finalize before skipping; add a harness where finalize has `PR_NUMBER` only and ship state carries the remaining required keys.
