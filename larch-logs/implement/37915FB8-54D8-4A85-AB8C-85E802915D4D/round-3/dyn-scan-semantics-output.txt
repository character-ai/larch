Reviewing scan semantics against the plan: reading the diff, `report_tokens_scan`, and its tests.
Comparing scan behavior with the legacy script and checking edge cases in manifest/limit/workflow handling.
### In-Scope Findings

- **correctness** `python/report_tokens_scan.py:173-176` — After a token report parses as JSON, `_record` treats any falsy mapping (`{}`, or a non-object such as `[]` / `"..."` coerced via `_as_mapping`) as an immediate `return None` with no stderr warning. That violates the documented fail-soft contract (`run-analysis.md` and the plan: invalid or schema-incomplete token reports must warn and skip, never disappear quietly). Operators can lose whole runs when logs contain an empty object or the wrong JSON shape, and the run count in the analysis will drop with no explanation. **Suggested fix:** After `_json_file`, if `report_obj is not None` and the value is not a `dict`, emit a warning naming the path and skip; if it is a `dict` but `not _has_numeric_tokens(report)`, reuse the existing “lacks vendor totals/BUCKETS…” warning (do not return silently on `{}`).

- **correctness** `python/report_tokens_scan.py:31-36,157-164` — `_json_file` returns `None` for a successfully parsed JSON `null` literal without logging anything (`json.loads("null")` is not an error). `_record` then hits `if not manifest:` / `if not report:` and skips with no warning, which is indistinguishable from a missing file and breaks the plan’s “invalid manifest.json → warn, skip” behavior. **Suggested fix:** In `_json_file`, treat a `None` parse result like invalid JSON (`_warn(...); return None`) or return a sentinel; in `_record`, distinguish “file missing” from “parsed null / wrong type” so every skipped run logs a reason.

- **correctness** `python/report_tokens_scan.py:88-106` — Workflow resolution no longer matches `scripts/read-workflow-path.sh`: when `timing-report*.json` or `run-params.json` exists and is valid JSON but lacks `workflow_path` / `design_classification` in `SIMPLE`/`HARD`, the scanner silently sets `workflow` to `"unknown"` and (for design) downstream render/plot code drops those runs from SIMPLE/HARD trend/plot series (`report_tokens_render.py:28-30`, `report_tokens_plot.py:35-36`) without the legacy `**⚠ read-workflow-path: …; defaulting to unknown**` stderr signal. That makes misclassified or missing workflow metadata harder to detect and can under-count design-tier trends. **Suggested fix:** When `_workflow_from` returns `"unknown"` for a readable file, emit a stderr warning patterned on `read-workflow-path.sh` (include the path); keep the `"unknown"` value for implement aggregation.

### Out-of-Scope Observations

- `python/test_report_tokens_scan.py` — The plan called for fixtures covering bad token-report JSON, bad manifest JSON, and schema-incomplete token reports; tests cover empty manifest, missing token file, incomplete tokens (`good_tokens=False`), and invalid auxiliary JSON, but not empty/non-object/`null` token reports, invalid manifest syntax, or `null` manifest. Adding those cases would lock in the fixes above.

- Pre-existing plan quirks (unchanged): `LARCH_REPORT_TOKENS_LIMIT` stops after N lexicographically first run directories regardless of parse success; duplicate `issue_number` values across dirs are not deduplicated; plot uses `closed_at` while per-day tables use `started_at`.
