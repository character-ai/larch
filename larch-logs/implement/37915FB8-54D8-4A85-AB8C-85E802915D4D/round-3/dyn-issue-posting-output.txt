Reviewing issue-posting and failure-propagation paths in the diff and source files.
### In-Scope Findings

- **risk-integration** `python/report_tokens_issue.py:92-97` — On `gh issue create` failure, `post_issue` forwards `(result.stderr or result.stdout)` into the operator-visible error line without passing it through `redact.redact()`, while the success path at lines 99–101 does redact. A failed `gh` invocation can echo repo paths, temp body-file paths, or token-shaped substrings from GitHub’s CLI output onto real stderr, which is the opposite of the single redaction pass used for the posted body and conflicts with the repo’s outbound-diagnostic hygiene elsewhere (e.g. `merge.redact_merge_diagnostic`). **Suggested fix:** Run the failure `detail` through `redact.redact()` (or `redact.redact_outbound`) before formatting/printing the `ERROR: gh issue create failed …` message, matching the success-path handling.

- **risk-integration** `python/report_tokens_cli.py:88-109` — The CLI always prints the full markdown analysis (including the `Cache JSON:` trailer from `render`) and plot status to stdout before calling `post_issue`; if filing then fails, it returns `config.EXIT_BAIL` (4) after only re-raising `ShipError`, with no additional stdout/stderr contract that the GitHub report was not created. Callers or wrappers that grep stdout for `## Report Tokens Analysis` / `Cache JSON:` but do not enforce exit status can treat a failed issue post as a complete successful run—the regression this branch was meant to fix for silent lib-quiet failures, applied to a different failure surface. **Suggested fix:** On issue-post failure, emit an explicit stderr banner (e.g. `ERROR: analysis printed but GitHub issue was not filed`) and/or avoid appending anything to stdout after the analysis block; document that exit code 4 means “analysis only.”

- **risk-integration** `python/report_tokens_issue.py:99-103` — After a successful `gh issue create`, `post_issue` prints the issue URL (or a fallback title line) to stdout, but `skills/report-tokens/scripts/run-analysis.md` documents that stdout ends with `Cache JSON: <path>`, and `report_tokens_cli.py` already prints plot paths after the analysis block when plotting is enabled. Issue-filing output on stdout makes the stream non-terminal for cache-path consumers and mixes operational metadata with the analysis artifact. **Suggested fix:** Print the created-issue URL on stderr (or fold it into a single final stdout block before the cache trailer), and align `run-analysis.md` / `SKILL.md` with the chosen stream contract.

### Out-of-Scope Observations

- Plot generation in `report_tokens_cli.py` also appends lines after the analysis string, so the documented “stdout ending with `Cache JSON:`” contract was already loosened for `--no-plot` vs default plot behavior before issue posting; that is adjacent stdout-contract drift, not introduced solely by `gh.issue_create`.
- `SectionPriority.BANNER` is defined in `report_tokens_models.py` but no `ReportSection` uses it in `report_tokens_render.py`; trimming cannot protect a dedicated banner section today (only the dynamically prepended truncation notice).
- `_posting_body` applies `redact.redact()` twice and `gh.issue_create` redacts again in `_body_file_args`; `redact()` is documented idempotent, so this is redundant rather than a sizing bug under normal content.
