Reviewing the scan pipeline: reading the diff and `report_tokens_scan.py`.
### In-Scope Findings

- **correctness** `python/report_tokens_scan.py:91-119` — `_workflow_from` only accepts `workflow_path` / `design_classification` when they are exactly `SIMPLE` or `HARD`, and otherwise returns `unknown`. It does not implement the third step of `scripts/read-workflow-path.sh`, which delegates to `scripts/read-design-classification.sh` and **defaults missing or invalid `design_classification` to `HARD`**. The old bash scanner used `read-workflow-path.sh` on timing/run-params, so those runs were billed as HARD. Here they stay `unknown`, and `report_tokens_render._workflow_groups` drops `unknown` from design per-day trends and plots (`python/report_tokens_render.py:31-38`), so design cost can be under-reported for older or partial run-params. **Suggested fix:** After the two-key scan in `_workflow_from`, if the artifact is `run-params.json` (or generally when classification is absent/invalid), apply the same fail-closed rule as `read-design-classification.sh` and return `HARD` with an stderr notice; keep invalid non-tier values as `unknown` with a warning.

- **correctness** `python/report_tokens_scan.py:285-290` — `LARCH_REPORT_TOKENS_LIMIT` is applied to every directory returned by `_run_dirs` via the `seen` counter, but the removed bash loop only incremented `run_count` after both `manifest.json` and the skill-specific token report file were present (`diff.txt` around the old `run-analysis.sh` loop). Empty, partial, or junk run directories therefore consume the limit before later valid runs are visited when operators set a cap. **Suggested fix:** Increment/limit only on directories that pass the same eligibility gate as `_record` (at minimum: readable `manifest.json` with positive `issue_number` and present skill token-report basename), or stop the loop only after N successfully parsed records if the intended semantics are “N runs analyzed.”

### Out-of-Scope Observations

- **correctness** `python/report_tokens_scan.py:272-291` — Duplicate `issue_number` values across multiple run directories are still aggregated with no deduplication; the plan documents this as a known quirk and the old scanner behaved the same way.

- **correctness** `python/report_tokens_scan.py:225-227` / `python/report_tokens_render.py:131-148` / `python/report_tokens_plot.py:37-40` — Plot series use `closed_at` while per-day tables use `started_at`; that date-axis split predates this branch and is called out in the plan edge cases.

- **code-quality** `python/report_tokens_scan.py:196-198` — An empty `{}` manifest triggers the same warning text as a missing `issue_number` (`lacks numeric issue_number`), which can mislead debugging; behavior (skip run) is correct.
