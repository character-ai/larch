Reviewing the branch diff and tracing stderr-tail FD routing through producers and callers.
### In-Scope Findings
- **risk-integration** `scripts/launch-cursor-implement.sh:325-333` — On agent failure after `run-external-agent --capture-stdout-only`, the launcher unconditionally calls `write_failed_agent_stderr_tail "$_FAILURE_OUTPUT" "$TRANSCRIPT_PATH"` with `_FAILURE_OUTPUT` defaulting to non-empty `$SIDECAR_LOG` (wrapper progress plus merged `2>&1` capture from `>$SIDECAR_LOG 2>&1`). That runs even when `run-external-agent` has already written a `${TRANSCRIPT_PATH}.stderr-tail` from `${TRANSCRIPT_PATH}.diag`, and the fallback to `.diag` only applies when the sidecar is empty (`[[ ! -s "$_FAILURE_OUTPUT" && -s "${TRANSCRIPT_PATH}.diag" ]]`). A noisy sidecar can overwrite a better agent stderr tail before `step2-implement.sh` surfaces it via `emit_failed_agent_stderr_tail_larch_err`, weakening or misleading chat output on the cursor-implement lane. **Suggested fix:** Treat `run-external-agent` as the producer on the agent path: skip the post-loop write when `[[ -s "${TRANSCRIPT_PATH}.stderr-tail" ]]`, or prefer `${TRANSCRIPT_PATH}.diag` over `$SIDECAR_LOG` when both are non-empty (matching the manifest-`bailed` block at `354-361` and the plan’s “verify mode first / no clobber” rule). Keep explicit `write_failed_agent_stderr_tail` only for pre-agent paths (model-args, preflight) where `run-external-agent` never runs.

### Out-of-Scope Observations
- **risk-integration** `skills/review-and-fix/scripts/review-and-fix.sh:7-14` — Step 5 lint stderr surfacing uses `emit_failed_agent_stderr_tail_larch_err` only after `lint-fix-loop.sh` is invoked with `2>&1` capture into `$lint_out`; the emit itself runs in the parent loop with `LARCH_QUIET_DISABLE=1`, so tails go to real FD 2 rather than quiet-mode FD 4. That matches existing review-and-fix diagnostics and is not introduced by the #3227 consumer wiring, but any future wrapper that redirects review-and-fix stderr to a file would swallow Step 5 tails unless surfacing is moved to a caller with an unredirected FD 4 path.

That may be desirable forensics or stale noise depending on failure mode; not a new FD-routing defect from this branch.
