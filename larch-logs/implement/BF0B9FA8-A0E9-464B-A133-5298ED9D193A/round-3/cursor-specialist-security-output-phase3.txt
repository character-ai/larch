### In-Scope Findings

1. **latent** `security` `scripts/check-reviewers.sh:73-76,118-124` — `TMPDIR` is used without canonicalization or traversal-checking in both the stamp path constructor (`larch_stamp_path`) and the `mktemp -p "${TMPDIR:-/tmp}"` call inside `larch_write_bool_stamp`. An operator running in a CI environment where an attacker controls `TMPDIR` (e.g., `TMPDIR=/tmp/foo/../../root/.ssh`) could redirect stamp `mktemp` calls and the subsequent `mv` to arbitrary filesystem locations writable by the current user. Stamp content is restricted to `true`/`false`, so confidentiality is not at risk, but unexpected file creation at attacker-chosen paths is possible. The `mktemp || return 1` guard means the attack fails if the directory is not writable, limiting practical impact. **Suggested fix:** at script entry add a guard such as `[[ -d "${TMPDIR:-/tmp}" && -w "${TMPDIR:-/tmp}" ]] || TMPDIR=/tmp` before `TMPDIR` is used in probe-file and stamp-path construction.

2. **latent** `security` `scripts/check-reviewers.sh:179-181` — The Codex probe sidecar is derived from the `mktemp` output as `probe_out + ".sidecar"` without its own `mktemp` call, then created with `: >"$probe_side"`. In a shared `/tmp`, an attacker monitoring the directory for newly created files matching the prefix could race to place a symlink at `probe_out.sidecar` pointing to a user-writable victim file before `: >"$probe_side"` runs, causing that file to be truncated. The race window is extremely narrow (two consecutive shell statements), but the pattern is structurally TOCTOU-unsafe. **Suggested fix:** create the sidecar with its own `mktemp` call (`probe_side=$(mktemp "${TMPDIR:-/tmp}/larch-codex-probe-side.XXXXXX")`) so both files get independently random names, eliminating the predictable relationship.

3. **nit** `code-quality` `scripts/session-setup.sh:424-429` — `CALLER_CODEX_BINARY_FOUND` and `CALLER_CURSOR_BINARY_FOUND` read from the caller-env file are passed to `emit_kv` without first validating they are exactly `true` or `false`. The new keys follow the same pre-existing pattern as `CALLER_CODEX_PRESENT`. Downstream `write-session-env.sh` does validate the values before writing to session-env, so the overall chain catches bad inputs, but a tampered caller-env value propagates further into `session-setup.sh` stdout than needed before being rejected. **Suggested fix:** add a `[[ "$CALLER_CODEX_BINARY_FOUND" == "true" || "$CALLER_CODEX_BINARY_FOUND" == "false" ]]` guard before `emit_kv`, matching the style used by `write-session-env.sh` for the same values.
