### In-Scope Findings

1. **security** `scripts/check-reviewers.sh:75` — **Latent** — TMPDIR stamp poisoning: `larch_stamp_path` builds the stamp path as `${TMPDIR:-/tmp}/larch-${1}-present-${_u:-larch}.stamp`, trusting the `TMPDIR` environment variable without sanitization or containment check. A local attacker who controls `TMPDIR` (or any process running as the same user that sets `TMPDIR` before `check-reviewers.sh` runs) can pre-seed the expected stamp file with content `true` and a current mtime, causing the probe to report `CURSOR_PRESENT=true` or `CODEX_PRESENT=true` without executing the runtime health check. Concrete scenario: `TMPDIR=/tmp/attacker-dir`, pre-create `/tmp/attacker-dir/larch-cursor-present-$(whoami).stamp` containing `true` with a fresh timestamp — any subsequent `check-reviewers.sh` invocation within `LARCH_PROBE_TTL_SECONDS` will cache-hit and skip auth entirely, allowing a broken/malicious cursor binary to be treated as healthy by `/implement`. **Suggested fix:** Derive stamp paths from a fixed prefix that does not vary with `TMPDIR` — for example `${HOME}/.cache/larch/stamps/` (already used for session tmpdirs in `session-setup.sh`) or `${XDG_RUNTIME_DIR:-/tmp}` validated against a known absolute prefix via `realpath` — so environment manipulation cannot redirect stamp reads or writes. Alternatively, explicitly document that `TMPDIR` is trusted and warn in the script header that the stamp TTL provides no security boundary when `TMPDIR` is attacker-controlled.

2. **risk-integration** `scripts/check-reviewers.sh:226-250` — **Latent** — `cursor_launcher_cleanup_private_config_dir` is always called after the setup/probe block, even when `cursor_launcher_setup_private_config_dir` never ran (because `cursor_preread_service_token` or `cursor_auth_argv` failed first). If the cleanup function is not a robust no-op when setup was never invoked (e.g., it unconditionally removes a dir computed from a global that was never set), this could silently corrupt the user's real Cursor config directory rather than the private probe copy. The plan acknowledges "`cursor_launcher_setup_private_config_dir` fails → set `CURSOR_PRESENT=false`, skip loop" but does not address the cleanup-after-partial-setup path. **Suggested fix:** Guard the cleanup with the same boolean that tracks whether setup succeeded (e.g., introduce `_cursor_setup_ok=false` before the setup block and set it to `true` only on full success), so cleanup is skipped when no private dir was ever created.

### Out-of-Scope Observations

1. **security** `scripts/check-reviewers.sh:155-156` — **Latent** — cursor authentication tokens that `cursor_auth_argv` injects into `CURSOR_AUTH_ARGS` appear in the process argv (`cursor agent … --api-key $TOKEN`) for the duration of the probe subprocess, making them visible in `/proc/$pid/cmdline` and `ps aux` output to co-users. This is a pre-existing pattern shared with all Cursor launchers and is not introduced by this diff; noting it here in case hardening (e.g., via environment variable passing instead of CLI args) is planned in a follow-up. Out of scope because this pattern predates the branch.
