### In-Scope Findings

1. **security** `scripts/check-reviewers.sh:225-231` — `${USER:-larch}` is interpolated directly into stamp file paths in `larch_stamp_path_cursor` and `larch_stamp_path_codex` without any sanitization. If an attacker controls the process environment (e.g., via a malicious CI runner or wrapper script), setting `USER='../../etc/cron.d/evil'` causes `larch_write_bool_stamp` to create or overwrite a file at an arbitrary path outside `$TMPDIR` — the full path resolves via the shell to whatever the adversarial `USER` component dictates. The atomicity of `mktemp+mv` doesn't help here because the *destination* path is the vector. **Suggested fix:** Sanitize `USER` before embedding it in the path, e.g., `local _u="${USER//[^A-Za-z0-9._-]/}"; printf '%s' "${TMPDIR:-/tmp}/larch-cursor-present-${_u:-larch}.stamp"`.

2. **security** `scripts/check-reviewers.sh:322-323` — In `larch_run_one_codex_probe`, `probe_side="${probe_out}.sidecar"` derives the sidecar path by appending a fixed suffix to a mktemp filename, then creates it non-atomically with `: >"$probe_side"`. Although the random suffix inherited from `probe_out` makes the path hard to predict, the sidecar is not itself mktemp'd — there is a TOCTOU window between derivation and creation that a same-UID attacker on a sticky-less `/tmp` could exploit with a pre-placed symlink, redirecting the stderr from the `codex exec` background process to an arbitrary file owned by the victim. **Suggested fix:** Replace the derived name with a second `mktemp` call: `probe_side=$(mktemp "${TMPDIR:-/tmp}/larch-codex-probe-side.XXXXXX") || { rm -f "$probe_out"; return 1; }`.
