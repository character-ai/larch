### In-Scope Findings

1. **correctness** `skills/implement/SKILL.md:1433-1434` — The Option A bail messages say "Cursor/Codex runtime probe failed" unconditionally, but `cursor_available=false` also fires when `CURSOR_BINARY_FOUND=false` (binary not installed at all). The two-tier distinction (`BINARY_FOUND=false` → "binary not found" vs `PRESENT=false` → "probe failed") is carefully established in Step 0 warnings and `external-reviewers.md`, but the Option A bail messages collapse both into "runtime probe failed." Concrete scenario: a user who never installed Cursor runs with `--coder=cursor` and sees "Cursor runtime probe failed. Re-run without --coder" instead of the more actionable "Cursor binary not found." **Suggested fix:** split the Option A bail into two sub-bullets: one for `CURSOR_BINARY_FOUND=false` (say "binary not found") and one for `CURSOR_PRESENT=false && CURSOR_BINARY_FOUND=true` (say "runtime probe failed"), consistent with the Step 0 warning pattern already on the same page.

2. **risk-integration** `skills/implement/scripts/test-step2-dispatch.sh:1595` — The Test 3e assertion `! grep -Eiq 'error|fatal|failed' <<<"$ERR"` runs with `LARCH_QUIET_DISABLE=1` (verbose mode), making it sensitive to any diagnostic text emitted to stderr that contains "error", "fatal", or "failed" — including phrases like "retry after failure" or soft-fallback messages from larch launcher helpers. All other tests in this file combine stdout+stderr with `2>&1` and don't apply this grep filter; Test 3e uniquely separates stderr and requires it to be clean, which is a stricter contract. Concrete failure scenario: a future change to `lib-cursor-launcher-common.sh` that adds a diagnostic `larch_warn "auth preflight returned non-fatal failure"` would cause Test 3e to fail even though the actual dispatch result is correct. **Suggested fix:** either narrow the grep to only critical-exit signals (e.g., `FATAL:` prefix) or accept "failed" appearing in informational messages and remove the filter, relying on the existing `STATUS=bailed REASON=stub-bailed` assertion to verify correctness.

3. **correctness** `scripts/check-reviewers.sh` `larch_try_read_fresh_stamp` (~line 258) — `age=$((now - mtime))` has no guard against negative values. If the stamp file carries a future mtime (NTP correction, cross-host filesystem, or manually `touch -t <future>`), `age` is negative and `(( age > LARCH_PROBE_TTL_SECONDS ))` is false for any positive TTL, making the stamp appear perpetually fresh until the clock catches up. Since `larch_write_bool_stamp` uses the current time at write, this can only occur if a pre-existing stamp has a future mtime. **Suggested fix:** add `if (( age < 0 )); then return 1; fi` after computing `age` to treat future-dated stamps as cache misses.
