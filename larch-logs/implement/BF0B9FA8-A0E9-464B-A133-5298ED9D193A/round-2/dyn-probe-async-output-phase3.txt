### In-Scope Findings

- **correctness** `scripts/check-reviewers.sh:131-134,146-151` — `larch_run_one_cursor_probe` sets `probe_rc=124` in the timeout branch (lines 133-134), but immediately after the polling loop the auth-failure check at line 146 (`if external_is_auth_failure "cursor" "$probe_out"; then`) runs unconditionally regardless of `probe_rc`. If the killed Cursor process had already emitted auth-shaped text to stdout/stderr before the timeout was hit, `external_is_auth_failure` returns true, the inner guard `AUTH_ATTEMPT < MAX_AUTH_RETRIES` passes, and the function returns 2 — consuming an auth-retry slot for what is effectively a timeout event. The implementation plan explicitly states: "Probe timeout: timeout poll kills PID, sets `probe_rc=124`, *treats as non-auth failure*." The code does not implement that guarantee. The identical defect exists in `larch_run_one_codex_probe` at lines 188-193 (Codex auth-failure check runs without a `probe_rc != 124` guard). In a realistic scenario where a Codex or Cursor process starts printing an auth error before getting stuck and timing out, all `MAX_AUTH_RETRIES` slots would be consumed by the repeated timeouts, leaving no retries available for a clean auth-error retry on a less-loaded attempt. **Suggested fix:** Guard both auth-failure checks with `(( probe_rc != 124 )) &&` (or add an explicit `if (( probe_rc == 124 )); then rm -f ...; return 1; fi` guard immediately after the timeout-`break` fallthrough at line 141/182) so timed-out probes always classify as hard failures (return 1) rather than auth retries (return 2).

- **correctness** `scripts/check-reviewers.sh:127,169` — `SECONDS=0` inside `larch_run_one_cursor_probe` (line 127) and `larch_run_one_codex_probe` (line 169) resets the shell-global `SECONDS` builtin. These are ordinary shell functions (not subshells), so the reset is visible to all surrounding code. For the current sequential layout — Cursor probe loop finishes completely before the Codex probe loop starts — the global reset is harmless. However, if a future refactor runs both probe retry loops concurrently (e.g. `larch_run_one_cursor_probe & larch_run_one_codex_probe &`), interleaved `SECONDS=0` resets from one function would silently corrupt the timeout counter of the other, causing both probes to never time out (each reset restarts the other's window). There is no comment at either call site documenting the sequential-only constraint. **Suggested fix:** Use a `PROBE_SECONDS_START=$SECONDS` local reference point instead of resetting the global: `(( elapsed = SECONDS - PROBE_SECONDS_START ))` for the timeout check. This is Bash 3.2-compatible, makes each probe function self-contained, and survives any future concurrent invocation.
