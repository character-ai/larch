Reviewing the flush-split invariant across `run_logs.py`, `merge.py`, and related config—reading the diff and source files.
### In-Scope Findings

- **architecture** `python/run_logs.py:198-211,267-278` — `flush_logs_pre` renders token/timing batches under `ctx.tmpdir/larch-logs/implement/<run_id>/`, but `_larch_log_commit` never copies that tree into the consumer repo before committing. It unconditionally runs `git.add(runner, "larch-logs", cwd=cwd)` against the **repository** `larch-logs/`, so the pre-push path can commit unrelated or stale repo log state while leaving the freshly rendered tmpdir artifacts uncommitted. That breaks the intended pre-push contract (parity with `larch-log.sh commit`, which copies `src_path` → `repo_path` then scopes git to `larch-logs/$SKILL/$RUN_ID`). **Suggested fix:** Port the `larch-log.sh commit` copy/publish steps (tmpdir run dir → `larch-logs/implement/<run_id>`, scoped `git add`/`status`/`commit` on that rel path only, `no-changes` short-circuit) inside `_larch_log_commit` or a dedicated helper; only call `git.commit` when the scoped pathspec has staged changes.

- **architecture** `python/run_logs.py:267-278` — Even after a correct copy step, staging the entire top-level `larch-logs` pathspec is broader than bash (`git add -- larch-logs/implement/$run_id`), so concurrent or multi-run dirty paths under `larch-logs/` could be swept into a flush commit. **Suggested fix:** Scope all pre-push git operations to `larch-logs/implement/{ctx.run_id}` (validate `run_id` with `validate_run_id_slug` first), matching `scripts/larch-log.sh` lines 534–545.

- **architecture** `python/merge.py:56-58` — `merge_pr` treats only `reason == "commit-failed"` as fatal; every other `flush_logs_pre` skip (`state-file-missing-fail-closed`, `post-merge`, `no-run-id`, etc.) is ignored and merge proceeds. That weakens the cross-module invariant that merge should not run when pre-push refresh was intentionally skipped (bash documents missing state as fail-closed “treat as merged”). Phase 7 can still pass `state_file`, but nothing in `merge_pr` enforces that boundary today. **Suggested fix:** Either require a successful non-skipped `flush_logs_pre` before merge (return `MERGE_RESULT_ERROR` on any `skip.skipped`), or explicitly whitelist skip reasons that are safe to continue past (document each in `config.py`) and fail closed on the rest—including missing `state_file` when `merge` is true.

- **architecture** `python/run_logs.py:58-59,142-163` — Manifest I/O uses `ctx.tmpdir/manifest.json`, while batches and bash recovery live under `ctx.tmpdir/larch-logs/implement/<run_id>/` (bash: `mf_impl="$log_root/implement/$run_id/manifest.json"`). `RunContext.manifest_path` is unused, so `load_or_recover_manifest` recovery from log dirs never reconciles with the manifest file `update_manifest` writes—corrupt/missing top-level manifest can silently re-init via `init_run` and drop `steps_ran` that only existed in a run-scoped manifest. **Suggested fix:** Single canonical manifest path under `larch-logs/implement/<run_id>/manifest.json` (derive from `ctx.run_id` + slug guard), align recovery to read that path first, and drop or wire `manifest_path` on `RunContext` to the same location.

- **correctness** `python/run_logs.py:209-210` — `commit-failed` is a bare string literal, not a `config.REFRESH_SKIP_*` constant, while `merge.py:57` hard-codes the same literal for the only handled skip. A typo on either side would stop aborting merge on commit failure. **Suggested fix:** Add `REFRESH_SKIP_COMMIT_FAILED = "commit-failed"` (and optionally `REFRESH_SKIP_NO_CHANGES`) to `config.py`; use it in `run_logs.flush_logs_pre`, `merge.merge_pr`, and tests.
