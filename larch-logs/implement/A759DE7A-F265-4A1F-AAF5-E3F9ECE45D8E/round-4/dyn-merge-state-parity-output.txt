Reviewing merge-state parity: reading the diff and tracing `merge.py` against `merge-pr.sh` and the plan.
### In-Scope Findings

- **correctness** `python/merge.py:240-242` — `_ensure_head_matches_pr` treats a failed `git rev-parse HEAD` (`try_rev_parse` returns `None`, or an empty string) as success via `if not local_head or local_head == state.head_ref_oid: return state`, so the function never reaches the bash-parity error path that `merge-pr.sh` takes when `LOCAL_HEAD` is empty but `PR_HEAD_OID` is set (lines 272–342: mismatch block → `MERGE_RESULT=error` with “refusing to evaluate same-version gate”). After CI/admin gates pass, `merge_pr` can continue into `_version_race_gate` and `_attempt_merge` without establishing that local HEAD matches the PR head OID. **Suggested fix:** Only short-circuit when `local_head` is non-empty and equals `state.head_ref_oid`; if `local_head` is missing/empty, return `MergeResult(result=MERGE_RESULT_ERROR, error=...)` (mirror bash’s mismatch message, or a dedicated “could not resolve local HEAD” diagnostic) before flush recovery or the version gate.

- **correctness** `python/merge.py:169-172` — `_merge_noop_if_pr_closed` catches `ShipError` from `gh.pr_view` and returns `None`, so a transient or hard failure on the merged-state probe is indistinguishable from “PR still open” and `merge_pr` proceeds through flush/merge instead of idempotently returning `merged`/`admin_merged`. That breaks scout item (4) for post-merge re-entry whenever `pr view` fails after the PR is already `MERGED`. **Suggested fix:** Fail closed on `pr_view` failure (return `MERGE_RESULT_ERROR` with a redacted diagnostic), or retry `pr_view` with the same transient budget used elsewhere before continuing; do not fall through to a merge attempt when merge-state cannot be read.
