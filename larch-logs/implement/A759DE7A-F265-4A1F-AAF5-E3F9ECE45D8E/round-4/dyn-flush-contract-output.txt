Reviewing the flush-contract architecture: reading the diff and key modules.
Checking whether post-flush paths invoke git indirectly and how early merge returns handle post-flush.
### In-Scope Findings

- **architecture** `python/run_logs.py:73-82` — `_read_state_kv` only treats a missing path as empty; if `ctx.state_file` exists but is unreadable or not valid UTF-8, `Path.read_text` raises `OSError` or `UnicodeDecodeError`. That propagates through `read_state_kv` into `merge._merge_noop_if_pr_closed` (`python/merge.py:174`), so idempotent merge re-entry can crash instead of falling back to a safe empty sentinel and classifying from `gh pr view` alone. **Suggested fix:** Wrap state-file reads in a narrow try/except (or read with `errors="replace"`) and return `""` on any read/decode failure, matching the fail-closed “missing file → empty” behavior `refresh-run-logs.sh` assumes for probes.

- **architecture** `python/run_logs.py:429-452`, `python/merge.py:150-155` — `flush_logs_post` calls `_render_token_timing_batches`, which uses `_redact_batch_payload` and can raise `ShipError` on redaction failure. `merge_pr` always calls `_post_flush` on terminal merge paths but never catches that exception, so a post-merge tmpdir flush can abort the whole merge with an uncaught error instead of a `MergeResult`. That breaks the frozen-dataclass result contract Phase 7 is meant to route on. **Suggested fix:** Either catch `ShipError` inside `flush_logs_post` and return a `RefreshSkip`/`PostFlushResult` failure, or wrap `_post_flush` in `merge_pr` and map flush failures to `MergeResult(result=MERGE_RESULT_ERROR, error=...)`.

- **architecture** `python/run_logs.py:605-677` — When `flush_logs_pre` is invoked with `cwd=None` (as `merge.merge_pr` allows at `python/merge.py:46-47,78`), `_publish_run_tree_to_repo` skips copying the tmpdir run tree into the repo (`python/run_logs.py:618-619`) but `_larch_log_commit` still runs `git status` / `git add` / `git commit` on `larch-logs/implement/<run_id>` under the process cwd. Pre-push flush can therefore commit stale or unrelated repo `larch-logs/` content without publishing the tmpdir batches just rendered. **Suggested fix:** Require an explicit repo `cwd` before attempting commit (fail-closed `RefreshSkip`), or resolve/copy to the repo root when `cwd` is omitted so the pre-flush publish+commit steps are atomic.

### Out-of-Scope Observations

The post-merge invariant itself looks sound: `flush_logs_post` (`python/run_logs.py:429-452`) only touches tmpdir paths, manifest writes, token/timing re-render, and optional `write-final-report.sh` (no `git` usage in that script). `test_flush_logs_post_no_git_commit` enforces no `git commit` on the injected runner. `merge_pr` calls `flush_logs_pre` before merge work (`python/merge.py:78-80`) and `_post_flush` on every terminal path after the pre-flush gate except skip modes, `pr_number` missing, pre-flush `commit-failed`, CLOSED-not-merged, and the first already-`MERGED` noop (`post_flush=False` at `python/merge.py:72-76`) — the last mirrors `ship-pr.sh` routing `already_merged` to `postmerge` rather than re-running merge-time refresh. Phase 7 must still call `flush_logs_post` from a post-merge driver for that early-noop case if tmpdir manifest `status=done` is required on idempotent re-entry.
