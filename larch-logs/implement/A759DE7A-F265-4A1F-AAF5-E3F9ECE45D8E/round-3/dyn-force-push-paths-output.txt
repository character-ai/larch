Tracing force-push paths in the branch diff and comparing them to the bash originals.
### In-Scope Findings

- **correctness** `python/pr.py:72-87` — On the existing-OPEN-PR path, the first push is `git push -u origin HEAD`, so the remote ref is whatever branch HEAD is on (`symbolic-ref`), while escalation calls `force_push_recovery(..., branch=ctx.branch)`, which force-pushes to `refs/heads/{ctx.branch}` (`python/git.py:613-623`). `create-pr.sh` derives `BRANCH` from `git symbolic-ref --short HEAD` for both steps; if `RunContext.branch` ever diverges from the checked-out branch, recovery can update a different remote ref than the failed plain push, leaving the PR branch stale or corrupting the wrong ref. **Suggested fix:** Resolve the branch once with `git.try_current_branch(runner)` (or pass `branch=None` into `force_push_recovery`), fail closed when it differs from `ctx.branch`, and use that name for recovery; mirror `create-pr.sh`’s fetch + `branch --set-upstream-to` only if you keep a bare `git push --force-with-lease` path.

- **correctness** `python/git.py:599-605` — When `git status --porcelain` fails (`returncode != 0`), `force_push_recovery` returns `status="dirty_worktree"`. `git-force-push.sh` exits **2** on status inspection failure and **1** only when porcelain is non-empty (`scripts/git-force-push.sh:62-74`), so merge/pr callers can mis-report a tooling/repo failure as a dirty tree (e.g. `merge.py:245-250`). **Suggested fix:** Return a distinct status (e.g. `status_failed`) or propagate stderr; map that to `MERGE_RESULT_ERROR` / `ShipError` with the underlying message, not `dirty_worktree`.

- **correctness** `python/git.py:593-623` — When callers pass `branch=ctx.branch` (`merge.py:238-244`, `pr.py:87`), `force_push_recovery` never reconciles that name with `try_current_branch` (unlike `git-force-push.sh`, which always uses HEAD’s branch). For flush recovery, the lease is `refs/heads/{ctx.branch}:{expected_remote_oid}` while the pushed objects come from HEAD; a ctx/HEAD name mismatch targets the wrong remote ref. **Suggested fix:** Always resolve the branch from HEAD inside `force_push_recovery`, treat an explicit `branch` only as a validation hint (error if it disagrees with HEAD), or drop the parameter and use HEAD only.

### Out-of-Scope Observations

- **correctness (checked, no issue):** Production `status_porcelain` defaults to `--untracked-files=all` (`python/git.py:440-449`), stricter than `git-force-push.sh`’s plain porcelain; tests stub the same argv (`python/test_git.py:448-451`). Not a production/test mismatch.

- **correctness (checked, no issue):** Lease form `refs/heads/{branch}:{oid}` with `git push --force-with-lease=… <remote>` matches `git-force-push.sh:77-82` / `merge-pr.sh:290`; `noop_same_ref` after fetch when `HEAD` equals `{remote}/{branch}` (`python/git.py:630-634`) matches the bash race path (`scripts/git-force-push.sh:96-104`).

- **correctness (checked, no issue):** `git push -u origin HEAD` is parity with `create-pr.sh:156`; with matching branch names, `HEAD:refs/heads/{branch}` in recovery is equivalent to bare `--force-with-lease` after upstream setup.

- **risk-integration:** `rebase._force_push_branch` (`python/rebase.py:429-475`) duplicates recovery logic instead of calling `git.force_push_recovery`; pre-existing pattern, not introduced by the Phase 5 call sites under review.

- **risk-integration:** `force_push_recovery` has no unit tests for `noop_same_ref`, lease+retry argv, or `expected_remote_oid` push shape beyond dirty-tree (`python/test_git.py:444-463`); regressions rely on merge parity / integration coverage.
