Reviewing flush-boundary architecture: reading the diff and the key modules.
### In-Scope Findings

- **architecture** `python/run_logs.py:387-401` — `flush_logs_post` always writes `manifest.status = "done"`, but `merge.merge_pr` calls `_post_flush` on every terminal path after `flush_logs_pre`, including failures (`main_advanced`, `ci_not_ready`, `version_already_published`, `policy_denied`, `admin_failed`, `error`). That marks incomplete runs as finished in the tmpdir manifest, which diverges from bash (`ship-pr.sh` only finalizes manifest in the `postmerge` phase after `merged`/`admin_merged`/`already_merged`). **Suggested fix:** Split “tmpdir token/timing refresh” from “finalize manifest to done”; only set `MANIFEST_STATUS_DONE` when `merge_outcome.result` is `merged` or `admin_merged` (or when the driver has set post-merge state). On non-success merge outcomes, re-render batches if needed but leave `status=partial`.

- **architecture** `python/run_logs.py:348-384` — `flush_logs_pre` does not port the `write-final-report.sh` step that `scripts/refresh-run-logs.sh` runs between execution-issues and token/timing (bash lines 71–72). The Phase 5 plan lists “write-final-report inputs” in the pre-push sequence; omitting it breaks parity for summary/final-report artifacts that downstream post-merge logic expects to exist before merge. **Suggested fix:** Add a `write_final_report` (or shell-out) hook in `flush_logs_pre` after the first execution-issues pass and before `_render_token_timing_batches`, matching bash ordering; mirror the post-merge re-render in `flush_logs_post` per `ship-pr.sh` postmerge (lines 3652–3657).

- **architecture** `python/merge.py:80-82` — After a successful `flush_logs_pre` (log batches may have been committed), `_merge_noop_if_pr_closed` can return early without calling `_post_flush`, so the tmpdir manifest may never reach `status=done` and post-merge token/timing refresh is skipped on an idempotent “PR already closed” re-entry that happens after pre-flush. **Suggested fix:** Call `_post_flush(ctx)` before returning the terminal `MergeResult` from the post–`flush_logs_pre` noop check (or only when `pr.state` is `MERGED`/`CLOSED` and pre was not skipped).

### Out-of-Scope Observations

- **architecture** `python/merge.py:77-78` — When `flush_logs_pre` returns `reason="commit-failed"`, `merge_pr` returns without `_post_flush`. Tmpdir batches may be partially written while the repo commit failed; this is a narrower edge case than the failure-path `status=done` issue above and may be acceptable if Phase 7’s driver retries pre-flush, but it is worth tracking separately.

- No test in `python/test_merge.py` asserts that failed merge outcomes leave `manifest.status` as `partial`; `test_flush_logs_post_no_git_commit` only checks the no-git-commit invariant, not when `status=done` is appropriate.
