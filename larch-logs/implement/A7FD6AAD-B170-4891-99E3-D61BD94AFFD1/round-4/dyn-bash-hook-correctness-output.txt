### In-Scope Findings

- **correctness** `.tmp-debug-cf.sh:1-26`, `.tmp-debug-cf2.sh:1-22`, `.tmp-debug-cf3.sh:1-24`, `.tmp-debug-cf4.sh:1-18` — Four ad-hoc debug harnesses with hardcoded `/Users/zhupanov/larch4` paths are tracked on the branch (visible in the precomputed diff and `git ls-files`). They are not part of the #3202 / hook plan, will ship with the plugin if not removed, and confuse operators and automation about what is supported runtime surface. **Suggested fix:** Delete all `.tmp-debug-cf*.sh` from the branch before merge; if any scenario still needs manual reproduction, fold it into `scripts/test-collect-findings.sh` or `scripts/test-collect-agent-results.sh` using repo-relative paths and the existing harness tempdir pattern.

- **correctness** `scripts/hook-anti-read-poll.sh:24-28,206` — Task-output counters key on `session_hash` derived from `session_id` / `conversation_id`, but when both are absent every caller shares the literal `nosession` bucket (`hook-anti-read-poll.md:24-29` documents “cross-session bleed”). Concurrent Claude sessions on one host polling the same `tasks/<id>.output` under the same `cwd` can false-trigger reminders on the second read or suppress a legitimate second-session warning. **Suggested fix:** Fold a per-process discriminator into the fallback key when metadata is missing (e.g. `PPID`, a hook-supplied env var, or a small nonce written once per hook parent), and add a harness case that two synthetic “nosession” streams with different discriminators do not share `state-taskout-*` files.

- **correctness** `scripts/hook-anti-read-poll.sh:206-231,247-270` — State updates use non-atomic read–modify–write (`read` TSV → increment → `>` overwrite) with no `flock`. PostToolUse hooks can run back-to-back for the same session; interleaved writes can drop counts (missed reminder) or corrupt fields (path/offset bleed in the generic `state-<cwd_hash>.tsv` file). **Suggested fix:** Wrap each update in `flock -x "$state_file"` (or write via a temp file + `mv` after `flock` on a per-bucket lock file); extend `scripts/test-hook-anti-read-poll.sh` with a simulated concurrent double-invoke if feasible.

- **correctness** `scripts/hook-anti-read-poll.sh:53-55,115-152` — `bash_strip_quoted_for_read_verb` uses `sed -E "s/'[^']*'//g"`, which does not understand Bash’s `'\''` single-quote encoding, so paths split across quote runs leave literal `tasks/…output` fragments in the “stripped” view while `extract_task_output_token` still matches the full line (`scripts/hook-anti-read-poll.sh:177-189`). That can mark a non-poll segment as poll-bearing (false positive) or pair a read verb with a path from different quote runs (false negative). The harness only covers simple `cat '/abs/path/tasks/id.output'` (`scripts/test-hook-anti-read-poll.sh:210-215`), not escaped quotes. **Suggested fix:** Either document and test the limitation explicitly, or replace the sed stripper with a small character-wise state machine (or only extract tokens from segments already known to contain a read verb after a dedicated quote-aware scan).

- **correctness** `scripts/hook-anti-read-poll.sh:120-137` — Segment splitting treats `;`, then `&&`, then `||` left-to-right without shell precedence, so commands like `cmd1 || cat "$TASK_OUT" && cmd2` are not parsed the way Bash executes them; poll detection may attach to the wrong segment or miss the `cat` entirely. This is called out as a heuristic in comments (`scripts/hook-anti-read-poll.sh:102-105`) but remains a real correctness gap for compound one-liners. **Suggested fix:** Prefer detecting poll only on segments that both contain a read verb and a `tasks/<id>.output` token after strip (already mostly true), and add harness cases for mixed `||`/`&&` chains that match real orchestrator patterns; long term, only split on `;` (statement boundaries) unless you implement precedence-aware parsing.

- **correctness** `skills/review/scripts/collect-findings.sh:85-147,297-298` — The FINDING_3 fallback `replay_collector_failed_stderr_tails` runs when collect succeeds and `collector_stderr` is empty, but it only replays `${_reviewer}.stderr-tail` (`skills/review/scripts/collect-findings.sh:106-107,134-135`), not `*-retry.txt.stderr-tail`, `*-ns-retry.txt.stderr-tail`, or `${_reviewer}.launch-stderr` resolved the way `scripts/collect-agent-results.sh:1464-1494` does. If collector FD-2 capture ever fails while sidecars exist on retry/launcher paths, `/review` still loses tails despite the acceptance criterion. **Suggested fix:** Reuse the same resolver as the collector (factor `_resolve_collector_stderr_tail_file` into a shared lib or call it from both places) before replaying blocks to the wrapper FD.
