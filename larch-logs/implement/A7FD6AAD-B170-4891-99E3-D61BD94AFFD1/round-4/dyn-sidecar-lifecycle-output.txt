Reviewing sidecar lifecycle across the branch diff and related source files.
### In-Scope Findings

- **architecture** `scripts/launch-claude-subprocess.sh:224-227` and `scripts/launch-claude-review.sh:160-214` — The Claude launcher path never clears `${OUTPUT}.stderr-tail` before a run or after a successful exit (unlike `scripts/run-external-agent.sh:143`, which removes it in pre-launch cleanup). Reusing the same `--output` / `--output-file` after a failed invocation can leave a redacted failure sidecar on disk while the sentinel and collector record `STATUS=OK`; §3.8 dedup correctly skips OK slots, but artifacts can still be picked up by `skills/review/scripts/collect-findings.sh:106-107` (`replay_collector_failed_stderr_tails` reads only `${_reviewer}.stderr-tail`) and by `design-log-publish.sh` (`.stderr-tail` is not in `design_artifact_excluded` at `scripts/design-log-publish.sh:259`). **Suggested fix:** Mirror `run-external-agent.sh`: `rm -f "${OUTPUT_CANON}.stderr-tail"` at subprocess entry and on exit 0 (or call `write_failed_agent_stderr_tail` with an empty/disabled source so the library removes the sidecar).

- **architecture** `scripts/collect-agent-results.sh:1395-1414` — NS-retry success only runs `rm -f "${ORIG_OUTPUT}.stderr-tail"` while the NS attempt writes tails against `${ORIG_OUTPUT%.txt}-ns-retry.txt` (`NS_RETRY_OUTPUT` at `scripts/collect-agent-results.sh:1316`). A recovered slot keeps `${ORIG}-ns-retry.txt.stderr-tail` beside `STATUS=OK` / `REVIEWER_FILE=$ORIG_OUTPUT`, which can be published under `larch-logs/` and misrepresent a successful reviewer. Transient retry success has the symmetric gap only when a tail exists on the retry path, but NS-retry is the clear hole in the plan’s FINDING_2 stale-tail removal. **Suggested fix:** On every NS-retry OK path, also `rm -f "${NS_RETRY_OUTPUT}.stderr-tail"` (and any `*-retry.txt.stderr-tail` tied to that slot if present).

- **architecture** `scripts/dispatch-with-waterfall.sh:269-284` and `scripts/collect-agent-results.sh:1483-1493` — `.launch-stderr` sidecars are created per phase output stem but never appear in any explicit `rm -f` lifecycle (only truncated when the same `${output}` is relaunched). Earlier-phase files such as `slot.txt.launch-stderr` persist when the final failure is recorded on `slot-phase3.txt`; `_resolve_collector_stderr_tail_file` walks phase ancestors and can render an older phase’s launcher stderr when the failing phase has no `.stderr-tail` / empty `.launch-stderr`, surfacing superseded launcher errors as the “current” failure tail. **Suggested fix:** Either limit on-demand `.launch-stderr` resolution to the primary `REVIEWER_FILE` only (keep phase fallback for `.stderr-tail` if desired), or `rm -f` prior-phase `*.launch-stderr` when advancing the waterfall / at `launch_slot` for non-first phases so only the active phase stem can contribute launcher stderr.

### Out-of-Scope Observations

- Temp lifecycle for on-demand launcher tails looks sound: `_resolve_collector_stderr_tail_file` removes failed render temps at `scripts/collect-agent-results.sh:1491`, and `_cleanup_collector_dedup_tail_file` runs on every §3.8 branch (empty signature, dedup suppress, first emit) at `scripts/collect-agent-results.sh:1525-1539`; `scripts/test-collect-agent-results.sh:787-791` asserts no `larch-launch-stderr-tail.*` leaks after harness runs.
- `scripts/run-external-agent.sh:143` includes `${OUTPUT_FILE}.stderr-tail` in pre-launch stale cleanup as planned; `write_failed_agent_stderr_tail` still clears stale sidecars on disabled/empty render (`scripts/lib-failed-agent-stderr-tail.sh:132-136`).
- Phase-level `.stderr-tail` fallback (e.g. phase-2 tail when phase-3 has no sidecar) is intentional and covered by `scripts/test-collect-agent-results.sh:794-818`, distinct from the `.launch-stderr` stale-phase issue above.
