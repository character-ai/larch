Reviewing the stderr-to-chat pipeline for security: reading the diff and tracing redaction at every emission path.
Checking whether `append-tool-failure` predates the launch-stderr addition and how `larch_err` handles redaction failures for tail replay:
Branch commits (since `main`): `b46e8b0cc` (#3202 core), review-fix rounds, `fc94b8fe2` shellcheck, plus version/log chores.

### In-Scope Findings

- **security** `scripts/compose-collector-failure-log.sh:58-59` — The new `## Launcher stderr (${REVIEWER_FILE}.launch-stderr)` section is copied with raw `cat` from `${output}.launch-stderr`, which `dispatch-with-waterfall.sh` fills with unredacted launcher stderr. That composed log is fed to `append-tool-failure.sh --redact` in `skills/design/scripts/plan-review-loop.sh:806-813`, but `--redact` runs only `scripts/redact-secrets.sh` (see `scripts/append-tool-failure.sh:115-126`), not `redact-tmpdir-paths.sh`. Session tmpdir and operator repo paths in launcher validation stderr can therefore land in `execution-issues.md` even though chat surfacing for the same bytes uses `render_failed_agent_stderr_tail` (dual redaction). **Suggested fix:** Run `.launch-stderr` through `render_failed_agent_stderr_tail` (or `redact-tmpdir-paths.sh | redact-secrets.sh`) inside `dump_section` before writing, or extend `append-tool-failure.sh --redact` to apply the same dual pipeline used at publish time.

- **security** `scripts/lib-failed-agent-stderr-tail.sh:76-86` — The spool pipeline wraps `tail | redact-tmpdir-paths.sh | redact-secrets.sh` with `set +o pipefail`, stderr discarded (`2>/dev/null || true`), and emits whenever the spool is non-empty (comment at line 85). That diverges from fail-closed redaction elsewhere (e.g. `SECURITY.md` Step 0 plan-materialization, `redact_gh_error`). If a redactor exits non-zero after `tail` has partially filled the spool, pre-redaction bytes can be written to `${output}.stderr-tail` and replayed to FD 2. **Suggested fix:** Capture the pipeline exit status; on any redactor failure, delete the spool, skip `.stderr-tail` write/emission, and surface only a generic warning (no raw spool bytes).

- **security** `scripts/collect-agent-results.sh:1690-1693`, `scripts/lib-failed-agent-stderr-tail.sh:137-140` — Redacted tail lines are emitted via `larch_err "$_tail_line"` / `cat "$tail_file" >&2` without `sanitize_diagnostic_line`, despite `scripts/lib-quiet.sh:83-85` requiring explicit sanitization before forwarding external content. Hostile stderr can inject C0 controls/terminal escapes into operator chat and the session transcript. **Suggested fix:** Pipe each tail line through `sanitize_diagnostic_line` before `larch_err` / `printf`, matching `scripts/ci-failed-jobs.sh:80-101`.

- **risk-integration** `scripts/collect-agent-results.sh:1426-1540` — §3.8 intentionally places bounded, redacted external-agent stderr on FD 2 for orchestrator visibility. Aside from secret/path redaction and fence lines, there is no neutralization of content shaped like larch `KEY=value|…` RESULTS lines, hook JSON, or `<!-- … -->` / system-reminder markers; a compromised or malicious CLI could use stderr to influence the orchestrator transcript (stdout KV parsing stays safe). **Suggested fix:** Document this as accepted residual risk in `SECURITY.md` §Failed-agent stderr tails; optionally add a fixed “untrusted subprocess stderr” banner and strip or escape lines matching `^[A-Z_]+=` / `^<!--` before `larch_err`.

### Out-of-Scope Observations

- **Dual redaction on the primary chat path is implemented correctly:** `render_failed_agent_stderr_tail` applies `tail -n` → `redact-tmpdir-paths.sh` → `redact-secrets.sh` → `head -c 5120` on the spool (`scripts/lib-failed-agent-stderr-tail.sh:71-83`), so the byte cap is after redaction, not before. `.stderr-tail` sidecars, collector §3.8 on-demand `launch-stderr` renders, and `design-log-publish.sh` staging (`.stderr-tail` not in `design_artifact_excluded`) align with `SECURITY.md:256`.

- **`emit_failed_agent_stderr_tail_raw` / `run-external-agent.sh`** emit the already-redacted sidecar with plain `cat` to FD 2 (no second `larch_err` pass); acceptable given the sidecar write path, but it inherits the fail-open spool behavior above.

- **`larch_err` re-redacts with `redact-secrets.sh` only** (`scripts/lib-quiet.sh:98-124`); tmpdir scrubbing relies on the first pass in `render_failed_agent_stderr_tail`. Collector tails are fine; the compose/append path for raw `.launch-stderr` is the gap.

- **Gitleaks does not scan `larch-logs/`** — documented in `SECURITY.md:256` / `.gitleaks.toml`; committed `*.stderr-tail` artifacts depend on redaction quality, not scanner backstop.

- **Pre-existing pattern:** `.diag` in `compose-collector-failure-log.sh:57` was already raw-`cat`’d into the same secrets-only `append-tool-failure.sh --redact` path; this branch amplifies exposure by adding `.launch-stderr` with the same treatment.
