Reviewing branch changes for stderr-tail vs `.done` ordering and related correctness issues.
### In-Scope Findings

- **correctness** `scripts/collect-agent-results.sh:1393-1412` — NS-retry success paths that land in `CURSOR_EMPTY_RESPONSE` keep `REVIEWER_FILE=$ORIG_OUTPUT` but only remove `${ORIG_OUTPUT}.stderr-tail` in the plain-`OK` branches (lines 1397 and 1412). The transient-retry path already hoists `rm -f "${ORIG_OUTPUT}.stderr-tail"` for both `OK` and `CURSOR_EMPTY_RESPONSE` (line 1157), so this is an inconsistency within the same change. When an original run failed (writing a `.stderr-tail`) and the NS retry then succeeds with a cursor empty/degraded sentinel, the stale pre-retry tail survives; section 3.8’s dedup pass does not skip `CURSOR_EMPTY_RESPONSE`, resolves tails against `ORIG_OUTPUT`, and can emit the old failure stderr to FD 2 even though the slot recovered. That is not a concurrent race with dedup (both run sequentially in one collector process), but it is a correctness bug in stale-tail cleanup relative to the dedup reader. **Suggested fix:** Mirror the transient-retry pattern: after any successful NS retry (both structured and substantive paths), unconditionally `rm -f "${ORIG_OUTPUT}.stderr-tail"` regardless of whether the final status is `OK` or `CURSOR_EMPTY_RESPONSE`; optionally add a harness case where an original failure sidecar plus NS-retry `CURSOR_EMPTY_RESPONSE` must not emit the stale tail.

### Out-of-Scope Observations

- **Sentinel vs tail ordering on the main paths looks correct.** In `scripts/launch-claude-subprocess.sh:224-227`, a non-empty agent stderr gets `.stderr-tail` before `.done`. In `scripts/launch-claude-review.sh:186-191`, the parent only backfills a missing tail and writes `.done` only if the subprocess did not; validation-only failures exit without subprocess `.done`, so the parent writes tail then sentinel. In `scripts/run-external-agent.sh:266-273,308-322`, stderr-tail is written synchronously before `exit`, and the EXIT trap publishes `.done`/`.inner.done` afterward; `scripts/launch-review.sh:833-834` promotes `.inner.done` only after the wrapper has finished.
- **Stale-tail removal vs dedup is not racy** when implemented: retry-success cleanup in section 3 completes before section 3.8 reads tail files in the same shell process.
- **Minor residual window:** if a subprocess fails with empty `${OUTPUT}.stderr` it writes `.done` at `scripts/launch-claude-subprocess.sh:227` before the parent’s fallback at `scripts/launch-claude-review.sh:186-187`; a collector could theoretically observe `.done` first, but the fallback source (`SUBPROCESS_STDERR`) is usually empty under `larch_quiet_init`, so practical impact is low.
