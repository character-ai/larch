### FINDING_1: Non-JSON manifest “no bullets” path drops execution-issues telemetry
- **severity**: Important  
- **focus_area**: risk-integration  
- **location**: [scripts/implement-finalize.sh](scripts/implement-finalize.sh) (failure branch after `changelog_categories_to_markdown` returns non-zero; `fallback_allowed != true` branch around the new `skipped-no-bullets` / `emit_breadcrumb` path in the diff)  
- **issue**: For manifests where `jq -e .` fails (non-JSON / misrouted `manifest.env`), the new logic routes to `CHANGELOG_STATUS=skipped-no-bullets` with only a compact breadcrumb and **no longer** calls `append_execution_issue` or the prior human `warn_line` that recorded `manifest_path`, `manifest_exists`, and `coder`.  
- **scenario_or_breakage**: A run misroutes a shell KV manifest into `MANIFEST_PATH`; Step 8a still skips the amend (intended), but the tracking issue / `execution-issues.md` trail loses the structured “why we skipped” record operators used to triage #2233-class mistakes—failure recovery becomes harder and diverges from the documented “append … note” contract in `implement-finalize.md` for empty-bullet skips.  
- **suggested_fix**: In the `fallback_allowed != true` branch, restore `append_execution_issue` (and optionally the prior `warn_line` or an equivalent `larch_err`) with the same `manifest_path` / `manifest_exists` / `coder` payload while keeping `CHANGELOG_STATUS=skipped-no-bullets` and the new “no synthetic fallback for invalid JSON” behavior.

### FINDING_2: “No bump within N commits” warning can overstate how far history was scanned
- **severity**: Latent  
- **focus_area**: correctness  
- **location**: [scripts/drop-bump-commit.sh](scripts/drop-bump-commit.sh) (walk loop break on `git rev-parse` failure; WARN `no bump commit found within $MAX_DEPTH commits of HEAD`)  
- **issue**: The loop stops early when `HEAD~$_depth` is missing, but the user-visible message always names `MAX_DEPTH`, not the actual number of commits examined.  
- **scenario_or_breakage**: A short branch (fewer than `MAX_DEPTH` commits) with no bump subject anywhere yields `DROPPED=false` with text implying a full `MAX_DEPTH` walk (e.g. “within 10 commits”) even though only 2–3 commits were reachable—misleading when choosing `--max-depth` or debugging “missing bump” stalls.  
- **suggested_fix**: Track `_depth` at exit (last successfully verified index or “walked D commits”) and include that count in the WARN string, or reword to “no bump found within reachable history (stopped after D commits / MAX_DEPTH=M).”
