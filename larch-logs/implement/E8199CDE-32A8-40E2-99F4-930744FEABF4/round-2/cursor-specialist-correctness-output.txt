### In-Scope Findings

1. **Important** (`correctness`, source: `plan` + `requirements`) — [skills/implement/SKILL.md](skills/implement/SKILL.md) **1348–1352** instructs the orchestrator to set `dynamic_archetypes_cap` from `dynamic_archetypes_value` or from `LARCH_DYNAMIC_ARCHETYPES_MAX` in `$IMPLEMENT_TMPDIR/session-env.sh` with fallback `4`. That omits the **process environment** tier that [skills/review-and-fix/scripts/review-and-fix.sh](skills/review-and-fix/scripts/review-and-fix.sh) **700–715** applies (`CLI > non-empty LARCH_DYNAMIC_ARCHETYPES_MAX env > session-env > 4`). **Concrete scenario:** operator exports `LARCH_DYNAMIC_ARCHETYPES_MAX=1`, runs `/implement` without `--dynamic-archetypes` / `--no-dynamic-archetypes`, so Step 0 does not persist the key and `run-step5-review.sh` does not pass `--dynamic-archetypes`; `review-and-fix.sh` still resolves the cap to **1**, but Step 5 prose can still print `dynamic-archetypes cap=4` per the SKILL fallback. **Suggested fix:** extend the Step 5 derivation (or the printed explanation) to mirror the same three-way rule as `review-and-fix.sh` (e.g. also consult `${LARCH_DYNAMIC_ARCHETYPES_MAX:-}` when session-env is empty), or document that breadcrumbs intentionally reflect only persisted/session state and may diverge from env-only overrides.

2. **Nit** (`risk-integration`, source: `plan`) — [scripts/test-run-step5-review.md](scripts/test-run-step5-review.md) **12–14** claims session-env forwarding is what lets “`/implement` operator flags override any ambient shell env.” Forwarding helps when the cap is **in the file** (then CLI beats env in `review-and-fix.sh`), but if the key is **absent** and only the shell sets `LARCH_DYNAMIC_ARCHETYPES_MAX`, no `--dynamic-archetypes` is added and the **process env still wins** over the default `4`. **Suggested fix:** narrow the bullet to “when `LARCH_DYNAMIC_ARCHETYPES_MAX` is persisted, forwarded CLI overrides ambient env,” or mention the env-only case explicitly.

3. **Latent** (`correctness`, source: `requirements`) — [skills/implement/SKILL.md](skills/implement/SKILL.md) **152–153** documents `--no-dynamic-archetypes` and `--dynamic-archetypes <N>` but does not define behavior if **both** appear (e.g. last flag wins vs abort). A careless parse order could set `dynamic_archetypes_value` inconsistently with operator intent. **Concrete scenario:** `$ARGUMENTS` contains `--dynamic-archetypes 3 --no-dynamic-archetypes`; without an explicit mutual-exclusion rule, the orchestrator might persist `3` or `0` depending on parse order, changing scout behavior for the same argv. **Suggested fix:** add a short mutual-exclusion rule (prefer hard-abort with a warning, or define deterministic last-wins).

4. **Latent** (`correctness`, source: `plan`) — The plan specified treating **`LARCH_DYNAMIC_ARCHETYPES_MAX` set to an empty string** as a defined process-env tier (`[[ ${LARCH_DYNAMIC_ARCHETYPES_MAX+x} ]]`); the shipped logic in [skills/review-and-fix/scripts/review-and-fix.sh](skills/review-and-fix/scripts/review-and-fix.sh) **704–715** uses `[[ -n "${LARCH_DYNAMIC_ARCHETYPES_MAX:-}" ]]`, so an **empty** export is treated like **unset** and resolution falls through to session-env / default. That matches the new harness intent (`test-review-and-fix.sh` empty-env case) but **diverges from the written plan**. **Concrete scenario:** `export LARCH_DYNAMIC_ARCHETYPES_MAX=` with session-env `LARCH_DYNAMIC_ARCHETYPES_MAX=3` — implementation yields **3**; strict plan-style `[[ ...+x ]]` would bind the empty string and then fail validation unless special-cased. **Suggested fix:** treat as intentional and update the plan/spec, or align code with the original `+x` semantics if empty-string binding was required.
