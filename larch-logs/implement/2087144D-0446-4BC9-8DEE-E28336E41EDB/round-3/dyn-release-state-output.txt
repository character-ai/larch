Reviewing the branch diff and release Step 7/8 flow for risk-integration issues.
### In-Scope Findings

- **risk-integration** `.claude/skills/release/SKILL.md:167-168` and `skills/upgrade-larch/scripts/upgrade-larch.sh:15-17,398-406` — Step 7 sources the full `upgrade-larch.sh` only to call `resolve_release_step7_root`, but sourcing still runs `larch_quiet_init` (redirecting the orchestrator shell’s stdout/stderr into a quiet log) and only restores FD 1 via `exec 1>&3`, leaving FD 2 redirected. It also assigns `LARCH_CACHE_DIR` and `INSTALLED_VERSION` from `PLUGIN_ROOT` (often the live `CLAUDE_PLUGIN_ROOT` cache) before the sourced early-return. Step 7’s `echo "Warning: …"` and other stderr diagnostics can land in the quiet log instead of the operator transcript, and later steps in the same Bash fence can see polluted globals. **Suggested fix:** Move `resolve_release_step7_root` and its dependencies into a sourced-only helper (no `larch_quiet_init`, no top-level assignments), or gate lines 15–17 and 398–401 behind the same `BASH_SOURCE` check that currently sits at 404–406, placed immediately after loading `lib-sparse-dirs.sh`.

- **risk-integration** `.claude/skills/release/SKILL.md:168` and `skills/upgrade-larch/scripts/upgrade-larch.sh:190-233` — Root resolution is invoked as `resolve_release_step7_root "${CURRENT_VERSION:-}" 2>/dev/null || true`, so `get_installed_larch_version` / `claude` failures are indistinguishable from “no cache root.” That pushes the flow into the Skill-tool fallback path (lines 191–199), which may run the **installed** `/upgrade-larch` implementation—the same stale-skill failure mode RC1 was meant to eliminate—after a failed or ambiguous resolution. **Suggested fix:** Stop discarding stderr; treat only a non-empty resolved path as success; reserve the Skill fallback for the documented zero/ambiguous-cache cases, and surface resolution errors when `claude` or metadata parsing fails.

- **risk-integration** `.claude/skills/release/SKILL.md:245-263` and `skills/upgrade-larch/scripts/upgrade-larch.sh:516-544` — Step 8 restart guidance depends on re-reading `$PREPARE_DIR/release-step7.env` via `PR_LIST_FILE`, but Step 8’s first Bash fences (cleanup) never mention `PR_LIST_FILE`. If the orchestrator does not carry `PR_LIST_FILE` from Step 2 into the Step 8 state-read fence, `release-step7.env` is skipped, all flags default to `false`, and the operator gets **no restart instruction** after a successful same-version cone reconcile (`CONE_RECONCILED=true` was written in Step 7). That recreates the stale in-memory plugin failure mode Step 8 was added to prevent. **Suggested fix:** Require `PR_LIST_FILE` (or an explicit `PREPARE_DIR`) in the Step 8 restart block, fail loudly if missing when Step 7 ran, or persist `release-step7.env` to the durable recovery path under `~/.cache/larch/release-notes/` alongside redacted notes.

- **risk-integration** `.claude/skills/release/SKILL.md:57-58,160-209` and `skills/upgrade-larch/scripts/upgrade-larch.sh:409-444,541-544` — Step 7 runs immediately after Step 6 promote/tag, but the upgrade script’s target version comes from `gh api …/releases` (`LATEST_STABLE`). If GitHub’s release list lags the just-promoted tag, Step 7 can take the “upgrade unconditionally” or verification-failure path (`exit 1`), leave `NEW_VERSION_INSTALLED` / `CONE_RECONCILED` unset in `release-step7.env`, and continue to Step 8 with warn-and-continue semantics while the marketplace cone still lacks the new allowlist dir. **Suggested fix:** Pass the known `NEW_VERSION` from prepare output into the working-tree upgrade invocation (e.g. env override or flag) so release Step 7 does not depend solely on `gh` seeing the release that Step 6 just cut.

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:9-11` and `.claude/skills/release/SKILL.md:167-168` — Missing `lib-sparse-dirs.sh` uses `exit 1` before the sourced guard. When Step 7 sources the script, that terminates the **orchestrator** shell mid-release rather than returning an error. **Suggested fix:** Use `return 1` when `BASH_SOURCE[0] != $0`, or keep the missing-lib check only in the executable path after the source guard.

- **risk-integration** `.claude/skills/release/SKILL.md:191-199` — The Skill-tool fallback branch is comment-only in the Bash fence; there is no mechanical capture/parse of fallback output in-repo. Whether that is a gap depends on orchestrator discipline outside the diff.
