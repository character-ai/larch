Reviewing the branch diff and release Step 7/8 integration against the plan.
### In-Scope Findings

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:521-554` and `.claude/skills/release/SKILL.md:176-197,253-275` — On `/release` Step 7, `LARCH_EXPECTED_STABLE_VERSION="$NEW_VERSION"` always sets `LATEST_STABLE`, so a post-reinstall verification miss (`VERIFIED_TARGET=false`) ends with exit **1** and **no** `LARCH_RESTART_REQUIRED=true` (that line is only emitted when `LATEST_STABLE` is empty or verification succeeds). Step 7 only records restart/cone flags when `upgrade_rc -eq 0`, and Step 8 restarts only from `release-step7.env`, so the operator can finish `/release` with a mutated marketplace/plugin install, no mandatory restart, and a failed Step 7 warning—the same stale in-memory state the fix targets. **Suggested fix:** After any uninstall/marketplace refresh/install path, emit `LARCH_RESTART_REQUIRED=true` whenever the install was mutated but stable verification failed (or have Step 7 treat non-zero `upgrade_rc` after a captured reinstall as `RESTART_REQUIRED=true` unless output explicitly says “No upgrade needed”).

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:521-527` and `.claude/skills/release/SKILL.md:183-194` — If `MARKETPLACE_CONE_WILL_RECONCILE=true` but `marketplace_sparse_cone_matches` is still false after reinstall while `VERIFIED_TARGET=true`, the script exits **0** without `LARCH_CONE_RECONCILED=true` or `LARCH_RESTART_REQUIRED=true` (only a prose warning). Release Step 7 then leaves `CONE_RECONCILED`/`RESTART_REQUIRED` false, so Step 8 omits the restart instruction even though the documented failure mode is stale plugin state after cone repair. **Suggested fix:** On that branch, exit non-zero and/or always emit `LARCH_RESTART_REQUIRED=true`; optionally set `LARCH_CONE_RECONCILED=false` explicitly so release automation can warn that allowlist propagation did not complete.

- **risk-integration** `skills/upgrade-larch/scripts/release-step7-root.sh:88-95` and `.claude/skills/release/SKILL.md:198-220` — When `get_installed_larch_version` returns a version but the matching cache directory is missing, `resolve_release_step7_root` returns **1** immediately and does not try `CURRENT_VERSION` or the sole-cache fallback. Right after a release, metadata can name `NEW_VERSION` before that cache dir exists, so Step 7 skips the working-tree upgrade and falls through to the installed `/upgrade-larch` Skill—the pre-fix RC1 path that may still lack the new allowlist. **Suggested fix:** If `metadata_root` is missing, fall through to prepare/sole-cache resolution (or run the working-tree script with `CLAUDE_PLUGIN_ROOT` unset so `SCRIPT_ROOT` still supplies the allowlist) instead of failing closed into the Skill fallback.

- **risk-integration** `.claude/skills/release/SKILL.md:198-207` — The Skill-tool fallback is described only in comments; the Step 7 fence has no capture/parse block analogous to the working-tree path, so an orchestrator can invoke `/upgrade-larch`, warn, and still write `release-step7.env` with all flags false even when the fallback actually reconciled the cone. **Suggested fix:** Mirror the working-tree pattern in the fallback branch (capture `2>&1`, parse machine-readable lines, write `release-step7.env`) or state explicitly that fallback must not run without the same capture contract.
