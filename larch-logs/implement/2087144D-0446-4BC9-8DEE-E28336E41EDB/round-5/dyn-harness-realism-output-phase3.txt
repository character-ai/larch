### In-Scope Findings

- **code-quality** `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:121-146` — `resolve_release_step7_root_for_test` calls `source "$RELEASE_STEP7_ROOT_SCRIPT"` inline, permanently overriding `is_safe_version`, `get_installed_larch_version`, `is_cache_shaped_larch_root`, `single_larch_cache_version_dir`, and `resolve_release_step7_root` in the harness process with the `release-step7-root.sh` versions. After the root-resolution block (lines ~296–342) runs, subsequent `source_upgrade_for_case` calls re-source `upgrade-larch.sh` and restore the correct definitions for the production integration tests. But the ordering is now load-bearing with no in-harness guard: if any new test case calls `resolve_release_step7_root_for_test` between the `already_latest_and_cone_ok` unit tests and their `source_upgrade_for_case` setup, the harness silently uses the wrong `is_cache_shaped_larch_root` (the `release-step7-root.sh` version calls `release_step7_cache_parent()` while the `upgrade-larch.sh` version uses `$HOME` directly). **Suggested fix:** Run `resolve_release_step7_root` in a subprocess (`bash -c "source ...; resolve_release_step7_root ..."`) rather than sourcing into the harness namespace, or add an explicit `source_upgrade_for_case` guard after the root-resolution block to restore `upgrade-larch.sh` function definitions before proceeding.

- **code-quality** `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:550-589` — The `production-active-root-stale` case verifies "Installing larch plugin..." but asserts nothing about restart signals. In this scenario (`CLAUDE_PLUGIN_ROOT` at 8.0.0, `claude plugin list` returns 9.0.0), `CURRENT_INSTALLED_VERSION` reads "9.0.0" (from metadata) both before and after reinstall, so `ACTUAL_VERSION != CURRENT_INSTALLED_VERSION` is false and `LARCH_NEW_VERSION_INSTALLED=true` is never emitted; `MARKETPLACE_CONE_WILL_RECONCILE` is also false (cone matched), so `LARCH_RESTART_REQUIRED=true` is not emitted either. The `/release` Step 7 SKILL.md code therefore receives no restart signal after an upgrade that moved the session from 8.0.0 to 9.0.0. The test passes without catching this gap and gives false confidence that the restart contract is covered for the stale-active-root scenario. **Suggested fix:** Add an explicit assertion: either `assert_failure` for `LARCH_RESTART_REQUIRED=true` (documenting that no restart signal is emitted and why this is intentional) or fix the production logic to compare `INSTALLED_VERSION` (from `PLUGIN_ROOT`) against `ACTUAL_VERSION` rather than `CURRENT_INSTALLED_VERSION` from metadata.

- **code-quality** `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh` (no production test for `LARCH_EXPECTED_STABLE_VERSION`) — `/release` Step 7 in `.claude/skills/release/SKILL.md` invokes `upgrade-larch.sh` with `LARCH_EXPECTED_STABLE_VERSION="$NEW_VERSION"` to bypass `gh` API calls entirely (lines ~175–195 of the new SKILL.md step). No production integration test case sets this variable; all production cases either stub `gh` or let `gh` fail. A regression in the `if is_safe_version "${LARCH_EXPECTED_STABLE_VERSION:-}"` guard (e.g., the variable being ignored or misread) would go undetected. **Suggested fix:** Add a `production-release-expected-version` case that sets `LARCH_EXPECTED_STABLE_VERSION`, omits or fails the `gh` stub, and asserts that the correct `LATEST_STABLE` is used, `LARCH_NEW_VERSION_INSTALLED=true` is emitted (or `LARCH_CONE_RECONCILED=true` if cone-only), and the script exits 0.

- **code-quality** `scripts/test-sessionstart-health.sh:348-365` (case 4f2) — The test is labelled "sparse library unset-variable failure is fail-open" and uses `: "${LARCH_TEST_UNSET}"` in a stub library. But `probe_sparse_cone_drift` explicitly does `set +u` before sourcing the library, so `: "${LARCH_TEST_UNSET}"` silently expands to empty—no unset-variable error fires. The library also defines no `normalize_sparse_dirs`, so `declare -F normalize_sparse_dirs` fails and the probe skips. The test therefore exercises the same "missing function" path as case 4f rather than the `set -u`-triggered abort path it claims to cover. The label gives false confidence that the `set -e`/`set -u` failure-isolation path has been exercised. **Suggested fix:** Either rename case 4f2 to describe what it actually tests ("library defines no normalize_sparse_dirs via unrecognized syntax"), or restructure it to place `set -u` inside the library's function bodies and verify the `set +e` + `set +u` in `probe_sparse_cone_drift` still protects the hook.

- **code-quality** `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:257-261` — `cone-empty` constructs its fixture by calling `git sparse-checkout set --no-cone` (requires git ≥ 2.25 for the `--no-cone` flag) and then writing `printf '\n' > "$clone/.git/info/sparse-checkout"` directly. The `git sparse-checkout list` output after direct file manipulation depends on whether git reads `.git/info/sparse-checkout` or its own internal config state; on git ≥ 2.36 with `core.sparseCheckoutCone=true` still set in `.git/config`, the list command may not consult the file at all and may return the previously-set cone pattern (`.claude`) rather than empty output, causing `configured` to be non-empty and `assert_failure` to produce a false pass. **Suggested fix:** Construct the "empty sparse list" fixture without `sparse-checkout init`—use a bare `git init` without any `sparse-checkout` commands, then confirm `git sparse-checkout list` is empty, rather than overwriting internal state files.

- **code-quality** `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:401-404,461-463,512-514,562-564,605-607` — All `gh` stubs in the production integration tests match any argument string and unconditionally print `v9.0.0\n` (or exit 1). The production `get_stable_releases` calls `gh api --paginate repos/character-ai/larch/releases --jq '...'`; if a future refactor switched to `gh release list`, the same stub output would flow through `sed 's/^v//'` and the tests would still pass. No stub validates that `api` was the subcommand. **Suggested fix:** Add a minimal argument check inside each `gh` stub: `case "$1 $2" in "api "*)` to verify the `api` subcommand is reached, and `exit 1` on mismatch, so a command-shape regression is caught.
