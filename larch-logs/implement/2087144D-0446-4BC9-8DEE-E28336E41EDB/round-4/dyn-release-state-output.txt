Reviewing the release Step 7/8 integration against the branch diff and related source files.
### In-Scope Findings

- **risk-integration** `.claude/skills/release/SKILL.md:59-72,250-272` — Step 7 sets `CONE_RECONCILED` and `RESTART_REQUIRED` from substring/`LARCH_*` matches in `upgrade_out` without requiring `upgrade_rc=0`. The reconcile banner is printed at the start of the reconcile path (`skills/upgrade-larch/scripts/upgrade-larch.sh:471`) before uninstall/install/verification, so a failed run can still leave `CONE_RECONCILED=true` in `release-step7.env` and Step 8 will tell the operator to restart even though the install may be incomplete. **Suggested fix:** Gate flag parsing on `upgrade_rc=0` (or a dedicated `LARCH_UPGRADE_SUCCEEDED=true` line), and treat the prose fragment as advisory only when the machine-readable reconcile line is present; persist `CONE_RECONCILED=false` on non-zero exit unless an explicit partial-success contract is added.

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:518-549` — `LARCH_CONE_RECONCILED=true` is emitted whenever `MARKETPLACE_CONE_WILL_RECONCILE` was true before reinstall, including when post-install verification fails (`VERIFIED_TARGET=false`, exit 1 at 547) and even when `marketplace_sparse_cone_matches` still fails after reinstall (warning at 519-520, signal at 522). `/release` Step 7 treats that line as authoritative restart state, so operators can be told the cone was repaired when it was not. **Suggested fix:** Emit `LARCH_CONE_RECONCILED=true` only when `VERIFIED_TARGET=true` (or at least when `marketplace_sparse_cone_matches` succeeds after reinstall); on verification failure or persistent drift, omit the signal or emit an explicit failure token for Step 7 to record.

- **risk-integration** `skills/upgrade-larch/scripts/release-step7-root.sh:89-95` — If installed metadata resolves to a semver but `$HOME/.claude/plugins/cache/larch-local/larch/$installed_version` is missing, `resolve_release_step7_root` returns 1 immediately and does not try prepare `CURRENT_VERSION` or unambiguous sole-cache fallbacks (documented in `.claude/skills/release/SKILL.md:152-153`). After metadata/cache skew (e.g. metadata already names the new release, cache not populated yet), Step 7 gets no `RESOLVED_ROOT` and falls through to the stale installed `/upgrade-larch` Skill path, partially reintroducing RC1. **Suggested fix:** On missing metadata cache dir, fall through to rules 3–4 (validated `CURRENT_VERSION`, sole cache dir, or `NEW_VERSION` cache when `LARCH_EXPECTED_STABLE_VERSION` is set) instead of hard-failing; add a harness case for metadata-ahead-of-cache during release.

- **risk-integration** `.claude/skills/release/SKILL.md:159-214` — Step 7 always writes `release-step7.env` using `PREPARE_DIR="$(dirname "$PR_LIST_FILE")"` with no guard that `PR_LIST_FILE` is set. In Bash, `dirname ""` is `.`, so a lost prepare artifact writes state into the repo working tree; Step 8 only warns when `PR_LIST_FILE` is missing and will not read that file, so restart guidance is silently dropped across steps. **Suggested fix:** Before writing state, require a non-empty `PR_LIST_FILE` whose dirname exists (or re-parse Step 2 `prepare_out` for `PR_LIST_FILE` inside the Step 7 fence); skip the env write with an operator-visible warning when it is missing.

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.md:13,33` vs `.claude/skills/release/SKILL.md:59-61` — The contract says `LARCH_CONE_RECONCILED=true` is emitted after a successful reinstall and that `/release` parses machine-readable lines from successful invocations only, but the skill also treats the early reconcile prose fragment as sufficient and the script emits the reconcile signal before the final verification gate. Orchestrators following the doc can mis-handle failed upgrades. **Suggested fix:** Align `upgrade-larch.md`, `upgrade-larch.sh`, and release Step 7 on one rule: success-gated machine-readable lines only, or document and implement the prose fallback as an explicit non-success partial signal with different Step 8 behavior.
