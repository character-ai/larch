Reviewing release Step 7/8 workflow changes against the plan and diff.
### In-Scope Findings

- **risk-integration** `.claude/skills/release/SKILL.md:148-166` — Step 7 defines a four-step `RESOLVED_ROOT` order and cache-shaped `CLAUDE_PLUGIN_ROOT` rules, but the only executable fence leaves `RESOLVED_ROOT=""` with `# Resolve RESOLVED_ROOT using the ordering above before this point`. There is no shipped helper under `.claude/skills/release/scripts/`; the mirror logic lives only in `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh` (`resolve_release_step7_root_for_test`, ~132–173). A `/release` run therefore depends on prompt-side interpretation, which can drift from the tested contract (active root vs metadata vs `CURRENT_VERSION` vs ambiguous cache). **Suggested fix:** Extract root resolution into a repo-root or release-script helper (e.g. `scripts/resolve-release-upgrade-root.sh`) that emits `RESOLVED_ROOT=` / empty, call it from the Step 7 fence, and have the retention harness source or diff against that script instead of a test-only copy.

- **risk-integration** `.claude/skills/release/SKILL.md:187-204` — When `RESOLVED_ROOT` is empty, the fenced bash still atomically writes `release-step7.env` with `CONE_RECONCILED=false` and `NEW_VERSION_INSTALLED=false`, while the Skill-tool fallback is described only in prose (“record … unless the captured fallback output explicitly includes…”). There is no second fence to capture Skill output and rewrite state. A fallback that reconciles the cone (the old RC1 failure mode) can complete without updating `release-step7.env`, so Step 8 will skip the mandatory restart even though allowlist repair may have occurred via the stale installed skill. **Suggested fix:** Either require a follow-up bash block after Skill fallback that captures `2>&1`, re-parses the same signals, and rewrites `release-step7.env`, or move fallback into the same script path as the working-tree invocation so state is always written from one capture site.

- **risk-integration** `.claude/skills/release/SKILL.md:175-185` — `CONE_RECONCILED=true` is set when captured output contains the pre-install reconcile fragment (`Already at latest stable` + `sparse checkout is out of date` + `Reconciling`), but `skills/upgrade-larch/scripts/upgrade-larch.sh:379-448` emits `LARCH_CONE_RECONCILED=true` only after `VERIFIED_TARGET=true`. If marketplace remove/install fails (`upgrade_rc != 0`), Step 7 warns and continues while Step 8 may still restart because fragment-based `CONE_RECONCILED` was set before success was verified. **Suggested fix:** Gate `CONE_RECONCILED` on `upgrade_rc=0` and presence of `LARCH_CONE_RECONCILED=true` (drop fragment-only inference, or treat fragment as “in progress” only), and optionally persist `UPGRADE_RC` in `release-step7.env` for Step 8 messaging.

- **risk-integration** `.claude/skills/release/SKILL.md:181-182` — `NEW_VERSION_INSTALLED` is inferred solely from the substring `Upgrading larch from * to *`, matching `upgrade-larch.sh:385-386`. When `LATEST_STABLE` is empty (`gh` failure), the script prints `Latest stable release could not be determined; upgrading unconditionally...` (`upgrade-larch.sh:387-388`) with no `Upgrading larch from` line, so a successful unconditional reinstall after a release cut may not set `NEW_VERSION_INSTALLED` and Step 8 will not mandate restart. **Suggested fix:** Also set `NEW_VERSION_INSTALLED` when `upgrade_rc=0` and output contains `Verified: larch <version> installed successfully.` (or emit a dedicated machine line from `upgrade-larch.sh` for any successful reinstall).

- **risk-integration** `.claude/skills/release/SKILL.md:152-153` — Item 3 allows `$HOME/.claude/plugins/cache/larch-local/larch/${CURRENT_VERSION}` when metadata is unavailable and `CURRENT_VERSION` is the “sole defensible cache target,” but unlike item 4 it does not explicitly require “exactly one version-shaped directory under cache.” The harness only accepts this path when `single_cache_version_dir_for_test` equals that directory (`test-upgrade-larch-retention.sh:157-162`). An orchestrator following item 3 alone could select a `CURRENT_VERSION` directory that exists alongside other cache versions while item 4’s ambiguity rule is never reached. **Suggested fix:** Align item 3 prose with the harness (require matching installed metadata, or exactly one cache dir and it equals `${CURRENT_VERSION}`), or fold items 3–4 into one numbered rule that matches `resolve_release_step7_root_for_test`.

### Out-of-Scope Observations

- **risk-integration** `.claude/skills/release/SKILL.md:237-249` — Step 8 restart guidance depends on re-deriving `PREPARE_DIR` from `PR_LIST_FILE` (Step 2 `mktemp` artifact). If the orchestrator loses that path between steps, missing `release-step7.env` defaults both flags to false and restart is skipped silently; this is pre-existing release tempdir coupling, now higher stakes because cone-only repair requires restart without a version bump.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:434-436` — Same-version cone repair does not emit `LARCH_CONE_RECONCILED=true` when post-install verification fails (`VERIFIED_TARGET=false`), even though the reconcile preamble was printed; release fragment parsing can still set `CONE_RECONCILED` (see in-scope item above). Worth tightening in the upgrade script, not only in release parsing.
