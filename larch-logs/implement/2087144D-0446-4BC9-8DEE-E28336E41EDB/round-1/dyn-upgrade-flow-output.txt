Reviewing the branch diff and upgrade-larch implementation for correctness issues.
### In-Scope Findings

- **correctness** `.claude/skills/release/SKILL.md:174-186` — Step 7 sets `CONE_RECONCILED=true` when captured output contains the *start-of-run* reconcile fragment (`Already at latest stable` + `sparse checkout is out of date` + `Reconciling`), which `upgrade-larch.sh` prints at lines 381–383 before uninstall/reinstall/verification. Parsing runs before the `upgrade_rc` check, so a failed reconcile (non-zero exit, `VERIFIED_TARGET=false`, no `LARCH_CONE_RECONCILED=true`) can still persist `CONE_RECONCILED=true` in `release-step7.env`, and Step 8 will instruct a restart as if repair succeeded. **Suggested fix:** Treat `LARCH_CONE_RECONCILED=true` as the only positive machine signal; if keeping the fragment fallback, require `upgrade_rc=0` (and ideally presence of the verified-success line) before setting `CONE_RECONCILED=true`, and never set it when Step 7 only warns that upgrade failed.

- **correctness** `.claude/skills/release/SKILL.md:181-186` — Step 7 sets `NEW_VERSION_INSTALLED=true` when output merely contains `Upgrading larch from … to …`, which is emitted at the beginning of a version-changing run (lines 385–386 in `skills/upgrade-larch/scripts/upgrade-larch.sh`) and can appear even when the script later exits 1 because `ACTUAL_VERSION` did not match `LATEST_STABLE`. That yields the same false-positive restart coupling as the cone fragment bug. **Suggested fix:** Set `NEW_VERSION_INSTALLED=true` only after a successful run (`upgrade_rc=0`) and a verified install signal (e.g. `Verified: larch … installed successfully.` or `LARCH_CONE_RECONCILED=true` / post-verify stamp path), not from the pre-flight upgrade banner alone.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:66-70,371-377` — `already_latest_and_cone_ok()` gates the idempotent early-exit on `CURRENT_INSTALLED_VERSION` (from `get_installed_larch_version` / metadata) matching `LATEST_STABLE`, but not on `INSTALLED_VERSION` (basename of `CLAUDE_PLUGIN_ROOT` / the running cache). After an upgrade without restart, metadata can read `47.0.70` while the session still runs from `…/cache/larch-local/larch/47.0.69`; if the marketplace cone already matches the new allowlist, the script early-exits with “No upgrade needed” and never reinstalls/refreshes the active cache—so dirs like `python/` can remain absent from the tree the session actually loads. **Suggested fix:** Require `INSTALLED_VERSION="$LATEST_STABLE"` (or `INSTALLED_VERSION="$CURRENT_INSTALLED_VERSION"`) inside `already_latest_and_cone_ok()` before returning 0, or skip early-exit whenever the active cache-shaped `PLUGIN_ROOT` version differs from `CURRENT_INSTALLED_VERSION`.

- **correctness** `scripts/sessionstart-health.sh:92-93,485-486` — The new sparse-cone drift probe runs only inside `JQ_AVAILABLE && GIT_AVAILABLE`, so environments with `git` but without `jq` never get the drift advisory (Case 2 in `scripts/test-sessionstart-health.sh` only asserts the jq-missing message). That conflicts with acceptance that SessionStart warns on cone drift independently of jq. **Suggested fix:** Call `probe_sparse_cone_drift` when `GIT_AVAILABLE` alone (or move it before the jq gate), keeping the probe’s own fail-open guards; add a harness case with drift fixture + jq missing to pin the intended behavior.
