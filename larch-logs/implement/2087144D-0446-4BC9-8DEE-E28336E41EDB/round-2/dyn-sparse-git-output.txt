### In-Scope Findings

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:384-438` — `LARCH_CONE_RECONCILED=true` is driven by `MARKETPLACE_CONE_WILL_RECONCILE`, which is set from a **pre-reconcile** `!marketplace_sparse_cone_matches` check, not from a post-install cone re-check or from `VERIFIED_TARGET`. The script therefore emits the machine-readable reconcile signal even when stable verification fails and it is about to `exit 1` (lines 460–462), and it can do so even if the marketplace cone is still wrong after `refresh_larch_marketplace` / `claude plugin install`. That contradicts `skills/upgrade-larch/scripts/upgrade-larch.md:13` (“After the reinstall command succeeds, it emits `LARCH_CONE_RECONCILED=true`”) and can make `/release` Step 8 tell the operator to restart as if the cone were repaired when it was not. **Suggested fix:** Set the flag only after a successful end-state check, e.g. `MARKETPLACE_CONE_WILL_RECONCILE=true` at entry plus `marketplace_sparse_cone_matches` succeeding after install (and, when `LATEST_STABLE` is set, `VERIFIED_TARGET=true`) before printing `LARCH_CONE_RECONCILED=true`; do not emit it on the failure path.

- **correctness** `.claude/skills/release/SKILL.md:168-183` — Step 7 sets `CONE_RECONCILED=true` whenever captured output contains `LARCH_CONE_RECONCILED=true`, even when `upgrade_rc -ne 0` and the skill only prints a warning. Combined with the upgrade-script issue above, a failed Step 7 run can still write `CONE_RECONCILED=true` into `release-step7.env` and Step 8 can mandate a restart without a successful cone repair. **Suggested fix:** Require `upgrade_rc=0` (and optionally re-read `release-step7.env` only after success) before honoring `LARCH_CONE_RECONCILED=true`, or have the upgrade script stop emitting the line unless reconcile verification passed.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:55-66` — `marketplace_sparse_cone_matches` treats exact string equality between sorted `git sparse-checkout list` output and `normalize_sparse_dirs` as ground truth, but only normalizes the **expected** side. Git cone output can include extra patterns (e.g. `/*`, `!/*/`, trailing slashes, or other formatting) depending on git version and on whether the cone was created by `claude plugin marketplace add --sparse` vs raw `git sparse-checkout set`. A format skew produces a **false negative** (perpetual “drift” → remove/re-add every `/upgrade-larch`) or, if extra lines appear only on the configured side, a false positive drift signal in `scripts/sessionstart-health.sh:73-76`. Hermetic coverage in `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:84-92` and the production-drift stub at `339-367` exercise `git sparse-checkout set "$@"`, not real Claude marketplace sparse output, so the comparison contract is not validated against production cones. **Suggested fix:** Normalize **both** sides with the same rules (strip cone scaffolding, optional trailing `/`, `LC_ALL=C sort`), add a fixture built from captured `claude plugin marketplace add --sparse …` output on supported git versions, or compare set equality of directory tokens instead of raw multiline string equality.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:63-66` vs `scripts/sessionstart-health.sh:73-76` — On `git sparse-checkout list` failure or empty output, upgrade treats empty `configured` as drift (`[ -n "$configured" ] || return 1` → reconcile/reinstall), while SessionStart skips the advisory when `configured` is empty. An operator with a broken or too-old `git` sparse-checkout subcommand gets no SessionStart hint but still hits the heavy reinstall path on every `/upgrade-larch` (or release Step 7), with no cone signal if install also fails verification. **Suggested fix:** Share one helper that classifies “empty because error/unreadable” vs “empty because non-cone/legacy” vs “non-empty mismatch”, and either fail loudly or skip reconcile consistently in both upgrade and SessionStart.
