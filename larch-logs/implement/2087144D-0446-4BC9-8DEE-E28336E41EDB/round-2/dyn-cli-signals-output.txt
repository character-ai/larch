Reviewing the diff and tracing signal emission, capture, and restart semantics.
### In-Scope Findings

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:437-462` — `LARCH_CONE_RECONCILED=true` is printed whenever `MARKETPLACE_CONE_WILL_RECONCILE` was set at the pre-reinstall probe (lines 384–385), before stable verification and before the script’s `exit 1` path when `VERIFIED_TARGET=false` (lines 460–462). A failed or partial upgrade can still emit the machine-readable line while exiting non-zero. That contradicts `skills/upgrade-larch/scripts/upgrade-larch.md:13` (“After the reinstall command succeeds, it emits …”) and the `/upgrade-larch` skill’s “verify the script exited successfully” rule (`skills/upgrade-larch/SKILL.md:21`). **Suggested fix:** Emit `LARCH_CONE_RECONCILED=true` only after a successful run (e.g. `upgrade_rc=0` equivalent: `VERIFIED_TARGET=true`, or when `LATEST_STABLE` is empty and install completed) **and** a post-reconcile `marketplace_sparse_cone_matches` succeeds; do not emit it on the verification-failure exit path.

- **correctness** `.claude/skills/release/SKILL.md:175-179` — Step 7 sets `CONE_RECONCILED` / `NEW_VERSION_INSTALLED` from substring matches in `upgrade_out` without requiring `upgrade_rc=0`. Step 7 warns on failure (lines 181–182) but still writes those flags into `release-step7.env` (lines 196–200). Step 8 then mandates a Claude restart when either flag is true (lines 252–252), even if the upgrade failed and the sparse cone or cache was not actually repaired. **Suggested fix:** Only set `CONE_RECONCILED` / `NEW_VERSION_INSTALLED` when `upgrade_rc=0`, or gate emission in `upgrade-larch.sh` so failed runs never print the machine-readable lines; persist `UPGRADE_STEP7_RC=<n>` in `release-step7.env` if Step 8 needs to distinguish warn-and-continue from success.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:437-438` — The cone signal is tied to the **pre-reinstall** `MARKETPLACE_CONE_WILL_RECONCILE` flag, not to a post-`refresh_larch_marketplace` / post-install `marketplace_sparse_cone_matches` check. If marketplace refresh or reinstall does not actually repair the cone (tooling glitch, partial failure before `set -e` exit, or comparison drift), automation still reports success via `LARCH_CONE_RECONCILED=true`. **Suggested fix:** After `refresh_larch_marketplace` and plugin install, call `marketplace_sparse_cone_matches` again and emit `LARCH_CONE_RECONCILED=true` only when it returns 0 on that post-check (still combined with overall success gating above).

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:440-444` — When `gh` cannot resolve `LATEST_STABLE`, `LARCH_NEW_VERSION_INSTALLED=true` can be emitted whenever `ACTUAL_VERSION != CURRENT_INSTALLED_VERSION` even though `VERIFIED_TARGET` stays false and the script exits 0 without the verification-failure `exit 1` (lines 460–462 are skipped when `LATEST_STABLE` is empty). `/release` Step 7 will record `NEW_VERSION_INSTALLED=true` and Step 8 will instruct a restart after a best-effort, unverified install—common on release machines if `gh` flakes right after tag publish. **Suggested fix:** Require `VERIFIED_TARGET=true` (or an explicit “gh unavailable” contract documented and tested) before emitting `LARCH_NEW_VERSION_INSTALLED=true`; if `gh` is down during `/release` Step 7, leave the flag false and tell the operator to re-run `/upgrade-larch` once `gh` works.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:440-444` — If `get_installed_larch_version` fails after install (`ACTUAL_VERSION` empty or not version-shaped), neither `LARCH_NEW_VERSION_INSTALLED=true` nor a failed verification path sets `NEW_VERSION_INSTALLED`, yet the script may still exit 0 when `LATEST_STABLE` is empty. `/release` Step 8 will not require restart (`NEW_VERSION_INSTALLED=false`) even when the plugin actually changed version—false negative for the restart contract. **Suggested fix:** When install commands succeed and `CURRENT_INSTALLED_VERSION != LATEST_STABLE` (or `NEEDS_CONE_RECONCILE` / version-upgrade path was taken), emit `LARCH_NEW_VERSION_INSTALLED=true` based on `LATEST_STABLE` vs pre-run version, or fail closed (`exit 1`) if post-install version cannot be resolved when `LATEST_STABLE` was set.
