Reviewing the branch diff and key files for SCRIPT_ROOT vs PLUGIN_ROOT and root-resolution architecture.
### In-Scope Findings

- **architecture** `skills/upgrade-larch/scripts/upgrade-larch.sh:384-439` — `LARCH_CONE_RECONCILED=true` is emitted whenever the marketplace cone was drifted at entry (`MARKETPLACE_CONE_WILL_RECONCILE=true`), before post-install verification and even when the script later exits 1 because `VERIFIED_TARGET=false` (`skills/upgrade-larch/scripts/upgrade-larch.sh:460-462`). Round 1 moved the signal out of the `VERIFIED_TARGET` / `NEEDS_CONE_RECONCILE` block, so a failed reinstall can still advertise a successful cone repair. **Suggested fix:** Emit `LARCH_CONE_RECONCILED=true` only after a successful same-version reconcile (for example `NEEDS_CONE_RECONCILE=true`, `VERIFIED_TARGET=true`, and a post-reinstall `marketplace_sparse_cone_matches`), and align `skills/upgrade-larch/scripts/upgrade-larch.md:13` with that gate.

- **architecture** `.claude/skills/release/SKILL.md:54-62,175-177` — Step 7 sets `CONE_RECONCILED=true` from a substring match in captured output without requiring `upgrade_rc=0`, while Step 8 treats `CONE_RECONCILED=true` as a mandatory restart condition (`skills/upgrade-larch/scripts/upgrade-larch.sh:437-439` can appear on failed runs). Operators can be told to restart after a failed Step 7 even though the sparse cone and cache were not repaired. **Suggested fix:** Set `CONE_RECONCILED=true` only when `upgrade_rc=0` and the captured output contains `LARCH_CONE_RECONCILED=true` (or gate the machine line in the upgrade script on verified success as above).

- **architecture** `skills/upgrade-larch/scripts/upgrade-larch.sh:69-73,372-382` — `already_latest_and_cone_ok()` compares `get_installed_larch_version` metadata to `LATEST_STABLE`, not `INSTALLED_VERSION` from `basename "$PLUGIN_ROOT"` (`skills/upgrade-larch/scripts/upgrade-larch.sh:319-322`). With `CLAUDE_PLUGIN_ROOT` bound to an older cache-shaped root (release Step 7 item 1 in `.claude/skills/release/SKILL.md:29-34`) while metadata already names the latest stable version and the marketplace cone matches, the script can early-exit without reinstalling the active cache tree—leaving a stale plugin checkout (for example missing a newly allowlisted top-level dir) despite a matching cone. **Suggested fix:** Require `INSTALLED_VERSION="$LATEST_STABLE"` (or explicit metadata/cache alignment) inside `already_latest_and_cone_ok()`, or skip early-exit when `INSTALLED_VERSION` differs from `CURRENT_INSTALLED_VERSION`.

- **architecture** `.claude/skills/release/SKILL.md:26-81` — `RESOLVED_ROOT` ordering and ambiguity rules exist only as prompt-side prose plus a parallel copy in `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:132-173`; there is no shared release helper script consumed by `/release` and tests. Any orchestrator drift from the documented order (active `CLAUDE_PLUGIN_ROOT` vs metadata vs `CURRENT_VERSION` vs sole-cache fallback) can run the working-tree upgrade against the wrong cache root, breaking the SCRIPT_ROOT/PLUGIN_ROOT split and prune protection described in `scripts/lib-sparse-dirs.md` and `skills/upgrade-larch/scripts/upgrade-larch.md:27-29`. **Suggested fix:** Extract root resolution into a small repo-root script (for example under `.claude/skills/release/scripts/`) that emits `RESOLVED_ROOT=` / exit codes, invoke it from Step 7, and source or mirror it in `test-upgrade-larch-retention.sh` so prose, runtime, and harness share one implementation.

- **architecture** `.claude/skills/release/SKILL.md:175-177` vs plan acceptance — Step 7 parses only `LARCH_CONE_RECONCILED=true` / `LARCH_NEW_VERSION_INSTALLED=true`, but the plan and `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:320-321` expect a reconcile-prose fragment fallback; the harness explicitly rejects that fragment. If the machine line is absent or stdout is truncated, Step 8 will not require restart after a real same-version cone repair. **Suggested fix:** Add the documented substring fallback to Step 7 parsing (and a harness case that accepts it) while keeping machine lines primary, or document machine-only detection and ensure the upgrade script never omits `LARCH_CONE_RECONCILED=true` on success.

### Out-of-Scope Observations
