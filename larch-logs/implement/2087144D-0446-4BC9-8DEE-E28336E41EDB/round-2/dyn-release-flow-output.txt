Reviewing the branch diff and release-flow changes for risk-integration issues.
### In-Scope Findings

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:437-463` — Round 1 moved `LARCH_CONE_RECONCILED=true` ahead of the `VERIFIED_TARGET` gate and keys it only on the pre-reconcile `MARKETPLACE_CONE_WILL_RECONCILE` flag, so a failed reinstall (verification miss, `claude` error, partial marketplace repair) can still print the success signal and then exit 1. That contradicts the cross-step contract in `skills/upgrade-larch/scripts/upgrade-larch.md`, which treats the line as post-success state for `/release` Step 8. **Suggested fix:** Emit `LARCH_CONE_RECONCILED=true` only after a successful reconcile, e.g. when `VERIFIED_TARGET=true` (or exit 0) and the post-install cone matches `normalize_sparse_dirs`; keep the pre-reconcile prose message separate from the machine-readable success marker.

- **risk-integration** `.claude/skills/release/SKILL.md:168-201` — Step 7 sets `CONE_RECONCILED` / `NEW_VERSION_INSTALLED` from captured output without requiring `upgrade_rc -eq 0`, then always writes those values to `release-step7.env`. Combined with the upgrade-script behavior above, a failed Step 7 can persist `CONE_RECONCILED=true`, Step 8 reads it, and the operator is told to restart even though the local install refresh failed and may still lack the new allowlist. **Suggested fix:** Gate both flag assignments on `upgrade_rc -eq 0` plus the machine-readable lines (or move flag parsing after the failure warning and force both flags false when `upgrade_rc -ne 0`); optionally add a Step 8 branch that says “upgrade failed — run `/upgrade-larch` manually before restart” when `upgrade_rc` was nonzero.

- **risk-integration** `.claude/skills/release/SKILL.md:159-202` — The Step 7 bash fence is not runnable as written: it initializes `RESOLVED_ROOT=""` and delegates the four-step resolution table to prose outside the fence, so a literal execution always falls into the stale Skill-tool fallback—the exact RC1 failure mode this change is meant to eliminate. Resolution logic exists only as `resolve_release_step7_root_for_test()` in `skills/upgrade-larch/scripts/test-upgrade-larch-retention.sh:132-173`, not as a repo script the release orchestrator must call. **Suggested fix:** Extract a shared helper (e.g. `scripts/resolve-release-cache-root.sh`) implementing the documented ordering, invoke it inside the Step 7 fence before the upgrade call, and keep the harness function mirroring that script so release behavior is mechanically enforced instead of prompt-reimplemented.
