### In-Scope Findings

- **architecture** `skills/design/SKILL.md:1082-1093` — Step 3 entry prose limits the downstream `rm`, `step-1e` write, and Step 2 bypass restoration to “Gate A Ready for review” / backward re-entry, but the Bash fence runs those operations on **every** Step 3 entry with no route guard. On a first-time entry after a normal 2b→2b.5 path this is mostly harmless, but if the orchestrator ever reaches Step 3 with missing Step 2 markers (corrupt resume, manual tmpdir edit, or routing bug), the `[ -f … ] || : > …` restore lines will **fabricate** `step-2a`/`step-2a.5`/`step-2b`/`step-2b.5` and `design-pause-save.sh` will treat Step 2 as complete, letting pause/resume jump to review instead of replaying sketches/plan work. **Suggested fix:** Gate the `rm`, `step-1e` write, and bypass-package restore behind an explicit re-entry predicate (e.g. backward-loop sentinel, absence of `step-2b.5` with `plan.txt` present, or a dedicated `$DESIGN_TMPDIR/.step3-reentry` flag set only by Gate A direct-review / Gate C re-run paths), and keep first-time Step 3 entry to source-env + pause-check + timing only.

- **architecture** `skills/design/SKILL.md:80-82,2479-2526` — Phase 7 moves absorbed completion sentinels from step **success** boundaries to **host entry** fences (before pause-check). That inverts the original contract (“sentinels written only after the step body succeeds”) into “orchestrator reached the next Bash host.” For the folded discussion block (1c→1e batched at Step 2a entry), a pause/crash after the entry fence but before sketch/plan LLM work completes will still leave those markers set, so `design-pause-save.sh`’s registry walk (`scripts/design-pause-save.sh:180-186`) resumes forward instead of replaying in-flight discussion/sketch work. The tradeoff is documented, but it is a real architectural regression in sentinel semantics versus pre-Phase 7 behavior. **Suggested fix:** Either (a) restrict pre-work batch writes to idempotent **repair** paths only (no-brainstorm repair, backward re-entry) and keep first-time discussion markers at true success boundaries, or (b) add a parallel “in-progress” marker (e.g. `.completed/step-2a.pending`) that pause-save consults before treating folded steps as done.

- **architecture** `skills/design/SKILL.md:92-100,1616` — The Phase 7 audit table lists `step-5c` as hosted in the `design-publish.sh` fence “when `PLAN_WRITE_OK=true`,” but the fence (`skills/design/SKILL.md:1541-1603`) only adds pause-check + publish; `step-5c` is written in orchestrator prose **after** the fence returns (`item 6`, line 1616). Structure tests correctly pin the prose gate (`scripts/test-design-structure.sh:1950-1962`) and forbid an in-fence write, but the SKILL audit table and completion-sentinel section still claim an in-fence host. That split contract is easy to mis-implement in a future edit (moving `step-5c` into the fence and bypassing the `step-5b` precondition). **Suggested fix:** Align the audit table and “Completion sentinels” prose with the actual host: “orchestrator Step 5c item 6 after `PLAN_WRITE_OK` parse; not inside `design-publish.sh` fence,” and add a negative harness assertion that the publish fence must not contain `step-5c` (already partially present).

- **architecture** `skills/design/SKILL.md:2220,2389-2406,2479-2496` — With brainstorm off, pure-LLM Steps 1c, 1d, 1d.7, and 1e have **no** Bash boundary with pause-check between Step 0c and Step 2a entry (Step 1d.5 prelude is skipped). Phase 7 documents coarser timing, but this is the largest structural pause-latency gap in the skill and is not covered by `assert_bash_fences_have_pause_check` because those steps no longer have fences. **Suggested fix:** Accept explicitly in the audit table as a named exception, or retain a single lightweight “folded discussion checkpoint” Bash fence after Step 1d.7 (source-env + pause-check only, no timing prelude) for the no-brainstorm route so pause latency is bounded without reintroducing per-step preludes.
