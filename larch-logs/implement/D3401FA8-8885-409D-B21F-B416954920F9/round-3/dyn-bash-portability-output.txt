Checking `set -e` interaction with `grep -c` on empty input:

### In-Scope Findings

- **correctness** `.claude/skills/audit-runs/scripts/audit-title.sh:40-44` — With `set -euo pipefail`, `PR_COUNT=$(printf '%s' "$SORTED_PRS" | grep -c .)` runs before the empty guard; when every token in `--pr-list` is invalid so `SORTED_PRS` is empty, `grep -c .` matches nothing and exits status 1, so the shell exits immediately and the intended error path (`--pr-list contains no valid PR numbers`) never runs. **Suggested fix:** Count lines without a failing exit on zero matches (for example `PR_COUNT=$(printf '%s\n' "$SORTED_PRS" | awk 'NF{c++} END{print c+0}')`, or keep `grep -c` but wrap so the assignment never inherits a non-zero status, e.g. `PR_COUNT=$(printf '%s' "$SORTED_PRS" | { grep -c . || true; })` and then coerce empty to `0` before the `-eq` checks).

- **correctness** `.claude/skills/audit-runs/scripts/audit-title.sh:57` — Contiguity uses `EXPECTED_COUNT=$(( LAST - FIRST + 1 ))` where `FIRST`/`LAST` come from `grep -E '^[0-9]+$'`, which still allows leading zeros (e.g. `010`); in Bash 3.2 arithmetic constants with a leading `0` are interpreted as octal, so the range width can be wrong or the expansion can error on invalid octal digits. The same pattern appears in `test-audit-runs.sh:750` inside `is_contiguous`. **Suggested fix:** Force decimal radix when expanding, e.g. `EXPECTED_COUNT=$(( 10#$LAST - 10#$FIRST + 1 ))`, or normalize PR tokens to strip leading zeros before arithmetic.
