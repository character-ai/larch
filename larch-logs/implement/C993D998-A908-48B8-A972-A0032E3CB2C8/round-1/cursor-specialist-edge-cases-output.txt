### In-Scope Findings

1. **Latent** (`risk-integration`) [skills/implement/scripts/write-rejected-findings.sh:41-63](skills/implement/scripts/write-rejected-findings.sh): `REJECTED_COUNT` and the human-facing `count=` line are always derived from `rejected-findings.md` via `grep`, while the run-log copy can come from `rejected-findings-full.md`. The harness in [skills/implement/scripts/test-write-rejected-findings.sh:29-45](skills/implement/scripts/test-write-rejected-findings.sh) already encodes a case where the log contains a full `### [rejected] FINDING_1` block but the bare file is a single token with no ledger matches, so the script coerces `count` to `1` ([write-rejected-findings.sh:49-50](skills/implement/scripts/write-rejected-findings.sh)) while the log body can imply a different cardinality. **Scenario:** an operator or downstream step trusts `REJECTED_COUNT` / the `emit` line against the richer log and mis-prioritizes work. **Fix:** when the full file is chosen as the copy source, compute the count from that same source (for example `grep -c` on `^###[[:space:]]\\[rejected\\]` against `rejected-findings-full.md`) or document that telemetry is “bare-ledger only” and must not be cross-checked against the log.

2. **Latent** (`correctness`) [skills/implement/scripts/write-rejected-findings.sh:41-46](skills/implement/scripts/write-rejected-findings.sh): The “empty” gate is `-s` on `rejected-findings.md` only. If an upstream fault ever produced a non-empty `rejected-findings-full.md` with an empty or missing bare `rejected-findings.md`, the script exits `STATUS=empty` and never reaches the copy block, so the run log would miss rejected detail despite data existing in `full`. **Fix:** treat “has actionable rejected content” as `-s` on either file (with the same preference order as the copy path) before early exit.

3. **Latent** (`risk-integration`) [scripts/hook-anti-read-poll.sh:41-55](scripts/hook-anti-read-poll.sh): After the third identical read, every further identical read within the same 30 s window still satisfies `count >= 3` and `age <= 30`, so the hook can emit on the 4th, 5th, … reads, not only at the threshold crossing. **Scenario:** an agent stuck in a read loop gets a growing stream of `additionalContext` payloads and may treat them as errors or waste context budget. **Fix:** fire only when `count -eq 3`, or persist a `last_warned_at` / `last_warned_count` in the state row and suppress repeats until the streak resets or the window elapses.

4. **Latent** (`correctness`) [scripts/hook-anti-read-poll.sh:35-48](scripts/hook-anti-read-poll.sh): State is a single-line TSV with raw `file_path`. A literal tab in `tool_input.file_path` (pathological or hostile payload) breaks `IFS=$'\\t' read` so `last_path`, `last_offset`, `count`, and `first_ts` deserialize incorrectly, corrupting streak accounting for that CWD hash. **Fix:** reject paths containing tabs/newlines, URL-encode, or store JSON in the state file instead of hand-rolled TSV.

5. **Nit** (`risk-integration`) [scripts/test-hook-anti-read-poll.sh:1-67](scripts/test-hook-anti-read-poll.sh): The harness covers threshold=3, offset changes, non-Read tools, and path switches (via a fresh `cwd`), but never asserts the `WINDOW_SECS=30` branch (expiry after idle gap) or the “4th read in-window” behavior above, so timer and repeat-emission logic can regress unnoticed.

6. **Latent** (`architecture`) [scripts/compose-review-findings.sh:127-144](scripts/compose-review-findings.sh): Inside `code-review-rejected`, only inner lines matching `^###[[:space:]]+(FINDING_|OOS_)` are kept in-body; any other `### …` heading inside a rejected block still hits the generic `^###[[:space:]]` handler and calls `flush_pending`, which can split one tally block into multiple composed records or drop prose if future tally output adds non-`FINDING_`/`OOS_` subsections. **Fix:** broaden the inner-heading allowlist or nest-aware parse to match whatever `tally-code-votes.sh` can emit.
