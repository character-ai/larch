### In-Scope Findings

1. **Important** (`correctness`, `requirements` + `plan`) — [`scripts/hook-anti-read-poll.sh:41-56`](scripts/hook-anti-read-poll.sh)  
   The hook advances the streak on every `Read` with the same `file_path` + `offset` within 30s; it does **not** require that those `Read` calls be consecutive in the overall tool stream (e.g. `Read`, `Bash`, `Read`, `Bash`, `Read` still reaches `count=3` and fires). The feature text calls for “read 3+ times **consecutively**,” which is usually read as back-to-back `Read` invocations only. **Scenario:** an agent alternates small `Bash` checks with the same `Read` and gets warned without having issued three `Read` calls in a row. **Fix:** Narrow the contract to “repeated identical `Read` within 30s” in docs/requirements, or encode “last tool was `Read`” / session-level consecutiveness if the product meaning is strict (harder in a hook-only design).

2. **Important** (`correctness`, `plan`) — [`scripts/compose-review-findings.sh:127-139`](scripts/compose-review-findings.sh)  
   `code-review-rejected` parsing now only opens a block on `### [rejected] …`. Any older or stubbed `rejected-findings-full.md` that still uses `### [Code Review] …` section heads is no longer parsed as rejected findings at all (generic `###` branch flushes and drops the section). **Scenario:** Re-run `compose-review-findings.sh` on an archived tmpdir or fixture whose full rejected artifact predates the tally header format; composed `FINDINGS_TOTAL` omits those rejections and bodies disappear from the composed markdown. **Fix:** Optionally accept both header shapes, or document a one-time migration path for old logs.

3. **Latent** (`correctness`, `both`) — [`skills/implement/scripts/write-rejected-findings.sh:41-59`](skills/implement/scripts/write-rejected-findings.sh)  
   If `rejected-findings.md` is missing or empty, the script exits `STATUS=empty` before the log copy path runs, even when `rejected-findings-full.md` exists and is non-empty. **Scenario:** Unusual or hand-built tmpdir state (or a partial pipeline failure) with only the full file materialized; the run log never receives the detailed rejected artifact despite “full” content on disk. **Fix:** Before the early exit, treat a non-empty `rejected-findings-full.md` as evidence of non-empty rejected state (or merge gates with the plan’s “prefer full” rule). In the normal `emit-tally.sh` path, the compact file still gets a non-empty `# Rejected Findings` header, so this is an edge case outside the happy path.

4. **Nit** (`risk-integration`, `plan`) — [`scripts/hook-anti-read-poll.sh:50-56`](scripts/hook-anti-read-poll.sh)  
   The condition uses `count >= 3`, so every further identical `Read` in the same 30s window emits another `additionalContext` JSON line. **Scenario:** Pathological polling floods the hook channel with duplicate reminders after the first warning. **Fix:** Fire only on `count == 3`, or add a “warned until reset” bit in the state file.

5. **Nit** (`code-quality`, `plan`) — [`scripts/test-hook-anti-read-poll.sh:45-47`](scripts/test-hook-anti-read-poll.sh)  
   The comment “Wipe state by using a new cwd” does not match the test (same `cwd`, different `offset`). Misleading for future maintainers. **Fix:** Correct the comment to describe offset-based reset on the same project.
