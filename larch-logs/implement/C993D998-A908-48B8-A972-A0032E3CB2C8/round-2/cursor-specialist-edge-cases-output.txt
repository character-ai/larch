### In-Scope Findings

1. **Important** (`risk-integration`) — [`skills/implement/scripts/write-rejected-findings.sh:66-71`](skills/implement/scripts/write-rejected-findings.sh): The log write path runs redaction and copy under `2>/dev/null || true`, so a missing/non-executable redactor, broken pipe, or disk error can yield an empty or partial `rejected-findings.md` in the run log while the script still emits `STATUS=ok` and a positive `REJECTED_COUNT`. Operators and downstream automation then trust a “successful” rejected-findings export that never actually persisted. Surface write failures (at least non-zero exit from the pipeline) and downgrade status or emit a failure envelope instead of swallowing everything.

2. **Latent** (`correctness`) — [`skills/implement/scripts/write-rejected-findings.sh:45-76`](skills/implement/scripts/write-rejected-findings.sh): When `emit-tally.sh` has rewritten `rejected-findings.md` to grep ledger lines like `12:FINDING_1_OUTCOME=rejected` (see [`skills/review/scripts/emit-tally.sh:92-99`](skills/review/scripts/emit-tally.sh)), those lines do not match the count regex on line 62, so `grep` returns 0 and line 63 forces `count=1` even if several findings were rejected and `rejected-findings-full.md` lists them all. After this change the log body is the full multi-finding file while the quiet stream can still report `REJECTED_COUNT=1`, which is plausible-looking but wrong under multi-reject rounds. Prefer counting from the same source as the copied detail (e.g. count `### [rejected]` blocks in `detail_file`, or read tallies from `review-summary.json` / tally file if available).

3. **Latent** (`correctness`) — [`scripts/compose-review-findings.sh:127-148`](scripts/compose-review-findings.sh): For `code-review-rejected`, only inner headings matching `### FINDING_` / `### OOS_` are kept in the body; any other `### …` line hits the generic `^###[[:space:]]` branch and calls `flush_pending`, which splits one logical rejected block across multiple composed records or drops narrative between headings. If a future tally or reviewer template inserts headings such as `### Vote tally` or `### Evidence` inside a `[rejected]` section, composition silently fragments. Extend the inner-heading guard or skip generic flushing while inside an open `code-review-rejected` block except for known terminators.

4. **Latent** (`risk-integration`) — [`scripts/hook-anti-read-poll.sh:41-61`](scripts/hook-anti-read-poll.sh): State is read and later rewritten without locking; concurrent `Read` PostToolUse invocations (same `cwd`) can interleave read/update and produce arbitrary `count`/`first_ts`, causing missed warnings or extra warnings. Unlikely in a single-threaded client, but fail-open does not mean “accurate.” If this matters, use atomic write (`mktemp` + `mv`) or `flock` on the state file.

5. **Nit** (`risk-integration`) — [`scripts/hook-anti-read-poll.sh:64-68`](scripts/hook-anti-read-poll.sh): Once `count>=3` inside the window, every further identical read in that window re-emits the JSON reminder, so sustained polling can spam `additionalContext` on every read. Consider emitting only on the transition to `count==3` or rate-limiting repeats.

6. **Nit** (`code-quality`) — [`scripts/test-hook-anti-read-poll.sh:32-38`](scripts/test-hook-anti-read-poll.sh): The first scenario relies on wall-clock time (`HOOK_ANTI_READ_POLL_NOW` unset) while the window test uses a frozen clock; if three sequential hook runs were ever delayed by more than 30 seconds, the “third fires” assertion could flake. Drive the first block with monotonic injected timestamps like the window section.

7. **Nit** (`risk-integration`) — [`scripts/hook-anti-read-poll.md`](scripts/hook-anti-read-poll.md): The doc states that different offsets “do not trigger” the warning, which reads as if offsets are exempt entirely; the implementation resets the counter per offset and still fires on the third read at that offset (see [`scripts/test-hook-anti-read-poll.sh:50-63`](scripts/test-hook-anti-read-poll.sh)). Tighten wording so operators expect per-(path,offset) streaks.
