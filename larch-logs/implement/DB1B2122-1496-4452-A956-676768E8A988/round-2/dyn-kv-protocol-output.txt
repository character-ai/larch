Tracing the stdout KV protocol from the parser through the SKILL.md consumer. Reading the diff and implementation files.
### In-Scope Findings

- **architecture** `skills/design/SKILL.md:159-195` — After `_argv_rc=0`, the Step 0-pre consumer loop never checks that stdout actually contains the full eight-KV success matrix from `parse-design-argv.md`. If the script regresses (empty stdout, truncated output, or a partial line set) while still exiting 0, the fence keeps its pre-loop defaults (`hard_requested=false`, `POSITIONAL_KIND=none`, empty `run_id`, etc.) and continues into Step 0a without aborting. That breaks the documented contract (“exactly these eight KVs on success”) and can silently drop flags or mis-classify the positional tail. **Suggested fix:** After the `while` loop on the success path, require all eight keys (count lines, or set `_seen_*` flags per key) and `exit 1` with a diagnostic if any are missing; mirror the “mandatory KV matrix” pattern used by `design-postplan-emit.sh` tests.

- **architecture** `skills/design/SKILL.md:145-198` — The parser→consumer KV split is correct *inside* the fence (`_key="${_line%%=*}"` / `_value="${_line#*=}"` preserves embedded `=` in values such as `RUN_ID=a=b`, and validation vs success output is separated), but on success the fence never emits `_argv_out` to orchestrator-visible stdout (unlike Step 0a, which prints `session-setup.sh` KV lines). Bash variables set in the loop do not survive the subshell, so Step 0b’s prose (“consume only `POSITIONAL_KIND` / `POSITIONAL_VALUE` from Step 0-pre”) has no machine-readable artifact on the happy path—only empty tool output plus LLM memory of `$ARGUMENTS`. That re-opens the FINDING_1 drift the refactor removes at the script layer (e.g. `3249 --hard` pinned as issue + `HARD_REQUESTED=false`). **Suggested fix:** On `_argv_rc=0`, `printf '%s\n' "$_argv_out"` (or emit the bound KVs) before the fence ends, so the next turn can parse the same stream Step 0b is required to trust; alternatively fold argv parse into the Step 0a block where session KVs are already echoed.

- **correctness** `skills/design/SKILL.md:163-171` — The consumer assigns flag KVs verbatim (`hard_requested="$_value"`) with no `true`/`false` validation. A corrupted or mistyped line like `HARD_REQUESTED=yes` is accepted; Step 0b tier prose (`hard_requested=true`) and `--partition-requested "$partition_requested"` may then disagree (init validates bools, but tier resolution in prose may already have chosen SIMPLE). **Suggested fix:** In the `case` arms for the five `*_REQUESTED` keys, reject values other than `true`/`false` with the same abort path used for unexpected keys; keep `RUN_ID` / positional fields unrestricted aside from the parser’s newline guard.

### Out-of-Scope Observations

- **architecture** `skills/design/SKILL.md:24` — The top-level “Positional tail” bullet still describes only “first non-flag token” and does not mention that a numeric issue consumes only the first positional token and ignores later tokens (documented in `references/flags.md` and `parse-design-argv.md`). Minor doc drift, not introduced by the KV consumer loop itself.

- **code-quality** `skills/design/scripts/test-parse-design-argv.sh:39-42` — Harness `kv_value` correctly uses `substr($0, length(k)+2)` (so `RUN_ID=a=b` would parse correctly), but there is no case covering `=` inside `RUN_ID` or `POSITIONAL_VALUE`. Protocol supports it; coverage gap only.

- Within the scoped parser→0-pre-consumer path: `VALIDATION_ERROR` vs exit-code ordering (`180-195`) is sound; `<<<"${_argv_out:-}"` + `read -r` handles empty `RUN_ID` / `POSITIONAL_VALUE` and normal trailing-newline stripping from command substitution; validation failure emits only `VALIDATION_ERROR=` (no partial success KVs); the `*)` branch would reject a ninth KV line.
