Reviewing the branch diff and parser/harness implementation for partial-KV assertion gaps and trailing-token behavior.
### In-Scope Findings

- **architecture** `skills/design/scripts/test-parse-design-argv.sh:54-61` — `assert_no_flag_kvs` only rejects stdout lines matching `^(HARD_REQUESTED|POSITIONAL_KIND)=`, but the Step 0-pre contract (`parse-design-argv.md:26`, plan acceptance) requires validation exits to emit **only** `VALIDATION_ERROR=<token>` with no success-path KVs. A regression that printed the other six keys (`PARTITION_REQUESTED`, `BRAINSTORM_REQUESTED`, `MANUAL_REQUESTED`, `NO_DEDUP_REQUESTED`, `RUN_ID`, `POSITIONAL_VALUE`) before or after `VALIDATION_ERROR` would still pass every `assert_no_flag_kvs` call on the duplicate-hard, retired-flag, bogus-flag, and missing-`--run-id` paths. **Suggested fix:** Replace the two-key grep with a denylist of all eight success KV prefixes (or assert stdout is exactly one `VALIDATION_ERROR=` line plus optional trailing newline), and add a harness case that deliberately expects failure if any success KV appears on exit 3.

- **architecture** `skills/design/scripts/parse-design-argv.sh:78-98` — After the flag scan, the parser joins every remaining argv token into `positional_value` (lines 80–87), but the issue branch then sets `POSITIONAL_VALUE` to `first_positional` only (lines 93–95), silently discarding trailing tokens (e.g. `parse-design-argv.sh 3249 extra` → `POSITIONAL_KIND=issue`, `POSITIONAL_VALUE=3249`). Verbal classification keeps the full joined tail; issue classification does not. That asymmetry is not covered by `test-parse-design-argv.sh` (there is no `3249 extra`-style case), and `parse-design-argv.md:32-34` / `references/flags.md:29` describe the first token only without stating that extra argv words after a numeric issue are dropped. **Suggested fix:** Document the discard rule explicitly in `parse-design-argv.md` and `references/flags.md` if it is intentional; add a harness case pinning `POSITIONAL_VALUE=3249` for `3249 extra` (and optionally `3249 --hard` vs verbal `3249 --hard` via `--`). If trailing words should be preserved or rejected, change classification accordingly and test that behavior.

- **architecture** `skills/design/scripts/parse-design-argv.sh:78-98` — The issue branch’s use of only `first_positional` leaves the tail-join loop as misleading structure: tokens after a numeric first arg are accumulated then thrown away, which makes the “positional tail joined by single spaces” rule true for verbal paths only. That increases the risk of future edits that emit the joined value for issues and diverge from harness expectations (`positional then flaglike` at `test-parse-design-argv.sh:135-140`). **Suggested fix:** Either skip the join loop when `first_positional` matches `^[0-9]+$`, or classify issue vs verbal before joining so the implementation matches the documented contract in one place.

### Out-of-Scope Observations

- **architecture** `scripts/test-design-structure.sh:195-201` — Structural pins assert the parser script contains `VALIDATION_ERROR=` and `POSITIONAL_KIND=` and that `SKILL.md` wires `parse-design-argv.sh`, but they do not require the offline harness to enforce full stdout on validation failure. Harness strengthening (first finding) would close that gap without changing runtime behavior; today `validation_error()` in `parse-design-argv.sh:16-18` correctly emits only `VALIDATION_ERROR` and exits 3.
