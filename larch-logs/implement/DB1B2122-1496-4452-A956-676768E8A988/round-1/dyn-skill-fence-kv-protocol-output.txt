Checking pause-check fence scope, CLAUDE_PLUGIN_ROOT handling elsewhere, and whether the harness covers embedded `=` in POSITIONAL_VALUE.
### In-Scope Findings

- **risk-integration** `skills/design/SKILL.md:130-138` — The Step 0-pre fence uses `export CLAUDE_PLUGIN_ROOT='${CLAUDE_PLUGIN_ROOT}'` and only aborts when the variable is empty. If the skill loader fails to expand the template, Bash assigns the literal string `${CLAUDE_PLUGIN_ROOT}` (non-empty), the guard does not fire, and the invoke resolves to a bogus path such as `${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/parse-design-argv.sh` instead of failing closed before session setup. **Suggested fix:** After export, reject the literal unexpanded token (e.g. `[ "$CLAUDE_PLUGIN_ROOT" = '${CLAUDE_PLUGIN_ROOT}' ]`) and/or require `-x "${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/parse-design-argv.sh"` before running the parser, matching a path-exists check rather than emptiness alone.

- **risk-integration** `skills/design/SKILL.md:127-138` — argv is passed through the `<PUBLIC_ARGV_WORDS>` placeholder with no structural pin that the rendered fence contains real shell words. If the orchestrator leaves the placeholder literal or substitutes a single re-tokenized string, Bash can treat `<PUBLIC_ARGV_WORDS>` as stdin redirection (or otherwise mis-invoke the script) while `parse-design-argv.sh` and `test-parse-design-argv.sh` still pass; verbal tails with spaces/metacharacters depend entirely on per-token shell quoting discipline in prose. **Suggested fix:** Add a `test-design-structure.sh` grep pin forbidding literal `<PUBLIC_ARGV_WORDS>` in the Step 0-pre fence, document a concrete before/after example in `parse-design-argv.md` (e.g. three-token verbal tail → `'--hard' 'add' 'a foo'`), and/or pass argv via a dedicated env var or newline-delimited stdin protocol so the fence is not LLM-interpolated.

- **risk-integration** `skills/design/scripts/parse-design-argv.sh:107`, `skills/design/SKILL.md:151-165` — `POSITIONAL_VALUE` is emitted with a single `printf '%s\n'` line; an argv token containing an embedded newline produces extra stdout lines, and the orchestrator’s `while read` + `%%=*`/`#*=` loop only binds the first line (or mis-handles trailing lines). There is no harness case for multiline verbal input or for `POSITIONAL_VALUE` containing `=` on the orchestrator handoff path (the `%%=*`/`#*=` split itself is fine for embedded equals on one line). **Suggested fix:** Reject or escape embedded newlines in `parse-design-argv.sh` (validation error or encode), or switch the machine contract to length-prefixed/base64/JSON lines; add a harness case for `POSITIONAL_VALUE` with `=` and document that newlines are unsupported.

### Out-of-Scope Observations

No change required for that split pattern on single-line KVs.
