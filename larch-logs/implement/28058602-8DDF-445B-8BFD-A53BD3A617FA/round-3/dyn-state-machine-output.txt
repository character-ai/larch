### In-Scope Findings

- **architecture** `skills/design/scripts/run-step3-review.sh:256-259` — On the outer Gate-C cap path (`STEP3_REVIEW_CAP_REACHED=true`), the driver deletes `oos-accepted-design.md` together with Gate-B-facing artifacts (`accepted-plan-findings.md`, `ballot.txt`, etc.). Unlike a normal Step 3 completion, no new review runs and nothing repopulates that file. After several Gate C re-entries (e.g. SIMPLE cap 3), accepted OOS accumulated across rounds 1–3 can be erased on the cap-reached entry, while the run can still continue to Gate C approval and Step 5b (`file-design-oos.sh` reads `oos-accepted-design.md`). That breaks the cumulative-OOS contract in `plan-review-loop.md` and `references/plan-review.md`. **Suggested fix:** On `cap-reached`, clear only Gate-B-stale in-scope review artifacts; keep `oos-accepted-design.md` (or archive it before delete and restore after the cap branch). Add a `test-step3-review-cap.sh` case that seeds cumulative OOS, hits cap, and asserts Step 5b input survives.

- **architecture** `skills/design/SKILL.md:1101-1108` — Step 3 prose says the plan preview is gated by `.step3-entry-plan-printed` and skipped on Gate C / Gate A re-entries, but the Bash fence calls `emit-design-plan-preview.sh --variant step3` directly. Per `emit-design-plan-preview.md`, that script is a pure renderer: it neither reads nor writes the sentinel. Sentinel ownership lives in `run-step3-review.sh --preview-only` (`run-step3-review.md`), which SKILL does not invoke here. The Step 3 preview state machine is therefore split across two contracts, and re-entry skip behavior is not mechanically enforced. **Suggested fix:** Route preview through `run-step3-review.sh --preview-only` (single owner for render + sentinel), or update SKILL/docs to drop sentinel claims and document unconditional re-print on every Step 3 entry.

- **architecture** `skills/design/SKILL.md:1117` — Step 3 still documents a “Between-round revision helper for the forthcoming plan-review-loop integration” pointing at `revise-plan-with-waterfall.sh`. Keeping this in the normative Step 3 load list tells the orchestrator inter-round auto-revision may still exist and conflicts with the new state machine. The implementation plan explicitly called for removing this S030 pin. **Suggested fix:** Delete the `revise-plan-with-waterfall.sh` integration sentence from Step 3; if the helper stays for legacy/orphan use, mention that only in `revise-plan-with-waterfall.md` / SECURITY, not as an active Step 3 integration surface.
