### In-Scope Findings

- **correctness** `skills/design/scripts/check-plan-size.sh:187-218` — When `drift-baseline.env` exists as a regular file but is unreadable (empty file, missing keys, or non-integer values), the script emits a WARN and skips drift for that call, but it never removes or re-seeds the file. Because the write-once seed path only runs in the final `else` branch when the path is absent, every later invocation hits the unreadable-file branch again and drift stays permanently disabled for the rest of the session. That defeats the cumulative drift guard after a corrupted or zero-byte baseline artifact is left in `$DESIGN_TMPDIR`. **Suggested fix:** Treat unreadable baselines as absent: delete or ignore the broken file and fall through to the one-time seed write (or only skip re-seed for the symlink case that tests already pin). Add a harness case that creates `touch drift-baseline.env` and asserts a later call re-seeds and can fire drift.

- **correctness** `skills/design/scripts/design-postplan-emit.sh:559-572` — On initial Step 2b, `design-postplan-emit.sh` exits `10` for validator defects before `_postplan_run_plan_size` and `_postplan_snapshot_drift_baseline` run, so no `drift-baseline.env` is captured for the first `plan.txt` draft. After Fix-and-retry, the first successful emit seeds the baseline from the repaired plan, not the original Step 2b write. Growth between the first draft and the validator-fixed draft is therefore invisible to the drift guard, which weakens the stated goal of anchoring to the initial Step 2b size estimate. **Suggested fix:** Either snapshot baseline immediately after the first successful plan emit (before validator), or persist a separate pre-validator baseline and compare drift against that anchor while still gating hard/partition checks on the post-validator size.

- **correctness** `skills/design/scripts/check-plan-size.sh:200-204` — Drift evaluation is gated on `baseline_* != current_*` in addition to `drift_exceeds`. That matches the strict `>` threshold at exactly `2×`, but it also means a plan can change materially while line counts stay equal (same `PLAN_LINES` / `DIFF_LINES`, different body text or metadata) without ever re-entering the exceedance check once counts match the stored baseline. The guard is line-count-based only, so content sprawl with stable counts bypasses drift entirely. **Suggested fix:** If content-sensitive drift is required, compare a hash or byte size of the plan body in addition to line counts; otherwise document explicitly that drift is count-only so operators know text-only creep is out of scope.

- **risk-integration** `skills/design/scripts/design-postplan-emit.sh:395-414` — When `HARD_TRIGGER_FIRED=true` or `PARTITION_REQUESTED=true`, the driver exits `12`/`13` before the drift branch even if `DRIFT_TRIGGER_FIRED=true` was already computed. That matches documented precedence, but the operator gets no drift Continue/Cancel prompt in those combined cases (for example, a plan that is both over the hard body cap and more than `2×` the baseline). **Suggested fix:** If dual signaling is desired, include drift ratios in the hard-trigger FD3 section when `DRIFT_TRIGGER_FIRED=true`, or document that hard/partition paths intentionally suppress the drift prompt.
