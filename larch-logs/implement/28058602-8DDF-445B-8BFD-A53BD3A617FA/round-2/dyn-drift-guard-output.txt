Reviewing the branch diff and key drift-guard files for correctness issues.
### In-Scope Findings

- **correctness** `skills/design/scripts/design-postplan-emit.sh:401-407` — When `check-plan-size.sh` returns rc `2` (missing/malformed `diff_lines` trailer, missing plan, etc.), `_postplan_finish_merged_plan_size` flushes and exits `0` without ever evaluating drift, even if `drift-baseline.env` was written earlier by `_postplan_seed_initial_drift_baseline` (line 514) or a prior successful emit. A Gate B / discussion rewrite can grow `plan.txt` substantially while leaving the trailer broken; the merged fence then proceeds as “ok” and skips both hard-size and drift prompts, defeating the new sprawl guard on a realistic failure path. **Suggested fix:** On rc `2`, if a readable `drift-baseline.env` exists, still parse `plan_lines` from the body (or run a drift-only helper) and surface drift via rc `14` or a dedicated warning before the degraded proceed; at minimum, do not treat rc `2` as unconditional success when a baseline snapshot is present.

- **correctness** `skills/design/scripts/check-plan-size.sh:170-175` — If `drift-baseline.env` exists but is partially corrupt (one key invalid), the script emits `WARN=…drift baseline unreadable…`, leaves `baseline_plan_lines` / `baseline_diff_lines` at the **current** plan metrics (lines 163–164), and never loads the still-valid key from disk. Drift is disabled for that call (intentional per docs), but the stdout contract still emits `BASELINE_PLAN_LINES` / `BASELINE_DIFF_LINES` as if they were the anchored baseline. Any caller that prints those KVs in a drift prompt (Step 2b.5 step 6, merged rc `14` arms in `skills/design/SKILL.md` and `skills/design/references/approval-gates.md`) can show a false “baseline” equal to the current size while drift is silently off. **Suggested fix:** On unreadable baseline, emit empty or `unknown` baseline KVs (or repeat the parsed file values with an explicit `BASELINE_STATUS=unreadable` flag) and require orchestrator fences to treat unreadable baseline as a loud warning, not as display evidence.

- **correctness** `skills/design/scripts/design-postplan-emit.sh:514-587` — Baseline anchoring is split across `_postplan_seed_initial_drift_baseline` (runs after emit, **before** validator) and `_postplan_snapshot_drift_baseline` (runs only after a successful `_postplan_run_plan_size`). The plan/docs say the write-once baseline is taken from the initial Step 2b plan-size computation after `--snapshot-original`; in practice the first write often happens at line 514, before validator pass/fail and before the authoritative plan-size call at 585. If validator returns rc `10` and the operator later replaces `plan.txt` on Fix-and-retry, the baseline remains the pre-validation snapshot; that is mostly desirable, but if `_postplan_seed` fails while the later plan-size call succeeds, only the second call’s metrics are compared and the snapshot helper at 587 becomes a no-op when the file already exists—leaving baseline potentially misaligned with the post-validator plan-size parse. **Suggested fix:** Write `drift-baseline.env` only once in a single place immediately after the first successful `_postplan_run_plan_size` when `--snapshot-original` is set (remove the early seed call), and keep the Override-path seed solely inside `check-plan-size.sh` when no file exists.

### Out-of-Scope Observations

- **risk-integration** `skills/design/scripts/test-design-postplan-emit.sh` — The harness covers merged hard trigger (case D14) but has no cases for merged drift (`exit 14`, `PLAN_SIZE_STATUS=drift-trigger`, `## Plan Size — Drift`, baseline write-once / no-overwrite). Plan acceptance explicitly calls for these; their absence increases regression risk for the rc `14` contract but is a test-gap rather than a proven runtime defect.

- **risk-integration** `docs/configuration-and-permissions.md` — `LARCH_DESIGN_DRIFT_MULTIPLE` is documented in `skills/design/references/flags.md` but not in the configuration env-var table the plan listed; operators may miss the knob (documentation only).
