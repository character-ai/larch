### In-Scope Findings

- **correctness** `python/ci_monitor.py:911-933` — The unified substantive-attempt contract in the plan requires setting `code_fix_attempted_on_ready_log` only after ready logs **and** ready jobs **and** either per-job machinery actually runs or vendor verification is consumed (`vendor_rc==4` / `verify-failed`). Bash follows that in `scripts/ship-pr.sh:2606-2683` (flag at per-job entry with `ci_failed_count > 0`, or on `vendor_rc==4`). Python instead sets `code_fix_attempted = bool(classified.fixable)` before the tier waterfall and passes it through on `waterfall-failed` returns such as `all tiers failed` **before** the per-job loop at `937-943` ever runs. That makes `evaluate_failure` return `fix-exhausted` / `ci-fix-exhausted` when only launchers failed, which `test_evaluate_failure_per_job_exhausted` encodes (`launcher_exit=1`, no winning tier). The important divergence is vendor-only exhaustion (`FAILED_JOBS_COUNT=0` / no fixable per-job path in Bash): after a winning tier, push failure leaves Bash without the flag and on `exit_stall` (exit 4), while Python still sets the flag via `code_fix_attempted or bool(waterfall.winning_tier)` at `936` and routes to `fix-exhausted` (`test_evaluate_failure_push_failed_routes_fix_exhausted`). That violates FINDING_1’s launcher/push carve-out relative to `scripts/test-ship-pr.sh:4188-4230` (`ci_fix_launcher_only_exhausted` expects exit 4). **Suggested fix:** In `run_ci_fix`, drop the upfront `bool(classified.fixable)` assignment; set `code_fix_attempted_on_ready_log` only when the per-job loop over `classified.fixable` is entered (after `winning_tier`), on `verify-failed`, or on verification-retry re-drive—mirroring Bash. Do not pass the flag on `all tiers failed` / `push failed` unless one of those paths ran. Add a Python regression with ready logs, empty/zero fixable job dispatch, winning tier + push failure → `waterfall-failed` / `STALLED`, not `ci-fix-exhausted`.
