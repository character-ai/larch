Reviewing the branch diff and comparing Bash vs Python CI-failure handling for parity.
### In-Scope Findings

- **architecture** `python/ci_monitor.py:926-970` — The unified substantive-attempt contract is not aligned with Bash ordering. In `scripts/ship-pr.sh`, `_code_fix_attempted_on_ready_log` is set when `run_per_job_local_fix_loop` is entered (`ci_failed_count > 0`, ~2604–2606) **before** the vendor waterfall; exhaustion after all launcher tiers fail still routes to `ci-fix-exhausted` (exit 3). In Python, `code_fix_attempted` is only assigned **after** `run_waterfall` returns a `winning_tier` (~930); if every tier fails (~926–928), `run_ci_fix` returns `waterfall-failed` without ever setting `code_fix_attempted_on_ready_log`, so `evaluate_failure` ends at `waterfall-failed` / `STALLED` instead of `fix-exhausted` / autonomous exit 3. That is the same scenario `ci_fix_exhausted` in `scripts/test-ship-pr.sh` (~3418–3471) covers for Bash but has no Python counterpart to the planned `test_evaluate_failure_per_job_exhausted_routes_needs_user_input`. **Suggested fix:** Mirror Bash by setting and propagating `code_fix_attempted_on_ready_log` when ready logs + ready jobs exist and the per-job phase is entered (before or independent of tier success), e.g. set the flag as soon as `classified.fixable` is non-empty and jobs are ready, or restructure `run_ci_fix` to run the per-job phase before/alongside the vendor waterfall like Bash; add a Python test with fixable jobs and all tiers failing to lock parity.

- **architecture** `python/ci_monitor.py:963-970` — After a winning tier, per-job verify, and local fix work, `code_fix_attempted` is set to `True` (~930) but a push failure returns `FixResult(status="waterfall-failed", detail="push failed")` without `code_fix_attempted_on_ready_log=True` (~969–970). `evaluate_failure` only promotes the outer flag from `fix.code_fix_attempted_on_ready_log` (~1062–1063), so substantive work followed by push failure stalls (`waterfall-failed` / exit 4) instead of routing to `fix-exhausted` / autonomous CI-fix. Bash keeps `_code_fix_attempted_on_ready_log=true` from per-job entry (~2606) through push failure (~2610–2622, ~2703–2705). **Suggested fix:** Include `code_fix_attempted_on_ready_log=code_fix_attempted` (or `True` when the per-job loop ran) on the `push failed` return, and add a unit test that stubs a successful verify with a failed push and expects `fix-exhausted`.

- **architecture** `python/ci_monitor.py:1004-1021` — Upfront log reuse when the transient rerun budget is exhausted diverges slightly: Bash skips the entire upfront block when `TRANSIENT_RETRIES >= 1` (`scripts/ship-pr.sh:2504–2526`), while Python always calls `collect_failed_logs` (~1004) but only stashes inside `if transient_retries < CI_MONITOR_TRANSIENT_RERUN_MAX` (~1006–1021), so with `transient_retries >= 1` Python performs an extra upfront fetch that Bash does not. Behavior of iteration-1 stash/re-fetch matches when cap is not exhausted; this is extra I/O, not a logic fork on the gate itself. **Suggested fix:** Wrap the upfront `collect_failed_logs` call in the same `transient_retries < CI_MONITOR_TRANSIENT_RERUN_MAX` guard as the rerun/stash logic, or document the intentional extra probe if you prefer simpler Python control flow.
