Reviewing Bash/Python parity for the CI failure gate: reading the diff and the corresponding sections in both implementations.
### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:2606-2608` vs `python/ci_monitor.py:928-936` — The unified substantive-attempt predicate diverges on the fixable-jobs + launcher-exhaustion path. Bash sets `_code_fix_attempted_on_ready_log=true` as soon as `ci_failed_count > 0` and the TSV is non-empty, **before** `run_per_job_local_fix_loop` and **before** any vendor tier succeeds. Python sets `code_fix_attempted` only **after** `agents.run_waterfall` yields a `winning_tier`, immediately before the per-job loop inside `run_ci_fix`. When all launcher tiers fail but failed jobs are fixable, Python correctly ends in `waterfall-failed` / stall (`python/test_ci_monitor.py:809-840`), while Bash still accumulates a substantive flag and should route to `BAIL_REASON=ci-fix-exhausted` exit 3 at `scripts/ship-pr.sh:2705-2708`—contradicting FINDING_1 and the new Bash regression `ci_fix_fixable_launcher_only_exhausted` at `scripts/test-ship-pr.sh:4233-4284`, which expects exit 4. **Suggested fix:** Align the predicate in both trees: either move the Bash flag to after per-job machinery actually runs (e.g., per-job loop returns without immediate exhaustion, or `vendor_rc==4` / verification-retry consumption), or gate Python’s flag on per-job entry without requiring a winning vendor tier—matching the plan’s “entered `run_per_job_local_fix_loop` with `ci_failed_count > 0`” wording—and add/keep cross-tree tests for fixable jobs + all-fail launchers.

- **risk-integration** `scripts/ship-pr.sh:2562-2576` vs `python/ci_monitor.py:998-1058` — Bash has a `CI_FIX_REBASE_PENDING` branch at the top of each fix-loop iteration that sets `_code_fix_attempted_on_ready_log=true` on `stage_rc==4` **before** the `gh_logs_rc` / `ci_failed_rc` readiness deferrals at `2590-2602`. Python `evaluate_failure` has no equivalent pending-rebase path. A deferred iteration in Bash can therefore mark a substantive attempt without ready logs/jobs in that outer attempt; Python would defer without setting `code_fix_attempted_on_ready_log`, changing whether outer exhaustion becomes `ci-fix-exhausted` vs stall after `LARCH_SHIP_PR_IMPL=python` cutover. **Suggested fix:** Either port `CI_FIX_REBASE_PENDING` handling into `evaluate_failure` with the same readiness guards, or move the Bash flag assignment below the log/job-ready checks (and only set it when rebase-pending staging actually runs against ready failure data).

- **risk-integration** `python/ci_monitor.py:1014-1031` vs `scripts/ship-pr.sh:2504-2527` — Upfront log fetch timing differs when `TRANSIENT_RETRIES` / `transient_retries` is already at cap: Bash skips the entire upfront `gh-run-logs.sh` block when `retries >= 1`, while Python always calls `collect_failed_logs` once before the fix loop (stash is correctly withheld when the transient cap is reached). Behavior for blind rerun and ready-only reuse is aligned, but the extra upfront fetch on the Python path is a minor behavioral/API-call difference under retry exhaustion. **Suggested fix:** Optional parity: wrap the upfront `collect_failed_logs` call in the same `transient_retries < CI_MONITOR_TRANSIENT_RERUN_MAX` guard as the rerun branch, or document the extra fetch as an acceptable Python-only optimization.

### Out-of-Scope Observations

That leaves a documented Bash/Python parity case (`ci_fix_exhausted` in `scripts/test-ship-pr.sh:3418-3486`) without a matching pytest that exhausts after per-job entry without `verify-failed`.
