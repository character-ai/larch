Reviewing the branch diff and key Python CLI files for runtime code-quality issues.
### In-Scope Findings

- **code-quality** `python/ship.py:310-324` — The CLI surface is incomplete relative to the bash Step 8+ argv contract and the plan’s own `RunContext` fields: `build_parser()` exposes only a subset of flags and has no `--no-logs-commit`, while bash always passes `--no-logs-commit "$no_logs_commit"` and seeds `NO_LOGS_COMMIT` in `ship-pr-state.sh`. `_ctx_from_args()` only overlays argparse fields and never reads that state file, so a Python invocation that mirrors the documented `--branch … --merge …` argv list but does not explicitly export `NO_LOGS_COMMIT`/`LARCH_NO_LOGS_COMMIT` into the process environment will silently run with `no_logs_commit=False` and may commit log batches when the operator requested `--no-logs-commit`. **Suggested fix:** Add a `--no-logs-commit` flag (defaulting from `NO_LOGS_COMMIT`/`LARCH_NO_LOGS_COMMIT` like other booleans), merge it in `_ctx_from_args()`, document it in the SKILL python branch, and add a unit test that argv `"true"` suppresses pre-push commits.

- **code-quality** `python/ship.py:327-345` — `_ctx_from_args()` always overwrites `RunContext.from_env()` branch/issue fields with argparse defaults that only consult `BRANCH_NAME` and `ISSUE_NUMBER`, even when those argv defaults resolve to `""`. That clobbers valid `from_env()` fallbacks (`BRANCH`, `ISSUE`) and leaves no way to recover alternate env keys once argparse has run. Any caller that relies on secondary env names (or omits `--branch`/`--issue` while alternate keys are set) gets an empty branch/issue in the live context. **Suggested fix:** Only apply argparse overrides when the parsed value is non-empty, or mirror `from_env()`’s fallback chain in `build_parser()` defaults; add tests in `python/test_run_context.py`/`python/test_ship.py` for `BRANCH`-only and `ISSUE`-only env construction through `main()`.

- **code-quality** `python/run_context.py:9-13` — `_env_bool()` treats truth as strictly `raw.lower() == "true"`, but other runtime code (e.g. `logging_util._quiet_disabled()` at `python/logging_util.py:17-21`) accepts `1`, `yes`, and `on`. Session/bootstrap paths may therefore set `LARCH_NO_LOGS_COMMIT=1` or similar while `RunContext.from_env()` still yields `no_logs_commit=False`, breaking log-commit suppression without an obvious failure mode. **Suggested fix:** Centralize boolean parsing (shared helper accepting the same truthy set as bash/session-env writers) and cover `NO_LOGS_COMMIT`/`LARCH_NO_LOGS_COMMIT` variants in `test_run_context.py`.

- **code-quality** `python/ship.py:181-187` — `run_ship()` hardcodes `codex_present=True` and `cursor_present=True` into `checks.run_checks_phase()`, ignoring the session’s degraded-tool probe results that bash reads from session-env. On a reduced-panel run this misreports tool availability to the checks/lint-fix loop and can dispatch fixers the session marked absent. **Suggested fix:** Thread `CODEX_PRESENT`/`CURSOR_PRESENT` from `RunContext.from_env()` (new fields with defaults), pass them through `run_ship()`, and assert the wiring in `test_ship.py`.

- **code-quality** `python/ship.py:348-354` — `main()` has no top-level exception handler: any uncaught exception aborts before `emit_result()`, so stdout carries no JSON envelope and the Step 8+ orchestrator cannot distinguish crash vs stall/transient. That violates the “single JSON object on stdout” contract the SKILL branch depends on. **Suggested fix:** Wrap `run_ship()` in `main()` with a broad `except Exception` path that emits a `ShipResult(outcome=STALLED, detail=…)` (or a dedicated failure outcome if you add one), always calls `emit_result()`, and returns the mapped exit code; add a CLI test that forces an internal error and still yields parseable JSON.

- **code-quality** `python/test_ship.py:71-203` — Runtime CLI seams are largely untested: there are no tests for `build_parser()`, `_ctx_from_args()`, or `main()` exit codes, and the plan’s acceptance scenarios (PR-only, draft, forked, transient, stall, GOTO-rebase, cap exhaustion, each `needs_user_reason`) are absent despite being listed in the issue plan. Only `run_ship()`/`emit_result()` helpers are covered, so argv/env regressions like the missing `--no-logs-commit` flag would not be caught in CI. **Suggested fix:** Extend `test_ship.py` with subprocess or `main([...])` tests for argv/env construction, exit-code mapping, JSON stdout shape, and at least one test per documented `needs_user_reason`/`failed_run_id` handback.

### Out-of-Scope Observations

- **code-quality** `python/config.py:15-16` — `EXIT_BAIL`/`EXIT_STALLED` and `EXIT_STALL`/`EXIT_TRANSIENT` share identical numeric values; the branch adds the new Outcome map without removing the legacy names, which increases the chance of routing through the wrong constant in future edits. Consider deprecating or aliasing with comments pointing exclusively to `OUTCOME_EXIT_MAP`.
