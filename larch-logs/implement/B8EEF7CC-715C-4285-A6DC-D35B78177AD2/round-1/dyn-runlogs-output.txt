Reviewing run-log integration in the branch diff and key implementation files.
Checking whether post-merge manifest updates should call `larch-log.sh` and how bash sets `pr_number`:
### In-Scope Findings

- **risk-integration** `python/run_logs.py:533-546` — Post-merge finalization writes `pr_number` into `steps_ran["pr_number"]` as a string, but the live bash path and `larch-log.sh manifest` store a **top-level** numeric `pr_number` (see `scripts/ship-pr.sh` ~3100–3105 and `scripts/larch-log.sh` ~465–473). `scripts/verify-run-log-completeness.sh` reads `manifest_field pr_number` from the root object (~69–75, ~251), so merged Python-path runs can pass `status=done` while audit tooling still treats `pr_number` as missing. **Suggested fix:** Set top-level `pr_number` the same way bash does—either extend the manifest writer to preserve jq-updated top-level fields or shell out to `larch-log.sh manifest --field status=done --field pr_number=<N>` for the terminal update—and align tests to assert `manifest["pr_number"]`, not `steps_ran`.

- **risk-integration** `python/ship.py:180-208` and `python/finalize.py:54-65` — `run_ship` computes `repo_root = cwd or str(Path.cwd())` for checks and the dedicated pre-push flush, but passes the raw `cwd` argument into `finalize.postbump`, which runs `flush_logs_pre` and `rebase_and_push` before the pre-push flush. When `cwd` is `None`, postbump refresh hits `REFRESH_SKIP_NO_REPO_CWD` (no log commit) while `rebase_and_push` can still force-push; only the later pre-push flush commits batches. That inverts bash bump-phase ordering (`refresh-run-logs.sh` commits before postbump rebase/push in `scripts/ship-pr.sh` ~1097–1105) and can leave an intermediate remote tip without committed run logs. **Suggested fix:** Pass `repo_root` (or `cwd or str(Path.cwd())`) consistently into `finalize.postbump` for both `flush_logs_pre` and `rebase_and_push`, and add a driver test that `cwd=None` still commits before any push.

- **risk-integration** `python/ship.py:159-163` — `run_postmerge_phase` only calls `load_or_recover_manifest` then `flush_logs_post`. Bash `run_postmerge_phase` (`scripts/ship-pr.sh` ~3062–3091) runs `larch-log.sh init` when `manifest.json` is missing, tags `status=partial` with `recovery_reason=manifest_lost_mid_run`, and **skips** `status=done` / `write-final-report.sh` if recovery fails. The Python path can synthesize a minimal manifest via `init_run` without `recovery_reason` and still proceed to `status=done`, losing the partial-recovery signal and fail-closed report skip. **Suggested fix:** Port the bash recovery block (init with issue, partial + `recovery_reason`, gate `flush_logs_post` / `_write_final_report` on recovery success) before the existing manifest-before-report ordering.

- **risk-integration** `python/run_logs.py:304-332` and `488-512` — Every `load_or_recover_manifest` / `update_manifest` / `_write_manifest` round-trip keeps only `{status, version, run_id, steps_ran, created_at, updated_at}` and rewrites `manifest.json`, dropping schema_version-2 fields (`skill`, `issue_number`, `schema_version`, etc.) that earlier implement steps create via `larch-log.sh init`. Phase 7 amplifies this because `finalize.postbump` and the pre-push flush always call `flush_logs_pre` → `update_manifest` on the live Python path. **Suggested fix:** Use jq-preserving updates (delegate to `larch-log.sh manifest` for field merges) or merge unknown keys on read before write so pre-ship manifests stay schema-complete for downstream audit and completeness tooling.

### Out-of-Scope Observations

- The plan called for a unit test asserting manifest `status=done` and `pr_number` are written **before** `_write_final_report` in `flush_logs_post`; `python/test_run_logs.py` covers no-commit behavior and `steps_ran["pr_number"]` but not call-order / top-level field placement. That is a test-gap against the stated acceptance criteria, not a separate runtime defect beyond the `pr_number` location bug above.

- `python/config.py` still defines legacy `EXIT_BAIL=4` / `EXIT_STALL=6` alongside the new Outcome map; confusing but unchanged in intent and outside the run-log flush scope.
