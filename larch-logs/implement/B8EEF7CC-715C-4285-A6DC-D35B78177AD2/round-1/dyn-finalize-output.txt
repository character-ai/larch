Reviewing finalize-related changes: reading the diff, commit history, and key implementation files.
### In-Scope Findings

- **correctness** `python/finalize.py:46-71` — `postbump` routes through `rebase.rebase_and_push` with `defer_push` only when `repo_unavailable` is true, so any available-repo path always force-pushes after rebase. Bash Step 8b runs `rebase-push.sh --no-push`, then `run_force_push_gate`, which calls `git-force-push.sh` only when `check-remote-branch.sh` reports the feature branch is already on the remote (`scripts/implement-finalize.sh:461-512`). On a first push (remote absent), bash correctly leaves `FORCE_PUSH_STATUS=absent`; Python can push prematurely or fail when the remote branch does not exist yet. **Suggested fix:** Split postbump into rebase-with-`defer_push=True` plus a ported force-push gate (remote presence check before push), matching bash ordering and outcomes instead of unconditional `_force_push_branch`.

- **correctness** `python/finalize.py:46-71` — Postbump never validates that the current git branch matches `ctx.branch_name` / `ctx.branch` before rebase/push. Bash calls `validate_postbump_state_branch` before rebase and again before the force-push gate (`scripts/implement-finalize.sh:402-407`, `472-476`), returning branch-mismatch without mutating the tree. Python can rebase/push from `main` or the wrong branch and surface misleading stalls later. **Suggested fix:** Add the same branch-name guard (current branch must equal `BRANCH_NAME` from context) and map mismatch to `Outcome.STALLED` with a dedicated status, consistent with bash exit 4 semantics.

- **correctness** `python/finalize.py:107-126` — `postmerge` only runs `git switch main` and `git branch -D`, then compares `git log -1 --format=%s` to the expected title with **exact equality**. Bash uses `local-cleanup.sh` (checkout, fetch, pull, orphan log-flush handling) before `verify-main.sh`, which accepts a **prefix** match and a **(#{N}) suffix** fallback for `--admin` merges (`scripts/local-cleanup.sh:66-127`, `scripts/verify-main.sh:75-90`). Python can falsely return `Outcome.STALLED` / `verify-main-unexpected` on normal squash merges with slightly different subjects, and on valid admin merges. **Suggested fix:** Port `local-cleanup` sync behavior (or call equivalent `git` steps) and reuse `verify-main.sh` matching rules (prefix + PR suffix), not strict string equality.

- **correctness** `python/ship.py:150-165` — When `finalize.postmerge` returns non-OK (e.g. verify-main failure), `run_postmerge_phase` returns immediately and **does not** call `finalize.write_finalize_state`. On the Python ship path, Step 18 still expects `$IMPLEMENT_TMPDIR/finalize-state.sh` (`skills/implement/SKILL.md` Phase 7 contract). A verify-main stall leaves Step 18 without required keys and can break `implement-finalize.sh teardown` / `restore-finalize-state.sh`. **Suggested fix:** Write `finalize-state.sh` on all post-merge driver exits (including verify failure), or document and implement an alternate Step 18 path; at minimum mirror bash ship-pr behavior of persisting state before stall handoff.

- **correctness** `python/finalize.py:258-265` — `_cleanup_target_ok` does not implement `verify_cleanup_target` from bash (`scripts/implement-finalize.sh:593-637`). If the tmpdir basename matches `expected_tmpdir_basename_prefix`, cleanup is allowed **without** reading `session-id`; if the prefix is empty, cleanup is always allowed. Bash requires basename **and** session match (with session-only authorization when the prefix mismatches but the UUID matches). Python can delete the wrong session tmpdir or skip validation entirely. **Suggested fix:** Port `verify_cleanup_target` logic verbatim (including default prefix from clone tag, session-id file check, and session-match override path) before `shutil.rmtree`.

- **correctness** `python/finalize.py:209-211` — Branch A stalled rename calls `_rename_issue` whenever `stall_tracking` is true, without checking the tracking issue is still `OPEN`. Bash fetches issue state via `get-issue-info.sh` and renames only when `VALUE=OPEN` (`scripts/implement-finalize.sh:910-924`). Python may attempt rename on already-closed issues and report `failed` or behave differently from production teardown. **Suggested fix:** Gate stalled rename on `gh issue view` / `get-issue-info` state `OPEN`, matching bash Branch A.

- **correctness** `python/finalize.py:174-197` — `_write_stalled_sentinel` always writes `ISSUE_URL=` empty and omits `TIMESTAMP`, while bash `write_stalled_run_sentinel` fills `ISSUE_URL` from `get-issue-info.sh` and records a UTC timestamp (`scripts/implement-finalize.sh:820-850`, `938-947`). Stalled-run recovery tooling that reads `larch-stalled-run.txt` loses the tracking-issue URL. **Suggested fix:** Resolve issue URL before writing the sentinel and include `TIMESTAMP` with the same format as bash.

### Out-of-Scope Observations

- **correctness** `python/finalize.py:46-67` — Postbump uses full `rebase_and_rebump` conflict resolution (agent launches via `_resolve_conflicts`), whereas bash Step 8b treats rebase conflicts as `rebase-failed` and bails without in-phase fixers (`scripts/implement-finalize.sh:431-440`). That behavioral gap is outside the scout’s post-merge/stalled-run focus but will affect parity when `LARCH_SHIP_PR_IMPL=python` is enabled.

Likely idempotent but doubles commit work on the live path; not introduced as a finalize-contract violation in this review.

- **architecture** `python/finalize.teardown` is not invoked from `ship.py` (by design); live Step 18 still uses `implement-finalize.sh teardown`. Several teardown gaps above matter most when Python teardown is wired later; Branch A rename and cleanup guards still affect parity tests and future cutover.
