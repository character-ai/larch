Reviewing the branch diff and key integration points for PR/CI/rebase/merge risks.
### In-Scope Findings

- **risk-integration** `python/ship.py:266-288` — After the CI loop breaks on `monitor.action in {"merge", "already_merged"}`, `merge.merge_pr(..., post_flush=False)` can still return non-terminal results such as `ci_not_ready` or `main_advanced` (see `python/merge.py:111-127`). Bash treats those as “stay in the CI loop” (`scripts/ship-pr.sh:2957-2958` returns without advancing to postmerge). Python only special-cases `MERGE_RESULT_ERROR` and otherwise always calls `run_postmerge_phase`, which runs `finalize.postmerge` (branch delete + main verify) even though the PR was not merged and `pr_closed` stays false, so manifest `status=done` is skipped. That can delete the feature branch on a recoverable merge race and stall with a misleading cleanup path instead of re-polling CI. **Suggested fix:** Mirror bash: if `merged.result` is `ci_not_ready`, `main_advanced`, or other retryable merge literals, continue the CI `while` loop (or return a distinct outcome for orchestrator re-invoke) and only enter `run_postmerge_phase` when `merged.result` is in `POST_MERGE_MERGE_RESULTS` or you have an explicit terminal error.

- **risk-integration** `python/ship.py:232-264` — The CI monitor loop always passes `transient_retries=0` into `ci_monitor.monitor` and never updates it between iterations. Inside `evaluate_failure`, the blind `rerun_failed` path is gated by `transient_retries < CI_MONITOR_TRANSIENT_RERUN_MAX` (`python/ci_monitor.py:1072-1080`). Bash persists `TRANSIENT_RETRIES` in `ship-pr-state.sh` across `run_evaluate_failure` / rebase (`scripts/ship-pr.sh:2142-2153`, `3004`). On the Python path, every outer loop iteration resets the budget, so transient-looking CI logs can trigger repeated blind reruns across polls instead of one bounded rerun per failure episode. **Suggested fix:** Track `transient_retries` in the driver loop (increment when monitor/evaluate_failure performs a blind rerun, reset on successful fix push or `goto_rebase`, same as bash state transitions) and pass the accumulated value into each `monitor()` call.

- **risk-integration** `python/ship.py:253-261` — On `monitor.goto_rebase`, the driver calls `rebase.rebase_and_push` only. Bash `run_rebase_rebump` first runs `refresh-run-logs.sh` (and optional `larch-logs/` fixup) before rebasing (`scripts/ship-pr.sh:2703-2718`). Skipping that refresh on the Python GOTO-rebase path can push a branch whose pre-rebase log batches / token-timing / session-transcript commits were never flushed, so CI-fix rebases may not carry the same artifacts bash merges. **Suggested fix:** Before `rebase.rebase_and_push` on `goto_rebase`, invoke the same pre-rebase log refresh surface used in postbump (e.g. `run_logs.flush_logs_pre` with repo-root `cwd` and current `RunContext`, or a dedicated refresh helper ported from `refresh-run-logs.sh`).

- **risk-integration** `python/ship.py:400-414` — After `pr.ensure_pr` updates `working.pr_number` / `working.pr_url`, the driver returns or enters CI without a post-create `write-final-report.sh --comment-only` pass. Bash always re-runs that helper after PR creation to refresh the tracking-issue `larch:final-summary` comment with the live PR URL (`scripts/ship-pr.sh:1313-1322`); pre-push refresh only runs `_write_final_report` without `--comment-only` (`python/run_logs.py:469-475`). Python-path runs can leave the tracking issue on placeholder PR fields while still exiting 0. **Suggested fix:** After a successful `ensure_pr`, call `write-final-report.sh --implement-tmpdir … --comment-only` (best-effort, matching bash warnings-only failure semantics) with `RunContext` carrying the new PR URL before continuing to CI or early exit.

### Out-of-Scope Observations

- `python/test_ship.py` covers happy-path stage order, OOS gating, exit-code map, and `failed_run_id` plumbing but not `ci_not_ready` / `main_advanced` merge retry, GOTO-rebase log refresh, or post-PR comment-only final-report behavior; those gaps align with the integration issues above.
- `python/config.py:15-16` keeps legacy `EXIT_BAIL=4` / `EXIT_STALL=6` names alongside the new `OUTCOME_EXIT_MAP`; routing uses the map, but the duplicate constants are easy to misuse in later phases (not introduced as a functional bug in this diff’s call sites).
