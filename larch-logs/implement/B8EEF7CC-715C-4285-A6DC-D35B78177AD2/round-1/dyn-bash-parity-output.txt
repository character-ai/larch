Reviewing the branch diff and key Python/bash parity surfaces for correctness.
### In-Scope Findings

- **correctness** `python/finalize.py:115-120` — `postmerge` treats a verify-main mismatch as `Outcome.STALLED`, but bash `implement-finalize.sh postmerge` + `scripts/ship-pr.sh` `run_postmerge_phase` always finish with exit **0**; verify failure is only a warning (`VERIFY_MAIN_STATUS=unexpected`). On the Python path this wrongly surfaces exit **4** after a successful merge. **Suggested fix:** Keep `verify_main_status` advisory (always return `Outcome.OK` from `postmerge` when cleanup ran), matching bash; let `ship.py` continue to `flush_logs_post` and exit **0** unless cleanup itself hard-fails.

- **correctness** `python/ship.py:156-163` — Because `run_postmerge_phase` bails on any non-OK `postmerge` outcome, a verify-main mismatch also skips `run_logs.flush_logs_post`, so `manifest.json` never reaches `status=done` and `write-final-report` post-merge never runs even though `PR_CLOSED=true`. Bash still writes `status=done` and re-renders the final report after verify warnings (`scripts/ship-pr.sh` ~3056–3127). **Suggested fix:** Decouple verify warnings from terminal outcome (above), then always run the gated post-merge flush when `RUN_ID`, `PR_NUMBER`, `REPO_UNAVAILABLE=false`, and `PR_CLOSED=true`, as bash does.

- **correctness** `python/ship.py:212-218` — After `pr.ensure_pr`, `working` is updated with `pr_number` and `pr_url` but not `pr_title`, even though `title` was computed for create. `finalize.postmerge` builds `expected_title` from `ctx.pr_title` (`python/finalize.py:115-119`); orchestrator runs typically leave `PR_TITLE` unset in env, so verify almost always becomes `unexpected` and triggers the stall/flush-skip chain above. **Suggested fix:** `working = ctx.with_(pr_number=..., pr_url=..., pr_title=title, pr_closed=False)` (and persist the same title into `write_finalize_state`).

- **correctness** `python/finalize.py:107-119` — Post-merge cleanup is only `git switch main` + `git branch -D`; it does not fetch/pull `main` like `scripts/local-cleanup.sh` (which bash postmerge calls). `verify-main.sh` explicitly assumes main was already pulled. Without fetch/pull, `git.log_subject(..., "main")` reads stale HEAD and verify fails even when the merge succeeded. **Suggested fix:** Port the fetch/pull steps from `local-cleanup.sh` (or shell out to it) before verify, and align matching with `verify-main.sh` prefix/suffix rules instead of exact string equality.

- **correctness** `python/finalize.py:463-467` — Verify uses exact equality on the full subject, while `scripts/verify-main.sh` accepts a prefix match and a `(#N)` suffix fallback for `--admin` merges. Admin merges can pass in bash but return `STALLED` in Python. **Suggested fix:** Reuse the same prefix/suffix logic as `verify-main.sh` (or invoke that script) when setting `verify_main_status`.

- **correctness** `python/ship.py:212-226` — Bash runs a best-effort `write-final-report.sh --comment-only` after PR create to refresh the tracking-issue `larch:final-summary` with the live `PR_URL` (`scripts/ship-pr.sh` ~1313–1322); `pr.ensure_pr` / `ship.py` have no equivalent. **Suggested fix:** After a successful `ensure_pr`, call `run_logs._write_final_report` (or a small helper) with `--comment-only` when `PR_URL` is known, best-effort (warn-only on failure), matching bash.

- **correctness** `python/run_logs.py:469-475` — `_write_final_report` ignores the subprocess exit code. Bash treats pre-PR `write-final-report.sh` failure as terminal (`exit_stall 9b` at `scripts/ship-pr.sh` ~1265–1267) before `create-pr.sh`. Python still calls `pr.ensure_pr` after a failed report via `flush_logs_pre`. **Suggested fix:** Check `CommandResult.returncode` in `_write_final_report` (or in `flush_logs_pre`) and propagate a `Stalled`/`ShipResult` so pre-PR report failure matches bash fail-closed behavior.
