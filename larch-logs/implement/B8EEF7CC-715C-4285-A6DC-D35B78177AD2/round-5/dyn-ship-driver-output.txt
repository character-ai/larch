Reviewing the branch diff and `python/ship.py` orchestration against the plan.
### In-Scope Findings

- **architecture** `python/ship.py:305-360` — The CI monitor loop keeps `iteration`, `rebase_count`, `fix_attempts`, and `transient_retries` only in process memory. Each orchestrator re-invocation of `python/ship.py` (exit **3** after main-agent CI fix, exit **6** TRANSIENT, or `oos-filing` handback) restarts those counters at zero, while bash persists them in `$IMPLEMENT_TMPDIR/ship-pr-state.sh` (`REBASE_COUNT`, `FIX_ATTEMPTS`, `ITERATION`, `TRANSIENT_RETRIES`). That breaks the plan’s idempotent re-entry story and lets the 50/20/10 caps in `ci_monitor.decide()` be bypassed across multiple driver processes in one `/implement` run. **Suggested fix:** Persist loop counters under the implement tmpdir (e.g. `ship-driver-counters.env` or keys in `finalize-state.sh`) at the end of each monitor iteration and reload them at `run_ship` entry before entering the loop; mirror bash semantics on orchestrator re-invoke.

- **architecture** `python/ship.py:416-421`, `skills/implement/SKILL.md:955`, `skills/implement/SKILL.md:1040` — The JSON envelope exposes `outcome`, `needs_user_reason`, `failed_run_id`, etc., but not the active ship phase. Exit **6** handling in Step 8+ still keys transient retries off `PHASE` in `ship-pr-state.sh` (`$IMPLEMENT_TMPDIR/ship-pr-net-retries-$PHASE.count`), which the Python path does not write and explicitly tells the orchestrator not to read for routing. With `LARCH_SHIP_PR_IMPL=python`, transient retries cannot follow the documented per-phase budget. **Suggested fix:** Add a stable `phase` (or `transient_phase`) field to `ShipResult`/stdout JSON and document the Python branch to use it for counter file names; optionally append the same value to the JSONL journal on every terminal result.

- **architecture** `python/ship.py:246-276` — Every `run_ship` call runs `checks.run_checks_phase` then `finalize.postbump` (log refresh + rebase + force-push) from the top, with no ground-truth short-circuit (e.g. “PR already open and CI state X → enter monitor only”). Bash resumes from persisted `PHASE` in `ship-pr-state.sh` without repeating earlier phases. After a CI-fix handback or transient retry, the Python driver can repeat Step 8b rebase/push even when a PR already exists, which is extra churn versus bash and weakens “re-derive position from gh/git” in practice. **Suggested fix:** Add an entry probe (gh PR for branch, merge state, OOS disposition) that selects the first required stage, or persist last-completed stage in tmpdir and skip postbump/PR-prep when ground truth shows they already succeeded.

### Out-of-Scope Observations

- **architecture** `python/test_ship.py` — The plan calls for broad driver tests (goto-rebase loop, cap exhaustion, draft/forked/repo-unavailable paths, single post-merge flush). The branch only adds five focused tests (happy-path order, OOS gate, exit map, `failed_run_id`, JSON emit). That gap does not change runtime behavior but leaves the orchestration issues above unguarded in CI.

- **correctness** `python/finalize.py:145-150` — `postmerge` returns `Outcome.OK` when main verification is `unexpected`, so `run_postmerge_phase` can still surface overall `OK` and run manifest `status=done` flush. That matches current bash `run_postmerge_phase` behavior (record failure, still flush when `PR_CLOSED=true`), so it is not a Python-only regression introduced here.
