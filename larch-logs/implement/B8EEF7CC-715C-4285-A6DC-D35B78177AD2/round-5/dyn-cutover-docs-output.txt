### In-Scope Findings

- **risk-integration** `skills/implement/SKILL.md:955-1040` — The new Python selector tells the orchestrator to route on `ship.py` JSON + exit codes and not to read `ship-pr-state.sh`, but the rest of Step 8+ is still written entirely for bash: mandatory initial `ship-pr-state.sh` seeding (971–983), post-return parsing from that file (1020–1040), Exit 6 counters keyed on `PHASE` from state (1040), OOS checkpoint fork/unavail probes from state (1042), and CI-fix `refresh-run-logs.sh --state-file …/ship-pr-state.sh` (1035). `python/ship.py` never updates `ship-pr-state.sh`, so any path that still writes the initial file but follows the Python routing paragraph leaves helpers with a frozen snapshot (`PHASE=checks`, empty `PR_NUMBER`, stale flags) while the live run state lives only in JSON/`finalize-state.sh`. **Suggested fix:** Add an explicit `LARCH_SHIP_PR_IMPL=python` fork for Step 8+ (separate Invoke fence, skip state-file routing, JSON-driven Exit 3/4/6 tables, reinvoke `python3 …/ship.py` instead of `ship-pr.sh`, and either stop seeding `ship-pr-state.sh` or document a minimal sync writer). Teach downstream helpers (`oos-disposition-checkpoint.sh`, Step 18a, `refresh-run-logs.sh`) to read `finalize-state.sh` and/or `session-env.sh` when the Python driver is active.

- **risk-integration** `skills/implement/SKILL.md:1040` — Exit 6 tells the orchestrator to maintain `$IMPLEMENT_TMPDIR/ship-pr-net-retries-$PHASE.count` using `PHASE` from `ship-pr-state.sh`, but the Python path explicitly does not persist `PHASE` anywhere on disk. Reusing the bash counter contract on a Python run either shares one bucket under a stale `checks` phase or forces the model to invent a phase name, so transient retry budgeting will not match bash. **Suggested fix:** Specify a Python-path counter (e.g. fixed `ship-pr-net-retries-python-ship.count` or a `detail`/journal token from JSON) in the Python selector paragraph, or have `ship.py` emit a machine-stable phase label on stdout for counter naming.

- **risk-integration** `python/finalize.py:72-82`, `python/ship.py:344-353`, `skills/implement/SKILL.md:1039` — Postbump and CI `goto_rebase` call `rebase.rebase_and_push(..., allow_conflict_fix=False)`, which raises `Stalled` on conflicts (`python/rebase.py:338-339`). Bash instead surfaces `exit 4` with `RESUME_PHASE=ship-pr-rrr-phase14`, `CALLER_KIND=ship_pr_pre_push`, and `CONFLICT_FILES=` for the orchestrator conflict-resolution procedure. On `LARCH_SHIP_PR_IMPL=python`, push/rebase conflicts become a bare stall with no `CONFLICT_FILES` handoff, so the documented Phase 1–4 recovery path never runs. **Suggested fix:** Port the bash handoff (emit conflict CSV + a JSON/`needs_user_reason` the SKILL maps to the existing conflict-resolution block) or enable controlled in-process conflict fix where parity allows; do not leave postbump/CI rebase as silent `STALLED` only.

- **risk-integration** `skills/implement/SKILL.md:1035`, `scripts/refresh-run-logs.sh:22-36` — The autonomous CI-fix sub-procedure still refreshes logs via `--state-file "$IMPLEMENT_TMPDIR/ship-pr-state.sh"`. On a Python-only ship leg that file is never updated (and may be absent), so `refresh-run-logs.sh` can skip commits (`REFRESH_SKIP_*`) or use stale `RUN_ID`/`NO_LOGS_COMMIT`/`MERGE_RESULT` while the orchestrator correctly used JSON for `failed_run_id`. **Suggested fix:** For the Python branch, pass `--state-file "$IMPLEMENT_TMPDIR/finalize-state.sh"` (after `ship.py` has written it) or extend `refresh-run-logs.sh` to accept finalize-state and document that in the Python selector’s CI-fix steps.

- **risk-integration** `skills/implement/SKILL.md:1189-1214`, `python/ship.py:174-178` — Step 18a resolves `STALL_TRACKING` only from memory, `ship-pr-state.sh`, and `session-env.sh`. `ship.py` records stalls in `finalize-state.sh` via `_write_terminal_state` / `write_finalize_state`, not in `ship-pr-state.sh`. A Python stall with `STALL_TRACKING=false` in memory and an initial state file can skip Step 18a recovery and teardown title-prefix handling even though `finalize-state.sh` says stalled. **Suggested fix:** Add `finalize-state.sh` as a fourth layer in Step 18a (and in stall-recovery’s disk reads) when `LARCH_SHIP_PR_IMPL=python`, or require the orchestrator to set in-memory `STALL_TRACKING=true` on every Python `outcome=STALLED` before Step 18.

- **risk-integration** `python/ship.py:448-451`, `skills/implement/SKILL.md:1002-1016` — Docs say to pass the “same” argv as bash, but bash uses `--no-logs-commit "$no_logs_commit"` (string true/false) while `ship.py` defines `--no-logs-commit` as `store_true`. Copying the bash Invoke line can set `no_logs_commit=True` whenever the flag token is present (including `--no-logs-commit false`) or omit suppression when bash passes `false` without the flag. **Suggested fix:** Match bash with `--no-logs-commit` accepting an explicit boolean argument, or document that the Python path must rely on `NO_LOGS_COMMIT` / `LARCH_NO_LOGS_COMMIT` env from session-env and must not copy the bash flag shape literally.
