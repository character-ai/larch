Reviewing CI monitor, rebase, and ship driver interactions from the branch diff and source files.
### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:1249-1283`, `python/ship.py:335-360`, `scripts/ship-pr.sh:3010-3012` — The branch refactors `rebase_then_evaluate` so `monitor()` runs `evaluate_failure()` first and only sets `goto_rebase` on selected outcomes, while bash always calls `run_rebase_rebump` before `run_evaluate_failure` and uses `CI_FIX_REBASE_PENDING` to force-push/retry without re-running fixers on stale logs. Fixes can therefore land on a branch that is still behind `main`, post-fix pushes use normal `git push` (`stage_and_push` at `python/ci_monitor.py:860-882`) instead of bash’s post-rebase force-push path, and failed fix attempts on a behind+fail PR never get the upfront rebase bash always performs. **Suggested fix:** Restore bash ordering for `rebase_then_evaluate`: rebase (with the same conflict/force-push semantics as `run_rebase_rebump`) before any fixer dispatch, or port the `CI_FIX_REBASE_PENDING` short-circuit so a pending rebase skips vendor work and uses force-push after verify; gate `goto_rebase` on `decision.action == "rebase_then_evaluate"` or `status.behind_count > 0`, not unconditionally on every `pushed` result.

- **risk-integration** `python/ci_monitor.py:1278-1283`, `python/ship.py:336-354` — After a successful CI fix, `monitor()` always returns `goto_rebase=True` even when `decide()` chose plain `evaluate_failure` (`fail` with `behind_count == 0`). Bash only rebases inside `_stage_and_push_ci_fixes` when `ci-behind-count` is positive (`scripts/ship-pr.sh:1615-1634`). The Python driver will therefore run an extra `rebase.rebase_and_push`, increment `rebase_count`, and force-push on every fix-only cycle, increasing conflict risk and burning the 20-rebase cap on active repos. **Suggested fix:** Set `goto=True` on the `pushed` path only when `decision.action == "rebase_then_evaluate"` or `status.behind_count > 0`; add a `test_ci_monitor.py` case for `evaluate_failure` + `pushed` + `behind=0` asserting `goto_rebase is False`, and a ship-loop test that rebases are not invoked in that scenario.

- **risk-integration** `python/ship.py:344-353`, `python/rebase.py:336-339`, `scripts/ship-pr.sh:2743-2751` — CI-loop rebases call `rebase.rebase_and_push(..., allow_conflict_fix=False)`, which raises `Stalled` on any conflict. Bash uses `rebase-push.sh --no-push --keep-on-conflict`, deterministic prepass, vendor/orchestrator conflict resolution, and can resume via `ship-pr-rrr-phase14`. Under `LARCH_SHIP_PR_IMPL=python`, a routine CI rebase conflict exits **4** instead of handing control back for inline resolution, diverging from the live bash recovery contract. **Suggested fix:** Use the same conflict policy as bash for CI rebases (`allow_conflict_fix=True` with the existing launch_fn path, or a dedicated CI rebase helper mirroring `run_rebase_rebump` / `--keep-on-conflict` handoff); map unresolved conflicts to `NEEDS_USER_INPUT` or the documented stall step rather than an immediate terminal stall when orchestrator recovery is expected.

- **risk-integration** `python/ship.py:305-360`, `scripts/ship-pr.sh:2188,2640-2643` — Counter semantics diverge from bash in ways that tighten budgets mid-run. `ship.py` increments `iteration` after every non-merge monitor pass and on `MERGE_RESULT_MAIN_ADVANCED` / `CI_NOT_READY` retries (`359-365`), while bash only bumps `ITERATION` on rebase paths (`2642`, `3004`); long fix-only CI loops can hit the 50-iteration stall in Python while bash keeps `ITERATION=0`. `transient_retries` is incremented on blind reruns (`355-356`) but never reset to `0` after a successful rebase or fix, whereas bash clears `TRANSIENT_RETRIES` on those paths; later failures lose the one allowed blind `ci-rerun-failed` retry (`CI_MONITOR_TRANSIENT_RERUN_MAX=1`). **Suggested fix:** Match bash counter rules: reset `transient_retries=0` after successful rebase and after `did_fixing` pushes; increment `iteration` only when a rebase actually runs (or when bash would have incremented `REBASE_COUNT`/`ITERATION`), not on every monitor/merge-not-ready cycle; add driver tests that simulate multi-pass fix loops and assert counters stay below caps when bash would continue.

### Out-of-Scope Observations

- `python/test_ship.py` stubs `ci_monitor.monitor` to a single happy-path return and does not exercise the goto-rebase loop, cap exhaustion, transient rerun accounting, or `rebase_then_evaluate` ordering described in the Phase 7 acceptance criteria. That gap makes the CI/rebase integration regressions above unlikely to be caught before cutover to `LARCH_SHIP_PR_IMPL=python`.

- `python/stage_and_push` always uses a normal `git push` (`python/ci_monitor.py:882`); bash switches to `git-force-push.sh` after rebase or when `CI_FIX_REBASE_PENDING` is set (`scripts/ship-pr.sh:1654-1658`). This is related to the rebase-ordering findings but is pre-existing in Phase 6 `ci_monitor.py` and amplified by the Phase 7 driver wiring.
