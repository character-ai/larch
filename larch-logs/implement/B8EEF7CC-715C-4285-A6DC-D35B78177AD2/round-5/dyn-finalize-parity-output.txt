Reviewing `python/finalize.py` against bash parity and the branch diff, with emphasis on risk-integration.
### In-Scope Findings

- **risk-integration** `python/finalize.py:120-151` — `postmerge()` reimplements cleanup with `git switch` / `git pull --ff-only` / `git branch -D` instead of the bash `local-cleanup.sh` contract (`scripts/implement-finalize.sh:668-684`, `scripts/local-cleanup.sh:66-136`). The bash helper fetches `origin/main` with transient retry, drops ahead-of-`origin/main` commits that are **only** `chore(larch-logs): flush …` orphans (reset hard to `origin/main`), then pulls with ahead-count diagnostics; Python skips fetch, orphan-drop, and non-`ff-only` recovery. On `LARCH_SHIP_PR_IMPL=python`, a common post-merge failure mode is local `main` still carrying prior larch-log flush commits: `pull --ff-only` fails, cleanup is marked `partial`, but the function still returns `Outcome.OK`, so the driver can proceed to manifest `status=done` while the workstation is left in a bad state. **Suggested fix:** Port the `local-cleanup.sh` / `verify-main.sh` behaviors into `postmerge()` (or shell out to those scripts until parity is proven), including orphan-flush reset, fetch+retry, and the same verify-title rules; add a regression test that simulates ahead-only larch-log commits on `main` and asserts cleanup reaches a pullable, verified HEAD.

- **risk-integration** `python/finalize.py:716-719` — When the remote-branch probe fails with a return code other than `0` or `2`, `postbump()` raises `TransientNetworkError`, which the driver surfaces as exit **6** (re-invoke). Bash `implement-finalize.sh` maps `check-remote-branch` transport/auth failures to `remote-check-failed` and `ship-pr.sh` stalls (exit **4**) (`scripts/implement-finalize.sh:514-519`, `scripts/ship-pr.sh:1117-1118`). That changes operator recovery: Python retries the whole ship driver; bash stops for Step 18 stall handling. **Suggested fix:** Classify `ls-remote` / remote-presence failures the same way as bash (stall on persistent remote-check failure, reserve TRANSIENT for signatures that `retry.is_transient_net_signature` would accept), and pin the mapping in `python/test_finalize.py` or `test_ship.py`.

- **risk-integration** `python/finalize.py:48-88` — Postbump folds log refresh (`flush_logs_pre`), rebase, and force-push into one call, while bash runs `refresh-run-logs.sh` once, then `implement-finalize.sh postbump` with **no** log write (`LOG_WRITE_STATUS=skipped`, `scripts/implement-finalize.sh:526-527`, `scripts/ship-pr.sh:1097-1105`). `ship.py` also calls `flush_logs_pre` again before PR create (`python/ship.py:260-278`), so the Python path can emit **two** pre-PR log commits and always force-pushes when `origin/<branch>` resolves, without the separate `check-remote-branch.sh` + `git-force-push.sh` gate (`scripts/implement-finalize.sh:478-507`). Lease/dirty-tree failures still stall, but push timing and remote-state handling can diverge from the soak-tested bash integration. **Suggested fix:** Match bash ordering explicitly: Trigger-C refresh once before rebase, keep postbump rebase/push-only (or split `rebase_and_push` into `--no-push` + gated push mirroring `run_force_push_gate`), and assert call order in `python/test_ship.py`.

- **risk-integration** `python/finalize.py:251-307` — `teardown()` omits several bash Step 18 integration steps that are still live for both impl modes today (`scripts/implement-finalize.sh:887-1037`): `flush_execution_issues_safety_net`, manifest recovery via `larch-log.sh`, optional teardown `larch-log.sh commit` (when no post-merge sentinel), `kill_session_background_processes`, and `cleanup-tmpdir.sh` (Python uses `shutil.rmtree(..., ignore_errors=True)` after `_cleanup_target_ok`). The module is not called from `ship.py` yet, but it is the planned port; drift here will matter the moment Step 18 branches to Python. **Suggested fix:** Port or delegate the missing teardown sub-steps, keep Branch A “preserve tmpdir” behavior, and extend `python/test_finalize_bash_parity.py` (or `scripts/test-implement-finalize.sh`) to cover teardown—not only postmerge skip flags.

- **risk-integration** `python/test_finalize_bash_parity.py:46-88` — The new “bash parity” harness only checks postmerge skip labels and that `postbump` calls flush+rebase without changelog; it does **not** exercise postmerge cleanup/verify mechanics, postbump force-push gate outcomes, remote-check failure routing, or teardown session guards. That leaves the highest-risk integration gaps above unguarded during the `LARCH_SHIP_PR_IMPL=python` soak. **Suggested fix:** Add table-driven cases sourced from `scripts/test-implement-finalize.sh` (or subprocess parity) for postmerge orphan-flush, verify-main suffix match, postbump `remote-check-failed` vs push-failed, and teardown stall preservation.

### Out-of-Scope Observations

- **risk-integration** `scripts/implement-finalize.sh:272-340` — Postbump state validation still references `BUMP_TYPE` / `NEW_VERSION` keys from the pre-#3368 surface; Python `postbump()` does not validate analogous context fields. This predates the branch’s Python port and is not introduced by `finalize.py`, but it remains a cross-path consistency footgun if bash postbump state files are ever fed into Python helpers.
