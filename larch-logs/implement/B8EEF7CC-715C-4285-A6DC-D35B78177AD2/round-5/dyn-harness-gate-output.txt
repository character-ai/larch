### In-Scope Findings

- **code-quality** `docs/linting.md:262` — The harness catalog documents `make test-merge-pr` on shard 5 but never adds a sibling row for the new `make test-merge-parity` target, even though `Makefile:83` and `Makefile:372-373` wire it into `test-harnesses-5` next to `test-merge-pr`. Operators following `docs/linting.md` will not discover the pytest parity gate or its co-location with the bash merge harness. **Suggested fix:** Add a `make test-merge-parity` table entry (purpose, `python/test_merge_bash_parity.py`, shard 5, pytest requirement) beside `test-merge-pr`, and mention it in any shard-5 summary lists if present.

- **code-quality** `Makefile:372-373` — `test-merge-parity` runs `python3 -m pytest python/test_merge_bash_parity.py` from the repo root, while `py-test` uses `cd python && pytest` (`Makefile:33-34`). Both rely on `python/pyproject.toml` `pythonpath`, but the split invocation style is easy to break when copied into scripts or run from a non-root cwd. **Suggested fix:** Match `py-test` with `cd python && python3 -m pytest test_merge_bash_parity.py` (or `pytest test_merge_bash_parity.py`) so harness and full-suite invocations share one pattern.

- **correctness** `python/test_ship.py:71-205` — The Phase 7 plan’s driver acceptance matrix (draft, forked, repo-unavailable, transient retry, each `needs_user_reason`, GOTO rebase loop, cap exhaustion, single post-merge flush beyond happy path, etc.) is largely unimplemented: only five tests exist (exit map, happy-path order, OOS gate, `failed_run_id` helper, JSON emit). Those tests run only under `make py-test` / the `python-tests` CI job, not under `make lint` harness shards—unlike merge parity, which #3339 explicitly co-located with `test-merge-pr`. **Suggested fix:** Expand `test_ship.py` toward the plan’s scenario list (or split focused modules) and consider whether any minimal ship-driver smoke belongs in a harness target if regressions should be caught without running the full `py-test` suite.

- **code-quality** `python/test_merge_bash_parity.py:25-28` — A module-level `pytest.mark.skipif(shutil.which("bash") is None)` skips the entire file, including `test_python_merge_behind_emits_admin_merged` (`python/test_merge_bash_parity.py:84-135`), which never shells out to bash. On environments without bash, `make test-merge-parity` can exit 0 with all tests skipped, weakening the “do not silently drop coverage via skipif” intent from the plan (even though Ubuntu CI has bash). **Suggested fix:** Remove the module-level skip; keep bash-only `skipif` on subprocess tests (e.g. `test_behind_emits_admin_merged` at `python/test_merge_bash_parity.py:138-139`) so pure-Python parity still runs.

- **architecture** `python/test_finalize_bash_parity.py:1-89` — The module is named and documented as “bash-parity” but only exercises in-process `finalize.postmerge` / `finalize.postbump` mocks; it does not subprocess `scripts/implement-finalize.sh` or compare stdout/KV output like `python/test_merge_bash_parity.py` does for `merge-pr.sh`. It is not wired into any `test-harnesses-N` shard—only `py-test`—so finalize parity is not co-gated with `test-implement-finalize` the way merge parity is co-gated with `test-merge-pr`. **Suggested fix:** Either extend the file with subprocess parity cases (post-#3368 skip branches) and/or add a `test-finalize-parity` Makefile target on an appropriate shard, or rename/reword the module to “smoke” so it does not imply bash parity that CI harnesses do not enforce.
