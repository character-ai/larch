Reviewing run-log manifest behavior: reading the diff and key source files.
### In-Scope Findings

- **correctness** `python/run_logs.py:487-537` — `flush_logs_pre` calls `_write_final_report`, which raises `ShipError` when `write-final-report.sh` exits non-zero. Bash `scripts/refresh-run-logs.sh` runs the same script with `2>/dev/null || true` and still attempts `larch-log.sh commit` (lines 71–72, 138–150). On the Python path, a transient or benign report-render failure aborts the whole pre-push phase (propagating from `finalize.postbump` and `python/ship.py:278-281` as `Outcome.STALLED`) even though log batches may be ready to commit. That diverges from bash’s non-fatal refresh semantics and can block PR creation for a failure unrelated to log-batch integrity. **Suggested fix:** Match bash: log report failures to execution issues (or return a skippable `RefreshSkip` reason) and continue to ledger render + `_larch_log_commit`; reserve hard failure for redaction/commit failures only.

- **correctness** `python/run_logs.py:353-370` — For the state-file-less path (`ctx.state_file is None`), `_pre_push_probe` only reads `ctx.merge_result` from `RunContext` env/argv. It does not consult `$IMPLEMENT_TMPDIR/finalize-state.sh` (`MERGE_RESULT`, written by `finalize.write_finalize_state` in `python/finalize.py:344-368`) or `$IMPLEMENT_TMPDIR/post-merge-sentinel` (written at `python/ship.py:208-209`). After a successful merge in the same tmpdir, a re-invoked `python/ship.py` (e.g. Exit 6 retry) with `MERGE_RESULT` unset in the environment will not hit `REFRESH_SKIP_POST_MERGE`, will run a full pre-push refresh, and hit `REFRESH_SKIP_COMMIT_FAILED` when `larch-log.sh` refuses commit due to the sentinel—non-fatal but wrong probe classification and unnecessary work. **Suggested fix:** When `ctx.state_file` is absent, fall back to `finalize-state.sh` and/or `post-merge-sentinel` for `merge_result` (and optionally `PR_CLOSED`) before applying the post-merge skip, mirroring how `flush_logs_post` already falls back to `ctx.merge_result` at `python/run_logs.py:569`.

- **correctness** `python/run_logs.py:560-595` — `flush_logs_post` writes `status=done` to `manifest.json` before `_write_final_report` / ledger renders. If `_render_token_timing_batches` raises `ShipError` (redaction failure), the function returns `RefreshSkip(skipped=True, reason="redaction-failed")` after the manifest already shows `done` (`python/ship.py:217-221` then stalls only when `post.outcome is Outcome.OK`). This matches the planned manifest-before-report ordering but leaves a “done” manifest with incomplete terminal artifacts. **Suggested fix:** Either document this as acceptable (manifest is source of truth for merge completion) or make post-merge flush transactional: write `status=done` only after report/ledger steps succeed, or roll manifest back to `partial` when returning `redaction-failed`.

### Out-of-Scope Observations

- The plan calls for a unit test asserting `flush_logs_post` writes `status=done` before `_write_final_report`; `python/test_run_logs.py` covers `status=done`, `pr_number`, and no git commit (`test_flush_logs_post_no_git_commit`) but not call ordering—worth adding to prevent reordering regressions.

- `REFRESH_SKIP_COMMIT_FAILED` is in `REFRESH_SKIP_MERGE_OK` (`python/config.py:175-183`), so `python/ship.py` and `finalize.postbump` treat commit failure as non-fatal; that matches bash `refresh-run-logs.sh || true` / non-fatal commit semantics, but differs from older review notes that expected merge to hard-abort on commit failure when `merge.py` still called `flush_logs_pre` with default `post_flush=True`. The ship driver uses `post_flush=False`; behavior is consistent for Phase 7.
