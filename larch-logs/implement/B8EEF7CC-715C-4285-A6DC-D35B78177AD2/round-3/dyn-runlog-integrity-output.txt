Reviewing run-log integrity changes: reading the diff and key implementation files.
### In-Scope Findings

- **correctness** `python/run_logs.py:559-607` — `flush_logs_post` writes `status=done` and `pr_number` only after `_write_final_report` and ledger renders, which inverts the fail-closed ordering required by the Phase 7 plan and the live bash driver. In `scripts/ship-pr.sh` `run_postmerge_phase` (lines 3098–3126), `larch-log.sh manifest … status=done pr_number=…` runs first and `write-final-report.sh` runs only when that manifest update succeeds; the Python path can leave `manifest.json` at `partial` while `summary-final.md` is refreshed, and if `_write_final_report` raises `ShipError`, `status=done` is never written at all. **Suggested fix:** Reorder `flush_logs_post` to match bash: when `finalize` is true, atomically set `status=done` and `pr_number` on the manifest first; run `_write_final_report` / ledger renders only after a successful done write; treat report/ledger failures as warnings (return a skip reason or log) without rolling back `status=done`. Add a unit test that records call/write order (manifest done before any `write-final-report.sh` invocation).

- **correctness** `python/ship.py:183-190` — `run_postmerge_phase` skips `flush_logs_post` whenever `finalize.postmerge` returns a non-`OK` outcome (for example partial local cleanup or `verify-main` title mismatch), but bash still runs the post-merge manifest `status=done` flush whenever `RUN_ID`, `PR_NUMBER`, `REPO_UNAVAILABLE=false`, and `PR_CLOSED=true`, even if `implement-finalize.sh postmerge` logged warnings (see `scripts/ship-pr.sh:3047-3128`, which always reaches the manifest block after postmerge). A merged PR can therefore end with `Outcome.STALLED`, no `status=done`, and a stale final summary while bash would have finalized the run log. **Suggested fix:** Decouple run-log finalization from postmerge success: always run the gated `flush_logs_post` when `_postmerge_should_flush(ctx)` is true (after writing `post-merge-sentinel`), and surface postmerge cleanup/verify problems via warnings/`detail` without blocking manifest/report finalization; align behavior with bash’s `record_failure` + continue pattern.

### Out-of-Scope Observations

- The plan called for an explicit `flush_logs_post` ordering test in `python/test_run_logs.py`; current coverage (`test_flush_logs_post_no_git_commit`, `test_flush_logs_post_leaves_partial_on_failed_merge`) asserts end state only, not manifest-before-report ordering, which made the regression above easy to miss.
