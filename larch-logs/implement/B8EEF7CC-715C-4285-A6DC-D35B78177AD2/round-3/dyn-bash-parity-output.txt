Reviewing the branch diff against bash contracts for risk-integration and bash-parity issues.
### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:1136-1316` — Bash maps per-job local CI failures to **exit 3** with `BAIL_REASON=ci-local-unfixable:…` (`scripts/ship-pr.sh:2023-2033`), which routes through the Step 8+ user-input / `AskUserQuestion` path. The Python monitor treats `local-unfixable` like other fix failures and returns `Outcome.STALLED` (exit **4**) via the generic branch at `1313-1316`. Enabling `LARCH_SHIP_PR_IMPL=python` changes operator handling for the same failure class. **Suggested fix:** Map `fix.status == "local-unfixable"` to `Outcome.NEEDS_USER_INPUT` with a stable `needs_user_reason` aligned to bash (e.g. prefix `ci-local-unfixable` in JSON `detail`/`needs_user_reason`), and add a `test_ship.py` case asserting exit **3**.

- **risk-integration** `skills/implement/SKILL.md:955-1040` — The Python selector says not to read `ship-pr-state.sh` for routing, but the Exit **6** block still requires `PHASE` from that file and a per-phase counter (`ship-pr-net-retries-$PHASE.count`). `python/ship.py` emits only JSON on stdout and does not persist `PHASE`. Transient retries on the Python path have no defined counter key, so the orchestrator cannot mirror bash’s cap-and-escalate behavior. **Suggested fix:** Extend the JSON contract with a `phase` (or `retry_key`) field and document a Python-specific counter path in the SKILL, or require a minimal auxiliary state file written only for retry bookkeeping.

- **risk-integration** `skills/implement/SKILL.md:1025-1037` — Autonomous CI-fix steps still read `FAILED_RUN_ID` / `REPO` from `ship-pr-state.sh` and call `refresh-run-logs.sh --state-file "$IMPLEMENT_TMPDIR/ship-pr-state.sh"` (step 10). On the Python path that file is intentionally absent; `scripts/refresh-run-logs.sh:25-26` treats a missing state file as fail-closed “merged” and skips the refresh commit. Post-fix log batches may not land before re-invoking `ship.py`. **Suggested fix:** Add a Python-path SKILL branch that refreshes via `RunContext`/`finalize-state.sh` (or `IMPLEMENT_TMPDIR` + `RUN_ID` env only), and/or teach `refresh-run-logs.sh` to accept finalize-state or env fallbacks when `ship-pr-state.sh` is missing.

- **risk-integration** `skills/implement/SKILL.md:1039-1040` — Exit **4** `ship_pr_pre_push` handoff depends on `RESUME_PHASE`, `CALLER_KIND`, and `CONFLICT_FILES=…` from bash `ship-pr.sh` stdout/state (`scripts/ship-pr.sh:2840-2844`). `python/ship.py` does not emit those KVs; rebase conflicts surface as `Outcome.STALLED` with text in JSON `detail` only (`ship.py:285-305`, `finalize.postbump` with `allow_conflict_fix=False` at `finalize.py:79`). Python-path operators lose the mandated conflict-resolution procedure. **Suggested fix:** Emit bash-compatible `CONFLICT_FILES` / handoff fields on stdout (or structured JSON fields) for rebase-conflict stalls, and document the Python Exit **4** branch in `SKILL.md`.

- **risk-integration** `python/run_logs.py:576-606` — The plan requires manifest `status=done` **before** final-report rendering. `flush_logs_post` writes `pr_number` into the manifest, calls `_write_final_report` at `586-587`, then sets `status=done` at `594-606`. A report render failure can leave `status=done` unset while summaries advance, breaking fail-closed ordering promised for Step 18 / audit tooling. **Suggested fix:** Move the `MANIFEST_STATUS_DONE` write to immediately after `pr_number` is recorded and before `_write_final_report`; extend `test_run_logs.py` to assert ordering, not only final field values.

- **risk-integration** `python/ship.py:389-437` and `skills/implement/SKILL.md:955` — Bash passes `--expected-session-id` and `--expected-tmpdir-basename-prefix` into `ship-pr.sh` (`SKILL.md:1009-1010`); the Python CLI has no matching flags and the selector’s argv list omits them. `finalize.write_finalize_state` (`finalize.py:349-350`) then often writes empty `EXPECTED_*` keys, weakening Step 18 teardown guards in `implement-finalize.sh`. **Suggested fix:** Add CLI flags (or require exports in the SKILL invoke block) and populate `RunContext` before any `write_finalize_state` call.

- **risk-integration** `python/ship.py:135-137` — The OOS pre-PR gate always uses `git log … origin/main..HEAD` for inline-triage breadcrumb matching, even when `forked`/`forked_target` is true. Fork runs compare CI against `upstream/main` elsewhere; this mismatch can false-trigger `oos-filing` or fail disposition checks vs `oos-disposition-checkpoint.sh` (`skills/implement/scripts/oos-disposition-checkpoint.sh:122-128`). **Suggested fix:** Use `upstream/main..HEAD` when forked, mirroring the checkpoint helper’s base-remote logic.

- **risk-integration** `python/finalize.py:126-128` — `postmerge` always runs `git pull --ff-only origin main`. Bash postbump/postmerge fork paths use `upstream` for rebase (`scripts/implement-finalize.sh:413`). Forked Python ship runs can verify the wrong default branch tip after merge. **Suggested fix:** Parameterize default remote/ref from `RunContext` (`upstream`/`main` when `forked_target`) in `postmerge`, with parity tests in `test_finalize.py`.
