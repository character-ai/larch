Reviewing CI harness and parity-test wiring from the branch diff and related files.
### In-Scope Findings

- **risk-integration** `python/test_ship.py:71-205` — Phase 7 acceptance calls for end-to-end driver coverage (PR-only, draft, forked, repo-unavailable, transient retry, each `needs_user_reason`, stall, GOTO-rebase loop, cap exhaustion, single post-merge flush, and related invariants). The new module only has five heavily mocked tests (exit map, one happy-path order walk, OOS gate, `failed_run_id` helper, JSON emit). `make py-test` / the `python-tests` CI job can stay green while most of the listed acceptance paths are untested, so regressions on the live cutover surface would not be caught until manual `LARCH_SHIP_PR_IMPL=python` runs. **Suggested fix:** Add the missing stubbed `run_ship` scenarios to `python/test_ship.py` (or a dedicated driver parity module) so `make py-test` exercises the acceptance matrix from the plan, not only stage-order smoke on one happy path.

- **risk-integration** `python/test_finalize_bash_parity.py:1-88` — The file is labeled bash-parity but never shells out to `scripts/implement-finalize.sh`; it only checks Python skip branches and mocked `postbump` call order. There is no `test-finalize-parity` Makefile target and no shard co-location with `test-implement-finalize` (shard 15), unlike merge parity (`test-merge-parity` beside `test-merge-pr` in `test-harnesses-5`). Post-merge/teardown drift against bash therefore depends on the separate bash harness plus a thin py-test smoke layer that does not compare outputs to bash. **Suggested fix:** Either extend this module (or add `test-finalize-parity` wired next to `test-implement-finalize`) with subprocess parity cases modeled on `test_merge_bash_parity.py` / `test_checks_bash_parity.py`, including `shutil.which("bash")` skip guards, or narrow the acceptance/docs claim so “bash parity” is explicitly owned only by `scripts/test-implement-finalize.sh`.

- **risk-integration** `python/test_merge_bash_parity.py:132-257` — Bash-subprocess cases skip only when `merge-pr.sh` is missing, not when `bash` is absent (`test_checks_bash_parity.py` guards both). On a runner without `bash`, `test-merge-parity` / shard 5 would error instead of skip, unlike the plan’s “skipif when bash is absent locally” parity pattern. Ubuntu CI has bash today, but the harness contract is inconsistent and brittle for minimal images. **Suggested fix:** Add `shutil.which("bash")` to the module-level or per-test `skipif` predicates, matching `python/test_checks_bash_parity.py`.

- **risk-integration** `skills/implement/SKILL.md:955` — `LARCH_SHIP_PR_IMPL` cutover is documented in SKILL, `docs/configuration-and-permissions.md`, and `python/config.py`, but no `scripts/test-implement-*.sh` harness asserts the selector, `python/ship.py` argv surface, or JSON+exit-code routing described in the Step 8+ branch. CI therefore does not mechanically guard the only live wiring change operators will flip during soak. **Suggested fix:** Add a small structural harness (e.g. extend `scripts/test-implement-structure.sh` or a dedicated `test-implement-ship-pr-impl.sh`) that greps/pins the SKILL python branch, required JSON keys, and exit-code literals, and register it on a `test-harnesses-N` shard line.
