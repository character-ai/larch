Reviewing run-log and manifest changes: reading the diff and key source files.
### In-Scope Findings

- **risk-integration** `python/run_logs.py:586-607` — `flush_logs_post` writes `status=done` only after `_write_final_report` and ledger/token renders, which inverts the bash post-merge contract in `scripts/ship-pr.sh` (manifest `status=done` + `pr_number` first, then `write-final-report.sh` only when `manifest_ok=true`) and the Phase 7 fail-closed requirement. If report or redaction fails, the manifest can remain `partial` while `summary-final.md` was already regenerated, and operators lose the bash guarantee that a failed manifest write blocks report refresh. **Suggested fix:** Reorder `flush_logs_post` to set `status=done` and top-level `pr_number` immediately when `finalize` is true (after the first manifest write with `pr_number`), then run `_write_final_report` / ledger renders only on success; on report failure, return a skip reason and do not leave a misleading partial manifest without surfacing stall to `run_postmerge_phase`.

- **risk-integration** `python/ship.py:203-208` — `run_postmerge_phase` overwrites `pr_closed` in `finalize-state.sh` from `postmerge` outcome (`post.outcome is Outcome.OK`) instead of preserving merge-time `PR_CLOSED=true` after a successful merge. Bash sets `PR_CLOSED=true` when merge completes and does not clear it when local cleanup or verify-main fails. Step 18 `implement-finalize.sh` `compute_run_outcome` and tracking-issue rename branches read `PR_CLOSED` from that file, so a merged PR with a failed verify can be classified as blocked/pr-open rather than closed. **Suggested fix:** Keep `ctx.pr_closed` from the merge path when writing finalize state; record postmerge failure via `STALL_TRACKING` / `STALL_STEP` / `verify_main_status` without resetting `PR_CLOSED`.

- **risk-integration** `python/ship.py:209-213` — Post-merge manifest recovery is weaker than bash: `run_postmerge_phase` only calls `load_or_recover_manifest`, while `scripts/ship-pr.sh:3062-3091` runs `larch-log.sh init` (with issue when available), tags `status=partial` + `recovery_reason`, and skips `status=done` when init fails. Python always local-inits via `init_run`, so a run can reach `flush_logs_post` → `status=done` in tmpdir even when bash would have aborted the flush after failed recovery, desyncing run-log audit state from GitHub-backed init. **Suggested fix:** Port the bash recovery gate (init + partial tag + `recovery_ok` flag) before `flush_logs_post`, and stall without writing `status=done` when recovery fails.

- **risk-integration** `python/test_run_logs.py` — The plan calls for a post-merge ordering test (manifest `status=done` + `pr_number` before final-report rendering), but existing tests only assert end state (`test_flush_logs_post_no_git_commit` at lines 116-125) and never observe call order inside `flush_logs_post`. The manifest-before-report regression in `run_logs.py` is therefore unguarded on the Python path. **Suggested fix:** Add a test that monkeypatches `_write_final_report` to record manifest `status` at invocation time and asserts it is already `done` with `pr_number` set.
