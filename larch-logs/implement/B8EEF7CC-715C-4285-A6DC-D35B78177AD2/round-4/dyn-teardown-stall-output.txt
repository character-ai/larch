Reviewing `finalize.py` and teardown/stall parity against bash — reading the diff, commit history, and implementation files.
### In-Scope Findings

- **correctness** `python/finalize.py:145-152` — `postmerge()` maps partial local cleanup or a failed main-HEAD title check to `Outcome.STALLED`, while `scripts/implement-finalize.sh` `run_postmerge()` always exits 0 and only emits `LOCAL_CLEANUP_STATUS=partial` / `VERIFY_MAIN_STATUS=unexpected` with warnings (`scripts/test-implement-finalize.sh` around the partial-cleanup case). On the live Python path, `python/ship.py:214-215` treats that as a hard ship failure instead of bash’s warn-and-continue post-merge behavior. **Suggested fix:** Match bash: keep `postmerge()` at `Outcome.OK` for partial/unexpected verify, encode severity in `local_cleanup_status` / `verify_main_status`, and let `ship.py` decide whether to stall (if at all) using the same rules as `ship-pr.sh` (which does not gate on those KVs).

- **correctness** `python/finalize.py:126-134` — Post-merge cleanup is an inline `git switch` / `git pull --ff-only` / `git branch -D` sequence and does not port `scripts/local-cleanup.sh` behavior: no `git fetch` (with transient retry) before pull, and no dropping of ahead-only `chore(larch-logs): flush` commits before syncing `main`. After a merged run with log-flush commits still on local `main`, verify can run against the wrong HEAD or pull can fail/partially succeed. **Suggested fix:** Port the fetch, orphan-flush detection/reset, and pull steps from `local-cleanup.sh` (or shell out to that script until a faithful Python port exists), then keep `verify-main.sh`-equivalent matching on the updated HEAD.

- **correctness** `python/finalize.py:193-212` — `auto_stash_stalled_changes()` returns `""` when `git stash push` fails (lines 206–207) and `teardown()` does not surface that failure. Bash `auto_stash_stalled_changes()` warns on stash failure and may fall back to resolving another stash ref (`scripts/implement-finalize.sh:789-815`). Stalled Branch A can write `larch-stalled-run.txt` with an empty `STASH_REF` while the worktree still has dirty files. **Suggested fix:** Mirror bash: warn/append execution-issue on stash or `git status` failure, only write the sentinel when stash resolution is reliable, and propagate a non-empty `stash_ref` or an explicit failure status into `FinalizeResult` / Step 18 KVs.

- **correctness** `python/finalize.py:204-211` — The stalled stash message is `larch-stalled-{issue}-{step}` with no UTC timestamp; bash uses `larch-stalled-${issue}-${step} ${timestamp}` (`scripts/implement-finalize.sh:781-783`) specifically so `git stash list` grepping stays unambiguous under concurrent runs. **Suggested fix:** Append the same UTC timestamp suffix to the stash `-m` label and keep label-based ref resolution (with bash’s fallback + warning if grep misses).

- **correctness** `python/finalize.py:155-190` — Branch A rename proceeds when `gh issue view` JSON omits `state` or returns an empty string (lines 174–175 treat that as rename-eligible). Bash only renames when `get-issue-info.sh` reports `STATE=OPEN` (`scripts/implement-finalize.sh:914-923`). A malformed/empty `state` can rename a non-open tracking issue to `[STALLED]`. **Suggested fix:** Require `state.upper() == "OPEN"` before calling `tracking_issue.rename()`; treat missing/unknown state as `rename_status=skipped` or `failed`, matching bash.

- **correctness** `python/finalize.py:48-88` — `postbump()` drives Step 8b through `rebase.rebase_and_push()` (single combined rebase+push path) instead of bash’s `rebase-push.sh --no-push` then `check-remote-branch.sh` + `git-force-push.sh` (`run_step8b_rebase` / `run_force_push_gate`). Failures diverge (e.g. bash `STATUS=push-failed` / `remote-check-failed` / `branch-mismatch` vs Python `Outcome.STALLED` / `TransientNetworkError`), and remote-branch/lease semantics are not the same code path. **Suggested fix:** Split postbump into the same two gates as `implement-finalize.sh postbump` (rebase without push, then conditional force-push), or thin-wrap those shell helpers until behavior is byte-aligned.

- **correctness** `python/finalize.py:249-305` — `teardown()` omits major bash Step 18 behavior still defined in `run_teardown()`: `flush_execution_issues_safety_net`, manifest recovery/`larch-log.sh` init, stall-only `stalled_at_step` manifest update, best-effort `larch-log.sh commit` (respecting `post-merge-sentinel` / `NO_LOGS_COMMIT`), and `kill_session_background_processes`. The module is not called from `ship.py` today (Step 18 stays on bash), but `python/test_finalize.py` and the Phase 7 plan treat this as the ported teardown surface. **Suggested fix:** Port those blocks (or delegate to `implement-finalize.sh teardown` until parity is complete) so stalled runs still persist partial manifest state and committed run logs, and session background jobs are reaped before tmpdir preservation.

- **correctness** `python/finalize.py:308-339` — `_cleanup_target_ok()` builds the default basename prefix from `Path.cwd().name` (lines 327–328), while bash `verify_cleanup_target()` uses `clone_basename_prefix` from the repo working tree at teardown time. If `teardown()` is invoked with a `cwd` outside the consumer clone, prefix/session checks can refuse legitimate tmpdirs or accept wrong ones. **Suggested fix:** Derive the default prefix from the repo root used for git operations (explicit `repo_root` argument or `git rev-parse --show-toplevel`), matching `clone_basename_prefix` semantics.

### Out-of-Scope Observations

- `python/test_finalize_bash_parity.py` and `python/test_finalize.py` only smoke-test skip branches, happy-path postmerge, and one stall path; they do not exercise partial postmerge, cleanup-guard refusal, stash/sentinel failure modes, or teardown log flush—so the gaps above are unlikely to be caught before `LARCH_SHIP_PR_IMPL=python` soak.

- `python/ship.py:209-215` uses pre-postmerge `ctx` (not `state_ctx`) for `_postmerge_should_flush()`, so a merge that set `pr_closed=true` can still run `flush_logs_post` after a failed `finalize.postmerge()`—related to the postmerge `Outcome` mismatch but outside `finalize.py` itself.
