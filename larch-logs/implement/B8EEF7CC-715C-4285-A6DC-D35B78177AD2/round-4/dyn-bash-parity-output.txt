Reviewing the branch diff and key Python/bash contract files for risk-integration parity.
### In-Scope Findings

- **risk-integration** `skills/implement/SKILL.md:955-1040` — The Python selector at line 955 says to route on JSON + exit code and **not** read `ship-pr-state.sh`, but the very next operational block still opens with “Parse the process exit code and then read `$IMPLEMENT_TMPDIR/ship-pr-state.sh`” and the Exit 3/4/6 matrices are entirely state-file keyed (`BAIL_REASON`, `FAILED_RUN_ID`, `PHASE`, `RESUME_PHASE`, `CALLER_KIND`, `OOS_PENDING`). For `LARCH_SHIP_PR_IMPL=python`, an orchestrator that follows the default Step 8+ prose will look for keys that `python/ship.py` never writes (by design), breaking CI-fix handback, transient retries (`ship-pr-net-retries-$PHASE.count` needs `PHASE`), exit-4 conflict handoff, and the OOS checkpoint’s `FORKED_TARGET`/`REPO_UNAVAILABLE` reads from state. **Suggested fix:** Add a parallel, python-only exit-routing subsection (or clearly label lines 971–1040 as bash-only) that maps JSON `outcome` / `needs_user_reason` / `failed_run_id` to the same continuations; for TRANSIENT, either emit a stable `phase` (or equivalent) in the JSON envelope for counter files, or document a single global counter when state is absent.

- **risk-integration** `python/run_logs.py:560-607` — Post-merge manifest finalization does **not** match bash ordering. `flush_logs_post` calls `_write_final_report` and ledger renders (lines 587–593) before writing `status=done` (lines 595–607). Bash `run_postmerge_phase` in `scripts/ship-pr.sh` sets `status=done` and `pr_number` via `larch-log.sh manifest` **first**, then runs `write-final-report.sh` only if manifest write succeeded (approximately lines 3100–3120). That fail-closed ordering was an explicit Phase 7 / #3339 requirement; reversing it means a failed or partial final-report can leave the manifest non-`done` while downstream tooling assumes the opposite sequencing bash provides. **Suggested fix:** Reorder `flush_logs_post` to set `MANIFEST_STATUS_DONE` and `pr_number` before any `_write_final_report` / ledger work, mirroring `ship-pr.sh`; add a unit test that records call order and fails if `write-final-report` runs before `status=done`.

- **risk-integration** `python/ship.py:327-344` — CI `goto_rebase` uses `rebase.rebase_and_push(...)` with default `allow_conflict_fix=True` (`python/rebase.py:289`), so conflicts are handled inside the Python driver via vendor resolution or a generic `Stalled`. Bash `ship-pr.sh` uses `rebase-push.sh --no-push --keep-on-conflict` and, on conflict, sets `RESUME_PHASE=ship-pr-rrr-phase14`, `CALLER_KIND=ship_pr_pre_push`, emits `CONFLICT_FILES`, and exits **4** for the orchestrator Conflict Resolution Procedure (approximately lines 2743–2842). The Python path therefore cannot trigger the documented `ship_pr_pre_push` handoff in `skills/implement/SKILL.md` exit-4, which is a material integration regression for merge-capable runs with rebase conflicts after CI fixes. **Suggested fix:** Port the keep-on-conflict pause contract: call rebase with `allow_conflict_fix=False`, surface conflict file lists in JSON (and/or write orchestrator-visible finalize/state fields), and return `Outcome.STALLED` (exit 4) with tokens the SKILL python branch can route to `conflict-resolution.md`, or explicitly document and test that Python auto-resolution fully replaces that handoff.

- **risk-integration** `python/ship.py:243-248` — In `run_postmerge_phase`, `finalize.write_finalize_state` uses `state_ctx` where `PR_CLOSED` is set from `post.outcome is Outcome.OK` (postmerge local cleanup/verify), not from the merge result. If the PR merged but `finalize.postmerge` stalls (e.g. main title mismatch in `python/finalize.py:146-149`), `finalize-state.sh` gets `PR_CLOSED=false` even though `ctx.pr_closed` was set true at merge time and `_postmerge_should_flush(ctx)` may still run post-merge log flush using the pre-postmerge context. Step 18 `implement-finalize.sh teardown` reads `PR_CLOSED` from finalize-state, so tracking-issue rename / terminal semantics can diverge from bash after a successful merge with a failed verify-main. **Suggested fix:** Keep `PR_CLOSED` aligned with merge/PR ground truth (the `pr_closed` flag set when `merge_result` enters `POST_MERGE_MERGE_RESULTS`); record postmerge verify failure via `STALL_TRACKING` / `STALL_STEP` without clearing `PR_CLOSED`.

- **risk-integration** `skills/implement/SKILL.md:1025-1037` — Autonomous main-agent CI-fix step 10 still requires `refresh-run-logs.sh --state-file "$IMPLEMENT_TMPDIR/ship-pr-state.sh"`, and `scripts/refresh-run-logs.sh:25-26` treats a missing state file as fail-closed “merged” skip. On the Python path, if the orchestrator skips seeding `ship-pr-state.sh` (consistent with “do not read for routing”), post-fix log refresh can silently skip, unlike bash. **Suggested fix:** For `LARCH_SHIP_PR_IMPL=python`, either require a minimal compat state file for refresh helpers only, or change step 10 to use `RunContext`/tmpdir-only refresh (e.g. `flush_logs_pre` with repo-root `cwd`) and document that in the python-only exit matrix.

- **correctness** `python/ship.py:54-68` — `_step_result_to_ship` normalizes `needs_user_reason` only when `detail.startswith(config.NEEDS_USER_CI_FIX_EXHAUSTED)`; it does not similarly canonicalize `first-fixer-non-health` or `fix-attempts-exhausted`. `ci_monitor.py` can emit richer `detail` strings (e.g. `ci-fix-exhausted: <jobs>` at lines 1047, 1305). The SKILL python branch dispatches autonomous CI-fix on exact `needs_user_reason` tokens; a non-canonical JSON value can skip the sub-procedure even when `failed_run_id` is present. **Suggested fix:** Map `StepResult.detail` to the fixed `config.NEEDS_USER_*` literals for all exit-3 reasons (same as OOS uses `config.NEEDS_USER_OOS_FILING`), keeping verbose text in `detail` only.
