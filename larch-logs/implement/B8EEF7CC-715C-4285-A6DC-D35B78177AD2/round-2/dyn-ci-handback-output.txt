Reviewing CI monitor integration in the branch diff and related source files.
### In-Scope Findings

- **correctness** `python/ci_monitor.py:1315-1331` — On `decision.action == "bail"`, `monitor()` always returns `Outcome.STALLED` with `detail=decision.bail_reason`, even when that reason matches a transient network signature. Bash `ship-pr.sh` maps the same bail path through `is_transient_net_signature` and `exit_transient_net` (exit **6**). Under `LARCH_SHIP_PR_IMPL=python`, transient CI-wait/poll failures surface as exit **4** instead of **6**, so the Step 8+ orchestrator will stall instead of sleeping and re-invoking idempotently. **Suggested fix:** Before the generic bail branch, if `decision.bail_reason` and/or collected failure text matches `retry.is_transient_net_signature`, return `StepResult(outcome=Outcome.TRANSIENT, ...)` (and map to exit **6** in `ship.py`); add a parity test mirroring `scripts/ship-pr.sh` lines 3027–3028.

- **correctness** `python/ship.py:230-272` — The CI loop initializes `transient_retries = 0` and passes it into every `ci_monitor.monitor()` call, but never updates it between iterations. Bash persists `TRANSIENT_RETRIES` in `ship-pr-state.sh` across `run_evaluate_failure` / CI-loop turns (`scripts/ship-pr.sh` ~2142–2152, 3004, 3207). After a blind transient `ci-rerun-failed` submission in one iteration, the next iteration still passes `transient_retries=0`, so `evaluate_failure()` can repeat the transient rerun path (`CI_MONITOR_TRANSIENT_RERUN_MAX`) instead of proceeding to the fix waterfall like bash. **Suggested fix:** Track `transient_retries` in the `ship.py` loop (increment when `evaluate_failure` submits a new rerun, reset to `0` on successful push/rebase like bash `state_set_many TRANSIENT_RETRIES 0`), or have `monitor()` return an updated counter and thread it through `MonitorResult`.

- **correctness** `python/ci_monitor.py:1239-1244`, `python/ship.py:253-272` — For `decision.action == "rebase_then_evaluate"`, `monitor()` only sets `goto_rebase=True` and does not run `evaluate_failure()` in the same call. `ship.py` rebases, increments `iteration`, and loops; failure evaluation happens on a later `monitor()` / `poll_ci()` pass. Bash handles `rebase_then_evaluate` atomically (`run_rebase_rebump` then `run_evaluate_failure` in one handler; `scripts/ship-pr.sh` ~3010–3012) with a single `ITERATION` bump per rebase (`~2640-2643`). The split consumes two `iteration` slots against `CI_MONITOR_MAX_ITERATIONS` (50) and can add an extra full poll wait before fixers run. **Suggested fix:** In `monitor()`, when `decision.action == "rebase_then_evaluate"`, perform rebase (or return a composite result) and call `evaluate_failure()` in the same invocation before returning to `ship.py`; alternatively, teach `ship.py` not to increment `iteration` until both rebase and evaluate complete, matching bash `ITERATION` accounting.
