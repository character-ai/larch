### In-Scope Findings

- **correctness** `python/ship.py:274-299` — After `merge.merge_pr`, only `ci_not_ready` and `main_advanced` loop back into CI monitoring. Bash `ship-pr.sh` also handles `version_already_published` (rebase or treat as merged), recoverable `policy_denied` / `admin_failed` / head-divergence `error` via rebase, and stalls on other merge failures. Python treats `version_already_published`, `policy_denied`, and `admin_failed` like non-error outcomes: `pr_closed` stays false, `run_postmerge_phase` still runs, and the driver can return exit **0** even though the PR was never merged. **Suggested fix:** Mirror the bash `merge_result` case matrix before post-merge (re-enter the CI loop with `rebase.rebase_and_push` / PR-state probe for `version_already_published`; map hard failures to `Outcome.STALLED` with `STALL_TRACKING` semantics; only call `run_postmerge_phase` when `merge_result` is in `POST_MERGE_MERGE_RESULTS` or PR ground truth is merged).

- **correctness** `python/ship.py:220-221` — `run_logs.write_final_report_comment` raises `ShipError` on failure, and `run_ship` converts that to exit **4** (`STALLED`). Bash explicitly treats the post-create `--comment-only` `write-final-report.sh` pass as best-effort after the PR exists (`record_failure` only; no stall). A comment refresh failure after a successful `ensure_pr` can incorrectly send `/implement` to Step 18 stall instead of continuing. **Suggested fix:** Catch failures around `write_final_report_comment`, log them (execution-issues / journal), and continue with `Outcome.OK` when the PR was already created—matching bash.

- **correctness** `python/ship.py:112-138` — `_oos_gate` calls `oos.disposition_ok` with accepted and filed-url files only. Bash `run_oos_disposition_gate_if_required_before_oos_pending_false` also passes `--commit-range` (for inline-triage commit messages) and `--oos-issues-ndjson` (for rejected markers in the run-log batch). Without those inputs, disposition that is already satisfied via inline triage or NDJSON rejection can still surface `needs_user_reason="oos-filing"` and spurious exit **3** handbacks. **Suggested fix:** Compute the same commit range as bash (`merge-base..HEAD` / `origin/main..HEAD`), pass `oos_issues_ndjson` from the run-log tree, and pass `commit_range_messages` into `disposition_ok`.

- **correctness** `python/ship.py:150-170` — `run_postmerge_phase` returns `Outcome.STALLED` when `flush_logs_post` skips (e.g. redaction failure) and returns **before** `write_finalize_state`. Bash records post-merge manifest/report failures as warnings and still exits **0** after writing `finalize-state.sh` at the start of post-merge. A successful merge can therefore leave no `finalize-state.sh`, breaking Step 18 `implement-finalize.sh teardown`, while the orchestrator sees a stall. **Suggested fix:** Write `finalize-state.sh` before post-merge flush (bash order), treat non-fatal flush/report failures like bash (warn + continue), and reserve `STALLED` for true unrecoverable post-merge errors.

- **correctness** `python/ship.py:150-170` — The Python post-merge path never writes `$IMPLEMENT_TMPDIR/post-merge-sentinel`, which bash creates via `write_post_merge_sentinel` before post-merge work. `scripts/larch-log.sh` uses that sentinel as the mechanical NEVER #19 guard against post-merge commits. Python relies only on `merge_result` in `RunContext` for `_pre_push_probe` skips, so any helper that commits without that field set is less protected than on the bash path. **Suggested fix:** Write the same sentinel file (with `MERGE_RESULT=`) immediately before `run_postmerge_phase` when entering a merged/post-merge path, aligned with `scripts/ship-pr.sh` `write_post_merge_sentinel`.

### Out-of-Scope Observations

- **correctness** `python/config.py:353-354` — `EXIT_BAIL=4` and `EXIT_STALL=6` remain alongside the new bash-compatible `OUTCOME_EXIT_MAP` (`NEEDS_USER_INPUT=3`, `STALLED=4`, `TRANSIENT=6`). `ship.py` routes through the map, but duplicate legacy constants invite future mis-wiring; this naming collision predates the Phase 7 map and is not introduced by the driver logic itself.
