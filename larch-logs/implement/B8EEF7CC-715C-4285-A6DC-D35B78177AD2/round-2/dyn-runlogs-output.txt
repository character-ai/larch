Reviewing `run_logs.py` and callers for state-file-less pre-push and post-merge correctness.
### In-Scope Findings

- **correctness** `python/run_logs.py:486-495`, `python/ship.py:150-162`, `skills/implement/scripts/write-final-report.sh:72-92` — `flush_logs_post()` always calls `_write_final_report()`, which shells out to `write-final-report.sh`. That script derives `MERGE_RESULT`, `PR_NUMBER`, and `PR_URL` from `$IMPLEMENT_TMPDIR/ship-pr-state.sh`, not from `RunContext` or `finalize-state.sh`. The Python driver never updates `ship-pr-state.sh` (it only writes `finalize-state.sh`, and only **after** `flush_logs_post()` in `run_postmerge_phase()`). On a typical `/implement` run the orchestrator still seeds `ship-pr-state.sh` with empty `MERGE_RESULT` / `PR_NUMBER` before Step 8+, so the post-merge refresh writes `manifest.json` with `status=done` (via `merge_result=` on `RunContext`) but `summary-final.md` is rendered with `OUTCOME=bailed` and placeholder PR fields. That breaks the fail-closed manifest-before-report contract in substance even though call order inside `flush_logs_post()` is correct. **Suggested fix:** Before any `_write_final_report()` / `--comment-only` invocation, sync `ship-pr-state.sh` from `RunContext` (at minimum `MERGE_RESULT`, `PR_NUMBER`, `PR_URL`, `PR_CLOSED`, `PR_TITLE`), or extend `write-final-report.sh` / `finalize-state.sh` so the Python path can supply those fields without relying on a bash-only state file; call that sync **before** `run_postmerge_phase()`’s `flush_logs_post()`, and again after `ensure_pr()` for the comment-only refresh.

- **correctness** `python/ship.py:208-220`, `python/run_logs.py:516-556` — Pre-PR `flush_logs_pre(..., ctx.with_(state_file=None), cwd=repo_root)` correctly implements the state-file-less probe (#3339), but `finalize.postbump()` at `python/finalize.py:62` runs an earlier `flush_logs_pre(runner, ctx, cwd=cwd)` without clearing `state_file`. If `SHIP_PR_STATE_FILE` (or a future wiring of `--state-file`) points at a stale file with `MERGE_RESULT` in `POST_MERGE_MERGE_RESULTS`, the postbump refresh is skipped while the later pre-PR call still runs; worse, the CI `goto_rebase` path at `python/ship.py:255` calls `flush_logs_pre(runner, working, ...)` without `state_file=None`, so a stale state file can skip the pre-rebase log commit while `ship.py` treats the skip as benign via `REFRESH_SKIP_MERGE_OK`. **Suggested fix:** Use a single helper (e.g. `_ship_log_ctx(ctx) -> ctx.with_(state_file=None)`) for every live-path `flush_logs_pre` / `flush_logs_post` caller in `ship.py` and `finalize.postbump`, and only honor `state_file` in unit tests or explicit bash-parity entrypoints.

- **correctness** `python/ship.py:150-162`, `scripts/ship-pr.sh:3056-3125` — Bash `run_postmerge_phase()` runs explicit manifest recovery (`larch-log.sh init` + `status=partial` + `recovery_reason=manifest_lost_mid_run` when `manifest.json` is missing) before `status=done` and only then calls `write-final-report.sh` if manifest update succeeded. Python only calls `load_or_recover_manifest()` then `flush_logs_post()`; recovery is weaker and still proceeds to `_write_final_report()` even when manifest initialization is best-effort. **Suggested fix:** Port the bash recovery branch into `run_postmerge_phase()` (init partial manifest when the run dir exists but `manifest.json` does not), fail closed on recovery failure before `_write_final_report()`, and add a `test_run_logs.py` / `test_ship.py` case for missing-manifest post-merge.

### Out-of-Scope Observations

- `python/test_run_logs.py` mocks `_write_final_report` in several `flush_logs_pre` tests and does not assert manifest-`status=done` is written before `_write_final_report` in `flush_logs_post()` (called out in the Phase 7 acceptance criteria). Worth adding an ordering test with call-order spies.

- `config.REFRESH_SKIP_MERGE_OK` includes `commit-failed`, so `ship.py` continues to PR create / rebase when `flush_logs_pre` cannot commit log batches — this mirrors bash `refresh-run-logs.sh` / `|| true` behavior but leaves runs without committed larch-logs on the branch (pre-existing policy, amplified by the new driver).
