Reviewing the branch diff and comparing the Python ship path against bash parity contracts.
### In-Scope Findings

- **risk-integration** `python/finalize.py:48-80` — Postbump is supposed to mirror the trimmed `implement-finalize.sh postbump` contract (`run_step8b_rebase` + `run_force_push_gate` via `rebase-push.sh --no-push`, conflict → stall, no agent resolution), but the Python path calls `rebase.rebase_and_push()` instead, which auto-invokes conflict fixers on unmerged paths (`python/rebase.py:335-343`) and collapses rebase + force-push into one helper. That is a live behavioral drift from bash Step 8b: runs can silently attempt automated conflict resolution and continue where bash would `exit_stall 8b`. **Suggested fix:** Port the post-#3368 Step 8b surface explicitly (no-push rebase, separate force-push gate, conflict → `Outcome.STALLED` without agent launch), and extend `python/test_finalize_bash_parity.py` to assert the same status tokens bash emits for rebase/push failures.

- **risk-integration** `python/ship.py:191-210,284-291` and `skills/implement/SKILL.md:955,1272-1287` — On most `Outcome.STALLED` exits (checks/postbump/pre-push flush/CI monitor), `ship.py` returns exit **4** without writing `finalize-state.sh` with `STALL_TRACKING=true`/`STALL_STEP`, yet Step 18 still runs `restore-finalize-state.sh` → `implement-finalize.sh teardown`, which rebuilds from `ship-pr-state.sh` (absent on the Python path) and reads stall flags from `finalize-state.sh`. Bash always persists stall metadata in `ship-pr-state.sh` before exit **4**; Python-path stalls therefore lose Branch A parity (no `[STALLED]` rename, no stash/sentinel, tmpdir cleanup proceeds). **Suggested fix:** On every terminal non-OK outcome, write `finalize-state.sh` via `finalize.write_finalize_state()` with `stall_tracking=True`, a meaningful `stall_step`, and populated `EXPECTED_SESSION_ID` / `EXPECTED_TMPDIR_BASENAME_PREFIX`; update the SKILL Python branch to require those env exports and document that Step 18 must not depend on `ship-pr-state.sh` when `LARCH_SHIP_PR_IMPL=python`.

- **risk-integration** `skills/implement/scripts/oos-disposition-checkpoint.sh:106-170` and `skills/implement/SKILL.md:955,1042` — The Python selector says not to read `ship-pr-state.sh` for routing, but the OOS disposition checkpoint still derives `FORKED_TARGET` / `REPO_UNAVAILABLE` only from that file. After a Python-path `needs_user_reason=oos-filing` handback, Step 9a.1 can run without `--fork-mode` / `--repo-unavailable` gate flags even when the run is forked or repo-unavailable, causing false validation failures or incorrect gate strictness versus bash. **Suggested fix:** Teach `oos-disposition-checkpoint.sh` to fall back to `finalize-state.sh`, exported env, or explicit orchestrator flags when `ship-pr-state.sh` is missing; document the Python-path OOS re-entry contract in `skills/implement/SKILL.md`.

- **risk-integration** `skills/implement/SKILL.md:955,1039-1040` and `python/ship.py:382-392` — The Python branch promises bash-compatible Exit **6** retry semantics (“same per-phase retry counter shape”), but `ship.py` emits no `PHASE` and the selector omits `--no-logs-commit`, `--expected-session-id`, and `--expected-tmpdir-basename-prefix` even though bash passes them and `RunContext.from_env()`/`finalize.write_finalize_state()` depend on those values for log commits and teardown guards. Orchestrators following the SKILL literally can neither key transient retries correctly nor populate finalize-state reliably. **Suggested fix:** Expand the documented Python invocation to include all bash-parity flags/env (`--no-logs-commit`, expected session/tmpdir prefix exports, `IMPLEMENT_TMPDIR`), define a fixed retry bucket for Python (e.g. `ship-pr-net-retries-python.count`), and add an integration test that asserts env/argv round-trip into `RunContext`.

- **risk-integration** `python/ship.py:106-110,212-213` and `scripts/ship-pr.sh:1233-1239` — PR title derivation diverges: bash prefixes `Fixes #<issue>:` (filtering larch-log flush commits) before `create-pr.sh`, while Python `_pr_title()` uses raw `git.log_subject(HEAD)` or a generic fallback with no issue prefix. That changes PR titles, tracking-issue rename inputs, and postmerge main-title verification expectations. **Suggested fix:** Port the bash title rule into `_pr_title()` (merge-base scoped subject, flush-commit filter, `Fixes #N:` prefix) and cover it in `python/test_ship.py`.

- **risk-integration** `python/ship.py:181-186` — The driver hardcodes `codex_present=True` and `cursor_present=True` for `checks.run_checks_phase()`, ignoring Step 0 session-env probe results that bash ship-pr respects. In degraded-tool sessions, Python can attempt external lint-fix tiers bash would skip, changing checks outcomes and stall/handback behavior. **Suggested fix:** Read `CODEX_PRESENT` / `CURSOR_PRESENT` from `session-env.sh` (or CLI/env mirrors) before calling `run_checks_phase()`, matching bash probe propagation.

- **risk-integration** `python/test_finalize_bash_parity.py:1-78` — Acceptance called for bash-parity coverage of postbump/postmerge/teardown against post-#3368 `implement-finalize.sh`, but the added harness only parametrizes three postmerge skip branches and a mocked postbump call-order smoke test. The highest-risk postbump drift (`rebase_and_push` vs Step 8b) and teardown Branch A stalled behavior have no automated parity guard, so regressions against the live bash contract will not be caught in CI. **Suggested fix:** Expand the parity module (or wire `scripts/test-implement-finalize.sh` cases) to compare postbump status tokens, push-gate outcomes, and teardown stall/cleanup decisions against bash fixtures.
