Reviewing the branch diff and commit history, then tracing the /design control-flow changes.
### In-Scope Findings

- **architecture** `skills/design/references/approval-gates.md:109` — The Step 3 outcomes bullet still says that on `LOOP_STATUS=complete` or `zero-findings-degraded-panel`, “Gate B uses the full explicit prompt below” and that revision happens only after the operator picks Apply all / Go through each. That contradicts the new default branch (`approve_requested=false` auto-applies with no prompt) documented eight lines above and in `SKILL.md` Step 3.5. Because `approval-gates.md` is the normative Gate B source, an orchestrator that follows this stale bullet will re-prompt every round and undo the core #3628 behavior. **Suggested fix:** Reword line 109 to branch on `approve_requested` (auto-apply vs explicit prompt), and add a `test-design-structure.sh` pin so the stale “full explicit prompt below” wording cannot return.

- **architecture** `skills/design/SKILL.md:1340-1361`, `skills/design/scripts/snapshot-plan-round.sh:112-138`, `skills/design/references/approval-gates.md:200-206` — The new Revert path restores `plan.txt` and rolls back cursor/count, but leaves round-scoped review artifacts intact (`accepted-plan-findings.md`, `rejected-findings.md`, `voting-tally.md`, `assessor-verdict-round-<N>.txt` / `.env`). After Revert → Step 3b → Step 4 → Gate C, the operator can approve a plan that no longer contains voter-accepted edits while artifacts still record those findings as accepted/applied and the assessor still records a WORSE verdict for that round. That breaks the documented invariant that `plan.txt` reflects the latest Gate B apply outcome and makes run logs misleading if the operator approves without a Gate C re-run. **Suggested fix:** On successful `revert-round`, also reconcile or clear round-<N> review/assessor artifacts (or move accepted findings to rejected with a “reverted by operator” marker), and extend `test-snapshot-plan-round.sh` / assessor harness with an end-to-end Revert → Gate C artifact-consistency case.

- **architecture** `skills/design/scripts/auto-fix-plan-commands.sh:73,116-118`, `skills/design/SKILL.md:1962-1971`, `skills/design/scripts/design-postplan-emit.sh:538` — Auto-fix re-validation passes an explicit `--repo-root` derived from the plan file’s directory (session tmpdir outside the consumer clone), while the initial failure path goes through `invoke-plan-validator.sh` → `validate-plan.sh`, which defaults `REPO_ROOT` to the plugin tree. The two validation passes can therefore disagree on Tier 3 path resolution and dry-run context, so auto-fix may report `AUTOFIX_STATUS=ok` while the surrounding `design-postplan-emit.sh` fence still sees `defects-found` (or the reverse). **Suggested fix:** Thread the consumer repo root into the shared handler (same source other design scripts use) and pass `--repo-root` consistently; add a harness case where `plan.txt` lives under `$DESIGN_TMPDIR` but commands reference consumer-repo paths.

- **architecture** `skills/design/scripts/auto-fix-plan-commands.sh:145-179`, `skills/design/scripts/auto-fix-plan-commands.md:38-38` — Codex is launched with `--workdir "$DESIGN_TMPDIR"` and Cursor with `--workspace "$DESIGN_TMPDIR"`, so auto-fix agents operate only inside the session tmpdir, not the consumer working tree. Plans whose fenced commands reference repo scripts, Makefile targets, or paths outside the tmpdir may be unfixable by vendors even when defects are syntactic, causing premature escalation to the operator prompt. **Suggested fix:** Launch vendors with the consumer repo as workdir/workspace (keeping `$DESIGN_TMPDIR` as an add-dir/read target for the plan file), or copy the plan into the repo for the fix pass; document the trust boundary in `auto-fix-plan-commands.md`.
