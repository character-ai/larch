### Out-of-Scope Observations

I traced the three contracts the scout called out against the branch implementation; none rise to an in-scope architecture defect.

**Tally-error metadata clearing** — The invariant is wired consistently. In `plan-review-loop.sh`, `_snapshot_terminal_exit_preserving_status` runs `_clear_design_round_meta` on `*:tally-error` and defers on `main-agent-vote-required:*`; it never calls `write-design-round-meta.sh` on those paths. Fatal tally-error is always paired (`TALLY_PLAN_REVIEW_FATAL=true` whenever `TALLY_PLAN_REVIEW_STATUS=tally-error`), and the terminal block at lines 1782–1793 sets `LOOP_STATUS=tally-error` before snapshotting. In `persist-retally-step3-env.sh`, `_clear_design_round_meta_on_tally_error` runs after rollback helpers and before env rewrite; `_refresh_design_round_meta_after_ok_retally` is gated on `TALLY_PLAN_REVIEW_STATUS=ok` only. `write-design-round-meta.sh` is only reachable from the non–tally-error branches of those two callers. Harness coverage in `test-plan-review-loop.sh` and `test-persist-retally-step3-env.sh` matches this contract (including stale-meta removal and MAV deferral).

**`render-final-summary.sh` guard structure** — The implementation matches the plan pseudocode. The `if [ -d "$DESIGN_TMPDIR/plan-review" ]` block closes at line 456; the `-s "$_rpd_out"` append at lines 457–462 sits outside that guard, so a pre-existing non-empty `review-phase-detail.md` could still be honored if `plan-review/` were absent. In practice `_rpd_out` is removed at line 428 first, so the append path is effectively gated on a successful compose/render pass.

**Both-externals-absent dispatch** — `_append_manifest_row` at line 217 is unconditional (even when `_generic_has_output` is false), matching the stated intent that degraded rounds still report `total_slot_count ≥ 1`. With `set -e`, a manifest-append failure (no `jq` and no `python3`) aborts dispatch rather than silently emitting a zero-slot manifest.

**Round resolution on MAV retally** — `persist-retally-step3-env.sh` reads `.step3-plan-review-result.env` only; `write_step3_result_env` persists `ROUNDS_COMPLETED` (the artifact round number passed to `_terminal_exit`), not `ROUND_NUM`. That is sufficient in production because snapshot dirs and `ROUNDS_COMPLETED` both use the same `--round-num` value from `run-step3-review.sh`. The `ROUND_NUM` preference path is exercised only when tests seed both keys manually.
