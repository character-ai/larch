### In-Scope Findings

1. **security** `skills/design/scripts/design-postplan-emit.sh:158-163` — `_postplan_resolve_issue()` sources `$DESIGN_TMPDIR/source-env.sh` unconditionally before falling through to the awk extraction. Sourcing executes arbitrary shell code: any process with write access to `~/.cache/larch/sessions/<session>/` can plant content in `source-env.sh` that runs inside the driver on the very next plan emit, re-emit, or pause checkpoint. This is new code introduced by this diff (the function is entirely new); the pre-existing SKILL.md orchestrator fences also source session files, but this driver runs on every plan-emit path in a single subshell that already has `ISSUE_NUMBER` set via its prelude in most callers. **Suggested fix:** Try `${ISSUE_NUMBER:-}` from the environment first (line 157), then go directly to the awk extraction at lines 163–165 — which safely matches only `^export[[:space:]]+ISSUE_NUMBER=` lines without executing the file. Skip the `source` branch entirely; the awk path already covers the export-format contract required by harness case #11.

2. **security** `skills/design/scripts/design-postplan-emit.sh:43-53` — `json_scalar_or_sed` embeds `$key` directly in a sed substitution expression via shell string concatenation (`'s/.*"'"$key"'"…/\1/p'`). A `$key` value containing `/`, `\`, or `&` would break the sed expression or inject into the replacement. Current callers pass only hardcoded alphanumeric strings (`review_budget`, `workflow_path`), so this is not immediately exploitable, but the function signature accepts any string and provides no escaping. **Suggested fix:** Validate the key is alphanumeric with underscores before interpolating, or prefer jq-only parsing and omit the sed fallback for this controlled use case.
