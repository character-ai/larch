### In-Scope Findings

- **architecture** `skills/design/scripts/design-postplan-emit.sh:179,194,210` — The three `_postplan_pause_checkpoint()` calls are invoked from inside the `$()` command substitution that captures `_postplan_out` in every orchestrator fence (e.g., `SKILL.md` Step 2b: `_postplan_out=$("${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/design-postplan-emit.sh" ...)`). An `exec` inside a `$()` subprocess replaces only that subprocess, not the orchestrator shell. If `.pause-requested` is created after the orchestrator prelude fires (which runs once, before `$()`is entered) but while the driver is executing — for example between the EMIT_PLAN call and the snapshot step, or between snapshot and validator — the driver's checkpoint calls `exec design-pause-save.sh` inside the subprocess. That subprocess exits with whatever code pause-save emits (typically 0), the orchestrator's `_postplan_rc` captures that code, and the orchestrator's mandatory-key check (`[[ -z "${POSTPLAN_EMIT_STATUS:-}" || -z "${VALIDATE_STATUS:-}" ]]`) fires because no result env was written and no KV was emitted to stdout, producing a confusing "result env missing/unreadable" abort rather than a clean pause state. The original three-fence design placed the pause check as an `exec` in the orchestrator's own shell context for each fence, so it would actually replace the orchestrator process. Consolidating into a single driver call inside `$()` reduces the three genuine inter-step pause opportunities to one (the prelude before `$()`). Mid-driver pauses now produce error aborts, not clean session saves. This contradicts the plan's invariant claim "This restores the three inter-step pause opportunities that today sit between the three inline fences." **Suggested fix:** Remove the driver-internal `_postplan_pause_checkpoint` calls (or document them as best-effort only). To restore the three-checkpoint semantic, the orchestrator fence should run the driver as a foreground invocation in a subshell (not `$()`) and insert pause checks via a wrapper that can trap the driver's exit and re-check `.pause-requested` after the driver exits; alternatively, the driver could write a `PAUSE_REQUESTED=true` KV to the result env file when it detects the flag, and each orchestrator fence could check for `POSTPLAN_EMIT_STATUS=paused` and exec pause-save in the main shell before continuing. The simpler mitigation is to add a second orchestrator-level prelude check immediately after the `set +e` / `$()` block in SKILL.md Step 2b (and the re-emit reference sites) so that a pause created during driver execution is caught in the orchestrator shell on the next fence boundary.
