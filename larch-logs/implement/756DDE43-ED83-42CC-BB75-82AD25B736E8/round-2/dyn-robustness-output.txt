Reviewing the flagged failure-recovery paths in the new Python primitives.
### In-Scope Findings

- **risk-integration** `python/ci_cli.py:119-177` — The new `wait_main` does not implement the bash `ci-wait.sh` EXIT-trap contract for `--output-file` mode. `scripts/ci-wait.sh` installs a trap that, on trap-deliverable termination (notably SIGTERM from harness cleanup), atomically publishes the current KV payload and writes `<path>.done` with the captured exit status; `scripts/ci-wait.md` and `scripts/test-ci-wait-exit-trap.sh` Sub-test A depend on that behavior. The Python port only publishes at normal return from `poll_ci`, so a mid-poll SIGTERM leaves no output and no `.done` sentinel even though stale files were cleared at entry (lines 137–145). That is a fail-closed stall for `.done`-polling consumers and a direct gap against plan acceptance item F4 (“trap-deliverable exits”). **Suggested fix:** Port the trap semantics into `wait_main` (e.g., `atexit` plus a SIGTERM handler) that mirrors the bash defaults (`ACTION=bail`, etc.), calls `_publish_wait_output`, and gates `.done` on publish success; add a pytest analogue of `test-ci-wait-exit-trap.sh` Sub-test A against `python3 cli.py ci wait`.

- **correctness** `python/ci_cli.py:168-176` — On `--output-file` publish or `.done` write failure after a valid `poll_ci` result, `wait_main` returns exit code `1`. In `scripts/ci-wait.sh`, exit `1` is reserved for usage/argument errors; when `emit_output` fails or the `.done` write fails, the script still exits with the captured poll outcome (always `0` on the normal decision path) and simply omits `.done`, per the fail-closed gate documented at `scripts/ci-wait.sh:164-173` and `scripts/ci-wait.md:45-49`. Returning `1` misclassifies an I/O failure as a usage error and can cause upstream callers that branch on process exit code to take the wrong recovery path, even though `.done`-based consumers correctly stall. **Suggested fix:** After a successful poll, return `0` on publish/done-write failure (matching bash), rely on absent `.done` for fail-closed consumer behavior, and optionally unlink any partial `.tmp` in `_publish_wait_output`’s `except` block; add tests for both failure paths.

### Out-of-Scope Observations

- **`git_cli.py` `commit_main` double-staging:** Not a defect. The flow mirrors `scripts/git-commit.sh`: `git add` stages paths, then `git.commit_with_trailer()` passes the same pathspec to `git commit` for scoping/`--only` parity — it does not call `git add` again inside `commit_with_trailer` (`python/git.py:257-307`).

- **`phantom.py` `runner.run(..., env=...)`:** Correct. The `Runner` protocol in `python/proc.py:23-35` declares an `env` keyword; `RecordingRunner` in `python/test_support.py:29-38` accepts it the same way.

- **`snapshot_untracked` atomicity:** No meaningful `.tmp` leak on the success path — `Path.replace` removes the temp file after a successful rename (`python/git.py:865-870`). The `except OSError` branch deletes both `output` and `.tmp` on failure, matching `scripts/snapshot-untracked.sh:62-63`.

- **`_write_failure_log` chmod TOCTOU:** Not a meaningful regression in this branch. The diff shows newly added redaction before `write_text`, and `tempfile.mkstemp` already creates the file mode `0600`; the post-write `chmod(0o600)` is belt-and-suspenders, not exposure of unredacted content (`python/ci_monitor.py:813-819`).
