### In-Scope Findings
- **code-quality** `python/ci_cli.py:135-178` — `wait_main` removes stale output/sentinel files and then calls `ci_monitor.poll_ci`, but it only publishes the output file and `.done` sentinel after a normal return. Any unexpected exception after validation—such as `FileNotFoundError` from a missing `git`/`gh`, an `OSError` during stale cleanup, or an uncaught bug in polling—leaves file-mode consumers with no fresh `<output-file>.done` after the stale sentinel was deleted. That regresses the old `ci-wait.sh` trap-style failure-recovery contract. **Suggested fix:** Initialize default bail `CiStatus`/`Decision` values after argument validation, wrap cleanup/polling/output construction in `try`/`except`, and publish a bail payload in a `finally`/single exit path for file mode, writing `.done` only after successful atomic output publish.

- **code-quality** `python/git.py:847-870` — `snapshot_untracked` is documented to always return 0 and remove both the output and temp files on operation failure, but its cleanup path can itself raise. If `write_text`/`replace` fails, or if the git failure branch tries to unlink an unremovable output/temp file, the `except OSError` handler calls `output_path.unlink()` / `tmp_path.unlink()` without suppressing secondary `OSError`s, so the CLI can crash and stale files can remain. **Suggested fix:** Make cleanup best-effort and non-throwing, e.g. use `contextlib.suppress(OSError)` around each unlink in both failure paths, and keep returning 0 after cleanup attempts.
