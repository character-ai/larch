### In-Scope Findings
- **correctness** `python/ci_cli.py:39-57` — `ci status` accepts invalid `--base-remote`/`--base-ref` and negative `--empty-checks-grace` values instead of treating them as argv errors. The shell contract emitted the four KVs with `CI_STATUS=error` for these validation failures; the Python path can now report `pending` after a fetch failure and continue the CI loop. `ci wait` has the same missing validation around `python/ci_cli.py:146-160` and should reject invalid counters/base labels with usage exit 1 before polling. **Suggested fix:** Add explicit non-negative/base-ref validation after argparse; for `status_main`, emit `_status_error_kv()` and return 0 on validation failure; for `wait_main`, return 1 before clearing/publishing output files.

- **correctness** `python/ci_monitor.py:656` — `ci rerun-failed` casts `run_id` to `int` before invoking `gh`, so a non-numeric but otherwise present `--run-id` raises `ValueError` and emits no `RERUN_SUBMITTED`/`ALREADY_RUNNING`/`ERROR` KVs. The bash script passed the value to `gh` and always emitted those KVs after argument parsing. The same traceback-shaped regression exists for `ci failed-jobs` at `python/ci_monitor.py:600`. **Suggested fix:** Keep run IDs as strings through the gh wrapper, or catch `ValueError` and return the same structured failure result the gh error path would produce.

- **correctness** `python/git_cli.py:344-348` — `git phantom-probe` now always emits `PHANTOM_COUNT=0` and `PHANTOM_PATHS_FILE=` for clean/tracked-only/unknown results, while `scripts/lib-phantom-probe.sh` only emitted those optional keys when `check-phantom-dirty` produced a phantom artifact. `push checkpoint-probe` repeats the drift at `python/push_cli.py:161-166`. This violates the optional-key contract consumed by token scanners. **Suggested fix:** Only emit `PHANTOM_COUNT`/`PHANTOM_PATHS_FILE` when the dirty result actually contains a phantom paths artifact, matching `check_phantom_dirty`/old shell output.

- **correctness** `python/pr_cli.py:123-129` — `pr body-update` returns exit 2 for argparse failures and invalid `--repo`, but `gh-pr-body-update.sh` used exit 1 for usage/argument errors and reserved exit 2 for an attempted update failure with structured `UPDATED`/`ERROR` output. This can make caller error routing classify bad input as a gh update failure. **Suggested fix:** Return 1 for parse errors and repo validation failures, with no KVs; keep exit 2 only for missing body files or `gh pr edit` failures that emit `UPDATED=false`/`ERROR=...`.
