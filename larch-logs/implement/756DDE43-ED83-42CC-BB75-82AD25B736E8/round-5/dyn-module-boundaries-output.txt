Reviewing the branch diff and key Python modules for CLI/library boundary violations.
### In-Scope Findings

- **architecture** `python/ci_cli.py:146-256` — The full `ci-wait.sh` wrapper (default trap state, SIGTERM/SIGINT/SIGHUP handlers, atomic `--output-file` publish, `.done` sentinel, and `_wait_output_lines` formatting) lives in `ci_cli.wait_main` instead of `ci_monitor.py`, even though the plan assigns F4 to the library (“full ci-wait wrapper for `ci_cli`”; `poll_ci` is only the inner loop). That breaks the stated thin-CLI invariant: non-trivial orchestration and I/O semantics sit in the CLI layer, so a future Python ship driver or other internal caller would have to duplicate this logic or shell out to `cli.py`. **Suggested fix:** Add something like `ci_monitor.wait_ci(...)` (or `run_ci_wait`) in `python/ci_monitor.py` that owns trap handling, output-file atomic publish, line ordering, and elapsed timing; keep `ci_cli.wait_main` as argparse → library call → exit-code relay only.

- **architecture** `python/ci_cli.py:259-312` and `python/ci_monitor.py:38,548-589` — `_JOB_NAME_RE` is defined identically in both modules, and `failed_jobs_main` re-derives `malformed` plus `history-scan` / `malformed-job-name` reason tokens after `classify_failed_jobs`, duplicating `scripts/ci-failed-jobs.sh:43-49` logic that is already semantically tied to classification in `ci_monitor`. `JobClass` exposes only `name`/`shard`/`klass`, so the CLI cannot format `FAILED_JOBS_UNFIXABLE` without a second regex pass, creating a three-way drift surface (retained bash for E1, library classifier, CLI formatter). **Suggested fix:** Centralize job-name validation and reason-token mapping in `ci_monitor` (e.g., extend `JobClass` with `malformed`/`reason_token`, or add `format_failed_jobs_output(classified) -> (tsv_lines, fixable_kv, unfixable_kv)`), delete `_JOB_NAME_RE` and `_failed_job_reason_token` from `ci_cli.py`, and have `failed_jobs_main` only parse argv and emit the library result.

- **architecture** `python/push_cli.py:34-68` — `_emit_rebase_checkpoint_keys` and `_conflict_files_csv` implement the `rebase-checkpoint-probe` contract (exit-code → `REBASE_OUTCOME`, conflict-file fallback via `git.try_conflict_files`) inside the CLI module rather than `rebase.py`, while `rebase_main` separately emits a overlapping subset of KVs (`SKIPPED_ALREADY_*`, `CONFLICT_FILES`, `REBASE_ERROR`) without sharing a library helper. That splits one primitive’s presentation contract across two CLI functions and leaves conflict enumeration in the wrapper layer. **Suggested fix:** Move checkpoint KV mapping and conflict CSV fallback into `rebase.py` (e.g., `format_checkpoint_probe_result(result) -> tuple[list[str], int]`), call it from both `checkpoint_probe_main` and any internal Python consumers, and keep `push_cli` limited to argparse plus `emit_kv` of library-produced lines.

### Out-of-Scope Observations

- Python internals honor the “no `cli.py` subprocess” rule on the rewired paths: `python/checks.py` calls `git.commit_with_trailer` directly, and `python/ci_monitor.py` / `python/finalize.py` call `git.commit_with_trailer`, `rebase.rebase_push`, and `git.remote_branch_state` instead of absorbed `.sh` helpers.
- `_wait_output_lines` key order matches the documented `ci-wait.sh` stdout contract and `python/test_ci_cli.py:119-149`; no ordering mismatch with `poll_ci` return values was found.
- `python/git_cli.py`, `python/gh_cli.py`, and `python/merge_cli.py` are largely thin argparse/KV wrappers as intended; `python/pr_cli.py` orchestration (repo resolve, body-file read) is CLI-glue-level rather than core business logic.
- `python/test_ci_monitor.py` still constructs paths like `SCRIPTS_DIR / "git-commit.sh"` for subprocess-mocking fixtures; that is test harness residue, not a live runtime boundary violation.
