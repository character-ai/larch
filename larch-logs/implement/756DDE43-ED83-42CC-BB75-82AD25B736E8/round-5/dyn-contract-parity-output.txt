### In-Scope Findings

- **correctness** `python/ci_cli.py:39-62,146-256` — `status_main` and `wait_main` never validate `--base-remote` / `--base-ref` the way retired `scripts/ci-status.sh` and `scripts/ci-wait.sh` did (`CI_STATUS=error` + exit 0 / exit 1). Invalid labels are passed straight into `gather_status`, which fail-opens on fetch/probe errors (`CI_STATUS=pending`, exit 0) instead of surfacing an argv/label error. That diverges from the bash contract and from `ci_monitor.behind_count`, which already calls `git.validate_base_remote_ref` and fail-opens only for that verb’s semantics. **Suggested fix:** Reject unsupported `--base-remote`/`--base-ref` in both entrypoints before calling `gather_status` — `status_main` should emit the four error KVs (`CI_STATUS=error`, etc.) and return 0; `wait_main` should return 1 without publishing `--output-file` output, matching the bash pre-trap validation paths.

- **correctness** `python/ci_cli.py:45-57,152-232` — Neither `status_main` nor `wait_main` enforces non-negative `--empty-checks-grace`, but `_resolve_checks_status` calls `sleep_fn(float(empty_checks_grace))` (`python/ci_monitor.py:357-372`). A negative value makes `time.sleep` raise `ValueError`, so the process exits without emitting the four guaranteed `ci status` KVs (and without the `ci wait` trap/output-file contract). Bash rejected non-integer/non-negative grace with `CI_STATUS=error`. **Suggested fix:** After argparse, reject `empty_checks_grace < 0` (and non-integer forms) in both CLIs with the same error surfaces as bash; add pytest cases for `--empty-checks-grace -1`.

- **correctness** `python/ci_cli.py:146-160` — `wait_main` does not replicate `ci-wait.sh`’s numeric validation for `--iteration`, `--rebase-count`, `--fix-attempts`, `--timeout`, or `--empty-checks-grace` (bash required `^[0-9]+$` and exited 1). Argparse `type=int` accepts negatives, so callers can pass e.g. `--iteration -1` and reach `decide()` with semantics unlike bash (no immediate usage failure; different interaction with iteration caps). **Suggested fix:** Mirror the bash numeric guard in `wait_main` before entering the poll loop; return exit 1 without writing `--output-file` / `.done`.

- **correctness** `python/ci_cli.py:249-256` — In non-`--output-file` mode, `wait_main` writes the eight-line contract via `sys.stdout.write`, while every other CI verb (including `status_main`) uses `logging_util.emit_kv` → `contract_stream()`. Retired `ci-wait.sh` used `emit_kv` (fd 3 after `larch_quiet_init`). If `cli.py` later adopts the `migration_lint.py` pattern of calling `quiet_init`, `status_main` KVs would route to fd 3 but `wait_main` KVs would still land on fd 1 (the quiet log), breaking orchestrator parsing. **Suggested fix:** Build the wait contract through `emit_kv`/`logging_util.emit` (one key per line, same ordering as today) instead of raw `sys.stdout.write`; add a quiet-routing parity test alongside `test_wait_bail_exits_zero_and_emits_contract`.

- **correctness** `python/git_cli.py:344-348` — `phantom_probe_main` always emits `PHANTOM_COUNT` and `PHANTOM_PATHS_FILE`, even when status is `clean` and `paths_file` is empty. Retired `scripts/lib-phantom-probe.sh` only emitted those keys when non-empty (`if [ -n "$ph_count" ]` / `if [ -n "$ph_paths" ]`), and `check_phantom_dirty_main`/`_emit_phantom_dirty_result` preserved that omission shape (`python/test_git_cli.py:67-68`). Extra empty keys can confuse KV parsers that treat key presence as signal. **Suggested fix:** Emit `PHANTOM_COUNT` / `PHANTOM_PATHS_FILE` only when count > 0 / `paths_file` is non-empty, matching bash and `push_cli.checkpoint_probe_main`’s conditional paths-file emission (`python/push_cli.py:165-166`).

### Out-of-Scope Observations

- `python/cli.py` does not call `logging_util.quiet_init()` on dispatch, unlike every retired bash helper and unlike `python/migration_lint.py:131`. That is a broader quiet-routing gap than the `wait_main`-specific issue above; worth addressing holistically if `/implement` subprocess callers inherit `LARCH_QUIET_*` env during B1 cutover.

- `CiStatus.pr_view_ok` is populated in `gather_status` (`python/ci_monitor.py:394-446`) but intentionally not exposed on the four-KV `ci status` surface; current tests confirm fail-open probe behavior (`python/test_ci_monitor.py:241-258,368-388`). No CLI contract bug there.

- `poll_ci`’s three-strike bail on empty/`error` status (`python/ci_monitor.py:495-511`) is effectively unreachable with in-process `gather_status` (which never returns `""` or `"error"` on probe failure); this is defensive residue from the subprocess `ci-status.sh` era, not a live regression given the fail-open refactor.
