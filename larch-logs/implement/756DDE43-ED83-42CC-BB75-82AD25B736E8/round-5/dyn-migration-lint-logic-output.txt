Reviewing `migration_lint.py` deletion-safety logic against the diff and call-site patterns.
### In-Scope Findings

- **correctness** `python/migration_lint.py:59-65` — `_line_references_retired` applies two different `$SCRIPT_DIR/<basename>` rules: non–`ship-pr.sh` files use a simple substring match whenever `Path(rel).parent == Path(retired_path).parent`, but `scripts/ship-pr.sh` is routed only through `_ship_pr_live_ref`, whose leading-token regex does not treat `=` as a boundary. A line like `launcher="$SCRIPT_DIR/git-commit.sh"` (already used for non-retired helpers at `scripts/ship-pr.sh:1620-1622`) would not block retirement, even though the same line in any other `scripts/*.sh` caller would. Deferred E1 helpers in `ship-pr.sh` are invoked in command position today, so this is latent, but it is a real asymmetry in the deletion gate. **Suggested fix:** Either add an assignment-shaped pattern to `_ship_pr_live_ref` (e.g. allow `(^|[\s;|&(=])` before the optional quote) or, for `rel == "scripts/ship-pr.sh"`, also run the same-parent `$SCRIPT_DIR/<basename>` substring check from `_script_dir_refs` before/alongside the regex filter; add pytest covering `launcher="$SCRIPT_DIR/<retired>.sh"` in a synthetic `scripts/ship-pr.sh`.

- **correctness** `python/migration_lint.py:49-50` — `_ship_pr_live_ref` pattern 2 flags any whitespace-delimited `scripts/<retired>.sh` substring in `ship-pr.sh`, not just invocation/source forms. That diverges from F18/docs intent (`docs/python-migration.md:72-75`) and from the negative tests, which only cover full-line `#` comments (`python/test_migration_lint.py:167-176`) and basename-only `record_failure` labels (`python/test_migration_lint.py:151-164`). A future non-comment string such as `larch_err "removed scripts/ci-wait.sh from tree"` would incorrectly block manifest retirement. **Suggested fix:** Remove bare full-path pattern 2 from `_ship_pr_live_ref`, or require invocation context (leading `"`, `(`, `source`/`.`, or `$SCRIPT_DIR/…`) before the manifest path; add a pytest with a ship-pr-shaped quoted-string prose line containing only `scripts/<retired>.sh`.

- **risk-integration** `python/test_migration_lint.py:127-176` — Ship-pr coverage exercises only negative cases (comment prose and `record_failure` basename labels). There is no positive test proving a live `"$SCRIPT_DIR/<retired>.sh"` invocation in `scripts/ship-pr.sh` is flagged, even though that is the main reason for the F18 carve-out and the regex work in `_ship_pr_live_ref`. A regression that stops matching live ship-pr invocations would let deferred-closure scripts be deleted while `LARCH_SHIP_PR_IMPL=bash` still calls them. **Suggested fix:** Add `test_ship_pr_live_script_dir_invocation_blocks_deletion` with a synthetic `scripts/ship-pr.sh` line like `repo=$("$SCRIPT_DIR/resolve-repo.sh" 2>/dev/null)` and assert exit code 1.

- The same-parent gate on `$SCRIPT_DIR/<basename>` (`python/migration_lint.py:64-65`, documented at `docs/python-migration.md:66-68`) is consistent with this repo: cross-directory callers use `$PLUGIN_ROOT/scripts/...` or `$SCRIPT_DIR/../../../scripts/...`, both caught by the full-path substring on line 62. I did not treat that as a defect.

- `python/migration_lint.py:3-5` and `python/migrated-scripts.tsv:6-8` still describe “full path only” matching; the branch updates `docs/python-migration.md` but not those two headers. Doc drift only.

- `_ship_pr_live_ref`’s `(?:/[^\"'\s;|&)]+)*` segment is bounded by line length and fixed manifest tokens; I did not find a practical ReDoS issue in normal repo scanning.
