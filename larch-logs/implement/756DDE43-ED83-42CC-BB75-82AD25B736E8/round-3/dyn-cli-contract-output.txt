### In-Scope Findings

- **architecture** `python/ci_cli.py:23-27` — The shared `_parse()` helper catches every `SystemExit` from argparse, including the successful `--help` path (`SystemExit(0)`), and maps it to the usage-exit code (`1` or `2`). Bash counterparts (`ci-behind-count.sh`, `ci-wait.sh`, `ci-status.sh`, `ci-decide.sh`) all exit **0** on `--help`. A caller such as `python3 cli.py ci behind-count --help` therefore exits **2** and emits no `BEHIND_COUNT` line, while `ci wait --help` exits **1** instead of **0**, and `ci status --help` exits **1** after emitting `CI_STATUS=error` rather than printing help. **Suggested fix:** In `_parse()`, distinguish `SystemExit.code` (re-raise or return `0` when `code in (0, None)` for help; return `usage_exit` only for non-zero codes), or disable argparse help and handle `-h`/`--help` explicitly to mirror each bash script.

- **architecture** `python/ci_cli.py:37-60,121-173` — `status_main` and `wait_main` forward `--base-remote` / `--base-ref` straight into `gather_status` / `poll_ci` without the label validation bash performs before any probe. In `ci-status.sh`, unsupported characters set `CI_STATUS=error` and exit **0**; in `ci-wait.sh`, the same condition exits **1** before the EXIT trap installs (no KV output). The Python path instead runs probes against invalid refs and can surface `CI_STATUS=pending` (fail-open) or start polling, silently diverging from the bash argv-error contract. **Suggested fix:** Call `git.validate_base_remote_ref()` at the top of both entrypoints; on failure emit the bash-shaped response (`CI_STATUS=error` + four KVs + exit **0** for `status_main`; exit **1** with no trap output for `wait_main`).

- **architecture** `python/ci_cli.py:44-45,127-132` — Numeric argv validation is weaker than bash. `status_main` and `wait_main` use `type=int` (and `wait_main` uses `type=float` for `--timeout`) without enforcing non-negative integers. Bash rejects values that do not match `^[0-9]+$` (`CI_STATUS=error` / exit **0** for `ci-status.sh`; exit **1** for `ci-wait.sh`). Python accepts negatives and fractional timeouts (e.g. `--empty-checks-grace -1`, `--timeout 1.5`), which changes grace-period and poll-budget behavior instead of treating them as argv errors. **Suggested fix:** After argparse, validate each numeric flag with the same `^[0-9]+$` rule (and integer-only `--timeout`) and route failures through the same error envelopes as the bash scripts.

- **risk-integration** `python/ci_cli.py:160-193` — With `--output-file` set, `wait_main` wraps `poll_ci` in a bare `except Exception`, sets `trap_exit = 1`, publishes bailout KVs, writes `<path>.done` with `1`, and **always returns process exit code 0**. Bash trap-deliverable paths on normal bail/merge completion write `.done` with `0` because the script explicitly `exit 0`; only pre-trap usage errors return **1** without publishing. File-mode consumers are documented to read `.done`, but any wrapper that treats a **0** process exit as success without reading the sentinel will miss internal failures that bash would not encode as `.done=1` on comparable paths. **Suggested fix:** Either align the process exit code with the `.done` sentinel when `--output-file` is set (return `trap_exit` instead of hard-coded `0`), or document and test that all file-mode callers must gate on `.done` before trusting success; add a pytest case where `poll_ci` raises and assert the consumer-visible contract.

### Out-of-Scope Observations

- **`merge_cli.pr_main` always returning 0 on valid argv** matches `merge-pr.sh` (“Exit codes: 0 — always (result communicated via MERGE_RESULT); 1 — usage/argument error”). Usage failures correctly return **1** via the `SystemExit` handler at `python/merge_cli.py:23-26`. Not a defect.

- **`behind_count_main` usage exit 2** is reachable for unknown flags and missing flag values via `_parse(..., 2)` at `python/ci_cli.py:266-268`; the only gap is `--help` mishandled by the shared `_parse` issue above, not unreachable dead code.

- **`sync_local_main_main` emitting `RESULT` only on `rc == 0`** (`python/git_cli.py:178-179`) matches `git-sync-local-main.sh`, which prints `RESULT=…` only on success paths and uses stderr + exit **1** on the “on main” guard without a `RESULT` KV.
