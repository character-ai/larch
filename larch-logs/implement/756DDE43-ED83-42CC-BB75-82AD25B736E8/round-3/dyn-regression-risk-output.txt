### In-Scope Findings

- **risk-integration** `python/ci_monitor.py:392-395,444-505,1623-1648` — `gather_status` now maps `gh pr view` failures to `status="pending", conflicted=True` instead of `status="error"`, so `poll_ci` no longer increments `ci_failures` and never hits the three-strike bail (`"ci-status.sh returned no valid output 3 times consecutively"`). Persistent probe failures instead spin until the full poll budget (`CI_WAIT_TIMEOUT_SEC` = 1800s at 10s intervals) and `monitor()` classifies the bail as `Outcome.STALLED` with a `"Poll budget … exhausted"` detail. On `main`, the same failure mode bailed in ~30s with `Outcome.TRANSIENT`, which engaged `ship.py`'s `_PYTHON_TRANSIENT_STALL_ATTEMPT` auto-retry path (`python/ship.py:1411-1431`). That is a material integration regression for the default Python ship driver: longer hangs on `gh` API outages and loss of transient-retry semantics, even though bash `ci-status.sh` fail-open parity was the stated goal (`python/test_ci_monitor.py:426-452` locks in the new STALLED behavior). **Suggested fix:** Either restore a dedicated consecutive-probe-failure counter in `poll_ci` that re-emits the fast bail + `Outcome.TRANSIENT` classification for repeated `gather_status` degradations (without reviving `CI_STATUS=error` on the CLI surface), or explicitly document/accept the 30-minute hang and add a matching transient-retry hook for poll-budget exhaustion if bash parity is the only requirement.

- **risk-integration** `python/ci_monitor.py:607-636,1257-1276` — `collect_failed_logs` now returns redacted partial log text for `in_progress` and `error` states (parity with `scripts/gh-run-logs.sh` tail-on-failure), but `_fix_exhausted_detail` still gates on `logs.state == "ready"` before attaching any tail. When the CI-fix waterfall exhausts while logs remain `in_progress`/`error` (common right after a failed run), operators get only the `ci-fix-exhausted: <jobs>` header with no log context, even though `collect_failed_logs` already paid for the fetch/redaction work. That weakens Step 18a stall-recovery routing that depends on log content in `BAIL_FAILURE_DETAIL_LOG` (`python/test_ship.py:2023-2054`). **Suggested fix:** Allow `_fix_exhausted_detail` to include `logs.text` when `state in {"ready", "error"}` (and optionally `in_progress` once logs stabilize), or stash the last non-empty `collect_failed_logs` text across waterfall retries so fix-exhausted detail always carries the best available tail.

### Out-of-Scope Observations

- `git.rebase_abort` (`python/git.py:838-842`) always normalizes failures to exit 0; that matches the idempotent contract of `scripts/git-rebase-abort.sh` and is distinct from ship-internal `_abort_rebase` in `python/rebase.py:91-92`, which remains unchanged.

- `_fix_exhausted_detail`'s added `redact.redact(tail)` (`python/ci_monitor.py:1275`) is redundant with upstream redaction in `collect_failed_logs`, but `redact.redact` is documented as idempotent (`python/redact.py:310-311`), so this is not a functional defect.

- Bash `/implement` call sites (`skills/implement/SKILL.md`, `skills/implement/scripts/step-7a.sh`) still invoke `rebase-checkpoint-probe.sh` / `phantom-probe-with-warn.sh` while Python CLI verbs exist; that interim dual-path state is expected before the mechanical cutover/deletion phase and is not itself a new regression in the modified modules.
