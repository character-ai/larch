### In-Scope Findings
- **architecture** `python/ci_cli.py:176-193` — `ci wait --output-file` suppresses any exception from `ci_monitor.poll_ci`: it writes a `.done` value of `1` but still returns process exit `0`. That diverges from the retained shell trap contract in `scripts/ci-wait.sh:164-174`, where the captured failing exit status is preserved for the process while also being written to `.done`. Any synchronous caller or retry wrapper that checks the command return code can now treat a fatal polling failure as success. **Suggested fix:** After publishing the output/sentinel, return `trap_exit` instead of unconditional `0` when an exception occurred, while still preserving the `.done` side channel.

- **architecture** `python/ci_cli.py:63-88` — `ci decide` no longer validates semantic inputs before producing an action. The old contract in `scripts/ci-decide.sh:78-102` rejects unknown statuses, negative numeric counters, and non-boolean `--conflicted` with exit `1`; the new path parses integers only and lets `ci_monitor.decide()` map unknown statuses to `ACTION=wait` and negative counts to normal decisions. Malformed upstream CI state can therefore become a valid orchestration action. **Suggested fix:** Add explicit validation for allowed `CI_STATUS`, non-negative counters, and `conflicted in {true,false}` before calling `ci_monitor.decide()`, returning usage exit `1` with no action KVs on invalid input.

- **architecture** `python/pr_cli.py:117-129` — `pr body-update` maps argument/validation failures to exit `2`, but the legacy contract in `scripts/gh-pr-body-update.sh:49-60` uses exit `1` for usage/argument errors and reserves exit `2` for an attempted update failure that emits `UPDATED=false`/`ERROR=...`. This collapses caller-visible “bad invocation” vs “GitHub update failed” states. **Suggested fix:** Return `1` for argparse failures and invalid `--repo`; keep exit `2` only for body-file/update failures that emit the structured result KVs.

- **architecture** `python/gh_cli.py:25-34` — `gh remote-repo` loses the legacy exit-code distinction for an unresolved remote name. `scripts/github-remote-repo.sh:18` exits `1` when `git remote get-url <name>` fails, while parse failures of an actual URL exit `2` at `scripts/github-remote-repo.sh:35-37`; the new `gh.remote_repo()` returns `None` for both and `remote_repo_main()` always exits `2`. **Suggested fix:** Have `gh.remote_repo()` return a structured state or raise/encode the `git remote get-url` failure separately so the CLI can preserve exit `1` for missing remote and exit `2` for unparsable URLs.

- **architecture** `python/git_cli.py:260-276` — The registered `git check-phantom-dirty` CLI does not preserve the script interface/contract: it omits `--phantom-paths-dir`, depends on `IMPLEMENT_TMPDIR`, and returns `1` with no `STATUS=unknown` payload on parse failures, while `scripts/check-phantom-dirty.sh:26-50` accepts `--phantom-paths-dir` and degrades parse errors into structured `STATUS=unknown` output with exit `0`. Combined with `python/phantom.py:45-72` shelling back to the retained script, this is a partial shim rather than the typed primitive the CLI registry advertises. **Suggested fix:** Move the check-mid-run-dirty-tree/phantom-path copy logic into `phantom.check_phantom_dirty()`, expose/derive the paths directory explicitly, and preserve the structured parse-error output contract.
