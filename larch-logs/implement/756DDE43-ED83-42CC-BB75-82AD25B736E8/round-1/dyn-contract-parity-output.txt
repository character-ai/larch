Reviewing the branch diff for contract-parity issues, starting with the precomputed diff and the scout-flagged hotspots.
### In-Scope Findings

- **correctness** `python/pr.py:122` — `create_branch` rejects any branch not starting with the literal `sergey-zhupanov/`, but `scripts/create-branch.sh:39-55,98-101` derives `USER_PREFIX` from `git config user.name` (lowercase, sanitize, truncate, fallback `dev`). Any other operator gets `STATUS=invalid` / exit 2 for valid branches. **Suggested fix:** Port `derive_user_prefix()` (read `git config user.name`, same sanitization rules) and validate `branch.startswith(f"{prefix}/")`; add pytest cases for varied `user.name` values and the `dev` fallback.

- **correctness** `python/pr.py:113-141`, `python/pr_cli.py:26-45` — `pr create-branch` does not match `scripts/create-branch.sh`. Check mode: bash `--check` needs no branch and emits `CURRENT_BRANCH` / `IS_MAIN` / `IS_USER_BRANCH` / `USER_PREFIX` (`scripts/create-branch.sh:75-92`); Python requires `--branch`, treats `--check` as “does this ref exist?” via `try_rev_parse`, and emits `BRANCH` / `BASE` / `STATUS`. Create mode: bash uses `git checkout -b` and exits **1** if the branch exists (`scripts/create-branch.sh:103-107,124-127`); Python uses `checkout -B` (resets an existing branch) and never returns exit 1 for “already exists”. Fetch failure is exit **2** in bash (`scripts/create-branch.sh:119-122`) vs exit **1** in Python (`python/pr.py:136-137`). **Suggested fix:** Split `--check` vs `--branch` like the shell script; emit the original KV keys and exit codes; use `checkout -b` with an existence pre-check; port `scripts/test-implement-bootstrap.sh` branch-create semantics into `python/test_pr_cli.py`.

- **correctness** `python/pr.py:155-166`, `python/pr_cli.py:48-86` — `create_pr_parity` diverges from `scripts/create-pr.sh` on the existing-PR fast path and push failures. On an open PR, bash still pushes (with force-with-lease recovery) and sets `PR_TITLE` from the GitHub PR (`scripts/create-pr.sh:165-202`); Python returns immediately with the caller’s `--title`, skipping push (`python/pr.py:155-163`). Push failure is exit **1** in bash (`scripts/create-pr.sh:176-191,256-258`) but `exit_code=2` in Python (`python/pr.py:164-166`). **Suggested fix:** On existing open PR, push/force-push like bash, then read title from `gh pr view`/`pr_for_branch`; map `push_failed` to exit **1**; add pytest for existing-PR push + title parity.

- **correctness** `python/push_cli.py:96-132` — `push checkpoint-probe` never emits `REBASE_OUTCOME`, which `scripts/rebase-checkpoint-probe.sh:95-130` always does (`ok` / `skipped` / `conflict` / `failed`). `/implement` Rebase Checkpoint Macro branches on `REBASE_OUTCOME` (`skills/implement/SKILL.md`). On conflict/failure the Python wrapper may emit `CONFLICT_FILES` / `REBASE_ERROR` but returns without `REBASE_OUTCOME`; on success it emits skip markers but still omits `REBASE_OUTCOME`. **Suggested fix:** Mirror the bash exit/KV table in `checkpoint_probe_main` (including `unexpected-rc-<n>` on unknown codes) before returning; extend `python/test_push_cli.py` to assert the full envelope.

- **correctness** `python/ci_cli.py:26-39` — `ci status` returns exit **1** on argv/parse errors, but `scripts/ci-status.sh:17,52-58` always exits **0** and communicates errors via `CI_STATUS=error` in the four-line KV block. Callers treating non-zero as a hard failure will mis-handle usage errors. **Suggested fix:** On invalid argv, emit all four KVs with `CI_STATUS=error` and return **0**, matching the shell trap contract; add a `test_ci_cli.py` usage-error case.

- **correctness** `python/ci_monitor.py:357-370` — In the `gh pr checks` text fallback (when JSON is empty/invalid), a `fail` classification does not populate `failed_run_id`, but bash extracts it from the failing line’s URL (`scripts/ci-status.sh:172-178`). Downstream `ci decide` / CI-fix paths that rely on `FAILED_RUN_ID` will get an empty ID on the text-only path. **Suggested fix:** After matching `\bfail`, parse the first failing line’s `https://…` URL and apply the same `runs/<id>` extraction as `_extract_run_id` / bash `grep -oE 'runs/[0-9]+'`; cover in `python/test_ci_monitor.py`.

- **correctness** `python/git.py:298-306`, `python/git_cli.py:55-62` — With `--only`, bash passes a bare `--only` flag to `git commit` (`scripts/git-commit.sh:125-126`); Python passes `["--only", ""]` because `commit_main` sets `only=""` when `args.only` is true and `commit_with_trailer` treats any non-`None` `only` as a two-argument pair. That can change `git commit` behavior vs the shell script. **Suggested fix:** Use a boolean `only: bool = False` in `commit_with_trailer` and append only `["--only"]` when set; add a CLI contract test for `--only` + pathspec-from-file.

- **correctness** `python/ci_monitor.py:327-342` — When `gh pr checks --json` returns non-empty but non-array JSON, bash falls through to text parsing (`scripts/ci-status.sh:104-157`); Python’s `_classify_checks_json` treats a non-list as `empty`/`pending` and never tries the text fallback. Malformed JSON can yield a different `CI_STATUS` than the shell helper. **Suggested fix:** If JSON is present but `_parse_check_rows` is empty and `json.loads` did not produce a list, treat it like the bash `else` branch and run `gh.pr_checks_text_read` classification.
