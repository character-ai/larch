### In-Scope Findings

- **code-quality** `scripts/upsert-diagrams-comment.sh:205-228,278-282` — Every upsert performs a paginated `gh api …/issues/$ISSUE/comments` list (and often a per-id body fetch), then delegates to `tracking-issue-summary.sh`, which lists the same comments again before PATCH/CREATE. On issues with long comment histories this doubles network work and widens the read-merge-write race window the plan already accepts. **Suggested fix:** Extend `tracking-issue-summary.sh upsert-summary` with an optional `--comment-id` (or have the helper call the PATCH/CREATE path directly after merge) so the merged body is written without a second marker scan.

- **correctness** `scripts/upsert-diagrams-comment.sh:103-110` — The fence state machine only treats ` ```mermaid` blocks as opaque; a generic ` ``` ` fence containing a literal `## Code Flow Diagram` or `## Architecture Diagram` line is still interpreted as a section boundary. A diagram or note block using a non-mermaid fence could cause the next upsert to drop half the comment silently. **Suggested fix:** Track any open triple-backtick fence (same pattern as `scripts/write-tally.sh`), or document that section bodies must use mermaid fences only and add a harness case with a plain code fence containing a heading-like line.
