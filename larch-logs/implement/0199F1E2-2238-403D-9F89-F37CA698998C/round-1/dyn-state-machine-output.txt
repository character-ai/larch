Examining the diff and key files for the dual-status envelope design and post-loop routing.
### In-Scope Findings

- **architecture** `skills/design/SKILL.md:1241-1276` — The post-loop matrix says routing is keyed on `STEP3_REVIEW_LOOP_STATUS`, but the paragraphs immediately below still drive control flow from legacy `LOOP_STATUS` (`Continue to Step 3.5 IMMEDIATELY`, cap/bypass checks on `LOOP_STATUS=cap-reached`, skipped-empty → Step 3.5). On loop bail-outs the per-round env often still has `LOOP_STATUS=complete` (review finished) while stdout carries `STEP3_REVIEW_LOOP_STATUS=main-agent-apply-required` / `per-round-approval-required` / etc., so an orchestrator that follows the legacy block can enter Gate B or Step 3.5 instead of the bail-out/resume handlers. **Suggested fix:** Add an explicit first-class branch immediately after the parse fence: when `--mode loop` was used, route only on `STEP3_REVIEW_LOOP_STATUS` (with a closed enum guard); gate legacy `LOOP_STATUS` prose behind `--mode single` or mark it harness-only; and add a hard rule that bail-out statuses must not fall through to Step 3.5.

- **architecture** `skills/design/SKILL.md:1230` — The parse fence validates `LOOP_STATUS` with a regex that merges loop-envelope tokens (`main-agent-apply-required`, `per-round-approval-required`, `postplan-operator-required`, `postplan-failed`) into the single-pass enum, while `cap-hit` exists only on `STEP3_REVIEW_LOOP_STATUS` and `cap-reached` only on `LOOP_STATUS`. There is no symmetric validation of `STEP3_REVIEW_LOOP_STATUS`, so a missing or mistyped envelope can slip through while `LOOP_STATUS=complete` still passes. **Suggested fix:** Validate `STEP3_REVIEW_LOOP_STATUS` with its own closed enum after loop-mode returns; keep `LOOP_STATUS` validation to single-pass values only (`complete`, `zero-findings-degraded-panel`, `tally-error`, `degraded-empty-collector`, `panel-failed`, `main-agent-vote-required`, `cap-reached`); fail closed when loop mode returns without a recognized `STEP3_REVIEW_LOOP_STATUS`.

- **architecture** `skills/design/scripts/review-design-step3-loop.sh:31-51` — `step3_loop_emit_envelope` prints `STEP3_REVIEW_LOOP_STATUS` (and bail-out KVs) to stdout only; it never updates `.step3-review-result.env`. The last `run_step3_round_body` write still holds per-pass `LOOP_STATUS` (e.g. `complete`), not the terminal loop outcome. Pause/resume or any consumer that reads the env file without stdout therefore sees the wrong state; this fights the plan’s “durable handoff” story. **Suggested fix:** On every terminal exit and bail-out, atomically merge `STEP3_REVIEW_LOOP_STATUS`, `FINAL_ROUND_NUM`, `POSTPLAN_RC`, `DEDUP_RC`, and related carry-through keys into `.step3-review-result.env` via `phase_driver_write_result_env`, mirroring how `run_step3_round_body` persists per-round state.

- **architecture** `skills/design/SKILL.md:1280-1283` — Step 3.5’s entry fence unconditionally writes `.completed/step-3`, but loop mode is supposed to write that sentinel only on terminal Step 3b transitions (and bail-outs must not). Combined with the routing ambiguity above, a mis-routed bail-out can mark Step 3 complete before apply/postplan/continuation finish, breaking pause/resume and step ordering. **Suggested fix:** Guard the Step 3.5 prelude: skip the `step-3` write when `STEP3_REVIEW_LOOP_STATUS` is any mid-loop bail-out; rely on the loop (or `design-step3-state.sh --gate-b-bypass` on legacy paths) as the sole writers per the completion-sentinel table.

- **architecture** `skills/design/SKILL.md:1312-1314` — The “Heuristic multi-round continuation check” still re-invokes `run-step3-review.sh --no-preview` (single-pass) and tells the orchestrator to “Process the resulting `LOOP_STATUS` per the Step 3 branch matrix, then Gate B, then re-evaluate.” That reintroduces the orchestrator-driven multi-round loop the refactor removed, duplicates continuation already inside `review-design-step3-loop.sh`, and splits cap/apply semantics across two controllers. **Suggested fix:** For loop-mode runs, delete or narrow this block to legacy `--mode single` / Gate-B-only paths; after Gate B bail-out apply, resume with `run-step3-review.sh --mode loop --starting-round "$N"` instead of another single-pass driver plus Gate B cycle.

- **architecture** `skills/design/scripts/test-step3-orchestrator-fence.sh:50-114` — The harness that mirrors the SKILL parse fence was not updated for the dual-status contract: it does not parse `STEP3_REVIEW_LOOP_STATUS`, `POSTPLAN_RC`, `DEDUP_RC`, or `FINAL_ROUND_NUM`, and its `LOOP_STATUS` regex is still the pre-refactor single-pass set. Structural CI therefore cannot catch regressions in loop envelope parsing or bail-out routing. **Suggested fix:** Extend `apply_step3_handoff` to match the SKILL allowlist and add cases for each `STEP3_REVIEW_LOOP_STATUS` terminal/bail-out, including fail-closed behavior when the envelope is missing after `--mode loop`.

- **correctness** `skills/design/scripts/review-design-step3-loop.sh:226-249` — `terminal_rounds` is initialized to `0` and never incremented, yet `step3_loop_emit_envelope cap-hit` passes it as `ROUNDS_COMPLETED`. Cap-hit envelopes therefore always emit `ROUNDS_COMPLETED=0`, which can skew timing, MAV deferred reads (`round-${ROUNDS_COMPLETED}`), and any downstream logic keyed on that KV. **Suggested fix:** Set `ROUNDS_COMPLETED` from the last consumed review round (`FINAL_ROUND_NUM` / `STEP3_REVIEW_ROUND_NUM` / `round_num`) at envelope emission, or remove the unused `terminal_rounds` variable and derive the count consistently.
