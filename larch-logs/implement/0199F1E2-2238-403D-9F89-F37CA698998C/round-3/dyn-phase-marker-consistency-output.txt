Reviewing the phase-marker state machine in the diff and key implementation files.
### In-Scope Findings

- **architecture** `skills/design/scripts/review-design-step3-loop.sh:246-251` — After a successful reviser run, `awaiting-post-apply` is written only *after* `revise-plan-with-waterfall.sh` returns; until then the phase file stays `awaiting-apply` while `plan.txt` may already differ from `plan-pre-apply-round-N.txt`. A pause/crash/kill in that window resumes at `awaiting-apply`, skips re-snapshotting (lines 225–227), and re-invokes the reviser on an already-revised plan, breaking the exactly-once apply invariant the phase machine is meant to enforce. **Suggested fix:** On `awaiting-apply` resume, if the pre-apply snapshot exists and `plan.txt` is not byte-identical to it, promote to `awaiting-post-apply` and skip the reviser (jump straight to dedup/postplan), or persist an intermediate phase (e.g. `awaiting-revise`) before calling the reviser.

- **architecture** `skills/design/scripts/review-design-step3-loop.sh:297-300,423-448` and `skills/design/SKILL.md:1264` — `postplan-operator-required` exits with phase still `awaiting-post-apply` and `.gate-b-postapply-ready-N` already set; promotion to `awaiting-continuation` (Override/Continue) or demotion back to `awaiting-post-apply` (plan-changing fix) is prompt-only in SKILL.md, with no helper script or Bash fence that atomically writes the phase file. If the orchestrator resumes the loop without that write, the controller re-enters `awaiting-post-apply` and calls `design-postplan-emit.sh` again (line 435), re-firing operator brakes instead of advancing to continuation. **Suggested fix:** Add a small `write-step3-round-phase.sh` (or extend `design-step3-state.sh`) invoked from fenced Step 3.5 branches after operator decisions, and assert in `test-review-design-step3-loop.sh` that `postplan-operator-required` leaves `awaiting-post-apply` and that a simulated Override resume requires `awaiting-continuation` on disk before continuation runs.

- **architecture** `skills/design/SKILL.md:1337` and `skills/design/SKILL.md:1264` — The Gate B “resume idempotency” block tells the orchestrator that when `.gate-b-postapply-ready-N` exists it should jump to shared post-apply step 7 (`design-postplan-emit.sh`) and then resume the loop at `awaiting-continuation`. That matches pause mid-postplan after dedup, but conflicts with `postplan-operator-required`, where postplan already ran in-loop, dedup succeeded, and the operator brake was already taken. Misapplying the idempotency rule re-runs postplan instead of only updating `.step3-round-N.phase` to `awaiting-continuation` and resuming the loop. **Suggested fix:** Scope the idempotency guard explicitly to `main-agent-apply-required`/pause paths (phase `awaiting-post-apply`, postplan not yet settled), and add a separate `postplan-operator-required` resume contract: write phase first, then `run-step3-review.sh --mode loop --starting-round N` with no second `design-postplan-emit.sh` unless the operator chose a plan-changing fix.

- **architecture** `skills/design/scripts/test-review-design-step3-loop.sh:139-162` — The `postplan-operator-required` harness asserts the envelope and `POSTPLAN_RC` but not that phase remains `awaiting-post-apply` with `.gate-b-postapply-ready-1` present and without promotion to `awaiting-continuation`, so the very state the scout prompt cares about is untested on the operator-bail-out path. **Suggested fix:** After the postplan-operator test, assert `[[ "$(cat "$D4/.step3-round-1.phase")" == awaiting-post-apply ]]` and `[[ -f "$D4/.gate-b-postapply-ready-1" ]]`, plus a follow-on resume case that only passes after writing `awaiting-continuation`.
