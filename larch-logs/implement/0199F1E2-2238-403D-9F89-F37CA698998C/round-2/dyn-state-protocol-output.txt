Reviewing the branch diff and key state-machine files for architecture issues.
### In-Scope Findings

- **architecture** `skills/design/scripts/run-step3-review.sh:457-477` — When `--starting-round` is omitted, the loop always starts at `review-round-count.txt + 1`. That is correct for a fresh round, but it breaks mid-round pause/resume: after an in-loop pause (e.g. `design-postplan-emit.sh` rc 11) the tmpdir can still have `.step3-round-N.phase` in `awaiting-apply` or `awaiting-post-apply` while `review-round-count.txt` is already `N`. A `/design` resume at Step 3 invokes `run-step3-review.sh --mode loop` with no `--starting-round` (`skills/design/SKILL.md` ~1193–1195), so the loop jumps to round `N+1` and abandons unfinished apply/postplan/continuation for round `N` — the exact “apply exactly once / never re-run review” invariant the phase FSM is meant to enforce. **Suggested fix:** In `validate_step3_loop_starting_round()`, when `--starting-round` is omitted, scan for the highest `N <= last_count` with a readable `.step3-round-N.phase` and default `STARTING_ROUND` to that `N`; only use `last_count + 1` when no in-flight phase exists. Mirror the behavior in pause/resume docs and add a `test-design-pause-resume.sh` / `test-run-step3-review.sh` case (count=1, `awaiting-post-apply`, omitted `--starting-round` must resume round 1, not 2).

- **architecture** `skills/design/SKILL.md:1238-1242` — The Step 3 handoff fence remaps `STEP3_REVIEW_LOOP_STATUS=postplan-failed` to `LOOP_STATUS=complete`, while the post-loop matrix says `postplan-failed` is a hard-fail that must not transition to Step 3b (`skills/design/SKILL.md` ~1262). There is no mechanical abort between the Step 3 fence and Step 3.5/3b (unlike `cap-hit` / `panel-failed`, which have explicit bypass helpers). Any downstream branch that keys off `LOOP_STATUS=complete` — including legacy Gate B prose at ~1267 and the Step 3.5 entry fence — can treat a terminal postplan failure as a normal complete review and advance the workflow with a potentially invalid plan. **Suggested fix:** Do not alias `postplan-failed` to `LOOP_STATUS=complete`; keep `LOOP_STATUS` distinct (or empty) and add a Bash guard immediately after envelope parse (`case "$STEP3_REVIEW_LOOP_STATUS" in postplan-failed) exit/abort`) before Step 3.5. Pin this in `test-step3-orchestrator-fence.sh` / `test-design-structure.sh`.

- **architecture** `skills/design/scripts/review-design-step3-loop.sh:384-394` — On `awaiting-post-apply` resume, if `.gate-b-postapply-ready-${round_num}` already exists, dedup is skipped and `design-postplan-emit.sh` runs directly. After `postplan-operator-required`, the SKILL instructs plan-changing Fix-and-retry/autofix to demote back to `awaiting-post-apply` (`skills/design/SKILL.md` ~1261), but the loop does not clear `.gate-b-postapply-ready-N` or re-run `gate-b-dedup-plan.sh --snapshot-trailers`. A plan-changing operator fix can therefore bypass fresh trailer snapshot/dedup and continue with stale mechanical state. **Suggested fix:** On any path that re-enters `awaiting-post-apply` after a plan-changing operator action, remove `.gate-b-postapply-ready-N` (and optionally refresh the loop-owned `plan-pre-apply-round-N.txt` snapshot) before resuming; always run `--snapshot-trailers` + `--dedup` when the plan file changed.

- **architecture** `skills/design/SKILL.md:1275` vs `skills/design/SKILL.md:1258` — The MainAgent vote/re-tally block still says to refresh state and “continue to Gate B as complete-equivalent,” but loop-mode routing now requires resuming `run-step3-review.sh --mode loop --starting-round "$N"` (and promoting `.step3-round-N.phase` to `awaiting-continuation` when re-tally accepts zero findings). An orchestrator following the MAV paragraph instead of the post-loop matrix can re-enter Gate B after MAV even though the in-loop controller already owns apply/postplan on the happy path, causing duplicate apply risk and breaking parity with `/implement` Step 5’s “resume the loop, not the legacy apply surface” model. **Suggested fix:** Split MAV prose into explicit loop-mode vs `--mode single` branches; loop mode should only describe re-tally → phase update → `--starting-round` resume, with no Gate B entry.

- **risk-integration** `skills/design/SKILL.md:1293-1295` — The Step 3.5 prelude does `: > "$DESIGN_TMPDIR/.completed/step-3"` without `mkdir -p "$DESIGN_TMPDIR/.completed"` (removed from this fence in the refactor). Terminal loop paths create the directory in `step3_loop_write_completed_step3()` (`skills/design/scripts/review-design-step3-loop.sh:80-84`), but bail-out paths (`main-agent-apply-required`, etc.) enter Step 3.5 before the loop writes those sentinels. If `.completed` is missing, the prelude can fail before Gate B runs. **Suggested fix:** Restore `mkdir -p "$DESIGN_TMPDIR/.completed"` in the Step 3.5 fence (or a shared helper) before touching `step-3`.
