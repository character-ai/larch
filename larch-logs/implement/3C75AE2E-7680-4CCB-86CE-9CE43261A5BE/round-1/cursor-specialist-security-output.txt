### In-Scope Findings

1. **Important** (`risk-integration`) [.github/workflows/ci.yaml](.github/workflows/ci.yaml) (lint job step `make lint-only`) vs [Makefile](Makefile) `lint:` / [docs/linting.md](docs/linting.md): CI runs `make lint-only` and sharded `make test-harnesses-N`; it does **not** invoke `make lint-bash32`. The regression target `test-lint-bash32` only runs `lint-bash32.sh` on disposable fixture trees, not a full-repo scan of all tracked `*.sh` files. **Concrete scenario:** A PR adds `declare -A` (or another forbidden construct) to a real script; `test-lint-bash32` still passes because it never scans that path, and nothing in the shown CI workflow runs `bash scripts/lint-bash32.sh` at the repo root. **Suggested fix:** Run `make lint-bash32` (or `bash scripts/lint-bash32.sh`) in CI alongside `lint-only` / harnesses, or register an equivalent pre-commit hook so the “all 281 scripts must pass” invariant is enforced on every push.

2. **Important** (`correctness`) [scripts/test-lint-bash32.sh:105](scripts/test-lint-bash32.sh): The `assert_case` needle for the `&>>` rule is not the literal substring `&>> append-all redirection` emitted by [scripts/lint-bash32.sh:84](scripts/lint-bash32.sh) (`report("&>> append-all redirection")`). The checked-in line shows an extra `"` between `&>` and `>>` (i.e. it reads like `&>">` before `append-all redirection`), so `grep -Fq` is very likely looking for the wrong bytes and the “append-all redirection” class may not be asserted. **Suggested fix:** Use a single-quoted needle (`'&>> append-all redirection'`) or another form that cannot corrupt `>>`, and re-run `make test-lint-bash32`.

3. **Latent** (`security`) [scripts/lint-bash32.sh](scripts/lint-bash32.sh) (awk body, skip before rules): Any line matching `/lint-bash32: ok/` is skipped in full, not only a trailing suppression token. That matches the documented “same-line” escape hatch but makes the guard **policy-based**: a contributor can silence every pattern on that line with one inline marker. **Concrete scenario:** `declare -A malicious=(); : # lint-bash32: ok excuse` never trips the associative-array rule. **Suggested fix:** Tighten the skip to an end-of-line anchored token (or only a trailing `# lint-bash32: ok …` comment) and require human review for any suppression.

4. **Latent** (`security`) [scripts/collect-agent-results.sh](scripts/collect-agent-results.sh) (new `launch_outer_retry_or_mark` / `launch_cmd_json_retry_or_mark`): The branch adds `eval "$launched_var=1"` / `eval "$sentinels_var+=(…)"` style updates. Today the variable names are constructed internally, which keeps risk low. **Concrete scenario:** If a future refactor ever derived `launched_var` or `sentinels_var` from untrusted or loosely validated input, this would become direct `eval` injection. **Suggested fix:** Prefer `printf -v` / `nameref` (where acceptable) or a fixed `case` of allowed destination names instead of `eval` on dynamic names.
