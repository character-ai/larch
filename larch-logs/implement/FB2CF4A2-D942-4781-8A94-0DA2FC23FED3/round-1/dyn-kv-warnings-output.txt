### In-Scope Findings

- **correctness** `skills/design/scripts/design-postplan-emit.sh:96-184` — Classification stderr is captured into `WARN_LINES` before the `plan.txt` guard, but `fail 'plan.txt missing or empty'` (and other early `fail()` calls after that read) exit **2** without calling `_postplan_write_result_and_emit`, so those warnings never land in `.design-postplan-emit-result.env` or the stdout `WARN=` contract stream. That undercuts the branch goal of operator-visible classification warnings under quiet mode on paths that die before the first emit. **Suggested fix:** On fatal exits after the classification read, either invoke a small helper that writes/emits `WARN_LINES` (with a terminal `POSTPLAN_EMIT_STATUS` such as `emit-failed` / `missing-plan`) or emit each warning via `larch_err` / `emit_kv WARN` before `exit 2`.

- **correctness** `skills/design/scripts/design-postplan-emit.sh:129-158` — `WARN=` values are written to the result env via `phase_driver_write_result_env` without newline validation, while stdout uses `emit_kv`, which rejects embedded `\n`/`\r` and returns **2** under `set -euo pipefail`. A multiline `WARN` (e.g. from a later `parse_kv_from_output` merge) can leave a complete result-env file but abort mid–stdout emit, so file-first vs stdout contracts diverge and the orchestrator may treat exit **2** as a configuration error. **Suggested fix:** Sanitize or split warning text before appending to `WARN_LINES`, validate when building `_kvs`, and/or wrap the WARN `emit_kv` loop in `set +e` with explicit handling so one bad line cannot truncate the contract stream.
