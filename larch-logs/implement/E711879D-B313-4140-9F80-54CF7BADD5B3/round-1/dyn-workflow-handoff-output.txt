### In-Scope Findings

- **architecture** `skills/implement/SKILL.md:630` — The post-dispatch hard-bail path now mirrors `IMPLEMENT_BAIL_REASON=main-branch-post-dispatch`, but `main-branch-post-dispatch` is not in `safe_bail_reason_value()` (`skills/implement/scripts/stall-recovery-report.sh:540`). Step 18a will classify using the argv token, yet the public `| Bail reason |` row will render `redacted`, so the branch adds handoff wiring without closing the reporting contract for this stall site. **Suggested fix:** Add `main-branch-post-dispatch` to `safe_bail_reason_value`, the documented `BAIL_REASON` enum in `stall-recovery-report.md` / `SECURITY.md`, and a body-render regression (similar to case 13 bail-row tests).

- **architecture** `skills/implement/SKILL.md:616-632` — Step-2 hard-bail sites set in-memory `STALL_TRACKING`, `IMPLEMENT_BAIL_REASON`, and `FINAL_BAIL_REASON`, but never `STALL_STEP` or `PHASE`. Pre-ship failures have no `ship-pr-state.sh`, so Step 18a `seed-terminal-state` defaults to `STALL_STEP=8` / `PHASE=ci-initial` (`skills/implement/references/stall-recovery.md:32`). A Step-2 dispatch failure can therefore be mislabeled as step 8 and get `RESUME_HINT=step8-shippr` instead of `step2-impl` via `resume_hint_for()` (`skills/implement/scripts/stall-recovery-report.sh:475-482`). New regressions (case 7g–7j) mask this by seeding disk state with `write_state … 2 implementation`. **Suggested fix:** At each Step-2 hard-bail site, also set in-memory `STALL_STEP=2` and an appropriate phase (e.g. `implementation` or `checks`), pass them into classify if needed, and add an argv-only fixture with `--in-memory-stall-tracking true`, no `ship-pr-state.sh`, and assert `STALL_STEP=2` plus `RESUME_HINT=step2-impl`.

- **architecture** `skills/implement/SKILL.md:632` — The new `STATUS=bailed` bullet mirrors dispatcher `REASON` verbatim into `IMPLEMENT_BAIL_REASON` / `FINAL_BAIL_REASON`, but most dispatcher bail tokens (`codex-runtime-failure`, `commit-failed`, `manifest-schema-invalid`, `dirty-state-after-timeout`, etc.) are outside the closed enum in `safe_bail_reason_value()`. Orchestrator prose treats the mirror as durable handoff evidence; the report layer will still emit `| Bail reason | \`redacted\` |` for those common failures. **Suggested fix:** Either map known dispatcher `REASON` tokens to allowlisted equivalents before setting `IMPLEMENT_BAIL_REASON` (e.g. `wrapper-validation-failure`, `qa-loop-exceeded`), or document in §2.2 that only allowlisted tokens produce a verbatim Bail reason row and raw tokens are classification-only.

- **architecture** `skills/implement/SKILL.md:647` — The branch adds `IMPLEMENT_BAIL_REASON=recovery-out-of-scope` on the manifest-recovery fail-closed path, but unlike envelope-invalid (`:616`), post-dispatch mismatch (`:630`), and `STATUS=bailed` (`:632`), this site does not set `STALL_TRACKING=true` or route to Step 12d. That makes the new mirror inconsistent with the other Step-2 bail handoffs and with `stall-recovery.md` classify, which only runs when a stall layer is truthy. **Suggested fix:** Either add `STALL_TRACKING=true` plus explicit Step 12d routing (and include `recovery-out-of-scope` in the allowlist if it should appear in reports), or drop the `IMPLEMENT_BAIL_REASON` mirror here and state that recovery scope failure is not a stall-recovery handoff.

- **architecture** `skills/implement/SKILL.md:569-632` — Multiple Step-2 paths say “bail to Step 12d,” but Step 12d is only procedurally defined in the ship-pr Exit 3 user-input flow (`skills/implement/SKILL.md:1112`); pre-ship Step-2 failures never reach ship. The new explicit `STATUS=bailed` bullet sets stall variables but still does not say whether the orchestrator skips to Step 16, seeds terminal state first, or invokes another sub-procedure. That leaves contradictory orchestration guidance across the legal-actions matrix, §2.2 bullets, and stall-recovery Step 18a entry. **Suggested fix:** Add a short §2.2 “Step 12d hard-bail routing” subsection that names the concrete next steps for pre-ship Step-2 failures (e.g. skip Steps 3–15, continue through Steps 16–17, run Step 18a with in-memory `--bail-reason "${IMPLEMENT_BAIL_REASON:-${FINAL_BAIL_REASON:-}}"` and optional `seed-terminal-state --stall-step 2 --phase …`).
