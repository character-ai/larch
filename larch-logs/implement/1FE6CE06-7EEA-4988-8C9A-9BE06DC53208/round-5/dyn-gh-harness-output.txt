Reviewing the branch diff and gh harness stubs for risk-integration issues.
### In-Scope Findings

- **risk-integration** `scripts/test-design-multi-round-integration.sh:12-68` — The integration harness embeds a second, simplified `gh` stub instead of reusing `make_gh_stub` from `scripts/test-design-log-publish.sh`. The copy only models happy-path `--json` / `--watch` / `headRefOid` behavior and cannot drive registration-race, never-registered, non-zero `--json` rc, or stale-head knobs. Publish parity (`scripts/test-design-multi-round-integration.sh:296-307`) only asserts `PUBLISH_OK=true` and artifact paths, so drift between the two stubs could leave integration green while the canonical harness or production gate regresses. **Suggested fix:** Factor shared stub helpers (or source `make_gh_stub` from one file) and add at least one integration assertion that exercises registration (e.g. `GH_STUB_CHECKS_JSON_EMPTY_FIRST` + `GH_STUB_LOG` probe counts) or document that merge-gate coverage is exclusively in `test-design-log-publish.sh`.

- **risk-integration** `scripts/test-design-log-publish.sh:208-214` — Stale-head scenarios (`GH_STUB_PR_HEAD_OID_MISMATCH`, `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST`) return an all-zero `headRefOid`, not a plausible prior commit SHA. Production compares `headRefOid` to `PUSH_HEAD_SHA` (`scripts/design-log-publish.sh:862-864`); the realistic pause/force-push failure mode is “checks green for old head + `headRefOid` still points at old tip,” which a valid but wrong SHA exercises better than `000…0`. **Suggested fix:** In stale-head cases, set `GH_STUB_PR_HEAD_OID` (or the mismatch knob) to the pre-push commit from the harness clone (e.g. `HEAD~1` or the seed pause commit) while `resolve_pr_head_oid` returns the new tip after alignment, so registration must reject a syntactically valid stale OID.

- **risk-integration** `scripts/test-design-log-publish.sh:53-71` — Default `headRefOid` resolution always uses `git ls-remote origin "$branch"` on `TEST_CLONE_ROOT`, which is updated synchronously when the publish script pushes. That cannot reproduce GitHub lag where required-check JSON is already non-empty but `headRefOid` still reflects a prior force-push head—the scenario the dual predicate is meant to fix (`scripts/design-log-publish.sh:848-865`). Registration-race coverage only empties the checks array (`GH_STUB_CHECKS_JSON_EMPTY_FIRST`), not “checks for wrong head.” **Suggested fix:** Add a case that keeps non-empty `--json` output while `GH_STUB_PR_HEAD_OID` (or a first-N knob) returns the previous push SHA, then flips to `PUSH_HEAD_SHA` after K probes—mirroring pause reuse without relying on all-zero OIDs.

- **risk-integration** `scripts/test-design-log-publish.sh:160-166` — The `--watch` arm matches any `pr checks` invocation that includes `--watch` and `--fail-fast`, but does not require `--required`. Production always passes `--required` on both registration and watch (`scripts/design-log-publish.sh:834,894`). A regression that dropped `--required` only on the watch call would still pass CI-fail and happy-path harness cases. **Suggested fix:** Add `has_arg --required "$@"` to the watch branch (and optionally to the `--json` branch) so unhandled or under-specified `pr checks` shapes fail with exit 99.
