### In-Scope Findings

- **risk-integration** `skills/design/scripts/design-publish.sh:312-320` — The `elif [[ "${PUBLISH_OK:-}" == false ]]; then` branch calls `append-tool-failure.sh --exit-code "${_publish_rc:-1}"`. There is one reachable path where `_publish_rc=0` while `PUBLISH_OK=false`: the pre-push `PR_BODY_TMP` mktemp failure at `scripts/design-log-publish.sh:678-683`. That path calls `emit_publish_failure` (no args), which since `PUSH_DONE=false` calls `emit_publish_result false "" ""` and exits 0. The caller's branch 1 (`_publish_rc -ne 0 AND no PUBLISH_OK=`) is false; branch 2 (`PUBLISH_OK==false`) fires with `_publish_rc=0`. The `:-1` fallback in `${_publish_rc:-1}` never activates because `_publish_rc` is always set by `_publish_rc=$?`. Result: `execution-issues.md` records a publish failure with exit code 0, which may mislead operators into thinking the failure was a "clean expected" vs an actual mktemp error. No `RECOVERY_BRANCH` is emitted on this path (PUSH_DONE=false), so `publish_recovery_detail` returns the neutral "no PR or recovery branch metadata was returned" string — accurate but devoid of diagnostic detail. **Suggested fix:** In the `elif PUBLISH_OK==false` arm, use `--exit-code "${_publish_rc:-1}"` → `--exit-code "${_publish_rc:-0}"` only for the zero-exit-expected case, or defensively use `1` as the floor: `--exit-code "$(( _publish_rc == 0 ? 1 : _publish_rc ))"` so failure logs always carry a non-zero exit code that `append-tool-failure.sh` will surface as an actual failure; the pre-existing `_publish_rc -ne 0` first branch already uses the raw rc directly.

- **risk-integration** `skills/design/scripts/design-publish.sh:149-153` / `scripts/design-log-publish.sh` (whole file) — `design-log-publish.sh` never emits `LOG_RECOVERY_BRANCH`; it only emits `RECOVERY_BRANCH`. The `design-publish.sh` `parse_kv_from_output` function parses only `RECOVERY_BRANCH` (correct). Then `write_result_env_and_emit` synthesizes both `RECOVERY_BRANCH=$RECOVERY_BRANCH` and `LOG_RECOVERY_BRANCH=$RECOVERY_BRANCH` in the result-env, making the two keys always identical. The `design-publish.md` result-env allowlist lists both, so the doc is internally consistent. However, `render-final-summary.sh` uses the env-exported `DESIGN_LOG_RECOVERY_BRANCH` (set from `$RECOVERY_BRANCH` directly at `skills/design/scripts/design-publish.sh:342-344`), not the result-env key — so `LOG_RECOVERY_BRANCH` in `.design-publish-result.env` is currently unread by any consumer in this diff. If a future caller reads `LOG_RECOVERY_BRANCH` expecting it to differ from `RECOVERY_BRANCH` (e.g., distinguishing flush-PR recovery from a local branch recovery), they will silently get the wrong value. **Suggested fix:** Either document in `design-publish.md` that `LOG_RECOVERY_BRANCH` is always identical to `RECOVERY_BRANCH` and exists for legacy compatibility, or drop the redundant key since no current consumer reads it and the exported env var `DESIGN_LOG_RECOVERY_BRANCH` already covers the one live use.

### Out-of-Scope Observations

- **correctness** `scripts/design-log-publish.sh` (registration loop) — The two-step `jq` check (`jq -e 'type == "array"'` then `jq -e 'length > 0'`) forks two processes instead of one combined expression (`jq -e 'type == "array" and length > 0'`) as specified by the plan. Not a correctness defect since both checks are separately guarded with `>/dev/null 2>&1`, but it runs `jq` twice on the same captured string per probe, parsing it twice. Pre-existing design decision.
