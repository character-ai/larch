- **correctness** `scripts/test-design-log-publish.sh:907-908,942-943,975-976` — Four new test cases set `SLEEP_SCRIPT_DIR` to a local per-case stub directory and then `rm -rf` that tmpdir without restoring to `$GLOBAL_SLEEP_STUB`: "registration race" (line 908 rm-rf, no restore), "required checks never register" (line 943, no restore), "registration probe fails fast on non-array JSON" (line 976, no restore), and "stale head checks wait until PR head matches pushed head" (lines 1056-1057, no restore). The immediate victim is the "registration probe accepts non-zero rc with pending JSON" case (lines 978-999): it never sets `SLEEP_SCRIPT_DIR`, so it runs with the stale, already-deleted `$TMPREGOBJ/sleep` path. The case escapes failure only because `GH_STUB_CHECKS_JSON_RC=8` with non-empty JSON satisfies the dual registration predicate on the first probe, so the production loop never reaches the sleep call. Any future modification that adds a retry phase to that case (e.g., making the first probe return empty) would cause `sleep-seconds.sh` not to be found, fall back to system `sleep $REG_INTERVAL` (10s × probes), and make the test slow without any diagnostic. **Suggested fix:** After each of the four rm-rf lines that delete a local sleep stub (lines 908, 943, 976, and 1057), add `export SLEEP_SCRIPT_DIR="$GLOBAL_SLEEP_STUB"` to restore the invariant. The "registration probe accepts non-zero rc with pending JSON" case should also add an explicit `export SLEEP_SCRIPT_DIR="$GLOBAL_SLEEP_STUB"` at its start for clarity.

- **correctness** `scripts/test-design-log-publish.sh` (gh stub, `has_arg`/knob-count section) — The stub's knob-count file paths for `GH_STUB_CHECKS_JSON_EMPTY_FIRST` and `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST` are derived as `${GH_STUB_CHECKS_JSON_COUNT_FILE:-${GH_STUB_LOG:-}.checks-json-knob-count}` and `${GH_STUB_PR_HEAD_OID_COUNT_FILE:-${GH_STUB_LOG:-}.head-knob-count}`. When `GH_STUB_LOG` is unset or empty (the `pause reason stages .completed` case explicitly does `unset GH_STUB_LOG`), these expand to the bare dotfiles `.checks-json-knob-count` and `.head-knob-count` in the CWD (the consumer clone directory). The `if [[ -n "$knob_count_file" ]]` guard does not prevent this because the dotfile string is non-empty. This is structurally asymmetric with the main `checks-json-count` counter, which correctly uses a two-step expansion (`count_file=""`; then `if [[ -n "${GH_STUB_LOG:-}" ]]; then count_file="${GH_STUB_LOG}.checks-json-count"; fi`) and only writes when the log path is non-empty. No current test case simultaneously unsets `GH_STUB_LOG` and sets the EMPTY_FIRST/MISMATCH_FIRST knobs, so no dotfile is created today — but if a future case ever does so, the knob counter would accumulate across sequential cases that share the same CWD, producing wrong probe-count assertions. **Suggested fix:** Apply the same two-step pattern for the knob-count paths: initialise `knob_count_file=""` then set it only when `GH_STUB_LOG` is non-empty (mirroring the main counter), or add an explicit guard that exits the stub with an error when `GH_STUB_LOG` is unset but a knob that requires a count file is active.
