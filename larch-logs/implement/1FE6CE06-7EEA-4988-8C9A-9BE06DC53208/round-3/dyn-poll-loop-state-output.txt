Reviewing the branch diff and the registration-loop implementation for correctness issues.
### In-Scope Findings

- **correctness** `scripts/design-log-publish.sh:825-865` — The registration loop bounds only the number of `REG_INTERVAL` sleeps (`reg_probe < REG_MAX_PROBES`), not total wall time. Whenever `checks_json_nonempty` is true, each probe also calls `with_transient_retry` for `gh pr view` (lines 844–849), which can add up to two backoff sleeps (2s + 4s) per probe on transient failures. In the worst case (non-empty checks every probe, head never aligns or `pr view` keeps retrying), that is up to 31 × 10s = 300s from the poll sleeps plus up to 31 × 6s ≈ 186s from retries—well past the advertised `${REG_TIMEOUT}s` in the registration-timeout `larch_err` (line 874). Operators and tests that treat `REG_TIMEOUT=300` as a hard ceiling can still wait ~8+ minutes while stderr claims a 300s budget. **Suggested fix:** Either (a) use a wall-clock deadline (`deadline=$((SECONDS + REG_TIMEOUT))` and stop probing when `SECONDS >= deadline`, counting all sleeps including `with_transient_retry`), (b) drop `with_transient_retry` inside the registration loop and rely on the outer poll cadence for transient `pr view` errors, or (c) cap registration `pr view` to a single attempt per probe and document that `REG_TIMEOUT` is sleep-budget-only.

- **architecture** `scripts/design-log-publish.sh:843-858` — Registration requires non-empty required-check JSON and matching `headRefOid`, but does not assert that individual check runs belong to `PUSH_HEAD_SHA`. After a force-push, GitHub could theoretically expose prior-head green checks while `headRefOid` already matches; that race is mitigated in tests (stale-head cases) but not fully ruled out by API semantics—worth monitoring in production pause/reuse runs.
