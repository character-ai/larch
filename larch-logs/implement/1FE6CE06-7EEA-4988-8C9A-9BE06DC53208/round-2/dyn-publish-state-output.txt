Reviewing the branch diff and publish lifecycle across the changed scripts.
### In-Scope Findings

- **architecture** `skills/design/scripts/design-publish.md:31-33` — The result-env allowlist still documents only `PLAN_WRITE_OK`, `PUBLISH_OK`, `RENAMED`, `UPSERT_STATUS`, `ARCHITECTURE_SOURCE`, `FINAL_SUMMARY_PATH`, and `WARN`, but `design-publish.sh` now also writes `PR_NUMBER`, `PR_URL`, `RECOVERY_BRANCH`, and `LOG_RECOVERY_BRANCH` to `.design-publish-result.env` and stdout (see `design-publish.sh:147-164`). That is a contract drift: readers of the sibling doc and anything using an allowlist derived from it will miss publish-recovery fields the harness already asserts (`test-design-publish.sh:281-284`). **Suggested fix:** Extend the `## Result env` allowlist and responsibilities in `design-publish.md` to document all eight publish-related keys (including when each is set on success vs failure), and update the “Edit in sync” list so `skills/design/SKILL.md` Step 5c parsing stays aligned.

- **architecture** `skills/design/SKILL.md:1515-1525` — Step 5c’s file-first and stdout-fallback parsers only bind `PLAN_WRITE_OK|PUBLISH_OK|RENAMED|UPSERT_STATUS|ARCHITECTURE_SOURCE|FINAL_SUMMARY_PATH`, while `design-publish.sh` now forwards `PR_NUMBER`, `PR_URL`, `RECOVERY_BRANCH`, and `LOG_RECOVERY_BRANCH` from `design-log-publish.sh` into the result env. After a failed flush, operators are told to find recovery-branch notes in `design-log-publish.sh` stderr/stdout (`SKILL.md:1582`), but the structured recovery data is already on `.design-publish-result.env` and is dropped by the orchestrator. Re-enabling the flush makes that gap operational again (stuck PR + branch, no `[DESIGNED]` rename, tmpdir preserved). **Suggested fix:** Extend the Step 5c `case` allowlist to parse the four publish fields; on `PUBLISH_OK=false` with non-empty `PR_URL` / `RECOVERY_BRANCH` / `LOG_RECOVERY_BRANCH`, surface them in the Step 5d WARN replay (or a single machine breadcrumb) so recovery does not depend on re-reading `design-log-publish.failure.log`.

- **architecture** `skills/design/scripts/design-publish.sh:320-324` and `skills/design/scripts/render-final-summary.sh:322-332` — Post-publish summary always calls `render-final-summary.sh` with `--outcome approved` and `render-run-summary.sh` with `--pr-number 0` / `--pr-url N/A`, even when `PUBLISH_OK=false` after a real flush (PR created, merge refused, `RECOVERY_BRANCH` set). The terminal summary therefore still reads as Gate-C “approved” and shows only a not-yet-merged `larch-logs/design/<RUN_ID>/` path, not the open design-log PR or recovery branch the publish step just produced. Re-enabling GitHub flush amplifies this lifecycle mismatch. **Suggested fix:** Either pass parsed `PR_NUMBER`/`PR_URL` into `render-final-summary.sh` (new flags or env) so the `- **PR**:` bullet reflects the flush PR on failure, and/or select a distinct post-publish outcome (or note line) when `PUBLISH_OK=false` so the summary does not imply a completed log publish; keep rename/cleanup gating on `PUBLISH_OK=true` unchanged.
