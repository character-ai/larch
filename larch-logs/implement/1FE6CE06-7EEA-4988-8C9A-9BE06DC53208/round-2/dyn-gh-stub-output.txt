### In-Scope Findings

- **correctness** `scripts/test-design-log-publish.sh:583-609` — The pause branch-reuse case claims to cover stale-head retry (`head-count == 2` with `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST=1`), but the stub’s `head_probe` is stored in a persistent sidecar (`$GH_STUB_LOG.head-count`) and is **not** reset between the seed publish and the reuse publish. The seed run performs at least one successful `pr view … headRefOid`, so the reuse run’s first head probe is `head_probe=2`. With `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST=1`, mismatch only applies when `head_probe <= 1`, so the reuse publish **never** returns the stale OID; it resolves `headRefOid` on the first reuse registration attempt. The test can still pass (`1` head view from seed + `1` from reuse = `2`) without exercising force-push stale-head behavior that production guards (`headRefOid` ≠ `PUSH_HEAD_SHA` while checks are already non-empty). **Suggested fix:** Truncate or use fresh `GH_STUB_PR_HEAD_OID_COUNT_FILE` / `GH_STUB_LOG.head-count` before the reuse invocation (and similarly for `.checks-json-count` when using `*_EMPTY_FIRST`), or set `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST` relative to the post-seed probe index (e.g. `2` after one seed head probe). Assert that an early reuse `pr view` log used the stale OID (e.g. grep stub log / capture OID) before the aligned OID.

- **correctness** `scripts/test-design-log-publish.sh:132-190` — `GH_STUB_CHECKS_JSON_EMPTY_FIRST` and `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST` are keyed off **cumulative** probe counters in files derived from `GH_STUB_LOG`, while only `GH_STUB_LOG` itself is truncated (`: >"$GH_STUB_LOG"`). Any case that runs `design-log-publish.sh` twice against the same log path (pause reuse seed + reuse, or similar) shifts the meaning of “first K probes” away from “first K probes of this publish run,” so knobs can silently stop modeling registration race / stale-head windows. **Suggested fix:** Reset `${GH_STUB_LOG}.checks-json-count` and `${GH_STUB_LOG}.head-count` (or dedicated `*_COUNT_FILE` env vars) at the start of each publish invocation under test, or document and enforce one publish per log file for `*_FIRST` knobs.

- **risk-integration** `scripts/test-design-log-publish.sh:53-71` — `resolve_pr_head_oid` models GitHub `headRefOid` as `git ls-remote origin "$TEST_MERGE_BRANCH"` on `TEST_CLONE_ROOT`, while production compares `gh pr view` to `PUSH_HEAD_SHA` from the publish worktree (`scripts/design-log-publish.sh:713-853`). The harness assumes `TEST_MERGE_BRANCH` matches `larch-log-design-${RUN_ID}` and that the remote tip equals the worktree commit just pushed; it does not cross-check worktree `rev-parse HEAD`. A wrong or leaked `TEST_CLONE_ROOT` / `TEST_MERGE_BRANCH` (see sequential cases that export one clone then run another without updating env) can make registration pass in the stub while production would time out or wait longer. **Suggested fix:** After push in the harness (or in the stub on first `headRefOid` call), derive the expected OID from the same repo/commit the publish script pushed (e.g. `git -C "$TEST_CLONE_ROOT" rev-parse "$TEST_MERGE_BRANCH"` after fetch, or record `PUSH_HEAD_SHA` from the worktree in a test-only file the stub reads).

- **correctness** `scripts/test-design-log-publish.sh:985-1006` — Stale-head coverage that **does** match production intent lives in the dedicated `=== stale head checks wait until PR head matches pushed head ===` block (`GH_STUB_PR_HEAD_OID_MISMATCH_FIRST=2` on a fresh log). That is sound. The pause-reuse block does not add incremental regression for pause/force-push reuse beyond that case; rely on the dedicated case or fix pause-reuse as above.
