Reviewing the branch diff and harness changes for fidelity issues.
### In-Scope Findings

- **correctness** `scripts/test-design-log-publish.sh:954-957` — The new “stale head eventual match” case (`RUNSTALE1`) asserts `PUBLISH_OK=true`, `head-count == 3`, and `pr merge`, but unlike the registration-race, CI-fail, and non-zero-JSON cases it never asserts that `gh pr checks … --watch --fail-fast` ran. A regression that treated “JSON non-empty + `headRefOid` match” as sufficient and merged without the completion watch would still pass this test, while violating the production two-phase gate in `scripts/design-log-publish.sh` (~854-860). **Suggested fix:** Add the same log assertion used elsewhere, e.g. `grep 'pr checks' "$GH_STUB_LOG" | grep -q -- '--watch'`, and optionally assert `--json` probes occurred before the first `--watch` line.

- **correctness** `scripts/test-design-multi-round-integration.sh:24-30` — The integration `gh` stub splits `--json` vs non-`--json` `pr checks`, but the non-JSON arm returns success for any `pr checks` invocation that lacks `--json`, without requiring `--watch` and `--fail-fast` like the canonical stub in `scripts/test-design-log-publish.sh:152-161`. If `design-log-publish.sh` ever regressed to a bare `--watch` (or another unhandled shape), this harness would still report “all checks passing” and `PUBLISH_OK=true` on the publish-parity path (~290-301), while the main harness would exit 99 (`STUB ERROR: unhandled pr checks`). **Suggested fix:** Mirror the main stub’s watch arm (`has_arg --watch` && `has_arg --fail-fast`) and fail closed on other `pr checks` shapes, or share one stub implementation between the two harness files.

- **risk-integration** `scripts/test-design-log-publish.sh:132-136` — JSON probe numbering uses `${GH_STUB_LOG}.checks-json-count` only when `GH_STUB_LOG` is set (or `GH_STUB_CHECKS_JSON_COUNT_FILE` is exported). When `GH_STUB_LOG` is unset—as in the pause reuse block (~555-596)—`checks_probe` stays at 1 on every registration poll, so probe-count assertions (e.g. never-registered `== 31`, registration-race `== 3`) do not run on those paths. Pause reuse can still pass on the first probe, so a broken counter would not be caught there. **Suggested fix:** Always derive a per-run counter file (e.g. from `mktemp` or require `GH_STUB_LOG` in any case that reaches the merge gate), or export a dedicated `GH_STUB_CHECKS_JSON_COUNT_FILE` in pause-reuse / force-push scenarios that are meant to stress multi-probe registration.

- **correctness** `scripts/test-design-log-publish.sh:53-71` — `resolve_pr_head_oid` resolves the PR head via `git ls-remote origin "$branch"` on `TEST_CLONE_ROOT`, while production compares `gh pr view … headRefOid` to `PUSH_HEAD_SHA` from `git -C "$WT_DIR" rev-parse HEAD` after push (`scripts/design-log-publish.sh:705, 837`). In the local bare-repo harness that usually matches, but the stub does not model API lag where `headRefOid` trails the pushed worktree tip, nor pause/force-push reuse where green checks from an old head could exist while `headRefOid` is stale. Case 5 mitigates this with `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST`, but the real pause-reuse test (~573-596) does not assert any multi-probe head-alignment behavior on force-push reuse. **Suggested fix:** Either extend the pause-reuse test with `GH_STUB_PR_HEAD_OID_MISMATCH_FIRST` (and log assertions), or document that stale-head coverage is knob-only; optionally resolve OID with `git -C "$TEST_CLONE_ROOT" rev-parse "$branch"` after fetch to better match post-push worktree state.
