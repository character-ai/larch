Reviewing the branch diff and merge-gate implementation for GitHub CI registration risks.
Branch commits (vs `main`): `01a6d33fd` (re-enable + two-phase gate), `68394499f` (lint fixes), `45b8751ef` (multi-round gh stub), plus an implement run-log chore commit.

### In-Scope Findings

- **risk-integration** `scripts/design-log-publish.sh:788-847` — The registration loop advertises a `${REG_TIMEOUT}s` (300s) bound, but enforcement is probe-count only (`REG_MAX_PROBES` = 31 with 10s sleeps). Each iteration where required-check JSON is non-empty also calls `gh pr view` under `with_transient_retry` (up to three attempts with 2s/4s backoff on transient failures), so wall-clock duration can exceed 300s without consuming extra probes. Operators and SECURITY.md readers may treat a registration-timeout as “GitHub was slow to register checks,” when the script may still be inside the registration loop, or may eventually fail with timing text that understates how long the run actually waited. **Suggested fix:** Either cap total wall-clock time for the registration phase (monotonic clock + `REG_TIMEOUT`) in addition to probe count, or apply the same transient-retry budget to both `pr checks` and `pr view` and document/emits elapsed seconds in the timeout `larch_err` so diagnostics match behavior.

- **risk-integration** `scripts/design-log-publish.sh:837-868` — `PUSH_HEAD_SHA` / `headRefOid` equality is checked only to exit the registration loop; after that, the script hands off to `gh pr checks --watch` and then `gh pr merge --squash --admin` with no second head binding. If the disposable branch head moves after registration (force-push by another process with write access, or GitHub updating the PR head while a long watch runs), `--watch` evaluates the live PR head while `PUSH_HEAD_SHA` still refers to the commit this run pushed. A passing watch plus `--admin` can then merge content that is not the SHA this publish flushed—re-enabling the GitHub flush (#3378 revert) widens exposure of that window. **Suggested fix:** Immediately before `gh pr merge`, re-fetch `headRefOid` and refuse merge unless it still equals `PUSH_HEAD_SHA` (same `with_transient_retry` / `redact_diagnostic` pattern as registration); treat mismatch as `PUBLISH_OK=false` with a dedicated diagnostic distinct from registration-timeout and watch-failure.

### Out-of-Scope Observations

- **risk-integration** `scripts/design-log-publish.sh:854-857` — The completion `--watch` remains intentionally unbounded (pre-existing; documented in `design-log-publish.md`). A hung required job can leave a flush PR open indefinitely after registration succeeds; that is orthogonal to the #3413 registration race fix.

- **architecture** `scripts/design-log-publish.sh:821-823` — Registration treats “reported” as “non-empty JSON array,” not “at least one `pending`/`in_progress` bucket.” That matches the plan and is reasonable because `--watch --fail-fast` is supposed to wait for terminal states; it still depends on `gh` correctly representing the full required-check set after partial registration (same dependency as before, now with a safer entry into `--watch`).
