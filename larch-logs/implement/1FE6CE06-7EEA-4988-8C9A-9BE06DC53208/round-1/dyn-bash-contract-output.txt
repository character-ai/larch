### In-Scope Findings

- **code-quality** `scripts/design-log-publish.sh:802-810` — After a successful `git push` (`PUSH_DONE=true`), the new registration-phase `mktemp` failure handlers call `emit_publish_result false` and `exit 0` without emitting `RECOVERY_BRANCH`, even though the script header (lines 15–16) says post-push failures should exit **1** and the success path at lines 887–890 always emits `RECOVERY_BRANCH` when `PUSH_DONE=true`. A full disk or `mktemp` failure at this point leaves a pushed `larch-log-design-<run-id>` branch and possibly an open PR, but the caller only sees `PUBLISH_OK=false` with no recovery pointer—harder to diagnose than registration-timeout / CI-fail paths. **Suggested fix:** Mirror the post-push contract: on registration `mktemp` failure after push, `emit_kv RECOVERY_BRANCH "$WT_BRANCH"` (when `PUSH_DONE=true`), then `exit 1` (not `exit 0`).

- **code-quality** `scripts/design-log-publish.sh:179-192,802-810` — `reg_checks_err_file` and `reg_view_fail_file` are removed in the loop tail (`848`) but are not listed in `wt_cleanup`’s `rm -f` list. If the first `mktemp` succeeds and the second fails (lines 807–810), the script `exit 0`s before the loop runs, so the first temp file is never deleted and the EXIT trap does not clean it up. **Suggested fix:** Add both paths to `wt_cleanup`, or `rm -f` the first file in the second `mktemp` failure branch before exiting.

- **risk-integration** `scripts/design-log-publish.sh:825-830,842-843` — Each registration probe that sees non-empty check JSON calls `with_transient_retry` on `gh pr view`. With `transient_envelope_predicate_none`, transient network signatures can add up to 6s of retry sleep per probe on top of the 10s `REG_INTERVAL` sleeps, so worst-case wall time can exceed the `${REG_TIMEOUT}s` message (300s nominal) without being obvious to operators. **Suggested fix:** Either document that `REG_TIMEOUT` bounds only registration-interval sleeps (not `with_transient_retry` backoff), or use a wall-clock deadline / fewer view retries inside the registration loop.

### Out-of-Scope Observations

- **code-quality** `skills/design/scripts/design-publish.sh:268-297` — If `design-log-publish.sh` exits non-zero but stdout still contains `PUBLISH_OK=true`, none of the failure branches run and rename can proceed as if publish succeeded. This matches the restored pre-#3378 envelope handling, not new logic from this branch.

- **correctness** `scripts/design-log-publish.sh:854-860` — After registration succeeds, the script does not re-check `headRefOid` before `--watch`/merge; protection relies on GitHub associating `--watch` with the current PR head. Reasonable for a bot-only branch, but an external push to the same branch during watch would be out of scope for this fix.

Overall: the two-phase gate (`--json` registration + head binding + `--watch`) addresses the #3413 race correctly; `set +e`/`set -e` boundaries around `gh pr checks`, `jq` redirected to `/dev/null`, and stub split in tests look sound. The main actionable gap is post-push recovery semantics for the new registration `mktemp` paths.
