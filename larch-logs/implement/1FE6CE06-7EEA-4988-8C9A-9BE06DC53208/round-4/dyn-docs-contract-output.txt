### In-Scope Findings

- **risk-integration** `scripts/design-log-publish.md:52-76`, `SECURITY.md:217` — The updated docs describe a bounded registration grace (`REG_TIMEOUT` / `ceil(timeout/interval)+1` probes) but no longer state that the post-registration `gh pr checks --required --watch --fail-fast` phase is still locally unbounded. The script still relies on GitHub per-job timeouts for that watch (`scripts/design-log-publish.sh:798-799`, `882-884`). Operators can reasonably read “bounded grace/probe budget” as capping total publish-tail wait, which understates stuck-run risk when CI is slow after checks register. **Suggested fix:** In `design-log-publish.md` and the `SECURITY.md` design-log paragraph, explicitly split “registration wait (bounded)” from “completion watch (unbounded locally; bounded by GitHub job timeouts)” so the two phases are not conflated.

- **risk-integration** `scripts/design-log-publish.sh:825-879`, `scripts/design-log-publish.md:67-76` — The registration-timeout `larch_err` always prints `${REG_MAX_PROBES} probes` even though the loop also stops when `SECONDS` exceeds `REG_DEADLINE` (`825`), so a wall-clock cutoff can occur after fewer probes than the message claims. That weakens the new operator contract that distinguishes registration timeout from CI failure via stderr wording. **Suggested fix:** Report the actual completed probe count (e.g. `reg_probe - 1` after the loop) and, if useful, note whether the loop ended on probe budget vs deadline; align the doc examples with that wording.

- **risk-integration** `scripts/design-log-publish.sh:811-813`, `SECURITY.md:217` — When `PUSH_HEAD_SHA` is empty after push, the script emits the registration-timeout substring (`did not register within … (0/${REG_MAX_PROBES} probes; pushed head SHA unavailable)`) without running any registration probes. That matches the plan’s fail-closed path but reads like a check-registration race, not a local git/head capture failure. **Suggested fix:** Either use a dedicated diagnostic for missing head SHA, or document in `design-log-publish.md` / `SECURITY.md` that `0/N probes` plus “pushed head SHA unavailable” means head capture failed, not “GitHub never reported checks.”

- **risk-integration** `skills/design/scripts/render-final-summary.sh:313-328`, `SECURITY.md:217`, `scripts/design-log-publish.md:72-76` — This branch adds `failed-publish` rendering and stresses distinct stderr substrings (`did not register within` vs `did not pass`), but the operator-facing `final-summary.md` note still only says “design logs did not finish publishing” with PR/recovery metadata. Chat/summary readers get no signal about registration-timeout vs CI-failure vs merge failure unless they dig into `design-log-publish.failure.log`. **Suggested fix:** Parse the last publish failure log (or pass a short failure class from `design-publish.sh`) into the `failed-publish` note lines so the summary echoes the same registration vs watch distinction documented in `SECURITY.md`.

- **risk-integration** `scripts/design-log-publish.md:129-131`, `scripts/design-log-publish.md:114-120` — The exit-code section lists “required-check registration timeout” as a failure mode, but the `PUBLISH_OK` table still only mentions “a required check that did not pass during the CI-wait gate,” omitting registration timeout and head-mismatch paths that also yield `PUBLISH_OK=false`. **Suggested fix:** Extend the `PUBLISH_OK` row to name registration timeout / head mismatch and no-merge explicitly, matching the exit-code list and `SECURITY.md`.

- **risk-integration** `scripts/design-log-publish.md:52-76`, `SECURITY.md:217` — Pre-change `design-log-publish.md` documented that a repo with no required checks fails closed (`PUBLISH_OK=false`). That operator-facing failure mode was removed in the rewrite and is not carried into `SECURITY.md`, even though runtime behavior is unchanged (empty `--json` array never satisfies registration). **Suggested fix:** Restore a short “zero required checks → registration-timeout, no merge” bullet under Security / merge-gate failure modes so consumers without branch-protection checks know the flush PR will not auto-merge.
