Checking how `check_and_retry_voter_parse_rate` is invoked and whether unconditional `rm -f` can remove a wanted sidecar.

Call sites are single-invocation per slot per run (`scripts/dispatch-code-voters.sh` ~398–400), so unconditional `rm -f` won’t erase a sidecar from an earlier call in the same process. Verifying `emit_breadcrumb` behavior when `cp` fails.

### In-Scope Findings

### FINDING_1: Breadcrumb and audit trail omitted when `cp` fails despite successful promotion (**Important**, **correctness**, source: **plan** / **both**)
- **Location:** [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh) `check_and_retry_voter_parse_rate` (sidecar copy + breadcrumb block, approximately lines 263–266 in the post-change file).
- **Issue:** On the parse-retry success branch, `emit_breadcrumb` runs only inside `if cp "$voter_path" "$first_pass_sidecar" 2>/dev/null; then`. The implementation plan and feature text call for preserving first-pass content for observability and emitting a breadcrumb; when `cp` fails (e.g. disk full, permission denied on the sidecar path), the code still runs `mv "$retry_output" "$voter_path"`, so the canonical file is promoted and stdout still reports `OK`, but there is no sidecar and no breadcrumb.
- **Concrete failing scenario:** First-pass narrative is `NOT_SUBSTANTIVE`; retry parses as `OK`; `cp` to `*-vote-output-first-pass.txt` fails; `mv` succeeds. Operators get a clean final vote file with no first-pass artifact and no quiet-stream breadcrumb, so the observability gap the change is meant to fix persists exactly when preservation I/O fails.
- **Suggested fix:** After a failed `cp`, still emit a stderr breadcrumb (worded as “preservation failed” or similar) while keeping promotion fail-open; optionally align with the plan’s unconditional `emit_breadcrumb` after `cp … || true`.

### FINDING_2: Proactive `rm -f` of the sidecar path on every parse-rate check (**Latent**, **correctness**, source: **requirements**)
- **Location:** [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh) `check_and_retry_voter_parse_rate` (approximately lines 240–244).
- **Issue:** `rm -f "$first_pass_sidecar"` runs before `NOT_SUBSTANTIVE` is known, so any pre-existing file at the computed sidecar path is removed even when the slot returns `OK` without a retry.
- **Concrete failing scenario:** A `REVIEW_TMPDIR` is reused or pre-populated with a deliberately kept `*-vote-output-first-pass.txt` (e.g. manual copy from an earlier run); a subsequent dispatch for the same slot with `OK` parse rate deletes that file at entry before returning, so the artifact disappears without a parse-retry.
- **Suggested fix:** Restrict removal to the `NOT_SUBSTANTIVE` branch (or only remove immediately before a successful `cp`), if preserving arbitrary pre-seeded sidecars matters; otherwise document that the sidecar path is owned by this function.
