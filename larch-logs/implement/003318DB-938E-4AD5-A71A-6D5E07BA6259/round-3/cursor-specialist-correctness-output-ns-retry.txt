### In-Scope Findings

### FINDING_1: Leading sidecar rm can drop a leftover first-pass artifact before OK fast-path
- **severity**: **Latent**
- **focus-area**: `correctness` (source: `plan` / operational semantics not spelled out in plan)
- **file:line**: [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh):244-246
- **what**: `rm -f "$first_pass_sidecar"` runs on every `check_and_retry_voter_parse_rate` entry, before `status` is computed and before the `NOT_SUBSTANTIVE` gate; on the `OK` early-return path the function still deletes the sidecar path if it already exists.
- **concrete scenario**: A prior run (or tooling) left `claude-vote-output-first-pass.txt` under the same `REVIEW_TMPDIR`; a later run hits `NOT_SUBSTANTIVE` for a different slot first, or the same slot is re-dispatched into a reused tmpdir, and the voter is ultimately `OK` without a new parse-retry — the unconditional `rm` removes the older sidecar before any new preservation occurs, so the earlier first-pass snapshot is lost with no replacement.
- **suggested fix**: Restrict removal to the retry-success path immediately before `cp` (or only run the cleanup once `status` is `NOT_SUBSTANTIVE`), so the no-retry `OK` path never deletes unrelated pre-existing sidecars.

### FINDING_2: Plan’s “always emit breadcrumb after best-effort cp” is only partially met
- **severity**: **Nit**
- **focus-area**: `correctness` (source: `plan` — completeness w.r.t. plan)
- **file:line**: [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh):263-268
- **what**: The plan called for a single fail-open `cp … || true` plus a breadcrumb; the implementation emits `emit_breadcrumb` only when `cp` succeeds and uses `larch_err` on failure (retry promotion still proceeds, which matches fail-open for `mv`).
- **concrete scenario**: Disk full or permission denied on the sidecar path: operators get a generic warning line but no breadcrumb in the breadcrumb channel, so observability differs from the plan’s uniform breadcrumb signal.
- **suggested fix**: After the `larch_err` branch, also call `emit_breadcrumb` (or fold the warning text into one stderr-only breadcrumb) so both outcomes surface the same mechanism.

### FINDING_3: Docs understate allow-list coverage for waterfall-shaped voter paths
- **severity**: **Nit**
- **focus-area**: `risk-integration` (source: `requirements` / operator docs accuracy)
- **file:line**: [scripts/larch-log.md](scripts/larch-log.md):239-244
- **what**: Docs highlight `*-vote-output-first-pass.txt`; waterfall final paths like `codex-vote-output-phase3.txt` produce `codex-vote-output-phase3-first-pass.txt`, which is not matched by that narrower glob but is still included via the existing `*-output-*.txt` arm in `round_artifact_included`.
- **concrete scenario**: A reader disables or doubts logging for phase-3 outputs because the named pattern does not mention `*-phase*-first-pass.txt`, though commits still work.
- **suggested fix**: Mention in `larch-log.md` that non-base voter filenames remain governed by the broader `*-output-*.txt` allow-list patterns.
