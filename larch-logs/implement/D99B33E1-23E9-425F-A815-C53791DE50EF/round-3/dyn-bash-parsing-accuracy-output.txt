Reviewing branch changes with focus on Bash command-classification correctness in the anti-read-poll hook.
Examining edge cases in the Bash parser and cross-checking harness coverage.
Checking a few parsing edge cases against the regex logic:
### In-Scope Findings

- **correctness** `scripts/hook-anti-read-poll.sh:87-110` — `bash_line_task_output_poll_token` only splits on `;` and `&&`, not `||`. A command like `test -f "$LOCK" || cat …/tasks/<id>.output` is kept as one segment; when the left-hand test succeeds, Bash never runs `cat`, but `bash_has_read_verb` still sees `cat` plus a `tasks/…output` substring and can advance the poll counter. That is a semantic mismatch for a common guard pattern (warn-only false positive). **Suggested fix:** extend splitting to treat `||` like `&&` (iterate segments and only treat a segment as a poll-read when it both matches read-verb + task-output path and is not provably dead code on the RHS of `||` when a preceding segment is a simple success test), or document `||` guards as unsupported and accept the false-positive rate for a warn-only hook.

- **correctness** `scripts/hook-anti-read-poll.sh:87-110` — After `&&` splitting, each RHS segment is classified independently with no short-circuit model, so `false && cat …/tasks/<id>.output` (and similar `:! cmd && cat …`) still counts the right-hand `cat` even though Bash will not execute it. The harness explicitly covers the desirable wrapper case (`sleep 1 && cat …`), but not this dead-code case; incident-shaped polling is unaffected, yet guard-and-read compound commands can spuriously trip the reminder. **Suggested fix:** when walking `&&`-split segments left-to-right, skip segments after an earlier segment that is a known false literal (`false`, `:`) or add a conservative “only count the rightmost segment that both has a read verb and task-output token” rule for `&&` chains.

- **correctness** `scripts/hook-anti-read-poll.sh:87-110` — Segment splitting is not quote-aware: a semicolon inside a quoted path (e.g. `cat "/tmp/proj/with;semicolon/tasks/id.output"`) fractures the command before the closing quote, so the `cat` fragment may lose the path match while a later fragment can contain `tasks/id.output` without a read verb, yielding a false negative (missed poll). Default task-output paths are unlikely to contain `;`, but the classifier is not robust to quoted metacharacters. **Suggested fix:** either strip or mask quoted spans before `;`/`&&` splitting, or rely on the Read branch for quoted paths and document that Bash classification is best-effort for unquoted paths only.

- **correctness** `scripts/hook-anti-read-poll.sh:53-61` — `bash_has_read_verb` uses `(^|[^[:alnum:]_])(cat|…)([^[:alnum:]_]|$)`, so an identifier like `cat_output` at the start of a segment matches `cat` with a following `_` boundary; combined with a `tasks/…output` substring in the same segment, the hook can warn when no `cat`/`tail`/… utility ran. This is lower severity than the `||`/short-circuit issues but is a real word-boundary false positive. **Suggested fix:** tighten the pattern to require `cat` as a standalone token (e.g. `\<cat\>` with grep `-w` for the simple verbs, or require whitespace/`$` after `cat` and disallow immediate `_`).

### Out-of-Scope Observations

- `scat`, `concat`, and `headless` do not false-match the read-verb regex; the harness’s `cat notes.txt` and `sed -i.bak …; grep -rn` cases cover the main false-positive guards the plan cared about.
- `extract_task_output_token` (`grep -oE … | tail -1`) and `extract_bash_task_output_poll_token` (first logical line with a match) behave as designed for incident shapes (multiline leading assignments, suffixes after `.output`, wrapper variants sharing one normalized key); a single line with two `tasks/…output` paths only attributes to the rightmost id, which is an acceptable limitation for per-turn polling.
- `bash_normalize_cmd`’s BSD/GNU `sed` continuation join (`:a` / `ta` with `N`) is a standard idiom and is appropriate for the repo’s macOS target; no portability defect was identified without executing `sed` on the host.
- Exotic reads (`awk`, `read`, redirection-only, variable indirection) remain documented gaps in `scripts/hook-anti-read-poll.md` and are intentional for a warn-only hook.
