Reviewing branch changes for `--repo` routing and integration risks. Reading the diff and tracing repo-validation paths.
### In-Scope Findings

- **risk-integration** `skills/design/scripts/design-publish.sh:209` — Step 5c resolves and validates `REPO` (argv `--repo` or `resolve-repo.sh` / `gh repo view` at lines 196–202) and forwards it to `design-log-publish.sh`, `render-final-summary.sh`, `upsert-diagrams-comment.sh`, and `tracking-issue-write.sh`, but the `plan-block-write.sh` call on line 209 omits `${REPO:+--repo "$REPO"}`. `plan-block-write.sh` delegates to `named-block-write.sh`, which calls `resolve_repo` on an empty `--repo` and falls back to `gh repo view` from the consumer cwd. On a non-default repo (fork/upstream mismatch, org project board, etc.), the plan can be written to the wrong repository while publish/rename/log paths target the intended one. **Suggested fix:** Forward `${REPO:+--repo "$REPO"}` on the `plan-block-write.sh` invocation (and add a harness assertion that the call includes `--repo` when `REPO` is set).

- **risk-integration** `skills/design/SKILL.md:460-464` — The Step 0b clarify loop runs `plan-block-write.sh` in sub-step 1 before sub-step 2 re-resolves `REPO`, and sub-steps 1 and 4 do not require `${REPO:+--repo "$REPO"}` on `clarify-state.sh`, `plan-block-write.sh`, `clarify-comment-post.sh`, or `clarify-label.sh`. That ordering was already weak; this branch makes it worse by persisting `REPO` into `source-env` only on the `ROUTE=proceed` path via `design-init-runparams.sh` (PLAN_FINDING_5), not on `ROUTE=clarify`. After Step 0b’s first Bash block, later pause-check preludes source `current-design-env` without `export REPO=...`, so the new `${REPO:+--repo "$REPO"}` pause-save forwarding does not bind clarify-only runs even when Step 0b already resolved a non-default repo for the initial `gh issue view`. **Suggested fix:** Persist `REPO` for all routes (e.g. a Step 0b `write-design-current-env.sh` refresh when `REPO` is non-empty, not only inside `design-init-runparams.sh`); move clarify `REPO` resolution before sub-step 1; and document `${REPO:+--repo "$REPO"}` on every clarify `gh` helper in sub-steps 1 and 4.

- **risk-integration** `scripts/design-pause-load.sh:94-107` — The branch threads `${REPO:+--repo "$REPO"}` from `design-route.sh` (which validates `REPO` at `skills/design/scripts/design-route.sh:143`) into `design-pause-load.sh`, but `design-pause-load.sh` itself never validates argv `--repo` before building `gh_repo_args` and calling `gh issue view`. `validate_repo_value` runs only on `MARKER_REPO` / restored pause state (lines 142–147, 272–275), not on the caller-supplied flag. A direct or future caller that skips `design-route.sh`’s validation can pass a malformed `--repo` straight to `gh`. **Suggested fix:** Add the same `validate_repo` helper used in `design-pause-save.sh` / `design-log-publish.sh` immediately after argv parse (before the first `gh issue view`), mirroring the fail-closed `invalid-repo` posture documented in `SECURITY.md` for pause/resume.

### Out-of-Scope Observations

- **risk-integration** `scripts/write-design-current-env.sh:114-117` — `REPO` persistence uses regex-only checks (`^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`) and does not apply the stricter `validate_repo` rules (reject `/*`, `../`, embedded newlines) used at publish/pause entry. In-repo callers that use `design-init-runparams.sh` / `design-publish.sh` are protected today, but a looser writer path could still poison `source-env.sh` and affect awk-based readers such as `_postplan_resolve_repo`. **Suggested fix:** Share one `validate_repo` implementation for all writers/readers, or call the strict validator from `write-design-current-env.sh` before emitting `export REPO=...`.

- **risk-integration** `skills/design/scripts/design-publish.sh:196-202` — After auto-resolving an empty argv `REPO`, the script does not re-run `validate_repo` on the filled value (only explicit `--repo` is validated at line 115). `resolve-repo.sh` self-validates, but the `gh repo view` fallback does not. **Suggested fix:** Call `validate_repo "$REPO"` once after the resolution block whenever `REPO` is non-empty, before any `gh` downstream calls.
