Reviewing the branch diff and commit history for shell-parsing security issues.
### In-Scope Findings

- **security** `scripts/design-pause-save.sh:82-88` — This branch adds argv-first `validate_repo` for `--repo` and persists `REPO` into `source-env.sh` via `design-init-runparams.sh`, but `design-pause-save.sh` still `source`s `$DESIGN_TMPDIR/source-env.sh` before adopting `REPO_ARG`. That contradicts the new awk-only pattern in `skills/design/scripts/design-postplan-emit.sh:193-206`, which explicitly avoids sourcing because it executes arbitrary shell. Anyone who can tamper with a session tmpdir (or plant a malicious `source-env.sh` before pause) gets code execution before `gh` / publish, regardless of the new repo grammar checks. **Suggested fix:** Stop sourcing in the pause path; read only allowlisted keys (`SESSION_ID`, `REPO`, etc.) with the same awk/`%q`-safe parser used in `_postplan_resolve_repo`, or source only after verifying the file was written by `write-design-current-env.sh` (e.g., signature / known writer mtime) and contains nothing except `export KEY=%q` lines.

- **security** `scripts/design-pause-save.sh:191-207` — Publish metadata is parsed with `awk -F= … '{print $2}'` and written into pause state via `printf 'LOG_RECOVERY_BRANCH=%s\n' "$RECOVERY_BRANCH" >> "$state_tmp"` without the newline/CR rejection that `emit_kv` enforces (`scripts/lib-quiet.sh:166-172`). A hostile `design-log-publish.sh` (notably via `LARCH_DESIGN_LOG_PUBLISH`) or corrupted stdout can inject extra `KEY=value` lines into `pause-state.txt` before `redact-secrets.sh`, and that file is posted to the GitHub issue through `named-block-write.sh`. The branch’s FINDING_17 normalization increases reliance on this parse path but does not harden it. **Suggested fix:** Reject values containing newline/CR (same rule as `emit_kv`), or parse publish stdout through a shared KV reader used by `design-publish.sh`’s `parse_kv_from_output`, and only allow `RECOVERY_BRANCH` values matching the known `larch-log-design-*` slug regex before appending to state.

- **security** `skills/design/scripts/design-publish.sh:38-53,325-331` and `skills/design/scripts/render-final-summary.sh:300-314` — `parse_kv_from_output` copies `PR_URL` / `RECOVERY_BRANCH` from publish stdout into `DESIGN_LOG_*` exports and then into operator-facing `final-summary.md` (`printf … %s` for URLs/branches) without scheme or slug validation. This branch amplifies that surface on clarify failed-publish and `failed-publish` outcomes (SKILL Step 0b sub-steps 3/6, `SUMMARY_OUTCOME=failed-publish`). Compromised or mistaken publish output can place attacker-chosen links or branch names into summaries that may be echoed on GitHub issues. **Suggested fix:** Allowlist `PR_URL` to `https://github.com/…/pull/<digits>` (or the repo’s `gh` host) and `RECOVERY_BRANCH` to `^larch-log-design(-recovery)?-[A-Za-z0-9_.-]+$` before exporting `DESIGN_LOG_*` or calling `append_failed_publish_notes`; drop or replace anything else with a redacted placeholder.

### Out-of-Scope Observations

- **security** `skills/design/scripts/design-publish.sh:196-202` — When `--repo` is omitted, `REPO` is filled from `resolve-repo.sh` / `gh repo view` and used in `${REPO:+--repo "$REPO"}` without a second `validate_repo` pass. This predates the publish-honesty work; `resolve-repo.sh` already regex-filters, so risk is low but inconsistent with the new fail-closed `--repo` gates elsewhere.

- **security** `scripts/design-pause-save.sh:176` — `publish_cmd="${LARCH_DESIGN_LOG_PUBLISH:-…}"` lets the environment substitute the publish implementation. That trust boundary existed before this branch; the new contradictory-envelope handling assumes publish stdout shape but cannot constrain a custom publisher.

- The branch’s `validate_repo` additions in `scripts/design-log-publish.sh`, argv precedence in `design-pause-save.sh`, awk-only repo resolution in `design-postplan-emit.sh`, and `${REPO:+--repo "$REPO"}` pause-check forwarding in `skills/design/SKILL.md` are directionally sound for injection and wrong-repo targeting; the gaps above are mostly inconsistent hardening rather than missing validation at the new entry points.
