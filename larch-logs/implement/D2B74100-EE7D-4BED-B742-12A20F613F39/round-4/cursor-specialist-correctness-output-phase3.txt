Based on my thorough analysis of the diff, here are my findings:

### In-Scope Findings

1. - **correctness** `skills/design/scripts/design-postplan-emit.sh:217-229` — `_postplan_pause_checkpoint` writes `POSTPLAN_EMIT_STATUS=paused` to the result env via `_postplan_write_result_and_emit` unconditionally before the repo-validity branch. When `_repo` is non-empty but malformed (e.g. `--bad/repo` from a corrupted source-env.sh), the code skips the `exec` path and instead emits `PAUSE_OK=false; ERROR=invalid-repo` to stdout, but `POSTPLAN_EMIT_STATUS=paused` is already persisted in `.design-postplan-emit-result.env`. The orchestrator parses `POSTPLAN_EMIT_STATUS` from the result env (file-first) and interprets the run as paused-and-resumable, while no pause marker was ever written to the issue. An operator seeing this status would attempt `/design` resume and find no marker. **Suggested fix:** Set `POSTPLAN_EMIT_STATUS=paused` only immediately before the exec paths (valid repo and empty-repo branches), or emit a distinct status like `POSTPLAN_EMIT_STATUS=pause-invalid-repo` when falling through to the error path so the orchestrator can surface the failure accurately.

2. - **correctness** `scripts/design-pause-save.sh:27-47` — `source_env_get`'s awk script handles single-quoted (`'...'`) and double-quoted (`"..."`) values by stripping the outer quotes, but does not handle the `$'...'` quoting style that `printf '%q'` produces for values containing shell-special characters. If `write-design-current-env.sh` ever writes a `SESSION_ID` or `REPO` value containing characters like `!` or `%`, the awk would return the raw `$'...'`-prefixed string rather than the decoded value, causing `validate_repo` or the `RUN_ID` derivation to see garbage. In practice today both fields are restricted to alphanumeric/hyphens/slashes so the issue is dormant; however the contract says `printf '%q'` is used for values in source-env.sh. **Suggested fix:** Add a third branch in the awk quote-stripping block: `(substr(v,1,2) == "$'" && substr(v,length(v),1) == "'")` — or document that `source_env_get` only handles simple quoted/unquoted values and is not `printf '%q'`-safe for values with special characters.

3. - **correctness** `skills/design/scripts/design-publish.sh:281-340` — The `sanitize_publish_metadata` helper calls `validate_recovery_branch`, which calls `git check-ref-format --branch` at runtime. If `git` is absent from `PATH` (e.g., inside a restricted container or CI step) the call silently returns non-zero, causing `RECOVERY_BRANCH` to be cleared before it is logged in the `add_warn` call or written to `DESIGN_LOG_RECOVERY_BRANCH`. An operator who hits a publish failure in such an environment loses the recovery branch pointer entirely. `render-final-summary.sh` has the same issue (pre-existing), and this diff adds a second `validate_recovery_branch` call in `design-publish.sh`. **Suggested fix:** In both `sanitize_publish_metadata` and `sanitize_failed_publish_notes`, treat `git check-ref-format` failures as "pass" (keep the value) rather than "reject" (clear it) when git is unavailable — or check `command -v git` first and only call `git check-ref-format` when git is present.

4. - **correctness** `scripts/test-design-log-publish.sh:374-393` — The malformed-repo test loop iterates `for bad_repo in --owner/repo 'owner\repo' ../repo` but the loop does **not** include `bad..repo` or `a/b/c`, which the plan's FINDING_11 section explicitly names as required test values. `bad..repo` tests the `..` case in the owner component (different from `../repo`), and `a/b/c` tests extra-slash multi-component repos. The existing `../repo` and `/abs` cases in the earlier test cover some invalid shapes, but the plan acceptance criterion states these specific values. **Suggested fix:** Add `bad..repo` and `a/b/c` to the bad-repo loop, or confirm the earlier block (which tests `/abs`) is accepted as a substitute for the plan's explicit list.
