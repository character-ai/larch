Reviewing the branch diff and commit history, then inspecting summary-renderer changes for correctness.
### In-Scope Findings

- **correctness** `skills/design/SKILL.md:1549-1555` — Step 5d routes `publish-skipped` runs (empty `SESSION_ID`, `SUMMARY_OUTCOME=publish-skipped` in the rendered summary) through the same success footer as a completed publish: `➡️ 5: finalize — plan written to issue #<N>; NEXT REQUIRED: continue`. That contradicts the FINDING_4 fix: the summary honestly says publish was skipped, but the last machine line reads like a normal successful finalize. Operators can miss that run logs were never flushed. **Suggested fix:** Add a third footer branch for `publish-skipped` (or whenever `SESSION_ID` is empty after Gate C), e.g. `plan written; run-log publish skipped (no SESSION_ID); NEXT REQUIRED: continue`, and keep the success footer only when publish actually succeeded (`PUBLISH_OK=true`).

- **correctness** `skills/design/scripts/render-final-summary.sh:357-390,435-450` — Primary and degraded paths disagree on where outcome-specific notes land. `invoke_render` feeds `publish-skipped` / `failed-publish` notes through `--note-lines-file`, and `scripts/render-run-summary.sh:256-262` appends them **after** `<!-- larch:run-summary v=1 -->` (the harness enforces that ordering for `cancelled-outline` at `skills/design/scripts/test-render-final-summary.sh:54-57`). `compose_self_fallback` prints the same notes **before** Plan review / Run logs and **before** the sentinel. A renderer failure therefore changes note placement, not just the degraded banner. **Suggested fix:** In `compose_self_fallback`, emit the standard bullet block and `<!-- larch:run-summary v=1 -->` first, then append publish-skipped / failed-publish notes (mirror `render-run-summary.sh`), then emit `<!-- larch:final-summary-fallback v1 -->`; extend `test-render-final-summary.sh` with the same post-sentinel line-order assertion used for `cancelled-outline`.

- **correctness** `skills/design/scripts/render-final-summary.sh:357-358,437-438` — The `publish-skipped` note is always `no SESSION_ID / run-log`, but callers may pass a real `--run-id` while still using outcome `publish-skipped` (see `scripts/test-render-run-summary.sh:402-425`). Run logs correctly stay `N/A`, yet the Publish note can falsely claim there was no session id. **Suggested fix:** Gate the note on `RUN_ID` / `SESSION_ID` (e.g. “publish skipped — run log not flushed” when `RUN_ID` is set, keep the SESSION_ID wording only when `RUN_ID` is `unknown`), or reject `publish-skipped` with a non-`unknown` run id at enum validation time.
