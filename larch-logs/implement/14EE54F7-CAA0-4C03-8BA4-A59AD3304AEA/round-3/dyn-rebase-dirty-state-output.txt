Tracing the post-rebase verify-failure path and reading the branch diff.
### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:1870-1939,1947-1950,2406-2423` — Post-rebase verification (`_verify_failed_jobs_locally` / `run_checks_with_lint_fix_loop`) lives entirely inside `if [ "$behind" -gt 0 ]`. After a deferred rebase succeeds, the next `_stage_and_push_ci_fixes` call almost always sees `BEHIND_COUNT=0`, so the re-verify block is skipped while `CI_FIX_REBASE_PENDING=true` still forces `git-force-push.sh`. That violates the plan’s “never push an unverified tree” gate: a pending retry can force-push a locally rebased branch without re-running failed-job verification (only the upfront `run_checks_with_lint_fix_loop` at 1818–1821 runs). The TSV guard at 1882–1887 is inside the same `behind > 0` block, so it never fires on the common pending-retry path. **Suggested fix:** Factor post-rebase re-verify into a helper invoked whenever `CI_FIX_REBASE_PENDING=true` or `did_rebase=true` on this call, independent of `behind`; require `effective_failed_jobs_tsv` before push; only clear the pending flag after verify passes and push succeeds.

- **correctness** `scripts/ship-pr.sh:1962,1886,1956` — Successful push ends with `_ci_fix_rebase_pending_set false`, but that function is not defined anywhere in the repo (only three call sites exist). Under `set -uo pipefail` without `set -e`, Bash logs “command not found” and leaves `CI_FIX_REBASE_PENDING=true` after an otherwise successful push. Later `_stage_and_push_ci_fixes` calls with `did_rebase=false` can still take the force-push branch (1947–1948), and `run_evaluate_failure` keeps treating the run as pending (2406, 2470, 2566). **Suggested fix:** Either define `_ci_fix_rebase_pending_set` (if persistence was intended) or replace all three calls with direct `CI_FIX_REBASE_PENDING=true/false` assignments matching the diff’s original `CI_FIX_REBASE_PENDING=false` at push success.

- **risk-integration** `scripts/ship-pr.sh:1894-1933,1818-1821` — On post-rebase verify failure (`verify_rc=4` or non-zero lint), the function sets `CI_FIX_REBASE_PENDING` and returns without staging commits from the `verify_rc=0` branch (1905–1922), leaving per-job / lint-fix working-tree deltas uncommitted on the rebased HEAD. The pending-only retry at 2406–2409 re-enters `_stage_and_push_ci_fixes` and immediately runs `run_checks_with_lint_fix_loop` again on that dirty tree before any job re-verify, which can double-apply lint fixes or produce a different delta than the aborted first pass. **Suggested fix:** On failed post-rebase verify, either commit/stash the captured lint delta before returning, or on pending retry skip the upfront lint loop and re-run only the gated post-rebase verify + targeted staging path; avoid treating aborted-verify dirt as a fresh vendor baseline.

### Out-of-Scope Observations

- **risk-integration** `scripts/ship-pr.sh:2061-2066,2508-2511` — When `run_ci_fix_vendor` returns `4` from pre-push `_verify_failed_jobs_locally` (before `_stage_and_push_ci_fixes`), `CI_FIX_REBASE_PENDING` is not set; the next outer attempt can call `run_ci_fix_vendor` again with a new baseline that includes the prior attempt’s uncommitted verify deltas, and `_ci_fix_rollback` (1733–1777) will preserve those paths across tier failures. That is adjacent to the scout prompt but not introduced by the deferred-rebase path (which correctly avoids re-entering the vendor waterfall while pending).

- **architecture** `scripts/test-ship-pr.sh:5261-5367` — `ci_fix_no_double_rebase_pending_retry` asserts no second rebase when `BEHIND_COUNT=0` on retry, but does not assert that `_verify_failed_jobs_locally` runs on the pending retry; the harness can pass while the production gap above remains.
