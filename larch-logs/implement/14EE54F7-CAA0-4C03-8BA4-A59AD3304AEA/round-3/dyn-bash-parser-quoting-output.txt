### In-Scope Findings

- **correctness** `scripts/ship-pr.sh:1870-1939,1947-1951` — Post-rebase verification (`_verify_failed_jobs_locally` and `run_checks_with_lint_fix_loop`) runs only inside `if [ "$behind" -gt 0 ]`. After a deferred rebase succeeds, `BEHIND_COUNT` is typically 0 on the next `_stage_and_push_ci_fixes` call, but `CI_FIX_REBASE_PENDING` still forces `git-force-push.sh`. That retry path can force-push without re-running failed-job or lint gates, which conflicts with the acceptance criterion that an unverified tree must never be pushed. The `ci_fix_no_double_rebase_pending_retry` harness in `scripts/test-ship-pr.sh` encodes this gap (lint fails once post-rebase, then push succeeds on retry with `BEHIND_COUNT=0`). **Suggested fix:** Extract post-rebase verify into a helper and call it whenever `did_rebase=true` **or** `CI_FIX_REBASE_PENDING=true`, even when `behind=0`; only skip the `run_rebase_rebump` call when already current.

- **correctness** `scripts/ship-pr.sh:1870-1872,2886-2890` — For `FORKED_TARGET=true`, the CI-fix path calls `run_rebase_rebump … defer-push upstream main` (rebase onto `upstream/main`), but `_run_rebase_rebump_from_step3` still runs `git-sync-local-main.sh` with no `--base-remote/--base-ref` and the version-regression guard still reads `origin/main:.claude-plugin/plugin.json`. Rebump classification can therefore use the wrong merge base on fork flows—the first time full `run_rebase_rebump` is used for fork CI-fix in this change. **Suggested fix:** Thread `base_remote`/`base_ref` into `git-sync-local-main.sh` and the version-regression lookup (e.g. `git show "${base_remote}/${base_ref}:.claude-plugin/plugin.json"`), matching `rebase-push.sh`.

- **correctness** `scripts/hook-anti-read-poll.sh:87-114,130-138` — `bash_line_task_output_poll_token` splits on literal `;`, `&&`, and `||` without respecting quotes, so operators inside quoted strings fracture segments (e.g. `echo 'foo||bar' || cat tasks/id.output` becomes segments like `echo 'foo` and `bar' || cat …`). Detection often still works for simple `;`-then-`cat` patterns, but the model is fragile. **Suggested fix:** Either document this as best-effort and add harness cases for quoted-operator edge cases, or replace the splitter with a quote-aware scanner (even a small state machine over `'"`\`).

- **correctness** `scripts/hook-anti-read-poll.sh:53-61,77-84,130-138` — Poll detection only treats `cat|tail|head|less|more` and a narrow `sed -n` pattern as read verbs; paths reached via `$var`, `read`, `awk`, `python`, etc. are false negatives. Example: `TASK=tasks/foo.output; cat "$TASK"` — `extract_task_output_token` greps the literal segment and finds no `tasks/…` token. **Suggested fix:** Expand verb coverage conservatively and/or resolve simple `"$VAR"` expansions when the assignment appears earlier in the same line; at minimum document unsupported shapes in `scripts/hook-anti-read-poll.md`.

- **correctness** `scripts/hook-anti-read-poll.sh:87-112,117-126` — `bash_line_task_output_poll_token` returns the first segment that matches, while `extract_bash_task_output_poll_token` only considers the first line of a multiline command. A single invocation like `cat tasks/A.output; cat tasks/B.output` only ever keys off `A`, so alternating reads of two task outputs can under-count (false negative for the anti-poll goal). **Suggested fix:** Either scan all segments (and optionally all lines) and increment counters per distinct `tasks/<id>.output` token, or document that only the leftmost qualifying segment per Bash invocation is tracked.
