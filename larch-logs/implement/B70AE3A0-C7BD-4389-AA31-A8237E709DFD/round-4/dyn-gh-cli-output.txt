Reviewing the branch diff and git history, focusing on GitHub CLI integration around PR creation and recovery.
### In-Scope Findings

- **risk-integration** `python/gh.py:334-336` — `_repo_matches_pr_url` hardcodes `github.com/{repo}/pull/`, so URL-based PR recovery rejects valid PR URLs on GitHub Enterprise or any non-`github.com` host even when `gh pr create`/`gh pr view --repo` succeed under `GH_HOST`. That is stricter than bash recovery (`create-pr.sh` greps any `https?://…/pull/N`) and unlike `python/oos.py:45-54`, which already honors `GH_HOST` for GitHub URL matching. On GHE, a successful create with a stdout URL can still end in `ShipError("…could not be resolved")` and STALLED exit 4. **Suggested fix:** Build the repo URL needle from `GH_HOST` (default `github.com`), mirroring `_github_issue_url_pattern()` in `python/oos.py`, and add a stub test with a non-`github.com` host plus fixture URL to lock the behavior.

- **risk-integration** `python/gh.py:351-371,509-518` — Post-create resolution now requires a single immediate `pr_view` inside `_validate_recovered_pr` for every stdout/stderr URL fallback. A transient “not found” / non-retryable `ShipError` from `pr_view` right after `gh pr create` rc=0 is swallowed and treated as “unresolved”, even when stdout already contains a valid PR URL and `pr list` is empty due to index lag (the soak scenario #3/#5 family). Bash parity (`scripts/create-pr.sh:315-321`) accepts the create stdout URL without an extra view call. **Suggested fix:** Poll `pr_view` with bounded backoff (reuse an existing retry constant or add a dedicated one) before giving up on URL recovery, and/or treat rc=0 + repo-matching stdout URL as sufficient when list lag persists; add a regression test where list stays empty and the first one or two `pr_view` calls fail before succeeding.

- **risk-integration** `python/test_gh.py:404-424` — The acceptance “real-CLI/recorded-transcript” gate for dropping `--json` is only a one-line URL fixture replayed through `RecordingRunner`; it does not exercise representative real `gh pr create` stderr/prose, multi-line output, or argv capture against the actual `gh` binary. Stub tests already cover the happy path, so a future reintroduction of unsupported flags or a change in gh’s human-readable output format could slip through CI. **Suggested fix:** Commit a fuller recorded transcript (stderr + stdout as gh 2.92 emits) and/or add a `pytest.mark.skipif` subprocess test that runs `gh pr create --help` or a dry-run harness to assert `--json` is absent from the constructed argv when real `gh` is on PATH.

### Out-of-Scope Observations

- **code-quality** `python/gh.py:237-266` — `pr_view_current` / `pr_view_current_read` were added in this branch but are unused after round 3 removed the `pr_view_current` fallback from `pr_create`; dead surface that may confuse future recovery work.

- **risk-integration** (pre-existing) `python/pr.py:67-74` — `ensure_pr` calls `gh.pr_create` without a `--base`, unlike `scripts/create-pr.sh:269-274`, which resolves the repo default branch before create. Not introduced by this diff, but it remains a bash/Python parity gap for repos whose default branch is not `main`.
