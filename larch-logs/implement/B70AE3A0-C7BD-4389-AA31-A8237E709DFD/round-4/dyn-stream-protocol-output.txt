Reviewing the branch diff and stream-protocol implementation for stdout/stderr/quiet-mode behavior.
### In-Scope Findings

- **architecture** `python/logging_util.py:54-57` — In quiet mode, `BreadcrumbWriter.emit` sets `routed = True` unconditionally after the `os.write(4, …)` attempt (errors suppressed via `contextlib.suppress`), then returns without ever writing to `sys.stderr` when `routed or quiet is True`. If `LARCH_QUIET_ACTIVE` and `LARCH_QUIET_PID` are set but `LARCH_QUIET_LOG_FILE` is empty/unwritable and FD 4 is not the lib-quiet breadcrumb channel (common for a bare `python3 …/ship.py` child that never ran `larch_quiet_init`), ship-phase and CI poll breadcrumbs are dropped entirely instead of falling back to stderr. That regresses the pre-branch behavior (always wrote to stderr unless `quiet=True`) and directly conflicts with the scout goal that progress must not “disappear unexpectedly under quiet mode.” **Suggested fix:** Only set `routed = True` when a destination actually succeeds (log append and/or a successful FD 4 write); on quiet-mode routing failure, fall through to `sys.stderr` (or mirror bash `larch_err` semantics). Add a harness case: quiet env active, no log file, invalid FD 4 → breadcrumb still visible on stderr.

- **architecture** `python/run_logs.py:948-964` — `_warn_secret_scrub` still writes its multi-line security banner with raw `sys.stderr.write`, bypassing `BreadcrumbWriter` and lib-quiet’s FD 4 / quiet-log routing. Ship-path flush now hits this more often (volatile-only / pre-commit scrub in `_larch_log_commit`), so under a quiet session (redirected stderr) operators can miss “rotate credentials” warnings that bash ship progress gets via `larch_err` on FD 4. Stdout JSON remains clean, but stderr-side observability is split across two incompatible channels. **Suggested fix:** Route scrub banners through `BreadcrumbWriter().emit(...)` (or a shared diagnostic helper that uses the same quiet/FD 4 contract as `ci_monitor._warn_stderr`); reserve raw `sys.stderr` only for pre-quiet bootstrap or document that ship.py must not run inside quiet until wrapped.

- **architecture** `skills/implement/SKILL.md:1003-1041` — The Python driver is invoked directly (`python3 …/ship.py`) and never enters `scripts/ship-pr.sh`’s `larch_quiet_init` (line ~3134), while the branch wires breadcrumbs through `logging_util` assuming lib-quiet parity. In the default `/implement` path this means progress goes to real stderr (acceptable for #6), but any caller that exports `LARCH_QUIET_*` without duplicating FD 3/4 setup hits the silent-drop path above; bash and Python observability contracts diverge. **Suggested fix:** Either add a thin `scripts/ship-py.sh` wrapper that runs `larch_quiet_init` then execs `python/ship.py` (matching report-tokens), or document that Python ship ignores quiet unless wrapped and make `BreadcrumbWriter` fail-open to stderr when quiet routing cannot deliver.

### Out-of-Scope Observations

- **Pre-existing:** `ship.py` `main()` only guarantees JSON on stdout for exceptions caught in its broad `except Exception`; `argparse` failures and other early exits can still yield non-JSON stdout with a non-contract exit code — not introduced by this branch’s breadcrumb work.
- **Pre-existing:** `python/version_bump.py:421` also uses direct `sys.stderr.write` for bump warnings; same quiet-routing gap as `_warn_secret_scrub`, but not part of the new breadcrumb/CI-monitor changes.
- **Positive (no issue):** `emit_result` remains the sole `print()` to stdout; `proc.run` captures subprocess stdout/stderr; `test_ship.py` and `test_ci_monitor.py` pin JSON-on-stdout / breadcrumbs-on-stderr; the SKILL’s Python &lt; 3.11 guard emits JSON on stdout before exit 4, preserving the Step 8+ machine contract.
