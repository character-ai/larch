Reviewing the branch diff with focus on run-log volatile-only cleanup and git porcelain safety.
### In-Scope Findings

- **risk-integration** `python/run_logs.py:549-564` — `flush_logs_pre` always calls `_render_token_timing_batches` before `_larch_log_commit`, and that helper appends to `token-report.ndjson` (and rewrites `timing-report.ndjson`) via `tokens.scrape_run` whenever sidecar JSON exists (`python/run_logs.py:630-658`, `python/tokens.py:109-110`). Those canonical batch files are intentionally excluded from the volatile allowlist (`python/run_logs.py:804-811`), so a typical live `/implement` run with Codex/Cursor/Claude sidecars will still dirty non-volatile paths on every pre-push refresh even when only `*-refresh.json` / `session-transcript-refresh.txt` churn. The new volatile-only skip then never runs, and `flush_logs_pre` can still emit `chore(larch-logs): flush` commits on the CI/rebase loop path in `python/ship.py:413-419`. That partially undermines O1/#7: removing `merge_pr`'s pre-merge flush fixes the merge-time infinite loop, but pre-rebase refreshes can still diverge HEAD from the green PR OID when token totals tick upward. **Suggested fix:** Treat refresh-time NDJSON updates separately from substantive canonical commits—e.g. skip `append_token_record` when the normalized record is unchanged, gate `_render_token_timing_batches` during refresh so NDJSON is not republished unless totals changed, or extend the classifier with an explicit refresh-mode rule—so “refresh sidecar only” porcelain can actually reach the volatile-only cleanup path under real sidecars.

- **risk-integration** `python/run_logs.py:875-880` — `_cleanup_volatile_run_tree` uses `has_staged` to run `git reset HEAD -- <rel>` for any index-column change under the scoped run tree, but `reset` is scoped to the entire `larch-logs/implement/<run_id>/` directory, not just the volatile paths being cleaned. On the intended volatile-only path this is usually harmless because classification requires all porcelain under `rel` to be allowlisted refresh sidecars, yet any future broadening of the allowlist or a classifier bug that mis-labels a tree as volatile-only while a staged non-volatile file remains under `rel` would be reset-unstaged repo-wide under that prefix before per-path `restore`/`clean`, which is a wider blast radius than the narrow refresh contract documents. **Suggested fix:** Reset and restore only the volatile path list (or run `git restore --staged --worktree` per path) instead of `git reset HEAD -- <rel>`, and add a regression test that stages a non-volatile file under the same run tree and proves volatile-only cleanup does not leave it staged or dirty.

Worth tightening when touching cleanup, but not introduced by the AM path itself.
