### In-Scope Findings

- **risk-integration** `python/logging_util.py:30-49` — `BreadcrumbWriter.emit` treats `LARCH_QUIET_ACTIVE` alone as “quiet mode,” but `scripts/lib-quiet.sh` deliberately does **not** redirect when `LARCH_QUIET_ACTIVE=1` and `LARCH_QUIET_PID` is unset (stray export / unbound session). The `/implement` Python path invokes `python/ship.py` directly (no `larch_quiet_init`), so a leaked `LARCH_QUIET_ACTIVE=1` is plausible. In that case all breadcrumbs with `quiet=None` skip `sys.stderr`, only append to `LARCH_QUIET_LOG_FILE` when set, and otherwise rely on `os.write(4, …)` inside `suppress(OSError)`—which fails silently when FD 4 was never dup’d—recreating the soak’s “long silent intervals” despite #6. `config.ENV_LARCH_QUIET_PID` is defined but unused in this module. **Suggested fix:** Mirror the bash guard: treat quiet routing as active only when `LARCH_QUIET_ACTIVE` is set **and** `LARCH_QUIET_PID` is non-empty (and optionally when `os.getpid() != int(LARCH_QUIET_PID)` for inherited FD-4 children). On `os.write(4, …)` failure, fall back to `sys.stderr` instead of swallowing; add a regression test in `python/test_logging_util.py` and/or `python/test_ship.py` for `ACTIVE=1` + empty `PID` + no log file.

- **risk-integration** `python/ship.py:354,588-589` — `write_final_report_comment` warnings and the `main()` unexpected-exception path use raw `sys.stderr.write` / `traceback.print_exc`, bypassing `BreadcrumbWriter`. Phase progress uses the writer (with quiet routing), so under a bound quiet parent (valid FD 4) or the stray-`ACTIVE` case above, operators can see `ship.py: warning:` / tracebacks on process stderr while phase/`ci_monitor` breadcrumbs vanish or land only in the quiet log—split observability channels and inconsistent with `scripts/lib-quiet.md` (operator-visible progress on FD 4 via `larch_err`). **Suggested fix:** Route those diagnostics through `BreadcrumbWriter` or a shared helper that applies the same quiet/FD-4/stderr policy as breadcrumbs.

- **risk-integration** `python/run_logs.py:963-964` — `_warn_secret_scrub` still writes its multi-line banner directly to `sys.stderr` while in-loop flush paths now depend on `BreadcrumbWriter` for progress; the O1 volatile-only / fail-closed flush work makes this banner more likely during ship. Under the same quiet-env combinations as above, a secret-scrub event may not reach the operator-visible FD 4 channel. **Suggested fix:** Emit the banner through `logging_util.BreadcrumbWriter` (or duplicate the FD-4 write + stderr fallback used there) so scrub warnings follow the same routing contract as ship/CI breadcrumbs.

- **risk-integration** `python/test_ship.py:263-318` — Tests pin JSON-on-stdout and breadcrumbs on stderr in default (non-quiet) capsys runs, but there is no integration test that `LARCH_QUIET_ACTIVE=1` with an empty `LARCH_QUIET_PID` (lib-quiet “stray export”) still delivers breadcrumbs to stderr, nor that a child with inherited FD 4 receives breadcrumbs on FD 4. That leaves acceptance #6 / quiet-contract parity unguarded against the main regression above. **Suggested fix:** Add cases alongside `python/test_logging_util.py:test_breadcrumb_routes_to_quiet_log_when_active` covering `ACTIVE`+missing `PID`, failed FD 4, and (if harness can dup FD 4) inherited quiet-child behavior.
