Reviewing the branch diff and `gh.pr_create` recovery flow for correctness issues.
### In-Scope Findings

- **correctness** `python/gh.py:411-429` — On the post-create success path, `_recover_pr_from_create_output` treats any non-empty `stdout_urls` as terminal: it returns whatever `_recover_pr_from_urls` yields and never consults `stderr`, even when every stdout URL fails `_validate_recovered_pr` (wrong repo substring, wrong `headRefName`, closed state, or transient `pr_view` failure). That can turn a successful `gh pr create` into `ShipError("…could not be resolved")` when the real PR URL is only on stderr (warnings/progress on stdout are common). The conflict path is fine because it uses `_combined(result)`; this gap is specific to the stdout/stderr split on `returncode == 0`. **Suggested fix:** After `_recover_pr_from_urls` on stdout URLs, if the result is `None` and `stderr_urls` is non-empty, run the same recovery on stderr; only prefer stdout when it yields a validated PR (mirror `test_pr_create_prefers_stdout_url_over_stderr` intent without blocking stderr fallback).

- **correctness** `python/gh.py:506-511` — When `pr_for_branch` succeeds immediately after create, the PR is returned with `created=True` without `_validate_recovered_pr` (no `pr_view` head-ref/state check). URL-based recovery is validated; list-based recovery is not. If `gh pr list --head …` returns a stale or mismatched row while create output carried a different PR number, ship state can bind to the wrong PR while still reporting a fresh create. **Suggested fix:** Run the same `_validate_recovered_pr` helper on the list result before returning `(recovered, True)`, or re-resolve via `pr_view` on the listed number and compare `head_ref`/`state` to `branch`.

### Out-of-Scope Observations

- **correctness** `python/test_gh.py` — Coverage is strong for happy paths, stderr-only URL lag, stdout-over-stderr when both validate, and the recorded fixture gate for no `--json`, but there is no test where stdout contains a matching-regex URL that fails validation while stderr holds the real PR URL; that case would have caught the `_recover_pr_from_create_output` early-return behavior above.

- **risk-integration** `python/gh.py:340-342` — `_repo_matches_pr_url` requires a `github.com/{repo}/pull/` substring, so GitHub Enterprise hosts will not resolve via URL recovery (may be acceptable if larch only targets github.com).

- **architecture** `python/test_gh.py:358-379` — The “real-CLI/recorded” acceptance gate is satisfied by a committed stdout fixture, not a live `gh` invocation; flag reintroduction is still caught, but CLI drift in non-transcript fields would not be.
