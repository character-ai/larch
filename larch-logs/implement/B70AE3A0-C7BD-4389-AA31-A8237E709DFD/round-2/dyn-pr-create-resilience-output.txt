Reviewing the `pr_create` rewrite and its fallback chain for correctness issues.
### In-Scope Findings

- **correctness** `python/gh.py:413-415` — On the post-success path, URL recovery calls `_recover_pr_from_conflict_text(_combined(result), …)` where `_combined` is `stdout + stderr` and the helper selects `matches[-1]`. When both streams contain different `/pull/N` URLs, the stderr URL wins even if stdout carries the newly created PR link. That diverges from bash `create-pr.sh`, which parses stdout only on the success path, and can resolve the wrong PR number with `created=True`. **Suggested fix:** Resolve stdout first (e.g. call `_recover_pr_from_conflict_text(result.stdout, …)` and only fall back to stderr when that returns `None`), or explicitly prefer the last stdout URL before scanning stderr; add a regression test with rc=0, a create URL on stdout, and a different PR URL on stderr.

- **correctness** `python/gh.py:340-353,413-415` — `_recover_pr_from_conflict_text` never validates that the parsed URL belongs to `branch`; it fabricates `head_ref=branch` and hardcodes `state="OPEN"`. Any spurious `/pull/N` match in create output (warning text, copy-paste, multiple links) is returned as the created PR with `created=True`, with no `gh pr view`/`pr_for_branch` confirmation. **Suggested fix:** After extracting a candidate URL/number, confirm via `pr_for_branch` or `pr_view(number)` that `headRefName` matches `branch` (normalize `owner:branch` vs bare branch) and `state` is `OPEN` before returning; only then set `created=True`.

- **correctness** `python/gh.py:416-421` — The new `pr_view_current` fallback returns a PR whenever `recovered.head_ref == branch` but does not check `recovered.state == "OPEN"`. If `gh pr view` (cwd-scoped, no explicit `--head`) returns a closed/merged PR whose `headRefName` still equals the feature branch, `pr_create` reports `created=True` for a non-mergeable PR. **Suggested fix:** Require `recovered.state == "OPEN"` (or re-fetch via `pr_for_branch`) before accepting the `pr_view_current` result; treat closed/merged as unresolved and continue to `ShipError`.

### Out-of-Scope Observations

- **correctness** `python/gh.py:407-410,394-397` — The scout’s exception-handling concern is handled correctly: `ShipError`/`TransientNetworkError` from post-create `pr_for_branch` set `recovered = None` and the chain continues rather than re-raising.

- **correctness** `python/gh.py:391-405 vs 407-424` — Success and conflict recovery paths are mutually exclusive by `returncode`; a successful create cannot accidentally consume conflict stderr from a prior branch in the same call.

- **correctness** `python/gh.py:420-421` — For the “multiple closed + one open PR on the same branch” case, the guard is sufficient in normal larch flow: initial `pr_for_branch` is `--state open`, and `pr_view_current` is scoped to the checked-out branch via `cwd`. Residual risk is qualified `headRefName` values (`owner:branch`) not matching bare `branch`, which would false-negative to `ShipError` rather than return the wrong PR; current `--head` usage passes the short branch name only.

- **correctness** `python/gh.py:368-370,399-405,412-421` — `created` semantics are correct: existing/conflict paths return `False`; all three post-success resolution paths return `True`.
