Reviewing the branch diff and ship driver stream contract (stdout JSON vs stderr breadcrumbs).
### In-Scope Findings

- **architecture** `python/ship.py:580-587` — `main()` always calls `emit_result()` only when `run_ship()` returns normally; any uncaught exception (`ValueError`, `KeyboardInterrupt`, etc.) bypasses `emit_result()` and leaves stdout without the single JSON object the `/implement` Python selector contract requires (while stderr gets a traceback). `_error_to_result()` maps `ShipError` to `STALLED`, but that path is only reached via the narrow `except` at `run_ship` lines 492–493, not for unexpected failures at the process boundary. **Suggested fix:** Wrap `run_ship` + `emit_result` in `main()` with a top-level handler that maps unexpected failures to a `ShipResult(Outcome.STALLED, …)` (or a dedicated bail outcome) so stdout always receives exactly one JSON line before exit, matching acceptance for operational/error routing and bash exit-code parity.

- **architecture** `python/ship.py:100-103` and `python/logging_util.py:26-35` — Progress output uses a new ad-hoc `_breadcrumb()` that writes directly to `sys.stderr`, while the tree already defines `logging_util.BreadcrumbWriter` (stderr stream, optional quiet suppression via `LARCH_QUIET_DISABLE`). `ci_monitor.py` adds a third channel via `_warn_stderr()`. The split means there is no single module-level stream contract (prefix, quiet behavior, flush semantics), and ship progress cannot be suppressed consistently with other Python observability helpers. **Suggested fix:** Route ship phase lines through `BreadcrumbWriter` (or a thin shared `progress.py` wrapper used by both `ship.py` and `ci_monitor.py`) so stderr breadcrumbs share one API and quiet policy; keep `emit_result()` as the sole stdout writer.

- **architecture** `python/test_ship.py:255-281` and `python/test_ship.py:81-170` — Stream-contract regression coverage is thin: `test_main_emits_json_stdout_and_breadcrumb_stderr` mocks `run_ship` and manually calls `_breadcrumb`, so it does not prove real phase breadcrumbs or CI poll lines during `run_ship`; `test_happy_path_stage_order` asserts call order only and never captures stdout/stderr. `test_poll_ci_emits_poll_breadcrumb_to_stderr` and `test_emit_result_prints_json` are isolated. There is no test that `main()` → real `run_ship` (merge path with `poll_ci`) leaves stdout as a single JSON line with all progress on stderr, including on `ShipError`/`STALLED` paths. **Suggested fix:** Add capsys integration tests: (1) happy-path `main()` with monkeypatched phases through `monitor`/`poll_ci` asserting `captured.out` is one JSON line and stderr contains `ship.py:` / `ci_monitor:` markers; (2) `main()` after a `ShipError` from `run_checks_phase` asserting exit 4, JSON `outcome == "STALLED"`, and no traceback-only failure mode on stdout.

### Out-of-Scope Observations

- **architecture** `python/ship.py:354` — The `write_final_report_comment` warning uses a one-off `sys.stderr.write("ship.py: warning: …")` instead of `_breadcrumb()`, so warning lines do not share the same formatting contract as phase breadcrumbs (minor consistency; still stderr-only).

- **architecture** `skills/report-tokens/scripts/run-analysis.sh:2578-2582` — Report-tokens explicitly restores FD 1/2 after lib-quiet so Python CLI output stays visible; the Python ship driver has no analogous quiet-session handling. That may be intentional for #6 (visible CI progress), but it is a behavioral difference from bash `ship-pr.sh` + `larch_quiet_init`, not introduced as a regression in the ship stream split itself.
