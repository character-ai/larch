Reviewing the branch diff and run-log flush changes for risk-integration issues.
### In-Scope Findings

- **risk-integration** `python/run_logs.py:864-906` — Volatile-only cleanup decides what to `git restore` from a **pre-reset** porcelain snapshot and explicitly skips any line whose first two columns contain `A` (`"A" not in line[:2]`). For an indexed add plus worktree edit (`AM` on a refresh sidecar—plausible after publish/scrub), `git reset HEAD -- rel` clears the index but leaves the worktree modified, `restore` is never run for that path, and `git clean -fd` does not remove tracked modifications. The fail-closed repo-wide `git status` then raises `ShipError` (“dirty porcelain”), so a merge-loop flush that was meant to be a no-op can STALL the ship (exit 4) instead of converging. **Suggested fix:** After `git reset`, re-read porcelain (or always `git restore --worktree --staged --source=HEAD` for every path in `volatile_paths`, including `AM`/`A ` rows), then run `clean` only if still needed; keep the repo-wide empty-porcelain gate.

- **risk-integration** `python/run_logs.py:968-992` — The volatile-only path runs **after** `_scrub_run_tree` on the published repo tree. For tracked refresh sidecars that are classified volatile-only, `_cleanup_volatile_run_tree` restores them to `HEAD`, undoing in-worktree redactions from the pre-flush scrub gate without committing scrubbed content. That is usually safe (unpublished secret is dropped), but if `HEAD` already contains a refresh sidecar with a secret-shaped value, a volatile skip returns success while leaving the committed tree unredacted and skipping the flush commit that would have fixed it. **Suggested fix:** Either run volatile classification before scrub (and only scrub when committing), or after scrub treat any `SECRET_SCRUB_VIOLATIONS > 0` as non-volatile (force commit or fail-closed) so redactions on refresh sidecars cannot be reverted by `restore`.

### Out-of-Scope Observations

- **risk-integration** `scripts/larch-log.sh:550-567` — Bash `larch-log.sh` still always `git add` + commit under `rel` with no volatile-only classify/restore path. Python now skips refresh-only churn; bash parity is unchanged on this branch, so behavior diverges until bash gains the same contract (not a regression in bash, but an integration gap for mixed `LARCH_SHIP_PR_IMPL` environments).

- **risk-integration** `python/run_logs.py:628-656` — `_render_token_timing_batches` overwrites `token-report.ndjson` / `timing-report.ndjson` on each `flush_logs_pre` when sidecars exist; those basenames are correctly excluded from the volatile allowlist, so many real pre-push refreshes will still produce a flush commit even when only refresh JSON churn was the motivation for O1. That limits how often volatile-only activates during CI retry loops, but matches the plan’s “substantive canonical/ndjson must commit” rule rather than a cleanup bug.
