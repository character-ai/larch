Reviewing the branch diff and gh CLI integration changes.
### In-Scope Findings

- **risk-integration** `python/test_gh.py:261-273`, `python/fixtures/gh-pr-create-success.txt` — Acceptance #3 / FINDING_3 calls for a real-CLI or recorded-transcript gate so unsupported `gh` flags and real stdout behavior are caught; the branch adds `gh-pr-create-success.txt` and `test_pr_create_recorded_gh_transcript_no_json_flag`, but the test never loads the fixture, still drives `RecordingRunner` with inline canned stdout, and there is no subprocess/`gh`-when-present integration test (unlike bash-parity suites elsewhere under `python/`). Stub `--json not in create_argv` checks guard argv construction only; they would not detect real `gh` stdout/format drift or a future change that re-parses fake JSON from stubbed responses while breaking live CLI behavior—the exact class of failure that blocked the soak. **Suggested fix:** Wire the test to replay `python/fixtures/gh-pr-create-success.txt` through a transcript-style runner (or add a `pytest.mark.integration` case that shells out to `gh` when authenticated and skips otherwise), and assert rc=0 resolution with no `--json` in captured create argv; keep the fast stub cases as supplementary coverage.

- **risk-integration** `python/gh.py:370`, `python/gh.py:349-360` — Post-success PR resolution parses only `result.stdout` for the URL fallback, while the conflict-recovery path searches `_combined(result)` (stdout+stderr). If `gh pr create` exits 0 but emits the PR URL on stderr (conflict-style diagnostics already use stderr; success paths can carry warnings/progress on stderr in some CLI versions), resolution skips a valid URL and raises `ShipError("…could not be resolved")`, which #4 maps to JSON STALLED even though GitHub already created the PR. **Suggested fix:** Run URL recovery against `_combined(result)` on the rc=0 path as well (or at minimum fall back to `_combined(result)` when stdout parsing fails), matching conflict recovery and reducing false stalls after successful creates.

- **risk-integration** `python/gh.py:364-374`, `scripts/create-pr.sh:323-325` — Bash `create-pr.sh` retains a branch-context `gh pr view --json number` fallback when stdout lacks a parseable PR number; Python stops after one `pr_for_branch` call plus stdout URL regex, with no `gh pr view` (or polled list) fallback when stdout is non-URL success text (e.g. prose-only confirmation) and `pr list --head` lags or errors. That is a create-parity gap introduced by the new resolution strategy: a successful create can still end in STALLED JSON while an open PR exists. **Suggested fix:** After list/stdout recovery fails on rc=0, add a branch-context `gh pr view --json number,url,state,headRefName` fallback (with the same transient retry policy as other read helpers, and optional short poll for list lag) before raising `ShipError`, mirroring `create-pr.sh`; add a regression test where create rc=0 has non-URL stdout, list returns empty/errors, and view resolves the PR.
