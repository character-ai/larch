### In-Scope Findings

- **correctness** `python/ship.py:580-591` — The branch lowers the documented runtime floor to 3.11 and acceptance claims the `/implement` selector enforces `python3 ≥ 3.11`, but `main()` has no interpreter check. Unlike `skills/report-tokens/scripts/run-analysis.sh:69-73`, which fails closed before `exec python3 … report_tokens_cli.py`, `ship.py` can be invoked directly (manual runs, future default cutover, automation that skips the skill prose). On Python &lt; 3.11 that yields import/syntax failures or opaque runtime errors instead of a clear “requires Python 3.11 or newer” message. **Suggested fix:** Add the same `sys.version_info >= (3, 11)` guard at the top of `main()` (or a small shared helper used by `ship.py` and `report_tokens_cli.py`) and exit non-zero with an explicit stderr message before `run_ship()`.

- **correctness** `skills/implement/SKILL.md:955-1018` — The new 3.11 requirement is only in narrative text (lines 955–956); the load-bearing Step 8+ fenced Bash block still unconditionally calls `ship-pr.sh` (lines 992–1018) with no `LARCH_SHIP_PR_IMPL=python` branch and no embedded version probe. Runtime floor enforcement for the Python driver therefore depends entirely on orchestrator discipline, not a mechanical fence in the skill script surface. That diverges from `/report-tokens`, where the floor is enforced in shell before Python starts. **Suggested fix:** Add a parallel fenced invocation (or extend the existing block) that runs the version probe and then `python3 "${CLAUDE_PLUGIN_ROOT}/python/ship.py" …` when `LARCH_SHIP_PR_IMPL=python`, mirroring the bash path structure so a missed probe cannot silently run the driver on the wrong interpreter.
