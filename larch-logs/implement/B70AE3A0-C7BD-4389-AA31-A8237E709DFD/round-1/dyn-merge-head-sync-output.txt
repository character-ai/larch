Reviewing merge-head-sync changes: reading the diff and inspecting merge-related code.
### In-Scope Findings

- **correctness** `python/merge.py:123-148` and `python/ship.py:440-444` — The ship loop only re-enters `ci_monitor.monitor()` when `merge_pr` returns `MERGE_RESULT_CI_NOT_READY` or `MERGE_RESULT_MAIN_ADVANCED`, but after `ci_monitor` has already chosen `action=merge` for PR head **X**, `_ensure_head_matches_pr` can still take the flush-recovery path: `force_push_recovery` advances the branch to local head **Y**, `_poll_head_oid_match` waits for GitHub’s `headRefOid` to catch up, and then a single `gh.pr_checks_all_pass` call (lines 351–354) is the only CI gate before `_attempt_merge` runs in the same iteration. That check is coarser than `ci_monitor`’s `gather_status` / `decide` pipeline and can still report success while check suites are tied to the pre-push head, so squash-merge can proceed on **Y** without a full CI-wait cycle for the head the merge API will actually use. Removing the per-attempt `flush_logs_pre` in `merge_pr` (#7) reduces churn but does not remove this recovery path when earlier flushes or pushes left local ahead of the green PR OID. **Suggested fix:** After any successful flush-recovery force-push inside `_ensure_head_matches_pr`, fail closed into `MERGE_RESULT_CI_NOT_READY` (or a dedicated “re-poll CI” result) so `ship.py` always runs another `ci_monitor.monitor()` before `_attempt_merge`, even when `pr_checks_all_pass` is still true; optionally pin checks to `local_head` / current `headRefOid` instead of PR-level aggregate status alone.

- **correctness** `python/merge.py:258-273` — `_poll_head_oid_match` treats `headRefOid == local_head` as sufficient to stop polling and does not require a non-empty OID or agreement between `headRefOid` and the remote tracking ref (`git rev-parse origin/<branch>`). A transient or partial `gh pr view` JSON failure already yields `head_ref_oid=""` from `_refresh_pr_info`; the loop then sleeps through `MERGE_PR_POST_PUSH_UNKNOWN_RETRIES` and surfaces `MERGE_RESULT_ERROR`, but if the API ever returns a matching OID while the branch ref on the server is still behind (extreme lag or inconsistent fields), the function returns success and downstream merge proceeds without comparing to the remote ref. **Suggested fix:** After OID match (or on poll exhaustion), add a fail-closed comparison of `local_head` to `git.try_rev_parse(runner, f"{remote}/{branch}", cwd=cwd)` and/or reject empty `head_ref_oid` before treating the poll as successful.
