### In-Scope Findings

- **correctness** `python/gh.py:370` — `_recover_pr_from_conflict_text` is now applied to `result.stdout` on the success path (rc=0) as a fallback when `pr_for_branch` fails or lags. The function's URL regex `r"https?://[^\s]+/pull/\d+"` carries no repo constraint and takes the **last** match in the text. If a future `gh` version prints additional context on create success (e.g., a "Related PR" note echoing another repo's URL), the last match could resolve to a different repository's PR number. The `head_ref` is correctly set from the caller-supplied `branch`, but `pr.number` and `pr.url` would be wrong, potentially causing the merge phase to merge a PR in the wrong repo. This requires both `pr_for_branch` to fail/lag AND `gh` to emit extra URLs — low probability, but the original conflict path guarded against it by context (`_is_create_conflict`), while the new success path has no such guard. **Suggested fix:** before returning a URL-extracted PR on the success path, verify the extracted URL contains the expected `repo` slug (e.g., `f"/{repo}/pull/"` in url), mirroring how `pr_for_branch` scopes its list to `--repo repo`.
