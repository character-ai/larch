### In-Scope Findings

- **code-quality** `python/test_run_logs.py:test_larch_log_commit_volatile_cleanup_restores_am_porcelain` — The test uses `"AM {path}\n"` as the porcelain status (staged+modified). In `_cleanup_volatile_run_tree`, the expression `not line.startswith("?? ") and line[:1] != " "` evaluates to `True` for "AM" (since `line[:1] = "A" != " "`), setting `has_staged = True`. This triggers `_run_git_cleanup(runner, ["git", "reset", "HEAD", "--", rel], ...)` before `git restore`. The test only supplies three responses (`status`, `restore`-labeled, `status`-labeled) but the code path requires four (`status_porcelain_paths`, `git reset`, `git restore --worktree --staged`, `git status --porcelain` repo-wide check). The second response labeled `("git", "restore")` is consumed by `git reset`; the third response labeled `("git", "status")` is consumed by `git restore`; then the final repo-wide status check runs with no remaining response. The test will silently pass only if `RecordingRunner` returns a default-success response when the list is exhausted—which means the test does not actually validate the expected `git reset` → `git restore` sequence for AM-status files. **Suggested fix:** Add a fourth response for the `git reset HEAD -- rel` call, placed between the initial status response and the restore response, e.g. `CommandResult(("git", "reset"), 0, "", "", 0.01)`, so the response sequence correctly mirrors the four git operations (`git status`, `git reset HEAD`, `git restore --worktree --staged --source=HEAD`, `git status --porcelain`).
