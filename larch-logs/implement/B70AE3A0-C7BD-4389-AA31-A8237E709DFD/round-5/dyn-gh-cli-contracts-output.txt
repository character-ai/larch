Reviewing the branch diff and gh CLI integration changes.
### In-Scope Findings

- **risk-integration** `python/gh.py:440-457,360-383` — Create-conflict recovery now routes stderr/stdout URLs through `_recover_pr_from_urls(..., allow_unverified=False)`, which requires a successful `pr_view` (open state + `headRefName` match). Bash `create-pr.sh` still recovers from the conflict URL alone when `gh pr list` fails (`recover_existing_pr_after_create_conflict`, lines 230–234). If both `pr list` and `pr view` fail after an “already exists” conflict (permissions blip, hosted-repo errors, or sustained API errors), Python raises from `_ensure_success` on the failed create even when the conflict text contains a valid PR URL—regression vs bash parity and a soak-relevant stall path. **Suggested fix:** After list exhaustion on the conflict path, either use `allow_unverified=True` with repo-slug URL matching (mirroring bash), or add a URL-only fallback when `pr_view` fails with non-transient errors; keep the stricter open/head checks when `pr_view` succeeds.

- **risk-integration** `python/gh.py:375-377,412-436` — Post-create URL recovery (`_recover_pr_from_create_output`) sets `allow_unverified=True`, so any `ShipError` from `pr_view` (not only 404/lag) returns the URL-derived candidate with hard-coded `state="OPEN"` and without confirming the PR exists or matches the branch. A permanent auth/GraphQL failure after `gh pr create` exit 0 can therefore yield a synthetic `PullRequest` and let ship continue on the wrong or non-existent PR. **Suggested fix:** Restrict unverified fallback to not-found/lag signatures (e.g. match `Could not resolve to a PullRequest`, HTTP 404 text), add a short bounded `pr_view` poll before unverified fallback, or require list/view success and only then fall back to stdout URL parsing without fabricating `OPEN`.
