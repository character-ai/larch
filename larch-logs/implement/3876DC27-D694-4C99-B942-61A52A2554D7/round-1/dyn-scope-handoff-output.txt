Reviewing the branch diff and scope-anchor handoff code paths.
### In-Scope Findings

- **risk-integration** `skills/design/scripts/plan-review-loop.sh:229-245` — `_scope_anchor_handoff_value()` gates `SCOPE_ANCHOR_FILE` emission solely on `TALLY_PLAN_REVIEW_STATUS` being `ok` or `main-agent-vote-required`, and never consults `LOOP_STATUS`. After a successful tally, later failures that set `LOOP_STATUS=panel-failed` (for example the snapshot-failed exit at `1920-1924`) leave `TALLY_PLAN_REVIEW_STATUS=ok`, so `write_step3_result_env()` / `emit_loop_kvs()` still persist and relay the anchor. That contradicts FINDING_6, `run-step3-review.md`, and the new `SECURITY.md` claim that `panel-failed` paths omit the key. **Suggested fix:** Gate `_scope_anchor_handoff_value()` on both tally terminal and loop terminal — emit only when `TALLY_PLAN_REVIEW_STATUS` is `ok|main-agent-vote-required` **and** `LOOP_STATUS` is not in an explicit denylist (`panel-failed`, `tally-error`, `cap-reached`, `degraded-empty-collector`, `plan-size-trigger`, `plan-validator-defects`, `emit-plan-failed`, etc.), or invert to a positive allowlist of loop terminals that may carry the handoff (`complete`, `main-agent-vote-required`, and any others intentionally documented).

- **risk-integration** `skills/design/scripts/run-step3-review.sh:148-150` — `scope_anchor_relay_allowed()` repeats the same asymmetry: it permits relay whenever `TALLY_PLAN_REVIEW_STATUS=ok`, without requiring a compatible `LOOP_STATUS`. A loop-produced `.step3-plan-review-result.env` with `LOOP_STATUS=panel-failed` and `TALLY_PLAN_REVIEW_STATUS=ok` (snapshot-failed shape above) will still be forwarded to stdout and `.step3-review-result.env`, widening stale-handoff exposure at the Step 3 outer relay boundary the branch just hardened. **Suggested fix:** Mirror the loop-side terminal matrix here — require `TALLY_PLAN_REVIEW_STATUS` in `ok|main-agent-vote-required` **and** `LOOP_STATUS` not in the same denylist (or only in the documented allowlist), then clear `SCOPE_ANCHOR_FILE` before emit/write when the pair is incompatible.

- **risk-integration** `skills/design/scripts/test-run-step3-review.sh:539-552` — The plan/acceptance called for a stale-seed regression on the outer relay (`panel-failed` / `tally-error` with a pre-existing `SCOPE_ANCHOR_FILE`, inner stub omitting the KV). The branch added strong loop-side cases (`test-plan-review-loop.sh:1245-1278`, `1652`) and panel-failed recovery coverage (`738-743`), but `test-run-step3-review.sh` never asserts that `panel-failed` with `TALLY_PLAN_REVIEW_STATUS=ok` omits `SCOPE_ANCHOR_FILE` from stdout/result env. The existing `panel-failed` stub uses matching `TALLY_PLAN_REVIEW_STATUS=panel-failed`, so it cannot catch the `panel-failed`+`ok` mismatch introduced by the new gating logic. **Suggested fix:** Add a harness where the loop stub (or real loop snapshot-failed fixture) returns `LOOP_STATUS=panel-failed` with `TALLY_PLAN_REVIEW_STATUS=ok` and optionally seeds a stale anchor path; assert both normalized stdout and `.step3-review-result.env` omit `SCOPE_ANCHOR_FILE=`.

- **risk-integration** `skills/design/SKILL.md:1213` — MainAgent re-tally `SCOPE_ANCHOR_FILE` refresh (`_RETALLY_SCOPE_ANCHOR_IN` / `_RETALLY_PARSED_SCOPE_ANCHOR_FILE`, omit on `tally-error`, dual env rewrite) is enforced only through orchestrator prose and `test-step3-orchestrator-fence.sh` grep pins, unlike the loop and `run-step3-review.sh` paths which now have script-level terminal gating. A prompt-side miss on re-tally error can still leave a stale anchor in `.step3-plan-review-result.env` / `.step3-review-result.env` despite the branch’s stated stale-leak mitigations (FINDING_5/7/12). **Suggested fix:** Extract re-tally scope-anchor parse/persist into a small helper (parallel to `_scope_anchor_handoff_value()` / `scope_anchor_relay_allowed()`) invoked from the re-tally Bash fence, or add a behavioral harness that simulates re-tally stdout/env refresh rather than only checking documentation strings.

This predates the branch diff and is documented in `plan-review-loop.md`, but it remains a secondary path-only surface if any consumer ever treats `round-summary.env` as authoritative for Step 3 handoff rather than forensics.

- **architecture** `skills/design/scripts/plan-review-loop.sh:235-236` — When `_PARSED_SCOPE_ANCHOR_FILE` is set, it wins over `_LOOP_SCOPE_ANCHOR_IN` with only CR/LF rejection and no `DESIGN_TMPDIR` containment check inside the loop; containment is deferred to `run-step3-review.sh:152-177`. That is acceptable while `tally-plan-review.sh` never emits the KV, but it is a latent footgun if tally output ever gains `SCOPE_ANCHOR_FILE=` without matching validation in the loop writer.
