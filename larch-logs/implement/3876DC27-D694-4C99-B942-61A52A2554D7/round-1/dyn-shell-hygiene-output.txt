Reviewing the branch diff and commit history for shell-hygiene issues.
### In-Scope Findings

- **code-quality** `skills/design/scripts/run-step3-review.sh:148-150` — `scope_anchor_relay_allowed()` gates relay on `LOOP_STATUS==main-agent-vote-required || TALLY_PLAN_REVIEW_STATUS==ok`, but `plan-review-loop.sh` gates the same handoff on `TALLY_PLAN_REVIEW_STATUS` in `ok|main-agent-vote-required` only (`_scope_anchor_handoff_value`, lines 229–234). The predicates are not equivalent: a desynced parse where `LOOP_STATUS=complete` and `TALLY_PLAN_REVIEW_STATUS=main-agent-vote-required` would clear a valid anchor here even though the loop would still emit it, and the inverse (`LOOP_STATUS=main-agent-vote-required` with a non-terminal tally) would relay when the loop would not. **Suggested fix:** Mirror the loop contract—e.g. `case "${TALLY_PLAN_REVIEW_STATUS:-}" in ok|main-agent-vote-required)` (and optionally require matching `LOOP_STATUS` for `main-agent-vote-required`)—so both layers share one terminal gate.

- **code-quality** `skills/design/scripts/plan-review-loop.sh:207-217,229-245` — `emit_loop_kvs()` accepts `tally_status` as a parameter but `_scope_anchor_handoff_value()` (called before emitting that KV) reads the global `TALLY_PLAN_REVIEW_STATUS` instead of `$tally_status`. Today callers pass the global through unchanged, but any future refactor that passes a different `tally_status` while leaving the global stale would emit mismatched `TALLY_PLAN_REVIEW_STATUS` and `SCOPE_ANCHOR_FILE` lines. **Suggested fix:** Pass `tally_status` into `_scope_anchor_handoff_value` (or read only the parameter inside `emit_loop_kvs`) so the relay gate and emitted tally KV share one value.

- **code-quality** `skills/design/scripts/plan-review-loop.sh:1700-1731` — On tally failure the script forces `TALLY_PLAN_REVIEW_STATUS=tally-error` but leaves `_PARSED_SCOPE_ANCHOR_FILE` populated from the raw tally stream; safety currently depends entirely on `_scope_anchor_handoff_value()` re-checking tally status. That is easy to break if a later edit writes result env or stdout from the parsed variable before the gate runs. **Suggested fix:** Unset `_PARSED_SCOPE_ANCHOR_FILE` (or clear it in the `tally-error` branch) when `_tally_rc -ne 0`, matching the input/output separation the plan describes.

- **code-quality** `skills/design/scripts/run-step3-review.sh:334-340` — The pre-parse reset clears `TALLY_PLAN_REVIEW_STATUS`, `VOTING_TALLY_FILE`, etc., but not `SCOPE_ANCHOR_FILE`, relying solely on the empty initialization at line 146. Any future early path that sets `SCOPE_ANCHOR_FILE` before the loop invocation could leak into the parse/fallback block because stdout fallback only fills empty keys (`[[ -n "${!_key:-}" ]] || printf -v …`). **Suggested fix:** Add `SCOPE_ANCHOR_FILE=""` to the same reset block as the other handoff fields.
