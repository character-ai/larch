Reviewing the branch diff and commit history for scope-anchor handoff risks.
### In-Scope Findings

- **risk-integration** `skills/design/SKILL.md:1155-1183` — Step 3 orchestrator handoff loads `SCOPE_ANCHOR_FILE` from `.step3-review-result.env` and stdout without the terminal gate that `run-step3-review.sh` applies via `scope_anchor_relay_allowed`. With file-first parsing, a stdout line carrying `SCOPE_ANCHOR_FILE=` on `panel-failed` / `tally-error` would populate orchestrator state even when `LOOP_STATUS` is an error terminal, because the handoff never clears the key when tally/loop terminals are incompatible. `run-step3-review.sh` is gated today, so this is a defense-in-depth gap rather than an active leak, but it is the weakest link in the new handoff chain. **Suggested fix:** After the existing handoff parse block, mirror `scope_anchor_relay_allowed` (or call a shared helper) and unset `SCOPE_ANCHOR_FILE` unless `TALLY_PLAN_REVIEW_STATUS` is `ok|main-agent-vote-required` and `LOOP_STATUS` is `complete|main-agent-vote-required`; add an orchestrator-fence case where env omits the key but stdout carries it on `panel-failed`.

- **risk-integration** `skills/design/SKILL.md:1213` / `skills/design/references/approval-gates.md:95` — MainAgent re-tally `SCOPE_ANCHOR_FILE` refresh is prompt-only: `_RETALLY_SCOPE_ANCHOR_IN` / `_RETALLY_PARSED_SCOPE_ANCHOR_FILE` separation, terminal-gated dual env refresh, and `tally-error` omission are documented in SKILL/approval-gates but not enforced by any shell helper. Loop and `run-step3-review.sh` handoffs are mechanically gated; re-tally depends entirely on orchestrator discipline when rewriting `.step3-plan-review-result.env` and `.step3-review-result.env`. A re-tally `tally-error` with sloppy refresh could leave a prior `SCOPE_ANCHOR_FILE` in one or both env files and mislead pause/resume or Gate B. **Suggested fix:** Extract a small `refresh-step3-scope-anchor-handoff.sh` (or extend `lib-phase-driver.sh`) that accepts tally terminal status plus optional parsed path / `_RETALLY_SCOPE_ANCHOR_IN`, applies the same CR/LF and `DESIGN_TMPDIR` containment checks as `_scope_anchor_handoff_value`, and writes both result envs; call it from a harnessed re-tally path instead of prose-only persist instructions.

- **risk-integration** `skills/design/scripts/plan-review-loop.sh:560-583` — `_write_round_summary` always writes `SCOPE_ANCHOR_FILE=${SCOPE_ANCHOR_FILE:-}` to `round-summary.env`, bypassing `_scope_anchor_handoff_value` terminal gating used by `emit_loop_kvs` and `write_step3_result_env`. On `tally-error` / `panel-failed` terminals the durable handoffs correctly omit the key, but per-round forensics still record it, contradicting the two-surface contract in `SECURITY.md` (path-only handoffs omitted on those terminals). The value is the materialized anchor path, not an arbitrary stale export, so impact is contract drift and possible operator/automation confusion rather than arbitrary path injection. **Suggested fix:** Gate `round-summary.env` writes through `_scope_anchor_handoff_value` (or omit the key when the round’s tally/loop terminal does not permit relay), and add a harness asserting `tally-error` round summaries lack `SCOPE_ANCHOR_FILE=`.

### Out-of-Scope Observations

- **risk-integration** `skills/design/scripts/plan-review-loop.sh:229-238` — `_scope_anchor_handoff_value` / `scope_anchor_relay_allowed` allow relay only when `LOOP_STATUS` is `complete|main-agent-vote-required`, excluding `converged|cap-hit`. That matches the plan’s terminal matrix (assessor/Gate B read the staged file directly on converged paths), but any future consumer expecting `SCOPE_ANCHOR_FILE` in `.step3-review-result.env` on `converged` will not find it. Worth documenting explicitly if new consumers are added.

- **architecture** `skills/design/scripts/run-step3-review.sh:371-380` — Multi-round `plan-review-loop.sh` stdout can include intermediate per-round tally KVs before the terminal `emit_loop_kvs`; orchestrator parsing is first-wins per key. That predates this branch and is broader than scope-anchor, but it can leave stale `TALLY_PLAN_REVIEW_STATUS` from an earlier round if later rounds do not re-emit it.
