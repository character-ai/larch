### In-Scope Findings

- **risk-integration** `skills/implement/scripts/stall-recovery-report.sh:1143-1147` — On the success path, `atomic_write_text` failure emits `REASON=write-failed` and exits `1`, but unlike every other rejection branch it does **not** remove a pre-existing `stall-recovery-issue.env`. If a prior run (or hand-written orchestrator bookkeeping) left canonical `ISSUE_NUMBER`/`ISSUE_URL` in that file and a later normalization attempt fails at temp-write/`mv`, Step 8 `bug-comment` can still load the stale number and post the terminal exhaustion comment to the wrong issue. **Suggested fix:** On `write-failed`, `rm -f "$out_file"` before exiting (mirror `emit_issue_env_false`), and add a harness case that seeds a stale env file then forces `atomic_write_text` failure.

- **risk-integration** `skills/implement/references/stall-recovery.md:19` — Step 4 passes `--issue-exit-code "$ISSUE_RC"` into `normalize-issue-env`, but the procedure never defines how `ISSUE_RC` is obtained (Skill-tool process exit vs inferred from stdout). The helper’s exit-code gate is therefore entirely dependent on prompt-side orchestrator discipline; a mistaken `ISSUE_RC=0` when `/larch:issue` actually failed would skip the `issue-exit-code` rejection path and rely only on stdout parsing. **Suggested fix:** Pin in step 4 that `ISSUE_RC` must be the foreground `/larch:issue` invocation’s process exit code captured in the same Bash block that writes `stall-recovery-issue.stdout`, and add a `test-implement-structure.sh` grep for `normalize-issue-env` plus `--issue-exit-code` alongside the existing `issue-input-file` pins.

- **risk-integration** `scripts/test-implement-structure.sh:118-129` — The new Step 4 structure assertions pin `issue-input-file` and the `--input-file …stall-recovery-issue-input.md` line, but nothing pins the `normalize-issue-env` call or `stall-recovery-issue.stdout` capture. A future prose edit could drop normalization and revert to orchestrator-hand-written `stall-recovery-issue.env` (the pre-#3568 failure mode seen in run logs) while CI still passes. **Suggested fix:** Extend the Step 4 awk window with greps for `normalize-issue-env`, `stall-recovery-issue.stdout`, and `ISSUE_ENV_WRITTEN`.

- **risk-integration** `skills/implement/scripts/stall-recovery-report.sh:1124-1130` — Canonical `ISSUE_NUMBER` validation accepts any all-digit string, including `0`; `ISSUE_NUMBER=0` would be written and later consumed by Step 8 `gh issue comment`. Real `/larch:issue` output should never emit `0`, but the new protocol surface does not enforce positive issue numbers. **Suggested fix:** Reject `issue_number` unless it matches `^[1-9][0-9]*$` (and the same for `duplicate_number` before fallback).

- **risk-integration** `skills/implement/scripts/stall-recovery-report.sh:1067-1089` — `--issue-stdout-file` is path-contained under `$IMPLEMENT_TMPDIR` but, unlike `--failure-detail-log`, has no size bound before `awk`/`kv_get` processing. A corrupted or accidentally verbose stdout capture could load unbounded content into memory during normalization. **Suggested fix:** Apply the same 64 KiB cap used for failure-detail logs (reject with `issues-stdout-oversize` and stale-env removal) before filtering.
