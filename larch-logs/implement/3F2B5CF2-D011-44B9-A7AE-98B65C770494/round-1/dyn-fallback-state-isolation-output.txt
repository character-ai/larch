Reviewing the branch diff and tier-4 fallback state isolation in the revise-plan waterfall script.
Checking merge precedence against `finalize()` classification and a few edge-case pairs:
### In-Scope Findings

- **correctness** `skills/design/scripts/revise-plan-with-waterfall.sh:183-199` — `merge_tier4_status()` does not consistently keep the more severe status when tier-4 mini-waterfall attempts mix `invalid-patch`, `apply-failed`, and `emit-plan-failed`. Documented precedence is `ok > emit-plan-failed > apply-failed > invalid-patch > …` (worst wins), but the `case "$tier4_status:$new"` arms treat the left-hand status as authoritative in ways that downgrade severity. Example: after codex records `invalid-patch`, cursor `emit-plan-failed` matches `*:invalid-patch` and sets `tier4_status=emit-plan-failed` (lines 183–186), dropping `invalid-patch`. Conversely, `emit-plan-failed` then `apply-failed` matches `emit-plan-failed:*` and keeps `emit-plan-failed` (lines 195–198) instead of upgrading to `apply-failed`. `finalize()` classifies `REVISE_STATUS` via substring search on `all_statuses` (lines 450–456), so if tiers 1–3 are only `no-patch`/`skipped-not-present` and tier 4 loses its `invalid-patch` this way, a run can emit `failed-apply` instead of `failed-validation`. **Suggested fix:** Replace the pairwise `case` matrix with a single severity rank lookup (numeric ranks for each status) and set `tier4_status` to whichever of `{tier4_status, new}` has the higher rank; keep the early exits for `ok` and empty initial state. Add a harness case where tier 4 records `invalid-patch` then `emit-plan-failed` and assert `REVISE_TIER_4_STATUS=invalid-patch` and `REVISE_STATUS=failed-validation`.
