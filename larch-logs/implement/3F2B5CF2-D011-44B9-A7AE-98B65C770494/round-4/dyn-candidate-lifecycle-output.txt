Reviewing the branch diff and the multi-candidate extraction flow in `revise-plan-with-waterfall.sh`.
Checking review-round fixes and glob-order behavior in tests.
### In-Scope Findings

- **risk-integration** `skills/design/scripts/revise-plan-with-waterfall.sh:318-335,511-524` — Extraction copies candidates into `$REVISE_DIR` in encounter order (`codex-output-candidate.patch`, then `codex-output-candidate-2.patch`, …) and only then deletes the temp dir, so copy-before-`rm -rf` is safe. Validation in `attempt_tier` does **not** preserve that order: the loop `for candidate in "$REVISE_DIR/${output_name%.txt}-candidate"*.patch` uses pathname expansion, and every `…-candidate-N.patch` sorts **before** `…-candidate.patch` because `-` (0x2d) is less than `.` (0x2e). With two blocks, the second extracted patch is always tried first; with ten or more, `…-candidate-10.patch` sorts before `…-candidate-2.patch`. The harness cases “later valid beats earlier wrong” / “earlier valid beats later corrupt” pass only for the two-fence layout because validation fails on the wrongly ordered try, not because encounter order is enforced. Any tier that emits three or more fenced diffs can apply a later-listed but lexicographically earlier patch, or skip the first valid one silently. **Suggested fix:** Record candidate paths in encounter order during `extract_unified_diff_candidates` (e.g. append to `$tmpdir/candidate-order.lst` while copying) and have `attempt_tier` iterate that list (or emit zero-padded suffixes such as `candidate-001.patch` for **all** outputs including the first, then iterate with width-fixed sorting). Do not rely on bare `candidate*.patch` glob order.

- **risk-integration** `skills/design/scripts/revise-plan-with-waterfall.sh:272-316` — The shared `$tmpdir/found` marker is set whenever **any** fenced block yields at least one `candidate-*.patch`, which disables the `extract-fallback` pass over the full raw `$output`. If the model puts a wrong-path or corrupt diff inside ` ```diff ` fences but a valid `plan.txt` diff outside fences (the #3143 Cursor preamble pattern), extraction never scans the unfenced body and `attempt_tier` only sees bad fenced candidates. That amplifies `failed-validation` even when a usable unfenced patch exists. **Suggested fix:** Run fallback when no **plan-targeting** candidate survives header/`git apply` checks (or always merge fallback candidates into the ordered candidate list), instead of gating fallback solely on “any patch-like span existed in a fence.” Alternatively, treat `found_file` per block and still run fallback when the union of block candidates is empty or all fail validation.
