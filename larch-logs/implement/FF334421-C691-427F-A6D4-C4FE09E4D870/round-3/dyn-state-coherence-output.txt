### In-Scope Findings

- **correctness** `python/ship.py:1194-1208` — On the postmerge success path, `_write_terminal_finalize_if_terminal(state_ctx, Outcome.OK, "")` runs at line 1195 and writes a terminal OK-shaped `finalize-state.sh` before the matching terminal `ship-pr-state.sh` sync at line 1208. In between, merge-preserving `_write_ship_state` logic (lines 697-700) can leave orchestrator-seeded `STALL_TRACKING=true` in `ship-pr-state.sh` because stall keys are only cleared in the `phase == "done"` block (lines 686-695), which has not run yet. That yields a split-brain window where `finalize-state.sh` says success (`STALL_TRACKING=false`, `EXIT_CODE=0`) while `ship-pr-state.sh` may still say `STALL_TRACKING=true` with `PHASE=postmerge`. Step 18’s Python restore gate (`skills/implement/SKILL.md` ~1366-1375) treats ship-pr-state stall flags alone as stale and calls `restore-finalize-state.sh`, so a crash or a failed line-1208 write after line 1195 (for example the new fail-closed read at lines 650-651) can overwrite a valid OK finalize with stall-shaped reconstruction. **Suggested fix:** Write terminal OK finalize only after the line-1208 `_write_ship_state(..., phase="done", terminal_outcome=Outcome.OK)` succeeds, or atomically update both files in one helper; alternatively clear/normalize `STALL_TRACKING`/`STALL_STEP` in `ship-pr-state.sh` immediately before writing OK finalize at 1195.

- **correctness** `python/ship.py:654-700` — `STALL_TRACKING` and `STALL_STEP` are deliberately excluded from `_TERMINAL_ONLY_STATE_KEYS` (lines 68-74), and the non-terminal branch only overwrites them when `terminal_outcome is not None`, `ctx.stall_tracking`/`ctx.stall_step` is truthy, or the key is absent (lines 697-700). After a prior terminal write set those keys, a later routine write with `terminal_outcome=None` and `ctx.stall_tracking=False` leaves stale stall metadata in place until an explicit `phase=="done"` write runs. That is mostly harmless on mid-loop `NEEDS_USER_INPUT`/`TRANSIENT` paths (overlay clears on terminal writes), but it amplifies the postmerge ordering bug above and can also leave `EXIT_CODE` pruned (lines 680-682) while `STALL_TRACKING=true` remains, confusing Step 18 restore and `stall-recovery-report.sh classify` consumers that read ship-pr-state first. **Suggested fix:** Either add `STALL_TRACKING`/`STALL_STEP` to the non-terminal prune set whenever `terminal_outcome is None` and `ctx.stall_tracking` is false, or explicitly zero them in that branch before merge-overlay; keep the orchestrator-seed preservation behavior only when `ctx.stall_tracking` is still true or the key is missing.
