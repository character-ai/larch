### In-Scope Findings

- **architecture** `skills/design/scripts/plan-review-loop.sh:1271-1286` — Plan-review dedup builds `problem_text()` from only the `### FINDING_N:` heading (or the first body line), while canonical `[SCOPE-REDUCTION]` detection in `scripts/check-scope-reduction-marker.sh` also inspects `Concern:` and `what:` lines. When the marker lives only in those fields, dedup can treat two semantically different findings as duplicates (shared heading, divergent scope-reduction prose) or fail to merge true duplicates that share `what:` text but differ in headings, so tagged scope-reduction semantics diverge between the detector, ballot rendering, and pre-vote dedup. **Suggested fix:** Reuse the same candidate extraction as `check-scope-reduction-marker.sh` inside the embedded dedup helper (or call the helper per block) so `problem_text` and `is_scope_reduction_block()` agree on which text constitutes the finding; add a harness case where the marker appears only on `what:` and dedup must not collapse an untagged sibling.

- **architecture** `scripts/check-scope-reduction-marker.sh:35-36` — Severity normalization strips only `[important]`, `[nit]`, and `[latent]` before testing for `[SCOPE-REDUCTION]`, but plan-review ballots and voter prompts allow other bracketed severities. A finding shaped like `### FINDING_2: [blocking] [SCOPE-REDUCTION] …` or `Concern: [critical] [SCOPE-REDUCTION] …` will not be classified as scope-reduction, so it enters LLM aggregation and normal voting instead of the withhold-and-append-verbatim path in `skills/review/scripts/aggregate-findings.sh`. **Suggested fix:** Either extend `norm()` to strip any leading `[word]` token (with tests), or document and enforce a single severity vocabulary across reviewer templates and the detector.

- **architecture** `python/ship.py:914-928` — On the now-default Python Step 8+ path, `_resume_plan()` returns exit **3** `needs_user_reason=unsupported-rebase-continuation` whenever `RESUME_PHASE` / `CALLER_KIND` are set in merged `ship-pr-state.sh` but `ship-pr-rrr-after-phase14.flag` is absent. That blocks the bash-style resume contract (`ship-pr.sh --resume-phase ship-pr-rrr-phase14`) documented for `ship_pr_pre_push` in `skills/implement/SKILL.md:1112` and `python/README.md:68-79`. After conflict resolution, a re-invoked Python driver can therefore stall on exit 3 instead of continuing the phase-14 rebase loop unless the flag file is present and intact — the documented #3404 gap is now on the default driver. **Suggested fix:** Teach `_resume_plan()` to honor the same `ship_pr_pre_push` / `ship-pr-rrr-phase14` handoff as bash (recreate or trust the flag, or accept resume tokens when `CONFLICT_FILES` was cleared by conflict-resolution), and add an integration test that simulates post–conflict-resolution re-entry.

- **architecture** `python/ship.py:1782-1790` — `PrePushConflictHandoff` is explicitly excluded from `_write_terminal_finalize_if_terminal()`, so exit **4** pre-push conflict handoffs persist `CONFLICT_FILES` / resume tokens in `ship-pr-state.sh` but leave `finalize-state.sh` absent. That matches the SKILL’s conflict-resolution branch, but it diverges from other terminal stalls and from Step 18’s “read `STALL_*` from `finalize-state.sh` when present” guidance (`skills/implement/SKILL.md:1112`). Stall recovery and final-report consumers must always consult `ship-pr-state.sh` for this path, which is easy to miss now that Python is default. **Suggested fix:** Either write a minimal stall-shaped `finalize-state.sh` on `PrePushConflictHandoff` (without treating the run as fully terminal), or narrow SKILL Step 18a/Exit 4 prose to state that `ship_pr_pre_push` stalls are finalize-absent by design and classify only from `ship-pr-state.sh`.

- **architecture** `skills/implement/SKILL.md:1091-1114` — The bash-only gate at line 1091 is immediately followed by exit-matrix bullets that still prescribe Python-path reads (`finalize-state.sh`, JSON `needs_user_reason`, `ship-pr-net-retries-python.count`).
