Reviewing the branch diff and commit history, focusing on Python ship driver state transitions and merge/finalize behavior.
### In-Scope Findings

- **correctness** `python/ship.py:1930-1961` — `_ctx_from_args` binds `--state-file` after `RunContext.from_env()` has already run, but it never re-reads state-file keys into the context. `RunContext.from_env()` only consults `SHIP_PR_STATE_FILE` in the environment (`python/run_context.py:112-137`), while `/implement` passes `--state-file "$IMPLEMENT_TMPDIR/ship-pr-state.sh"` without requiring that env var. On the live CLI path, `stall_tracking`, `stall_step`, `oos_pending`, `ci_fix_rebase_pending`, and related seeded markers therefore stay at defaults even when present in the pre-seeded file. **Suggested fix:** After applying CLI overrides, re-hydrate from `ctx.state_file` (same helpers as `RunContext.from_env()`, or a shared `overlay_from_state_file(ctx)`), and use that in `_hydrate_resume_context` for open-pr resumes as well.

- **correctness** `python/ship.py:659-706` — Because of the hydration gap above, the first routine `_write_ship_state` on a default `/implement` invocation runs with `ctx.stall_tracking=False`. The merge path explicitly drops `_NON_STALL_STATE_KEYS` when `not ctx.stall_tracking` and then writes `STALL_TRACKING=false`, which clears orchestrator-seeded `STALL_TRACKING=true` / `STALL_STEP=…` from `ship-pr-state.sh` on the first refresh. That breaks the acceptance/manual matrix item that post-run state must retain seeded stall metadata after `--state-file`, and it can hide Step 18 terminal-override signals that depend on `ship-pr-state.sh` still carrying `STALL_TRACKING=true`. Unit coverage passes only when tests inject `stall_tracking=True` directly (`python/test_ship.py:2459-2472`) or call `_write_ship_state` outside `main()`; there is no `main([..., "--state-file", ...])` case with seeded stall keys. **Suggested fix:** Fix context hydration first; if stale-clearing remains desired for genuinely fresh runs, gate clearing on an explicit “healthy/fresh” signal rather than default-false context on the production CLI path.

- **correctness** `python/ship.py:149-151,177-180,2215-2223` — `_is_infrastructure_ship_error()` is a stub that always returns `False`, so infrastructure `ShipError`s such as `cannot read existing ship state: …` (`python/ship.py:656`) are converted to `Outcome.STALLED` instead of `Outcome.INTERNAL_ERROR`. The `run_ship` exception handler then treats those as terminal stalls and calls `_write_terminal_state`, writing stall-shaped `finalize-state.sh` / merged `ship-pr-state.sh` for what should be a non-resumable driver failure. That conflicts with `python/test_ship.py:1404-1420`, which expects `INTERNAL_ERROR` and no finalize file. **Suggested fix:** Implement `_is_infrastructure_ship_error()` for state I/O / contract failures (matching the error text or error subclass), map those to `Outcome.INTERNAL_ERROR`, and skip terminal stall persistence for that class.

### Out-of-Scope Observations

- `python/ship.py:1765-1774` duplicates the postmerge `phase=done` write already performed inside `run_postmerge_phase()` (`python/ship.py:1248`); redundant but not functionally harmful on success.
- `python/ship.py:647-656` vs `python/finalize.py:642-657`: `_write_ship_state` merge parses raw `KEY=value` lines while `_state_file_kv()` uses `finalize.read_finalize_state()` (shlex-aware). Quoted or shell-metacharacter values in seeded state could round-trip inconsistently; pre-existing parity risk, not introduced by the default-flip itself.
- Local pytest could not execute `python/test_ship.py` here because `python/ship.py` hard-requires Python 3.12+ and the shell has 3.11; CI/`make py-test` is the authoritative runner for those tests.
