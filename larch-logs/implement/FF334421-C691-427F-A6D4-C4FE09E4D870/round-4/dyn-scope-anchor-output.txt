Reviewing the branch diff and commit history for architectural issues in the Python-default ship driver flip.
Examining core architectural changes in `python/ship.py`, the implement skill routing, and the scope-anchor pipeline.
### In-Scope Findings

- **architecture** `skills/implement/SKILL.md:995` — The Python driver selector collapses every exit-4 outcome into “continue to Step 16/Step 18 as a stall,” but it does not call out the mandatory `ship_pr_pre_push` branch (`RESUME_PHASE=ship-pr-rrr-phase14`, `CALLER_KIND=ship_pr_pre_push`, `CONFLICT_FILES` in merged `ship-pr-state.sh`) that must run `conflict-resolution.md` before Step 16. That handoff is documented later under the exit-4 bullets (~1112), not in the selector summary that claims JSON-only routing. An orchestrator that stops at the selector paragraph can treat a pre-push conflict handoff as a terminal stall and skip automated conflict recovery on the new default Python path (#3404).

  **Suggested fix:** Extend the Python selector exit-4 sentence to mirror the bash matrix: when merged `ship-pr-state.sh` has `RESUME_PHASE=ship-pr-rrr-phase14` and `CALLER_KIND=ship_pr_pre_push`, load `conflict-resolution.md`, run Phases 1–4 with `caller_kind=ship_pr_pre_push`, then re-invoke `python/ship.py` (with `--state-file`, no `--resume-phase`); only other exit-4 cases go straight to Step 16/18. Add a structure-test pin so the selector and exit-4 bullets cannot drift again.

- **architecture** `skills/review/scripts/aggregate-findings.sh:211-221` and `skills/design/scripts/plan-review-loop.sh:1494-1503` — Scope anchoring stops at reviewers and voters. Scout, panel dispatch, revise, and voter prompts all receive `plan-review-scope-anchor.txt`, but the plan-review aggregator is invoked with only `findings-in-scope.md` and `plan.txt`. The LLM merge/dedupe pass therefore has no binding issue-scope evidence; scope-reduction findings that lose the leading `[SCOPE-REDUCTION]` marker can be merged with expansion findings and weaken proportionality before voting.

  **Suggested fix:** Thread `--scope-anchor-file "$SCOPE_ANCHOR_FILE"` (or inline the same untrusted block used by `render-voter-prompt.sh`) into `aggregate-findings.sh` for `--input-mode plan`, with proportionality instructions matching the voter prompt. Extend `test-plan-review-loop.sh` / `test-aggregate-findings.sh` to assert the anchor reaches the aggregator argv or prompt body.

- **architecture** `python/ship.py:1742-1750` and `skills/implement/SKILL.md:1093-1112` — `PrePushConflictHandoff` is excluded from `_write_terminal_state`, so exit-4 handoffs update merged `ship-pr-state.sh` but leave `finalize-state.sh` absent. That matches immediate re-entry, but it conflicts with SKILL guidance to read Python exit-4 stall metadata from `finalize-state.sh` first (~1093, ~1112). The split contract (JSON exit 4 + disk state only in `ship-pr-state.sh`, no terminal finalize) is easy to mis-route unless the orchestrator always reaches the detailed exit-4 bullets and reads `RESUME_PHASE`/`CALLER_KIND`/`CONFLICT_FILES` from `ship-pr-state.sh`.

  **Suggested fix:** In the Python selector and anti-halt boundary, state explicitly that exit-4 `ship_pr_pre_push` is a non-terminal handoff: no `finalize-state.sh`, classification keys live only in merged `ship-pr-state.sh`, and conflict-resolution must run before any Step 16 stall handling. Optionally have `python/ship.py` set a distinct JSON field (e.g. `handoff=ship_pr_pre_push`) so routing does not depend on a secondary file read.

- **architecture** `python/ship.py:1292-1300` — After a successful `run_postmerge_phase`, the caller issues a second `_write_ship_state(..., phase="done")` without `terminal_outcome=Outcome.OK`, even though `run_postmerge_phase` already wrote terminal finalize and a terminal `phase="done"` overlay (~1500-1517). The extra write uses `working` instead of `state_ctx` and can diverge from the postmerge context (e.g. `pr_closed`, `merge_result`, stall overlays) depending on merge-loop mutations.

  **Suggested fix:** Drop the redundant post-OK write in the caller, or pass `terminal_outcome=Outcome.OK` and the same `state_ctx` used inside `run_postmerge_phase` so success path state/finalize stay single-sourced.

If brainstorm should ever inform plan review, the injection point is still missing.
