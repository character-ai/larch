Reviewing the branch diff for Python 3.12 runtime/versioning risks across CI, docs, and Step 8+ invocation.
### In-Scope Findings

- **risk-integration** `python/ruff.toml:1` — Ruff is still pinned to `target-version = "py311"` while this branch raises the runtime floor to 3.12 (`python/pyproject.toml` `requires-python = ">=3.12"`, `python/ship.py` module guard, `python/pyrightconfig.json` `pythonVersion: "3.12"`). CI and local `make py-lint` will not apply 3.12-aware syntax or version rules from Ruff, so 3.12-only constructs could slip through until runtime. **Suggested fix:** Bump `target-version` to `"py312"` in `python/ruff.toml` in the same change set as the pyproject/pyright bump, and add a structure pin or grep guard so it cannot drift again.

- **risk-integration** `python/.pylintrc:90` — Pylint’s `py-version=3.11` was not updated when the tree moved to a 3.12 runtime contract. `make py-lint` still runs `pylint .` with 3.11 semantics while production Step 8+ requires 3.12. **Suggested fix:** Set `py-version=3.12` (or remove it and run pylint via `$(PYTHON) -m pylint` after pinning `PYTHON` to 3.12).

- **risk-integration** `Makefile:32-36` — Only `py-test` was wired to `PYTHON ?= python3.12`; `py-lint` still invokes bare `ruff`, `pylint`, and `pyright` from whatever is on `PATH`, with no interpreter pin. That diverges from CI (Python 3.12 job) and from the production default path, so a developer can pass local lint with an older toolchain while shipping code that stalls at Step 8+. **Suggested fix:** Run linters through `$(PYTHON) -m ruff`, `$(PYTHON) -m pylint`, and `$(PYTHON) -m pyright` (or document/export `PYTHON=python3.12` as mandatory and enforce it in `py-lint`).

- **risk-integration** `docs/linting.md:30` — The relevant-checks paragraph still says Python tree changes run `py-test` “only when `pytest` is already on `PATH`”, but `scripts/relevant-checks.sh` now requires a `python3.12` binary and `python3.12 -m pytest`. Operators and `/implement` runners can believe checks ran under the production interpreter when they were skipped. **Suggested fix:** Update the `docs/linting.md` relevant-checks bullet to match `maybe_append_py_test_target()` (and mention the `PYTHON ?= python3.12` Makefile default).

- **risk-integration** `scripts/relevant-checks.sh:67-75` vs `skills/implement/SKILL.md:1044-1049` — Relevant-checks gates `py-test` on the presence of a `python3.12` executable, while Step 8+ gates on `python3` with `sys.version_info >= (3, 12)`. On hosts where `python3` is 3.12+ but only exposed as `python3` (no `python3.12` on `PATH`), `/implement` can reach Step 8+ yet silently skip `py-test` during relevant-checks; conversely, `py-lint` has no interpreter gate at all. **Suggested fix:** Align the relevant-checks probe with the SKILL fence (`python3 -c 'import sys; …'`) or invoke `make py-test` only after verifying the same predicate; optionally mirror that check for `py-lint`.

- **risk-integration** `docs/installation-and-setup.md:100`, `skills/report-tokens/scripts/run-analysis.sh:74-76`, `python/pyproject.toml:4` — After bumping the shared `python/` package to `requires-python = ">=3.12"`, docs and the report-tokens wrapper still advertise/enforce a 3.11 floor for `/report-tokens`. An operator on Python 3.11 can satisfy report-tokens prerequisites, then hit a Step 8+ stall late in `/implement` (unless they set `LARCH_SHIP_PR_IMPL=bash` before the session). **Suggested fix:** Raise report-tokens documentation and the `run-analysis.sh` guard to 3.12 (or state clearly that the whole `python/` tree is 3.12+ and 3.11 is unsupported), matching `python/README.md`’s ship-driver line and the workflow prerequisites at `docs/installation-and-setup.md:290`.
