### In-Scope Findings

- **correctness** `python/run_context.py:113-137` — `RunContext.from_env` hydrates `CI_FIX_REBASE_PENDING` from `ship-pr-state.sh` when the env var is unset, but `stall_tracking` / `stall_step` come only from `STALL_TRACKING` / `STALL_STEP` in the environment (`python/run_context.py:136-137`). On the first routine `_write_ship_state` with `ctx.stall_tracking=false`, `python/ship.py:658-660` removes `STALL_TRACKING` and `STALL_STEP` from the merged state file before overlaying phase fields. That contradicts the branch plan/acceptance that orchestrator-seeded stall metadata in `ship-pr-state.sh` should survive `--state-file` merge until the driver is actually in a stall or writes a terminal outcome; `python/test_ship.py` (`test_ship_state_merge_clears_stale_stall_keys_on_healthy_write`) encodes the clearing behavior. A pre–Step-8 stall that later enters Step 8+ can lose disk stall keys on the first healthy Python refresh, so Step 18a / `stall-recovery-report.sh classify` may see `STALL_TRACKING=false` on disk even though the run had stalled earlier. **Suggested fix:** Hydrate `stall_tracking` / `stall_step` from the state file the same way as `ci_fix_rebase_pending`, or skip the `_NON_STALL_STATE_KEYS` pop when the parsed merge dict already has `STALL_TRACKING=true` until `terminal_outcome` or an explicit driver stall sets `ctx.stall_tracking=true`.

- **correctness** `python/ship.py:1509-1521` — On `PrePushConflictHandoff`, the driver writes `RESUME_PHASE`, `CALLER_KIND`, and `CONFLICT_FILES` to `ship-pr-state.sh`, then re-raises. Because `ctx.stall_tracking` is false, the same `_write_ship_state` path strips any existing `STALL_TRACKING` / `STALL_STEP` and writes `STALL_TRACKING=false` (`python/ship.py:658-660`, `701-702`). The exception handler deliberately skips `_write_terminal_state` for `PrePushConflictHandoff` (`python/ship.py:1744-1749`), and `_persist_stall_metadata_if_needed` is also skipped while the handoff is active (`python/ship.py:1855-1859`). Exit 4 JSON therefore says STALLED, but disk has handoff keys without stall shape and no `finalize-state.sh`. `skills/implement/SKILL.md:1112-1113` tells the orchestrator to read stall keys from `finalize-state.sh` when present (often absent here) and scoped keys from `ship-pr-state.sh`; Step 18a four-layer classify (`skills/implement/scripts/stall-recovery-report.sh:638-647`) only sets `stall_tracking=true` from in-memory, ship-pr, finalize, or session — not from `RESUME_PHASE`/`CALLER_KIND` alone. If the orchestrator does not set in-memory `STALL_TRACKING` on Exit 4, classify can return `failure_class=unrecoverable` despite a real `ship_pr_pre_push` conflict. **Suggested fix:** In the handoff `_write_ship_state`, set `stall_tracking=True` with an appropriate `stall_step` (e.g. `rebase` / `ship_pr_pre_push`), or write a narrow partial finalize/ship-pr stall overlay that preserves handoff keys without blocking the no-finalize-until-resolved contract.

- **correctness** `python/ship.py:1272-1278` — When `_resume_plan` returns `start=="done"` (e.g. `PHASE=done` in `ship-pr-state.sh` at `python/ship.py:1077-1087`), `run_ship` returns `Outcome.OK` immediately and does not verify or refresh `finalize-state.sh`. If `PHASE=done` was persisted without a matching terminal finalize (crash between state write and finalize, or partial resume), the driver emits success JSON while Step 18 teardown still depends on `finalize-state.sh` (with `restore-finalize-state.sh` as fallback). JSON outcome and disk state can disagree until restore runs. **Suggested fix:** On the `done` fast path, require a readable finalize with required keys or call `_write_terminal_finalize_if_terminal(Outcome.OK, …)` when finalize is missing but merge completion is otherwise proven.

- **risk-integration** `skills/implement/SKILL.md:1113-1114` — Python Exit 6 fourth-failure stall persistence (`STALL_TRACKING=true` key-rewrite of `ship-pr-state.sh` before Step 16/18) is specified only in prompt prose; `python/ship.py` returns `Outcome.TRANSIENT` without writing stall keys on the fourth failure. Disk/JSON routing diverges if the orchestrator does not follow the SKILL rewrite literally. **Suggested fix:** Either persist stall keys inside `python/ship.py` on the terminal transient-to-stall transition (mirroring bash parity), or add a small helper/script the selector invokes mechanically on the 4th Exit 6.
