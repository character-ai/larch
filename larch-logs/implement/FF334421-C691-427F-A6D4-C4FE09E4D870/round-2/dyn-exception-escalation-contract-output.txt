Reviewing the branch diff and `python/ship.py` around stall persistence and the outer exception handler.
### In-Scope Findings

- **correctness** `python/ship.py:1798-1892` — `_persist_stall_metadata_if_needed` now re-raises on any gap-fill failure, and `main()` overwrites a `ShipResult(Outcome.STALLED)` with `Outcome.INTERNAL_ERROR` (exit 1, detail `stall metadata gap-fill failed: …`). That contradicts the documented best-effort contract for gap-fill (“must never replace STALLED JSON with INTERNAL_ERROR”) and `skills/implement/SKILL.md`, which treats exit 1 / `INTERNAL_ERROR` as a hard tool-failure path that does not run the stall rename / Step 16–18 stall flow. A run can therefore return STALLED from `run_ship` (e.g. `invalid state_file` at 1197–1198, or any stall path that did not write `finalize-state.sh` inline) and still surface exit 1 if gap-fill fails, even though the JSON `detail` still describes a stall. `stall-recovery-report.sh classify` may still see stall keys on disk, but the orchestrator routes on stdout JSON + exit code, not classify alone. **Suggested fix:** Restore fail-open gap-fill: log the breadcrumb and leave `result` / exit code unchanged on gap-fill failure (as `test_main_stalled_metadata_write_failure_surfaces_internal_error` currently encodes the opposite — change the test too). Only escalate to `INTERNAL_ERROR` when `run_ship` itself did not return `STALLED`.

- **correctness** `python/ship.py:1685-1693` — The outer `except (…, ShipError, Stalled, …)` handler maps every `ShipError` (including `_write_ship_state` read failures at 625–626) to `Outcome.STALLED` via `_error_to_result`, then unconditionally calls `_write_terminal_state`, which always invokes `_write_ship_state` again (483–493). If the original failure was “cannot read existing ship state”, the retry typically raises the same `ShipError` inside the handler; that exception is not caught there and escapes `run_ship`, so `main()`’s broad `except Exception` (1883–1887) emits `INTERNAL_ERROR` instead of exit 4. `_write_terminal_finalize_if_terminal` may already have written `finalize-state.sh` with `STALL_TRACKING=true` before the second read fails, yielding exit 1 + `INTERNAL_ERROR` JSON while disk state looks like a stall — a contract split the Python selector does not handle. **Suggested fix:** Do not call `_write_terminal_state` from the outer handler when `exc` is a `ShipError` whose message indicates state-file I/O (`cannot read existing ship state`, etc.), or wrap the handler’s `_write_terminal_state` in `try/except ShipError` and still `return result` with the original stall mapping; alternatively, treat infrastructure `ShipError` as `INTERNAL_ERROR` in `_error_to_result` and skip terminal disk writes for that class.

- **correctness** `python/ship.py:150-151,1687-1692` — `ShipError` is overloaded: semantic stalls (`ensure-pr failed`, validation errors) and infrastructure faults (unreadable `ship-pr-state.sh`) both map to `Outcome.STALLED` and both trigger the outer handler’s terminal rewrite. Semantic cases are covered by `test_main_ensure_pr_stall_creates_finalize_state` and `test_outer_stalled_exception_writes_terminal_state`; infrastructure read failures are only tested as a direct `_write_ship_state` raise (`test_ship_state_read_error_fails_closed`) with no `run_ship` / `main()` integration test for the double-failure path above. **Suggested fix:** Split or tag infrastructure vs semantic `ShipError` (subclass or stable error prefix), route infrastructure failures to `INTERNAL_ERROR` without retrying `_write_ship_state`, and add a test where `Path.read_text` fails mid-run to assert exit code / JSON / finalize-state consistency.
