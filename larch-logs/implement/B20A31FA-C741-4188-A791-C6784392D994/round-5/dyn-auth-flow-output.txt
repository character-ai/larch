Reviewing the branch diff and commit history for Codex auth-flow consistency and risk-integration issues.
### In-Scope Findings

- **risk-integration** `skills/review-and-fix/scripts/review-and-fix.sh:340-343` vs `scripts/launch-codex-implement.sh:316-318,415-418` and `scripts/launch-codex-ci.sh:166-170,230-237` — Only the Step 5 `review-and-fix` Codex branch writes explicit `codex-env-key-failure` / `larch_err` breadcrumbs when `external_codex_env_key_enabled` is true and auth setup or dispatch fails. The three Codex launchers and the health probe still emit generic `codex-auth-setup: failed…` or `auth-retries-exhausted` text with no indication that the run was pinned to the `OPENAI_API_KEY` / `openai-larch-env` path (not `~/.codex/auth.json` login). On `/implement` Step 2 that surfaces as `codex-runtime-failure` bail, which is easy to misread as a generic Codex outage or ChatGPT-plan issue—the exact billing surprise this change targets. **Suggested fix:** Add a shared helper (for example `external_codex_log_env_key_failure <logfile> <exit> <stage>`) and call it from every wired failure path when `external_codex_env_key_enabled` is true: implement launcher sidecar + `append_launch_failure` site, review launcher `.diag`/sidecar, CI launcher sidecar, and probe sidecar on auth-classified failure—parity with `review-and-fix.sh` and the “fail loud” docs in `docs/configuration-and-permissions.md`.

- **risk-integration** `scripts/lib-external-launcher-common.sh:658-666` — `external_prepare_codex_auth` always runs `external_strip_codex_larch_env_provider` and `external_strip_codex_literal_credentials` on an existing temp `config.toml` before it checks `external_codex_env_key_enabled`. The plan’s env-key branch was “no disk provider auth; pass `-c` overrides only,” with strip reserved for login fallback. If a copied `~/.codex/config.toml` cannot be rewritten (permissions, strip edge case), a valid non-empty `OPENAI_API_KEY` still fails auth prep even though argv-only `-c` auth does not require mutating config. Callers then hit the same generic auth-setup failure paths above, with no symlink to login (correct for “no silent ChatGPT fallback”) but poor failure visibility. **Suggested fix:** Branch first: when `external_codex_env_key_enabled`, skip config strip and return 0 after `mkdir -p`; run strip + `auth.json` symlink only on the login/whitespace-only path. Keep the existing fail-closed strip-before-symlink behavior for login mode only.

- **risk-integration** `scripts/check-reviewers.sh:319-321` — Auth-mode-aware stamps fix “cached login `false` blocks env-key retry,” but a fresh `codex-env-key` stamp `true` is still honored for the full TTL even after the key is revoked or rotated. `session-setup` can keep emitting `CODEX_PRESENT=true` / `CODEX_AVAILABLE=true` while every subsequent launcher/probe fails auth on the env-key path, which looks like Codex being “available” but broken rather than an API-key configuration problem. **Suggested fix:** On env-key probe/auth exec failure, write `false` to the env-key stamp (or invalidate both mode stamps), or include a coarse key-presence fingerprint in the stamp key that ignores secret bytes (for example length + last-modified time of `OPENAI_API_KEY` in the environment) so rotation forces a re-probe.
