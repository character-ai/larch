### In-Scope Findings

- **code-quality** `scripts/lib-external-launcher-common.sh:576-585` — In `external_strip_codex_larch_env_provider`, the `skip_larch_provider` rule skips every body line with bare `next` and never calls `update_multiline_state($0)`. Multiline string state (`in_dq_multiline` / `in_sq_multiline`) therefore freezes for the whole skipped block. Two consequences: (1) a `[...]` line inside a triple-quoted value in that table can match `is_table_header`, end the skip early, and leave part of the larch provider table in the file; (2) after the block, `was_in_multiline` can be wrong and top-level strip rules can mis-fire. Harnesses cover headers inside an `instructions = """..."""` block, not multiline values inside `[model_providers.openai-larch-env]`. **Suggested fix:** In the `skip_larch_provider` block, call `update_multiline_state($0)` on every skipped line (including before `next`), and only treat `is_table_header($0)` as ending the skip when `!in_dq_multiline && !in_sq_multiline` (same guard as the other rules).

- **correctness** `scripts/lib-external-launcher-common.sh:594-595` — Login-branch removal of `model_provider` / `env_key` only matches spaced forms with quoted values (`model_provider[[:space:]]*=[[:space:]]*["']openai-larch-env["']`). Common TOML spellings such as `model_provider="openai-larch-env"` or `env_key="OPENAI_API_KEY"` (no spaces around `=`) are left in copied `config.toml`. On the login path that can keep env-key selection active alongside a symlinked `auth.json`, undermining “strip larch-owned env-key artifacts before login fallback.” Tests cover single-quoted and spaced double-quoted forms, not compact double-quoted. **Suggested fix:** Extend the two patterns (or add a small normalizer) so compact `key="value"` / `key='value'` forms are stripped too, and add harness lines for them.

- **code-quality** `scripts/check-reviewers.sh:208-261` — `larch_run_one_codex_probe` appends each `codex_home` to `PROBE_DIRS` and also `rm -rf`s it on success, auth-retry (`return 2`), and failure before returning. EXIT cleanup still walks `PROBE_DIRS`, so behavior is correct, but every probe pass leaves stale paths in `PROBE_DIRS` until script exit. That is harmless today but brittle if later logic assumes entries always exist. **Suggested fix:** Either drop the path from `PROBE_DIRS` when removing the directory early, or rely on a single `trap 'rm -rf "$codex_home"' RETURN` inside the function and only use `PROBE_DIRS` as a backstop—document one cleanup owner.
