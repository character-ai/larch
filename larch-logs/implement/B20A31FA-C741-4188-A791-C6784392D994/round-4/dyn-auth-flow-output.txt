Reviewing branch auth-flow changes: reading the diff, commit history, and key implementation files.
### In-Scope Findings

- **correctness** `scripts/lib-external-launcher-common.sh:522-525` — `external_codex_env_key_enabled` treats any non-zero-length `OPENAI_API_KEY` as “env-key mode,” including whitespace-only values such as `OPENAI_API_KEY='   '`. The plan and docs define unset **or empty** as login fallback; whitespace-only is neither, so those runs stay on the env-key path (no `auth.json` symlink, env-key `-c` overrides) instead of falling back to `codex login`. That diverges from the documented unset/empty contract and can surface as unexplained API-key auth failures rather than login auth. **Suggested fix:** Treat whitespace-only as absent (for example, require at least one non-whitespace character via a value-free check such as `[[ "$OPENAI_API_KEY" =~ [[:space:]]*[^[:space:]] ]]`, or trim in a way that never expands the secret under `set -x`).

- **correctness** `scripts/check-reviewers.sh:317-320` — Codex probe caching is auth-mode-aware (`codex-env-key` vs `codex-login`), but a fresh `false` result in env-key mode is still written to `larch-codex-env-key-present-$USER.stamp` and honored until `LARCH_PROBE_TTL_SECONDS` (default 60s). After a transient env-key probe failure, a corrected or rotated `OPENAI_API_KEY` will not be re-probed within the TTL, so `CODEX_PRESENT=false` can persist even though login-mode stale `false` no longer blocks env-key probes. This misses the plan’s “preferably treat cached `false` in env-key mode as a miss” behavior. **Suggested fix:** On env-key mode, skip the stamp fast-path when the cached value is `false` (always re-probe), or use a separate short TTL / negative-cache policy for env-key failures only.

- **correctness** `skills/review-and-fix/scripts/review-and-fix.sh:279-314` — In `run_coder_dispatch`, a failure to `cp ~/.codex/config.toml` into the temp `CODEX_HOME` sets `codex_rc=1` before `external_prepare_codex_auth` runs, but the failure path always logs `codex-auth-setup: failed…` and, when `external_codex_env_key_enabled`, `codex-env-key-failure: … OPENAI_API_KEY auth path`. That mislabels a config-copy I/O failure as an env-key auth failure and can send operators down the wrong diagnosis path (they may rotate the API key instead of fixing permissions/disk). **Suggested fix:** Distinguish copy failures from auth-prep failures (separate log lines and only emit `codex-env-key-failure` when `external_prepare_codex_auth` or the subsequent `codex exec` actually ran on the env-key path).

### Out-of-Scope Observations

Login-fallback symlink behavior for the implement launcher is therefore less mechanically pinned than for review.
