### In-Scope Findings

- **security** `SECURITY.md:240` — The new Codex env-key paragraph states the key value never appears in “Codex event streams” or “probe output,” but larch does not sanitize Codex CLI output at capture time. On auth/API failures, upstream messages can include partial key material in session-local `${OUTPUT}.events.jsonl`, probe stderr sidecars (`check-reviewers.sh` writes `2>>"$probe_side"`), and `review-and-fix` round artifacts (`coder-codex.events.jsonl`, `coder-codex.wrapper.log`). `append-tool-failure.sh --redact` covers launcher failure paths that use it, but not all Codex stderr/events sinks. **Suggested fix:** Narrow the SECURITY.md claim to what larch controls (no value in larch-written argv/config/`CMD_JSON`/xtrace), and either pipe Codex stderr/events excerpts through `redact-secrets.sh` before they land in sidecars/round dirs, or document that session-local Codex telemetry may contain upstream error text and must be treated as sensitive.

- **risk-integration** `SECURITY.md:240` vs `SECURITY.md:254-260` — Env-key auth intentionally leaves the full `OPENAI_API_KEY` value in the child process environment (Codex reads it via `env_key`), so same-UID introspection (`/proc/<pid>/environ` on Linux, some `ps` variants) can expose the secret for the lifetime of the `codex` process. That surface is not documented for Codex, unlike the explicit `CURSOR_API_KEY` argv/`ps` tradeoff. This branch amplifies exposure by preferring env-key mode whenever the var is set. **Suggested fix:** Add a parallel “process environment visibility” bullet under the Codex env-key section (and `docs/configuration-and-permissions.md`) stating the value stays in environ only, is not written to disk by larch, and shares the same multi-user-host caveats as other env-based CLI auth.

- **security** `scripts/check-reviewers.sh:211-212`, `skills/review-and-fix/scripts/review-and-fix.sh:279-280` — New call sites `cp ~/.codex/config.toml` into ephemeral `/tmp/.../larch-codex-*-home.*` before auth prep. On the env-key branch, `external_prepare_codex_auth` does not strip or redact unrelated config content (`scripts/lib-external-launcher-common.sh:608-609` returns early). If the operator ever stored a literal API key in `~/.codex/config.toml` (legacy/manual setup), that material is duplicated into the temp home for the probe/Step 5 run. Launchers already merge the same file (`launch-codex-implement.sh:297-310`, `launch-review.sh:425-438`); this branch extends the copy pattern. **Suggested fix:** Document that `~/.codex/config.toml` must not contain literal key values; optionally run `redact-secrets.sh` on the copied file (or skip copying provider blocks with inline `api_key`/`key` fields) when `external_codex_env_key_enabled` is true.
