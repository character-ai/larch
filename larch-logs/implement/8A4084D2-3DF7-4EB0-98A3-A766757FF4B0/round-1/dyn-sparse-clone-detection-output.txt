Checking pre-change marketplace logic and whether sparse-checkout leaves other detectable markers.
Checking whether git sparse-checkout metadata offers a more reliable signal than the filesystem probe.
### In-Scope Findings

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:280` — Sparse detection uses `[ ! -d "$MARKETPLACE_CLONE/larch-logs" ]`, so only a missing or non-directory path counts as “sparse.” A regular file or a dangling symlink named `larch-logs` is treated like a sparse clone and routes to `claude plugin marketplace update` instead of the one-time `remove` + `add --sparse` migration path. That contradicts the contract in `skills/upgrade-larch/scripts/upgrade-larch.md:15-16`, which defines legacy state as still having `larch-logs/`, not merely lacking a directory. **Suggested fix:** Treat any existing `larch-logs` path as legacy, e.g. `[ -e "$MARKETPLACE_CLONE/larch-logs" ]` in the `else` branch condition (or combine `! -d` with `[ -f ]` / `[ -L ]` checks), or probe git sparse-checkout state (`git -C "$MARKETPLACE_CLONE" sparse-checkout list`) instead of inferring from filesystem shape alone.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:280-287` — A legacy **full** marketplace clone whose `larch-logs/` directory was removed (or never checked out) but `.git` remains matches the steady-state probe and runs `marketplace update` on a non-sparse worktree. A normal `git pull` on that clone can re-materialize the full tracked `larch-logs/` tree (~59k files) before a later upgrade ever hits the `else` sparse re-add branch, partially defeating the slimming goal for that run and delaying migration. **Suggested fix:** Add secondary legacy signals the sparse cone will never have after migration—e.g. `[ -e "$MARKETPLACE_CLONE/package.json" ]` or `[ -d "$MARKETPLACE_CLONE/mermaid-lint" ]` on pre-migration trees—or require `git -C "$MARKETPLACE_CLONE" sparse-checkout list` to succeed and show the expected cone before taking the update path; otherwise force the `remove` + `add --sparse` branch.

- **correctness** `skills/upgrade-larch/scripts/upgrade-larch.sh:282-286` — On `marketplace update` failure, fallback runs `marketplace remove` with `|| true` and then a mandatory `marketplace add`. If `remove` fails (stale registration, permissions, or a half-updated tree) but `add` also fails, `set -e` aborts after the plugin was already uninstalled at `skills/upgrade-larch/scripts/upgrade-larch.sh:270-271`, potentially leaving `~/.claude/plugins/marketplaces/larch-local` corrupt and `larch-local` not installable without manual cleanup. The script does not surface remove failure or suggest deleting `$MARKETPLACE_CLONE` when add fails. **Suggested fix:** After a failed `remove`, log an explicit warning with the clone path; if `add` fails, extend the verification-failure / `recover()` text to include `rm -rf` of `$MARKETPLACE_CLONE` plus the sparse `marketplace add` command, or gate `add` on a successful remove / absent directory check.

### Out-of-Scope Observations

- **`LARCH_SPARSE_DIRS` usage is correct:** CLI paths at `skills/upgrade-larch/scripts/upgrade-larch.sh:285-286` and `291-292` use intentional word-splitting with `# shellcheck disable=SC2086`; recovery and verification strings at `skills/upgrade-larch/scripts/upgrade-larch.sh:26` and `311` only echo the expanded command and do not execute it—appropriate for copy-paste.
- **`.git` as a file (worktree):** `[ -d "$MARKETPLACE_CLONE/.git" ]` is false, so the script takes the `else` re-add path—safe, if slightly heavy-handed.
- **Pre-existing teardown risk:** Uninstall-before-marketplace at `skills/upgrade-larch/scripts/upgrade-larch.sh:270-271` means any marketplace/install failure leaves the operator without an installed plugin; that pattern predates this branch.
- **Intentional test removal:** `test-upgrade-larch*` references remain only under `larch-logs/` and `CHANGELOG.md`, not in runtime/Makefile surfaces—consistent with Part 4 of the plan.
