### In-Scope Findings

- **risk-integration** `skills/upgrade-larch/scripts/upgrade-larch.sh:81-96` — In `refresh_larch_marketplace`, both the update-failure fallback (`remove_larch_marketplace || true` then `add_sparse_larch_marketplace`) and the legacy/stale-cone branch use the same pattern: a failed `claude plugin marketplace remove` is ignored, but the script still calls `marketplace add` without removing `$MARKETPLACE_CLONE`. When the clone directory and `.git` remain (the case `warn_marketplace_remove_failure` at `skills/upgrade-larch/scripts/upgrade-larch.sh:64-67` targets), `marketplace add` commonly fails with an already-exists error. That trips `set -e` and the `ERR` trap (`skills/upgrade-larch/scripts/upgrade-larch.sh:32`), so `recover()` at `skills/upgrade-larch/scripts/upgrade-larch.sh:24-31` does document `rm -rf`, but only after a hard failure. On the full upgrade path (`skills/upgrade-larch/scripts/upgrade-larch.sh:328-337`), `claude plugin uninstall` has already run, so this failure mode leaves the operator with no installed plugin and a wedged marketplace tree until they run recovery manually. **Suggested fix:** Mirror `recover()` inside the automated re-add paths: if `remove_larch_marketplace` fails (or before any sparse re-add), `rm -rf -- "$MARKETPLACE_CLONE"` when `[ -d "$MARKETPLACE_CLONE" ]`, then call `add_sparse_larch_marketplace`; optionally log that automatic cleanup ran. Keep the existing warning/recovery banner as a backstop for add/network failures.
