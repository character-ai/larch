### In-Scope Findings

1. **Important** (`correctness`) [`scripts/merge-pr.sh:166-170`](scripts/merge-pr.sh) — `FLUSH_COUNT=$(printf '%s\n' "$FLUSH_AHEAD" | grep -c . 2>/dev/null || echo "0")` is unsafe: when `git log "${PR_HEAD_OID}..HEAD"` yields no subjects (empty range: local behind PR, unrelated divergence, or any OID mismatch with an empty stub log), `grep -c .` prints `0` but exits `1`, so `echo "0"` runs and `FLUSH_COUNT` becomes two lines (`0` twice). Then `[[ "$FLUSH_COUNT" -gt 0 ]]` triggers `bash: [[: 0\n0: syntax error in expression` on **stderr** while still falling through to the non-recoverable error branch. Scenario: normal `oid_mismatch` / refuse path now emits spurious bash errors; any caller that treats stderr as fatal noise is at risk. Suggested fix: drop the `|| echo "0"`, use `grep -c . || true` without appending, or replace with a line count that does not treat “zero matches” as failure (e.g. `wc -l` after `grep -v '^$'`).

2. **Nit** (`risk-integration`, `plan`) [`scripts/test-merge-pr.sh:334-392`](scripts/test-merge-pr.sh) — Plan/feature called for merge success when **1–5** flush-only commits are ahead; K only covers **one** flush commit. The cap `>5` is covered (N); intermediate counts (e.g. exactly **5** flush-only lines) are not exercised on the success path. Suggested fix: add one sub-test with five valid `chore(larch-logs): flush …` subjects and the same recovery stubs, expecting `MERGE_RESULT=admin_merged` (or `merged` per harness).

3. **Nit** (`code-quality`) [`scripts/merge-pr.md:26-31`](scripts/merge-pr.md) — The new section says recovery runs “Before the OID precondition in step 1,” but the script implements recovery **inside** the OID mismatch handling for the same-version gate. Suggested fix: rephrase to “When the OID precondition fails, …” so docs match control flow.
