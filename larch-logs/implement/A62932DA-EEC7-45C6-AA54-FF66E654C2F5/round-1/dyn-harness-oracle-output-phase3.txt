### In-Scope Findings

- **correctness** `scripts/test-design-structure.sh:68-93` — The `assert_gate_b_bypass_branch_sentinels` function uses `index($0, ": > \"$DESIGN_TMPDIR/.completed/step-3\"")` as the awk filter to locate a sentinel-write line, then also checks `': > "$DESIGN_TMPDIR/.completed/step-3"'` in the `required` inner loop. Because the awk filter and the `step-3` required literal are identical strings, the required check for `step-3` is **unreachable as a failure path**: if the awk matched, the line already contains step-3; if it didn't match, `fail "$branch branch missing literal Gate-B-bypass sentinel-write line"` fires before the required loop runs. Concretely, if a branch's prose has the step-3.5 and step-3.6 writes but is missing the step-3 write, the awk finds no matching line and emits the "missing literal Gate-B-bypass sentinel-write line" message rather than "step-3 sentinel", silently hiding the true cause of failure. The negative self-tests in `run_gate_b_bypass_branch_sentinel_self_tests` only exercise removal of `step-3.5`, so this diagnostic gap is never caught by the self-test suite — a removal of `step-3` from a non-`plan-size-trigger` branch would trigger the wrong error label. **Suggested fix:** Change the awk filter to key on the branch token alone (`index($0, token) && index($0, "Gate-B-bypass")` or any prose unique to bypass lines), then validate all four required literals — including step-3 — in the `required` loop with accurate labels. Alternatively, remove the redundant step-3 entry from the `required` for-loop and accept that step-3 absence is reported via the "missing literal … sentinel-write line" path.

- **correctness** `scripts/test-design-structure.sh:211-231` — The `write_gate_b_bypass_fixture` helper only parameterizes removal of `step-3.5` (via `if [[ "$branch" == "$missing_branch" && "$missing_sentinel" == step-3.5 ]]`). Any other `missing_sentinel` value (`step-3`, `step-3.6`, `mkdir`) silently produces a complete fixture — the parameter is ignored. The self-tests `run_gate_b_bypass_branch_sentinel_self_tests` only pass `step-3.5`, so the silent-ignore behaviour is never observed, but it means the negative tests do not cover `step-3.6` absence from non-`plan-size-trigger` branches, which is an accepted requirement of the pin. If `step-3.6` were dropped from (e.g.) the `tally-error` bullet in SKILL.md, CI would catch it (the `required` loop checks `step-3.6`) but the self-test would not prove the assertion can detect that specific omission. **Suggested fix:** Add a `step-3.6`-removal case inside `write_gate_b_bypass_fixture` (e.g. a parallel `step36` variable mirroring `step35`), and add a third negative control in `run_gate_b_bypass_branch_sentinel_self_tests` that removes `step-3.6` from `degraded-empty-collector` and asserts the assertion FAILS.
