### In-Scope Findings

- **correctness** `python/git.py:26-67` — `rev_parse`, `current_branch`, `rev_count`, and `merge_base` always parse `stdout` and never inspect `CommandResult.returncode`. On a failed `git` invocation (missing ref, detached HEAD with `symbolic-ref`, etc.), callers get empty strings or `0` instead of a failure signal, which can mis-drive later ship-pr ground-truth checks. **Suggested fix:** After each `_run`, require `returncode == 0` before parsing (raise `ShipError` or return `CommandResult` and let callers branch); only use the typed helpers when the command succeeded.

- **correctness** `python/gh.py:56-393` — All typed `gh` helpers (`pr_view`, `pr_for_branch`, `pr_create`, `run_list`, `run_view`, `failed_jobs`) call `json.loads` on stdout without checking `returncode`, including after `_retry_read` exhausts retries. A failed `gh` call (auth, 404, malformed output) surfaces as `JSONDecodeError` or fabricated empty objects instead of a controlled error. **Suggested fix:** Gate parsing on `result.returncode == 0`; on failure, raise a typed error or return `StepResult` with detail from `_combined(result)` so later phases do not treat CLI failures as valid PR/run state.

- **correctness** `python/gh.py:120-156` — `pr_create` deduplicates only via `pr_for_branch` and has no equivalent of `recover_existing_pr_after_create_conflict` in `scripts/create-pr.sh` (lines 192–229, 286–290). If the list probe returns `None` (transient/persistent `gh pr list` failure) or `gh pr create` fails with “pull request already exists”, the wrapper still attempts `json.loads` on failure output rather than recovering the existing PR. **Suggested fix:** After a non-zero `pr create`, scan combined output for the existing-PR conflict pattern and re-list by `--head` (with retry); only parse create JSON on `returncode == 0`, matching bash recovery semantics.

- **correctness** `python/agents.py:171-202` — `run_waterfall` iterates `tiers` in list order and only applies first-fixer short-circuit when `idx == 0` and `tier == first_tier`. Bash `run_ci_fix_vendor` rotates the tier loop via `start_attempt % 3` (`scripts/ship-pr.sh:2032-2035`), so the “first fixer” is `tiers[offset]`, not always `tiers[0]`. Calling `run_waterfall(config.FIXER_TIER_ORDER, …, first_tier="codex")` without pre-rotating the list will not short-circuit on the real first fixer. **Suggested fix:** Rotate `tiers` inside `run_waterfall` (find `first_tier` index, `tiers = tiers[i:] + tiers[:i]`) or drop `first_tier` and take `start_offset: int` mirroring bash; add a test with `start_offset=1`.

- **correctness** `python/agents.py:122-165` — `build_launch_argv` / `launch_tier` invoke `scripts/launch-*-ci.sh` as a relative path, while live bash uses `"$SCRIPT_DIR/launch-…-ci.sh"` (`scripts/ship-pr.sh:2044-2058`). Unless `runner.run(..., cwd=<repo-root>)` is always set, launches fail from other working directories. **Suggested fix:** Resolve launcher paths from a known repo root (e.g. `Path(__file__).resolve().parents[1] / "scripts" / …`) or require and document `cwd`; add a unit test asserting absolute or repo-root-relative argv.

- **correctness** `python/git.py:22-23`, `python/gh.py:34-35` — `_run` / `_gh` call `runner.run` with no `timeout`, unlike `agents.launch_tier` (`agents.py:165`). Any stuck `git`/`gh` child blocks the whole ship-pr process indefinitely despite `config.SUBPROCESS_DEFAULT_TIMEOUT_SEC`. **Suggested fix:** Pass `timeout=float(config.SUBPROCESS_DEFAULT_TIMEOUT_SEC)` (or per-operation overrides) through the git/gh wrappers, and assert timeout `returncode` handling in stub-runner tests.

- **correctness** `python/proc.py:48-55` — When `env` is not `None`, `subprocess.run` receives only the supplied mapping, replacing the process environment instead of merging with `os.environ`. A partial env dict drops `PATH` and breaks `git`/`gh`/launcher execution. **Suggested fix:** Use `env=None` to inherit, or `env={**os.environ, **dict(env)}` when callers pass overrides; document the contract and add a test that `PATH` is preserved.

- **correctness** `python/test_gh.py:1-91` — Tests use order-based `RecordingRunner` stubs with truncated argv keys (e.g. `("gh", "pr", "list")` vs the full `pr list --repo …` argv) and do not cover transient retry re-invocation or full argv construction required by the plan. Regressions in retry policy, flags, or dedupe argv will not be caught before integration. **Suggested fix:** Assert full per-call argv (including `--repo`, `--json`, `--head`), add a test where the first `gh` response carries a transient signature and the second succeeds, and verify mutating ops still invoke exactly once.
