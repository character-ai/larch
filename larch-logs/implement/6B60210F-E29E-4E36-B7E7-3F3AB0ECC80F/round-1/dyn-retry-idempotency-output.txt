Reviewing retry/idempotency in `retry.py` and `gh.py` against bash precedent and the branch diff.
### In-Scope Findings

- **risk-integration** `python/gh.py:1322-1393` — `pr_for_branch` and `pr_create` never inspect `CommandResult.returncode` after `_retry_read` / `_gh`. On any non-zero `gh pr list` (auth failure, rate limit without a transient signature, exhausted transient retries), `pr_for_branch` still does `json.loads(result.stdout or "[]")` and returns `None` when stdout is empty, which is indistinguishable from “no PR for this branch.” `pr_create` then issues a mutating `gh pr create`. That is the opposite of fail-closed deduplication: a failed lookup can trigger a second create attempt (duplicate PR or a conflict error) instead of surfacing the list failure. On create, `json.loads(result.stdout)` runs unconditionally, so real `gh` failures are masked as `JSONDecodeError` rather than propagating stderr/exit code. **Suggested fix:** After `_retry_read`, treat `returncode != 0` as an error (raise `ShipError` / `TransientNetworkError` with redacted combined output). Only treat an empty list as “no PR” when `returncode == 0`. On `pr_create`, check `result.returncode` before parsing; port `recover_existing_pr_after_create_conflict` from `scripts/create-pr.sh:192-229` for the “already exists” race (list → create → conflict → re-list / URL parse) so dedup matches bash idempotency.

- **risk-integration** `python/gh.py:42-53,186-275` — `_retry_read` returns only `retried.value` and drops `RetryResult.last_returncode` / `attempts`, so every read wrapper (`pr_view`, `run_list`, `run_view`, `failed_jobs`, etc.) cannot distinguish “successful empty result” from “failed after retries.” Helpers that coerce with `json.loads(result.stdout or "[]")` (`pr_for_branch`, `run_list`) can return empty tuples/`None` on persistent `gh` errors, which will mislead later idempotency logic (e.g., “no workflow runs,” “no failed jobs”) when Phase 7 wires this module into the state machine. **Suggested fix:** Have `_retry_read` raise on final non-zero `returncode` (or return a small frozen `GhResult` with `ok`, `result`, `attempts`). Stop using `or "[]"` unless `returncode == 0`; otherwise fail closed.

- **risk-integration** `python/gh.py:1357-1393` — Deduplication is check-then-create only: no post-create conflict recovery equivalent to `scripts/create-pr.sh:268-290` + `recover_existing_pr_after_create_conflict`. Bash retries `gh pr create` only inside `with_transient_retry`, but on “pull request for branch … already exists” it re-lists and returns `PR_STATUS=existing` instead of failing. Python correctly avoids retrying the mutating create, but without conflict recovery a TOCTOU race (list empty, concurrent create succeeds) surfaces as an unhandled error instead of returning the existing PR—operators may retry the whole step and amplify side effects. **Suggested fix:** On non-zero `pr create`, scan combined output for the same conflict substring bash uses; on match, call `pr_for_branch` again (or parse PR URL from stderr) and return that `PullRequest` without re-running create.

### Out-of-Scope Observations

- **risk-integration** `python/test_gh.py:44-91` — The implementation plan calls for tests that idempotent reads retry on transient signatures and mutating ops do not; only dedup and `pr_merge` single-call are covered. No regression lock on retry policy yet (lower urgency while `python/` is not on the live path).

- **correctness** `python/retry.py:21-55` vs `scripts/lib-net.sh:7-17` — `is_transient_net_signature` matches bash structure (including `no such hosted` / `no such hostname` negatives); `test_retry.py` exercises parity on a small vector set. No retry-classification drift found in-scope.

- Mutating wrappers (`pr_merge`, `run_rerun`, `issue_comment`, `issue_edit`) call `_gh` once with no `with_transient_retry` — aligned with the plan’s no-auto-retry policy for non-idempotent ops.
