### In-Scope Findings

- **architecture** `python/test_gh.py` — The plan’s per-operation retry contract for `gh.py` is implemented via `_retry_read` → `with_transient_retry` in `python/gh.py:50-61`, but `test_gh.py` never exercises it: there is no stub-runner test that simulates a transient signature on `pr_view` / `run_list` and asserts multiple `gh` invocations, and no complementary test that a read op exhausted after retries surfaces the last failure. Only `test_mutating_helpers_build_argv_without_retry` guards the no-retry path. That leaves the most failure-prone seam (idempotent `gh` reads under network flake) unverified while later phases will treat `gh.py` as canonical. **Suggested fix:** Add colocated tests with `RecordingRunner` returning transient stderr (e.g. `Connection reset by peer`) for the first N−1 calls and success on the last, asserting call count and parsed records; add a failure-path test that after `TRANSIENT_RETRY_MAX_ATTEMPTS` the public API raises `ShipError` (or documents returning the last `CommandResult` if you change `_ensure_success` policy).

- **architecture** `Makefile:25` — `lint` now lists `py-lint` and `py-test` as hard prerequisites, so every `make lint` requires Python 3.12, installed `ruff`/`pylint`/`pyright` (and thus Node for pyright), and pytest. The Phase 1 plan only added standalone `py-lint` / `py-test` targets and documented `relevant-checks.sh` as running `py-test` always while skipping `py-lint` when tools are absent; it also stated no behavior change to existing Makefile targets. This couples the legacy bash-centric lint umbrella to the new Python toolchain and will break contributors who run `make lint` without the dev env. **Suggested fix:** Remove `py-lint` / `py-test` from the `lint:` prerequisite list (keep them as explicit targets and in CI); align local ergonomics with `scripts/relevant-checks.sh`’s conditional `py-lint` behavior.

- **architecture** `python/agents.py:38-43,172-207` — `run_waterfall` correctly short-circuits on first-tier `failure_class == "other"` (parity with `scripts/ship-pr.sh:2076-2082`), but `WaterfallResult` only carries `short_circuited: bool`, not the bash bail token `first-fixer-non-health` that ship-pr maps to exit 3 (`scripts/ship-pr.sh:2081,2595-2597`). Phase 7 orchestration must re-derive bail semantics from `attempts[0].failure` instead of consuming a typed, stable contract. **Suggested fix:** Extend `WaterfallResult` with an optional `bail_reason: str | None` (e.g. `"first-fixer-non-health"`) set when short-circuiting on first-tier non-health, and unit-test that field against the existing waterfall fixtures.

- **architecture** `python/gh.py:43-47,50-61` — `python/errors.py` and `python/outcomes.py` define `TransientNetworkError` / `Outcome.TRANSIENT` / `StepResult`, but the subprocess stack never uses them: `with_transient_retry` returns `RetryResult`, and `_retry_read` always ends in `_ensure_success` raising generic `ShipError`. Later ship-pr phases will need a single outcome vocabulary for re-entrant idempotent steps; without a mapping layer now, Python and bash state machines risk divergent classification of the same transient `gh`/`git` failures. **Suggested fix:** Either have exhausted transient retries raise `TransientNetworkError` (or return `StepResult(Outcome.TRANSIENT, …)`) from a thin `gh`/`git` wrapper, or add a shared `command_result_to_step_result` helper in `outcomes.py` and use it at the `gh`/`git` boundary so Phase 7 does not re-invent error typing.
