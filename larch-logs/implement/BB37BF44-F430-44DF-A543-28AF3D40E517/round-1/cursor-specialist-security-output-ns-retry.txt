### In-Scope Findings

- **correctness** `.github/workflows/ci.yaml:187-195` — The new `actions/cache` step caches `~/.local/lib/python${{ steps.setup-python.outputs.python-version }}/site-packages`, but the install step runs plain `pip install -r .github/workflows/requirements-test-harnesses.txt` with no `PIP_USER`/`--user`, so on `ubuntu-latest` packages normally land under the setup-Python toolcache prefix (for example `/opt/hostedtoolcache/Python/.../lib/python3.12/site-packages`), not under `~/.local/...`. Even if you switched to user installs, `steps.setup-python.outputs.python-version` is typically a full `3.12.x` string while the user-site directory layout is usually `.../python3.12/site-packages`, so the interpolated path can miss the real directory. Together, the cache can restore an empty or irrelevant tree while `cache-hit` becomes `true`, the guarded `pip install` is skipped, and matrix shards can fail immediately with missing `yaml`/import errors or flake depending on ordering. **Suggested fix:** Cache the directory that actually receives wheels (for example run `python -c 'import site; print(site.getsitepackages()[0])'` after `setup-python` and cache that path, or use `pip install --user` and cache the path from `python -m site --user-site`), and ensure the path segment matches how Python names that directory (major.minor, not necessarily the full `setup-python` output string). Alternatively drop the second cache and rely on the existing `cache: pip` from `actions/setup-python` if site-package caching is not worth the path fragility.
