### In-Scope Findings

- **correctness** `scripts/launch-review.sh:986-1057` — The branch introduces a second retry counter (`EMPTY_RESULT_ATTEMPT`) that is bounded independently of `TRANSIENT_ATTEMPT`, both gated by `MAX_TRANSIENT_RETRIES=2`. That diverges from the binding plan decision to **reuse `TRANSIENT_ATTEMPT`** and cap total cursor backend calls at **3** per slot. In a single auth-loop pass, exit-code transients can consume up to two retries (three calls with exit 4/8) and empty-result failures can consume up to two more (three calls with exit 0 + empty `.result`), yielding up to **five** backend invocations before terminal `CURSOR_EMPTY_RESPONSE` (e.g., two exit-8 transients → one empty → one empty retry → success = **four** calls, as encoded in `SL-cursor-transient8-then-empty`). Under an ~8-slot parallel burst, that multiplies backend load versus the planned shared budget and works against the jitter goal of reducing synchronized rate-limit pressure. **Suggested fix:** Drop `EMPTY_RESULT_ATTEMPT` and drive empty-result retries through the existing `TRANSIENT_ATTEMPT` counter (increment before `continue` in either branch, single `_cursor_transient_backoff` using that counter), so the combined transient budget stays at `MAX_TRANSIENT_RETRIES + 1 = 3` total calls; update `SL-cursor-transient8-then-empty` and the docs in `scripts/launch-review.md` / `docs/configuration-and-permissions.md` to match the shared-budget semantics.
