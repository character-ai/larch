### In-Scope Findings

- **security** `scripts/launch-review.sh:1170-1214` — The new `${OUTPUT}.diag` writer interpolates jq-extracted envelope fields (`_diag_error`, `_diag_type`, `_diag_subtype`, `_diag_request_id`, etc.) into a `FAILURE_REASON=…` line via bare `printf '%s'` with no newline or delimiter sanitization. `jq -r` on a string `.error` preserves embedded newlines; the object branch can emit multi-token JSON on one line. That breaks the intended two-line `TOOL=` / `FAILURE_REASON=` sidecar shape (extra physical lines can look like new KV records), diverges from existing launcher diagnostics that use `head -1 … | tr '\n' ' '` (e.g. `503-504`), and feeds richer attacker-controlled text into downstream surfaces: `compose-collector-failure-log.sh` `cat`s `.diag` without the redaction path used for `*.launch-stderr` / `*.stderr-tail` (`60-62`), and plan-review collector failures paste that composed log into `execution-issues.md` via `append-tool-failure.sh --redact` (`plan-review-loop.sh:923-934`). `collect-agent-results.sh` only collapses newlines when `build_failure_reason` runs (`345-357`); the `CURSOR_EMPTY_RESPONSE` path hardcodes `FAILURE_REASON` and never reads the new `.diag` (`869-872`), so the enriched diagnostic mainly reaches operators through the failure-log / execution-issues pipeline, where structure corruption and regex-shaped substrings in untrusted envelope text are the practical risk. **Suggested fix:** Before interpolation, normalize every extracted field the same way as model-args failures (`tr '\n\r|'` to spaces, collapse runs, cap length), or emit envelope diagnostics as a single JSON line / base64 blob instead of inline `printf` fragments; add a harness case with a stub envelope whose `.error` contains embedded newlines and `usage limit` / `TOOL=fake` substrings and assert `.diag` stays two lines and `compose-collector-failure-log` output survives `--redact`.

- **security** `scripts/launch-review.sh:1124-1201` — The branch documents and tests retention of the full Cursor JSON envelope at `${OUTPUT}.json` while only `${OUTPUT}.diag` passes through `redact-tmpdir-paths.sh` and `redact-secrets.sh` (`1206-1211`). Envelope fields such as `.error` (string or object) are not covered by the redactor’s pattern families (`scripts/redact-secrets.sh` header: opaque bearer tokens and connection strings are explicit non-coverage). The new `.diag` line explicitly points operators and tooling at `(full envelope: ${OUTPUT}.json)`, increasing the chance that session tmpdirs, failure logs, or manual debugging expose backend error text that never went through the `.diag` scrubber. **Suggested fix:** Run the same redaction pipeline on `${OUTPUT}.json` (or a redacted copy used for diagnostics), omit the pointer to the raw envelope from operator-visible `.diag` text, or restrict full-envelope retention to a test-only / opt-in env flag.

### Out-of-Scope Observations

- **`scripts/compose-collector-failure-log.sh:60-62`** — Pre-existing: `.diag` sections are `cat` without `render_failed_agent_stderr_tail` / secret redaction; this branch amplifies how much untrusted content can land there, but the missing redaction path predates #3393.

- **`scripts/collect-agent-results.sh:869-872`** — Pre-existing: `CURSOR_EMPTY_RESPONSE` slots discard the new rich `.diag` for the pipe-delimited `FAILURE_REASON` field, so the instrumentation’s primary consumer today is failure-log composition, not the collector RESULTS row.

- **`${OUTPUT}.diag.$$` temp naming (`1188`, `1216`)** — Not a practical collision issue in the parallel burst: each reviewer slot uses a distinct `OUTPUT` path and each launcher runs in its own process (`$$` differs); cleanup removes both `$_diag_tmp` and `${_diag_tmp}.out`. No change required for safety on that basis alone.
