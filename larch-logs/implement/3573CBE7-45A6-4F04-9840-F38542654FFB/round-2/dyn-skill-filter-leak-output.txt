Reviewing the diff and the scout-notes focus areas in the audit-resolve and audit-map scripts.
### In-Scope Findings

- **correctness** `.claude/skills/audit-runs/scripts/audit-resolve-prs.sh:86-96` — For `--skill=implement`, `filter_prs_for_skill` keeps every merged-to-`main` PR whose title does **not** match the design regex (`^chore\(larch-logs\): design run [0-9A-F-]+$`). That is a negative filter only: it does **not** restrict to implement log-flush PRs (`chore(larch-logs): flush implement run …`) or other run-log-bearing merges. Bulk modes (`since last audit`, `since <ISO>`, `last N PRs`) therefore still admit feature/fix/automation PRs with no `larch-logs/implement/<RUN_ID>` tree. Downstream, `audit-map-runs.sh:258-275` emits rows with an empty `run_id` for those PRs, and the orchestrator in `.claude/skills/audit-runs/SKILL.md:90-100` still invokes `audit-scan-run.sh` with `--run-dir "larch-logs/implement/"`, which hits the `run-dir-invalid` guard in `audit-scan-run.sh:99-102` (or `run-dir-missing` when the path is wrong). That yields error NDJSON per PR rather than a clean skip, and it undermines the stated goal that `--skill` selects which skill’s run logs are analyzed. Design gets a positive title filter; implement does not get a symmetric positive filter. **Suggested fix:** For `--skill=implement`, apply a positive title filter aligned with the real flush PR title (e.g. `^chore\(larch-logs\): flush implement run [0-9A-F-]+$`), or filter to PRs whose `manifest.json` exists under `larch-logs/implement/` before building `PR_LIST`. Document in `audit-resolve-prs.md` if “all non-design merges” is intentional for implement.

- **correctness** `.claude/skills/audit-runs/scripts/audit-resolve-prs.sh:139,222-229` — `fetch_merged_main_prs_json` always runs `filter_prs_for_skill` before callers slice the list, so `last N PRs` for `--skill=implement` means “last **N** merges among non-design titles,” not “last **N** merges to `main`” as on `main` and as `audit-resolve-prs.md:28` still describes. If recent merges include design log PRs, the implement batch can omit genuinely recent implement-log PRs and include older non-design PRs instead. **Suggested fix:** Either document skill-specific semantics in the contract/SKILL (“last N skill-eligible PRs”) or apply skill filters **after** selecting the global last-N window (design: intersect; implement: positive filter or post-filter by map success), so operator-facing “last N PRs” stays aligned with merge order on `main`.

### Out-of-Scope Observations

- **Pre-existing breadth:** On `main`, `audit-resolve-prs.sh` already returned all merged-to-`main` PRs with no title filter; the implement branch mainly **excludes** design-titled PRs. Noise from unmapped feature PRs is not new, only slightly narrowed.

- **`--log-root` validation bypass:** In `audit-map-runs.sh:60-71`, cross-skill checks run only when `--log-root` matches `larch-logs/{design,implement}` (or `*/larch-logs/…`). Hermetic tests correctly use arbitrary temp roots (e.g. `test-audit-runs.sh:2609`); production SKILL paths never pass `--log-root`. Not a production correctness gap.

- **`run-dir-invalid` guard:** `audit-scan-run.sh:99-102` reliably rejects skill roots for both relative (`larch-logs/design`) and absolute temp paths (`test-audit-runs.sh:2669-2672`). Empty `RUN_ID` expanding to `larch-logs/$SKILL/` is caught; per-run paths with a UUID basename are not.

- **Mis-titled design PRs:** A PR titled `chore(larch-logs): flush design run <UUID>` (commit-subject shape) does not match the design regex (`test-audit-runs.sh:2614-2621`) and would be included in `--skill=implement` bulk lists—edge case only if titles diverge from `design-log-publish.sh:601`.
