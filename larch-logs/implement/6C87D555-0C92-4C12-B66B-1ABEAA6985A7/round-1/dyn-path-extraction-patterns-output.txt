### In-Scope Findings

- **correctness** `scripts/lint-fix-loop.sh:111` — The fifth extractor (`grep -oE '[A-Za-z0-9_.-]+/[A-Za-z0-9_./-]+'`) matches any two-segment token with a slash, not only linter file citations. Because `_lint_fix_path_safety_ok` only requires `[ -f "$REPO_ROOT/$path" ]`, incidental mentions of real paths in the checks log (script names in banners, cross-references in hook output, plan-like prose in stderr) can land in `## In-scope files` even when they are not the reported failure. That steers the external coder toward edits the log never flagged, which is the same class of mis-scoping this change is meant to stop (just narrower than “fix the whole repo”). **Suggested fix:** Drop or sharply narrow pattern 5 (e.g. require a known extension on both sides or anchor to the same line context as patterns 1–4); alternatively gate inclusion on failure-adjacent context (same line as `SC####`, `MD###`, `Failed`, `error:`, etc.) instead of existence alone.

- **correctness** `scripts/lint-fix-loop.sh:102-106` — The line-start and whitespace-prefixed `path:line` patterns use `[^:[:space:]]+:[0-9]+`, which also matches extensionless coordinates such as `Makefile:42` inside GNU make’s `*** [Makefile:42: target] Error` lines and the `SKIPPED_NON_CANONICAL: scripts/foo.sh:1196:` prefix emitted by `scripts/check-contains-pins.sh` (see `scripts/check-contains-pins.sh:164` and captured implement logs under `larch-logs/implement/*/breadcrumbs/larch-quiet-run-relevant-checks-captured.sh-*.log`). `Makefile` exists at repo root, so it can appear in-scope while the real shellcheck/pre-commit failure is elsewhere; `SKIPPED_*` paths are diagnostics, not failing checks. The repo already documents this ambiguity for similar grep in `scripts/eval-research.sh:391-393`. **Suggested fix:** Exclude known non-failure prefixes (`SKIPPED_NON_CANONICAL:`, `make[` recipe brackets) before accepting `path:line`, or require a file extension / shellcheck `In … line` form for extensionless basenames.

- **correctness** `scripts/lint-fix-loop.sh:123` — After filtering, `awk … | head -n "$cap"` keeps the first 50 unique paths in candidate-file order (patterns 1→5). A log with many distinct `path:line` hits (e.g. numerous `SKIPPED_NON_CANONICAL` lines plus real violations) can fill the cap before a later, actual failure path is reached, so `## In-scope files` may omit the file that must be fixed while still presenting a non-empty scoped list. **Suggested fix:** Prefer paths tied to the last failing phase or last error block in the excerpt, rank shellcheck `In …` / hook failure lines above generic `path:line` and slash-only matches, or raise/prioritize rather than blind first-50 truncation.
