Reviewing the branch diff and dirty-tree recovery architecture.
Checking whether the parse block runs unconditionally after non-zero wrapper exits:
### In-Scope Findings

- **architecture** `skills/implement/SKILL.md:403-419` — The dirty-tree recovery fence only branches on `_inv_rc -eq 2`, then unconditionally file-parses `$IMPLEMENT_TMPDIR/bootstrap-routing.env`. On a failed `--mode resume` call (`_inv_rc` neither 0 nor 2), the wrapper does not rewrite that file (`scripts/implement-bootstrap-invoke.sh:135-137,164`), but `IMPLEMENT_TMPDIR` is already exported (`skills/implement/SKILL.md:388-389`), so the parse still reads the first-pass artifact that contains `IMPLEMENT_BAIL_REASON=dirty-tree`. That re-applies the bail reason the prose explicitly `unset`s at recovery entry (`skills/implement/SKILL.md:385`), making a bootstrap/wrapper failure look like another dirty-tree bail and preventing a clean recovery retry. This is amplified by the new file-first transport; the old resume path parsed stdout only and did not resurrect bail state from disk after a non-2 failure. **Suggested fix:** Gate routing re-parse on `_inv_rc -eq 0` (both Step 0 call sites), or unlink/ignore `bootstrap-routing.env` when the wrapper returns non-zero; on dirty-tree recovery specifically, treat any non-0/non-2 resume as a hard stop instead of continuing to the routing table.

- **architecture** `skills/implement/SKILL.md:416-449` — The shared routing parse uses unconditional overwrite from `bootstrap-routing.env`, but stdout fallback goes through `_inv_apply_routing_line_if_empty`, which preserves any pre-recovery shell value when a key is absent from both transports. Item 3 prose requires post-recovery routing keys (`IMPLEMENT_BAIL_REASON`, `BRANCH_NAME`, `BRANCH_ACTION`, `PLAN_FILE`, etc.) to come from the resumed tail, not the pre-recovery pass (`skills/implement/SKILL.md:385`). If the env file is skipped (symlink guard) or incomplete, stale first-pass values can leak into later steps after operator cleanup. **Suggested fix:** For the dirty-tree recovery fence only, parse resumed stdout with the same unconditional `_inv_apply_routing_line` helper used for the file path (or reset all routing keys before re-parse); keep `if_empty` fallback solely for the initial Step 0 path where `IMPLEMENT_TMPDIR` is not yet known.

### Out-of-Scope Observations

- **Pre-existing resume/coder gap:** `--mode resume` hardcodes `--up-to-phase plan --resume-plan-tail` (`scripts/implement-bootstrap-invoke.sh:76-77`), so dirty-tree recovery never re-runs `phase_coder_select` even though initial `--mode initial` stops at `--up-to-phase coder`. After plan-only resume, implicit-waterfall runs can still have an empty `coder` unless the operator passed `--coder` on argv (and the routing envelope may clear it). This matches the old inline dirty-tree fence; `test-implement-bootstrap.sh` covers the coder-resume variant separately (`B7-coder-dirty-tree`) but the SKILL orchestrator path does not use it.

- **Maintainability:** The routing-envelope parse block is duplicated verbatim in the initial Step 0 fence (`skills/implement/SKILL.md:321-365`) and the dirty-tree recovery fence (`skills/implement/SKILL.md:407-451`), increasing drift risk between the two orchestration paths; no harness asserts they stay identical.

- **Test gap:** `skills/implement/scripts/test-implement-bootstrap-invoke.sh` validates resume argv/`IMPLEMENT_TMPDIR` pass-through and envelope emission, but has no case for dirty-tree recovery semantics (failed resume + stale `bootstrap-routing.env`, or post-recovery full routing refresh vs pre-recovery shell state).
