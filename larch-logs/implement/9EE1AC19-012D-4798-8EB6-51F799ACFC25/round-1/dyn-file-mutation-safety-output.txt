Reviewing file-mutation safety in the new Python modules: reading the diff and the cited code paths.
Checking bash parity for rollback behavior and whether `git.add` failures are handled.

Checking `git-commit.sh` behavior and whether `commit_changelog` can write without a content change path:
### In-Scope Findings

- **risk-integration** `python/version_bump.py:511-514,537-578,584-589` — `rollback_before_commit()` restores `plugin.json` with `shutil.copy2` but never removes `plugin_path.bump-backup`, unlike `apply-bump.sh` which uses `mv "$BACKUP" "$PLUGIN_JSON"` and therefore consumes the backup on every rollback. After any fetch/guard/commit failure that calls rollback, an untracked `.claude-plugin/plugin.json.bump-backup` remains; it is not in `APPLY_BUMP_ALLOWED_UNTRACKED_SUFFIXES`, so a follow-up `apply_bump` hits the clean-tree guard and refuses to bump until the artifact is removed manually. **Suggested fix:** Mirror bash: `backup_path.replace(plugin_path)` (or `unlink` after a successful restore) inside `rollback_before_commit`, and `unlink`/`rm -f` the backup in `backup_rewrite_stage` error paths; only leave the backup file transiently between backup and successful commit.

- **risk-integration** `python/version_bump.py:516-531,576-578` — When `backup_rewrite_stage` returns `ApplyResult` from its `except` block, or when the retry loop returns early on `stage_err`, there is no call to `rollback_before_commit()` and no backup cleanup. Bash removes `"$_tmp"` and `"$BACKUP"` on jq rewrite failure (`apply-bump.sh` ~159–161). Python can leave a bumped `plugin.json` (after `tmp.replace`) plus a staged index from a prior successful `git.add`, or at minimum a stale `.bump-backup`, without restoring the pre-bump tree. **Suggested fix:** On any `backup_rewrite_stage` failure, restore from `backup_path` if it exists, `git.unstage` `PLUGIN_JSON_PATH`, delete `backup_path` and any `.tmp` sibling, then return the error; never return `stage_err` while the worktree still reflects a partial stage.

- **risk-integration** `python/version_bump.py:524-531` — `git.add`’s return code is ignored inside `backup_rewrite_stage`. Bash relies on `set -e`, so a failed `git add` aborts the script before the fetch/retry loop. Python treats a failed add as success (`return None`) and can enter the origin/main race loop with a rewritten `plugin.json` that is unstaged or only partially indexed, then call `git.commit` on an inconsistent index. **Suggested fix:** Check `add_result.returncode` (and optionally `git diff --cached --quiet` on `PLUGIN_JSON_PATH`); on failure invoke the same rollback/cleanup path as other stage errors and return `ApplyResult(applied=False, error=...)`.

- **risk-integration** `python/changelog.py:640-657` — After `changelog_path.write_text`, a failed `git.add` or `git.commit` leaves the modified CHANGELOG on disk (staged if add succeeded) with no restore of the pre-call content. This matches `scripts/commit-changelog.sh` (mutate via `mv`, then `git-commit.sh`; no rollback on commit failure), so it is not a regression versus bash, but it is a real partial-failure surface for Phase 7 wiring. **Suggested fix:** If stricter than bash is desired, snapshot `read_text` before `write_text` and restore on add/commit failure (and `git reset HEAD` the path); otherwise document that callers must treat `committed=False` after a heading-changing `replaces_version` as a dirty-tree state requiring manual fix or re-run from git.

### Out-of-Scope Observations

- **risk-integration** `python/changelog.py:473-500` / `scripts/auto-resolve-changelog.sh:289` — `auto_resolve` writes the merged result directly to the conflict path with no rollback, same as bash’s `mv "$out_tmp" "$conflict_path"`. Until the caller runs `git add`, conflict stages `:2:` and `:3:` remain recoverable via `git show`; aborting the rebase should still discard the working-tree write. No additional defect beyond the existing bash contract.

- **correctness** `python/changelog.py:626-640` — `commit_changelog` only applies in-memory insert/retitle when `replaces_version` is set; with an empty `replaces_version` it always `write_text`s without inserting a new `## [version]` heading (bash `commit-changelog.sh` also does not insert unless the replaces-version block runs). Callers must pre-edit or pass `replaces_version`; not a file-mutation-safety issue.
