Reviewing the branch diff and commit history, then tracing the Step 3 / Gate B / Gate C control flow in the changed files.
### In-Scope Findings

- **architecture** `scripts/design-pause-save.sh:175-176` — The pause router treats `step-3` present + `step-3.5` absent as “resume at Gate B (STEP=3.5)”. The new auto-continuation loop deliberately leaves that sentinel pair set while re-entering Step 3 (`skills/design/SKILL.md:1276-1277` skips writing `step-3.5` on continue). A pause during round 2+ Step 3 therefore resumes at Gate B instead of Step 3, which can skip an in-flight panel, re-apply stale findings, or strand partially written review artifacts. **Suggested fix:** On the continue branch, clear `.completed/step-3` (and ideally add a dedicated marker such as `.plan-review-auto-continue`) before re-invoking `run-step3-review.sh`, and teach `design-pause-save.sh` to prefer STEP=3 when that marker is set; add a pause/resume harness case for “mid auto-continue loop”.

- **architecture** `skills/design/references/approval-gates.md:93` vs `skills/design/scripts/run-step3-review.sh` — Docs say “New Step 3 entries … clear `.gate-b-postapply-ready-*` before reviewers run”, but only `design-step3-state.sh --direct-review-entry` (`.step3-reentry` / Gate C manual re-run) performs that cleanup (`design-step3-state.sh:65`). Automatic continuation re-enters Step 3 without `.step3-reentry`, so per-round `.gate-b-postapply-ready-N` files accumulate and pause/resume idempotency depends on the orchestrator still binding the correct `STEP3_REVIEW_ROUND_NUM`. **Suggested fix:** Clear `.gate-b-postapply-ready-*` at the start of every `run-step3-review.sh` launch (or in the SKILL continue branch), and add a harness asserting markers are removed before automatic round N+1.

- **architecture** `skills/design/scripts/plan-review-continuation.sh:177-185` vs `skills/review-and-fix/scripts/review-implement-step5-loop.sh:410-411` — The branch advertises mirroring `/implement`, but continuation predicates diverge materially: design continues on any `HIGH_ACCEPTED_COUNT > 0`, while implement requires `high_n >= 2` (plus `structural_loc >= 100` or `post_fix >= 8`). The motivating case in the plan (4 important accepted → continue) would match both, but a single-important round will always auto-continue in `/design` yet converge in `/implement`, re-opening the symmetry gap this change targets. **Suggested fix:** Align thresholds with implement (≥2 important, or add structural/large-change proxies equivalent to `structural_loc` / fix-count), and document any intentional `/design`-only differences in `plan-review-continuation.md`.

- **architecture** `skills/design/scripts/plan-review-continuation.sh:140-185` — `STRUCTURAL_OR_LARGE_CHANGE` is true when `plan_lines > 120` (same order of magnitude as the summary threshold), `diff_lines > 500`, or tier is HARD. On round 1 with any accepted finding, most real plans therefore hit `structural-or-large-change` and force a second panel even for a single nit-only round (SIMPLE) or any HARD run. That is much looser than implement’s `structural_loc >= 100` after actual fixes. **Suggested fix:** Narrow the proxy (e.g., use post-apply `diff_lines` delta, a higher line threshold, or HARD-only with an accepted non-nit count gate) so “small-clean” convergence is reachable on typical plans.

- **correctness** `skills/design/references/approval-gates.md:296` vs `skills/design/SKILL.md:1274-1277` — Gate B’s zero-findings short-circuit still says it “proceeds to Step 3b”, but the orchestrator now mandates the heuristic continuation check after every settled Gate B path (including zero-findings when `DEGRADED_PANEL=1`). An executor following `approval-gates.md` literally can skip continuation and miss the degraded-panel auto-loop that `approval-gates.md:379` elsewhere describes. **Suggested fix:** Update the zero-findings short-circuit prose to “return to SKILL.md continuation check” (not Step 3b), matching §Shared post-apply pipeline step 9.

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:174-176` — `DEGRADED_PANEL=1` alone forces continuation until the cap, even when `ACCEPTED_COUNT=0` (zero-findings degraded panel). That can burn up to five full review panels with no accepted work. **Suggested fix:** Gate degraded continuation on at least one accepted finding or a failed-collector recovery predicate, unless a deliberate “retry degraded panel” policy is documented.
