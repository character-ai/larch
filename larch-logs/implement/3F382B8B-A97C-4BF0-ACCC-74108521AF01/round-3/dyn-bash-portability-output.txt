Reviewing the branch diff and key Bash helpers for portability issues.
### In-Scope Findings

- **code-quality** `skills/design/scripts/plan-review-continuation.sh:67-151` — The new continuation helper wraps all stat extraction in `stats="$(python3 …)"` under `set -euo pipefail`, with no `command -v python3` guard, no `set +e` around the substitution, and no stderr diagnostic. If `python3` is missing or exits non‑zero (syntax error, bad env, etc.), the script aborts before emitting any `PLAN_REVIEW_CONTINUE*` KVs, while `skills/design/SKILL.md` Step 3.5 expects those KVs to drive the multi-round loop. That is a brittle subprocess/`set -e` interaction on a new control-path script. **Suggested fix:** Follow the `check-plan-size.sh` pattern: probe `command -v python3` first and fail with a clear `plan-review-continuation.sh: python3 required` message; wrap the Python call in `set +e` / capture `$?`, and on failure print safe default KVs (`PLAN_REVIEW_CONTINUE=false`, `PLAN_REVIEW_CONTINUE_REASON=stats-error`) before exiting non‑zero.

- **code-quality** `skills/design/scripts/persist-retally-step3-env.sh:68-101` — The new `_merge_retally_accepted_all` inline Python merge has the same hard dependency: it runs unconditionally (when tally is `ok` and `accepted-plan-findings.md` is non-empty) with no availability check and no error handling, so any `python3` failure aborts the whole persist step under `set -e` after Gate B re-tally. That can leave Step 3 env KVs stale while the orchestrator assumes cumulative accepted findings were merged. **Suggested fix:** Guard with `command -v python3`, log via `larch_err` on absence, and either skip merge with an explicit WARN KV or use a small awk/sed fallback that appends only when Python is unavailable; at minimum wrap the Python call, check `$?`, and fail loudly with a dedicated exit code.

- **risk-integration** `scripts/relevant-checks.sh:132-136` — This branch wires `plan-review-continuation.sh` to `test-step3-review-cap`, but the substantially changed `persist-retally-step3-env.sh` (new Python cumulative-merge path plus expanded `test-persist-retally-step3-env.sh` coverage) has no `relevant-checks.sh` mapping. Edits to persist-retally during implement will not auto-run `test-persist-retally-step3-env` via `scripts/relevant-checks.sh`, even though that harness now covers the merge/idempotency behavior introduced here. **Suggested fix:** Add a `case` arm mapping `skills/design/scripts/persist-retally-step3-env.sh|…|skills/design/scripts/test-persist-retally-step3-env.sh|…` to `append_target_once test-persist-retally-step3-env`, mirroring the continuation/cap routing.

- **code-quality** `skills/design/scripts/plan-review-loop.sh:598-613` vs `skills/design/scripts/persist-retally-step3-env.sh:68-101` — The branch introduces two different bash/Python strategies for building `accepted-plan-findings-all.md`: `plan-review-loop.sh` concatenates prior + current with `sed`, while `persist-retally-step3-env.sh` dedupes exact block text in Python. On multi-round runs both paths can execute, so whitespace-tolerant duplicates from `sed` concat will inflate `render-final-summary.sh`’s new block-counting awk (which sums `### FINDING_` / `### OOS_` headers across the cumulative file). **Suggested fix:** Use one merge implementation everywhere (prefer the Python deduper, or share a single helper script), or teach the `sed` path the same exact-block dedup semantics so cumulative artifacts stay consistent before `render-final-summary.sh` reads them.

- Widespread pre-existing `python3` / `jq` / process-substitution usage in `plan-review-loop.sh` and `render-final-summary.sh` follows established repo patterns; this review focused on new/changed control-path surfaces from the branch diff.
