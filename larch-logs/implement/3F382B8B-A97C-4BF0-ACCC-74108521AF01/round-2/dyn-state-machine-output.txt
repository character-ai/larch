Reviewing the branch diff and commit history, then tracing Step 3/3.5 state-machine behavior in the changed scripts.
### In-Scope Findings

- **risk-integration** `skills/design/SKILL.md:1267-1269` — Gate B pause/resume idempotency tells the orchestrator to jump from the post-apply fence straight to Step 3b when `.gate-b-postapply-ready-*` exists and `.completed/step-3.5` does not, but the new multi-round contract requires the heuristic continuation check to run after every settled Gate B path (including post-fence) before Step 3b. A pause after round 1 auto-apply (e.g. four important findings already written into `plan.txt`) therefore resumes into Gate C without ever evaluating `plan-review-continuation.sh`, skipping automatic rounds the loop was added to enforce. **Suggested fix:** Align the resume branch with `approval-gates.md` shared post-apply step 9: after the merged `design-postplan-emit.sh` fence settles on resume, always invoke `plan-review-continuation.sh` (unless Gate B was bypassed); only proceed to Step 3b when `PLAN_REVIEW_CONTINUE=false`, and loop back to Step 3 when true.

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:177-179` — The automatic continuation predicate fires on `HIGH_ACCEPTED_COUNT > 0` (any single `important` finding), while `/implement` Step 5 continues only when `high_n >= 2` (or structural LOC / fix-count thresholds) per `review-implement-step5-loop.sh`. The motivating #3662 scenario had four important findings, but a single-important round still forces another full 10+ reviewer panel, consuming `review-round-count.txt` budget without matching the symmetric `/implement` bar the plan described (`important-accepted ≥ 2`). **Suggested fix:** Change the continue predicate to `HIGH_ACCEPTED_COUNT >= 2`, or add the missing `/implement` substantial-round signals (`structural_loc >= 100`, `fix_count >= 8`) so single-important rounds can converge after Gate B apply instead of always scheduling another panel.

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:174-176` — Any round with `DEGRADED_PANEL=1` unconditionally sets `PLAN_REVIEW_CONTINUE=true` until the shared cap is reached, with no convergence escape hatch for repeated degraded-zero-finding rounds (`LOOP_STATUS=zero-findings-degraded-panel`). A persistently degraded panel (one external down, format-gate drops, etc.) can burn all five review slots on full panel launches that accept zero findings and never revise `plan.txt` via Gate B, then still advance to Gate C. **Suggested fix:** Track consecutive degraded continuation rounds (or require non-zero accepted findings / successful collector quorum) before re-queueing another panel; alternatively stop with a loud warning and operator choice when degraded continuation would consume the last cap slots without prior Gate B applies.

- **risk-integration** `skills/design/scripts/design-step3-state.sh:71-73` — Gate C / Gate A manual re-entry via `--direct-review-entry` clears `accepted-plan-findings-all.md` (added in this branch) but does not reset `oos-accepted-design.md` or its `.prev` sidecar, while `approval-gates.md` state invariant #2 says manual re-runs overwrite prior review artifacts. `plan-review-loop.sh` snapshots and re-accumulates the stale cumulative OOS file, so a manual “Re-run review panel” after an automatic multi-round sequence can inflate the final-summary Plan review OOS count with findings from superseded runs. **Suggested fix:** On `--direct-review-entry`, also `rm -f` `oos-accepted-design.md` and `.oos-accepted-design.prev.md` (mirror the accepted-all reset), or teach `_clear_session_root_review_artifacts` to truncate cumulative files whenever `.step3-reentry` is absent vs present.

- **risk-integration** `skills/design/scripts/run-step3-review.sh:354-364` — `LOOP_STATUS=panel-failed` persists the incremented `review-round-count.txt` (same as successful rounds), but the Step 3 branch matrix bypasses Gate B and the new continuation check, advancing to Step 3b/4/Gate C with the plan unchanged. Repeated panel failures can exhaust the shared cap without any auto-apply or re-review benefit, leaving the operator at Gate C with stale artifacts and no further “Re-run review panel” if cap is hit. **Suggested fix:** Either roll back the counter on `panel-failed` (parity with `tally-error` / `degraded-empty-collector`), or block Gate C approval until a successful review round lands and document a loud cap-consumption warning when panel-failed persists the slot.

### Out-of-Scope Observations

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:103-118` — The unstructured-severity fallback treats any concern matching `\bhigh\b` as “high accepted,” which can false-positive on benign phrasing (“high-level overview”) and trigger extra review rounds; consider tightening patterns or requiring structured `important` severity when artifacts are well-formed.

- **risk-integration** `skills/design/scripts/test-step3-review-cap.sh` — New continuation harness cases cover cap-reached, explicit-approve, high-fallback, and degraded-panel continue paths, but there is no regression for the `small-clean` stop path or for resume-after-`.gate-b-postapply-ready-*` interacting with continuation; those gaps leave the highest-risk state-machine edges unpinned.

- **code-quality** `/implement` Step 5 emits a churn warning when round *N* accepts more findings than round *N−1* (`review-and-fix.sh` Part C); the new `/design` automatic loop has no analogous operator-visible churn signal across continuation rounds.
