### In-Scope Findings

- **architecture** `skills/design/references/plan-review.md:48-60` — The normative plan-review contract still centers on a “Single-pass review” section for `plan-review-loop.sh` / `run-step3-review.sh`, but the orchestrator lifecycle is now multi-round via `SKILL.md` Step 3.5 and `plan-review-continuation.sh`. `plan-review.md` mentions “automatic continuation rounds” only in artifact bullets and tail prose; it never defines continue/stop predicates, cap interaction, or the split between `accepted-plan-findings.md` (per-round apply set) and `accepted-plan-findings-all.md` (cumulative reporting). `approval-gates.md` defers to “`SKILL.md`'s heuristic multi-round continuation check,” so the review pipeline has no single normative doc for the full round lifecycle. **Suggested fix:** Add a dedicated “Multi-round orchestration” section to `plan-review.md` (or elevate `plan-review-continuation.md` as a cited normative sibling) that documents predicates, cap semantics, Gate B → continuation → Step 3 re-entry flow, and artifact ownership; cross-link from `approval-gates.md` §Gate B shared post-apply pipeline step 9 instead of only pointing at `SKILL.md`.

- **architecture** `skills/design/scripts/plan-review-continuation.sh:178-187` — The continuation heuristic does not mirror `/implement`’s substantial-round shape. `/implement` continues when `high_n >= 2 || structural_loc >= 100 || fix_count >= 8` (`skills/review-and-fix/scripts/review-implement-step5-loop.sh:405-411`); this branch continues on `HIGH_ACCEPTED_COUNT > 0`, `NON_NIT_ACCEPTED_COUNT > 5`, degraded panel, or first-round structural/large (`STRUCTURAL_OR_LARGE_CHANGE` from tier/plan metadata, not git LOC). A round with exactly one `important` finding stops `/implement` but auto-continues `/design`. The issue plan explicitly cited `important-accepted ≥ 2` as the substantial threshold; `SKILL.md` Step 3.5 prose says predicates “mirror `/implement`” while encoding the looser `> 0` rule. **Suggested fix:** Align thresholds with `/implement` (at minimum `HIGH_ACCEPTED_COUNT >= 2`), add an accepted-count ≥ 8 continue path, and replace plan-metadata “structural” with a post–Gate-B delta signal (e.g., `diff_lines` / `diff_added` delta after apply) closer to `structural_loc >= 100`; update `SKILL.md`, `plan-review-continuation.md`, and `test-step3-review-cap.sh` together.

- **correctness** `skills/design/scripts/plan-review-continuation.sh:120-123` — `HIGH_ACCEPTED_COUNT` is recomputed independently of `IMPORTANT_ACCEPTED_COUNT` from `plan-review-loop.sh` (`_count_important_findings` only matches `- **Severity**: important`). When any accepted block lacks structured severity, the helper falls back to concern-text heuristics (`\bhigh\b`, `\bcritical\b`, etc.) and can mark `PLAN_REVIEW_CONTINUE=true` with `reason=high-accepted` even when `IMPORTANT_ACCEPTED_COUNT=0` in `.step3-review-result.env`. The Step 3.5 breadcrumb prints `high=<HIGH_ACCEPTED_COUNT>` from the helper, so operators and run logs can disagree on whether the round was “important-heavy.” **Suggested fix:** Reuse the same counting function as `plan-review-loop.sh` for structured severity, or read `IMPORTANT_ACCEPTED_COUNT` from `.step3-review-result.env` and only apply concern-text fallback when that KV is absent; add a harness case where concern-text fallback fires but `IMPORTANT_ACCEPTED_COUNT=0` to lock expected behavior.

- **architecture** `scripts/test-design-structure.sh` — The structure harness pins Gate C cap prose and `plan-review-loop.sh` statelessness, but has no `contains` pins for `plan-review-continuation.sh` invocation, “Heuristic multi-round continuation check,” or `design-step3-state.sh --auto-continuation-entry` in `SKILL.md`. - **risk-integration** `skills/design/scripts/design-step3-state.sh:77-80` — `--auto-continuation-entry` clears `step-3`…`step-4b` and `.gate-b-postapply-ready-*` but is not covered by `test-design-pause-resume.sh` (unlike `--gate-b-bypass` and `--direct-review-entry`).
