Reviewing the branch diff and commit history, then tracing the Step 3/3.5 multi-round state machine transitions.
### In-Scope Findings

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:175-177` — A degraded panel with zero accepted findings still schedules another full review round (`CONTINUE=true`, `REASON=degraded-panel`) whenever `DEGRADED_PANEL` is set in `.step3-review-result.env`, even after Gate B’s zero-findings short-circuit leaves `accepted-plan-findings.md` empty. That path is explicitly tested (`test-step3-review-cap.sh` “continuation helper continues on degraded zero-findings”) and documented in `approval-gates.md`, but it diverges from `/implement` Step 5, which retries a degraded panel once inside the same round and converges on a subsequent non-degraded small round. On `/design`, repeated `zero-findings-degraded-panel` rounds can consume the shared cap of 5 with full panel/voter cost and no plan movement until the cap stops the loop. **Suggested fix:** Gate the `degraded-panel` continue predicate on evidence that the round produced actionable output (e.g. `ACCEPTED_COUNT > 0` or `NON_NIT_ACCEPTED_COUNT > 0`), or cap degraded-only auto-continuations to one follow-up round before requiring operator action at Gate C.

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:177-180` — The “substantial round” continuation threshold fires on any single Important-classified finding (`HIGH_ACCEPTED_COUNT > 0`), while the combined issue plan and `/implement`’s Step 5 continuation heuristic use `important-accepted ≥ 2` (plus structural LOC / fix-count signals in implement). `SKILL.md` documents “any High/Important,” so this may be intentional, but it materially increases automatic round count and cost for single-Important rounds that `/implement` would treat as converged-small-changes on the next clean pass. **Suggested fix:** Align the predicate with `/implement` (`HIGH_ACCEPTED_COUNT >= 2`, optionally plus plan-size/`diff_lines` analogues), or document the asymmetry as a deliberate `/design` policy and add a harness case for the 1-important-finding stop/continue boundary.

- **risk-integration** `skills/design/scripts/plan-review-continuation.sh:134-140` — Missing or invalid `design_classification` in `run-params.json` defaults to `HARD`, which sets `STRUCTURAL_OR_LARGE_CHANGE=true` and can force a second automatic round on any first-round accepted finding via `structural-or-large-change` (`REVIEW_ROUND_COUNT < 2`). That fail-open default is tested (`test-step3-review-cap.sh` “invalid classification should default HARD and continue”) but creates an integration risk: corrupted or partial `run-params.json` silently escalates review spend instead of stopping on a small-clean round. **Suggested fix:** Default invalid/missing classification to `SIMPLE` (conservative stop) or treat parse failure as `PLAN_REVIEW_CONTINUE=false` with a loud warning in `execution-issues.md`.

- **risk-integration** `skills/design/scripts/run-step3-review.sh:212-228` — Each automatic continuation re-entry calls `run-step3-review.sh`, which deletes every `plan-review/round-*` snapshot directory before launching the next round. That behavior predates this branch, but the new multi-round loop amplifies it: only the latest round’s forensics survive, while `plan-review.md` and `approval-gates.md` now promise cumulative `accepted-plan-findings-all.md` and per-round artifacts for automatic sequences. This blocks downstream #3619-style per-round reviewer pruning and weakens post-run auditability across automatic rounds. **Suggested fix:** Stop wholesale `rm -rf` of prior `plan-review/round-N/` trees on auto-continuation entry (only remove the upcoming round slot), or snapshot rounds to monotonically numbered directories that are never deleted until design publish.

- **architecture** `skills/design/SKILL.md:1274-1277` — The multi-round controller is prompt-orchestrated (orchestrator loops Step 3 → Gate B → `plan-review-continuation.sh` → Step 3) rather than enclosed in a single bash driver like `/implement`’s `review-implement-step5-loop.sh`. Mechanical helpers (`plan-review-continuation.sh`, `design-step3-state.sh --auto-continuation-entry`) cover individual transitions, but there is no end-to-end harness that exercises a two-round auto-continue → Gate B double-apply → Gate C path; only isolated continuation-helper cases exist in `test-step3-review-cap.sh`. A missed orchestrator step (e.g. skipping `--auto-continuation-entry`, writing `.completed/step-3.5` on a continue path, or jumping to Step 3b without the continuation check) would double-apply findings or bypass Gate C without a script-level fail-closed guard. **Suggested fix:** Add an integration harness that simulates two continuation cycles through `run-step3-review.sh` + Gate B sentinel files + `plan-review-continuation.sh`, asserting cap consumption, no duplicate `.gate-b-postapply-ready-*` apply, and preserved `accepted-plan-findings-all.md`.
