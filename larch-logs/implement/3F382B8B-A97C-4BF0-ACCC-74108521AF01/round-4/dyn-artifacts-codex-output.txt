### In-Scope Findings
- **correctness** `skills/design/scripts/run-step3-review.sh:212-222` — The new auto-continuation path re-enters Step 3 via `skills/design/SKILL.md:1274-1276`, but every `run-step3-review.sh` invocation deletes all existing `plan-review/round-*` directories before launching the next round. In a multi-round review, round 2 therefore erases round 1 snapshots, `findings-classification.tsv`, timing markers, and summaries, contradicting the per-round artifact model and leaving logs/debug state with only the latest round. **Suggested fix:** Only clean round artifacts at the start of a fresh manual review sequence, or delete/recreate just the pending current round directory; preserve prior `round-N` directories during automatic continuation and add a multi-round harness assertion that round 1 and round 2 snapshots coexist.

- **correctness** `skills/design/scripts/design-step3-state.sh:59-73` — Manual Step 3 re-entry clears `accepted-plan-findings-all.md` but not `oos-accepted-design.md`; then `skills/design/scripts/plan-review-loop.sh:1574-1589` treats the existing OOS file as prior cumulative state and merges it into the new review. This violates the new invariant in `skills/design/references/approval-gates.md:204` / `skills/design/references/plan-review.md:58` that OOS accumulation is only for the current automatic sequence, so a Gate C “Re-run review panel” can carry stale accepted OOS items into final summaries and issue filing. **Suggested fix:** On `direct-review-entry`, also clear `oos-accepted-design.md` and its `.oos-accepted-design.prev.md` state, or otherwise mark automatic-continuation sequences so `_accumulate_round_oos` only preserves prior OOS inside that sequence.

- **correctness** `skills/design/scripts/persist-retally-step3-env.sh:68-143` — Successful MainAgent re-tally now merges `accepted-plan-findings.md` into `accepted-plan-findings-all.md`, but the refreshed `.step3-plan-review-result.env` / `.step3-review-result.env` keep the stale pre-adjudication `ACCEPTED_COUNT` and severity counters; the helper only zeroes those fields on `tally-error`. A 0-judge round that MainAgent later accepts findings can therefore persist `TALLY_PLAN_REVIEW_STATUS=ok` with `ACCEPTED_COUNT=0`, producing inconsistent Step 3 state for downstream consumers and logs. **Suggested fix:** On `TALLY_PLAN_REVIEW_STATUS=ok`, recompute accepted, important, nit, and non-nit counts from the post-retally `accepted-plan-findings.md` and rewrite both env files; extend `test-persist-retally-step3-env.sh` to assert non-zero counts after an accepted MainAgent re-tally.
