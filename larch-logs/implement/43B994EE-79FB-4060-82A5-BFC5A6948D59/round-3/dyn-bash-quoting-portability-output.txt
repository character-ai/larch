### Out-of-Scope Observations

- **Investigated (not a defect):** `ref="${ref%'^{commit}'}"` in `.claude/skills/release/scripts/test-release-prepare.sh:80` and `.claude/skills/release/scripts/test-release-finish.sh:85`. In Bash 3.2 and 5.x, single quotes inside `${ref%'^{commit}'}` delimit the `%` suffix pattern; they are not treated as literal characters inside the outer `"…"` assignment. The pattern is `^{commit}`, so `v1.0.0^{commit}` / `deadbeef…^{commit}` strip correctly. That matches what `release-prepare.sh:127-137` and `release-finish.sh:153-168` pass to `git rev-parse`. If stripping failed, fake `git` would hit `unexpected git` (exit 9) or `--verify` would return 1, and prepare/finish would fail closed (`ERROR=baseline-tag-unresolvable`, `ERROR=invalid mergeCommit.oid`) — not silent wrong tags. Harness cases that depend on stripped refs (prepare cases 1/4/6, finish cases 1/4/6) would also fail.

- **`scripts/promote-release.sh:74-92` — `${REPO_ARGS[@]+"${REPO_ARGS[@]}"}`:** Same empty-array + `set -u` idiom as `scripts/create-pr.sh` (fixed in #1496). With `REPO_ARGS=()`, it expands to nothing; with `--repo`, it expands to `--repo owner/repo`. No Bash 3.2 defect found in the expansion form itself.

- **Harness coverage gap (precedent exists elsewhere):** Unlike `scripts/test-create-pr.sh` (explicit `/bin/bash` 3.2 rerun for empty `GH_REPO_ARGS`), `scripts/test-promote-release.sh` case 1 only exercises the no-`--repo` path under default `bash`. A wrong copy of the `[@]+` idiom would likely still pass on Linux CI (Bash 4+/5+) while breaking on macOS `/bin/bash` 3.2. Low risk here because the idiom is already repo-canonical.

- **Optional hardening (not required for correctness):** A `case "$ref" in *'^{commit}') ref="${ref%^{commit}}";; esac` suffix strip in the fake-`git` stubs would avoid `%`-pattern quoting subtleties (including `extglob` if ever enabled) without changing production scripts.
