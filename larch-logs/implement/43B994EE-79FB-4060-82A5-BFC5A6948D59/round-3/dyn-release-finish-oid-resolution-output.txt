Reviewing `release-finish.sh` TARGET_OID resolution, fetch-by-SHA behavior, tag TOCTOU, and cleanup trap — reading the diff and full script.
### In-Scope Findings

- **correctness** `.claude/skills/release/scripts/release-finish.sh:153-172` — `TARGET_OID` is validated with `git rev-parse --verify` on `mergeCommit.oid` **before** `git fetch origin main` (line 160) and before the `git fetch origin "$TARGET_OID"` fallback (lines 167–168). On a normal `/release` run the squash-merge commit often is not in the local object database yet (remote-only merge via `merge-pr.sh`, re-run of `release-finish.sh` after a partial failure, or API returning `mergeCommit` before `origin/main` has caught up). The script then exits with `ERROR=invalid mergeCommit.oid` and never reaches the fetch path that would populate the object — even when `git fetch origin main` or `git fetch origin <sha>` would succeed. **Suggested fix:** Move `git fetch origin main` (and tag fetch if needed) immediately after resolving `merge_oid`, then `git rev-parse --verify` / `git show` for `plugin.json`; only use the SHA-specific fetch when `origin/main^{commit}` ≠ `TARGET_OID` after a successful main fetch, with bounded retries aligned with the `mergeCommit` poll loop.

- **correctness** `.claude/skills/release/scripts/release-finish.sh:166-170` — When `origin/main^{commit}` ≠ `TARGET_OID` after `git fetch origin main`, the fallback is `git fetch origin "$TARGET_OID"` with stderr discarded. On GitHub’s HTTP smart protocol, fetching a bare SHA only works when that commit is reachable from advertised refs; if `mergeCommit` is visible in the API but `refs/heads/main` has not yet advanced (or another tip is ahead and the commit is not yet reachable), the fetch can fail and the script exits with the generic `ERROR=could not resolve TARGET_OID after fetch`, which is easy to misread as a bad OID rather than a timing/reachability problem. **Suggested fix:** After reordering fetches (above), prefer repeated `git fetch origin main` (with the same backoff used for `mergeCommit`) until `git merge-base --is-ancestor "$TARGET_OID" origin/main` or `origin/main^{commit}` equals `TARGET_OID`; treat SHA-only fetch as a last resort; surface `git fetch` stderr on failure and distinguish errors (e.g. `ERROR=target-oid-not-on-origin-main` vs `ERROR=fetch-failed`).

### Out-of-Scope Observations

- **TOCTOU tag push vs `release-tag.yaml`:** The `ls-remote` → local tag → re-`ls-remote` → `git push` → on failure re-`ls-remote` sequence at lines 197–232 is sound for the planned race: if `release-tag.yaml` creates `vX.Y.Z` at `TARGET_OID` between probe and push, push fails, the post-failure `ls-remote` sees the correct peeled OID, and the script continues without a false fatal exit. No in-scope defect there; `test-release-finish.sh` does not exercise that push-failure recovery path (cases 1–6 only).

Exits before line 129 have no temp file to clean. No issue.
