Reviewing the branch diff and `release-finish.sh` idempotency paths.
### In-Scope Findings

- **architecture** `.claude/skills/release/scripts/release-finish.sh:206-224` — After the `target_oid_resolved` poll exhausts, the fallback only runs `git fetch origin "$TARGET_OID"` when non-`--verify` `rev-parse` output for `TARGET_OID` differs from `origin/main^{commit}`. Those parses can return the same SHA from remote-tracking refs while `git rev-parse --verify "${TARGET_OID}^{commit}"` still fails because the commit object is not in the local ODB (shallow/partial clone, or `main` updated but the object was never fetched). The branch then skips the SHA fetch and exits with `ERROR=fetch-failed: could not resolve TARGET_OID after fetch` even though the OID is already known and reachable on `origin/main`. **Suggested fix:** In the `target_oid_resolved != true` block, gate the fetch skip on successful `--verify` for both sides (or always run `git fetch origin "$TARGET_OID"` / deepen `origin/main` when `--verify` fails), and only then re-check ancestor/`origin/main` equality.

- **architecture** `.claude/skills/release/scripts/release-finish.sh:256-271` — Tag idempotency is oriented around remote peeled OIDs (`remote_oid` at 256–262, 274–291), but a stale **local** tag on a different commit still aborts at 266–268 before release create/edit or promote. That breaks the documented partial-failure path when `release-tag.yaml` (or a prior push) already placed the remote tag on `TARGET_OID` while this clone retains an old `vX.Y.Z` ref—exactly the workflow race the skill is meant to tolerate. Release and promote never run; re-running with the same args cannot self-heal without manual local tag deletion. **Suggested fix:** When `remote_oid` is non-empty and equals `TARGET_OID`, treat the remote as authoritative: skip the hard error (or `git tag -f "$TAG" "$TARGET_OID"` to realign the local ref), then continue to `gh release` and `promote-release.sh` as today.

- **risk-integration** `.claude/skills/release/scripts/test-release-finish.sh:167-320` — The harness covers create/edit, version mismatch, remote wrong OID, merge-commit fallback, and local wrong OID, but not the contract in `release-finish.md` (lines 43–45): tag + `gh release` succeed, `promote-release.sh` fails, then a second invocation with identical args should hit `RELEASE_ACTION=edit` and complete promote. `PROMOTE_RC` is wired in the fake promote script but no case sets `PROMOTE_RC=1` on first run and `0` on second. **Suggested fix:** Add an offline two-invocation case: first run with `PROMOTE_RC=1` (expect exit 1, no success KV); second with `GH_FIXTURE_RELEASE_EXISTS=1` and `PROMOTE_RC=0` (expect exit 0 and `RELEASE_ACTION=edit`).

### Out-of-Scope Observations

- **correctness** `scripts/promote-release.sh:79` — `CURRENT_LATEST` uses `gh release list … | select(.isLatest)` without enforcing a unique Latest row; multiple `isLatest=true` releases yield a multi-line value and brittle string compare. This predates the branch; `/release` now depends on `promote-release.sh` more heavily but the ambiguity is not introduced by this diff.

- Tracing the tag/release/promote tail when the remote tag already matches `TARGET_OID`: there is no early exit after tag skip—`gh release` and promote still run (294–311), which matches the `release-tag.yaml` coexistence design.

- Post-push TOCTOU handling (284–291): a failed push followed by `ls-remote` showing the tag at `TARGET_OID` continues correctly; the second `remote_tag_commit_oid` read is not compared twice in a way that can “pass then fail” on the same variable within one run.

- Partial-failure **re-run** logic (release exists → `edit`, then promote) is sound in `release-finish.sh` itself; the gap is local-tag blocking (in-scope above) and missing harness coverage (in-scope above), not the `gh release view` branch choice.
