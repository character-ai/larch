Reviewing tag idempotency and race paths in `release-finish.sh` against the plan.
### In-Scope Findings

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:153-160` — After `merge-pr.sh` returns, `release-finish.sh` calls `git show "${TARGET_OID}:.claude-plugin/plugin.json"` without fetching the squash-merge commit into the local object database. `merge-pr.sh` only runs `git fetch origin main` **before** the merge (see `scripts/merge-pr.sh:346-358`); `ci-wait.sh` does not fetch either. In the normal `/release` sequence (merge → `release-finish`), `TARGET_OID` comes from `gh pr view … mergeCommit.oid` and is often not present locally yet, so the fail-closed version check can spuriously exit with `ERROR=could not read plugin.json at TARGET_OID` even when the merge succeeded. **Suggested fix:** After resolving `TARGET_OID`, run `git fetch origin main` (or `git fetch origin "$TARGET_OID"` when supported) and verify `git rev-parse "origin/main^{commit}"` equals `TARGET_OID` before `git show`; fail closed on fetch/verify mismatch.

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:186-200` — Tag idempotency re-probes `git ls-remote` only when the **first** probe found no remote tag (`remote_oid` empty at line 168). If `release-tag.yaml` pushes `refs/tags/${TAG}` on the correct OID in the window after local `git tag` (line 183) but before the second `ls-remote` (lines 186–188), the script skips `git push` because `remote_oid` is now non-empty, but it never re-checks `remote_oid == TARGET_OID` on that path (unlike the push-failure handler at lines 194–197). A concurrent wrong-OID tag (manual ops or future workflow change) could pass the initial empty-remote branch and still reach `gh release create` / `promote-release.sh`. **Suggested fix:** After every `ls-remote` that yields a non-empty `remote_oid`, compare peeled commit OID to `TARGET_OID` (e.g. `git ls-remote origin "refs/tags/${TAG}^{}"` or `git rev-parse` after `git fetch origin tag`) and exit **1** on mismatch before release/promote steps.

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:168-169,186-188` — Remote tag checks use `git ls-remote origin "refs/tags/${TAG}"` without the `^{commit}` peel used locally at lines 176–177. For **annotated** tags, `ls-remote` returns the tag object SHA, not the commit; comparing that to `TARGET_OID` yields a false `remote tag exists on different commit` failure, or a false match if logic were relaxed. `.github/workflows/release-tag.yaml:48` creates lightweight tags today, but promoted historical tags may differ. **Suggested fix:** Query peeled refs consistently, e.g. `refs/tags/${TAG}^{}` (or normalize with `git rev-parse "${oid}^{commit}"` after fetch).

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:132-145` — `mergeCommit.oid` polling is five attempts with `sleep 2` (~8s of backoff after the first miss). GitHub often exposes `mergeCommit` later than that after squash merge under load; round 1 **removed** the prior `git fetch origin main` + `origin/main` fallback (see commit `bb55e1f45`), and `release-finish.md:17-18` documents fail-closed `ERROR=merge-commit-missing` only. That leaves a brittle handoff between `merge-pr.sh` and `release-finish.sh` with no recovery besides operator re-run. **Suggested fix:** Extend backoff (e.g. 30–60s total), and/or after merge add a guarded fallback: `git fetch origin main` then require `origin/main^{commit}` equals `mergeCommit.oid` (or equals `TARGET_OID`) before proceeding—only when version at that commit matches `--version`.

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:207` — `gh release create` omits `--latest=false --prerelease`, while `.github/workflows/release-tag.yaml:102-106` always creates prereleases non-latest. If `/release` wins the race, it can publish a non-prerelease and/or Latest release with different semantics than the workflow; `promote-release.sh` repairs Latest afterward but not necessarily prerelease flags until promote runs. **Suggested fix:** Align flags with the workflow (`--latest=false --prerelease` on create; keep edit path for races).

### Out-of-Scope Observations

- **risk-integration** `.github/workflows/release-tag.yaml:73-88` — The workflow still builds release notes from `CHANGELOG.md`, which the versioning overhaul de-emphasizes; when the workflow wins the release-creation race, `/release` overwrites notes via `gh release edit`, but there is a window of workflow-authored notes. Pre-existing overlap behavior, not introduced by this branch’s core helpers.

- **architecture** `implementation_plan` Step 6 vs `.claude/skills/release/scripts/release-finish.md:15-18` — The plan still describes `mergeCommit` with `origin/main` fallback; the branch intentionally dropped fallback in round 1. Documentation drift only; behavior is defined by the script and contract file.
