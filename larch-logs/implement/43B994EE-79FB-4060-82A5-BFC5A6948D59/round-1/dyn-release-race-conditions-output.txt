Reviewing the branch diff and release scripts for race-condition and integration risks.
Checking whether `git show` on `mergeCommit` requires a fetch and how `merge-pr` updates local refs:
### In-Scope Findings

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:114-134` — Tag handling has a TOCTOU gap between the initial `git ls-remote` and `git push`. If `release-tag.yaml` creates `refs/tags/v<VERSION>` on the same `TARGET_OID` in that window, `remote_oid` was still empty at line 114, so the script still attempts `git push` (line 132–133). With `set -euo pipefail`, push is rejected (“tag already exists”) and the script exits before `gh release edit`/`create` and `promote-release.sh`, even though the remote tag is on the intended commit. The error is not swallowed, but the planned idempotent coexistence with the workflow is broken on the first attempt; only a full re-run succeeds. **Suggested fix:** Re-run `git ls-remote` immediately before push, or on push failure re-check whether the remote tag exists at `TARGET_OID` and continue to release edit/promote when it matches; only fail closed when the remote OID differs.

- **risk-integration** `.claude/skills/release/scripts/release-finish.sh:93-111` — When `gh pr view … mergeCommit.oid` is empty (GitHub propagation lag) the fallback sets `TARGET_OID` to `origin/main^{commit}` after one `git fetch`, with no retry on `mergeCommit` and no check that the tip is the release PR’s squash merge. If another commit landed on `main` after the release merge but did not change `.version`, `git show` at the tip can still report the expected `NEW_VERSION`, so the version gate passes while the tag is placed on a descendant commit, not the merge commit. **Suggested fix:** Poll `mergeCommit.oid` with bounded backoff before falling back; or resolve the squash merge via `git log origin/main --grep` / merge-base against the release PR branch; or require `TARGET_OID` to equal `mergeCommit.oid` when the PR is `MERGED` before tagging.

- **risk-integration** `.claude/skills/release/scripts/release-prepare.sh:152-177` with `.claude/skills/bump-version/scripts/classify-bump.sh:108-112,175-194` — Re-running `release-prepare.sh` after a successful release PR merge (e.g. `release-finish.sh` failed after `merge-pr.sh`) always re-classifies `BASELINE_TAG..HEAD` with `SKIP_IDEMPOTENCY=true`, reads `CURRENT_VERSION` from bumped `plugin.json` on `main`, and still applies at least PATCH over the aggregate diff, so `NEW_VERSION` advances again (e.g. 47.0.57 → 47.0.58). There is no guard that the intended cut is already on `origin/main` or that `CURRENT_VERSION` already matches the prepared release. `SKIP_IDEMPOTENCY` also blocks the `BUMP_TYPE=NONE` path when HEAD is still a legacy per-PR `Bump version to X.Y.Z` commit and the release PR has not merged, so a retry cannot surface “already prepared” via idempotency. A full `/release` retry after merge can mislead Step 4 or open a second bump PR. **Suggested fix:** In `release-prepare.sh`, detect an in-flight or completed cut (open `release/v*` PR, `Release v*` on `origin/main`, or `CURRENT_VERSION` vs Latest tag); emit a distinct `ERROR=` or freeze `NEW_VERSION` when `plugin.json` on `origin/main` already reflects the target cut. Optionally narrow `--base` idempotency to ignore only bump-shaped commits, not all release states.

### Out-of-Scope Observations

- The plan called for offline `release-finish` fixtures (version mismatch at `TARGET_OID`, remote tag on wrong OID, create-vs-edit race), but the branch adds harnesses only for `release-prepare` and `release-set-version`; tag/`mergeCommit` race behavior is not regression-tested in-tree.
- `release-finish.sh` does not `git fetch` the resolved `TARGET_OID` before `git show`; this is usually fine after `merge-pr.sh`’s `git fetch origin main`, but shallow or partial clones could fail closed at the version read with a less actionable error.
