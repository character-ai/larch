### In-Scope Findings

- **architecture** `.claude/skills/release/SKILL.md:40-45` — Step 2’s bash block is not a valid script invocation: `PREPARE_OUT="$PWD/.claude/skills/release/scripts/release-prepare.sh" \` only assigns the path to `PREPARE_OUT`, and the continued lines (`--repo`, `--bump`, `--out-dir`) are parsed as separate shell commands, so `release-prepare.sh` never runs and no KV/TSV is produced for Steps 3–4. **Suggested fix:** Invoke the helper directly (or capture stdout), e.g. `PREPARE_DIR="$(mktemp -d)"` plus `"$PWD/.claude/skills/release/scripts/release-prepare.sh" --repo "$REPO" ${BUMP_FLAG:+--bump "$BUMP_OVERRIDE"} --out-dir "$PREPARE_DIR"`, then parse that command’s stdout; reserve `PREPARE_OUT` for output if you still want the name.

- **architecture** `.claude/skills/release/scripts/release-prepare.sh:6-8,97-155` — The script resolves `REPO_ROOT` for `classify-bump.sh` but never `cd`s there; all `git` calls and `classify-bump.sh` (via `$PWD/.claude-plugin/plugin.json`) use the caller’s working directory. The contract says classify runs “on repo root” (`.claude/skills/release/scripts/release-prepare.md:37`), but nothing enforces that, so running the helper off-repo-root mis-anchors the PR window and bump. **Suggested fix:** `cd "$REPO_ROOT"` immediately after computing `REPO_ROOT` (and document “always run from any cwd” in `release-prepare.md`), or pass an explicit repo-root flag through to `classify-bump.sh`.

- **architecture** `.claude/skills/release/scripts/release-finish.sh:114-133` — Git operations are hard-wired to `origin` (`git ls-remote origin`, `git push origin`) while every `gh` call respects `--repo "$REPO"`. On a fork or multi-remote clone, tags can be pushed to the wrong remote while Releases are created on `$REPO`, breaking the plan’s “same hub repo for all steps” invariant. **Suggested fix:** Resolve the git remote that matches `$REPO` (e.g. via `gh repo view --json url` / existing remote helpers) and use that remote for fetch/ls-remote/push; document the coupling in `release-finish.md`.

- **architecture** `.claude/skills/release/scripts/release-finish.md:41-43` — The contract lists `TARGET_OID`, `TAG`, `VERSION`, and `RELEASE_ACTION` as outputs but does not state they are emitted only on full success (exit 0). The implementation prints `RELEASE_ACTION` after create/edit, then runs `promote-release.sh`; if promote fails, the process exits 1 without emitting `TARGET_OID`/`TAG`/`VERSION` (`.claude/skills/release/scripts/release-finish.sh:136-153`), leaving a partial KV stream. **Suggested fix:** Document “all listed keys only on exit 0 after promote succeeds,” or reorder so tail KVs are printed only after promote, or print a failure `ERROR=` and exit before any success keys on promote failure.

- **architecture** `.claude/skills/release/scripts/release-finish.md` — The contract documents exit **1** for tag/OID conflicts (`.claude/skills/release/scripts/release-finish.md:28`) but not exit **2** for usage/validation errors, which the implementation uses for missing args, bad semver, and missing notes (`.claude/skills/release/scripts/release-finish.sh:24-73`). Orchestrators and future harnesses cannot distinguish operator misuse from operational failure. **Suggested fix:** Add an “Exit codes” table mirroring `release-set-version.md` (0 success, 1 operational/`gh`/git/promote, 2 usage/validation).

- **architecture** `.claude/skills/release/scripts/release-prepare.sh:133-144` — PRs parsed from `git log` but skipped silently when `gh pr view` fails (`|| continue`), so `PR_COUNT`/`PR_LIST_FILE` can under-report merges vs the log window without `ERROR=` or stderr warning; Step 3 release notes then omit PRs with no signal to the operator. **Suggested fix:** Fail closed, or emit `WARN_PR_SKIPPED=<n>` / log skipped numbers to stderr and document partial metadata in `release-prepare.md`; at minimum warn in `SKILL.md` Step 2 when `PR_COUNT` is less than the number of `(#N)` tokens seen in the log.

- **architecture** `.claude/skills/release/scripts/release-prepare.sh:64-83` — Failure modes split `ERROR=` across streams: baseline/stale-main errors go to stdout (e.g. `89-92`, `105-119`), while dependency/`gh release list` failures go only to stderr (`64-83`). `SKILL.md:47` says to parse `ERROR=` on exit 1 without specifying stdout, so some failures are not machine-parseable. **Suggested fix:** Emit a single `ERROR=<token>` line on stdout for every exit 1 path (keep human detail on stderr), and document the contract in `release-prepare.md`.
