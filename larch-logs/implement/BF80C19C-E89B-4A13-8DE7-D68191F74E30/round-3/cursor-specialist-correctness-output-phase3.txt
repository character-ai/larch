### In-Scope Findings

1. - **correctness** `skills/design/scripts/design-route.sh:1160-1181` — `render_cancel_summary` declares `local _render_rc=0`, then overwrites it with `$?`, then unconditionally `return 0`. The captured value is never inspected or logged. On a render failure (e.g., render script missing, network error during upsert), the driver silently continues with no trace beyond what the child wrote to FD 4/stderr. Per the plan this is intentional ("tolerate non-zero render rc"), but the dead capture is a shellcheck SC2034 (unused variable) lint failure waiting in CI, and it also means render failure is completely unobservable at the driver level even in non-quiet mode. **Suggested fix:** Either drop the capture entirely (`render_cancel_summary() { ... ; return 0; }` with no `_render_rc`) to make intent explicit and silence shellcheck, or promote it to a `WARN` KV via `WARN_LINES+=("render-cancel-summary-failed rc=$_render_rc")` before `return 0` so CI/ops can detect render failures.

2. - **correctness** `skills/design/scripts/design-route.sh:1146-1157` — `route_emit_stdout_and_exit` iterates the global `ROUTE_KVS` array, which is populated only inside `route_build_kvs` (called by `route_write_result_env`). The three call chains — `emit_route_result`, `emit_cancel_route_result` — all correctly call `route_write_result_env` first. However, `ROUTE_KVS` is declared as a module-level global (`ROUTE_KVS=()`), so if `route_emit_stdout_and_exit` were ever called directly (e.g., from a future hotfix or a `set -e`-masked error path), it would silently emit zero KVs followed by `exit 0`, producing a valid-looking but empty result-env / stdout that the orchestrator would accept as `ROUTE=""` and then fail at the `_route_valid` check with an opaque "missing or invalid ROUTE" error. **Suggested fix:** Add a guard: `[[ ${#ROUTE_KVS[@]} -gt 0 ]] || { larch_err 'route_emit_stdout_and_exit: ROUTE_KVS not built'; exit 2; }` at the top of `route_emit_stdout_and_exit`, or make `ROUTE_KVS` local by inlining `route_build_kvs` into `route_write_result_env`.

3. - **correctness** `skills/design/scripts/design-init-runparams.sh:752-759` — The old `if ! "${_wdce_args[@]}"; then` ran `write-design-current-env.sh` without stdout redirection, so any KVs (including `WARN=…`) it emitted on stdout were captured by the orchestrator's `_init_out` subshell and could be parsed via the allowed-list. The new code pipes stdout to `/dev/null` in both branches, silently discarding all child stdout. If `write-design-current-env.sh` emits WARN= entries to stdout on partial failure, those are now lost. The plan declares this intentional ("keep driver stdout clean"), but it creates a silent protocol assumption: this change is correct only if `write-design-current-env.sh` never writes parsed KVs to stdout. No test or comment anchors that assumption. **Suggested fix:** Add an inline comment at the `>/dev/null` line stating "write-design-current-env.sh must not emit KVs to stdout; only stderr diagnostics are expected" to document the protocol assumption and make a future violation detectable.

4. - **correctness** `scripts/test-design-structure.sh:306-309` — The `bare_devnull_count` check (`grep -cE '>/dev/null$'`) counts lines ending exactly with `>/dev/null` (no trailing characters). This is intended to assert that non-quiet branches redirect child stdout. However, `grep -cE` with `-E` and patterns containing `$` behaves differently on macOS (BSD grep) vs GNU grep in some edge cases with trailing anchors inside character classes. More importantly, the count threshold `< 2` is brittle: the current diff produces exactly 2 matching lines (one in `render_cancel_summary`, one in the resume `write-design-current-env.sh` branch). Adding a third child invocation that lacks the non-quiet redirect would still pass (count would be 3 ≥ 2). **Suggested fix:** Instead of counting bare `>/dev/null` lines globally, pin specific non-quiet branch patterns for each child invocation (similar to how the quiet branch is tested via the `[ "${LARCH_QUIET_PID:-}" = "$$" ]` grep), or document the current count as an explicit minimum and bump it when new child calls are added.

5. - **correctness** `skills/design/SKILL.md:588` — The post-fence cancel rule is expressed entirely as prose: "After the route fence exits 0, read `$DESIGN_TMPDIR/.design-route-result.env` directly (file-first; refuse symlinks)…". The test pins check this prose is present, but no bash fence enforces it. The `ROUTE` variable set inside the preceding fence (via `printf -v` in the file-first loop) is already available after the fence exits. Directing the LLM to "read the file again" post-fence is the SKILL.md pattern and is correct, but the prose lacks the explicit bash syntax for the second read (the test pins the `-s` gate and "Cancel routes always terminate" text, but not the symlink-refusal code). If an LLM turn skips the second file read and uses the in-fence `ROUTE` value instead, behavior is equivalent (same value) — but the symlink-refusal contract is only documented in the prose and never executed mechanically. **Suggested fix:** Add a bash fence for the post-fence cancel handling (read `.design-route-result.env`, symlink check, `ROUTE=` parse, `[ -s ... ]` emit, unconditional abort), making it mechanical rather than instructional.
