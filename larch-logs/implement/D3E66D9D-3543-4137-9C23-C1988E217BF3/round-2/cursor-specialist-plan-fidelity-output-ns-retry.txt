### FINDING_1: Path guard keys off `REVIEW_TMPDIR` basename, not `voter_path` / harness prefix
- **Severity:** **Important**
- **Focus:** `correctness`
- **Location:** [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh) (`should_suppress_parse_rate_issue_append`, ~lines 156–168 in branch); [scripts/test-dispatch-code-voters.sh](scripts/test-dispatch-code-voters.sh) regressions 1–2 (~344–380); [scripts/dispatch-code-voters.md](scripts/dispatch-code-voters.md) (new guard paragraph ~line 118 in diff)
- **Issue:** Suppression runs only when `basename "$REVIEW_TMPDIR"` matches `test-dispatch-code-voters.*|test-collect-*|test-check-*|test-tally-*` and `voter_path` is under that directory. The harness always passes `--review-tmpdir` as nested children of `$TMP` (e.g. `$TMP/env-isolation-review`, basename `env-isolation-review`), so the case arm does not match even though `voter_path` is under `/tmp/test-dispatch-code-voters.XXXX/...`.
- **Concrete scenario:** Regressions 1 and 2 set `LARCH_EXECUTION_ISSUES_LOG` to explicit files and expect **no** append to those logs; with the real `append-tool-failure.sh` (harness uses repo `PLUGIN_ROOT`, not a stub), `should_suppress_parse_rate_issue_append` returns false, `append-tool-failure.sh` should run, and those log files should become non-empty → assertions `[[ -s "$env_isolation_parent" ]]` / `[[ -s "$path_guard_issues" ]]` should trip.
- **Suggested fix:** Align guard with the stated intent: match `voter_path` (or `REVIEW_TMPDIR`) against the harness path patterns (e.g. path segment `test-dispatch-code-voters.` / `test-collect-` / etc.), or pass `--review-tmpdir` at the `test-dispatch-code-voters.*` root in regressions so basename matches; update docs/tests accordingly.

### FINDING_2: Retry-fail comments misattribute “no issues-log write” to the path guard
- **Severity:** **Nit**
- **Focus:** `correctness`
- **Location:** [scripts/test-dispatch-code-voters.sh](scripts/test-dispatch-code-voters.sh) ~247–250, ~309–311
- **Issue:** Those invocations omit `LARCH_EXECUTION_ISSUES_LOG`; `check_voter_parse_rate` then falls through to `$REVIEW_TMPDIR/execution-issues.md`, so parent logs are not touched regardless of `should_suppress_parse_rate_issue_append`.
- **Concrete scenario:** Readers maintain the wrong mental model of which layer prevents parent leakage and may “verify” the path guard via scenarios that never exercise it.
- **Suggested fix:** Reword comments to cite unset-at-harness-start plus `_issues_log` fallback, or set `LARCH_EXECUTION_ISSUES_LOG` in those tests only if the goal is to assert guard behavior.
