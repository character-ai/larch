### In-Scope Findings

### FINDING_1: Regression 3 replaces EXIT trap and leaks the harness `$TMP` directory
- **severity:** **Important**
- **focus_area:** `correctness`
- **source:** `plan` (regression harness change)
- **location:** [scripts/test-dispatch-code-voters.sh](scripts/test-dispatch-code-voters.sh) — lines **26** and **385–386**
- **issue:** A second `trap 'rm -rf "$prod_tmp"' EXIT` overwrites the earlier `trap 'rm -rf "$TMP"' EXIT`. Bash keeps only one `EXIT` handler; the first is discarded.
- **concrete failing scenario:** On a successful run, after regression 3 runs, process exit runs only `rm -rf "$prod_tmp"`. The main harness directory `$TMP` (stubs under `$TMP/bin`, ballot copies, intermediate fixtures) is never removed, so `/tmp/test-dispatch-code-voters.*` accumulates on every passing invocation.
- **suggested fix:** Avoid a second `EXIT` trap: e.g. `mkdir -p "$TMP/prod-shape"` and use that subtree (cleaned with `$TMP`), run regression 3 in a subshell with its own trap, or chain traps (`trap 'rm -rf "$prod_tmp"; '"$(trap -p EXIT | sed -E "s/trap -- '(.*)' EXIT/\1/")" EXIT` is fragile; prefer `prod` under `$TMP` or a subshell).

### FINDING_2: Path guard returns before `larch_err`, not only before `append-tool-failure.sh`
- **severity:** **Latent**
- **focus_area:** `correctness`
- **source:** `both` (feature B: refuse parent log; [scripts/dispatch-code-voters.md](scripts/dispatch-code-voters.md) says only append is suppressed)
- **location:** [scripts/dispatch-code-voters.sh](scripts/dispatch-code-voters.sh) — lines **155–160** vs **161–177**
- **issue:** The `case` arm `return 0` exits before the `if [[ "$log_mode" == "log" ]]` block, so `larch_err` is skipped for matched `voter_path` values, not only the `append-tool-failure.sh` call.
- **concrete failing scenario:** Any caller with `log_mode=log` and a `voter_path` that matches `*/test-collect-*` (or the other patterns) for a legitimate non-harness reason would get `PARSE_RATE_STATUS=NOT_SUBSTANTIVE` and a diag file but no stderr warning from `larch_err`, unlike non-matching paths.
- **suggested fix:** After the guard, skip only the `_issues_log` / `append-tool-failure.sh` block for test patterns, still run `larch_err` when `log_mode=log`, or narrow the patterns if they are meant to be harness-exclusive.

### FINDING_3: Retry-fail fixtures no longer assert issues-log content for claude/codex parse-rate failures
- **severity:** **Latent**
- **focus_area:** `risk-integration`
- **source:** `plan` (tests updated; coverage trade-off)
- **location:** [scripts/test-dispatch-code-voters.sh](scripts/test-dispatch-code-voters.sh) — **retry-fail** / **retry-fail-codex** blocks (~**249–324**); new **regression 3** (~**383–401**)
- **issue:** Removed greps for `launch-claude-review.sh (voter parse-rate check)`, `launch-review.sh --tool codex`, and “exactly one warning” counts. Regression 3 only checks `'dispatch-code-voters.sh claude'` in the issues log for a production-shaped path.
- **concrete failing scenario:** A regression that breaks `parse_rate_check_tool_label` or `--tool` / `--category` wiring for codex/cursor parse-rate warnings could still pass CI because those assertions are gone and prod-shape covers claude only.
- **suggested fix:** Add a second prod-shaped tmpdir (non-matching prefix) that forces voter 2 parse-rate failure and assert the expected codex tool line in `$prod_issues`, or restore one codex-specific issues-log assertion outside the test-tmpdir prefix.
