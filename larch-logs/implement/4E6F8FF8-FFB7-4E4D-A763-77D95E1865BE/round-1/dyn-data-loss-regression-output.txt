### In-Scope Findings

- **risk-integration** `skills/cleanup/scripts/cleanup.sh:39-86` — Replacing `newest_activity_mtime` (depth-5 descendant scan) with top-level `find … -mtime +N` plus unconditional `rm -rf` reintroduces mid-run data loss for long-lived session trees: an active `/implement` or `/design` tmpdir under `~/.cache/larch/sessions/` or `/tmp` (`claude-implement-*`, etc.) whose **directory** mtime is older than `LARCH_CLEANUP_RETENTION_DAYS` (default 7) is deleted even when descendants are still being written (e.g. `round-<N>/`, `larch-logs/implement/<RUN_ID>/`). On typical Unix filesystems, writes only under subdirectories update those subdirectories’ mtimes, not necessarily the session root; `.larch-keepalive` is written once in `session-setup.sh` and is **not** a retention shield (the branch adds `stale-dir-with-keepalive-removed` and `stale-toplevel-with-fresh-deep-child-removed` to codify that). Root-level churn (`session-env.sh`, stderr logs, etc.) usually refreshes the root mtime during normal multi-hour runs, but resumed/stalled runs on an **old** `IMPLEMENT_TMPDIR`, or any session with >7 days between root-level writes, can be removed while Claude is still running; `SESSION_COUNT` is informational only. **Suggested fix:** Either restore a bounded activity signal for cache session dirs (e.g. shallow `find` or touch the session root when any descendant under known prefixes is written), or add an explicit “active session” skip (e.g. refresh `.larch-keepalive` mtime on hook cadence, or skip dirs whose keepalive `SESSION_ID` matches a live token) so `/cleanup` cannot delete trees that still match `lib-resolve-implement-tmpdir.sh` / SessionStart routing.
