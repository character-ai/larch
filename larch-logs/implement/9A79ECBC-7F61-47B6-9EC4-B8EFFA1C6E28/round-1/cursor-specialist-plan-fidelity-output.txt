### In-Scope Findings

1. **Important** (`correctness`) — [scripts/measure-realized-cost.sh](scripts/measure-realized-cost.sh) `52-54` vs implementation plan “scan `larch-logs/implement/*/manifest.json` …”  
   The script iterates `sorted((repo / "larch-logs").glob("*/*"))`, so any future two-level tree under `larch-logs/<category>/<run>/` that contains `manifest.json` / timing artifacts will be folded into the same counters, not only `implement/` (and not only the “similar subdirs” named in the ticket). That widens the population beyond the plan’s scoped root and can silently mix unrelated run types into `invocations` / `realized_tokens`. Restrict the glob to `larch-logs/implement/*` plus any explicitly enumerated sibling categories from the plan/ticket.

2. **Latent** (`correctness`) — [scripts/measure-realized-cost.sh](scripts/measure-realized-cost.sh) `56-86` vs ambiguous “invocations” intent  
   Skills are collected in a `set` per run directory, so `invocations[skill] += 1` counts at most **once per skill per run** even when `timing-report.json` lists many `per_step` rows for the same skill (e.g. long `implement` runs). If #2241 intended “one invocation per timing step” (each row a potential SKILL reload), `tokens_per_invocation` / `realized_tokens` are understated by a large factor. If the intended unit is “per completed run,” the set semantics are fine—confirm the metric definition and document or change counting accordingly.

3. **Nit** (`correctness`) — [feature_description](feature_description) item (2) “shell/awk helper” vs [scripts/measure-ngram-duplication.sh](scripts/measure-ngram-duplication.sh) (embedded Python)  
   The numbered ticket text still specifies a shell/awk helper, while the later “Implementation Plan” block and the shipped script use Python for shingling. Behavior matches the internal implementation plan, not the ticket’s “shell/awk” wording; update the ticket or add an explicit supersession note so acceptance checks do not reject the branch.

4. **Nit** (`architecture`) — Implementation plan bullet “read `SKILL.md` **byte counts**” vs [scripts/measure-realized-cost.sh](scripts/measure-realized-cost.sh) `104-105` and [scripts/measure-realized-cost.md](scripts/measure-realized-cost.md)  
   The plan text says bytes; the implementation and sibling doc use `tiktoken` token counts (which aligns with the TSV column names in the feature description). Refresh the implementation-plan wording to “token counts” to avoid contradictory sources of truth.

5. **Nit** (`risk-integration`) — Added committed artifact `larch-logs/measure-md-cost/2026-05-18.tsv` (large generated TSV) not listed in the implementation plan’s “Files to create/modify”  
   Shipping a dated measurement snapshot increases repo noise and is easy to misread as a required contract file. If the plan only required scripts to *write* under `larch-logs/...` at run time, prefer `.gitignore` or omit the committed snapshot unless the team explicitly wants a checked-in baseline.
