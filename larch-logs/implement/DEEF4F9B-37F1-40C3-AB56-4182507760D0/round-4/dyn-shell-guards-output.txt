### In-Scope Findings

- **code-quality** `skills/design/SKILL.md:813-816` — The Step 2a.5 resume-compatibility `elif` branch that only backfills `.completed/step-2a.5` does not use the same fail-fast pattern as the full artifact-repair branch above it (`set -e` after the `if [ "$_simple_artifacts_ok" != true ]` path). If `mkdir -p` or `: > "$DESIGN_TMPDIR/.completed/step-2a.5"` fails, the fence can still fall through and the orchestrator can print the SIMPLE skip breadcrumb and proceed to Step 2b with a missing `step-2a.5` marker, breaking pause/resume routing for legacy SIMPLE sessions. **Suggested fix:** Mirror the entry-fence/repair-branch pattern: wrap the marker-only branch in `set -e` (or explicitly test each write’s exit status and `exit 1` on failure) so a failed marker write halts the fence before Step 2b.

- **code-quality** `scripts/test-design-structure.sh:253-257` — `assert_step2a_entry_simple_guard` locates the SIMPLE guard’s closing `fi` via the first exact-line `fi` after the guard (`awk ... $0 == "fi"`). That is brittle: a nested `if`/`fi` inside the SIMPLE branch, or any future line that is exactly `fi`, will make the harness validate the wrong block boundaries and either false-pass (sentinel writes outside the guard) or false-fail on an otherwise correct fence. **Suggested fix:** Pin the closing `fi` with a more specific anchor (e.g., grep for the unique sentinel-write block tail, count `if`/`fi` depth between guard open and fence close, or assert line-order relative to a unique final line inside the SIMPLE branch such as the `step-2a.5` write).

- **code-quality** `scripts/test-design-structure.sh:333-359` — The new line-scoped Step 3b→Step 4 routing guard scans Step 3 through 3.5 and several reference files, but it does not scan the Step 3.6 slice (`<!-- step:3.6` through `<!-- step:3b`). Step 3.6 prose still says things like “then proceed to Step 3b” (`skills/design/SKILL.md:1243`) without naming the completion boundary on that line, so a future edit could add a direct “Step 3b → Step 4” shortcut in 3.6 without tripping the harness even though FINALIZE would be bypassed. **Suggested fix:** Add `assert_no_direct_step3b_step4_routes` for the Step 3.6 region (`'<!-- step:3.6'` → `'<!-- step:3b'`) and document that coverage in `scripts/test-design-structure.md`.

- **code-quality** `skills/design/SKILL.md:649,799` — Both the Step 2a entry fence and the Step 2a.5 repair fence call `read-design-classification.sh` with `2>/dev/null`, which suppresses the helper’s “defaulting to HARD” stderr warnings. If `run-params.json` is missing or malformed on a SIMPLE run, the fence silently treats the tier as HARD, skips the guarded SIMPLE writes, and the operator only sees that from later sketch-path behavior rather than from the classification Bash output. **Suggested fix:** Drop `2>/dev/null` on the classification read in these fences (the script already exits 0 when defaulting), or capture stderr and print a single warning breadcrumb when the helper emits its default-to-HARD message.
