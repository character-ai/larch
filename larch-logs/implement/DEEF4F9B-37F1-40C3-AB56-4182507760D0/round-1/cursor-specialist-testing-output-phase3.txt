### In-Scope Findings

- **risk-integration** `scripts/test-design-structure.sh:226` — `BEGIN { IGNORECASE=1 }` in `assert_no_direct_step3b_step4_routes` is a gawk-only extension. On macOS, `/usr/bin/awk` is BSD one-true-awk, which silently ignores `IGNORECASE`; matching becomes case-sensitive. The arrow/comma patterns (`Step 3b → Step 4` etc.) already use exact mixed-case literals and work correctly, but the verb pattern `/(continue|proceed|auto-continue|route|jump|enter|go)/` would miss capitalized forms — e.g. a future line "Continue to Step 4" without a boundary qualifier would pass the guard on macOS but fail on Linux CI, creating a platform divergence in the harness. The project's `BASH_AUTHORING.md` mandates macOS-toolchain compatibility for committed scripts. **Suggested fix:** replace `BEGIN { IGNORECASE=1 }` and the verb pattern with `tolower($0) ~ /(continue|proceed|auto-continue|route|jump|enter|go)/`, or use `command grep -i` for the verb scan separately.

- **risk-integration** `scripts/test-design-structure.sh:145-146` — `assert_step2a_entry_simple_guard` checks that `set -e` appears somewhere in the extracted fence body, but does not verify that `set -e` is lexically inside the `if [ "$_design_classification" = SIMPLE ]; then` branch. An implementation that placed `set -e` unconditionally before the `if` block would pass this assertion while activating fail-fast for HARD paths too (where a non-fatal exit code after the `||` rescue could abort). The `guard_line < first_artifact_line` ordering check correctly gates sentinel writes, but the `set -e` scope check leaves the fail-fast contract partially unverified. **Suggested fix:** after extracting `guard_line` and the `set -e` line number, assert `set_e_line > guard_line` to confirm `set -e` appears inside the SIMPLE branch.

- **risk-integration** `scripts/test-design-structure.sh:358-383` (new assertion calls) — The four new structural assertions (`assert_step3b_finalize_boundary`, `assert_step2a_entry_simple_guard`, `assert_simple_branch_has_no_sentinel_fence`, `assert_no_direct_step3b_step4_routes`) have no companion self-test blocks that deliberately trigger a failure to prove the assertion is effective. The existing `assert_gate_b_bypass_branch_sentinels` has this pattern (the `.md` contract documents self-tests that verify non-`plan-size-trigger` branches fail when a sentinel is dropped). Without self-tests, a latent bug in any new assertion (e.g. awk `found` variable never set, or scoped-slice extraction producing empty output) would silently pass, giving false confidence. **Suggested fix:** add self-test snippets analogous to the `Gate-B-bypass` self-test pattern, or at minimum add a comment noting the harness was manually validated against a deliberately broken version of the target file.

- **Nit** `code-quality` `scripts/test-design-structure.sh:139-165,221-234` — Both `assert_step2a_entry_simple_guard` and `assert_no_direct_step3b_step4_routes` create temp files with `mktemp` but call `rm -f "$tmp"` only at the normal exit path; an early `fail` call (which calls `exit 1`) skips the cleanup. Minor resource leak in CI. **Suggested fix:** use a `trap 'rm -f "$tmp"' EXIT` or `trap ... RETURN` immediately after `mktemp`, mirroring how `assert_thin_fence` already handles this via `scoped` guard.
