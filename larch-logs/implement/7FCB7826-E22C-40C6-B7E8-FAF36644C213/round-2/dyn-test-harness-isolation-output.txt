### In-Scope Findings

- **correctness** `skills/design/scripts/test-design-publish.sh:259-356` — Stub exports are not reset between cases that call `bash "$SUBJECT"` directly. After **PUBLISH_OK=false** (lines 263–264) `PUBLISH_OK_VALUE=false` stays exported. After **unexpected publish** (lines 290–291) `PUBLISH_STUB_RC=2` and `PUBLISH_EMIT_OK=false` stay exported. **clear-architecture** (314–331) and **upsert failure** (333–356) inherit that state: publish runs with `session-id` set, so `design-log-publish.sh` exits 2 without emitting `PUBLISH_OK=`, exercising the unexpected-failure path instead of the default happy stub. Both cases still pass because they only assert `--clear-architecture` in `UPSERT_LOG` or `PLAN_WRITE_OK=true` / exit 0, not clean publish/rename behavior. **Suggested fix:** Add a `reset_publish_stub_env()` (or per-case `unset`/`export` block) before every direct `bash "$SUBJECT"` invocation and at the start of `run_publish`, clearing `PLAN_BLOCK_RC`, `PUBLISH_STUB_RC`, `PUBLISH_EMIT_OK`, `PUBLISH_OK_VALUE`, `UPSERT_STUB_RC`, `UPSERT_STATUS_VALUE`, `ARCH_SOURCE_VALUE`, `RENAME_STUB_RC`, and `RENAMED_OMIT_LINE`, then set only what the case needs.

- **correctness** `skills/design/scripts/test-design-publish.sh:111-136` — `run_publish` uses `${PUBLISH_STUB_RC:-0}` (and similar) so once a prior case exports a non-default value, later `run_publish` calls keep it. Only `PLAN_BLOCK_RC` is unset after the plan-write-failure case (line 185); publish/upsert/rename stub vars are not cleared between `run_publish` cases. **Suggested fix:** Either call the same reset helper at the top of `run_publish` before applying defaults, or use explicit assignments (`export PUBLISH_STUB_RC=0`) instead of `:-` so each invocation gets a known baseline unless the case overrides.

- **correctness** `skills/design/scripts/test-design-publish.sh:187-217` — The plan acceptance criteria call for happy-path ordering including **marker before publish/rename**, but the harness only checks `CALL_LOG` order for `plan-block-write` → `upsert-diagrams` → `design-log-publish` (lines 200–208). `design_reentry_marker_write` is sourced from the real `lib-design-reentry-guard.sh` (line 41) and does not log to `CALL_LOG`, so marker-before-publish is not verified at runtime in this harness (static line-order pins live in `scripts/test-design-structure.sh:1032-1035`). **Suggested fix:** In the happy-path case, after `run_publish`, assert the reentry marker file exists (e.g. `$HOME/.cache/larch/sessions/design-completed-42-9999` for `--issue 42 --claude-pid 9999`) and that its mtime is not after the first `design-log-publish` entry in `PUBLISH_LOG` / `CALL_LOG`, or add a thin test-only wrapper that logs marker invocation before publish.

### Out-of-Scope Observations

- The rename-failure assertion at `skills/design/scripts/test-design-publish.sh:381-382` uses `grep -q 'WARN=.*\[DESIGNED\].*rename failed'`. Because `\[` and `\]` are escaped, `[DESIGNED]` is matched literally, not as a character class; the literal driver WARN line matches and `WARN=**⚠ 5c: D] rename failed` does not false-positive in basic grep on this platform.

- `RENAMED_OMIT_LINE` is defined in the tracking stub (lines 88–90) but no case sets it; that is unused harness surface, not contamination.

- Runtime marker ordering is covered by `scripts/test-design-structure.sh` source line-order pins on `design-publish.sh`; the gap above is harness-runtime coverage vs. the implementation plan’s ordering acceptance, not absence of all CI pins.
