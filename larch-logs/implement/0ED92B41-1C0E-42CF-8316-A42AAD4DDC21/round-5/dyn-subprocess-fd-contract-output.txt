Reviewing the diff and relevant source for subprocess FD contract correctness.
### In-Scope Findings

- **correctness** `python/proc.py:61-68,106-111` — `run_relevant_checks` passes a real log FD as both `stdout` and `stderr` (`checks.py:355-359`), so `proc.run` takes the non-`PIPE` branch with `popen_text=False` but still passes `errors="replace"` into `subprocess.Popen` / `subprocess.run`. In Python 3.12 binary mode that raises `ValueError: errors must be None` (same class of bug as the scout’s `TypeError` note). The only production caller of raw FD redirect is this path; unit tests use `StubRunner`, which never calls `proc.run`, so the defect is masked in `test_checks.py`. `test_checks_bash_parity.py:99-107` (`_ProcRunner` → real `proc.run`) should fail on `py.phase == "agent-lint"` because `checks.py:361-370` catches the exception and returns a generic `exit_code=1` / `phase="unknown"` result with no log content. **Suggested fix:** Only pass `errors="replace"` when `popen_text` is true (or set `encoding="utf-8", errors="replace"` for the PIPE path only). Add a `test_proc.py` case that runs a trivial command with `stdout=<open fd>` and asserts no exception and that bytes land in the file.

- **correctness** `python/checks.py:352-386` — The `os.close(log_fd)` in the outer `finally` runs only after `runner.run` returns, and `subprocess.run` blocks until the child exits, so there is no “close while child is still writing” race on the real `proc.run` path. The bash port uses the same pattern (`run-relevant-checks-captured.sh:188-192`: redirect to file, then read the path). **Suggested fix:** No change required for ordering; optional comment that the FD must stay open for the duration of `runner.run` only.

### Out-of-Scope Observations

- **correctness** `python/proc.py:117-122` — When callers pass a raw FD, `CommandResult.stdout` / `stderr` are always `''` (`_decode_output` on `None`/empty capture). That breaks the nominal `str` capture contract but is **safe for all current `checks.py` readers**: `run_relevant_checks` ignores `result.stdout` and reads `log_file` from disk (`checks.py:386-411`); every other `checks.py` use of `result.stdout` uses default PIPE capture (e.g. `583-627`, `757`, `1215`, `1336`). **Suggested fix (if tightening the seam later):** Document FD mode in the `Runner` protocol or return a sentinel / optional bytes field.

- **risk-integration** `python/test_proc.py` — No test covers the FD redirect branch introduced on this branch; combined with stub-only `run_relevant_checks` tests, the `errors`+`text=False` bug can ship while `make py-test` stays green on the stub path only. The parity test in `test_checks_bash_parity.py` is the right place to catch it once `proc.run` is fixed.
