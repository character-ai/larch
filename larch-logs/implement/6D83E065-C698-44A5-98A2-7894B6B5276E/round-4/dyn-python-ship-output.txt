Reviewing the Python OOS shipping path for correctness against the diff and Bash parity.
### In-Scope Findings

- **correctness** `python/ship.py:491-505` — After Step 9a.1 completes, the orchestrator re-invokes `ship.py` with `OOS_PENDING=false`, but `run_ship` still returns `NEEDS_USER_OOS_FILING` whenever any accepted-OOS markdown file is non-empty (`oos-accepted-main-agent.md`, resolved design path, or `oos-accepted-review.md`). That short-circuit runs before `_oos_gate` and never consults disposition evidence (`oos-issues-created.md`, `oos-issues.ndjson`, inline triage), so PR creation cannot succeed on the normal post-filing re-invoke while those artifacts remain on disk (the expected case). Round 3 added this block for bash `pr-prep` parity, but Python has no resume-phase bypass equivalent to bash reaching `pr-create` with `OOS_PENDING=false`. **Suggested fix:** Remove the unconditional size check, or gate it on missing disposition evidence; on re-invoke with `not ctx.oos_pending`, fall through to `_oos_gate` and allow `ensure_pr` when `disposition_ok` passes.

- **correctness** `python/ship.py:264-274` — NDJSON discovery diverges from `scripts/ship-pr.sh` `run_oos_disposition_gate_if_required_before_oos_pending_false` (lines 726–730): bash falls back to a single `*/oos-issues.ndjson` candidate when the canonical `$run_id` path is missing (`if [ -z "$oos_ndjson" ] || [ ! -f "$oos_ndjson" ]`), but Python only globs when `run_id` is empty (`if not run_id:`). If `ctx.run_id` is set while `larch-logs/implement/<run_id>/oos-issues.ndjson` is absent but exactly one alternate NDJSON exists, Python returns `NEEDS_USER_OOS_FILING` at lines 276–282 instead of using the discovered file, blocking PR creation after a successful Step 9a.1 step 6 write to a non-canonical path. **Suggested fix:** Mirror bash: after building the canonical path, if it is missing, glob for candidates; use the sole match; error on ambiguity only when `run_id` is empty.

- **correctness** `python/ship.py:491-505` — The accepted-file trigger uses `-s` / `st_size > 0`, matching bash `pr-prep`, but it does not distinguish security-routed-only content. `_oos_gate`/`oos.count_non_security` would treat security-only blocks as `non_sec == 0` and allow shipping, while the size check always forces another OOS-filing handoff for any non-empty accepted file. That is a behavioral mismatch with disposition semantics and amplifies the post-filing deadlock above. **Suggested fix:** Replace the raw size probe with the same non-security block count used in `_oos_gate`, or delegate entirely to `_oos_gate` for the “needs filing vs disposition satisfied” decision.
