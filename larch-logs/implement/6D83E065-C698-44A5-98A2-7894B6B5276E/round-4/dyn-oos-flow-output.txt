### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:1239-1281` — After Step 9a.1 completes and the orchestrator clears `OOS_PENDING=false` and re-invokes with `--resume-phase pr-create`, `run_pr_prep_phase` still keys off non-empty accepted-OOS markdown (`-s` on `oos-accepted-*.md`) and unconditionally re-sets `OOS_PENDING=true`, without running `run_oos_disposition_gate_if_required_before_oos_pending_false`. Round 1 added the `pr-create` guard that refuses PR creation while `OOS_PENDING=true` and exits 0, so the resume path becomes a closed loop: pr-prep → OOS_PENDING → pr-create refusal → orchestrator Step 9a.1 (sentinel idempotent) → checkpoint pass → clear → resume → pr-prep re-triggers OOS_PENDING forever, and no PR is ever created once any accepted-OOS file remains on disk. **Suggested fix:** Replace the file-size shortcut with gate-aligned logic: compute `non_sec_oos` (as already done in `run_oos_disposition_gate_if_required_before_oos_pending_false`), run the disposition gate when blocks exist, and set `OOS_PENDING=true` only when non-security blocks lack satisfied disposition (missing/invalid ndjson or gate failure); when the gate passes after filing, set `OOS_PENDING=false` and advance to `pr-create` without handing back to the orchestrator.

- **risk-integration** `python/ship.py:491-505` — The Python ship driver mirrors the same file-size trigger: after materialization it returns `NEEDS_USER_OOS_FILING` whenever any accepted-OOS markdown is non-empty, before calling `_oos_gate`. That bypasses the disposition logic added in `_oos_gate` (non-security count, ndjson discovery, `disposition_ok` with `filed_urls_strict_files`, sentinel URLs) which would return `None` and allow PR creation once Step 9a.1 has written `oos-issues-created.md` and `oos-issues.ndjson`. Re-invoking `python/ship.py` after a successful filing round therefore cannot reach `pr.ensure_pr`, matching the bash deadlock and breaking bash/Python parity for `LARCH_SHIP_PR_IMPL=python`. **Suggested fix:** Delete the non-empty-file early return at 491–505 and rely on `_oos_gate` (keeping the separate `security-oos-observations.md` block); extend `python/test_ship.py` with a post-filing scenario where accepted markdown, sentinel, and ndjson are present and `run_ship` reaches `Outcome.OK`.

- **risk-integration** `scripts/ship-pr.sh:763-767` — `run_oos_disposition_gate_if_required_before_oos_pending_false` omits `--filed-urls-strict-file "$oos_design_path"` even though `skills/implement/scripts/oos-disposition-checkpoint.sh:199` passes it and the gate counts pre-filed design `- **Filed URL**:` lines only via that strict surface. Today the internal gate is unreachable whenever design-export markdown is non-empty (because of the `-s` shortcut above), but once pr-prep routing is gate-aligned, an all-already-filed design batch could pass the orchestrator checkpoint yet fail the ship-pr internal clear path because strict field-line URLs are ignored. **Suggested fix:** Add `--filed-urls-strict-file "$oos_design_path"` to the internal gate invocation to match the checkpoint argv shape, and pin it in `scripts/test-implement-structure.sh` or an offline gate harness.
