Reviewing the branch diff and commit history with a focus on OOS redaction and security-routing boundaries.
### In-Scope Findings

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:114-120` — Manifest OOS is routed to the private sidecar only when structured `focus_area` matches `security…` or when the raw `description` contains a line shaped like `- **focus-area**: security…`; titles and prose such as `focus-area = security` stay on the public path (explicitly tested in `test-materialize-manifest-oos.sh` as “Security title only” → `oos-accepted-main-agent.md`). A Codex/Cursor implementer can therefore place vulnerability narratives in `oos_observations[].description` without any security marker and have them mechanically merged into `oos-accepted-main-agent.md` and onward toward public `/issue` filing after only `redact-secrets.sh` plus the helper’s regex PII/internal-URL pass—not the fenced/unfenced `focus-area=security` heuristic used for review/design OOS in `SECURITY.md`. **Suggested fix:** Either fail closed when `oos_observations[]` is non-empty and no item carries a security marker but description/title matches a conservative security classifier, or document and enforce in `codex-manifest-schema.md` + Step 2 validation that security findings must use structured `focus-area` and reject complete manifests that omit it for obviously security-shaped content; at minimum add a harness case proving sensitive manifest text never lands in `oos-accepted-main-agent.md` without an explicit security field.

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:114-119` — `security_signal` builds the probe line with `printf -- '- **focus-area**: %s\n' "$focus_area"` on unsanitized manifest JSON; embedded newlines in `focus_area` can inject extra `- **focus-area**:` lines into the awk stream and mis-classify routing on attacker-controlled or malformed manifest input. **Suggested fix:** Normalize structured `focus_area` to a single line (strip/ reject `\n`) and match the value with a direct regex (same as `oos-non-security-block-count.awk`) instead of re-serializing into markdown for parsing.

- **security** `python/ship.py:246-309` — `_oos_gate` counts non-security blocks and runs `disposition_ok` but never inspects `security-oos-observations.md`; the block only exists in `run_ship` (`python/ship.py:483-490`). Bash parity is enforced in `ship-pr.sh:756-758`, `ship-pr.sh:1234-1237`, and `oos-disposition-checkpoint.sh:176-178`. **Suggested fix:** Have `_oos_gate` return `NEEDS_USER_OOS_FILING` when the security sidecar is non-empty (with the same fork/repo-unavailable carve-outs as the checkpoint), so disposition cannot pass if a future caller invokes `_oos_gate` without the `run_ship` pre-check.

- **risk-integration** `skills/implement/references/oos-pipeline.md:15` — Step 1 states manifest `focus_area` is “preserved … as this dedicated field” in accepted markdown, but `materialize-manifest-oos.sh:207-213` writes public blocks without any `- **focus-area**:` line (only title, description, reviewer, vote tally, phase). Orchestrator-driven Step 9a.1 security exclusion that scans file bodies can miss JSON-only `focus_area` metadata that was already dropped at materialization, while still allowing description-only public filing for unmarked security content. **Suggested fix:** Align docs with behavior (routing uses JSON/description probe, public blocks omit focus-area) or emit `- **focus-area**:` on non-security materialized blocks when manifest supplies it so Step 1 file reads match the gate predicate.

- **security** `skills/implement/references/oos-pipeline.md:26,46,52` — Sanitization before combine, `/issue`, and `oos-issues` NDJSON compose is specified only as orchestrator/LLM duty; unlike the new mechanical boundary in `materialize-manifest-oos.sh:104-111`, there is no script enforcement on those Step 9a.1 outputs. A model following `oos-pipeline.md` can still file or log session-derived secrets, internal URLs, or PII that survived manifest materialization. **Suggested fix:** Add a mechanical redaction helper invoked on `oos-combined.md` / NDJSON bodies before `/issue` and `larch-log.sh append`, or narrow the contract to require running the same `sanitize_public_text` pipeline used by `materialize-manifest-oos.sh`.
