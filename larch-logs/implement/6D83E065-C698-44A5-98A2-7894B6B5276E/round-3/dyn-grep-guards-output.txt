Reviewing structure-test guards and Makefile wiring against the branch diff.
### In-Scope Findings

- **code-quality** `scripts/test-implement-structure.sh:542-550` — The `ship-pr.sh` ordering guard sets `mat` on the first line matching `materialize-manifest-oos\.sh` inside `run_pr_prep_phase`, which is the `materialize_oos="…/materialize-manifest-oos.sh"` assignment at `scripts/ship-pr.sh:1192`, not the `bash "$materialize_oos" …` invocation at `scripts/ship-pr.sh:1201`. Deleting the `bash` call while leaving the assignment (or a comment containing the script name) still yields `mat < pend` and passes CI even when manifest OOS is never materialized before `state_set OOS_PENDING true`. **Suggested fix:** Pin the first `bash` (or `"$materialize_oos"`) invocation line vs the first `state_set OOS_PENDING true` in `run_pr_prep_phase`, e.g. `awk` on `bash.*materialize-manifest-oos` or `bash "\$materialize_oos"`, and add a companion `grep -Fq 'bash "$materialize_oos"'` (or equivalent) so path assignment alone cannot satisfy the guard.

- **code-quality** `scripts/test-implement-structure.sh:525-527` — `step2-implement.sh` is only checked for the substring `materialize-manifest-oos.sh`, with no assertion that materialization runs under `if [[ "$STATUS" == "complete" ]]` or before Step 2 emits `STATUS=complete`. Moving the block outside the `complete` branch (or leaving only log/tool-failure strings that mention the helper) would still pass while breaking the manifest-only-OOS contract at Step 2. **Suggested fix:** Add a scoped `awk`/`sed` range from `if [[ "$STATUS" == "complete" ]]` through the materialize block (mirroring the ship-pr order pin) requiring `bash "$MATERIALIZE_OOS"` (or `"$HELPER"`) before `emit` of the final KV envelope.

- **code-quality** `scripts/test-implement-structure.sh:483-489` — The assertion 8b negative check only scans an 8-line window after each `ISSUES_FAILED>0` occurrence in `oos-pipeline.md`. A later step (outside that window) could reintroduce “append accepted disposition URL rows” without `do **not**` and the harness would still pass, weakening the partial-failure gate pin the plan called for. **Suggested fix:** Scope the negative rule to step 4/6 bodies (same `awk` boundary style as step 1’s `harvest`/`jq` pins) or require that every line matching `append accepted disposition URL rows` in the file also matches the `do **not**` form.

- **code-quality** `scripts/test-implement-structure.sh:430-431` — `load_count >= 3` counts every `${CLAUDE_PLUGIN_ROOT}/skills/implement/references/oos-pipeline.md` mention in `SKILL.md`, including policy cross-refs (e.g. lines 440, 459) and the Python selector paragraph, not only the three Step 9a.1 entry points. That duplicate signal can read as “three entry points wired” when only the separate 8-line `awk` block (443-454) actually enforces proximity; extra see-also lines make the count check easier to satisfy without fixing broken entry-point wiring if the scoped `awk` is loosened later. **Suggested fix:** Drop the global `>= 3` count (keep only the scoped `awk`), or count only lines that also contain the full `MANDATORY — READ ENTIRE FILE before executing the OOS pipeline` directive.
