### In-Scope Findings

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:104-111,189-204` — `security_signal` only routes observations when the title matches `^security`, the jq `focus_area` field is security-prefixed, or the description contains a dedicated `- **focus-area**:` line. Manifest text that describes a real security issue in `description` without that field line (including prose like `focus-area = security`, which the harness explicitly keeps on the public path in `test-materialize-manifest-oos.sh:66-73`) is written to `oos-accepted-main-agent.md` and is eligible for public `/issue` filing. That widens the manifest→public pipeline introduced by this branch while `codex-manifest-schema.md` still says `oos_observations[]` excludes security findings. **Suggested fix:** Align materialization with the gate predicate (dedicated `- **focus-area**:` line only, or an equivalent structured manifest field written as that line) and fail closed or route to `security-oos-observations.md` when description/title heuristics indicate security content; document the rule in `materialize-manifest-oos.md` and add a regression case for “sensitive description, no field line → never lands in `oos-accepted-main-agent.md`.”

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:96-101` — `sanitize_public_text` is the only mechanical redaction before public-boundary markdown is written. Internal URLs are limited to localhost, RFC1918, and hostnames ending in `.internal|.local|.corp|.lan|.intranet`; `redact-secrets.sh` explicitly does not cover private hostnames. Corporate or SaaS-internal URLs (for example `https://github.example.com/...`) can survive into `oos-accepted-main-agent.md`, `oos-combined.md`, public GitHub issues, and committed `oos-issues` NDJSON. **Suggested fix:** Reuse the same outbound redaction path as SKILL.md (shared helper or `redact-secrets.sh` extension for internal URLs/PII), run it on every manifest-derived title/description before append, and add harness cases for non-matching internal hosts and for secret-shaped tokens asserting `<REDACTED-TOKEN>`.

- **security** `skills/implement/references/oos-pipeline.md:25-26,42-46,51-52` — Steps 3.4, 4, and 6 require prompt-side “Sanitize before compose” / “sanitize NDJSON `body`”, but there is no script enforcement on `oos-combined.md`, `oos-grouping-worksheet.md`, or `/issue` input. With this branch, manifest OOS is mechanically copied into `oos-accepted-main-agent.md` first; a missed orchestrator sanitize step can propagate session-derived text unchanged to public issues and committed logs. **Suggested fix:** Add a mechanical sanitize pass (same rules as `sanitize_public_text` or a shared library) immediately before writing `oos-combined.md` and before `/issue` batch invocation, or wire an existing redaction script into a small helper invoked from the documented steps.
