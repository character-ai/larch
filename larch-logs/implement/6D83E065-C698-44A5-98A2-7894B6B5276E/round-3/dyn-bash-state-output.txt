### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:1204-1252` + `skills/implement/references/oos-pipeline.md:17-19` — When `materialize-manifest-oos.sh` fails in `run_pr_prep_phase` but `jq` still reports a non-empty `oos_observations[]`, the script sets `OOS_PENDING=true` and hands off to the orchestrator, yet no accepted-OOS markdown is written. Step 9a.1 step 2 treats that as a “true no-input batch” and early-exits before filing; `oos-disposition-checkpoint.sh` then sees `non_security_oos=0` and can exit 0, allowing `OOS_PENDING=false` and `--resume-phase pr-create` while manifest OOS never reach `oos-accepted-main-agent.md` or GitHub. **Suggested fix:** On materialize non-zero with `materialize_count>0`, do not allow a no-input early-exit to clear disposition—e.g. stall, keep `OOS_PENDING` until materialize succeeds (retry helper from step 1 or a dedicated fail-closed branch), or treat the run as a checkpoint validation failure until `oos-accepted-main-agent.md` exists.

- **risk-integration** `python/ship.py:459-478` + `python/oos.py:164-196` — Round 2 removed the non-empty `oos-accepted-*.md` presence check; the Python path now goes straight from materialize to `_oos_gate` via `disposition_ok()`, which does not enforce `oos-disposition-checkpoint.sh`’s rule that `non_security_oos>0` requires a resolvable `oos-issues.ndjson`. If loose URL evidence in `oos-issues-created.md` satisfies `disposition_ok`, `ensure_pr` can run without the orchestrator executing Step 9a.1 step 6 (NDJSON append), diverging from bash where any `-s` accepted file forces `OOS_PENDING=true` and the full pipeline. **Suggested fix:** Mirror bash: after materialize, if any accepted-OOS file is non-empty or `security-oos-observations.md` is non-empty, return `NEEDS_USER_OOS_FILING` without calling `ensure_pr`; or invoke `oos-disposition-checkpoint.sh` (including its NDJSON pre-validation) instead of the slimmer `disposition_ok()` shortcut.

- **risk-integration** `scripts/ship-pr.sh:3271-3298` + `run_pr_create_phase` at `1256-1262` — `--resume-phase pr-create` jumps directly to `run_pr_create_phase`, skipping `run_pr_prep_phase` and a second `materialize-manifest-oos.sh` call. That is safe only if the orchestrator actually materialized and filed OOS before clearing `OOS_PENDING`; it amplifies the first finding when materialize failed at pr-prep but the checkpoint still cleared. **Suggested fix:** On `--resume-phase pr-create`, either re-run pr-prep materialize or refuse resume until `oos-accepted-main-agent.md` reflects manifest `oos_observations` (or a Tool Failures stall is recorded).
