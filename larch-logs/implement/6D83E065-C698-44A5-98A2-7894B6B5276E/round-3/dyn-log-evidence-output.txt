Reviewing the branch diff and commit history for risk-integration issues in the OOS pipeline changes.
### In-Scope Findings

- **risk-integration** `skills/implement/references/oos-pipeline.md:17-19` + `scripts/ship-pr.sh:1215-1218` — Manifest-only security OOS are written to `security-oos-observations.md` and both `ship-pr.sh` and `python/ship.py` force `OOS_PENDING=true`, but `oos-pipeline.md` step 1 never reads that file and step 2 classifies the run as a true no-input batch (`early-exit before steps 3–7`). The disposition gate then sees `non_security_oos=0`, passes, and the post-checkpoint block can write `run-statistics` and clear `OOS_PENDING` even though the only new OOS evidence is a Warning breadcrumb — not SECURITY.md private disclosure and not any `oos-issues` NDJSON row for the security observations. **Suggested fix:** Add an explicit security-routed branch in `oos-pipeline.md` (read `security-oos-observations.md`, require SECURITY.md private-disclosure completion or an explicit audit row, and only then hand off to the checkpoint), or stop setting `OOS_PENDING` when materialization produces security-only output with no accepted-OOS markdown inputs.

- **risk-integration** `skills/implement/references/oos-pipeline.md:20-23,51-55` — Sentinel-recovery ownership of the `oos-issues` larch-log batch is duplicated: step 3 already mandates `larch-log.sh append … --batch oos-issues` from recovered sentinel URLs, and step 6 also says “Sentinel-recovery … branches still write the required evidence rows.” An orchestrator that follows both steps can append duplicate NDJSON records on idempotent rerun; URL de-duplication in the gate may still pass, but the committed run-log contract gets noisy/possibly inconsistent evidence and `run-statistics` filed counts can drift from actual new filings. **Suggested fix:** Make step 3 the sole sentinel-recovery writer (step 6 should explicitly skip sentinel-recovery and only cover normal filing and all-already-filed paths), or add an idempotency guard keyed on existing `oos-issues.ndjson` rows before append.

- **risk-integration** `skills/implement/references/oos-pipeline.md:17-19,51-55` + `skills/implement/scripts/oos-disposition-gate.sh:195-201` — The new all-already-filed branch requires step 6 NDJSON evidence, but the mechanical gate still passes whenever strict `- **Filed URL**:` lines in the design accepted file yield `filed_urls > 0` (disjunctive pass, not per-block coverage). An orchestrator can therefore skip step 6, clear `OOS_PENDING`, and ship while the committed `larch-logs/implement/<RUN_ID>/oos-issues.ndjson` batch is missing — breaking the larch-log evidence contract the branch is trying to restore. **Suggested fix:** Either require `--oos-issues-ndjson` presence/non-empty accepted rows before gate pass on the all-already-filed path, or add a mechanical step-6 helper (similar to `oos-disposition-checkpoint.sh`) that materializes NDJSON from `- **Filed URL**:` / sentinel URLs and fails closed if the batch is absent.

- **risk-integration** `skills/implement/scripts/materialize-manifest-oos.sh:104-110` + `skills/implement/scripts/materialize-manifest-oos.md:5` + `skills/implement/references/oos-pipeline.md:15` — Security routing in the new materializer is broader than the gate-aligned predicate documented in `oos-pipeline.md` and enforced by `oos-non-security-block-count.awk`: `security_signal()` also excludes observations whose title begins with `security` (see `test-materialize-manifest-oos.sh` “Security title only”), while the contract text mentions only dedicated `- **focus-area**:` field lines. The same observation would be counted and publicly filed if it arrived via `oos-accepted-review.md` instead of manifest JSON, creating inconsistent disposition/evidence paths across Step 2 materialization vs Step 9a.1/gate counting. **Suggested fix:** Align `security_signal()` with the gate predicate (drop title-prefix routing, or document and mirror it in `oos-pipeline.md` step 1 and the awk gate counter), and update `materialize-manifest-oos.md` to match the implemented rule.
