Comparing Python and bash ship paths for OOS resolution and materialization parity.
### In-Scope Findings

- **architecture** `python/ship.py:451-478` — Bash `run_pr_prep_phase` in `scripts/ship-pr.sh:1220-1223` unconditionally sets `OOS_PENDING=true` and hands off to the orchestrator whenever any accepted-OOS markdown file is non-empty (`-s` on `oos-accepted-main-agent.md`, resolved design path, or `oos-accepted-review.md`), **before** running `oos-disposition-gate.sh`. The new Python path skips that size gate and goes straight to `_oos_gate` / `oos.disposition_ok`; when disposition already satisfies the gate (e.g. design blocks with `- **Filed URL**:` plus sentinel/NDJSON evidence), `run_ship` proceeds to `pr.ensure_pr` without `NEEDS_USER_OOS_FILING`. That bypasses mandatory Step 9a.1 orchestration documented in `oos-pipeline.md` (step 2 all-already-filed still requires step 6 NDJSON evidence; step 7 checkpoint handoff), which bash always routes through `OOS_PENDING=true` while those files remain non-empty. `python/test_ship.py:193-215` encodes this divergent behavior. **Suggested fix:** After materialization and the `security-oos-observations.md` check, mirror bash with an explicit non-empty accepted-OOS probe on the three resolved paths (same `resolve_oos_accepted_design_path` as bash) and return `NEEDS_USER_OOS_FILING` with `oos_pending=True` whenever any probe is non-empty; only call `_oos_gate` when all accepted-OOS sources are empty/missing, matching the bash branch that reaches `run_oos_disposition_gate_if_required_before_oos_pending_false`.

- **architecture** `python/ship.py:257-267` — NDJSON discovery in `_oos_gate` keys only on `ctx.run_id` (CLI/env `RUN_ID`) and a glob fallback when `run_id` is empty. `oos-disposition-checkpoint.sh:131-144` resolves `_RUN_ID` from `ship-pr-state.sh` / `finalize-state.sh`, then falls back to `$IMPLEMENT_TMPDIR/session-id`; `scripts/ship-pr.sh:721` uses `session-id` for the pr-prep gate path. If `RUN_ID` is unset in the Python invocation but `session-id` is populated (a supported session layout), Python may miss the run-scoped `oos-issues.ndjson` while bash/checkpoint find it, yielding different disposition or ambiguous-NDJSON handling under `LARCH_SHIP_PR_IMPL=python`. **Suggested fix:** Add a shared resolver (e.g. in `python/oos_paths.py`) that mirrors checkpoint order: state `RUN_ID` → `session-id` file → env/argv, and use it in `_oos_gate` before the single-candidate glob fallback.

### Out-of-Scope Observations

- `scripts/ship-pr.sh:744-748` vs `skills/implement/scripts/oos-disposition-checkpoint.sh:192-197` — pr-prep’s internal `run_oos_disposition_gate_if_required_before_oos_pending_false` omits `--filed-urls-strict-file`, while the Step 8+ checkpoint and Python `_oos_gate` include strict design-path counting; this predates the branch and only affects the rare “all accepted-OOS files empty” pr-prep path.

- `python/oos.py` reimplements `oos-disposition-gate.sh` instead of invoking it; long-term drift risk, but not a regression introduced by this diff’s materialization/resolver work.
