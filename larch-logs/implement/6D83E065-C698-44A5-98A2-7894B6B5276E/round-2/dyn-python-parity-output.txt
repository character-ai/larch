Reviewing the branch diff and comparing Python `ship.py` with bash `ship-pr.sh` for OOS-path parity.
### In-Scope Findings

- **architecture** `python/ship.py:415-434` — Round-1 added a non-empty accepted-OOS file size guard (`st_size > 0`) that returns `NEEDS_USER_INPUT` / `oos-filing` **before** `_oos_gate` runs. After Step 9a.1, those markdown files normally stay populated (with filed URLs in `oos-issues-created.md`), so a second `python3 …/ship.py` reinvoke still hits this guard even when disposition is satisfied. Bash avoids that by resuming with `ship-pr.sh --resume-phase pr-create`, which skips `pr-prep`; the initial branch commit called `_oos_gate` directly and did not have this guard. **Suggested fix:** Remove the size-only shortcut or run `_oos_gate` first and only hand back on `disposition_ok` failure; optionally add a Python `pr-create`-only resume path aligned with bash so post-filing reinvokes do not re-enter full `pr-prep`.

- **correctness** `python/ship.py:226-231` — `_oos_gate` feeds `oos.disposition_ok` commit text from `git log --format=%s` (subjects only) and only when `ctx.run_id` is set. Bash `oos-disposition-gate.sh` scans full commit bodies (`--format=%B`) over merge-base `..HEAD` on every run. Inline-triage breadcrumbs in commit bodies can satisfy the gate in bash but be invisible to the Python driver, so Python may block PR creation or re-request `oos-filing` after inline disposition. **Suggested fix:** Mirror bash: always resolve `merge-base..HEAD` (or `origin/main..HEAD`) and pass full commit messages into `commit_range_messages`, or invoke `oos-disposition-gate.sh` instead of the inlined helper.

- **architecture** `python/ship.py:202-248` — Pre-PR OOS enforcement is duplicated in `oos.disposition_ok` instead of calling `skills/implement/scripts/oos-disposition-gate.sh` / `oos-disposition-checkpoint.sh`. The branch added ndjson discovery and `filed_urls_strict_files`, but checkpoint-only rules (e.g. requiring `--oos-issues-ndjson` when `non_sec_oos > 0` in `oos-disposition-checkpoint.sh:175-179`) are not applied on the Python path, so bash and Python can disagree on pass/fail at the same tmpdir. **Suggested fix:** Subprocess the same gate/checkpoint scripts with the same argv shape as `ship-pr.sh` / `oos-disposition-checkpoint.sh`, or add explicit parity tests that run both paths on identical fixtures.

- **architecture** `python/ship.py:415-420` vs `scripts/ship-pr.sh:1204-1208` — On `materialize-manifest-oos.sh` failure with non-empty `oos_observations[]`, bash sets `OOS_PENDING=true` in `ship-pr-state.sh` and advances to `pr-create` (which refuses PR creation while pending). Python returns `NEEDS_USER_INPUT` but does not set `ctx.oos_pending` or persist `OOS_PENDING=true` in the state file it writes; `RunContext.from_env()` never reads `OOS_PENDING` back from `ship-pr-state.sh`. Mixed bash/Python sessions or tooling that keys off state can see divergent “pending OOS” signals. **Suggested fix:** On the same failure predicate as bash, persist `OOS_PENDING=true` via `_write_ship_state` before returning `NEEDS_USER_OOS_FILING`, or document and test that the Python path is JSON-outcome-only and never consults state for OOS pending.

### Out-of-Scope Observations

- **architecture** `python/ship.py:366-437` — The Python driver still has no phase-resume equivalent to `ship-pr.sh --resume-phase pr-create`; every invoke reruns checks, postbump, and pr-prep. That predates this branch but amplifies the size-guard regression above.

- **architecture** `scripts/ship-pr.sh:744-748` vs `skills/implement/scripts/oos-disposition-checkpoint.sh:192-197` — `run_oos_disposition_gate_if_required_before_oos_pending_false` in `pr-prep` omits `--filed-urls-strict-file`, while the Step 8+ checkpoint passes it. Not introduced by the Python OOS changes; both bash entrypoints already differ.
