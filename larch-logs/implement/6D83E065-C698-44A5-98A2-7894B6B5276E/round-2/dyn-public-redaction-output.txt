Reviewing the branch diff and commit history for security/redaction issues in OOS pipeline changes.
### In-Scope Findings

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:147-159` — Security routing runs only on the manifest `description` string (`printf '%s\n' "$description" | security_focus_area`); it does not inspect the observation `title`, JSON keys such as `"focus-area"` / `"focus_area"`, or any other manifest field. An implementer can mark an item security-only via a top-level JSON field or by putting `- **focus-area**: security` in `title` while keeping exploit details in `description`; the helper materializes it into `oos-accepted-main-agent.md`, and `oos-non-security-block-count.awk` will still count it as non-security because the gate only matches a dedicated `- **focus-area**:` **body** line, not text embedded in the `### OOS_N:` heading. That path reaches public `/issue` filing. **Suggested fix:** Before append, evaluate title, description, and structured manifest fields with the same gate-aligned predicate used in `oos-non-security-block-count.awk`; when routing to the private path, emit a proper `- **focus-area**:` field line in the security audit artifact (not in public markdown) and add harness cases for JSON-field and title-only markers.

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:92-101` — Mechanical redaction in `sanitize_public_text` covers a fixed internal-host/PII regex set but omits common non-public endpoints such as link-local/cloud metadata (`169.254.169.254`) and internal hostnames outside the hard-coded TLD suffix list. Manifest-derived descriptions sanitized here are written to `oos-accepted-main-agent.md` and can later be forwarded verbatim by `/issue` batch mode per `skills/implement/references/oos-pipeline.md:46`, so those URLs can become public issue content even though `oos-pipeline.md` documents broader dual-write redaction. **Suggested fix:** Reuse or extract the shared outbound scrubber used elsewhere (or expand the regex set to include link-local/metadata ranges) and add regression tests for metadata-style URLs and non-suffix internal hosts.

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:131-143` — Security-routed manifest observations are withheld from public OOS markdown, but `append_security_audit` persists only the normalized title plus a disposition line; the observation description (often the actionable security content operators need for SECURITY.md private disclosure) is discarded from every tmpdir artifact except the still-present manifest JSON. That breaks the documented private-flow intent in `skills/implement/references/oos-pipeline.md:15` and makes security findings easy to lose operationally without reducing public exposure. **Suggested fix:** Append a redacted copy of title, description, phase, and any focus-area metadata to `security-oos-observations.md` (never to `oos-accepted-main-agent.md`), using the same `sanitize_public_text` path, and test that security-routed items retain redacted body text in the audit file only.

- **security** `skills/implement/scripts/materialize-manifest-oos.sh:92-97` — If `scripts/redact-secrets.sh` is missing or not executable, `sanitize_public_text` passes manifest title/description through with only the local sed rules, failing open on the secrets family even though `step2-implement.sh` fail-closes on an unexecutable manifest redactor and `/issue` relies on that scrubber as outbound defense-in-depth. A degraded environment can therefore materialize token-bearing manifest text into gate-visible accepted-OOS files. **Suggested fix:** Fail closed (non-zero exit) when `oos_observations[]` is non-empty and `redact-secrets.sh` is not executable, mirroring the Step 2 redactor contract; keep fail-open behavior only for empty/absent observation arrays.

### Out-of-Scope Observations

- **security** `skills/implement/references/oos-pipeline.md:25-46` — Steps 3.4, 4, and 6 rely on prompt-side “Sanitize before compose” instructions rather than a mechanical scrubber at combine/file time; that predates this branch but remains a residual public-filing risk for design/review accepted-OOS sources that never pass through `materialize-manifest-oos.sh`.

- **security** `skills/implement/references/codex-manifest-schema.md:53-63` — Security-routed manifest observations can remain in `$IMPLEMENT_TMPDIR/manifest.json` with full descriptions; this branch does not introduce that surface, but it is unchanged by the new security-routing helper and can still leak if the manifest is copied into committed run-log artifacts without additional redaction.
