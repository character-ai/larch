Reviewing the branch diff and Python/bash OOS integration points for risk-integration issues.
### In-Scope Findings

- **risk-integration** `python/ship.py:188-224` — `_oos_gate` calls `oos.disposition_ok` without `filed_urls_strict_files`, while `oos-disposition-checkpoint.sh` always passes `--filed-urls-strict-file` on the resolved design path (`196:196:skills/implement/scripts/oos-disposition-checkpoint.sh`). The branch adds `resolve_oos_accepted_design_path` and includes that path in `accepted_files`, but design-phase `- **Filed URL**:` lines (the all-already-filed carve-out in `oos-pipeline.md` step 2) are not counted in the Python pre-PR gate. Under `LARCH_SHIP_PR_IMPL=python`, runs can spuriously return `needs_user_reason=oos-filing` even when bash’s post–Step 9a.1 checkpoint would pass, or operators must redo filing work that bash would treat as already disposed. **Suggested fix:** Pass `filed_urls_strict_files=(str(design_path),)` into `disposition_ok` when `design_path.is_file()`, mirroring the checkpoint argv, and add a `test_ship.py` / `test_oos.py` case with design-export `- **Filed URL**:` lines and no sentinel.

- **risk-integration** `python/ship.py:188-224` — `scripts/ship-pr.sh` pr-prep treats any non-empty accepted-OOS markdown as mandatory filing work (`1209:1213:scripts/ship-pr.sh`: `-s` on main-agent, resolved design, or review → `OOS_PENDING=true` and handoff) without running a disposition pre-check. Python’s `_oos_gate` runs `disposition_ok` first and, if it returns `ok=True`, `run_ship` proceeds to `pr.ensure_pr` (`387:395:python/ship.py`) even when those same accepted files are still non-empty. With the new design-export resolution, design-only accepted OOS now participates in disposition; a stale `oos-issues-created.md` with any matching URL can satisfy `filed > 0` (`188:188:python/oos.py`) and skip the orchestrator’s full Step 9a.1 steps 1–7 that bash always enters when accepted files exist. **Suggested fix:** After materialization, if any resolved accepted path is a non-empty file, return `NEEDS_USER_OOS_FILING` (or set `OOS_PENDING` in written state) regardless of `disposition_ok`, matching bash’s `-s` trigger; reserve `disposition_ok` for the post–9a.1 clearance path only.

- **risk-integration** `python/ship.py:201-216` — `oos-disposition-checkpoint.sh` fails closed when `non_security_oos > 0` but the run-keyed `oos-issues.ndjson` path is missing or undiscoverable (`175:179:skills/implement/scripts/oos-disposition-checkpoint.sh`). Python passes `oos_issues_ndjson=None` when `tmpdir/larch-logs/implement/<run_id>/oos-issues.ndjson` is absent and may still treat disposition as satisfied via `oos-issues-created.md` or inline triage alone, allowing PR creation without the NDJSON evidence surface the checkpoint requires before clearing `OOS_PENDING`. **Suggested fix:** Port the checkpoint precondition into `_oos_gate` (count non-security blocks first; require a readable ndjson path when count > 0) or invoke `oos-disposition-checkpoint.sh` from the Python driver instead of the inlined `disposition_ok` subset.
