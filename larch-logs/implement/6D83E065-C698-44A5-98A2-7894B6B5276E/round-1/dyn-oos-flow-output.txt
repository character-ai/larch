### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:1201-1205`, `skills/implement/references/oos-pipeline.md:11-19`, `python/oos.py:176-180` — On `materialize-manifest-oos.sh` failure, `run_pr_prep_phase` sets `OOS_PENDING=true`, advances to `pr-create`, and exits 0 without guaranteeing manifest `oos_observations[]` were written to accepted markdown. Step 9a.1 step 1 is explicitly markdown-only (no manifest re-materialization), so if Step 2 also failed to materialize (fail-open when `MAT_OOS_COUNT` reads 0, helper missing with a miscounted array, or a resume path that skipped Step 2 materialization), the orchestrator can hit oos-pipeline step 2 “true no-input,” run the checkpoint with zero `### OOS_` blocks in accepted files, get `non_security_oos=0`, clear `OOS_PENDING`, and resume PR creation while manifest JSON still carries unfilled OOS — a NEVER #14 silent-drop hole. **Suggested fix:** On ship pre-trigger materialize failure when the manifest reports a non-empty `oos_observations[]`, fail closed (stall or keep `OOS_PENDING` without advancing to `pr-create`) instead of handing off to prompt-only Step 9a.1; alternatively, add a mandatory `materialize-manifest-oos.sh` re-invocation at the start of the Exit 0 / OOS checkpoint / Python `oos-filing` path (before oos-pipeline step 1), and add a structure or integration test that simulates manifest-only OOS plus materialize failure and asserts the checkpoint blocks rather than passing with `non_security_oos=0`.

- **risk-integration** `python/ship.py:188-223`, `skills/implement/scripts/oos-disposition-checkpoint.sh:175-179` — Bash checkpoint plumbing requires a resolvable `oos-issues.ndjson` whenever `non_security_oos > 0` before invoking the gate, but Python `_oos_gate` calls `oos.disposition_ok` directly with no equivalent pre-validation. Because `disposition_ok` treats `filed > 0` from `oos-issues-created.md` alone as sufficient (`python/oos.py:188`), the Python ship path can proceed to `pr.ensure_pr` when accepted-OOS blocks exist and a sentinel URL table satisfies the loose URL counter, even though the staged NDJSON batch the bash checkpoint mandates is absent — bypassing the evidence surface NEVER #14/#15 rely on. **Suggested fix:** Port the checkpoint’s ndjson discovery and mandatory pre-check into `_oos_gate` (or invoke `oos-disposition-checkpoint.sh` from Python before PR create), and pass `filed_urls_strict_files` for the resolved design path to match bash `--filed-urls-strict-file`; add a `python/test_ship.py` case with accepted OOS blocks, sentinel URLs, and no ndjson that expects `NEEDS_USER_OOS_FILING` rather than `Outcome.OK`.

- **risk-integration** `python/ship.py:175-185`, `skills/implement/scripts/materialize-manifest-oos.md:11` — The materialize contract says callers should fail closed only when the manifest has a non-empty `oos_observations[]`, and fail open (Tool Failures breadcrumb only) when the array is empty or absent. Python `_materialize_manifest_oos` returns `NEEDS_USER_OOS_FILING` on any non-zero helper exit without checking observation count, so benign infrastructure failures on an empty manifest (missing `jq`, tmpdir glitch) force a full Step 9a.1 orchestrator loop even though no OOS exists to file. **Suggested fix:** Mirror `step2-implement.sh` and `ship-pr.sh` by jq-counting `oos_observations[]` before branching: non-empty array + materialize failure → `NEEDS_USER_OOS_FILING`; empty/absent array + failure → append Tool Failures and continue to `_oos_gate`.

- **risk-integration** `scripts/ship-pr.sh:1203-1205`, `scripts/ship-pr.sh:1246-1307` — The new materialize-failure branch advances `PHASE` to `pr-create` while leaving `OOS_PENDING=true`, but `run_pr_create_phase` never reads `OOS_PENDING` and will open a PR if invoked with `--resume-phase pr-create` before the orchestrator completes the OOS checkpoint. That was always a discipline gap; this branch adds a new path that reaches `pr-create` with pending OOS and no accepted markdown, increasing the blast radius of a mistimed resume. **Suggested fix:** Add a hard guard at the top of `run_pr_create_phase` (and the Python PR-create entry) that exits non-zero or stalls when `OOS_PENDING=true`, matching the checkpoint-before-clear invariant in NEVER #15.
