Reviewing the branch diff and bash control-flow changes in the scoped files.
### In-Scope Findings

- **code-quality** `skills/implement/scripts/step2-implement.sh:1115-1125` — On `materialize-manifest-oos.sh` failure, `append-tool-failure.sh` is always called with `--exit-code "1"` even though the helper can exit for several distinct reasons (usage, missing tmpdir, malformed JSON, `jq` failure, write error). That loses the real exit code in `execution-issues.md` and makes post-run triage harder. **Suggested fix:** Capture the helper status immediately after the `bash` invocation (`mat_rc=$?` inside the `if !` branch) and pass `--exit-code "$mat_rc"` to `append-tool-failure.sh` in both the failure and missing-helper paths.

- **risk-integration** `scripts/ship-pr.sh:1201-1205`, `python/ship.py:175-185`, `skills/implement/scripts/materialize-manifest-oos.md:11` — Caller failure policy is inconsistent. `materialize-manifest-oos.md` says callers should fail closed only when `oos_observations[]` is non-empty; `step2-implement.sh` follows that via `MAT_OOS_COUNT`. `ship-pr.sh` and `python/ship.py` set `OOS_PENDING` / return `NEEDS_USER_OOS_FILING` on **any** non-zero materialize exit, including infrastructure failures on an empty array (e.g. `jq` missing, unreadable tmpdir, invalid top-level JSON) after Step 2 already returned `STATUS=complete`. That can stall shipping with no manifest OOS to file. **Suggested fix:** Mirror the Step 2 guard: parse observation count (or a dedicated helper KV like `OBSERVATIONS=`) and only force the OOS checkpoint when count &gt; 0; otherwise log via `record_failure` / `append-tool-failure.sh` and continue pr-prep when there is nothing to materialize.

- **correctness** `skills/implement/scripts/step2-implement.sh:1112` — `MAT_OOS_COUNT` uses `jq … 2>/dev/null || printf '0'`, so a transient `jq` parse failure is treated as zero observations. Combined with the fail-open branch (`MAT_OOS_COUNT` not &gt; 0 → no `emit_bailed`), Step 2 can emit `STATUS=complete` while manifest OOS never reach `oos-accepted-main-agent.md`, relying on a later ship hook to recover. **Suggested fix:** Treat a non-zero `jq` exit as a hard error when evaluating count (or reuse the helper’s exit status after a materialize attempt) instead of defaulting to `0`; only suppress bail when the manifest is provably empty.

- **code-quality** `skills/implement/scripts/materialize-manifest-oos.sh:61-70,116-118` — `has_title` passes the manifest title into `awk -v wanted="$title"` without escaping. Titles containing `"`, backslashes, or newlines can break AWK parsing or defeat deduplication, causing duplicate `### OOS_N:` blocks on rerun and inconsistent idempotency. **Suggested fix:** Compare titles in Bash (e.g. `grep -F` on normalized heading lines) or pass titles via `awk -v` only after `awk -v`/`ENVIRON` safe escaping, or write titles to a delimited temp file and let AWK read them as data.
