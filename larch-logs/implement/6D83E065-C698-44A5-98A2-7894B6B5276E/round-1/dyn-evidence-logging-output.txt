### In-Scope Findings

- **architecture** `skills/implement/SKILL.md:1042` — The post-checkpoint `run-statistics` contract defines `$ACCEPTED` as “the count of accepted-OOS items filed” without scoping that count to issues created in the current Step 9a.1 pass (e.g. `ISSUES_CREATED` from step 4). `skills/implement/references/oos-pipeline.md:59` separately requires that “Recovered-from-sentinel items remain excluded from newly filed counts,” but that rule is not wired into the authoritative consumer text that actually writes `run-statistics`. On sentinel-idempotent reruns, an orchestrator can satisfy the disposition checkpoint (URLs already in `oos-issues-created.md` / NDJSON) and still write inflated filed counts in `run-statistics.md`, breaking the intended split between gate-visible `oos-issues` evidence and post-checkpoint statistics. **Suggested fix:** Align `SKILL.md` OOS checkpoint prose with `oos-pipeline.md` step 7: define `$ACCEPTED` as newly filed issues from the current `/issue` batch only (or `0` on sentinel-recovery / all-already-filed branches), and add a structure-test pin that the checkpoint example references sentinel exclusion or `ISSUES_CREATED`-scoped counting.

- **architecture** `skills/implement/references/oos-pipeline.md:51-55` — Step 6 owns checkpoint-visible `oos-issues` NDJSON evidence for accepted/disposition URLs, but it only states that “Rejected/non-accepted entries remain under the Rejected sub-block” without an executable sub-step to **collect** non-accepted review OOS (e.g. from accumulated review markdown minus `oos-accepted-review.md`) and append a `## Rejected / Out-of-Scope Observations (not filed)` section in the same step 6 `larch-log.sh append`. The disposition gate counts `rejected_oos_markers` only from that NDJSON body (`skills/implement/scripts/oos-disposition-gate.md`), while accepted blocks live in separate markdown inputs—so a procedure that writes accepted URL rows in step 6 but never composes the Rejected sub-block can pass filing checks yet fail the gate when some blocks were voted down. **Suggested fix:** Add an explicit step 6 bullet: derive rejected `### OOS_` markers from review artifacts, sanitize, and include them in the same NDJSON record before step 7; reference `scripts/larch-log-batches.md` schema and the SKILL.md carve-out at `skills/implement/SKILL.md:407`.

- **architecture** `python/ship.py:208-216` — `_oos_gate` calls `oos.disposition_ok()` with `filed_urls_files` (sentinel + NDJSON loose grep) but omits `filed_urls_strict_files`, while `skills/implement/scripts/oos-disposition-checkpoint.sh:194-196` passes `--filed-urls-strict-file` for the resolved design path so `- **Filed URL**:` field lines count toward disposition. That breaks bash/Python parity for the all-already-filed path in `oos-pipeline.md:19` (design blocks with pre-filed URLs, no new `/issue` batch): the Python driver can keep returning `NEEDS_USER_OOS_FILING` or disagree with the bash checkpoint even after step 6 materialization, depending on whether URLs landed only as strict field lines vs loose NDJSON tokens. **Suggested fix:** Pass `filed_urls_strict_files=(str(design_path),)` when `design_path.is_file()` in `_oos_gate`, mirroring the checkpoint; extend `python/test_ship.py` with a case where design-export blocks carry only `- **Filed URL**:` lines and assert disposition parity.

### Out-of-Scope Observations

- **architecture** `scripts/ship-pr.sh:684-688` and `python/ship.py:144-147` — When `DESIGN_TMPDIR` is set but `oos-accepted-design.md` is missing/empty, both resolvers prefer that path over `design-export/oos-accepted-design.md`; this predates the branch and is not amplified by it, but it can still leave design-export OOS invisible to triggers and gates in mixed design/implement sessions.
