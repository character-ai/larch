Reviewing the branch diff and Python/bash OOS parity paths.
### In-Scope Findings

- **risk-integration** `python/ship.py:489-507` — After Step 9a.1, the orchestrator is supposed to clear `OOS_PENDING`, run the disposition checkpoint, and reinvoke `python/ship.py` (see `skills/implement/SKILL.md` Python driver selector). `run_ship` always runs the pr-create block from the top; when `oos-accepted-*.md` are still non-empty (expected after filing), lines 489–503 return `NEEDS_USER_OOS_FILING` again and never reach `pr.ensure_pr`, even though disposition is already satisfied. Bash avoids this by re-entering with `ship-pr.sh --resume-phase pr-create`, which skips pr-prep’s accepted-file trigger. **Suggested fix:** On re-entry when `OOS_PENDING` is false, either skip the size-based accepted-file shortcut and call `_oos_gate` (proceed to PR create only if disposition passes), or add phase/resume support (e.g. read `PHASE=pr-create` from `--state-file` and jump straight to PR creation), matching bash resume semantics.

- **risk-integration** `python/ship.py:265-280` — `_oos_gate` resolves `run_id` from `ctx.run_id` and then `session-id` only. `oos-disposition-checkpoint.sh` and `run_logs.effective_run_id` also read `RUN_ID` from `ship-pr-state.sh` and `finalize-state.sh` (lines 131–140 of the checkpoint). If the orchestrator reinvokes with `--state-file` but omits `--run-id`, Python can miss the canonical ndjson path, fall through to the single-candidate glob, or treat multiple ndjson files as ambiguous while bash would use the state-file id. **Suggested fix:** Resolve ndjson via `run_logs.effective_run_id(ctx)` (or the same state-file → finalize → session-id order) before building `run_dir_ndjson`.

- **risk-integration** `python/ship.py:271-274` — When `run_id` is set but `larch-logs/implement/<run_id>/oos-issues.ndjson` is missing, Python still glob-fallbacks to any single `*/oos-issues.ndjson`. `oos-disposition-checkpoint.sh` only glob-fallbacks when `_RUN_ID` is empty; with a set `RUN_ID` and missing ndjson it fails validation before the gate when `non_sec_oos > 0` (lines 179–182). Python can therefore attach another run’s ndjson evidence or pass disposition via sentinel URLs alone while the checkpoint would exit 2. **Suggested fix:** Mirror checkpoint rules: glob only when no resolved `run_id`; if `run_id` is set and the expected ndjson is missing, return `NEEDS_USER_OOS_FILING` (or exit 2-equivalent stall) instead of scanning sibling run dirs.

- **risk-integration** `python/ship.py:252-307` — `_oos_gate` calls `oos.disposition_ok` directly and does not enforce the checkpoint’s pre-gate rule that non-security accepted OOS requires a resolved `oos-issues.ndjson` when block count &gt; 0 (`oos-disposition-checkpoint.sh:179-182`, mirrored in `ship-pr.sh:752-755`). `disposition_ok` can return `ok=True` from `oos-issues-created.md` URLs or inline-triage alone (`python/oos.py:186-193`), without ndjson. That diverges from bash’s fail-closed integration path and from `test_oos_gate_allows_inline_triage_without_ndjson`, which encodes the looser Python-only behavior. **Suggested fix:** Before `disposition_ok`, if `oos.count_non_security(accepted) > 0` and the resolved ndjson path is not a readable file, return `NEEDS_USER_OOS_FILING`; optionally invoke `oos-disposition-checkpoint.sh` instead of duplicating gate logic in Python.

### Out-of-Scope Observations

- **architecture** `python/ship.py:426-516` — The Python driver has no `--resume-phase` or phase-aware entry; every invocation reruns checks → postbump → full pr-create OOS sequence. That is broader than this branch’s OOS parity work but explains why bash resume tokens cannot be ported literally.

- **correctness** `python/test_ship.py:193-242` — Tests named `test_design_export_oos_allows_pr_create_after_disposition` / `test_design_tmpdir_oos_allows_pr_create_after_disposition` assert `NEEDS_USER_INPUT`, not PR creation; they document first-pass OOS blocking, not post-9a.1 resume. The missing post-filing resume test is the gap above.
