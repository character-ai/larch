### In-Scope Findings

- **risk-integration** `scripts/ship-pr.sh:3291,1240-1283` — Changing `--resume-phase pr-create` to `advance_phase pr-prep` (was `advance_phase pr-create` on `main`) re-enters `run_pr_prep_phase` after Step 9a.1 has already filed OOS. Accepted-OOS markdown (`oos-accepted-*.md`) is intentionally left on disk, so the `-s` probe at lines 1240–1243 always sets `OOS_PENDING=true` again. Together with the new `run_pr_create_phase` guard (lines 1279–1282) that refuses PR creation and bounces back to `pr-prep`, the state machine can loop (`pr-prep` → `OOS_PENDING=true` → `pr-create` → `pr-prep`) instead of opening the PR after the orchestrator cleared `OOS_PENDING` and checkpoint passed. **Suggested fix:** Restore `pr-create` resume to `advance_phase pr-create` (as on `main`), or teach `run_pr_prep_phase` to run `oos-disposition-checkpoint.sh` / gate when disposition is already satisfied (sentinel + ndjson) before re-arming `OOS_PENDING` from file size alone; keep the materialize hook on first `pr-prep` entry only if needed.

- **risk-integration** `python/ship.py:489-503` — This branch adds a bash-style “any accepted-OOS file is non-empty → `NEEDS_USER_OOS_FILING`” gate before `_oos_gate`. On `main`, `python/ship.py` went straight to `_oos_gate` / `disposition_ok`, so a second `ship.py` invocation after successful filing could still reach `pr.ensure_pr` when disposition evidence was present. With the new check, every re-invoke while `oos-accepted-*.md` still contains blocks (normal after Step 9a.1) returns `oos-filing` again even when `OOS_PENDING=false` in state, blocking the Python ship path from progressing to PR create. **Suggested fix:** Remove the size-only shortcut or replace it with the same disposition preflight as `_oos_gate` (including `security-oos-observations.md` and ndjson preconditions from `oos-disposition-checkpoint.sh`); only return `NEEDS_USER_OOS_FILING` when disposition is actually unsatisfied.

- **risk-integration** `skills/implement/scripts/materialize-manifest-oos.sh:123-128` — `security_signal` routes observations to `security-oos-observations.md` when either the structured `focus_area` field or **any line in `description`** matches `security_focus_area` awk. That is broader than the gate-aligned rule documented in `oos-pipeline.md` step 1 / `oos-non-security-block-count.awk` (dedicated `- **focus-area**:` line on the assembled block only). A manifest description that embeds `- **focus-area**: security-…` as narrative can be withheld from public OOS filing while still looking like a normal non-security block to downstream reviewers. **Suggested fix:** Limit routing to the JSON `focus-area` / `focus_area` field (the branch already passes it separately) and drop the `printf '%s\n' "$description" | security_focus_area` fallback, matching the gate predicate and the “prose in Description does not mark” contract.
