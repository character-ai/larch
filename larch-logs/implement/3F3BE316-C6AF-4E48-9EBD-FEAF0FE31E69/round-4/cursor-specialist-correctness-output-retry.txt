### In-Scope Findings

1. **Important** (`correctness`, `both`) — `skills/implement/scripts/stall-recovery-report.sh:357-362` — The `same-cause-repeat` override runs after `classify_from_evidence` and can replace `contract-failure` for `STALL_STEP=3` or `6`. **Concrete scenario:** a Step 6 checks stall (`STALL_STEP=6`, `PHASE=checks`) is classified `contract-failure` / `RESUME_HINT=none` (harness case 5b); after one failed recovery attempt with the same signature, re-classify returns `same-cause-repeat` (case 20b) and `retry-policy` grants `MAX_ATTEMPTS=1`. The reference then runs the alternate “restart failed step” path (procedure step 6), which conflicts with the plan and `SKILL.md` Step 8 Exit 4: no main-agent edits on `PHASE=checks` exhaustion. **Suggested fix:** Skip the signature override when `stall_step` is `3` or `6`, or when the pre-override class is `contract-failure`, so contract steps stay at 0 attempts and terminal-only handling.

2. **Latent** (`correctness`, `plan`) — `skills/implement/scripts/stall-recovery-report.sh:197-203` — Symbolic `STALL_STEP` values such as `12d` (written by `scripts/ship-pr.sh` at line 2930) fall through to `RESUME_HINT=none` even when evidence classifies `transient-infra` (harness case 20a). **Concrete scenario:** a CI-merge stall with `STALL_STEP=12d` and rate-limit/network evidence reaches Step 18a with `STALL_TRACKING=true`; the helper emits `transient-infra` but `none`, so dispatch never re-invokes `ship-pr.sh` despite four transient retries in the cap table—recovery goes straight to terminal failure. **Suggested fix:** Map known ship-phase symbolic steps (`12d`, and any others `ship-pr.sh` emits) to `step8-shippr`, or document that 18a must not run for those stalls and ensure Step 16 clears `STALL_TRACKING` before Step 18.

3. **Latent** (`correctness`, `plan`) — `skills/implement/references/stall-recovery.md:13` vs `skills/implement/scripts/stall-recovery-report.sh:617-656` — First-detection issue filing is keyed on `attempt_count==0`, but `bug-body` has no guard for `FAILURE_CLASS=contract-failure` or `unrecoverable`. **Concrete scenario:** a terminal Step 0 bail (`tracking-init-failed`, `STALL_STEP` empty) still gets a larch bug filed on first detection before dispatch/terminal handling, even though recovery will not run. **Suggested fix:** Either skip `bug-body`/`/larch:issue` when `FAILURE_CLASS` is `contract-failure` or `unrecoverable`, or state explicitly in the reference that filing on unrecoverable stalls is intended.

4. **Nit** (`correctness`, `plan`) — `skills/implement/SKILL.md:1748` — Step 18a’s skip condition is prose-only (“false or empty”) while `classify` uses `truthy()` (accepts `TRUE`, `1`, `yes`, etc.). **Concrete scenario:** `ship-pr-state.sh` contains `STALL_TRACKING=True`; the diagnostic block prints `STALL_TRACKING_DISK=True`, but an orchestrator doing a strict string compare against `true` skips recovery while the gate should fire. **Suggested fix:** Add a one-line normative rule: treat disk/session values with the same truthiness rules as `stall-recovery-report.sh` `truthy()`, or provide a small helper invocation in the Step 18a bash block.
