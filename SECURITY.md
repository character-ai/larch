# Security Policy

## Supported Versions

| Version | Supported |
|---------|-----------|
| Latest  | Yes       |
| Older   | No        |

Only the latest released version receives security updates.

## Reporting a Vulnerability

If you discover a security vulnerability in larch, please report it responsibly:

1. **Email**: Send details to <zhupanov@yahoo.com>
2. **Do not** open a public GitHub issue for security vulnerabilities
3. Include steps to reproduce the issue and any relevant context

You should receive an acknowledgment within 72 hours. We will work with you to understand the issue and coordinate a fix before any public disclosure.

## Security Findings in OOS Workflows

Accepted security-tagged review/design OOS findings (`focus-area=security`) are held locally and NEVER written to public OOS issue artifacts (`oos-accepted-design.md`, `oos-accepted-review.md`, or the `oos.md` visibility export). Public-boundary writers apply the unified fenced/unfenced discrimination contract: for every literal occurrence of the canonical token in a block, classify it as fenced when inside an inline backtick code span or triple-backtick fenced code region, and unfenced otherwise; route as security only when at least one unfenced occurrence exists. If every occurrence is fenced, the block is meta-discussion and routes through the normal public OOS path. Real security findings MUST include at least one unfenced occurrence. Security findings are also NEVER filed via `/issue` or `/umbrella`; use the private disclosure flow above instead.

The external implementer prompts (`agents/codex-implementer.md`, `agents/cursor-implementer.md`, `agents/gemini-implementer.md`) likewise prohibit folding security findings inline and prohibit emitting them in `oos_observations[]`. `/implement` Step 9a.1 defensively re-excludes any security-tagged OOS entries that slip through upstream filters before the `/issue` handoff.

## Trust Model

Larch is a Claude Code plugin that runs within Claude Code's permission boundary. It does not bypass Claude Code's built-in permission system at the operator level — all tool calls (file edits, shell commands, etc.) at the user-facing assistant level go through the standard permission flow. Consumers running in strict-permissions mode must grant both the bare and fully-qualified `Skill(...)` form for each larch skill they invoke — see the "Strict-permissions consumers — Skill permission entries" subsection in [`docs/configuration-and-permissions.md`](docs/configuration-and-permissions.md#strict-permissions-consumers--skill-permission-entries) for the required allowlist convention, the shadowing caveat (bare names may resolve to project-local skills before reaching the plugin), and the reason `Skill(larch:*)` wildcards do not currently work.

**External tool delegation**: When Codex, Cursor, or Gemini are available, larch delegates tasks to them. For **review, sketches, and dialectic** tasks routed through `scripts/launch-review.sh --tool cursor` and `scripts/launch-review.sh --tool codex`, Codex and Cursor are now mechanically sandboxed at the CLI level (issue #1529): Codex review runs as `codex exec --sandbox read-only` and Cursor review runs as `cursor agent -p --trust --mode plan` (issue #1583 removed `--sandbox enabled`, which crashed hosts where the cursor-agent sandbox runtime is unavailable — the prior `codex exec --full-auto` (workspace-write) and `cursor agent -p --force --trust` (force-allow commands) postures are gone). `/design` plan-review voting uses `scripts/dispatch-plan-voters.sh`, which launches external voters through `scripts/run-external-agent.sh` directly but keeps the same read-only CLI posture (`codex exec --sandbox read-only` and `cursor agent -p --trust --mode plan`) and waits on wrapper sentinels before returning voter paths. The review launchers also provide a HARD CONSTRAINTS read-only preamble so the model reasons about its read-only role: Cursor prepends it to the prompt, while Codex writes it to a per-invocation `CODEX_HOME/config.toml` top-level `instructions` key outside both `$PWD` and the review output `--add-dir`. The plan-voter dispatcher includes a narrower do-not-modify voter prompt but does not publish launcher-owned dirty-tree sidecars; its primary mechanical controls are the external CLI read-only modes plus the monitored wrapper. For Codex, the CLI sandbox is the primary mitigation and the instructions preamble is its prompt-level reinforcement; for Cursor, read-only enforcement relies on `--mode plan` plus the prompt preamble plus the post-hoc `${OUTPUT}.dirty-tree` detector on review-launcher lanes (Cursor/Codex/Gemini parity). Mechanical guarantee depends on the upstream Codex / Cursor CLIs continuing to honor `--sandbox read-only` / `--mode plan` respectively; the launcher harnesses (`scripts/test-launch-review.sh`) and plan-voter dispatcher harness (`scripts/test-dispatch-plan-voters.sh`) pin the argv literally, and review-launcher dirty-tree sidecars catch post-run mutation if a future CLI release silently changes those flags' semantics. Note that this hardening applies only to the **review-launcher and plan-voter lanes** — the implementer launchers (`scripts/launch-codex-implement.sh`, `scripts/launch-cursor-implement.sh`, `scripts/launch-gemini-implement.sh`) intentionally retain workspace-write / `--trust` because the implementer's job is to edit the tree (see "Step 2 implementation" paragraph below). The Gemini reviewer call sites have been removed from `/review` and `/implement --quick`, so the "review/sketches/dialectic" trust framing applies to Gemini only if those call sites are re-enabled (see "Gemini reviewer delegation (dormant)" below); the only currently-active Gemini delegation is the `--coder=gemini` implementer slot described in this paragraph. `/design` adaptive sketch process counts are projected in [`docs/topology.md`](docs/topology.md#design.sketch.regular_slots): full sketch mode launches 4 external agents, quick/simple sketch mode launches 2, and the codebase-scan-confirmed trivial-doc path launches 0 external sketch agents and writes sentinel artifacts instead. The trust model for nonzero sketch modes is unchanged — same scripts, same prompt constraints. `/implement` Step 2 implementation without an explicit `--coder` first honors the `/design` `diff_lines < 30` carve-out, then falls through Codex → Cursor → Claude by availability; an explicit `--coder=codex` still runs Codex (`codex exec --full-auto`, `approval: never`, `sandbox: workspace-write`). The Codex implementer launcher (`scripts/launch-codex-implement.sh`) writes the static implementer agent preamble to a per-invocation `CODEX_HOME/config.toml` top-level `instructions` key, symlinks `~/.codex/auth.json` into that temporary home only when the file exists, and keeps the temporary home outside both `$PWD` and the dispatcher session tmpdir. The launcher also passes `--add-dir "$(dirname "$MANIFEST_PATH")"` to `codex exec` so Codex's `workspace-write` sandbox can atomic-write `manifest.json` and `qa-pending.json` to the dispatcher-owned session tmpdir, which lives outside `$PWD` (typically under `~/.cache/larch/sessions/...`). This widens Codex's writable surface from `$PWD` only to `$PWD` plus the entire session tmpdir; operators should treat any artifact placed in that tmpdir (transcripts, sidecars, dispatcher baseline / spawn / resume-count sentinels) as Codex-writable, but not as containing Codex's temporary config or auth symlink. Cursor (`--trust`) and Gemini (`--approval-mode yolo --skip-trust`) already permit writes to arbitrary absolute paths and require no analogous launcher flag. The operator can opt into Cursor (`cursor agent ... --workspace "$PWD"`) with `--coder=cursor`, Gemini (`gemini --prompt ... --approval-mode yolo --skip-trust --model "$GEMINI_MODEL"`, where `$GEMINI_MODEL` is passed as a single quoted argv token so an operator-controlled `LARCH_GEMINI_MODEL` / `CLAUDE_PLUGIN_OPTION_GEMINI_MODEL` value cannot expand into additional `gemini` CLI flags via word-splitting) with `--coder=gemini`, or the main Claude agent's Edit/Write path with `--coder=claude`. Gemini's `yolo` mode auto-approves all tool calls including shell commands, and `--skip-trust` bypasses Gemini's per-workspace trust prompt. When `--coder=cursor` or `--coder=gemini` is requested but the tool is unhealthy or unavailable, the dispatcher falls back to the main-agent Edit/Write path (`STATUS=claude_fallback`), symmetric to passing `--coder=claude` directly. **Codex, Cursor, and Gemini do not commit** — Codex cannot write `.git/` under `workspace-write`, and Cursor/Gemini prompts forbid commits. Cursor and Gemini have full filesystem access, so the dispatcher (`skills/implement/scripts/step2-implement.sh`) mechanically asserts `HEAD == BASELINE_SHA` before committing on their behalf and bails with `cursor-modified-history` or `gemini-modified-history` if the tool created or amended commits, preserving partial work for operator inspection. Operators who want a stricter sandbox model should prefer `--coder=codex`. The dispatcher pipes `manifest.commit_message` through `scripts/redact-secrets.sh`, writes the redacted output to a tmpfile, and runs `git add -A && git commit -F <tmpfile>` on the implementer's behalf — so what lands in git history is the manifest's `commit_message` modulo the redactor (the same scrubber used downstream for the canonical on-disk manifest). The redactor pass before `git commit` is load-bearing: without it, a secret accidentally embedded in `commit_message` would land permanently in git history while the on-disk canonical manifest's redacted copy would suggest the secret had been scrubbed (split brain). `git add -A` stages every working-tree change (tracked + untracked) — under this trust model the working tree IS the source of truth, `manifest.files_touched` is advisory documentation only (no diff cross-check), and operator review + `/review` (Step 5) + the regular pre-commit hook chain are the downstream backstops against external implementers committing files outside the declared scope. Operators concerned about scope drift should review the produced commit before allowing the merge. There is no Claude-side diff verification — the working tree IS the source of truth, and `commit_message` flows into `git commit -F` modulo the secrets-family redaction described above. External implementer process writes bypass the Edit/Write PreToolUse hook chain (including `block-submodule-edit.sh`); the regular `pre-commit` hook chain runs when the dispatcher commits, providing a second-line backstop. Post-implementer validation in `skills/implement/scripts/step2-implement.sh` mechanically enforces, BEFORE the dispatcher commits: (1) `git rev-parse --abbrev-ref HEAD` matches the spawn-time branch (→ `branch-changed`); (2) `git hash-object .claude-plugin/plugin.json` matches the spawn-time baseline, catching working-tree edits to the version-bump-reserved file (→ `protected-path-modified`); (3) `git submodule status --recursive` reports clean (→ `submodule-dirty`); (4) every manifest path is rejected if it contains `..`, starts with `/`, equals `.claude-plugin/plugin.json`, or resolves under a submodule (→ `protected-path-modified`); (5) Cursor/Gemini only: `HEAD` still matches the spawn-time baseline (→ `cursor-modified-history` / `gemini-modified-history`). The earlier diff cross-check (`manifest-diff-mismatch`), commit-subject equality (`commit-subject-mismatch`), working-tree-clean (`dirty-tree-after-codex`), and commits-since-baseline (`no-commit-since-baseline`) checks were removed when commit responsibility moved off Codex — they were tautological under the new model, since the dispatcher itself produces the commit from `manifest.commit_message`. If `git commit` fails (empty working tree, pre-commit hook rejection, transient git error), the dispatcher emits `commit-failed`, removes the un-sanitized `manifest.json` from `$IMPLEMENT_TMPDIR` to avoid leaving raw text fields on disk, captures `git commit` stderr to `$IMPLEMENT_TMPDIR/<tool>-commit-stderr.txt`, and bails — the index stays fully staged from the prior `git add -A` (no new commit was produced) so operators may need `git reset` or `git commit --amend` after diagnosing the failure, not only inspection. Manifest text fields (`commit_message`, `summary_bullets[]`, `todos_left[]`, `oos_observations[*].title|description`) are run through `scripts/redact-secrets.sh` before any consumption by downstream Steps 4 / 8a / 9a / 9a.1, since they flow verbatim into commit messages, the CHANGELOG, the PR body, and public GitHub issues. Claude does NOT inspect implementer transcripts or run `git diff` to figure out what changed — only the validated, sanitized manifest is consumed downstream. For `/research` — which launches external agents directly against `$PWD` — the trust framing (mechanical PreToolUse hook on `/research`'s `Edit|Write|NotebookEdit` surface, prompt-only posture for Bash and external agents, residual risks, and scope of the mechanical guarantee) is documented in the [External reviewer write surface in /research](#external-reviewer-write-surface-in-research) subsection below.

**Claude review subprocesses**: `scripts/launch-claude-subprocess.sh` is used for `/review` Claude fallback slots and tie-breaker style tasks. It validates prompt, context, and output paths against containment roots (plugin root or the session tmpdir), rejects symlinks, rejects `..` and control characters, caps context to 20 files and 256 KB per file, and wraps context as untrusted input. It emits `.meta`, `.done`, and `.dirty-tree` sidecars so the collector can reason about the subprocess like an external reviewer. The default model is `claude-sonnet-4-6` and can be overridden with `--model`. Unlike Codex and Cursor review launchers, this wrapper has no mechanical read-only CLI sandbox; read-only behavior is prompt-level only and enforced post-hoc through dirty-tree sidecar aggregation.

Current omitted-`--coder` routing narrows Claude inline implementation to `/design` plans whose exported `diff_lines` estimate is below 30, then falls through Codex → Cursor → Claude by availability. This can select Cursor without an explicit `--coder=cursor` when Codex is unavailable; the Cursor implementer trust model above applies to that fallback path, and the run manifest records `coder_fallback=true`.

**Fork setup destructive sync**: `/set-up-forked-open-source-repo` can perform an explicitly destructive fork sync. When upstream and fork `refs/heads/main` differ, the coordinator verifies `gh repo view <fork>` reports a parent equal to the declared upstream — preferring `parent.nameWithOwner` when populated, otherwise composing it from `parent.owner.login` and `parent.name` — compared case-insensitively, prints the upstream/fork main SHAs, requires TTY confirmation or `--mirror-confirmed`, re-probes both SHAs immediately before pushing, then runs `git push --prune` from a fresh temporary mirror clone with scoped refspecs for branches and tags only. Residual risk remains: a confirmed sync overwrites all fork branches and tags to match upstream, including deleting fork refs that upstream lacks, and there is still a narrow TOCTOU window between the final re-probe and the push. The destructive-sync threat model is unchanged for github.com and now applies equivalently to GitHub Enterprise hosts selected from `origin`.

**Fork setup URL-override footgun**: the coordinator supports `LARCH_FORKED_REPO_URL_OVERRIDE_{UPSTREAM,FORK}_{HTTPS,SSH}` env vars as a test seam so the offline harness can exercise mirror-sync paths against local bare repos. Production runs leave them unset and the URLs are derived deterministically from the verified `--upstream` / `--fork` arguments. Because the override is an absolute URL with no scheme/host check, a stale operator-environment export or a CI profile that leaks test env vars into the production lane could redirect the destructive `git push --prune` to whatever URL the env var names — independent of `gh repo view`'s parent-verification guard. The coordinator therefore requires an explicit `LARCH_FORKED_REPO_ALLOW_URL_OVERRIDE=1` opt-in before the override fires; without that flag, the env vars are ignored even if set. The harness sets the opt-in itself; operators should not export it in interactive shells. Pushurl-survival hardening: after remote rewrites the coordinator unsets `remote.origin.pushurl`, so a stale or hostile pushurl carried over from a renamed `<named-fork>` remote cannot redirect future `git push origin ...` to the wrong repository while origin's fetch URL still points at the declared fork. Residual `url.*.insteadOf` footgun: `git config --global` (or any user-scope) `url.<other>.insteadOf https://github.com/` rewrites silently redirect every `git ls-remote`, `git clone`, `git push`, and `git fetch` issued by the coordinator — bypassing both the env-var allowlist above and the `gh repo view` parent guard. The coordinator does NOT scan or override `insteadOf` rules; the same-user threat model treats global gitconfig as already trusted by the operator, but operators sharing a profile or inheriting dotfiles from an untrusted source should audit `git config --global --get-regexp '^url\..*\.insteadOf$'` before running the skill. Pre-fetch URL classification: `phase_preflight` inspects `origin`'s configured fetch URL with `lib-remotes::normalize_github_url` BEFORE the first `git fetch origin` and refuses non-parseable URLs and mixed-host or multi-URL origin configurations — so a malformed or hostile origin URL is rejected without any network round-trip against the unvalidated remote.

**Plugin-shipped hooks for post-/design halt protection**: `hooks/hooks.json` registers two additive hooks for `/implement`'s post-/design boundary. The `PostToolUse` hook on `Skill` runs when `/design` or `larch:design` returns; `skills/implement/scripts/hook-post-design.sh` resolves the active `/implement` tmpdir by filtering `.larch-keepalive` `CLONE_PATH` against the hook `cwd`. Resolution fails open (returns no tmpdir) only when `cwd` is missing, empty, or matches no `.larch-keepalive`; when multiple eligible candidate dirs share the same `CLONE_PATH`, the freshest `manifest.env` mtime wins with a lexicographic tie-break on equal mtimes, so the residual concurrent-run risk in that narrow case is deterministic rather than fail-open. The hook invokes `post-design-boundary.sh --hook-mode true` and injects the gate's stdout into the next assistant turn via `hookSpecificOutput.additionalContext`. **Hook-mode sentinel split**: `--hook-mode true` instructs the gate to skip writing `.boundary-gate-passed` and to emit `POST_DESIGN_BOUNDARY_HOOK_INJECTED=true` instead of `POST_DESIGN_BOUNDARY_OK=true`. This keeps the Stop hook armed (sentinel absent) after the PostToolUse hook fires — a spurious halt between the hook and the orchestrator's mandatory Bash wrapper is then caught and blocked by the Stop hook. Only the orchestrator's own (non-hook-mode) Bash invocation writes the sentinel, signaling the boundary was truly crossed. The hook never sources session files, never writes outside `$IMPLEMENT_TMPDIR`, and exits 0 on probe failures. The `Stop` hook (`skills/implement/scripts/hook-stop-fail-close.sh`) refuses session stop only when a resolved tmpdir has `design-export/manifest.env` but neither `.boundary-gate-passed` nor `.run-cleaned-up`, and the Stop event is not a `stop_hook_active` continuation-loop reentry. Its reason includes only the tmpdir basename. Operator escape paths are hard-quit, removing the stale manifest, or touching `.run-cleaned-up` to abandon the run.

Reduced residual risk for stale `claude-implement-*` tmpdirs after issue #1419: the post-/design Stop hook can no longer be tripped by a stale tmpdir from a crashed prior `/implement` session that never ran Step 18 cleanup, due to `LARCH_TOKEN_SESSION_ID` binding (when set) and a 6-hour TTL backstop on `manifest.env` mtime. Exact session-id matches bypass TTL so a paused or long-running active session remains protected; TTL-only resolution applies when no authoritative session signal is available.

`compose-review-findings.sh` adds a pre-archive redaction boundary for `docs/review-archive/*.jsonl`: free-form fields (`prose_body`, `reviewer`, embedded title) flow through `redact-tmpdir-paths.sh | redact-secrets.sh` before JSON encoding, mirroring `tracking-issue-write.sh`'s posture. Bounded enums (`id`, `phase`, `outcome`, `category`) bypass redaction because they are script-derived, but still pass through `jq --arg` for JSON safety; the same redacted free-form values feed inline markdown mode.

`sessionstart-health.sh` uses a fixed-literal jq-missing fallback: when `jq` is unavailable, the emission path no longer interpolates dynamic content. Future probe additions that operate outside the `JQ_AVAILABLE && GIT_AVAILABLE` gate cannot reach JSON output via that path.

**Relevant-checks captured logs**: `/implement` and `/review` run project-local relevant checks through `scripts/run-relevant-checks-captured.sh` instead of invoking the `/relevant-checks` Skill on the green path. Raw check output is captured under the session tmpdir in a mode-`700` `relevant-checks/` directory with mode-`600` logs. Successful runs expose only a bounded `RELEVANT_CHECKS_OK=true` machine line. Failed runs write a redacted companion log through `scripts/redact-tmpdir-paths.sh | scripts/redact-secrets.sh`; orchestrators are instructed to read `REDACTED_LOG_FILE`, not raw `LOG_FILE`. If redaction fails, the helper emits `STATUS=fail FAILURE_REASON=redaction-failed` without publishing the raw log path. The scrubber covers tmpdir paths and known secret token families only; internal URLs, private hostnames, and PII still require prompt-level/operator discipline.

**Gemini reviewer delegation (dormant)**: the Gemini reviewer call sites in `/review` and `/implement --quick` have been removed. The launcher (`scripts/launch-review.sh --tool gemini`) is also disabled by default at runtime: valid invocations exit 0 with an empty output file unless `GEMINI_REVIEW=1` is set. Its admin-policy file (`scripts/gemini-reviewer-policy.toml`), the regression harness (`scripts/test-launch-review.sh`), the Gemini health probe in `scripts/check-reviewers.sh`, and the `--check-gemini-reviewer` opt-in flag in `scripts/session-setup.sh` are retained as machinery so the lane can be re-enabled deliberately by setting the env gate and re-introducing call sites in those skills. The reviewer prompt is inlined at the call sites and is not a separate file. (`agents/gemini-implementer.md` is the system prompt for the **implementer** slot — `--coder=gemini` — and is unrelated to the dormant reviewer launcher.) The mechanical posture described below applies if those call sites are restored and `GEMINI_REVIEW=1` is set. The argv shape would be `gemini -m "$GEMINI_MODEL" -p "$PROMPT" -o json --skip-trust --approval-mode yolo --admin-policy "$SCRIPT_DIR/gemini-reviewer-policy.toml"` — `$GEMINI_MODEL` resolves from `LARCH_GEMINI_MODEL` then `CLAUDE_PLUGIN_OPTION_GEMINI_MODEL`, defaulting to `gemini-2.5-pro` — wrapped by `scripts/launch-review.sh --tool gemini`. The plugin-shipped admin policy denies Gemini reviewer file-write tools (`write_file`, `replace`, `edit`, `edit_file`, `delete_file`) at admin priority 5999, while shell remains governed by `--approval-mode yolo` so reviewers can inspect `git diff`, `git log`, and repository files. Gemini is also available as `--coder=gemini` for the implementer slot (see External tool delegation above). The implementer launcher (`scripts/launch-gemini-implement.sh`) keeps the yolo + write-tools posture and remains separate from this read-only reviewer policy; implementer Gemini does not vote, and does not participate in design sketches or dialectic/research lanes. Note: the implementer launcher normalizes its preflight envelope on `resolve_gemini_model` failure (always emits `MANIFEST_WRITTEN=false` / `QA_PENDING_WRITTEN=false` so a stale manifest left by an earlier attempt cannot be misclassified as a completed run); this hardens the launcher's KV stdout grammar without changing its trust posture. Reviewer prompts ask Gemini to inspect the live repository directly and include explicit `Do NOT modify files. Do NOT commit. Do NOT push.` instructions, matching the prompt constraints used for Cursor's `--trust` reviewer lane and Codex's `--full-auto` reviewer lane; the launcher also prepends a stronger read-only preamble that bans shell redirects, `tee`, mutating filesystem commands, git/index/ref mutation, and write-capable tools. `--approval-mode yolo` auto-approves Gemini tool calls, including shell commands, and `--skip-trust` bypasses Gemini's trust prompt; the admin policy adds a file-write-tool deny rule for Gemini reviewer mode, but it is not a general filesystem sandbox and depends on stable Gemini tool names. The reviewer launcher therefore adds a repo-root snapshot guard: after stale launcher artifacts are removed and before Gemini launches, it records `HEAD` plus tracked and untracked file hashes, then compares after JSON normalization. Any repo mutation, including shell-redirect bypasses the policy cannot see, fails the lane with a loud diagnostic and reverts modified tracked files, deleted tracked files, and new untracked files to their pre-launch state where possible. The guard is fail-open outside git worktrees and bounded by `LARCH_GEMINI_SNAPSHOT_TIMEOUT` (default 30s); those cases fall back to the policy-plus-prompt posture and emit diagnostics. Gemini-cli tool catalog drift is checked at health-probe time: unknown tool names emit a `GEMINI_TOOL_DRIFT_WARNING=` key that `session-setup.sh` re-emits as a banner, while unknown names whose tokenized form (camelCase / `_` / `-` / `.` boundaries) anchored-matches a write-style keyword, or fixture-known write-style tools missing from the deny list, mark Gemini unhealthy until the deny list or fixture is updated. The alarm covers the gemini-cli catalog discovered under the probe argv (`--approval-mode plan`); the reviewer runs under `--approval-mode yolo --admin-policy`, so probe-mode catalog drift is a proxy for, not a strict superset of, reviewer-mode catalog drift. This mechanical guarantee depends on gemini-cli continuing to honor `--admin-policy` from arbitrary file paths; gemini-cli's documentation describes admin-policy as "OS-specific system directories", so a future release that restricts the flag would degrade the launcher to prompt-only plus snapshot enforcement (the existing fail-closed path catches gemini-cli flag-parse failures). When Gemini is unavailable, unhealthy, times out, emits invalid JSON, or trips the snapshot guard, larch skips the Gemini lane for the remainder of the session instead of substituting Claude, preserving the strict additive contract. The launcher also emits a `${OUTPUT}.dirty-tree` sidecar (matching the Cursor/Codex contract introduced for `/review` Step 5 by #1437) so that, when the Gemini reviewer call sites are reintroduced, sidecar-only consultation picks up Gemini coverage automatically with the same `STATUS=clean|dirty|unknown` enum and the same recovery contract; this dirty-tree sidecar is additive to the repo-root snapshot guard described above.

**Model-env trust boundary**: `LARCH_CURSOR_MODEL`, `LARCH_CODEX_MODEL`, `LARCH_GEMINI_MODEL`, and their `CLAUDE_PLUGIN_OPTION_*_MODEL` fallbacks are operator-supplied input that becomes privileged external-agent CLI argv. `scripts/agent-model-args.sh` now emits one argv token per stdout line, and consumers read that stream into Bash arrays instead of expanding a shell string. Successful stdout is machine-only and contains no empty lines; diagnostics and Codex effort warnings go to stderr. Explicit blank / whitespace-only model values and any value containing a POSIX `[[:cntrl:]]` character fail closed before the external CLI is invoked. This is a breaking stdout-shape change for out-of-tree callers of `agent-model-args.sh`: callers must consume line tokens, not word-split command substitution output.

**Retry-metadata deserialization (issue #1154)**: External-agent `.meta` sidecars store the child argv as a JSON array (`CMD_JSON`), validated as an `array` of `string` before deserialization. Retry launches use direct Bash array expansion; `eval` is no longer used to reconstruct argv from persisted shell-quoted text. Malformed or missing metadata fails closed: the original result is marked unhealthy and the tool is flipped to unhealthy for the rest of the session. `TIMEOUT=` is part of validated retry metadata. Missing, non-digit, or zero/zero-padded values fail closed for that reviewer (`mark_retry_metadata_invalid` + `set_tool_unhealthy`), aligning the reader-side contract with `scripts/run-external-agent.sh`'s writer-side validation. The legacy `CMD_JSON` branch also applies per-tool argv-shape allowlists: Cursor must look like `cursor agent ... --workspace ...` and cannot carry `--add-dir`; Codex must look like `codex exec ... -C ... --output-last-message ...`; Gemini must start as `launch-review.sh --tool gemini`, `launch-gemini-implement.sh`, or `gemini` and cannot carry Codex/Cursor workspace-widening flags. Unknown `TOOL=` values fail closed. `.done` sentinel content is also treated as tamperable data: the collector accepts only `^[0-9]{1,3}$` digit strings in the `0..255` range, otherwise stderr-logs and forces `EXIT_CODE=99`; `.done` files are per-session local artifacts under the session tmpdir and are not an authentication boundary. `.meta` files remain per-session local artifacts under the session tmpdir and are not an authentication boundary; the trust model treats them as data that may be tampered with by anything writing to that tmpdir.

**Cursor/Codex outer-launcher retry metadata and dirty-tree guard**: Cursor and Codex review retries may carry `OUTER_LAUNCHER`, `OUTER_LAUNCHER_PROMPT_FILE`, and `OUTER_LAUNCHER_WORKDIR` in the same `.meta` sidecar so retries replay through `scripts/launch-review.sh --tool cursor` or `scripts/launch-review.sh --tool codex` and keep launcher-owned post-processing. The collector treats these fields as tamperable data: all three must be present together, `OUTER_LAUNCHER` is rejected if it contains `..` and must canonicalize to the tool-matched allowlisted launcher, `OUTER_LAUNCHER_PROMPT_FILE` is pinned to `${ORIG_OUTPUT}.prompt` and must be a readable regular non-symlink file, and `OUTER_LAUNCHER_WORKDIR` is rejected on `..` and must be an existing directory. Invalid outer metadata fails closed instead of falling back to `CMD_JSON`, because replaying the inner command would skip launcher-owned post-processing and the mid-run dirty-tree guard. Each launcher captures a pre-launch untracked baseline and writes `${OUTPUT}.dirty-tree` before `${OUTPUT}.done`; `STATUS=dirty` or `STATUS=unknown` triggers automatic log-and-discard of the reviewer-introduced changes — no operator prompt is issued and no stash is created (see `skills/review/SKILL.md` Step 3a and `skills/implement/SKILL.md` Step 5.3.b). This guard detects reviewer writes after the fact; it does not prevent the reviewer process from writing during its run. `launch-cursor-implement.sh` writes analogous outer-launcher metadata for forward compatibility, but the collector does not allowlist it until an implement-side replay caller exists.

### External reviewer write surface in /research

`/research` delegates review tasks to Cursor and Codex when those tools are available; it launches external reviewers directly against the working tree.

Non-modification is requested in the reviewer prompt only — this is a **behavioral constraint** (prompt-enforced), not a sandbox. The hook described below governs only `/research`'s own Claude tool calls; it does not extend to subprocess-spawned external reviewers.

- **`/research` orchestrator: mechanical limits + prompt-enforced caveats**: the `/research` skill's `Edit | Write | NotebookEdit` tool surface is mechanically guarded by the skill-scoped PreToolUse hook `${CLAUDE_PLUGIN_ROOT}/scripts/deny-edit-write.sh`, which matches `Edit|Write|NotebookEdit` and permits the call only when the target path resolves under canonical `/tmp`, denying every other outcome. The `allowed-tools` frontmatter lists `Edit`, `Write`, `NotebookEdit`, and `Skill` — it declares the orchestrator's surface but does NOT confine writes by itself; the hook is the sole mechanical enforcer of the `/tmp`-only policy. **The hook's matcher does NOT include `Bash`** — Claude's own Bash calls (heredoc writes, `>>` redirects, subprocesses, `git`) are prompt-only constrained. The matcher likewise does not cover `Skill`; `Skill` is deliberately unscoped so `/research` can invoke `/issue` — this also admits other skill invocations, so operators relying on the read-only contract for the whole call graph should treat `Skill`'s breadth as a known residual risk and, where possible, constrain plugin/skill visibility at the Claude Code level.

- **Residual risk recap**: the mechanical hook depends on the running Claude Code version honoring `permissionDecision: "deny"` — a non-honoring host has no fallback, and the agent can write anywhere the `Edit`/`Write`/`NotebookEdit` tools reach. **Scope of the mechanical guarantee**: the `/research` hook governs only `/research`'s own tool calls — child skills invoked via `Skill` run under their own `allowed-tools` and hooks, not under this one. `/issue`'s writes go to `$ISSUE_TMPDIR` under `/tmp` by its own convention (prompt-enforced, not mechanically inherited from the parent). `/tmp` itself is shared scratch, not session-scoped; one skill's tmpdir is readable by other skills invoked in the same session — `/tmp` placement is **not a confidentiality boundary**.

- **Current `/research` flag surface**: `/research` now exposes only `--no-issue`; previously documented `--scale`, `--plan`, `--interactive`, `--adjudicate`, and `--keep-sidecar` modes are removed. The current topology is planner pre-pass plus the [research lanes](docs/topology.md#research.lanes), followed by the [validation panel](docs/topology.md#research.validation_panel) and unconditional citation validation. Security-sensitive operators should use `--no-issue` when they do not want the report published to GitHub.

- **`/research` synthesis + revision subagents**: `/research` Step 1.5 (synthesis) and `/research` Step 2 Finalize Validation (revision) each launch a separate Claude Agent subagent. Both run as separate subprocesses with their own `allowed-tools`; the `/research` skill-scoped `deny-edit-write.sh` PreToolUse hook does NOT propagate. Output capture paths (`$RESEARCH_TMPDIR/synthesis-raw.txt` and `$RESEARCH_TMPDIR/revision-raw.txt`) remain under canonical `/tmp`. Prompt-injection hardening continues to use file-path tags and `<accepted_findings>` wrappers as model-level conventions, not parser boundaries.

**Consumers running in strict-permissions environments** that depend on `/research`'s read-only-repo contract should validate hook behavior on their target Claude Code version and, where available, pin `Skill(...)` / `Edit` / `Write` / `NotebookEdit` permissions narrowly. **`Bash(...)` is the residual mechanical bypass on `/research`** — the hook does not match `Bash`, so a `Bash`-mediated repo write cannot be prevented by the skill-scoped hook alone. Operators relying on the read-only contract should also pin `Bash(...)` permissions narrowly at the Claude Code level (per `docs/configuration-and-permissions.md`); if a project cannot meaningfully constrain `Bash`, the read-only posture for `/research` is best-effort behavioral, not mechanical. See `skills/research/SKILL.md` ("Read-only-repo contract") for the skill-side framing and [`docs/review-agents.md`](docs/review-agents.md#external-reviewer-trust-boundary-skills-using-cursor--codex-against-pwd) for the skill-author-facing summary.

**Layered secret scanning**: larch runs pattern- and verification-based secret scanners at three layers. The layers enforce different guarantees, and conflating them leads to false-confidence gaps — especially around `make lint-only` and `/relevant-checks`, which are pre-commit-driven and therefore depend on the pre-commit hook's actual scan scope.

- **Layer 1 — commit-time working-tree scan (opt-in via `pre-commit install`)**: `.pre-commit-config.yaml` registers `gitleaks` with an `entry` override to `gitleaks detect --source . --no-git --redact --no-banner`. `--no-git` is load-bearing: without it, `gitleaks detect` scans only the git log and silently passes secrets that are staged but not yet committed. With `--no-git`, the hook scans the working-tree filesystem — which includes both tracked and staged content at commit time — and blocks the commit on any finding. Hook `pass_filenames: false` means `pre-commit run --files <paths>` still triggers a full-tree scan, so scoped paths like `/relevant-checks` cannot silently miss a secret that lives outside the changed file set. This layer is bypassable via `git commit --no-verify`; Layer 2 is the enforced backstop. Git-history scanning is explicitly NOT Layer 1's job — that is Layer 2.
- **Layer 2 — PR gate, git-history scan (CI)**: `.github/workflows/ci.yaml` defines a dedicated `gitleaks` job that checks out with `fetch-depth: 0`, installs the same pinned `v8.18.4` engine used by pre-commit (downloaded directly from the gitleaks release), and runs `gitleaks detect --source .` (without `--no-git`) so it walks the full git log. This is complementary to, not redundant with, the `lint` job (which runs the pre-commit hook in working-tree mode): together they cover the whole codebase in both dimensions — current working-tree state AND complete history — with a single pinned engine version.
- **Layer 3 — PR gate, live verification (CI)**: the `trufflehog` job pins `trufflesecurity/trufflehog` to its commit SHA for `v3.82.13` (tags are mutable — a force-pushed upstream tag could silently swap a security scanner's binary; SHAs are immutable) with `version: 3.82.13` pinning the Docker image and `--only-verified`, meaning findings fire only for credentials that actually authenticate against a live provider API. This is non-redundant with gitleaks: gitleaks catches regex-matched patterns including synthetic tokens; trufflehog catches ONLY exploitable live secrets. A finding in any layer blocks the PR.

`.gitleaks.toml` maintains a narrow path-based allowlist: the config's self-allowlist (`^\.gitleaks\.toml$`), redaction-scanner source (`scripts/redact-secrets.sh`), redaction-scanner test fixtures (`scripts/test-redact-secrets.sh`), the tracking-issue-write lifecycle shell helper plus its contract doc and regression harness (`scripts/tracking-issue-write.sh`, `scripts/tracking-issue-write.md`, `scripts/test-tracking-issue-write.md`), and the committed run-log tree (`^larch-logs/`). The first four paths legitimately carry token-shaped strings throughout — regex literals, token-family tables, and synthetic test inputs — so per-line allowlisting would churn without adding signal. The `larch-logs/` allowlist suppresses `generic-api-key` false positives on UUID-shaped `LARCH_TOKEN_SESSION_ID` values that appear in committed session transcripts; **this means gitleaks Layers 1–2 do NOT scan files under `larch-logs/` for any pattern** — contributors must not paste live credentials, API keys, or other secrets into run-log files and must rely on the redaction pipeline (`scripts/redact-secrets.sh`, applied by `larch-log.sh` before each write) as the primary defence for that subtree. **High-churn documentation is NOT allowlisted** (#375): `README.md`, `CHANGELOG.md`, `SECURITY.md` itself, `skills/issue/SKILL.md`, and `skills/issue/scripts/create-one.sh` are scanned by gitleaks in both Layer 1 (pre-commit, working tree) and Layer 2 (CI, full history). The layer responsibilities remain distinct: gitleaks Layers 1–2 catch regex-matched patterns including synthetic token-shaped literals in docs; trufflehog Layer 3 (`--only-verified`) catches ONLY live, authenticable credentials and is non-redundant with gitleaks for that reason, NOT a replacement for it — an accidental paste of a revoked token or a covered-family token in an unusual format is caught by gitleaks Layers 1–2, not by the verified-only scan. Tokens whose format falls outside gitleaks' covered rule families (see the "Outbound shell-layer redaction" subsection below for the covered families) may slip both Layer 1–2 (no matching regex rule) and Layer 3 (nothing to authenticate against a live API) — contributors must not rely on scanner layers as a substitute for editorial discipline in docs. Contributors adding new token-shaped examples to docs should use non-detector-matching forms: short prefixes without the high-entropy suffix (e.g., `ghp_` as a prefix mention rather than a full 40-character token) or an explicit placeholder like `<REDACTED-TOKEN>`.

**Reviewer archetype security lane**: The Code Reviewer archetype (`agents/code-reviewer.md`, generated from `skills/shared/reviewer-templates.md`) includes a first-class §5 Security focus area covering injection, authN/authZ, secret scanning, crypto, deserialization, SSRF, path traversal, and dependency CVEs. Review findings may be tagged `security` as their primary focus area. Reviewer `{CONTEXT_BLOCK}` material (diffs, plans, commits) is wrapped in namespaced `<reviewer_*>` XML tags with a prepended instruction sentence that the tags are literal input delimiters. This is a model-level convention that reduces prompt-injection attack surface; it is NOT a parser-enforced security boundary. A crafted payload inside the content (e.g., a diff line containing a literal matching closing tag) can theoretically defeat the wrapper, and the primary defense is the instruction sentence combined with the namespaced prefix. See `docs/review-agents.md` for the full residual-risk discussion and possible stronger follow-up mitigations.

**Untrusted GitHub Issue Content (`/issue` Phase 2)**: The `/issue` skill performs LLM-based semantic duplicate detection in 2 phases. Phase 1 reads only issue titles from `gh issue list`; Phase 2 fetches full bodies and comments for shortlisted candidates via `${CLAUDE_PLUGIN_ROOT}/skills/issue/scripts/fetch-issue-details.sh`. All fetched content is untrusted — issue authors can write arbitrary text including text that looks like instructions. Phase 2 wraps each fetched issue in a per-issue `<external_issue_<N>>…</external_issue_<N>>` block inside an outer `<external_issues_corpus>…</external_issues_corpus>` envelope. New items being created in the same batch are separately wrapped in `<new_item_<i>>…</new_item_<i>>` blocks. Both wrappers are prefaced with a literal instruction that the tags delimit data, not instructions — the same model-level convention used by the reviewer archetype. These tags are a prompt-level convention only; they reduce but do not eliminate prompt-injection risk. A crafted payload (e.g., content containing a literal matching closing tag) can theoretically defeat the wrapper, and the primary defense is the instruction sentence combined with the namespaced tag prefix. Phase 2 also applies candidate-ID whitelist validation — the LLM may only mark an existing issue as a duplicate if that issue's number appeared in the Phase 1 snapshot; unknown numbers are rejected and fall back to CREATE. This is a correctness guard, not a security sandbox.

**`/issue --go` approval semantics (single and batch modes)**: The `--go` flag posts `GO` as the final comment on each newly-created issue, which is the approval sentinel that makes an issue eligible for `/fix-issue` automation (see `skills/fix-issue/SKILL.md`). `--go` works in both single and batch modes — in batch mode (`--input-file F --go`) it can approve multiple newly-created issues for `/fix-issue` in a single invocation (one `GO` comment per successful CREATE; duplicates, failed creates, and dry-run items never receive a `GO` comment). `gh issue comment` stderr from a failed GO post is piped through `scripts/redact-secrets.sh` before being surfaced in the per-item warning, matching the posture of `create-one.sh`'s outbound redaction. **Operator guidance**: orchestrators that rely on human GO-gating to throttle `/fix-issue` queue growth should restrict which `/issue` callers may pass `--go` (or avoid `--go` in batch mode) — a single batch invocation can approve many issues at once. **Fail-open-dedup amplifier**: `/issue`'s 2-phase semantic dedup fails open (any Phase 1 / Phase 2 helper failure — network, rate limit, gh auth — falls through to create-all); combined with `--go` in batch mode this means a transient dedup-helper failure can produce a burst of newly-created AND auto-approved issues for `/fix-issue`. GO-post failures themselves are non-fatal and audited via per-item `ISSUE_<i>_GO_POSTED=true|false` stdout lines; a `false` value means the issue exists but is NOT yet eligible for `/fix-issue` until a human adds `GO` manually.

**Dev-only PostToolUse audit log (`scripts/audit-edit-write.sh`)**: `scripts/audit-edit-write.sh` is a contributor-local debugging aid that, when opted in via `.claude/settings.local.json`, records a JSONL trail of every `Edit` / `Write` tool invocation to `.claude/hook-audit.log`. The log is **intentionally unredacted** — it captures the raw PostToolUse payload including `tool_input` fields like `file_path`, `content`, and `old_string` / `new_string`, which may contain secrets, credentials, PII, or proprietary code. The file is **gitignored by default** (`.gitignore` lists `.claude/hook-audit.log`) and the script is **not registered in shipped config** (`hooks/hooks.json`) or in committed dev config (`.claude/settings.json`) — it runs only when a developer explicitly adds a `PostToolUse` entry to their local, gitignored `.claude/settings.local.json`. There is no automatic rotation or retention policy; the log grows until the developer clears it (`truncate -s 0 .claude/hook-audit.log`). Operational discipline: never commit the log, never paste its contents into issues/PRs/screenshots, clear it after debugging, and treat it as a secret-bearing artifact if the project handles secrets. See `docs/dev-hook-audit.md` for enable/disable/privacy details. The script always exits 0 so it cannot block tool use, and the regression test (`scripts/test-audit-edit-write.sh`, wired into `make lint`) uses `CLAUDE_PROJECT_DIR` override plus a tmpdir to verify behavior without touching the real log.

The write helper keeps the fail-closed redaction posture: body and title content is composed in memory, passed through `redact-tmpdir-paths.sh` and `redact-secrets.sh`, and only then sent to `gh`; captured `gh` stderr is redacted before surfacing in `ERROR=`.

**External CLI startup locks**: Review, implement, and CI-fix spawn sites for Cursor, Codex, and Gemini share a Darwin-only `/tmp/larch-<tool>-serial-$USER.lock` directory lock plus bounded auth-startup retry wrapper. The lock is a reliability mechanism, not an authorization boundary: `/tmp` is shared scratch, the path includes the local username, stale locks are removed by age, and acquisition fails open after a bounded wait. Operators on multi-user hosts should not treat the lock directory as confidential or tamper-resistant; it only reduces concurrent CLI startup/auth races.

**Submodule edit guard anchor (`scripts/block-submodule-edit.sh`)**: The `PreToolUse` hook anchors its superproject-root detection to `CLAUDE_PROJECT_DIR` (with `$PWD` fallback for non-Claude-Code invocations), closing the cd-into-submodule bypass (issue #150) where a session that had `cd`'d into a submodule collapsed the guard's notion of "superproject root" to the submodule root, allowing same-submodule edits to slip past.

**`CURSOR_API_KEY` argv visibility tradeoff (issue #1358)**: When `CURSOR_API_KEY` is set in the operator's environment, larch's Cursor call sites (`scripts/launch-review.sh --tool cursor`, `scripts/launch-cursor-implement.sh`, `scripts/check-reviewers.sh`'s Cursor probe, `scripts/run-negotiation-round.sh`, plus the runtime markdown templates that emit `cursor agent` Bash blocks: `skills/shared/voting-protocol.md`, `skills/shared/dialectic-protocol.md`, `skills/research/references/validation-phase.md`) pass `--api-key "$CURSOR_API_KEY"` explicitly to the Cursor child process. On Darwin, the shared Cursor launchers (`launch-review.sh --tool cursor`, `launch-cursor-implement.sh`, and `launch-cursor-ci.sh`) also best-effort pre-read the exact `cursor-user` / `cursor-access-token` keychain service when `CURSOR_API_KEY` is empty, export the token into the launcher process, and pass it as `--api-key` if the read succeeds. This bypasses Cursor's own keychain access in the child process and eliminates the intermittent concurrent-launch failure mode (`Password not found for account 'cursor-user'` / `Security process exited with code: 45`) for those launcher lanes when the keychain service is readable. The explicit-argv path has two visibility surfaces operators should be aware of:

1. **Process argv visibility** — while the `cursor` child process is running, the API key is visible in `ps`, `/proc/<pid>/cmdline` (Linux), and any other process-listing surface available to other users on the same host. This is a standard CLI-tool tradeoff, not solvable in a wrapper. Multi-user shared hosts where untrusted users have shell access on the same machine should treat the key as compromised in that environment regardless of whether `CURSOR_API_KEY` is set or not (a `cursor login`-keychain user has their cleartext key on disk in the keychain blob, which is also the keychain's threat model).

2. **At-rest visibility in `.meta` `CMD_JSON` sidecars** — `scripts/run-external-agent.sh` records the full child argv into `${OUTPUT}.meta` as a `CMD_JSON=` line, because `scripts/collect-agent-results.sh` reconstructs retry argv from `CMD_JSON` on empty-output retries. Persisting `<redacted>` in `CMD_JSON` would silently break those retries by passing the literal `<redacted>` token to a relaunched Cursor child, so the larch design explicitly does NOT redact `CMD_JSON`. The `${OUTPUT}.meta` sidecars live under `${XDG_CACHE_HOME:-$HOME/.cache}/larch/sessions/...` (session-tmpdir scoping; cleaned up by Step 18 of `/implement` and the parallel cleanup paths in `/design` / `/review` / `/research`). The session tmpdir is treated as session-scoped private state under existing `SECURITY.md` conventions; this PR does not change that posture.

Operators who require zero at-rest secret persistence in larch session tmpdirs should not use the shared Cursor launcher lanes on Darwin with a readable `cursor-access-token` keychain service: leaving `CURSOR_API_KEY` unset no longer guarantees zero persistence there because the launcher pre-read intentionally converts a readable keychain token into explicit `--api-key` argv. Prefer Claude/Codex/Gemini for those runs, or remove the readable Cursor keychain entry before launching and accept that Cursor auth may fail. The Darwin-gated pre-launch sanity check (`scripts/lib-cursor-auth.sh`'s `cursor_auth_preflight`) refuses to launch with both auth sources demonstrably absent, so a misconfigured `CURSOR_API_KEY=`-empty + missing-service state surfaces an actionable error rather than the cryptic `Security process exited with code: 45`. The check and pre-read are strictly read-only — they never invoke `security delete-*`, never spawn a Cursor subprocess, and never perform network I/O.

## Fixed-string matching for interpolated values (issue #775 unified grep -F doctrine)

Any shell-script call site that matches a literal value (label name, comment marker, edge identifier) MUST use a fixed-string matcher — `grep -F` family or `awk` with `index()`/field-equality — when the searched-for value is interpolated from a variable. Using BRE/ERE matchers (`grep -E`, `grep` default) on interpolated values is a regex-injection class: a value containing regex metacharacters (`.`, `[]`, `(`, `^`, `$`, `|`, `*`, `+`, `?`, `{}`) can over-match, fail closed unexpectedly, or shift match semantics in ways the call site does not anticipate. The `-x` (whole-line) and `-q` (quiet) flags are independent and may be combined with `-F`.

**Sites currently following the doctrine** (closes #775; closes #743 as duplicate):

- **`skills/issue/scripts/create-one.sh:182`** — label-existence probe: `gh label list ... --jq '.[].name' | grep -Fqx -- "$L"`. Active shipped path: `/umbrella` forwards operator `--label` values verbatim through `/issue` to here. A label like `bug.feature` or `release[2026]` cannot false-match a regex-interpretation sibling.
- **`skills/umbrella/scripts/helpers.sh` wire-dag back-link probe** — anchored fixed-string via awk: `awk -v m="$backlink_marker" 'index($0, m) == 1 { found=1; exit } END { exit !found }'`.
